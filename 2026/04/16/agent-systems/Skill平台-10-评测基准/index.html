10 · Skill 评测基准体系：触发、执行、结果三层与持续优化闭环

企业级 Skill Registry 平台工程手册 · 第 10 篇（扩展卷）
前置阅读：02 篇 §8（description 优化闭环）、05 篇 §9（统计与评分）、08 篇 E 系列（作者侧义务）、09 篇 §8（回归对制作）
本篇回答：评什么（三层指标模型）、怎么评得统计上可信（重复/切分/功效）、用什么评（断言 / 结构比对 / LLM-as-Judge 各就其位）、以及评测体系自身如何不腐化。

1. 概述：三层评测模型

技能的失败可以发生在三个互相独立的层面，评测体系必须分层归因——“用户不满意”混在一起测，永远不知道该修 description 还是修脚本：

分层的直接工程收益：每层有独立的评测手段与失败归因，L-D 用触发协议（§3）、L-E 用断言与结构比对（§4）、L-O 用 Judge 与线上信号（§5）——三种手段成本差一个量级，分层让贵的手段只用在必须的地方。

2. 指标定义（口径钉死版）

指标 定义 口径要点
trigger rate trigger 集中目标技能被激活的比例 每条 query ≥3 次独立会话取率；”激活”= skill_activated 事件，不是”提到了技能名”
negative rejection negative 集中目标技能未被激活的比例 同上重复协议
activation precision（线上） 激活后未被 correction 的比例 correction 窗口 = 激活后 3 轮（05 §9）
执行成功率 exit 0 且未进 fallback 且回归断言通过 三条件同时满足；fallback 成功恢复计入”成功但降级”单列
步骤遵循度 关键步骤（标 critical 的）按序执行比例 从 trace 的 tool_call 序列自动判定（§4.3）
产出质量分 Judge 按 rubric 的 1~5 分 必须报告与人类金标的一致率（§5.2），无校准的 Judge 分不进质量分
变异稳健度 query 释义扰动下 trigger rate 的保持率 §3.4
串味回归 技能完成后续无关任务的格式/行为污染检出率 平台级横切，§6.3

3. L-D：触发评测协议

3.1 评测集 Schema

三个字段是协议的牙齿：snapshot_pin + model_pin（E-3，无锁的评测结果不可比不可复现）；complexity_check——入库时由一个廉价分类器判定 query 是否过复杂度门槛（01 §3.2），单步 query 直接拒收（09 篇 AP-4 的机器闸）；source 保证语料可追溯，”现编”的 case 在源头可识别。

3.2 运行协议

3.3 混淆归因与边界攻击

触发失败的产出不是一个分数，是混淆矩阵的域内展开：漏触发的 query 实际激活了谁（或谁都没激活）、误触发抢了哪个相邻技能的场景。这份矩阵直接生成两类工单：本技能 description 修改建议、相邻边界配对修改建议（D-4 的评测驱动版）。

boundary-suite（E-4）是矩阵的主动版：族内任意两技能，用 A 的 trigger_examples 打 B（期望全不触发）。发布流水线必跑；矩阵中任何非对角命中 = 域内重叠病灶定位完成。

3.4 变异测试

trigger_examples 会被 description 优化过程”过拟合”。防线：对每条 case 生成 3~5 个释义变体（同义改写 / 口语化 / 加干扰上下文 / 换语种混排），变体集只用于验收不用于优化。变异稳健度 = 变体触发率 / 原句触发率，<0.8 说明 description 拟合的是措辞不是意图——这是”触发率 95% 但用户还是说触发不了”的标准病因。

4. L-E：执行评测

4.1 三种手段的分工

手段 判什么 成本 适用
断言（assertion） 可机器验证的硬性质：文件产出存在、JSON schema 合规、分类字段全等、数值在容差内 最低 一切能写成谓词的期望（优先用满）
结构比对 产物的章节/字段/表格结构与期望产物一致（措辞不比） 低 报告类交付物（E-2）
LLM-as-Judge 归因合理性、建议可行动性、不确定性表述纪律 高 断言与结构够不着的质量维度

纪律：能断言的绝不上 Judge。Judge 是用来判”归因是否讲理”的，不是用来判”parsed.json 存不存在”的——后者用 Judge 既贵又引入无谓方差。

4.2 回归对执行（E-2/T-3 的平台侧）

“不强制激活”有一个例外：L-D 已单独覆盖的技能，在 L-E 的高频回归里可以直接注入激活（省 L-D 的重复成本）——但每个发布门槛跑一次全链路（触发→执行）的端到端。

4.3 步骤遵循度的自动判定

关键步骤在 SKILL.md 模板中可标注（脚手架支持 #! critical 批注编译为 manifest 的 critical_steps），判定器对 trace 的 tool_call 序列做子序列匹配：parse_logs.py → classify_failure.py → (references 读取) → generate_summary.py 的序缺失或倒置即违例。这是”模型激活了但没照做”（07 §6 第三类失败）唯一的规模化检测手段。

5. L-O：结果评测与 LLM-as-Judge

5.1 Rubric 设计

Judge 只能和 rubric 一样好。合格 rubric 的形状（以诊断报告为例）：

锚点必须是可观察行为（”引用证据链条目”）而非形容词（”分析深入”）——形容词锚点的 Judge 分数与人类一致率通常掉到不可用区间。

5.2 Judge 校准（无校准不上岗）

你平台已有 LLM-as-Judge 基建（轻量模型做批量评审）的，接入前同样要过这套校准，基建的存在不豁免校准义务：

  1. 金标对齐：金标集（每 rubric ≥30 例，人类双标 + 仲裁）上跑 Judge，报告与人类的一致率（容差 ±1 分）与系统性偏移（Judge 均值 − 人类均值）。一致率 <80% 的 rubric 回炉改锚点，不是换更大的 Judge 模型——锚点问题换模型治不了。
  2. 偏差控制：位置偏差（比较式评测中 A/B 位置轮换）、长度偏差（金标中刻意包含”长而空”与”短而准”的对照例，验证 Judge 不奖励长度）、自我偏好（Judge 模型与被评模型同源时倾向偏高，校准报告必须披露同源性）。
  3. 漂移监控：金标集按月重跑，一致率跌 >5 个点触发 rubric 复审——Judge 模型升级、金标老化都会表现为漂移，先归因再修。

5.3 线上信号回接

L-O 的最终裁判在线上：correction / adoption（05 §9 四信号）按技能×版本聚合，与离线 Judge 分做相关性体检（季度）：离线分高而线上 correction 高的技能，说明 rubric 漏掉了用户真正在意的维度——这是 rubric 迭代的唯一可靠外部参照。

6. 平台级横切基准

6.1 成本与时延基准

每技能每版本记录：单次执行 token 成本分解（L2 注入 + L3 读取 + 推理轮次 + 脚本 stdout）、端到端 P50/P95。基准的用途不是排名而是回归检测：新版本成本涨幅 >30% 且无对应能力说明的，流水线警告——“悄悄变贵”是 references 膨胀和 stdout 泄洪（07-F4）的早期信号。

6.2 全库回归的触发时机

事件 回归范围
模型换代（08 §14.4） 全库 L-D + 全库回归对；pushy 登记表重审
平台系统提示变更 全库 L-D 抽样（每族 top-3）——组装顺序上游的变更会整体移动触发分布
域卡片/routing_card 变更 该域全量 L-D
单技能 description 变更 本技能全量 + conflicts_with 邻居的 boundary-suite（D-7 联动）
沙箱/工具协议变更 全库回归对（L-E）

6.3 串味回归

固定一组”无关后续任务”探针：先完整执行目标技能，同会话紧接一个与之无关的任务（写邮件/查天气类），断言后续产出不携带技能残留（格式强加、术语污染、无关免责声明）。每技能 stable 化前必跑一次，无条件命令式指令（Doc-1）的漏网之鱼在这里现形。

7. 统计功效：让数字可信

触发率是比例估计，小样本下的”95% vs 88%”很可能是噪声。三条底线：

  1. 区间报告：一切触发率带 Wilson 95% 区间。速查（N = case 数 × 重复数）：
N 观测 90% 时的区间
24（8 case×3） [71%, 97%] —— 基本不可判
60（20×3） [80%, 95%]
150（50×3） [84%, 94%]
300（100×3） [86%, 93%]

直接推论：8 条 trigger_examples（D-3 下限）只够冒烟，SLO 判定（90 线）至少 50 case——核心技能的评测集扩充是运营常态任务，02 附 B.3 的挖掘管道是补给线。
2. 对比要检验：版本 A/B 触发率对比用双比例检验（或直接看区间是否分离），差异小于区间宽度的”提升”不许写进发布说明。
3. 方差先于均值：新评测集先跑方差体检（同版本重复 5 轮的率波动），轮间波动 >8 个点说明 case 质量问题（歧义 query、复杂度不足），先修集再谈优化——在坏集上优化 description 是对着噪声回归。

8. 评测基础设施

成本控制三法：分层抽样（全库回归时非核心技能抽 30% case，核心全量）；结果缓存（case+snapshot+model 三元组命中即免跑——产物不可变让缓存永久有效）；Judge 批处理错峰。经验预算线：评测 token 支出占平台推理总支出 5%~10% 属健康区间，超过说明回归范围设计过宽，低于 2% 说明在裸奔。

9. 评测体系自身的腐化与防治

腐化模式 症状 防治
评测集过拟合 离线全绿、线上 correction 不降 变异验收集（§3.4）+ 语料季度换血（老 case 退役 20%）
金标老化 Judge 一致率缓降 金标集纳入线上争议样本（correction 的实例）滚动更新
指标游戏化 激活量被冲、negative 集越写越弱 negative 必含最易混淆邻居（09 §5）+ 08 反模式”考核激活量”禁令
回归疲劳 假失败多→团队开始忽略红灯 比对层级标注（09 §8）治措辞假失败；假失败率 >10% 时冻结新增断言先修旧
复现性流失 “上周还能复现” snapshot/model 双锁强制 + 结果带锁指纹，无指纹结果视为无效

10. 持续优化闭环全景

flowchart LR
    A[作者提交<br/>evals 随技能入库] --> B[发布门槛<br/>L-D 全量 + L-E 回归<br/>+ boundary-suite]
    B --> C[灰度<br/>租户环 + 线上 A/B<br/>correction/份额护栏]
    C --> D[stable 运营<br/>周指标归 owner<br/>SLO 看板]
    D --> E[线上信号<br/>correction/adoption<br/>未触发复杂 query 采样]
    E --> F[语料挖掘<br/>02 附B.3 管道<br/>缺口→新 case/新技能]
    F --> G[离线优化<br/>description 迭代 60/40<br/>变异验收]
    G --> B
    E -.相关性体检.-> H[rubric/金标迭代]
    H -.-> B

闭环的健康判据一句话：每个环节的产出都是下一环节的输入，且没有一个环节依赖”某人记得去做”——事件驱动（05 §10 主题）串起 B→C→D，采样管道串起 E→F，剩下 G 的迭代节奏由 SLO 破线工单驱动。人只出现在两处：金标标注与打回修复。

11. 反模式

  • AP-1 单次定胜负：不重复、无区间的触发对比（§7 三底线全违）。
  • AP-2 Judge 万能：断言能判的上 Judge（§4.1 纪律）。
  • AP-3 无校准 Judge：一致率没测过就进质量分（§5.2 门槛）。
  • AP-4 优化验收同集：description 对着将要考它的题目优化（train/test 纪律 + 变异集只验收）。
  • AP-5 强制激活跑全部执行评测：触发→执行的衔接环永不被测（§4.2 例外的滥用）。
  • AP-6 评测无锁：snapshot/model 不锁，结果不可比（E-3）。
  • AP-7 绿灯崇拜：假失败靠放宽断言消除而非修比对层级——断言逐步松弛到测不出任何东西。

12. 检查清单

  • 三层指标口径表落地，failure 归因按层出工单
  • 评测集 schema：snapshot/model 双锁 + complexity_check + source 追溯
  • N≥3 重复 + 位置轮换 + Wilson 区间为报告默认格式
  • boundary-suite 进发布流水线；混淆矩阵自动生成配对工单
  • 变异验收集与优化集物理隔离
  • 断言优先纪律 + 回归对比对层级机制上线
  • critical_steps 编译 + trace 子序列判定器
  • rubric 锚点行为化 + 金标 ≥30 双标 + 一致率 ≥80% 上岗线
  • Judge 漂移月检 + 离线/线上相关性季检
  • 全库回归触发时机表（§6.2）接入事件总线
  • 串味探针进 stable 门槛
  • 评测 token 预算 5%~10% 区间监控 + 结果缓存
  • 腐化五模式各有监测信号（§9）
