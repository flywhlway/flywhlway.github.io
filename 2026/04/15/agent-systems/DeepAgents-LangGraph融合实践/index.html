DeepAgents × LangGraph 深度融合实践：四种模式与生产化

基于 deepagents 0.5 与 LangGraph 1.1，拆解 Supervisor 调度、Agent 内嵌子图、双向嵌套、异步子代理四种融合模式…

Flywhl 62 分钟 更新于 2026.09 #架构设计#LangGraph#Agent

先读结论

  1. create_deep_agent 返回的就是编译后的 LangGraph 图：能挂 checkpointer、能当子图、能被 Supervisor 调度，融合的前提是分清谁管流程、谁管推理。
  2. 确定性流程交给 StateGraph，开放式推理交给 DeepAgent；子图要当 CompiledSubAgent 用，必须以 messages 收发结果。
  3. deepagents 0.5 推荐直接传后端实例，StoreBackend 显式声明 namespace；后端工厂写法已弃用，弃用警告写明将在 0.7 移除。
  4. 分钟级以上的任务用 AsyncSubAgent 放到后台，任务 ID 由内置 async_tasks 状态通道保存，不会因上下文压缩而丢失。

本文以 2026-04-15 的版本为基线：deepagents==0.5.3、langgraph==1.1.6、langchain==1.2.15、langgraph-supervisor==0.0.31，Python ≥ 3.11。文中代码均在该组合下做过导入与构图验证，关键链路（子图中断冒泡、审批恢复、跨线程记忆、Supervisor 嵌套中断）用假模型跑通过。

1. 架构全景：理解两者的本质关系

1.1 核心定位

在 LangChain 官方生态中，DeepAgents 与 LangGraph 的关系不是竞争，而是分层：

关键事实：create_deep_agent() 内部调用 langchain.agents.create_agent，再叠加一组中间件（待办、文件系统、子代理、摘要、工具调用修补），返回的是一个 CompiledStateGraph。所以 DeepAgent 天然具备 LangGraph 的全部能力：checkpointer、store、interrupt、stream、在 LangSmith Studio 中可视化调试，也可以作为节点嵌进任何一张图。

1.2 能力互补矩阵

任务规划 write_todos 待办清单，由模型自主拆解与更新 无内置规划，步骤由图结构预先确定 开放式任务交 DeepAgent，固定步骤交图

3. DeepAgents 核心机制详解

3.1 create_deep_agent 核心参数

0.5 的签名相比 0.2 有两处关键变化：同步与异步子代理合并到同一个 subagents 参数；backend 推荐直接传实例，后端工厂（lambda rt: ...）和给 StateBackend(runtime) 传运行时都会触发弃用警告。

StoreBackend 不传 store 时，会在运行时通过 get_store() 取图上挂载的 store，所以同一个后端实例既能用在独立 DeepAgent 上，也能用在被 Supervisor 调度的 Worker 上（取到的是父图的 store）。

3.2 内置工具体系

注意并不存在 read_todos 工具：待办清单保存在 todos 状态键里，模型每次重写整张清单。

3.3 SubAgent 的三种声明方式

task 工具调用子代理时的状态约定，直接决定了模式二、三能否跑通：

  1. 输入：父状态去掉 messages、todos、structured_response 等键后传给子代理，messages 被替换为一条内容为任务描述的 HumanMessage。子代理看不到父级对话历史，这就是上下文隔离。
  2. 输出：取子代理最终状态 messages 的最后一条消息文本，包装成 ToolMessage 回给父代理；配置了 response_format 时改用结构化结果。
  3. 状态回流：子代理返回状态中除上述排除键之外的字段，会以 Command(update=...) 合并回父状态，父状态里没有的键被丢弃，同名键会被覆盖。
  4. 契约：CompiledSubAgent 的图必须有 messages 键，否则抛出 ValueError。

另外，0.5 起声明式子代理默认继承父代理的 interrupt_on，想放开时在子代理字典里显式覆盖。

这是最常用的企业级主架构：LangGraph 负责路由、状态与持久化，DeepAgent 负责需要多步推理的深度任务。

5.1 架构示意

5.2 完整代码实现

coding_agent 在 Supervisor 内部触发 deploy_service 审批时，中断会沿嵌套层级冒泡：app.get_state(config).interrupts 能直接拿到 HITL 请求，用 Command(resume=...) 对最外层图恢复即可，不需要关心中断发生在哪一层。

5.3 工具化 Supervisor：官方更推荐的写法

把每个 DeepAgent 包成一个工具，由 create_agent 充当 Supervisor。和 create_supervisor 相比，好处是可以精确控制传给 Worker 的输入（只传任务描述，而不是整段对话），返回值也可以裁剪。

在工具内部调用的 DeepAgent 同样作为子图运行，deploy_service 的审批中断照样能冒泡到 tool_supervisor。

6. 融合模式二：DeepAgent 内嵌 LangGraph SubGraph

当 DeepAgent 在执行中遇到必须按固定规则走的流程时，把流程做成 StateGraph，再包成 CompiledSubAgent 交给 DeepAgent 调用。

6.1 适用场景

  • 变更审批（固定审批链、风险分级）
  • CI/CD 流水线（确定性步骤序列）
  • 合规检查（规则引擎，结果必须可复现）
  • OTA 升级（严格状态机，禁止模型跳步）

6.2 完整代码实现

子图要满足第 3.3 节的契约：从 messages 读取任务描述，最后把结论写回 messages。

执行链路是：主代理调用 task → 审批子图在 human_review 里 interrupt() → 中断穿过 task 工具冒泡到主代理 → 调用方拿到 out.interrupts → Command(resume=...) 恢复时，task 工具重新执行，子图从 human_review 接着跑，report 写回的结论作为 ToolMessage 回到主代理。子图状态里的 risk_level、approval_status 等字段在父状态中不存在，回流时被丢弃；如果子图里有和父状态同名的键（例如 files），则会覆盖父状态，命名时要避开。

8. 融合模式四：异步子代理（AsyncSubAgent）

同步子代理会阻塞主代理直到返回。对于分钟级以上的任务（长篇调研、批量数据处理），0.5 提供了 AsyncSubAgent：主代理启动任务后立刻拿到任务 ID 并把控制权还给用户，之后按需查询、追加指令或取消。

8.1 配置与调度

五个工具由 AsyncSubAgentMiddleware 自动注册：start_async_task、check_async_task、update_async_task、cancel_async_task、list_async_tasks。其中 update_async_task 的语义是中断当前运行、在同一线程上带着新指令重新开始，所以任务 ID 保持不变。

远端对接的是 Agent Protocol，LangSmith Deployment 和自托管的 Agent Server 都可以作为远端；鉴权方面，SDK 会自动读取 LANGGRAPH_API_KEY、LANGSMITH_API_KEY 或 LANGCHAIN_API_KEY。

8.2 任务状态：内置的 async_tasks 通道

主代理会在对话变长时自动摘要，如果任务 ID 只存在于消息里，摘要之后就可能丢失。中间件因此把任务记录放在独立的 async_tasks 状态键中（带合并 reducer），每条记录包含 task_id（即远端 thread_id）、agent_name、run_id、status、created_at、last_checked_at、last_updated_at。这是框架内置行为，不需要自己在状态里再加字段。

graph_id 必须对应 langgraph.json 中注册的图，主代理与同部署的子代理写在同一份配置里：

9. 生产级最佳实践：状态、记忆与持久化

9.1 共享状态设计

自己编写的外层图（而不是 create_supervisor 生成的）需要一份明确的共享状态。原则是：并发写入的键必须有 reducer，只由单个节点写入的键保持覆盖语义。

9.2 生产级持久化配置

from_conn_string 返回的是异步上下文管理器，不能直接当 checkpointer 用；首次部署要调用 setup() 建表（也可以放进迁移脚本）。

部署到 LangSmith Deployment 时不需要这段：平台为每张图注入 PostgreSQL checkpointer 和 store，导出的图不要再绑定自己的 checkpointer。

9.3 跨线程记忆模式

memory=["/memories/AGENTS.md"] 会在每次运行开始时通过后端读取该文件并注入系统提示词；模型用 edit_file / write_file 更新它。因为 /memories/ 路由到按 user_id 分区的 StoreBackend，同一用户的新会话自动带上旧偏好，不同用户互不可见。

只配 /memories/ 路由而不配 memory=，模型并不会主动去读记忆目录，除非在系统提示词里明确要求。

10. Human-in-the-Loop 集成

10.1 DeepAgent 级 HITL（工具审批）

HumanInTheLoopMiddleware 把同一轮模型输出中所有需要审批的工具调用合并成一个中断，中断值是 HITLRequest：action_requests（每个调用的 name、args、description）和 review_configs（每个工具允许的决策）。恢复时按 action_requests 的顺序给出同样数量的决策。

reject 的 message 会作为该工具调用的 ToolMessage 返回给模型，模型据此调整后续动作；edit 可以同时改工具名和参数。

10.2 LangGraph 流程级 HITL

工具审批解决”某个动作能不能做”，流程级审批解决”流程能不能往下走”。后者直接在节点里 interrupt()，审批数据结构完全自定义：

恢复后该节点从头重新执行，interrupt() 这次直接返回恢复值。所以 interrupt() 之前不要放有副作用的代码（发通知、写库），否则会执行两次。

14. 常见陷阱与调试指南

14.1 上下文爆炸

内置的兜底是：单次工具结果超过 2 万 token 会被写到 /large_tool_results/<tool_call_id>，主上下文只保留引用。但落盘后模型往往还会再读回来，靠子代理隔离才是根治。

14.2 异步任务 ID 丢失

用 create_deep_agent 时不存在这个问题，任务记录在内置的 async_tasks 通道里。只有自己手写外层图、又自己实现了异步委派时才需要注意：任务 ID 必须存到带 reducer 的独立状态键，不能只出现在消息里，否则摘要或裁剪消息后就找不回来了。

14.3 HITL 缺少 checkpointer

没有 checkpointer 时，interrupt_on 不会在构建阶段报错，第一次调用也会正常返回中断；直到恢复时才抛出 RuntimeError: Cannot use Command(resume=...) without checkpointer。这类问题往往在联调审批端时才暴露，建议在工厂函数里对”配置了 interrupt_on 却没有 checkpointer”直接断言失败。

14.4 给子图单独挂 checkpointer

子图作为节点运行时，LangGraph 优先使用父图传下来的 checkpointer；只有子图显式设为 checkpointer=False 才会关闭持久化。

14.5 CompiledSubAgent 契约不满足

最常见的三种报错与原因：

  • ValueError: CompiledSubAgent must return a state containing a 'messages' key：子图状态里没有 messages。
  • 子图节点 KeyError：节点直接读 state["vin"] 之类的业务字段，但 task 只传入 messages。先加一个解析节点，从最后一条消息里取参数。
  • 父代理拿到的结果是空字符串：子图最后一条消息是用户那条 HumanMessage，因为没有节点往 messages 写结论。

0.6 新增能力与本文的关系

  • 消息通道默认改用 DeltaChannel：从 0.6.0 起，DeepAgent 的 messages 使用增量通道（每 50 次更新写一次完整快照），checkpoint 不再每一步重复序列化整段历史，源码注释给出的效果是 checkpoint 增长从 O(N²) 降到 O(N)。代价是升级到 0.6 并产生持久化数据后不支持回滚，官方说明增量 checkpoint 与旧版本不兼容，升级前要备份或规划好线程数据。0.7 通过 state_schema 参数公开了 DeepAgentState，自定义状态要继承它才能保留这一行为。注意这只覆盖 DeepAgent 自己的消息：create_supervisor 生成的外层图和本文手写的子图仍用 add_messages，长对话的写放大主要出在外层。
  • CodeInterpreterMiddleware（实验性）：基于 QuickJS 的受限运行时，通过 deepagents[quickjs] 安装，支持代码执行与程序化工具调用，可以替代第 5 节里 run_code 这类需要外部沙箱的示例工具的一部分用途。
  • stream_events / astream_events 支持 version="v3"，以及 harness profiles、ContextHubBackend 等配置化能力。

LangGraph 1.2 对长任务的意义

节点级 timeout 与 error_handler 正好补上模式三的短板：中间层图的 ai_analyze 节点内部跑着一整个 DeepAgent，1.1 时代只能在外部加超时。1.2 的行为要点（在 1.2.12 上验证）：

  • 超时只支持异步节点，给同步节点设置 timeout 会在运行时抛 ValueError；超时触发 NodeTimeoutError，它不继承内置 TimeoutError，因此默认 RetryPolicy 会把它视为可重试。
  • TimeoutPolicy 区分 run_timeout（单次尝试的硬上限）与 idle_timeout（无进展时长，默认任何回调事件都会刷新，也可改为只认 runtime.heartbeat()）。
  • error_handler 通过类型为 NodeError 的参数拿到失败节点名和异常；返回普通 dict 时该分支到此结束，要继续后续节点必须返回 Command(goto=...)。
  • StateGraph.set_node_defaults(...) 可以给全图设默认策略，但不会被子图继承。

DeltaChannel（beta） 可以用在自己的长生命周期外层图上：它在 checkpoint 中只存占位，读取时回放历史写入重建状态，默认每 1000 次更新写一次快照。reducer 必须是批处理形式 (state, writes) -> new_state，且对分批方式不敏感。LangGraph 自带的消息版 reducer _messages_delta_reducer 仍是下划线开头的实验接口，而且不处理 REMOVE_ALL_MESSAGES；DeepAgent 的摘要中间件正是用这个标记清空历史，所以 deepagents 自带了一份能处理它的 reducer。外层图如果也会做消息压缩，不要直接套用 LangGraph 的实验版本。PostgreSQL 侧，langgraph-checkpoint-postgres 3.1 为增量历史读取提供了专门的查询实现。

平台侧

LangSmith Engine 于 2026-05-13 以公开 beta 发布：从生产 trace 中聚类出问题、对照代码诊断根因、起草修复 PR，并为该问题生成在线评估器、把失败 trace 收进离线数据集。对本文这类多层嵌套系统，它能直接利用第 12 节打好的 tags / metadata 按故障类型聚类，是 12 节可观测性配置的下游用法。
