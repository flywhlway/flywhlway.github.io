08 · Langfuse 与 OTel 双层观测融合

目标：一次埋点，双端消费。同一份 gen_ai.* Trace 同时进入 Tempo（系统层：延迟/错误/依赖/SLO）与 Langfuse（AI 业务层：Prompt/会话/成本/评测），两层通过 trace_id 与会话属性互相印证。

1. 分工模型（先说清楚为什么要两层）

维度 LGTM（系统层） Langfuse（AI 业务层）
核心问题 慢在哪、错在哪、依赖谁 答得好不好、贵不贵、哪个 Prompt 版本更好
数据粒度 全服务 Span（HTTP/DB/MQ/LLM） LLM 相关 Span（会话视图渲染）
特色能力 服务拓扑、TraceQL、日志/指标联动、告警 会话回放、成本核算、Prompt 管理、评测/标注、数据集回归
使用者 SRE / 平台工程 AI 工程师 / 产品 / 算法

反模式提醒：不要试图用 Langfuse 看微服务拓扑，也不要用 Grafana 做 Prompt 评测——让每层做擅长的事。

2. Langfuse 作为 OTLP 后端的硬约束

  • 端点：{LANGFUSE_HOST}/api/public/otel（trace 专用路径 /api/public/otel/v1/traces）；自托管需 ≥ v3.22.0；
  • 仅支持 OTLP/HTTP（protobuf），不支持 gRPC——metrics/logs 端点不存在（发送会 404），Langfuse 只消费 Traces；
  • 认证：Basic Auth，base64(pk-lf-xxx:sk-lf-xxx)；
  • Langfuse 会把 gen_ai.*（含 OpenLLMetry/OpenInference 等社区属性）映射到自身数据模型，Token 属性（gen_ai.usage.*）存在且模型名可识别时自动核算成本。

5. Langfuse 侧的增值动作

数据进入后，在 Langfuse UI 完成业务层闭环：

  1. Sessions 视图：按 session.id 回放多轮诊断会话，检查上下文携带是否正确；
  2. 成本核算：Model 设置中登记 deepseek-chat 价格表（输入/输出单价），Token 属性自动折算成本，按 user/session/model 聚合；
  3. 评测（LLM-as-Judge）：配置 Judge 模型对回答打分（准确性/幻觉），分数落到对应 Trace，可导出为 gen_ai.evaluation.*；
  4. Prompt 管理：Prompt 版本化后，Trace 关联 prompt version，A/B 对比不同版本的成本与评分；
  5. 数据集回归：把线上问题 Trace 一键加入 Dataset，作为发布前回归集。

6. 双层互跳与对账

  • Langfuse Trace 详情保留 OTel trace_id → 在 Grafana Tempo 中粘贴同一 trace_id 查看系统层全貌（含 DB/网关 Span）；
  • 对账基线：Tempo 中 gen_ai Span 数 ≈ Langfuse observations 数（差异来源：filter 规则、Langfuse 默认只保留 LLM 相关 scope）。差异 >10% 时检查 filter 与根 Span 完整性；
  • Token 对账：sum(gen_ai.client.token.usage)（Prometheus）与 Langfuse 成本页总 Token 应量级一致。

7. 验收清单

  • 同一次请求在 Tempo 与 Langfuse 均可见，trace_id 一致；
  • Langfuse Trace 上有 user/session 归属，Sessions 视图可回放多轮会话；
  • deepseek-chat 成本自动核算生效；
  • Collector otelcol_exporter_send_failed_spans{exporter="otlphttp/langfuse"} 为 0；
  • 非 AI 的基础设施 Span（DB/健康检查）没有涌入 Langfuse。
