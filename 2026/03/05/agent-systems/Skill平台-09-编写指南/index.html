09 · Skill 编写规范：从任务样本到一次过审

企业级 Skill Registry 平台工程手册 · 第 09 篇（扩展卷）
定位：08 篇是执法者视角的规范总集，本篇把同一套规范反转为作者视角的操作教程。读者是要写技能的领域工程师——他们懂 OTA、懂 K8s、懂财务流程，但第一次给模型写作。目标只有一个：第一次提交就通过流水线与人审。
全篇以规范编号（N/F/D/S/R/E/Doc 系列，见 08 篇）作行内锚点，写作时随手对照。

1. 概述：给模型写作是一种新的技术写作

技能作者最常见的心智错位：把 SKILL.md 当成”给同事看的操作文档”。两者读者根本不同：

给人的文档 给模型的技能
背景铺垫 必要（人需要 why 才有动力） 有害（稀释指令注意力，01 篇 §2.2）
语气 陈述、委婉 指令、直接、条件式（Doc-1）
步骤粒度 可以跳步（人会脑补） 分支必须显式（模型的脑补 = 不可控行为）
阈值 “较大时注意” “解析率 <60% 时执行 X”（数值化）
知识边界 可以说”具体情况具体分析” 必须给出裁决框架或明确移交（Doc-4）

一句话校准：你不是在写文档，你是在给一个能力很强但没有你的领域经验的执行者写作战指令。它读得懂一切，但只会做你写了的事和它自己推断的事——你的工作是让前者覆盖关键路径、给后者划好边界。

2. 写作之前：立项三问与形态判定

2.1 立项三问（都是”是”才继续）

  1. 复杂度门槛之上吗？ 模型不查技能就做不好吗？”把 JSON 转 CSV”过不了这一问——模型本来就会，写成技能也不会被触发（01 篇 §3.2）。测法：拿 3 个真实任务样本直接问模型（无技能），产出可接受则不立项。
  2. 复用频率够吗？ 02 篇附录 B.3 的缺口清单是最好的立项来源；没有该管道时，用工单/会话语料手工估频。经验线：月均 <20 次的任务，维护成本大概率高于收益，先沉淀为 reference 挂到相邻技能。
  3. 知识足够稳定吗？ 核心流程的半衰期短于发版周期的（如”本周活动规则”），走工具实时取数或配置，不进技能（R-3）。

4. SKILL.md 写作实务

4.1 语用学七则

  1. 第二人称指令式：”先跑解析脚本”而非”解析脚本可用于……”。
  2. 条件式包裹一切非普适指令：”当输出结构化结果时使用 JSON”，永远不写”所有输出必须 JSON”（技能串味，01 篇 AP-7）。
  3. 动词具体：”核对 / 比对 / 声明 / 移交”优于”处理 / 关注 / 注意”。
  4. 阈值数值化：模型执行”<60% 时”远比”过低时”稳定。
  5. 禁止句要给替代路径：”不要逐行读日志”必须跟着”一律先跑解析脚本”——只堵不疏的禁令会把模型逼进未定义行为。
  6. 重要纪律前置：SKILL.md 开头一段话给核心方法论与分界声明（03 篇两技能的”脚本给证据，你给结论”），模型对开头的遵循度最高。
  7. 不确定性有台词：明确规定证据不足时怎么说（”宁可给’待定 + 取证方案’，不要给低置信度的确定性结论”）——不写这条，模型会按通用倾向自行拿捏，跨会话不一致。

4.2 写作病对照（作者最常犯的五种）

病 1 · 背景瘤
❌ “OTA 是整车软件升级的重要手段，随着软件定义汽车的发展……（三段）”
✅ 删除。背景中真正影响执行的事实（”PRECHECK 失败是可恢复失败，不计缺陷”）改写为对应步骤内的条件指令。

病 2 · 人称漂移
❌ “工程师此时应该登录平台查看……”
✅ “让用户从 campaign 平台导出该 VIN 的任务记录”——模型不是工程师本人，它引导用户或调用工具。所有”人做的动作”要翻译成”模型引导/模型调用”。

病 3 · 隐式专家跳步
❌ “确认不是电源问题后，分析总线。”（怎么确认？）
✅ “若冻结帧电压在 10.5~15.8V 之间且无 P056x 码 → 排除电源级联，进入总线分析（§2）。”

病 4 · 万能兜底步
❌ “第 5 步：综合以上信息给出专业结论。”
✅ 拆为必须回答的问题清单（03 篇第 4 步范式：失败在哪环 / 为什么 / 个体还是批次）。”专业结论”不是指令，是愿望。

病 5 · reference 甩锅
❌ “详细信息参见 references/ 目录。”
✅ 路由表（R-4）：”出现刷写类失败码 → 读 error_code_mapping.md §3 + ecu_matrix.md 涉事 ECU 小节。不要一次读完所有 reference。”

5. Description 写作操作流

02 篇是理论，作者的操作流五步（半天工作量）：

  1. 从 §3 第 5 步的样本原话里摘触发词，按”名词（OTA/差分包）、动词（升级/刷写）、症状语（卡在 45%/升不上去）、文件信号（swdl.log）”四类各凑 2~4 个;
  2. 套四段模板（02 §3）写初稿；
  3. 找相邻技能（同域清单在 Registry 搜索页）读它们的 description，写第④段负面边界，同时给对方 owner 发配对声明请求（D-4 是双向的，先发起的一方主动）；
  4. trigger_examples ≥8 / negative ≥4 入库（D-3），negative 里必须含”最容易混淆的相邻场景”而不是随便找不相关的凑数;
  5. 本地触发自测（§9.2），不达 80% 不提交——流水线评测更严（90 SLO），本地先过粗筛省一轮打回。

6. Scripts 开发实务

6.1 心智设定：模型是你的用户

脚本的”用户体验”三件套，模型全都消费：

  • --help 即接口文档（S-8）：模型在不确定用法时真的会跑 --help。参数名自解释、默认值写明、示例命令一行。
  • stderr 是给模型的旁白（S-3）：元质量信息（解析率、丢弃行、警告）走 stderr 并给出行动指引——“解析率 41%，疑似格式不匹配”比裸数字好，因为 SKILL.md 里对应的分支指令可以引用同一措辞。
  • exit code 是分支信号（S-2）：0/1/2 语义严格遵守；exit 1 时 stderr 必须回答”缺什么、下一步是什么”，这是 SKILL.md fallback 节的燃料。

6.2 输出契约先行

写代码前先写输出 JSON 的 schema（哪怕就是注释里的示例），并回答三个问题：字段名是否自解释（模型按字段名理解语义，furthest_stage 优于 fs）；哪些字段是模型裁决的输入（这些字段的取值集合要在 SKILL.md 或 reference 里有解释）；体量是否可控（列表字段带 top-N 截断，如 03 篇 evidence 取前 5——脚本输出也是上下文成本）。契约测试（T-2）就是对这份 schema 的机器化。

6.3 防御式解析与真值分离

  • 输入永远脏：编码错误 errors="replace"、畸形行跳过但计数、空文件明确报错——03 篇 A.4 的解析率报告模式直接抄。
  • 领域真值（码表/拓扑）能放 reference 的放 reference；必须内嵌的（脚本要用）建立 CI 同步检查（S-6）并在两侧文件头互相注明”与 X 同步，改动需成对提交”。
  • 幂等写（S-4）：tmp + os.replace，两行代码换来模型层重试安全（07 §6）。

7. References 写作：为”被检索而读”优化

与 SKILL.md 相反，reference 的读者不会通读——模型带着一个具体问题跳进来。三条：

  1. 节内自足：任何一节被单独读到都能用，不依赖”上文提到的”。代价是少量重复，值得付。
  2. 三段式（R-2）：领域裁决类资料用”判据（可核对的条件清单）/ 反例（表象相同根因不同的陷阱）/ 处置（动作序列）”——03 篇 SOP 的反例栏是模型最需要而作者最容易漏的部分，因为专家的陷阱识别是内隐知识，要刻意外化。
  3. TOC + 稳定锚点：>300 行必须 TOC（F-3）；SKILL.md 路由表引用”§3”这样的锚点，reference 改版时锚点保持稳定（增节不重排号）。

8. Examples 回归对制作

§3 第 2 步的”理想产出”在此正式化。合格的回归对：

  • 输入样例覆盖脚本的字段分支（03 篇 sample_ua.log 刻意含三类失败）+ 至少一个走 fallback 的失败路径样例（08 附录 E 评审项）；
  • 期望产物标注比对层级：哪些字段必须全等（分类结果、终态判定），哪些只比结构（报告章节存在性），哪些不比（措辞）——E-2 的作者侧责任就是把这个标注写清，否则流水线只能按最严比对，措辞抖动会造成大量假失败；
  • 样例数据脱敏且自造：VIN/工单号用测试段，别偷懒拿生产数据截屏改两笔。

9. 本地自测流程（提交前一小时）

9.1 结构自查

跑本地 lint（脚手架自带），然后人工过 08 附录 E 的”内容质量”五项——重点走一遍”每个 fallback 分支的’然后呢？’”。

9.2 触发自测协议

9.3 执行自测

按 SKILL.md 逐字执行一遍 examples（假装自己是没有你经验的模型：只做写了的事）——凡是你发现自己”顺手”补了一个没写的判断，那个判断就是缺失的指令，回填。这一步的自我角色扮演是性价比最高的质检手段。

10. 提交与打回处理

findings 的正确读法：每条 = 规范 ID + 位置 + 修法（08 附录 B 消息纪律保证了这一点）。历史打回 Top 6 及其一次修复法：

打回原因 占比感 一次修复
D-3 evals 数量不足 高 回 §3 样本库补挖，别现编
D-4 边界未配对 高 §5 第 3 步提前发起，别等评审才通知对方
背景瘤 / Doc-1 无条件指令 高 §4.2 病 1、语用学第 2 则
F-4 缺失败路径样例 中 §8 第一条
S-6 真值不同步 中 成对提交习惯 + 文件头互注
S-7 静态扫描误中（合法但可疑模式） 低 提交说明里预先解释（如 base64 用途），评审员按 08 附录 E 核对

打回不是失败是校准；但同一规范连续两次打回说明没读懂规范本身，去读 08 篇对应条目的”根治机制”列。

11. 迭代与版本（作者侧速查）

  • 加触发场景 / 新增可选输入 / 新增输出字段 → MINOR；
  • 收窄触发域 / 删改输出字段 / 新增工具权限 → MAJOR（且订阅方不自动升，五维判定见 05 §5）——改 description 前先跑旧评测集，跌幅 >10% 流水线会强制 MAJOR，自己先知道比被判了才知道好；
  • 任何正文/脚本能力变更，description 复核是流水线强制联动项（D-7），提交说明里写清”本次是否影响触发域”。

12. 反模式（作者行为层）

  • AP-1 从记忆写作：不采样本直接写——触发词失真 + examples 后补敷衍，两个高频打回的共同根源。
  • AP-2 演示驱动：只用最顺利的案例开发，fallback 全是想象——§8 失败路径样例强制项就是治它。
  • AP-3 防御性堆叠：怕模型出错就把同一叮嘱写五遍、把所有 reference 都标”必读”——稀释效应让真正关键的指令反而失焦。信任分级：关键纪律前置一遍，其余靠条件分支。
  • AP-4 私藏语料：trigger_examples 现编而真实工单语料不入库——评测体系（10 篇）的地基被偷工。
  • AP-5 一人全干：description 的负面边界不与相邻技能 owner 沟通，单方面写完提交——D-4 打回 + 两不管地带。
  • AP-6 跳过角色扮演自测（§9.3）——最便宜的质检被跳过，最贵的人审来兜底。

13. 作者检查清单（提交前逐项勾）

  • 立项三问全”是”，形态判定为完整技能
  • ≥10 任务样本 + 理想产出先于代码存在
  • SKILL.md：开头有方法论与分界声明；全篇条件式；阈值数值化；≤500 行
  • 第 0 步输入判定 + 错误处理/fallback 节 + 边界节齐备
  • reference 路由表无悬空；references 三段式 + TOC
  • scripts：–help / exit code / stderr 协议 / 幂等写 / 解析率报告
  • 输出契约 schema + 契约测试 + 畸形输入单测
  • 真值同步成对提交 + 文件头互注
  • examples 含失败路径 + 比对层级标注 + 数据自造脱敏
  • trigger ≥8 / negative ≥4，negative 含最易混淆场景
  • 边界配对请求已发给相邻 owner
  • 本地触发自测 trigger ≥80% / negative ≥90%（各 3 次）
  • 角色扮演执行自测完成，”顺手补的判断”已回填
  • 提交说明：是否影响触发域 + 可疑模式预解释

附录 D：作者高频问答（FAQ）

Q1 我的领域没有可脚本化的操作，全是判断，还写 scripts 吗？
不硬写。纯裁决型技能（如 architecture-adr）合法存在，scripts 为空即可。但先自问一遍：判断的输入整理（从 PR 拉 diff 统计、从工单聚合信息）往往可脚本化——“没有确定性操作”常常是”没把取证环节当操作”。

Q2 SKILL.md 可以引用外部 wiki 链接吗？
不可以作为执行依赖（沙箱默认无网络，且外链内容不受发布评审与版本锁管辖——等于给技能开了个不签名的后门）。执行需要的内容收进 references；仅供维护者溯源的链接放 README。

Q3 我想让模型”始终先问用户三个问题再动手”，怎么写？
警惕这类无条件前置（Doc-1 亲戚）：输入已齐备时还机械三问是糟糕体验。改写为第 0 步的条件分流——“缺 X 时询问 X；样本/文件已提供时直接进第 1 步”。让提问由缺什么驱动，而不是由流程驱动。

Q4 同一个脚本两个技能都要用，复制还是共享？
族内 → 上提 plugin 级 shared（04 §3.1）；跨族 → 优先复制（两份独立演进），只有当它大到值得独立维护时，走”工具化”路线（登记为平台工具/MCP），而不是技能间私相授受——跨族共享文件没有依赖语义承载，是隐式依赖反模式（04 AP-5）的变体。

Q5 触发自测总差几个点，能不能先提交线上看看？
不能拿生产会话当评测环境。差几个点的标准修法顺序：查漏触发 query 的实际激活对象（混淆归因）→ 补症状语类触发词（作者最常漏的一类，见附录 A.4）→ 若漏触发集中在间接表达，加③段泛化子句 → 仍不行申请 pushy 登记（D-5，评测数据随附）。

Q6 评审说我的 fallback”是死胡同”，什么意思？
fallback 的验收标准是”模型执行它之后，用户手里多了什么”。”联系管理员”之后用户手里什么都没多；”输出取证清单：缺哪段日志、从哪个系统导出、导出后如何复跑”之后用户有了下一步。把每个 fallback 的产出物写成名词，死胡同自动现形。

Q7 我该为不同车型/平台写多个技能还是一个？
判据在 description：如果各车型的触发场景相同（用户不会说”帮我用 A 平台的方式诊断”），是一个技能 + 按变体拆 references（01 §6.3 域内变体模式，脚本以参数区分）；只有触发语言本身分化时才拆技能。

Q8 写完发现和已有技能重叠怎么办？
立即停笔联系对方 owner，三选一：合入对方（你的样本与 evals 是最好的见面礼）/ 重切边界后配对声明 / 确认对方僵尸化则走接管流程。抢发上线赌评审漏检，重叠检测（02 附录 A）大概率拦下，即便漏网也是给自己埋域内内耗（02 §4 双雄病）。

附录 E：写作病扩展（病 6~8）

病 6 · 工具幻觉
❌ “调用车辆实时状态接口查询在线情况。”（该接口未在 required_tools 声明，目标 surface 也没有）
✅ 写作时对照 manifest 的 required_tools 清单——SKILL.md 只许指挥声明过的工具；缺口走”引导用户提供”过渡 + 工具需求登记（附录 A.3 范式）。评审时 M-3 一致性核对会抓，但作者侧先自查省一轮。

病 7 · 格式过度规定
❌ 用 40 行规定报告的字体层级、分隔线样式、emoji 用法。
✅ 结构性要求（必答问题、章节存在性）保留并进回归比对；纯观感规定删除或降为一句风格提示——模型的默认排版能力足够，过度规定既占行数又制造回归假失败（10 篇 AP-7 的上游成因）。

病 8 · 移交话术缺失
❌ 边界节只写”不处理 DTC 分析”。
✅ 补全三要素：”识别信号（上下文出现升级/刷写场景）→ 移交对象（ota-log-diagnosis）→ 话术（’这属于 OTA 升级过程的伴生故障码，我按 OTA 诊断流程来分析’）”。没有话术的移交，模型只能生硬拒绝，用户体验断崖——移交是体验的接力棒，不是免责声明。

三病与正文五病共同的根源可以归为一句：作者写下了自己视角的世界（我知道的接口、我喜欢的格式、我的职责范围），而不是模型执行时的世界（声明过的工具、被比对的结构、用户眼中的连续服务）。写完通读一遍时切换到后一个视角，八种病都能自查出大半。
