Claude Code 开源生态：热门插件与技能框架评测

按五种扩展原语拆解 everything-claude-code、claude-code-best-practice、GSD、awesome-claude-skills、super…

Flywhl 17 分钟 更新于 2026.09 #AI工具#开发效率#Claude Code

先读结论

  1. 五个项目分属不同扩展原语：superpowers、everything-claude-code 是插件，GSD 是安装器写入的命令与代理，awesome-claude-skills 是索引，claude-code-best-practice 是参考仓库。
  2. 流程型框架只能选一个当主流程：GSD 与 superpowers 都要接管“规划—执行—验证”，叠加只会产生两套计划。
  3. 常驻成本主要来自 hooks 与启动注入，而不是技能数量；技能只有 name 与 description 常驻上下文。
  4. 技能脚本与 hook 等同于以本人权限执行任意代码，安装前按固定清单审查，并把插件市场固定到 tag。

写作时点为 2026-03 下旬，Claude Code 最新版本为 v2.1.84（2026-03-25 发布），star 数与版本号均取自当月的 GitHub 快照与 release 记录。

扩展原语速览

五个热门项目经常被放在一起比较，但它们落在 Claude Code 不同的扩展点上：有的是一个插件，有的是往 ~/.claude/ 里写文件的安装器，有的只是链接清单。先分清原语，才能判断“装上之后到底多了什么”。

原语 放在哪里 何时生效 常驻上下文开销 是否执行代码 上线时间
Skills ~/.claude/skills/<name>/SKILL.md、项目 .claude/skills/、插件内 模型按 description 判断自动加载，或用 /<name> 手动调用 只有 name 与 description 常驻，正文触发时才加载 可附带脚本，经 Bash 工具执行，受权限规则约束 2025-10-16；2026-01-09 起自定义命令并入 Skills
Plugins 市场（一个 git 仓库）→ /plugin install 启用即生效 取决于内含组件 取决于内含组件；其中的 hooks 与 MCP server 随启用运行 2025-10-09
Hooks settings.json 的 hooks 字段、插件内 hooks/hooks.json 生命周期事件确定性触发（SessionStart、PreToolUse、PostToolUse、Stop 等） 默认为零；向上下文输出内容时（如 SessionStart 的 additionalContext）每次都计入 是，command 类型直接执行 shell；2026-02-28 起另有 HTTP hooks 2025-06-30
Subagents ~/.claude/agents/、.claude/agents/<name>.md 主会话委派任务时 独立上下文窗口，主会话只收回结果 使用其被授予的工具 2025-07-24
MCP 项目 .mcp.json、用户级 ~/.claude.json 模型调用工具时 工具定义；2026-01-13 起 MCP Tool Search 默认开启，工具描述超过窗口 10% 时改为按需加载 server 是独立进程或远程服务，通常持有凭据 协议 2024-11 发布

两点常被忽略：

  • Plugin 只是打包格式。它把 skills、agents、commands、hooks、MCP 配置装进一个可版本化的单元，风险与开销取决于包里装了什么，而不是“插件”这个名字。
  • Hooks 不经过权限确认。Bash 工具调用会弹权限提示，hook 命令在事件发生时直接执行。评估一个项目的侵入性，首先看它注册了多少 hook。

五个项目与原语的对应关系：

项目 分发形态 实际落地的内容
everything-claude-code 插件 + 安装脚本 28 个 agent、125 个 skill、60 个 command、7 类事件共 28 条 hook，另需手动安装 rules
claude-code-best-practice 参考仓库 各原语的示例实现与 86 条技巧，不作为依赖安装
get-shit-done npx 安装器 57 个 /gsd:* 命令、18 个 agent、5 个 hook 脚本、statusLine，并改写 settings.json
awesome-claude-skills 索引 + 技能目录 + 1 个插件 第三方技能链接、仓库内技能、832 个 Composio 应用自动化技能、connect-apps 插件
superpowers 插件 14 个 skill、1 个 SessionStart hook、1 个 agent、3 个 command

评测维度

维度 关注什么 怎么查
维护活跃度 发版节奏、最近提交、是否有 release 与变更日志 release 列表、git log --since、issue 响应
侵入性 写入哪些目录、是否改 settings.json、注册多少 hook、能否干净卸载 读安装脚本与 hooks.json，装在临时 HOME 里对比文件树
上下文开销 启动时注入多少文字、技能 description 总量、是否强制每次任务先走流程 装前装后各跑一次 /context 对比
可审计性 代码与提示词是否在同一仓库、有无 tag 可固定、许可证是否明确、文档与实现是否一致 看 LICENSE、tag、README 中的路径与命令能否跑通
与团队规范冲突 是否强制 TDD、强制 worktree、固定目录结构、推荐跳过权限、命令名与现有约定重叠 读核心 skill 的“必须”条款与推荐配置

活跃度高不等于更好：一个月发十几个版本意味着提示词行为随时会变，团队场景下反而需要固定版本。

五个项目逐一分析

everything-claude-code

仓库与状态：affaan-m/everything-claude-code，约 11.9 万 star（2026-03），MIT。v1.0.0 发布于 2026-01-22，到 2026-03-21 的 v1.9.0 共发了 11 个版本。v1.8.0 起自我定位为“agent harness 性能系统”，同时适配 Claude Code、Cursor、Codex、OpenCode。

解决什么问题：把作者长期使用积累的 agents、skills、commands、hooks、rules 与 MCP 配置模板打成一个包，覆盖多语言代码审查、构建错误修复、TDD、E2E、安全扫描、会话记忆等场景。

安装方式：插件部分走市场；README 明确说明插件机制无法自动分发 rules，这部分必须另装。

v1.9.0 引入清单驱动的选择性安装：scripts/install-plan.js 只解析计划不改文件，install.sh 转调 scripts/install-apply.js 执行，并用状态库记录已装组件以便增量更新。

核心机制：

  • Hook 档位：ECC_HOOK_PROFILE=minimal|standard|strict 控制严格程度，ECC_DISABLED_HOOKS 按 ID 关闭单条 hook，不必改文件。
  • Instincts（continuous-learning-v2）：从会话中提炼带置信度的行为规则，/instinct-status、/instinct-export、/evolve 管理与聚类成技能。
  • AgentShield：独立仓库 affaan-m/agentshield，npx ecc-agentshield scan 扫描 CLAUDE.md、settings.json、MCP 配置、hooks、agent 定义中的密钥、权限与注入风险，发现严重问题时退出码为 2，可直接做 CI 门禁。

适用：多工具并用、希望一套配置同时服务 Claude Code 与 Codex/Cursor 的个人；想找现成 agent 定义做参考的人。

不适用：已有团队规范的仓库（它的 rules 与 agents 自带一套编码约定）；对启动速度和工具调用延迟敏感的场景。

风险：

  • 28 条 hook 中 11 条挂在 PreToolUse、8 条挂在 PostToolUse，每次工具调用都要经过它们，问题排查时很难区分是模型行为还是 hook 改写。
  • 插件与 rules 两条安装路径，升级时容易只更新一半。
  • README 中“MCP 过多会把 200k 窗口吃到约 70k、保持 10 个以内”的建议写于 Tool Search 默认开启之前；如今工具定义按需加载，这条的紧迫性下降，但每个 MCP server 仍是一个进程加一份凭据，数量控制依然有意义。

claude-code-best-practice

仓库与状态：shanraisshan/claude-code-best-practice，约 2.3 万 star（2026-03），MIT，没有 release，README 徽章标注随 Claude Code v2.1.84 同步更新。

解决什么问题：它是知识库加参考实现，不是依赖。内容包括各原语的“最佳实践 + 已实现示例”对照表、Command → Agent → Skill 编排示例 /weather-orchestrator、86 条技巧（大量来自 Claude Code 团队成员的公开分享），以及对 Superpowers、Spec Kit、BMAD、GSD、OpenSpec 等开发工作流的横向对比，结论是它们都收敛到 Research → Plan → Execute → Review → Ship。

使用方式：

然后回到自己的项目，让 Claude 以该仓库的某一篇 best-practice 文档为参照审查现有配置，只吸收差异，不整体复制。

值得直接采纳的技巧（均可在官方文档找到对应能力）：

  • skill 设置 context: fork 后在隔离的子代理中运行，主上下文只看到最终结果。
  • 每个 skill 维护一节 Gotchas，记录 Claude 在该领域反复犯的错，这是信息密度最高的部分。
  • skill 的 description 是触发条件，要写“什么时候该用我”，而不是功能摘要。
  • 用 PostToolUse hook 自动格式化，把最后 10% 的格式问题交给确定性工具。

风险：内容追随社交媒体上的分享快速更新，没有版本号，引用时应记下 commit；仓库自带的 .claude/ 配置为演示服务，不适合原样放进业务仓库。

get-shit-done（GSD）

仓库与状态：gsd-build/get-shit-done（旧地址 glittercowboy/get-shit-done 会重定向），2025-12 创建，约 4.4 万 star（2026-03），MIT。2026-03 的前 25 天就从 v1.22.1 发到 v1.29.0（2026-03-25，即写作时点的版本）。

解决什么问题：针对 context rot（上下文越满、输出质量越差），用“薄编排器 + 全新上下文的子代理”执行规格驱动的阶段流程，让主会话上下文保持在 30%–40%。

安装方式：

装完后在 Claude Code 里用 /gsd:help 验证；命令文件位于 ~/.claude/commands/gsd/ 或 ./.claude/commands/gsd/。

核心机制：

  • 状态落在文件里：.planning/ 下的 PROJECT.md、REQUIREMENTS.md、ROADMAP.md、STATE.md、每个任务的 PLAN.md 与 SUMMARY.md，跨会话靠文件而不是靠对话记忆。
  • 阶段流程：/gsd:new-project（已有代码先跑 /gsd:map-codebase）→ /gsd:discuss-phase N → /gsd:plan-phase N → /gsd:execute-phase N → /gsd:verify-work N → /gsd:ship N；小改动走 /gsd:quick。
  • 计划用 XML 表达：每个任务含 <files>、<action>、<verify>、<done>，验证步骤写进计划本身。
  • 分波并行与原子提交：执行阶段按依赖分波派发执行器，每个任务完成后立即单独提交。
  • 模型档位：/gsd:set-profile quality|balanced|budget|inherit 决定规划、执行、验证各用 Opus、Sonnet 还是 Haiku，默认 balanced（规划 Opus，其余 Sonnet）。

适用：从零开始、周期数周以上的个人项目；需要跨会话延续状态的长任务。

不适用：已有成熟需求与评审流程的团队仓库；一次性小修改（流程开销大于收益）。

风险：

  • README 推荐以 claude --dangerously-skip-permissions 运行，理由是避免反复确认 date、git commit；替代方案给出了一份 permissions.allow 白名单，团队环境应使用后者。
  • 安装器会改写 settings.json（hooks 与 statusLine），并写入数十个命令与代理文件；卸载依赖安装器自身的清理逻辑。
  • v1.27 起加入提示注入检测与 gsd-prompt-guard hook，但该 hook 是提示性的，不会阻断写入。
  • 发版极快，同一条命令在两周内行为可能不同，团队使用需固定版本（npx get-shit-done-cc@1.29.0）。

awesome-claude-skills

仓库与状态：ComposioHQ/awesome-claude-skills，约 5.0 万 star（2026-03），没有 release。README 声明 Apache 2.0，但仓库根目录没有 LICENSE 文件，并注明单个技能许可各异。

解决什么问题：它混合了三样东西，需要分开看：

  1. 索引：按文档处理、开发工具、数据分析、安全等分类链接到第三方仓库，如 anthropics/skills、obra/superpowers、NeoLabHQ/context-engineering-kit 以及个人作者的技能。链接大多指向对方 main 分支，内容随时变化。
  2. 仓库内技能：约 30 个顶层目录，如 mcp-builder、webapp-testing、skill-creator、changelog-generator；另有 composio-skills/ 目录收录 832 个基于 Composio 的 SaaS 应用自动化技能。
  3. connect-apps 插件：通过 Composio 托管鉴权，让 Claude 对 Gmail、Slack、GitHub 等应用执行真实操作。

安装方式：

核心机制：/connect-apps:setup 在对话中索取 Composio API Key，用硬编码的 /opt/homebrew/bin/python3.11 调 composio SDK 取得 MCP URL，再把 URL 与明文 Key 写入 ~/.mcp.json。

适用：发现技能的入口；需要让 Claude 操作 SaaS 且接受第三方托管鉴权的个人实验。

不适用：把整个仓库当依赖装进项目；在处理客户数据的环境里启用 connect-apps。

风险：

  • 索引不等于审查，收录标准只是 PR 被合并。
  • 文档与实现有出入：技能路径写错；connect-apps 写入的 JSON 缺少官方 .mcp.json 的 mcpServers 顶层键，装完要用 /mcp 确认是否真正加载。
  • API Key 经过对话记录、命令行参数与明文配置三处，且所有操作经 Composio 中转，数据出境与合规需单独评估。

superpowers

仓库与状态：obra/superpowers，作者 Jesse Vincent（Prime Radiant），2025-10 发布，约 12.7 万 star（2026-03），MIT。写作时点版本为 v5.0.6（2026-03-25），已进入官方插件市场。

解决什么问题：把“先澄清需求、再写计划、测试先行、逐任务评审”的工程方法写成一组会自动触发的技能，让 Claude 在动手前先走流程。

安装方式：

验证方式：新开会话说“帮我规划这个功能”，应看到 brainstorming 技能被调用。

核心机制：

  • 启动注入：插件注册一条 SessionStart hook（matcher 为 startup|clear|compact），把 using-superpowers 技能全文（约 5.2 KB）作为 additionalContext 注入，要求模型在任何任务前检查相关技能。“自动触发”靠的是这段注入，而不是技能数量。
  • 主流程：brainstorming（设计写入 docs/superpowers/specs/）→ using-git-worktrees → writing-plans（计划写入 docs/superpowers/plans/，拆成 2–5 分钟的小任务）→ subagent-driven-development 或 executing-plans → test-driven-development → requesting-code-review → finishing-a-development-branch。
  • 配套技能：systematic-debugging、verification-before-completion、dispatching-parallel-agents、receiving-code-review、writing-skills 等，共 14 个。

适用：想给 Claude 加一套稳定工程纪律的个人与小团队；认可 TDD 的项目。

不适用：不做 TDD 的团队——TDD 技能的条款是“先写了实现就删掉重来”；以短平快问答为主的会话，每次都走 brainstorming 显得过重。

风险：

  • 每次启动、/clear、压缩后都会重新注入约 5 KB 文本，属于固定上下文成本。
  • 技能措辞强硬，会与项目 CLAUDE.md 中的流程约定竞争；冲突时需在 CLAUDE.md 明确优先级。
  • using-git-worktrees 会自动创建 worktree，与团队的分支规范可能不一致。

叠加与冲突

这些项目不会互相覆盖文件，冲突发生在“谁来主导流程”和“同名能力谁先触发”上。

组合 冲突点 处理方式
GSD + superpowers 两者都要接管需求澄清、计划、执行、评审，产出两套计划文件（.planning/ 与 docs/superpowers/） 只保留一个主流程；另一个仅取不重叠的技能，如 systematic-debugging
everything-claude-code + superpowers 都带 planner、code review、TDD 能力，模型按 description 选择，结果不稳定 用 install profile 去掉 ECC 的同类组件
多个 SessionStart 注入 各自往上下文塞一段“必须遵守”的说明，相互矛盾时模型只能猜 用 /context 检查启动注入总量，只保留一个
多套 PreToolUse hook 执行顺序与相互影响难以推断，拦截原因难定位 同一事件只保留一个来源的 hook
第三方 rules + 项目 CLAUDE.md 编码约定打架（命名、测试位置、提交格式） 项目 CLAUDE.md 声明优先级，第三方 rules 只装通用部分

组合方案

个人开发者

  • 主流程：superpowers（官方市场一键安装，升级路径清晰）。周期长、需要跨会话状态的独立项目可以改用 GSD，但二选一。
  • 按需技能：从 awesome-claude-skills 索引里挑具体技能（如 mcp-builder、webapp-testing），复制到 ~/.claude/skills/ 并记下来源 commit。
  • 参考：claude-code-best-practice 只读不装。
  • 不装：everything-claude-code 全量档；确有需要时用 --profile core 起步。

小团队（5–20 人）

  • 把团队用到的插件写进项目 .claude/settings.json 的 extraKnownMarketplaces 与 enabledPlugins，保证成员拿到同一套配置。
  • 市场固定到 tag 或分支：/plugin marketplace add <owner>/<repo>@<tag>（v2.1.71 修复了 @ 分隔符的解析，此前只能用 #）。
  • 技能以 vendoring 方式签入 .claude/skills/，在 SKILL.md 顶部注释来源仓库与 commit，升级走 PR 评审。
  • 流程框架统一为一个，并在 CLAUDE.md 写明与团队规范冲突时以哪个为准。
  • 不推荐 --dangerously-skip-permissions，用 permissions.allow 白名单代替。

企业

  • 用托管设置（managed settings）的 strictKnownMarketplaces 限定可添加的市场，只放行内部镜像市场。
  • 内部市场收录的每个插件都经过下一节的审查，并固定到审查过的 commit。
  • CI 里对 .claude/ 目录跑配置扫描（例如 AgentShield 的 npx ecc-agentshield scan，严重问题退出码为 2），扫描器本身也要固定版本。
  • 需要 SaaS 集成时优先使用官方或自建 MCP server，第三方托管鉴权方案须先过数据合规评审。

供应链安全：安装前审查什么

基本判断：技能附带的脚本与 hook 命令都以当前用户的权限运行，等同于执行任意代码。hook 不经过权限确认；SKILL.md 正文会作为指令进入上下文，本身就是提示注入面；MCP server 是常驻进程，往往持有令牌。

审查项 位置 看什么
Hook 清单 hooks/hooks.json、安装器写入的 settings.json 事件类型、matcher 范围、执行的脚本；PreToolUse/PostToolUse 越多，影响面越大
脚本行为 hooks/、scripts/、各 skill 的 scripts/ 网络请求（curl、wget、fetch）、eval、base64 解码后执行、写 shell 配置文件、读取 ~/.ssh 或 .env
安装器 install.sh、bin/install.js、package.json 的 postinstall 写哪些目录、是否改全局设置、是否覆盖已有文件、能否卸载
技能正文 SKILL.md 是否要求跳过确认、自动推送、关闭测试；allowed-tools 是否过宽
MCP 配置 .mcp.json、插件内的 MCP 声明 远程端点属于谁、凭据如何传递、是否把 Key 写进明文文件
依赖与许可 LICENSE、package.json、requirements.txt 许可是否明确、依赖是否固定版本
版本固定 tag、release 能否固定到一个可复查的版本

可以直接执行的检查步骤：

装完后在会话里复核：/plugin 查看启用的插件，/hooks 查看实际注册的 hook，/mcp 查看已连接的 server，/context 对比装前装后的常驻上下文。发现不需要的 hook 时，项目级可以用 disableAllHooks 做紧急止血，再逐个排查。

  • claude-code-best-practice：约 6.7 万 star（2026-09），仍持续跟随 Claude Code 版本更新，依旧没有 release。
