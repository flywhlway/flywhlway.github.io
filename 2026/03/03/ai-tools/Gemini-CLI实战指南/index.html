Gemini CLI 实战：配置、MCP、扩展与 Hooks

以 Gemini CLI v0.31 为基准…

Flywhl 41 分钟 更新于 2026.09 #AI工具#开发效率#MCP

先读结论

  1. 认证先定路线：本机交互用 Google 登录，CI 用 API Key 或 Vertex AI；.env 只加载找到的第一个文件，不合并。
  2. settings.json 自 v0.3.0 起是嵌套结构，旧教程的顶层键不再生效；项目配置、MCP 与自定义命令只在受信任文件夹里加载。
  3. MCP 子进程继承的环境会被强制过滤，凭据必须写进服务器自己的 env；gemini mcp add 默认写入项目级配置。
  4. 扩展清单只有 name、version、mcpServers、contextFileName、excludeTools、settings、themes 等真实字段，命令、hooks、skills 靠目录约定；从 Git 安装不会执行 npm install。
  5. Hooks 的工具 matcher 是未锚定正则、timeout 以毫秒计；从 Claude Code 迁移后要手工修正超时与工具名。

Gemini CLI 是 Google 在 2025-06-25 开源（Apache 2.0）的终端 Agent，npm 包名 @google/gemini-cli，命令是 gemini。它每周发布一个稳定版，配置键和功能变化很快：网上不少教程还停在 2025 年年中的扁平配置写法，包名、字段也常有错误。本文以 2026-02-27 发布的 v0.31.0 为基准，文中的命令、配置键、事件名和清单字段均对照该版本的官方文档与源码核对过；标注「实验」的功能需要手动开启。

安装与认证

安装

稳定版每周发布一次（由上周的 preview 版晋升），@preview、@nightly 是更激进的通道。团队在 CI 里使用时建议锁定版本，例如 npm install -g @google/gemini-cli@0.31.0，避免某次周更改了配置键导致流水线失败。

三种认证方式怎么选

方式 启用方式 额度与计费 适合 注意
Google 账号登录 启动 gemini，选 Login with Google，凭据缓存在本地 个人账号免费 60 次/分、1000 次/天，模型由 CLI 在 Gemini 家族内路由；AI Pro/Ultra 订阅额度更高 本机交互开发 需要能打开浏览器；公司、学校、Workspace 账号及 Code Assist 许可要设置 GOOGLE_CLOUD_PROJECT
Gemini API Key 设置 GEMINI_API_KEY，选 Use Gemini API key 免费层 250 次/天、10 次/分，且只能用 Flash；付费层按 token 计费 CI、无浏览器环境、需要固定模型 Key 等同账单权限，泄露即被盗刷
Vertex AI 设置 GOOGLE_CLOUD_PROJECT、GOOGLE_CLOUD_LOCATION，再从 ADC、服务账号 JSON、Google Cloud API Key 中选一种 按量计费或预购吞吐；Express Mode 可 90 天免开通计费 企业、需要 IAM 审计和数据合规 用 ADC 或服务账号前先 unset GOOGLE_API_KEY GEMINI_API_KEY，否则会被 Key 抢先

取舍规则很简单：

  • 本机交互：Google 登录额度最高且免费，首选。
  • 无头与 CI：gemini -p "..." 这类非交互调用不会弹浏览器，本机没有缓存过登录凭据时只能用 API Key 或 Vertex AI。
  • 企业：Vertex AI 服务账号（GOOGLE_APPLICATION_CREDENTIALS 指向 JSON 文件，授予 Vertex AI User 角色），再用 security.auth.enforcedType 锁定认证类型，防止成员切回个人账号。

额度用量随时用 /stats model 查看，/auth 切换认证方式。

.env 只认第一个

CLI 从当前目录逐级向上查找 .gemini/.env 或 .env，找不到再用 ~/.gemini/.env、~/.env，只加载找到的第一个文件，不做合并。典型事故：项目根目录有一个给应用自己用的 .env，于是 ~/.gemini/.env 里的 Key 整个失效，表现为「换个目录就要重新认证」。处理办法二选一：认证变量写进 shell 配置文件（export），或者在项目里建 .gemini/.env 并补齐认证变量。另外，项目 .env 里的 DEBUG、DEBUG_MODE 默认被排除，调试 CLI 本身要写进 .gemini/.env。

GEMINI.md：分层上下文与 /memory

三层加载

层 位置 加载时机 适合放
全局 ~/.gemini/GEMINI.md 每个会话 个人偏好：回答语言、提交信息格式
项目与祖先目录 从当前目录向上，直到含 .git 的项目根（或 home） 启动时 技术栈、构建与测试命令、目录禁区
子目录 当前目录以下，默认最多扫描 200 个目录（context.discoveryMaxDirs） 启动时；开启实验项 experimental.jitContext 后改为工具访问到该目录时才加载 模块专属约定

所有找到的文件会拼接后放进系统提示，而不是由下层覆盖上层。两份文件写了相互矛盾的规则，模型会同时看到两条，结果不可预期。子目录文件要改变上层规则时，应写明「本目录例外：……」。底栏会显示已加载的上下文文件数，/memory show 能看到最终拼接结果。

最后一行是导入语法：@相对或绝对路径 会把另一个 Markdown 文件内联进来，主文件因此保持简短。三类内容不要放进 GEMINI.md：长篇参考资料（每轮都占上下文，改用导入或 Skills）、密钥（会随提示词发往模型服务）、每周都变的信息（很快过期，反而误导模型）。

/memory 与 save_memory

命令 作用
/memory show 显示当前拼接后的完整上下文

/memory refresh 重新扫描并加载所有上下文文件（改了文件后执行）

对话里说「记住……」时，模型调用的是 save_memory 工具，它同样写入全局文件的 ## Gemini Added Memories 小节。项目专属的事实被这样记下后，会出现在你所有项目的上下文里。建议：项目事实手工写进项目 GEMINI.md，全局小节定期清理。

settings.json：分层与关键配置

优先级

从低到高：默认值 → 系统默认文件 → 用户文件 ~/.gemini/settings.json → 项目文件 .gemini/settings.json → 系统覆盖文件 → 环境变量 → 命令行参数。系统覆盖文件在 Linux 为 /etc/gemini-cli/settings.json，macOS 为 /Library/Application Support/GeminiCli/settings.json，管理员用它强制下发配置。字符串值里可以写 $VAR 或 ${VAR} 引用环境变量，加载时展开。编辑器可关联仓库里的 schemas/settings.schema.json 获得补全和校验。

受信任文件夹：配置不生效先查这里

开启 security.folderTrust.enabled 后，首次在某目录启动会弹出信任对话框，并列出该目录里发现的命令、MCP 服务器、Hooks、Skills 和覆盖项。选择不信任时，CLI 进入安全模式：

  • 不读项目 .gemini/settings.json 和项目 .env；
  • 不连接任何 MCP 服务器；
  • 不加载自定义命令，连全局命令也不加载；
  • 所有工具调用都要确认，不能安装、更新、卸载扩展。

「MCP 没连上」「命令找不到」时，先用 /permissions 查看并修改当前目录的信任状态，所有规则存放在 ~/.gemini/trustedFolders.json。官方配置参考与受信任文件夹文档对该开关默认值的描述不一致，显式写进用户配置最稳妥。

内置工具、审批与安全边界

工具名速查

写策略规则和 Hooks matcher 都要用工具的内部名称：

类别 工具名
读取 read_file、read_many_files、list_directory、glob、grep_search
写入 write_file、replace
执行 run_shell_command
网络 web_fetch、google_web_search
协作 save_memory、write_todos、ask_user、activate_skill、enter_plan_mode、exit_plan_mode

部分文档仍写 search_file_content，那是旧名，v0.31 源码中的名称是 grep_search。提示词里的 @路径 会触发 read_many_files，!命令 直接执行 shell。

审批模式

模式 行为 切换
default 写文件、执行命令前逐次确认 默认
auto_edit 自动批准 write_file、replace，命令仍需确认 Shift+Tab 循环，或 --approval-mode auto_edit
plan 只读，只能写计划文件 Shift+Tab、/plan（需开启实验项）
yolo 全部自动批准，并默认启用沙箱 Ctrl+Y，或 --approval-mode yolo

非交互模式下，需要确认的调用会按拒绝处理。所以在 CI 里要么只做只读分析，要么用 --allowed-tools 或策略规则显式放行。

策略引擎：比 tools.exclude 更细

tools.exclude 屏蔽命令的写法已标记弃用，改用策略引擎。规则写在 TOML 文件里：用户级放 ~/.gemini/policies/*.toml，工作区级放 .gemini/policies/*.toml。

decision 取 allow、deny、ask_user。最终优先级 = 层级基数 + priority/1000，层级依次为默认 1、工作区 2、用户 3、管理员 4，因此用户规则总能压过项目里提交的规则。要注意边界：commandPrefix 是前缀匹配，git push -f 就绕过了上面那条 --force 规则，需要再补一条或改用 argsPattern 正则匹配参数。策略用来减少误操作，真正的隔离靠沙箱。

沙箱

方式 平台 隔离程度 启用
Seatbelt（sandbox-exec） macOS 默认 profile permissive-open：禁止写项目目录之外，网络放开 GEMINI_SANDBOX=sandbox-exec，用 SEATBELT_PROFILE 切换 profile
Docker / Podman 全平台 容器级隔离 GEMINI_SANDBOX=docker，或配置 "tools": {"sandbox": "docker"}

开关优先级：-s/--sandbox 参数 > GEMINI_SANDBOX 环境变量 > tools.sandbox 配置。macOS 内置六个 profile，按「permissive / restrictive / strict」三档限制强度和「open / proxied」两种网络策略组合，例如 restrictive-proxied。项目需要额外依赖时，在 .gemini/sandbox.Dockerfile 里基于 gemini-cli-sandbox 镜像扩展，再用 BUILD_SANDBOX=1 gemini -s 构建。开沙箱后，MCP 服务器的可执行文件和网络也要在沙箱内可用，这是「开沙箱后 MCP 连不上」的常见原因。

检查点与 /rewind

检查点 + /restore /rewind
开启 general.checkpointing.enabled: true（v0.11 起已移除命令行开关） 默认可用，输入 /rewind 或连按两次 Esc
快照时机 每次批准写文件类工具之前 按对话轮次
存储 影子 Git 仓库 ~/.gemini/history/<project_hash>，对话与工具调用存于 ~/.gemini/tmp/<project_hash>/checkpoints 会话数据
回退内容 文件、对话，并重新提出原工具调用 三选一：对话和代码 / 仅对话 / 仅代码
盲区 纯 shell 改动不会单独产生检查点 不回退 shell 工具（!）和手工修改

两者都不影响项目自己的 Git 仓库，也都不能替代提交：大改动前先 git commit，出了问题靠 Git 回滚最可靠。只回退代码而保留对话时，要告诉模型「文件已恢复」，否则它会基于过期认知继续工作。

MCP：接入外部能力

配置字段

MCP 服务器写在 settings.json 顶层的 mcpServers 里，command、url、httpUrl 至少写一个，同时出现时优先级为 httpUrl > url > command。

字段 说明
command / args / cwd / env stdio 传输：启动子进程，经 stdin/stdout 通信
url SSE 端点
httpUrl Streamable HTTP 端点
headers HTTP 请求头，值可写 $VAR
timeout 请求超时，毫秒，默认 600000（10 分钟）
trust true 时跳过该服务器全部工具的确认
includeTools / excludeTools 工具白名单 / 黑名单，同时命中时以排除为准
description 显示用描述
authProviderType / oauth 认证方式与 OAuth 参数，见下文

用命令管理

三个坑：

  1. -s/--scope 默认是 project，写进仓库里的 .gemini/settings.json，个人 token 配置很容易被提交。个人服务器一律加 -s user。
  2. 用双引号写 -H "Authorization: Bearer $GITHUB_MCP_PAT"，shell 会先展开变量，明文 token 就落进了配置文件。
  3. 未知选项会自动当作服务器参数传下去，但与 mcp add 自身选项同名的（-e、-s、-t、-H 等）会被吃掉，服务器参数统一放在 -- 之后最稳。

会话内对应的斜杠命令是 /mcp list（默认）、/mcp desc（带工具描述）、/mcp schema（带参数结构）、/mcp refresh（重启所有服务器并重新发现工具）、/mcp enable|disable <名称>。

凭据必须显式传递

CLI 启动 stdio 服务器时会强制过滤继承来的环境变量：名字含 TOKEN、SECRET、PASSWORD、KEY、AUTH、CREDENTIAL、PRIVATE、CERT 等字样的变量，值看起来像 GitHub、Google、AWS、Slack 等密钥的变量，以及 DATABASE_URL、GOOGLE_CLOUD_PROJECT 等固定黑名单都会被去掉。典型症状是「终端里直接运行服务器正常，接进 Gemini 就 401」。解决方法是把服务器需要的变量写进它自己的 env，值用 $VAR 引用，显式声明的变量不会被过滤；同时不要在 JSON 里写明文。

工具过滤与信任

  • 调用 MCP 工具时的确认框有四个选项：允许一次、总是允许该工具、总是允许该服务器、取消。
  • trust: true 跳过该服务器的全部确认，只给你完全掌控、且没有写操作的服务器开。扩展里声明的 MCP 服务器不支持 trust。
  • 多个服务器暴露同名工具时，先注册的保留原名，后注册的改名为 服务器名__工具名。工具名中字母、数字、下划线、点、连字符以外的字符会被替换成下划线，超过 63 个字符会从中间截断。
  • 为兼容 Gemini API，工具参数 schema 中的 $schema、additionalProperties 会被移除，参数校验要在服务器端自己做，不能依赖 additionalProperties: false。
  • 服务器暴露的 prompts 会变成斜杠命令（如 /poem-writer --title="..."），resources 可以像文件一样用 @server://路径 引用。

OAuth 与 Google 云认证

远程服务器返回 401 时，CLI 会自动发现 OAuth 端点、尝试动态注册客户端、打开浏览器授权，token 存到 ~/.gemini/mcp-oauth-tokens.json 并自动刷新。/mcp auth 列出需要认证的服务器，/mcp auth <名称> 发起或重新授权。授权依赖本机浏览器和本地回调（默认 http://localhost:7777/oauth/callback，可用 oauth.redirectUri 修改），因此纯 SSH、没有浏览器的容器里走不通，这类环境改用 headers 携带 token，或使用 Google 凭据方式：

authProviderType 还有 service_account_impersonation，配合 targetAudience（IAP 白名单中的 OAuth Client ID）和 targetServiceAccount（被模拟的服务账号邮箱），用本地 ADC 换取 OIDC ID token，访问受 IAP 保护的 Cloud Run 服务。使用者需要 roles/iam.serviceAccountTokenCreator 权限，项目要开启 IAM Credentials API。

状态 DISCONNECTED 命令路径错、依赖没装 在终端单独运行同一条命令；gemini --debug 启动后按 F12 看日志

stdio 服务器偶发协议错误 服务器往 stdout 打了日志 日志一律写 stderr

改了配置没生效 未刷新、目录不受信任、写到了另一个 scope /mcp refresh；/permissions；gemini mcp list 核对来源

扩展的组成

扩展是 ~/.gemini/extensions/<name>/ 下的一个目录，根目录必须有 gemini-extension.json。清单里真实存在的字段只有这些：

字段 说明
name 必填。小写字母、数字和连字符，应与目录名一致；用户用它引用扩展
version 必填。缺少 name 或 version 时扩展加载失败
description 展示在扩展库页面
mcpServers 与 settings.json 同构，但不支持 trust；与用户配置同名时以 settings.json 为准
contextFileName 上下文文件名；不写而目录里有 GEMINI.md 时自动加载
excludeTools 从模型可用工具中排除，支持 run_shell_command(rm -rf) 这种命令级限制
settings 安装时向用户索取的配置：name、description、envVar、sensitive
themes 自定义配色

其余能力靠目录约定：commands/**/*.toml 是自定义命令，hooks/hooks.json 是钩子（不写在清单里），skills/<名称>/SKILL.md 是技能，agents/*.md 是子代理（预览功能）。清单和 hooks.json 中可用三个变量：${extensionPath}（扩展目录绝对路径）、${workspacePath}（当前工作区绝对路径）、${/}（平台路径分隔符）。

网上流传的 author、license、repository、plan 等清单字段并不存在；「项目级 .gemini/extensions/ 目录」也不是加载位置，扩展只从用户目录加载，按工作区启停用 gemini extensions disable <name> --scope workspace。settings 中 sensitive: true 的值存入系统钥匙串，其余写入扩展目录的 .env，安装后可用 gemini extensions config <name> 修改。

安装、更新与发布

  • install 是复制，源仓库更新后要执行 update；开发期用 link 省去这一步。
  • install 会先显示安全提示并请求确认，--consent 可跳过，只在脚本化安装时使用；--auto-update 开启自动更新。

Hooks：在生命周期上插确定性逻辑

Hooks 是 CLI 在 Agent 循环特定节点同步执行的外部命令。模型可能忘记遵守 GEMINI.md 里的规则，Hook 不会：它适合做安全拦截、自动检查、审计日志和上下文注入。

事件与触发位置

flowchart TD
  S([SessionStart]) --> U[用户提交提示词]
  U --> BA[BeforeAgent]
  BA --> BM["BeforeModel / BeforeToolSelection"]
  BM --> LLM[(模型请求)]
  LLM --> AM["AfterModel（每个响应块）"]
  AM -->|请求调用工具| BT[BeforeTool]
  BT --> T[执行工具]
  T --> AT[AfterTool]
  AT --> BM
  AM -->|给出最终回答| AA[AfterAgent]
  AA --> U
  U -.->|退出或 clear| SE([SessionEnd])

另有两个旁路事件：PreCompress 在压缩历史前异步触发，Notification 在出现工具权限确认等系统提醒时触发，二者都只能观察，不能阻断。

事件 能做什么 不能做什么
SessionStart additionalContext 注入为首轮上下文（非交互模式下前置到提示词） 阻断启动
BeforeAgent 追加本轮上下文；decision: "deny" 丢弃用户消息；continue: false 保留消息但终止本轮 —
BeforeModel 改写请求（换模型、调温度）；返回合成响应，直接跳过模型调用 —
BeforeToolSelection 用 toolConfig.mode（AUTO/ANY/NONE）和 allowedFunctionNames 收窄可用工具；多个 hook 的白名单取并集，NONE 优先 使用 decision、continue、systemMessage
AfterModel 替换响应块，用于实时脱敏 一次处理完整回答（它逐块触发）
BeforeTool deny 阻止执行，reason 作为工具错误回给模型，本轮继续；hookSpecificOutput.tool_input 合并覆盖参数 —
AfterTool deny 隐藏真实结果并用 reason 替代；additionalContext 追加到结果；tailToolCallRequest 串接下一个工具 —
AfterAgent deny 拒绝回答，reason 作为新提示触发重试；clearContext 清空模型记忆 —
SessionEnd 显示提示 让 CLI 等它执行完
PreCompress / Notification 记录、转发 阻断或改变流程

AfterAgent 的重试要防死循环：输入里的 stop_hook_active 为 true 表示已处于重试中，此时应直接放行。

配置结构

  • 来源与优先级：项目 .gemini/settings.json > 用户 > 系统 > 扩展的 hooks/hooks.json（顶层同样是 {"hooks": {...}}，可用 ${extensionPath}）。
  • 字段：type 目前只支持 command；timeout 单位是毫秒，默认 60000；name 用于 /hooks 管理。
  • matcher：工具事件是正则，而且源码用 new RegExp(matcher).test(toolName) 匹配，不锚定。写 replace 会命中所有名字里含 replace 的 MCP 工具，务必写成 ^(...)$。生命周期事件是精确字符串（如 SessionStart 的 startup、resume、clear），* 或空串匹配全部。
  • 并发：同一事件匹配到的 hook 默认并行执行；任一定义写了 sequential: true，本次匹配到的全部改为串行。
  • 变量：命令字符串里的 $GEMINI_PROJECT_DIR 由 CLI 替换成已做 shell 转义的路径，不要再套双引号，否则路径含空格时会变成 "'/a b'/..."。子进程环境里同时有 GEMINI_PROJECT_DIR 和兼容用的 CLAUDE_PROJECT_DIR；会话 ID、当前目录请从 stdin 的 session_id、cwd 读取。
  • 管理：/hooks panel 查看状态，/hooks enable|disable <名称>、/hooks enable-all|disable-all 启停；hooksConfig.disabled 可按名称永久停用。

输入输出协议

stdin 收到一个 JSON 对象，公共字段为 session_id、transcript_path、cwd、hook_event_name、timestamp，再加上事件专属字段（工具事件有 tool_name、tool_input，AfterTool 另有 tool_response）。

stdout 只能输出最终那一个 JSON，日志全部写 stderr。常用输出字段：

字段 含义
decision allow 或 deny（别名 block），具体效果因事件而异
reason 拒绝原因，多数事件里会回给模型
systemMessage 直接显示给用户
continue / stopReason continue: false 立即终止整个 Agent 循环
suppressOutput 在日志和遥测中隐藏 hook 元数据
hookSpecificOutput 事件专属输出，如 additionalContext、tool_input、toolConfig

退出码语义：

退出码 文档语义 实践建议
0 解析 stdout 的 JSON；推荐所有逻辑（包括拒绝）都走这条路 用 {"decision": "deny", "reason": "..."} 表达拦截
2 系统级阻断，stderr 作为原因 用于守卫脚本自身出错时的兜底阻断
其他 警告，按原参数继续 需要警告放行时只用 1

最后一行有个源码层面的细节：v0.31 在输出不是 JSON 时，只把退出码 1 当作警告，其余非零码（包括脚本不存在时 shell 返回的 127）一律按拒绝处理。反过来，退出码为 0 但 stdout 混入了非 JSON 文本，会被当成放行，文本作为 systemMessage 显示。结论是：守卫类 hook 要主动决定出错时「放行」还是「阻断」，不要依赖默认行为。

安全方面，Hooks 以你的用户权限执行任意命令。项目级 hook 会被 CLI 记录指纹，名称或命令变化（例如 git pull 带来的修改）后视为新的未受信任 hook，执行前会警告。打开陌生仓库时要看清这个提示。

与 Claude Code Hooks 对照

两者的设计高度相似，Gemini CLI 甚至内置了迁移命令，但细节差异足以让迁移后的配置悄悄失效：

维度 Gemini CLI（v0.31） Claude Code
配置位置 settings.json 的 hooks：项目 > 用户 > 系统 > 扩展 settings.json 的 hooks：用户、项目、本地及插件
工具事件 BeforeTool / AfterTool PreToolUse / PostToolUse
轮次事件 BeforeAgent / AfterAgent UserPromptSubmit / Stop
模型请求级事件 BeforeModel、AfterModel、BeforeToolSelection 无直接对应
压缩前 PreCompress PreCompact
timeout 单位 毫秒，默认 60000 秒
结构化拦截 顶层 decision: "deny" + reason PreToolUse 用 hookSpecificOutput.permissionDecision（allow/deny/ask）
退出码 2 阻断，stderr 作为原因 阻断，stderr 反馈给 Claude
改写工具参数 hookSpecificOutput.tool_input hookSpecificOutput.updatedInput
工具名 write_file、replace、run_shell_command Write、Edit、Bash
项目目录变量 GEMINI_PROJECT_DIR（兼容 CLAUDE_PROJECT_DIR） CLAUDE_PROJECT_DIR

gemini hooks migrate --from-claude 读取当前目录 .claude/settings.json 或 settings.local.json，映射事件名，把命令里的 $CLAUDE_PROJECT_DIR 替换成 $GEMINI_PROJECT_DIR，并改写 matcher 中的工具名，结果写入项目 .gemini/settings.json。按 v0.31 源码，迁移后必须手工检查四处：

  1. timeout 原样复制数值。Claude 的 30（秒）到了 Gemini 变成 30 毫秒，hook 几乎必然超时，需要乘以 1000。
  2. 部分名称映射有误或缺失。Grep、LS 被映射成 grep、ls，而实际工具名是 grep_search、list_directory：grep 靠未锚定匹配碰巧能命中，ls 什么也匹配不到；MultiEdit 没有映射，原样保留。事件映射表写的是 SubAgentStop，与 Claude Code 实际的 SubagentStop 大小写不一致，该事件不会被转换，留下一个 Gemini 不认识的事件名。
  3. 同名事件整体覆盖。迁移结果按事件名覆盖已有配置，项目里原有的 BeforeTool 等会被替换，迁移前先备份。
  4. 脚本本身不会被改写。脚本里判断的工具名、输出的 permissionDecision 等字段，要按 Gemini 协议逐一核对。

Agent Skills 与 Plan Mode

Agent Skills

Skill 是一个带 SKILL.md 的目录，遵循 agentskills.io 开放格式。会话开始时只把每个 Skill 的名称和描述放进系统提示；模型判断任务匹配时调用 activate_skill，经你确认后才加载正文，并把该目录加入可读路径。它解决的是「专业流程很长，但大多数时候用不上」的问题。

description 决定何时被激活，要写清触发场景，而不是泛泛地说「数据库专家」。发现位置与优先级：工作区（.gemini/skills/ 或别名 .agents/skills/）> 用户（~/.gemini/skills/ 或 ~/.agents/skills/）> 扩展；同一层里 .agents 别名优先。

会话内对应 /skills list|enable|disable|reload|link。

Plan Mode（实验）

v0.29 引入，写作时仍需在配置里开启 "experimental": {"plan": true}。进入方式：/plan、Shift+Tab 循环到 Plan、--approval-mode=plan，或直接说「先做个计划」让模型调用 enter_plan_mode（YOLO 模式下不可用）。

  • 只读：可用 read_file、list_directory、glob、grep_search、google_web_search、ask_user、activate_skill 和只读 MCP 工具；write_file、replace 只能写 ~/.gemini/tmp/<project>/<session-id>/plans/ 下的 .md 文件，目录可用 general.plan.directory 改到仓库里便于评审。
  • 流程：探索并提出至少两种方案 → 用 ask_user 让你选 → 写计划文件 → exit_plan_mode 提交审批，批准后退出计划模式开始实施。
  • 模型路由：general.plan.modelRouting 默认开启，规划阶段用 Pro，实施阶段切 Flash，兼顾质量与额度。
  • 放宽限制：用策略引擎给 Plan 模式单独加规则，例如允许查看 Git 状态、自动批准带只读注解的 MCP 工具：

迁移步骤

  1. 盘点现状：在常用项目里分别执行 gemini -l（列出扩展）、gemini mcp list、gemini skills list，会话内用 /hooks panel 记下 hooks；备份整个 ~/.gemini/ 和各项目的 .gemini/。
  2. 首次启动 agy：检测到旧配置时会弹出清单，勾选要迁移的扩展和全局配置，会话 token 迁入系统 keyring。
  3. 转换扩展：未在首启时转换的，执行 agy plugin import gemini；输出里逐项核对 skills、agents、commands（转为 skills）、mcpServers（写入 mcp_config.json）的处理结果。
  4. 搬迁 skills：工作区技能移到 .agents/skills/。v0.31 已经把 .agents/skills/ 当作别名识别，提前搬过去可以让两个工具同时生效，过渡期最省事。
  5. 拆出 MCP 配置：把 mcpServers 从 settings.json 移入对应的 mcp_config.json，远程服务器的 url/httpUrl 改为 serverUrl；stdio 服务器的 env 继续用变量引用，不要借迁移写入明文。
  6. 单独处理 hooks：官方迁移页没有给出 hooks 的转换方式，按目标工具的文档逐条重写，并用前文的伪造输入方法重新验证。
  7. 逐项验收：上下文文件是否被读取、每个 MCP 服务器的工具是否齐全、原来的斜杠命令是否以 skill 形式可用。

仍在企业许可下使用 Gemini CLI

  • 继续跟进周更：此后的版本以安全修复为主，长期锁在旧版本反而积累风险；CI 可以锁版本，但要定期跟进升级。
  • 用系统级配置统一管控：系统覆盖文件和管理员策略目录（Linux /etc/gemini-cli/policies、macOS /Library/Application Support/GeminiCli/policies）优先级最高，可集中设置 security.auth.enforcedType、mcp.allowed、security.allowedExtensions、security.disableYoloMode 等。以上为 v0.31 键名，升级后对照 changelog 核对。
  • 不再期待新功能：功能开发已转向 Antigravity CLI，新能力不要默认会回到 Gemini CLI。
  • 为迁移铺路：技能统一放 .agents/skills/，上下文统一用 AGENTS.md/GEMINI.md，MCP 配置按服务器整理成可直接搬进 mcp_config.json 的片段；hooks 脚本保持「stdin JSON 进、stdout JSON 出」的无状态写法，换宿主时只需调整事件名和字段。
