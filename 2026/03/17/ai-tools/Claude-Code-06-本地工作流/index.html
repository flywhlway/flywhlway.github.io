Claude Code 本地高效工作流：探索、计划、编码、验证

以 Claude Code 2.1.7x 为准…

Flywhl 19 分钟 更新于 2026.09 #AI工具#开发效率#Claude Code

先读结论

  1. 效率的关键是给 Claude 一个能自己运行的检查：测试、类型检查或截图，让验证回路不依赖你盯着。
  2. plan 模式把「弄清楚」和「动手改」分开；一句话能描述的 diff 就跳过计划。
  3. CLAUDE.md 是建议，Hooks 是强制：必须每次都发生的事交给 hook，按目录生效的约定放进 .claude/rules 并用 paths 限定。
  4. Checkpoints 只回滚 Claude 用编辑工具改过的文件；Bash 改动、数据库、推送和部署都不在它的覆盖范围内。
  5. 上下文是最贵的资源：任务之间 /clear，冗长输出交给子代理，非交互 -p 接入 CI 时用 --max-turns 与预算上限兜底。

一个闭环，五个阶段

用 Claude Code 写代码，效率差距很少来自提示词措辞，主要来自两件事：每个阶段有没有交给合适的能力，Claude 能不能自己闭合验证回路。本文按一个任务的生命周期展开，截至 2.1.7x（2026 年 3 月中旬）。

阶段 目标 主要能力 退出条件
探索 弄清现状 plan 模式、Explore 子代理、@ 引用文件 能说清要改哪些文件、为什么
计划 定方案 plan 模式出方案、Ctrl+G 在编辑器里改方案 方案里写了验收命令
编码 实现 acceptEdits 模式、权限白名单、格式化 hook 代码改完
验证 证明正确 测试、类型检查、截图、Stop hook 门禁 检查通过，并且有输出作为证据
提交 固化 git、gh 提交信息写清动机 
flowchart LR
    E[探索] --> P[计划] --> C[编码] --> V[验证] --> G[提交]
    V -->|检查失败| C
    P -->|方案站不住| E
    C -->|发现理解偏差| E

回边比主线更重要：验证失败回到编码是常态；编码时发现理解错了，应该退回探索，而不是在错误的方案上继续打补丁。

探索：先读后改

进入 plan 模式有三种方式：会话中按 Shift+Tab 在普通、自动接受编辑和 plan 模式之间循环切换；启动时用 claude --permission-mode plan；或者输入 /plan（2.1.0 起），2.1.72 起还可以直接带上描述，如 /plan 修复登录后偶发 401，进入 plan 模式的同时开始调研。

plan 模式下 Claude 只读不写，大面积的代码调研会委派给内置的 Plan 子代理，探索输出不会堆进主会话。探索阶段的提问要具体到路径和问题：

几条经验：

  • 用 @src/auth/session.ts 直接引用文件，比描述「那个 session 文件」可靠。
  • 报错、截图直接贴进对话，不要转述。
  • 让 Claude 标出不确定之处，比让它给出一个自信的完整答案更有用，这些标记就是下一步要验证的点。
  • 如果你能用一句话描述要改的 diff，比如改拼写、加一行日志、重命名变量，就跳过探索和计划直接改，plan 模式本身也有开销。

计划：让方案可审

在 plan 模式里要求 Claude 给出的方案至少包含四部分：要改的文件清单、步骤顺序、风险点、验收命令。最后一项最容易被漏掉，却决定了后面的验证能不能自动化。

方案出来后按 Ctrl+G 可以在外部编辑器里直接改，比在对话里来回说「第 3 步改成……」快得多。方案文件默认保存在本地，2.1.9 起可以用 plansDirectory 设置指定存放位置，需要团队评审的方案可以落到仓库的文档目录里。确认方案后退出 plan 模式，进入实现。

实现过程中看到方向不对，立刻按 Esc 打断并纠正，比等它写完再返工便宜。同一个问题纠正两次还不对，通常说明上下文里已经积累了错误假设，这时 /clear 后带着更好的提示重新开始，往往比继续纠正更快。

验证：让 Claude 自己闭环

Claude 在「看起来完成」时就会停下。没有它能自己运行的检查，你就成了验证回路本身，每个错误都要等你发现。给它一个能产出通过或失败信号的检查，回路就能自己闭合。

检查手段 适用 怎么接入
单元测试 逻辑正确性 需求里给出测试用例，或要求先写失败的测试再实现
类型检查、lint 接口一致性、低级错误 CLAUDE.md 写明命令；Stop hook 强制执行
构建 集成问题 验收命令里包含构建
截图对比 UI 改动 Claude in Chrome 打开页面截图，与设计稿逐项对比
输出比对 脚本、数据处理 准备 fixture，用 diff 比较期望输出与实际输出

几个具体写法：

  • 把验收写成可执行的：「实现 validateEmail，user@example.com 返回 true，user@.com 返回 false，写成测试并运行」，而不是「实现邮箱校验」。
  • 要证据而不是结论：要求贴出运行的命令和输出原文。看证据比你自己再跑一遍快，也适用于你没盯着的会话。
  • UI 改动用浏览器闭环：Claude in Chrome 从 2.0.72 起以 Beta 提供，需要安装 Chrome 扩展，用 claude --chrome 启动或在会话里执行 /chrome 连接。之后可以让 Claude 打开本地页面、截图、读控制台报错，再对照设计稿修改。
  • 修根因而不是压症状：贴出构建报错时加一句「修复根因，不要通过跳过检查或放宽类型让构建通过」。

提示词里的要求可能被遗忘，真正的强制靠 Stop hook，见下文「Hooks 做质量门禁」。

CLAUDE.md 与 .claude/rules：写给模型的操作手册

CLAUDE.md 在每次会话开始时载入上下文，每一行都在持续消耗 token 和注意力。写法原则：

  1. 短：每一行都问一句「删掉它，Claude 会犯错吗」，不会就删。文件越长，规则越容易被忽略。
  2. 可执行：写命令、路径和具体约束，不写形容词。「提交前运行 pnpm test」而不是「注意测试」；「API handler 放在 src/api/handlers/」而不是「保持结构清晰」。
  3. 只写代码里推断不出来的：构建与测试命令、与默认习惯不同的风格约定、分支与 PR 规范、环境变量要求、踩过的坑。语言通用规范、逐文件的目录说明都不必写。
  4. 偶尔才用的流程不放这里：发版、数据修复这类流程做成 Skill，按需加载，不占常驻上下文。

其他要点：

  • 层级：~/.claude/CLAUDE.md 放个人偏好，项目根目录的 CLAUDE.md 提交进仓库给团队共享，子目录里的 CLAUDE.md 在 Claude 处理该目录文件时按需加载。
  • 导入：用 @docs/git-workflow.md 这样的语法引用其他文件，避免把同一份内容复制两处。
  • 起步：/init 根据仓库结构生成初稿，然后大刀阔斧地删；/memory 打开编辑。2.0.70 起去掉了 # 快捷记忆，需要补充规则时直接让 Claude 修改 CLAUDE.md。
  • auto memory：2.1.59 起 Claude 会自动把有用的上下文存为 auto memory，同样用 /memory 管理。它是 Claude 自己的笔记，团队约定仍应写进受版本控制的 CLAUDE.md。
  • CI 注意：带 paths 的条件规则和子目录 CLAUDE.md 在 -p 模式下不加载的问题，2.1.69 才修复，CI 里使用的版本不要低于它。

最重要的一条边界：CLAUDE.md 是上下文，不是强制配置。「永远不要修改 lockfile」写在 CLAUDE.md 里，大多数时候有效；写成 PreToolUse hook，就每次都有效。

Checkpoints 与 /rewind：边界在哪里

2.0.0（2025-09-29）起，每次你发出提示都会自动创建一个检查点。/rewind 或在输入框为空时连按两次 Esc 打开回退菜单，可以只恢复代码、只恢复对话或两者都恢复；2.1.32 起还可以「从这里开始摘要」，把某个位置之后的冗长对话压缩掉而保留前面的指令。检查点随会话保存，恢复会话后依然可用，默认和会话记录一起在 30 天后清理，由 cleanupPeriodDays 控制。

它能回滚什么、不能回滚什么，必须心里有数：

变更来源 能否回滚 说明
Claude 用编辑工具修改的文件 能 检查点的设计目标
Bash 命令造成的文件变化 不能 rm、mv、代码生成器、脚本写出的文件都不追踪
你在编辑器里手工改的内容 不能 外部修改不追踪
其他并行会话的修改 不能 只追踪当前会话
数据库迁移、已发出的 HTTP 请求、消息通知 不能 外部副作用，回退代码不会撤销它们
git commit、git push、部署 不能 需要用 git 或部署系统自己的回滚

由此得出三条做法：

  • 有外部副作用的步骤，例如跑迁移、调用生产接口、推送，单独确认、单独执行，不要混在一大段自动操作里。
  • 高风险改动开始前先提交一次，把 git 当作真正的安全网，检查点只是会话内的快速撤销。
  • 「试两种方案」用检查点很方便：方案 A 不行就回退到分叉点，再让 Claude 试方案 B。

Hooks 做质量门禁

Hooks 是在固定生命周期节点运行的 shell 命令，结果不取决于模型是否记得规则。退出码的语义：0 表示通过；2 表示阻断，stderr 会反馈给 Claude；其他非零值是非阻断错误，只提示给你。

节点 典型用途 设计原则
PostToolUse，匹配 Edit|Write 格式化、快速 lint 必须快，每次编辑都会触发
PreToolUse，匹配 Edit|Write 保护 lockfile、迁移历史、.env 以退出码 2 阻断并说明原因
PreToolUse，匹配 Bash 拦截危险命令 规则宁窄勿宽，误拦会打断正常工作
Stop 类型检查与受影响目录的测试 防止「看起来完成」
Notification 桌面通知 长任务等你输入时提醒

worktree：多会话并行

一个会话在跑长任务时，你可以在另一个 worktree 里开第二个会话做别的事。2.1.49 起 claude --worktree <名字>（简写 -w）会在 .claude/worktrees/<名字>/ 创建工作树和 worktree-<名字> 分支并在其中启动；2.1.63 起同一仓库的各个 worktree 共享项目配置与 auto memory。

常见的并行节奏：

  • 一个会话实现功能，另一个会话在独立 worktree 里为同一功能补测试或做评审，互不踩文件。
  • 同一个问题的两种方案各开一个 worktree，最后比较 diff 再决定。
  • 2.1.63 新增的 /batch <指令> 适合大范围的机械性改动：它先调研并把工作拆成若干独立单元，你批准计划后，每个单元由一个后台子代理在独立 worktree 里实现并跑测试。

每个新 worktree 都是干净检出，需要重新安装依赖、准备被 gitignore 掉的本地配置；开发服务器端口和测试数据库是共享的，需要错开。子代理的 isolation: worktree、Agent Teams 的文件归属等更细的编排，见本系列上一篇《Claude Code 多智能体编排：从子代理到 Agent Teams》。

上下文管理

上下文窗口是会话里最稀缺的资源，被无关内容占满之后，模型对早期指令的遵循会明显变差。

手段 什么时候用
/context 看上下文被什么占用：系统提示、MCP 工具定义、CLAUDE.md、对话
/clear 切换到不相关的任务之前；同一问题纠正两次仍失败时
/compact <保留重点> 同一任务还要继续，但历史太长，例如 /compact 保留接口设计决定和未通过的测试
rewind 中的「从这里开始摘要」 只压缩某段冗长的调试过程，保留前面的需求与约束
子代理 跑全量测试只报失败项、全仓搜索只报位置，冗长输出留在子代理里
/rename 加 /resume 清空前先给会话命名，之后可以回来继续

另外两个容易被忽略的占用源：MCP 工具定义（2.1.7 起，工具描述超过上下文 10% 时会自动延迟加载，但用不到的服务器仍应关掉），以及膨胀的 CLAUDE.md。

非交互 -p 与 CI

claude -p 以非交互方式执行一次任务，适合脚本和 CI。常用参数：

参数 作用
--output-format json 或 stream-json 机器可读输出；json 结果中包含 total_cost_usd

--append-system-prompt 在默认系统提示后追加约束

/loop：会话内定时任务

2.1.71（2026-03-06）新增 /loop，在当前会话里按固定间隔重复执行一段提示或一个斜杠命令：

背后是会话内的 cron 调度工具（CronCreate、CronList、CronDelete），也可以直接用自然语言让 Claude 列出或取消已有任务。第二行示范的是把一个自定义斜杠命令放进循环。需要立即停掉所有定时任务时，设置 CLAUDE_CODE_DISABLE_CRON=1（2.1.72）。

它的边界很清楚：任务属于当前会话，机器要开着、会话要开着，退出就停止；每次触发都是一轮完整的模型调用，间隔设得太密就是在烧 token。它适合「接下来一小时盯着 CI 和评审意见」这类临时轮询，不适合替代真正的定时作业，后者应该交给 cron 或 CI 的定时触发。

新仓库第一天：落地清单

步骤 做法 为什么
1 /init 生成 CLAUDE.md，删到只剩命令、约定和已知坑 每个会话都知道怎么构建、怎么测试
2 在 CLAUDE.md 写明最快的验证命令：单测、类型检查、lint 验证闭环的前提是 Claude 知道怎么验
3 .claude/settings.json 放行测试和只读 git 命令，拒绝读取 .env 与 git push 减少打断，同时守住底线
4 加 PostToolUse 格式化 hook 格式问题不再占用对话轮次
5 加 PreToolUse 保护文件 hook lockfile、已有迁移不会被顺手改掉
6 加 Stop 门禁 hook，先只跑类型检查，稳定后再加测试 挡住「看起来完成」，又不至于一开始就拖慢每一轮
7 前后端约定拆进 .claude/rules/，用 paths 限定 只在相关文件被读取时加载，互不干扰
8 .gitignore 加入 .claude/settings.local.json 和 .claude/worktrees/ 个人配置与临时工作树不会被误提交
9 选一个真实的小任务，完整走一遍探索、计划、编码、验证、提交 在真实任务上暴露 CLAUDE.md 缺什么
10 任务结束时让 Claude 把这次踩到的坑补进 CLAUDE.md，你来审核 规则来自真实失败，而不是想象
11 流程稳定一两周后再用 /install-github-app 接入 CI 先让本地约定收敛，再自动化，避免把不成熟的规则放大到每个 PR

2026-09 补记：半年后的变化

  • Auto mode 成为默认：Auto mode 在 2026-03-24 以研究预览推出，由一个独立的分类器模型在执行前审查操作，替代大部分权限确认。2026-08-14 起对 Pro、Max、Team 计划默认开启；2.1.283（09-25）起成为所有计划和提供方下交互式终端与 VS Code 会话的内置起始模式。权限策略建议：deny 规则继续保留，Auto mode 下它们照样生效；需要每次都问你的操作写成显式的 ask 规则，按当前文档它们仍会强制弹出确认；对接触生产凭据或部署脚本的仓库，在项目 settings 里用 permissions.defaultMode 固定为 default 或 acceptEdits；组织层面可以在托管设置里把 permissions.disableAutoMode 设为 "disable"。另外，Auto mode 下 Claude 会更多地直接执行 Bash，而 Bash 造成的改动不在检查点覆盖范围内，高频提交就更重要了。
  • /goal：2.1.139（2026-05-11）加入。设定一个完成条件后，每轮结束由一个小而快的模型判断条件是否满足，不满足就继续下一轮，可在交互、-p 和 Remote Control 中使用。它适合「所有调用点编译通过且测试全绿」这类可验证的终态，和 Stop hook 门禁互补：前者判断任务整体是否达成，后者保证每一轮都守住底线。
  • Routines：2026-04-14 推出，研究预览。它是保存下来的一份配置（提示词、仓库、连接器），在云端基础设施上运行，可以定时、通过 API 调用或由 GitHub 事件触发，CLI 里用 /schedule 创建，最小间隔 1 小时。和 /loop 的分工是：/loop 依赖本机和会话一直开着，适合临时轮询；Routines 不依赖你的电脑，适合每晚巡检、定期整理 issue 这类长期任务。
  • Remote Control：claude remote-control 在 2026-02-23（2.1.51）就已加入，正文没有展开。会话仍在本机运行，文件系统、MCP 与项目配置都留在本地，你可以从 claude.ai/code 或手机 App 查看和继续对话，适合长任务中途离开电脑的场景。电脑必须保持开机，claude 进程要一直运行。
  • AGENTS.md 支持：2.1.277（2026-09-18）起，项目里没有 CLAUDE.md 时，Claude Code 会改为读取 AGENTS.md；两者同时存在时默认只读 CLAUDE.md，可在 /config 的 Project instructions 中调整。对清单第 1 步的影响：如果团队还在用其他 coding agent，把通用约定写进 AGENTS.md，CLAUDE.md 只放 Claude 专属的部分，并用 @AGENTS.md 导入通用内容，避免两份文件逐渐分叉。
