重要区分：并非所有”Agent”都需要 LLM。表中 4 个职能体不含 LLM（Router、Skill、Tool、部分 System Agent 能力）。把它们称为 Agent 是因为它们有自主策略，但实现上是策略引擎。混淆这一点会导致把简单路由做成大模型调用，延迟与成本双输。

2. 三类核心 Agent 的职责边界

2.1 System Agent（端侧总控）

维度 内容
唯一性 单例，与车机同生命周期
核心职责 会话所有权、落点决策、User Agents 生命周期管理、能力权限代理、端云链路管理、结果仲裁、断网缓冲
不做什么 不做业务逻辑、不直接调用大模型、不承载人设
状态 有状态（会话表、待同步队列、能力清单版本）
失败影响 端侧全部 AI 能力不可用 → 必须进程守护 + 5 s 内自恢复 + 会话可重放

为什么必须有 System Agent：若 User Agents 各自直连云端，则端侧限流、权限、埋点、落点决策全部旁路（违反 P2）。System Agent 在端侧扮演”端内网关 + 调度器”双重角色。

2.2 User Agents（端侧场景智能体）

维度 内容
数量 多实例，动态装载
核心职责 场景化多轮对话、人设与语气、场景内任务执行
约束 不可直连云、不可直接调用车控能力、必须声明终止条件
状态 会话内有状态，状态由 System Agent 托管（便于崩溃恢复）
失败影响 局部场景不可用

termination_conditions 是必填项而非可选项。没有终止条件的 Agent 会在异常输入下无限循环，端侧表现为算力占满、云端表现为账单飙升。

2.3 Cloud Agents（云端业务智能体）

维度 内容
数量 每业务域一个或多个，独立部署
核心职责 ReAct 多轮推理、工具编排、长任务执行、流式输出
状态 无状态服务 + 外置状态（Checkpoint 存储）
隔离 独立 Deployment、独立配额、独立 SLO、独立熔断
失败影响 单业务域不可用，其他域不受影响

为什么每 Agent 独立部署：AI Agent 的资源消耗方差极大（一个长任务 Agent 可能占用 10 倍于问答 Agent 的资源）。混部会导致互相拖垮。独立部署使故障与成本都可隔离归因。

3.1 生命周期各阶段的治理要求

阶段 治理要求 门禁
注册 描述完整、≥10 正例 + ≥5 反例、Schema 合规、权限最小化 自动校验 + 人工审核
发布 通过回归评测集、灰度计划明确、回滚方案就绪 评测门禁（阻断式）
灰度 观察窗口内异常率、满意度、成本三项达标 自动扩量或自动回滚
运行 预算强制、轨迹上报、SLO 监控 超预算熔断
弃用 Sunset 日期公示、流量迁移路径明确 流量归零才可下线

最常缺失的是”弃用”阶段。企业平台上线一年后往往积累几十个无人维护的 Agent，既占资源又是安全隐患。注册时即应要求声明 owner 与复核周期。

4. 通信协议

通信路径 协议 特性 承载组件
User Agent → System Agent 端内 IPC / 进程内调用 低延迟、无网络 端侧运行时
System Agent → 云 HTTPS + SSE（经 Agent 网关） 流式、单向推送、可续传 Agent 网关
端 Agent ↔ 云 Agent A2A（经 Agent 网关桥接） 跨域寻址、任务与结果传递 Agent 网关
Planner → Cloud Agent 内部 RPC（gRPC）+ 流式 低延迟、强类型 服务网格
Cloud Agent → 工具 MCP / REST 标准化工具接入 能力中心适配
Cloud Agent → 模型 HTTP（经 LLM 网关） 流式、语义化意图 LLM 网关
Agent → 记忆/知识 内部 RPC 读多写少 基础能力层
端云状态同步 mTLS 长连接/批量 HTTP 幂等、断点续传 双向认证网关

4.1 A2A 桥接的安全模型

sequenceDiagram
    autonumber
    participant EA as 端侧 Agent
    participant BR as A2A 桥接（网关）
    participant AUTH as 权限服务
    participant CA as 云端 Agent
    EA->>BR: A2A 请求（目标 Agent + 任务 + 自身身份）
    BR->>AUTH: 校验：调用方身份 + 目标白名单 + 权限交集
    AUTH-->>BR: 允许（有效权限集 = 调用方∩目标∩用户授权）
    BR->>CA: 转发（附有效权限集，非原始身份）
    Note over BR,CA: 关键：不传递调用方身份，只传递计算后的有效权限集
    CA->>CA: 在有效权限集内执行
    CA-->>BR: 结果
    BR-->>EA: 结果

A2A 最危险的实现方式是”身份透传”：Agent A 把自己的令牌传给 Agent B，B 用 A 的身份调用高权限能力。正确做法是桥接层计算权限交集并下发有效权限集，每跳独立鉴权。

    end
    subgraph M4["模式四：端云互补"]

    end
模式 适用场景 优点 代价
层级委派 主链路（本架构选择） 职责清晰、可控、易归因 层级延迟累积
并行竞速 意图置信度中等（0.6–0.85） 降低误判损失、延迟取最优 成本翻倍（可用小模型缓解）
管道串联 复杂研究型任务 各步可独立优化与评测 总延迟长，需流式反馈进度
端云互补 长回答场景 首字极快（端侧）+ 质量保障（云端） 需处理两段内容的衔接自然度

不推荐的模式：自由多 Agent 讨论（多个 Agent 互相对话直到收敛）。在企业生产环境中，它的成本不可预测、延迟不可控、结果不可复现。适合研究与创意场景，不适合承载 SLA。

6. 状态管理

6.1 状态分类与存放位置

状态类型 内容 存放 生命周期 丢失影响
会话状态 当前轮次、已用预算、待确认动作 Redis（云）/ 内存+WAL（端） 会话周期 会话需重启
执行状态 ReAct 轨迹、已调工具、中间结论 Checkpoint 存储（PG） 任务周期 长任务需重跑
短期记忆 最近 N 轮对话与摘要 Redis 会话周期 失去上下文连贯
长期记忆 跨会话事实 PG + 向量库 长期（带 TTL） 失去个性化
Agent 配置 清单、人设、预算 注册中心 + 本地缓存 版本周期 用快照兜底
端侧待同步 记忆变更、埋点缓冲 本地持久队列 至同步成功 数据丢失

6.2 Checkpoint 设计（长任务）

sequenceDiagram
    autonumber
    participant CA as Cloud Agent
    participant CP as Checkpoint 存储
    CA->>CP: 写入初始状态（task_id, context_ref, budget）
    loop 每步执行后
        CA->>CP: 增量写入（step_n: thought/action/observation）
    end
    Note over CA: 进程崩溃 / 扩缩容驱逐
    CA->>CP: 新实例按 task_id 恢复
    CP-->>CA: 完整轨迹
    CA->>CA: 从最后一步继续（跳过已完成的副作用操作）

恢复的难点是副作用幂等。若第 3 步已经”提交了订单”，恢复时不能重复提交。因此所有有副作用的工具调用必须记录幂等键，恢复时先查询状态而非直接重试。

7. 上下文管理

7.1 上下文的四个来源与优先级

flowchart LR
    S["系统指令<br/>优先级 1<br/>不可裁剪"] --> Q["用户当前问题<br/>优先级 2<br/>不可裁剪"]
    Q --> K["知识片段<br/>优先级 3<br/>可裁剪至 Top-3"]
    K --> M["记忆<br/>优先级 4<br/>可裁剪至高置信项"]
    M --> P["画像<br/>优先级 5<br/>可全部裁剪"]
    P --> T["工具描述<br/>优先级 3（若需工具）<br/>可用渐进式披露压缩"]

7.2 上下文管理的五条实践规则

规则 说明 反例后果
硬预算 总 Token 上限固定，超出必须裁剪或压缩 上下文溢出报错或成本失控
优先级固定 裁剪顺序写死在代码中，不随实现变化 同问题不同时刻表现不一致，无法复现
稳定内容前置 系统指令与工具描述在前，用户问题在后 前缀缓存失效，成本与延迟上升
来源可追溯 每段上下文标记来源与版本 答错时无法定位是知识错还是记忆错
压缩优于裁剪 超预算时先压缩（结构化摘要），最后才丢弃 关键信息被静默丢弃

7.3 多轮上下文演化

flowchart TB
    T1["轮次 1<br/>完整上下文"] --> T2["轮次 2<br/>+ 轮1摘要"]
    T2 --> T3["轮次 3<br/>+ 轮1-2摘要"]
    T3 --> TN["轮次 N<br/>滚动摘要 + 最近3轮原文"]
    TN --> CMP{"超预算?"}
    CMP -->|是| SUM["触发二次压缩<br/>摘要的摘要"]
    CMP -->|否| GO["继续"]
    SUM --> RISK["风险：实体与数字丢失"]
    RISK --> FIX["缓解：实体表单独维护<br/>不参与摘要压缩"]

实体表是被广泛忽略的关键设计。摘要压缩最容易丢失的正是具体实体与数字（车型、日期、金额、地点）。解决办法是维护一个结构化实体表随上下文传递，它不参与自然语言摘要，因此不会被压缩丢失。

8. 记忆机制在 Agent 中的应用

Agent 使用的记忆类型 访问模式 命名空间隔离
System Agent 端侧短期 + 端侧偏好 读写 系统级
User Agent 场景记忆 + 用户偏好切片 读多写少 按 Agent 隔离
Cloud Agent 短期 + 长期 + 画像 读多写少（写走异步） 按 Agent 隔离 + 共享区
Memory Agent 全部 读写（唯一写权威） 全局

8.1 命名空间隔离规则

flowchart TB
    U["用户记忆空间"] --> SH["共享区<br/>基础事实、通用偏好<br/>所有 Agent 可读"]
    U --> NS1["Agent A 私有区<br/>仅 A 可读写"]
    U --> NS2["Agent B 私有区<br/>仅 B 可读写"]
    U --> PRI["隐私区<br/>不出端、不进训练集"]
    MA["Memory Agent"] -->|"唯一写权威"| SH
    NS1 -.->|"经审核可提升"| SH

为什么需要私有区：若所有 Agent 共享全部记忆，会出现隐私越界（娱乐 Agent 读到用户在其他场景的敏感表达），且记忆空间会被无关内容污染。私有区内容经审核后可”提升”到共享区。

9. 任务编排与预算控制

9.1 三重预算

预算 默认值（推断设计） 超限动作 目的
最大轮次 对话型 4 / 任务型 8 强制输出已有结论 防无限循环
最大工具调用 6 拒绝新调用并告知模型 防工具滥用
最大 Token 8k（单次任务累计） 中止并返回部分结果 成本可控
最大耗时 对话型 10 s / 任务型 60 s 中止并说明 用户体验

9.2 预算耗尽的正确处理

flowchart LR
    B["预算耗尽"] --> W1["❌ 错误：静默返回空结果"]
    B --> W2["❌ 错误：假装完成"]
    B --> R1["✅ 正确：返回已有部分结论"]
    R1 --> R2["✅ 明确说明未完成的部分"]
    R2 --> R3["✅ 提供下一步选项（继续/换方式）"]
    R3 --> R4["✅ 上报 budget_exhausted 埋点"]

9.3 失控防护（Runaway Protection）

失控形态 检测 防护
重复调用同一工具同一参数 调用指纹去重计数 3 次相同则强制中止
思考不收敛（轮次增加但无进展） 连续轮次无新信息增量 相似度检测 + 中止
上下文持续膨胀 每轮 Token 增量监控 超阈值触发压缩或中止
Agent 间循环调用（A→B→A） A2A 调用链深度与环检测 深度上限 3 + 环检测拒绝
成本异常 单会话成本 vs 分位数 超 P99 × 3 自动熔断并告警

成本熔断是必备而非可选。一个进入循环的 Agent 在无防护情况下，单会话可产生数百次模型调用。必须在网关侧设置单会话硬上限。

10. Agent 评测

评测维度 指标 方法
意图路由准确率 落对 Agent 的比例 标注集 + 混淆矩阵
工具选择准确率 选对工具的比例 标注集（含”不该用工具”的负例）
任务完成率 端到端达成用户目标 人工标注 + 隐式信号（是否重问）
轮次效率 平均轮次 / 最优轮次 与人工最优路径对比
成本效率 单任务 Token 数 分布监控
稳定性 同输入多次运行结果一致性 重复运行差异率
安全性 越权尝试、注入抵抗 红队测试集

稳定性常被忽略但极其重要。同一问题连续三次得到三种不同答案，用户信任会迅速崩塌。降低温度、固定工具集、结构化输出都可提升稳定性。

11. 风险与最佳实践总结

风险 最佳实践
Agent 数量膨胀无人维护 注册时必填 owner 与复核周期；无流量 Agent 自动进入弃用流程
端侧 Agent 直连云导致治理旁路 System Agent 强制代理；网关侧校验调用来源
A2A 越权 权限交集计算 + 每跳鉴权 + 白名单 + 深度上限
