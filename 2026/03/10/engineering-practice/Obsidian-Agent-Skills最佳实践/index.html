让 AI Agent 操作 Obsidian：obsidian-skills 与 Obsidian CLI 实践

obsidian-skills 教 Agent 写 Obsidian 格式，Obsidian CLI 让 Agent 调用运行中的 Obsidian。

Flywhl 12 分钟 更新于 2026.09 #Claude Code#Agent Skills#工程效率

先读结论

  1. 技能只是说明书，真正的能力来自两条通道：直接读写文件，或通过 Obsidian CLI 让 Obsidian 自己执行。
  2. 新建笔记直接写文件；搜索、反链、移动、改名、查询 Bases 走 CLI，因为只有 Obsidian 知道链接关系。
  3. 让 Agent 只在 inbox 新建、只追加日记、不碰模板，并用权限规则兜底；但前缀匹配的 deny 规则拦不住所有写法，删除保护最终要靠回收站和 git。
  4. obsidian-cli 技能示例里的 silent 在 1.12.2 之后已无必要，CLI 默认就不打开文件。

先分清两样东西

“让 Agent 操作 Obsidian”常被混成一件事，实际上是两层：

  • obsidian-skills（kepano/obsidian-skills，2026 年 1 月开源，维护者是 Obsidian 的 Steph Ango）：一组遵循 Agent Skills 规范的 SKILL.md，告诉 Agent Obsidian 的文件格式怎么写、CLI 怎么调用。它本身不提供任何能力，只是说明书。
  • Obsidian CLI：Obsidian 1.12.0 抢先体验版（2026-02-10）引入，1.12.4 公开版（2026-02-27）正式发布。它把命令发给正在运行的 Obsidian 应用执行，能用到 Obsidian 的链接索引、模板、Bases 查询引擎。

截至本文写作时，仓库里有五个技能：

技能 教会 Agent 什么 外部依赖 主要用在
obsidian-markdown 双链、嵌入、Callout、Properties 等 Obsidian 风格 Markdown 无 写任何笔记
obsidian-bases .base 文件的过滤、公式、视图、汇总语法 无 建看板、做查询
json-canvas .canvas 文件的节点、连线、分组 无 画关系图
obsidian-cli CLI 语法、文件与仓库定位规则、插件开发调试 Obsidian 1.12+，且应用在运行 搜索、反链、移动、查询
defuddle 用 Defuddle 把网页转成干净的 Markdown npm install -g defuddle 剪藏

两条通道的分工决定了后面所有工作流怎么设计：

操作 直接写文件 走 CLI 理由
新建笔记 推荐 可以 没有链接要维护；长正文用 content= 要把换行转义成 \n，不如直接写文件
搜索、反链、未解析链接、孤立笔记 只能 grep，别名和嵌入识别不了 推荐 Obsidian 有完整的链接索引
移动、改名 不要 必须 shell 里 mv 后，指向它的双链全部失效；CLI 的 move/rename 会按”自动更新内部链接”设置修正链接
删除 不要 慎用 CLI 的 delete 默认进回收站，rm 直接没了
查询 Bases 视图 自己解析 YAML 再筛选，结果不可靠 推荐 base:query 直接返回视图结果
Obsidian 没有运行时 可用 第一条命令会把 Obsidian 拉起来 批处理脚本要考虑启动时间

参数用 key=value，布尔开关直接写名字；file= 按双链规则解析（只写文件名），path= 是相对仓库根的精确路径。给 Agent 用时一律写 path=，避免同名笔记被解析到别处。多个仓库时 vault="名称" 必须放在第一个参数。

1.12.2 改了默认行为：命令默认静默执行、不打开文件，原来的 silent 参数被 open 取代，all 被 active 取代。obsidian-cli 技能的示例里仍然写着 silent，照抄不会带来好处，可以在规则文件里告诉 Agent 不要再加。

知识库结构约定

Agent 能不能稳定地干活，取决于知识库有没有它能读懂的约定。两种常见组织方式都可以：

方式 目录 适合
PARA 10-Projects、20-Areas、30-Resources、40-Archive 以项目推进为主，笔记有明确的生命周期
主题目录 Kubernetes/、数据库/、读书/ 以长期积累为主，主题边界稳定

边界：Agent 能写哪里

规则文件

仓库根目录的 CLAUDE.md（Codex 读 AGENTS.md）写清楚：

权限兜底

规则文件是给 Agent 看的，权限配置是给 Claude Code 执行的。.claude/settings.json：

/ 开头的路径相对于这份配置所在的项目根。eval 能在 Obsidian 里执行任意 JavaScript，一并禁掉。

这份配置有三个漏洞，必须清楚：

  1. Bash 规则是前缀匹配。 obsidian vault="Notes" delete path=… 不以 obsidian delete 开头，deny 拦不住。
  2. Read 规则管不住 CLI。 obsidian read path="Journal/…" 读的是 Obsidian 返回的内容，不经过文件读取工具；search 也会搜到 Journal 里的内容。
  3. CLI 能访问本机所有已注册的仓库。 把隐私内容挪到另一个仓库，并不能让它脱离 Agent 的访问范围。

所以权限配置只是减少误操作，不是安全边界。真正的兜底是：仓库纳入 git 或至少开启核心插件”文件恢复”（CLI 的 history 可列出版本），删除走回收站；高度隐私的内容不放进这台机器上 Agent 能调用的 Obsidian 里。

会议纪要入库

目标：把转写稿或速记整理成结构化纪要，行动项可追踪，日记里留入口。技能：obsidian-markdown + obsidian-cli。

Agent 再直接编辑这个文件填正文：结论、决策、行动项。行动项统一写成任务，- [ ] 事项（负责人，截止日期），这样可以按文件列出：

如果要先看模板里的变量展开成什么样，用 obsidian template:read name="Meeting" resolve title="2026-03-10 架构周会"。

边界：纪要里点名的人和事，转写稿里常有不该落盘的内容，Agent 输出后人要过一遍再移出 inbox。

按 Bases 生成周报

目标：每周五用固定的查询得到本周变化，Agent 据此写周报。技能：obsidian-bases + obsidian-cli。

Bases/Weekly.base：

format=paths 只输出路径，Agent 按需逐篇 obsidian read path=… 读正文，写成 00-Inbox/周报 2026-W11.md。好处是”哪些笔记算本周”由 .base 决定而不是由 Agent 临场判断，每周结果可复现；调整口径只改 .base，在 Obsidian 里打开就能直接看到筛选结果。

边界：file.mtime 是文件修改时间，同步工具或批量改属性都会刷新它。口径要求严格时，改用笔记里自己维护的日期属性过滤。

批量重构双链

目标：合并重复概念（比如 K8s 和 Kubernetes 两篇）、修复断链，而不留下一地失效链接。技能：obsidian-cli + obsidian-markdown。

先确认设置 → 文件与链接 → 自动更新内部链接已打开，再给仓库打快照：

盘点：

执行分三步，每一步都先让 Agent 列清单、人确认后再动手：

  1. 把 K8s.md 独有的内容合并进 Kubernetes.md，并把 K8s 加进后者的 aliases 属性，以后输入 [[K8s 时链接补全仍能找到它。
  2. 逐篇把 [[K8s]] 改成 [[Kubernetes|K8s]]，保留原来的显示文字。
  3. 旧笔记不删，移走：obsidian move path="30-Resources/K8s.md" to="40-Archive/"。

验证：

只是改名的话不需要这么多步骤：obsidian rename path="30-Resources/K8s.md" name="Kubernetes" 会同步修正所有链接，前提同样是那个设置已打开。

风险清单

风险 典型场景 缓解
同步冲突 Agent 改的文件正开在编辑器里，或另一台设备同时在改，同步后内容被覆盖或出现冲突副本 Agent 只在 inbox 新建文件，不改已有文件；批量重构前暂停同步，做完确认再恢复
断链 在 shell 里 mv、改名 规则文件禁止 mv，移动改名只走 CLI
误删 rm、delete permanent deny 规则 + 回收站 + git 快照；deny 有前缀绕过，不能只依赖它
模板被改坏 Agent 把模板当普通笔记”顺手优化” Edit(/Templates/**) 进 deny，规则文件写明只读
隐私外泄 读到日记、病历、账号类笔记并发给模型 规则文件划出禁区；真正敏感的内容不进 Agent 能访问的 Obsidian
批量操作失控 一次改几百个文件，出错后难以定位 每步先出清单再执行；执行前后对比 unresolved total 和 git diff --stat

总结

obsidian-skills 解决”Agent 会不会写 Obsidian 的格式”，Obsidian CLI 解决”Agent 能不能用 Obsidian 自己的能力”。实践中的分工很简单：新建直接写文件，涉及链接关系的一律走 CLI。真正决定效果的是知识库的约定：固定的 inbox、固定的属性、用 Bases 固化查询口径，以及一份写清楚读写边界的规则文件。

2026-09 补记：半年来的变化

obsidian-skills 仓库：

  • 2026-09-10 新增第六个技能 knap：用 Knap CLI（npm install -g knap，需要 Node.js 20+）把 JSON 或 CSV 数据按模板渲染成 Markdown，支持批量生成文件，也能把 Defuddle 的输出套进笔记模板。剪藏工作流里”Agent 按约定拼属性和正文”的那一步，可以改由模板固定下来。
  • README 补充了 npx skills add https://github.com/kepano/obsidian-skills 的 https 写法，并把 defuddle 链接指向合并后的 defuddle 主仓库（npm 上的 defuddle 包自 0.8.0 起自带命令行）。
  • obsidian-cli 技能的示例截至 2026-09 仍写着 silent，规则文件里那条提醒继续有用。

Obsidian：

  • 1.12.7（2026-03-23 公开版）为 CLI 附带了独立的可执行文件，不再通过 Electron 主程序调用，终端交互明显更快，需要重新下载安装包。现在的官方文档要求安装包版本 1.12.7 及以上；macOS 上注册 CLI 会在 /usr/local/bin/obsidian 建一个指向应用内 obsidian-cli 的符号链接。
  • 1.13 公开版（2026-07-30）的更新说明里，CLI 只有一条修复（flatpak 安装），本文用到的命令没有行为变化。
  • 1.14 抢先体验版（2026-09）给 Bases 加了看板布局；按 file.folder 分组时，拖动卡片会把笔记移到对应文件夹。用它来整理 inbox 很顺手，但要知道拖动就是在移动文件。
