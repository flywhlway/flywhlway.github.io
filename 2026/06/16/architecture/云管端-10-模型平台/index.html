1.1 核心设计原则

原则 含义 实现
意图化调用 业务声明 model_intent，不指定模型名 网关维护意图→模型映射表，可热更新
能力矩阵驱动 模型选择基于能力矩阵而非硬编码 模型注册时声明能力、成本、延迟、上下文长度
分级用模 任务复杂度决定模型档位 分类用 SLM、闲聊用中档、复杂推理用旗舰
多源冗余 同一能力至少两个可用后端 自建 + 外部，或两家外部供应商
成本可归因 每次调用带成本标签 cost_tag（业务/Agent/场景/用户群）必填

2. 模型分层与选型

2.1 模型能力矩阵（推断设计模板）

model_intent 能力要求 推荐档位 上下文 延迟目标 相对成本
classify.fast 意图分类 SLM / 判别模型 2k ≤120 ms 1×
extract.structured 结构化抽取（记忆/槽位） SLM 8k ≤300 ms 1×
compress.context 上下文压缩 SLM 32k ≤400 ms 2×
rewrite.query 查询改写 SLM 2k ≤60 ms 1×
chat.short 短对话、闲聊 中档 LLM 8k 首字≤250 ms 8×
chat.long 复杂问答、多轮 旗舰 LLM 128k 首字≤320 ms 30×
reason.complex 多步推理、规划 旗舰推理模型 128k 首字≤600 ms 60×
tool.call 函数调用 函数调用稳定的模型 32k 首字≤300 ms 20×
vision.describe 图像理解 VLM 32k + 图像 ≤800 ms 25×
embed.text 文本向量化 Embedding 模型 512 ≤30 ms 0.1×
rerank.pairs 相关性重排 Cross-Encoder 512×50 ≤50 ms 0.3×
guard.classify 内容安全判定 安全专用模型 4k ≤35 ms 0.5×

成本列是最重要的一列。chat.long 的单位成本是 classify.fast 的 30 倍。多数平台把 60%+ 的请求错误地送给了最贵的档位——分级用模是最直接的降本手段，通常一次性降低 40%+ 成本且用户无感。

2.2 三类模型的定位差异

维度 LLM（云端旗舰） SLM（小模型） VLM（多模态）
主战场 复杂推理、长上下文、工具编排 分类、抽取、压缩、改写、端侧 图像理解、多模态指代
部署 外部 API + 自建旗舰 自建（成本低）+ 端侧 外部 API 为主
关键指标 推理质量、函数调用稳定性、长上下文有效性 延迟、成本、量化后精度 图像分辨率、OCR 能力
主要风险 成本、供应商依赖 能力上限 延迟高、成本高
优化重点 缓存、路由、上下文压缩 蒸馏、量化、多任务复用 图像预处理、按需触发

2.3 端侧小模型选型要点

要点 说明
一基座多任务 一个小基座 + 多 LoRA/适配器，而非多个独立模型（内存节省显著）
量化档位 int4 通常够用于分类/抽取；生成任务建议 int8
分档部署 按车机算力等级下发不同尺寸（高配 3B、中配 1.5B、低配仅分类模型）
Embedding 独立 Embedding 模型小且常驻，与生成模型分开管理
预热 冷启动首次推理延迟高，需常驻或预热
降载 车机主功能优先，AI 推理可被抢占降级

3.1 路由策略类型

策略 逻辑 适用 风险
静态映射 意图 → 固定模型 起步阶段 无法优化
成本优先 满足质量下限的最便宜模型 成本压力大 长尾质量下降
难度感知（推荐） 先用小模型预测难度，简单走小模型 成熟阶段 需难度预测准确
延迟优先 选当前 P95 最低的后端 交互敏感场景 可能选到质量较差模型
质量优先 评测得分最高 高价值场景 成本高
混合加权 上述加权组合 生产推荐 权重需调优

3.2 难度感知路由（Cascade 模式）

sequenceDiagram
    autonumber
    participant GW as 网关
    participant SM as 小模型
    participant LG as 旗舰模型
    GW->>SM: 先用小模型尝试（成本 1/30）
    SM-->>GW: 结果 + 自评置信度
    alt 置信度 ≥ 阈值
        GW-->>GW: 采用小模型结果（省 96% 成本）
    else 置信度 < 阈值
        GW->>LG: 升级到旗舰模型
        LG-->>GW: 结果
    end
指标 说明
小模型采纳率 目标 40–60%（视场景）
额外延迟 未采纳时增加小模型延迟（约 150 ms），需权衡
成本收益 采纳率 50% 时约省 45% 成本
适用场景 非流式或可容忍首字略慢的场景；流式交互场景不适用（会导致首字延迟翻倍）

流式交互场景不要用 Cascade。用户等待首字时，先跑一遍小模型再决定升级会让首字延迟从 320 ms 变成 470 ms+。Cascade 更适合离线批处理、记忆抽取、评测等非交互场景。

4. Fallback 与容错

4.1 降级链

flowchart TB
    A["主模型调用"] -->|"超时/5xx/限流"| B{"错误类型"}
    B -->|"限流 429"| C1["同供应商其他实例/区域"]
    B -->|"服务错误 5xx"| C2["切换备用供应商同档模型"]
    B -->|"超时"| C3["切换低延迟模型"]
    C1 & C2 & C3 -->|"仍失败"| D["降档至小模型"]
    D -->|"仍失败"| E["语义缓存近似回答<br/>阈值可放宽至 0.88"]
    E -->|"无缓存"| F["指令端侧 SLM 兜底"]
    F -->|"不可用"| G["显式失败 + 引导重试"]
    C1 & C2 & C3 & D & E & F & G --> H["降级埋点 + 告警 + 计入 SLO"]

4.2 熔断器配置（推断设计）

参数 建议值 说明
熔断粒度 供应商 × 模型 单模型故障不影响同供应商其他模型
错误率阈值 50%（滑动窗口 30 s）
最小请求数 20 避免低流量误熔断
熔断时长 30 s，指数递增至 300 s
半开探测 每次放行 5 个请求
超时设置 首字 5 s / 整体 60 s 首字超时更敏感
重试 仅对幂等且未开始流式输出的请求重试 1 次 已流式输出不可重试

重试的关键约束：一旦开始向用户流式输出，就不能重试（用户会看到内容突然重新开始）。因此重试窗口只在”首字返回前”。

5. 负载均衡

策略 是否适用 AI 场景 原因
轮询（Round Robin） ❌ 不适用 请求耗时方差极大（短问答 vs 128k 长上下文），轮询会造成严重不均
随机 ❌ 不适用 同上
最少未完成请求数 ✅ 推荐 自然适配耗时差异
按预估输出 Token 加权 ✅ 更优 需预估模型，实现复杂
一致性哈希（按会话） ⚠️ 特定场景 可提升前缀缓存命中，但会造成不均

5.1 自建推理集群的调度要点

flowchart LR
    Q["请求队列"] --> B["连续批处理<br/>Continuous Batching"]
    B --> P["Prefix Caching<br/>共享前缀复用"]
    P --> S["调度器<br/>按 SLA 分优先级队列"]
    S --> G1["GPU 实例 1"] & G2["GPU 实例 2"] & G3["GPU 实例 N"]
    S --> PRE["预热与常驻<br/>避免冷启动"]
要点 说明 收益
连续批处理 请求动态加入批次，无需等齐 吞吐提升数倍
Prefix Caching 相同前缀 KV 复用 首字延迟与算力双降
优先级队列 交互请求优先于批处理任务 保障交互 SLA
常驻预热 避免模型加载冷启动 消除长尾延迟
显存管理 合理设置最大批次与序列长度 避免 OOM

6. 缓存体系（四层）

flowchart TB
    R["请求"] --> L1{"L1 · 精确缓存<br/>完全相同的请求"}
    L1 -->|"命中"| H1["直接返回<br/>延迟 <5 ms"]
    L1 -->|"未命中"| L2{"L2 · 语义缓存<br/>向量相似度 ≥0.92"}
    L2 -->|"命中"| H2["返回缓存答案<br/>延迟 ~25 ms<br/>仍需过围栏"]
    L2 -->|"未命中"| L3["L3 · 前缀/KV 缓存<br/>推理引擎层"]
    L3 --> L4["L4 · Token 计量缓存<br/>成本统计与配额"]
    L3 --> INF["模型推理"]

6.1 L1 精确缓存

项 内容
键 Prompt 完整哈希 + 模型 + 参数（温度等）
命中率 5–10%（重复提问、重试）
TTL 短（分钟级），时效性意图不缓存
收益 延迟几乎为零，成本为零

6.2 L2 语义缓存（图示圈注核心）

项 内容
原理 查询向量化 → 向量库检索 → 相似度超阈值返回缓存答案
缓存键维度 语义向量 + 知识版本 + 车型/配置 + 语言 + 用户群 + Skill ID
相似度阈值 ≥ 0.92（宁高勿低）
命中率目标 ≥ 25%，问法收敛后可达 35%+
TTL 按意图类别设定（稳定知识 7 天，动态内容 bypass）
失效触发 知识版本变更、Embedding 版本变更、人工干预
注意 缓存答案仍必须过安全围栏（策略可能已变更）

收益量化（基于 01 文档 6.2 容量模型）：

命中率 节省推理算力 节省成本（相对） 平均延迟改善
10% 10% 10% -70 ms
25% 25% 25% -175 ms
35% 35% 35% -245 ms
50% 50% 50% -350 ms

语义缓存是本架构 ROI 最高的单项优化。每提升 5 个百分点命中率 ≈ 省 10% 推理算力预算。车载场景问法高度收敛（”怎么开空调””附近充电桩””续航多少”），是语义缓存的理想场景。

6.3 语义缓存的三个陷阱

陷阱 表现 解决
误命中 “A 车型续航” 命中 “B 车型续航” 的缓存 车型/配置必须进缓存键；阈值提高
时效性内容被缓存 缓存了”当前剩余电量” 意图分类标记时效性 → 强制 bypass
知识更新后缓存未失效 知识改了但仍返回旧答案 知识版本进缓存键 + 更新时主动失效

6.4 L3 前缀/KV 缓存

项 内容
原理 相同前缀的注意力 KV 复用，仅计算增量部分
前提 自建推理（vLLM Automatic Prefix Caching / SGLang RadixAttention）或供应商支持
零成本优化 Prompt 组织顺序：系统指令 → 工具描述 → 知识 → 记忆 → 用户问题
收益 首字延迟显著下降；自建场景算力节省明显

Prompt 顺序调整是”改几行代码换来大幅收益”的典型。把变化最少的内容放最前，前缀缓存命中率可从近乎为零提升到很高。这一优化不需要任何新组件。

6.5 L4 Token 计量与配额

项 内容
计量口径 以网关为唯一权威，禁止业务侧自报
归因维度 业务线 / Agent / Skill / 场景 / 用户群 / 模型 / 缓存命中
配额层级 全局 → 业务线 → Agent → 单会话
限流单位 Token/s + 并发数双维度（不用 QPS）
异常熔断 单会话 Token 超 P99×3 自动熔断
成本看板 日/周成本趋势 + Top 消耗方 + 单位业务成本

7. Prompt 与模型版本管理

flowchart LR
    P1["Prompt 模板<br/>版本化 · 纳入代码评审"] --> P2["与模型族绑定<br/>不同模型族模板不同"]
    P2 --> P3["灰度发布<br/>按流量比例"]
    P3 --> P4["评测门禁<br/>回归集必须通过"]
    P4 --> P5["上线 + 记录 prompt_version"]
    P5 --> P6["效果监控<br/>按 prompt_version 分组对比"]
    P6 -->|"劣化"| P7["快速回滚"]
要求 说明 不做的后果
Prompt 版本化 等同代码，进版本库与评审 线上效果波动无法归因
每次调用记录版本 prompt_version 埋点必填 无法按版本对比效果
模型-模板绑定 不同模型族的函数调用与格式约定不同 换模型后格式解析失败
灰度 + 门禁 变更必须过回归评测 一次改动全量劣化
快速回滚 配置级回滚，不需发版 故障时间拉长

7.1 模型上线流程

sequenceDiagram
    autonumber
    participant ALG as 算法团队
    participant MR as 模型注册中心
    participant EV as 评测
    participant GW as LLM 网关
    ALG->>MR: 注册模型（版本 + 能力声明 + 训练血缘）
    MR->>EV: 触发评测（回归集 + 盲测集）
    EV-->>MR: 评测报告（质量/延迟/成本）
    alt 达标
        MR->>GW: 注册到能力矩阵（初始权重 0）
        GW->>GW: 影子流量（复制请求不返回，仅对比）
        GW->>GW: 灰度 5% → 观察 → 50% → 100%
        GW->>GW: 保留上一版本 7 天备回滚
    else 不达标
        MR-->>ALG: 打回
    end

影子流量是模型上线的最佳前置手段：真实请求复制到新模型但不返回给用户，可在零风险下对比真实分布下的质量与延迟。这是评测集无法替代的（评测集永远无法覆盖真实长尾）。

8. 上下文长度管理

上下文档位 典型用途 成本影响 注意
2k 分类、改写 极低 够用
8k 短对话、抽取 低 主流场景
32k 多轮 + 工具 + 知识 中 需预算管理
128k+ 长文档分析 高 谨慎使用

长上下文不是”免费的记忆”。128k 上下文的成本与延迟远高于 8k，且”中间信息丢失”（lost-in-the-middle）现象使有效利用率下降。优先用检索与压缩，而非无脑塞长上下文。这是与”上下文预算硬约束”（01 文档 3.4）一致的判断。

10. 风险与治理

风险 影响 治理
网关单点 全平台模型能力不可用 多副本 + 多区域 + 无状态化 + 健康检查
供应商依赖 涨价/限流/停服 多源冗余 + 意图化调用（换模型为配置变更）
成本失控 账单超预算 分级用模 + 缓存 + 配额 + 会话熔断 + 成本看板
语义缓存误命中 答错且难发现 维度键完整 + 高阈值 + 命中样本抽检
模型换代效果劣化 用户感知下降 影子流量 + 灰度 + 回归门禁 + 快速回滚
长上下文滥用 成本与延迟双升、效果反降 上下文预算硬约束 + 压缩优先
端侧模型占用车机资源 主功能受影响 资源配额 + 分级降载 + 抢占策略
Prompt 无版本管理 效果波动无法归因 版本化 + 埋点 + 分组对比
流式已输出后重试 用户看到内容重来 重试窗口限定在首字前
自建集群显存 OOM 服务不可用 最大批次与序列长度限制 + 压测定容
