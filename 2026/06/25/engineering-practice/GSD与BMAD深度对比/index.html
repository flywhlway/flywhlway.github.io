1. 背景：为什么需要 SDD 框架

1.1 Vibe Coding 的致命缺陷

2025 年 2 月，Andrej Karpathy 提出了「Vibe Coding」的说法——开发者描述意图，AI 生成代码，人几乎不看就接受。这种模式在 Demo 和原型阶段效率惊人，但在真正的生产项目中会产生三类系统性缺陷：

上下文腐烂（Context Rot）：随着会话变长，AI 的输出质量明显下降。Chroma 在 2025 年发布的 Context Rot 技术报告测试了 18 个前沿模型，所有模型都在输入变长时出现性能退化。落到工程上，常见表现是：先开始「简洁化」、切角、遗漏需求，再往后出现幻觉、遗忘早期规格。GSD 把这件事做成了可监控的指标：上下文监控钩子在剩余上下文 ≤35% 时告警、≤25% 时要求停手保存状态；/gsd-health --context 在占用达到 60% 时提示、70% 时判为危险。

跨会话失忆：每次新会话 AI 都从零开始，前一个会话的架构决策、技术约定、踩过的坑统统消失。

规格漂移：没有明确的规格文件作为真理源，随着需求演进，代码逐渐与原始意图背离，产生无法追溯的技术债。

1.2 SDD 的解法

规格驱动开发把结构化规格（Specification）而非即兴提示（Prompt）作为开发的源头，代码是规格的生成产物，而非随机意图的结果。截至 2026 年上半年，SDD 工具已有数十个，其中 GSD 和 BMAD-METHOD 是关注度最高的两个代表：按 2026-06-23 的快照，GSD 原仓库约 6.45 万 star、BMAD 约 4.95 万 star，合计超过 11 万。

GSD 由开发者 TÂCHES（GitHub 账号 glittercowboy）于 2025 年 12 月创建（仓库创建于 2025-12-14），最初定位是「给 Claude Code 的轻量工作流系统」。不到 5 个月，原仓库积累了约 6.2 万 star（2026-05-12 快照），在 GitHub Releases 上发布了 60 余个正式版本。

3. GSD 深度解析

3.1 核心设计哲学

GSD README 的核心主张是：

「复杂性在系统里，不在你的工作流里。」
— TÂCHES（GSD 原作者）

GSD 把工程复杂性封装在框架内部（上下文工程、XML 提示格式、子代理编排、状态管理），对用户只暴露几个命令。原 README 明确把自己放在「反仪式」一侧：点名 BMAD、Spec Kit 等工具「把事情搞得过于复杂」（冲刺仪式、故事点、干系人同步、回顾会、Jira 流程），并声称不做「企业角色扮演」。

3.2 解决的核心问题：上下文腐烂

GSD 对上下文腐烂的解法是架构性的，而非提示性的：

  1. 主会话轻载：主会话保持在 30%–40% 上下文占用，不在主会话中执行重度工作。
  2. 子代理新鲜上下文：研究、规划、执行、验证等重度任务由独立子代理完成，每个执行器从干净的 200k token 上下文启动。
  3. 文件系统状态机：.planning/ 下的 STATE.md、阶段 CONTEXT.md 等结构化文件在会话间持久化状态，代理重置不会丢失项目决策。

3.3 核心工作循环：初始化 + 五步

GSD 将开发组织为里程碑 → 阶段 → 计划三级层次。/gsd-new-project 初始化后，每个阶段重复五步循环：

3.5 Wave 并行执行机制

Wave 是 GSD 区别于串行 AI 工作流的关键特性：

  • 独立计划在同一 wave 内并行执行
  • 有依赖关系的计划等待前序 wave 完成后进入下一 wave
  • 每个执行器均在全新的 200k 上下文中启动
  • 每个任务产生独立的原子提交，形成清晰的 Git 历史

3.6 质量门控体系

v1.34.0（2026-04-06）引入四种规范化门控类型，并接入 plan-checker 与 verifier 代理：

  • Pre-flight Gate：执行前的可行性验证
  • Revision Gate：执行中的修订触发
  • Escalation Gate：质量问题的上报机制
  • Abort Gate：不可恢复情况的中止

4. BMAD-METHOD 深度解析

4.1 核心设计哲学

BMAD 的核心主张是：通用 AI 产出通用结果，让 AI 以特定领域专家的身份参与，质量会发生质变。

BMAD 不是上下文管理工具，而是开发过程的完整结构化——从构思、需求到架构、实现、测试、文档，每个阶段都有专属的 AI 专家人格（Persona）参与。其设计信条是「AI 作为思维伙伴，而非思维替代」：Agent 不替你思考，而是通过结构化流程引导你想清楚。

4.2 规模自适应智能（Scale-Adaptive Intelligence）

BMAD 的核心差异化能力是按项目复杂度调整规划深度和流程严肃性：

  • Bug 修复：轻量工作流，直接切入
  • 新功能：中等流程，PRD + 架构审查
  • 企业级平台：完整流程，全角色协作 + 冲刺规划 + 回顾

团队因此不必在「流程过多」和「结构不足」之间二选一。

4.3 Agent Persona 体系

v6.8.0 的核心模块内置 6 个 Agent 人格，领域知识编码在各自的技能里：

5. 核心理念对比

5.1 哲学层面的根本分歧

维度 GSD BMAD
核心问题定义 上下文腐烂是 AI 开发的首要杀手 流程缺失导致 AI 产出不可预测
解决方向 上下文工程（Context Engineering） 流程工程（Process Engineering）
复杂性归置 复杂性在系统内部，工作流保持简洁 复杂性在流程中，由 AI 承担执行
对敏捷的态度 反仪式 拥抱敏捷，AI 让仪式高效执行
人机协作模式 人类审批关键节点，AI 自主执行 AI 作为专家协作者，引导人类思考
质量保障方式 上下文新鲜度 + 目标回溯验证 对抗性代码审查 + 多角色交叉校验

5.2 目标用户画像

GSD 的典型用户：

  • 独立开发者 / 小团队（1–5 人）
  • 追求快速交付，不愿承担仪式成本
  • 项目复杂度中等，但担心长时间会话的质量退化
  • 已在用 Claude Code 等编码 agent，希望在现有工具上叠加工作流

BMAD 的典型用户：

  • 中等规模团队（5–20 人）
  • 采用敏捷方法论，习惯角色分工
  • 架构错误代价高昂（监管领域、全新平台）
  • 需要完整的 SDLC 产物链用于审计和传承

5.3 成功度量的差异

GSD BMAD
成功信号 代码运行，测试通过，PR 合并 架构文档完整，Story 验收标准满足，测试覆盖达标
失败检测 验证阶段的目标回溯验证 对抗性代码审查 + Party Mode 交叉质疑
历史可追溯性 原子化 Git 提交，每任务一次提交 结构化产物链（PRD → 架构 → Story → 代码）

方向调整 /gsd-phase --edit 修改阶段，或插入新阶段后重新规划 bmad-correct-course 评估变更影响，bmad-edit-prd 修订 PRD，再同步下游 Story
代码审查 按需独立触发 实现后纳入标准流程
团队协作 .planning/ 随仓库共享，workstream 支持分区域并行 产物链适合多人按角色接力，Story 分配需人为协调

7.3 第三方实测参考

2026-04-13 发表的一篇「三款规格驱动工具实测」（作者 Itzhak Eretz Kdosha）正式评测了 BMAD、Spec Kit 与 OpenSpec：

  • BMAD Full 在「迭代精化与纠偏」一项得到 5/5。作者认为对抗性代码审查能在交付前发现问题，测试中抓到了常规审查会漏掉的内容；Party Mode 让多个 Agent 人格在实现前过一遍设计；对合适的项目，这份「复杂性税」值得付。
  • 作者还指出，BMAD 的定制能跨升级保留，「不合用」时倾向于改配置而不是放弃工具。
  • GSD 未进入正式评测，只作为「荣誉提名」出现，被描述为「独立开发者的 vibe coding 工具」，作者认为它对结构化的团队评测来说过于简单。

这份实测的结论只覆盖团队评测视角；对单人、规格明确的项目，GSD 的轻量恰恰是优点（见 §8、§14）。

8.2 典型场景判断

明确选 GSD 的场景：

  • 独立开发者，用编码 agent 构建复杂 SaaS
  • 长会话后 AI 质量明显退化，这是首要痛点
  • 不需要正式的 PRD 或架构文档，但需要 Git 历史可追溯
  • 希望在本地模型（Ollama、LM Studio）或按量计费的 API 上使用
  • 项目规格明确，主要问题是执行一致性

明确选 BMAD 的场景：

  • 5 人以上的开发团队，有角色分工
  • 构建核心业务系统，架构错误会造成数月的技术债
  • 监管合规场景，需要完整的决策追溯链（PRD → 架构 → Story → 代码）
  • 团队已经在用敏捷，希望 AI 融入而非替换现有流程
  • 明确需要多视角（PM + 架构师 + QA）交叉验证

考虑轻量替代的场景：

  • 单个 Bug 修复或小型功能：直接用编码 agent + 项目指令文件（CLAUDE.md / AGENTS.md）
  • 需要与 CI/CD 深度集成：考虑 OpenSpec 或 Kiro
  • 多个 AI 工具混用（Copilot + Claude Code + 其他）：考虑 Spec Kit

13. 高级策略：混合使用

GSD 和 BMAD 解决的是相邻问题，可以叠加使用。

13.1 层次模型

据社区讨论，也有人把 gstack（战略决策）、GSD（上下文稳定性）与 Superpowers（执行纪律）当作三个互补层来组合，而不是互相替代。

13.2 BMAD + GSD 协作工作流

这个组合获得了 BMAD 的规格严谨性和 GSD 的执行效率，代价是学习两套工具，以及要明确「实现环只由 GSD 驱动」，不要同时再跑 BMAD 的 Story 实现流程。

14. 示例项目：规格已就绪的单人开发项目

用一个典型场景演示如何套用 §12 的决策框架：单人开发一个多组件的 Agent 平台，规格套件已经写好。

14.1 项目特征分析

  • 规模：单人开发，已有 PRD 与十余份 ADR（架构决策记录）
  • 复杂度：多组件后端——编排层、记忆与持久化、检索、API 层之间互相依赖
  • 首要风险：长会话中的上下文腐烂，组件之间的约定在会话切换时容易丢失
  • 文档就绪度：需求与架构已定稿，不需要从头走 BMAD 的规划阶段

按五问推导：首要痛点是上下文腐烂（Q1 → GSD），团队 1 人（Q2 → GSD），大部分架构决策已被 ADR 锁定（Q3 → GSD 可承接），文档产物已有、不需要再生成（Q4 → GSD）。

14.2 推荐方案

主推：GSD Core（open-gsd/gsd-core）

理由：

  1. 规格已就绪：用 /gsd-import 导入现有计划，或在 /gsd-new-project 采访中直接引用 PRD，跳过 BMAD 的规划阶段。
  2. 单人开发的上下文腐烂是核心痛点，GSD 的新鲜子代理机制直接对症。
  3. 组件边界清晰时，互不依赖的组件计划可以放进同一 wave 并行实现，有依赖的自动排到后续 wave。

配合策略：

  • ADR 映射：ADR 的结论写入 PROJECT.md 的关键决策；与某阶段相关的 ADR 在 /gsd-discuss-phase 时作为输入，写进该阶段的 CONTEXT.md，避免 agent 重新讨论已定决策。
  • 事前验尸（pre-mortem）：关键架构决策前借用 BMAD Party Mode 的思路，让「架构师」和「安全审查者」两个角色质疑设计，但不走完整 BMAD 流程。
  • 安装形态：只用 Claude Code 时可选插件形态 jnuyens/gsd-plugin；需要多个运行时则用 npm 安装器。

15. 总结

15.1 结论性判断

GSD 和 BMAD 不是同一问题的两种答案，而是两个不同问题的专属答案：

GSD BMAD
它解决的核心问题 AI 在复杂项目中的上下文退化 AI 在复杂项目中的流程无序
最佳比喻 专业的「工程项目经理」，确保每个工人都在峰值状态下工作 专业的「虚拟全栈团队」，每个角色各司其职
一句话定位 让编码 agent 从始至终保持高质量 让 AI 成为完整敏捷团队的成员

对于绝大多数独立开发者和小团队：从 GSD 开始（使用 GSD Core），当需要更多架构纪律和文档完整性时，引入 BMAD 的特定工作流（至少用 Quick Flow）。

对于中等规模团队和企业项目：从 BMAD 开始建立规范，用 GSD 优化长周期实现阶段的上下文管理，用 Superpowers 强化执行纪律。

15.2 行业大趋势

这些框架指向同一个判断：前沿编码模型已经足够写出生产级代码，问题在于驱动它们的方式让质量无法稳定。每个框架回答的是同一个问题——哪种干预最重要：上下文纪律（GSD）、角色分工（BMAD）、规则约束（Superpowers）。

未来的竞争焦点不再只是哪个 LLM 写代码更好，而是哪个系统能最有效地协调 AI 代理的工作。SDD 框架生态是这个方向上最早、最活跃的一批探索。
