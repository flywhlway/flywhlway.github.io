13 · 反模式总清单：全册反模式的独立查阅册

企业级 Skill Registry 平台工程手册 · 第 13 篇（收官参考册）
定位：08 篇的反模式总目录服务于规范执法，本篇是独立的速查册——把 01–12 篇散落的全部反模式汇成一册，按”你正在做什么”而非”哪一篇”组织，供设计评审、故障复盘、新人培训时快速定位。每条含：症状（你会看到什么）、根因（为什么会掉进去）、根治（平台机制，非口号）、出处（回溯详解）。

使用指南

三种查阅入口：

  1. 按活动查（§1–§8）：你正在设计路由？看 §2。正在写脚本？看 §6。
  2. 按症状查（§10 症状索引）：线上出现”某技能随机不触发”？症状索引直接指向条目。
  3. 按严重度查（§9 红线清单）：哪些反模式是一票否决的架构红线，先看这张表。

每条编号 AP-<域>-<序>，域缩写：CTX 上下文 / RT 路由 / ORG 组织 / CNT 内容 / REG 控制面 / DST 分发 / RUN 运行时 / AUTH 作者 / EVL 评测 / SEC 安全 / IR 跨生态。

§1 上下文管理反模式（CTX）

AP-CTX-1 巨型 SKILL.md

  • 症状：单个 SKILL.md 数千行；模型激活后行为发散、关键指令被淹没；L2 token 成本畸高。
  • 根因：作者把”给人的操作文档”直接当 SKILL.md，背景铺垫与防御性重复堆叠。
  • 根治：F-2 lint 硬闸 ≤500 行；超限强制”层级导航 + references 下沉”。长度裁决树（09 §4.3）逐段问”每次激活都需要它吗”。
  • 出处：01 §2.2，08 §13，09 §4.3。

AP-CTX-2 预载所有 references

  • 症状：SKILL.md 开头把全部 reference 标”必读”或一次性读入；上下文暴涨。
  • 根因：作者怕模型漏读，用”全都读”求安心。
  • 根治：R-4 路由表（”何时读哪个”）替代”详见 references/“；违反”预载即巨兽”进 lint。
  • 出处：01 §6，08 §13，09 §4.2 病 5。

AP-CTX-3 description 写实现细节

  • 症状：description 里出现”用 LangGraph 构建””基于向量检索”等实现词；触发失准。
  • 根因：作者从”我怎么实现的”而非”用户何时需要”出发写。
  • 根治：D-6 禁用模式表 + LLM 复核；描述做什么不描述怎么做。
  • 出处：02 AP-7，08 §13，09 §4.2 病 1。

AP-CTX-4 examples 内联进 description

  • 症状：description 塞满示例，L1 预算爆炸，触发词被示例稀释。
  • 根因：混淆了 description（触发判据）与 trigger_examples（评测燃料）的职责。
  • 根治：D-3 要求 examples 进独立字段；D-6 检出内联。
  • 出处：02 AP-7，08 §13。

§2 路由与触发反模式（RT）

AP-RT-1 框架旁路注入

  • 症状：Runtime/框架绕过模型自主激活，按规则强行把技能内容注入上下文。
  • 根因：工程团队想”确保技能被用上”，用确定性注入替代模型判断。
  • 根治：激活权宪法（01 §2）——外部路由只影响 L1 召回，激活权永远在模型；框架不得注入 L2。
  • 出处：01 AP-2，07 §1 忠实原则。

AP-RT-2 泛化巨兽

  • 症状：一个技能触发域宽到无法用一句负面边界说清；频繁误触发或与多技能重叠。
  • 根因：作者贪多，把多个能力域塞进一个技能。
  • 根治：02 §4 单一触发域原则；触发域无法一句话划清即拆分。
  • 出处：02 AP-3，09 附 D Q8。

AP-RT-3 单边切割

  • 症状：技能 A 声明不处理某场景，但接手方 B 未声明接手，形成两不管地带。
  • 根因：D-4 边界的双向性被忽略，只做了一半。
  • 根治：D-4 对称性检查（图对称性 lint）；配对声明工单机制。POC 已验证两技能双向声明配对。
  • 出处：02 §4，08 §13，09 §5。

AP-RT-4 标签路由

  • 症状：用人工标签/分类而非 description 语义驱动激活；标签维护成本高且与真实触发脱节。
  • 根因：想用”可控的”标签替代”不可控的”语义激活。
  • 根治：description 语义为主，标签仅作 Marketplace 筛选（05 §8 人机双索引分工）。
  • 出处：02 AP-4，04 AP-7。

AP-RT-5 路由劫持（安全）

  • 症状：某技能 description 过度贪婪，抢走敏感技能（compliance:*）的触发流量。
  • 根因：无意的过宽，或有意的攻击。
  • 根治：敏感域触发重叠 = elevated 硬规则（11 §4.3）；重叠检测安全专项。
  • 出处：11 §4.3。

§3 组织与命名空间反模式（ORG）

AP-ORG-1 技术栈命名空间

  • 症状：python:、java: 这类按技术栈划的 namespace；能力域被技术实现切碎。
  • 根因：按”怎么实现”而非”什么能力”组织。
  • 根治：N-3 namespace 对齐能力域；技术栈命名进 lint 模式表。
  • 出处：04 AP-1，08 §13。

AP-ORG-2 组织架构镜像

  • 症状：namespace 照搬部门结构（dept-x:）；组织调整即 namespace 大迁移。
  • 根因：用组织图当技术架构。
  • 根治：N-3 + namespace 稳定性压测（04 附 C：能说出两年内改名场景的重新设计）。
  • 出处：04 AP-2。

AP-ORG-3 单技能 plugin

  • 症状：每个技能一个 plugin；plugin 作为分发单元的意义丧失，管理开销翻倍。
  • 根因：不理解 plugin = 族级分发单元。
  • 根治：04 §3 plugin 为族聚合；单技能族触发合并建议。
  • 出处：04 AP-3。

AP-ORG-4 胶水 meta-skill

  • 症状：一个技能只是固定顺序调用几个已有技能，无新增领域知识。
  • 根因：把编排逻辑塞进技能层。
  • 根治：04 §5.3 禁令——无新知识不建技能；编排属 Agent 层。
  • 出处：04 AP-6，09 §2.2。

AP-ORG-5 隐式跨族依赖

  • 症状：技能间私相传递文件/共享脚本，无 requires 声明。
  • 根因：图省事跨族复制文件而不走依赖或工具化。
  • 根治：M-4 依赖显式化；跨族复用走三原语（复制/工具化/requires），09 附 D Q4。
  • 出处：04 AP-5。

§4 内容与描述反模式（CNT）

AP-CNT-1 易变数据入技能

  • 症状：reference 里写”本周活动规则””当前联系人”等变更快于发版的数据。
  • 根因：把技能当数据库用。
  • 根治：R-3——变更频率 > 发版频率者走工具实时取。
  • 出处：01 AP-6，08 §13。

AP-CNT-2 无条件命令式

  • 症状：SKILL.md 出现”所有输出必须 JSON””总是先问三个问题”；跨任务串味。
  • 根因：作者想”确保”某行为，用无条件命令替代条件分支。
  • 根治：Doc-1 条件式纪律；无条件命令模式进 lint；09 §4.1 语用学第 2 则。
  • 出处：01 AP-7，02 AP-6，09 附 D Q3。

AP-CNT-3 全员 pushy

  • 症状：大量技能 description 加主动扩大触发的 pushy 子句，FP 全面恶化。
  • 根因：每个作者都怕自己的技能欠触发。
  • 根治：D-5 pushy 登记制——仅评测证实欠触发者可用。
  • 出处：02 §2，08 §13。

AP-CNT-4 描述漂移

  • 症状：技能能力变了但 description 没跟着改；触发与实际能力脱节。
  • 根因：改正文/脚本时忘了联动 description。
  • 根治：D-7 能力变更强制 description 复核 + 触发回归（流水线 diff 联动）。
  • 出处：02 §8，08 §13。

§5 控制面反模式（REG）

AP-REG-1 Registry 上会话关键路径

  • 症状：每次会话初始化直连 Registry resolve；Registry 抖动全平台会话失败。
  • 根因：没做本地缓存，把控制面当数据面用。
  • 根治：本地缓存 + 事件驱动标脏（06）；Registry 读路径全可缓存。
  • 出处：05 AP-1，06 §1。

AP-REG-2 可变版本

  • 症状：允许覆盖已发布版本”改个小错”；回滚/审计/as_of 复现全失效。
  • 根因：图方便，不想为小改发新版本。
  • 根治：产物不可变（WORM）；补救走新版本（V-4）。
  • 出处：05 AP-2，06 §1。

AP-REG-3 质量字段自填

  • 症状：发布方在 manifest 里自报 trigger_rate 等质量数据。
  • 根因：schema 没做写保护。
  • 根治：quality 段 API 层剥离（M-2）；只由评测/统计服务回写。
  • 出处：05 §3，08 §13。

AP-REG-4 全量人审

  • 症状：每次发布都人审；规模上来后退化为橡皮图章。
  • 根因：怕漏，用”全审”求全。
  • 根治：分级审批（05 §6）+ owner 信誉分，火力集中 elevated。
  • 出处：05 §6，08 §13。

AP-REG-5 统计直连

  • 症状：控制面 DB 直接承接原始遥测流量。
  • 根因：图省事不做聚合层。
  • 根治：日聚合表 + 单向统计管道（05 §4）；原始遥测留观测系统。
  • 出处：05 §4。

AP-REG-6 结果层租户过滤

  • 症状：先查全量再滤结果；私有技能名通过计数/时延侧信道泄露。
  • 根因：过滤加在了错误的层。
  • 根治：索引层过滤（05 §10）+ RLS。
  • 出处：05 AP-6。

AP-REG-7 搜索单索引通吃

  • 症状：人机两类查询共用一套排序；机器召回被人气分污染。
  • 根因：没区分 Marketplace（人）与补充召回（机）。
  • 根治：三索引分排序（05 §8）。
  • 出处：05 AP-7。

§6 分发反模式（DST）

AP-DST-1 可变 latest 指针进产物层

  • 症状：产物层有 latest tag；缓存漂移。
  • 根因：借用镜像仓库的可变 tag 习惯。
  • 根治：channel 解析只在 Registry/resolved_set 层；产物层只有 digest。
  • 出处：06 AP-1。

AP-DST-2 缓存原地覆盖实现”热更新”

  • 症状：缓存文件原地覆盖；进行中会话前后看到两个版本，行为精神分裂。
  • 根因：把”热更新”理解成”立即替换文件”。
  • 根治：热更新唯一合法语义 = 新会话解析到新版本（06 §6）；会话快照锚定。
  • 出处：06 AP-2，07 §7。

AP-DST-3 TTL 式缓存失效

  • 症状：缓存按时钟失效；同一会话中途重取到新版本。
  • 根因：用通用缓存 TTL 而非会话粒度失效。
  • 根治：失效单位是会话，标脏靠事件不靠时钟（06 §4）。
  • 出处：06 AP-3。

AP-DST-4 边缘全量同步

  • 症状：把万级技能库全量推到厂端/车端磁盘。
  • 根因：不做订阅域过滤。
  • 根治：订阅域过滤 + L3 懒拉 + surfaces 过滤（06 §9）。
  • 出处：06 AP-4。

AP-DST-5 上游自动跟版

  • 症状：vendored 上游一改就自动跟；上游维护者进入你的信任基座。
  • 根因：图省事不做准入重审。
  • 根治：vendored 准入流水线（06 §10）；上游更新进标准发布重审。
  • 出处：06 AP-5，11 §12。

AP-DST-6 回滚绕过流水线

  • 症状：”紧急”手工改指针不签名不留痕；事故最需审计时销毁审计。
  • 根因：以为回滚快 = 可以跳过流程。
  • 根治：回滚也走流水线快速通道 + 签名 + 审计（Rel-1）。回滚快是因机制轻，非跳流程。
  • 出处：06 AP-6，11 §10。

AP-DST-7 遥测阻塞分发

  • 症状：边缘节点”必须回传成功才继续服务”。
  • 根因：把尽力而为的遥测当作阻塞依赖。
  • 根治：遥测永不阻塞，服务优先（06 §9，07 F8）。
  • 出处：06 AP-7。

§7 运行时反模式（RUN）

AP-RUN-1 语义化重试

  • 症状：Runtime 自作主张重跑脚本（超出模型指令）。
  • 根因：想”帮”模型自动恢复。
  • 根治：重试分层（07 §6）——仅幂等基础设施层自动，脚本业务失败归模型决策。
  • 出处：07 AP-1。

AP-RUN-2 输出自动修复

  • 症状：Gateway”好心”修复脚本的微损 JSON 再回给模型；模型建立的格式信念与真实脱钩。
  • 根因：想让模型体验更顺。
  • 根治：忠实回传 + 让模型走 fallback（07 §1）。
  • 出处：07 AP-2。

AP-RUN-3 无差别强隔离

  • 症状：全部脚本上 gVisor/Kata；冷启动与内存税吃掉沙箱池容量。
  • 根因：一刀切求”安全”。
  • 根治：按代码可信度分档（07 §5.1）——评审过的脚本容器级够用，现场生成代码才强隔离。
  • 出处：07 AP-3。

AP-RUN-4 workspace 即弃

  • 症状：取消/失败即清 workspace；销毁恢复资本。
  • 根因：把 workspace 当临时垃圾。
  • 根治：workspace 保留（07 §6 纪律 1）；checkpoint = 中间文件。
  • 出处：07 AP-4，07 §7。

AP-RUN-5 引擎级透明续跑

  • 症状：试图把模型推理状态图灵完备外化做透明断点续跑。
  • 根因：照搬工作流引擎的 checkpoint 模型。
  • 根治：状态就是文件与对话（07 §7）；引擎管 Agent 图，技能管证据文件。
  • 出处：07 AP-5。

AP-RUN-6 技能指令写记忆

  • 症状：SKILL.md 出现”将 X 写入用户记忆”；绕过隐私过滤管道。
  • 根因：作者想让技能”学习”。
  • 根治：技能无状态，经验积累走发版（07 §8）；发布扫描 + 运行时双防。
  • 出处：07 §8，11 §4.1 C4。

§8 作者、评测、跨生态反模式（AUTH/EVL/IR）

AP-AUTH-1 从记忆写作

  • 症状：不采样本直接写；触发词失真、examples 后补敷衍。
  • 根因：自信”我懂这个域”。
  • 根治：逆向工作法（09 §3）——先 ≥10 样本、后写作。
  • 出处：09 AP-1。

AP-AUTH-2 演示驱动

  • 症状：只用最顺利案例开发，fallback 全是想象。
  • 根治：examples 含失败路径强制项（F-4，09 §8）。
  • 出处：09 AP-2。

AP-AUTH-3 跳过角色扮演自测

  • 症状：不做”假装自己是模型只做写了的事”的执行自测；缺失指令流到人审。
  • 根治：09 §9.3 角色扮演自测——最便宜的质检。
  • 出处：09 AP-6。

AP-EVL-1 单次定胜负

  • 症状：不重复、无区间的触发对比；噪声当信号。
  • 根治：N≥3 重复 + Wilson 区间（10 §7）。
  • 出处：10 AP-1。

AP-EVL-2 Judge 万能 / 无校准 Judge

  • 症状：断言能判的上 Judge；或 Judge 未校准就进质量分。
  • 根治：能断言绝不上 Judge（10 §4.1）；金标一致率 ≥80% 上岗线（10 §5.2）。
  • 出处：10 AP-2,3。

AP-EVL-3 优化验收同集 / 绿灯崇拜

  • 症状：description 对着将要考它的题优化；或靠放宽断言消假失败。
  • 根治：train/test 切分 + 变异集只验收（10 §3.4）；假失败靠修比对层级不靠松断言。
  • 出处：10 AP-4,7。

AP-SEC-1 扫描器万能论

  • 症状：静态库当唯一防线，语义复核与运行时防线缺位。
  • 根治：五层纵深（11 §3）——扫描器只是 L1 的一半。
  • 出处：11 AP-1。

AP-SEC-2 信任已签名内容

  • 症状：签名过就不再运行时防护。
  • 根治：签名证明来源与完整性，不证明无害；L2 过了 L1 照做（11 §3）。
  • 出处：11 AP-2。

AP-SEC-3 原始数据直喂模型

  • 症状：”让模型自己读日志更灵活”；放弃抗注入架构红利 + 上下文成本控制。
  • 根治：脚本给证据模式窄化数据（11 §8 防线 1）。
  • 出处：11 AP-7。

AP-SEC-4 审计与业务同库 / 例外无期限

  • 症状：DBA 一条 DELETE 灭证据；或永久例外堆积。
  • 根治：平台域审计 append-only 独立存储（11 §9）；例外时限化（11 §11.2）。
  • 出处：11 AP-4,5。

AP-IR-1 最小公约数 IR

  • 症状：为”公平支持所有端”把 IR 削到交集；渐进披露、脚本全丢。
  • 根治：IR 是超集不是交集（12 §9）。
  • 出处：12 AP-1。

AP-IR-2 静默降级 / 假装无损

  • 症状：编译丢能力不标注，用户拿残废技能；或前端编造缺失字段。
  • 根治：每次 loss 进 capability_matrix（12 §5）；前端产 gaps 清单（12 §4.1）。
  • 出处：12 AP-2,4。

AP-IR-3 治理接在形态层

  • 症状：审批/扫描/评测挂在 SKILL.md 而非 IR；扩端每端重做治理。
  • 根治：治理下沉 IR 层（12 §6，附 B）。
  • 出处：12 AP-6。

§9 架构红线清单（一票否决）

以下反模式违反即架构不合格，无论其它做得多好——它们破坏的是全体系依赖的地基不变量：

红线 破坏的地基 条目
框架旁路激活 激活权在模型 AP-RT-1
可变版本/产物 不可变 → 回滚/审计/复现全免费 AP-REG-2, AP-DST-1
原地热更覆盖 会话快照一致性 AP-DST-2
Registry 上关键路径 控制面/数据面分离 AP-REG-1
技能作为权限载体 技能只收窄不放大权限 11 §6
审计与业务同库 审计不可销毁 AP-SEC-4
信任已签名内容 纵深不得因上层降强度 AP-SEC-2
最小公约数 IR IR 超集性 AP-IR-1

红线的共性：它们都是”图一时方便，毁一类能力”——每条红线换来的短期便利，代价是永久失去一个系统级属性（可回滚性、可审计性、一致性、纵深性）。评审时对红线零容忍。

§10 症状索引（故障复盘入口）

线上出现症状 → 直接定位候选反模式：

你观察到的症状 候选反模式
某技能”随机”不触发 AP-CTX-1（被淹没）、F1 预算截断（07）、AP-CTX-4
技能激活了但没照 SKILL.md 做 步骤遵循度问题（10 §4.3），非反模式，进评测
无关任务被强加了某格式/术语 AP-CNT-2 无条件命令式（串味）
两个技能抢同一场景 AP-RT-2 巨兽、AP-RT-3 单边切割
某场景两个技能都不管 AP-RT-3 单边切割
会话中途技能行为变了 AP-DST-2/3 热更/TTL 失效
Registry 抖动全平台会话失败 AP-REG-1 关键路径
私有技能名疑似泄露 AP-REG-6 结果层过滤
沙箱池容量不够/冷启动慢 AP-RUN-3 无差别强隔离、F3 冷启动风暴
取消后残留进程/丢失半成品 F5 僵尸执行、AP-RUN-4 workspace 即弃
离线全绿但线上 correction 高 AP-EVL-3 优化验收同集、评测集过拟合（10 §9）
报告里出现可疑的外呼/大批量数据 AP-SEC-3 原始数据直喂、DLP 告警（11 §7.2）
编译到某端后技能”没用” AP-IR-2 静默降级（应编译失败而非产空壳）

§11 反模式的元规律

通览全册反模式，五条元规律浮现——理解它们比记住单条更重要：

  1. 图方便毁地基（红线类）：短期便利换永久属性丢失。防法：把地基不变量写成 ADR，评审对照。
  2. 好心办坏事（运行时类 AP-RUN-1/2）：想”帮”模型/用户，结果侵蚀可预测性。防法：忠实原则——组件不替代决策。
  3. 从自我视角写作（内容/作者类）：写”我怎么实现/我懂什么”而非”用户何时需要/模型如何执行”。防法：逆向工作法 + 切换到模型执行视角通读。
  4. 执法滞后于规范（治理类）：宣布规范但没建 lint/机制，规范失信。防法：执法点先行（08 §1）。
  5. 上层信任下移（安全/纵深类 AP-SEC-2）：某层以”上一层查过”降低自身强度。防法：每层独立强度，纵深不打折。

对着这五条元规律做设计评审，比逐条背反模式更能防住尚未被编号的新反模式——它们几乎总是这五条的新变体。

本册是活文档：新反模式经复盘确认后，按域编号补入，并回填对应篇章的根治机制。反模式清单的增长是平台成熟的正常代谢，不是退步——它意味着团队正在把踩过的坑变成后人的护栏。
