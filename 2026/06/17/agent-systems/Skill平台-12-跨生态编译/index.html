Flywhl 28 分钟 发布于 2026.06 #Agent Skills#架构设计#Agent

先读结论

  1. 同一个文件格式不等于同一个技能：平台元数据、工具扩展字段、落点目录、非 SKILL.md 目标四类差异，决定了平台需要自己的 IR。
  2. IR 是超集不是交集；每次投影的损失都进 capability_matrix，必需能力无法投影时编译失败，而不是产出空壳。
  3. 导入外部形态时前端只产出 gaps 清单，不编造缺失字段；目标档案是带来源与核实日期的版本化数据。
  4. 产物是 IR、编译器版本、目标档案版本的确定性函数，因此审批、扫描、签名、评测都挂在 IR 层，扩一个端不重做一遍治理。

12 · 统一技能描述格式与跨生态编译

企业级 Skill Registry 平台工程手册 · 第 12 篇：01–11 篇在一个运行时里解决了技能的设计、分发、运行、评测与治理，本篇把同一份技能交付到多个 Agent 工具，是统一技能中心的编译层。
前置阅读：01 篇 §7（跨生态机制对比）、04 篇 §9（跨生态对照）、05 篇 §3（元数据 Schema）、10 篇 §3（触发评测协议）。
本篇回答：SKILL.md 已是开放标准，平台为什么还要一层中间表示；这层表示长什么样，怎样编译到各生态，损失怎样登记，治理挂在哪里。

1. 为什么需要统一中间表示

2025-12-18，Agent Skills 成为开放标准（agentskills.io）；随后 Codex、Cursor、VS Code、Gemini CLI 相继支持 SKILL.md。直觉上，格式统一之后”一次编写、多端分发”只剩复制文件。实际落地时，同一个文件格式不等于同一个技能，差异集中在四处：

差异 表现 不处理的后果
平台元数据不在 SKILL.md 里 05 篇 manifest 的 routing、capabilities、requires、sandbox_profile、critical_steps、provenance 在标准 frontmatter 中没有位置 分发到外部工具后，路由评测、沙箱档、依赖、溯源全部丢失，且无人知道丢了
扩展字段方言 “只允许用户手动调用”在 Claude Code、Cursor、VS Code 写作 disable-model-invocation: true，在 Codex 写作 agents/openai.yaml 的 policy.allow_implicit_invocation: false 同一语义多处手写，改一处漏一处
落点目录不同 .claude/skills、.agents/skills、.cursor/skills、.github/skills、.gemini/skills 各有读取方 要么漏端，要么同一技能被同一工具发现两次
非 SKILL.md 目标仍然存在 Cursor Rules（.mdc）、AGENTS.md、MCP、Gemini Gems 渐进式披露与脚本在这些目标上部分或全部失效

还有一个容易忽略的事实：Claude Code 的扩展字段（context、agent、hooks 等）在 Claude Code 里合法，但官方文档说明带有标准外字段的技能上传到 claude.ai 或 Skills API 时会直接报错。同一厂商内部就已经存在两个编译目标。

因此 01 篇 §7 的结论在这里落成架构：平台内部维护一份规范化 IR（元数据 + 指令体 + 资源清单 + 能力声明），各生态格式都是它的投影，任何一个生态的文件格式都不是平台的内部真理源。

IR 不是在所有情况下都值得引入：

情况 建议
只用标准字段、只面向原生支持 SKILL.md 的工具、没有平台元数据 直接分发标准 SKILL.md，按落点复制即可，不需要编译器
有平台元数据（注册中心、评测、治理在用） 引入 IR
使用任一工具的扩展字段 引入 IR
需要投影到 Rules、AGENTS.md、MCP、Gems 等非 SKILL.md 目标 引入 IR

2. 目标生态：目录、字段与调用方式

下表按各工具官方文档整理。这些信息在 2026 年上半年仍在变化（Codex 的技能目录就从 .codex/skills 迁到了 .agents/skills），编译器必须把它们当作带来源与核实日期的版本化数据维护（§4.3），不能写死在代码里。

标准本身对编译器有三条硬约束，所有 SKILL.md 目标共享：name 为 1–64 个小写字母、数字或连字符，首尾不能是连字符、不能出现连续连字符，且必须与父目录同名；description 不超过 1024 字符；compatibility 不超过 500 字符。标准还建议 SKILL.md 正文少于 500 行、约 5000 token。

01 篇 §7 设想的”MCP tool manifest”目标，在 Skills 扩展出现之前是接入 MCP 的唯一办法：把技能包装成一个 prompt（正文作模板，由用户触发），或包装成一个 tool（description 进工具描述，调用时返回正文）。tool 形态让模型以”选工具”的方式激活技能，但正文作为工具结果一次性注入，references 无法按需读取，脚本也无处执行——它是 ◐ 路由加 ○ 披露的组合。新接入优先走 Skills 扩展，tool 形态只保留给尚未支持扩展的宿主。

AGENTS.md 与 MCP 均已于 2025-12-09 成为 Linux Foundation 旗下 Agentic AI Foundation 的创始项目——开放治理意味着格式会继续演进，这再次说明目标档案必须版本化。

编译器沿用 09 篇的 skillctl 命令族，入口为 skillctl build。

4.1 前端：解析与导入

前端有两个入口。作者源是 03 篇那样的 SKILL.md + manifest.json，解析是无损的：四段 description 按 02 篇结构拆分（拆不出四段本身就是 D-1 lint 失败），manifest 字段逐一落位。

外部形态导入用于接管存量资产：团队已有的 Cursor 规则、AGENTS.md 章节、带 Claude Code 扩展字段的技能。导入的铁律是前端不编造缺失字段——源格式里没有的东西，产出到 gaps 清单，交给作者补，而不是让模型”合理补全”。导入一条 Cursor 规则的结果：

gaps 未清零的 IR 只能以 experimental 进入 dev 通道（05 篇 lifecycle），不能发布到 stable。这样导入工作量是显式的、可排期的，而不是藏在一堆”看起来完整”的技能里。

4.2 校验

层 检查内容 失败处理
标准层 name 规则与目录一致、description ≤ 1024、compatibility ≤ 500、正文行数；对标准产物运行 skills-ref validate 阻断全部 SKILL.md 目标
平台层 08 篇 lint 全集（D / F / M / S / R / Doc 系列） 按 lint 级别
目标可满足性 对每个启用的目标：essential 能力能否投影、x.<target> 字段是否在档案允许列表、权限类扩展字段是否有审查记录 仅阻断该目标，其余目标继续

一处需要显式对齐的数字：05 篇 Schema 中 description 的 maxLength 为 1200，而标准上限是 1024。启用任一 SKILL.md 目标时，IR lint 按 1024 执行——平台上限可以更宽，但不能比共同目标更宽。实际上 08 篇 D-2 的 L1 token 预算通常先触线。

4.3 降级与适配

每个目标对应一份目标档案，适配器是通用的，差异全部在档案里：

每项 IR 能力在每个目标上只有四种结局：

结局 含义 例 编译行为
native 目标有等价字段或机制 model_invocable=false → Codex policy.allow_implicit_invocation: false 直接投影
emulated 用目标已有机制等价改写 渐进式披露 → AGENTS.md 中只放路由条目 + 正文路径 投影并登记改写方式
degraded 可用但丢了一部分语义 file_scope → Gemini CLI 无对应字段，技能退化为全局可见 投影并登记损失
unsupported 无法表达 捆绑脚本 → Gems 该能力在 essential 中则该目标编译失败；否则按 degraded 处理

essential 的默认推导规则：存在 role=script 的资源且 critical_steps 非空 → scripts 必需；SKILL.md 正文含 reference 路由表 → progressive_disclosure 必需。作者可以在评审中把某项降为非必需，但必须写明理由。这条规则就是 13 篇症状索引里”应编译失败而非产空壳”的实现：把 03 篇技能编译成 Gem，只会得到一段不能运行任何脚本的指令，用户拿到的是一个看起来存在、实际无用的技能。

4.4 产物与落点

落点选择是一个最小覆盖问题。项目级目录的读取方：

目录 Claude Code Codex Cursor VS Code Copilot agent / CLI Gemini CLI
.claude/skills 读 — 兼容读 读 读 —
.agents/skills — 读 读 后续版本读 读 读（别名，同层优先）
.cursor/skills — — 读 — — —
.github/skills — — — 读 读 —
.gemini/skills — — — — — 读

结论：.agents/skills + .claude/skills 两个落点覆盖全部六个工具。代价是 Cursor、VS Code、Copilot 会从两个目录发现同名技能，而同名重复时的处理方式各家文档均未说明。编译器的约束因此是：

  1. 目标集合允许时只用一个落点（例如团队只用 Codex、Cursor、Gemini CLI，只写 .agents/skills）；
  2. 必须双落点时，两份副本由同一 IR 生成、字节一致，build.lock 记录双落点，一致性测试比对两份 digest；Codex 文档明确支持软链接，其余工具对软链接的处理以实测为准；
  3. 禁止手工编辑任一副本——产物目录头部写入”由 skillctl 生成，勿手改”，CI 对产物目录做”重新编译后无 diff”检查。

4.5 一致性测试

层 方法 通过标准
往返一致 产物经前端重新导入得到 IR′，与原 IR 做字段级 diff diff 恰好等于 capability_matrix 中登记的损失：无未登记损失，也无多出来的字段（多出即前端或适配器在编造）
静态合规 标准产物跑 skills-ref validate；逐目标检查 frontmatter 是否只含档案允许的字段、name 与目录一致 全部通过
落点一致 双落点副本 digest 比对；产物目录重新编译无 diff 字节一致
触发一致 用 IR 中同一份 eval_set，按”目标 × 该目标生产模型”运行 10 篇 L-D 协议 各目标触发率与参考目标之差 ≤ 5 个百分点；超出即该目标的 description 投影有问题
执行一致 对 capability_matrix 中 scripts 为 native 的目标运行 examples 回归对 按 09 篇 §8 的比对层级判定

触发一致性是最容易被省略、也最有价值的一层：同一段 description 在不同工具中与不同的技能列表、不同的系统提示竞争，触发率会漂移。格式一致只是必要条件，行为一致才是编译正确的定义。

登记损失的两条纪律：

  1. 每一次损失都进矩阵，包括”看起来无关紧要”的：file_scope 丢失意味着技能从”只在编辑报告文件时出现”变成”全局可见”，它会参与所有会话的 L1 路由竞争——这是触发率漂移的常见来源。
  2. 矩阵是编译产物，不是文档。它由适配器根据档案计算得出，人不手写；往返测试用它作为”允许的 diff”判据，所以矩阵写错会直接导致测试失败。

6. 治理下沉到 IR 层

产物是 IR × 编译器版本 × 目标档案版本 的确定性函数。这句话决定了治理的挂载位置：只要 IR 经过治理、编译器与档案经过一次性评审，所有产物就被覆盖；新增一个目标 = 新增一份档案 + 评审这份档案，不需要对全库技能重做一遍审批、扫描与评测。

反过来，把治理接在形态层（审批 SKILL.md、扫描 .mdc、分别评测每个产物）有三个后果：扩一个端，全部治理动作乘以技能数重做一遍；不同形态的审批结论可能互相矛盾；导入的外部形态绕过了本该经过的门禁。

治理挂在 IR 层并不意味着产物完全免检，有两类例外需要单独处理：

  • 权限类扩展字段。x.claude-code 下的 allowed-tools、hooks，x.codex 下的 dependencies，本质是权限或执行行为的授予。它们仍在 IR 层审查，但走 05 篇的 elevated 审批通道；编译器只在 governance.review_record 覆盖这些字段时才投影，否则该目标编译失败。
  • 完整性。签名对象是 IR digest 与 build.lock（其中含逐产物 digest），分发与加载时按 build.lock 校验产物，沿用 06 篇 §3 与 11 篇 §12.1 的签名链。

各治理动作的具体挂载点见附录 B。

7. 与相邻篇的衔接

7.1 与 04 篇插件化：namespace 的投影

所有 SKILL.md 目标只有平铺的 name，没有 namespace。投影规则：

目标 族（namespace）的表达
Claude Code plugin：技能放在 plugin 的 skills/ 下，调用形式 /<plugin>:<name>——唯一原生保留族的 SKILL.md 目标
Gemini CLI extension 的 skills/ 目录可作为族的打包单元
Codex / Cursor / VS Code / Copilot 的项目目录 平铺，无族；同名冲突时加前缀
Cursor Rules 族 → .cursor/rules/<族>/ 子目录（04 篇 §9）
AGENTS.md 族 → 章节，或拆到子目录的 AGENTS.md
MCP Skills 扩展 族 → URI 前缀段

前缀规则受标准约束：name 不允许点号与连续连字符，因此 vehicle.diag:ota-log-diagnosis 冲突时投影为 vehicle-diag-ota-log-diagnosis，并受 64 字符上限约束。改名会改变 L1 中的名称，所以只在冲突时加前缀，并作为一项损失登记进 capability_matrix。

7.2 与 06 篇分发：IR 是分发单元，产物是派生物

  • 注册中心存 IR 版本；产物按 (IR digest, 目标, 编译器版本, 档案版本) 内容寻址缓存，可随时重建。
  • 通道、灰度、回滚都作用在 IR 版本上；回滚一个 IR 版本即回滚它的全部产物。
  • 仓库型目标（.agents/skills、.claude/skills、AGENTS.md）的分发形态是同步机器人向业务仓库提交产物目录；MCP 型目标的分发形态是由注册中心驱动的 MCP 服务端直接响应 skills/list。
  • 吊销时按 build.lock 反查全部派生产物，包括已同步进业务仓库的副本。

7.3 与 10 篇评测：评测集在 IR，运行在目标

  • eval_set 属于 IR，与目标无关；运行按”目标 × 该目标生产模型”展开，model_pin 必须与目标 surface 的生产模型一致（10 篇 §3.1）。
  • capability_matrix 决定适用的评测层：scripts 为 native 的目标跑执行回归，为 emulated 的目标只跑触发与结果评测。
  • 触发一致性（§4.5）作为新的发布门槛进入 10 篇附录 C 的门槛配置：某目标的触发率偏离参考目标超过阈值时，只阻断该目标的分发，不影响其他目标。

8. 存量迁移的顺序

平台从”单生态”走向 IR 的实际顺序，按风险从低到高：

  1. 先接管平台自有技能：03 篇这类作者源（SKILL.md + manifest.json）解析无损，编译器上线即可产出 Claude Code 与 .agents/skills 两个落点，往返测试建立基线。
  2. 再导入带扩展字段的技能：扩展字段迁入 x.<target>，权限类字段补审查记录；严格标准产物首次可以上传 claude.ai 与 Skills API。
  3. 然后导入 Cursor 规则与 AGENTS.md 章节：全部以 experimental 进入 dev 通道，gaps 清单进作者待办；Cursor 自带的 /migrate-to-skills 可用于把规则先转成 SKILL.md，但转换结果同样要经过前端导入与 gaps 审查。
  4. 最后开启非 SKILL.md 目标：AGENTS.md 片段、MCP Skills 条目；Gems 只对 essential 为空的纯知识类技能开放。

每一步的退出条件都是同一个：往返测试未登记损失为 0，触发一致性通过。

9. IR 是超集不是交集：八条设计原则

  1. IR 是超集不是交集。IR 表达平台所需能力的并集，各目标只是投影。为了”公平支持所有端”把 IR 削到交集，渐进式披露与脚本会首先被砍掉——这是一票否决的红线（13 篇 §9）。
  2. 有损必须显式。每次投影的损失进 capability_matrix；必需能力无法投影时，该目标编译失败。
  3. 前端不编造。导入只产出 gaps，缺失字段由作者补，模型生成的补全内容不能冒充源数据。
  4. 编译确定性。相同 IR、编译器版本、档案版本产出字节一致的产物，这是治理下沉与内容寻址缓存的前提。
  5. 治理在 IR。审批、扫描、签名、评测的对象是 IR；产物只做完整性校验。
  6. 目标档案版本化。落点、字段、能力表都是带来源与核实日期的数据，工具更新时改档案、升档案版本、重编译，不改编译器代码。
  7. 权限不因编译放大。required_tools 描述”技能需要什么”，allowed-tools 授予”免审批使用什么”，二者语义不同；编译器永不自动把前者投影为后者。这是 11 篇 §6”技能只收窄不放大权限”在编译层的落点。
  8. 标准优先，扩展隔离。标准字段在 IR 主体，厂商字段只在 x.<target> 下、只透传给对应目标；严格标准产物中出现任何扩展字段即编译错误。

10. 反模式

  • AP-1 最小公约数 IR：为了每个端都能”完整”表达，把 IR 削到所有目标的交集，渐进式披露、脚本、调用策略全丢。根治：原则 1，IR 是超集。
  • AP-2 静默降级：编译丢了能力但不标注，订阅方拿到一个在某端残缺的技能而不自知；或 essential 能力不可投影时仍产出空壳。根治：原则 2，每次损失进 capability_matrix，essential 不可投影即失败。
  • AP-3 以某一生态文件为真理源：直接把 Claude Code 的 SKILL.md 当源，扩展字段随之流入所有产物，上传 claude.ai 或 Skills API 时失败，其他工具面对陌生字段的行为无法预期。根治：原则 8，源是 IR，严格标准产物单独生成。
  • AP-4 前端编造缺失字段：导入 Cursor 规则时让模型生成触发场景、负面边界、触发样例，然后当作完整技能发布——编造的边界没有经过 08 篇 D-4 的双向核对，编造的样例会让评测自证正确。根治：原则 3，gaps 清单 + experimental 通道。
  • AP-5 双落点失控：为了覆盖所有工具同时写 .agents/skills 与 .claude/skills，之后有人手改其中一份，同一工具从两个目录读到两个不同版本的同名技能。根治：§4.4 的三条落点约束，产物目录禁止手改并由 CI 校验。
  • AP-6 治理接在形态层：审批、扫描、评测挂在 SKILL.md、.mdc 等产物上，每扩一个端就把全部治理动作重做一遍，且导入路径绕过门禁。根治：§6 与附录 B，治理下沉到 IR 层。
