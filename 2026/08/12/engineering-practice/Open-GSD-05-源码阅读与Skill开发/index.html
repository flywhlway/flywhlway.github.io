11.1 Parser 模块：src/frontmatter.cts

重要 Function：parseYamlRegion()

这是一个手写的、不依赖任何外部 YAML 库的解析器（本系列第二篇第二部分已记录 package.json 的 dependencies 只有 @anthropic-ai/claude-agent-sdk 与 ws 两项，不含 js-yaml 之类的库，这里得到了直接印证）。核心结构是一个按缩进层级维护的栈：

逐行处理时：计算当前行缩进 → 把栈弹回到”缩进小于等于栈顶”的层级 → 用正则 ^(\s*)([a-zA-Z0-9_-]+):\s*(.*) 匹配 key: value。三种取值情况分别处理：值为空或为 [（可能是嵌套对象或数组的开始，压入新栈帧）、值形如 [a, b, c]（行内数组，交给 splitInlineArray 做引号感知的切分）、普通标量值（去除首尾引号）。数组项（- item 形式的行）额外处理了一种边界情况——如果当前上下文是一个空对象，就把它就地转换成数组（因为在遇到第一个 - item 之前，解析器还不知道即将到来的是对象还是数组）。

重要 Function：extractFrontmatter() ——一段值得逐字学习的启发式推理

这个函数的文档注释本身就是一篇小型的”如何设计一个不产生误报的启发式检测器”教程，值得完整还原其推理链条：

要解决的问题：文档没有 frontmatter 时返回 {}；frontmatter 围栏被打开但从未闭合时（自 #1882 起）同样返回 {}——这个返回值被有意保留（ADR-1411 的修正案要求保留它，因为改变它会破坏那些把”没有 frontmatter”和”frontmatter 不可用”同等对待的调用方）。#1882 真正新增的是：第二种情况不再是静默的。

判别式为什么不是”围栏未闭合”本身：一份 Markdown 文档，如果第一行恰好是一个”主题分隔线”（---），就会恰好走进这个分支——所以只依据”围栏缺失”来报”损坏”，会把完全正常的 Markdown 也判定为损坏。于是转而把这段未终止的区域喂给这个模块自己的解析器，只有当它解析出两个或更多键时才报告。

为什么是二，不是一：单独一行 key: value 本身就是真正的歧义——--- 后面跟一行 Note: this is a paragraph.（或 Author:、TODO:、See:）是完全正常的技术写作：一条主题分隔线上面接一行带标签的文字，它解析出来恰好是一个键。没有任何文本信号能把这种情况和”写到第一个键就被中断”区分开来，所以阈值被设在”歧义结束”的那个点上。代价是漏报“恰好在第一个键之后被截断的文件”；收益是对一种非常常见的 Markdown 形状保持沉默。这个取舍方向是刻意的，与”零个键”时已经做出的选择一致——因为这个诊断是无条件触发、无法关闭的，在合法 Markdown 上的一次误报，比漏掉一个边界情况更糟。GSD 守护的每一种制品（STATE.md、PLAN.md、ROADMAP.md、SUMMARY.md、agent/command 文档）都携带两个或更多 frontmatter 键，所以现实中的”截断窗口”依然被覆盖到了。

这段推理值得被当作一个通用方法论提炼：设计任何”无法关闭的自动诊断”时，误报的代价与漏报的代价从来不是对称的——一个不可关闭的诊断如果误报，会持续骚扰用户直到有人去改代码；而一个漏报只是”没有额外帮上忙”，回到了不做这项检测之前的状态。因此不可关闭的启发式检测器，应当把阈值设在”歧义消除”而非”检测覆盖率最大化”的位置，这是一条可以直接写进本系列第六篇（第十六部分）自研框架编码规范的原则。

11.2 Dispatcher 模块：src/command-routing-hub.cts

重要 Class（类型）：封闭的 Result 判别联合

配套一个冻结的错误分类常量：

重要 Function：hub.dispatch({ family, subcommand, args, cwd, raw })

源码注释直接列出的不变量（本文认为这是全篇最简洁有力的一段”契约声明”，逐条翻译）：

  • Hub 永远只通过 CJS 处理器路由——没有 SDK 路径（#175：SdkLoadFailed/SdkDispatchFailed 两个错误类型已被移除，Hub 现在是纯 CJS）；
  • Hub 从不向 stdout/stderr 打印，从不调用 process.exit——它是一个纯函数式的调度核心，I/O 副作用留给上层调用者；
  • Hub 从不抛出异常——内部所有 throw 都会被捕获并转换成 { ok:false, kind:'HandlerFailure', message, cause }；
  • kind 分类法是封闭的——调用方对 ERROR_KINDS 的值做 switch，而不是猜测字符串；
  • 每个错误变体只携带自己的类型化载荷（#176）——不存在跨变体的 message/details 逃生舱。

历史演进（#3788 起源 → #175 简化 → #176 类型化 → #177 可观测性）是一处清晰的”逐步收敛到纯净契约”的重构轨迹——最初可能同时支持 CJS 与某种 SDK 双路径（呼应本系列第二篇第二部分记录的 docs/adr/0174-retire-gsd-sdk-package-boundary.md），后来 SDK 路径被整个退役，错误类型也从松散的字符串收敛成了判别联合。

这是”Railway-Oriented Programming”（铁路编程，一种把错误处理内建进类型系统而非依赖异常的函数式模式）在一个 CLI 调度核心里的教科书级实现——对本系列第六篇（第十六部分）设计企业级 Skill Runtime 的调度层而言，这个 Result 类型定义几乎可以原样搬用。

11.3 Runtime 模块：src/state-transition.cts 的表驱动状态机

这是本次研究读到的规模最大、也最能体现”确定性逻辑”复杂度的模块（2,109 行，24 个导出/内部函数）。

重要 Class（数据结构）：FIELD_CLASSIFICATION 表

STATE.md 的每一个字段被归类到一张常量表里，每行两个维度：

source 回答”这个字段的权威值应该从哪来”（正文文本 / 自由生成如时间戳 / 磁盘扫描 / 人工策展），preservation 回答”一次状态转换（Discuss→Plan、Plan→Execute 等）发生时这个字段该怎么办”（值不变就保留 / 每次都重新推导 / 无条件保留旧值）。

重要 Function：getFieldClassification(field) ——第四处防原型污染实例

本系列第四篇（第十部分）归纳过”防原型污染”这条贯穿代码库的纪律出现在 install-profiles.cts（BANNED 数组）与 gsd-prompt-guard.js（用 Map 代替对象字面量）两处；这里是第三处、也是第四种实现手法——显式调用 Object.prototype.hasOwnProperty.call() 而非直接用 in 或裸访问，防止查询 toString/valueOf 这类继承自原型链的”字段名”时返回一个看似合法却完全无意义的函数引用。同一条安全纪律，在这个代码库里至少用三种不同的技术手段（显式排除数组、Map 数据结构、hasOwnProperty 显式调用）反复实现——这比”团队记得要小心”更有说服力：它说明这条规则已经变成了代码评审中会被反复要求的标准动作，而不是依赖某个人记性好。

重要 Function：applyStatePreservation() ——一次三合一去重的真实案例

源码注释直白地记录了这次重构的动机：

吸收了此前散落在 readModifyWriteStateMd（state.cts）里的”同步后保留”逻辑块。一个纯粹的、由字段分类表驱动的实现，取代了此前三处正在漂移的编码（RMW 同步后逻辑块、syncStateFrontmatter、cmdStateBuildFrontmatter 的读路径复制）。现在每一个被保留的字段——progress、status、stopped_at、current_phase_name——都由它在 FIELD_CLASSIFICATION 表里的那一行统一治理，策略变更从”改好几处调用点”变成了”改表里一行”。

这是”多处重复实现同一逻辑、随时间彼此漂移、最终收敛成一张数据表”这一常见工程债生命周期的一个完整真实样本——从”发现漂移”（多个函数各自维护一份相似但不完全一致的保留逻辑）到”消除漂移”（ADR-1769/#1796 把它们统一收编进一张显式的分类表）。本系列第六篇（第十九部分）会把这条模式列为可迁移的最佳实践之一。

Runtime 的另一面：能力覆盖层的运行时组装

本系列第二篇（第三部分）3.11 节已详解 loadRegistry({ includeInstalled }) 的四阶段激活链，此处不重复，只做一次交叉引用——如果把 state-transition.cts 看作”项目状态的运行时”，那么 capability-loader.cjs 就是”能力集合的运行时”：前者在每次状态转换时决定”哪些字段该保留、该重算”，后者在每次工具调用时决定”哪些第三方能力该生效、该跳过”。两者都遵循同一条设计哲学：把”运行时该如何决策”外化成一张显式的、可审计的规则/数据表，而不是散落在调用点的 if-else 里。

11.4 Planner 模块：agents/gsd-planner.md

这是一份 992 行的 Agent Prompt，语义块划分极细（<role>、<documentation_lookup>、<project_context>、<context_fidelity>、<scope_reduction_prohibition>、<planner_authority_limits>、<philosophy>、<discovery_levels>、<task_breakdown>、<verify>、<comment_text_discipline>、<region_scoped_negative_gate>、<dependency_graph>、<scope_estimation>、<plan_format> 等）。挑三处最能体现设计哲学的片段：

  • <context_fidelity> 标题就是”CRITICAL: User Decision Fidelity”（用户决策保真度）——这与本系列第三篇（第五部分）记录的”决策覆盖门禁在 Plan 阶段是阻断型”（#2492）形成呼应：规划者被 Prompt 层面直接告知”用户的决策必须被忠实地落实到计划里”，而门禁机制是这条 Prompt 指令的程序化兜底——Prompt 约束与程序化门禁双管齐下，而不是只靠其中一种；
  • <scope_reduction_prohibition> 标题是”CRITICAL: Never Simplify User Decisions — Split Instead”（绝不简化用户决策——拆分，而不是简化），并要求每套计划都要做”Multi-Source Coverage Audit”（多来源覆盖审计，标注为 MANDATORY）——这条规则直接回应了一种真实的 LLM 失效模式：当一个需求”太复杂”时，模型的本能反应往往是悄悄削减范围而不明说，这条规则把这个本能显式地禁止了，并给出正确替代方案——拆分成更多计划，而不是砍掉部分需求；
  • <planner_authority_limits> 标题是”The Planner Does Not Decide What Is Too Hard”——这是一条授权边界声明：规划者没有权限单方面判断”这个需求太难了、跳过它”，这类判断必须升级给人类（对应本系列第三篇第四部分的 Escalation Gate），而不能由规划者自己悄悄拍板。

三条规则合起来讲的是同一件事的三个角度：规划阶段的最大风险不是”规划者能力不够”，而是”规划者会在无人察觉的情况下悄悄让步”——三条 CRITICAL/MANDATORY 标注的规则，都是在用 Prompt 语言把这种”悄悄让步”的空间堵死。

11.6 Verifier 模块：agents/gsd-verifier.md + src/verification.cts

<adversarial_stance>：一个专门命名的对抗性姿态语义块

970 行的 Verifier Prompt 专门辟出一个 <adversarial_stance> 段落，这与本系列第三篇（第五部分）引用的 plan-checker “不要让通过的维度锚定判断”是同一条设计哲学在 Verifier 身上的对应版本——验证者的默认姿态被 Prompt 层面设定为”假设有问题，去找证据推翻这个假设”，而不是”假设做对了，去确认一下”。

<verification_process>：五步走查，其中 Step 4b 是全系列最精妙的验证技术

  • Step 0：检查是否存在既往验证记录（避免重复劳动）；
  • Step 1（仅初次模式）：加载上下文；
  • Step 2（仅初次模式）：建立”必真断言”（Must-Haves）；
  • Step 3：逐条验证”可观察的事实”（Observable Truths）；
  • Step 3b：核查验证覆盖的例外规则（Verification Overrides）；
  • Step 4：三层级验证制品（源码里有真实的 Bash 伪代码注释——“Import check”/“Usage check (beyond imports)”）；
  • Step 4b：数据流追溯（Data-Flow Trace，”Level 4”）；
  • Step 5：验证关键链路（Wiring）——细分为”Component → API”与”API → Database”两种模式。

Step 4b 值得完整还原其追溯路径（源码内联的 Bash 注释串成的推理链）：

这条追溯路径直接针对的正是本系列第三篇（第五部分）反复强调的”确信地造出一个内部自洽但偏离目标的东西”这个失效模式的一个极具体子类——一个前端组件可以完美渲染、通过所有 UI 层的测试，但如果它渲染的数据其实来自一个写死的 mock 返回值而非真实的数据库查询，普通的”跑起来了/测试通过了”这类验证完全抓不出这个问题，因为从 UI 层看一切正常。Data-Flow Trace 的价值在于它沿着数据流向反向追溯到数据的真正来源，专门用来捕获这类”表面完整、内里空心”的实现。这是本文认为整个 GSD 框架里最值得原样搬进任何 AI 辅助验证流程的一条具体技术，因为它精确命中了 LLM 生成代码时最容易出现、又最难通过表层测试发现的一类缺陷。

verification.cts 的 readVerificationStatus()

（本系列第三篇第四部分已引用其行为，此处补充”为什么”）——它读取第一个 *-VERIFICATION.md 的 frontmatter status，通过 VERIFICATION_ROUTING_TABLE 映射，且明确”fail-closed”：只有 {passed} 这一种状态满足”canonical gate”（规范意义上的通过），missing/unknown/gaps_found/human_needed/stale 全部路由为”未通过”。这是”宁可保守判定为未通过，也不要在状态含糊时误判为通过”的 fail-closed 原则，与本系列第四篇（第九部分）readVerificationStatus 的”任何文件系统错误都无声降级为 missing/非陈旧”（opts.fs 可注入、无抛出契约）合起来看，构成了一套”对外严格 fail-closed、对内部错误 fail-safe（不崩溃）”的一致设计。

11.7 Git Integration 模块：src/worktree-safety.cts（1,812 行）

这是全部七个模块里函数数量最多的一个，梳理出的完整生命周期呈现出一个反复出现的架构模式——“Plan / Execute” 拆分（注意：这与 SDD 五阶段循环里的 Plan/Execute 阶段是两个不同层面的同名概念，此处特指”先算出一个只读的执行计划对象，再单独执行它”这一函数级模式）：

关注点 Plan 函数（只读，产出一个计划对象） Execute 函数（真正调用 git，产生副作用）

波次执行后清理 planWorktreeWaveCleanup() executeWorktreeWaveCleanupPlan()（内部调用 rescueSummaryArtifacts() ——清理前先抢救 SUMMARY.md，防止波次清理误删尚未被读取的执行记录）

为什么要把”计划”和”执行”拆成两个函数：这让计划生成逻辑可以被单元测试而不触碰真实 git（纯函数，输入状态、输出一个描述”打算做什么”的对象），也天然支持”预览/dry-run”能力——调用方可以先看一眼计划对象再决定要不要真的执行。这是”Plan/Execute 分离”这一 SDD 核心哲学，在一个具体子系统的函数签名级别上的自我印证——GSD 不仅在宏观的五阶段循环里应用这个分离原则，在微观的 git 操作封装里也复用了同一个模式。

其余几个函数揭示的细节同样值得记录：

  • reapOrphanWorktrees() + defaultIsPidAlive(pid)——检测”孤儿 Worktree”（其宿主进程已经死掉，但 Worktree 本身还留在磁盘上）的机制，直接对应本系列第三篇（第五部分）讨论过的”会话崩溃后如何安全续跑”这一场景在 Git 层面的具体实现：通过检查记录在案的 PID 是否还存活，来判断一个 Worktree 是不是该被回收；
  • inspectWorktreeHealth() / snapshotWorktreeInventory()——都接受 staleAfterMs/nowMs 参数，说明”陈旧”判定是基于可注入的时钟而非硬编码的 Date.now()，这是让涉及时间的逻辑变得可确定性测试的标准手法；
  • normalizeCleanupManifestEntry() / normalizeCleanupManifest()——对清理清单条目做归一化校验，这类”先归一化再处理”的模式在一个要接受可能不可信/不完整输入的系统里反复出现，与本系列第四篇（第八部分）讨论的”归一化规则”（技能发现契约）是同一种防御性编程思路的不同应用场景。

11.10 本部分小结与下文预告

第十一部分逐模块解读了七类核心源码，三条最值得带走的结论：

  1. “Plan / Execute 分离”不只是 SDD 五阶段循环的宏观哲学，在 worktree-safety.cts 这样的具体子系统里，同一个分离原则被复用到了函数签名级别——先产出只读计划对象，再单独执行，天然支持单元测试与预览；

Step 3 — 写 capability.json

五处必须理解的细节（官方教程原文逐条说明）：

  1. version 在 1.6.0 起是必填项，用 semver；engines.gsd 是一道硬性门禁——GSD 会拒绝在低于 1.6.0 的版本上安装或加载这个能力；
  2. role: "feature" 意味着这个能力给循环增加的是可选行为，不是运行时描述符；一个 feature 能力必须声明 runtimeCompat，{"supported": ["*"]} 意为”支持全部运行时”；
  3. 这是一个 contribution，不是一个 step——contribution 把一段 Prompt 片段注入某个具名的 Agent 角色（into），不需要调度目标；step 则必须携带 ref，且 ref 恰好是 skill/agent/command 三者之一——所以一个”只做纯片段注入”的能力永远是 contribution，这正是为什么这里 steps 留空；
  4. into: "planner" 指定接收这段片段的 Agent 角色——planner 是 plan:pre 这个扩展点所”发布”的角色之一（另外还有 researcher、checker）；这个值必须是该扩展点确实发布过的角色，否则清单校验会失败；
  5. produces 告诉注册表”这个 contribution 会写出 HELLO.md“，供注册表在更复杂的场景下排序 Hook 与检测未满足的依赖；onError: "skip" 意味着即便这个 contribution 失败，循环也会继续——对第一个能力而言这是安全的默认选择。

12.2 参数：$ARGUMENTS 的解析规范

本系列第四篇（第六、七部分）已详解 argument-hint（简短提示）与 argument-instructions（多行详细指导，仅 1/71 使用）的取舍标准——多数场景一行 argument-hint 就够，只有参数结构本身很复杂（如混合整数/小数/字母后缀的 phase 编号 + 可选自由文本）时才值得追加 argument-instructions。写自己的能力/命令时，先尝试用一行 argument-hint 说清楚，写不清楚再升级，而不是一开始就写一大段说明。

12.3 Prompt：contribution 还是 step——本次教程带来的关键新区分

前十一部分（本系列前四篇）聚焦的都是 commands/gsd//skills/ 这条路径的 Prompt 结构（<objective>/<execution_context>/<process> 等语义块）。本次教程揭示了 Capability 路径下平级但不同的 Prompt 组织方式——contribution 与 step 的选择：

  • 只需要往某个 Agent 的 Prompt 里”塞一段话” → 用 contribution，指定 into（目标角色）+ fragment（片段路径）；
  • 需要真正调度一个具体的技能/子代理/命令去执行动作 → 用 step，必须携带 ref，且 ref 恰好是 skill/agent/command 三者之一。

判断标准：问自己”这次扩展是要改变 Agent 怎么想，还是要让某件事真的发生“——前者是 contribution，后者是 step。hello-note 只是往规划者脑子里加了一句提醒，所以是纯 contribution；如果你想让”生成 HELLO.md”这件事由一个专门的子代理去做（而不是指望规划者读了提示后顺手写），就该用 step 去调度一个 Agent。

12.4 模板：片段的”引用 + 加载时物化”机制

gsd-core/templates/（34 个文件，本系列第二篇第二部分已详解）是规划制品模板，与 Capability 的 Prompt 片段是两套不同的机制，不要混淆。Capability 片段的模板性体现在：capability.json 里只写 fragment: { path: "fragments/plan-pre.md" }（一个相对路径引用），加载时由能力系统读入文件内容并写进注册表的 fragment.inline 字段——这与本系列第二、三篇（第三、四部分）反复强调的”惰性加载/渐进式披露”是同一哲学：manifest 本身保持精简（只存路径），真正的文本内容只在被加载的那一刻才物化。

12.5 测试：六大测试严谨性契约

TESTING-STANDARDS.md（依据 ADR-456）定义了每一个测试都必须满足的六条契约：

# 契约 一句话含义
1 检验真实代码，而非源码或输出文本 调用导出的函数，或跑 CLI 并解析结构化输出；绝不 readFileSync 源文件去断言其文本内容，也不对原始 stdout/stderr 字符串做断言（退出码除外）——由自定义 ESLint 规则 local/no-source-grep 强制
2 不做”永真断言” 断言的左值必须在被测系统出现合理缺陷时有可能失败；assert(true) 或断言一个此前已被无条件赋值的变量”不是 undefined”都不算数
3 不做”永过测试” （标题清单已列出，第 3 条与第 2 条呼应，强调测试必须有真正失败的可能路径）
4 测试所声称的那条路径 测试标题声称测的是什么，断言就必须真的覆盖那条路径
5 完整的 Mock Mock 掉的依赖必须覆盖被测代码实际会用到的全部接口面，而非只覆盖”恰好让测试跑过”的那一小块
6 为”负空间”写反向测试 不仅要测”该发生的事发生了”，也要测”不该发生的事确实没发生”

TEST-EXAMPLES.md 给出的具体范例之一是 “CLI 负向矩阵”——用真实的子进程执行（spawnSync）而非拼接 shell 字符串去测试恶意/边界输入（空 phase、路径穿越 ../../outside、重复标志、看起来像标志的值如 --weird），每一条都断言一个具体的 expectedReason 错误码。”用真实进程执行、把危险值当作 argv 元素传入而非拼进 shell 字符串”这条具体写法，与本系列第四篇（第六、十部分）反复出现的”消毒/边界校验必须具体到可执行细节”是同一种工程纪律的测试侧体现。

12.8 版本升级

VERSIONING.md 定义的是 GSD Core 自身的发版策略（三级：Patch/Minor/Major，对应 npm 的 latest/next 两个 dist-tag，主版本走 beta 预发布、次版本走 rc 预发布），这套体系不直接约束你自己写的 Capability，但理念可以照搬：

  • 你的 capability.json 的 version 应遵循语义化版本；
  • engines.gsd 区间应该诚实反映”这个能力实际测试过的 GSD 版本范围”，而不是随手写一个 >=0.0.0——本系列第二篇（第三部分）已述，GSD 自身升级后会在加载期重新校验这个区间，不满足的能力会被跳过并响亮告警（而不是静默失败）。

12.9 兼容性

runtimeCompat: { supported, unsupported } 字段（12.1 节已示范 {"supported": ["*"]}）用于声明这个能力兼容哪些宿主 Runtime——如果你的能力依赖某个特定宿主才有的行为（比如某个仅 Claude Code 支持的 Hook 事件），应该把 unsupported 列出来，而不是让它在不兼容的宿主上默默产生未定义行为。这与本系列第四篇（第六部分）6.4 节”插件提供的技能形态仅 Claude 可用，其他运行时跳过并告警”是同一套”显式声明兼容边界，而非隐式假设全宿主通用”的纪律。

12.10 最佳实践清单（汇总本教程与前十一部分）

  1. 先问”这是 contribution 还是 step”，别一上来就假设需要调度一个完整 Agent；
  2. onError 默认写 "skip"，除非你确实需要一个失败就要整体中止的强约束（那种情况该用 gate，本系列第二篇第三部分已述）；
  3. description（若你的能力包含 skills）严格控制在 100 字符内，参考竖线关键词标签写法（本系列第四篇第七、九部分）；
  4. 写完 capability.json 后先跑 gsd loop render-hooks <point> --raw 确认接线，再去跑真实会话；
  5. 版本号与 engines.gsd 区间要诚实，不要为了”图省事”写成通配；
  6. 测试要覆盖负空间——想清楚”这个能力在什么输入下应该拒绝/跳过”，并为之写断言；
  7. 能不写可执行代码就不写——纯声明式能力（只有 Prompt 片段 + Hook 声明）不需要经过信任提示，能大幅降低你自己团队采纳的门槛。

12.11 本部分小结与下文预告

第十二部分完整复现了官方”Hello Skill”教程的全部七步，并把参数、Prompt、模板、测试、调试、发布、版本、兼容性八个维度逐一对应到本文前十一部分（本系列前四篇）已建立的概念体系上。contribution vs step 的区分，以及 gsd loop render-hooks --raw 这条调试命令，是本部分两个最具体、最可立即上手使用的收获。

下一部分（第十三部分 · 高级 Skill）将探讨多 Skill 组合、Skill Graph、Skill Chain、Composite/Dynamic/Conditional/Context-Aware/Domain/Enterprise Skill 这些更高阶的设计模式——沿用本系列第一篇（第〇部分）建立的纪律，凡是 GSD 源码中能找到直接对应机制的，给出实证；凡是需要从多处证据综合推导的，明确标注为”推导”而非”官方原文”。

第十三部分 · 高级 Skill

本部分讨论九个高阶概念（多 Skill、Skill Graph、Skill Chain、Composite Skill、Dynamic Skill、Conditional Skill、Context Aware Skill、Domain Skill、Enterprise Skill）。GSD 源码里没有任何一处使用这些确切英文术语——这九个词是分析性的概念框架，不是 GSD 的原生词汇。本部分对每一个概念都做同一件事：先诚实说明”GSD 里最接近的真实机制是什么”，再展开该机制的源码依据；凡是本文自己做的归纳、类比或推导，都会显式标注，不会包装成”GSD 官方设计”。

13.1 多 Skill 组合 / Skill Graph：两张真实存在的图

13.2 Skill Chain：workflow 内部的 Agent 派生序列

GSD 没有”Skill 调用 Skill”意义上的 Chain（本系列第四篇第六部分已述，Skill 委托后自身生命周期即告终）。最接近”Chain”这个概念的真实机制，是一个 workflow 内部按顺序派生多个 Agent、通过磁盘制品传递状态的序列——本系列第三篇（第五部分）详解的 plan-phase 三段式（Researcher → Planner → Plan-Checker，带修订循环）就是最典型的样本。

本文的推导（非 GSD 原文用语）：如果把”一次 workflow 编排”整体看作一条 Chain，那么链上每一环的”输入契约”就是磁盘上的某份具体制品（RESEARCH.md→PLAN.md→校验结果），这与传统”Skill A 的输出直接管道给 Skill B”的 Chain 概念在效果上等价，但实现机制完全不同——GSD 的链条环环相扣靠的是”共享文件系统 + 编排器路由”，而不是”技能之间直接互相调用”。这个区别很重要：它意味着链条上任意一环可以在完全不同的会话里执行（本系列第三篇第四部分讨论过的”跨会话续接”），因为环与环之间不存在运行时的直接耦合，只有文件系统上的间接耦合。

13.3 Composite Skill：Capability 的多贡献点组合

capability.json 允许一个能力同时声明 skills、agents、commands、hooks、steps、contributions、gates 多个字段——一个能力包本身就是一个”复合体”，这是 GSD 里最接近”Composite Skill”的真实机制。第十二部分的 hello-note 是最简单的复合（只用了 1 个 contributions 条目）；本系列第二篇（第三部分）引用过的 graphify 能力则复合了 skills: ["graphify"] + commands（family: "graphify" 路由到 graphify-command-router.cjs）+ 一个 activationKey 控制的 config 项——同一个能力包，同时是一个 Skill 的提供者、一个 CLI 命令族的提供者、一个配置项的提供者。

13.4 Dynamic Skill：gsd-spike --wrap-up——一个真实的、源码实证的动态技能生成机制

这是本部分含金量最高的一节——GSD 确实有一个把”探索过程的产出”自动固化成一个新技能的真实机制，源码：commands/gsd/spike.md + gsd-core/workflows/spike-wrap-up.md。

完整流程：

flowchart TB
    A["/gsd:spike 'some idea' --quick"] --> B["快速实验，产出 .planning/spikes/&lt;NNN&gt;/README.md<br/>（含 YAML frontmatter：验证状态）"]
    B --> C{"验证结果"}
    C -->|"VALIDATED"| D1["提供已证实的模式"]
    C -->|"PARTIAL"| D2["提供受约束的模式"]
    C -->|"INVALIDATED"| D3["提供地雷与死胡同——<br/>明确记录'此路不通'"]
    D1 --> E["/gsd:spike --wrap-up"]
    D2 --> E
    D3 --> E
    E --> F["读 .planning/spikes/MANIFEST.md<br/>+ 遍历全部 spikes/*/README.md"]
    F --> G{"项目已有<br/>spike-findings-* SKILL.md?"}
    G -->|"是"| H["读其 processed_spikes 元数据<br/>过滤掉已处理的 spike<br/>——只处理新增的"]
    G -->|"否"| I["全部 spike 都是候选"]
    H --> J["按 feature area 自动分组<br/>（依据 tags/名称/related字段/内容）"]
    I --> J
    J --> K["每组合成生成技能里的一份 reference 文件"]
    K --> L["写出 ./.claude/skills/spike-findings-[project]/SKILL.md<br/>（项目本地，持久化）<br/>+ .planning/spikes/WRAP-UP-SUMMARY.md"]

四处值得特别记录的设计细节：

  1. 增量而非重建：每次 --wrap-up 只处理上次生成之后新增的 spike（靠读取已生成 SKILL.md 里的 processed_spikes 元数据做差集）——这个动态技能会随着项目积累的探索次数持续生长，而不是每次都从零重新合成；
  2. 连”此路不通”也被固化：INVALIDATED 的 spike 不会被丢弃，而是作为”地雷与死胡同”被写进生成的技能里——这意味着这个动态技能不仅告诉未来的 Agent “怎么做”，还告诉它”已经试过且确认行不通的路”，这对防止未来的 Agent 重复踩同一个坑有直接价值；
  3. 按语义分组而非按时间顺序：多个 spike 依据 tags/名称/related 字段与内容被自动归类到同一个 feature area，每组产出生成技能里的一份独立 reference 文件，而不是简单地把所有 spike 记录顺序拼接；
  4. 落地位置是项目本地、非官方生成脚本产物：与本系列第二篇（第二部分）讨论的”declare→generate→lint 漂移校验”三件套（那是 GSD 自身仓库治理自己的 44 个能力/71 个技能的机制）不同，这里生成的 spike-findings-[project] 技能是面向单个使用者项目、没有 CI 漂移校验保护的产物——它的正确性依赖 spike-wrap-up 这个 workflow 本身的实现质量，而不是构建期的自动化校验。

这是本文认为最值得迁移到设备诊断平台的一个具体机制：如果诊断技能生态里也存在”先探索性诊断、再固化为可复用诊断技能”的场景（例如工程师对一类新出现的故障做了几次探索性排查，想把排查经验固化成技能），spike --wrap-up 提供了一个已经被验证可行的、含增量处理 + 三态经验分类（验证过的模式/受限模式/死胡同）+ 自动语义分组的现成范式，比从零设计一套”经验固化机制”要可靠得多。

旁注（划界，呼应本系列第一篇第〇部分）：生态里还存在一个第三方插件 Tibsfox/gsd-skill-creator，其定位是”观察你在 GSD 生命周期内的工作模式（工具序列、文件模式、纠正行为），检测到重复出现 3 次以上的模式后建议生成新技能”——这是一个概念上相似但实现完全独立的第三方”动态技能生成”尝试，不属于 GSD Core 官方仓库，本文不对其源码做核实，只做生态背景提及，避免读者把它误当作 GSD Core 自带能力。

13.5 Conditional Skill：三层条件化生效机制

GSD 里”技能/能力是否生效”从来不是非黑即白的静态开关，而是叠加了至少三层条件判断：

层级 机制 源码依据
功能开关条件 capability.json 的 activationKey + config 字段（如 graphify.enabled，默认 false） 本系列第二篇（第二部分）已引用的 graphify/capability.json
版本兼容条件 engines.gsd 区间——加载期二次门禁，不满足则跳过并告警 本系列第二篇（第三部分）3.11 节、第十二部分 12.8 节
运行时兼容条件 runtimeCompat.supported/unsupported 第十二部分 12.9 节

本文的归纳（非 GSD 原文用语）：这三层条件分别回答”用户是否主动打开了它””版本是否兼容””宿主是否兼容”三个正交的问题，任何一层不满足都会导致该能力不生效但不报错崩溃（本系列第二篇第三部分详述的”fail-open 但响亮告警”原则在此再次适用）——这是一套天然支持”Conditional Skill”这一诉求的、已经过 Capability 系统统一实现的机制，不需要在 Skill 层再造一套条件判断。

13.6 Context Aware Skill：两处真实的上下文感知机制

  • 自适应上下文增强（本系列第一篇第一部分、第二篇第三部分已详解）——当 context_window >= 500000 时，Executor/Verifier 会收到比 200K 窗口下更丰富的上下文（前序波次 SUMMARY.md、REQUIREMENTS.md 等），这是”同一个 Agent 角色，依据宿主模型的上下文容量，感知并调整自己实际接收的信息量”；
  • discuss-phase 的 assumptions 模式（本系列第三篇第五部分已详解）——子代理主动读 5–15 个代码库文件、依据代码库现状形成”带证据与置信度”的假设，是”依据项目的实际代码上下文，动态生成问题/假设“的具体样本。

13.7 Domain Skill：capabilities/ 目录本身就是按领域组织的

本系列第二篇（第二部分）已完整列出 44 个能力子目录，天然分成两类——按宿主 Runtime 划分的领域（claude/codex/cursor/codebuddy 等 22 个）与按横切功能划分的领域（security/tdd/code-review/ai-integration 等 22 个）。每个能力还携带一个 tier 字段（hello-note 示范为 "standard"，graphify 为 "full"）——本文推断（未在源码中找到 tier 的完整取值枚举与语义文档，如实标注）这大概率是一种”能力分级”机制，用于区分核心/标准/完整等不同重要程度的领域能力，具体的分级语义留待读者查阅 docs/reference/capability-manifest.md（本文未逐段核实）自行确认。

13.8 Enterprise Skill：信任模型全套 + 企业锁定杠杆

“企业级”在 GSD 里对应的不是某一种特殊的 Skill 类型，而是本系列第二篇（第三部分）已完整展开的整套 Capability 信任模型——同意（Consent）+ 完整性（Integrity）+ 可逆性（Reversibility）三重屏障、”第一方永远赢”的覆盖规则、strictKnownRegistries 三态开关（未设=许可制/空数组=锁死仅本地/非空数组=按 host 白名单）、以及本系列第一篇（第一部分）提及的 Reviewer Lane Registry（第三方 Reviewer Lane 的公开目录，供企业按 docs/reference/gsd-capability-command.md——本文未逐段核实——的流程安装受信的第三方评审工具）。

本文的归纳：一个”企业级”能力，实践中应该同时具备——诚实声明的 engines.gsd/runtimeCompat 边界（12.8/12.9 节）、tier 定位清晰、通过 strictKnownRegistries 可被管理员纳入白名单管控、可执行面（若有）经过 SHA 完整性定版、且可通过 gsd capability remove 完全撤销不留孤儿状态。这五点合起来，就是把本系列第二篇与本篇（第三、十二部分）的具体机制拼装成一份”企业能力自查清单”。

13.9 本部分小结与下文预告

第十三部分对九个高阶概念逐一做了”最接近的真实机制”映射，其中 gsd-spike --wrap-up 是本部分唯一一处完整的、源码实证的、名副其实的”动态技能生成”机制，含增量处理、三态经验分类（验证/受限/死胡同）、自动语义分组三个具体设计点，是本文认为最值得直接迁移到设备诊断平台的单一机制。其余概念（Graph/Chain/Composite/Conditional/Context-Aware/Domain/Enterprise）在 GSD 中都能找到对应的真实机制，但都是本文基于源码证据做的归纳性映射，而非 GSD 官方使用这些确切术语。
