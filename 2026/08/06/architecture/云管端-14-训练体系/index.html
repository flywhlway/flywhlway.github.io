14 · 训练与评测闭环（Training System）

文档类型：技术白皮书 · 训练闭环专章
对应图示：埋点数据回流 → 大数据平台 → （推断设计）评测 → 训练 → 模型上线
核心判断：训练不是这个闭环里最重要的环节。对企业 AI 平台而言，闭环价值排序是：知识补全 > 提示词与检索调优 > 数据集与评测 > 微调 > RLHF

1.1 为什么训练排在后面

改进手段 见效周期 单次成本 典型效果提升 可回滚性
知识补全 天~周 极低 直接消除某类失败 立即
检索参数调优 天 极低 召回率 +10~30% 立即
提示词优化 小时 极低 格式/风格问题直接解决 立即
上下文压缩与预算 天 低 成本 -20~40% 立即
SFT 微调 周~月 中 风格与术语对齐 需重新部署
DPO 月 中高 偏好对齐 需重新部署
RLHF 季度 极高 精细对齐 困难

多数企业的正确判断是：不做 RLHF。投入产出比远低于把 RAG 与上下文质量做好。原图把「大数据平台」画为埋点回流终点而未画出复杂训练链路，这一克制的表达本身就是合理的架构判断。

2. 反馈数据体系

2.1 显式与隐式反馈

类型 信号 数据密度 可靠性 用途
显式 点赞 / 点踩 极低（<2%） 高 高质量偏好对
显式 文字反馈 极低 高 问题定位
显式 用户纠正（”不是这个，我是说…”） 低（3–8%） 极高 最优质的偏好对来源
隐式 重问率 高 中高 负样本挖掘
隐式 打断率 高 中 回答过长或不对路
隐式 追问轮次 高 中 效率评估
隐式 会话放弃 中 中高 失败代理
隐式 任务完成（业务信号） 中 高 最终目标达成
隐式 采纳（用户按建议操作） 中 高 正样本

“用户纠正”是数据金矿。当用户说”不对，我是问 X”时，系统同时得到了：① 一个负样本（原答案）② 正确意图（用户澄清）③ 一个天然偏好对。这类样本应 100% 采集并优先进入标注队列。

2.3 根因分类（决定用哪种改进手段）

根因 判定依据 正确修复手段 错误做法
意图误判 intent 与用户真实意图不符 意图归并 + 反例扩充 + 分类器重训 ❌ 微调生成模型
检索未命中 empty_recall 或召回片段无关 知识补全 + 查询改写 + 混合检索调优 ❌ 微调
检索命中但答偏 有正确片段但答案没用上 提示词强化引用约束 + Rerank ❌ 补知识
记忆错误 召回了错误记忆 回溯干预 + 抽取策略收紧 ❌ 微调
工具选错 tool_ids 不含正确工具或选错 Skill 描述优化 + 反例 + 工具集裁剪 ❌ 微调
格式/风格不符 内容对但形式不符要求 提示词优化 → 仍不行才 SFT 一上来就 SFT
事实幻觉 无引用支撑的编造 强制引用 + 拒答策略 + 知识补全 ❌ 微调（微调不能消除幻觉）
偏好不对齐 内容正确但用户不喜欢 DPO SFT（SFT 学不到”不要什么”）

这张表是训练体系最重要的产出。绝大多数团队的错误在于：遇到任何效果问题都想微调。实际上上表中只有两行（格式风格、偏好对齐）真正适合微调，其余六行微调都是错误手段且会浪费数月时间。

3. 评测体系

3.1 三套集分离（与 09 文档一致，此处展开管理机制）

集合 规模 维护者 更新频率 访问权限
公开集 200–500 算法/研发 随时 全员可见
回归集 300–800 质量团队 月度扩充 可见但不可用于调优
盲测集 200–500 独立质量角色 季度扩充 调优人员不可见

管理机制：

flowchart TB
    NEW["新增候选样本<br/>来自负反馈与线上挖掘"] --> LB["人工标注"]
    LB --> RV["交叉复核（双人）"]
    RV --> SP["分配"]
    SP -->|"60%"| P1["公开集"]
    SP -->|"25%"| P2["回归集"]
    SP -->|"15%"| P3["盲测集（隔离存储）"]
    P1 --> TUNE["日常调优"]
    P2 --> GATE["发布门禁"]
    P3 --> AUDIT["季度真实评估"]
    AUDIT --> CMP{"公开集提升 vs 盲测集提升"}
    CMP -->|"差距大"| OF["判定：过拟合评测集<br/>需扩充与轮换"]

过拟合检测方法：若公开集指标提升 15% 而盲测集只提升 2%，说明优化在拟合评测集而非真实提升。这个对比是评测体系健康度的唯一可靠信号。

3.2 评测维度矩阵

层 指标 自动化程度 频率
检索 Recall@K、MRR、NDCG、空召回率 全自动 每次变更
生成 答案正确性、忠实度、引用准确率 LLM-as-Judge + 人工校准 每次变更
工具 工具选择准确率、参数正确率 全自动（有标注） 每次变更
意图 分类准确率、混淆矩阵 全自动 每次变更
安全 红队用例通过率、误拦截率 半自动 每次变更 + 周度
稳定性 同输入重复差异率 全自动 每次变更
端到端 任务完成率、满意度 人工 月度
成本 单任务 Token、单位业务成本 全自动 持续

3.3 LLM-as-Judge 工程化

flowchart LR
    J1["评分标准 rubric<br/>明确分档定义"] --> J2["参考答案<br/>金标"]
    J2 --> J3["强模型评判<br/>不与被评模型同源"]
    J3 --> J4["结构化输出<br/>分数 + 理由 + 引用依据"]
    J4 --> J5["人工校准<br/>Kappa ≥ 0.7 才采信"]
    J5 --> J6["定期抽检 10%"]
    J6 -->|"一致性下降"| J1
陷阱 表现 规避
自评偏袒 用同一模型评自己，分数虚高 用不同厂商强模型评判
无 rubric 分数不稳定、不可比 明确分档定义与扣分项
位置偏见 偏好排在前面的答案 A/B 位置随机交换
长度偏见 偏好更长的答案 rubric 明确”简洁性”权重
未校准 与人工判断不一致但被当真 Cohen’s Kappa 验证

4. 数据集构建

4.1 SFT 数据集

要点 说明
来源优先级 线上高质量真实对话 > 人工编写 > 合成数据
筛选标准 用户正反馈 + 任务完成 + 人工复核通过
数据量 风格对齐 1k–5k 条足够；不需要海量
多样性 覆盖全部意图类别，避免头部意图占比过高
去重 语义去重（近似样本会导致过拟合）
授权校验 必须校验数据是否在用户授权范围内
PII 剔除 训练集必须无 PII
血缘记录 每条样本记录来源 trace_id，支持事后撤回

4.2 偏好数据集（DPO）

flowchart TB
    P1["来源一：用户纠正<br/>原答案=rejected，纠正后=chosen"] --> DS["偏好对数据集"]
    P2["来源二：点赞/点踩对<br/>同问题两次回答"] --> DS
    P3["来源三：人工标注<br/>对同一问题的多个候选排序"] --> DS
    P4["来源四：模型生成多候选<br/>+ Judge 排序"] --> DS
    DS --> Q["质量校验"]
    Q --> Q1["chosen 与 rejected 差异是否有意义<br/>（避免仅措辞差异）"]
    Q --> Q2["chosen 是否真的更好<br/>（人工抽检）"]
    Q --> Q3["是否覆盖多样偏好维度<br/>（简洁性/准确性/语气/结构）"]
要点 说明
数据量 2k–10k 偏好对可见效
差异有意义 若 chosen 与 rejected 只是措辞不同，模型学不到有效信号
维度平衡 不要全是”更简洁”的偏好，否则模型会过度简化
合成数据谨慎 模型生成 + 模型排序的数据存在自我强化偏差

4.3 合成数据的正确用法

适用 不适用
扩充长尾意图的训练样本 替代真实数据作为主体
生成评测集的干扰项 生成金标答案（需人工确认）
数据增强（同义改写扩充） 偏好数据（自我强化偏差）
冷启动阶段快速起量 成熟阶段的主要来源

5. 训练方法

5.1 方法对比

方法 学什么 数据需求 算力 周期 适用判定
提示词优化 无（不改权重） 0 0 小时 先做这个
少样本示例 无 几十条 0 小时 格式问题优先尝试
SFT（LoRA） 模仿好答案 1k–5k 对 单卡~多卡 天~周 风格、术语、格式稳定不达标时
SFT（全参） 同上，更彻底 10k+ 多卡 周 极少需要
DPO 偏好（好与不好的差异） 2k–10k 对 单卡~多卡 周 需要”学会不要什么”时
RLHF（PPO） 精细对齐 大量偏好 + RM 大规模 月~季 企业平台通常不需要
Reward Model 打分能力 大量偏好 多卡 周 可作自动评测器
蒸馏 把大模型能力压进小模型 大模型输出 多卡 周 端侧 SLM 的关键手段

5.2 端侧小模型的蒸馏路径（本架构重点）

flowchart LR
    T["教师：云端大模型"] --> D1["在真实线上分布上生成标注<br/>意图/槽位/压缩结果"]
    D1 --> D2["质量筛选<br/>用金标集验证教师输出"]
    D2 --> D3["学生：端侧小模型 SFT"]
    D3 --> D4["量化 int4/int8"]
    D4 --> D5["端侧评测<br/>精度损失 + 延迟 + 内存"]
    D5 --> D6{"达标?"}
    D6 -->|"否"| D7["调整：模型尺寸 / 量化档位 / 任务拆分"]
    D7 --> D3
    D6 -->|"是"| D8["按算力等级分档打包下发"]
要点 说明
用真实分布 蒸馏数据必须来自线上真实查询分布，而非公开数据集
单任务专精 端侧模型不追求全能，每个任务单独蒸馏（意图/抽取/压缩）效果远好于通用
一基座多 LoRA 共享基座节省内存
量化后评测 量化必然掉精度，必须在量化后重新评测
分档 高/中/低算力设备用不同尺寸

端侧蒸馏是本架构最值得投入的训练方向：它同时改善延迟（390 ms vs 1225 ms）、成本（端侧推理零边际成本）、隐私（不上云）与可用性（离线可用）。收益是四重的，而云端微调通常只改善单一维度。

6.2 发布流程（与 10 文档 7.1 呼应，此处补充门禁细节）

flowchart TB

门禁必须是阻断式而非提示式。若评测不通过只是”警告”，则在项目压力下必然被跳过。门禁的价值在于它不可绕过。

7. CI/CD 与 LLMOps / AgentOps

7.1 变更类型与对应流程

变更类型 触发的门禁 灰度要求 回滚方式
Prompt 模板 回归集 + 稳定性 5% → 100% 配置回滚（秒级）
检索参数（切分/权重/TopK） 检索指标 + 端到端 5% → 100% 配置回滚
知识内容 检索指标 + 抽样人工 灰度知识版本 知识版本回滚
Skill 描述 工具选择准确率 5% → 100% 配置回滚
意图分类器 分类准确率 + 混淆矩阵 5% → 100% 模型版本回滚
模型版本 全部 5 道门禁 + 影子流量 5% → 50% → 100% 网关权重回滚
Agent 代码 回归集 + 单元测试 常规发布流程 部署回滚
围栏策略 拦截率 + 误拦截率 可全量（安全优先） 配置回滚
端侧模型/知识包 端侧评测 + 灰度设备集 分批设备灰度 端侧本地回滚

关键洞察：AI 平台中大部分变更不是代码变更（提示词、检索参数、知识、Skill 描述、模型版本）。因此传统 CI/CD 覆盖不到这些变更。必须把它们纳入统一的”变更 → 评测 → 灰度 → 回滚”流程，否则会出现”代码严格管控，但改一句提示词就能全量影响用户”的失衡状态。

9. 指标与目标

指标 定义 目标（推断设计）
知识缺口修复周期 空召回查询到知识生效 ≤ 7 天
知识覆盖率 1 - 空召回率 ≥ 95% 且持续上升
评测自动化率 自动评测覆盖的维度比例 ≥ 80%
回归门禁执行率 变更经过门禁的比例 100%
门禁拦截有效率 被拦截变更中真实有问题的比例 ≥ 70%（过低说明门禁过严）
公开集 vs 盲测集提升差 过拟合检测 差距 ≤ 3×
金标集扩充速度 月新增标注样本 ≥ 100 条
负反馈样本利用率 进入标注队列的比例 ≥ 90%
端侧模型精度保持率 量化后 vs 量化前 ≥ 95%
模型发布回滚率 上线后回滚的比例 ≤ 10%

10. 风险与治理

风险 影响 治理
把所有问题都当微调问题 浪费数月且效果不涨 强制根因分类（2.3 表）+ 分类后才决定手段
评测集过拟合 指标涨体验不涨 三集分离 + 盲测集独立维护 + 提升差检测
门禁被绕过 劣化变更全量上线 阻断式门禁 + 绕过需高层审批与记录
训练数据超出授权范围 合规风险 授权校验 + 数据血缘 + 可撤回机制
PII 进入训练集 严重合规事故 自动 PII 扫描 + 人工抽检 + 血缘可追溯
合成数据自我强化偏差 模型能力收窄 合成数据比例上限 + 真实数据为主
LLM-as-Judge 未校准 评测结论错误 Kappa 验证 + 定期人工抽检
Prompt 变更不走门禁 一句话改动影响全量用户 提示词纳入统一变更流程
端侧量化后精度未评测 端侧体验劣化不可见 量化后强制端侧评测
失败案例无人负责 闭环空转 失败案例池 + 根因派单 + owner 机制
微调模型无法回滚 故障时间长 保留上版本 7 天 + 网关权重回滚

11. 演进路线

阶段 训练闭环演进 退出准则
阶段一 三集分离建立；根因分类表落地；空召回 → 知识工单闭环；提示词与检索参数纳入变更流程；负反馈 100% 采集 知识缺口 ≤7 天修复；所有变更有门禁
阶段二 回归门禁接入 CI 且阻断式；LLM-as-Judge 校准；偏好对自动构造（用户纠正）；端侧蒸馏 pipeline 建立；影子流量机制 评测自动化 ≥80%；端侧模型可迭代
阶段三 SFT/DPO 常态化（月度节奏）；失败案例自动派单；成本-质量帕累托优化；Reward Model 作为自动评测器；端侧模型按算力分档自动构建 改进从人工驱动转为数据驱动；模型迭代不依赖外部供应商
