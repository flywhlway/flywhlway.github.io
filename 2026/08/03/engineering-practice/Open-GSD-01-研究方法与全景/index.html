第〇部分 · 研究方法与信息来源说明

0.1 研究对象界定

通常所说的 “Open-GSD”，经检索与源码核实，指向 GitHub 组织 open-gsd 名下的核心仓库 open-gsd/gsd-core（npm 包名 @opengsd/gsd-core，官网 opengsd.net）。这是一个 MIT 许可、TypeScript/Node.js 编写、以 Markdown Prompt 文件为主体形态的”元框架”（meta-framework），核心定位是：

通过一套上下文工程（Context Engineering）与规范驱动开发（Spec-Driven Development）的纪律，把 Claude Code、Codex、Cursor 等 AI 编程 Agent 的长期自治能力变得可靠。

本系列以这一仓库的 next 分支（研究快照见本篇开头）作为唯一的一手信息源，所有架构结论、目录职责、字段含义均来自对该仓库源码与官方文档的直接阅读，而非对 Open-GSD 的概括性转述。

0.2 版本谱系与生态定位（关键澄清）

open-gsd 这一名字下的生态并不是单一产品，而是至少 5 个独立代码库的集合，命名相近但架构、版本号、产品形态完全不同。这是深入研究前必须先厘清的陷阱——如果不做这层澄清，后续对”目录结构””Skill 数量””命令语法”的任何具体论断都可能张冠李戴。经逐仓库核实，谱系如下：

项目 仓库 定位 与本文研究对象（GSD Core）的关系
GSD Core（本文唯一研究对象） open-gsd/gsd-core 不是独立 Agent，是叠加在宿主 Agent Runtime 之上的 Meta-Prompting / Context Engineering / Spec-Driven Development 框架；以 Skill、Command、Agent、Workflow 等 Markdown Prompt 文件为主体，配合一个 Node.js CLI 工具（gsd-tools.cjs）做确定性状态管理 ——
GSD Pi open-gsd/gsd-pi 独立的本地优先编码 Agent 产品：自带 TUI 终端界面、可选 Web 控制台（gsd --web）、多 Provider 模型路由（可以把 Claude Code、Cursor Agent 当作”外部 CLI Provider”来调用）、自有的 .gsd/ 项目记忆体系与安装器 @opengsd/gsd-pi 同一 GitHub 组织下的姊妹项目，但代码库、版本号（近期重新从 1.0.0 起跳，目前已到 v1.11.0）、产品形态均与 GSD Core 不同。GSD Pi 是一个可以运行的 Agent 程序本身，GSD Core 是喂给别的 Agent 程序吃的”纪律说明书”——这是两者最本质的区别，本文后续不会混用
GSD 2 gsd-build/gsd-2 历史版本，是早期 get-shit-done-cc 之后、open-gsd 组织成立之前的过渡形态 仓库 README 已显式声明”项目现已在 Open GSD 仓库以 GSD Pi 的形式延续”，代码不再更新；GSD Core 文档树中仍保留 docs/how-to/migrate-from-gsd-2.md 供历史用户迁移，侧面印证 GSD Core 与 GSD 2 存在血缘但已完全重写
get-shit-done-cc（旧 npm 包名） —— 项目最早期的 npm 分发名 GSD Core 文档中的 docs/cleanup-get-shit-done-cc.md 专门处理”从旧包名迁移到 @opengsd/gsd-core 后遗留产物”的问题，是包名演进的直接证据
gsd-opencode（rokicool） rokicool/gsd-opencode 社区维护的 OpenCode 专用移植版（作者署名 “by TACHES”） GSD Core 官方 README 的 Community 表格中明确收录为 “Original OpenCode port”，属独立第三方仓库，非官方组织资产
gsd-skill-creator（Tibsfox） Tibsfox/gsd-skill-creator 第三方”学习层”插件：观察用户在 GSD 生命周期内的操作模式（工具序列、文件模式、纠正行为），用 N-gram + DBSCAN 聚类检测重复模式，达到阈值后建议自动生成新 Skill / Agent README 中明确写明”不替代任何 GSD 功能，只是观察你在 GSD 生命周期内的工作方式”，是生态圈内的第三方增强工具，不属于官方仓库范围

为什么这层区分很重要：讨论 GSD 的框架定位（Framework Position）时，需要分析它与 Claude Code / Codex / Cursor / Gemini CLI / OpenCode / Copilot 的关系——这些确实都是 GSD Core 的宿主对象。但如果不做上表的澄清，很容易把 GSD Pi（一个独立 Agent 产品，拥有自己的 TUI 和模型路由）的特性错误地归到 GSD Core 头上，或者反过来把 GSD Core 的”寄生式”安装模型套到 GSD Pi 上——这是本系列在后续 19 个部分中会持续保持警惕的一条红线。

此外，行业内还存在与 GSD 同一品类（”驱动编码 Agent 的元框架”）但代码库完全独立、不属于 open-gsd 组织的竞品，例如 Superpowers（侧重测试驱动的 Skill 触发）与 GSTACK。这些将在 1.6 节做简要定位性介绍，但不构成后续源码分析的对象，以避免”不做主观臆测”的研究红线被稀释到非本体项目上。

0.3 研究方法与工具链

本系列所有事实性论断遵循以下证据优先级（从高到低）：

  1. 直接阅读的源码文件（.md / .cjs / .cts / .json 等，本次已克隆到本地的 next 分支全量文件）——最高优先级，行文中标注具体文件路径。
  2. 官方仓库中的架构决策记录（ADR）与 Issue/PR 编号 —— 如 docs/adr/0656-research-module-seam.md、#2792、#921 等，这些是项目维护者自己写下的设计权衡记录，可信度仅次于源码本身。
  3. 官方仓库根目录与 docs/ 下的说明性文档（README、ARCHITECTURE.md、各 explanation/*.md）—— 用于理解”为什么这样设计”，与源码相互印证。
  4. GitHub 仓库主页元信息（Star 数、Fork 数、License、Topics）—— 用于外部认知定位，会标注”研究快照时点”，因为这类数字持续变化。
  5. 第三方报道/博客（如比较 GSD、Superpowers、GSTACK 的行业博客）—— 仅用于补充生态定位背景，不作为架构细节的依据；凡与一手源码/官方文档冲突之处，一律以一手来源为准，并在文中注明差异（例如某博客所述的社区 Star 数汇总口径与官方仓库页面直接读取的数字不一致，本文采用后者）。

本文不采用的做法：不臆测未读过的源码行为、不对”可能存在”但未在仓库中找到的机制做描述性展开、不将 GSD Pi / GSD 2 / 第三方分支的特性套用到 GSD Core 名下。

0.4 引用规范

正文中出现的以下标注方式均指向可在仓库中直接核实的位置：

  • 路径/文件名：仓库内真实文件路径，如 docs/ARCHITECTURE.md、skills/gsd-quick/SKILL.md
  • #数字：GitHub Issue 或 PR 编号，如 #2792
  • ADR-数字：docs/adr/ 下的架构决策记录编号
  • 引用官方文档原文时，会控制引用长度并以自己的语言转述架构含义，避免整段照搬

第一部分 · Open-GSD（GSD Core）全景介绍

1.1 一句话定义

GSD Core 是一个元提示（meta-prompting）、上下文工程（context engineering）、规范驱动开发（spec-driven development）框架，通过一套磁盘化的状态文件与”新鲜上下文子代理”编排模式，驱动 Claude Code、Codex、Cursor 等 AI 编程 Agent 以纪律化的五阶段循环（Discuss → Plan → Execute → Verify → Ship）交付软件，同时对抗长会话中不可避免的”上下文腐化”（context rot）。

——定义直接来自 README.md 与 docs/ARCHITECTURE.md 的 “System Overview” 一节，本文仅做了中文层面的整合表述，未添加原文没有的推断性内容。

1.2 为什么会有 GSD —— 起源与问题空间

docs/ARCHITECTURE.md 与根 README 的 “Why it works” 一节，把 AI 辅助编程在规模化场景下失效的原因归纳为三条，这三条共同构成了 GSD 存在的理由：

  1. 上下文膨胀会静默拉低输出质量（Context bloat silently degrades output quality）——模型不会报错，只会”悄悄变差”。
  2. 会话之间没有共享记忆（No shared memory between sessions）——每次 /clear 或话题切换，此前建立的架构共识、边界条件都需要重新解释。
  3. 没有任何机制验证代码真的能跑（Nothing verifies that code actually works）——“生成完成”不等于”目标达成”。

GSD Core 给出的解法逐条对应：新鲜子代理解决第一条、磁盘化的结构化产物（STATE.md / CONTEXT.md 等）解决第二条、Verify 阶段的目标回溯核查解决第三条。这三条并非孤立特性，而是同一套设计哲学的三个切面——这也是为什么后文会反复看到”Context Engineering””Spec-Driven Development””Meta-Prompting”这三个词总是成对出现。

1.3 Context Rot：AI 编程助手的隐形杀手

docs/explanation/context-engineering.md 对 Context Rot 给出了目前为止我读到的最清晰的工程化解释，摘要还原如下（转述，非逐字引用）：

  • 每一次 AI 编程会话本质上都是从零开始的：模型读取问题、推理、作答。但真实会话很少只有一轮——你会追问、粘贴报错、迭代代码、把跑偏的模型拉回来。每一轮交互都会把新的 token 塞进上下文窗口（模型一次能”看见”的有限缓冲区）。
  • 随着窗口被填满，一种隐蔽的现象会发生：模型不会大声宣告失败，它会继续作答，但答案的质量在悄悄劣化。早期给出的约束、双方确认过的架构、提到过的边界条件，会在注意力分配中逐渐被后来的内容稀释——这不是”遗忘”（模型从未以人类的方式”记住”过），而是 Transformer 注意力在长序列上的必然属性：窗口中积累的噪声越多，信噪比就越差。
  • Context Rot 的四种典型症状（原文列出）：
    • 模型开始与它自己此前已确认过的决策相矛盾；
    • 代码风格逐渐偏离会话最初约定的规范；
    • 制定计划时开始忽略明确提出过、但已被埋在历史深处的需求；
    • 模型会”幻觉”出二十条消息之前还答对过的文件名或函数签名。
  • 朴素的应对方式是执行 /clear 推倒重来，但这会丢失连续性——你必须重新解释背景、重新粘贴相关文件、重新陈述约束，会话实质上被清零重启。

GSD Core 的核心洞察是：一次编码会话中的”重活”（研究、规划、编写代码、验证）大多根本不需要发生在主上下文里。这些都是离散的、有边界的任务，完全可以交给一个专门的子代理去做——子代理从一个干净的、被精心限定范围的上下文窗口开始，把结果汇报给一个保持精简的”薄编排层”。

原文特别强调了一句话，本文认为值得完整保留其含义：”这不是应对 Context Rot 的权宜之计（workaround），而是一种结构性解法（structural solution）。”

1.4 GSD 的解法：三位一体

结合 docs/ARCHITECTURE.md、docs/explanation/context-engineering.md 与根 README，GSD Core 的解决方案可以拆解为三个相互耦合、缺一不可的支柱：

支柱一：Context Engineering（上下文工程）——新鲜上下文子代理

主编排会话（你的主 session）从不直接触碰源码文件。它只做四件事：加载一个精简的 JSON 上下文载荷（通过 gsd-tools.cjs init <workflow>）、派生带聚焦提示词的专职子代理、收集结果、在步骤之间更新共享状态。因为主编排层”什么重活都不干”，它的上下文窗口增长得缓慢且可预测；真正的重活发生在每次都全新起步、只接收任务所需精确上下文、完成即终止的子代理里。

支柱二：Spec-Driven Development（规范驱动开发）——先产出结构化制品，再执行

仅有新鲜上下文还不够——如果一个”全新”的 Agent 收到的却是含糊的指令，它只会产出含糊的输出。每个阶段在执行前都要先产出结构化制品：CONTEXT.md 固化 Discuss 阶段的实现决策，RESEARCH.md 记录研究发现，PLAN.md 把工作拆解为带显式验收标准、按依赖关系排序的离散任务。等到执行子代理（Executor）真正动手改文件时，它面对的是一份精确的规格说明，而不是对一段长对话的重新诠释。

支柱三：Meta-Prompting（元提示）——把工程经验固化进 Prompt 本身

gsd-core/workflows/ 与 agents/ 下的文件不是临时拼凑的指令，而是被精心设计的提示词，编码了”如何界定任务范围、要验证什么、什么时候该升级给人类做检查点”这类来之不易的经验。用户不需要在每次会话里重新解释这些知识——它们已经烘焙进了系统自己的提示词中。

三者的组合是刻意为之的：”新鲜上下文确保每个 Agent 能清晰推理；规范驱动的制品确保每个 Agent 在推理正确的事情；元提示确保每个 Agent 知道如何推理得好。”（转述自 context-engineering.md）

1.5 Framework Positioning：GSD Core 是什么，不是什么

这是最容易被误解的一点，也是讨论框架定位（Framework Position）时真正要回答的问题。基于源码与文档，可以给出一个不含糊的定位：

GSD Core 本身不是一个 Agent，不内置模型调用能力，不自己”跑”起来。它是一套安装进宿主 Agent Runtime 里的 Prompt 文件 + 一个辅助性的确定性 CLI 工具（gsd-tools.cjs）。真正执行推理、调用 LLM API、读写文件的，始终是宿主 Runtime 自己（Claude Code / Codex / Cursor 等）的原生能力。

这一点从安装方式上就能直接验证——README.md Quickstart 一节写明：

安装器会询问你使用的 Runtime（Claude Code、OpenCode、Antigravity CLI、Kimi CLI、Kilo、Codex、Copilot、Cursor、Windsurf 等），以及是全局安装还是项目本地安装。安装器是跨 Runtime 兼容性的必经之路——不要直接从 agents/ 或 commands/ 复制文件。（转述自 README，加粗为本文强调）

也就是说，GSD Core 的”产品形态”就是一批 Markdown 文件，通过安装器被适配、翻译、放置到各个宿主 Runtime 各自的扩展目录里（Claude Code 的 ~/.claude/skills/ 或 commands/、OpenCode 的 .opencode/、Codex 的 ~/.codex/……），然后由宿主 Runtime 自己的原生 Skill/Command/SubAgent 机制去解释执行这些 Markdown Prompt。

OpenCode 开源、多模型的 Agentic CLI 平级支持的宿主之一，同时也是社区独立移植版 gsd-opencode（rokicool 仓库）的目标平台 Slash Commands（连字符形式），插件位于仓库自带的 .opencode/plugins/

除以上用户明确点名的六个之外，源码中 capabilities/ 目录下还能直接看到 Kimi CLI、Kilo、Windsurf、Trae、Cline、Augment Code、CodeBuddy、Qwen、Ollama、LM Studio、llama.cpp、VS Code、zcode 等更多受支持的运行时适配目录，docs/how-to/install-on-your-runtime.md 中提到”全部 16 个受支持 Runtime”的说法（这是官方文档中的原始措辞，与 capabilities/ 目录下可数出的 20+ 个细分适配相比，说明”正式安装矩阵”与”能力/插件级适配”是两个不完全重合的统计口径，本文如实呈现这一差异而非强行统一）。

值得一提：capabilities/codebuddy 的存在，说明腾讯云 CodeBuddy CLI 也在 GSD Core 官方支持的宿主列表中——对同时面向 Claude Code 与 CodeBuddy CLI 双 Runtime 的技能项目而言，这意味着后续本系列第六篇（第十四、十七部分）讨论”设备诊断 Skill 如何落地”时，GSD Core 在 CodeBuddy 上的具体加载形态（下文会看到，CodeBuddy 被归入”扁平/flat 技能加载”一类宿主）是可以直接参照的一手依据，而不需要额外假设。

与同类竞品的简要定位（非本文源码分析对象）

一篇比较 Claude Code 编排框架选型的行业博客（Pulumi Blog）将 GSD、Superpowers、GSTACK 并列为三种可选框架，给出的定性区分是：Superpowers 侧重”测试驱动的强制门禁”（每次代码变更都必须先有一个失败的测试），GSD 的核心架构决策是”不用单一超级编排器，而是每个阶段各配一个独立编排器，每个编排器的上下文占用都控制在其容量的 50% 以下”。这与本文直接从源码读到的”薄编排器 + 阶段化五步循环”完全吻合，故予以采信作为生态背景介绍；但该博客给出的具体 Star 数（数万级）与本文直接从 open-gsd/gsd-core 仓库主页读取到的数字（研究快照时点为 7.1k Star、483 Fork）存在明显差异，可能统计口径不同（例如是否合并了 GSD Pi、社区分支等生态整体声量），本文不对差异原因做推测，仅如实并列呈现，并以直接读取的仓库页面数字作为后续引用的基准。

1.6 五阶段循环总览（详解见本系列第三篇第五部分）

docs/explanation/the-phase-loop.md 将 GSD Core 的核心工作节奏概括为一句话：

每一个”阶段”（Phase）都会依次走完这五步（UI 设计为可选的第 1.5 步），循环不是形式主义——每一步都在防御上一步单独无法防御的某一类失败模式：Discuss 防止”规划建立在错误假设之上”；Plan 防止”执行一个根本走不通的设计”；Verify 防止”交付了偏离真实需求的成果”。这一模型将在本系列第三篇（第五部分）逐阶段展开输入/输出/Prompt/状态/依赖/典型 Skill 的完整分析，此处仅做全局定位。

1.7 Skill Runtime 与 Prompt Runtime 速览（详解见本系列第四篇第六~十部分）

GSD Core 的可扩展性单元是 Skill——本次克隆的 next 分支 skills/ 目录下共有 71 个技能子目录（含命名空间路由技能，详见下文），每个都是一个独立的 SKILL.md Prompt 文件。docs/ARCHITECTURE.md 中记录了一项影响深远的架构演进——两阶段分层路由（Two-stage hierarchical routing，v1.40，issue #2792）：

  • 早期做法是把全部具体技能平铺在顶层，模型每一轮都要”眼前过一遍”全部技能列表，token 成本随技能数量线性增长；
  • v1.40 引入 6 个命名空间元技能（gsd-workflow、gsd-project、gsd-quality、gsd-context、gsd-manage、gsd-ideate，源文件为 commands/gsd/ns-*.md），作为悬浮在具体子技能之上的一层路由；
  • 在”非递归技能加载器”的宿主（cline、qwen、hermes、augment、trae）上，安装器只暴露这 6 个命名空间路由作为顶层技能，把约 61 个具体技能嵌套到 <router>/skills/<name>/SKILL.md 下，模型选中一个命名空间路由后，路由体内嵌的路由表会指示它去读取具体技能文件——眼前技能列表从约 67 条压缩到约 6 条；
  • 在”支持递归或加载行为未确认”的宿主（claude global、cursor、codex、copilot、windsurf、codebuddy、opencode、kilo、antigravity）上，仍保持全部技能平铺（这里有两处历史反复：Antigravity 曾从嵌套改回扁平——因为它的技能扫描器 agy 只扫描 skills/<name>/SKILL.md 一层，嵌套的子技能根本无法被发现；Claude 全局安装同理曾被改回扁平——因为 Claude 的 Skill 工具在遇到未知技能名时会直接硬报错，而不会重试走路由，导致嵌套的具体技能变得不可调用）。

这是一处教科书级别的”多版本实现差异”案例——按照”若源码存在多个实现版本，应分析差异”的研究原则，这里的差异不是历史遗留，而是同一套路由机制在不同宿主能力矩阵下的两种并存实现，将在本系列第四篇（第八、九部分）结合具体源码与真实 SKILL.md 路由文件展开。

命名空间路由技能的 description 字段本身也是一处值得留意的设计——例如 gsd-ns-workflow 的描述写的是 "workflow | discuss plan execute verify phase progress"，用竖线分隔关键词标签而非自然语言句子。docs/ARCHITECTURE.md 中给出的理由是”Tool Attention 相关研究表明，关键词密集型标签在路由任务上的表现优于自然语言描述，且 token 成本约为后者的 40%”——这一细节将在本系列第四篇（第九部分）”Skill Matching”中结合更多真实 description 样本展开分析。

分层要点（来源：docs/ARCHITECTURE.md “Design Principles”）：

  • Fresh Context Per Agent：每个被编排层派生的 Agent 都拿到一个干净的上下文窗口（最高可达 200K token，1M 级模型下更多），这是消灭 Context Rot 的机制本体，而非权宜之计；
  • Thin Orchestrators（薄编排器）：gsd-core/workflows/*.md 从不亲自干重活，只做四件事——通过 gsd-tools.cjs init <workflow> 加载上下文、派生带聚焦 Prompt 的专职 Agent、收集结果并路由到下一步、在步骤之间更新状态；
  • File-Based State（文件化状态）：全部状态活在 .planning/ 下的人类可读 Markdown 与 JSON 中，没有数据库、没有服务端、没有外部依赖——这意味着状态能扛住 /clear、能被人类和 Agent 同时检视、能被提交进 Git 供团队可见；
  • Absent = Enabled（缺省即启用）：config.json 中缺失的功能开关字段默认视为 true，用户需要显式关闭功能，而不是显式打开默认项；
  • Defense in Depth（纵深防御）：Plan 在执行前先被 plan-checker Agent 校验；执行按任务粒度产生原子提交；执行完成后有 Verify 阶段对照阶段目标复核；UAT（用户验收测试）作为人工把关的最终闸门。

1.9 项目生命周期图（Milestone → Phase → 五阶段循环）

stateDiagram-v2
    [*] --> Discuss
    Discuss --> UIDesign: 存在可视化交付物（可选步骤）
    Discuss --> Plan: 无 UI 交付物，直接进入 Plan
    UIDesign --> Plan: 产出 UI-SPEC.md 设计契约
    Plan --> PlanCheck: Planner 产出 PLAN.md
    PlanCheck --> Plan: Plan Checker 打回（最多 3 轮修订）
    PlanCheck --> Execute: Plan Checker 通过
    Execute --> Verify: Executor 按依赖波次完成，产出 SUMMARY.md
    Verify --> Plan: 发现偏差，生成针对性修复计划
    Verify --> Ship: Verifier 判定目标达成，产出 VERIFICATION.md
    Ship --> [*]: 创建 PR，归档本 Phase 制品
    Ship --> Discuss: Milestone 未完成，进入下一个 Phase

关键概念区分（来源：docs/explanation/the-phase-loop.md）：

  • Milestone（里程碑）：一个版本周期——一次有意义、可发布的产品增量，拥有名称、版本号、一组界定”必须交付什么”的需求。里程碑完成的标志是它所有的 Phase 都已 Ship，且需求全部被覆盖。
  • Phase（阶段）：一个里程碑内的一个工作单元，拥有一个目标、一组它要覆盖的需求、一组实现它的 Plan。
  • 二者的关注范围不同：里程碑问的是”这个版本的产品要做什么、不做什么”；阶段问的是”下一件能被安全地研究、规划、执行、验证的有边界的事情是什么”。
  • 原文给出了判断”好的 Phase 边界”的具体标准与反例，颇具实操价值，将在本系列第三篇（第五部分）完整展开——例如”新增 HMAC-SHA256 签名校验中间件”是一个恰当的 Phase 范围，而”构建整个认证系统”通常不是（几乎总是包含多个本该拆分为独立 Phase 的关注点），”修复 README 里的错别字”则达不到需要走循环的门槛，应使用 /gsd-quick 处理。

1.10 Context 生命周期与关键时序图

Context Rot 的对抗机制不是抽象概念，而是体现在每一次具体的 Agent 派生动作里。以下时序图还原 /gsd-plan-phase 命令触发后的真实调用序列（来源：docs/explanation/context-engineering.md 给出的具体步骤描述 + docs/ARCHITECTURE.md “Data Flow → Phase Execution Flow”）：

sequenceDiagram
    participant U as 用户
    participant O as 主编排会话 Orchestrator<br/>（上下文缓慢、可预测地增长）
    participant CT as gsd-tools.cjs
    participant R as Researcher Agent<br/>（全新 200K 上下文）
    participant P as Planner Agent<br/>（全新 200K 上下文）
    participant PC as Plan-Checker Agent<br/>（全新 200K 上下文）
    participant FS as .planning/ 文件系统

    U->>O: /gsd-plan-phase
    O->>CT: gsd-tools.cjs init plan-phase
    CT-->>O: 精简 JSON 上下文载荷（项目摘要/阶段目标/相关配置）
    Note over O,R: 主会话从不直接读写源码文件——<br/>它只派生 Agent、收集结果、更新状态
    O->>R: 派生（携带 CONTEXT.md）
    R->>FS: 写入 RESEARCH.md
    R-->>O: 返回结果引用（非原始抓取内容）
    O->>P: 派生（携带 RESEARCH.md 路径 + CONTEXT.md + 可达性检查）
    P->>FS: 写入多份 PLAN.md（按依赖关系分波次）
    P-->>O: 返回结果引用
    O->>PC: 派生（携带全部 PLAN.md）
    PC->>FS: 校验完整性/一致性/范围/可达性
    alt 校验不通过（最多 3 轮）
        PC-->>O: 打回，携带修订意见
        O->>P: 重新派生 Planner（新鲜上下文）
    else 校验通过
        PC-->>O: 通过
        O->>FS: state planned-phase → 更新 STATE.md
        O-->>U: 阶段就绪，可执行
    end

这张图揭示的核心机制（转述自 context-engineering.md “Lifecycle hooks and context headroom” 一节）：

  • 新鲜上下文子代理模型保护的是每一个被派生的 Agent；但还有一个更微妙的问题——编排会话本身也会随时间被填满。长时间运行的编排过程会静默消耗自己的上下文窗口（加载载荷、读取状态输出、在阶段之间路由）。如果没有任何关于剩余余量的信号，会话可能悄悄劣化，或者更糟——触发一次自动压缩（compaction），静默丢弃编排器原本依赖的规划状态。
  • 自 GSD 1.4.0 起，这一问题通过注册运行时生命周期 Hook 来解决：Claude Code 会在 PreCompact（即将发生压缩前）、Stop（一轮会话结束）、SubagentStop（派生的子代理完成）这些事件上触发 Hook；Qwen 暴露的是同名的 SubagentStop/Stop/PreCompact 事件。这是”多运行时哲学在可观测性层的应用”——GSD 在每个运行时各自暴露的位置注册语义等价的 Hook，而不是要求所有运行时统一采用同一套事件模型。
  • 一个值得记录的历史反复：早期版本曾对 plan-phase、execute-phase、autonomous 这三个”重”技能额外施加 context: fork（子代理化的上下文隔离），但后来被移除（#921）——原因是这三个恰恰是派生型编排器（spawning orchestrators），它们的核心职责就是派生子代理（gsd-planner、gsd-executor 等），而一个被 fork 出去的子代理上下文本身没有 Agent 工具，无法再派生下一层子代理。这三个技能真正的上下文隔离来自于它们所派生的子代理，而不是编排器自身的 fork——这是又一处”分析实现版本差异”的真实案例。

1.12 本部分小结与下文预告

第一部分回答了”GSD 是什么、为什么存在、和谁是什么关系”这三个最基础也最容易被误解的问题，其中最重要的两个结论是：

  1. GSD Core 是寄生于宿主 Agent Runtime 之上的纪律层，不是与 Claude Code/Codex/Cursor 平级的竞争产品——它靠三位一体（新鲜上下文子代理 + 规范驱动制品 + 元提示）解决”上下文腐化、无跨会话记忆、无人验证”这三个规模化失效模式；
  2. “open-gsd” 这个名字下并存着代码库、版本号、产品形态都不同的多个项目（GSD Core / GSD Pi / 历史版本 GSD 2 / 社区分支 / 第三方学习层插件），本文后续 19 个部分将全部聚焦于 GSD Core 这一个代码库，任何看起来像是”GSD 特性”但实际来自 GSD Pi 或第三方项目的描述都会被明确标注区分。

下一篇《Open-GSD 源码解析（二）：仓库结构与十一层架构》将从第二部分 Repository 全面解析开始，逐目录展开——.claude-plugin/、agents/、capabilities/（含其 40+ 子目录的角色地图）、commands/gsd/、docs/（四象限文档体系）、gsd-core/（bin/ workflows/ references/ templates/）、hooks/、pi/、scripts/、skills/、src/、tests/ 等每一个顶层目录的用途、生命周期、依赖关系、入口位置、主要对象与典型调用，并配一张全目录依赖图。
