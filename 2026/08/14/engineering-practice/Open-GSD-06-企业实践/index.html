先读结论

  1. 一套统一模板可以覆盖 27 个领域的企业级 Skill 设计，领域差异主要落在“替换”与“扩展”，可复用抽象几乎不需要改动。
  2. 自研 Enterprise Skill Runtime 的绝大多数设计是 GSD 原则的服务化放大，只有沙箱一条因多租户威胁模型而做了相反选择。
  3. 纯日志诊断必须区分察觉新颖、刻画结构与命名解释三种能力，平台目标不是消除专家，而是把专家的边际产出最大化。
  4. 面对全新故障时的自信错误是最大的生产级风险，把“新模板数 > 0”接入弃权决策是投入产出比最高的修复。
  5. 能在 CI 期强制的约束绝不留到运行期，这一原则同时贯穿 GSD 与诊断平台设计。

本篇导读：本篇是系列的最后一篇，把前五篇核实的源码事实转化为工程设计：27 个领域的企业级 Skill 设计模式、跨业务领域的迁移方法、一套下一代 Enterprise Skill Runtime 设计、车辆纯日志诊断场景的平台设计，以及源码阅读路线、最佳实践与十大系列总结。与前五篇以研究为主不同，本篇以设计为主，每一处设计都标注其依据的 GSD 机制或实测来源。

第十四部分 · 企业级 Skill 设计模式（27 个领域范例）

14.0 方法论说明：两个完整示范 + 一份紧凑目录

本部分要覆盖的领域多达 27 个（代码生成、Code Review、API 设计、架构评审、安全评审、性能、DevOps、数据库、微服务、RAG、Agent、Prompt、MCP、知识管理、文档、测试、发布、Git、CI/CD、可观测性、根因分析、日志分析、设备诊断、OTA、CAN、遥测、汽车 AI）。逐一展开”目录+SKILL.md+Prompt+Workflow+最佳实践”五件套，会让本部分本身膨胀成一份独立的大文档，稀释可读性。本部分采取的策略是：

  1. 两个完整示范——第一个（Code Review）100% 基于 GSD 仓库里真实存在的 gsd:code-review 技能与 gsd-code-reviewer Agent逐字段复现，不是虚构范例；第二个（设备诊断集群）直接对接一个示例诊断技能包已完成的架构决策，给出 GSD 模式与该诊断技能包既有架构的对照，而非另起炉灶设计一套。
  2. 其余 25 个领域给出统一模板下的紧凑目录（目录结构一行、SKILL.md 核心字段一行、Prompt 要点一行、Workflow 骨架一行、2-3 条最佳实践），按集群分组呈现，保持信息密度的同时避免与前两个示范重复展开已经讲过的通用机制。

14.1 完整示范一：Code Review ——直接复现 GSD 真实实现

这不是本文设计的范例，而是对仓库里已经存在的 commands/gsd/code-review.md + agents/gsd-code-reviewer.md 的逐字段还原，用意是给读者一份”教科书级别的、已经跑在生产环境里的” SKILL.md + Agent 设计范本。

目录

SKILL.md 核心字段（真实内容）

三档深度（真实定义，附耗时估计——这是本文在 71 个技能里少见的、把预期耗时也写进 description/objective 的样本）：

深度 内容 预期耗时
quick 仅模式匹配 ~2 分钟
standard（默认） 逐文件分析 + 语言特定检查 ~5–15 分钟
deep 跨文件分析，含 import 图与调用链 ~15–30 分钟

文件范围裁定优先级（真实决策编号 D-08）：--files 显式列表 > SUMMARY.md 提取 > git diff 兜底——这与本系列第三篇（第五部分）讨论的”多个可能来源，需要显式优先级”是同一治理风格。

Prompt：gsd-code-reviewer.md 的关键语义块

  • <adversarial_stance>——与本系列第五篇（第十一部分）Verifier 共享同一种”默认假设有问题、去找证据推翻”的姿态设定，证实这不是 Verifier 独有，而是一切”审查类” Agent 的共同底色；
  • <review_scope>——“Issues to Detect” 明确列出检测类别，且给出了具体的检测模式样本：”Hardcoded secrets”（硬编码密钥）、”Dangerous functions”（危险函数）、”Debug artifacts”（调试残留）、”Empty catch”（空 catch 块）——四个都是可以直接映射成正则/AST 规则的具体代码异味，而不是”注意代码质量”这种空泛表述；
  • 严重度分类与编号——REVIEW.md 产出里用 CR-01/WR-01/IN-01 分别编号 Critical/Warning/Info 三级发现，与本系列第三篇（第五部分）plan-checker 的”每个问题必须携带显式严重度”是同一条纪律的落地；
  • 一处特殊 Hook：before_write（与本系列第五篇第十一部分记录的 PostToolUse Write|Edit 不同的另一种 Hook 触发时机）——本文未深入核实其具体行为，但从命名推断大概率是在 Agent 真正落笔写 REVIEW.md 之前做某种前置校验。

Workflow：三个门禁 + 修复迭代闭环

命令本身是”薄分发层”（<process> 原文自陈：”This command is a thin dispatch layer”），真正的门禁在 workflow 里：Phase 校验 → 配置门禁（workflow.code_review 开关）→ 文件范围裁定 → 空范围检查（无文件则跳过）→ 派生 gsd-code-reviewer → 呈现结果。--fix --auto 会触发”修复→重新审查”迭代闭环，上限 3 次——与本系列第三篇（第五部分）Plan-Checker 的修订循环、本系列第二篇（第三部分）Escalation Gate 的迭代上限是同一条”有限迭代，达到上限就升级给人”的纪律。

最佳实践（从这个真实样本提炼）

  1. 深度分级要给出具体耗时预期，而不是只给”快/慢”这种相对描述；
  2. 文件范围来源多于一个时，显式写出优先级顺序并给它一个可引用的决策编号（如 D-08）；
  3. 检测类别要具体到”硬编码密钥””空 catch 块”这种可执行细节，而非”检查代码质量”。

SKILL.md / Prompt / Workflow：可直接引入的三个具体增量

  1. 用 contribution 机制承载”领域降级提示”——示例诊断技能包当前对 TSP 远控/智驾/座舱的处理是”占位并降级引导 Agent 回复暂不支持”。用 GSD 的语言重新表述：这正是一个 contribution（往某个诊断入口 Agent 的 Prompt 里注入”该领域尚不支持”的提示片段），而不需要在主 Agent 逻辑里写死判断——这样新增第四个完整领域时，只需要新增一个 capability.json + 撤销对应的降级 contribution，而不需要改动主流程代码。

  2. 用 Verifier 的 Data-Flow Trace 技术校验诊断报告的证据链——本系列第五篇（第十一部分）详解的”沿 UI 渲染反向追溯到真实数据源、标记静态返回值”技术，直接翻译到设备诊断场景就是：沿着诊断报告里的每一条结论，反向追溯到它引用的证据工具输出，标记”结论存在但证据链断裂或指向伪造证据”的情况。诊断技能包已有的”伪造 row_hash 被质量门 block 拦截”正是这一思路的一个具体实例（校验证据指纹的真实性）；Data-Flow Trace 提供的是一个更系统化的版本——不只校验单个证据的真实性，还校验”结论→证据”这条引用链本身是否完整、有没有中间环节被静默跳过。

  3. 用 gsd-spike --wrap-up 的模式固化探索性诊断经验——本系列第五篇（第十三部分）详解的这个机制，可以直接对应到”工程师对一类新故障做了几次探索性排查”的场景：每次探索性诊断产出一份带验证状态（验证有效/部分有效/已证伪）的记录，达到一定数量后自动按故障特征分组、合成一个新的领域诊断技能——连”已确认无效的排查方向”也要被固化，这对应诊断技能包未来扩展 TSP/智驾/座舱领域时，可以先用一种”探索模式”积累诊断经验，成熟后再固化成正式的知识树节点，而不必一开始就要求完整设计。

最佳实践

  1. 领域降级用声明式 contribution 承载，而不是主流程里的硬编码分支；
  2. 证据链校验从”单点证据真实性”升级到”结论到证据的引用链完整性”（Data-Flow Trace 思路）；
  3. 新领域先用探索模式积累经验（含”确认无效”的死胡同记录），成熟后再固化为正式知识树节点，避免过早设计。

应该保持不变——工程基础设施，与领域无关

  • 三层独立注入防御（第四篇第十部分）——只要系统会读取外部/用户输入喂给 LLM，这套写入侧/读取侧/Prompt 自我护栏就该原样搬；
  • 防原型污染纪律（第四篇第十部分、第五篇第十一部分）——纯 JavaScript/TypeScript 工程实践，与业务领域无关；
  • 测试六大契约（第五篇第十二部分）——“测真实代码不测源码文本””不做永真断言”这类纪律不因领域而变；
  • 构建-安装-发现-加载的分层解耦（第四篇第八部分）——扫描逻辑不关心宿主是谁、也不该关心业务领域是什么。

应该替换——领域特定，不能照搬

  • 具体 Agent 角色——gsd-planner/gsd-executor/gsd-verifier 是”软件工程”语境的具体化身；换到医疗领域，对应的应该是”诊疗方案规划者/执行记录员/复核医师”这类完全不同的角色定义，共享的只是”规划者→执行者→核验者”这个三段式骨架，不是这三个 Agent 的 Prompt 内容；
  • 具体制品格式——PLAN.md/SUMMARY.md 是为”代码变更”设计的字段（files_modified、commit hash 等）；金融领域的对应制品可能是”交易审批单”（字段是金额、风险评级、审批链），字段集合必须重新设计；
  • Git Layer 整个概念——“用 Git 记录变更”是软件工程独有的；金融/医疗领域的”变更留痕系统”通常是审计日志或电子病历版本控制，这个替换不是”换个工具”这么简单，而是换一套完全不同的留痕哲学（Git 允许历史重写与分支实验，多数强合规场景不允许）。

应该扩展——GSD 有雏形但深度不够

  • 合规/监管维度——第十四部分的”安全评审”领域目前只对应到 STRIDE 威胁建模层面；金融（PCI-DSS/反洗钱）、医疗（HIPAA/临床数据保护）领域需要在 Gate 体系里新增一类”合规 Gate”，且这类 Gate 的判定标准往往需要外部权威数据源（监管规则库）而非纯静态代码分析；
  • 领域知识注入——agent_skills 机制（第四篇第六部分）足以注入”编码规范”，但医疗/金融领域需要注入的是结构化的领域本体（ICD 编码、金融产品分类），这比一份 Markdown Skill 文件承载的信息密度要求更高，需要扩展成”本体/术语表”这一新的引用类型；
  • 多级审批链——GSD 的 checkpoint:human-verify/checkpoint:decision（第三篇第四部分）是”一个人确认一次”模型；企业客服升级、金融大额审批场景常需要”A 批准后 B 才能看见”的链式审批，这是当前 Gate 体系里没有的一种新拓扑，需要在 Escalation Gate 基础上扩展出”多签”变体。

应该插件化——用 Capability 机制承载

  • 领域特定的规则库（车辆 DTC 码库、医疗 ICD 编码、金融产品分类）——每一套规则库对应一个独立 capability.json，声明自己的 config/activationKey，可以独立开关、独立升级，不与主框架代码耦合（第五篇第十二、十三部分已示范这一模式）；
  • 第三方合规工具/评审服务——直接复用 Reviewer Lane（第二篇第三部分已述其”披露解析后的目标主机而非仅二进制名”的信任模型）这一机制，企业可以把”KYC 检查服务””临床指南比对服务”接成一条 Reviewer Lane，而不需要为每个合规工具单独设计集成方式。

应该配置化——config.json 式参数，不需要改代码

  • 审批阈值（金额、风险等级门槛）；
  • 数据保留期限（合规要求因司法辖区而异）；
  • 语言/术语表（客服、教育领域天然多语言）；
  • 模型分级策略（第四篇第六部分的 Model Profile 机制——不同领域对”准确性 vs 成本”的权衡完全不同，金融风控可能永远选最高档模型，客服闲聊可能优先选便宜档）。

设计决策 2 —— 保留”依赖是构建期概念”这一判断（第四篇第六、七部分实证：requires 在生成 SKILL.md 时被剥离）。ESR 的 Registry 同样把依赖闭包计算放在发布期而非调用期：技能发布时就算好闭包并固化成一个”技能包快照”，调用期只做快照查表，不做图遍历。理由与 GSD 一致——闭包计算的输入（依赖声明）在发布后不再变化，没有必要每次调用都重算。

设计决策 3 —— 保留”无有效输入时回退到过度安装”的防御性默认值（第四篇第八部分实证：resolveProfile() 在 mode 全部无效时返回 full 而非空集，源码注释”避免空安装”）。ESR 的对应实现是：租户策略解析失败时，回退到该租户的最小可用集而非空集——注意这里做了一处方向调整：GSD 单机场景下”过度安装”是安全的（大不了多占点 token），但企业多租户场景下”过度授予”是危险的，所以 ESR 回退到最小可用集而非全集。这是本文对 GSD 原则做的一次有意识的方向反转，理由是威胁模型不同。

设计决策 4 —— 把 lint-skill-deps.cjs 的两项检查提升为发布门禁（第四篇第六部分已归纳其价值：把悬空引用从运行时问题变成构建期失败）。ESR 在技能发布 API 上强制执行：①技能正文引用的其他技能必须在依赖声明里；②每个可发布 profile 的闭包必须自洽。不通过则拒绝发布，而不是发布后再靠运行时告警。

16.2.4 Durable Layer（Temporal）：把断点续跑做成基础设施

设计决策 8：第三篇第五部分详解的”断点续跑三选项”（close out manually / re-execute from scratch / mark-and-skip）与第三篇第四部分的检查点续接机制，在单机 GSD 里靠”检查 SUMMARY.md 是否存在”这类文件系统探测实现；服务化后应当交给 Temporal 的持久化工作流引擎，因为它原生提供：任务重试、超时、幂等、长时间等待人工回执（可以等数天而不占用计算资源）、以及最关键的——故障后从确切位置恢复而非从头重跑。

一个具体的映射：第三篇第五部分记录的”提交存在但 SUMMARY.md 缺失”这个边界情况，在 Temporal 模型下对应”Activity 已执行但结果未持久化”——这是 Temporal 有成熟解法（幂等键 + 结果查询）的一类已知问题，不需要每个团队自己重新设计三选项菜单。

设计决策 9 —— 冷启动成本必须被计量（第三篇第四部分实证：#3309 数据”每次中断=一次完全冷启动=数万 token”）。ESR 在 Temporal 的每个 Activity 边界埋点，把”因中断导致的重复上下文加载”单独计量为一项成本指标，让”这个流程的人工检查点是不是设得太多了”变成一个有数据支撑的问题，而不是靠感觉。

16.2.5 Sandbox Runner：补上 GSD 明确没有的那一层

第二篇 3.11 节已完整引用 GSD 拒绝沙箱的理由：Node 级沙箱要么需要独立进程+IPC 开销，要么需要剥掉能力合法需要的 Node 全局对象；完整制品对等与有意义的沙箱互相冲突，维护者选择了完整对等。

设计决策 10 —— ESR 做相反的选择，因为约束条件不同。 GSD 是单机开发者工具，用户对自己机器上跑什么有完全的知情与控制；ESR 是多租户服务，一个租户提交的技能代码可能在承载其他租户数据的基础设施上执行——这是一个质变，使得”没有沙箱”从”可接受的诚实取舍”变成”不可接受的风险”。

分级沙箱设计：

技能类型 沙箱级别 依据
纯声明式（只有 Prompt 片段 + Hook 声明） 无需沙箱 直接沿用 GSD 的判断（第五篇第十二部分：声明式能力不需要信任提示，因为没有可执行代码）
确定性脚本（数据处理、格式转换） 容器沙箱（无网络、只读挂载输入、限时限内存） ——
需要网络/外部调用 容器沙箱 + 出网白名单 + 全量出网审计 对应第二篇第三部分对 Reviewer Lane”出口通道”的特别关注
需要访问租户数据 容器沙箱 + 数据面代理（技能拿不到原始凭据，只能通过代理按已授权范围取数） ——

设计决策 11 —— 沿用”披露解析后的实际目标”而非”仅披露二进制名”（第二篇第三部分实证：Reviewer Lane 的 spawned 型披露完整参数，因为声明 python3 的 lane 可以事后把参数改成 -c <任意程序> 而二进制名不变；HTTP 型披露目标主机而非 curl；且 Consent 绑定解析后的实际 host 而非配置键）。ESR 的出网白名单同样绑定解析后的实际目标，且配置变更触发重新审批。

16.2.6 State Store & Evidence Store

设计决策 12 —— 状态用 FIELD_CLASSIFICATION 式的数据表驱动（第五篇第十一部分实证：state-transition.cts 用 source × preservation 两维表统一治理每个字段，把”三处漂移实现”收敛成”改表里一行”）。ESR 的状态模型同样用一张显式的字段分类表定义每个字段的来源（用户输入/派生/外部系统/人工策展）与转换时的保留策略，而不是把这些规则散落在各个状态转换函数里。这是本文认为 GSD 最值得原样搬运的架构级模式之一。

设计决策 13 —— 证据存储采用内容寻址 + 不可变。依据两条：第四篇第六部分记录的 Research Store 已经用了 sha256(...) 内容寻址 + 分级 TTL；示例诊断技能包已验证的 row_hash 行级证据指纹与”伪造 row_hash 被质量门拦截”实践。企业场景下证据链的可审计性要求更高，因此 ESR 的证据一旦写入不可修改，任何”更正”都表现为一条新证据 + 一条指向旧证据的作废记录。

16.2.7 可观测平面：OTel + Langfuse + Cost Ledger

设计决策 14 —— 三层观测各司其职，不重复造轮子：

层 工具 观测对象 依据
系统层 OpenTelemetry HTTP/DB/队列/沙箱调用的 trace、metric、log 通用可观测性实践；GSD 自身也有 observability/event.cjs/logger.cjs/redaction.cjs 模块（第二篇第二部分、第五篇第十一部分提及），说明这个关注点在框架层就该存在
LLM 层 Langfuse 每次模型调用的输入/输出/token/延迟/评分 GSD 缺失这一层（第三篇第四部分的余量监控是单机 Hook，非集中式）
成本层 Cost Ledger 按租户/项目/技能/run 归集的 token 与费用 第三篇 4.7 节的估算校准是单项目局部实现，企业需要集中核算

设计决策 15 —— 沿用”拒绝模型自评、路由到实测历史”（第三篇第四部分实证：GSD 的 confidence 由校准样本数推导，不允许模型自评；原文明确说明该项目实测过自评置信度并发现它很弱）。ESR 的技能质量评分同样不接受模型自评，而是由 Langfuse 上累积的真实评估数据（成功率、人工回执的通过率、返工率）计算得出。这条原则在企业场景下比单机场景更重要，因为”技能质量分”会直接影响 Marketplace 的排序与推荐。

设计决策 16 —— 观测数据的脱敏是一等公民。GSD 源码里有 observability/redaction.cts 模块（第二篇第二部分目录清点时记录），说明这个问题在单机场景就已被意识到；服务化后风险更高（观测数据集中存储、多人可查），因此 ESR 的脱敏必须发生在数据离开执行环境之前，而不是在查询侧过滤。

16.2.8 MCP 与 A2A

设计决策 17 —— MCP 作为”对外暴露”与”对内消费”的双向标准。第二篇第二、三部分已核实 GSD 用顶层 bin/gsd-mcp-server.js 把核心能力暴露成标准 MCP Server，理由是”任何消费 MCP 的宿主都能驱动它，无需为每个宿主写专属插件”。ESR 沿用这条路径：对外把 Skill 调用暴露为 MCP 工具（任何 MCP 宿主可用），对内把企业既有系统（工单、CMDB、知识库）通过 MCP 接入。

设计决策 18 —— A2A 用于跨团队 Agent 协作，但必须过同一套治理。这是本文的推导（GSD 中无 A2A 相关实现）：当 A 团队的 Agent 调用 B 团队的 Agent 时，这次调用应当被视为一次”跨租户技能调用”，同样经过网关的认证/配额/审计，而不是绕过控制平面直连。理由直接来自第二篇第三部分的信任模型——“制品对等不等于信任对等”：A2A 让对端 Agent 具备了与本地 Agent 同等的调用能力（制品对等），但它的信任地位不应因此自动等同于本地 Agent。

16.2.9 Marketplace & Governance

设计决策 19 —— 直接移植 GSD 的三重屏障 + 第一方永远赢（第二篇第三部分完整引用）：

  • 同意（Consent）：技能安装时披露其全部可执行面（Hook/MCP Server/命令模块/出网目标），且可执行面集合变化触发重新审批；
  • 完整性（Integrity）：SHA 定版；
  • 可逆性（Reversibility）：卸载精确撤销登记过的一切，不留孤儿状态；
  • 第一方永远赢：企业自有的核心技能永远不能被第三方技能通过同名碰撞遮蔽（第二篇第三部分的理由：否则”安装”本身就成了攻击面）；
  • 保留前缀：企业应保留自己的技能命名空间前缀（如 corp-），拒绝第三方使用。

设计决策 20 —— 但增加 GSD 明确拒绝的那一项：分级审核。第二篇第三部分记录了 GSD 拒绝 Obsidian 式中心化审核的理由——会让维护者成为无穷尾部的瓶颈，复刻 Obsidian 自己都在承受的痛苦。但企业场景的约束不同：技能总量有界（不是开放生态的无穷尾部），且合规要求往往强制人工审核。因此 ESR 采用分层方案：核心/共享层技能强制人工审核，团队内部技能仅需团队负责人批准，个人实验技能免审但不可被他人安装。这样既避免了全量人工审核的瓶颈，又满足了对高影响面技能的管控。

16.5 实施路线建议（四个阶段）

设计决策 21 —— 用 GSD 自己的方法论来建这套东西（这不是玩笑，而是最省心的路径：五阶段循环本身就是为”如何在不确定中稳步交付”设计的）：

阶段一 Registry + Resolver + Gateway 最小闭环 能发布一个技能、能按 profile 解析出闭包、能被一个宿主拉取；闭包自洽门禁生效
阶段二 Orchestrator + Durable Layer 五阶段循环跑通，含有界修订循环与人工检查点；故障后能从确切位置恢复

阶段四 可观测 + 成本 OTel/Langfuse 接入；Cost Ledger 按租户出账；冷启动成本单列可查

每个阶段都应当先产出一份”决策记录”（对应 GSD 的 CONTEXT.md/ADR 实践），再规划、再执行、再核验——用被验证过的方法去建造建造方法的工具本身，这是本部分最后一条建议。

16.6 本部分小结与下文预告

17.1 先把问题定义准：什么是”纯日志故障诊断”，为什么它是最难的一档

车辆故障诊断按可用信号强度可以分成四档，”纯日志”是其中最难的一档：

档位 可用信号 诊断难度 典型手段
一档 DTC 故障码 + 冻结帧 低 查码表，DTC→故障映射基本是确定的
二档 CAN 信号 + 时序数据 中 信号阈值判定、时序模式匹配
三档 结构化埋点日志（有 schema、有 traceId） 中高 链路追踪、指标聚合
四档：纯日志 只有各 ECU/组件写出的自由格式文本日志，无统一 schema、无全局 traceId、无 DTC 对应 最高 本部分讨论的全部内容

为什么第四档质变地难，五个结构性原因：

  1. 黑盒 ECU——日志由不同供应商的不同团队按各自习惯打印，没有统一规范。示例项目的实测数据：单车单次 OTA 升级的日志压缩包内含 10 多种组件模块、20 多种日志文本格式、分布在数十个目录、数百万行（已验证，某 OTA 日志分析项目）。
  2. 没有全局因果链——不同 ECU 的时钟可能不同步，无法凭时间先后断言因果。这正是 RCA MVP 里设计”因果四条件”（两 ECU 时钟对不上就不能凭时间说谁导致谁）的原因（已验证）。
  3. 证据是可消失的——车端日志有保留期，等到复盘时原始日志可能已过期。这是”证据快照双源解析（10 年追溯）”成为核心设计的直接动因（已验证）。
  4. 正常与异常高度混杂——一次升级失败的日志里，99% 以上是正常流水。实测压缩率 99.4%（3004→18 行）且根因链零丢失（已验证，诊断技能包），反过来说明信噪比之低。
  5. 最危险的一类失效：症状同构的新故障——两个完全不同的根因可能产生几乎一样的日志症状。实测暴露了这一点的严重性：把某类故障移出知识窗口后，25 个全新故障会话中 0 次弃权、25/25 全部给出错误命名（已验证，实验 B）——系统从不说”我不认识”。

阶段② 证据化：时间基准 + 行级指纹 + 脱敏

这是整条流水线可信度的地基，三个机制缺一不可：

  1. 两遍法时间基准推断（已验证）——优先级：文件内时间戳 > 文件 mtime > 上传时间，并打 ts_quality 标记做置信度传播。为什么必须做：纯日志场景下，跨 ECU 时钟不同步是常态，如果不标记时间质量，后续所有”A 先于 B 所以 A 导致 B”的推理都建立在流沙上。
  2. 行级证据指纹 row_hash（已验证）——每一行日志的稳定指纹，是”结论→证据”引用可解析性的锚。实测伪造 row_hash 被质量门 block 拦截（已验证）。
  3. 掩码脱敏——VIN、手机号、位置等敏感字段在离开执行环境之前脱敏。设计：这里直接沿用 GSD 的一条纪律（第十六部分决策 16 引用的 observability/redaction.cts 存在性）——脱敏必须发生在数据产生侧，而不是查询侧过滤。

阶段④ 故障存在性判定：先回答”到底有没有故障”

这是一个容易被跳过、但代价极高的阶段。 实测暴露了跳过它的后果：不做存在性判定时，健康车假阳性率高达 47.5%——即近一半的正常车辆会被硬安一个根因；引入依终态证据的三态判定后降至 0.0% 且 Top-1 零损失（已验证，存在性判定机制）。

一个已被实测排除的错误做法：单纯提高弃权分数阈值无效，因为良性噪声与真故障的分数分布重叠（已验证）。这说明存在性判定必须依据终态证据的结构性特征，而不是给现有打分器加一道阈值。

阶段⑤ 新颖性判定：★当前最大缺口，也是最高优先级修复项

问题现状（已验证，实验 A/B）：

  • 实验 A（保留语义标注、移出知识图）：25 个全新故障会话中 0 次弃权、18 次正确命名、7 次自信答错；
  • 实验 B（真·全新故障，标注与传播边一并移除）：0 次弃权、25/25 全部给出错误命名（19 次误归 cert_expired、6 次误归 network_loss）。

这是一个必须修复的生产级风险：面对完全没见过的故障，系统 100% 硬安已知标签，从不说”我不认识”。在售后场景下，这意味着把维修人员导向完全错误的方向。

决定性发现（已验证）：纯确定性的新颖性信号一直存在，只是没有接进弃权决策。7 组种子 × 2 种故障类型交叉验证的判据对比：

判据 召回 误报 结论
新模板数 > 0 100.0% 0.0% ★最佳单一判据（全新故障会话平均 2.76 个新模板；已知故障 0.00 个）
未解释症状 > 0 100% 33.9%~55.7% 不可单用
未解释症状 ≥ 2 — 0% 召回仅 47%~79%，漏检

修复方案（P0，工作量小、收益极大）（已验证的建议）：

  1. 把”新模板数 > 0”直接接入弃权决策；
  2. 新模板存在时，已知根因置信度封顶；
  3. 输出结构化”未知故障签名”（模块/时间窗/新模板列表/违反的不变式/首次偏离点）替代猜一个名字。

  3. 新增 provenance.validated_sessions——该知识节点在多少个真实会话上被验证过，直接影响它在 Marketplace 的可信度排序；
  4. tier 取值定义为 experimental/candidate/production——对应知识的成熟度，与 17.6 节的审批分级挂钩。

设计决策 4 —— 三个占位领域用声明式 contribution 承载降级提示，而非硬编码分支（第十四部分已给出此建议，此处落实）。TSP/智驾/座舱三个领域各自有一个 capability.json，其 contribution 注入”该领域尚不支持，建议…”的提示片段。收益：开放第四个领域时只需新增一份清单 + 撤销降级 contribution，主流程代码零改动。

17.6.1 分级审核（设计，对应第十六部分决策 20）

诊断知识的错误代价远高于代码技能——一条错误的诊断断言可能把整个售后网络导向错误方向。因此审核分级比通用平台更严格：

技能层级 审核要求 可见范围

candidate 领域专家 1 人评审 + 必须附 ≥N 个验证会话 本部门可见，报告中标注”候选知识”
production 领域专家 2 人 + 质量部门会签 + 盲测集通过 全网可见，可进入正式诊断报告

设计决策 6 —— 晋级必须靠数据而非资历。 直接沿用 GSD 的”拒绝模型自评、路由到实测历史”原则（第三篇第四部分）：candidate → production 的晋级依据是该知识节点在盲测集上的实测表现，而不是提出人的判断或评审人的印象。示例项目既有的评测方法论纪律 D1~D6（报 CI 而非点估计 / McNemar 显著性 ns 不计贡献 / 必须纳入健康会话负样本 / 口径可辩护 / 自证指标单列 / 负面结果如实记载）（已验证）直接作为晋级评审的判定标准。

17.6.2 反馈治理与三集门禁

示例平台既有的机制（已验证）：反馈治理 + 影响域 + 按提交人隔离的三集门禁；实测投毒反馈被门禁 REJECT。

MVP 开发中发现并修复的四个真 bug 必须写进平台设计（已验证，且这些是极有价值的踩坑记录）：

  1. 必须区分 NOT_APPLICABLE（前件不适用，不罚）与 UNDETERMINED（缺口/时钟不可判），否则罕见故障传播断言会被系统性埋没；
  2. apply_patch 须 pin 住被反馈命中的断言，不被重放覆盖；
  3. 投毒必须针对承重根因边，且门禁须用严格正增益 τ_gain>0——因为图有冗余路径，回归集检测拦不住单点投毒；
  4. 三集隔离的作者分派须避免全员被污染。

设计：这四条应当作为平台的回归测试用例永久保留——它们是”曾经真的出过问题”的证据，对应 GSD 的做法（第四篇第十部分：universal-anti-patterns.md 把踩过的坑固化成 29 条规则；eslint-rules/ 把教训固化成 15 条自定义静态检查）。

17.7 Generator / Builder / AI Generator：让专家的边际产出最大化

这是 17.2 节那条结论的直接工程化：既然语义标注是不可替代的人工环节，平台的核心价值就在于把专家在这个环节的产出效率提到最高。

设计决策 7 —— 这套流程直接移植 GSD 的 spike --wrap-up 机制（第五篇第十三部分，本文唯一完整源码实证的动态技能生成机制）。三个可直接照搬的设计点：

  1. 增量而非重建——每次只处理上次生成之后新增的排查轨迹（靠 processed_* 元数据做差集），知识随排查次数持续生长；
  2. 三态经验分类，连死胡同也固化——INVALIDATED 的排查方向不丢弃，作为”地雷与死胡同”写进知识节点，防止未来的 Agent 重复踩同一个坑。这在诊断场景下价值极高：一个有经验的诊断专家的核心资产，恰恰是”我知道哪些方向不用查”；
  3. 按语义分组而非时间顺序——多次排查依据故障特征自动归类，每组产出一个独立的知识节点草案。

设计决策 8 —— AI Generator 只生成草案，绝不自动入库。 依据是 17.2 节的硬约束（无语义标注时命名级 Top-1 = 0）与三层准入模型（L0 结论层禁 LLM）。生成器可以做的是：聚类、提取共性模板、列出候选证据、起草结构；不能做的是：给根因命名、断言因果、直接写入生产准入子图。

17.9 生产落地最佳实践指南（十二条）

综合前八节，给出可直接执行的实践清单：

  1. 先修 NV-3——把”新模板数 > 0”接入弃权决策是投入产出比最高的一项：工作量小，把自信错误率从 100% 降到接近 0（已验证的判据，100% 召回/0% 误报）。
  2. 永远不要跳过故障存在性判定——否则健康车假阳性率 47.5%（已验证）。且注意：提高分数阈值这条路已被实测证伪。
  3. 时间质量必须标记并传播——跨 ECU 时钟不同步是纯日志场景的常态，ts_quality 标记是所有时序因果推理的前提。
  4. 压缩必须保留稀有模板——这是已验证的关键设计（99.4% 压缩率下根因链零丢失的原因）。稀有 ≠ 不重要，恰恰相反，纯日志场景下罕见模板往往就是故障信号。
  5. Tier-A 零 LLM 是硬性约束，且要在 CI 层面强制——import-linter/ArchUnit 静态检查 + NetworkPolicy 双重阻断（已验证），不要靠代码评审自觉。
  6. 确定性必须有跨进程回归测试——示例项目踩过这个坑（集合迭代顺序受哈希随机化影响 + 分数并列依赖插入顺序，导致同一输入三次运行结果 0.49/0.40/0.81）（已验证）。修复方式：全程定序 + 按字典序消解并列 + 三独立进程输出逐位比对进 CI。
  7. 诊断专家是瓶颈资源，按此排产——语义标注是根因命名的必要条件（四臂实验已证），排期时应把专家时间当作最稀缺资源来规划（已验证的实施计划判断）。
  8. 知识晋级靠盲测数据，不靠资历——candidate → production 的门槛是盲测集表现，评测口径遵循 D1~D6 纪律。
  9. 把踩过的坑固化成回归测试——17.6.2 节的四个真 bug 应永久保留为测试用例（对应 GSD 把教训固化成 eslint 规则与反模式清单的做法）。
  10. 报告里的每条结论都必须可追溯到 row_hash，且质量门要校验引用可解析性——已验证有效（伪造指纹被拦截）。建议进一步引入 Data-Flow Trace 校验完整引用链而非单点。
  11. 第三方依赖进入诊断关键路径前必须做供应链评估——LiteLLM 供应链事件是示例平台的真实教训（已验证）。
  12. 指标看板要诚实——不显著的项标 ns，权衡项标为权衡而非提升，自证指标单列不与外部验证指标混排。

17.11 本部分小结与下文预告

第十七部分把纯日志故障诊断这一最难档位的场景做了完整设计，核心结论三条：

  1. 必须区分三种能力——察觉新颖（能，实测 100% 召回 0% 误报）、刻画结构（能）、命名解释（不能，硬约束）。平台设计的正确目标不是消除专家，而是把专家的边际产出最大化；
  2. 当前最大的生产级风险是自信错误率 100%——面对全新故障从不弃权、100% 硬安已知标签。修复方案已验证可行且工作量小（把”新模板数>0”接入弃权决策），应列为 P0；
  3. GSD 的三条机制可直接迁移——spike --wrap-up 式的三态经验固化（含死胡同）用于知识生成、Data-Flow Trace 用于证据链完整性校验、”能在 CI 期强制的约束绝不留到运行期”用于 Tier-A 零 LLM 的硬性保障。

18.3 建议 Debug 顺序：从外到内、从声明到执行

当”某个能力/技能为什么没有生效”时，按以下顺序排查（设计，综合第四篇第八部分、第五篇第十二部分已验证的调试手段）：

    Q["现象：某能力/技能似乎没生效"] --> S1["① gsd loop render-hooks &lt;point&gt; --raw<br/>——检查它是否真的进入了运行时注册表<br/>（不需要跑真实会话）"]
    S1 -->|"不在 activeHooks 里"| S2["② gsd capability list<br/>——检查 status：active/incompatible/inactive"]
    S1 -->|"在，但内容不对"| S6["直接检查 fragment.inline 的实际渲染内容"]
    S2 -->|"incompatible"| FIX1["检查 engines.gsd 区间"]
    S2 -->|"inactive"| FIX2["检查本机 consent 记录（项目级能力）"]
    S2 -->|"active 但还是不对"| S3["③ gsd-tools skill-manifest<br/>——检查技能是否被正确发现（根路径/frontmatter）"]
    S3 --> S4["④ 检查 resolveProfile 输出<br/>——技能是否在当前 profile 闭包内"]
    S4 --> S5["⑤ 检查 STATE.md 的 status 字段<br/>——工作流是否处于预期阶段"]
    S5 --> S7["⑥ 最后才进入具体 Agent 的 Prompt 本身调试"]

这个顺序的设计理由：越靠前的检查点，验证成本越低（一条命令、不涉及真实 LLM 调用）；先排除”根本没被系统看见”，再排除”看见了但没生效”，最后才排查”生效了但内容不对”——这与本系列第五篇（第十二部分）强调的”用 render-hooks --raw 而非跑一次完整会话去调试”是同一条纪律的延伸。

20.1 Open-GSD 架构思想（一段话版）

GSD Core 的架构思想可以浓缩成一句话：把”如何让一个会退化的推理者，在一个不提供任何原生持久性保证的环境里，稳定完成复杂任务”这个问题，拆解成三个可以分别独立解决的子问题——上下文工程（对抗退化）、规范驱动开发（对抗歧义）、元提示（对抗知识流失）——然后用文件系统作为三者共享的、不依赖任何一次对话的真相之源。 它不试图让模型变得更强，而是设计一套让”当前这个模型”在恰当的约束与制品支持下稳定发挥的脚手架。

20.2 十大设计原则

  1. 薄编排器——编排层永不干重活，只路由、只更新状态（第一篇第一部分、第五篇第十一部分）；
  2. 新鲜上下文是结构性解法——不是权宜之计，是对 Context Rot 的直接回应（第一篇第一部分、第三篇第四部分）；
  3. 文件系统是唯一真相之源——对话历史随时可安全丢弃（第一篇第一部分、第三篇第四部分）；
  4. 缺省即启用——用户显式关闭而非显式开启默认行为（第一篇第一部分）；
  5. 纵深防御——多层独立机制各自生效，不依赖任何单一层完美（第一篇第一部分、第四篇第十部分、19.1 节）；
  6. 制品对等不等于信任对等——扩展能力可以对等，权威性不能对等（第二篇第三部分）；
  7. 第一方永远赢——覆盖被禁止，只能新增（第二篇第三部分、第四篇第六部分）；
  8. 响亮地失败开放——缺失一个控制点必须被看见，不能被静默吞掉（第二篇第三部分）；
  9. 拒绝模型自评，路由到实测历史——置信度必须来自历史数据而非自陈（第三篇第四部分）；
  10. 能在构建期/CI 期强制的约束，绝不留到运行期靠自觉——从技能依赖到编译产物同步，一以贯之（第二篇第二部分、第四篇第六部分、第十七部分）。

  5. computeClosure()/resolveProfile()——含能力贡献技能的闭包前注入 + 原型污染防护（第四篇第八部分）；
  6. worktree-safety.cts 的 Plan/Execute 拆分——SDD 哲学在函数签名级别的自我印证（第五篇第十一部分）；
  7. gsd-verifier.md 的 Data-Flow Trace（Step 4b）——沿数据流反向追溯到真实来源（第五篇第十一部分）；
  8. 两阶段命名空间路由 + spec-phase 的双父节点——DAG 而非树的技能路由（第一篇第一部分、第四篇第八、九部分）；
  9. untrusted-input-boundary.md——引用真实学术技术的 Prompt 级注入防御（第四篇第十部分）；
  10. spike-wrap-up.md——增量 + 三态经验（含死胡同）+ 自动分组的动态技能生成（第五篇第十三部分）。

20.4 十大值得借鉴（面向自研平台）

  1. “声明→生成→校验漂移”三件套，把一致性从自觉变成 CI 门禁（第二篇第二部分）；
  2. Capability 信任模型的三重屏障（同意+完整性+可逆性），诚实面对”没有沙箱”（第二篇第三部分）；
  3. Gate 四分类法作为全流程统一词汇表（第二篇第三部分、第五篇第十一部分、第十六部分）；
  4. 表驱动的状态治理模式（FIELD_CLASSIFICATION），策略变更降级为改一行（第五篇第十一部分、第十六部分）；
  5. Data-Flow Trace 验证方法论，适用于任何”表面完整、内里空心”的缺陷类别（第五篇第十一部分、第十四、十七部分）；
  6. 双缝注入 + 去重守卫，应对”宿主特性不可靠”的通用模式（第四篇第六部分）；
  7. 用确定性程序观测、用 Prompt 通道回传，绕开”LLM 无法自省”的死结（第三篇第四部分）；
  8. 拒绝模型自评、路由到实测历史的估算/置信度体系（第三篇第四部分）；
  9. 分层路由降低单次分类熵，而非追求更聪明的分类器（第四篇第九部分）；
  10. 把踩过的坑固化成可执行的静态检查规则（eslint-rules/ 与反模式清单），而不是写进永远不会被重读的文档（第四篇第十部分、第十九部分）。

20.5 十大可迁移思想（跨行业）

  1. 五阶段判据——“每一步防御上一步无法防御的失效模式”，任何行业的流程设计都可以用这条判据自检（第三篇第五部分、第十五部分）；
  2. “可迁移的是回答方式，不是回答内容”——上下文经济学/信任边界/验证方法论/工程一致性纪律这四个问题的答案可搬，具体 Agent 角色与制品格式不能搬（第十五部分）；
  3. “替换”永远集中在角色定义与留痕系统两处，其余大概率可复用（第十五部分）；
  4. 三层条件化生效（功能开关/版本门禁/运行时门禁）比单一 if-else 更适合长期演进（第五篇第十三部分）；
  5. 探索期先积累经验（含死胡同），成熟后再固化为正式资产，不要求一步到位设计完整（第五篇第十三部分、第十七部分）；
  6. 能力边界要靠受控实验诚实划定（如四臂归因分离实验），而不是靠直觉或愿望（第十七部分）；
  7. 分级审核优于”全开放”与”全审核”两个极端，取舍依据是生态规模与合规约束（第十六部分）；
  8. 观测数据脱敏是数据产生侧的责任，不是查询侧的责任（第十六部分）；
  9. 负面与不显著结果要如实呈现在指标看板上，不能只展示漂亮数字（第十七部分）；
  10. 用被验证过的方法论去建造承载这套方法论的工具本身（16.5 节，”用五阶段循环去建 ESR”）。

20.6 十大反模式

  1. 让通过的维度锚定判断——一份计划/一次审查可以在多数维度上通过，仍在关键维度上失败（第三篇第五部分、第十四部分）；
  2. 用非领域专属的通用 Agent 类型绕开审计与项目感知（第四篇第十部分、第十九部分）；
  3. 逐项走查检查清单式提问（第四篇第十部分）；
  4. 提高弃权/置信度阈值来掩盖分布重叠问题（第十七、十九部分）；
  5. 只验证”有引用”而不验证”引用链完整”（第五篇第十一部分、第十七部分）；
  6. 把宿主层面的成本问题（如 MCP Schema）误当成框架自身问题去优化（第三篇第四部分）；
  7. 固定分隔符包裹不可信内容（可被伪造）（第四篇第十部分）；
  8. 为了”图省事”给技能声明全部工具权限而非最小必要集合（第四篇第七部分、第十四部分）；
  9. 过度追求分类互斥性，牺牲可发现性（技能/知识节点必须唯一归属一个类目）（第四篇第九部分、第十七部分）；
  10. 声称”全自动学习出新知识/新根因”而没有实证过语义标注环节的必要性（第五篇第十三部分、第十七部分）。

20.7 十大最佳实践（可直接落地执行）

  1. Phase/任务开始前审计并关闭不需要的外部工具（MCP 等）接入（19.1 节）；
  2. 优先精简安装，按需扩展，而非默认全量（19.1 节）；
  3. 安全防线多层独立部署，不依赖单一层（19.1 节）；
  4. 强制第三方依赖/包合法性审计，警惕”幻觉包名被抢注”这类供应链攻击（第十七部分、19.1 节）；
  5. 技能描述控制在极小字符预算内，总预算按上下文窗口的固定比例设定（19.10 节）；
  6. 安全约束写到可执行细节（字符集/长度/拒绝模式），不停留在原则声明（19.10 节）；
  7. 依赖闭包与命名冲突检查提升为构建期门禁（19.11 节）；
  8. 把每一次真实故障复盘固化为一条永久回归测试，而非只写进文档（17.6.2、19.6 节）；
  9. 中断点数量本身要被计量为成本，检查点尽量批量后移（第三篇第四部分、19.9 节）；
  10. 指标看板如实呈现负面与不显著结果，权衡不等于提升（第十七部分、19.6 节）。

20.8 十大企业级落地建议

  1. 不要直接照搬 GSD 单机形态，服务化时明确”哪些原则不变、哪些取舍要反转”（沙箱是目前唯一确认要反转的一条）（第十六部分）；
  2. 用编排图引擎（如状态图/工作流引擎）实现五阶段循环，不要自研编排 DSL（第十六部分）；
  3. 把断点续跑交给成熟的持久化工作流引擎，而不是自己维护文件探测逻辑（第十六部分）；
  4. 观测三层分工——系统层/LLM 调用层/成本层各自用专门工具，不要试图一个工具包打天下（第十六部分）；
  5. Marketplace 治理采用分级审核而非全开放或全人工审核两个极端（第十六部分）；
  6. 领域知识资产（诊断规则、合规条款、行业本体）用能力清单机制承载，独立版本、独立开关（第十四、十七部分）；
  7. 涉及”发现新模式/新故障/新知识”的能力，必须先做受控实验诚实划定”能做到什么、做不到什么”，再设计产品形态（第十七部分）；
  8. 涉及人身安全或高代价错误的领域（医疗、金融、设备诊断），验证层要比通用软件工程领域更重，且要有专门的合规 Gate（第十四、十五、十七部分）；
  9. 把专家在系统中不可替代的环节（如语义标注、根因命名）识别出来，设计流程把专家的边际产出最大化，而不是试图让 AI 越俎代庖（第十七部分）；
  10. 把”这套方法论如何指导自己的建设过程”作为验收标准之一——如果一个团队设计的 Skill 平台自己都不用五阶段循环去管理自己的开发，这本身就是一个信号（第二篇第二部分 GSD 自我 dogfooding 的印证 + 16.5 节）。
