Open-GSD 源码解析（二）：仓库结构与十一层架构

Open-GSD 源码解析系列第二篇：逐目录解析 gsd-core 仓库的顶层入口与七个功能簇，梳理声明式、命令式、协议化三条分发路径，再把仓库切分为十一层抽象架构…

先读结论

  1. commands/gsd/ 与 skills/ 是同一源头的两种生成形态，而不是两套并行维护的逻辑。
  2. 声明式、命令式、协议化（MCP Server）三条分发路径并存，同一核心逻辑以多种形态分发到不同宿主。
  3. “声明 → 生成 → 校验漂移”的闭环纪律贯穿几乎所有派生产物，由生成脚本与 Lint 共同保障。
  4. 十一层架构用 Context、Configuration、Git 三个横切关注点，把横向的五阶段循环与纵向的基础设施粘合起来。
  5. Capability 体系的“制品对等不等于信任对等”“第一方永远赢”“Gate 必须响亮地失败开放”是全框架工程含金量最高的设计之一。

本篇导读：本篇回答两个问题：open-gsd/gsd-core 仓库里每个顶层目录放了什么、负责什么；这些目录又如何被组织成十一层抽象架构。上一篇界定了 GSD Core 的定位与五阶段循环，本篇把视角落到仓库与架构本身，为后续的上下文工程与 Skill 机制分析提供一张可回查的源码地图。

第二部分 · Repository 全面解析

2.0 总览：24 个顶层入口，按七个功能簇归类

open-gsd/gsd-core 仓库顶层直接可见的目录与关键文件多达 20 余个，逐一平铺讲解会失去结构感。本文按职责相似性将其归入七个功能簇，再逐一展开每个目录的”用途 / 职责 / 生命周期 / 依赖关系 / 入口位置 / 主要对象 / 典型调用”七维信息。七个簇分别是：

  • 簇 A 用户可见 Prompt 层——commands/gsd/、skills/、agents/
  • 簇 B 编排引擎室——gsd-core/（内含 bin/ workflows/ references/ templates/ contexts/）
  • 簇 C 能力与生态适配层——capabilities/、hooks/、pi/、vscode/、.opencode/、.kilo/、.claude-plugin/
  • 簇 D 确定性源码与构建——顶层 src/、顶层 bin/、scripts/
  • 簇 E 质量保障——tests/、eslint-rules/、.githooks/、.github/
  • 簇 F 文档体系——docs/（21 个子目录）
  • 簇 G 项目自我治理与元数据——.changeset/、.plans/、.out-of-scope/、assets/、examples/、根目录治理文件

本节末尾给出覆盖全部七簇的依赖关系图。

2.1 簇 A · 用户可见 Prompt 层

这一簇是用户直接触达的表层——一条 /gsd-plan-phase 命令，背后牵动的正是这三个目录的协同。

commands/gsd/（71 个 .md 文件，含 6 个命名空间路由命令）

  • 用途：用户在宿主 Runtime 中键入的斜杠命令的 Prompt 源文件，是”人类意图”进入 GSD 世界的第一道入口。
  • 职责：解析命令参数（$ARGUMENTS）、做最基本的子命令分流（如 gsd-quick 内部区分 list/status/resume/run），然后把控制权移交给 gsd-core/workflows/ 里对应的工作流文件；命令文件本身不承载重编排逻辑。
  • 生命周期：每次用户键入命令时从磁盘重新加载（无常驻状态），执行完毕后生命周期结束，状态留存在 .planning/。
  • 依赖关系：通过 YAML frontmatter 的 allowed-tools 声明工具白名单；通过 <execution_context> 块里的 @-引用指向 gsd-core/workflows/*.md；两阶段路由下，6 个 ns-*.md 命名空间命令还会指向具体命令文件。
  • 入口位置：commands/gsd/<name>.md；生成的派生形态还会被复制到各宿主的斜杠命令目录（如 Claude Code 本地安装的 commands/gsd/）。
  • 主要对象：Frontmatter 字段 name/description/argument-hint/allowed-tools；正文的 <objective> <execution_context> <context> <process> <notes> <security_notes> 语义块（完整字段级解析见本系列第四篇第七部分）。
  • 典型调用：用户输入 /gsd-plan-phase、/gsd-quick fix the login bug。

skills/（71 个目录，与 commands/gsd/ 一一对应）

  • 用途：把 commands/gsd/ 里的同一批能力，转换为 Claude Code 官方 Agent Skills 标准形态（SKILL.md + frontmatter），供支持原生 Skill 机制的宿主（Claude Code 全局安装、Codex、Antigravity、Kimi CLI 等）加载。
  • 职责：与 commands/gsd/ 完全相同的编排职责，只是打包格式不同——这不是两套独立逻辑，而是同一源头的两种分发形态。直接证据：package.json 的 gen:plugin-skills 脚本（node scripts/gen-plugin-skills.cjs --write）——skills/ 目录的内容是从 commands/gsd/ 生成出来的派生产物，而非独立维护的第二份源码。这也解释了为什么两个目录下文件数量恰好都是 71：一一对应。
  • 生命周期：随 npm run build（内含 gen:plugin-skills）重新生成；lint:generated-sync 会检查这份生成产物是否与源头保持同步（漂移即报错），防止手工改了一份却忘了另一份。
  • 依赖关系：源自 commands/gsd/*.md（生成关系）；6 个命名空间路由技能（gsd-ns-*）内嵌路由表指向具体技能；两阶段路由（v1.40，#2792）下，非递归加载器宿主会把约 65 个具体技能嵌套到 <router>/skills/<name>/SKILL.md。
  • 入口位置：skills/<name>/SKILL.md。
  • 主要对象：与 commands/gsd/ 相同的 frontmatter + 语义块结构（详见本系列第四篇第七部分逐字段解析），外加两阶段路由场景下的路由表（竖线分隔关键词标签，见本系列第一篇第一部分 1.7 节）。
  • 典型调用：模型在推理过程中根据用户自然语言意图自主匹配并调用 Skill 工具（而非用户手打斜杠），或先命中命名空间路由技能再被指引读取具体技能文件。

agents/（33 个 .md 文件）

  • 用途：定义每一种”可被派生”的专职子代理的角色、能力边界与输出契约。
  • 职责：每个 Agent 文件是一份独立的角色 Prompt——研究、规划、执行、验证、审计、调试等各司其职（完整角色一览见本系列第一篇第一部分 1.5 节的”主编排层派生分类”表）；Agent 本身不感知整个项目历史，只感知被显式传入它的那份上下文载荷。
  • 生命周期：由某个 workflow 在需要时派生（spawn），带着全新 200K（或 1M）上下文窗口运行，任务完成、产出约定的 Markdown 制品后终止——不常驻、不复用会话。
  • 依赖关系：Frontmatter 声明 name/description/tools（工具白名单）/color（终端区分色）；被 gsd-core/workflows/*.md 中的派生指令（Task/Agent 工具调用）引用；部分”进阶/专用”Agent（如 gsd-pattern-mapper、gsd-mempalace-curator）由 capabilities/*/capability.json 的 agents 字段声明归属，说明 Agent 目录也是第三方能力可以贡献新角色的扩展点之一。
  • 入口位置：agents/gsd-<role>.md。
  • 主要对象：Frontmatter 里的工具白名单（决定这个 Agent 能不能写文件、能不能跑 Bash、能不能联网搜索）是它安全边界的核心。
  • 典型调用：gsd-core/workflows/plan-phase.md 内部以 Task 工具派生 gsd-phase-researcher → 完成后再派生 gsd-planner → 再派生 gsd-plan-checker，形成本系列第一篇（第一部分）1.10 节时序图里的那条链路。

2.2 簇 B · 编排引擎室 —— gsd-core/

这是整个框架”脑干”所在的目录，内部又分五个子目录，各自职责分明：

子目录 用途 规模（本次克隆实测） 典型调用方式
gsd-core/workflows/ 编排逻辑本体——加载上下文、派生 Agent、管理 Gate/Checkpoint、更新状态 顶层 91 个 .md，另有 discuss-phase/ plan-phase/ help/ execute-phase/ 四个子目录承载”按模式拆分”的正文体（见下文） 被 commands/gsd/*.md 或 skills/*/SKILL.md 的 <execution_context> 块通过 @~/.claude/gsd-core/workflows/<name>.md 引用加载

2.2.1 渐进式披露：workflow 文件的字节预算纪律

docs/ARCHITECTURE.md 记录了一项对上下文工程哲学高度自洽的工程纪律——workflow 文件字节预算分级：

分级 单文件字节上限 适用对象
XL 90,000 字节 顶层编排器（execute-phase、plan-phase、new-project）
LARGE 54,000 字节 多步骤规划器与大型功能工作流
DEFAULT 38,000 字节 聚焦的单一用途工作流（目标分级）

预算以字节而非行数计量（#717）——原文给出的理由是：行数计量会误伤散文、又漏抓 token 密集的表格与代码块，而字节是确定性的，且恰好匹配供应商侧的真实限制单位（Codex 会在 32,768 字节处截断指令文档）。XL/LARGE 的上限之所以高于 32,768，是因为这些是被 Claude 加载的”祖父级”顶层编排器，不是 Codex 的 AGENTS.md。

为什么要设这个预算：原文特别区分了”成本”与”质量”两个理由——启用 Prompt 缓存后，加载一个大型 workflow 的单次调用成本其实并不高（缓存命中约为原生输入成本的 10%）；真正更硬核、且与缓存无关的理由是质量：随着上下文增长，模型的召回与推理能力会退化（也就是 Context Rot / 注意力预算问题），所以更精简、信噪比更高的指令会产出更好的规划结果。这个字节上限保护的是 Agent 的注意力，而不仅仅是账单。

当一个 workflow 文件超出所属分级时，标准做法是把”按模式变化的正文体”拆分到 workflows/<workflow>/modes/<mode>.md，把模板拆到 workflows/<workflow>/templates/，把共享知识拆到 gsd-core/references/，父文件退化为一个”薄分发器”——只在被实际调用的那个模式下才去 Read 对应的 mode/template 文件。workflows/discuss-phase/ 正是这一模式的范例：父文件负责分发，modes/ 目录下的 power.md、all.md、auto.md、chain.md、text.md、batch.md、analyze.md、default.md、advisor.md 各自承载对应 --power/--all/--auto 等参数下的具体行为，templates/ 目录下的 CONTEXT.md、DISCUSSION-LOG.md、checkpoint.json 模板只在真正要写那个输出文件时才被读取。

这条纪律在 plan-phase.md、execute-phase.md 以及 gsd-planner/gsd-executor 两个 Agent 定义上同样适用——planner-mvp-mode.md、user-story-template.md、skeleton-template.md、execute-mvp-tdd.md 这些”仅 MVP/Walking-Skeleton/MVP+TDD 路径才需要”的引用体被设计为按需 Read，而不是无条件 @-导入，以防止”@-导入即使被包在条件分支里，加载时仍会无条件触发”这个真实踩过的坑（#720：条件分支背后的 @-导入依旧会被急切加载,这是它的机制性质决定的，不是文档写法问题）。

2.2.2 gsd-core/bin/：CLI 工具层的双重结构

这里存在一处需要格外小心的命名相似性陷阱——gsd-core/bin/ ≠ 顶层 bin/，二者角色完全不同（顶层 bin/ 见簇 D 的展开）。gsd-core/bin/ 内部结构：

  • 用途：gsd-tools.cjs 是整个框架里唯一的确定性程序——负责状态机（STATE.md 读写）、模板填充、配置解析、能力注册表加载等一切”不该交给 LLM 去猜”的逻辑。
  • 职责：所有 workflow 通过 Bash 工具调用它来做确定性操作（如 gsd-tools.cjs init plan-phase、gsd-tools.cjs state update），本身不调用任何 LLM。
  • 生命周期：每次被 Bash 调用时启动、执行、退出（无常驻进程）。
  • 依赖关系：require() 加载 gsd-core/bin/lib/*.cjs 中的领域模块；通过 capability-loader.cjs 的 loadRegistry({ includeInstalled }) 合并第三方能力注册表。
  • 入口位置：package.json 的 bin.gsd-tools 字段指向 gsd-core/bin/gsd-tools.cjs。
  • 主要对象：command-routing-hub.cjs（无抛出的纯结果契约：dispatch() 内部捕获异常，返回 { ok:false, kind, ...typedPayload }；封闭的错误分类法 UnknownCommand/InvalidArgs/HandlerRefusal/HandlerFailure）。
  • 典型调用：gsd-tools.cjs init plan-phase、gsd-tools.cjs query research-plan、gsd-tools.cjs capability state。

编译产物 vs 源码——一处需要如实存疑的地方：gsd-core/bin/lib/ 本次实测只有 17 个文件（api-coverage.cjs、assumption-delta.cjs、capability-command-router.cjs、capability-registry.cjs、capability-validator.cjs、claude-orchestration.cjs 等），而顶层 src/ 目录下有约 180 个 .cts（TypeScript CommonJS 源文件）。package.json 的 build:lib 脚本明确写的是 tsc -p tsconfig.build.json，说明 src/*.cts 确实是通过 TypeScript 编译产出 .cjs 的源头——但 17 对 180 的数量差距相当悬殊，直接断言”每个 src/*.cts 都一一编译进 gsd-core/bin/lib/“并不严谨。较可能的情况是：tsconfig.build.json 的 include 范围只覆盖需要被独立 require()（例如被第三方能力路由、被安装器直接调用）的一小部分模块，其余大多数 src/*.cts 可能是被打包进单体 gsd-tools.cjs（打包方式尚未在本次研究中直接追踪到），或是仅服务于测试。本文不对这一构建拓扑做进一步猜测，把它列为本系列第五篇（第十一部分）”源码阅读”里值得亲自用 tsc --listFiles 或追踪 tsconfig.build.json 的 include/exclude 字段去验证的具体问题，而不是在此断言一个我未曾亲眼验证的编译映射关系。

2.3 簇 C · 能力与生态适配层

capabilities/（44 个子目录）

  • 用途：GSD Core 的扩展系统本体——每个子目录代表一个可插拔的”能力”（Capability），既包括按宿主 Runtime 划分的适配器（claude、codex、cursor、copilot、gemini、antigravity、opencode、kilo、kimi、kimi-code、cline、trae、windsurf、augment、coderabbit、codebuddy、qwen、ollama、lm-studio、llama-cpp、vscode、zcode、pi —— 共 22 个），也包括跨运行时的横切功能特性（ai-integration、assumption-delta、audit、broken-windows、claude-orchestration、code-review、drift、external-job、gap-analysis、graphify、hermes、intel、mempalace、nyquist、pattern-mapper、profile-pipeline、research、schema-gate、security、tdd、ui —— 共 22 个）。
  • 职责：每个能力子目录内的 capability.json 声明它自己的元数据、依赖、启用条件与贡献点（skills/agents/commands/hooks），由中心化的能力注册表在启动时统一装配，而不是散落地写死在主程序里。本次实测的 graphify/capability.json 示例（本系列第一篇第一部分未展开，此处补全）：

（完整字段级语义解析——tier、engines.gsd、activationKey、信任模型——将在本系列第四篇第六、第七部分结合 capability-trust-model.md 与 capability-overlay-model.md 展开，此处仅作为目录职责的实证。）

  • 生命周期：由 capability-loader.cjs 的 loadRegistry({ includeInstalled }) 在运行时装配——第一方能力（内置于本仓库的 44 个）永远最先被冻结进 capability-registry.cjs（由 scripts/gen-capability-registry.cjs 生成）；第三方能力从全局 $GSD_HOME/.gsd/capabilities/ 或项目级 <projectRoot>/.gsd/capabilities/ 读取，经过同意（consent）与完整性校验后以”覆盖层”（overlay）形式叠加，第一方永远优先，装载失败的能力”失败即开放”（fail-open：不阻断整体运行，只报警告）。
  • 依赖关系：capability.json 里的 commands 字段指向 gsd-core/bin/lib/ 下的路由模块（如上例的 graphify-command-router.cjs）；skills/agents 字段与 skills/、agents/ 目录的具体条目建立映射关系；hooks 字段与 hooks/ 目录的钩子建立映射。
  • 入口位置：capabilities/<id>/capability.json（清单）+ 该目录下可能存在的 fragments/ 子目录（部分能力如 ai-integration、assumption-delta、claude-orchestration、external-job、mempalace、pattern-mapper、research、schema-gate 携带 fragments/ 子目录，推测是可复用的 Prompt 片段库，留待本系列第四篇第六部分深挖）。
  • 主要对象：capability.json 清单本身；对应的 commands/gsd/*.md、skills/*/SKILL.md、agents/*.md、hooks/*.js 条目。
  • 典型调用：gsd capability list / gsd capability install <id> / gsd capability remove <id>（第三方能力生命周期管理命令，详见本系列第四篇第九部分 docs/reference/gsd-capability-command.md）。

hooks/（运行时生命周期钩子，与 .githooks/ 严格区分）

  • 用途：安装进宿主 Agent Runtime、在其生命周期事件（而非 Git 生命周期事件）上被自动触发的 JS/Shell 脚本——这与簇 E 里”仓库自己开发用”的 .githooks/（pre-commit/pre-push）是两个完全不同的概念,极易混淆,本文做明确切割。
  • 职责：见本系列第一篇（第一部分）1.10 节已列出的钩子表（gsd-statusline.js/gsd-context-monitor.js/gsd-check-update.js/gsd-prompt-guard.js/gsd-read-injection-scanner.js 等）——涵盖状态栏渲染、上下文余量监控预警、后台更新检查、Prompt 注入扫描、未读文件写保护等。
  • 生命周期：由宿主 Runtime 原生的 Hook 注册机制（如 Claude Code 的 settings.json “hooks” 字段）在 SessionStart/PreCompact/PostToolUse/PreToolUse/Stop/SubagentStop 等事件触发时调用,GSD 自身不主动轮询。
  • 依赖关系：被 bin/install.js 安装时写入宿主对应的 Hook 注册配置（如 Claude Code 的 .claude/settings.json）；部分钩子（gsd-ensure-canonical-path.js）专门处理 Claude Code 插件安装形态下的符号链接自愈（~/.claude/gsd-core/{bin,contexts,references,templates,workflows} 软链到插件自带目录树，在 claude plugin update 后自我修复，#997）。
  • 入口位置：hooks/<name>.js 或 .sh。
  • 主要对象：每个钩子文件对应一个具体宿主事件类型。
  • 典型调用：完全被动——宿主 Runtime 在到达对应事件时自动调用，用户或 Agent 均无需显式触发。

pi/、vscode/、.opencode/plugins/、.kilo/plugins/、.claude-plugin/：五种”命令式/声明式”分发末梢

这五个目录都服务同一个目的——把 GSD 的能力接到某个特定宿主的原生插件 API 上，但彼此实现方式不同，值得并列澄清（src/adapter-declarative.cts 与 src/adapter-imperative.cts 两个源文件名恰好印证了这里存在”声明式 vs 命令式”两条路径）：

  • pi/gsd.cjs（务必注意：这与”GSD Pi”独立产品没有任何关系，纯属命名巧合——见本系列第一篇第〇部分 0.2 节的谱系澄清表）——这是为第三方 Programmatic-CLI 宿主 pi（pi.dev，npm 包 @earendil-works/pi-coding-agent）编写的命令式扩展，通过 registerCommand/registerTool/pi.on(event, handler) 等 ExtensionAPI 把 GSD 命令面绑定进 pi。安装时被复制为 ~/.pi/agent/extensions/gsd.js（注意目标文件后缀被人为改成 .js，因为 pi 的 isExtensionFile() 探测函数只认 .ts/.js，.cjs 会被静默跳过而不报错——#2470 记录的一处真实踩坑；源文件自身仍保留 .cjs 后缀是因为测试要直接 require() 它，而 pi 加载复制后的文件走的是 jiti，对 CommonJS/ESM 都能处理，所以后缀只影响”能否被发现”，不影响”能否被解析”）。
  • vscode/（extension.js/browser.js/host-binding.js/package.json）——一个真实、独立的 VS Code 扩展实现，而不只是 capabilities/vscode/ 里的能力声明。
  • .opencode/plugins/gsd-core.js、.kilo/plugins/gsd-core.js —— 分别是 OpenCode 与 Kilo 两个宿主的命令式插件入口（package.json 的 main 字段直接指向 .opencode/plugins/gsd-core.js，说明 OpenCode 路径是 npm 包的默认主入口）。
  • .claude-plugin/ —— Claude Code 插件市场（Marketplace）清单，本次实测内容确认了包名、版本（1.9.1，与 package.json 一致）、owner 为 open-gsd 组织；这是 GSD Core 除”手动 npx 安装”之外的第二条分发通道——通过 Claude Code 官方插件市场机制直接安装。

这一小节的核心结论：GSD Core 对”如何把自己接进宿主”这件事,并非只有一种”复制 Markdown 文件”的套路——面对原生支持 Skill/Command 机制的宿主（Claude Code、Codex、Cursor、Copilot、Antigravity 等）走声明式路径（纯 Prompt 文件 + 安装器搬运）；面对暴露编程式扩展 API 的宿主（OpenCode、Kilo、pi.dev）走命令式路径（真正的 JS/TS 代码去调用宿主的 registerCommand/registerTool API）。这是理解”Skill Runtime 如何跨生态迁移”（本系列第六篇第十五部分的核心问题）时最值得借鉴的一处设计。

2.4 簇 D · 确定性源码与构建

顶层 src/（约 180 个 .cts 文件，唯一真源）

  • 用途：整个 gsd-tools.cjs CLI 与各类能力路由器背后真正的 TypeScript 实现，是全部确定性逻辑的唯一权威源码。
  • 职责：按领域拆分得极细——从状态管理（state.cts/state-transition.cts/state-io.cts/state-document.cts）、配置（config.cts/config-loader.cts/config-schema.cts/federated-config.cts）、能力全生命周期（capability-activation.cts/capability-consent.cts/capability-ledger.cts/capability-lifecycle.cts/capability-loader.cts/capability-lock.cts/capability-source.cts/capability-state.cts/capability-trust.cts/capability-writer.cts——十个模块专门服务能力子系统,足见其复杂度）、到质量类横切能力的具体实现（assumption-delta.cts/broken-windows.cts/drift.cts/edge-probe.cts/gap-checker.cts/prohibition-enforcement.cts，与 capabilities/ 下同名目录一一对应）、安装器迁移链（installer-migrations/000-first-time-baseline.cts 一路到 006-pi-extension-cjs-to-js.cts，编号化管理每一次破坏性安装拓扑变更，其中 003-rename-get-shit-done-to-gsd-core.cts 直接印证了本系列第一篇第〇部分记录的包名迁移史)。
  • 生命周期：开发者本地或 CI 执行 npm run build:lib（等价于 tsc -p tsconfig.build.json）编译；不会被运行时直接执行——运行时执行的是编译产物。
  • 依赖关系：编译目标为 gsd-core/bin/lib/*.cjs（数量对应关系见 2.2.2 节的存疑说明）；被 tests/*.test.cjs 直接测试（多数测试针对编译前的 .cts 还是编译后的 .cjs，需按具体测试文件的 import 路径确认，本文不做统一断言）。
  • 入口位置：无单一入口——是一整片按领域拆分的模块集合，tsconfig.build.json 决定实际编译范围。
  • 主要对象：.cts 文件（TypeScript 编写但产出 CommonJS 的约定后缀）。
  • 典型调用：npm run build:lib、npm run prepack（发布前自动触发）。

顶层 bin/（与 gsd-core/bin/ 严格区分——这是包级入口，不是运行时库）

  • 用途：npm 包的顶层可执行入口，是外部世界（npx、其他 MCP 宿主）唯一直接调用的地方。
  • 职责与主要对象：
    • install.js（615KB，单体巨型文件）——安装器本体，负责探测目标 Runtime、做安装形态转换（如 convertClaudeCommandToClaudeSkill）、把 commands//skills//agents//hooks//capabilities//pi//vscode//.opencode//.kilo/ 等一切”要交付给用户机器”的内容，按目标 Runtime 的目录规范转换、复制、注册。
    • gsd-mcp-server.js——MCP Server 独立入口（ADR-1239 Phase C-2/#1681）。这是一枚容易被忽视但意义重大的组件：它把 GSD 的”接口点 1（命令）+ 接口点 5（状态 I/O）”通过标准 stdio JSON-RPC 2.0 协议暴露出来，使得任何”消费 MCP”的宿主（Claude、Codex、OpenCode、VS Code、Gemini、Cursor、Cline、Hermes 等，源码注释原文列举）都可以在无需为 GSD 编写专属插件的前提下驱动它——这是继”声明式 Prompt 安装”与”命令式插件 API”之后的第三条集成路径：协议化（MCP）。源码注释特别强调：这个文件必须放在顶层 bin/，而不能放进 gsd-core/bin/，因为后者的内容会被安装器复制进每一个宿主的安装目录——放错位置会导致这个”包级二进制”被错误地散落进每一份 Runtime 安装产物里，破坏”golden parity”（黄金基线一致性，scripts/ 目录下的 gen-install-tree-fixtures.cjs 正是用来生成/校验这份基线的）。
  • 生命周期：install.js 仅在用户安装/更新时运行一次；gsd-mcp-server.js 作为长驻 stdio 进程运行，直到 stdin 关闭。
  • 依赖关系：install.js 大量依赖 gsd-core/bin/lib/ 下的辅助模块（shell-command-projection.cjs、command-roster.cjs、runtime-homes.cjs 等，从其 require 语句直接可见）；gsd-mcp-server.js 委托给 gsd-core/bin/lib/mcp-server.cjs（编译自 src/mcp-server.cts）。
  • 入口位置：package.json 的 bin 字段——"gsd-core": "bin/install.js"、"gsd-mcp-server": "bin/gsd-mcp-server.js"。
  • 典型调用：npx @opengsd/gsd-core@latest（安装/更新）；npx gsd-mcp-server（作为 MCP Server 被拉起）。

scripts/（约 90 个文件，构建/生成/Lint 三位一体）

  • 用途：项目自身的工程化基础设施——不是面向最终用户的功能,而是保障”仓库这个复杂系统自身不腐化”的一整套自动化。
  • 职责：三大类脚本各司其职：
    1. 代码生成（gen-*.cjs，约 12 个）——gen-capability-registry.cjs、gen-capability-matrix.cjs、gen-inventory-manifest.cjs、gen-loop-host-contract.cjs、gen-adr-index.cjs、gen-plugin-skills.cjs、gen-registry.cjs、gen-research-agents.cjs、gen-install-tree-fixtures.cjs 等，均支持 --write（生成/覆写）与 --check（只校验、不改写，供 CI 判断是否漂移）两种模式；
    2. 漂移防护 Lint（lint-*.cjs，约 20 个）——lint-alias-drift、lint-command-contract、lint-compiled-artifact-sync（校验 src/*.cts 与 gsd-core/bin/lib/*.cjs 是否同步）、lint-descriptions（校验 SKILL.md 等的 description 字段质量）、lint-skill-deps、lint-table-schema-drift、lint-test-file-count 等；
    3. Changesets 版本管理（changeset/ 子目录）——cli.cjs/new.cjs/parse.cjs/render.cjs/serialize.cjs/github-release-notes.cjs，对应根目录 .changeset/ 的消费端。
  • 生命周期：由 package.json 的 scripts 字段编排——npm run build（全量重建：identity→lib→plugin-skills→loop-host-contract→capability-registry→hooks）、npm run regen:derived（更彻底的全量再生成，含 ADR 索引/能力矩阵/清单/版本同步）、npm run lint:ci（CI 专用的完整 Lint 链，串联十余个独立校验脚本）。
  • 依赖关系：gen-*.cjs 读取 capabilities/*/capability.json、skills/、agents/、commands/ 等声明式源头,写出 gsd-core/bin/lib/capability-registry.cjs、docs/reference/capability-matrix.md、docs/registries/reviewer-registry.md、docs/INVENTORY.md（经 INVENTORY-MANIFEST.json）等派生产物。
  • 入口位置：scripts/<name>.cjs，经由 package.json scripts 字段暴露的 npm run 命令调用。
  • 主要对象：每个脚本对应一类”声明 → 生成物”的单向数据流,配合对应的 --check 模式形成”生成 + 校验”闭环。
  • 典型调用：npm run gen:capability-registry -- --write（本地生成）、CI 中的 npm run lint:generated-sync（校验所有生成物是否与声明保持同步,任何手改声明忘记重新生成的情况都会在这一步被拦截）。

这一簇最值得借鉴的模式（详细展开见本系列第六篇第十九部分，此处先点出）：GSD Core 把”声明 → 生成 → 校验漂移”做成了一条闭环流水线,任何人手改 capability.json 却忘了跑生成脚本,CI 会直接拒绝合并——这比”文档写了让大家自觉保持同步”可靠得多,是后续本系列第六篇（第十六部分）设计下一代 Enterprise Skill Runtime 时应当直接复用的骨架模式。

2.9 本部分小结与下文预告

第二部分把 24 个顶层入口归入七个功能簇,逐一核实了用途/职责/生命周期/依赖/入口/主要对象/典型调用。三个最值得记住的结构性发现：

  1. commands/gsd/ 与 skills/ 是同一源头的两种生成形态（由 gen-plugin-skills.cjs 派生），而不是两套并行维护的逻辑——理解这一点,才能正确回答”改一个命令是不是要改两个地方”这类实操问题；
  2. “声明式 vs 命令式”两条分发路径并存：面向原生 Skill/Command 机制的宿主走纯 Prompt 文件路径，面向暴露编程 API 的宿主（OpenCode、Kilo、pi.dev）走真正的 JS/TS 插件代码路径，此外还有第三条协议化路径——顶层 bin/gsd-mcp-server.js 把核心能力暴露成标准 MCP Server；
  3. “声明 → 生成 → 校验漂移”的闭环工程纪律贯穿 capability.json、skills/、docs/INVENTORY.md、docs/reference/capability-matrix.md 等几乎所有派生产物,由 scripts/gen-*.cjs + scripts/lint-*.cjs + npm run lint:generated-sync 三件套共同保障，这是本仓库在工程纪律上最值得后续本系列第六篇第十六部分（自研 Enterprise Skill Runtime）直接借鉴的骨架。

3.1 Framework Layer

维度 内容
职责 定义 GSD 作为”元框架”的身份契约本身——不是一个 Agent,而是一套可安装进任意宿主 Runtime 的纪律层；同时拥有版本号、分发渠道（npm 包、Claude Code 插件市场）与跨语言文档
输入 用户”要不要采用 GSD 方法论”这一决策本身；安装时用户选择的目标 Runtime
输出 一份被安装、按目标 Runtime 转换过的 GSD Prompt + 工具集合,落在用户机器或项目目录里
生命周期 Install → Update（gsd-check-update.js 后台检查）→（较少见）Uninstall；贯穿一个 GSD 管理项目的整个生命周期,跨越无数个 Milestone 和 Phase
扩展点 新增目标 Runtime（新增 capabilities/<runtime>/）；新增分发渠道（目前已有 npm 包 + .claude-plugin/ 插件市场清单 + bin/gsd-mcp-server.js 协议化通道三条）
设计原因 “做一个能装进别的 Agent 里的框架”而不是”自己做一个 Agent 产品”,是 GSD 能够在一个高度碎片化（16+ 宿主并存）的生态里保持中立、不与任一头部产品正面竞争,同时反过来吃到所有头部产品用户增量的关键定位选择

3.2 Core Layer

维度 内容
职责 整个框架里唯一不关心自己正跑在哪个宿主上的部分——承载全部编排逻辑本体
输入 一次已被 Command/Skill 层解析过的调用（携带 $ARGUMENTS）+ 其 <execution_context> 指向的具体 workflow 文件
输出 一整条 Agent 派生链的执行结果,最终固化为 .planning/ 下的结构化制品
生命周期 每次命令调用都重新从磁盘加载（无常驻进程、无内存态）；唯一的”复用”来自宿主 LLM API 自身的 Prompt 缓存机制,与 GSD 无关
扩展点 新增 gsd-core/workflows/*.md（新编排逻辑）、新增 gsd-core/references/*.md（新共享知识,渐进式披露）、新增 gsd-core/templates/*（新制品模板）
设计原因 把全部编排逻辑收敛到一处、且与 Runtime 完全解耦,是让 16+ 个宿主能够共享同一份被持续维护的核心逻辑、而不是各自维护一份逐渐分叉实现的根本原因——第二部分 2.2.1 节的”字节预算分级”纪律正是为保护这层的可维护性而存在

3.3 Runtime Layer

维度 内容
职责 把 Core 层”与 Runtime 无关”的 Prompt 逻辑,转译成每个具体宿主真正认识的扩展形态
输入 Core 层的 Command/Skill Markdown 源文件 + 安装时确定的目标 Runtime 身份
输出 一个宿主原生的产物——Claude Code 的 Skill/Slash-Command、Codex 的 Skill、OpenCode 的插件 JS、pi.dev 的 Extension、VS Code 扩展,或者一个独立的 MCP Server 进程
生命周期 声明式路径在安装时一次性物化（复制+转换）；命令式路径由宿主自身的插件加载器在每次宿主启动时原生加载；协议化路径（MCP Server）作为长驻进程被宿主按需拉起
扩展点 新增 capabilities/<runtime>/ 适配目录；理论上还可以新增第四种适配范式（目前是声明式/命令式/协议化三种并存,源码里 src/adapter-declarative.cts 与 src/adapter-imperative.cts 两个文件名直接印证了前两种范式在源码层面就是分开建模的）
设计原因 三条并存的集成策略,让 GSD”就着每个宿主自己已有的扩展模型走”,而不是强迫所有 16+ 个宿主都支持同一套最小公分母机制——这也是第二部分 2.3 节”三种分发末梢”分析背后的架构原因

3.4 Skill Layer

本层此处只做架构定位（职责边界与生命周期骨架）,完整的字段级、加载器源码级、匹配算法级解析分别在本系列第四篇（第六～第十部分）展开,此处不重复。

维度 内容
职责 面向用户/模型的最小可触发能力单元——一个 Skill = 一个有边界的能力入口,自身不承载重逻辑
输入 用户的自然语言意图,或显式的斜杠命令
输出 一次被派生的 workflow 执行（Skill 本身只是”触发器”,不是”执行者”）
生命周期 发现（安装器/加载器扫描 skills/）→ 眼前列出（或被命名空间路由隐藏）→ 匹配/选中 → 调用 → 委托给对应 workflow → Skill 自身在委托完成的瞬间即结束生命周期
扩展点 新增 skills/<name>/SKILL.md；capability.json 的 skills 字段允许第三方能力贡献新 Skill；两阶段命名空间路由（本系列第一篇第一部分 1.7 节）是这一层为控制 token 成本而演化出的架构调整
设计原因 把”什么能被触发”（Skill,轻量、总是被列出）与”怎么被执行”（Workflow,重量、按需加载）严格分离,是让”眼前技能列表 token 成本”不随技能总数线性增长的关键设计——这也是为什么 v1.40 两阶段路由能够把 67 条压缩到 6 条而不损失任何可达性

3.5 Context Layer

维度 内容
职责 决定每一个被派生的 Agent 在那一刻究竟能看见什么信息
输入 项目状态的完整宇宙——STATE.md、CONTEXT.md、RESEARCH.md、PLAN.md、config.json、历史 SUMMARY.md 等一切潜在相关信息
输出 一份被精确圈定范围、交给某个具体 Agent 的上下文载荷（不是”全部塞进去”,而是”这个任务需要什么就给什么”）
生命周期 每一次 Agent 派生都重新构建一份全新载荷;从不以”会话历史”的形式被继承;信息只通过 .planning/ 文件系统在派生之间持久化,不通过对话记忆持久化
扩展点 gsd-core/contexts/（dev.md/research.md/review.md 三种操作模式引子）；1M 级模型的”自适应上下文增强”阈值（500K+ token 时才启用更丰富的载荷,见本系列第一篇第一部分 1.9 节引用的 ARCHITECTURE.md 描述）；examples/dynamic-context-management/ 提供的谓词化动态上下文加载范式
设计原因 这是对 Context Rot（本系列第一篇第一部分、第三篇第四部分核心议题）最直接的结构性回应——把”上下文”从一种随对话自然累积的副产品,重新定义为一种被主动工程化、按任务一次性构建、用后即弃的载荷

3.6 Execution Layer

维度 内容
职责 真正落笔改代码的一层——按依赖关系分波次、并行、原子化地把 PLAN.md 变成实际的代码变更
输入 一个 Phase 内全部 PLAN.md（已按依赖关系分组为若干”波次” Wave）
输出 代码变更本身 + 每个已完成任务对应的一次原子 Git 提交 + 每份 Plan 对应的一份 SUMMARY.md
生命周期 按波次派生——同一波次内的全部 Executor 并行运行,下一波次等待上一波次全部完成；每个 Executor 是一个全新上下文的 gsd-executor Agent,在完成自己那一份 PLAN.md 后终止
扩展点 自适应上下文增强（1M 级模型下 Executor 会额外收到前序波次的 SUMMARY.md + Phase 的 CONTEXT.md/RESEARCH.md,获得跨 Plan 感知能力）；并行提交安全机制（STATE.md.lock 文件锁 + O_EXCL 原子创建 + 10 秒陈旧锁检测 + 带抖动的自旋等待）
设计原因 波次化并行让多文件特性的完成耗时正比于”最长依赖链”,而不是”全部任务耗时之和”;任务级原子提交则让 Git 历史保持可审查、可二分定位（git bisect 友好）——这两点合起来是”纵深防御”设计原则（本系列第一篇第一部分 1.8 节）在执行层的具体落地

3.7 Planning Layer

维度 内容
职责 把一个 Phase 目标 + Discuss 阶段的决策,转化为一组具体、可验证、按依赖排序的 PLAN.md
输入 ROADMAP.md 里的 Phase 目标、CONTEXT.md 决策记录、RESEARCH.md 研究发现
输出 一份或多份（按依赖波次分组的）PLAN.md,每份都带显式验收标准
生命周期 Researcher → Planner → Plan-Checker 顺序链,每一环都是全新上下文的独立 Agent 派生；受限的修订循环（最多 3 轮,对应 gates.md 定义的 Revision Gate,详见 3.8 节）
扩展点 包合法性门禁（Package Legitimacy Gate）——RESEARCH.md 中提到的每一个第三方包都要过 slopcheck,产出 OK/SUS/SLOP 三态判定；需求覆盖门禁与决策覆盖门禁（后者依据 #2492 被明确标记为 阻断型 BLOCKING）；[BETA] 的 /gsd-ultraplan-phase 云端卸载路径（把研究+规划工作offload 给 Claude Code 的 ultraplan 云基础设施,详见第二部分 2.6 节 docs/superpowers/specs/ 的设计文档发现）
设计原因 把”消除歧义”这件事前置到一个专门的、可被机器检查的制品（PLAN.md）里,比等到执行阶段——多个并行 Executor 可能已经基于不同假设各自动手之后——才发现歧义要便宜得多

3.8 Verification Layer

维度 内容
职责 确认”造出来的东西”与”决定要造的东西””规划要造的东西”三者一致——而不只是”跑起来没报错”
输入 CONTEXT.md 决策、REQUIREMENTS.md、本 Phase 全部 PLAN.md + SUMMARY.md
输出 VERIFICATION.md（如发现偏差,附带针对性修复计划）；到 verify-work 步骤时进一步产出 UAT.md
生命周期 在本 Phase 全部波次的全部 Executor 完成之后才运行；单个 gsd-verifier Agent 顺序执行（不并行）
扩展点 本层是四种规范 Gate 类型（gsd-core/references/gates.md）体现最集中的一层，但这套分类法适用于全框架每一个验证检查点，值得单独展开（见下方”四种 Gate 类型”表）；这里的决策覆盖门禁被明确标记为非阻断 NON-BLOCKING——与 3.7 节 Planning Layer 里同名门禁的”阻断”形成一处值得记住的真实差异，二者检查的是同一件事（CONTEXT.md 的决策是否被覆盖）在循环两个不同位置的不同严格度
设计原因 把”跑起来了”和”符合目标”拆成两件独立被检查的事，专门针对 LLM 驱动开发最容易踩的一种失效模式——自信地造出一个内部逻辑自洽、但偏离真实目标的东西

四种规范 Gate 类型（源码：gsd-core/references/gates.md，本文首次在本系列第一篇第一部分之外被系统引用，因为它是理解 Verification Layer 乃至全框架”何时该拦、何时该问人、何时该整个中止”的统一词汇表）：

Gate 类型 作用 行为 恢复方式 典型样例
Pre-flight（预检） 操作开始前校验前置条件 条件不满足则拒绝进入,不产生任何半成品 补齐缺失的前置条件后重试 plan-phase 检查 REQUIREMENTS.md 是否存在;execute-phase 检查 PLAN.md 是否存在
Revision（修订） 评估产出质量,不足则打回重做 带具体反馈打回给产出者;受迭代次数上限约束 产出者依据反馈修正,校验者重新评估;若连续多轮问题数不降（stall detection）会提前升级;达到上限后无条件升级 Plan-checker 审查 PLAN.md（最多 3 轮）;Verifier 依据成功标准检查交付物
Escalation（升级） 把无法自动解决的问题交给开发者决策 暂停工作流,呈现选项,等待人工输入 开发者选择路径后工作流从该处恢复 修订循环耗尽 3 轮后;Worktree 清理时遇到合并冲突;需求本身有歧义
Abort（中止） 终止操作以避免损失或浪费 立即停止,保留状态,报告原因 开发者排查根因后从检查点重新开始 执行过程中上下文余量降到危险水平;STATE.md 处于错误态阻塞 /gsd:next;验证发现关键交付物缺失

Gate 矩阵样例（同样来自 gates.md，展示这套分类法在真实工作流里如何落地）：

工作流 阶段 Gate 类型 校验对象
plan-phase 入口 Pre-flight REQUIREMENTS.md、ROADMAP.md
plan-phase 第 12 步 Revision PLAN.md 质量（最多 3 轮）
execute-phase 完成时 Revision SUMMARY.md 完整性（重跑未完成任务）

3.9 Git Layer

维度 内容
职责 把 Phase/Plan/Task 的层级结构,翻译成一份”读起来像交付结果的变更日志,而不是规划活动的流水账”（git-integration.md 原文的核心原则）
输入 Execute 阶段的任务完成事件、Plan 完成事件、Ship 阶段的整个 Phase
输出 遵循 Conventional Commits 风格的原子提交（{type}({phase}-{plan}): {task-name},type 取 feat/fix/test/refactor/perf/chore 之一）;Ship 时进一步产出一个 PR
生命周期 每个任务完成 → 立即 1 次提交；每份 Plan 完成 → 1 次元数据提交（SUMMARY+STATE+ROADMAP）；Ship → 创建 PR + 归档 Phase 制品
扩展点 docs/CONFIGURATION.md “Git Branching” 一节提供的分支策略对比；Worktree 隔离执行（isolate-work-with-workspaces.md）；通过 workflow.worktree_skip_hooks 配置项可选地跳过 Hook
设计原因 见下方”一处需要专门指出的版本差异”

一处需要专门指出的版本差异（正是”若源码存在多个实现版本，应分析差异”这一原则的直接案例）：本系列第一篇（第一部分）1.8 节引用 docs/ARCHITECTURE.md 的”Parallel Commit Safety”一节时记录的说法是——并行 Executor 使用 --no-verify 跳过 pre-commit 钩子（原因是会导致构建锁争用，如 Rust 项目的 cargo lock 冲突），编排器在每个波次结束后统一跑一次钩子。但本部分为撰写 Git Layer 而直接阅读的、粒度更细的 gsd-core/references/git-integration.md 明确给出了不同的、更新的说法（并直接引用 #2924）：

并行 Agent：作为 execute-phase 派生的并行 Executor 运行时，正常执行提交，让 pre-commit 钩子照常运行。默认不要传 --no-verify（#2924）。钩子应当在引入变更的那次提交上触发；静默绕过违反了项目 CLAUDE.md 的指导原则。如果一个项目通过 workflow.worktree_skip_hooks=true 显式选择跳过，编排器会把这个标志体现在 Executor 的 Prompt 里；没有这个信号时，钩子照常运行。

两处文档字面上直接矛盾——本文的处理方式是：如实并列呈现两个版本，而不是隐去分歧或替读者选边。较合理的解释是 git-integration.md 反映的是更晚近的策略修正（#2924 这个 issue 编号本身就是证据链的一部分,建议读者在自己的checkout 里用 git log -p --follow -- gsd-core/references/git-integration.md docs/ARCHITECTURE.md 核实两份文档各自最后一次改动的时间顺序,本文未做这一步交叉核实,不代替读者下结论）。这也提示一个通用的源码阅读方法论：当高层次的 ARCHITECTURE.md 与细粒度的 references/ 文档在同一机制上给出不同细节时,优先信任细粒度文档,同时把差异本身记录下来——本系列第六篇（第十八部分）”源码阅读路线”会把这一条列为具体建议。

3.10 Configuration Layer

维度 内容
职责 承载一切可调行为——从 Git 分支策略、该 shell 出去调用哪个 Reviewer CLI,到某个能力整体的功能开关
输入 .planning/config.json（项目级）+ 能力自带的联邦化配置切片（federated-config.cjs 负责合并）+ 模型画像（Model Profile）选择
输出 一个被解析完毕、供上层每一层消费的单一配置视图
生命周期 每次 workflow 调用时由 config-loader.cjs 加载一次；在 Claude Code 上可通过 FileChanged Hook 实现会话中热重载（无需 /clear，见本系列第一篇第一部分 1.10 节引用）
扩展点 capability.json 自带的 config 字段让第三方能力把新的配置键联邦式地并入中心 Schema，而不需要中心 Schema 提前知道它们的存在——这正是 federated-config.cjs 存在的唯一理由；docs/CONFIGURATION.md 实测涵盖 Core Settings、Integration Settings（搜索 API Key、Code-Review CLI 路由、Reviewer 实例）、Workflow Toggles、Worktree Settings、Ship Settings、Hook Settings、Agent Skills Injection、Trusted Global Skill Roots、Capability Trust、Feature Flags（含 MemPalace 记忆模式、Graphify）、Parallelization Settings、Git Branching 等十余个板块
设计原因 “缺省即启用”（本系列第一篇第一部分设计原则之四）与联邦化配置合力产生的效果是：新能力上线时，默认体验永远不会退化，同时运维方仍能通过如 capabilities.strict_known_registries 这样的键把行为锁死——自由度与可治理性没有被做成互斥选项

3.11 Plugin Layer（Capability 体系）——本系列在架构层面着墨最重的一层

这一层承载”Skill Version / Skill Override / Skill Priority / Skill Registry”等一系列问题的真正答案——GSD Core 并没有把这些问题单独留给 Skill 层解决，而是把它们统一收拢进了一个独立的、更普适的 Capability（能力） 体系，Skill 只是 Capability 众多”贡献点”类型之一。这是本文认为最值得后续本系列第六篇第十六部分（自研下一代框架）直接借鉴的一层。

维度 内容
职责 让第三方在不依赖 GSD Core 自身发版流程的前提下，扩展 Skill/Agent/Command/Hook/Config 这每一层，同时确保第一方权威绝对不可被覆盖
输入 一份 capability.json 清单 + 其声明的完整能力包（skills/agents/commands/hooks/config）
输出 一个合成后的运行时能力注册表——一个通过全部校验的第三方能力，在每一个派生视图（bySkill/byAgent/byLoopPoint/configKeys/集群映射）里都与第一方能力无法被区分；或者，一次带完整原因说明的、响亮的”跳过”
生命周期 见下方”能力激活四阶段”图
扩展点 gsd capability install/update/remove/list/trust list/trust revoke 全套生命周期命令；capabilities.strict_known_registries 三态开关（未设=许可制+同意门禁 / 空数组=彻底锁死仅本地 / 非空数组=按 host 白名单）；Reviewer Lane 作为一种特殊披露类别（见下文）
设计原因 核心论点——“制品对等（artifact parity）不等于信任对等（trust parity）“：第三方能力被允许发布与第一方完全同等种类的可执行制品（Hook、MCP Server、命令模块、Reviewer Lane），但第一方的权威性来自”它就是 GSD Core 发版流程本身产出的”这一事实，第三方永远需要经过显式、知情、可撤销的同意 + SHA 完整性校验，才能激活任何可执行面

能力激活四阶段（loadRegistry 的实际行为，源码/文档：docs/explanation/capability-overlay-model.md）

flowchart LR
    INSTALL["① Install<br/>仅拷贝到安装根 + 写入 Ledger<br/>绝不 require() 任何能力代码"]
    LOAD["② Load / Compose<br/>loadRegistry()：项目级 Consent Gate<br/>+ 全维度碰撞消解（id/skill-agent-stem/config键/命令族）<br/>+ 全量交叉能力校验重跑"]

四条composition 规则,按重要性排列：

  1. 第一方永远赢（First-party always wins）——碰撞维度覆盖 id、Skill/Agent 词干、联邦配置键、命令族四个方面；外加 gsd-/gsd-core-/anthropic- 三个保留前缀被无条件拒绝。一个 Overlay 只能”新增”，永远不能”覆盖”——原因直指信任模型的中心论点：如果碰撞允许 Overlay 遮蔽第一方 Skill/Agent/命令，那么”安装”这个动作本身就变成了攻击面。
  2. 坏 Overlay 跳过，绝不崩溃——manifest 缺失/不可读/非常规文件（如被人为放置的 FIFO/设备文件）/超大/结构校验失败/碰撞/engines.gsd 版本不兼容/带有进行中的 _pending 标记/项目级但无 Consent 记录，都会被跳过并记入 _overlay.warnings，其余候选继续正常合成。
  3. Gate 类型必须”响亮地”失败开放——这是本文认为最精妙的一处设计：Step 与 Contribution 被跳过属于良性的”fail-open”（循环只是少了一个可选加项）；但 Gate 的存在意义就是”拦截”，如果一个声明 Gate 的能力被静默跳过、循环却假装 Gate 通过了继续往下走，等于放行了 Gate 本该拦截的东西却毫无信号。GSD 的选择（据维护者在 #2009 的明确决定）是：控制流上依然 fail-open（循环不因单个不兼容 Overlay 而项目级中止），但必须响亮——记录进 _overlay.incompatibleGateCapIds/blockedGates，同时通过 stderr 与 loop render-hooks JSON 信封的 warnings 数组两个通道发出警告，点名具体能力、失败原因、以及确切的补救命令 gsd capability remove <id>，直到操作者处理为止。
  4. 整体合成失败时，回退到纯第一方——当”全集”校验（跨 Overlay 才会出现的循环依赖等）失败时，GSD 丢弃全部 Overlay，只返回冻结的第一方注册表 + 一条警告；被丢弃 Overlay 的命令根路径会被清空（防止任何运行时分发器意外 require() 到已失效路径），且被丢弃 Overlay 声明的 Gate 依然会以同样机制响亮告警——“移除新增内容,但绝不让一个控制点悄悄消失”这一原则在这一层依然生效。

一个容易被忽视但极其关键的信任细节——Reviewer Lane 是唯一的”数据接收”类可执行面：capability-trust-model.md 特别指出，前述三类可执行面（Hook、MCP Server、命令模块）关心的都是”能力被允许执行什么代码”；而 Reviewer Lane（/gsd-review 交给的外部 CLI 或模型端点）是唯一一个反方向的数据通道——它被喂入完整的 Plan 文本、需求、研究发现、CONTEXT.md 决策，输出再被读回 REVIEWS.md。这是GSD 产出的最敏感制品的出口通道，因此披露规则专门做了区分：Spawned 型 Lane 披露其二进制及完整声明参数（因为仅披露二进制不够——一个声明为 python3 的 Lane 完全可以在后续把参数悄悄改成 ["-c", "<任意程序>"] 而二进制本身毫不改变）；HTTP 型 Lane 披露目标 Host（披露 curl 这个事实但毫无意义，真正重要的是它连到哪）；且 Consent 绑定的是解析后的实际 Host而非配置键本身，使得”事后把一个已同意的 Lane 重定向到别的地址”这种攻击手法变得可被检测而非静默发生。

诚实的局限性：GSD 不对第三方能力代码做沙箱隔离——文档原文直接承认这一点，而非暗示存在某种隐性防护。真正的三重屏障是 同意（Consent）+ 完整性（Integrity）+ 可逆性（Reversibility，gsd capability remove <id> 精确撤销 Ledger 记录的一切，不留孤儿状态）。这三者合起来意味着”你知道自己装了什么、你拿到的确实是你看过的那份、你可以完全撤销它”——但不意味着内容本身是安全的。文档甚至专门用 VS Code（2023 年发布者令牌被盗导致自动更新静默下发恶意版本）、npm（postinstall 脚本供应链攻击）、Obsidian（无沙箱但诚实声明 + 默认限制模式）、Claude Code（信任提示 + 市场白名单 + SHA 定版）四个真实生态的历史教训,逐一说明 GSD 从每一个身上具体借鉴了什么、又刻意没有照搬什么（例如明确拒绝了 Obsidian 式的”中心化人工审核每一个第三方插件”模式，理由是这会让维护者变成无穷尾部的瓶颈,复刻 Obsidian 自己都在承受的痛苦）。

3.12 本部分小结与下文预告

十一层拆解揭示的最重要的一条主线是：GSD Core 把”横向的五阶段循环”（Planning→Execution→Verification）与”纵向的基础设施”（Framework→Runtime→Core）用三种横切关注点（Context/Configuration/Git）粘合起来，再用两个对外开放的扩展入口（Skill 面向使用者、Plugin/Capability 面向第三方开发者）暴露可编程性——而不是把”可扩展性”作为事后补丁堆在某一层上面。Plugin Layer（Capability 体系）里”制品对等不等于信任对等””第一方永远赢””Gate 必须响亮地失败开放”这三条规则，是全系列二十部分里目前为止工程含金量最高的一段设计，会在本系列第四、六篇（第六、第十六部分）被反复引用。

本部分也留下了两处诚实的未决问题，供本系列第五篇（第十一部分）”源码阅读”时亲自验证：src/*.cts（约180个）与 gsd-core/bin/lib/*.cjs（17个）之间的确切编译映射关系；以及 ARCHITECTURE.md 与 git-integration.md 关于并行提交是否默认跳过 pre-commit 钩子的表述分歧，究竟哪一份文档的修改时间更晚。
