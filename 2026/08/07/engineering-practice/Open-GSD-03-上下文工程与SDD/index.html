第四部分 · Context Engineering（上下文工程深度解析）

上下文工程是整个系列的重点之一。本系列第一篇（第一部分）已从理念层面介绍过 Context Rot 与”新鲜子代理”解法；本部分不再重复理念，而是深入到机制层面——GSD Core 究竟用哪些具体的、可在源码中指认的手段，把”上下文工程”从一句口号变成一套可执行的纪律。

4.0 先结清一笔旧账：src/*.cts 与 bin/lib/*.cjs 的编译映射（本系列第二篇第二、三部分遗留的未决问题）

本系列第二篇（第二部分）2.2.2 节与本系列第二篇（第三部分）3.12 节都诚实地记录了一个未查清的问题：顶层 src/ 有约 180 个 .cts，而 gsd-core/bin/lib/ 只有 17 个 .cjs，数量对不上，当时我拒绝在未验证的情况下臆测其映射关系。本部分研究过程中因为需要追踪 prompt-budget.cts（token 估算模块）而顺带查清了这件事，现在给出结论性答案：

  1. tsconfig.build.json 的 include 是 ["src/**/*.cts"]，outDir 是 gsd-core/bin/lib ——也就是说，映射关系确实是全量 1:1 的，src/ 下每一个 .cts 都编译成 bin/lib/ 下的同名 .cjs。我此前的怀疑（”可能只编译一小部分”）是错的。
  2. 绝大多数编译产物被 .gitignore 显式忽略——实测 .gitignore 中针对 gsd-core/bin/lib/ 的忽略条目多达 166 条（逐个文件名列举，而非通配）。这就是为什么一次全新 git clone 只能看到 17 个 .cjs：其余的根本不在版本库里，它们在 npm run build:lib 时才被生成（package.json 的 prepare 与 prepack 钩子会自动触发）。
  3. tsconfig.build.json 顶部的注释一句话说明了这套设计的来龙去脉（ADR-457 “build-at-publish”）：“随着模块逐步迁移，它们会从手写的 bin/lib/*.cjs 搬进这里的 src/*.cts“ ——这是一场正在进行中的渐进式 TypeScript 迁移。
  4. 那么留在版本库里的 17 个 .cjs 是什么？实测分为三类：
    • 生成并提交型——capability-registry.cjs、loop-host-contract.cjs、package-identity.cjs 等，由 scripts/gen-*.cjs 生成后故意提交（package.json 的 version 钩子里能看到显式的 git add gsd-core/bin/lib/capability-registry.cjs），因为运行时需要一份”冻结的第一方注册表”（本系列第二篇第三部分 3.11 节 Plugin Layer 的核心前提）；
    • 尚未迁移的手写型——capability-command-router.cjs、capability-validator.cjs、legacy-cleanup.cjs、profile-pipeline-command-router.cjs、stale-bake-guard.cjs 等，还没轮到被搬进 src/；
    • 编译产物但故意提交型——api-coverage.cjs、assumption-delta.cjs、claude-orchestration.cjs、external-job.cjs、runtime-artifact-install-plan.cjs、state-transition.cjs 等既有 src/*.cts 源头、又被提交进库。这类文件的一致性由一个专门的 CI 校验脚本 scripts/lint-compiled-artifact-sync.cjs --check（串在 npm run lint:generated-sync 里）保障——又一次印证本系列第二篇（第二部分）2.4 节归纳的”声明 → 生成 → 校验漂移”三件套模式。

这个小插曲本身就是一条源码阅读方法论，值得记进本系列第六篇（第十八部分）：当仓库里”源文件数”与”产物数”对不上时，第一件该做的事不是猜测编译范围，而是去读 tsconfig/.gitignore/构建脚本这三件套——它们共同定义了”哪些东西是版本库里的真相，哪些是构建时才存在的真相”。

4.1 Context Rot 的机制性根因回顾（一句话版）

本系列第一篇（第一部分）已完整转述 docs/explanation/context-engineering.md 的论述，此处只保留最凝练的一句以承接下文：

模型不会”遗忘”（它从未以人类的方式”记住”过），它是在一个有限窗口上分配注意力权重；当窗口被累积的噪声填满，信噪比就下降——这不是模型 bug，而是 Transformer 注意力在长序列上的固有属性。

关键推论是：任何”提醒模型别忘了”的做法都是徒劳的，因为问题不在”记忆”而在”注意力预算”。唯一有效的干预是减少进入窗口的东西。GSD Core 的全部上下文工程机制，本质上都是这一条推论的不同施力点。

4.3 机制 1：新鲜子代理隔离 —— 以及一条”隔离不是免费的”的真实教训

新鲜子代理的原理本系列第一篇（第一部分）已述，此处补充一条在源码中被明确量化过的代价，它是本部分最有价值的发现之一。

gsd-core/references/checkpoints.md 记录了 #3309 引入的一次默认行为变更：workflow.human_verify_mode 的默认值从”mid-flight”（每遇到一个 checkpoint:human-verify 就当场停下等人）改为 end-of-phase（全程不中断，把所有需要人工确认的点收集起来，在 Phase 结束时一次性批量呈现）。变更理由原文如下（转述）：

每一次中途停顿都要付出一次 Executor 完全冷启动的代价（CLAUDE.md、MEMORY.md、STATE.md、重新读取 plan），因为子代理的上下文在暂停时会被丢弃。一个含 N 个 human-verify 检查点的 Plan，要付 N+1 次冷启动代价——在真实项目上实测为每次往返数万 token。

这段话极其重要，因为它揭示了新鲜上下文隔离的对称代价：

隔离带来的收益 隔离带来的代价
每个 Agent 在满血注意力下工作，不受历史噪声污染 每次派生都要重新加载全部必需上下文——没有任何跨派生的”记忆复用”
主编排会话的上下文增长缓慢可预测 一次中断 = 一次完整冷启动 = 数万 token
Agent 之间不会互相污染 任何需要跨 Agent 传递的信息必须先落盘，否则就丢了

设计启示（会在本系列第六篇第十六、十七部分复用）：在设计任何”子代理隔离”架构时，中断点的数量本身就是一项成本，而不是免费的安全措施。GSD 的应对不是取消检查点，而是把检查点批量化后移——从”N 次打断 + N+1 次冷启动”变成”0 次打断 + 1 次批量确认”。这与一些车辆日志诊断技能包里”非编排类技能尽量用 SubAgent 加载执行以保护主 Agent 上下文”的做法是同一族的权衡，但 GSD 的这条数据提醒：SubAgent 化的收益必须扣除冷启动成本后再评估，尤其当子代理需要反复往返时。

值得注意的是，这条变更只影响 checkpoint:human-verify（事后验证类）；checkpoint:decision 与 checkpoint:human-action（前者要人做决定、后者要人做机器做不了的操作，如提供 API Key）不受影响——因为这两类门的是”工作本身”，而不是”事后确认”，无法后移。这是一处很细腻的分类学处理。

4.4 机制 2：渐进式披露 —— 从”字节预算”到”@-导入陷阱”

本系列第二篇（第二部分）2.2.1 节已完整介绍 workflow 文件的三级字节预算（XL 90,000 / LARGE 54,000 / DEFAULT 38,000）及其”保护注意力而非账单”的理由。本部分补充执行层面最容易踩的一个坑，原文在 docs/ARCHITECTURE.md 中被明确警告（#720）：

因为预算衡量的是单个文件，它只是真实目标（受约束的已加载上下文）的一个代理指标。抽取只有在被抽取的内容是惰性加载（在需要它的那一步才 Read）时才真正有帮助。把散文挪进一个仍然被急切 @-导入的文件，只会缩小被测量的文件，而不会缩小已加载的上下文——那是在糊弄代理指标，而不是服务真实目标。

配套的具体反例（同样来自源码文档）：gsd-planner/gsd-executor 的 MVP 专用引用体（planner-mvp-mode.md、user-story-template.md、skeleton-template.md、execute-mvp-tdd.md）被刻意设计为由 Agent 在走到 MVP 路径时主动 Read，而不是写成 @-导入——因为**”@-导入即使被写在条件分支背后，仍然会被无条件急切加载”**。这是一个非常容易在自研框架里重犯的错误：以为”只在 if 分支里引用了这个文件”就等于”只在那个分支才付出 token 成本”，实际上如果引用机制是急切导入语义，成本在进入 if 之前就已经付掉了。

4.5 机制 3：读取深度纪律 —— 随上下文窗口大小自适应

gsd-core/references/context-budget.md 给出了一套所有派生子代理的工作流都必须遵守的通用规则，这是全框架最”硬”的上下文纪律：

五条通用规则（原文转述）：

  1. 永远不要读取 Agent 定义文件（agents/*.md）——subagent_type 会自动加载它们（重复读取纯属浪费）；
  2. 永远不要把大文件内联进子代理的 Prompt——告诉 Agent 自己去磁盘上读；
  3. 读取深度随上下文窗口大小伸缩——检查 .planning/config.json 里的 context_window 字段；
  4. 委派重活给子代理——编排器负责路由，不负责执行；
  5. 主动预警——如果已经消耗了可观的上下文（多次大文件读取、多个子代理结果），主动提醒用户考虑做检查点。

读取深度对照表（原文表格）：

上下文窗口 子代理输出读取 SUMMARY.md VERIFICATION.md 其他 Phase 的 PLAN.md
< 500k（200k 模型） 仅 frontmatter 仅 frontmatter 仅 frontmatter 仅当前 Phase
≥ 500k（1M 模型） 允许读完整正文 允许读完整正文 允许读完整正文 仍然仅当前 Phase

如何判断：读 .planning/config.json 检查 context_window；字段缺失时按 200k 处理（保守默认）。

这张表里藏着一个很聪明的设计：注意最右列——即便在 1M 模型下，”其他 Phase 的 PLAN.md”依然不允许读。也就是说，窗口变大只放宽”读多深”，不放宽”读多广”。原因不难理解：读得更深是在同一个任务上下文内提升精度；读得更广则是引入跨 Phase 的无关信息——那正是 Context Rot 的原材料。窗口扩大不是放弃纪律的理由，只是调整纪律参数的理由，这一条对任何准备”等 1M 上下文普及了就不用做上下文工程了”的团队都是一记提醒。

一个 GSD 明确声明”不归我管”、但影响可能更大的成本项：MCP 工具 Schema

context-budget.md 用了一整节讲一件 GSD 自己管不了的事，坦诚得少见（转述）：

每一个启用的 MCP Server 都会把它的工具 Schema 注入每一轮对话，无论你是否调用了它的任何工具。重量级 Server（浏览器/playwright、Mac-tools、Windows-tools）每个可能耗费 20k+ token/轮——这往往远远超过 GSD 自己通过 model_profile 调优所能节省的量。这是 Claude Code 宿主层面的事，不是 GSD 的事：开关在 .claude/settings.json 的 enabledMcpjsonServers / disabledMcpjsonServers 里。

原文进一步算了一笔账：如果一个项目有 5 个用不上的 MCP Server，各自平均 5k token 的 Schema，那么每一轮对话在助手读到第一个项目文件之前，就已经先交了 25k token 的”过路费”。而且这个成本有乘数效应——它与你选哪个 model_profile 无关，且会在编排器派生的每一个子代理上叠加。文档给出的”Phase 前 MCP 审计清单”（本 Phase 无 UI 工作就关掉浏览器工具、关掉跨项目遗留的 MCP、合并重复 Server 等）是本系列中对日常实操最立竿见影的一段建议——它甚至不需要你采用 GSD 就能受益。

4.6 机制 4：上下文余量监控 —— 一条完整的、可复制的观测链路

这是 GSD 上下文工程里工程实现最完整、也最容易被其他项目照搬的一条链路。源码：docs/context-monitor.md + hooks/gsd-statusline.js + hooks/gsd-context-monitor.js。

它要解决的问题（原文）：状态栏（statusline）把上下文使用量展示给了用户，但代理本身对上下文限制毫无感知。当上下文见底时，代理会一路工作到撞墙为止——可能正卡在任务中途，且没有保存任何状态。

完整链路：

    participant BR as 桥接文件<br/>/tmp/claude-ctx-{session_id}.json
    participant CM as Context Monitor<br/>(gsd-context-monitor.js)
    participant AG as Agent（对话上下文）

    Note over SL: 宿主在 statusLine 事件调用
    SL->>BR: 写入 {session_id, remaining_percentage, used_pct, timestamp}
    Note over CM: 宿主在 PostToolUse（Claude Code）/<br/>AfterTool（Antigravity CLI）事件调用
    CM->>BR: 每次工具调用后读取
    alt 剩余 > 35%（Normal）
        CM-->>AG: 不注入任何内容
    else 剩余 ≤ 35%（WARNING）
        CM-->>AG: 注入 additionalContext：<br/>"收尾当前任务，不要开始新的复杂工作"
    else 剩余 ≤ 25%（CRITICAL）
        CM-->>AG: 注入 additionalContext：<br/>"立即停止，保存状态（/gsd-pause-work）"
    end
    Note over CM,AG: 防刷屏（Debounce）：首次警告立即触发；<br/>后续警告需间隔 5 次工具调用；<br/>严重度升级（WARNING→CRITICAL）无视防抖

四条安全性设计（原文，值得逐条借鉴）：

  1. Hook 把一切包在 try/catch 里，出错时静默退出；
  2. 永不阻塞工具执行——一个坏掉的监控器不应该弄坏代理的工作流；
  3. 陈旧指标（超过 60 秒）直接忽略；
  4. 桥接文件缺失时优雅降级（子代理、全新会话等场景下文件本就不存在）。

这条链路的精妙之处在于它解决了一个看似无解的问题：LLM 无法感知自己的 token 用量（没有可编程的上下文百分比 API）。GSD 的做法是——绕过模型自省，从宿主侧测量，再通过 additionalContext 把测量结果”喂回”给模型当作普通对话内容。这是一个可以直接搬进任何自研 Agent 平台的模式：用确定性程序观测、用 Prompt 通道回传。

4.7 机制 5：Token 预算估算与项目级校准 —— 拒绝模型自评

context-budget.md 的后半段（”Phase Sizing”）与根 CONTEXT.md 里的 “Phase Estimation Module” 条目共同描述了一套相当严谨的估算体系（#2631、ADR-2629），其中有一条设计原则值得单独拎出来：

confidence 是被推导出来的，不是被判断出来的——它来自同一次校准查询的 confidence 值，按样本数量分档（low < 3、med 3–5、high ≥ 6）。不要给自己的确定性打分。 自评置信度在本项目中被实测过，结论是它很弱（见 references/honest-verifier.md:25-29）；这里的每一个信号都改为路由到实测历史上。

这是整个 GSD 源码里最”反直觉但正确”的一条设计。展开成三步算法：

  1. 按 estimateTokens 尺度累加计划成本（实现 + 每个任务要读的文件 + 验证输出，大致按”字符数/4”估算 Executor 真正会碰到的量）；
  2. 运行 estimate-calibration，把原始估算值乘以它返回的 factor——那是这个项目实测的”估算 vs 实际”比值（factor 为 1 意味着历史样本还不够，尚无法校正）；
  3. confidence 直接取校准查询的返回值，不允许模型自评。

配套的两条不变量（来自根 CONTEXT.md 的模块描述）：（1）每个信号都是外生的——修正基于实测的 actual/estimate 比值，confidence 基于校准样本数，永不基于模型的自我评估；（2）超预算标记是建议性的——只给警告和拆分建议，永不阻断。校准算法是”比值的中位数”，钳制在 [0.5, 3.0] 区间，样本数低于 3 时完全不生效。

还有一个精彩的类型设计细节：源码用编译期品牌类型（brand）把 RawTokens（规划器未修正的原始投影，也是唯一合法的校准分母）与 CalibratedTokens（已应用项目 factor、也是唯一对预算有意义的数字）区分开。根 CONTEXT.md 直接记录了引入品牌类型的原因——这两者混用在运行时根本抓不住：它们都是同一数量级的正整数，而这个混用错误在一个约 26,800 个测试全绿的测试套件下溜过去了两次（#2631 的”factor 平方”事故与 #2632 的”自我抵消循环”事故）。

这是全系列最值得记住的工程教训之一：当两个语义不同的值恰好类型相同、量级相同时，测试覆盖率再高也拦不住混用——只有类型系统能拦住。这条对设备诊断平台里的各种”时间戳”（车端时间 vs 云端接收时间 vs 日志内嵌时间）同样适用。

相关配置项：workflow.smart_zone_tokens（默认 100000）——文档明确称之为”策略默认值而非基准常数，因为有效上限依模型与任务而异”，定义是”模型上下文窗口中在输出质量退化之前真正可用的那段前缀“。此外规划层还有一条硬性建议：每份 Plan 最多 2–3 个任务，且计划应当在 ~50% 上下文（而非 80%）内完成，理由是”没有上下文焦虑、质量从头到尾一致、给意外复杂度留余地”。

4.8 机制 6：四级降级分级与上下文守卫

context-budget.md 定义了一套贯穿全框架的上下文降级词汇表：

分级 使用率 行为 execute-phase 的触发动作
PEAK 0–30% 全功能运行：读正文、派生多个 Agent、内联结果 无
GOOD 30–50% 正常运行：优先只读 frontmatter，积极委派 无
DEGRADING 50–70% 节约模式：仅 frontmatter、最小化内联、提醒用户预算情况 发出警告，继续
POOR 70%+ 紧急模式：立即做检查点，除非关键否则不再新增读取 warn：警告 + 建议 /gsd:pause-work；auto：在下一波次前直接调用 pause-work；off：照常继续

由 workflow.context_guard_mode 配置项（取值 auto/warn/off，默认 warn）控制 execute-phase 在波次边界上的响应策略（gsd-core/references/execute-phase-context-guard.md，#1452）。

这里有一个必须如实指出的诚实声明（原文）：

这个守卫是启发式的——不存在可编程的上下文百分比 API。请使用你对降级信号的判断，而不是一个固定的 token 数字。

也就是说，这一层与 4.6 节的监控 Hook 不同：Hook 那条链路有宿主侧的真实测量数据；而 execute-phase 内部的这个守卫，实际上是在要求模型自我评估。前面 4.7 节刚说过”自评置信度被实测为很弱”，这里却不得不依赖自评——这是一处架构上的无奈，而非疏忽。文档给出的补救办法是提供三条可观察的降级征兆，让自评有据可依，而不是凭空打分：

  • 静默的部分完成——Agent 声称任务已完成，但实现其实不完整。自检只能查文件是否存在，查不出语义上是否完整。永远要验证 Agent 的输出满足了计划的 must_haves，而不只是文件存在。
  • 越来越含糊——Agent 开始说”适当的处理””标准的模式”这类词，而不是给出具体代码。这个信号会在预算警告触发之前就出现。
  • 跳步——Agent 省略了它平时会遵守的协议步骤。如果一个 Agent 的成功标准有 8 项而它只报告了 5 项，就该怀疑上下文压力。

文档还坦承了一条根本性限制：编排器无法验证 Agent 输出的语义正确性，只能验证结构完整性。缓解手段是 must_haves.truths 与抽样式的点检验证。

4.9 机制 7：检查点、/clear 与续接 —— Context Restore 的真实形态

常说的 “Context Restore”，在 GSD 里的实现形态可能与直觉不同：它不是”把上下文恢复回来”，而是”确保上下文可以被安全地丢弃”。

gsd-core/references/continuation-format.md 定义了每个命令/工作流完成后必须呈现的标准续接格式，其核心结构是：

七条格式规则里，有三条直指上下文工程：

  • 规则 4：先 /clear ——“永远把 /clear 显示在命令之前，好让用户按正确顺序执行”。也就是说，主动清空上下文被设计成了工作流的标准动作，而不是异常处理；
  • 规则 2：从源头拉取上下文——Phase 信息从 ROADMAP.md 拿，Plan 信息从 PLAN.md 的 <objective> 拿，而不是从对话历史里回忆；
  • 规则 7：标题里带项目身份——把 [PROJECT_CODE] PROJECT_TITLE 放进标题，好让交接在跨会话时能自我标识。

这三条合起来构成了 GSD 对 “Context Restore” 的真正回答：

stateDiagram-v2
    [*] --> 工作中
    工作中 --> 磁盘状态已完备: 每个有意义的步骤都写回 .planning/
    磁盘状态已完备 --> 呈现续接卡片: 从 ROADMAP/PLAN 源头拉取而非对话回忆

    从磁盘重建 --> 工作中: 上下文重置为接近零，工作进度零丢失

这与传统”会话恢复”的本质区别：传统做法试图保存并还原对话历史（于是历史噪声也被一并还原了）；GSD 的做法是保证任何时刻的进度都已经完整落盘，因此对话历史本身随时可以被安全丢弃——恢复的是状态，不是对话。这也解释了为什么 STATE.md 被称为”这套系统的脊柱”：它不是”备份”，它是唯一的真相来源，对话反而是那个可丢弃的副本。

配套的检查点体系（gsd-core/references/checkpoints.md）定义了三类检查点与两级门禁，其中 gate="blocking-human" 的设计尤其值得记录：

gate 取值 自动模式下的行为 用于
gate="blocking" 被自动模式绕过（human-verify 自动批准、decision 自动选第一项） 默认值。事后验证与”走推荐路径也安全”的实现选择
gate="blocking-human" 永不绕过。即使在自动模式下也停下来等人 不可逆或需要建立信任的步骤：安装前的包合法性验证，以及任何”默认答案本身就是错的”的决策

原文对这个双层设计给出的解释相当到位：这道门横跨两层，两层都必须遵守它——gsd-executor 拒绝自动批准 blocking-human 检查点并向上升级，execute-phase 的 checkpoint_handling 步骤再决定用户实际看到什么。如果编排器只按检查点类型分发（而不看 gate 属性），它就会自动批准掉执行器刚刚拒绝自动批准的那个检查点，在上一层把下一层的拒绝作废掉，最终让一次无人值守的 --auto/--chain 运行安装一个从没有人审核过的包。

这是一条极具普适性的安全设计教训：当一道安全门需要跨多层生效时，每一层都必须独立地认识这道门——只要有任何一层是”按类型分发”而不是”按门禁属性分发”，整条链路的防护就会在那一层被静默作废。

4.10 前沿方向：动态上下文管理（ADR-1671，尚未进入生产）

仓库里 examples/dynamic-context-management/ 是一份明确标注为”非发布参考示例”的代码（原文强调：它在构建之外、npm 包 files[] 之外、安装器之外、CI 测试套件之外——没有任何东西会被编译进或安装进 GSD），对应 ADR-1671 与 Epic #1671。但它揭示的方向对本系列第六篇第十六部分（自研下一代 Skill Runtime）极有参考价值，因此在此记录。

它演示的是 “谓词事实库 → JIT 选择器” 这一片段：把仓库根部 CONTEXT.md 里的 CLASS.subkey=value 谓词解析成结构化记录，用漂移守卫保护一份生成的索引，然后为某个具体任务选出相关的谓词子集——这是”即时组装 Agent 简报”的构件，用来替代”手工引用一个 200KB 的大文件”这种做法。

实际的 CONTEXT.md 头部对这套格式有明确声明（转述）：

格式：本文档是机器可 grep 的。每一条运行事实都是一行谓词（CLASS.subkey=value）。Agent 简报逐字按 ID 引用谓词（依据 META.RULE.brief-must-cite-doc）——绝不从本文件转述。新的经验以谓词形式加入；编年体的散文属于文档底部的会话日志。

实测的 CONTEXT-INDEX.json 显示这份索引包含 416 条谓词、20 个类别，分布为：DEFECT 167 条（缺陷经验最多，符合直觉）、PRED 68、RULESET 56、RELEASE-NOTES 31、PROC 14、WORKTREE 12、PROBE 11、PROHIB 10、SESSION 9、EXEC 8 等。

为什么这个方向重要：它把”上下文”从”一份要么全读要么不读的文档”，升级成了”一个可查询的事实库“——Agent 简报不再是”把 CONTEXT.md 塞进去”，而是”按任务选出这 20 条相关谓词塞进去”。这与车辆日志诊断技能包里常见的”证据工具 + 五级预算感知压缩 + 稀有模板全保留”是同一个思路的两种实现：都拒绝”全量 vs 全无”的二元选择，改为让检索粒度可编程。

顺带一提，示例 README 里还记录了一个有意思的副产品：这套解析在验证过程中顺手发现了 CONTEXT.md 里 3 条潜伏的重复谓词 ID（RULESET.WORKFLOW_MARKDOWN.FENCES、RULESET.GEMINI.TOOLS.ask_user、RULESET.GEMINI.TEST_SENTINEL），并记录在索引的 duplicates 字段里——把知识库结构化的第一个收益，往往是发现它原本就不一致。

4.13 优缺点与 Token 节约原理总结

维度 评价
Token 节约原理 并非”压缩”，而是结构性地不让内容进入窗口：①主会话不读源码文件；②子代理只收到任务必需项；③引用文档惰性 Read 而非急切导入；④跨步骤信息走磁盘而非对话；⑤读取深度按窗口大小自适应
与 Claude Context Window 的关系 GSD 不做任何压缩或摘要式的 token 操作——它没有实现自己的 compaction。它做的是”避免触发宿主的自动压缩“：PreCompact Hook 的存在正是因为宿主自动压缩会静默丢弃编排器依赖的规划状态。换句话说，GSD 对 Context Window 的策略是规避而非管理
优点 结构性而非补丁式；状态可被人类与 Git 检视；跨会话零丢失；纪律以可执行的字节预算/Lint/CI 形式固化，而非靠自觉
缺点（源码文档自陈） ①开销真实存在——三步分开跑比直接说”写个功能”慢；②延迟——多次派生带来往返成本；③小任务上是过度仪式（因此提供 /gsd-quick、/gsd-fast 轻量原语）；④冷启动代价可观（数万 token/次往返）；⑤execute-phase 内的上下文守卫依赖模型自评，而自评已被本项目实测为不可靠——这是一处架构性无奈
最值得借鉴的三条 ①用确定性程序观测、用 Prompt 通道回传（4.6 节的监控链路）；②拒绝模型自评，路由到实测历史（4.7 节的校准体系）；③安全门必须每一层独立识别（4.9 节 blocking-human 的双层教训）

4.14 本部分小结与下文预告

第四部分把”上下文工程”从理念落到了七种可指认的机制上，并顺带结清了本系列第二篇遗留的编译映射问题。三条最值得带走的结论：

  1. 上下文隔离不是免费的——#3309 用”每次往返数万 token”的实测数据说明：中断点的数量本身就是成本，SubAgent 化的收益必须扣除冷启动成本后再评估；
  2. 窗口变大只放宽”读多深”，不放宽”读多广”——1M 模型下依然禁止读其他 Phase 的 PLAN.md，因为跨 Phase 信息正是 Context Rot 的原材料；
  3. Context Restore 的真实形态是”确保上下文可被安全丢弃”，而不是”把上下文恢复回来”——恢复的是磁盘状态，不是对话历史。

下一部分（第五部分 · Spec Driven Development）将逐阶段展开 Discuss → Plan → Execute → Verify → Ship 五个阶段的输入/输出/Prompt/状态/Artifacts/依赖/典型 Skill，为每个阶段配 Mermaid 流程图与 Sequence Diagram，并解释”为什么恰好是这五个阶段”。

第五部分 · Spec Driven Development（五阶段循环全解）

5.0 为什么恰好是这五个阶段

docs/explanation/the-phase-loop.md 给出的核心论证已在本系列第一篇（第一部分）1.9 节引用，此处提炼成一句可检验的判据：

每一步之所以存在，是因为它防御了一类”上一步单独无法防御”的失败模式。

把这句话展开成一张对照表，就能理解为什么少一步不行、多一步冗余：

阶段 防御的失败模式 如果删掉这一步会发生什么
Discuss 规划者被迫替你猜实现决策——有时猜对，更多时候猜得”合理但错误” 产出一份内部自洽、却与你真实偏好错位的计划；等执行完才发现，返工成本已经产生
UI Design（可选） 设计歧义导致多个执行者做出发散的实现选择 视觉/交互层出现互相冲突的实现，重做成本远高于先写一份设计契约
Plan 执行者面对模糊指令时各自做假设 多个并行执行者对同一关注点做出不同假设 → 冲突
Execute （这一步本身是产出，不防御，但它的新鲜上下文防御 Context Rot） 执行者带着 180k token 的会话历史工作 = 一个已退化的执行者
Verify “执行没报错”被误当成”目标已达成” 交付一个能跑但偏离需求的东西——LLM 驱动开发最典型的失效模式
Ship 工作完成但状态未归档，下一轮从脏状态起步 状态漂移累积，STATE.md 与真实进度脱节

判断”歧义在哪一步最贵”是这套设计的关键洞察——原文的原话是：Plan 步骤是歧义代价最高的时刻。因为一份含糊的计划会产出一个做假设的执行者，而多个并行执行者对同一关注点做出不同假设就会产生冲突。Plan-Checker 的职责正是在执行开始之前、而不是之后抓住这些问题。

断点续跑：三种恢复语义

这是 Execute 阶段设计最扎实的部分。如果执行中途停止（配额耗尽、网络中断、会话崩溃），波次级进度是被保留的——GSD 通过检查每份计划是否有 SUMMARY.md 来判断，有的直接跳过，从第一个未完成的计划继续。

但真正精彩的是那个边界情况：提交存在但 SUMMARY.md 缺失（执行者提交了代码，但还没来得及写摘要就死了）。这时 GSD 会浮出一道”安全续跑门禁”，给三个选项：

选项 语义
close out manually 你去检查那些提交，手工补写 SUMMARY.md，然后重跑
re-execute from scratch 先回退或作废那些部分提交，再派发一个新的执行者
mark-and-skip 记录这处异常并继续——仅在显式确认后才允许

这三个选项的设计哲学值得学习：它没有替用户猜“那些提交到底算不算数”，因为这个判断需要人看代码；它把三种可能的真实情况都摆出来，并对最危险的那个（跳过）加了显式确认门槛。

跨 AI 执行

--cross-ai 可以把执行委派给配置在 workflow.cross_ai_command 里的外部 AI CLI（Codex、Gemini 等）；--no-cross-ai 则在配置已开启跨 AI 时强制本地执行。这是”Runtime Layer 中立性”（本系列第二篇第三部分 3.3 节）在执行阶段的体现——GSD 不但能被不同宿主承载，还能在一次执行里调度另一个 AI CLI 当劳动力。

UAT 的三个精巧细节

  1. 严重度由描述推断，不要用户分类——原文：yes/y/空 → 通过；其他任何内容 → 记为问题，严重度从你的描述里推断（”crashes” → blocker，”doesn’t work” → major，”looks off” → cosmetic）。用户永远不需要自己给问题定级。这是一个降低认知负担的好设计。
  2. 进度可跨 /clear 存活——进度写入 {phase}-UAT.md；会话被打断后重跑 /gsd-verify-work 1，GSD 会提供”从上一个检查点继续”。这正是第四部分 4.9 节”Context Restore 的真实形态”的又一实例。
  3. 发现问题后的四步自动闭环：
flowchart LR
    A["UAT 报告问题"] --> B["① 并行派生 debug 代理<br/>每个问题一个<br/>把根因写回 UAT.md"]
    B --> C["② 派生 gsd-planner<br/>（gap-closure 模式）<br/>读带诊断的 UAT.md<br/>写出新的 PLAN.md"]
    C --> D["③ 派生 gsd-plan-checker<br/>确保修复计划可执行<br/>planner↔checker 最多迭代 3 轮"]
    D --> E["④ 呈现下一步：<br/>/clear then<br/>/gsd-execute-phase 1 --gaps-only"]
    E --> F["跑完后重跑 /gsd-verify-work 1 确认"]
    F -.仍有问题.-> A

注意 --gaps-only 这个标志：它让 Execute 阶段只跑缺口修复计划，而不是重跑整个 Phase。整个闭环没有引入任何新概念——它复用了已有的 planner、plan-checker、executor 三个 Agent 和同一套修订循环，只是换了输入源（UAT.md 而非 CONTEXT.md）。用同一套原语解决新问题，而不是为新问题发明新机制，这是 GSD 架构上一以贯之的克制。

这正是 Spec-Driven Development 的复利效应：前面每一步为了让机器能处理而写下的结构化制品，到最后一步自动变成了给人看的交付说明。如果前面是靠对话推进的，这一步就只能靠人回忆着手写。

一个体贴的工程细节：/gsd-pr-branch

如果你的分支里混着 .planning/ 的提交，而团队的评审规范不希望评审者看到这些规划噪声，/gsd-pr-branch 会创建一个只含代码变更的新分支，把规划制品的提交排除掉。这解决了一个 GSD 这类”把规划过程也提交进 Git”的框架必然会遇到的现实摩擦。

5.8 STATE.md：贯穿五阶段的状态机

docs/reference/state-md.md 定义的状态机是理解整个循环”当前在哪”的关键。这份文件被刻意保持在 100 行以内——原文的定位很清楚：它是项目状态的摘要（digest），不是归档（archive）。

状态归一化表（normalizeStateStatus()，源码 gsd-core/bin/lib/state-document.cjs）

规范值 匹配的正文文本（大小写不敏感）
discussing 含 discussing
planning 含 planning 或 ready to plan
executing 含 executing、in progress 或 ready to execute
verifying 含 verif
completed 含 complete 或 done
paused 含 paused 或 stopped，或存在 paused_at 字段
unknown 以上都不匹配

为什么要做这种”模糊匹配归一化”：因为 STATE.md 的正文是给人写的，人（和 LLM）会写出各种措辞变体。GSD 的做法不是强制人写标准枚举值，而是在读取侧做归一化——这是一个务实的容错设计，代价是必须维护这张映射表。

命令在执行期间写入的状态（#2833 约定）

命令 执行期间的 status
/gsd-discuss-phase discussing
/gsd-plan-phase planning
/gsd-execute-phase executing
/gsd-verify-work verifying

阶段/里程碑边界上的严格生命周期（ADR-2207）

值 写入者 含义
Ready to plan completePhaseCore（非最后一个 Phase） 下一个 Phase 可以开始规划了
All phases complete completePhaseCore（最后一个 Phase） 全部 Phase 完成；里程碑等待正式关闭
<version> milestone complete milestoneCompleteCore 里程碑已正式关闭并归档
Awaiting next milestone milestoneCompleteCore 终态/已归档

原文特别记录了一次纠错：Phase 级的完成动作永不写入 Milestone complete——那个含义过载的裸值在 #2204 中依 ADR-2207 被移除，目的是把 Phase 级的写入与 Milestone 终结解耦。这是一个典型的”枚举值语义过载”重构案例：同一个值被两个不同层级的动作写入，导致无法区分”这个 Phase 是最后一个”和”整个里程碑已经正式收尾”。

5.10 循环之外的轻量原语

原文反复强调”五阶段循环是一个工具，不是唯一的工具”。GSD 提供了一整套逃生阀，用于低于循环门槛的工作：

原语 定位 与循环的关系
/gsd-fast 琐碎任务内联执行——无子代理、无规划开销 完全绕过循环
/gsd-quick 保留 GSD 保证（原子提交、STATE 追踪）但跳过可选 Agent；任务活在 .planning/quick/ 而非 phases 目录，只更新 STATE.md 的”Quick Tasks Completed”表而不动 ROADMAP.md 循环的短路径版；--discuss/--research/--validate 可按需组合，--full 等于全开
/gsd-spike 快速用一次性实验试探想法；--wrap-up 可把发现打包成一个持久 Skill 循环之前的探索
/gsd-sketch 用一次性 HTML 稿快速草绘 UI/设计想法 循环之前的探索
/gsd-autonomous 无人值守跑完所有剩余 Phase 循环的自动串联

the-phase-loop.md 给出的判断标准非常实用：如果这个任务能用一句短提示词完整说清，并且一个 Agent 一轮就能做完、不需要进一步澄清——那就跳过循环。如果它需要研究、涉及你最近没读过的文件、或依赖尚未敲定的决策——那循环在保护你。

5.11 本部分小结与下文预告

第五部分逐阶段拆解了五阶段循环的输入/输出/Prompt/状态/制品/依赖/典型 Skill。四条最值得带走的结论：

  1. 每一步的存在理由都是”防御上一步无法防御的失效模式”——这个判据可以直接用来审视任何自研流程里的某个环节是否冗余；
  2. Plan 阶段是歧义代价最高的时刻——因为含糊的计划会让多个并行执行者各自做出不同的假设，冲突由此而生；
  3. 规范驱动的复利在 Ship 阶段兑现——前面为机器可读而写的结构化制品，最后自动装配成了给人看的 PR 正文；
  4. 用同一套原语解决新问题——UAT 失败后的 gap-closure 闭环没有发明任何新机制，只是把 planner/plan-checker/executor 换了输入源再跑一遍。

本部分也新增了一处文档滞后记录：plan-checker 的”八个维度”实际已增长到 16 个左右；同时记录了一次”grep 假阳性”的核查过程作为方法论示例。
