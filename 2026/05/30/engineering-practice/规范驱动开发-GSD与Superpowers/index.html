面向「Claude Code 与 Cursor 协同开发 · 中大型软件工程项目」的技术选型与落地指南

文档版本：v1.1 ｜ 编制日期：2026-05-29 ｜ 信息核验基准：2026-05-29 前的公开资料；2026-09-29 按一手来源（GitHub 仓库与 Release、npm、Wayback 快照）复核数据，之后的变化见文末补记

0. TL;DR：一页结论

  • 推荐方案：以 GSD（社区延续版 GSD Redux）作为「跨工具规格与状态主干」，在执行阶段叠加 Superpowers 作为「执行质量层」。
  • 核心理由：目标场景有两个硬约束——① Claude Code 与 Cursor 需要协同；② 项目是中大型。两个框架其实都能装进这两个工具（GSD 原生支持 Cursor 运行时；Superpowers 自 v4.3.1 起通过 Cursor 插件市场分发），真正的分水岭是项目级状态：GSD 把项目、需求、路线图、阶段与执行进度全部落盘在 .planning/，任何一侧打开仓库都能接着干；Superpowers 只产出任务级的设计文档与实现计划，不维护里程碑与阶段状态。
  • 安装级别：GSD 工具本体用户级（global）安装，项目状态 .planning/ 始终随仓库提交；Superpowers 以插件形式按工具分别安装，天然是用户级。
  • 必读风险：原仓库 gsd-build/get-shit-done 已停止维护。据分叉维护者 2026-05-22 发布的延续公告，原维护者 TÂCHES 自 2026-04-01 起无法联系，与项目关联的 $GSD Solana 代币被公开指为 rug-pull。只使用社区延续分叉 open-gsd/get-shit-done-redux（npm：@opengsd/get-shit-done-redux），并把引入过程当作一次供应链审查（详见 §8）。

追求极简：只用 Superpowers，两侧各装一份，靠提交到仓库的 spec / plan 文档交接。
追求单一工具栈贯穿两个 IDE：只用 GSD。
追求最高工程严谨度 + 双工具协同（推荐）：GSD 主干 + Superpowers 执行质量层。

1. 背景与需求理解

选型结论高度依赖以下几个约束：

约束维度 目标场景 对选型的影响
工具栈 Claude Code + Cursor 协同开发 决定性约束：两个工具能否共享同一份项目状态
项目规模 中大型、多模块 需要持久化状态、阶段化推进、抗上下文腐烂
使用者 单人或小团队 两个框架的设计初衷都对口（solo / small team）
诉求 高效、可复用、决策可追溯 偏向标准化工作流 + 落盘可复用资产

关键判断：中大型项目最致命的问题是 context rot（上下文腐烂）——随着对话堆积，模型逐渐丢失早期决策、自我重复、偏离原始意图。规格驱动开发（Spec-Driven Development，SDD）正是为此而生：把「设计决策」写成磁盘上的文件（spec → plan → code），并在每一对环节之间插入人工评审关口。GSD 和 Superpowers 都在这条路线上，只是切入的「层」不同。

2. 什么是规格驱动开发

两个框架共享同一套底层方法论。SDD 的核心是三份按顺序产生的文档 + 三道评审关口：

  1. Spec（规格）：用自然语言写清「这次改动要做什么、不做什么」——支持的格式、交付方式、半成品时的行为、明确排除项。评审关口 1：在它变成计划前评审，拦截范围蔓延和「错误根因」式的方案。
  2. Plan（计划）：把规格拆成带编号的原子任务，每个任务点名文件、改动、顺序、测试。评审关口 2：在它变成代码前评审，拦截半成品实现和与代码库不一致的模式。
  3. Code（代码）：按计划一次一个任务地写出来。评审关口 3：合并前评审，拦截「读起来没问题、一遇到失败测试就崩」的实现。

它和 Claude Code 内置 Plan Mode 的区别：Plan Mode 面向单次会话，计划在一轮对话内生成并执行，不进入仓库、没有跨阶段的评审关口；SDD 把 spec 和 plan 作为仓库里的文件持久化，每一阶段过人工评审，产物跨会话、跨工具存活。这正是中大型项目能否跑得动的分水岭。

经验法则：当一次改动触及约 4 个以上文件，或「它到底该怎么表现」本身就是难点时，就该上 SDD。

3. 两大框架概览

3.1 GSD（Get Shit Done）

  • 定位：轻量但强大的「元提示（meta-prompting）+ 上下文工程 + 规格驱动开发」系统。

  • 维护现状（重要）：原作者 TÂCHES（GitHub 账号 glittercowboy）。原仓库 gsd-build/get-shit-done 约 6.37 万 star（2026-05-25 快照），2026-05-22 起不再是活跃开发地；活跃开发迁至社区治理的 open-gsd/get-shit-done-redux（项目名 GSD Redux，约 1.4k star，2026-05-28 快照）。npm 包 @opengsd/get-shit-done-redux，编制日最新版本为 1.1.0（详见 §8）。

  • 工作流（主循环：discuss → plan → execute → verify → ship）：

    阶段 命令（连字符形式，Claude Code / Cursor 通用） 作用
    初始化 /gsd-map-codebase、/gsd-new-project 索引现有代码库、深度上下文采集、构建 .planning/ 结构与路线图
    讨论 /gsd-discuss-phase N 暴露「灰色地带」决策并锁定，写入阶段 CONTEXT.md（澄清怎么实现，不扩范围）
    UI 契约 /gsd-ui-phase N 前端阶段先锁定设计契约（间距、字体、配色、文案）
    计划 /gsd-plan-phase N 研究 + 生成 PLAN.md + 计划自检
    执行 /gsd-execute-phase N 波次（wave）并行执行，原子 git 提交，每个 plan 跑在全新上下文窗口
    验证 /gsd-verify-work N 目标回溯式（goal-backward）验证 + 人工 UAT
    交付 /gsd-ship N 从已验证的工作创建 PR，收尾并准备下一阶段

  • 内部架构（以 2026-05-22 分叉基线 v1.0.0 统计）：67 个斜杠命令、33 个专用 agent（planner / executor / verifier / code-reviewer / security-auditor 等）、约 100 个工作流文件、13 个钩子脚本（含 prompt 注入防护 gsd-prompt-guard.js、读取注入扫描、上下文用量监控、提交校验）。v1.41.0 起用 6 个命名空间元技能做两级路由，冷启动系统提示开销从约 2,150 token 降到约 120。

  • 抗上下文腐烂机制：独立 plan 在同一 wave 内并行、依赖 plan 排到后续 wave；每个执行器从干净的 200k 上下文启动，主会话保持在 30%–40% 占用。

  • 里程碑 / 工作流（workstream）：/gsd-workstreams 支持对一个里程碑的不同区域并行推进——对中大型项目分模块作战很关键。

  • 多运行时：开箱支持 Claude Code、Cursor、OpenCode、Gemini CLI、Kilo、Codex、Copilot、Windsurf、Antigravity、Augment、Trae、Qwen Code、CodeBuddy、Cline 等十余个运行时。通过 npx 安装，交互式多选运行时 + 选择 global / local 范围。

  • 配置哲学：工作流开关遵循「缺省即启用（absent = enabled）」——配置里没写的开关默认为开，按需在 /gsd-settings 里关掉。

3.2 Superpowers

  • 定位：一套可组合的 agentic 技能（skills）+ 软件开发方法论。

  • 维护现状：作者 Jesse Vincent（GitHub：obra），MIT 许可，约 21.2 万 star（2026-05-29 快照）；编制日最新版本为 v5.1.0（2026-05-04 发布）。

  • 安装与激活：Claude Code 通过 Anthropic 官方插件市场安装：/plugin install superpowers@claude-plugins-official。SessionStart 钩子自动加载 using-superpowers 技能，开机即生效，无需逐项目配置。

  • 核心技能（v5.1.0 共 14 个，按场景自动触发）：

    技能 作用
    brainstorming 苏格拉底式对话打磨设计，设计文档写入 docs/superpowers/specs/
    writing-plans 把已批准的设计拆成写明文件路径与验证步骤的小任务，计划写入 docs/superpowers/plans/
    subagent-driven-development 每个任务派一个实现子代理，完成后依次做规格符合性评审与代码质量评审
    test-driven-development 强制红-绿-重构：测试必须先失败再实现
    systematic-debugging 四阶段调试：先查根因再动手
    requesting-code-review 合并前派独立评审子代理冷读完整 diff，不带实现者的框架偏见

  • 调用方式：技能按场景自动触发，也可在对话里点名（如「用 superpowers:brainstorming 梳理需求」）。v5.1.0 已移除旧的 /brainstorm、/write-plan、/execute-plan 斜杠命令——它们此前只是提示改用技能的空壳。

  • 自治执行：设计与计划获批后说「go」，进入子代理驱动开发，逐任务实现、评审、继续；README 称连续自治工作一两个小时不偏离计划并不罕见。

  • 多运行时：官方 README 给出 Claude Code、Codex CLI / Codex App、Factory Droid、Gemini CLI、OpenCode、Cursor、GitHub Copilot CLI 的安装方式，每个工具需单独安装。Cursor 支持自 v4.3.1（2026-02-21）起提供，在 Cursor Agent 对话里执行 /add-plugin superpowers 即可。

  • 适用边界：产物是任务级 spec 与 plan，主控逻辑偏向「一个会话推进一份计划」；最适合单仓库、整体能装进一个会话的工作，面对多模块并行推进时需要额外的进度管理。

一句话对比：GSD 是「项目级的流程操作系统」，Superpowers 是「编码 agent 里的工程师良心」。两者不在同一层，因此既可单选，也能融合。

5. Claude Code + Cursor 协同场景的适配分析

5.1 决定性事实：共享的是项目级状态，而不只是插件

  • 协同的前提是两个工具看到同一份事实来源——落在仓库里的 spec、plan 与进度状态。
  • GSD 原生支持 Cursor 运行时，命令在两个工具里都是连字符形式（/gsd-new-project、/gsd-plan-phase 1…），.planning/ 落盘在仓库内，且 STATE.md 记录当前阶段、决策与阻塞项。于是在 Claude Code 里 /gsd-plan-phase 产出的计划，Cursor 打开同一仓库能直接读、直接执行，/gsd-progress 在任一侧都能判断「下一步该做什么」。
  • Superpowers 同样能装进 Cursor，两侧可以通过提交到仓库的 docs/superpowers/specs/、plans/ 交接单份计划；但它没有里程碑、阶段与执行进度的状态文件，多份计划之间「做到哪了」要靠人记。另外，它在 Cursor 里的自动触发与子代理行为取决于 Cursor 的插件与子代理能力，引入前应先用一个小任务验证。

结论：Superpowers 解决的是「单份计划怎么高质量地落地」，GSD 解决的是「一个中大型项目怎么在多个工具、多个会话之间持续推进」。协同场景下后者是主干。

5.2 两个工具的天然分工

  • Cursor：擅长 IDE 内的高频迭代、就地补全、可视化探索、快速读改。→ 适合「读共享计划状态 + 快速探索 / 局部修改」。
  • Claude Code：擅长长程自治、多 agent、终端化重活。→ 适合「按阶段严格执行 + 验证 + 交付」，并在此叠加 Superpowers 的 TDD / 评审纪律。

两个工具的用量配额各自独立，按上述分工也能顺带分流消耗：探索与轻量修改放在 Cursor，重活与自治执行放在 Claude Code，避免单侧触顶。

6. 三种方案对比

方案 A：单选 Superpowers（两侧各装一份）

  • 优点：安装最简单、自动触发几乎零心智负担、TDD / 调试 / 评审纪律最强、社区与治理最稳。
  • 缺点：两侧只能共享任务级 spec / plan，缺少里程碑与阶段状态，跨天、跨工具接力要靠人工记录进度；面对多模块并行推进时，单会话主控会吃紧。
  • 适合：项目中等规模、以 Claude Code 为主战场，Cursor 只承接局部修改。

方案 B：单选 GSD（双工具）

  • 优点：Claude Code 与 Cursor 共享同一套阶段状态、状态落盘可版本化、里程碑 / workstream / 波次并行天然适配中大型项目、单一工具栈贯穿两个 IDE。
  • 缺点：命令多、学习曲线较陡；TDD 与评审的「强制力」不如 Superpowers 那样深植于每个任务；需要承担分叉的供应链 / 治理风险。
  • 适合：重视双工具协同与项目可扩展性，愿意投入学习成本，并能做好依赖审查。

方案 C：融合 —— GSD 主干 + Superpowers 执行质量层（推荐）

  • 思路：让两者在不同的层各司其职，而不是抢同一个「头脑风暴 → 计划 → 执行」循环的方向盘。
    • GSD = 跨工具的规格 / 计划 / 状态主干：.planning/ 作为唯一事实来源，Claude Code 与 Cursor 共享；负责 macro 生命周期（discuss → plan → execute → verify → ship）、里程碑与波次并行。
    • Superpowers = 执行质量层：在执行密集的阶段，借助其 TDD、四阶段调试、冷读评审，把单个任务的实现质量拉满；主要在 Claude Code 侧使用，Cursor 侧验证可用后再按需启用。
  • 优点：兼得「双工具协同 + 中大型可扩展（GSD）」与「最强工程纪律（Superpowers）」。
  • 代价 / 注意：两者都会注入工作流指令，若同时全自动驱动会互相抢方向盘。融合的纪律是任一阶段只让一个框架当 driver：GSD 负责阶段编排与状态，Superpowers 的技能在执行阶段被点名使用（TDD / 调试 / 评审），不让它的 brainstorming → writing-plans 流程接管整个循环。
  • 适合：中大型项目 + 双工具协同 + 追求工程严谨度。

7. 安装级别：用户级 vs 项目级

要区分「工具本体」和「项目状态」两件事：

对象 推荐级别 理由
GSD 工具本体（命令 / agent / 技能） 用户级（global） 要在 Claude Code 和 Cursor 两个运行时、且在多个项目里复用；global 一次装好，避免每个项目、每个工具重复安装
GSD 项目状态 .planning/ 项目级，随仓库提交 它是规格、计划与决策的事实来源，必须可版本化、可回溯、可被两个工具共享
GSD 项目配置 .planning/config.json 项目级，提交 每个项目的工作流开关与模型档位随项目走
Superpowers 插件级（按工具分别安装） 安装后对该工具的所有项目生效；它的 spec / plan 产物落在项目 docs/superpowers/ 下，同样应提交

反模式提醒：不要把 GSD 工具本体只装在单个项目（local）却又指望在 Cursor 和其他项目里用——会反复缺命令。也不要把 .planning/ 放进 .gitignore——那等于丢掉了协同与可追溯的全部价值。

8. 必读：GSD 的治理与供应链风险

这是本次选型中最需要知情决策的一点：

  • 原维护者失联：据分叉维护者 trek-e 于 2026-05-22 在新仓库发布的延续公告，原维护者 TÂCHES 自 2026-04-01 起无法联系，社交账号疑似已删除，与项目关联的 $GSD Solana 代币被公开指为 rug-pull。公告同时写明：无法确认代币事件是维护者本人所为、合伙人退出还是账号被盗。
  • 发版记录：GitHub 上以原作者账号发布的最后一个版本是 v1.38.5（2026-04-25）；此后协作维护者经自动化流水线继续发版，原仓库最后一个稳定版是 v1.42.3（2026-05-16）。

行动指引：

  1. 只用社区延续分叉：open-gsd/get-shit-done-redux / npm @opengsd/get-shit-done-redux；移除任何旧的 get-shit-done-cc、@gsd-build/* 全局包。
  2. 把引入当作一次供应链审查：安装前过一遍近期提交与 release notes；GSD 能跑 shell、读写代码库，信任边界要谨慎。
  3. 锁定版本：在项目里固定 GSD 版本，不要永远跟随 latest，升级前读 CHANGELOG。
  4. 纵深防御：保留 GSD 的 prompt 注入防护与提交校验钩子，同时在工具权限配置里 deny 对 .env、密钥、凭据目录的读取。
  5. 风险偏好分流：对此类事件高度敏感、且阶段状态共享不是硬需求时，可以走「方案 A：只用 Superpowers」——治理更稳，这是完全合理的选择。

Superpowers 侧目前无同类治理事件：单一活跃维护者 + 官方插件市场分发，信任面更干净。

9. 最终推荐方案

GSD（Redux）为跨工具主干，Superpowers 为执行质量层。

整体形态：

  • GSD：用户级安装到 Claude Code + Cursor 两个运行时；.planning/ 随项目仓库提交，成为两个工具的唯一事实来源。
  • Superpowers：用户级安装到 Claude Code，在执行密集阶段提供 TDD / 调试 / 评审纪律；Cursor 侧按需安装。
  • 分工：
    • 规划与状态（discuss / plan / verify / ship 的编排）→ GSD，两个工具皆可读写。
    • 快速探索、就地小改、读取共享计划 → Cursor + GSD。
    • 严格分阶段执行、长程自治、高质量实现 → Claude Code + GSD（执行阶段点用 Superpowers 的 TDD / 评审技能）。

为什么是它而非单选：

  • 两个硬约束（双工具协同 + 中大型）让「只用 Superpowers」难以成为完整方案——它能装进两个工具，但不提供跨工具共享的阶段状态，中大型项目的进度接力缺一块。
  • 「只用 GSD」可行且简洁，但会浪费 Superpowers 那一层更严格的 TDD 与评审纪律。
  • 融合用很小的额外管理成本（守住「一阶段一个 driver」的边界），换来两边的长板叠加。

何时降级为单选（务实退路）：

  • 想要最低复杂度、项目规模可控 → 方案 A（仅 Superpowers）。
  • 对 GSD 治理风险高度敏感、又必须双工具 → 两侧都只装 Superpowers，把 spec / plan 提交入库作为交接物，另用一份简短的 STATUS.md 手工记录阶段进度；等分叉的信任度建立后再引入 GSD。

11. 落地最佳实践

  • 范围纪律：/gsd-discuss-phase 只澄清「怎么实现」，不在讨论里扩功能；要加功能就开新阶段或新里程碑。这是抑制 AI 范围蔓延的第一道闸。
  • 4 文件法则：触及约 4 个以上文件、或「该怎么表现」本身是难点时，才值得走完整 SDD；更小的改动直接做，或用 /gsd-quick，避免流程开销淹没收益。
  • 一阶段一 driver：融合方案的铁律。GSD 管编排与状态，Superpowers 在执行层管实现质量，互不抢方向盘。
  • 中大型分模块：用 /gsd-workstreams 把里程碑按区域（如 backend-api / web / infra）拆成并行工作流，对应项目的分层架构。
  • 每阶段后清场：阶段之间用 /clear + /gsd-progress --next，最大化「每个执行器全新上下文」的抗腐烂收益。
  • 冷读评审：合并前固定跑一次独立评审子代理（Superpowers requesting-code-review 或 GSD /gsd-code-review），评审者不带实现者的框架偏见。
  • 把决策沉淀进仓库：.planning/ 下的路线图、阶段 CONTEXT.md、PLAN.md、SUMMARY.md 全部提交——回看、交接、复盘都受益。
  • 断点恢复：长程执行被打断时，用 /gsd-pause-work 生成交接文件、/gsd-resume-work 恢复，而不是开新会话从头描述。

2026-09 补记：GSD 更名 GSD Core、Superpowers 进入 6.x，选型复核

以下为编制日之后的变化，均以 GitHub 仓库、Release 与 npm 记录为准。

GSD：更名 GSD Core，治理信号转好

  • 两次改名收敛：分叉最初以 GSD-redux/get-shit-done-redux 发布，当天迁到 open-gsd/get-shit-done-redux；2026-05-30 起 npm 包改名 @opengsd/gsd-core，2026-05-31 项目更名 GSD Core，仓库改为 open-gsd/gsd-core，首个正式版为 v1.2.0（2026-05-31）。旧包 @opengsd/get-shit-done-redux 停在 1.1.0 并被标记 deprecated（提示改装 @opengsd/gsd-core）；get-shit-done-cc 在 npm 上也已标记 deprecated。原仓库已归档，README 只剩一条指向 open-gsd/gsd-core 的迁移说明，警示文案改成了中性的「已迁移」。
  • 发版节奏：v1.5.0（06-17）、v1.7.0（07-15）、v1.9.1（07-31）、v1.13.0（09-06）直到 v1.15.0（09-26），约每一到两周一个 minor；发布说明中已有多名外部贡献者。站内另一篇《Open-GSD 源码深度解析》即以 v1.9.1 为基线。
  • 能力变化：v1.7.0 把宿主集成收敛为一套版本化的 Host-Integration Interface，十余个运行时统一走适配器，并新增配套 MCP 服务器；同版移除了 Gemini CLI 运行时，引导改用 Antigravity CLI。新增 /gsd-onboard 用于接入存量代码库。仓库自带 Claude Code 插件清单，可走原生插件安装，但官方文档注明它不执行 npm 安装器的安装期配置。
  • 表面积在膨胀：v1.15.0 为 72 个命令、64 个 agent 定义，分叉基线 v1.0.0 时是 67 个命令、33 个 agent。能力更全，冷启动开销也更大——只需要主循环时，--minimal 安装与 /gsd-surface 裁剪技能面更有价值。
  • 体量：GSD Core 约 9.9k star（2026-09-28），原仓库冻结在约 6.44 万。
  • 仍未改变的风险：截至 2026-09-29，延续公告未出现原维护者的新消息；社区治理已稳定运转，但依赖一个活跃维护者的格局没有根本变化，锁版本的纪律照旧。
  • 插件包装分道扬镳：jnuyens/gsd-plugin 于 2026-07-13 转到 buildomator 组织并更名 Buildomator，v4.0.0（06-27）起启用独立版本线，加入约定一致性门与漂移检测。它已是一条独立路线，不宜再当作「GSD 的 Claude Code 版」。

Superpowers：6.x 降本与覆盖更多工具

  • v6.0.0（06-16）：逐任务评审从两个评审子代理合并为一个，一次给出规格与质量两个结论；结尾增加一次整分支评审；执行前先对计划做冲突预检。官方在自家评测中称 Claude Code 与 Codex 上速度约翻倍、token 花费约减半（厂商自测数据）。同版新增 Kimi Code、Pi、Antigravity。
