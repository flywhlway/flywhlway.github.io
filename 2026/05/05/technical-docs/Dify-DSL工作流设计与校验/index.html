1. 方案详述（来源：LobeHub 功能调研与部署-dify深度研究DSL）

下面给你一份Dify v1.12.1 / Workflow 模式 / DSL v0.5.0 的企业版工作流 DSL，已将「搜索模块」替换为：

  • ✅ Tavily（默认必跑）
  • ✅ SearXNG（自建备选，配置了就自动参与）
  • ✅ Brave Search API（备选，配置了就自动参与）
  • ✅ 混合搜索聚合：三路结果统一解析 → 合并去重 → 域名黑白名单/每域名上限 → 进入证据流水线

实现方式为：在 Search Round Iteration 内并行/串行调用三路搜索，每个搜索节点都设置 error_strategy: default-value，所以即使你不配置 SearXNG/Brave，也不会影响导入与运行（只会使用 Tavily 的结果）。

✅ 可直接导入 DSL（企业版：Tavily + SearXNG + Brave 混合搜索）

保存为：manus_research_enterprise_tavily_mix_v1_12_1.yml
Dify → Studio → Workflow → Import DSL 导入即可。

导入后在 Environment Variables 填：

  • TAVILY_API_KEY（必填）
  • SEARXNG_BASE（可选，例如 http://searxng:8080）
  • BRAVE_API_KEY（可选）
  • 其他：黑白名单/每域名上限/缓存服务（可选）

2. 方案详述（来源：LobeHub 功能调研与部署-dify深度研究DSL）

下面给你一份 Dify v1.12.1 / Workflow 模式 / DSL v0.5.0 的企业私有化可落地版「Manus 深度研究」工作流 DSL（YAML），在不改 DSL 版本、不破坏可导入性前提下，完成你提出的升级点：

✅ 多轮 Iteration（Search Round 1..N）：按 search_queries[] 自动跑 N 轮搜索
✅ 来源去重 + 站点黑白名单 + 每域名上限：防刷屏、过滤低质站、控制覆盖面
✅ 证据缓存（同一次运行内）：跨轮去重 + 避免重复抓取同 URL（“运行内缓存”）
✅ 结构化引用输出：生成 BibTeX + GB/T 7714 两种格式（基于 URL/标题/访问日期，可落地）
✅ 标准化模块：Search Round Iteration → 聚合器 → Evidence Iteration → 总核查 → 报告排版 → 引用附录

重要说明（务实）：

  1. “跨运行持久化缓存”（例如把抓取结果缓存到 Redis/DB，下次直接复用）在纯 DSL 内不可靠，因为 v1.12.1 的 Workflow 更偏“单次运行编排”。企业版建议用一个 HTTP 缓存服务（可选），我已经预留了节点位（默认关闭，不影响导入）。
  2. 引用格式（BibTeX/GB/T）在不额外抓取 metadata 的情况下，最稳定做法是用 URL + title + access date 生成（可审计、可复现）。如果你要 DOI/期刊信息，需要额外接 Crossref/元数据抓取服务。

✅ 可直接导入的 DSL（企业可落地版）

复制为：manus_research_enterprise_v1_12_1.yml，在 Dify → Studio → Workflow → Import DSL 导入即可。

导入后请到 Environment Variables 填：

  • SERPER_API_KEY（必填，否则搜索节点会返回空）
  • DOMAIN_WHITELIST / DOMAIN_BLACKLIST（可选）
  • MAX_PER_DOMAIN（建议 2~3）
  • CACHE_SERVICE_BASE（可选，启用跨运行缓存时用）

4. 方案详述（来源：Dify DSL生成与校验）

从你导出的 DeepResearch.yml（Dify v1.12.1 导出格式）对比我上一版生成的 DSL，可以确定 App 打不开（前端 client-side exception） 的核心原因是：节点/条件/工具字段结构不符合你当前 Dify 前端期望的 DSL Schema，导致渲染工作流画布时直接崩溃（而不是“导入失败”）。

1) 你导出的 DSL 暴露出的关键 Schema 规则（与你环境一致）

我从 DeepResearch.yml 里看到你这套 Dify 的工作流节点结构有几个“硬要求”：

  1. 节点外层 type 固定是 custom，真正的节点类型写在 node.data.type（start/llm/if-else/tool/answer/template-transform/assigner…）
  2. if-else 节点必须使用 data.cases 结构（每个 case 里有 conditions[]，且 condition 里有 id / varType / value / variable_selector），而不是我上一版写的 data.conditions
  3. 大多数节点 data 里需要包含 isInIteration 与 iteration_id 字段（即便不在迭代中也要显式给 isInIteration: false，iteration_id 为空或缺省要符合前端预期）
  4. tool 节点必须使用 provider_id/provider_name/provider_type/tool_name/tool_parameters，而不是我上一版写的 plugin_unique_identifier 那一套
  5. 你导出的 LLM 节点并没有我上一版那种 structured_output_enabled/structured_output 结构；它是靠 response_format: json_object + （可选）json_process 工具解析来做结构化

以上任意一条不匹配，都很容易出现你截图这种“App 页面直接白屏报错”。

2) 修正策略（保证能打开 + 能导入 + 可运行）

  • 严格按你导出的 DSL Schema 改写节点字段（尤其 if-else 与 tool）
  • 结构化输出改为：LLM 输出 JSON（response_format=json_object）→ 用 langgenius/json_process 的 parse 工具读取字段（你环境里已存在该插件/格式，可靠）
  • 图片生成/编辑工具节点：我用 provider_id = openai / gemini_image，tool_name 采用常见命名 image_generation / image_editing。
    • 说明：不同插件版本工具名可能略有差异，但这不会再导致“App 打不开”；若导入后工具节点提示找不到工具，下拉重选一次即可（这是“运行时绑定”，不是 Schema 崩溃问题）。

3) 修正版：可导入可打开的 Dify v1.12.1 Chat App DSL（YAML 全文）

你可以直接用它替换上一版导入；如果导入后工具节点提示工具名不匹配，只需要进节点重选工具，不需要改结构。

10. 方案详述（来源：Dify 定时任务工作流）

1) Dify v1.12.1 是否“原生支持定时任务触发工作流”？

就 开源版 Dify v1.12.1 的常见能力来说：一般不提供“内置 Cron/定时触发器”去自动运行某个 Workflow App（工作流通常由 Chat/API 触发）。
因此要实现“每天自动跑一次”，最稳的做法是：

  • 用外部调度器（Linux cron / systemd timer / Jenkins / GitHub Actions 等）
  • 每天定时调用 Dify 的 Workflow 运行 API（相当于“定时触发工作流”）

你也可以在 Dify 的工作流编辑器里看看是否存在类似 Trigger / Schedule / Cron 的配置项：

  • 如果 UI 里就有 Schedule/Cron：那说明你当前版本/分支/插件已经支持原生定时触发；
  • 如果没有：就按外部 cron 调用 API 的方式做（下面我给你完整方案）。
