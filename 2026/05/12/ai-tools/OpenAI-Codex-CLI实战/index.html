OpenAI Codex CLI 实战：面向 Claude Code 用户的迁移手册

面向 Claude Code 用户，对照讲解 Codex CLI 的安装认证、config.toml、AGENTS.md、Skills、MCP、沙箱与审批、Hooks、exec 与…

Flywhl 55 分钟 更新于 2026.09 #AI工具#开发效率#Claude Code

先读结论

  1. 概念几乎一一对应：CLAUDE.md → AGENTS.md，.mcp.json → config.toml 的 [mcp_servers]，Skills 同为 Agent Skills 标准，hooks 采用兼容的 JSON 结构。
  2. Codex 的安全模型是两层：操作系统级沙箱决定能做什么，审批策略决定何时停下来问你；日常用 workspace-write + on-request。
  3. codex exec 默认只读沙箱，配合 --output-schema 与 -o 可以把 agent 变成 CI 里可靠的结构化步骤。
  4. 迁移的最小动作：AGENTS.md 作为单一事实源，CLAUDE.md 只保留一行 @AGENTS.md。

版本：2026-05 · 适用：Codex CLI 0.130（2026-05-08）及相近版本、GPT-5.5 · macOS / Linux / Windows
目标读者：有 Claude Code 实战经验、希望系统掌握 Codex 并用它做规范驱动开发的工程师
写法约定：命令与配置字段以 developers.openai.com/codex 文档和 openai/codex 发布说明为准；写作时点之后的变化统一放在文末补记

1. 认知重置

1.1 叫 “Codex” 的几样东西，不要混淆

“Codex” 这个名字在 OpenAI 的产品线里出现过多次，含义不同：

名称 时间 是什么 与本文的关系
Codex 模型（API） 2021 基于 GPT-3 微调的代码补全模型，曾为早期 GitHub Copilot 提供能力，2023 年停用 无关
Codex CLI 2025-04-16 开源 终端编码 agent，Apache-2.0，现以 Rust 实现，内置操作系统级沙箱 本文主角
Codex 云端 agent 2025-05 在 chatgpt.com/codex 提交任务，于云端容器中异步完成并开 PR 互补
Codex IDE 扩展 2025-08-27 在 VS Code、Cursor、Windsurf 等编辑器中使用同一个 agent 互补
Codex app 2026-02-02（macOS），2026-03-04（Windows） 桌面端多线程 agent 应用 互补

CLI、IDE 扩展、app 共用同一套配置（~/.codex/config.toml）、同一套 AGENTS.md 与 Skills。

一句话定位：Codex CLI 是终端里的 OpenAI 编码 agent，与 Claude Code 直接对标；它运行 GPT-5.x 系列模型，自带沙箱，能以非交互方式嵌入脚本和 CI。

1.2 为什么 Claude Code 用户值得认真学习 Codex

  • 迁移成本低：AGENTS.md、Agent Skills、MCP、生命周期 hooks、子代理——Claude Code 里的核心概念在 Codex 中都有对应物，多数只是文件位置和格式不同（第 2 章）；
  • 沙箱是默认的：命令在操作系统级沙箱中执行，默认只能写工作区、不能联网，越界时才请求批准；
  • 非交互能力强：codex exec 默认只读，支持 JSON Schema 约束最终输出，官方提供 GitHub Action，适合放进 CI；
  • 订阅内含额度：ChatGPT 付费计划包含 Codex 用量，高频使用者不必单独按 token 付费；
  • 第二意见：换一家模型审查同一份 diff，盲点不同；许多团队用 Claude Code 做复杂推理与长任务，用 Codex 做审查、批量任务和 CI——两者共存而不是替代。

4.4 模型选择指南

截至 2026-05-12，用 ChatGPT 账号登录时可选的主要模型：

模型 定位 适合
gpt-5.5 2026-04-23 进入 Codex，官方推荐的默认选择 实现、重构、调试、测试与验证等大多数任务
gpt-5.4 上一代旗舰（2026-03-05），首个原生支持 computer use 的通用模型，实验性支持 1M 上下文 GPT-5.5 尚未开放时的主力
gpt-5.4-mini 2026-03-17，速度超过 GPT-5 mini 两倍，只消耗 GPT-5.4 约 30% 的额度 代码库探索、大文件阅读、子代理
gpt-5.3-codex 2026-02-05，编码专用 偏好 codex 系列行为的存量配置

选择建议：

  • 默认 gpt-5.5 + medium，难题临时 -c model_reasoning_effort=high；
  • 探索和子代理用 gpt-5.4-mini，把主模型的额度留给规划与最终判断；
  • Fast 模式（0.110 起的 /fast 开关）用更高的服务档位换取速度，额度消耗也更快；
  • 用 API Key 登录时，可以选择 API 支持的其他模型，或通过 model_providers 接入其他提供方。

5. 规范驱动开发：AGENTS.md 深度实战

AGENTS.md 是 Codex 规范驱动开发的核心。它不只是一个说明文件，而是你与 agent 之间的持久契约。

5.1 AGENTS.md vs CLAUDE.md：迁移须知

Codex 如何加载 AGENTS.md（每次启动构建一次指令链）：

  1. 全局：~/.codex/AGENTS.override.md 存在则用它，否则用 ~/.codex/AGENTS.md；
  2. 项目：从项目根（通常是 Git 根目录）向下走到当前工作目录，每一级目录依次查找 AGENTS.override.md、AGENTS.md、project_doc_fallback_filenames 中的备用名，每级最多取一个文件；
  3. 合并：按从根到当前目录的顺序拼接，越靠近当前目录的内容越靠后、优先级越高；总大小超过 project_doc_max_bytes（默认 32 KiB）后不再追加。

6. Skills 体系：从入门到自建

6.1 Skills 是什么

Skills 是可复用的行为包：一个 SKILL.md（加可选的脚本和资源），告诉 Codex 如何完成某类特定任务。Codex 于 2025-12-19 支持 Skills，遵循与 Claude Code 相同的 Agent Skills 开放标准（agentskills.io）。AGENTS.md 定义项目规范，Skills 定义可移植的工作流程。

关键设计：渐进式披露

Codex 启动时只把每个 skill 的名称、描述和路径放进初始列表，这份列表最多占模型上下文窗口的 2%（无法得知窗口大小时按 8000 字符计）。只有判断任务匹配时，才读取完整的 SKILL.md。skill 太多时，Codex 会先缩短描述，仍然超出预算就省略部分 skill 并给出警告。

6.2 Skills 目录位置

范围 位置 适用
仓库 从当前目录向上到仓库根，每一级的 .agents/skills/ 模块专属或全仓共享的流程
用户 ~/.agents/skills/（兼容旧的 ~/.codex/skills/） 个人跨项目使用的流程
管理员 /etc/codex/skills/ 机器或容器级的默认 skills
系统 随 Codex 分发 如 skill-creator、skill-installer

.agents/skills 这个路径不绑定 Codex，适合多个工具共享；Codex 也支持软链接的 skill 目录。

MCP（Model Context Protocol）是 Codex 连接外部工具和数据源的标准接口。概念与 Claude Code 完全一致，差别在配置格式与少数字段语义。

含义 Codex 字段 说明

最常见的迁移错误是把 Claude Code 的 "env": {"GITHUB_TOKEN": "${GITHUB_TOKEN}"} 改写成 env = { GITHUB_TOKEN = "GITHUB_TOKEN" }——这会把字符串 GITHUB_TOKEN 当作 token 传给 server。正确写法是 env_vars = ["GITHUB_TOKEN"]。

8. 沙箱与审批机制：安全地放权给 AI

Codex 的安全模型有两个独立维度：沙箱模式决定命令在技术上能做什么（写哪里、能否联网）；审批策略决定何时必须停下来问你。这也是它与 Claude Code 在架构上差别最大的地方。

8.1 沙箱架构

平台 实现 备注
macOS 系统内置的 Seatbelt 框架 开箱即用
Linux / WSL2 bubblewrap（bwrap） 建议用包管理器安装 bubblewrap；2026 年初从 Landlock 方案逐步迁移而来
Windows（PowerShell） Windows 原生沙箱（受限令牌） 在 WSL2 中运行时使用 Linux 实现

沙箱作用于 agent 执行的命令及其子进程。即使发生提示词注入，命令也被限制在沙箱边界之内——默认只能写工作区、不能联网；需要越界时走审批流程，由人决定。

8.2 沙箱模式详解

模式 能做什么 适用
read-only 可以读文件；编辑文件或执行命令需要批准 了解陌生代码库、只读审查
workspace-write 可读文件、在工作区内编辑、执行常规本地命令；默认无网络 日常开发（推荐）
danger-full-access 无沙箱限制，文件系统与网络边界都被移除 只在一次性容器等隔离环境中使用

8.3 审批模式详解

策略 行为 适用
untrusted 除少量安全的只读命令外，执行命令前都询问 审查不熟悉的代码
on-request 沙箱内的操作自主执行，需要越界（写工作区外、联网等）时询问 日常交互（推荐）
never 从不询问，越界操作直接失败 非交互的自动化，配合合适的沙箱
on-failure 失败后才询问 2026-02 起废弃，不要再用

TUI 内动态调整：输入 /permissions（0.89 起，兼容旧的 /approvals）在会话中切换预设，例如临时切到只读模式讨论方案。

两个需要知道的参数：

  • --full-auto 是 --sandbox workspace-write --ask-for-approval on-request 的旧快捷方式，0.128（2026-04-30）起标记为废弃，新脚本请显式写出两个参数；
  • --dangerously-bypass-approvals-and-sandbox（别名 --yolo）同时关闭审批与沙箱，只允许在可随时销毁的隔离环境中使用。

8.4 细粒度控制：命令规则与自动审查

命令规则（rules/*.rules）：对”在沙箱外执行某类命令”做细粒度决策。规则文件放在任一配置层的 rules/ 目录下，例如 ~/.codex/rules/default.rules 或项目的 .codex/rules/：

  • decision 取值为 allow（沙箱外直接执行）、prompt（每次询问）、forbidden（直接拒绝）；多条规则同时命中时取最严格的一条；
  • pattern 按参数逐项做前缀匹配：上面的规则拦得住 git push --force origin main，拦不住参数顺序不同的 git push origin main --force，这类变体需要补规则或用 §9.6 的 hook 兜底；
  • 在 TUI 的审批提示里选择”以后都允许”，Codex 会把对应的前缀规则写进 ~/.codex/rules/default.rules；
  • 项目级规则只在受信任的项目中加载（0.122 起明确要求）。

自动审查（Auto-review）：2026-04-23 起，Codex 可以把符合条件的审批请求先交给一个审查 agent 判断，给出批准、拒绝或转交人工的结论，并显示风险等级。它不改变沙箱边界，只是替你处理一部分审批提示；2026-05-11 官方补充了专门的 Auto-review 文档，说明触发条件、失败行为与本地 / 托管配置方式。

8.5 常用安全组合

场景 沙箱 审批 / 其他 说明
审查陌生仓库 read-only untrusted 或 on-request 先读懂再授权
日常开发 workspace-write on-request 官方所说的 Auto 预设
需要安装依赖 workspace-write + network_access = true on-request 联网只开在需要的项目配置里
CI 只读审查 codex exec --sandbox read-only exec 不会交互询问 结果用 -o 写出
CI 自动修复 codex exec --sandbox workspace-write 运行在隔离 runner 中 修改以 PR 形式提交，由人合并
一次性容器内全自动 --yolo — 容器销毁即回收全部副作用

MCP server 认证失败 TOML 中用 env = { KEY = "KEY" } 传了字面字符串 改为 env_vars = ["KEY"] 或 bearer_token_env_var

13. 常见问题与排错

13.1 认证问题

问题：codex login 后仍提示未认证

凭据保存在 ~/.codex/auth.json（或系统钥匙串），不要为了排错把文件内容打印到终端或贴进 issue。

问题：有 ChatGPT 订阅，但提示额度用尽

Codex 的计划内额度同时受 5 小时滚动窗口和每周窗口约束，任一耗尽都会被限流。用 /status 查看两个窗口的剩余情况；急需继续时可以改用 API Key 登录按 token 计费。

13.2 沙箱问题

问题：命令报 Permission denied 或写文件失败

需要联网的命令失败，多半是 workspace-write 默认关闭了网络；在确实需要的项目中打开 network_access，而不是切到 danger-full-access。

问题：Linux 上沙箱启动失败

部分发行版通过 AppArmor 限制非特权用户命名空间，导致 bwrap 无法创建沙箱；按官方沙箱文档加载 bwrap 对应的 AppArmor profile，不要为此全局关闭该限制。

13.3 Skills 问题

问题：Skill 安装后不显示

  1. 确认目录位置：用户级是 ~/.agents/skills/<name>/SKILL.md，项目级是 .agents/skills/<name>/SKILL.md；
  2. 确认 frontmatter 包含 name 与 description，且 YAML 合法；
  3. 在 TUI 中输入 /skills 查看；仍然没有就重启 Codex；
  4. 检查是否被 [[skills.config]] 设置了 enabled = false。

问题：Skills 太多，部分没有出现在列表中

初始列表的预算是上下文窗口的 2%。缩短各 skill 的 description（关键信息放前面），并停用不常用的 skill：

13.4 性能问题

问题：响应慢

  • /model 切换到 gpt-5.4-mini 处理探索类任务；
  • /fast 开启 Fast 模式；
  • 长会话用 /compact 压缩上下文，或 /new 开新对话；
  • 批量任务改用 codex exec。

问题：大代码库探索慢

  • 在相关子目录启动（codex --cd services/ota），缩小搜索范围，同时加载该目录的 AGENTS.md；
  • 在 AGENTS.md 中写明模块地图（”设备认证在 src/infra/auth/，OTA 在 src/service/ota/“）；
  • 让 Codex 派 explorer 子代理并行检索，主会话只接收结论。

13.5 额度管理

节省额度的策略：

  1. 探索与子代理任务用 gpt-5.4-mini（约为 GPT-5.4 额度消耗的 30%）；
  2. 简单任务用较低的推理强度，难题再临时调高；
  3. 及时 /compact，避免长会话反复携带无关上下文；
  4. CI 与批处理用 API Key 单独计费，不占用个人订阅额度。

另有几处当前文档与正文写法不同，时间点无法精确到版本，统一列在这里：

  • Hooks 需要信任审查：非托管的 hooks 首次运行前需要在 /hooks 中审查并信任，定义变更后需要重新确认；事件也扩充到 PreCompact、PostCompact、SubagentStart、SubagentStop、SessionEnd、Interrupt 等。

  • 审批策略字段：当前配置参考中 approval_policy 只保留 on-request、never 和 granular 细粒度表，approvals_reviewer = "auto_review" 用于启用 §8.4 提到的自动审查。
