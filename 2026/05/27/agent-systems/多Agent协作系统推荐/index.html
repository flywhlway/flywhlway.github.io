2026 多 Agent 框架选型：以设备智能诊断为例

从多 Agent 的真实收益与代价出发，梳理四种协作拓扑在设备诊断中的用法，对照 7 个主流框架截至 2026-05 的能力与成熟度…

Flywhl 15 分钟 更新于 2026.09 #架构设计#LangGraph#Agent

先读结论

  1. 多 Agent 的收益来自上下文隔离、并行取证和权限分离，代价是 token 成倍增长、串行误差累积和排障变难；说不出单 Agent 在哪里失败，就不要拆。
  2. 诊断流程不同阶段适合不同拓扑：分诊用流水线，取证用主管-专家并行，根因推断用黑板，高风险结论再加评审。
  3. AutoGen 与 Semantic Kernel 已并入 Microsoft Agent Framework（2026-04-02 GA），新项目不应再以它们为起点。
  4. 专家之间传递带数据引用的结构化证据，不传大段自然语言；置信度由可观测特征合成，并用历史工单校准，不采信模型自评。

先问该不该用多 Agent

「多 Agent」常被当成架构升级的标志，但它本质上是一种拆分策略，有明确的收益，也有明确的代价。

真实收益

收益 机制 在设备诊断里的体现
上下文隔离 每个 Agent 只加载本领域的工具说明和资料 信号分析专家看不到维修手册检索工具，工具选错的概率下降
并行取证 互不依赖的证据收集可以同时进行 振动、温度、报警码、历史工单四路查询并行，端到端时延取决于最慢的一路
权限分离 只读分析与有副作用的动作由不同 Agent 执行 只有处置 Agent 能创建工单或下发诊断指令，而且必须经过审批
独立演进 每个专家有自己的评测集和负责团队 知识库团队改检索策略时，不需要回归整条链路
模型分级 不同环节使用不同档次的模型 分诊用小模型，仲裁用强模型

真实代价

  • token 成倍增长：每个 Agent 都要重新读一遍任务描述和共享上下文，协调消息本身也要消耗 token。
  • 串行误差累积：假设每一步的正确率是 95%，五步串行下来只剩约 77%。拆得越细、链条越长，端到端正确率越低。
  • 结论冲突：两个专家给出相反的判断，需要额外设计仲裁机制。
  • 排障困难：一个错误结论可能源自某个专家漏掉了证据、仲裁时权重给错了，或者上下文传递过程中被截断，没有链路追踪就无法定位。

判断标准

情况 建议形态
工具少于十来个、领域单一、步骤固定 单 Agent + 工具，或者固定工作流
步骤固定，但个别步骤需要模型判断 工作流里嵌入 LLM 节点，不需要 Agent 自主规划
证据来源多且可以并行、各领域有独立的负责人、工具集大到单 Agent 频繁选错 多 Agent
需要跨团队或跨语言（Java 平台调用 Python 分析服务） 多 Agent，并通过 A2A 协议互通

建议从单 Agent 起步，积累评测数据后再拆分。每次拆分前，都应能说出单 Agent 在哪一类用例上失败，并且拆分后能在同一评测集上验证改进。

协作拓扑与诊断场景映射

多 Agent 系统常用的拓扑有四种：

拓扑 结构 优点 风险
主管-专家 主管负责拆解任务、分派给专家、汇总结果 控制流清晰，容易加审批节点 主管成为瓶颈；拆解出错时，后续全部偏离
流水线 固定顺序，上一步的输出是下一步的输入 可预测，容易测试 误差逐级累积；无法处理需要回退的情况
辩论 / 评审 一方提出结论，另一方挑错，多轮收敛 能暴露单一视角的盲点 成本高；同一底座模型的「辩论」可能只是换个说法重复
黑板 各专家把证据写入共享存储，由控制器根据黑板状态决定下一步 适合证据逐步积累、假设不断修正的问题 需要严格的证据格式，否则黑板会变成垃圾堆

设备诊断不是只用一种拓扑，而是在不同阶段组合使用：

诊断阶段 拓扑 理由
告警接入与分诊 流水线 标准化、去重、分类，步骤固定
证据收集 主管-专家，并行扇出 各数据源相互独立，可以并行
根因推断 黑板 证据需要逐步积累，假设需要增删
结论复核 评审（按条件触发） 只在低置信或高风险时触发，控制成本
处置 流水线 + 人工审批关口 动作有副作用，必须可审计 
flowchart LR
  A["告警 / 工单"] --> T["分诊（流水线）"]
  T --> S{"主管：选择专家"}
  S --> E1["信号分析专家"]
  S --> E2["报警码专家"]
  S --> E3["知识检索专家"]
  S --> E4["历史工单专家"]
  E1 & E2 & E3 & E4 --> BB[("证据黑板")]
  BB --> ARB["仲裁"]
  ARB -- "证据不足（最多补查一轮）" --> S
  ARB -- "低置信 / 高风险" --> REV["评审 + 人审"]
  ARB -- "高置信 / 只读建议" --> OUT["诊断报告"]
  REV --> ACT["处置 Agent（唯一有写权限）"]

按场景挑选

  • 需要精确控制流程、长流程可恢复、审批节点多：选 LangGraph。它的状态图把分支、并行、中断都显式写出来，检查点和 interrupt() 的组合最成熟。代价是代码量比「角色扮演」式框架大。
  • .NET 技术栈，或者深度使用 Azure：选 MAF。它已经 GA，Workflow 自带检查点、时间回溯和 OTel。原来用 Semantic Kernel 的团队迁移成本最低。
  • 以 Gemini 或 Google Cloud 为主，重视跨团队 Agent 互通：选 ADK。A2A 是 Google 提出的协议，ADK 的原生支持最完整。但 2.0 刚发布一周，生产环境可以先留在 1.x，观察 2.x 的补丁节奏。
  • 想快速搭出角色分工清晰的原型：选 CrewAI。Crew 的角色与任务抽象上手快，Flows 补上了确定性控制流。但检查点仍标注为 early release，长流程的恢复能力需要自行验证。
  • 以 OpenAI 模型为主，要求轻量：选 OpenAI Agents SDK。handoff 和审批中断机制简洁。但它仍处于 0.x，小版本更新频繁，需要锁定版本并关注变更；没有原生 A2A，跨服务协作要自己封装。
  • Java 平台团队：选 Spring AI Alibaba 或 AgentScope Java，两者的对比见本站《Java 生态的 Agent 框架》一文。AgentScope Python 2.0 刚完成大规模重构：发布说明写明评测、RAG、TTS、实时语音等模块暂时弃用、等待重构，2.0.0 源码中也没有这些模块。依赖它们的项目应继续使用 1.0.x。

协议分层：何时用 MCP，何时用 A2A

  • MCP 解决 Agent 到工具的连接：时序库查询、报警码字典、工单系统都应封装成 MCP Server，由数据所有方维护。无论上层换哪个框架，工具层都不需要重写。
  • A2A 解决 Agent 到 Agent 的连接：当专家由另一个团队、用另一种语言、独立部署时使用，例如 Java 平台上的编排 Agent 调用 Python 的信号分析 Agent。A2A 于 2025-04-09 发布，2025-06 捐赠给 Linux 基金会；MCP 于 2025-12 进入 Linux 基金会旗下的 Agentic AI Foundation。注册发现可以使用 Nacos 3.1 起提供的 A2A Registry。
  • 同一进程内的专家不要走 A2A。 网络调用会增加时延，还会把本可共享的图状态拆成消息，得不偿失。

诊断多 Agent 参考设计

专家划分：按证据类型和权限，而不是按部件

直觉上会按部件划分专家，比如电机专家、电源专家、传感器专家。但设备故障往往跨部件传导：电源纹波可能引起传感器读数异常，轴承磨损可能表现为电流谐波。按部件切分，每个专家都需要全部数据工具，隔离的收益就没有了。

更稳妥的划分依据是证据类型加权限：

专家 输入 可用工具 输出 权限
信号分析 设备 ID、时间窗 时序库查询、异常检测服务 异常片段、统计特征、数据引用 只读
报警码 报警码列表 码表字典、共现统计 码的含义、频次、共现模式 只读
知识检索 症状描述、候选故障 手册与案例 RAG 相关段落与出处 只读
历史工单 设备型号、候选故障 工单库查询 同型号同故障的处置记录、复发率 只读
仲裁 黑板内容 不调用任何数据工具 结构化结论与引用 只读黑板
处置 已批准的结论 创建工单、下发诊断指令 执行回执 唯一有写权限，必须经过审批

仲裁 Agent 不调用数据工具，这一点是刻意的：它只能依据黑板上已有的证据下结论，因此每条结论都能追溯到具体的证据。

仲裁：先规则，后模型，冲突限轮

仲裁按以下顺序处理：

  1. 硬规则：安全相关的报警码一律升级到人工；证据全部来自单一来源的假设，置信度设上限。
  2. 假设打分：对每个假设，汇总支持与反驳证据，结合历史先验，给出排序。这一步可以用模型做综合判断，但输出必须引用 evidence_id。
  3. 冲突处理：遇到下表中的冲突，最多补查一轮，补查后仍无法区分的，交给人工。
冲突类型 处理方式
两个专家对同一时间窗给出相反判断 回查双方的 data_ref，由仲裁指定其中一个专家做针对性检验
知识库建议与本型号历史工单不一致 以本型号历史为准，并在报告中标注差异
头两个假设分数接近 请求能够区分二者的证据，比如特定频段或特定报警码，而不是再做一次泛泛的全面分析

不要用多数投票代替仲裁。几个专家往往用的是同一个底座模型、读的是同一批上下文，它们的错误是相关的，三票对一票并不比一票可靠多少。

置信度与人审

模型自己报出的「置信度 0.85」不是概率，不能直接用来决定是否自动执行。置信度应当由可观测的特征合成：

  • 支持证据的独立来源数，比如信号和工单算两个来源，同一信号的两个统计量只算一个；
  • 是否存在反驳证据；
  • 历史先验，即本型号该故障的发生频率；
  • 硬规则是否命中。

然后用已结案的工单做校准：把结论按置信度分桶，统计每桶的实际正确率。如果置信度在 0.8 到 0.9 之间的结论实际只有 60% 正确，就要调整合成权重，或者提高自动化阈值。

人审的触发条件由置信度和动作风险两个维度共同决定：

只读建议（报告、排查清单） 有副作用的动作（下发诊断指令、停机建议）
高置信 自动输出，定期抽检 人工一键确认
低置信 输出证据包，标注「待人工判断」 转人工诊断，Agent 只提供证据
涉及安全 始终人审 始终人审，且需要双人确认

工程师的审批结果，以及最终的维修结论，都要回写为带标签的数据，用于校准置信度和扩充各专家的评测集，形成闭环。

落地反模式

反模式 后果 改法
按组织架构切分 Agent，每个部门一个 Agent 边界跟着组织调整变动，证据类型相互重叠 按证据类型和权限划分
让专家在无结构的群聊里自由对话 token 消耗失控，出现循环，终止条件不明确 显式拓扑，设定轮数上限，由仲裁决定何时结束
专家之间只传自然语言总结 仲裁无法溯源，无法判断结论出自哪条证据 传结构化证据，必须带 data_ref
模型自评置信度直接决定是否自动执行 过度自信的错误结论会直接落地 用可观测特征合成置信度，并用历史数据校准
所有 Agent 共享全部工具，都有写权限 提示注入或推理错误可能触发写操作 只读专家与处置 Agent 分离，写操作走审批
长流程没有持久化检查点 审批等待期间服务重启，会话丢失，只能从头再来 使用 Postgres、Redis 等持久化检查点，thread_id 与工单号绑定
新增专家时不做评测 局部改进，整体退化 每个专家有独立评测集，新增或修改后跑端到端回归
业务逻辑写进框架特有的抽象 换框架等于重写 工具封装为 MCP Server，领域逻辑写成普通函数，框架只负责编排
新项目选用 AutoGen 或 Semantic Kernel 做编排 面临迁移，也拿不到新特性 评估 MAF 或其他仍在活跃维护的框架
