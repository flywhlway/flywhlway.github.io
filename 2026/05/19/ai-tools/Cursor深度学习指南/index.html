1. 前言：为什么 Cursor 值得被认真学习

1.1 从 “vibe coding” 到 “spec-driven coding”

vibe coding 的循环大家都熟悉：打开 chat，凭直觉写 prompt，看输出，不满意再聊几轮，把能跑的代码提交进去。这种方式对小工具、原型、个人项目非常高效，放到中大型项目里却几乎一定失控：

  • 上下文会爆——单轮对话很快塞满 token，模型开始忘掉前面的约定；
  • 代码风格会漂移——三天前生成的代码用 Tailwind，三天后又冒出 styled-components；
  • 架构会失控——本想只加一个接口，AI 顺手新建了三个 service 类和一个循环依赖；
  • review 成本反超手写——表面写得快，PR 打开发现要重构一半。

2026 年工程团队对 AI 编码工具的期望已经从”快”转向”稳”，关键词是 规范驱动开发（Spec-Driven Development, SDD）：先有清晰的规范、规则、计划，再让 AI 作为执行体在受约束的边界内工作。Cursor 适合落地这种工作流，原因不在于某个模型最强（模型层 Cursor 是路由，Composer 2.5、GPT-5.5、Claude Opus 4.7 等都能选），而在于它在 IDE 层提供了：

  1. Rules / Skills / Subagents / Hooks 四类可复用的上下文与控制机制；
  2. Plan 模式与 Agent 模式分离，先计划、后执行；
  3. Agents Window + /worktree + /best-of-n 的并行与隔离执行；
  4. MCP 原生支持，让 agent 能查数据库、读设计稿、操作 issue；
  5. Cloud Agents 与 Cursor SDK，把长任务从本地剥离，异步交付 PR。

本文要回答的核心问题是：何时不该 vibe coding，以及项目复杂度越过临界点后，如何用一套受控、可审计、团队可复用的工作流交付严肃软件。

2. Cursor 全景认知：2026 年的产品形态

2.1 Cursor 是什么、不是什么

Cursor 是：Anysphere 出品的 AI-native IDE，从 VS Code fork 而来，在 AI 集成层做了深度重写。VS Code 的扩展、键位、主题、设置几乎可以无缝迁移。

Cursor 不是：一个 VS Code 插件。它把索引、上下文管理、agent 调度都放在 IDE 内部处理，同时通过 CLI、SDK、Cloud Agents 把同一套 agent 运行时延伸到终端、脚本和云端。

它的产品定位很清晰：承担从单行补全到端到端特性交付的全谱 AI 编码场景。理解这一点，才能理解为什么同一个工具里同时存在 Tab、Plan、Subagents 和 Cloud Agents——它们分别服务于不同粒度的任务。

2.3 模型怎么选

Cursor 的模型选择器可以随时切换（Cmd+/ 循环切换，默认模型在 Cursor Settings > Models 设置）。与其记 benchmark，不如按任务性质选：

任务类型 推荐 理由
日常编辑、小范围重构、写测试 Auto 或 Composer 2.5 速度快、成本低，Cursor 针对自家 agent 工具链训练
需求澄清、架构设计、疑难调试 Claude Opus 4.7 或 GPT-5.5 长链推理与跨文件理解更稳，贵但值得
大范围探索、读大量文件 交给 Explore 子代理（默认用更快的模型） 中间输出留在子代理上下文里
超长上下文（大型迁移、读整份规范） 开启 Max Mode 的强模型 用更大上下文换一次性读全
拿不准哪个模型擅长 /best-of-n 多模型并行 用结果说话，代价是成倍的用量

原则只有一条：设计与关键算法用最强模型，实施与机械性修改用快模型。§15.6 会列出与之相反的反模式。

3. 入门配置：从零搭建专业开发环境

目标：从下载 Cursor 到第一个 commit，30 分钟内得到一个可用于团队项目的环境。

3.1 系统准备

  • 平台：macOS（Apple Silicon 与 Intel）、Windows、主流 Linux 发行版均有安装包；
  • 磁盘：应用本体之外，为代码库索引和 worktree 预留空间（每个 worktree 是一份完整检出，依赖另算）；
  • 网络：模型推理都在云端，需要稳定外网；企业网络需放行 Cursor 相关域名。

3.2 安装与初始登录

首次启动：

  1. 选择登录方式（GitHub 登录便于后续把仓库接入 Cloud Agents 与 Bugbot）；
  2. 选择是否导入 VS Code 配置（建议导入，扩展、键位、设置一次迁移）；
  3. 在命令面板执行 Install 'cursor' command，之后可以在终端用 cursor . 打开目录。

3.3 必做的 8 项初始设置

打开 Cursor Settings（Cmd+Shift+J，或 Cmd+, 进入 VS Code 设置后切换），按顺序完成：

① 启用 Privacy Mode

开启后 Cursor 承诺零数据保留、不用你的代码训练模型。团队计划可以由管理员对全员强制开启。处理公司代码时这是底线设置。

② 配置默认模型

在 Cursor Settings > Models 勾选常用模型并设置默认模型；日常建议 Auto 或 Composer 2.5，把 Claude Opus 4.7、GPT-5.5 保留给设计与疑难问题（见 §2.3）。

③ 启用 Codebase Indexing

在 Indexing & Docs 中开启代码库索引，等待状态显示索引完成。索引决定了 agent 做语义检索时能否找到相关代码（机制见 §5.1）。

跑一遍完整流程，确认环境就绪：

  2. 试 Tab：在 README.md 输入 ## Featu，观察补全与后续段落预测。
  3. 试 Inline Edit：选中标题行，按 Cmd+K，输入”改成更正式的项目简介”，查看 diff 后接受或拒绝。
  4. 试 Ask：打开 Agent 面板（Cmd+I），用模式选择器或 Shift+Tab 切到 Ask，问”这个项目的结构是什么？”。

3.5 推荐的扩展兼容性检查

Cursor 兼容大部分 VS Code 扩展，但 AI 补全类扩展会与 Cursor Tab 抢按键和上下文，建议禁用：

  • GitHub Copilot；
  • Windsurf（原 Codeium）插件；
  • Continue 等其他 AI 助手（不专门使用就关掉）。

建议保留：GitLens（Git 历史）、Error Lens（行内错误）、ESLint / Prettier（格式与静态检查）、Docker 与 Kubernetes 扩展、Markdown Mermaid 预览（配合 §10 的架构图）。

4. 核心交互模型：Tab、Inline Edit、Agent、Ask、Plan、Debug

推荐的学习路径：Tab → Inline Edit → Ask → Agent / Plan → Debug。直接跳到 Agent 的开发者最容易过度信任 AI、漏掉 bug。

4.1 Tab：智能下一步预测

Tab 不是简单的下一行补全，而是 next-edit prediction：Cursor 综合光标位置、周边代码、最近编辑历史，预测你接下来要做的整个编辑动作，可能是：

  • 在当前位置插入几行；
  • 跳到另一处（同文件甚至跨文件）继续相关修改；
  • 提示一次多行重命名或重构。

示例场景：给一个 TypeScript interface 加了字段 email: string。按 Tab 后，Cursor 可能依次提示：

  1. 在 mock 数据处给每个对象补 email: 'xxx@example.com'；
  2. 在对应的 Zod schema 补 email: z.string().email()；
  3. 在表单组件补 <input name="email" />。

操作：

  • 接受：Tab
  • 拒绝：Esc
  • 逐词接受：Cmd+→（macOS）/ Ctrl+→（Windows / Linux）

最佳实践：

  • Tab 适合惯性延续，不适合跨越意图边界。正在写认证逻辑时 Tab 却跳去数据库 schema 改字段，多半是误判，按 Esc。
  • Tab 的最大成本不是按下错误的代码，而是事后 review 它写出的隐性错误。每次接受前扫一眼 diff。

4.2 Inline Edit（Cmd+K）：外科手术式改写

选中代码 → Cmd+K → 输入指令 → 查看 diff → 接受 / 拒绝。

适合：单函数重构、补错误处理、补类型、生成单元测试、补注释。

不适合：让它”重写整个文件并加入 5 个新功能”——超出局部改写的设计目的，应该交给 Agent。

实战 prompt 写法：Inline Edit 的上下文就是选区，指令要把”目标、约束、不做什么”说全：

写法 示例 问题 / 效果
模糊 优化一下 可能改名、可能重排、可能删逻辑
只有目标 改成 async/await 可能顺手改签名、改错误处理方式
目标 + 约束 改成 async/await，函数签名与返回类型不变 行为可预期
目标 + 约束 + 验收 改成 async/await，签名不变；失败时返回 { ok: false, error } 而不是抛异常；不要改动选区外的代码 可以直接对照 diff 验收

4.3 Agent 模式：自主执行

Agent 是默认模式，拥有全部工具：代码搜索、读写文件、执行终端命令、内置浏览器、MCP 工具，并可派生子代理（§7.3）。

使用要点：

  • 给边界：指明涉及的目录、禁止改动的文件、验收命令；
  • 给验收：让它以 pnpm test、pnpm typecheck 的结果作为完成标准；
  • 看检查点：每轮修改都有检查点，结果不对时直接恢复，比追加 prompt”修修补补”更干净；
  • 要清单：在 prompt 末尾要求”最后列出所有修改过的文件”，review 时再用 git status 与 git diff 核对。

4.4 Ask 模式：只读问答

Ask 模式只读不写，适合：

  • 陌生代码库的结构梳理；
  • 需求澄清、方案讨论（§10.3 Step 1、Step 2 都在 Ask 中完成）；
  • 让 AI 对照 spec 检查实现是否偏离。

Ask 的价值在于没有副作用：讨论阶段不会有文件被悄悄改掉。

4.5 Plan 模式：先出计划，再执行

Shift+Tab 在输入框中轮换到 Plan 模式（输入疑似复杂任务的关键词时 Cursor 也会主动建议）。流程是：

  1. agent 提出澄清问题；
  2. 检索代码库收集上下文；
  3. 生成可编辑的实施计划（Markdown，可含 Mermaid 图）；
  4. 你在对话中或直接编辑 Markdown 调整计划；
  5. 点击构建，转入执行。

两个细节：

  • 计划默认保存在用户目录，点击 “Save to workspace” 可以存进仓库，作为 spec 的一部分参与评审；
  • 3.3 起计划可以点击 Build in Parallel：Cursor 识别计划中相互独立的部分，用异步子代理并行执行，有依赖的步骤保持顺序（§9.6）。

官方给出的经验同样适用：执行结果不符合预期时，回滚修改、把计划写得更具体、重新执行，通常比在错误的实现上追加指令更快。

4.6 Debug 模式：基于运行时证据排错

2.2 引入的 Debug 模式面向难以复现的 bug。它不直接猜修复方案，而是提出假设、在代码中插入日志、请你复现问题、根据运行时证据定位根因，修复后再清理插桩。适合：

  • 只在特定数据或时序下出现的问题；
  • 多个模块交互导致、单看代码看不出来的问题；
  • 已经”修了三次还没修好”的问题。

5. 上下文工程：@ 引用、索引与 .cursorignore

核心命题：AI 编码工具的真实瓶颈不是模型，而是上下文。哪些代码、文档、数据进入 prompt、以什么顺序、占多少 token，决定了输出质量的上限。

5.1 索引：Cursor 怎么知道你的项目

截至 2026 年 5 月，Cursor 同时使用两类检索：

  1. 语义索引：本地把代码切块并计算哈希（基于 Merkle 树做增量同步）；代码块上传到服务器计算 embedding，服务端只保存向量与混淆后的文件路径，明文代码在请求结束后不保留；提问时按语义召回相关片段。
  2. Instant Grep（2.1 起）：agent 执行的 grep 类搜索即时返回，适合精确匹配函数名、报错字符串、正则。

索引变慢或失准的常见原因：

  • monorepo 没有配置 .cursorignore，依赖目录和构建产物占满索引；
  • 频繁切换分支后索引尚未追上当前检出（§15.8）；
  • 仓库里有大量生成代码或大文件。

.cursorignore 与 .cursorindexingignore 的区别：

文件 效果 适用
.cursorignore 不进入索引，Agent / Tab / @ 引用也无法读取 凭证、敏感数据、与任务无关的大目录
.cursorindexingignore 只是不进入索引，仍可通过 @ 显式引用 生成代码、第三方 vendored 代码

5.2 @ 引用：精确控制上下文

在输入框输入 @ 会弹出上下文选择器。这是明确告诉 agent”你必须考虑这些”的方式：

引用 用途 典型场景
@文件 / @目录/ 附加文件或整个目录 @docs/specs/canary-release/ 引用整份 spec
@Terminals 附加终端输出 把失败的测试日志交给 agent
@Chats（过往对话） 引用之前对话的上下文 延续上周的设计讨论，不必重新解释
@Commit / @Branch 未提交改动 / 当前分支相对主干的完整 diff 让 agent review 当前改动
@Browser 附加内置浏览器中的页面上下文 前端调试
/技能名 调用 skill（输入 / 而不是 @） /code-review

原则：知道相关文件时用 @ 精确给出；不确定时不要乱塞，让 agent 自己检索——塞进无关文件只会稀释注意力。

5.3 上下文预算管理

  • 看占用：输入框旁的上下文环显示当前窗口占用，点开可以看到按类别拆分的明细（系统提示、工具、Rules、Skills、MCP、对话等，2026-05-06 起提供）。Rules 或 MCP 占比异常高，说明常驻内容需要瘦身。
  • 主动压缩：上下文接近上限时 Cursor 会自动把早期对话压缩为摘要；也可以手动 /summarize（1.6 起）。
  • 开新对话：一个对话只做一件事。跨任务的共识沉淀到 Rules 或 spec 文件，而不是留在聊天记录里。
  • 用子代理隔离噪声：大范围搜索、长命令输出、浏览器操作交给子代理（§7.3），主对话只接收结论。

6. Rules 系统：从 .cursorrules 到 .cursor/rules/*.mdc

核心思想：Rules 是给 AI 的持久化系统提示，是常驻的、声明式的约束。把团队约定、架构原则、命名规范、安全要求写进 Rules，是中大型项目使用 Cursor 的第一项基础工程。流程性的”怎么做”不属于 Rules，应该写成 Skills（§7.2）。

6.1 Rules 的层级

类型 位置 作用范围 适合放什么
Project Rules .cursor/rules/*.mdc，子目录可有自己的 .cursor/rules/ 当前仓库，随代码版本化 架构约定、编码规范、安全基线
User Rules Cursor Settings > Rules 中的纯文本 你本人的所有项目 个人偏好，如回复语言、解释详略
Team Rules 团队后台统一配置（Team / Enterprise） 团队全体成员 公司级合规要求、禁止事项
AGENTS.md 仓库根目录，也支持子目录嵌套 当前仓库，越靠近文件的越优先 多工具共享的项目说明（Codex 等同样读取）
.cursorrules 仓库根目录单文件 — 0.45 起被 Project Rules 取代，新项目不要再用

选择原则：团队约定进 Project Rules 或 AGENTS.md，个人偏好进 User Rules，强制合规进 Team Rules。如果团队同时使用 Cursor、Codex、Claude Code，项目通识写进 AGENTS.md，Cursor 专属的按文件类型生效的细则再放 .mdc。

6.2 .mdc 文件结构

每条 Project Rule 是一个 .mdc 文件：YAML frontmatter 加 Markdown 正文。

Frontmatter 字段：

  • description：一句话说明规则做什么、何时适用，agent 据此判断是否相关；
  • globs：文件路径模式，匹配的文件出现在上下文中时自动附加；
  • alwaysApply：true 表示每次对话都注入；false 表示按 description、globs 或手动 @ 触发。

官方建议单条规则控制在 500 行以内，过长就拆成多条可组合的规则。

6.3 四种激活模式

模式（界面名称） frontmatter 组合 何时注入 适合
Always Apply alwaysApply: true 每次对话 核心原则、安全底线（必须短）
Apply Intelligently alwaysApply: false + description，不写 globs agent 根据 description 判断 某类任务才需要的约定
Apply to Specific Files 写 globs 匹配文件进入上下文时 语言规范、目录规范
Apply Manually 三者都不依赖，需要时 @规则名 手动引用 很少用到的专项规范

一个值得注意的演进：2.4 的 /migrate-to-skills 会把”Apply Intelligently 且没有 globs”的规则转换成 Skills。换句话说，官方的划分是——常驻、声明式的约束留在 Rules；按需发现、带步骤的流程知识放进 Skills。

6.4 一套可直接落地的 Rules 模板

推荐按编号前缀组织，数字决定阅读顺序，也方便 review：

.cursor/rules/00-core-principles.mdc

.cursor/rules/10-typescript.mdc

.cursor/rules/40-security.mdc

6.5 Rules 的反模式

❌ 反模式 1：把规范当规则写

这是规范，不是规则。规范放 docs/specs/，规则放 .cursor/rules/。规则是给 AI 的行为约束，规范是给人和 AI 共同遵守的工程契约。混淆的后果：

  • 规范变化时忘了改规则；
  • 规则文件臃肿到 agent 读不完；
  • 规范走 PR 评审，规则改了却没人审。

❌ 反模式 2：超长 alwaysApply 文件

alwaysApply: true 的内容会注入每次对话。官方建议单条规则不超过 500 行；而对 alwaysApply 规则，更应该把所有常驻规则的总量压到最小——常驻内容越长，真正与任务相关的上下文越少。§5.3 的上下文明细可以直接看到 Rules 占了多少 token。

❌ 反模式 3：用否定句堆砌

否定句只告诉模型”不做什么”，没告诉它”该做什么”。优先正向陈述：

真正的红线（如”禁止修改 .env”）才保留否定句，并集中放在”禁止行为”小节。

规则写”使用 Drizzle ORM”，代码库里 60% 还在用 Prisma——agent 会在两种写法之间摇摆。先让代码库与规则一致（或在规则中写明迁移状态和新旧代码的边界），再要求 AI 守规则。

6.6 Rules 的演进：从 0 到团队级

  • 第 0 天：复制 §6.4 的模板，按项目修改；
  • 第 1 周：review 中每发现一次 AI 违反团队约定，就把约定固化进对应的 .mdc；
  • 第 2 周：把遗留的 .cursorrules 拆成多个 .mdc，按文件类型和目录设置 globs；
  • 第 1 个月：把”按需使用的流程型规则”用 /migrate-to-skills 迁移为 Skills；定期删除过时条目、合并重复条目；
  • 第 2 个月：规则修改走 PR，至少一位 reviewer。

7.3 Subagents：用独立上下文处理子任务（2.4+）

Subagent 是主 agent 可以委派任务的专用 agent：它从干净的上下文开始，只接收主 agent 传入的任务说明，独立完成后把结果返回。价值在于把噪声留在子代理里，主对话只看结论。

内置子代理（无需配置，agent 自动使用）：

Explore 检索与分析代码库 搜索产生大量中间结果；默认使用更快的模型，可并行多路搜索
Bash 执行一串 shell 命令 命令输出冗长，隔离后主 agent 专注决策
Browser 通过浏览器工具操作页面 DOM 快照和截图噪声大，子代理只回传相关结果

8. MCP 生态：把 Cursor 接入真实工具链

MCP = Model Context Protocol，由 Anthropic 提出、已被主流 AI 编码工具支持的开放协议，让 agent 通过统一接口接入外部工具与数据。Cursor 1.0 起支持 MCP 一键安装，2.5 起 MCP 也可以随插件分发。

8.1 MCP 是什么、为什么重要

传统插件机制是每个 IDE 各自定义扩展 API，工具厂商要写 N 套适配。MCP 把接口标准化为三类能力：

  • Tools：可调用的函数（如 create_issue、query）；
  • Resources：可读取的数据（如 schema、文档片段，1.6 起 Cursor 支持）；
  • Prompts：可注入的提示模板。

Cursor 作为 host，连接 MCP server——本地以 stdio 方式启动进程，远程通过 SSE 或 Streamable HTTP 连接——agent 自动发现 server 暴露的工具并按需调用。

对工程师的真实价值：

  • GitHub：agent 读 issue、看 PR 评论、提交 PR，不用切窗口；
  • 浏览器：agent 打开本地页面、点击、截图，验证前端修改；
  • 文档：按库和版本拉取最新 API 文档，减少”用了已废弃接口”；
  • 数据库（只读）：agent 查询真实 schema 与样例数据，不必手动粘贴；
  • 设计稿：读取设计稿的真实颜色、间距与组件结构。

9. Cursor 3 进阶：Agents Window、/worktree、/best-of-n、Cloud Agents

Cursor 3.0（2026-04-02）的核心变化是从单 agent 时代进入多 agent 编排时代。这一章是中大型项目的差异化能力区。

9.1 Agents Window：并行编排的指挥台

Cmd+Shift+P → Agents Window 打开。它与经典 IDE 是两个视图，可以随时切回，也可以同时打开：

  • 经典 IDE：日常编辑、单文件深度工作、多文件分屏；
  • Agents Window：同时运行和监控多个 agent，覆盖本地、worktree、云端和远程 SSH 四种环境。

Agents Window 的关键能力

  • 多环境并行：同一界面管理本地、worktree、Cloud、SSH 上的 agent；
  • Agent Tabs：多个对话并排或网格查看（编辑器中同样可用）；
  • Design Mode：在内置浏览器里直接标注 UI 元素，交给 agent 修改；
  • 从执行到 PR 一条线：agent 完成 → review diff → 提交 PR；3.3 起内置 PR Review 界面，可以在同一处查看评审线程、提交历史和文件改动；
  • /multitask（2026-04-24 起）：把请求交给多个异步子代理并行处理，而不是排队等待。

Design Mode 实战

  1. 让 agent 启动本地 dev server；
  2. 在 Agents Window 的内置浏览器打开页面；
  3. Cmd+Shift+D 进入 Design Mode；
  4. Shift + 拖拽框选要改的区域，或 Option + 点击把元素加入输入框；
  5. Cmd+L 把选中元素加入对话，例如”把这个按钮改成圆角，使用品牌主色”；
  6. agent 拿到的是具体的 DOM 节点、样式类与层级关系，而不是一张需要猜测的截图。

9.2 /worktree：每个 agent 一个隔离工作树

git 的 worktree 允许同一个仓库同时存在多个独立检出。3.0 把它做成了编辑器中的 /worktree 命令：以 /worktree 开头的任务，这个对话后续的所有修改都在一个独立检出中进行，主检出不受影响。

完成后的三种去向：

  • 直接在 worktree 中提交并推送分支、开 PR；
  • 用 /apply-worktree 把改动带回主检出进行测试；
  • 用 /delete-worktree 放弃并清理。

为什么这是关键能力：

  • 并行无冲突：两个 agent 同时改不同模块，互不踩脚；
  • 实验隔离：失败的尝试不污染主检出；
  • 安装与构建不打扰当前分支：依赖安装、构建、测试都发生在隔离目录里。

典型用例：

支持三个键：setup-worktree-unix、setup-worktree-windows 和通用兜底的 setup-worktree；值可以是命令数组，也可以是相对 worktrees.json 的脚本路径。$ROOT_WORKTREE_PATH 指向主检出目录。setup 出问题时，在输出面板选择 Worktrees Setup 查看日志。

9.3 /best-of-n：让多个模型比赛

Cursor 为每个模型创建独立的 worktree，并行执行同一任务，然后对比结果。它只负责比较，不会替你合并：选出最好的一份后，在对应 worktree 中提交，或用 /apply-worktree 带回主检出。

什么时候用：

  • 调试类任务（如偶现的测试失败），事先无法判断哪个模型更擅长；
  • 重要重构，想看不同的实现思路；
  • 团队评估新模型时做对照。

成本提醒：N 个模型就是 N 倍用量。日常不要滥用，留给关键决策。

9.4 Cloud Agents：把长任务交给云端

Cloud Agents（前身是 1.0 的 Background Agent）运行在 Cursor 云端的隔离 VM 中。2026-02-24 起支持 computer use：agent 可以在自己的 VM 里启动应用、操作界面、自测改动，并附上截图、录屏和日志作为交付证据。

典型用例：

  • 大范围、机械性的迁移（如全仓把 v0 接口调用迁到 v1）；
  • CI 失败的初步诊断与修复 PR；
  • 夜间批量处理 issue 队列（配合 2026-03-05 推出的 Automations 定时或事件触发）。

触发方式：

  • Agents Window 中新建 agent 时选择 Cloud；
  • 从 Slack、GitHub 等集成中触发；
  • 用 Cursor SDK 编程触发（§9.5）。

运行环境：云端 agent 需要能安装依赖、跑测试的环境。3.4（2026-05-13）起支持多仓库环境与”环境配置即代码”，把环境定义随仓库版本化，而不是在界面里手工配置。

成本与权限治理：

  1. 在团队后台为成员设置支出上限与告警（2026-05-04 起提供模型访问控制、软性支出上限与智能告警）；
  2. 用团队设置收紧云端权限，例如 3.0 起可以把团队 secrets 的增删改限制给管理员；
  3. 十分钟内能在本地完成的任务不必上云。

9.5 Cursor CLI 与 Cursor SDK

Cursor CLI

2.4 起终端命令统一为 agent，模式、Rules、Skills、Subagents、MCP 与编辑器共用同一套配置；在 CI 中通过 CURSOR_API_KEY 环境变量认证。

用途：

  • CI/CD 自动化（PR 自动审查、失败测试自动修复）；
  • 不离开终端的工作流；
  • 批量处理多个仓库。

Cursor SDK（2026-04-29 公测）

SDK 用与桌面端、CLI 相同的运行时和 agent 框架，让你用几行 TypeScript 驱动 agent，可以在本机运行，也可以在 Cursor 云端的专用 VM 上运行；按标准的 token 用量计费。

用途：

  • 内部工具：在内部平台里让非开发角色发起受控的 agent 任务；
  • 流水线深度集成：比 CLI 更细粒度地消费事件流；
  • 批量任务编排：按队列创建 agent、收集结果。

9.6 /multitask 与 Build in Parallel（3.3）

2026-05-07 的 3.3 版本把”并行”推进到计划执行层：

  • Build in Parallel：Plan 模式生成计划后点击该按钮，Cursor 识别计划中相互独立的部分，用异步子代理同时执行，有依赖的步骤保持顺序；
  • /multitask 进入编辑器：此前只在 Agents Window 可用，现在编辑器中也能把请求分派给异步子代理；
  • Split changes into PRs：多任务并行后，用内置快捷操作把改动按逻辑切分成多个 PR——默认切成相互独立的 PR，先创建备份快照，并给出切分方案请你确认；
  • Skills 固定为快捷按钮：常用 skill 钉在输入框旁。

执行示意：

并行的前提是计划本身写清了依赖。依赖写错，并行只会更快地制造冲突——这正是 §10 要求先写 tasks.md 的原因。

10. 规范驱动开发（SDD）：让 Cursor 严肃服务于中大型项目

这是全文最重要的一章。

10.1 vibe coding 在中大型项目为什么必败

随着项目规模增大，单纯的对话驱动开发会遇到：

  1. 回归不可控：AI 改 A 时不知道 B 也依赖这块；
  2. 架构腐化：每次”快速实现”都在积累技术债；
  3. 知识丢失：决策只存在于聊天记录里，人一走就失传；
  4. review 不可信：reviewer 不知道 AI 当时为什么这么写；
  5. 测试覆盖虚高：AI 写的测试常常只是镜像实现，恒真；
  6. 责任模糊：出了 bug，”AI 写的”不是合规理由。

SDD 的核心主张：把”AI 应该做什么”变成可读、可审、可版本控制的规范文档。代码是规范的实现，不是规范的替代品。

10.2 SDD 在 Cursor 中的落地骨架

关键原则：

  1. docs/specs/<feature>/ 是该特性的单一事实来源；
  2. AI 做该特性时，通过 @docs/specs/<feature>/ 引用完整 spec；
  3. 实现完成后，spec 与代码一起提交；
  4. spec 变更走 PR，代码评审 = spec 评审 + 代码评审。

10.4 Cursor 在 SDD 中的局限

要诚实：Cursor 是 SDD 的执行环境，不是 SDD 系统。它的天然不足：

  1. 没有 spec 生命周期管理：spec 改了，旧代码是否仍然合规，Cursor 不会自动追踪；
  2. Rules 不等于 spec：Rules 是 AI 行为约束，spec 是工程契约，混用会造成审计真空；
  3. 会话不延续：跨会话的 spec 上下文需要每次 @ 引用；
  4. 没有自动一致性校验：实现偏离 spec 时不会主动报警。

补偿方案：

  • 把关键不变量（如”决策必须确定性”）同时固化进 .cursor/rules/，每次生成时都有提醒；
  • 在 CI 中加入 spec 一致性检查：把 spec 与 diff 交给 agent -p 或 codex exec，要求输出结构化的偏离清单；
  • 需要更严格的生命周期管理时，引入 OpenSpec、Kiro 这类专门的 SDD 工具，Cursor 只做执行层。

10.6 Spec Kit 与 BMAD-Method：辅助框架

如果想更进一步，可以借助专门的 SDD 框架。

GitHub Spec Kit（轻量）

初始化后项目里会出现一组 /speckit.* 命令，流程是：

  1. /speckit.constitution：定义项目”宪法”（编码规范、测试策略、架构原则）；
  2. /speckit.specify：描述意图，生成 spec；
  3. /speckit.clarify：针对 spec 中的模糊点追问；
  4. /speckit.plan：生成技术实施计划；
  5. /speckit.tasks：拆分任务；
  6. /speckit.analyze：检查 spec、plan、tasks 之间的一致性；
  7. /speckit.implement：按任务执行。

适合：从 0 到 1 的中小型项目，以及想低成本引入 SDD 的团队。

BMAD-Method（重量级）

BMAD 用一组角色化的 agent 模拟完整研发团队：业务分析、产品经理（写 PRD）、架构师、UX、Scrum Master（拆 story）、开发、测试架构等。各角色之间通过 Markdown 文档移交上下文，每个角色有明确的输入输出契约。

适合：从需求到上线都希望显式建模的中大型新项目。

不适合：存量代码库的小步迭代，以及不愿承担角色与文档学习成本的团队。

10.7 SDD 检查清单（每个新特性）

  • requirements.md 已写并评审
  • design.md 已写并评审（含 Mermaid 图）
  • 相关 ADR 已链接或新建
  • tasks.md 已生成并人工调整依赖
  • .cursor/rules/ 是否需要新增条目（关键不变量）
  • 独立任务在独立 worktree 实现
  • 每个任务有单元测试，覆盖 design.md 列出的分支
  • /code-review 通过，spec-verifier 无未解释的偏离
  • PR 描述链接到 spec
  • 合并后 spec 与代码一起进入主干

12. Cursor + Codex 协作开发最佳实践

核心问题：Codex 和 Cursor 都是 AI 编码工具，为什么要一起用？Codex 擅长终端内的长任务、非交互批处理和 CI 集成，Cursor 擅长交互式开发、可视化 review 与多 agent 编排。组合使用覆盖更完整的场景。

Codex 是 OpenAI 的编码 agent，截至 2026 年 5 月有四种形态：

15. 反模式与陷阱

按类别整理常见的坑，建议在团队内部 wiki 中长期维护。

15.1 Prompt 反模式

❌ “改一下” / “修一下” / “优化一下”

模糊指令的输出永远是赌博：可能改名、可能重构、可能删掉一半。

改进：写明 what / why / how-to-verify：

❌ “尽量……” / “如果可以……”

模型会把”尽量”理解为”可做可不做”。

改进：明确强度：

❌ 一次性塞 10 件事

“加这个接口、改那个 schema、补几个测试、顺便格式化日志、README 也更新一下”。最后总有一两件被遗漏，而且不会被报告。

改进：1~3 件为一批，每批 review 后再下一批；或写成 tasks.md 交给 Plan 模式。

❌ 不给样例

“写一个数据校验函数”——AI 不知道团队用 zod、valibot 还是手写。

改进：给出模仿对象：

15.2 Cursor 配置反模式

❌ 不配 .cursorignore

索引慢、token 浪费、敏感文件可能进入上下文。

改进：从 §3.3 的模板开始按项目调整，并记住它挡不住终端与 MCP 工具的读取。

❌ alwaysApply 规则过多过长

每次对话都注入大量规则，挤占任务上下文，agent 注意力反而涣散。

改进：alwaysApply 只留核心原则和安全底线，其余改为按 globs 附加，或迁移为 Skills。

❌ 不区分 User Rules 和 Project Rules

个人偏好（例如”回复用中文”）写进 Project Rules，整个团队都受影响。

改进：个人偏好进 User Rules；团队约定进 .cursor/rules/ 或 AGENTS.md。

❌ Rules 互相矛盾

两条规则都常驻，一条要求 A 写法，一条要求 B 写法，agent 行为不可预测。

改进：定期审计规则，删除或合并冲突项；规则修改走 PR。

15.3 Agent 使用反模式

❌ 在生产仓库使用 Run Everything

agent 执行 git clean -fdx，把未跟踪的本地文件一起清掉。

改进：Run Everything 只用于可重置的隔离环境；生产仓库用 Auto-Run in Sandbox 或 Ask Every Time，并用 §7.4 的 hook 拦截高危命令。

❌ 超长会话

对话已经很长，后半段 agent 忘了开头的约束。

改进：上下文环接近满时 /summarize 或开新对话；需要长期遵守的约束写进 Rules 或 spec。

❌ Cursor agent 和 Claude Code 同时改同一个文件

git 也救不了。

改进：一文件一时刻一 agent，不同 agent 用不同 worktree。

❌ 相信 agent 的”测试通过”

agent 说”All passed”，实际跑的是缓存结果，或者只跑了一个文件。

改进：最终验证永远自己跑一遍。

15.4 MCP 反模式

❌ 给 agent 生产数据库的写权限

存在 prompt injection 风险，也存在 agent 误判的风险。

改进：生产数据只给只读凭证；写操作走人工确认或根本不接入。

❌ 装一大堆 MCP server

工具定义挤占上下文，agent 选错工具的概率上升。

改进：常驻 3~5 个高频 server，其余需要时再启用。

❌ 直接使用未经审查的社区 MCP server 或安装链接

CVE-2025-54136（MCPoison）表明：MCP 配置在首次批准后被悄悄替换为恶意命令，旧版本不会再次提示；CVE-2025-64106 表明：构造的深链可以在安装对话框里隐藏真实命令。两者均已修复，但风险模式仍然存在。

改进：安装前看源码、看维护者与更新记录；优先官方 server；项目级 mcp.json 的改动走 review。

15.5 SDD 实施反模式

❌ 写了 spec 但不维护

spec 成了”半年前需求评审的遗留物”，代码早已改了。

改进：spec 改动走 PR；合并前 spec 与代码必须同步更新。

❌ spec 详细到等于代码

spec 写成伪代码，等于先用文字写一遍代码再让 AI 翻译。

改进：spec 描述 what、why 与不变量，代码负责 how。

❌ Rules、spec、CLAUDE.md 各写一遍同一条约束

改的时候必漏一处。

改进：单一来源 + 引用。

❌ 不做 ADR

半年后没人记得为什么这么设计。

改进：每个架构级决策一份 ADR，几段话就够。

15.6 模型选择反模式

❌ 任何任务都用最贵的模型

额度很快耗尽，简单任务也没有变得更好。

改进：日常 Auto 或 Composer 2.5，复杂任务再切 Claude Opus 4.7 或 GPT-5.5。

❌ 永远不切模型

任务明显适合另一个模型，却一直用同一个。

改进：按 §2.3 的表格根据任务切换；拿不准时用 /best-of-n。

❌ 用快模型做架构设计

省了钱，设计漏洞百出。

改进：架构、设计、关键算法用最强模型；实施、测试、文档用快模型。

15.7 团队协作反模式

❌ 每个开发者各自维护 Rules

规则各不相同，代码风格漂移。

改进：Rules 入库、走 review；公司级要求用 Team Rules 下发。

❌ 不培训

新人一上来就用 Agent 模式大范围改代码。

改进：内部 wiki 写明 Tab → Inline Edit → Ask → Agent 的渐进路径，新人先用前两个。

❌ MCP 凭证散落在个人电脑上

每人本地一份 token，离职时没人记得吊销。

改进：凭证放进统一的密钥管理服务，通过环境变量注入；定期轮换；离职流程包含吊销。

❌ 不监控 AI 工具成本

月底账单超出预期，没人说得清钱花在哪。

改进：在 Cursor、Anthropic、OpenAI 的后台都开启预算告警，每月回顾用量分布（§16.3）。

15.8 容易被忽视的隐性陷阱

⚠️ 索引与当前分支不一致

切换分支后索引还没追上，agent 引用了不存在的文件。

改进：切分支后等索引完成再开始 agent 任务。

⚠️ monorepo 中规则的作用范围

改进：核心规则放仓库根的 .cursor/rules/；子包的规则放在子包自己的 .cursor/rules/ 或 AGENTS.md 中——嵌套的 AGENTS.md 在处理该目录的文件时生效，越具体的说明优先级越高。

⚠️ Tab 接受了不该接受的代码

Tab 提示太快，下意识接受了一大段错误代码。

改进：把 Tab 当”建议”而不是”自动完成”，接受前扫一眼 diff。

⚠️ 自动更新打断正在运行的任务

改进：关键任务期间推迟重启更新；或把长任务交给 Cloud Agents。

⚠️ agent 报告完成却没说改了哪些文件

改进：prompt 末尾要求”最后列出所有修改过的文件”；review 时永远 git status + git diff。

16. 团队协同、安全与成本治理

面向 tech lead 与平台架构师。

16.1 团队上车路径

Step 1：私下试点（1~2 周）

  • 1~2 名资深工程师个人订阅；

  • 整个小组（5~10 人）开团队计划试用；
  • 共同制定 .cursor/rules/、skills 与 hooks；
  • 用 DORA 指标和缺陷率衡量 PR 速度与质量变化；
  • 收集每个人的痛点与省时点。

Step 3：组织级铺开（1~2 个月）

  • 有 SSO / SCIM / 审计需求时申请 Enterprise；
  • 强制开启 Privacy Mode；
  • 统一 MCP 凭证管理与团队插件分发（团队 Marketplace）；

  • 制定使用规范：哪些代码不适合交给 AI、谁可以使用 Cloud Agents、支出上限。

Step 4：持续治理

  • 每月审计 Rules 与 hooks；
  • 每季度回顾成本；
  • 工程师定期分享高效用法。

16.2 安全治理清单

数据安全

  • 全员开启 Privacy Mode（团队计划由管理员强制）
  • .cursorignore 覆盖 secrets/、.env*、*.pem、*.key
  • MCP 凭证最小权限（数据库只读、token 限定范围）
  • Workspace Trust 保持开启
  • Rules、hooks、mcp.json 的改动必须经过 PR 评审
  • AI 生成的代码必须经人工 review 才能合并

凭证管理

  • 凭证由密钥管理服务或系统钥匙串注入，而不是明文 .env
  • 定期轮换 token
  • Cursor 账号接入企业 IdP（SSO）

合规

  • 列入 AI 工具治理清单（供 SOC 2 / ISO 27001 审计）
  • 与法务确认数据出境与隐私合规要求
  • Cloud Agents 处理业务数据前确认数据驻留与留存策略

漏洞跟踪

  • 订阅 Cursor changelog 与 GitHub Security Advisories
  • MCP 与插件来源设白名单
  • 安全公告发布后及时升级

  • 团队后台的用量分析页查看本月用量、按成员与模型的分布；
  • 2026-05-04 起可以为团队设置模型访问控制（限制可用模型）、软性支出上限与智能告警；
  • 各家模型厂商后台（Anthropic、OpenAI）同样开启预算告警，覆盖 Claude Code 与 Codex 的 API 用量。

优化策略

  • 模型路由：日常 Auto / Composer 2.5，关键任务再用最强模型；
  • 先计划：复杂任务先用 Plan 模式，减少 Agent 反复试错；
  • Cloud Agents 设上限：短任务本地跑，长任务上云并设支出上限；
  • /best-of-n 节制：N 倍用量，只在关键决策时使用；
  • Bugbot 审查强度按需设置：2026-05-11 起 Bugbot 支持设置 effort 等级，不是所有仓库都需要最高强度的审查。
