1. 写在前面：从 Vibe Coding 到 Agentic Engineering

1.1 为什么读这份指南

能熟练地把”想要一个 XX 功能”丢给 AI、来回调几次拿到能跑的代码，说明 vibe coding 阶段已经过关。但项目一旦超过单文件、单个会话、需要多人协作或长期维护，就会反复遇到同一类问题：

  • CLAUDE.md 里写了的硬性规则，模型仍会在长会话里偶尔忽略——提示词本质上是建议，不是强制。
  • 同一个错误被反复修复，因为结论只存在于某次对话里，没有沉淀成文件。
  • 大型重构中途丢失上下文，后半程的改动与前半程的决策对不上。
  • 修一个 bug 引入两个新 bug，因为没有”验证关卡”。
  • 会话越长输出越飘，上下文被探索过程的噪声占满。

Agentic Engineering 解决的是这些工程问题：把 Claude Code 当作团队成员而非聊天框——写规范、给工具、设质量门、安排子代理分工，再让它执行。人的角色从”打字员”变成”架构师 + 评审人”。

1.2 三个阶段对应的技能跃迁

阶段 典型做法 瓶颈 需要掌握的能力 对应章节
Vibe Coding 一句需求 → 看结果 → 追加修正 单次会话可控，跨会话和多文件时失控 基本对话、@ 引用文件、审 diff 2、3
结构化协作 有 CLAUDE.md、先让它出计划再动手 规则靠自觉遵守，质量依赖当次会话状态 CLAUDE.md 分层、plan mode、权限配置、Skills 4、5.1–5.2
Agentic Engineering 规格与计划落成文件，子代理按任务实施，自动化质量门把关 需要前期投入规范与工具链 Subagents、Hooks、MCP、SDD 四阶段、上下文预算 5.3–5.6、6、7、9

判断自己处在哪个阶段的简单方法：关掉当前会话、第二天新开一个，Claude 能否仅凭仓库里的文件接着干。能，就已经进入第三阶段。

2. Claude Code 核心架构与心智模型

2.1 Claude Code 到底是什么

官方定义：Claude Code 是一个 agentic coding 工具，能读取代码库、跨文件编辑、执行命令并与开发工具集成。它有四种使用形态：

  1. 终端 CLI：能力最完整，最适合工程化与脚本化（claude -p）。
  2. IDE 扩展：VS Code（含 Cursor 等衍生编辑器）与 JetBrains，提供 inline diff、选区引用与计划评审。
  3. 桌面应用：多会话并行与可视化 diff。
  4. Web：claude.ai/code，在云端环境运行长任务，不依赖本地机器。

它们读取同一套仓库内配置（CLAUDE.md、.claude/ 目录、.mcp.json），所以团队把配置提交进 Git 后，在哪种形态里都得到一致行为。本地会话还可以通过 Remote Control 从手机或浏览器继续操作。

2.2 心智模型一：Agent + Toolset + Loop

不要把 Claude Code 想成”会写代码的聊天机器人”，而是：一个拥有 Shell、文件系统、网络等工具的 Agent，在”读 → 想 → 改 → 验证”的循环中工作，直到任务完成或被叫停。

flowchart TD
    P[用户 Prompt] --> C[加载 CLAUDE.md、rules 与技能清单]
    C --> T[制定计划<br/>plan mode 下显式输出]
    T --> U[调用工具<br/>Read / Edit / Write / Bash / Grep / MCP]
    U --> H{PreToolUse hook}
    H -- exit 2 拦截 --> T
    H -- 放行 --> R[工具执行]
    R --> PH[PostToolUse hook]
    PH --> D{任务完成?}
    D -- 否 --> T
    D -- 是 --> S{Stop hook}
    S -- exit 2 要求继续 --> T
    S -- 通过 --> V[人工审查 diff]

理解这个循环，才能精准干预：CLAUDE.md 决定”读什么”，Skills 决定”用什么方法”，Hooks 决定”允不允许、做没做完”，Subagents 决定”由谁来做”。

2.3 心智模型二：六大扩展点

扩展点 解决什么 谁来触发 常驻上下文成本 详见
Slash Commands 把重复输入的指令固化成 /name 用户 无，调用时注入 5.1
Skills 可复用的领域做法，附带脚本与参考资料 模型按 description 判断，或用户 /name 仅 name 与 description 5.2
Subagents 把重型探索或专职任务放进独立上下文 主会话委派 无，结果回传主会话 5.3
MCP Servers 连接数据库、GitHub、浏览器等外部系统 模型调用工具 工具定义，超阈值时按需加载 5.4
Hooks 在生命周期事件上执行确定性脚本 事件 默认为零 5.5
Memory CLAUDE.md 与 .claude/rules/ 提供项目事实 启动或读到匹配文件时 全文计入 4.2、4.3、5.6

错配会让维护成本失控：把格式规则写进 CLAUDE.md（应交给 hook），把一次性的探索写成 Skill（应交给子代理），都是常见例子。

2.4 心智模型三：上下文是稀缺资源

无论模型多强，上下文窗口都是昂贵的稀缺资源。Opus 4.7 原生支持 1M token 窗口，但窗口大不等于可以随意填：

  • 系统提示、工具定义、CLAUDE.md、rules、技能清单在对话开始前就已占用一部分，用 /context 可以看到按类别拆分的占用。
  • 长上下文里的早期指令更容易被稀释；探索过程的文件内容、命令输出会迅速挤占空间。
  • 接近上限时 Claude Code 会自动压缩（compact），压缩是有损摘要，细节会丢。

直接的工程含义：

  • CLAUDE.md 短而精，只放每次会话都必须知道的事实。
  • 重型探索交给 Subagent，它有独立窗口，主会话只收结论。
  • 长会话不如多个有焦点的短会话，用规范文件做跨会话的持久记忆。
  • @ 引用大文件会把全文灌进上下文，改为告诉 Claude”遇到 X 时去读哪个文件”。

4. 核心配置：CLAUDE.md、settings.json 与权限

4.1 配置层级与文件位置

settings 的优先级从高到低：托管设置（managed）> 命令行参数 > 项目本地（settings.local.json）> 项目共享（settings.json）> 用户级。标量字段按此覆盖；permissions.allow 这类列表字段跨层合并，而不是覆盖。

4.2 CLAUDE.md：项目记忆文件

CLAUDE.md 在每次会话开始时加载，是 Claude 了解项目的第一入口。写法要点：

  • 控制长度：官方建议单个 CLAUDE.md 控制在 200 行以内，越长越占上下文、遵循度越低；社区实践中不少团队把根文件压到 60 行左右。超出的内容拆到 .claude/rules/ 或子目录 CLAUDE.md。
  • 写硬性事实与约束，不写人格指令（”你是一名资深工程师”几乎不改变行为）。
  • 写”为什么”：反直觉的决策要写明原因，否则模型会”好心地”改回常规做法。
  • 格式规则交给工具：有 formatter 就让 PostToolUse hook 去跑，不在 CLAUDE.md 里描述缩进与引号；没有 formatter 时，具体的”用 2 空格缩进”才值得写。

4.3 .claude/rules：路径作用域规则

CLAUDE.md 适合”全项目通用的事实”，而很多规则只对部分文件有效。.claude/rules/ 下的 Markdown 文件用 paths frontmatter 限定作用范围：

4.4 settings.json：权限与行为控制

项目级 .claude/settings.json 示例：

权限规则的要点：

  • 评估顺序是 deny → ask → allow，先命中者生效，与规则写得多具体无关。宽泛的 deny 会压过更具体的 allow。
  • 通配符前的空格有意义：Bash(ls *) 不匹配 lsof，Bash(ls*) 会匹配。Bash(git log *) 也匹配不带参数的 git log。
  • deny 不是安全边界：Bash 规则匹配的是命令文本，Bash(rm -rf *) 拦不住 rm -r -f。必须 100% 生效的拦截放到 PreToolUse hook（见 5.5），或使用沙箱。
  • 默认模式下文件编辑本来就会询问，不必把 Edit、Write 写进 ask。

attribution.commit 设为空字符串会去掉提交信息里的 Claude 署名。这类要求放在 settings.json 里由程序执行，比写进 CLAUDE.md 让模型”记得”可靠得多。

4.5 启动模式速查

权限模式在会话中用 Shift+Tab 循环切换，启动时用 --permission-mode 指定：

模式 行为 适用场景
default 编辑文件、执行未放行命令前询问 日常开发
acceptEdits 自动接受工作目录内的文件编辑 计划已评审、进入实施阶段
plan 只读探索，产出计划，不改文件 Specify 与 Plan 阶段
auto 后台分类器审查命令与敏感写入，替代逐条确认（2026-03-24 起研究预览，v2.1.111 起进入 Shift+Tab 循环） 长时间实施、减少打断
bypassPermissions 跳过所有权限检查，等同 --dangerously-skip-permissions 仅限一次性容器或沙箱

5. 六大扩展机制深度剖析

5.1 Slash Commands：注入预制 Prompt

一句话：/name 把一段预写的 Prompt 注入当前会话。用户主动触发、共享当前上下文、成本低。

2026-01 起自定义命令已并入 Skills：.claude/commands/<name>.md 与 .claude/skills/<name>/SKILL.md 都会生成 /name，旧的命令文件继续可用；新写的建议直接用 Skill 形式，以便附带脚本和参考文件。

示例 .claude/commands/recap.md：

调用：会话中输入 /recap。

判断标准：同样的指令一天里输入超过一次，就该固化成命令。典型场景是 PR 摘要、技术债盘点、会话交接、发版前检查。

5.2 Skills：渐进披露的领域知识包

一句话：Skill 是一个文件夹，包含 SKILL.md（YAML frontmatter + 指令）以及可选的脚本与参考资料。会话中常驻的只有 name 与 description；模型判断相关时才加载 SKILL.md 正文，正文里引用的参考文件再按需读取。

文件位置：.claude/skills/<name>/SKILL.md 或 ~/.claude/skills/<name>/SKILL.md。

常用 frontmatter 字段：

字段 作用
name / 菜单中的名称，缺省取目录名
description 触发条件。写”什么时候该用我”，而不是功能摘要
allowed-tools 调用该技能的这一轮中免确认的工具
disable-model-invocation 设为 true 后只允许用户手动 /name 调用，适合部署、发版这类有副作用的流程
context + agent context: fork 让技能在分叉的子代理中运行，主上下文只看到结果；agent 指定子代理类型

Skills 与 CLAUDE.md 的关键差别

维度 CLAUDE.md / rules Skills
内容性质 项目事实与约束（是什么、不许做什么） 做法与流程（怎么做）
加载时机 启动即加载；带 paths 的规则读到匹配文件时加载 常驻 description，触发时加载正文
上下文成本 全文计入 平时只有一两行
可附带内容 只有文字 脚本、模板、参考文档
触发方式 无需触发 模型自动判断或用户 /name
典型内容 技术栈、目录约定、禁止事项 迁移步骤、发版流程、代码评审清单

经验法则：如果一段说明只在做某类任务时才有用，就不该放进 CLAUDE.md。

5.3 Subagents：独立上下文的专职助手

一句话：Subagent 是一份带 frontmatter 的 Markdown 定义，主会话通过 Agent 工具（v2.1.63 之前叫 Task 工具）把任务委派给它。它有独立的上下文窗口、可限定的工具集与模型，只把结论交回主会话。

文件位置：.claude/agents/<name>.md 或 ~/.claude/agents/<name>.md，也可以在会话中用 /agents 交互式创建。

示例 .claude/agents/code-reviewer.md：

frontmatter 里 tools 限定可用工具（评审代理不给 Edit，天然只读），model 可取 sonnet、opus、haiku 或 inherit。此外还有 disallowedTools、isolation: worktree（在临时 git worktree 中运行）、memory（跨会话记忆作用域）等字段。

调用方式：让主会话自行委派，或显式输入 @agent-code-reviewer。

Subagent 的典型场景

场景 为什么用子代理 配置要点
大范围代码探索、调研 探索过程的文件内容不污染主上下文 只读工具；可用 Haiku 降本
代码评审、安全审计 与实现者隔离，避免”自己审自己” 不给 Edit/Write；明确输出格式
按计划逐任务实施 每个任务一个干净上下文，互不干扰 输入只给本任务与相关文件
并行改动互不相关的模块 并发执行缩短总时长 isolation: worktree 避免文件冲突
规格或计划的独立审阅 用新视角挑出遗漏与矛盾 只读；以 spec.md 为唯一依据

反例：一个只需两三步就能完成的小修改不值得委派，子代理启动与回传摘要本身有开销，且主会话看不到中间过程。

5.4 MCP：连接外部系统

一句话：MCP（Model Context Protocol）server 把外部系统包装成工具，让 Claude 能查 GitHub issue、读数据库、驱动浏览器。

三种作用域：

作用域 生效范围 是否与团队共享 存储位置
local（默认） 仅当前项目、仅本人 否 ~/.claude.json
project 当前项目 是，随仓库提交 项目根目录 .mcp.json
user 本人所有项目 否 ~/.claude.json

添加方式：

团队共享时写进 .mcp.json，凭据用环境变量展开，不把明文令牌提交进仓库：

项目级 .mcp.json 中的 server 首次加载时需要本人确认批准，防止克隆一个仓库就自动连上陌生服务。

上下文成本：2026-01 起 MCP Tool Search 默认开启，工具描述超过上下文窗口 10% 时自动转为按需加载，”装了 MCP 就吃掉大量上下文”的问题已明显缓解。但每个 server 仍是一个常驻进程加一份凭据，数量控制依然必要。

安全要点：数据库类 MCP 只接只读账号；远程 MCP 的端点属于谁、数据流向哪里，要像评估第三方 SaaS 一样评估；会话中用 /mcp 查看连接状态与认证。

5.5 Hooks：确定性的生命周期控制

一句话：Hook 在固定事件上执行脚本（或发 HTTP 请求），不依赖模型”记得”，适合必须 100% 生效的规则。

常用事件：

事件 触发时机 典型用途 exit 2 的效果
SessionStart 会话启动、/clear、压缩后 注入动态上下文（当前分支、待办） 不阻断
UserPromptSubmit 用户提交 prompt 后、模型处理前 拦截含敏感信息的输入、补充上下文 拒绝该 prompt
PreToolUse 工具调用前 拦截高危命令、保护敏感路径 阻止本次工具调用
PermissionRequest 弹出权限确认时 按自定义逻辑自动批准或拒绝 不靠退出码，用 JSON 的 decision 字段表达
PostToolUse 工具成功执行后 格式化、lint、类型检查 把 stderr 反馈给 Claude
Stop 主代理准备结束回复时 跑测试、检查验收清单 阻止结束，让 Claude 继续
SubagentStop 子代理结束时 校验子代理产出 阻止子代理结束
PreCompact 压缩前 备份完整对话记录 阻止本次压缩（v2.1.105 起）
Notification 需要用户注意时 桌面通知、提示音 不阻断
SessionEnd 会话结束 清理临时文件、记录日志 不阻断

输入与返回约定：

  • Hook 从 stdin 读取 JSON，其中 tool_name、tool_input（如 tool_input.command、tool_input.file_path）描述本次调用。没有 $CLAUDE_FILE 之类的环境变量，文件路径必须从 JSON 中取。
  • exit 0 表示通过；exit 2 表示阻断，stderr 作为原因反馈给 Claude；exit 1 及其他非零值是非阻断错误，动作照常执行——想拦截却写成 exit 1 是最常见的 bug。
  • 脚本中用 ${CLAUDE_PROJECT_DIR} 引用项目根目录，避免工作目录变化导致路径失效。
  • 2026-02-28 起还可以用 HTTP hooks，把事件 JSON POST 到内部服务，便于集中审计。

示例二：写入后自动格式化（.claude/hooks/format-on-write.sh）

示例三：结束前跑快速测试（.claude/hooks/run-tests-on-stop.sh）

6. 规范驱动开发（SDD）完整工作流

6.1 为什么 Vibe Coding 在中大型项目上崩溃

一个中等规模的功能往往隐含几十个需要拍板的决策：错误码怎么定、重试几次、数据放哪张表、谁有权限。Vibe coding 让模型在实施过程中逐个”猜”这些决策。假设有 20 个相互独立的模糊决策，每个猜对的概率是 90%，全部猜对的概率只有 0.9^20 ≈ 12%。

规范驱动开发（Spec-Driven Development，SDD）的本质是：先把模糊决策一次性收敛成写在文件里的清晰决策，再让 Claude 实施。规范文件同时是跨会话的记忆、评审的依据和验收的标准。

6.2 SDD 四阶段：Specify → Plan → Implement → Validate

flowchart LR
    S[Specify<br/>人主导] -->|Spec Gate| P[Plan<br/>人评审]
    P -->|Plan Gate| I[Implement<br/>AI 执行]
    I -->|Task Gate| V[Validate<br/>自动 + 人]
    V -->|未通过| I
    V -->|规格缺陷| S
阶段 产物 主导者 Claude Code 设置 进入下一阶段的关卡
Specify docs/specs/<feature>/spec.md 人 plan mode；让 Claude 用 AskUserQuestion 逐个提问 每条需求都有可检查的验收标准，没有待澄清项
Plan plan.md、tasks.md、decisions.md 人评审，Claude 起草 plan mode；可用 opusplan 或 Opus 任务粒度、文件清单、验证命令齐全，覆盖全部需求
Implement 代码、测试、每任务一个提交 Claude acceptEdits 或 auto；子代理逐任务执行；hooks 守门 每个任务测试通过并单独提交
Validate validation.md、评审报告、PR 描述 自动 + 人 评审子代理、/security-review、CI 每条验收标准有证据，无 Blocking 问题

所有产物都是提交进 Git 的 Markdown，任何一天新开会话，读取 docs/specs/<feature>/ 就能接上进度。

6.3 阶段一：Specify（撰写规范）

产物：docs/specs/<feature-name>/spec.md

规范的关键是可检查的成功标准：每条需求都要能回答”怎么证明做到了”。写”系统应快速回滚”无法验收，写”错误率超过阈值后 30 秒内完成回滚决策”才能写成测试。

推荐模板（结构参考 GitHub Spec Kit 的 spec 模板）：

写法要点：

  • 让 Claude 采访而不是让 Claude 猜：在 plan mode 下要求它用 AskUserQuestion 一次问一个问题，直到能填满模板。
  • “不做什么”与”要做什么”同样重要，它直接限制实施阶段的范围蔓延。
  • 需求编号贯穿全流程：FR/AC 编号会出现在 tasks.md、提交信息与 validation.md 中，形成可追溯链。
  • 待澄清项清零才能进入 Plan，否则这些问题会在实施时被模型默默”猜掉”。

Spec Gate 检查清单：

  • 每条 FR 至少对应一条 AC，AC 可以写成自动化测试或明确的人工检查
  • 非功能约束有数字（延迟、吞吐、保留期）
  • Out of Scope 已列出
  • 没有 [NEEDS CLARIFICATION] 残留
  • 领域专家或需求方已读过并确认

6.4 阶段二：Plan（技术方案与任务拆解）

产物：同目录下的 plan.md（技术方案）、tasks.md（任务清单）、decisions.md（关键决策记录）。

plan.md 回答”怎么做”：受影响的模块、数据结构与接口变更、与现有架构的衔接、风险与回退方案。

tasks.md 是 Implement 阶段的输入，每个任务要能被一个全新上下文的子代理独立完成：

[P] 标记可并行的任务（改不同文件、无依赖），这个约定来自 Spec Kit 的 tasks 模板。

decisions.md 记录方案取舍：选了什么、放弃了什么、为什么。它防止后续会话把已否决的方案重新提出来。

Plan Gate 检查清单：

  • 每条 FR 都被至少一个任务覆盖，任务标注了对应编号
  • 每个任务列出要改的文件与验证命令
  • 单个任务的改动量能在一次子代理会话内完成并验证
  • 依赖与可并行关系已标注
  • 与现有架构约定（CLAUDE.md、rules）不冲突，冲突处在 decisions.md 中说明
  • 人工在 plan.md 上的批注全部处理完毕，并已提交

人工评审计划时，直接在 plan.md 里写批注再让 Claude 统一处理，比在对话里口头修改更可追溯。

6.5 阶段三：Implement（按任务实施）

原则：每个任务一个干净上下文、一个提交、一次验证。

任务关系 执行方式 说明
有依赖的顺序任务 主会话逐个委派子代理，串行执行 每个任务完成并提交后再开始下一个
标记 [P] 的独立任务 同时委派多个子代理 改动文件不重叠时才并行
并行但可能碰同一文件 子代理加 isolation: worktree 各自在临时 worktree 中改，完成后合并
很小的收尾任务 主会话直接做 委派开销大于收益

实施阶段的护栏：

  • 权限模式：计划已评审后切到 acceptEdits 或 auto，减少打断；ask 与 deny 规则在 auto 模式下仍然生效。
  • hooks 守门：PostToolUse 负责格式化与 lint，Stop 负责快速测试，PreToolUse 负责拦截高危命令。
  • 提交粒度：每个任务完成后单独提交，提交信息带任务与需求编号（如 feat(T003): 错误率窗口判断 [FR-001]），出问题时可以精确回退。
  • 检查点：Claude Code 会为文件编辑自动建立检查点，Esc Esc 或 /rewind 可回退对话与代码；但 Bash 命令造成的改动（删文件、跑迁移）不在检查点范围内，这类操作要靠 git 与数据库备份兜底。
  • 进度可见：/tasks 查看后台运行中的子代理与任务。

6.6 阶段四：Validate（验证与验收）

验证分四层，由自动到人工：

层级 做什么 工具
自动测试 单元与集成测试全部通过 Stop hook（快速集）+ CI（全量）
规格追溯 逐条核对 AC，记录证据 让 Claude 以 spec.md 为唯一依据写 validation.md
独立评审 与实现者隔离的代码评审与安全审查 code-reviewer 子代理、/security-review
人工验收 看关键路径演示、抽查证据 人

validation.md 的格式建议：

未通过的 AC 回到 Implement 补任务；如果发现是规格本身有缺陷，回到 Specify 修改 spec.md，并同步更新 plan 与 tasks——不要只改代码不改规格，否则规格很快失去”单一事实来源”的地位。

6.7 与现成 SDD 工具的关系

上面的流程不依赖任何插件，用原生能力即可落地。现成工具把其中一部分固化成命令：

9. 上下文工程与成本控制

9.1 监控上下文使用

  • /context：以网格展示当前上下文占用，按系统提示、工具、记忆文件、技能、对话拆分，并给出优化建议。
  • /usage：查看会话成本与订阅用量；v2.1.118 起 /cost 与 /stats 合并进 /usage，仍可作为快捷入口。
  • /statusline：把上下文占用常驻显示在状态栏，不必反复手动查看。

经验上，任务进行到一半时占用已经过半，就该考虑交接或压缩，而不是等自动压缩发生。

9.2 上下文卫生的几条原则

  1. 交接优于硬撑：复杂任务进行到一半时，先让 Claude 把进度写进 markdown（如 /recap），再 /clear，新会话读取交接文件继续。
  2. 主动压缩带重点：必须继续当前会话时用 /compact <保留重点>，指定摘要要保留什么，比自动压缩可控。
  3. 避免 @ 引用大文件：改成”遇到 X 问题时读 docs/api-spec.md”，让 Claude 按需读取。
  4. 重型探索交给子代理：调研、全仓搜索放进子代理的独立窗口。
  5. 关掉用不到的 MCP：Tool Search 已让工具定义按需加载，但每个 server 仍会占用进程与连接；用 /mcp 禁用当前项目用不到的 server。
  6. CLAUDE.md 做减法：每条都问”删掉它，Claude 会犯错吗”，不会就删。

9.3 模型选择策略

场景 模型 effort 说明
Specify、Plan、架构评审、疑难调试 Opus 4.7 high 或 xhigh 1M 原生上下文；xhigh 为 Opus 4.7 新增档位
按计划实施、日常编码 Sonnet 4.6 medium 或 high 性价比最高的主力
子代理中的检索、格式整理、批量简单改动 Haiku 4.5 — 在子代理 frontmatter 写 model: haiku
规划用 Opus、执行用 Sonnet opusplan — plan mode 下自动用 Opus，退出后切 Sonnet

切换方式：会话内 /model 与 /effort，启动时 --model 与 --effort，或在 settings.json 中设置 model 与 effortLevel。SDD 的成本结构是”前重后轻”：Specify 与 Plan 值得用最强模型和高 effort，因为这里的一个错误决策会在实施阶段被放大；Implement 阶段任务已经足够明确，换成 Sonnet 往往质量不降、成本明显下降。

10. 常见反模式与排错指南

10.1 反模式：CLAUDE.md 是个垃圾桶

症状：CLAUDE.md 长到几百行，Claude 仍然不遵守其中的规则。

根因：项目的所有信息都堆在一个每次必读的文件里，关键约束被稀释。

修法：

  1. 只对部分文件有效的规则拆到 .claude/rules/*.md 并加 paths。
  2. 模块专属说明拆到子目录 CLAUDE.md。
  3. “怎么做”的流程挪进 Skills。
  4. 必须强制执行的规则交给 hooks 或 settings。
  5. 根文件控制在官方建议的 200 行以内，越短越好。

10.2 反模式：让 Claude 当保姆带

症状：每修一个 bug 都给出”先看 X 文件、再改 Y 函数”的详细步骤。

根因：没有信任它的探索能力，反而把它限制在自己的假设里。

修法：贴出现象、报错与复现方式，说”修复它”，不规定怎么修；只在它方向明显错误时介入。

10.3 反模式：跳过 plan 直接 implement

症状：实施半小时后才发现方向错了，大量改动需要回退。

根因：模糊决策没有收敛就开始写代码。

修法：超过三个文件的改动一律先进 plan mode（/plan 或 --permission-mode plan），计划评审通过后再实施。

10.4 反模式：长会话不分段

症状：会话后半程 Claude 开始忘记早期约定，重复已否决的方案。

根因：上下文被探索噪声占满，或经历了多次有损压缩。

修法：以任务为单位分段；阶段结束时交接（/recap → /clear → 读交接文件），把决策写进 decisions.md 而不是留在对话里。

10.5 反模式：用 PreToolUse 做质量检查

症状：PreToolUse hook 在每次 Write 前跑 lint 并阻断，Claude 反复重写同一个文件，进度停滞。

根因：写入前的内容无法被 lint 真实检查；阻断写入又让模型在不完整的状态下反复重试。

修法：PreToolUse 只用于安全拦截（高危命令、敏感路径）；格式与 lint 放在 PostToolUse，测试放在 Stop，让模型先写完再根据反馈修正。

10.6 反模式：MCP 越装越多

症状：工具选择变慢、调用了不该调用的 server、凭据散落在多个配置文件里。

根因：把”可能用得上”的 server 都装在 user 作用域，每个项目都加载。

修法：常用的少数几个放 user 作用域，其余按项目放进 .mcp.json；用 claude mcp list 定期盘点，删掉一个月没用过的。

10.7 常见错误排查

症状 可能原因 处理
Skill 从不自动触发 description 写成了功能摘要，没写触发条件 改成”当用户要……时使用”，加入常见说法
Hook 看起来没执行 脚本没有执行权限、matcher 大小写不符、用了 exit 1 而非 exit 2 chmod +x；用 /hooks 查看生效配置；拦截统一用 exit 2
Hook 取不到文件路径 以为有环境变量传入 从 stdin JSON 的 tool_input.file_path 读取
Stop hook 陷入循环 未检查 stop_hook_active 该字段为 true 时直接 exit 0
MCP 显示 failed 凭据错误、命令路径不对、项目级 server 未批准 /mcp 看错误详情；claude mcp get <name> 核对配置
路径规则没生效 paths 的 glob 写错，或 Claude 还没读到匹配文件 规则在读取匹配文件时才加载，先让它读一个目标文件验证
权限弹窗太多 allow 规则通配符写法不对 用 /permissions 查看规则；注意 * 前的空格
装完插件命令找不到 插件未启用或未刷新 /plugin 确认已启用，执行 /reload-plugins
安装后 claude 命令不存在 PATH 未包含安装目录 运行 claude doctor 查看安装方式与建议

11. 进阶路线图与持续学习

11.1 学习里程碑（按 30/60/90 天）

第一个 30 天 — 熟练度：

  • 安装、认证、IDE 集成全部跑通
  • 至少 3 个项目有精简过的 CLAUDE.md
  • 用 plan mode 完成过 1 个完整特性
  • 配置过自己的命令与至少 1 个 PostToolUse hook
  • 装好 Context7 MCP 与 1 个流程框架（或按第 6 节自建）

第二个 30 天 — 工程化：

  • 写过至少 2 个自己的 Skill，并维护了 Gotchas 一节
  • 写过至少 1 个自己的 Subagent（如只读评审代理）
  • 在一个真实需求上走完 Specify → Plan → Implement → Validate
  • 配好 Stop hook 跑快速测试
  • 用 .mcp.json 管理项目级 MCP，凭据走环境变量

第三个 30 天 — 多代理与扩展：

  • 用多个子代理并行完成过一次调研或独立模块改动
  • 试用过 Agent Teams（实验特性，需设置 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1）
  • 把团队规范沉淀成内部插件市场
  • 用 claude -p 或 Claude Agent SDK 写过一个 CI 自动化脚本
  • 能讲清 Skills、Subagents、Hooks 的边界与选型理由

11.2 持续学习的几个源

  • 官方文档：https://code.claude.com/docs/en/overview，唯一权威。
  • CHANGELOG：https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md。迭代非常快，2026 年 3–4 月 npm 上共发布了 53 个版本，建议每周扫一次。
  • anthropics/skills：学习 Skill 的写法与目录组织。
  • hesreallyhim/awesome-claude-code：社区资源索引。
  • wshobson/agents：观察大规模代理与插件如何拆分和组织。
  • obra/superpowers：方法论型技能的写法参考。

11.3 团队推广的推进顺序

  1. 单人试点：一名成员在一个真实需求上走完 SDD 四阶段，记录每个关卡发现的问题。
  2. 沉淀模板：把 spec/plan/tasks/validation 模板、code-reviewer 代理与 hooks 提交到仓库。
  3. 统一配置：团队共用的权限、hooks、插件写进 .claude/settings.json，个人偏好留在 settings.local.json。
  4. 接入 CI：Validate 阶段的自动测试与评审在 CI 中复跑，不只依赖本地 hook。
  5. 定期复盘：每月清理 CLAUDE.md、卸载无用插件、把反复出现的问题补进 Skill 的 Gotchas。

写在最后

Claude Code 的杠杆不只在模型本身，更在围绕模型搭建的工程化外壳：CLAUDE.md 给它项目知识，Skills 给它做事的方法，Hooks 给它不可违背的纪律，Subagents 给它专业分工，MCP 给它外部世界，规范驱动开发给它清晰的目标与验收标准。

这套外壳的价值不会随模型变强而消失：模型越能自主工作，越需要事先写清楚”做什么、做到什么程度算完成”。把时间花在规范、质量门和上下文管理上，回报会随每一次模型升级继续累积。

2026-09 补记：新能力对 SDD 流程的影响

本文写于 2026-05。此后几项变化直接影响上面的四阶段流程：

  • Agent view 与 /goal（2026-05-11）：/goal 设定一个完成条件，Claude 会跨轮次持续工作直到条件满足，官方文档把它描述为会话级的 prompt 型 Stop hook。Validate 阶段可以把”validation.md 中每条 AC 都有通过证据”设为 goal，替代手写的 Stop hook 脚本；但确定性的测试门禁仍应保留在脚本里。
  • Dynamic workflows（2026-05-28）：Claude 为任务编写一个 JavaScript 编排脚本，由运行时在后台驱动数十到上百个子代理，可中断后在同一会话恢复。它适合 tasks.md 中大量同构的任务（批量迁移、全仓审计）：Plan 阶段的产物从”任务清单”延伸为”可审阅、可重跑的编排脚本”，这份脚本本身应纳入 Plan Gate 评审。Pro 计划需要在 /config 中手动开启。
  • Auto mode 默认开启（2026-08-14）：Implement 阶段的权限打断大幅减少，第 4.4 节的 ask 与 deny 规则在 auto 模式下依然生效，PreToolUse 的 exit 2 拦截也照常工作，因此这两层配置的重要性反而上升——它们成了自动执行时仅剩的显式约束。
  • 模型更替：Sonnet 5 于 2026-06-30 成为默认模型，Opus 5（2026-07-24）与 Opus 5.5（2026-09-22）相继发布。第 9.3 节的分工思路不变（规划用最强模型，实施用主力模型），但具体型号要随之替换；另外 Opus 5.5 的 effort 默认从 medium 起步，且用户级 settings 中旧的顶层 effortLevel 对它不生效，升级后需重新用 /effort 设定。
  • AGENTS.md 支持（2026-09-18，需 v2.1.277 及以上）：Claude Code 可以直接读取 AGENTS.md。默认规则是”没有 CLAUDE.md 时才读 AGENTS.md”，两者并存时只读 CLAUDE.md。多工具共用的仓库有两种做法：只保留一份 AGENTS.md 承载 SDD 约定（目录结构、模板位置、关卡清单），或在 CLAUDE.md 中用 @AGENTS.md 导入它。不要在两个文件里各写一套流程说明。
  • 工具生态：GitHub Spec Kit 于 2026-08-21 发布 v1.0.0；GSD 原仓库已归档，2026-05-22 起以 GSD Core（open-gsd/gsd-core）延续，命令改为 /gsd-* 连字符形式。第 6.7 节的选型原则不变：一个仓库只保留一套主流程。
