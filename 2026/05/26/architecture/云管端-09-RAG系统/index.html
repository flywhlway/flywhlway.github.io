3. 关键设计决策

3.1 切分：结构化 + 父子分块

flowchart LR
    DOC["原文档"] --> H["按标题层级切分<br/>保留 heading_path"]
    H --> PAR["父块 800-1200 token<br/>提供完整上下文"]
    PAR --> CHI["子块 200-300 token<br/>用于精确检索"]
    CHI --> IDX["索引子块"]
    IDX --> HIT["检索命中子块"]
    HIT --> RET["返回对应父块"]
策略 优点 缺点 适用
固定长度 简单 切断语义 不推荐
递归分隔符 尊重段落 不理解结构 一般文本
结构化（按标题） 语义完整、可继承标题路径 依赖文档结构规范 技术文档、手册（首选）
父子分块 检索精确 + 上下文完整 存储翻倍 与结构化组合使用（首选）
语义边界（模型判定） 效果好 成本高、离线慢 高价值知识库

heading_path 是低成本高收益的元数据。把 “车辆设置 > 空调 > 自动模式” 写入 chunk 元数据并在生成时一并提供，可显著减少答案跑偏（模型知道这段话的上下文归属）。

3.2 混合检索：为什么不能只用向量

查询类型 纯向量表现 纯 BM25 表现 混合
口语化描述（”车里怎么变凉快”） ✅ 好 ❌ 差 ✅
专有功能名（精确名称查询） ⚠️ 中 ✅ 好 ✅
型号 / 编号 / 错误码 ❌ 差 ✅ 好 ✅
长句复杂意图 ✅ 好 ⚠️ 中 ✅
否定表述（”不想要 X”） ❌ 差 ❌ 差 ⚠️（需查询改写）

纯向量检索在型号与编号上系统性失败，因为 Embedding 会把 “A-1200” 和 “A-1300” 映射到几乎相同的向量。车载场景大量涉及配置型号、错误码、版本号，混合检索是必选而非优化。

RRF 融合公式：score(d) = Σ 1/(k + rank_i(d))，k 常取 60。优点是无需归一化不同检索器的分数，鲁棒性好。

3.3 元数据过滤前置

flowchart LR
    W["❌ 错误顺序"] --> W1["全库检索"] --> W2["检索后过滤车型"] --> W3["Top-K 可能全被过滤掉<br/>召回为空"]
    R["✅ 正确顺序"] --> R1["先按车型/版本/权限过滤"] --> R2["在子集内检索"] --> R3["Top-K 全部有效"]

车载知识库最典型的事故是答错车型：用户 A 车型的问题，被答了 B 车型的功能。必须把车型/配置/软件版本作为强制过滤维度，且过滤在检索之前。

3.4 查询改写：投入产出比最高的单点优化

改写类型 原查询 改写后 收益
口语化归一 “咋整才能凉快点” “如何降低车内温度 空调制冷设置” 召回率显著提升
指代消解 “那第二个怎么弄” “（结合上轮）自动模式如何设置” 多轮场景可用
拆解多意图 “怎么开空调还有充电桩在哪” 两个独立查询 避免检索混杂
补全隐含条件 “续航多少” “（补车型/配置）续航里程” 避免答错车型
生成假设答案（HyDE） 问题 生成一段假想答案再检索 长尾问题召回提升

查询改写用小模型即可（延迟约 60 ms，成本极低），是 RAG 优化清单上应当第一个做的事情，常带来 15–30% 召回率提升。

3.5 Rerank：性价比最高的精度提升

配置 召回数 Rerank 后 准确率变化 延迟增加
无 Rerank Top-5 直接用 — 基线 0
轻量 Rerank Top-20 → 5 ✅ +8~12% +30 ms
标准 Rerank Top-50 → 5 ✅ +10~20% +50 ms
重 Rerank Top-100 → 5 ✅ +12~22% +120 ms

Top-50 → 5 是甜点配置。继续加大召回数收益递减而延迟线性上升。

4.1 门户必备能力

能力 说明 缺失后果
解析预览 上传后立即看到切分结果 运营不知道切成什么样，全靠上线后发现
试检索 输入问题看召回片段与分数 无法自查，问题都留到线上
元数据打标 车型、权限、时效、来源 答错车型、越权泄露、过期信息
生效状态 索引进度、生效版本、覆盖范围 “我明明加了知识为什么答不出来”
知识缺口工单 从 empty_recall 自动生成待补清单 知识永远滞后于用户需求
版本与回滚 知识版本化，可回滚 错误知识无法快速撤回

「知识缺口工单」把闭环自动化了：线上检索为空的查询自动聚类生成工单，运营按热度补充知识。这是知识库覆盖率持续上升的唯一可持续机制。

5.2 三套评测集分离（关键实践）

集合 规模（推断设计） 用途 可否用于调参
公开集 200–500 日常调参、快速迭代 ✅ 可以
回归集 300–800 发布门禁，每次变更必跑 ❌ 不可（会过拟合门禁）
盲测集 200–500 真实效果评估，定期人工评 ❌ 严格禁止

不做三集分离的必然结果：指标持续上升但线上体验不变甚至变差（过拟合评测集）。盲测集必须由独立角色维护且不对调参人员开放。

5.3 忠实度评测：最重要的指标

判定 含义 处理
完全忠实 答案每个论断都有片段支撑 ✅
部分忠实 部分内容为模型自行补充 ⚠️ 需标注区分（哪些有据、哪些是推测）
不忠实（幻觉） 答案与片段矛盾或凭空生成 ❌ 严重缺陷，必须修复
正确但无据 答案对但检索片段不支撑 ⚠️ 是知识缺口（碰巧模型知道），需补知识

“正确但无据”是最容易被误判为成功的情况。它意味着系统实际上依赖模型内部知识而非企业知识库——一旦换模型就会失效，且无法保证时效性。评测必须把它单独归类。

5.4 LLM-as-Judge 的正确用法

要点 说明
必须校准 与人工标注做一致性验证（Cohen’s Kappa ≥ 0.7 才可信）
提供评分标准 给出明确 rubric 而非”打个分”
提供参考答案 有金标答案的对比判定远比开放判定可靠
用强模型评弱模型 不要用同一模型自评（有系统性偏袒）
定期抽检 每期评测抽 10% 人工复核

6. RAG 变体选型

方案 何时引入 建设成本 更新成本 适用问题类型
朴素 RAG + 混合检索 + Rerank 起步即用 低 低 单点事实查询（通常占 70%+）
父子分块 + 结构化切分 起步即用 低 低 技术文档、手册
HyDE / 多查询扩展 长尾召回不足时 低 无 表述差异大的长尾问题
GraphRAG 确认存在多跳需求后 极高（大量 LLM 建图） 高（难增量） 跨文档关系推理、全局性总结
LightRAG 需关系推理且知识持续更新 中高 中（支持增量） 关系型知识 + 频繁更新
HybridRAG（图+向量融合） 成熟阶段优化 高 中 覆盖面最大化

    C -->|"需要多跳推理"| D5{"这类问题占比?"}

最常见的错误决策是”效果不好 → 上 GraphRAG”。实际上多数团队在查询改写、混合检索、Rerank、元数据过滤这四项基础工作尚未做扎实时就转向图方案，结果建设成本上升 10 倍而效果提升有限。

7. 端侧 RAG

维度 云端 RAG 端侧 RAG
索引规模 百万~千万 chunk 万级
向量维度 768–1024 256–384（量化 int8）
检索方式 混合 + Rerank 混合（轻量）+ 无 Rerank 或极轻 Rerank
Embedding 模型 云端标准模型 端侧小模型（需与云端保持语义可比或独立索引）
知识内容 全量知识库 高频稳定子集（车辆手册、常用设置、常见问答）
更新方式 实时/准实时 差分包按需下载
延迟 250 ms 60 ms

7.1 端侧知识包设计

flowchart TB
    C["云端全量知识库"] --> SEL["子集筛选<br/>按查询频次 + 答案稳定性 + 离线价值"]
    SEL --> PKG["按场景切分知识包<br/>车辆功能包 / 设置包 / 故障处理包"]
    PKG --> QNT["量化 Embedding<br/>int8 · 256 维"]
    QNT --> DIFF["差分包生成<br/>vs 端侧当前版本"]
    DIFF --> SIGN["签名"]
    SIGN --> DL["按需下载<br/>WiFi 优先 · 后台低优先级"]
    DL --> VER["端侧验签 + 原子切换"]

端侧知识库的选品原则：高频 × 答案稳定 × 离线有价值。车辆功能说明完全符合这三条（问得多、答案不变、地库里也需要），是端侧知识库的最佳内容。而”附近充电桩”虽然高频但答案不稳定且离线无意义，不应进端侧。

8. 知识治理

治理项 要求 实现
权限 知识按可见范围分级 chunk 元数据带权限标签，检索时按用户权限过滤
时效 过期知识不得被检索 valid_from / valid_until 字段 + 检索时过滤
来源可信度 官方文档 > 工单沉淀 > 网页 来源等级作为 Rerank 加权项
版本 知识变更可追溯可回滚 知识版本号 + 变更日志
冲突 同一问题多份矛盾知识 冲突检测任务 + 人工裁定 + 权威源标记
Embedding 版本 换模型必须重建索引 embedding_version 强制字段 + 灰度双索引
缓存联动 知识更新使相关语义缓存失效 知识版本纳入缓存键

8.1 Embedding 模型更换流程

sequenceDiagram
    autonumber
    participant OP as 知识运营
    participant SYS as RAG 底座
    participant EVAL as 评测
    OP->>SYS: 申请更换 Embedding 模型
    SYS->>SYS: 用新模型构建影子索引（不对外）
    SYS->>EVAL: 在盲测集上双索引对比评测
    EVAL-->>SYS: 新索引召回率对比结论
    alt 新索引更优
        SYS->>SYS: 灰度切流（5% → 50% → 100%）
        SYS->>SYS: 全量后保留旧索引 7 天备回滚
        SYS->>SYS: 触发语义缓存全量失效
    else 不优
        SYS->>SYS: 丢弃影子索引
    end

换 Embedding 是高风险操作：它使全部历史向量失效，且效果变化不易感知（可能某类查询变好、另一类变差）。必须走影子索引 + 盲测对比 + 灰度，且必须触发语义缓存失效（旧缓存基于旧知识版本）。

10. 风险与治理

风险 影响 治理
答错车型/版本 严重误导，可能引发安全问题 元数据过滤前置 + 强制车型标签 + 评测集覆盖多车型
幻觉（无据生成） 信任崩塌 强制引用 + 忠实度评测 + 无据则拒答
知识缺口不可见 覆盖率长期停滞 empty_recall 埋点 + 自动工单
过期知识 误导 时效字段 + 定期复审 + 来源变更监听
评测集过拟合 指标涨体验不涨 三集分离 + 盲测集独立维护
