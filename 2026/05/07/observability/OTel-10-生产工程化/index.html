10 · 从 POC 到生产工程化演进

POC 的目标是”看得见”，生产的目标是”扛得住、管得住、算得清”。本篇按 拓扑高可用 → 数据治理 → 安全合规 → SLO 告警 → 组织流程 五个维度给出演进路线与配置基线。

1. 演进总览：三阶段门禁

维度 POC（本文档集现状） Pilot（单业务线试点） Production
Collector 单实例合一 Agent + Gateway 两层 Gateway 多副本 + 按 traceID 负载均衡
采样 100% 头采 50% + 尾采规则 尾采（错误/慢/高 Token 全留，基线 1~10%）
存储 本地盘 对象存储（MinIO/OSS） Mimir + 对象存储，多租户
内容捕获 开启 白名单服务开启 + 脱敏 默认关闭，事件通道 + 独立留存/权限
认证 无 Collector 入口 Token mTLS + 租户级鉴权
告警 手动看盘 RED 基线告警 SLO 燃尽率告警 + AI 指标告警

2.2 部署方式

  • 官方 OpenTelemetry Operator（Helm）：以 OpenTelemetryCollector CRD 管理配置，支持 Sidecar/DaemonSet/Deployment 三形态与自动注入（Java 服务可用 Instrumentation CRD 免改镜像注入 javaagent）；
  • 存储层用 Grafana 官方 Helm：tempo-distributed、loki、mimir-distributed；后端对象存储对接 MinIO/阿里云 OSS；
  • 弹性配置基线：exporter 开启 sending_queue（必要时 file storage 持久化队列）与 retry_on_failure，防后端抖动丢数。

3. 数据治理：成本与基数控制

遥测成本三大来源与对策：

来源 症状 对策
指标基数爆炸 Prometheus 内存暴涨 禁止把 user_id/session_id/trace_id 作为指标维度（放 Trace 属性）；Collector 用 transform 删除高基数标签；Mimir 设 per-tenant series 上限
Trace 内容膨胀 单 Span 数十 KB 内容捕获走事件/外部存储引用；attributes 处理器 truncate 长文本（如 4KB）
日志噪声 Loki 摄入量失控 采集侧按 level 过滤 DEBUG；健康检查/心跳路径在 SDK excluded_urls 与 Collector filter 双重排除

留存策略基线：Metrics 3090 天（降采样后更久）/ Traces 714 天（错误链路可延长）/ Logs 14~30 天 / Langfuse 业务 Trace 按评测需要 90 天+。

4. 安全与合规（车企场景重点）

  1. 传输安全：App→Collector 集群内 mTLS；Collector→后端 TLS + basicauth/bearertokenauth extension；OTLP 端口绝不裸露公网；
  2. PII 纵深防御（文档 02 §4 三层落地）：Collector redaction（白名单）+ transform OTTL 正则（手机号/VIN/身份证/坐标）双保险，脱敏规则纳入版本管理并配单元测试（ottl playground 验证）；
  3. 数据不出境：全自托管栈天然满足；若引入 SaaS 后端，LLM 内容类属性一律在 Collector 出口前剥离；
  4. 等保/审计：Grafana/Langfuse 开启 SSO + RBAC；含内容捕获的 Trace 单独租户存储、独立权限；Collector 配置变更走 GitOps 审计；
  5. 供应链：镜像固定 digest、私仓代理拉取；Collector 仅编译启用所需组件（ocb 自建发行版）以缩小攻击面——延续对第三方组件供应链风险的一贯审慎（LiteLLM 事件教训）。

5. SLO 与告警体系

5.1 指标分层

层 SLI 示例 数据来源
入口层 可用性、P95 延迟、TTFT P95 Higress/SCG 指标
Agent 层 诊断成功率、Agent 循环次数 P99、工具失败率 自定义 aits.* 指标
LLM 层 gen_ai.client.operation.duration P95、429 比例、Token 成本/千次请求 GenAI 指标
平台层 Collector 丢弃率、队列水位、Temporal 队列积压 otelcol/temporal 自身指标

5.2 告警规则示例（Prometheus rules）

SLO 告警采用多窗口燃尽率（burn rate）模式：以「诊断请求 30 天 99% 成功率」为例，5m/1h 双窗口燃尽率 >14.4 触发 critical，30m/6h >6 触发 warning。

6. 版本与规范治理

  • 语义约定版本：平台统一声明（OTEL_SEMCONV_STABILITY_OPT_IN）写入基础镜像/Chart，禁止服务自行漂移；GenAI 约定仍在 Development，每季度评审独立仓库 changelog，属性变更经 Collector transform 做过渡映射（文档 03 §5）；
  • 私有属性登记制：aits.* 属性统一登记（名称、类型、基数评估、负责人），防止野生属性造成基数事故；
  • 埋点即代码评审项：新服务上线 checklist 包含「资源属性齐全、健康检查排除、错误路径 record_exception、无 PII 明文属性」；
  • 升级节奏：Collector 按季度跟进（关注 breaking changes 章节）；SDK 随语言 BOM 半年一升；升级先过 staging 对账（Span 数/指标名 diff）。

7. 生产就绪终检清单

  • Gateway Collector ≥2 副本，尾采样 + loadbalancing 按 traceID 路由验证通过；
  • 后端全部对象存储化，单组件宕机不丢数（sending_queue 持久化实测）；
  • PII 脱敏规则有测试用例，内容捕获默认关闭且有审批开启流程；
  • OTLP 入口有认证，Grafana/Langfuse 接 SSO 与 RBAC；
  • SLO 告警接入值班体系，告警可一键下钻到 Trace（exemplar 链路验证）；
  • 遥测成本月报（存储量/序列数/摄入量 按团队归因）机制建立；
  • 灾备演练：Collector 全挂 30 分钟，应用无感（SDK 队列丢弃降级）且恢复后指标连续。

8. 结语：与平台架构的融合

可观测体系不是外挂，而是 AIDO「monitor → diagnose → treat → learn」运营闭环的 monitor 基座：GenAI 语义约定提供了 LLM 这一概率性组件的确定性度量面——Token、时延、错误、循环次数皆可入 SLO；而 Langfuse 层的评测与会话数据反哺 Prompt 与模型迭代，构成 learn 环节的数据来源。至此，”确定性 × 概率性融合”的架构原则在观测维度完成闭环。
