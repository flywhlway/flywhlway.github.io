Java 微服务调用 Python Agent 的流式链路：gRPC 双向流与统一 SSE 事件协议

从浏览器到 LangGraph 的端到端流式链路：proto 事件模型、grpc.aio 服务端、grpc-java 与 WebFlux 的背压和取消桥接、统一 SSE 协议与排错…

Flywhl 36 分钟 更新于 2026.09 #LangGraph#gRPC#SSE

先读结论

  1. 流式是整条链路的属性：任何一段缓冲、聚合或同步桥接，都会让前端退化成一次性收到全文。
  2. Java 与 Python 之间用 gRPC 双向流，是为了让取消、人工确认这类运行中控制消息与事件走同一条流、落到同一个实例。
  3. 对前端只暴露自有的 SSE 事件协议（token、tool_call、tool_result、state、error、done），不透传 LangGraph 原始事件，框架升级只改 Python 适配层。
  4. 每个 run 有且只有一个 done 且位于最后；上游异常由网关补发 error + done，前端没收到 done 一律按中断处理。

为什么要端到端流式

企业 Agent 平台的常见分工是：Java 微服务（Spring Cloud Alibaba）负责鉴权、租户、业务数据和对外 API，Python 执行面（FastAPI + LangGraph）负责模型调用与图编排。一次车辆故障诊断可能要查故障码库、检索维修手册、再让模型生成排查步骤，总耗时 20 秒以上很常见。不做流式，用户面对的是 20 秒空白；做了流式，1 秒内就能看到「正在查询 P0171」，随后是逐字输出的结论。

端到端流式要解决三件事：

目标 衡量方式 被什么破坏
首个有意义事件尽早到达 首事件延迟（不只是首 token，工具调用开始也算） 任一段缓冲；响应头迟迟不提交
过程可见 前端能画出「查故障码 → 检索 → 生成」轨迹 只透传文本，丢掉工具与阶段事件
取消能真正止损 用户点停止到模型请求被关闭的时间 取消信号在某一段断掉，Python 继续跑、继续计费

关键认识：流式是链路属性，不是组件属性。Python 侧逐 token 产出，只要 Java 侧某处用了 .collectList()、Nginx 开着 proxy_buffering，前端看到的就是一次性全文。所以下文按段讲，每段都说明它如何保持「逐事件、可背压、可取消」。

链路总览

sequenceDiagram

    participant L as LLM

    J->>P: 取消 gRPC 调用 或 发 CancelRun 帧

各段职责划分：

段 协议 负责 不负责
浏览器 ← 网关 HTTP + SSE 事件展示、按 seq 去重、断线判定 重放历史事件

Java 与 Python 之间的通信方式选型：

方案 适用 问题
Java 用 WebClient 消费 Python 的 HTTP SSE 原型、调试方便 事件无强类型；取消只能断连接，无法携带原因；无法在运行中回传人工确认结果
gRPC 服务端流（server streaming） 只有下行输出 运行中的控制消息要另开接口，而且必须路由到正在跑这个 run 的 Python 实例
gRPC 双向流（本文） 需要运行中取消、人工确认、回传补充信息 L4 负载均衡会把长连接钉在单实例上，需要客户端负载均衡或 L7 代理
RocketMQ 等消息队列 + 推送 分钟级异步任务、报告生成 顺序与延迟要额外保证，不适合 token 级输出

双向流的核心价值在最后一列的反面：控制帧（取消、审批）与事件共用一条 HTTP/2 流，天然落到持有该 run 的那个 Python 协程，不需要分布式的 run 注册表。

proto：一次 run 的事件模型

几个设计取舍：

  • 用 oneof 而不是「枚举 + JSON 字符串」：Java 侧 switch (ev.getPayloadCase()) 编译期穷举，新增事件类型时旧客户端拿到的是 PAYLOAD_NOT_SET，不会解析崩溃。
  • 工具参数与结果用 *_json 字符串：工具的入参出参结构各异，用 google.protobuf.Struct 需要两端各做一次转换，收益不大；网关最终也是把它原样放进 SSE 的 JSON。
  • seq 由 Python 单点生成：同一条 gRPC 流内消息本身有序，seq 的作用是给前端去重、给网关检测生产端 bug、给 SSE 的 id 字段提供值。
  • trace_id 同时放 metadata 和事件体：metadata 供 Python 日志与 OpenTelemetry 使用，事件体供前端上报问题时带上。
  • state 只报阶段和变更的 key：State 里可能有检索原文、内部评分等大对象或敏感字段，不应该顺着流式通道泄露到浏览器。

Python 执行面：LangGraph 流模式 → gRPC 事件

环境：Python 3.11+，以下版本为 2026-01 时点的稳定版本。

图与事件归一

LangGraph 1.x 的 astream 支持同时订阅多种流模式，传列表时每次产出 (mode, chunk) 二元组。本文用到三种：

stream_mode chunk 形态 映射为 说明
messages (消息块, 元数据)，元数据含 langgraph_node token 节点里调用 model.ainvoke 也会逐 token 产出，LangGraph 通过回调拿到增量
custom 节点内 get_stream_writer() 写入的任意对象 tool_call / tool_result 工具的开始与结束由节点显式上报，时机可控

STREAM_NODES 白名单容易被忽略：messages 模式会捕获图里所有 LLM 调用的 token，包括意图路由、结构化抽取这类输出 JSON 的调用。不加过滤，前端会先闪过一段 {"intent": "diagnosis"} 再出现正文。

gRPC 服务端

这段代码里决定正确性的四个点：

  1. 单写者队列。图执行（produce）和控制帧监听（watch_control）是两个协程，都可能产生事件；所有事件先进同一个队列，再由生成器唯一出口编号并 yield。这样 seq 连续、顺序确定，不会出现两个协程并发写流导致的交错。
  2. 有界队列即反压。前端读得慢 → Java 不再 request → HTTP/2 流控窗口耗尽 → yield 挂起 → 队列填满 → queue.put 挂起 → 图执行暂停在下一个事件点。整条链路没有无界缓冲。
  3. 两种取消都能走到图执行。软取消是收到 CancelRun 帧，主动取消 producer 并补一个 done(CANCELLED)，已生成内容保留；硬取消是 Java 取消 gRPC 调用（浏览器断开、超时），grpc.aio 取消 Chat 协程，finally 里取消 producer。CancelledError 必须原样抛出，一旦被 except BaseException 吞掉，模型请求会继续跑完。
  4. 异常转事件。节点异常不直接让 RPC 以错误状态结束，而是先发 error 再发 done(FAILED)，前端拿到的是可展示的错误码，而不是一条莫名断开的连接。

正常运行时事件顺序为 tool_call → tool_result → state(lookup_dtc) → token × N → state(answer) → done(COMPLETED)；带参数 5 运行时，取消帧发出前已进入队列的事件仍按序送达（假模型产出很快，通常还会再收到几个 token），随后是 done(CANCELLED)，seq 保持连续。

Channel 配置

gRPC 基于 HTTP/2 长连接，所有调用复用少量连接。如果 Python 实例前面是 L4 负载均衡（如 Kubernetes 普通 Service），连接建立后所有流都会落到同一个 Pod。两种解法：dns:/// 指向 Headless Service，配合 round_robin 做客户端负载均衡；或者前置 Envoy 这类按请求分发的 L7 代理。用 Nacos 做服务发现时，需要自定义 NameResolver 把实例列表喂给 gRPC，本文不展开。

gRPC 流桥接为 Flux

背压的关键是 disableAutoRequestWithInitial(0) 加 sink.onRequest：Reactor 下游（最终是 Reactor Netty 往 socket 写 SSE）要多少，才向 gRPC 要多少。溢出策略选 ERROR 而不是 BUFFER，因为按需 request 之后不应该出现超发；真出现了说明桥接写错了，应该尽早暴露，而不是悄悄堆在内存里。

背压、取消、超时、心跳如何落在代码里

关注点 实现 容易踩的坑
背压 disableAutoRequestWithInitial(0) + sink.onRequest → gRPC request(n) → HTTP/2 窗口 → Python 有界队列 在 beforeStart 里调 request 会因 call 未启动而抛异常；用 OverflowStrategy.BUFFER 会把背压问题藏成内存增长
硬取消 浏览器断开 → Reactor Netty 取消订阅 → sink.onCancel → call.cancel → Python CancelledError Flux 中间某处 .block() 或把事件丢进线程池，取消链就断了
软取消 POST /runs/{id}/cancel → CancelRun 帧 → Python 收尾并发 done(CANCELLED) running 表是单实例内存；多副本部署时取消请求可能打到另一个 Java 实例，需按 runId 做一致性路由或用 Redis Pub/Sub 广播
运行上限 withDeadlineAfter(5 min)，Python 侧可用 context.time_remaining() 自查 deadline 只在发起调用时设置一次，不是空闲超时
空闲超时 Flux.timeout(90s)：两个业务事件之间静默太久即判定上游卡死 心跳不能算业务事件，所以心跳必须在 timeout 之后再 merge
心跳 每 15 秒一个 SSE 注释帧 :ping，不占 seq 间隔要小于链路上最短的空闲超时（Nginx 默认 proxy_read_timeout 为 60 秒）
响应头 startWith(:open) 让响应头立即提交 响应头要等第一个事件才发出时，网关的响应超时会先触发 504
终止 takeUntil(done)；异常和「无 done 就结束」都由 SseEventMapper 补发 error + done 忘了 takeUntil，心跳流是无限的，连接永远不会关闭

软取消与硬取消怎么选：前端「停止生成」按钮直接 AbortController.abort() 断开连接，最简单也最可靠，任何实例都能生效；只有需要「保留已生成内容并由 Agent 写一句收尾」时才走软取消。

统一 SSE 事件协议

前端只认这一份协议，不认 LangGraph、LangChain 或任何模型厂商的事件格式。

线格式

  • id 等于 seq；event 等于信封里的 type，方便原生 EventSource 按类型 addEventListener。
  • 心跳与连接建立用注释帧（冒号开头），不分配 seq，前端解析时直接跳过。
  • 本协议不承诺断线续传：id 为将来基于 Last-Event-ID 的重放预留，实现重放需要把事件写入 Redis Stream 之类的存储，不在本文范围内。

信封字段

字段 类型 含义
v int 协议版本，当前为 1
type string 事件类型，见下表
traceId string 全链路追踪 ID，前端上报问题时必须带上
runId string 本次运行 ID，同时通过响应头 X-Run-Id 返回
seq long 本次运行内从 1 开始连续递增
ts long 事件产生时间（毫秒），网关补发的事件用网关时间
node string 产生事件的图节点，可为空
data object 各类型自己的负载

事件类型

type data 字段 前端处理
token text、messageId 按 messageId 追加文本；text 是增量，不是累计全文
tool_call callId、name、args 在轨迹里新增一个「进行中」的工具节点
tool_result callId、ok、elapsedMs、output 按 callId 找到对应节点并标记完成或失败
state phase、changedKeys 更新阶段指示（如「检索完成」）
error code、message、retryable 展示错误；retryable=true 时提供重试按钮
done status：completed / cancelled / failed 结束本次运行，关闭连接

协议规则

  1. 每个 run 有且只有一个 done，且一定是最后一个业务事件；error 可以出现零到多次，不一定致命。
  2. 前端收到 seq <= 已处理的最大 seq 的事件直接丢弃；连接在 done 之前关闭，一律按中断处理。
  3. 前端必须忽略未知的 type 和未知字段。新增事件类型、新增字段不升 v；删除字段或改变语义才升 v。
  4. tool_call 与 tool_result 通过 callId 配对，允许多个工具调用交错。
  5. state 不携带 State 内容；需要展示中间结果的，定义专门的事件类型并做字段级脱敏。

反例：直接把 astream_events 的原始事件 JSON.stringify 推给前端。前端会依赖 on_chat_model_stream、run_id、parent_ids 这类框架内部结构；图里多一层子图、框架升一个大版本，前端就要跟着改。文末补记里 LangGraph 与 LangChain 在 2026 年的两次流式接口变化，正好说明了这条边界的价值。

排错清单

先定位是哪一段坏了：用上文的 client_check.py 直连 Python，curl -N 分别直连 Java、经过网关、经过 Nginx，第一段出现「整块到达」「提前断开」的地方就是问题所在。

现象 常见原因 排查与修复
前端等很久后一次性收到全文 Nginx proxy_buffering、gzip；网关过滤器聚合响应体；Java 某处 collectList() / reduce；Controller 返回的不是 Flux 或缺少 produces = text/event-stream 逐段 curl -N；Nginx 关缓冲与压缩；检查 Flux 链上有无聚合操作符
Python 直连也是整块输出 节点里用的模型客户端不支持流式或关闭了流式；stream_mode 没包含 messages；token 被 STREAM_NODES 过滤 用 client_check.py 看 token 事件是否逐条出现；核对节点名
固定 60 秒左右断开 代理空闲超时（Nginx proxy_read_timeout、云负载均衡的 idle timeout） 心跳间隔小于最短空闲超时；按路径放宽读超时
长时间无事件后请求 504 响应头未提交，网关等待响应头超时 startWith 注释帧立即提交响应头
服务端认为连接还在，客户端早已离开（半开连接） 移动网络切换、NAT 表项过期，TCP 没有收到 FIN/RST SSE 层靠心跳写入失败来发现；gRPC 层靠 keepalive ping 发现，两段都要配
gRPC 连接反复被 GOAWAY，日志含 too_many_pings 客户端 keepAliveTime 小于服务端允许的最小 ping 间隔（服务端默认 5 分钟） 服务端配置 grpc.http2.min_ping_interval_without_data_ms 不大于客户端 ping 间隔，并开启 grpc.keepalive_permit_without_calls
用户点了停止，模型还在输出、还在计费 取消链某段断开：Flux 链中有 .block() 或线程池同步桥接；Flux.create 没注册 onCancel；Python 节点在 run_in_executor 线程里跑同步代码（线程无法被取消）；CancelledError 被宽泛的异常捕获吞掉 在 Python finally 与模型客户端关闭处打日志，自下而上确认每一段都收到了取消
事件乱序或重复 Python 多个协程直接写流、绕过单写者队列；Java 用了 flatMap 并发处理事件；前端重试后两次 run 的事件混在一起 所有事件经同一队列编号；Java 只用 map / concatMap；前端按 runId + seq 去重
RESOURCE_EXHAUSTED，工具结果大时出现 gRPC 默认单条消息上限 4MB 工具结果在 Python 侧截断或摘要后再上报，原文存对象存储，事件里只放引用
前端先闪过一段 JSON 再出正文 messages 模式捕获了路由或抽取节点的 LLM 输出 按 langgraph_node 白名单过滤 token

2026-09 补记：LangGraph v2 流式与 astream_events v3 的影响

本文写于 2026-01，之后两处流式接口有变化，结论是：协议层不用动，只改 Python 适配层。

LangGraph 1.1（2026-03-10）引入 version="v2" 类型安全流式。 该版本的发布说明写明：默认的 v1 行为不变，仍然产出 (stream_mode, data) 元组；显式传 version="v2" 后，stream() / astream() 产出带 type、ns、data 字段的 StreamPart 字典，每种模式有对应的 TypedDict，可以按 part["type"] 做类型收窄。上文 run_events 的改动只有解包方式：

langchain 1.3（2026-05-12）为 create_agent 构建的 Agent 提供 stream_events(..., version="v3") / astream_events(..., version="v3")。 它返回带类型化投影的运行对象：stream.messages 下每条消息有 .text、.reasoning、.tool_calls，stream.tool_calls 提供工具执行的生命周期（输入、输出增量、最终输出与错误）。对本协议的影响：

  • 如果执行面改用 create_agent，token 来自 message.text 的增量，tool_call / tool_result 来自 stream.tool_calls，不再需要在节点里手写 get_stream_writer() 上报工具事件。
  • v3 暴露了推理内容（reasoning）和工具输出增量，这两类信息在本协议里没有对应类型。按规则 3，新增 reasoning、tool_output_delta 两种事件类型不需要升协议版本，旧前端会忽略它们。
  • 自己用 StateGraph 编排的图，仍然按上文用 astream 的流模式映射即可，v3 是 langchain Agent 层的能力。

两次变化都印证了「不透传框架原始事件」的价值：前端和 Java 网关对这两次升级无感知。
