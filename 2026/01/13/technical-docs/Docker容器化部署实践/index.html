Docker 部署常见坑：挂载权限、容器代理与数据库远程访问

单机 Docker 部署的五类常见坑：挂载目录 UID/GID 与 ACL、容器访问模型 API 的代理与超时、MySQL 8 远程授权、MinIO 部署与 401、compose…

Flywhl 18 分钟 更新于 2026.09 #Docker Compose#排障#Docker

先读结论

  1. 内核只认数字 UID/GID：要么让容器以宿主机用户的 UID 运行，要么用默认 ACL，不要 chmod 777。
  2. 宿主机能访问外网不代表容器能：环境变量不会继承，代理不能只监听 127.0.0.1，应用还得读取代理变量。
  3. 官方 MySQL 镜像的环境变量只在数据目录为空时生效，改完 compose 不会改掉已有账号密码。
  4. 健康检查命令必须在镜像里真实存在，依赖关系用 service_healthy，而不是 sleep。

这篇把几个月来在单机 Docker 上反复遇到的问题按主题归并成五类。每一类都按「症状 → 根因 → 修复 → 验证」组织，先对照症状定位，再看根因决定修法，最后用验证命令确认，而不是改完重启、刷新页面看运气。

入口层（反向代理、证书、隧道）的问题在另一篇《家用服务器入口层：内网穿透 + Nginx Proxy Manager + 证书自动化》里，本文只讨论容器本身。

写作时的背景：Docker Compose 刚在 2025-12-02 从 v2.40 直接跳到 v5.0.0（跳过 3、4 是为了避免与 compose 文件格式的历史版本号混淆；同时移除了内置构建器，构建统一交给 Docker Bake）。本文涉及的 compose 语法在 v2 与 v5 上一致。

挂载目录：UID/GID 与 ACL

症状

  • 容器写入绑定挂载目录后，宿主机上看到属主是 root，或 999、1001 这类没有对应用户名的数字，日常账号无法编辑、备份脚本读不到；
  • 反过来，给容器加了 user:，或换成默认以非 root 运行的精简镜像后，容器启动报 Permission denied；
  • 修改了以单文件方式挂载的配置（./config.js:/app/config.js），不重启容器时容器里读到的仍是旧内容，应用的配置热加载永远不会触发。

根因

  1. 内核只认数字 UID/GID。容器内的 root 就是宿主机的 UID 0（未启用 userns-remap 时）；镜像内置用户也只是一个数字，例如官方 MySQL 镜像中的 mysql 是 999，很多第三方镜像默认 1001。名字不同、数字相同就是同一个用户，名字相同、数字不同就不是。
  2. 绑定挂载不做任何属主转换。命名卷在首次使用时会把镜像中该路径的内容和属主复制进卷，所以镜像作者预设的权限天然生效；绑定挂载直接用宿主机目录，属主是什么就是什么。
  3. 单文件挂载绑定的是 inode。vim、sed -i 和多数编辑器保存时会写新文件再改名替换，宿主机路径指向了新 inode，容器仍然挂着旧的那个。

修复

按能否控制容器运行用户选择：

情况 修法 注意
镜像支持以任意 UID 运行 compose 中 user: "${APP_UID}:${APP_GID}"，宿主机目录 chown 给同一 UID UID 是 bash 的 shell 变量，默认不导出，compose 读不到；把数值写进 .env 的 APP_UID / APP_GID
镜像提供 PUID/PGID 之类参数 按镜像文档设置，由入口脚本切换用户 各镜像参数名不同，以文档为准
镜像必须以 root 或固定 UID 运行 目录保持原属主，用 ACL 给日常账号授权 见下方命令
宿主机不需要直接编辑这些文件 改用命名卷 备份用 docker run --rm -v 卷名:/src ... 打包

ACL 方案需要同时设置「现有文件」和「默认 ACL」，后者决定以后新建的文件：

大写 X 只给目录和原本可执行的文件加执行位，避免把所有数据文件变成可执行。

单文件挂载的修法：挂载所在目录而不是单个文件（./config:/app/config）；或者接受「改完必须重启容器」，重启时会重新解析宿主机路径。

反例：

  • chmod -R 777：解决了今天的问题，同时让宿主机上任何进程都能改数据库文件；
  • 反复 chown -R：容器以 root 继续写，新文件还是 root，明天又要再来一次；
  • 在入口脚本里每次启动都 chown -R 大目录：数据量大时拖慢启动，还会覆盖你在宿主机上做的权限调整。

边界：

  • rootless Docker 或开启 userns-remap 后，容器内 UID 0 对应宿主机上 /etc/subuid 分配的一段高位 UID（常见如 100000 起），ls -ln 看到的是映射后的数字，user: 也要按映射关系换算；
  • SELinux 启用的发行版上，属主正确仍可能 Permission denied，需要在挂载后加 :Z（私有）或 :z（共享）重新打标签；
  • NFS 挂载若开启了 root_squash，容器内 root 写入会被映射为 nobody；
  • 精简加固类镜像（包括 2025-12 起对所有开发者免费的 Docker Hardened Images）通常默认以非 root 运行、不带 shell，这类权限问题只会更常见，事先把目录属主准备好。

验证

getfacl 输出中若某条用户 ACL 后面跟着 #effective:r--，说明被 mask 削弱了：应用创建文件时自己指定了较严的权限，或有人执行过 chmod g-w。用 setfacl -m m::rwX 恢复 mask。

容器内访问外部模型 API：代理与超时

症状

  • 应用调用模型 API 报 ETIMEDOUT、ECONNRESET 或 DNS 解析失败，同一台宿主机上 curl 正常；
  • 容器里 curl 已经能通，应用本身仍然超时；
  • 设置代理后，应用连数据库、连 MinIO 反而失败；
  • 普通请求正常，长时间的流式回答在固定时长后断开。

根因

这是四个独立问题叠在一起，要逐层排除：

  1. 环境变量不会从宿主机继承。宿主机终端里 export 的代理、桌面环境的系统代理，容器都看不到。
  2. 代理只监听 127.0.0.1。容器里的 127.0.0.1 是容器自己。宿主机上的代理程序需要监听 Docker 网桥可达的地址，并允许来自局域网或网桥网段的连接。
  3. 应用未必读取代理环境变量。HTTP_PROXY 只是约定，是否生效取决于 HTTP 库：
运行时 / 库 是否读取代理环境变量
curl 读取；但 HTTP 代理只认小写 http_proxy
Python requests / httpx 默认读取
Go net/http 默认 Transport 读取
Node.js node-fetch 与旧版本内置 fetch 都不读；v22.21 / v24 起可设 NODE_USE_ENV_PROXY=1 让内置 fetch 与 http 模块读取
Java 不读，需要 -Dhttps.proxyHost 等系统属性或在客户端代码中配置
  1. NO_PROXY 没写全。设置代理后，所有 HTTP 请求默认走代理，包括访问同一网络里的 minio:9000、内网 API，代理当然到不了这些地址。

超时则是另一回事：连接超时应该短（几秒内判定网络不通），读超时要覆盖最长的流式响应。任何一跳（应用 SDK、代理、前置的反向代理）的读超时小于响应时长，都会在固定时刻断流。

修复

把代理配置集中到一个文件，由 compose 注入（大小写各写一份，兼容只认其中一种的库）：

  • Linux 上 host.docker.internal 默认不存在，需要在服务里加 extra_hosts: ["host.docker.internal:host-gateway"]（见文末完整 compose）；
  • 宿主机代理监听 0.0.0.0 或网桥地址，并用防火墙限制只允许 Docker 网段访问，别把代理开放给整个局域网；
  • NO_PROXY 中 CIDR 写法并非所有库都支持，服务名要逐个列出；
  • docker pull 走的是 daemon 的代理（/etc/docker/daemon.json 的 proxies 或 systemd drop-in），与容器运行时的代理是两套配置，不要混为一谈。

反例：把 API 地址换成来路不明的第三方中转。它确实绕开了网络问题，但 API Key 和全部请求内容都会经过对方；确需使用，至少为它单独创建 Key 并设置额度上限。如果只是想在本地跑模型，Docker Model Runner 已于 2025-09 GA，可以完全绕开外网依赖。

验证

curl 通了而应用不通，就回到上表检查应用所用的 HTTP 库；最终以应用日志中的一次真实调用为准。

MySQL 8 远程授权与连接

症状与根因对照

报错 根因 修复方向
ERROR 2003 (HY000): Can't connect to MySQL server 端口只绑了 127.0.0.1、防火墙或安全组未放行、连错端口 检查 ports 与网络路径
ERROR 1130 (HY000): Host '10.0.0.x' is not allowed to connect 账号只存在 'user'@'localhost'，没有匹配来源地址的账号 按来源网段建账号
ERROR 1045 (28000): Access denied 密码错；或改了 compose 里的密码变量，但数据目录早已初始化 在库里 ALTER USER，而不是改环境变量
JDBC 报 Public Key Retrieval is not allowed caching_sha2_password 在非 TLS 连接上需要取服务端公钥 优先启用 TLS；可信内网可加 allowPublicKeyRetrieval=true
容器启动失败：unknown variable 'default-authentication-plugin' 镜像标签漂移到 8.4，该参数已被移除 删掉该参数，升级客户端驱动

根因展开

官方镜像的初始化逻辑决定了大部分「改了不生效」：

  • MYSQL_ROOT_PASSWORD、MYSQL_USER、MYSQL_PASSWORD、MYSQL_DATABASE 以及 /docker-entrypoint-initdb.d/ 下的脚本，只在数据目录为空时执行一次。之后再改 compose，已有账号不受影响。
  • root 账号的 host 由 MYSQL_ROOT_HOST 决定，默认就是 %；MYSQL_USER 创建的业务账号同样是 %。所以网上「手动创建 root@%」的初始化脚本在官方镜像里是多余的，远程连不上通常不是账号 host 的问题，而是端口绑定或防火墙。
  • mysql_native_password 在 8.0 中已被标记废弃，8.4 起默认禁用，--default-authentication-plugin 参数在 8.4 中被移除。为了兼容老客户端而强行切回旧插件，是在给后续升级埋雷；正确做法是升级驱动。
  • MySQL 8.0 将于 2026 年 4 月结束支持，新部署直接使用 8.4，并固定到明确的主版本标签（mysql:8.4），不要用 latest 或 8。

还有一个经常在数据库上暴露的问题：Docker 发布的端口不受 ufw 规则约束（原因与处理见入口层一文的网络隔离部分），「ufw 没放行 3306 所以安全」的判断并不成立。只把端口绑定到内网网卡地址，是最直接的控制手段。

修复

容器内的应用使用初始化时创建的 app@'%'；给局域网里的开发与运维工具单独建账号，限定来源网段与权限；root 只留给容器内使用（完整 compose 中设置了 MYSQL_ROOT_HOST: localhost，仅在首次初始化时生效）：

CREATE USER / GRANT / ALTER USER 会立即生效，不需要 FLUSH PRIVILEGES。删除 root@'%' 之前，先确认 root@'localhost' 存在且能登录。

验证

CURRENT_USER() 返回的是实际匹配到的账号（如 dev@10.0.0.%），能直接看出是否命中了预期的那一条。同名账号存在多个 host 时，MySQL 优先匹配最具体的 host，这也是「明明建了账号却用错密码」的常见来源。

MinIO 部署与 401

先了解 2025 年社区版的变化

在排障之前需要知道，MinIO 社区版在 2025 年发生了三件影响部署决策的事：

  • 2025-05-24（RELEASE.2025-05-24T17-08-30Z）：内置 Console 被替换为简化版 Object Browser，用户、策略、配置等管理页面以及 LDAP / OIDC 登录都从社区版移除。官方的建议是改用商业版 AIStor 或继续使用旧版本，日常管理改用 mc admin 命令。最后一个带完整 Console 的版本是 RELEASE.2025-04-22T22-12-26Z。
  • 2025-10-15：社区版改为只分发源码。官方预构建的二进制与 Docker Hub 镜像停在 RELEASE.2025-09-07T16-13-09Z；同日发布的安全修复版本 RELEASE.2025-10-15T17-29-55Z 没有预构建产物，需要 go install github.com/minio/minio@latest 或用仓库中的 Dockerfile 自行构建。
  • 2025-12-03：仓库进入维护模式，不再接受新功能与 PR，严重安全问题逐案评估。官方同月推出了免费的单节点版本 AIStor Free。

对部署的直接影响：

选择 代价
固定 RELEASE.2025-09-07T16-13-09Z（最后一个官方镜像） 之后的安全修复只能自行构建，需要持续关注安全公告
固定 RELEASE.2025-04-22T22-12-26Z 以保留完整 Console 错过更多安全修复，只可在内网使用
从源码构建最新版，推送到自己的镜像仓库 需要维护构建流程
迁移到 AIStor 或其它 S3 兼容实现 迁移成本；新项目应优先评估这条路

无论选哪条，都把所用镜像同步到自己可控的镜像仓库，不要假设上游会一直可以拉取。

症状

  • 容器能启动，浏览器打开 Console 输入账号密码后 POST /api/v1/login 返回 401；
  • 容器启动即退出，或 Console 端口每次重启都不一样；
  • 能登录，但找不到用户、策略等管理页面。

根因与修复

现象 根因 修复
启动即退出，日志提示凭据长度 MINIO_ROOT_USER 少于 3 个字符或 MINIO_ROOT_PASSWORD 少于 8 个字符 使用足够长的随机凭据
Console 端口随机变化，日志提示使用 --console-address 没有指定 Console 端口，或参数没被正确解析 server /data --console-address ":9001"
命令从网页复制后报 unknown flag、参数被忽略 命令里混入了不间断空格、全角空格等不可见字符 用 grep -nP '[\x{00A0}\x{3000}]' 检查并手工重打；compose 里用数组形式写 command
浏览器访问 9000 被重定向或打不开页面 9000 是 S3 API，Console 在 9001 访问 Console 端口或其反代域名
直连 9001 也返回 401 凭据错误：输错、或以为改了 compose 就改了密码 用 mc 以同一凭据登录验证（见下）

直连正常、经域名 401 或掉线 反代语义问题（Host、WebSocket 等） 见入口层一文的 MinIO 部分，不在容器侧改

先按入口层一文的方法绕过反代直连一次，确认问题在容器侧，再对照上表处理。

验证

另一个与 401 相邻的坑：应用在容器内用 http://minio:9000 生成预签名 URL，浏览器拿到后访问不了，或者改成公网域名访问时报签名不匹配。签名包含 Host，给浏览器用的预签名 URL 必须用浏览器可达的外部地址来生成，内部读写和对外签名要用两个不同 endpoint 的客户端。

compose 组织与健康检查

症状

  • depends_on 写了数据库，应用仍在启动瞬间报连接拒绝；
  • 健康检查一直 unhealthy，但服务明明能访问；
  • 修改了 compose 里的环境变量，docker compose restart 后没生效；
  • 启动时警告 version 属性已过时。

根因

  • depends_on 的默认语义是「对方容器已启动」，不是「对方服务已就绪」。MySQL 首次初始化要几十秒，期间端口不可用。
  • 健康检查命令在镜像里不存在：精简镜像往往没有 curl、wget 甚至 shell，CMD-SHELL 形式直接失败；另一种情况是检查的是 localhost，在部分镜像里解析为 ::1，而服务只监听 IPv4。
  • docker compose restart 只重启现有容器，不会应用 compose 文件的变更；需要 docker compose up -d 让 Compose 比较差异并重建容器。
  • 顶层 version: 字段早已被 Compose 规范废弃，只会产生警告，删掉即可。

修复与约定

  • 依赖关系写成 condition: service_healthy，并用 docker compose up -d --wait 等所有服务健康后再返回，适合放在部署脚本里；
  • 健康检查优先用镜像自带的工具（MySQL 用 mysqladmin ping，MinIO 用镜像内的 mc ready local），地址写 127.0.0.1；
  • mysqladmin ping 在「服务在运行但拒绝认证」时也返回 0，所以不需要把 root 密码写进健康检查；配合 -h 127.0.0.1 走 TCP，初始化阶段的临时实例不监听网络，健康检查自然不会提前通过；
  • compose 中的 $ 会被当作变量插值，需要在容器内展开的变量写成 $$；
  • start_period 给足初始化时间，start_interval（需要 Docker Engine 25 及以上）让启动期检查更频繁；
  • 端口号只能在 1–65535 之间，想避免冲突就给不需要对外的服务去掉 ports，而不是往更大的数字里挑；
  • 密码放 .env（权限 600、加入 .gitignore），上线前用 docker compose config 渲染出最终配置检查一遍。

总结

五类问题的共同点是：表面现象在应用层（权限拒绝、超时、401），根因在容器与宿主机的边界上——UID 映射、网络命名空间、初始化时机、镜像里有没有某个命令。排查时先确认「容器看到的世界」：id、env、stat、直连测试，再决定改哪里。

2026-09 补记：Compose、MinIO 与 MySQL 的后续变化

  • Docker Compose：写作后继续按新编号发布，截至 2026-09 的最新版本是 v5.5.1（2026-09-03），本文 compose 写法无需调整。
  • MinIO 彻底停止维护：2026-02-12 README 改为不再维护，随后仓库归档，mc 仓库也于 2026-07-14 归档；dl.min.io 的旧二进制下载在 2026-09 已返回 410。截至 2026-09-29 查询，Docker Hub 上的 minio/minio 仓库已不存在，quay.io/minio/minio 匿名拉取返回 401。已有主机上的镜像仍能运行，但新主机执行 docker compose pull 会失败，正文「同步到自己的镜像仓库」一条从建议变成了前提；仍在用社区版的项目应尽快完成迁移评估。
  • MySQL 8.0：已于 2026 年 4 月结束支持，官方镜像的构建清单中已不再包含 8.0，正文 compose 使用的 mysql:8.4 不受影响。
