08 · 工程规范总集：Conventions、反模式总目录与迁移策略

企业级 Skill Registry 平台工程手册 · 第 08 篇
定位：01~07 篇散落规范的收拢与补全，形成可直接进 lint / 评审模板 / 流水线配置的一册。每条规范带编号、级别（🔴阻断 / 🟡警告 / 🔵建议）与执法点（L=lint、R=评审、P=流水线、RT=运行时）。

1. 规范体系的组织原则

规范只有三种归宿：能写成代码的进 lint/流水线，需要判断的进评审清单，其余的不成为规范（写成”建议阅读”）。执法点缺失的规范等于没有规范——本册每条都标注执法点，落地时先建执法能力再宣布规范生效，顺序不可反。

2. 命名规范（N 系列）

# 规范 级别/执法
N-1 skill_ref 文法：[a-z0-9.-]+:[a-z0-9-]+，namespace ≤2 层，族内唯一（04 篇 §2.1） 🔴 L
N-2 技能名 = 能力动宾结构（ota-log-diagnosis），禁产品代号、禁版本后缀（-v2/-new/-final） 🔴 L（模式表）+ R
N-3 namespace 对齐能力域，禁技术栈（python:）、禁组织架构（dept-x:） 🔴 R（初始）+ 🟡 L（模式表）
N-4 文件命名：scripts 用动宾 snake_case（parse_logs.py），references 用名词域（ota_flow.md） 🟡 L
N-5 一个概念一个名字：manifest、SKILL.md、文档中同一实体措辞一致（别名进 aliases 字段而非正文混用） 🟡 R
N-6 vendored 技能强制 vendor.<origin>: 前缀（06 篇 §10） 🔴 P

3. 目录规范（F 系列）

# 规范 级别/执法
F-1 标准骨架：SKILL.md + manifest.json 必备；scripts/ references/ assets/ examples/ 按需，不得自创顶层目录 🔴 L
F-2 SKILL.md ≤500 行；超限必须以”层级导航 + references 下沉”重构而非删内容 🔴 L
F-3 reference >300 行必须带 TOC；按变体拆分（aws.md/gcp.md）而非合订 🟡 L + R
F-4 examples/ 必须构成执行回归对（输入样例 + 期望产物），可被流水线自动执行比对 🔴 P
F-5 README.md 面向维护者（背景/联调/发布注意），严禁复制 SKILL.md 内容——两文档读者不同 🟡 R
F-6 单文件 ≤5MB、bundle ≤200MB；大资产走外部存储 + 拉取脚本 🔴 L

4. Description 规范（D 系列，02 篇执法版）

# 规范 级别/执法
D-1 四段结构：能力陈述 + 触发场景枚举必备；有 conflicts_with 则负面边界必备 🔴 L
D-2 ≤150 L1 token；触发词用用户语言（工单语料佐证），外来术语不翻译 🔴 L（预算）/ 🟡 R（语言）
D-3 trigger_examples ≥8、negative_examples ≥4 方可发布 🔴 L
D-4 负面边界双向声明（conflicts_with 对称性） 🔴 L
D-5 pushy 子句登记制：仅评测证实欠触发者可用 🟡 P（登记核对）
D-6 禁：产品文案词、实现细节、同义反复、examples 内联 🔴 L（模式表）
D-7 能力变更（正文/脚本）必须联动 description 复核 + 触发回归 🔴 P（diff 联动检查）

5. Metadata 规范（M 系列）

# 规范 级别/执法
M-1 05 篇 §3 Schema 全量校验；未知字段拒绝（保 schema 演进主动权） 🔴 L
M-2 quality 段发布方禁填（API 层剥离） 🔴 P
M-3 capabilities 声明最小化：required_tools / data_access 按实际使用声明，多报少报皆检测（RT 偏差告警反哺） 🔴 R + RT
M-4 requires 与 conflicts_with 互斥；依赖图 DAG 🔴 L
M-5 owner 必须是团队实体（非个人账号），与 CODEOWNERS 一致 🔴 L
M-6 sandbox_profile 显式声明，禁缺省继承 🔴 L

6. Script 规范（S 系列，07 篇执行协议的作者侧）

# 规范 级别/执法
S-1 零三方依赖优先；确需依赖则锁版本 + 进 bundle 审查（禁运行时 pip install） 🟡 R / 🔴 P（安装行为扫描）
S-2 exit code 协议：0/1/2 语义遵守；业务失败必须 stderr 给模型可决策的说明 🔴 R + 回归用例
S-3 stdout 纪律：大结果落文件，stdout 只打摘要 + 路径；解析率/丢弃率等元质量信息走 stderr 🔴 R
S-4 幂等写：临时文件 + 原子 rename；重复执行安全 🔴 R
S-5 流式处理大输入：内存 O(状态) 非 O(行数)（03 篇 A.4 即范例） 🟡 R
S-6 脚本内嵌真值（码表/拓扑）必须与 reference 建立 CI 同步检查（03 篇 A.8） 🔴 P
S-7 禁网络调用（除非 profile 声明）、禁读 workspace/uploads 之外路径、禁自我修改 🔴 RT（沙箱）+ P（静态扫描）
S-8 argparse + --help 完备：模型是脚本的用户，用法即接口文档 🟡 L

7. Reference 规范（R 系列）

# 规范 级别/执法
R-1 按”变更频率”分文件：高频真值（码表/ECU 清单）独立成文走轻量发版 🔵 R
R-2 结构为”被检索而读”优化：TOC、节内自足、判据/反例/处置三段式（03 篇 SOP 范式） 🟡 R
R-3 易变数据禁入（变更频率 > 发版频率者走工具实时取，01 篇 AP-6 判据） 🔴 R
R-4 SKILL.md 必须给出”何时读哪个 reference”的路由表（03 篇第 3 步范式），禁”详见 references/“ 🔴 R

8. 评测规范（E 系列，10 篇的作者侧义务）

# 规范 级别/执法
E-1 触发评测集随技能入库（D-3 的燃料），query 必须有实质复杂度 🔴 L + R
E-2 执行回归对（F-4）比对分类/结构而非措辞 🔴 P
E-3 评测环境锁 snapshot（06 篇层 3），结果记录含 snapshot_id 🔴 P
E-4 族级 boundary-suite：任意两技能 trigger_examples 互不命中（04 篇附录 A） 🔴 P

9. 版本规范（V 系列）

# 规范 级别/执法
V-1 五维兼容性判定（05 篇 §5）自动判级；人工降级判定（MAJOR→MINOR）需平台审批 🔴 P
V-2 旧评测集回归跌幅 >10% 强制 MAJOR 🔴 P
V-3 deprecated 必填 successor_ref + migration_note + sunset_date 🔴 L
V-4 版本号只进不退；补救走新版本，不走覆盖（产物不可变的作者侧表述） 🔴 P

10. 发布规范（Rel 系列）

# 规范 级别/执法
Rel-1 全部发布经流水线（lint→评测→重叠→分级审批→签名），无人工后门；回滚同样过流水线快速通道（06 篇 AP-6） 🔴 P
Rel-2 回滚触发器目录 + 半径矩阵随首次发布提交（06 篇 §7 配套 1） 🔴 R
Rel-3 灰度默认走租户环，跳环需 elevated 审批 🔴 P
Rel-4 发布窗口：车端通道遵守 OTA 窗口与车型基线（06 篇 §9） 🔴 P
Rel-5 发布通告自动生成（版本/兼容级别/迁移说明），订阅租户可达 🟡 P

11. 测试规范（T 系列）

# 规范 级别/执法
T-1 脚本单测：核心解析/关联逻辑覆盖，含畸形输入（乱码/空文件/超大行） 🔴 P
T-2 契约测试：脚本输出 JSON 对 SKILL.md 声明的字段承诺做 schema 校验 🔴 P
T-3 端到端：examples 回归对 = 最小 e2e，每次发布必跑 🔴 P
T-4 触发测试重复 ≥3 次取率（02 篇硬规则），单次结果无效 🔴 P
T-5 破坏性测试进 elevated 评审：注入模式（SKILL.md 内越权指令）扫描自测 🟡 R

12. 文档规范（Doc 系列）

# 规范 级别/执法
Doc-1 SKILL.md 语态：对模型的第二人称指令 +条件式（禁无条件命令式，01 篇 AP-7） 🔴 R
Doc-2 错误处理与 fallback 为 SKILL.md 必备节（03 篇模板） 🔴 L（节存在性）+ R（质量）
Doc-3 “证据/结论”分界显式声明：哪些判断脚本做、哪些留给模型（03 篇 §0 模式） 🟡 R
Doc-4 边界节必备：何时移交、移交给谁 🔴 L + R
Doc-5 变更日志随版本维护，面向订阅方可读 🟡 P

14. 迁移策略

14.1 存量 Prompt 资产 → 技能化（四步法）

企业最普遍的起点：几百份散落的”提示词模板/操作文档/SOP wiki”。

14.2 单级路由 → 两级路由（规模触发）

触发条件：L1 总量逼近预算线（01 篇 §8）。迁移要点：域卡片先以既有 namespace 自动生成初稿（04 篇同构映射）→ 域卡片触发评测达标后切流 → 保留单级模式为小租户配置项（技能少的租户不该为两级路由付额外一跳）。

14.3 Monorepo → Registry-native

按 04 篇 §8.3 的方向，顺序钉死：先产物契约后仓库自由——流水线模板产品化完成前不允许任何族迁出 monorepo，否则各族 CI 立即漂移，一致性再也收不回来。

14.4 跨代模型迁移

底层模型升级换代时，技能库是平台资产中迁移成本最低的一层（自然语言指令 + 标准工具协议），但两处必须回归：触发行为分布会变（全库触发评测重跑，pushy 登记表重审——新模型欠触发特性可能减弱，存量 pushy 子句变 FP 源）；执行风格会变（examples 回归对全量重跑）。把”换模型”当作一次全库 MAJOR 事件建立标准动作清单，而不是逐技能救火。

15. 总检查清单（平台成熟度自评）

L1 起步级

  • N/F/D 系列 lint 上线，发布必经流水线
  • examples 回归对 + 触发评测集为发布门槛
  • 产物签名 + 不可变存储

L2 规模级

  • 分级审批 + owner 信誉分运转
  • 两级路由 + 补充召回 + 位置效应消偏
  • 三层版本锁 + 灰度自动推进 + 回滚演练完成
  • 反模式总目录的根治机制逐条对号入座

L3 治理级

  • 质量分驱动的 channel 自动降级提案
  • 声明-行为偏差检测（capability 审计）闭环
  • 用户语言漂移监控 → 能力缺口发现管道运转
  • air-gap / 边缘链路按需就绪
  • 跨代模型迁移动作清单演练一次

至此 01~08 篇构成原始规划的完整闭环。09（编写规范·作者视角教程化）、10（评测基准体系）、11（治理与供应链安全）、12（跨生态统一 IR）四篇为扩展卷。

规则 ID 实现方式 阻断消息示例（给 owner 的可行动文案）

Doc-1 无条件命令式模式（”总是/所有输出必须/永远”句首） “检出无条件指令 ‘所有输出必须为 JSON’：改为条件式 ‘当产出结构化结果时…’（防跨任务串味）”

Lint 消息的写作纪律本身也是规范：每条消息 = 违反了什么 + 为什么 + 怎么改，缺第三段的 lint 是给 owner 出谜题，会直接反映为发布流水线的一次通过率（平台北极星指标之一，建议目标 >70%）。

附录 C：迁移案例 Walkthrough——一份 Wiki SOP 的技能化

Before：某 wiki 页《车辆离线问题排查手册》，2,400 字——三段背景介绍、一张 T-Box 架构图、七个排查步骤（其中三步是登录某平台查数据的截图操作）、一个常见原因列表、两段”注意事项”。

四步法（§14.1）逐步执行：

  1. 盘点分级：query 聚类显示”车辆离线/T-Box/车在地图上消失”簇月均 240 次会话，入选迁移。
  2. 形态判定：整体判 a 类（完整技能）。内部再拆：七步排查 = SKILL.md 流程；架构图 + 常见原因表 = references；三步平台查数据操作 = 判定为工具缺口而非技能内容——截图操作说明该数据无 API 化入口，登记为 MCP 工具建设需求，技能第 0 步先以”引导用户导出数据文件”过渡。这一步是迁移最有价值的副产品：SOP 技能化过程系统性地暴露工具化欠账。
  3. 重写产物：

对照注记：原文 2,400 字 → SKILL.md 96 行 + references 约 180 行。删除量本身是质量信号——“注意事项”两段中一段是无条件命令式（Doc-1 违例），改写为分支内条件指令；另一段是过时的组织联系方式，属易变数据（R-3），改为指向值班系统的工具调用。
4. 影子期：beta 四周，触发率 87%（未达 90 SLO）→ 语料复查发现用户高频说法”车机上看不到车/双闪叫不醒”未入 description → 补入后 93%，转 stable，wiki 页顶部挂迁移横幅，60 天后归档。

这个案例的通用教训浓缩成一句：迁移不是格式转换，是一次强制的知识体检——背景水分、工具欠账、易变数据、无条件指令，四类沉疴在四步法里各有一步专门暴露它。

附录 D：规范生效的推行顺序（避免规范休克）

存量平台一次性启用全部 🔴 规则会冻结所有发布。推荐三波次：

每波次生效前两周开”预检模式”：lint 全跑但只警告不阻断，让 owner 看到自己的违规清单并有时间消化——规范的接受度来自可预期性，而不是强制力。

扩展卷预告：09 篇把本册规范反转为作者视角的教程（如何从零写出一次过审的技能）；10 篇建立触发/执行/回归三层评测基准；11 篇纵深治理与供应链安全；12 篇统一 IR 与跨生态编译。

附录 E：人工评审员清单（Standard / Elevated 档渲染版）

lint 管得住结构，管不住判断。评审员逐项核对（每项给出”看什么”）：

内容质量（standard 起）

  • “证据/结论”分界合理：脚本没有硬编码本该权衡的结论；模型没有被要求做本该脚本化的机械操作（看：SKILL.md 各步的动词——“计算/解析/统计”应指向脚本，”裁决/归因/权衡”应留给模型）
  • 每个 fallback 分支可执行：不是”联系管理员”这类死胡同，而是给模型可操作的降级路径（看：错误处理节逐条走一遍”然后呢？”）
  • reference 路由表与 references 实际文件一一对应，无悬空指针
  • examples 覆盖失败路径：至少一组样例走 fallback 分支而非全部快乐路径
  • 与相邻技能的让渡话术真实可用（看：negative_examples 拿去问对方技能的 trigger_examples 是否接得住）

风险面（elevated 追加）

  • scripts 逐文件读过：无混淆代码、无编码块（base64/hex 大段字面量需说明用途）、无动态代码执行（eval/exec/反序列化不可信输入）
  • SKILL.md 无越权指令模式：不指示模型绕过工具限制、不指示写入用户记忆、不指示隐瞒行为（07 篇 §8 + 06 篇 §10 扫描的人工复核层）
  • data_access 声明与脚本实际 I/O 一致（看：脚本的 open/路径拼接 vs manifest 声明）
  • 权限/工具需求升级有业务论证，且给出了不升级的替代方案评估
  • 车端/边缘 surface 声明与资源实测匹配（看：bundle 大小 vs 附录 C 配额）

评审产出纪律：结论只有三种——通过 / 打回（findings 逐条对应上表条目）/ 升级（发现超出本档的风险面转 elevated）。”有保留地通过”不是合法结论：保留意见要么是 findings（打回），要么是建议（不影响结论，进 backlog）——含糊的中间态是评审记录不可审计的头号来源。

附录 F：规范健康度看板（平台北极星）

规范体系自身也要被度量，否则它只会单调膨胀：

指标 目标 恶化含义与动作
发布流水线一次通过率 >70% 过低 = lint 消息不可行动或规范脱离实际 → 复查附录 B 消息纪律；抽样访谈 owner
单条规范的月均触发次数 长期为 0 的规范 <10% 零触发规范 = 已内化（转”建议阅读”）或从未必要（废除）——年度规范瘦身依据
波次豁免存量占比 单调递减 停滞 = 自然代谢失效，需专项迁移冲刺
评审平均周转 standard ≤2 工作日 P90 超时 = 评审员容量或清单过重 → 先扩容后砍项，顺序不可反
规范争议工单率 <5% 发布量 高争议规范进季度规范委员会复议（owner 代表 + 平台 + 安全三方）
lint 误报率（申诉成立比例） <3% 高误报直接烧掉规范公信力，优先级高于新增规则

最后一条元规范：本册自身按 V 系列管理版本——规范变更走与技能相同的评审与通告机制，🔴 级规则的增删属 MAJOR。平台对技能 owner 提出的一切纪律，先对规范自身生效；这不是姿态，而是规范公信力唯一的可持续来源。

附录 G：一个技能从零到 stable 的规范时间线

把全册规范按”何时咬合”串成作者视角的旅程（括号内为该节点生效的规范系列）：

这条时间线同时是平台工具链的验收清单：D0~持续 的每个节点都应有对应的平台能力承接（缺口清单服务、脚手架、本地 lint、评测流水线、灰度控制台、质量看板）——作者旅程里每个需要”找人/翻文档/手工操作”的节点，都是平台产品化的下一个需求。成熟的技能平台最终交付的不是规范文本，而是一条让遵守规范比违反规范更省力的路径。
