Java 生态的 Agent 框架：Spring AI、Spring AI Alibaba 与 AgentScope Java 选型

截至 2026-01，对比 Spring AI 1.1、Spring AI Alibaba 1.1 与 AgentScope Java 1.0 的定位与核心抽象…

Flywhl 15 分钟 更新于 2026.09 #架构设计#Agent#Java

先读结论

  1. Java 侧 Agent 负责贴近业务事务、权限与审计的编排；模型密集、快速试验的推理逻辑留在 Python 执行面，两边用 MCP 和 A2A 对接。
  2. Spring AI 是模型与工具的基础抽象，不提供 Agent 编排；需要状态、中断恢复和人工审批时，才引入 Spring AI Alibaba Agent Framework 或 AgentScope Java。
  3. Spring AI Alibaba 1.1 适合已有 Nacos/Higress 治理栈、以通义模型为主的团队；AgentScope Java 适合反应式栈，以及和 Python 版 AgentScope 团队共用概念的场景。
  4. 人工审批的等待时间可能跨越进程重启，生产环境的检查点必须落在 Redis/MySQL 等持久化存储上，而不是内存。

为什么 Java 团队需要原生 Agent 框架

在「Java 微服务底盘 + Python AI 执行面」的平台架构里，常有人问：既然 LangGraph、AgentScope Python 这些生态更成熟，为什么还要在 Java 侧写 Agent？

答案取决于 Agent 调用的工具离谁更近、出错时由谁负责。以车联网远程诊断为例，一次诊断会话涉及三类动作：

  • 读业务数据：车辆档案、历史工单、故障码知识库。这些数据由 Java 微服务管理，自带租户隔离和数据权限。
  • 有副作用的操作：下发远程诊断任务、创建工单、通知售后门店。这些操作要走现有的鉴权、幂等、审计和限流链路。
  • 模型密集的推理：信号时序异常检测、多份日志的归因分析、诊断报告生成。这类逻辑迭代快，依赖 Python 数据栈。

前两类如果放在 Python 侧，就得把 Java 里的权限模型、审计规则再实现一遍，或者开一个权限过大的内部 API 给 Python 调用。两种做法都会造出第二套事实来源。所以更稳妥的分工是：编排和副作用留在 Java，模型密集的推理放到 Python，两侧通过协议对接，不共享数据库。

这种分工有两个边界要守住：

放在 Java 侧 放在 Python 侧
需要事务一致性、审批或审计的步骤 需要 numpy/pandas/专用模型的分析步骤
调用存量 Java 服务的工具（直接进程内调用，不绕 HTTP） 实验频繁、Prompt 与策略每周都在变的推理链
面向终端用户的会话入口、SLA 由业务团队承担 离线评测、批量回放

反例：为了「统一技术栈」把时序异常检测也用 Java 重写，结果模型团队每次调参都要等 Java 发版。反过来，让 Python Agent 直连工单数据库写入，审计链路就断了。

三者定位与版本现状（截至 2026-01）

项目 定位 当前版本 技术基线
Spring AI Spring 官方的模型、工具、向量库、MCP 抽象层 1.1.2（2025-12-09）；2.0.0-M1（2025-12-11）已开始面向 Spring Boot 4 1.1 基于 Spring Boot 3.x
Spring AI Alibaba（SAA） 在 Spring AI 之上提供 Agent Framework、Graph 运行时和 Admin 平台 1.1.0.0（2025-12-30） Spring AI 1.1.0、Spring Boot 3.4.8、JDK 17
AgentScope Java AgentScope 的 Java 实现，面向 ReAct Agent 与多 Agent 协作 1.0.0（2025-11-30），当前 1.0.7（2026-01-14） JDK 17，基于 Project Reactor

几个版本细节会影响落地：

  • Spring AI 1.1（2025-11-12 GA）新增了 @McpTool / @McpResource / @McpPrompt 注解式 MCP 开发，MCP 传输除 STDIO 和 HTTP SSE 外支持 Streamable HTTP。另外还有 Anthropic、Bedrock 的 Prompt Caching，以及可递归调用的 Advisor。但它本身没有 Agent 类：官方把工作流、路由、编排者-执行者这些范式做成示例代码，没有做成框架抽象。
  • SAA 1.1.0.0 是一次结构重组。仓库分为 Agent Framework（ReactAgent 和 SequentialAgent / ParallelAgent / LlmRoutingAgent / LoopAgent / SupervisorAgent）、Graph（底层有状态运行时）和 Admin 三部分。DashScope 等模型接入迁到了独立仓库 spring-ai-extensions，但 Maven 坐标仍是 com.alibaba.cloud.ai。此前 1.0 线的 1.0.0.2（2025-05-29）是官方所称的首个 GA，主打 Graph、Nacos MCP Registry 和 NL2SQL。
  • AgentScope Java 与 Python 版（1.0.0 于 2025-08-15 发布）共享 ReAct、Msg、Toolkit、MsgHub 这套概念，但 API 是 Reactor 风格，call() 返回 Mono<Msg>。
  • 版本号以 Maven Central 为准。SAA 仓库在 v1.1.0.0 标签下的 README 依赖示例仍写着 1.1.0.0-RC2，而 Central 上 spring-ai-alibaba-agent-framework 与 spring-ai-alibaba-starter-dashscope 都已有 1.1.0.0。

看这张表时有三个判断要点：

  1. SAA 和 AgentScope Java 不在同一层。 SAA 构建在 Spring AI 之上，工具、模型、MCP 都复用 Spring AI 的类型。AgentScope Java 有自己的一套模型与工具抽象，和 Spring AI 的 @Tool 不能混用。已经写了一批 Spring AI 工具的团队迁到 AgentScope Java，需要把工具层重新包装。
  2. HITL 的实现方式决定审批能等多久。 SAA 的中断状态落在检查点里，只要检查点是持久化的，审批挂一夜也能恢复。AgentScope Java 的暂停状态在 Agent 实例的记忆里，跨进程恢复要配合 Session 持久化。
  3. Spring AI 缺的不只是 Agent 类。 它也没有检查点、中断和多 Agent 协议。如果需求只是「一次问答里调几个工具」，这反而是优点，依赖最少。

上面这段示例有三处容易写错：

  • 审批期间进程可能重启。 示例里的 MemorySaver 只适合单测。生产环境要用 Graph 模块自带的 RedisSaver、MysqlSaver 或 PostgresSaver，并把 threadId 与诊断工单号绑定。
  • 拒绝也要回给模型。 如果拒绝时不带原因，模型往往会换个参数再次申请。可以用 ToolFeedback 的 description 写明拒绝理由，比如「夜间禁止唤醒 ECU」，让模型改走只读路径给出结论。
  • 副作用工具自身也要做幂等。 审批只能保证「人同意了」，挡不住恢复时的重复执行。dispatchRemoteDiag 应以 threadId + ecu 作为幂等键。

Spring AI Alibaba Admin：作用与本地部署要点

Admin 的独立仓库 spring-ai-alibaba/spring-ai-alibaba-admin 于 2025-09-22 创建。按其 README（2026-01 版本）列出的功能，它是一个 Agent 开发与评估平台，不是运行时：

  • Prompt 管理：模板、版本、在线调试、多轮会话。配合应用侧的 Nacos 代理模块，可以实现 Prompt 动态下发。
  • 评测闭环：数据集（可以从 OpenTelemetry 链路直接生成）、评估器（带模板和版本）、批量实验与结果对比。
  • 可观测：接收应用上报的 OTel 链路，提供服务概览、Trace 与 Span 分析。
  • 模型配置：支持 OpenAI、DashScope、DeepSeek。

SAA 主仓库 README 对 Admin 的描述范围更大，包括可视化构建 Agent、MCP 管理、从 Dify DSL 迁移。落地前请以 Admin 仓库实际提供的功能为准来设定预期。

选型决策表

你的情况 建议 理由
在现有服务里加问答，最多调几个只读工具 Spring AI ChatClient 依赖最少；Agent 框架的检查点与中断机制用不上
多步诊断、需要中断恢复和人工审批 SAA Agent Framework HumanInTheLoopHook + 持久化检查点，现成可用
流程分支明确、希望导出流程图给业务评审 SAA Graph 条件路由和子图显式建模，可导出 Mermaid / PlantUML
以通义 / DashScope 为主，同时要兼容 OpenAI 协议模型 SAA 或 AgentScope Java 两者都内置 DashScope；Spring AI 也可以走 OpenAI 兼容接口，但厂商特性支持较少
已经用 Nacos 做配置与注册、用 Higress 做网关 SAA 优先 有 A2A-Nacos 与 Config-Nacos Starter；Higress 可托管 MCP Server，统一处理鉴权、限流和观测
WebFlux / Reactor 栈，高并发、长连接 AgentScope Java 原生 Mono / Flux，不需要把阻塞调用包装成反应式
Python 侧已在用 AgentScope，希望两侧概念一致 AgentScope Java Msg、Toolkit、MsgHub 概念与 Python 版对齐，A2A 互通
计划一年内升级到 Spring Boot 4 核心逻辑只依赖 Spring AI 接口，Agent 框架层做薄 SAA 1.1 基于 Boot 3.4.x，Spring AI 2.0 仍处于里程碑阶段，届时 Agent 框架层需要跟着迁移

两个不建议的做法：

  • 同一服务同时引入 SAA 和 AgentScope Java。 两套工具注解、两套记忆模型并存，排障时说不清哪一层吞掉了异常。需要两者时，按服务拆分，用 A2A 通信。
  • 把 Admin 当运行时依赖。 Admin 用于评测和观测，生产请求链路不应依赖它的可用性。Prompt 动态下发应以 Nacos 为准，Admin 只是编辑入口。

2026-09 补记：后续版本对选型的影响

  • Spring AI 2.0 GA（2026-06-12）：基线升级到 Spring Boot 4.0/4.1、Spring Framework 7 和 Jackson 3。工具调用移入 Advisor 链，由 ToolCallingAdvisor 负责；MCP 默认改用 Streamable HTTP，SSE 传输被弃用。之后 2.0.1 于 2026-08-21 发布，2.1.0-M1 于 2026-09-25 发布；1.1.x 仍在维护，已到 1.1.8。影响：升级是平台级迁移，Jackson 包名变化、自定义工具执行循环和 SSE 形态的 MCP 端点都要改。上文「Agent 框架层做薄」的建议依然成立。
  • AgentScope Java 2.0 GA（2026-07-10）：在 ReActAgent 之外新增 HarnessAgent，并引入 PermissionEngine、streamEvents 和 DistributedBackend，截至 2026-09 已到 2.0.3。权限引擎把上文用 Hook 手写的审批逻辑收进了框架，是反应式栈团队选它的新理由。
  • Spring AI Alibaba：1.1 线继续维护（1.1.2.0 于 2026-02-02 发布，Maven Central 上已有 1.1.2.4-security-fix）。2.0 目前只有里程碑版 2.0.0-M1.1（2026-06-25），还没有 GA。生产项目建议留在 1.1.2.x 并跟进安全修复版本，等 SAA 2.0 GA 后再与 Spring AI 2.0 一起迁移。社区的 JManus 已更名为 Lynxe。
  • Nacos 3.2.0（2026-03-27） 在 3.1.0 的 A2A Registry 基础上加入了 Skill Registry 和 Prompt Registry，注册中心已覆盖服务、MCP、A2A、Skill、Prompt。对选型的影响是，Prompt 与 Skill 的治理可以从 Admin 或应用配置里剥离出来，统一放在注册中心做版本和灰度管理，SAA 与 AgentScope Java 都能接入，框架差异对治理层的影响因此变小。
