AIHub：企业 AI 门户与 Agent 服务集成架构

通用聊天前台 + 独立 Agent 后端：门户、网关、执行三层分工，OpenAI 兼容与 Open WebUI Pipe 接入契约，前台选型…

Flywhl 27 分钟 更新于 2026.09 #云管端#架构设计#AI 门户

先读结论

  1. 门户只管交互与身份，AI 网关管路由、配额、协议转换与强制授权，LangGraph / Dify 只管执行；三层之间只用 OpenAI 兼容协议加一条原生事件流对接。
  2. Open WebUI 深度集成优先写 Pipe Function（进程内、可推状态事件），需要隔离重逻辑才上 Pipelines；两者接口不同，Pipelines 的入口是 Pipeline 类的 pipe(user_message, model_id, messages, body)。
  3. 身份以 IdP 或网关可信头为准，前台的模型可见性只是 UI 层，Agent 级授权必须在网关执行。
  4. trace_id 由网关生成并写入 traceparent，贯穿 LangGraph 节点、工具调用与 Dify 运行记录，门户只展示状态行与 trace_id，完整时间线放在后台 Trace 控制台。

企业内部的 Agent 越做越多之后，最先失控的往往不是模型效果，而是入口：每个 Agent 团队各做一套聊天页面、各管一套登录和会话历史，审计和计量散落在各处。本文给出一套「通用聊天前台 + 独立 Agent 后端」的门户架构（下文称 AIHub），覆盖分层职责、接入契约、前台选型、与若依/芋道一类 Java 管理后台的集成、Trace 贯通和部署安全边界。

写作时点为 2026-01-20，版本信息以此为准：Open WebUI 0.7.x、LibreChat 0.8.x、LobeChat 1.x、Dify 1.11 前后、LangGraph 1.0。之后的变化见文末补记。

问题定义：为什么要单独一层门户

每个 Agent 自带前端的代价

问题 表现 后果
身份分裂 每个 Agent 页面单独登录，或干脆共享一个账号 无法按人授权，离职回收靠人工
密钥外泄 前端直接持有 Dify App Key 或模型 Key Key 泄露即全量调用权限泄露
会话与审计分散 历史记录、调用日志各存一处 出了问题拼不出完整调用链
体验重复建设 流式渲染、文件上传、Markdown、代码块各写一遍 前端人力被通用能力吃掉
计量不可比 各 Agent 用各自口径统计 token 成本无法按部门分摊

Dify 官方文档明确要求 App API Key 只放在服务端、由自有后端转发调用，这一条本身就决定了「浏览器 → Agent」之间必须有一层服务端。

三层分工

层 负责 不负责 典型组件
门户（交互层） 登录、会话列表、流式渲染、文件上传、Agent 选择 任何业务推理、工具调用、密钥持有 Open WebUI、LibreChat、LobeChat、自研前台
网关（编排入口） 身份规范化、Agent 路由、配额限流、协议转换、trace_id 生成、审计 业务状态机 自研网关（FastAPI / Spring Cloud Gateway），可用 LiteLLM Proxy 起步
执行层 Agent 状态机、工作流、RAG、工具调用 用户界面、登录 LangGraph 服务、Dify、模型推理服务、MCP Server

三条约束贯穿全文：

  1. 门户不做智能。门户只把消息转发给网关、把事件渲染出来。
  2. Agent 不直接暴露。Agent 服务只在内网接受网关调用，不和浏览器直接通信。
  3. 协议收敛。门户到网关只用 OpenAI 兼容协议，另加一条原生事件流，承载 OpenAI 协议装不下的结构化步骤。

Open WebUI 0.7（2026-01-09）起具备原生 Function Calling 和内置工具（知识库、笔记、历史、网页搜索），门户本身已经能跑简单的工具型助手。边界这样划：个人生产力类的检索、问答、写作留在门户；涉及业务系统写操作、多步流程、人工审批的 Agent 一律放到网关后面的执行层。

几个关键设计：

  • 模型列表即 Agent 目录。管理后台维护 Agent 注册表（编码、显示名、路由目标 LangGraph 或 Dify、可见用户组、配额），网关的 GET /v1/models 按调用者身份过滤后返回。门户的模型下拉框因此自动变成「当前用户可用的 Agent 列表」，新增 Agent 不需要改前台。
  • 身份在网关规范化。不同前台透传用户身份的方式不同，网关把它们统一成内部头 X-AIHub-Tenant、X-AIHub-User、X-AIHub-Chat 和 W3C traceparent，执行层只认这一套。
  • 执行层可以互相调用。LangGraph 可以把 Dify 工作流当工具调用，Dify 也可以把 LangGraph 当模型调用（见下一节），但两者对外都只经过网关。

方式 耦合点 能表达什么 适合 代价

结论：网关对门户暴露 OpenAI 兼容端点作为默认契约，同时暴露一条原生事件流端点；以 Open WebUI 为主门户时，再用一个薄 Pipe Function 消费原生事件流，把步骤翻译成状态事件。MCP 只用在工具层。

契约二：原生事件流

OpenAI 协议只有 delta.content 一个正文通道，节点步骤、检索命中、工具调用、人审请求都装不下。网关另开 POST /v1/agent/runs，用命名 SSE 事件承载结构化信息，id 字段就是序号，客户端断线后可带 Last-Event-ID 续读：

kind 取值固定为 llm | retrieval | tool | decision | human，前台和 Trace 控制台都按 kind 渲染，不解析正文。这是把两份原稿里「Graph + Timeline + Event 三合一」的思路落成契约：事件本身带 span_id / parent_span_id，DAG 和时间线都能从事件流还原，不需要另存一份图结构。

LangGraph 侧：兼容适配层

LangGraph 服务本身不提供 OpenAI 兼容端点，需要一层适配。核心是三件事：会话键、流模式、断线处理。

会话状态：以前台为准还是以服务端为准

前台每次请求都会带上全量 messages，而 LangGraph checkpointer 也保存了一份线程历史，两份历史怎么对齐是这类集成里最容易出错的地方。

策略 做法 适合 风险
前台为准（无状态） 每次用全量 messages 构造输入，不设 thread_id 或每次新建 纯问答、检索类 Agent 长历史 token 成本高，需要自己截断或摘要
服务端为准（有状态） thread_id = 租户:用户:会话，只取最后一条 user 消息作为输入 多步流程、interrupt() 人审、跨轮工具状态 用户在前台「重新生成」或编辑历史消息后，两边历史分叉

采用有状态策略时，要检测分叉：比较请求中的 assistant 消息条数与线程状态中的条数，不一致就说明用户改过历史，此时以前台为准新建一个派生线程（例如 t01:u42:c009:r2），用全量 messages 重建状态。把全量 messages 直接追加进已有线程，是两份原稿里 {"input": ..., "history": messages} 写法的隐患：每轮都把历史再塞一遍，状态会成倍膨胀。

Open WebUI 侧：Pipe Function 薄适配

Pipe Function 在 Open WebUI 进程内运行，入口是 class Pipe；声明 pipes() 即成为 manifold，一个函数对外暴露多个模型，模型 id 会带上函数 id 前缀。下面这个函数消费网关的原生事件流：token 进入正文，步骤变成状态行，引用变成引用卡片。

要点：

  • 返回异步生成器即为流式；Open WebUI 会自行补 finish_reason: stop 与 [DONE]。从 pipe() 抛出的异常会显示为消息错误。
  • __event_emitter__ 支持 status、message、citation、notification 等事件类型；对纯 API 调用它是 None，必须判空。
  • 这个函数只做翻译，不做路由和鉴权；用户身份仍以网关校验为准。

Dify 放在哪一层

Dify 适合业务人员可视化维护的流程与知识库；LangGraph 适合需要代码化、可测试、有循环与人审的状态机。两者在 AIHub 中是并列的执行层，三种连接方向：

方向 做法 注意
门户 → 网关 → Dify 网关把 model 映射到 Dify 应用及其 App Key；对话型调 POST /v1/chat-messages，工作流型调 POST /v1/workflows/run Dify 没有 /models，Chatflow 不会自动出现在前台模型列表，映射只能在网关做
Dify → LangGraph 在 Dify 安装 langgenius/openai_api_compatible 插件，把 LangGraph 适配层注册为一个模型 只拿得到最终文本，LangGraph 内部步骤不会出现在 Dify 的节点日志里
LangGraph → Dify 把 Dify 工作流包装成 LangGraph 工具，response_mode: "blocking" 调用 长工作流要设超时，并把 workflow_run_id 记入 Trace

网关调用 Dify 时两个字段必须管好：user 用网关规范化后的稳定用户 id，conversation_id 由网关按 租户:用户:会话 保存映射。Dify 通过 API 产生的对话与其 WebApp 对话相互隔离，用户在两边看不到彼此的历史。

Dify 流式响应的事件名在 data 的 JSON 里（data: {"event": "message", ...}），不在 SSE 的 event: 行上。网关转换规则：

Dify 事件 转成
message、agent_message OpenAI delta.content / 原生 token
workflow_started、node_started、node_finished 原生 step（kind 按节点类型映射）
message_end finish_reason: "stop" + usage
error 流内 error 事件
ping 丢弃，由网关自己发心跳

选型建议：

  • 企业内部门户：Open WebUI。身份透传最完整，Pipe Function 能以最小代码展示执行过程。超过 50 人且要换成自有品牌时，先算清企业授权成本。
  • 面向外部用户或要白标：LibreChat。MIT 许可、SAML 与细粒度权限齐全，自定义端点可以用头部占位符把用户身份带给网关。
  • 类 Manus 的个人工作台：LobeChat 体验最好，但要把改造后的版本分发给别人，就需要商业授权。
  • 业务表单型应用（报告生成、批量翻译，这类应用不以聊天为主）：自研前台，直接调网关原生端点和 Dify 工作流，任务中心和产物中心按业务定制。
  • 不要再在管理后台里做第三套聊天页面。管理端和使用端各一套就够了。

与企业管理后台集成

若依、芋道这类 Java 管理后台已经有用户、组织、角色、菜单、审计与多租户。定位要清楚：后台是管理面，门户是使用面，网关是策略执行点。

反例：把 ruoyi-ai 一类项目的后端整个搬进芋道，或者复制它的表结构。两套都是完整体系，强行合并会得到两套权限模型和两套会话表。能复用的是业务设计（Prompt 管理、会话监控的页面思路），代码不要搬。

身份集成的三种方式

方式 做法 适合 注意
A. 独立 IdP（推荐） Keycloak、Casdoor 等 OIDC Provider 作为唯一身份源；后台和门户都是它的 client。Open WebUI 配 OPENID_PROVIDER_URL、OAUTH_CLIENT_ID / OAUTH_CLIENT_SECRET，开启 ENABLE_OAUTH_GROUP_MANAGEMENT 并用 OAUTH_GROUP_CLAIM 同步用户组 已有或愿意引入 IdP，多个系统要统一登录 后台原有账号需要迁移或与 IdP 联邦

  • 门户里的模型访问控制只决定下拉框里看得到什么，不是安全边界：用户可以拿自己的 API Key 直接调门户接口。真正的授权在网关，依据同一个组声明执行。

  • Agent 注册表、配额、Prompt 模板在后台维护，网关定时拉取或订阅变更。

菜单与入口

  • 管理后台（Vben）新增菜单：Agent 注册、模型接入、知识库、配额与计量、会话监控与 Trace 查询。
  • 门户入口用外链菜单在新标签页打开，靠 SSO 静默登录。不要用 iframe 内嵌门户：第三方 Cookie 的 SameSite 限制、X-Frame-Options / CSP frame-ancestors、WebSocket 跨域都会出问题，而且门户自身的路由和快捷键会与后台冲突。

Trace 贯通

目标：用户在门户看到的任何一条回答，运维都能凭一个 trace_id 查到它经过的网关路由、每个 LangGraph 节点、每次模型与工具调用、对应的 Dify 运行记录。

trace_id 的传递路径

环节 做法
门户 → 网关 门户一般不生成 trace；网关收到请求时生成 W3C traceparent（00-<32 位 trace-id>-<16 位 span-id>-01），已有则沿用
网关 → 门户 响应头 X-Trace-Id；原生事件流在 run.started 里也带上；Pipe Function 在完成状态行里显示，用户报障时直接截图
网关 → LangGraph 透传 traceparent；适配层写入 config["metadata"]["trace_id"] 并生成 run_id。LangChain 回调（Langfuse、LangSmith）会带上这些 metadata，能从 LLM 调用记录反查 trace
节点 → 工具 / MCP / 业务 API HTTP 调用透传 traceparent；业务系统日志打印 trace_id
网关 → Dify Dify 不接收外部 trace 上下文，网关把 task_id、workflow_run_id、conversation_id 与 trace_id 记为关联关系

后台 Trace 控制台提供 GET /api/traces/{trace_id} 与按用户、Agent、状态、时间范围的检索，页面由三部分组成：时间线（按 started_at 排列 span）、执行图（由 parent_span_id 还原，Vue 技术栈可用 Vue Flow）、节点详情（输入输出、耗时、token、错误）。

几条纪律：

  • 生产与调试分开。生产模式只记摘要、耗时、token 和状态；完整 Prompt 与工具入参只对白名单用户开启调试模式，并设置 7 天左右的过期时间。
  • Trace 也要授权。普通用户只能看自己的 trace，排障与审计角色才能跨用户查看；完整载荷访问要写审计日志。
  • 敏感字段先脱敏再落库。手机号、证件号、设备唯一标识在写入 span 之前处理，不要指望查询时再遮挡。
  • 门户里只展示状态行。两份原稿都提到通过 fork Open WebUI 的消息组件来渲染推理面板，不建议这么做：每次升级都要合并前端改动，替换 UI 还可能触及品牌保留条款。用 Pipe 的状态事件加后台控制台，就能覆盖「过程可见」和「事后可查」两个需求。

边界 规则
浏览器 ↔ 执行区 不可达。门户和前端代码中不出现 Agent 服务、Dify、模型服务的地址与 Key
门户 ↔ 网关 每个门户实例一个网关 Key；网关只信任来自门户网段且 Key 匹配的 X-OpenWebUI-* 头，其他来源的同名头一律剥离
插件代码 Functions 与 Pipelines 都是任意代码执行：只允许管理员安装，只装自己审过的代码。Pipelines 默认 API Key 为 0p3n-w3bu!，必须用 PIPELINES_API_KEY 改掉，9099 端口不出执行区
写操作工具 下发指令、改业务数据的工具必须经过 interrupt() 人工确认，确认人和确认内容写审计
出网 执行区通过出网代理访问云模型和搜索；NO_PROXY 要包含容器服务名与内网网段
多副本 Open WebUI 多副本需共享 DATABASE_URL、各副本 WEBUI_SECRET_KEY 一致、WEBSOCKET_MANAGER=redis 并配置 WEBSOCKET_REDIS_URL；网关与 Agent 服务无状态，运行状态在 checkpointer 和 Redis
SSE 链路 Ingress 与网关对 text/event-stream 关闭缓冲（Nginx proxy_buffering off 或响应头 X-Accel-Buffering: no），读超时大于 Agent 最长运行时间，网关每 15 秒左右发一次 : ping 注释行保活

常见坑

1. 按原稿写的 Pipelines 不会被加载。 原稿写成模块级 def pipe(request: dict)、返回 {"response": ...}，这不是 Pipelines 的接口。官方示例的结构是一个 Pipeline 类，入口签名固定，流式时直接返回字符串生成器或 iter_lines()：

Pipelines 容器以「OpenAI 连接」的方式加入 Open WebUI，地址填 http://pipelines:9099。

2. 流式变成一次性吐出。 链路上任何一层缓冲都会让 SSE 失效：Nginx 默认 proxy_buffering on，一些 API 网关会对响应做压缩或聚合。逐层排查时，用 curl -N 直接打网关和 Agent 服务对比。

3. 门户的后台任务触发整套 Agent。 Open WebUI 会用模型生成会话标题、标签和追问建议；如果任务模型设成「当前模型」，这些请求会打到 Agent 上，导致一次提问跑两三遍工具调用。在管理设置里把任务模型指定为一个便宜的普通模型；Pipe Function 也可以在签名中声明 __task__ 来识别这类请求。

4. thread_id 只用会话 id。 不同租户、不同门户实例的会话 id 可能重复，或者被人为构造，结果就是串会话。thread_id 必须由网关按 租户:用户:会话 拼出，Agent 服务不接受前台直接传入。

5. 把门户 ACL 当授权。 门户里隐藏某个 Agent，不等于用户调不到它。Agent 级授权与配额只能在网关执行。

6. 断线后 Agent 继续空跑。 用户关掉页面，Agent 还在调用工具、消耗 token。短任务在适配层检测 is_disconnected() 后中止；长任务改成异步 run，前台断线后凭 Last-Event-ID 从 Redis Stream 续读，页面上显式提供「取消」操作。

7. Dify 会话丢失或串号。 user 字段每次传不同的值（比如随机数或门户会话 id），会导致 Dify 找不到 conversation_id 或产生大量孤儿会话。user 用稳定的用户 id，conversation_id 的映射由网关持久化。

8. 容器代理不生效。 常见的三个原因：Docker daemon 拉镜像用的代理与容器运行时代理是两套配置；Node.js 原生 fetch 默认不读取 HTTP_PROXY 环境变量，LobeChat 要用它自己的 PROXY_URL 变量，接 OpenAI 兼容网关用 OPENAI_PROXY_URL；NO_PROXY 漏掉服务名或内网网段，导致内部调用绕到代理上，表现为变慢、登录回跳或连接失败。

2026-09 补记：2026 年的变化对选型的影响

以下是 2026-01-20 之后的变化，正文架构不变，个别选择需要调整：

  • Open WebUI 0.8（2026-02-12）：新增分析看板（按模型、用户统计 token）、按用户共享资源，以及实验性的 Skills 和 Open Responses 协议。门户侧看得到用量了，但计费仍以网关口径为准，两边口径要定期对账。
  • Open WebUI 0.9（2026-04）：桌面 App 与定时自动化。自动化任务会以用户身份定时调用 Agent，网关的配额需要区分交互调用和定时调用；0.11.4 起发往 OpenAI 连接的请求带 X-OpenWebUI-Auth-Type（jwt 为浏览器会话，api_key 为 Key 调用），可以据此区分。
  • Open WebUI 0.10（2026-06-29）：外部知识库连接、Event function 与 webhook 事件、长会话自动上下文压缩。外部知识库可以直接对接企业 RAG 服务，不必再在门户里存一份向量；上下文压缩会改写发给上游的 messages，「以前台为准」的无状态 Agent 要确认摘要后的历史仍然够用，有状态 Agent 的分叉检测不能再单纯比较消息条数。
  • Open WebUI 0.11（2026-07-27）：子代理。门户自己也有了编排能力，边界更要讲清楚：门户内的子代理用于个人生产力任务，涉及业务写操作、需要审计的流程仍然走网关后面的 LangGraph。
  • LobeHub v2.0（2026-01-27）：LobeChat 升级为 LobeHub，提供多 Agent 协作、Agent Builder、Memory 与知识库，仓库改名为 lobehub/lobehub，许可证仍是 LobeHub Community License。它作为团队工作台的竞争力明显上升，但分发衍生作品需要商业授权这一点没有变。
  • Dify 1.13（2026-02-11）与 1.16（2026-07-17）：分别带来 Human Input 节点和 Dify Agent（Beta）。人工审批可以放在 Dify 流程里完成，Dify 与 LangGraph 的能力边界也更模糊了。仍然建议把需要代码评审、单元测试、版本化的复杂 Agent 放在 LangGraph，Dify 负责业务人员能自行维护的流程。
  • MCP Apps：2026-01-26 由 MCP 官方博客宣布可用，成为首个官方扩展，并纳入 2026-07-28 规范。工具返回交互式 UI 从此有了标准路径，正文中靠自定义 citation、interrupt 事件渲染的部分，新项目可以优先评估 MCP Apps，前提是所选门户已经支持它。
