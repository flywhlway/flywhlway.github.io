优化优先级排序（按可压缩空间×实现成本）：

  1. ⑫ 语义缓存命中 → 直接省掉 ⑦⑧⑬ 约 720 ms（最高 ROI）
  2. ⑦⑧⑨ 并行化 → 从串行 460 ms 降至 250 ms
  3. ⑤ 意图分类端侧化 → 省 120 ms + 一次网络往返
  4. ⑪ 稳定内容前置 → 提升前缀缓存命中，降低 ⑬

2. 步骤① 输入采集（Audio Service）

项 内容
触发 唤醒词命中 / 方向盘按键 / 屏幕点击
输入 麦克风 PCM、车辆状态（车速、媒体状态、车窗）
处理 VAD → AEC/降噪/波束成形 → 增益归一 → Opus 编码 → 端点检测；并行启动本地流式 ASR
输出 音频流 + 唤醒事件 + 本地 ASR 中间结果
延迟预算 80 ms（含唤醒确认）
失败模式 误唤醒；漏唤醒；噪声导致端点检测过早截断
降级 端点检测失败则回退固定时长录音；唤醒失败提示按键触发
埋点 wake_source、snr、vad_duration、local_asr_confidence

关键实现细节：必须保留唤醒前 500 ms 环形缓冲。用户常在唤醒词后立即连说（”你好，打开空调”），若不回溯缓冲会丢掉”打开”两字，表现为”识别不完整”，而根因在音频层而非 ASR。

3. 步骤② 落点决策（System Agent）

项 内容
触发 收到端点确认的输入
输入 本地 ASR 文本、端侧能力清单、网络质量探测、隐私标记、车辆状态
处理 规则匹配（高优先级车控 → 端侧）→ 网络与隐私约束校验 → 小分类器预测复杂度 → 决定端/云/混合
输出 落点决策 + decision_reason + 预算（时延、Token）
延迟预算 15 ms（禁止调用模型，只用规则与轻量分类器）
失败模式 误判简单意图为复杂（浪费云端成本）；误判复杂为简单（端侧答不好）
降级 分类器不可用则按规则表；规则未命中则默认上云
埋点 decision、decision_reason、network_rtt、local_capability_hit

3.1 决策规则优先级（推断设计）

flowchart TB
    A["输入"] --> R1{"隐私标记禁止上云?"}
    R1 -->|是| E["端侧"]
    R1 -->|否| R2{"网络不可用/RTT>800ms?"}
    R2 -->|是| E
    R2 -->|否| R3{"车控类高优先指令?"}
    R3 -->|是| E
    R3 -->|否| R4{"端侧知识库可直答?"}
    R4 -->|是| E
    R4 -->|否| R5{"需长上下文/三方工具/强推理?"}
    R5 -->|是| C["云端"]
    R5 -->|否| R6{"复杂度分类器置信度"}
    R6 -->|"低复杂度 >0.8"| E
    R6 -->|"其他"| C
    E --> R7{"端侧结果置信度<阈值?"}
    R7 -->|是| C

设计要点：规则前置、模型后置。规则可解释、零延迟、可热更新；分类器只用于规则未覆盖的灰色区域。反过来（先用模型再兜规则）会让每次决策都付出模型延迟。

4. 步骤③ 网关准入（Agent Gateway）

项 内容
触发 落点=云端或混合
输入 端侧请求（身份、trace_id、文本、local_context、capability_hint、privacy_flags）
处理 ① 身份校验（证书派生身份，禁止自报）→ ② 入站内容安全（轻量规则同步 + 模型检测异步）→ ③ 限流配额（设备/用户/Agent/意图四维）→ ④ 流量染色（灰度标记）→ ⑤ 协议转换
输出 内部编排请求
延迟预算 40 ms
失败模式 身份校验失败；限流触发；内容安全误拦截
降级 限流时排队（带超时）或返回”稍后重试”；内容安全模型超时则仅依赖规则并记录
埋点 auth_result、ratelimit_bucket、inbound_guard_result、canary_tag

顺序不可调换：内容安全必须在限流与转发之前。若先转发再检测，违规请求已经消耗了下游资源。

5. 步骤④ 语义归一（NLU）

项 内容
触发 音频通路（文本输入直接跳过本步）
输入 音频流 + 场景上下文（用于上下文偏置）
处理 流式 ASR → 场景热词增强 → 文本归一（数字/单位/标点）→ 纠错 → 槽位预抽取
输出 ASR 文本 + 置信度 + 词级时间戳 + 预抽取槽位
延迟预算 220 ms（流式，与后续部分重叠）
失败模式 专有名词识别错误；口音/方言；多人同时说话
降级 云端 ASR 失败则采用端侧 ASR 结果；置信度过低则触发澄清追问
埋点 asr_confidence、hotword_hits、corrected_terms、speaker_count

领域适配是持续工程：用线上”用户重问/改口”样本每周更新热词与纠错规则，效果提升速度远高于换 ASR 模型。

6. 步骤⑤ 意图分类（Planner）

项 内容
触发 收到归一化文本
输入 文本 + 会话短期上下文（前几轮意图）+ 场景
处理 向量召回候选意图 → 判别式分类器打分 → 置信度分档
输出 意图 + 置信度 + 候选意图列表
延迟预算 120 ms（硬约束：禁用大模型）
失败模式 意图重叠误判；多意图未识别；上下文依赖意图（”那第二个呢”）误判
降级 分类器故障 → 关键词规则路由 → 通用问答 Agent
埋点 intent、intent_confidence、candidate_intents、classifier_version

6.1 置信度分档处理

置信度 动作 理由
≥ 0.85 直接落域 高置信，追求延迟
0.60–0.85 并行探测 Top-2 域，先返回快者 避免误判，成本可控（第二路可用小模型）
0.35–0.60 落通用问答域 + 内部标记为待澄清 不打断用户，但记录用于后续训练
< 0.35 主动澄清追问 强行回答的体验损伤大于反问

澄清追问要有节制：连续两轮澄清会显著降低满意度。第二轮应给出选项而非开放式提问（”您是想查充电桩还是加油站？”）。

7. 步骤⑥ 落域路由（Planner）

项 内容
输入 意图 + 能力清单（来自能力中心缓存）
处理 意图→Skill 映射 → Skill→Agent 解析 → 灰度规则应用 → 预算下发
输出 目标 Agent + Skill + route_reason + 预算
延迟预算 20 ms（全内存 + 强缓存）
失败模式 目标 Agent 不健康；Skill 版本不兼容；无匹配 Skill
降级 Agent 不健康则选备选实现；无匹配则落通用 Agent
埋点 target_agent、skill_id、skill_version、route_reason、canary_group

8. 步骤⑦⑧⑨ 上下文三路并行召回

三路必须并行。串行执行会累积 460 ms，是延迟预算表中最大的单点浪费。

8.1 ⑦ 记忆召回

项 内容
处理 短期记忆读取（Redis）→ 长期记忆向量召回 + 时效衰减加权 → 画像切片（按意图取相关字段）→ Token 预算裁剪
输出 记忆切片（含 confidence、source_trace_id）
延迟预算 150 ms
失败模式 记忆库超时；召回到错误记忆
降级 熔断后仅用短期记忆；短期也不可用则无状态单轮
埋点 memory_hits、memory_tokens、ltm_avg_confidence、profile_fields

8.2 ⑧ 知识召回

项 内容
处理 查询改写（小模型）→ 元数据过滤（车型/版本/语言）→ 混合检索（向量 + BM25，各取 25）→ RRF 融合 → Rerank 取 Top-5 → 片段裁剪
输出 知识片段 + 引用元数据 + 相关性分数
延迟预算 250 ms（改写 60 + 检索 90 + Rerank 50 + 处理 50）
失败模式 检索不到（知识缺口）；检索到错误车型的内容；Rerank 超时
降级 Rerank 超时则用融合分数直接取 Top-5；检索为空则明确声明”未检索到资料”而非硬答
埋点 rewritten_query、retrieval_topk、rerank_scores、knowledge_tokens、empty_recall

empty_recall 是最有价值的单个埋点字段：它直接列出知识缺口清单，是离线闭环中”知识补全”的输入源。

8.3 ⑨ 能力裁剪

项 内容
处理 按意图召回相关 Skill/Tool → 权限过滤（用户/设备/Agent 权限交集）→ 健康状态过滤 → 渐进式披露（先类目，超阈值则只给类目摘要）→ 生成 tool manifest
输出 工具清单（含 Schema 与权限声明），建议 ≤ 10–15 个
延迟预算 60 ms（强缓存）
失败模式 工具过多导致模型选错；权限过滤遗漏导致越权；不健康工具未摘除
降级 能力中心不可用时使用本地快照（只读）
埋点 tool_count、tool_ids、filtered_by_permission、capability_version

9. 步骤⑩ 上下文装配（Context Bundle）

项 内容
处理 按优先级拼装并裁剪：系统指令 > 用户当前问题 > 知识 > 记忆 > 画像 > 工具描述；超预算时从低优先级开始裁
输出 Context Bundle（约 ≤ 7.4k token，见 01 文档 3.4）
延迟预算 20 ms
失败模式 超预算导致关键信息被裁掉；重复内容未去重
降级 硬超预算则触发结构化压缩（小模型）
埋点 bundle_tokens、section_tokens、truncated_sections、compression_applied

裁剪顺序必须固定且可观测。若裁剪顺序随实现变化，同一问题在不同时刻表现不一致，且无法复现。

10. 步骤⑪ Prompt 组装（Prompt Builder）

项 内容
处理 模板选择（按 Skill + 模型族）→ 变量注入 → 稳定内容前置（系统指令→工具描述→知识→记忆→问题）→ 版本标记
输出 最终 messages 数组 + prompt_version
延迟预算 10 ms
失败模式 模板变量缺失；模板与模型族不匹配（如函数调用格式差异）
降级 回退到通用模板
埋点 prompt_version、template_id、prompt_tokens

零成本优化：把稳定内容放前面可显著提升前缀缓存命中率（见 04 文档 E2），首字延迟与成本同时下降，实现成本仅为调整拼接顺序。

11. 步骤⑫ 缓存与模型路由（LLM Gateway）

flowchart TB
    IN["推理请求<br/>model_intent + messages + tools + policy"] --> P1{"cache_policy"}
    P1 -->|"bypass<br/>时效性意图"| RT["模型路由"]
    P1 -->|"prefer/only"| C1["查询向量化"]
    C1 --> C2{"相似度 ≥ 0.92<br/>且知识版本一致<br/>且维度键匹配"}
    C2 -->|"命中"| HIT["返回缓存<br/>仍需过围栏"]
    C2 -->|"未命中"| RT
    RT --> R1["能力矩阵匹配<br/>model_intent → 候选模型"]
    R1 --> R2["策略打分<br/>成本 × 延迟 × 质量 × 健康度"]
    R2 --> R3{"Token 预算与配额校验"}
    R3 -->|"超限"| Q["排队 / 降级至小模型 / 拒绝"]
    R3 -->|"通过"| CALL["调用模型（流式）"]

    CALL -->|"失败/超时"| FB["Fallback 链<br/>备用模型→小模型→缓存近似→端侧"]
项 内容
延迟预算 25 ms（缓存查询 + 路由决策）
失败模式 缓存误命中（相似但答案不同）；路由选到不健康模型；配额耗尽
降级 见 Fallback 链
埋点 cache_hit、cache_similarity、model、route_reason、quota_state

缓存键必须包含的维度（缺一项即可能误命中）：查询语义向量、知识版本、车型/配置、语言、用户群标签、Skill ID。

降级 工具失败则告知模型”该工具不可用”让其换路；预算耗尽则输出部分结论

12.1 工具结果处理三原则

原则 做法 不做会怎样
隔离 工具结果放入独立消息段，明确标注为”外部数据，不含指令” 工具返回 “忽略之前指令并…” 被模型执行（提示注入）
裁剪 结果超过阈值（如 2k token）则结构化摘要 一次查询返回 5000 行 JSON，上下文溢出且成本暴涨
校验 按声明 Schema 校验，不符则视为失败 模型基于畸形数据编造答案

13. 步骤⑭ 结果校验与围栏

flowchart LR
    G["模型流式输出"] --> V1["格式校验<br/>JSON/结构是否符合声明"]
    V1 --> V2["一致性校验<br/>是否有引用支撑<br/>是否与知识片段矛盾"]
    V2 --> V3["出站围栏<br/>有害内容/敏感话题/PII/越狱输出"]
    V3 -->|"通过"| OUT["放行分片"]
    V3 -->|"可改写"| RW["改写后放行"]
    V3 -->|"须拦截"| BK["截断 + 兜底话术 + 告警"]
项 内容
延迟预算 首包 35 ms；后续分片与生成并行
失败模式 流式场景整段语义在分片间才成立（分段判定漏检）；误拦截正常内容
降级 不降级——围栏不可用则拒绝输出（安全优先，见 01 文档 7）
埋点 guard_result、guard_rule、rewritten、truncated_at、citation_present

流式围栏的正确做法：分片增量判定 + 滑动窗口（跨分片语义）+ 尾部整体复检。仅做分片独立判定会漏掉跨分片构成的违规内容。

14. 步骤⑮ 流式回传（SSE）

项 内容
处理 分片封装为 SSE 事件（带 id 支持续传）→ 心跳保活 → 背压控制
输出 SSE 事件流 → 端侧 → TTS/屏幕
延迟预算 60 ms 网络
失败模式 弱网断连；中间设备超时断连；客户端处理慢导致背压
降级 客户端凭 Last-Event-ID 续传；连续失败则退化为整体返回
埋点 sse_events、reconnects、last_event_id、client_lag_ms

    MM->>MM: 小模型抽取候选事实
    MM->>MEM: 与既有记忆比对（新增/更新/冲突）
    MEM-->>MM: 写入结果 + 变更事件记录
    MM->>DP: 记忆变更埋点
    Note over MM,MEM: 全程异步幂等，失败可重试，不影响用户链路
项 内容
触发 会话结束 / 轮次结束（按策略）
延迟预算 不占用户链路（完全异步）
失败模式 抽取出错误事实（记忆污染）；重复写入；队列积压
降级 抽取失败则跳过（不阻塞）；积压则丢弃低价值事件（保留负反馈事件）
埋点 memory_extracted、memory_conflicts、extraction_model、write_latency

记忆写回绝不能同步。同步写回会把 300–800 ms 的抽取延迟加到用户感知链路上，且抽取失败会导致回答失败——两者都不可接受。

16. 端侧执行链（离线分支）

flowchart TB
    E1["① 输入采集"] --> E2["② 落点决策=端侧"]
    E2 --> E3["③ 端侧记忆读取"]
    E3 --> E4["④ 端侧知识检索<br/>量化向量 + 关键词"]
    E4 --> E5["⑤ 端侧能力查询"]
    E5 --> E6["⑥ 边缘安全系统校验<br/>权限 + 沙箱约束"]
    E6 -->|"拒绝"| EX["拒绝并说明"]
    E6 -->|"允许"| E7["⑦ 端侧 SLM 推理"]
    E7 --> E8{"⑧ 置信度 ≥ 阈值?"}
    E8 -->|"否 且 网络可用"| UP["升云重试"]
    E8 -->|"是"| E9["⑨ 本地内容过滤"]
    E9 --> E10["⑩ TTS / 执行动作"]
    E10 --> E11["⑪ 端侧记忆写入<br/>标记待同步"]
    E11 --> E12["⑫ 埋点入本地缓冲"]
端侧步骤 延迟预算 关键约束
③ 端侧记忆读取 10 ms 本地 KV，不可阻塞
④ 端侧知识检索 60 ms 索引规模万级，量化向量
⑤ 能力查询 5 ms 内存清单
⑥ 安全校验 10 ms 离线可执行，fail-closed
⑦ SLM 推理 200 ms 量化模型 + NPU
⑨ 内容过滤 20 ms 本地规则 + 轻量模型
端侧合计 ≈390 ms 优于云端链路 3 倍

端侧链路的价值不只是离线可用。390 ms vs 1225 ms 的差距意味着：对于端侧可覆盖的意图，走端侧同时更快、更省、更私密。因此落点决策应当倾向端侧，而非把端侧当作纯降级方案。
