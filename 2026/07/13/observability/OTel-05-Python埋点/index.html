Python 埋点：FastAPI、LangGraph 与 mem0

AI 执行面的 Python 埋点：可复用的 telemetry.py、LangGraph 节点上下文修正、mem0 v2 埋点、批处理与导出失败的行为…

Flywhl 25 分钟 更新于 2026.09 #LangGraph#可观测性#Python

先读结论

  1. 开启 gen_ai_latest_experimental 后，内容捕获开关只认 span_only / event_only / span_and_event，写 true 会被静默当成不捕获。
  2. asyncio.create_task 与 asyncio.to_thread 会复制上下文；断链发生在 run_in_executor、线程池 submit 与流式响应生成器。
  3. OpenInference 不把节点 Span 设为当前上下文，节点内的手动 Span 与 chat Span 需要显式挂回节点。
  4. SDK 没有落盘缓冲，队列满丢最旧数据、导出失败重试有上限，可靠性要放在 Collector 侧。

Python 是 AI 执行面的主语言。本篇产出一个可复用的 telemetry.py 引导模块，覆盖 HTTP 层自动埋点、LLM 调用（DeepSeek，OpenAI 兼容端点）自动埋点、LangGraph 图执行埋点、mem0 手动埋点、日志与 Trace 关联、自定义业务指标，并把上下文传播、批处理导出、内容捕获这三块最容易出事故的地方讲透。文档 09 的 Demo 直接复用本篇代码。

1. 依赖安装与版本基线（uv）

版本约束的理由：

  • contrib 埋点包与 SDK 按「1.43.0 / 0.64b0」成对发布，混用不同批次会在 import 时报依赖冲突或静默缺字段，升级时整批一起升。
  • opentelemetry-instrumentation-openai-v2 仍是 beta（本文写作时最新 2.4b0），GenAI 语义约定也还在 Development 阶段，属性名会随版本变化，锁版本比追新重要。
  • mem0 2.0（2026-04-16 发布）是一次破坏性升级，第 7 节按 2.x 的 API 编写，不兼容 1.x 的写法。

埋点库选型（本文取 ① + ②）：

方案 覆盖 特点
① opentelemetry-instrumentation-openai-v2 OpenAI SDK 调用（DeepSeek 兼容端点同样生效） OTel 官方，产出 gen_ai.* Span 与两个标准指标，支持内容捕获分级
② openinference-instrumentation-langchain LangChain/LangGraph 链、图节点、工具 Arize 维护，基于 LangChain 回调，输出标准 OTel Span，Langfuse/Tempo 均可消费
③ OpenLLMetry（traceloop-sdk）/ OpenLIT 一键覆盖多框架 大而全，与 ① 同装会让每次 LLM 调用出两个客户端 Span，只能二选一

① 与 ② 同装时，同一次模型调用会出现两个 Span：② 的 LangChain 层 ChatOpenAI（openinference.span.kind=LLM）与 ① 的 SDK 层 chat deepseek-chat。两者都带 token 数，在 Tempo 里是两层视角，但在 Langfuse 里会被都识别为 generation，处理方式见文档 08。

2. 引导模块 telemetry.py（核心资产，全项目复用）

这份引导模块刻意避开了常见写法里三个会在生产中咬人的问题：

  1. 日志重复导出：instrumentation-logging 自 0.61b0 起接管了原 SDK 里的 LoggingHandler，instrument() 时默认就往 root logger 挂一个 OTLP Handler。如果再手动 addHandler(LoggingHandler(...))，每条日志会以两条记录进入 Loki。另外，root logger 已有 Handler 时，set_logging_format=True 内部调用的 logging.basicConfig() 会变成空操作，控制台里不会出现带 trace_id 的日志行。
  2. 端点写死：把 endpoint= 显式传给三个 Exporter，会盖掉 OTEL_EXPORTER_OTLP_TRACES_ENDPOINT 这类按信号区分的变量，导致「只把 Trace 分流到另一个 Collector」这种运维操作失效。
  3. 哈希标识可反查：VIN 这类标识格式固定、取值空间有限，不加密钥的 SHA-256 可以被字典穷举还原；改用 HMAC，密钥由部署环境注入。

3. FastAPI 接入

效果：每个 HTTP 请求生成一个 SERVER Span（http.route、状态码、时延），下游 httpx 调用生成 CLIENT 子 Span 并注入 traceparent 头，跨服务链路由此串联。exclude_spans 对流式接口尤其必要：SSE 每推一个分片就是一次 ASGI send，不排除的话一次长回答会在 Trace 里留下几百个 http send Span。

.env 里的 OTEL_SEMCONV_STABILITY_OPT_IN 同时带上 http，是为了和 Java Agent 对齐。不加时，FastAPI 与 httpx 埋点仍按旧版 HTTP 约定输出：Span 属性是 http.method、http.url，指标是毫秒单位的 http.server.duration / http.client.duration；加上之后改为稳定版的 http.request.method、url.full、url.path 与秒单位的 http.server.request.duration，和 Java 服务同名同单位，Collector 的过滤规则与 Grafana 大盘才能跨语言复用。

5. LangGraph / DeepAgents 图执行埋点

LangChainInstrumentor 为每次 graph.invoke/astream 生成一棵 Span 树：LangGraph → 各节点 → 节点内的 LLM 与工具调用。在此基础上补两类手动增强：整次 Agent 调用的根 Span，以及统一的工具 Span。

代码里的私有属性（com.example.vehicle.vin_hash 等）统一用反向域名前缀：app. 已是语义约定占用的官方命名空间（如 app.installation.id），官方命名指南建议私有属性用组织域名开头，实际使用时以你的组织域名替换 com.example。

in_node_span() 解决的是一个实测出来的结构问题。OpenInference 通过 LangChain 回调创建节点 Span，源码注释明确说明：回调的开始与结束不保证成对，把 Span attach 到上下文可能泄漏成后续所有 Span 的父节点，所以它只建 Span、不改当前上下文。后果是，节点内部用 start_as_current_span 建的 Span，以及 openai-v2 产出的 chat Span，都会挂到节点外层（根 Span 或 HTTP Span）下，Tempo 里看起来像节点什么都没做。包上 in_node_span() 之后，树形变为：

6. 上下文传播：原理与陷阱

6.1 原理：contextvars 决定「谁是父 Span」

OTel Python 的当前上下文存放在 contextvars 里。start_as_current_span 做两件事：创建 Span，把它写入当前上下文；退出 with 时恢复旧值。新 Span 的父节点，就是创建那一刻当前上下文里的 Span。所以判断会不会断链，只需要问一个问题：新代码执行时，拿到的是不是创建者那份上下文的副本？

6.2 哪些边界会断链

以下结果用本篇锁定的版本逐一实测：

执行方式 上下文 原因
asyncio.create_task(coro) 保留 Task 创建时复制当前上下文（PEP 567）
asyncio.to_thread(fn) 保留 内部先 copy_context() 再投递到线程池
loop.run_in_executor(pool, fn) 断链 只投递函数，不带上下文
ThreadPoolExecutor.submit(fn) 断链 同上，线程里的 Span 变成新 Trace 的根
LangChain / LangGraph 内部线程池 保留 框架自己用 copy_context().run 包装

所以「asyncio.create_task 会丢上下文」的说法不成立，真正的高发区是：同步 SDK 被丢进 run_in_executor、业务代码用 concurrent.futures 并行调工具。修复有两条路：业务代码改用 asyncio.to_thread；或者像引导模块那样启用 ThreadingInstrumentor，它会在 Thread.start、ThreadPoolExecutor.submit 时捕获并恢复上下文，上表两行断链在启用后实测全部恢复。

create_task 仍有一个需要注意的地方：fire-and-forget 的后台任务会复制「创建时」的上下文，父 Span 可能早已结束。Tempo 会照常展示，但子 Span 的时间落在父 Span 之外，读图时容易误判为时钟问题。长生命周期的后台任务（例如异步写记忆）更适合新开 Trace，并用 Span Link 指回触发它的请求。

7. mem0 记忆层手动埋点（v2 API）

mem0 没有官方 OTel 埋点，用工具 Span 包裹。按 2.x API 编写，要点有三：search() 的实体 ID 必须放进 filters（顶层传 user_id 会直接抛 ValueError）；top_k 默认值从 100 降为 20，threshold 默认 0.1；add() 改为单次 LLM 调用、只产生 ADD 事件。开源版的图记忆（enable_graph / graph_store）已移除，若旧配置里还有这两个键，升级前先删掉。

哪些子调用会自动出现在记忆 Span 下：

  • mem0 配置为 OpenAI 兼容的 LLM / Embedding Provider 时，底层走 OpenAI SDK，embeddings 与 chat Span 自动挂在 mem0_search / mem0_add 下。add() 的抽取调用会消耗 token，这部分成本在指标里与主对话混在同一个模型维度上，要拆分只能按 Trace 归因（Tempo 按父 Span 聚合，或在 Langfuse 里看）。
  • 向量库调用不会自动出现：pgvector 走 psycopg、Milvus 走 gRPC，需要另装 opentelemetry-instrumentation-psycopg 或 opentelemetry-instrumentation-grpc 才有 Span。
  • 同步版 Memory 必须在 async 代码里用时，用 asyncio.to_thread(memory.search, ...)，不要用 run_in_executor（原因见 6.2）。

8. 自定义业务指标

几条设计约束：

  • 自定义指标与属性一样使用 com.example. 前缀，避免与语义约定的命名空间冲突；单位用 UCUM 注解（{request} 这类花括号写法），经 Prometheus OTLP 接收后注解会被去掉，最终名称为 com_example_diagnose_requests_total、com_example_token_cost_total，不会带上奇怪的单位后缀。
  • 自定义直方图必须自己给桶边界。 SDK 默认桶是 0、5、10、25……10000 这组通用边界，秒级时延几乎全部落进第一个桶，P95 算出来毫无意义。openai-v2 的两个指标自带语义约定建议的桶，不受影响；上面的 explicit_bucket_boundaries_advisory 按首分片时延的常见范围设置。
  • 首分片时延直接复用语义约定里的 gen_ai.client.operation.time_to_first_chunk，将来 openai-v2 原生产出该指标时删掉手工埋点即可，大盘查询不用改。两套同时存在时，同名直方图会被重复记录，求和结果翻倍。
  • 维度只放低基数的值（模型、渠道、Agent 名），会话 ID、用户 ID 永远不进指标属性。

配合埋点库自动产生的 gen_ai.client.token.usage / gen_ai.client.operation.duration，即可在 Grafana 建立成本与时延大盘（PromQL 示例见文档 09 §6）。

9. 批处理与导出失败的处理

9.1 SDK 管道模型

三条信号的导出路径相同：业务线程产生数据 → 进入内存队列 → 后台线程攒批 → Exporter 发给 Collector。业务线程从不等待网络，代价是 SDK 必须在内存和丢数据之间做取舍。

参数（环境变量） 默认值 作用
OTEL_BSP_MAX_QUEUE_SIZE 2048 Span 队列上限
OTEL_BSP_SCHEDULE_DELAY 5000 ms 攒批间隔；队列超过一批大小时提前唤醒
OTEL_BSP_MAX_EXPORT_BATCH_SIZE 512 单批上限
OTEL_BLRP_* 同上 日志管道的对应参数
OTEL_EXPORTER_OTLP_TIMEOUT 10 单次导出（含重试）的总时限
OTEL_METRIC_EXPORT_INTERVAL 60000 ms 指标导出周期，本文设 15000

9.2 失败时实际发生什么

以 SDK 1.43 源码为准：

  • 队列满：新数据照常入队，从另一端挤掉最旧的一条，同时打一条 Queue full, dropping Span. 警告（有去重过滤，不会刷屏）。
  • Collector 不可达：gRPC Exporter 对 UNAVAILABLE、RESOURCE_EXHAUSTED、DEADLINE_EXCEEDED 等状态码做指数退避重试（1s、2s、4s……带 ±20% 抖动，最多 6 次），但总时长受 OTEL_EXPORTER_OTLP_TIMEOUT 约束，默认 10 秒内放弃这一批，并打 ERROR 日志。遇到 UNAVAILABLE 会重建 gRPC 通道。
  • 重试期间：导出线程被占住，新数据持续入队。Collector 中断超过十几秒，队列就会开始挤掉旧数据。
  • SDK 没有落盘缓冲，进程内的数据只存在内存里。

由此得出的工程结论：应用侧只负责尽快交给本机或同节点的 Collector，可靠性（持久化队列、重试、背压）放在 Collector 的 exporter 上。 不要试图通过把 OTEL_BSP_MAX_QUEUE_SIZE 调到几十万来抗后端故障，那只会把丢数据换成内存暴涨。Collector 侧的持久化队列配置见文档 10。

两个需要单独记住的差异：

  • Python SDK 把 OTEL_EXPORTER_OTLP_TIMEOUT 按秒解析，而规范与 Java SDK 按毫秒。照着规范写 10000，Python 进程会在一次导出上等将近 3 小时。多语言共用一份 Helm values 时，这个变量要按语言分开写。
  • 指标默认是累积（cumulative）时间性，某个周期导出失败，下个周期的累计值会覆盖回来，Counter 不会因此少计；Trace 与日志没有这种自愈能力。

9.3 让 SDK 自己报告丢了多少

SDK 1.42 起提供自身指标，设置 OTEL_PYTHON_SDK_INTERNAL_METRICS_ENABLED=true 后产出 otel.sdk.processor.span.processed（丢弃的数据带 error.type=queue_full）、otel.sdk.processor.span.queue.size / queue.capacity、otel.sdk.span.started 等，日志管道有对应的 log 版本。这组指标走同一个 MeterProvider，Collector 宕机时它们也发不出去，所以它回答的是「平时有没有悄悄丢」，Collector 可用性仍要靠 Collector 自身指标告警。

9.4 退出与多进程

  • TracerProvider / MeterProvider / LoggerProvider 默认 shutdown_on_exit=True，正常退出时 atexit 会冲刷队列；lifespan 里显式调用 shutdown_telemetry() 的意义是顺序可控，并且发生在 uvicorn 优雅退出窗口内。SIGKILL、OOM、容器超过 terminationGracePeriodSeconds 被强杀时，队列里的数据必然丢失。
  • uvicorn --workers N 每个 worker 独立 import 应用，各自初始化 SDK，这是正确的；BatchProcessor 也会检测 fork 后 PID 变化并重建后台线程。SDK 1.43 起每个进程自动生成 UUID 形式的 service.instance.id，Prometheus 里映射为 instance 标签，多 worker 不会写同一条序列；代价是每次重启都会产生新序列，大盘查询统一用 sum by (...) 聚合掉 instance。

10. 内容捕获开关与隐私

10.1 三套开关各管一段

来源 开关 默认 捕获什么
openai-v2 OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT 不捕获 提示词、回答、工具参数
OpenInference OPENINFERENCE_HIDE_INPUTS / _OUTPUTS / _INPUT_MESSAGES / _OUTPUT_MESSAGES 等 全部记录 链与节点的 input.value / output.value、LLM 消息
mem0 MEM0_TELEMETRY 开启 向 mem0 官方的 PostHog 上报使用统计

最容易踩的是第一行。开启 gen_ai_latest_experimental 之后，这个变量只接受四个取值：

  • no_content：不捕获（默认）；
  • span_only：写入 Span 属性 gen_ai.input.messages / gen_ai.output.messages；
  • event_only：写入日志事件 gen_ai.client.inference.operation.details；
  • span_and_event：两处都写。

早期文档里的 true 只在旧版约定（未开启实验特性）下有效。实验模式下写 true，SDK 只打一条 warning，然后按 no_content 处理。表现为「环境变量明明开了，Langfuse 里就是看不到提示词」，不少示例里的 .env 正是这样写的。

第二行是反方向的坑：即使 openai-v2 设为 no_content，OpenInference 仍会把节点输入输出和完整消息写进 Span。只关一边等于没关。

10.2 按环境分级

环境 openai-v2 OpenInference Collector
本地 / POC span_only 默认 数据只进自托管后端
测试 / 预发 span_only OPENINFERENCE_HIDE_INPUTS=true、OPENINFERENCE_HIDE_OUTPUTS=true Langfuse 管道脱敏，Tempo 管道删正文（文档 08）
生产 span_only；合规不允许正文出进程时改 no_content 或上传钩子 同上 同上

测试环境起就让正文只有一个来源：openai-v2 写 gen_ai.input.messages / gen_ai.output.messages，OpenInference 隐藏输入输出，只保留图结构。这样 Collector 的脱敏规则只需覆盖一套属性，Langfuse 里也不会同时出现两份正文。正文进入 Collector 后按管道分流：发往 Langfuse 的经过脱敏，发往 Tempo 的直接删除。

合规要求正文不能进入观测管道时，openai-v2 提供上传钩子：设 OTEL_INSTRUMENTATION_GENAI_COMPLETION_HOOK=upload 与 OTEL_INSTRUMENTATION_GENAI_UPLOAD_BASE_PATH（任意 fsspec 路径，需安装 opentelemetry-util-genai[upload]），正文写入受控的对象存储，Span 里只留引用。这样 Trace 后端的访问权限与内容的访问权限可以分开管理。

10.3 其他隐私边界

  • 业务标识进 Span 前用 pseudonymize() 做带密钥哈希；原值只允许出现在业务库里。
  • gen_ai.conversation.id 用会话 ID，不用手机号、账号这类可识别个人的值。
  • 单条 Span 属性过大（长上下文可达数十 KB）会拖慢 Collector 并撑大存储。OTEL_ATTRIBUTE_VALUE_LENGTH_LIMIT 可以截断，但截断后的 JSON 无法再被 Langfuse 解析成消息；超长上下文的场景更适合走上传钩子。
  • 私有化部署建议设 MEM0_TELEMETRY=False，避免使用数据发往外部。

  1. Grafana → Explore → Loki：{service_name="diag-agent"} |= "诊断完成"；
  2. 展开日志行，点击 trace_id 派生链接，直达 Tempo 对应 Trace；
  3. Tempo Trace 详情 → Logs for this span，反向回到 Loki。

如果第 2 步没有链接，先确认同一条日志在 Loki 里只有一份（重复导出说明还挂着手动 Handler），再检查 Grafana 数据源的 derivedFields 配置（文档 04）。

2026-09 补记：依赖升级带来的两处破坏

本文发布后，两次上游升级影响了第 1 节的依赖组合，均在隔离环境复现过：

  1. opentelemetry-util-genai 1.2b0（2026-09-24）与 openai-v2 2.4b0 不兼容。 openai-v2 2.4b0 对 util-genai 只声明了下限，新环境安装会拉到 1.2b0，import 时报 ModuleNotFoundError: No module named 'opentelemetry.util.genai.instruments'，整个 setup_telemetry() 失败。在 openai-v2 发布新版本之前，显式锁定 "opentelemetry-util-genai<1.2"；1.0b0 与 1.1b0 均验证可用。
  2. openai Python SDK 3.0（2026-08-12）之后，openai-v2 2.4b0 不再填充 server.address。 3.x 客户端的 base_url 换成了新的 URL 类型，埋点里的类型判断不再命中。Span 名称、token 用量、两个指标照常产出，但 Span 与指标都丢了 server.address，第 4 节「按 server.address 区分 Provider」的做法随之失效。第 1 节的 "openai>=2,<3" 约束正好挡住了这个问题，升级到 3.x 前需先确认埋点已适配。
