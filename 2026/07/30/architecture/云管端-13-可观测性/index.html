13 · 可观测体系（Observability）

文档类型：技术白皮书 · 可观测专章
对应图示：埋点 SDK（内嵌于 Planner 与 Cloud Agents，被圈注）+ 埋点数据回流 → 数据平台
核心判断：原图把埋点 SDK 画在模块内部而非旁挂，表达的是「默认埋点（Telemetry by Default）」——可观测是运行时的一部分，不是事后附加

1. 为什么 AI 系统的可观测与传统系统不同

维度 传统微服务 AI 平台 差异后果
失败形态 二元（成功/报错） 连续（答对/答偏/答错但流畅） HTTP 200 不代表成功，需语义级指标
成本 与请求数近似线性 与 Token 数相关，方差极大 必须按 Token 计量而非 QPS
延迟 单峰分布 长尾极重（长上下文/多轮工具） P50 无意义，必须看 P95/P99
可复现性 高（同输入同输出） 低（同输入不同输出） 需记录上下文快照才能复现
归因链路 服务调用链 服务链 + 推理决策链（思考、选工具、检索） 需记录 Agent 每步意图
质量判定 自动（断言） 需人工或模型判定 需评测体系而非单元测试

核心结论：AI 平台的可观测不是”把 OpenTelemetry 装上”，而是要额外回答三个传统系统不需要回答的问题：这次为什么这么答？成本花在哪？质量是好是坏？

3.2 必填 Span 属性

通用属性（所有 Span）：

属性 说明
trace_id / span_id / parent_span_id 链路标识
session_id 会话边界
component 模块 ID（M01–M24）
device_tier 端侧算力等级（用于分组分析）
canary_tag 灰度分组
status ok / error / degraded / blocked
degradation_level 降级层级（0 = 未降级）

llm.call Span 专属（六个必填，缺一即失去某类归因能力）：

属性 缺失后无法回答的问题
gen_ai.model 是哪个模型答的？
gen_ai.prompt_version 是哪版提示词？效果变化是提示词导致的吗？
gen_ai.usage.input_tokens / output_tokens 成本花在输入还是输出？
gen_ai.cache_hit / cache_similarity 缓存是否命中？是否误命中？
gen_ai.route_reason 为什么选了这个模型？
gen_ai.cost_tag 这笔成本该归给谁？

其他关键 Span 属性：

Span 关键属性

planner.intent intent、intent_confidence、candidate_intents、classifier_version

三个最容易漏、事后无法补齐的字段：

  1. decision_reason —— 端侧为什么没上云
  2. route_reason —— 为什么选了这个后端
  3. memory_hits 中的具体 memory_id —— 错误记忆的影响面分析依赖它（见 08 文档 5.2）

这三个字段成本极低（几十字节），但缺失后对应的问题类别永久无法归因。

3.3 Trace ID 必须端侧生成

flowchart LR
    W["❌ 常见错误：网关开始生成 trace_id"] --> W1["端侧决策不在链路内"]
    W1 --> W2["无法回答：为什么这次没上云？"]
    W2 --> W3["无法关联端侧闭环的质量数据"]
    R["✅ 正确：端侧生成 trace_id"] --> R1["端侧决策 + 云端链路 + 离线训练同一 ID"]
    R1 --> R2["端云链路完整可归因"]

端侧闭环的请求根本不经过云端网关。若 trace_id 由网关生成，则所有端侧闭环请求在可观测体系中完全不可见——而这类请求可能占总量的 30%+。

4. Metrics：指标体系

4.1 四层指标金字塔

flowchart TB
    L4["④ 业务层<br/>任务完成率 · 满意度 · 使用频次 · 留存"]
    L3["③ 质量层<br/>意图准确率 · 检索召回率 · 忠实度 · 拒答准确率 · 稳定性"]
    L2["② 服务层<br/>延迟 P95 · 成功率 · 降级率 · 缓存命中率 · 拦截率"]
    L1["① 资源层<br/>QPS · Token/s · GPU 利用率 · 连接数 · 队列长度 · 成本"]
    L1 --> L2 --> L3 --> L4

多数团队只建了 ①②，缺 ③④。结果是”系统很健康但用户不满意”——所有服务指标绿色，而回答质量在持续下降且无人察觉。

4.2 核心指标清单

延迟类（全部按 P50/P95/P99 + 分组维度）：

指标 分组维度 目标
端到端首字延迟 TTFT 落点（端/云）、意图、设备等级 云 P95 ≤1200 ms；端 P95 ≤400 ms
端到端完整延迟 同上 P95 ≤4 s
各 Span 耗时 Span 名称 见 06 文档 1.1 预算表
工具调用延迟 tool_name、mcp_server P95 ≤3 s
检索延迟 知识库 P95 ≤250 ms

成本类：

指标 分组维度 用途
Token/s 模型、Agent、意图 容量与限流
单会话平均成本 业务线、Agent、场景 成本治理
单位业务成本 业务价值单位 ROI 评估
缓存节省成本 缓存层级 缓存 ROI 证明
Top-N 消耗方 Agent、用户群 异常定位
无标签调用比例 — 治理健康度（目标 0%）

质量类：

指标 采集方式 目标
意图分类准确率 标注集 + 线上纠正样本 ≥92%
工具选择准确率 标注集 ≥90%
检索召回率 Recall@5 金标集 ≥85%
空召回率 线上埋点 ≤5%（且趋降）
忠实度（无幻觉率） 评测（LLM-as-Judge + 人工校准） ≥95%
引用准确率 评测 ≥95%
结果稳定性 同输入重复运行差异率 ≤10%
拒答准确率 评测 ≥90%

隐式反馈类（信号密度远高于点赞点踩）：

指标 含义 说明
重问率 用户在短时间内重复相似提问 最强的负反馈信号
打断率 用户打断播报 回答不对路或过长
追问轮次 达成目标所需轮次 效率指标
会话放弃率 未得到结果即退出 失败代理指标
任务完成率 达成用户目标 需结合业务信号判定
澄清触发率 需要反问的比例 意图识别质量

重问率是最被低估的指标。它无需任何标注、无需用户主动操作，且与满意度高度负相关。建立重问率看板通常能立刻暴露出几类此前完全未被发现的失败模式。

5. 上下文快照与可复现性

5.1 为什么必须存快照

AI 系统的核心难点是不可复现：同一 Trace 事后重跑，因为知识版本变了、记忆变了、模型变了，得到完全不同的结果。要复现必须固化当时的输入。

快照内容 存储 采样率
完整 Prompt（含所有上下文段） 对象存储 正常 1–5%；错误/负反馈 100%
检索命中的 chunk_id + 内容哈希 数仓 100%（ID）；内容按采样
召回的 memory_id 列表 数仓 100%
工具调用参数与返回摘要 数仓 100%
模型完整响应 对象存储 同 Prompt
各版本号（模型/prompt/embedding/capability/knowledge） 数仓 100%

只存 ID 不存内容是可接受的折中：ID + 版本号 + 内容哈希足以在需要时从当时的版本中还原内容，成本远低于全量存文本。

5.2 复现流程

sequenceDiagram

6. Logging 与审计

日志类型 内容 保留 脱敏要求
访问日志 网关请求元数据 30 天 无内容
应用日志 结构化运行日志 14 天 不含用户内容
错误日志 异常与堆栈 90 天 内容脱敏
审计日志 见 12 文档 9 90–永久 加密 + 访问审计
内容日志 Prompt 与响应 90 天（采样） PII 脱敏 + 加密 + 最小授权

日志与 Trace 的分工：Trace 回答”这次请求发生了什么”，日志回答”系统内部为什么这样处理”。AI 平台应以 Trace 为主、日志为辅——传统”翻日志排查”的方式在 AI 场景下效率极低，因为关键信息是结构化的决策与上下文，而非文本日志行。

8. 告警设计

8.1 告警分级

级别 触发条件示例 响应时限
P0 云端链路可用性 < 99%；围栏不可用；认证大面积失败 立即
P1 首字延迟 P95 > 目标 1.5×；降级率 > 5%；成本 > 预算 2× 15 min
P2 缓存命中率跌破基线 50%；空召回率突增；重问率上升 20% 1 h
P3 质量指标缓慢劣化；证书 30 天内到期；无标签调用出现 1 天

8.2 AI 平台特有的三个告警

告警 为什么特殊
降级率持续升高 系统”可用但一直在降级”是隐性故障——所有传统指标正常，用户体验在恶化
单会话成本异常 Agent 进入循环时，QPS 与错误率均正常，只有 Token 数暴涨
质量指标劣化（无技术故障） 换模型/改提示词/知识变更后效果下降，技术监控完全无感

8.3 告警反模式

反模式 后果 正确做法
只告警错误率 语义失败（答错但 HTTP 200）完全不告警 增加质量层告警
阈值静态固定 业务量波动导致误告警 基于基线的相对阈值
无分组维度 某车型/某意图劣化被整体平均掩盖 按意图、车型、Agent 分组告警
告警不带 Trace 样例 收到告警无法立即排查 告警附带典型 trace_id 列表

9. 埋点治理

9.1 Schema 集中管理

flowchart LR
    S["埋点 Schema 仓库<br/>单一权威定义"] --> G1["SDK 代码生成<br/>强类型，不可写错字段"]
    S --> G2["CI 校验<br/>新增字段需评审"]
    S --> G3["清洗层校验<br/>不符 Schema 的事件进死信队列"]
    S --> G4["数仓建模<br/>自动同步表结构"]
    S --> G5["文档自动生成"]
治理项 要求
SDK 内置 业务无需手工埋点，运行时自动产生
强类型 由 Schema 生成代码，避免字段名拼写错误
CI 校验 关键字段缺失则构建失败
死信队列 不符 Schema 的事件不静默丢弃
版本兼容 Schema 变更向后兼容，破坏性变更需版本化
覆盖率监控 Trace 完整性（各 Span 是否齐全）作为指标

9.2 成本控制

手段 说明
分层采样 骨架 Trace 100%，上下文快照 1–5%，错误与负反馈 100%
本地聚合 端侧高频事件本地聚合后上报
压缩批量 批量压缩上报，减少网络与存储
冷热分层 7 天热存储（可查询下钻），之后转冷存储
背压保护 队列积压时优先丢弃低价值事件（保留错误与负反馈）
属性裁剪 长文本只存哈希与引用，不存全文

绝不能因为成本而降低骨架 Trace 的采样率。骨架 Trace 是所有指标的计算基础，采样会导致指标失真。要省成本应从”上下文快照采样率”入手，而非骨架。

10. 技术选型

需求 首选 备选 说明
采集标准 OpenTelemetry + GenAI 语义约定 自研 SDK 标准化，避免厂商锁定
Trace 存储与查询 Langfuse / Phoenix（LLM 专用） Jaeger / Tempo LLM 专用平台原生支持 Prompt/Token 视图
指标 Prometheus + Grafana VictoriaMetrics 成熟生态
日志 Loki ELK / OpenSearch Loki 成本更低
数仓 企业既有数仓 ClickHouse / Doris 复用优先
消息队列 Kafka Pulsar / RocketMQ 高吞吐 + 分区键

10.1 LLM 专用平台 vs 通用 APM

维度 通用 APM（Jaeger 等） LLM 平台（Langfuse/Phoenix）
服务链路 ✅ 强 ⚠️ 中
Prompt/响应查看 ❌ 需自建 ✅ 原生
Token 与成本 ❌ ✅ 原生
评测集成 ❌ ✅ 原生
Prompt 版本管理 ❌ ✅ 部分
大规模服务链路 ✅ ⚠️

推荐组合：OpenTelemetry 统一采集 → 双写。服务链路进通用 APM，GenAI Span 进 LLM 专用平台。避免二选一带来的能力缺口。

    OBS --> L7["route_reason + 成本质量 → 路由策略权重调优"]
    OBS --> L8["缓存命中样本抽检 → 阈值与维度键调整"]

这张图是可观测体系的价值证明。可观测的目的不是”能看到”，而是每一类观测数据都对应一条改进闭环。若某类数据没有对应闭环，说明它可能不值得采集。

12. 风险与治理

风险 影响 治理
Trace 从网关才开始 端侧决策与端侧闭环完全不可见（可能占 30%+ 流量） trace_id 端侧生成并全链路透传；CI 校验
缺 route_reason / decision_reason 路由与落点问题永久无法归因 Schema 强制必填 + CI 校验
只有服务指标无质量指标 系统健康但用户不满意，无人察觉 建立质量层与业务层指标
埋点口径不一致 指标不可信，决策基于错误数据 Schema 集中管理 + SDK 内置 + 强类型
PII 随埋点入湖 合规风险 SDK 侧脱敏 + 清洗层二次校验 + 数据分级
埋点风暴导致成本失控 观测成本超过业务成本 分层采样 + 冷热分层 + 属性裁剪
骨架 Trace 被采样 所有指标失真 骨架必须 100%，只采样快照
无上下文快照 问题无法复现 错误与负反馈 100% 存快照
告警不带样例 收到告警无法排查 告警附 trace_id
观测数据无闭环 采了但没用，纯成本 每类数据对应明确改进闭环（见第 11 节）

13. 演进路线

阶段 可观测演进 退出准则
阶段一 OpenTelemetry + GenAI 约定接入；trace_id 端侧生成；六个 llm.call 必填属性 + 三个易漏字段；骨架 Trace 100%；SLO 与成本看板 Trace 覆盖率 100%；无字段缺失；成本可下钻到 Agent
阶段二 质量层与隐式反馈指标（重问率、打断率）；上下文快照采样；链路瀑布图（含并行标注）；降级率与成本异常告警；埋点 Schema 集中管理与 CI 校验 质量指标上看板；隐性故障可告警；埋点口径统一
阶段三 第 11 节全部八条闭环自动化；评测回归纳入 CI 门禁；观测数据驱动路由权重与落点策略自动调优；成本-质量帕累托前沿分析 观测数据全部有对应闭环；改进从人工驱动转为数据驱动
