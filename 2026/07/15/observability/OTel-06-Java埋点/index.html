Java 埋点：Spring Cloud Gateway 与 Nacos

Java 控制面埋点：Boot 3.5 与 4.0 两条版本线、Java Agent 与 Micrometer Tracing 的取舍、跨语言链路的逐跳验证、Nacos 与健康检查…

Flywhl 19 分钟 更新于 2026.09 #可观测性#OpenTelemetry#Spring Boot

先读结论

  1. Java Agent 2.x 默认走 http/protobuf，端点要指向 4318；指向 4317 会静默导出失败。
  2. Spring Boot 的默认采样率是 0.1，网关按 10% 采样会让下游 Python 服务跟着丢 90% 的 Trace。
  3. Nacos 2.x/3.x 客户端的注册、心跳、配置监听走内置的 gRPC 长连接，Agent 不会为它们生成 Span；真正的噪声大户是健康检查。
  4. Spring AI GA 版本的 log-prompt / log-completion 只写应用日志，不进 Span，属性名也仍是 gen_ai.system。

Java 控制面（网关、编排、管理服务）与 Python 执行面必须共享同一条 Trace。本篇给出两条埋点路线的配置与取舍、跨语言链路的逐跳验证方法、Nacos 与健康检查的降噪方案，以及 Spring AI 观测配置的真实行为。基准：JDK 21，按写作时点区分 Spring Boot 3.5 与 4.0 两条版本线。

1. 版本基线：两条线并存

维度 存量线 新建线
Spring Boot 3.5.x（开源支持已于 2026-06-30 结束） 4.0.x（2025-11 GA）
Spring Cloud 2025.0.x（Gateway 4.3） 2025.1.x（Gateway 5.0，2025-11-24 GA）
Spring Cloud Alibaba 2025.0.0.0（nacos-client 3.0.3） 2025.1.0.0（nacos-client 3.1.1）
Spring AI 1.1.x 2.0.x（2026-06-12 GA）
OTel 集成入口 手工组合 Micrometer 桥接与导出器 spring-boot-starter-opentelemetry
OTel Java Agent v2.29.0（写作时最新） 同左

Spring Boot 4.1 已于 2026-06 发布，但 Spring Cloud Alibaba 2025.1.0.0 的适配基线是 4.0，Nacos 体系的服务先停在 4.0.x，等 SCA 官方声明兼容再升。两条线在 OTel 层面的主要差异是 Micrometer 路线的配置键改名（见 4.2），Agent 路线的写法两条线完全一致。

2. 两条路线怎么选

维度 A. OTel Java Agent B. Micrometer Tracing 桥接
原理 -javaagent 字节码增强 Spring 的 Observation API，经 OTel 桥接导出
代码改动 零改动，只改启动参数 加依赖与配置，少量 Bean
覆盖面 200+ 库：WebFlux、Reactor Netty、JDBC、Lettuce、Kafka、gRPC、HttpURLConnection、OpenAI Java SDK 等 只覆盖接入了 Observation 的组件；new 出来的 RestTemplate / WebClient 不会传播上下文
三信号 Trace、指标、日志默认全开 Trace 与指标；日志需手动安装 Appender
默认采样 parentbased_always_on management.tracing.sampling.probability 默认 0.1
HTTP 指标命名 OTel 语义约定（http.server.request.duration，单位 s） Micrometer 的 http.server.requests，与 Python 侧不同名
Baggage 默认透传全部键 只透传 remote-fields 列出的键
Spring AI 观测 Agent 不桥接 Observation API，Spring AI 的 Span 不会出现 原生支持
版本耦合 Agent 需要覆盖你所用库的版本 随 Boot BOM 走
GraalVM 原生镜像 不支持 支持
与其他 APM Agent 共存 冲突风险高 无

决策规则：

  1. 存量服务批量接入、网关、没有 Spring AI 的服务：选 A。改动只在部署层，回滚就是去掉一个参数。
  2. 用 Spring AI 调模型的服务、原生镜像服务：选 B。
  3. 同一服务只选一条。 两条同时启用会有两套 SDK 各自创建 Span、各自导出，父子关系在两套 SDK 之间断开。
  4. 两条路线产出的都是标准 OTLP，同一集群混用没有问题，但 HTTP 指标名不同，跨服务大盘需要分开查询或用 recording rule 归一。

3. 路线 A：OTel Java Agent

3.1 获取与启动

容器化（Dockerfile 片段）：

三处容易照抄出错的地方：

  • 协议与端口必须匹配。 Agent 从 2.0 起默认协议是 http/protobuf，端点应指向 4318。沿用 1.x 时代的 http://...:4317 会把 HTTP 请求打到 gRPC 端口，Agent 只在自身日志里报导出失败，应用照常运行，很难第一时间发现。确实要走 gRPC 时，显式加 otel.exporter.otlp.protocol=grpc 再用 4317。
  • 下载地址锁版本。 releases/latest 会让两次构建拿到不同的 Agent，插桩行为随之变化。
  • 日志导出默认已开启。 2.x 的 otel.logs.exporter 默认就是 otlp，无需再显式设置；若日志已由 Filebeat 之类的采集器收走，要设为 none，否则 Loki 里会有两份。

3.2 Agent 自动覆盖的内容

  • Spring Cloud Gateway（WebFlux + Reactor Netty）入站 SERVER Span 与转发 CLIENT Span，自动透传 W3C traceparent / baggage；
  • 服务发现之后的 OpenFeign、RestTemplate、WebClient、RestClient 调用；
  • JDBC、Lettuce、Kafka 生产消费（含跨消息链路）；
  • JVM 指标（内存、GC、线程）与 HTTP 服务端/客户端时延直方图；
  • Logback/Log4j2 的 MDC 自动注入 trace_id / span_id，日志经 OTLP 发往 Collector；
  • OpenAI Java SDK 调用产出 gen_ai.* Span 与指标，内容捕获开关是 otel.instrumentation.genai.capture-message-content（默认 false，内容写入日志事件）。

Micrometer 指标在 Agent 路线下默认不导出（Agent 的 Micrometer 插桩默认关闭），如果业务自定义了 Micrometer 指标，需要加 -Dotel.instrumentation.micrometer.enabled=true。

3.3 网关路由维度

otel.instrumentation.spring-cloud-gateway.experimental-span-attributes=true 打开后，网关 Span 上会带 spring-cloud-gateway.route.id、spring-cloud-gateway.route.uri、spring-cloud-gateway.route.order。不必再手写 GlobalFilter 往 Span.current() 上写路由 ID。属性名带 experimental 前缀，升级 Agent 时留意变更日志。

  • 采样率必须显式写。 默认 0.1 意味着网关只采 10% 的请求，而下游 Python 服务的采样器是父级决定（ParentBased），跟随网关的 sampled 标志，于是整条链路 90% 的请求在两端都不会被记录。这是跨语言排障时「偶尔能查到、大多查不到」的首要原因。

4.4 线程切换与客户端构造

Micrometer 的上下文存放在 ThreadLocal 中，以下情况会断链：

  • @Async 与 AsyncTaskExecutor：注册一个 ContextPropagatingTaskDecorator Bean，Boot 会自动把它装进执行器。
  • 自己 new RestTemplate() / WebClient.create()：这样构造的客户端没有观测拦截器，不注入 traceparent。一律注入 RestTemplateBuilder、RestClient.Builder、WebClient.Builder 再构造。
  • WebFlux 中读取 MDC 或 Span.current()：默认的 limited 模式下 Reactor 算子之间不恢复 ThreadLocal，4.2 里的 spring.reactor.context-propagation: auto 就是为此设置的。

5. Spring Cloud Gateway 的链路职责

SCG 在链路中承担「入口 Span + 上下文透传」，两条路线都会自动完成 W3C Trace Context 传播。需要人工把关的有三点：

  1. 自定义 GlobalFilter 不要重建请求头。 转发时保留 traceparent、tracestate、baggage。用 exchange.getRequest().mutate() 增删单个头是安全的，整体替换 HttpHeaders 会把它们一起丢掉。
  2. 外部 baggage 不可信。 公网客户端可以随意构造 baggage 头，把伪造的 user.id 送进下游和 Langfuse。路线 A 的 Agent 在请求进入 WebFlux 之前就已经把入站 baggage 解析进上下文，在 GlobalFilter 里删头已经来不及，必须在网关之前的边缘代理上剥离；路线 B 只透传 remote-fields 白名单里的键，天然收窄了范围。无论哪条路线，下游消费端也只读白名单键（见文档 08 的 Baggage 白名单一节）。
  3. 业务标识由网关在鉴权之后写入。 user.id 用哈希值，session.id 用会话 ID，Python 侧与 Langfuse 都从这里取值。

6.3 断链时按症状定位

症状 最可能的原因
两个服务各有一条 Trace，trace id 不同 网关到 Python 之间有未透传头的中间层（Nginx、自研代理），或 GlobalFilter 重建了请求头
trace id 相同但 Python 段挂在根上 Python 侧在 extract 之前就创建了 Span（例如在中间件之外手动建 Span）

Python 日志 trace_sampled=False 上游传来的 sampled 标志为 0，问题在上游采样，不在 Python

7. Nacos 与健康检查降噪

7.1 先确认噪声来源

流传较广的「Nacos 心跳产生大量 Span、关闭 okhttp 插桩即可」的说法与当前版本不符，按客户端版本区分：

  • nacos-client 2.x / 3.x（SCA 2025.x 系列即 3.x）：服务注册、心跳、订阅推送、配置监听都走 gRPC 长连接，而这套 gRPC 被重新打包在 com.alibaba.nacos.shaded.io.grpc 下，Agent 的 gRPC 插桩匹配的是原始包名，不会为它们生成 Span。剩下的只有鉴权登录之类的零星 HTTP 调用。
  • nacos-client 1.x（遗留系统）：心跳是每 5 秒一次的 HTTP 请求（/nacos/v1/ns/instance/beat），配置监听是 30 秒挂起的长轮询（/nacos/v1/cs/configs/listener），经 JDK HttpURLConnection 发出，每一次都会成为一条独立的 CLIENT 根 Span，这才是真正的噪声。
  • Nacos 客户端不使用 OkHttp，关闭 okhttp 插桩对它没有任何作用；otel.instrumentation.common.default-enabled 默认值本来就是 true，写上也没有效果。

7.4 不建议的做法

  • 关闭 http-url-connection 插桩：会连带丢掉业务里所有经 HttpURLConnection 发出的调用。
  • 在网关用正则排除所有 /actuator 以外的路径：维护成本高，新接口上线就会漏。

网上常见的两种说法与现行版本不符：

  1. 提示词和回答不会进 Span。 log-prompt / log-completion 只是把内容写进应用日志（日志带 trace 信息，可以从 Trace 跳过去）。早期里程碑版本中把内容写成 Span 属性的 ChatModelPromptContentObservationFilter 在 1.0.0-RC1 已移除，网上照抄的 Bean 注册写法会直接编译失败。确实需要在 Langfuse 里看到 Java 侧的提示词，要么自定义 ObservationFilter 从 ChatModelObservationContext 取内容写入高基数键值，要么把调模型的逻辑放在 Python 执行面统一处理。
  2. 属性与 Python 侧并不同构。 Spring AI 的 Span 用的是 gen_ai.system，Python 侧开启最新实验约定后是 gen_ai.provider.name；工具内容的键是 spring.ai.tool.call.arguments / spring.ai.tool.call.result；指标由 Micrometer 产出（gen_ai.client.operation 计时器、gen_ai.client.token.usage 计数器），Python 侧的同名概念是 OTel 直方图。查询语句不能直接复用。

9. 验收清单

  • 固定 traceparent 的请求在 Tempo 中同时出现 scg-gateway 与 diag-agent，逐跳父子关系正确；
  • 不带 traceparent 连发 20 次，Tempo 中有 20 条 Trace（采样率已显式设为 1.0 或由 Agent 默认全采）；
  • Grafana 服务拓扑（Tempo service graph）出现 scg-gateway → diag-agent 边；
  • Loki 中 Java 日志携带 trace_id，与 Tempo 双向互跳成功，且每条日志只有一份；
  • Prometheus 中有网关的 HTTP 服务端时延指标（路线 A 为 http_server_request_duration_seconds_*）与 JVM 指标；
  • /actuator/* 与 Nacos 相关 Span 已按 7.2 或 7.3 处理，TraceQL 复查为空；
  • 网关之前的边缘代理已剥离外部 baggage 头。

2026-09 补记：规则采样器将被替换

2026-09-26，opentelemetry-java-instrumentation 主干合入了一项弃用：Agent 与 Spring Boot Starter 内置的声明式 rule_based_routing 采样器被标记为 deprecated，计划在 3.0 移除，官方建议迁移到 SDK 孵化模块中的组合式规则采样器（配置路径 composite/development 下的 rule_based），两者的配置结构与匹配行为并不相同。该变更随 v2.31.1 之后的版本发布，届时启用 7.2 的配置会在启动日志中看到弃用警告。7.2 的写法在 2.x 期间仍然可用；新服务如果准备直接上组合式采样器，注意它仍带 /development 后缀，属于实验特性，升级 Agent 时要重新验证。
