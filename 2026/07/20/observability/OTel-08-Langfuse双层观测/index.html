Langfuse 双层观测融合

一次埋点、双端消费：Collector 扇出到 Tempo 与 Langfuse，Langfuse 管道补上过滤与脱敏，Baggage 改为白名单…

Flywhl 15 分钟 更新于 2026.09 #可观测性#OpenTelemetry#Langfuse

先读结论

  1. 发往 Langfuse 的管道必须单独过滤和脱敏，Tempo 管道则去掉消息正文，内容只保留一份。
  2. BaggageSpanProcessor 放行全部键，等于允许外部请求往 Langfuse 写任意属性；只放行 session.id、user.id。
  3. 采样只裁决一次：尾采样放在扇出之前，两个后端才能看到同一批 Trace。
  4. 同一次模型调用可能在 Langfuse 里出现两到三个 generation，对账前先去重。

目标：一次埋点，双端消费。同一份 Trace 同时进入 Tempo（系统层：延迟、错误、依赖、SLO）与 Langfuse（AI 业务层：Prompt、会话、成本、评测），两层通过 trace_id 与会话属性互相印证。除了管道搭建，本篇重点讲三块容易被忽略的内容：Langfuse 管道的脱敏、Baggage 的白名单、两层数据的采样一致性与对账。

1. 分工模型

维度 LGTM（系统层） Langfuse（AI 业务层）
核心问题 慢在哪、错在哪、依赖谁 答得好不好、贵不贵、哪个 Prompt 版本更好
数据粒度 全服务 Span（HTTP、DB、MQ、LLM） AI 语义 Span（Agent、节点、工具、模型调用）
特色能力 服务拓扑、TraceQL、日志与指标联动、告警 会话回放、成本核算、Prompt 管理、评测与标注、数据集回归
使用者 SRE / 平台工程 AI 工程师 / 产品 / 算法

反模式：用 Langfuse 看微服务拓扑，或用 Grafana 做 Prompt 评测。每层做擅长的事，两层之间只靠 trace_id 和会话 ID 关联。

2. 双层架构的取舍

方案 密钥位置 过滤与脱敏 采样一致性 故障影响 结论
A. Collector 扇出 只在 Collector 集中在 Langfuse 管道 可在扇出前统一裁决 Langfuse 不可用只影响其管道（见 4.4） 推荐
B. 应用内双 Exporter 散落在每个服务 每个服务各写一套 各服务自行保证 应用进程直接受 Langfuse 延迟影响 不推荐
C. 应用改用 Langfuse SDK 散落在每个服务 SDK 的掩码回调 与 OTel 采样分离 同 B 与厂商绑定，本系列不采用
D. 只保留一层 — — — — 失去另一层能力

A 的额外收益是「内容只存一份」：消息正文只进 Langfuse（经过脱敏），Tempo 管道把正文属性删掉。Trace 后端的访问面通常比 Langfuse 宽得多，正文不该出现在那里。

3. Langfuse 作为 OTLP 后端的约束

  • 端点：{LANGFUSE_HOST}/api/public/otel，Trace 专用路径 /api/public/otel/v1/traces；自托管需 ≥ v3.22.0。
  • 协议：只支持 OTLP/HTTP（protobuf 与 JSON），不支持 gRPC；只消费 Trace，Collector 里不要把 metrics / logs 管道指向它。支持 gzip 压缩。
  • 认证：Basic Auth，base64(pk-lf-...:sk-lf-...)。
  • 实时性请求头：官方文档（2026-07）说明，Langfuse Cloud 的 Fast Preview（v4 数据模型）需要额外带 x-langfuse-ingestion-version: 4 才能实时可见；本系列自托管的是 v3（文档 04 锁定 LANGFUSE_VERSION=3），不需要这个头。
  • trace_id：Langfuse 直接使用 OTel 的 trace_id，两边可以用同一个 ID 互查。
  • 观测类型判定：带 gen_ai.operation.name=chat、openinference.span.kind=LLM 的 Span 会被识别为 generation；没有明确标注时，只要带 gen_ai.request.model、llm.model_name 或裸的 model 属性，也会按 generation 处理。这条兜底规则是后面「重复计费」问题的根源。
  • 会话与用户：session.id（或 gen_ai.conversation.id、langfuse.session.id）映射为会话，user.id 映射为用户，deployment.environment.name 映射为环境。
  • Trace 根：没有父 Span 的那个 Span 决定 Trace 的名称与输入输出。根被过滤掉时，Langfuse 只建一个空壳 Trace，靠其他 Span 上的 session.id、user.id、langfuse.trace.name 等 Trace 级属性补全归属。

端口规划与文档 03、04 保持一致：

组件 宿主机访问 容器网络内访问
Grafana http://localhost:3000 grafana:3000
Langfuse Web http://localhost:3001 langfuse-web:3000
Collector OTLP localhost:4317（gRPC）/ 4318（HTTP） otel-collector:4317 / 4318
Tempo http://localhost:3200 tempo:3200
Prometheus http://localhost:9090 prometheus:9090

Langfuse 在容器内监听 3000，映射到宿主机 3001，避开 Grafana。Collector 在容器网络里访问 langfuse-web:3000，宿主机上的脚本和浏览器访问 localhost:3001，两个端口都对，别混用。

4.2 过滤规则为什么这样写

filter/langfuse-scope 的两条条件满足任意一条即丢弃：

  1. 没有 AI 语义的 Span 不进 Langfuse：HTTP、数据库、ASGI 内部 Span 在 Langfuse 里只是噪声。按属性判断而不是按 Span 名单判断，新增 Agent 不用改配置。Higress 网关 Span 没有 gen_ai.operation.name，也在这一步被挡住，避免它的 model 属性触发兜底规则变成第三个 generation。
  2. 同一次模型调用只保留一层：文档 05 的埋点组合里，一次调用会同时产生 OpenInference 的 ChatOpenAI（LLM）和 openai-v2 的 chat deepseek-chat，两个都会被 Langfuse 识别为 generation，token 和成本翻倍。这里保留 openai-v2 这一层，因为它遵循 GenAI 约定，并且是文档 05 生产配置里唯一携带正文的来源。

第 2 条的前提是所有模型调用都经过 OpenAI SDK。如果某个 LangChain 组件用了别的 Provider SDK（openai-v2 覆盖不到），它只有 OpenInference 这一层，按这条规则会被整条丢掉；这时改为保留 OpenInference 层、丢弃 openai-v2 层。

4.3 脱敏规则的边界

  • 先规范化，再匹配。 openai-v2 写入 gen_ai.input.messages 时用的是 ASCII 转义的 JSON，「我手机13812345678」在属性里是 \u6211\u624b\u673a13812345678：号码前一个字符是转义序列末尾的 a，属于单词字符，\b 边界不成立，手机号原样漏过。把一句带手机号的中文问题送进 openai-v2 就能复现。去掉 \b 也不行：VIN 规则会从转义序列中间开始匹配，把 \u53f7 切坏成非法 JSON，Langfuse 就解析不了整条消息。ParseJSON 加 String 把两个消息属性重新序列化成 UTF-8 文本之后，\b 在中文与数字之间成立，三条规则都能精确命中，20 位的订单号也不会被误伤。
  • 规则顺序：身份证号（18 位）先于 VIN（17 位）、VIN 先于手机号（11 位），长规则先吃掉整段，短规则不会在长号码内部误中。
  • 作用范围：replace_all_patterns(span.attributes, "value", ...) 作用于所有字符串属性值，覆盖 OpenInference 的 input.value 等位置，不用逐个列键名。OpenInference 写入的 JSON 本身不转义中文，不需要规范化。
  • 失败时的行为：error_mode: ignore 下，解析失败（例如属性被截断成非法 JSON）只跳过该条语句，后面的正则照常执行，但只能在转义文本上匹配，可能漏。所以文档 05 建议不要靠 OTEL_ATTRIBUTE_VALUE_LENGTH_LIMIT 截断正文。
  • 定位：正则是兜底而不是第一道防线，业务标识在应用侧就应该用 pseudonymize() 哈希（文档 05）。规则变更要带样本回归：把脱敏后的真实会话整理成样本集，覆盖转义与非转义两种写法，每次改规则跑一遍对比。
  • Tempo 管道删除的是正文属性；如果系统层也需要保留正文用于排障，同样要挂这组处理器，不能只保护 Langfuse 一侧。

4.4 两条管道的故障隔离

扇出之后，每条管道有自己的 batch 处理器和发送队列。batch 与 tail_sampling 都是先接收、后异步下发，下游导出失败不会回传给客户端 SDK，所以 Langfuse 宕机既不会拖慢应用，也不会影响 Tempo 管道。代价是 Langfuse 这一侧会丢数据：发送队列在重试期间持续积压，满了之后新数据被丢弃，只留下日志和计数。因此要做三件事：

  • sending_queue 按「Langfuse 最长维护窗口 × 峰值 Span 速率」估算容量，不要沿用默认值；
  • 监控 Collector 自身指标里 exporter="otlphttp/langfuse" 的发送失败与入队失败计数（指标名与告警规则见文档 10），入队失败一出现就说明队列已满；
  • 生产上给 Langfuse exporter 挂持久化队列（file_storage），Collector 重启也不丢积压（见文档 10）。

4.5 备选：应用直连（仅本地调试）

tr -d '\n' 不能省：GNU coreutils 的 base64 默认每 76 个字符换行，Langfuse 的公私钥拼接后编码超过这个长度，换行符混进请求头会直接鉴权失败。直连没有过滤和脱敏，只用于快速验证。

5. 会话与用户维度：Baggage 白名单

user.id、session.id 只打在根 Span 上，Langfuse 里按会话筛选时会漏掉子 Span。做法是在入口把它们写入 OTel Baggage，再用 BaggageSpanProcessor 复制到该上下文内的每个 Span。很多示例直接用 ALLOW_ALL_BAGGAGE_KEYS，这是一个安全缺口：

  • baggage 是普通请求头，任何能访问入口的客户端都能构造；
  • 放行全部键，意味着外部请求可以往每个 Span 写任意属性，包括 langfuse.trace.name、langfuse.trace.tags、langfuse.observation.prompt.name 这类 Langfuse 的控制属性，直接篡改 Trace 命名、标签和 Prompt 关联，也可以塞入超长值撑大存储；
  • 伪造的 user.id 会让成本和评测数据归到别人名下。

6. 采样一致性

两层数据能对上的前提，是它们看到的是同一批 Trace。常见的不一致来源与对策：

不一致来源 表现 对策
两条管道各自做概率采样 Langfuse 有的 Trace 在 Tempo 查不到，反之亦然 尾采样放在扇出之前，只裁决一次（4.1 的 forward 连接器结构）
网关按 0.1 头部采样 两边都只有 10% 的 AI 会话，成本显著偏低 Micrometer 路线显式设 management.tracing.sampling.probability: 1.0（文档 06）
尾采样丢了部分 AI Trace Langfuse 会话缺轮次 keep-genai 策略保证含 AI 语义的 Trace 全量保留
长工作流超过 decision_wait 同一会话被切成多段、部分段被丢 文档 07 的做法：按 temporalWorkflowID 串联，保留规则覆盖这类 Span
多副本 Collector 各自尾采样 同一 Trace 的 Span 落在不同副本，决策不一致 前面加一层按 trace_id 路由的负载均衡导出器，保证同一 Trace 进同一副本（文档 10）

要不要对 AI Trace 采样，是一个取舍：AI 会话的量通常比基础设施流量小几个数量级，但单条价值高（评测、回归、成本核算都依赖完整数据），所以本系列对 AI Trace 全量保留，只对其余流量按 10% 概率采样。确实需要对 AI Trace 采样时，两层的成本数字都要按采样率还原，而且以 Prometheus 指标为准，因为指标在 SDK 侧产生，不受 Trace 采样影响。

7. 对账方法

对账回答的是「两层数据有没有丢、有没有重」。以一个整点小时为窗口，比较三个数：模型调用次数、输入 token、输出 token。

7.1 指标侧（Prometheus，不受采样影响）

在 Prometheus 的查询 API 上把评估时间设为窗口结束时刻（time=2026-07-20T11:00:00Z）。指标名的由来见文档 09 §6。

7.4 偏差解读

现象 最可能的原因
Langfuse token ≈ 指标的 2 倍 两层 LLM Span 都进了 Langfuse，filter/langfuse-scope 第 2 条没生效
Langfuse token ≈ 指标的 3 倍 网关 Span 也进了 Langfuse（带 model 属性被识别为 generation）
Langfuse 明显偏少且比例稳定 头部或尾部采样把 AI Trace 丢了一部分（见第 6 节）
Langfuse 偏少且集中在最近十几分钟 摄取尚未完成，等待后重查
调用次数对得上，token 对不上 流式调用未开 stream_options={"include_usage": True}，两侧都缺 usage；或模型名不一致导致分组错位
调用次数与 token 都对得上，成本为 0 Langfuse 的模型价目表里没有该模型，在项目设置中新增模型定义（匹配规则 + 单价）

经验阈值：窗口对齐后，调用次数应完全一致，token 偏差在 2% 以内（来源是 increase() 的外推误差）。超过阈值就按上表定位，不要调阈值。

8. Langfuse 侧的增值动作

  1. Sessions 视图：按 session.id 回放多轮诊断会话，检查上下文携带是否正确；
  2. 成本核算：确认 deepseek-chat 的价目表（输入/输出单价）生效，按用户、会话、模型聚合；
  3. 评测（LLM-as-Judge）：配置 Judge 模型对回答打分（准确性、幻觉），分数挂到对应 Trace；
  4. Prompt 管理：Prompt 版本化后，在 LLM Span 上写 langfuse.observation.prompt.name / langfuse.observation.prompt.version，就能 A/B 对比不同版本的成本与评分；
  5. 数据集回归：把线上问题 Trace 加入 Dataset，作为发布前回归集。

9. 验收清单

  • 同一次请求在 Tempo 与 Langfuse 均可见，trace_id 一致；
  • Tempo 中的 Span 不含 gen_ai.input.messages、gen_ai.output.messages、input.value、output.value；
  • Langfuse 中构造的手机号、身份证号、VIN 样本均显示为掩码；
  • 入站携带 langfuse.trace.tags 等非白名单 baggage 时，Span 上不出现这些键；
  • 一次模型调用在 Langfuse 中只对应一个 generation；
  • 7.1 与 7.2 的调用次数一致，token 偏差 < 2%；
  • Collector 中 otlphttp/langfuse 的发送失败、入队失败计数为 0。

2026-09 补记：Langfuse v4 与 OTLP 实时写入

Langfuse 自托管 v4.0.0 于 2026-07-29 发布。文档 04 锁定的 LANGFUSE_VERSION=3 不受影响，升级到 v4 之后有一处与本篇管道直接相关：v4 的 OTLP 直写如果不带 x-langfuse-ingestion-version: 4 请求头，数据最长可能延迟 15 分钟才可见（官方兼容性说明）。两种处理方式任选其一：在 otlphttp/langfuse 的 headers 里加上该头；或者在自托管实例上设置 LANGFUSE_MIGRATION_V4_NATIVE_OTEL_BEHAVIOUR=direct，让所有 OTLP 写入都走实时路径。升级后第 7 节对账表里「集中在最近十几分钟」的偏差应当消失，如果仍然存在，优先检查这一项。
