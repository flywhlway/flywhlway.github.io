可观测性与 OpenTelemetry 体系总览

可观测体系由哪些信号组成、OpenTelemetry 扮演什么角色、自托管 AI Agent 平台在 2026 年如何选型：本篇给出系列统一的心智模型、选型结论与端口规划。

Flywhl 8 分钟 更新于 2026.09 #可观测性#AI Agent#OpenTelemetry

先读结论

  1. OpenTelemetry 是采集标准与传输总线，不是监控平台；存储、展示、告警由 LGTM 与 Langfuse 承担。
  2. AI 可观测 = 传统链路观测 + gen_ai.* 语义约定 + AI 业务层平台，三者叠加而非替代。
  3. CNCF 毕业不等于全部稳定：Collector 仍是 v0.x，GenAI 约定已迁到独立仓库且仍处于 Development。

本篇回答三个问题：可观测体系由什么组成？OpenTelemetry 在其中扮演什么角色？2026 年年中自托管 AI Agent 平台的技术选型格局是什么？后续九篇的埋点、部署与排障都建立在这里的术语和结论之上。

1. 可观测性的四类信号

传统三大信号加上正在成熟的第四类信号：

信号 回答的问题 典型后端 数据特征
Metrics 系统趋势如何？（QPS、延迟、Token 消耗） Prometheus / Mimir 低基数、预聚合、时序
Logs 具体发生了什么？ Loki / Elasticsearch 高吞吐、文本或结构化
Traces 请求经过了哪些服务、慢在哪？ Tempo / Jaeger 树状 Span、单条价值高、留存短
Profiles CPU 与内存花在哪些函数上？ Pyroscope 采样火焰图；OTLP Profiles 于 2026-03-26 进入公开 Alpha，暂不作为生产依赖

AI Agent 系统没有发明新的信号类型，而是把 AI 语义以属性（Attributes）、事件（Events）和指标（Metrics）的形式附着在已有信号上。这里的「事件」需要按新口径理解：OpenTelemetry 在 2026-03-17 宣布弃用 Span Events API，新增事件一律用关联当前 Span 的 log-based events（即带 trace_id / span_id 的 LogRecord）表达，这也是 GenAI 约定把消息内容从 Span 事件迁走的背景之一（见 02 篇）。

一次诊断类 Agent 会话在 Trace 里的典型形态：

关键认知：AI 可观测 = 传统链路观测 + GenAI 语义约定（gen_ai.*）+ AI 业务层平台（Langfuse 等）。三者是叠加关系，不是替代关系：只有前者，看得到慢但看不懂「为什么这样回答」；只有后者，看得到回答质量却定位不到是网关、向量库还是模型拖慢了链路。

1.1 Agent 系统与传统微服务的观测差异

把微服务那套 RED 指标直接套到 Agent 上会漏掉大量问题，差异集中在四点：

差异 传统微服务 Agent 系统 对观测设计的要求
确定性 同样输入走同样代码路径 同样输入可能选不同工具、循环不同次数 除错误率外，必须记录决策依据：finish_reasons、选中的工具、循环次数
请求形态 毫秒到秒级，扇出有限 分钟级会话，几十次 LLM 与工具调用 采样必须按整条 Trace 决策（尾部采样），逐 Span 随机丢弃会把会话切碎
成本 以资源用量间接体现 Token 即费用，单次失控循环可烧掉可观成本 Token 指标是一等公民，需按模型 × 租户 × 路由归因，并控制标签基数
数据风险 请求体很少进入观测系统 Prompt 与回答天然包含用户输入和业务数据 观测管道本身是数据泄露面，内容捕获默认关闭，开启必须配脱敏与访问控制

这四点分别在 02（属性与内容捕获）、03（采样与脱敏）、05/06（埋点）、10（生产治理）中落地。

2. OpenTelemetry 是什么、不是什么

OpenTelemetry（OTel）不是监控平台，而是一套「遥测数据的采集标准 + 参考实现」：

组成部分 内容 本系列用到的部分
API / SDK 各语言埋点库（Java、Python、Go、JS 等）与自动埋点 Agent Python SDK + GenAI 埋点库、Java Agent
语义约定 属性与指标的命名标准（http.*、db.*、gen_ai.* 等） gen_ai.*、mcp.*、Resource 属性
OTLP 协议 统一传输协议，gRPC 默认端口 4317、HTTP 默认端口 4318 应用 → Collector → 后端全程 OTLP
Collector 与厂商无关的接收、加工、导出中转站 汇聚、脱敏、采样、多后端路由

它不负责存储、检索、可视化和告警，也不提供评测、Prompt 管理这类 AI 业务功能。选型时把「采集标准」与「后端产品」分开评估：前者几乎没有争议地选 OTel，后者才是真正需要权衡的地方。

2.1 截至 2026-07 的关键节点

  • 规范层面：声明式配置（declarative configuration）于 2026-03-05 进入 stable，SDK 可以用一份 YAML 统一描述 exporter、sampler 与 resource，替代散落的环境变量；2026-03-17 弃用 Span Events API；2026-03-26 Profiles 进入公开 Alpha。
  • 治理层面：OpenTelemetry 成为 CNCF 毕业项目（CNCF 项目页记为 2026-05-11，官方博客于 2026-05-21 发文）。毕业说明项目治理与生产采用度通过了 CNCF 评审，不等于每个组件都已稳定：Collector 仍以 v0.x 双周节奏发布（写作时最新为 v0.155.0，2026-06-24），GenAI 约定仍是 Development。
  • 语义约定层面：semantic-conventions v1.42（2026-06-12）把 GenAI（含 MCP）约定整体迁到独立仓库 open-telemetry/semantic-conventions-genai（2026-05-05 建仓），主仓库中对应部分标记为 deprecated。新仓库目前全部处于 Development、尚无独立 release，属性定义以新仓库为准，历史变更仍需对照主仓库 v1.37–v1.42 的发布说明（详见 02 篇）。
  • Metrics 生态：Prometheus 3.x 内置 OTLP 接收端（需以 --web.enable-otlp-receiver 开启）并支持 UTF-8 指标名，OTel 指标可以直接写入，不必再绕道 Prometheus exporter 抓取。
  • 框架与后端：LangChain / LangGraph、OpenAI Agents SDK、Spring AI、LlamaIndex、vLLM 等框架和 Grafana、Datadog、Honeycomb、Langfuse 等后端大多已能产出或消费 gen_ai.* 属性，但各自跟进的约定版本不一，这正是 02 篇强调「锁定版本 + Collector 兜底映射」的原因。

3. 生态格局与选型矩阵

3.1 五类角色

flowchart TD
    A["应用<br/>SDK 埋点 / 自动埋点"] -->|OTLP| B["Collector 层<br/>OTel Collector / Grafana Alloy"]
    B --> C["系统层存储<br/>Prometheus / Mimir · Loki · Tempo"]
    C --> D["可视化与告警<br/>Grafana"]
    B -->|OTLP/HTTP| E["AI 业务层<br/>Langfuse"]

关键点在最后一条边：AI 业务层平台和系统层后端消费同一份 OTLP 数据，由 Collector 分发，应用只埋一次点。

3.2 选型对比（面向自托管 AI Agent 平台）

能力 Prometheus OTel（标准） Jaeger Tempo Elastic Datadog
Metrics ★★★★★ 采集标准 — 经 metrics-generator 从 Trace 生成 ★★★ ★★★★★
Logs — 采集标准 — — ★★★★★ ★★★★★
Traces — 采集标准 ★★★★ ★★★★★ ★★★★ ★★★★★
按 gen_ai.* 检索与聚合 仅指标维度 约定定义者 ★★（按标签检索，无聚合查询语言） ★★★★（TraceQL 按属性检索与聚合） ★★★ ★★★★（LLM Observability 产品）
供应商锁定 无 无 无 无 低 高
数据出境风险 无 无 无 无 可自托管 有（SaaS，需做合规评估）
自托管成本 低 低 中 低（对象存储） 高 不适用

本系列采用的结论：自托管 LGTM 栈（Loki + Grafana + Tempo + Prometheus/Mimir）+ OTel Collector 作为系统层；Langfuse 作为 AI 业务层。理由：

  1. 全开源、可控、无数据出境问题，适合对数据留存和出境有强约束的行业（汽车、能源、政企等）；
  2. Tempo 基于对象存储、不建全文索引，存储成本低，TraceQL 可以直接按 gen_ai.* 属性检索；
  3. Tempo metrics-generator 可从 Trace 自动生成 RED 指标与服务拓扑图并写入 Prometheus，减少重复埋点；
  4. Langfuse 提供 OTLP 接收端（仅 OTLP/HTTP，路径 /api/public/otel），可直接接收 gen_ai.* Trace，与 LGTM 形成「一次埋点、双端消费」。

端口规划（全系列一致）：Grafana 占用 3000，Langfuse Web 映射到宿主机 3001；OTLP 4317/4318 由 Collector 独占，其余组件端口在 03、04 篇列出完整表格。

3.3 Grafana Alloy 与 OTel Collector 的关系

Grafana Alloy 是 Grafana 发行的 OTel Collector 发行版，内置 otelcol.* 组件收发 OTLP，另外提供 Prometheus 抓取、loki.source.docker（直接采集容器 stdout 日志）等组件，是 Grafana Agent 与 Promtail 的官方继任者（两者均已结束支持）。

选型建议：

场景 选择 理由
纯 OTLP 汇聚、加工与路由 官方 otelcol-contrib（本系列默认） 组件最全，配置与上游文档一一对应
还要抓取 Prometheus exporter、采集 Docker/K8s 容器日志 Alloy 一个进程覆盖指标抓取与日志采集，少部署一个组件
规模较大、边缘节点多 两者共存 Alloy 做边缘采集（Agent 模式），otelcol-contrib 做中心网关（Gateway 模式）

6. 本章小结

  • OTel 是标准与总线，LGTM 是系统层后端，Langfuse 是 AI 业务层后端；
  • Agent 观测的难点不在「看不看得到」，而在非确定性、长会话、Token 成本与内容风险四个维度，采样与脱敏必须在 Collector 层统一处理；
  • 2026 年选型的最大变化是 GenAI 语义约定成为跨框架、跨后端的公共契约，「AI 观测」不再需要私有 schema，但它仍处于 Development，版本锁定不可省；
  • 下一篇（02）深入 gen_ai.* 语义约定——整套 AI 可观测体系的数据契约。

2026-09 补记：两处后续变化

  • Langfuse 服务端 v4.0.0 于 2026-07-29 发布（全文检索、Monitors & Alerts、Observations API v2），截至 2026-09 已迭代到 v4.46。本系列 04 篇以写作时的 v3 服务端为部署基线，升级要点见该篇补记。
  • GenAI 约定仓库仍无 release：截至 2026-09，semantic-conventions-genai 全部内容仍为 Development，本篇「锁定版本、Collector 兜底映射」的建议不变。
