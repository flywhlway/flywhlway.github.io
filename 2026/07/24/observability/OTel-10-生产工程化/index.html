可观测性生产工程化演进

POC 的目标是看得见，生产的目标是扛得住、管得住、算得清：按拓扑高可用、数据治理、安全合规、SLO 告警、规范治理五个维度给出演进路线…

Flywhl 14 分钟 更新于 2026.09 #可观测性#OpenTelemetry#SLO

先读结论

  1. Collector 自身指标默认从 8888 端口拉取，名称不带 _total；存量规则里常见的 otelcol_processor_dropped_spans 已不存在，丢数据要看拒收、入队失败、发送失败三类计数。
  2. 尾采样多副本必须先按 trace_id 负载均衡，否则同一 Trace 的决策会分裂。
  3. Agent 级 SLO 可以直接用 Tempo 派生的 span 指标计算燃尽率，前提是 AI Trace 不被采样丢弃。

POC 的目标是「看得见」，生产的目标是「扛得住、管得住、算得清」。本篇按拓扑高可用 → 数据治理 → 安全合规 → SLO 告警 → 规范治理五个维度给出演进路线与配置基线。文中 Collector 配置在 otelcol-contrib 0.156.0 上做过 validate 校验，告警规则经 promtool 检查，Collector 自身指标名以实际抓取结果为准。

1. 演进总览：三阶段门禁

维度 POC（本系列现状） Pilot（单业务线试点） Production
Collector 单实例合一 Agent + Gateway 两层 Gateway 多副本 + 按 trace_id 负载均衡
采样 SDK 全量，Collector 尾采样（AI Trace 全留，其余 10%） 同左，按业务调整概率 同左，外加高 token、慢调用保留规则
存储 本地盘 对象存储（MinIO 等） Mimir + 对象存储，多租户
内容捕获 span_only，Langfuse 管道脱敏 同左，脱敏规则带样本回归 同左；合规更严时改用上传钩子或 no_content
认证 无 Collector 入口 Token mTLS + 租户级鉴权
告警 手动看盘 RED 基线告警 + Collector 自身告警 SLO 燃尽率告警 + AI 指标告警

采样与内容捕获两行与文档 05、08 保持一致：SDK 侧不做头部概率采样（Java 的 Micrometer 路线要显式把默认的 0.1 改成 1.0），采样裁决只在 Collector 做一次；正文只有 openai-v2 一个来源，进入 Collector 后 Tempo 管道删除、Langfuse 管道脱敏。

2. 高可用拓扑与 Kubernetes 落地

2.1 两层架构

尾采样要求同一 Trace 的所有 Span 落在同一个 Gateway 实例，否则每个实例只看到 Trace 的一部分，各自做出不同的决策，结果是一条 Trace 被保留一半。Agent 层用 loadbalancing exporter 按 trace_id 路由：

hostname 必须指向 Headless Service，DNS 解析才能拿到每个 Pod 的 IP。Gateway 扩缩容时哈希环会重排，正在进行中的 Trace 会有一小部分被分到新实例，表现为扩缩容窗口内少量 Trace 残缺；尾采样的 decision_wait 越长，受影响的 Trace 越多，这是选择 decision_wait 时要一并考虑的代价。

2.2 部署方式

  • 官方 OpenTelemetry Operator（Helm）：以 OpenTelemetryCollector CRD 管理配置，支持 Sidecar / DaemonSet / Deployment 三种形态；Java 服务可以用 Instrumentation CRD 在不改镜像的前提下注入 Java Agent。
  • 存储层用 Grafana 官方 Helm Chart：tempo-distributed、loki、mimir-distributed，后端对接对象存储。
  • 导出可靠性：所有跨网络的 exporter 开启 retry_on_failure 与 sending_queue，发往外部或易抖动后端（Langfuse、跨机房存储）的再挂持久化队列：

持久化队列只保护 Collector 这一跳。应用 SDK 到 Collector 之间仍然是内存队列（文档 05 §9），所以 Agent Collector 要部署在离应用最近的位置（同节点），让这段链路足够短、足够稳。

3. 数据治理：成本与基数控制

来源 症状 对策
指标基数爆炸 Prometheus 内存暴涨 禁止把 user_id、session_id、trace_id 作为指标维度（放 Trace 属性）；Collector 用 transform 删除高基数标签；Mimir 设租户级序列上限
进程级序列翻新 重启后序列数阶梯上涨 Python SDK 1.43 起每个进程自动生成 UUID 形式的 service.instance.id，映射为 instance 标签；大盘一律 sum by 聚合掉 instance，存储侧按保留期自然淘汰
Trace 属性膨胀 单 Span 数十 KB 正文只在 Langfuse 管道保留；Tempo 管道删正文后用 transform 的 truncate_all(span.attributes, 4096) 截断剩余长文本。不要在 Langfuse 管道截断正文，截断后的 JSON 无法解析
日志噪声 Loki 摄入量失控 采集侧按级别过滤 DEBUG；健康检查、探针路径在源头排除（Python 用 excluded_urls，Java 用规则采样器，文档 06 第 7 节），Collector filter 兜底

留存策略基线：Metrics 30–90 天（降采样后更久）；Traces 7–14 天（错误链路可延长）；Logs 14–30 天；Langfuse 业务 Trace 按评测与回归需要保留 90 天以上。Langfuse 保存的是脱敏后的正文，留存期要经过数据合规评审。

4. 安全与合规

  1. 传输安全：App → Collector 集群内 mTLS；Collector → 后端 TLS + basicauth / bearertokenauth 扩展；OTLP 端口不暴露到公网。
  2. PII 纵深防御：应用侧对业务标识做带密钥哈希（文档 05 pseudonymize()）；Collector 的 Langfuse 管道先把消息 JSON 规范化再做正则脱敏（文档 08 §4.3）；Tempo 管道直接删除正文。脱敏规则纳入版本管理，每次变更用 debug exporter 回放样本集（覆盖 ASCII 转义与非转义两种 JSON）比对输出。
  3. Baggage 边界：公网入口剥离外部 baggage 头，网关鉴权后写入，消费端只复制白名单键（文档 06 第 5 节、文档 08 第 5 节）；出口网关删除发往外部模型服务商的 baggage 头。
  4. 数据不出境：全自托管栈天然满足；若引入 SaaS 后端，消息正文类属性一律在 Collector 出口前删除。
  5. 审计：Grafana、Langfuse 接入 SSO 与 RBAC；含正文的数据单独租户存储、独立授权；Collector 配置变更走 GitOps。
  6. 供应链：镜像固定 digest、经私有仓库代理拉取；用 ocb（OpenTelemetry Collector Builder）只编译所需组件，缩小攻击面。Python 依赖锁定到传递依赖（uv.lock 提交入库），2026-03 LiteLLM 在 PyPI 上的供应链投毒事件说明，AI 工具链的第三方包同样需要按生产依赖对待。

5. SLO 与告警体系

5.1 指标分层

层 SLI 示例 数据来源
入口层 可用性、P95 延迟、平均首 Token 时延 SCG 的 HTTP 指标、Higress ai-statistics 指标（文档 07）
Agent 层 诊断成功率、单次诊断 token 数、工具失败率 Tempo 派生的 span 指标、com.example.* 自定义指标
LLM 层 gen_ai.client.operation.duration P95、限流比例、首分片时延 P95 GenAI 指标（文档 09 第 6 节）
平台层 Collector 拒收、入队失败、队列水位、SDK 丢弃 Collector 与 SDK 自身指标

自定义指标沿用系列统一的反向域名前缀，以你的组织域名替换 com.example。

5.2 Collector 自身指标：名称以实际抓取为准

Collector 默认在 :8888/metrics 暴露自身指标，这个默认读取器设置了 without_type_suffix 与 without_units，所以计数器不带 _total，时长也不带单位后缀。如果自定义了 service.telemetry.metrics.readers，或把自身指标经 OTLP 推给 Prometheus，名称会变成 otelcol_exporter_send_failed_spans_total 这种形式，告警表达式要跟着改。以 0.156.0 默认配置实测：

指标 含义 用途
otelcol_receiver_accepted_spans 接收端成功推入管道的 Span 数 流量基线
otelcol_receiver_refused_spans 接收端被拒绝的 Span 数（memory_limiter 触发背压时计入这里） 内存压力
otelcol_exporter_sent_spans 成功发往后端的 Span 数 与接收量对比算端到端损耗
otelcol_exporter_send_failed_spans 重试耗尽后发送失败的 Span 数 后端不可用
otelcol_exporter_enqueue_failed_spans 发送队列已满、入队失败的 Span 数 队列容量不足，数据正在丢
otelcol_exporter_queue_size / otelcol_exporter_queue_capacity 队列当前长度与容量（按批计） 水位告警
otelcol_processor_incoming_items / otelcol_processor_outgoing_items 处理器进出条目数 观察 filter、尾采样的丢弃比例（预期内的丢弃）
otelcol_processor_tail_sampling_sampling_trace_dropped_too_early 未等到 decision_wait 就被挤出内存的 Trace 数 尾采样 num_traces 不够
otelcol_process_memory_rss Collector 进程常驻内存 容量规划

不少存量告警规则里的 otelcol_processor_dropped_spans 在当前版本中并不存在，照抄的规则永远不会触发。「丢数据」要拆成三类看：接收端拒收（背压）、入队失败（队列满）、发送失败（后端故障）。

文档 05 §9.3 的 SDK 自身指标（OTEL_PYTHON_SDK_INTERNAL_METRICS_ENABLED=true）经 OTLP 进入 Prometheus 后名为 otel_sdk_processor_span_processed_total，队列满丢弃的数据带 error_type="queue_full"，用来发现应用侧的静默丢弃。

5.3 告警规则

阈值说明：TokenUsageSpike 里的第二个条件（速率大于 50 token/秒）用来屏蔽低流量时段的抖动，否则凌晨几次调用就能触发「翻倍」；TokensPerDiagnosisHigh 的 20000 与 FirstChunkLatencyHigh 的 3 秒是示例值，按上线后两周的实际分布取 P99 再留余量。error_type 取的是 SDK 异常类名，OpenAI Python SDK 的限流异常是 RateLimitError，超时是 APITimeoutError。

5.4 SLO 燃尽率

以「诊断请求 30 天 99% 成功」为例，错误预算是 1%。Agent 级成功与否直接取 Tempo metrics-generator 从 invoke_agent Span 派生的计数（文档 09 §6.5），前提是尾采样对 AI Trace 全量保留（文档 08 第 6 节），否则分子分母都被采样稀释：

双窗口的作用：长窗口保证燃尽确实持续，短窗口保证问题仍在发生，故障恢复后告警能及时消失。14.4 与 6 这两个倍率来自「1 小时耗掉 2% 预算」「6 小时耗掉 5% 预算」，与 SLO 目标值无关，换成 99.5% 只需把 0.01 改成 0.005。

Agent「成功」只覆盖了技术失败。回答质量（答非所问、幻觉）不会让 Span 变成 ERROR，这部分用 Langfuse 的评测分数单独建质量 SLO，两类 SLO 不要混在一个错误率里。

6. 规范治理

  • 语义约定版本：OTEL_SEMCONV_STABILITY_OPT_IN（本系列为 gen_ai_latest_experimental,http）写入基础镜像或 Chart，禁止服务自行漂移；GenAI 约定仍在 Development，每季度评审独立仓库的变更记录，属性改名先在 Collector 用 transform 做过渡映射（文档 03）。
  • 私有属性登记制：com.example.* 属性与指标统一登记名称、类型、基数评估与负责人，防止随手添加的属性引发基数事故。
  • 埋点即代码评审项：新服务上线清单包含「Resource 属性齐全、健康检查排除、错误路径 record_exception、无 PII 明文属性、节点内 Span 已挂回节点」。
  • 升级节奏：Collector 按季度跟进并通读变更记录中的 breaking changes；SDK 与埋点包按批次成对升级（如 1.43.0 / 0.64b0）；每次升级先在预发环境做对账：Span 数、指标名列表、Langfuse generation 数与升级前比对，任何一项有差异都要能解释。

7. 生产就绪终检清单

  • Gateway Collector ≥ 2 副本，loadbalancing 按 trace_id 路由已验证（扩缩容期间残缺 Trace 比例可接受）；
  • 发往 Langfuse 等外部后端的 exporter 挂了持久化队列，重启 Collector 后积压数据继续发送；
  • 5.3 的 Collector 告警在预发做过故障注入：停掉后端触发 CollectorExportFailing，压小队列触发 CollectorQueueFull；
  • 脱敏规则有样本集回归，Tempo 中无正文、Langfuse 中无明文手机号、身份证号、VIN；
  • OTLP 入口有认证，Grafana、Langfuse 接入 SSO 与 RBAC；
  • SLO 告警接入值班体系，告警可一键下钻到 Trace（exemplar 链路验证）；
  • 遥测成本月报（存储量、序列数、摄入量按团队归因）机制建立；
  • 灾备演练：Collector 全部不可用 30 分钟，应用无感（SDK 队列丢弃降级），恢复后指标连续（累积时间性自动补齐）。

8. 结语：与平台架构的融合

可观测体系不是外挂，而是诊断平台「monitor → diagnose → treat → learn」运营闭环里的 monitor 基座：GenAI 语义约定为 LLM 这一概率性组件提供了确定性的度量面——token、时延、错误、循环次数都可以进入 SLO；Langfuse 层的评测与会话数据反哺 Prompt 与模型迭代，构成 learn 环节的数据来源。至此，「确定性 × 概率性融合」的架构原则在观测维度完成闭环。

2026-09 补记：一次上游升级验证了「按批次锁版本」

2026-09-24 发布的 opentelemetry-util-genai 1.2b0 与当时最新的 opentelemetry-instrumentation-openai-v2 2.4b0 不兼容，新环境安装后 import 直接失败（复现与处理见文档 05 的补记）。openai-v2 只给这个传递依赖写了下限，没有写上限，所以只锁直接依赖的项目会在某次重新构建时突然坏掉，而提交了 uv.lock 的项目不受影响。第 6 节的两条规定因此需要落到可执行的层面：锁文件入库；依赖升级走单独的变更，并以预发对账通过作为合并条件。
