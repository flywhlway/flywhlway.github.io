端到端 Demo：一次 Agent 会话的全链路观测

把 05–08 篇串成一次可复现的演练：一次诊断会话在 Tempo 与 Langfuse 中各长什么样，日志、指标与 Trace 如何互跳，成本与时延大盘的 PromQL…

Flywhl 21 分钟 更新于 2026.09 #LangGraph#可观测性#OpenTelemetry

先读结论

  1. 同一个 trace_id 贯穿网关、Agent 节点、工具、mem0 与模型调用，Tempo 看全貌，Langfuse 只看 AI 语义那一部分。
  2. 指标名经过 Prometheus 的 OTLP 转换：单位变后缀、点变下划线、花括号单位被丢弃，写 PromQL 前先查实际名称。
  3. 首 Token 时延要用自带桶边界的直方图，成本以应用侧计数器为准、PromQL 折算做交叉校验。
  4. 排查断链先看 trace_id 是否一致，再看父子关系，最后看采样标志，顺序不能乱。

前八篇分别解决了埋点、传输、部署与双层消费，本篇把它们串成一次完整演练：用户经网关发起一次故障码诊断，Agent 查记忆、调模型、调工具、再调模型、最后异步写记忆。目标是回答文档 01 提出的第一个问题——一次用户会话完整经过了哪些服务、Agent 节点和工具——并在 Grafana 与 Langfuse 两端对照同一个 trace_id。文中的 Span 树与属性取自实际运行结果（模型端点换成了本地的 OpenAI 兼容桩服务，结构与真实调用一致）。

3. Agent 代码

app.py 共 170 余行，所有埋点能力都来自 telemetry.py，业务代码里只出现三类观测相关的写法：根 Span、工具 Span、in_node_span()。自定义指标与私有属性使用 com.example. 前缀（约定见文档 05），以你的组织域名替换 com.example。

与前几篇的对应关系：

  • 会话标识走 Baggage：入口把 session.id 与哈希后的 user.id 写入 Baggage，白名单处理器把它们复制到之后创建的每个 Span（文档 08 第 5 节）。演练里由 Agent 服务自己写入；生产上这一步在网关鉴权之后完成，Agent 只接收。
  • 节点内的 Span 挂回节点：recall_node 与 agent_node 都包了 in_node_span()，否则 mem0_search 与 chat Span 会挂到 invoke_agent 下，节点 Span 变成空壳（文档 05 §5）。
  • 流式调用的两个细节：stream_usage=True 让 DeepSeek 在最后一个分片返回 usage，openai-v2 才能记下 token；首分片时延用自带桶边界的直方图记录（文档 05 §8）。
  • 写记忆不阻塞响应：remember 在响应之后执行，用空的 Context() 新开 Trace，再用 Span Link 指回原会话。它复制不到入口的 Baggage，所以 session.id、user.id 显式写成属性，Langfuse 才能把它归到同一个会话。
  • 响应里带回 trace_id：用户反馈问题时附上这个 ID，运维可以直接在 Tempo 和 Langfuse 里打开这次会话。

6. PromQL：成本与时延大盘

6.1 指标名从哪来

Collector 把 OTLP 指标写入 Prometheus 的 OTLP 接收端，默认转换策略会改名：点换成下划线；有单位的加单位后缀（s → _seconds）；花括号里的注解单位（{token}、{CNY}）被丢弃；计数器加 _total；直方图拆成 _bucket / _sum / _count。本演练涉及的指标：

OTel 指标 类型与单位 Prometheus 中的名称
gen_ai.client.token.usage 直方图，{token} gen_ai_client_token_usage_bucket / _sum / _count
gen_ai.client.operation.duration 直方图，s gen_ai_client_operation_duration_seconds_*
gen_ai.client.operation.time_to_first_chunk 直方图，s gen_ai_client_operation_time_to_first_chunk_seconds_*
com.example.token.cost 计数器，{CNY} com_example_token_cost_total
com.example.diagnose.requests 计数器，{request} com_example_diagnose_requests_total
http.server.request.duration 直方图，s http_server_request_duration_seconds_*
Tempo 从 Span 派生 计数器 / 直方图 traces_spanmetrics_calls_total、traces_spanmetrics_latency_bucket

属性同样换成下划线：gen_ai_request_model、gen_ai_token_type、server_address、error_type。拿不准时先列出实际名称再写查询：

6.2 Token 用量

最后一个比值是最值得挂告警的业务指标：它突然翻倍，通常意味着 Agent 循环次数失控或记忆检索带回了过多上下文，比单看总量更早暴露问题。

6.4 首 Token 时延与调用时延

同一面板里叠加这三条线，能直接看出时间花在哪：端到端明显高于单次调用，说明循环次数多或记忆检索慢；首分片时延高而总时延正常，多半是模型侧排队。网关视角的平均首 Token 时延见文档 07 §1.2，两者之差是网关到应用这一段的开销。

6.5 错误率

三个错误率看的是不同层：模型调用失败不一定导致 Agent 失败（有重试或降级），Agent 失败也不一定是 5xx（可能返回了兜底答案）。只看 HTTP 5xx 会漏掉「答非所问但状态码 200」的情况，这部分要靠 Langfuse 的评测分数兜住。

traces_spanmetrics_* 来自 Tempo，只统计到达 Tempo 的 Span。文档 08 的尾采样对含 AI 语义的 Trace 全量保留，所以 Agent 级错误率不受采样影响；如果改动了采样策略，这条查询要按采样率重新解读。

6.6 从指标跳到 Trace

openai-v2 记录两个直方图时处在 chat Span 的上下文中，Python SDK 默认的 exemplar 过滤器（trace_based）会把当时的 trace_id 附在数据点上，实测每个数据点都带有对应会话的 trace_id。Prometheus 开启 exemplar-storage 之后，在 Grafana 的时序面板打开 Exemplars 开关，图上会出现可点击的点，直接跳到文档 04 配置的 Tempo 数据源。排查「P95 为什么突然升高」时，这是从指标到具体会话最短的路径。

7. 日志与 Trace 互跳

app.py 在会话结束时打了一条日志。OTLP 日志记录自带 trace_id 与 span_id 字段，Loki 把它们存为结构化元数据：

  • Loki → Tempo：展开日志行，文档 04 配置的 derivedFields 会把 trace_id 渲染成链接；
  • Tempo → Loki：Span 详情里的 Logs for this span，按 trace_id 与时间窗过滤；
  • 网关日志：Java Agent 发出的日志同样带 trace_id，同一个查询把 service_name 换成 scg-gateway 即可，两个服务的日志用同一个 trace_id 对齐。

一个小清理：LoggingInstrumentor 为了在控制台格式里显示 trace_id，会往每条日志记录上加 otelTraceID、otelSpanID、otelTraceSampled、otelServiceName 四个属性，它们随 OTLP 进入 Loki，与原生的 trace_id 字段重复。可以在 Collector 的 logs 管道里删掉：

8. 断链排查

排查顺序固定为三步：trace_id 是否一致 → 父子关系是否正确 → 采样标志是否为 1。前一步不成立，后面的现象都是它的衍生。

症状 定位方法 常见原因与处理
网关与 Agent 各有一条 Trace 按文档 06 §6.1 用固定 traceparent 发请求，看 Agent 收到的请求头 中间有代理没透传头；GlobalFilter 重建了请求头
Agent 的 Trace 缺网关部分 网关 Span 在 Tempo 中是否存在 Java Agent 端点指到了 4317 而协议是 http/protobuf（文档 06 §3.1）
节点 Span 下面是空的，chat 挂在 invoke_agent 下 看 chat 的父 Span 名称 节点函数里漏了 in_node_span()
某些 chat 或 POST 成了单独的 Trace TraceQL 查 { span.gen_ai.operation.name = "chat" }，看是否有根 Span 就是 chat 的 Trace 调用发生在线程池里：业务代码的 run_in_executor，或 mem0 同步版 Memory 做实体加权检索时用的线程池；启用 ThreadingInstrumentor（文档 05 §6.2）
invoke_agent 只有几毫秒 对比 HTTP Span 时长 流式接口把根 Span 包在了 return StreamingResponse(...) 外面（文档 05 §6.3）
chat Span 没有 token 看 gen_ai.usage.* 是否缺失 流式调用没开 stream_usage=True
Tempo 有、Langfuse 没有 Collector 自身指标里 otlphttp/langfuse 的发送失败计数；Collector 日志中的 401 密钥错误或 Base64 带了换行（文档 08 §4.5）；摄取延迟
Langfuse 里 Trace 没名字、不在会话下 看 invoke_agent 上是否有 langfuse.trace.name、session.id Collector 的 transform/langfuse-redact 没挂到 Langfuse 管道；Baggage 白名单漏了键
写记忆那条 Trace 不在会话里 看 mem0_add 上的 session.id 后台任务新开 Trace 时没显式写会话属性
日志里 trace_id 全是 0 看日志打印位置 日志发生在任何 Span 之外（启动、后台线程）；或 Handler 被重复挂载（文档 05 §2）
有指标没有 exemplar 看 Prometheus 启动参数 缺 --enable-feature=exemplar-storage
PromQL 查不到数据 6.1 的名称列表 单位后缀、_total 或 job 标签写错

9. 演练验收

  • 一次请求的 trace_id 在 Tempo 与 Langfuse 中都能打开，且网关、Agent、节点、工具、模型调用在 Tempo 中结构完整；
  • Langfuse 中该会话包含主会话与写记忆两条 Trace，每次模型调用只对应一个 generation；
  • Tempo 中没有消息正文，Langfuse 中的手机号显示为 [PHONE]；
  • 6.2–6.5 的查询都有数据，6.3 两个成本口径的差异可以解释；
  • 从 Loki 日志、Prometheus exemplar 都能跳到这次会话的 Trace。

2026-09 补记：按原文依赖重建环境会失败

2026-09-24 之后按第 2.2 节新建环境，会拉到与 openai-v2 2.4b0 不兼容的 opentelemetry-util-genai 1.2b0，setup_telemetry() 在导入 openai-v2 埋点时直接报错，整个演练起不来（原因与复现见文档 05 的补记）。在依赖里加一条 "opentelemetry-util-genai<1.2" 即可恢复，演练中的 Span 树、属性与指标名不受影响。另外，openai Python SDK 3.x 会让 chat Span 与两个 GenAI 指标缺少 server.address，文档 05 第 1 节 "openai>=2,<3" 的约束需要保留。
