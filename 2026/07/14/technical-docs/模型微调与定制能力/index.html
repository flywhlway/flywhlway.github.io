架构师的模型微调决策手册：何时微调、怎么做、如何验收

面向企业 Agent 平台的微调决策手册：四级手段阶梯、托管与自建取舍、成本模型、诊断工单数据飞轮…

Flywhl 29 分钟 更新于 2026.09 #模型微调#LoRA#DPO

先读结论

  1. 先穷尽提示词与 RAG，再考虑微调；微调教的是技能和格式，不是会过期的知识。
  2. 微调的主要成本在数据与评估，不在 GPU；立项前必须先有黄金集和确定性评分器。
  3. 检索微调（bge-m3）性价比最高、风险最低，应最先做；结构化输出用 LoRA-SFT；DPO 只在 SFT 之后做。
  4. 2026 年托管微调在收缩（OpenAI 自助微调分阶段关闭），企业的长期能力应落在开放权重模型、自有数据管线和自有评分器上。
  5. 验收只认生产同款部署形态下的黄金集指标；LoRA 产物走注册表、灰度和一键回退，大模型 API 永远是兜底。

这份手册回答什么

企业 Agent 平台做到一定阶段，总会有人提出「我们要不要微调一个自己的模型」。这个问题拆开是三个：

  1. 何时微调：问题是否真的需要改权重，还是提示词、检索、上下文工程没做到位；
  2. 怎么做：选哪种方法、哪个基座、哪个框架，数据从哪里来；
  3. 如何验收：用什么裁判、什么门槛判定成功，上线后如何回退。

本文以车联网智能诊断平台为例贯穿全文：Java 微服务负责工单、车辆与权限，Python 执行面负责检索与模型编排。围绕它有三个典型的「想微调」诉求，分别对应三个实战：

诉求 问题本质 方法 实战
「搜不到相关维修案例」 向量模型不懂领域术语 Embedding 对比学习微调 实战一：bge-m3
「根因假设的 JSON 经常不合法、根因码乱编」 格式与任务技能不稳 LoRA-SFT 实战二：Qwen 结构化输出
「结论对，但证据链东拼西凑」 输出质量偏好 DPO 实战三：偏好优化

一、何时微调

判断顺序是：先证明便宜手段已经用尽，再证明问题属于「改权重能解决」的类型，最后算清楚托管与自建、成本与收益。

1.1 四级手段阶梯

处理「模型在我的领域表现不好」，按成本从低到高升级，每级都要有「已经榨干」的证据才进入下一级：

级别 手段 周期 进入下一级的证据
L1 提示词工程：系统提示、少样本、结构化输出约束 小时级 5 组以上提示词变体在黄金集上的差距小于 2 个百分点
L2 RAG 与上下文工程：检索、重排、上下文压缩 天级 检索指标（如 recall@5）已达标，但生成质量仍不达标；或检索本身卡在领域术语上
L3 微调：Embedding 微调 → LoRA-SFT → 偏好优化 周级 SFT 数据的边际收益递减，且任务有可自动判定的提升空间
L4 强化学习：GRPO 等可验证奖励方法 月级 绝大多数企业场景到不了这一级，见 2.3 节的立项六问

注意 L2 的第二个出口：如果检索召回差是因为向量模型不认识「P0A1F」「绝缘电阻缓降」这类领域表达，那么 Embedding 微调属于 L2 的修补，应当比 LLM 微调更早做。

1.2 触发条件与反面清单

至少满足下表中的两条，才值得为 LLM 微调立项：

触发条件 判据 诊断场景对照
格式稳定性刚需 结构化输出在提示词约束下合法率仍低于 98% 「信号摘要 → 根因假设 JSON」
领域语义鸿沟 通用模型对领域术语的理解或检索系统性偏差 故障码、工况描述的检索
延迟或成本约束 高频调用下大模型 API 的延迟或单价不可接受 快诊链路一次请求内多次调用
风格一致性 输出风格需要长期稳定，提示词难以维持 诊断报告措辞规范
数据不出域 合规要求必须私有化部署 车辆数据本地化
蒸馏降本 大模型能做好，希望小模型学会 长期形态

出现以下任一情况，先别微调：

  • 知识频繁更新：新车型、新故障码每月都在增加。微调进权重的知识会过期，应该放在 RAG 里。
  • 任务边界模糊：说不清「好输出」长什么样，就构造不出训练对。
  • 没有评估集：没有裁判，微调前后无法比较，先建黄金集。
  • 数据少于 300 条且无法合成扩增。
  • 理由只是「别人都在微调」：用 1.5 节的成本模型对话。

1.4 托管微调还是自建：2026 年的新约束

托管微调（把数据交给模型厂商、训练结果留在厂商平台）省掉了 GPU 与框架运维，但 2026 年上半年出现了一个必须纳入决策的变化。OpenAI 在官方弃用页面公布了自助微调平台的收缩时间表（2026-05-07 通知）：

日期 变化
2026-05-07 此前从未运行过微调的组织，不能再创建微调任务
2026-07-02 过去 60 天内没有调用过微调模型的组织，不能再创建微调任务
2027-01-06 现有活跃客户也不能再创建新的微调任务；已有微调模型的推理保留到其基座模型下线为止

同一页面在 2026-04-22 公布的旧快照下线计划中，o4-mini-2025-04-16 以及基于 gpt-3.5-turbo、gpt-4、gpt-4.1-nano-2025-04-14 等基座的微调版本将于 2026-10-23 下线。而强化微调（RFT，2024-12 以研究预览形式推出，2025-05 对 o4-mini 开放）按官方指南目前只支持 o4-mini。此外，2026-06-03 公布的 Evals 平台弃用计划把评分器（graders）也纳入了迁移范围。

这对架构决策的含义：

维度 托管微调 开放权重模型 + 自建
启动成本 低，上传数据即可 需要 GPU、框架与部署能力
产物归属 权重不可导出，生命周期跟随厂商基座 adapter 与合并权重自有，可长期保存和复现
平台风险 已出现分阶段关闭的先例 框架可替换，基座可重选
适合 短期验证、非核心任务、已在用且有迁移预案的存量 核心业务能力、需要私有化、需要长期迭代

结论：微调的长期资产是数据管线、黄金集和评分器，而不是某个平台上的某个模型。数据和评分器可以在任何基座上重跑，这也是后文把评分器写成独立模块的原因。

1.5 成本模型

以实战二的规模（8B 级基座 LoRA，约 1500 条训练数据，3 个 epoch）为例，按资源类别估算全生命周期成本。数字是立项估算的起点，首轮实测后应回填校准：

成本项 估算 说明
数据构造 40–80 人时 大头：合成、过滤、终审，按 1500 条 × 2–3 分钟终审计
合成与评审调用 约 1500 次生成 + 1500 次评审 按所用 API 的 token 单价折算
训练算力 单卡 24GB，每轮 2–6 GPU 小时 × 2–3 轮 LoRA 与 QLoRA 差异见 2.1 节
评估 黄金集全量 × 3 个模型 × 2–3 轮 基座、微调版、大模型 API 对照
持续成本 每季度约为首次的 30%–50% 数据增量、重训、回归评估，最常被低估

收益侧的算法：月度节省 = 日均调用量 × 30 × (API 单次成本 − 自建单次成本) − 自建推理的固定成本。只有当这个数字为正，且格式与命中率达到 1.2 节的门槛时，「省钱」才成立；否则微调的价值只能来自数据不出域或延迟。

1.6 立项五问

每个微调项目在 ADR 里回答以下五个问题，任何一个答不上来就不开工：

  1. 裁判是谁：用哪个评估集、哪些指标判定成败，当前基线是多少？
  2. 数据从哪来：来源是否合规、是否脱敏，管线能否重跑，与评估集是否隔离？
  3. 何时止损：什么信号出现就停止投入（例如两轮迭代提升不足 2 个百分点）？
  4. 如何上线与回滚：LoRA 怎么部署、怎么灰度、怎么一键切回大模型 API？
  5. 谁来维护：季度重训的负责人和预算在哪里？

二、方法速览：架构师需要知道的部分

数学推导按需查论文，这里只保留影响选型、预算和风险判断的结论。

2.1 SFT 与 LoRA / QLoRA

SFT 用「输入 → 期望输出」对继续训练，教模型「这类输入产出这类输出」。LoRA 冻结原权重，只训练一对低秩矩阵（秩 r 通常 8–64），可训练参数降到原模型的 1% 以下；QLoRA 把冻结的底模量化到 4 bit 再训练 LoRA。LLaMA-Factory README 给出的显存估算：

方法 7B 14B 30B
LoRA（16 bit） 16GB 32GB 64GB
QLoRA（4 bit） 6GB 12GB 24GB

工程要点：

  • LoRA 产物是几十到几百 MB 的 adapter，可以独立分发、按请求切换（vLLM multi-LoRA），这是「一个基座 + 多个技能」部署形态的基础。
  • 24GB 卡上 8B 级模型用 16 bit LoRA 即可，显存不够时才上 QLoRA。QLoRA 训练更慢，而且合并 adapter 时不能使用量化后的底模（LLaMA-Factory 合并示例中有明确提示），要多走一步。
  • lora_target: all（所有线性层）是当前主流默认值；r 从 8–16 起步，输出结构复杂再调大。
  • SFT 教技能与格式，不教知识。硬灌进去的知识会以幻觉的形式出现。
  • 灾难性遗忘的首要原因是学习率过大、epoch 过多：LoRA 从 1e-4、2–3 个 epoch 起步，盯住验证集 loss。

2.2 DPO 及其变体

SFT 解决「会不会」，DPO 解决「好不好」。它把 RLHF 中「训练奖励模型 + PPO」的流程化简为一个直接在偏好对（同一输入的好输出与差输出）上优化的损失，工程难度接近 SFT。

  • 必须建立在 SFT 模型之上。
  • 偏好对的好坏差距要明显且维度单一，模糊的偏好会把模型教坏。
  • beta 从 0.1 起步，控制偏离参考模型的程度；学习率比 SFT 低一个数量级（5e-6 级）；百到千级偏好对即可见效。
  • LLaMA-Factory 用 pref_loss 切换 sigmoid（标准 DPO）、orpo、simpo 等，其中 ORPO 和 SimPO 不需要参考模型。

2.3 GRPO 与 RLVR：读懂，并能论证「暂时不上」

RLVR（可验证奖励强化学习）的奖励来自确定性判定器：答案对不对、格式是否合法、测试是否通过。GRPO 最早在 DeepSeekMath 论文（2024-02）中提出，因 DeepSeek-R1（2025-01-20）而普及：对同一问题采样一组回答，用组内相对好坏作为优势信号，省掉 PPO 需要的价值模型。R1 论文还有一个对企业最重要的结论：把大模型的推理能力蒸馏进小模型，效果好于直接对小模型做强化学习。

开源侧，TRL 提供 GRPOTrainer，verl 面向大规模 RL 训练，Unsloth 主打单卡低显存。工具已经不是门槛，门槛在立项条件。立项六问：

  1. 任务成败能否自动、低成本、防投机地判定？（否 → 不做）
  2. SFT 的数据红利是否已经吃完？（否 → 回去做数据）
  3. 是否有千级以上、难度有梯度的问题集？（否 → 不做）
  4. 预算能否承受 SFT 的 10–100 倍算力和数周迭代？
  5. 团队能否诊断奖励欺骗、熵塌缩这类训练失败？
  6. 蒸馏现成的推理模型能否达到八成效果？（能 → 蒸馏）

诊断场景的现状通常是：第 1 问部分满足（根因码可以对账），第 2、3 问不满足。结论是暂不上 RL，但把确定性评分器和问题集当作长期资产持续积累：后文的 grader.py 同时服务于验收、偏好对筛选，将来也可以直接作为 RL 的奖励函数。

2.4 Embedding 微调

向量模型的训练目标是把相关的拉近、不相关的推远（对比学习）。领域微调用「查询、正例、难负例」三元组继续训练。难负例是效果的关键：拿菜谱当诊断查询的负例，模型不用学就能区分；同故障域、不同根因的案例才会逼模型学会细粒度差别。

  • 性价比最高：bge-m3 约 5.7 亿参数，单卡数小时即可完成一轮，收益直接作用于整条 RAG 链路。
  • batch 越大，批内免费负例越多，这是典型的「显存换效果」。
  • 温度参数（0.02 级）先别动，先动数据。
  • 微调后的向量模型必须和 reranker 一起评估，只换向量模型可能让整条链路变差。

三、工具链与环境

选型原则是 LLM 微调用一个主框架加一个备选，向量模型用官方库，本地只做数据与冒烟、不在无 CUDA 的机器上硬跑正式训练。

3.2 本地与云端分工

Apple Silicon 笔记本没有 CUDA，bitsandbytes 量化、FlashAttention、vLLM GPU 推理都用不了，但统一内存足够做数据管线和小规模冒烟：

位置 做什么 工具
本地（Apple Silicon） 数据管线开发（占七成工作量）、50 条样本的 LoRA 冒烟、合并产物的推理抽检 Python、mlx-lm、Ollama
云端（单卡 24GB 及以上 CUDA） 正式训练、vLLM 部署与压测 LLaMA-Factory、FlagEmbedding、vLLM

冒烟的目的只有一个：在花 GPU 钱之前，确认数据格式、对话模板、loss 走向没有低级错误。

每次实验记录环境指纹：框架版本或 commit、基座模型版本、数据版本哈希、训练配置哈希。没有指纹的结果不进对比表。

4.2 七步管线

步骤 做什么 门禁
① 采集 按信噪比排序：已关单工单中的确认根因 > 历史案例库 > 专家访谈补录 种子集 80–150 条真实案例

⑦ 隔离与版本化 与黄金集做案例 ID 硬隔离 + 8-gram 重叠查重；JSONL + git 管理；train/val 按 95/5 切分 黄金集不参与训练的任何环节

边界样本（信息不足时输出 insufficient_evidence: true 且不给根因）必须占 8%–12%。模型学不会说「不知道」，上线后就会在信息不足时编造根因。

4.3 难负例的三个来源

  1. 词面陷阱负例：用检索模型取查询的前若干名、剔除正例后抽样，词面相似但语义不同。FlagEmbedding 的 hn_mine.py 可以直接产出这一路。
  2. 同域异因负例（价值最高）：同故障域不同根因、同 ECU 不同症状、同症状不同工况的案例互为负例。「什么容易混淆」只有懂业务的人知道，把它写成规则脚本沉淀下来。
  3. 剔除假负例：表述不同但根因相同的案例混进负例会严重伤害训练，用根因码做一致性校验剔除。

4.4 数据发布验收清单

  • 脱敏全量通过，人工抽检 50 条无泄漏
  • schema 校验通过率 100%
  • 与黄金集查重 0 命中
  • 单一根因占比低于 15%，否则模型会学成「万物皆此因」
  • 边界样本占 8%–12%
  • 终审通过率、淘汰原因分布写入数据卡
  • 数据版本哈希已生成，实验日志可引用

五、实战一：bge-m3 检索微调

先做它的理由：模型小、训练快、失败成本最低，而且收益直接体现在整条 RAG 链路上。

5.1 任务与成功标准

  • 任务：提升 bge-m3 在诊断案例库上的稠密检索质量。
  • 裁判：固定测试集（200 条查询 + 全量案例语料），按根因码与训练三元组隔离。
  • 成功标准：recall@5 提升不少于 8 个百分点，或 MRR@10 提升不少于 0.05；同时用 100 条通用中文查询做回归，下降不超过 2 个百分点。

5.2 难负例挖掘与训练

hn_mine.py 在 FlagEmbedding 仓库的 scripts/ 目录下，不在 pip 包的命令行入口里：

candidate_pool 每行一个 {"text": ...}，不指定时只从输入文件已有的 neg 里检索。range_for_sampling 越靠前，负例越难。之后再叠加同域异因规则负例，并跑一遍假负例剔除。

5.3 评估脚本

离线指标过关后，在 RAG 链路里切换向量模型、重建索引，用黄金集问题做一次端到端对比。

5.4 已知坑

坑 表现 对策
小语料过拟合 epoch 大于 5 或数据少于 1000 条时通用能力明显下降 混入 10%–20% 通用检索数据，或早停
测试集泄漏 查询的扰动变体与测试查询语义重复，离线指标虚高 按根因码切分训练与测试，同根因不跨界
batch 太小 loss 在降但指标不动 按 5.2 的顺序腾显存保 batch
与 reranker 口径错位 换了向量模型、没换 reranker，整体变差 先摘掉 reranker 比较裸检索；生产必须用 reranker 时，用新向量模型重挖难负例并配套微调
假负例 训练后同根因案例反而被推远 训练前必跑根因码一致性校验

六、实战二：Qwen LoRA-SFT 结构化输出

前置条件：黄金集与确定性评分器已经就绪，第四章管线已产出 1200–1800 条定版数据，并在本地冒烟通过。

6.1 任务与成功标准

  • 任务：信号摘要 → RootCauseHypothesis JSON，刻意收窄为单一结构化任务。
  • 裁判：黄金集 + 确定性评分器（格式合法率、根因 top-1 命中率），外加强模型对解释质量打分。
  • 成功标准：格式合法率不低于 99.5%；根因 top-1 命中率达到对照大模型 API 的 90% 以上；P95 延迟和单次成本有数量级优势。目标是「窄任务逼近 + 延迟成本占优」，不是全面超越。

6.2 基座选择

Qwen3-4B-Instruct-2507 2025-08 非思考指令模型，LLaMA-Factory 官方示例所用基座，冒烟和低成本部署首选 复杂任务能力弱于 8B
Qwen3.5-9B 2026-02 更新一代，LLaMA-Factory 0.9.5 已提供 qwen3_5 / qwen3_5_nothink 模板 原生多模态、混合注意力架构；量化与 LoRA 部署需按所用推理框架版本实测

七、实战三：DPO 偏好优化

目标是流程贯通、建立直觉，指标提升是加分项，不是 KPI。

7.2 参考模型的坑：先合并，再训练新 adapter

LLaMA-Factory 在 LoRA 模式下没有显式指定 ref_model 时，DPO 的参考模型是「关闭 adapter 的当前模型」。如果直接在 SFT adapter 上继续训练，关闭 adapter 后得到的是原始基座，而不是 SFT 模型，DPO 约束的方向就偏了。稳妥做法是先把 SFT adapter 合并成新底模（6.4 节的导出配置），再在合并模型上训练一个新的 DPO adapter：

另一种做法是显式设置 ref_model 与 ref_model_adapters 指向 SFT 版本，代价是训练时多加载一份模型。

7.3 观察与止损

观察三件事：黄金集硬指标不许倒退；评审维度分数是否上移；同一输入采样 4 次，输出多样性是否塌缩。出现以下任一信号即停止：任何硬指标回退超过 1 个百分点；两轮数据迭代后目标维度提升不足 0.2 分；输出多样性明显塌缩。

八、如何验收与上线

验收只回答一个问题：在生产同款部署形态下，微调版是否在同一裁判面前稳定优于替代方案，并且随时可以退回。

8.1 验收对比表

所有候选在同一份黄金集、同一个评分器、生产同款部署形态下测：

8.2 模型资产登记

manifest 必填：model_id、base_model、adapter_hash、data_version、train_config_hash、eval_summary（格式合法率、命中率、评审分）、created_at、status（candidate / staging / prod / retired）。没有 eval_summary 的版本不允许进入 staging，评估门禁从代码延伸到模型资产。

8.3 上线形态、灰度与回滚

形态 方式 适用
multi-LoRA 热插拔 vLLM --enable-lora，按请求选 adapter 多技能并存、快速 A/B，首选
合并量化独立部署 导出合并权重再量化 端侧或资源受限
网关路由 AI 网关按租户、场景路由到微调版或大模型 API 生产形态：大模型 API 永远是兜底

灰度按 5% → 25% → 100% 放量，每档观察 24 小时。回滚就是切 adapter 或切路由，秒级完成。

8.4 上线后的监控与飞轮

  • 在线质量信号：格式合法率每个请求都能确定性判定，直接进指标系统；诊断工程师对根因的采纳与驳回写回观测平台，同时就是下一轮偏好数据。
  • 漂移检测：每月用黄金集重跑线上版本，指标漂移超过 2 个百分点就调查。新车型、新故障模式进入，就是数据分布漂移。
  • 重训节奏：季度例行 + 漂移触发；每次重训重新回答 1.6 节的五问，并通过验收门禁。
