OpenTelemetry 自托管部署

用 Docker Compose 自托管 Collector、Prometheus、Loki、Tempo、Grafana 与可选的 Langfuse v3…

Flywhl 24 分钟 更新于 2026.09 #可观测性#OpenTelemetry#Langfuse

先读结论

  1. Langfuse 单节点 ClickHouse 必须设置 CLICKHOUSE_CLUSTER_ENABLED=false，否则迁移因 ON CLUSTER 语句失败。
  2. MinIO 要在启动前建好 langfuse bucket，否则 OTLP 接收端直接返回 500。
  3. Collector 与 Tempo 以 UID 10001 运行，命名卷需要先 chown，否则持久化目录不可写。
  4. 只有 Collector 对宿主机暴露 OTLP 端口；数据库、缓存、ClickHouse 一律不映射。

本篇产出一套可长期使用的本地观测底座：OTel Collector + Prometheus + Loki + Tempo + Grafana，外加可选的 Langfuse（--profile langfuse）。全部镜像提供 arm64 版本，在 Apple Silicon + OrbStack 上完整跑通：三类信号写入与查询、Grafana 数据源连通、Langfuse 的 OTLP 接收与查询都做过验证。完成后即可支撑 05~10 篇的全部实践。

1. 架构与原理

1.1 数据怎么流动

flowchart LR
    App["应用 SDK"] -->|"OTLP 4317/4318"| Col["OTel Collector"]
    Col -->|"OTLP gRPC"| Tempo
    Col -->|"OTLP HTTP /api/v1/otlp"| Prom["Prometheus"]
    Col -->|"OTLP HTTP /otlp"| Loki
    Tempo -->|"metrics-generator remote write"| Prom
    Graf["Grafana"] --> Prom
    Graf --> Loki
    Graf --> Tempo
    Col -.->|"08 篇追加：OTLP HTTP"| LfWeb["Langfuse Web"]
  • Collector 是唯一入口：应用只认识 otel-collector:4317/4318，后端换型、加脱敏、加采样都不需要改应用。Tempo 的 OTLP 端口只在容器网络内开放。
  • Tempo metrics-generator：从收到的 Trace 生成 RED 指标（traces_spanmetrics_*）和服务拓扑指标（traces_service_graph_*），通过 remote write 写进 Prometheus，同时附带 exemplar（指向具体 trace_id 的样本）。
  • Grafana 的三向跳转：指标 → Trace 靠 exemplar；Trace → 日志靠 trace_id 过滤；日志 → Trace 靠 Loki 数据源的 derivedFields。三者都在数据源 provisioning 中配置（第 4.4 节）。

1.2 Langfuse v3 为什么需要五个组件

组件 职责 配错的后果
langfuse-web UI、API、OTLP 接收端；启动时执行 PostgreSQL 与 ClickHouse 迁移 —
langfuse-worker 从队列取任务，把事件写入 ClickHouse，执行评测等异步任务 数据接收成功但界面里看不到
PostgreSQL 组织、项目、用户、Prompt、评测配置等事务数据 无法登录、无法建项目
ClickHouse Trace、Observation、Score 等分析数据 迁移失败则 web 无法启动
Redis BullMQ 任务队列与缓存 必须 noeviction，否则排队中的任务会被淘汰
MinIO（S3） 原始事件先落对象存储，再由 worker 异步读取入库；也存放媒体文件 bucket 不存在时接收端直接返回 500

一条 Trace 进入 Langfuse 的路径是：web 接收 → 原始事件写入 S3（实测路径形如 events/otel/<项目 ID>/...）→ 在 Redis 中入队 → worker 读取 S3 并写入 ClickHouse。先落对象存储再异步入库，使突发流量不会直接压垮 ClickHouse，代价是依赖链更长，任何一环配错都表现为「数据发出去了但看不到」。

2. 运行时与版本选择

  • 运行时：所有组件都是 CPU 负载，容器化没有障碍；需要 GPU/Metal 加速的本地推理服务（如 Ollama）保持在宿主机运行，容器通过 host.docker.internal 访问，OrbStack 与 Docker Desktop 都支持这个域名。
  • 资源：实测刚启动并写入少量测试数据时，LGTM + Collector 五个容器合计约 550 MiB；Langfuse 六个容器合计约 2.2 GiB，其中 web 约 0.9 GiB、ClickHouse 约 0.8 GiB、worker 约 0.4 GiB。内存紧张时可以只起 LGTM 部分。
  • 版本（2026-07-08 核对，统一写在 .env）：
组件 版本 选择理由
otelcol-contrib 0.156.0 写作前一天发布的最新版；03 篇全部配置用它做过 validate
Prometheus v3.5.4 3.5 是 LTS 线，底座求稳；OTLP 接收能力已足够
Loki 3.7.3 3.7 线最新补丁
Tempo 2.10.7 3.0（2026-05-28）完成新写入架构切换并移除 2.x 旧组件，配置有 breaking 变化；2.10 线仍在发补丁，先锁 2.10，待 3.x 稳定后用官方 tempo-cli migrate config 迁移
Grafana 13.0.3 13 线稳定补丁
Langfuse 3.206.0 锁定具体版本；官方 compose 使用主版本标签 3，会随发布自动漂移
ClickHouse 25.8 LTS 版本；Langfuse 官方 compose 此时未锁版本，拉的是 latest
PostgreSQL / Redis 17 / 7 与 Langfuse 官方 compose 一致

MinIO 使用 cgr.dev/chainguard/minio：Langfuse 官方 compose 自 2025-12 起改用这个镜像，原因是原先的 minio/minio 镜像已不再维护。Chainguard 免费镜像只提供 latest 标签，无法锁版本，生产环境建议换成自有的 S3 兼容存储。

4. docker-compose.yml

与 Langfuse 官方 compose 相比的改动及原因：

改动 原因
Web 映射到宿主机 3001，NEXTAUTH_URL 同步改为 3001 3000 留给 Grafana；NEXTAUTH_URL 与实际访问地址不一致会导致登录回调失败
MinIO S3 API 映射到 9190、控制台 9191 官方示例用 9090，与 Prometheus 冲突
PostgreSQL、Redis、ClickHouse、worker 不映射宿主机端口 只在容器网络内使用；也避免与本机已有的 PostgreSQL（5432）冲突
服务名加 langfuse- 前缀，与 LGTM 共用 otel-net Collector 在 08 篇需要通过 langfuse-web:3000 转发数据
锁定 Langfuse 与 ClickHouse 版本 避免 latest 或主版本标签随发布漂移

保留下来的三处关键配置正是旧版本配置跑不通的原因：CLICKHOUSE_CLUSTER_ENABLED: "false"、MinIO 启动命令里的 mkdir -p /data/langfuse、Redis 的 noeviction。依赖服务都配了健康检查，web 与 worker 等它们就绪后才启动。

5. 组件配置文件

5.1 otel-collector/config.yaml

直接使用 03 篇第 3 节的完整配置。它引用了 file_storage 持久化队列，数据卷属主由上面的 init-perms 修正。

5.2 prometheus/prometheus.yml

OTLP 写入的资源属性默认不会变成标签：service.namespace 与 service.name 组合成 job（实测为 diag-platform/diag-agent），其余资源属性进入 target_info 指标。经常按环境过滤的属性，用 promote_resource_attributes 提升为标签更方便。

5.3 loki/loki-config.yaml（单机模式，OTLP 原生写入）

OTLP 日志进入 Loki 后，service.name 等少数资源属性成为索引标签（service_name），日志属性与 trace_id、span_id 成为结构化元数据，日志正文是 LogRecord 的 Body。这决定了查询写法：按 trace_id 查日志要用 {service_name="diag-agent"} | trace_id="..."，而不是行过滤 |=。

5.4 tempo/tempo.yaml（含 metrics-generator）

local-blocks 处理器为 TraceQL 指标查询提供数据，Grafana 的 Traces Drilldown 依赖它。span-metrics 的维度只放低基数属性。注意：这里的派生指标基于 Tempo 收到的数据，一旦在 Collector 启用尾部采样，就要按 03 篇 4.6 节改在采样前生成。

5.5 grafana/provisioning/datasources/datasources.yaml（三信号互跳的关键）

两处容易出错的地方：

  • $$ 转义：Grafana 的 provisioning 文件会展开 $VAR 形式的环境变量，查询模板里的 ${__value.raw}、${__tags} 必须写成 $${...}。
  • Trace → 日志不要用 filterByTraceID：这个开关生成的是日志正文的行过滤，只对「把 trace_id 打进日志正文」的应用有效；OTLP 日志的 trace_id 在结构化元数据里，必须用上面的自定义查询按字段过滤。tags 把 Span 的 service.name 映射为 Loki 标签 service_name，组成流选择器。

7. 按症状排错

现象 原因 处置
langfuse-web 反复重启，日志含 code: 139 ... There is no Zookeeper configuration，下一行是 CREATE TABLE schema_migrations ON CLUSTER default 未设置 CLICKHOUSE_CLUSTER_ENABLED=false，迁移按集群模式执行 ON CLUSTER 语句，单节点 ClickHouse 没有 ZooKeeper 配置（实测复现） 在 web 与 worker 的环境变量中设置为 "false" 后重启
OTLP 发往 Langfuse 返回 500 {"error":"Failed to upload JSON to S3"}，web 日志含 NoSuchBucket MinIO 中没有 langfuse bucket（实测复现） 使用第 4 节的 MinIO 启动命令预建目录；已运行的实例可在 MinIO 控制台（127.0.0.1:9191）手动创建
首次启动时 worker 日志出现一批 prisma:error worker 与 web 同时启动，web 还在执行 PostgreSQL 迁移，表尚不存在（实测复现） 等 web 日志出现 All migrations have been successfully applied 后执行 docker compose restart langfuse-worker，错误不再出现
Collector 启动即退出，日志含 open /var/lib/otelcol/file_storage/...: permission denied 命名卷属主是 root，Collector 以 UID 10001 运行（实测复现） 确认 init-perms 已成功执行；它的退出状态应为 0
Tempo 报 WAL 或 blocks 目录无写权限 同上，Tempo 同样以 UID 10001 运行 同上
Langfuse 启动报 ENCRYPTION_KEY 格式错误 仍是占位值，或不是 64 位十六进制 按第 3 节用 openssl rand -hex 32 生成
Langfuse 能登录但看不到数据 worker 未运行，或 worker 连不上 ClickHouse / MinIO 查看 worker 日志；确认 worker 与 web 使用同一组 x-langfuse-env 变量
登录后被重定向到错误地址 NEXTAUTH_URL 与浏览器实际访问的地址不一致 本地为 http://localhost:3001，反向代理后改为对外域名
界面上传图片等媒体文件失败 LANGFUSE_S3_MEDIA_UPLOAD_ENDPOINT 写成了容器名，浏览器无法访问 改为宿主机可达地址（本篇为 http://localhost:9190）
端口被占用导致容器起不来 本机已有服务占用 3000、9090 等端口 只改宿主机侧映射，容器网络内地址（otel-collector:4317 等）保持不变
Prometheus 查不到 traces_spanmetrics_* 未开 --web.enable-remote-write-receiver；或 overrides 中未启用 span-metrics 处理器 检查启动参数与 tempo.yaml 的 overrides
Grafana 的 exemplar 点不出来 Prometheus 未开 --enable-feature=exemplar-storage 补启动参数后重启 Prometheus

9. 运维备忘

  • 数据留存：Prometheus 15 天，Tempo 与 Loki 7 天，Langfuse 不自动清理（生产在 10 篇收紧）；
  • 持久化队列：otelcol-queue 卷里是尚未发出的数据，down -v 会一并删除；
  • 升级顺序：先改 .env 中的版本号，docker compose pull 后逐个重启；Collector 升级前先用新版本镜像对配置执行 validate。

2026-09 补记：Langfuse v4 与官方 compose 的变化

  • 服务端 v4.0.0 于 2026-07-29 发布，截至 2026-09 已到 v4.46。v4 改为以 Observation 为中心的数据模型，带来全文检索、Monitors & Alerts、Observations API v2。基础设施组件不变（web、worker、PostgreSQL、ClickHouse、Redis、S3），但最低版本提高：ClickHouse ≥ 25.12（推荐 26.4）、PostgreSQL ≥ 15、Redis ≥ 7.0。本篇锁定的 ClickHouse 25.8 需要先升级，PostgreSQL 17 与 Redis 7 满足要求。
  • 升级路径（官方指南分三步，每步都可独立停留）：先在 v3 上把 ClickHouse 升到兼容版本；再把 LANGFUSE_VERSION 升到 v4，并以 legacy 或 dual 写入模式保持原有行为；最后迁移 SDK、API 调用方、评测与导出，再切换到 v4 默认的 events_only 模式。升级前先升到最新的 v3 版本，并确认所有后台迁移已完成。v3 的安全补丁维持到 2027 年 1 月底。
  • 影响本篇验证步骤：切换到 events_only 后，GET /api/public/traces 等旧读接口返回 404，改用 Observations API v2；OTLP 接收端 /api/public/otel 不变。
  • 官方 compose 的调整：2026-07-23 起把 ClickHouse 锁定为 25.12；2026-07-30 起默认拉取 v4 镜像；2026-08-18 起镜像改从 docker.langfuse.com 分发（如 docker.langfuse.com/langfuse/langfuse:4）。
