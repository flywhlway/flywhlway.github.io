GenAI 语义约定与 AI 可观测标准

gen_ai.* 语义约定是 AI 可观测体系的数据契约。本篇给出 2026-07 时点的 Span 建模、按版本整理的属性迁移对照、标准指标、内容捕获开关与私有属性命名规范。

Flywhl 13 分钟 更新于 2026.09 #可观测性#OpenTelemetry#GenAI

先读结论

  1. GenAI（含 MCP）约定已于 v1.42 迁到独立仓库 semantic-conventions-genai，全部仍是 Development，平台必须锁定版本。
  2. 旧属性迁移集中在 v1.28 与 v1.37 两个版本：token 字段改名、gen_ai.system 改为 gen_ai.provider.name、逐条消息事件改为结构化 messages 属性。
  3. 自定义字段一律用 app.* 前缀，绝不放进 gen_ai.* 等官方命名空间；高基数字段只进 Span，不进指标维度。

gen_ai.* 语义约定是整个 AI 可观测体系的数据契约：SDK 按它埋点，Collector 按它路由和脱敏，Tempo、Langfuse、Grafana 按它检索和算成本。约定本身还在快速变化，所以本篇先讲版本策略，再讲 Span 建模、指标、内容捕获，最后给出本平台的私有属性命名规范。

1. 现状与版本策略（务必先读）

1.1 约定放在哪里、稳定到什么程度

  • 仓库：GenAI 约定由 GenAI SIG 维护。semantic-conventions v1.42.0（2026-06-12）把 model/gen-ai/、model/openai/、model/mcp/ 下的全部定义迁到独立仓库 open-telemetry/semantic-conventions-genai（2026-05-05 建仓），主仓库中的对应内容标记为 deprecated。主仓库里最后一个完整、未标 deprecated 的版本是 v1.41（v1.41.1，2026-05-11）。
  • 稳定性：新仓库中的 GenAI 与 MCP 约定全部处于 Development，截至本文写作尚无独立 release。它的 main 分支仍在做 breaking 调整，例如 gen_ai.request.top_k 改为整数、检索 Span 改用新的 gen_ai.retrieval.top_k，内部 invoke_agent Span 不再要求 gen_ai.provider.name。
  • 实际可用度：推理 Span 的核心属性和 Token 指标在各后端中已经相对稳定，Grafana、Datadog、Honeycomb、Langfuse 都能直接消费；Agent、检索、MCP 相关部分仍在频繁调整。

因此版本策略是：以 v1.41 的定义为基线，关注新仓库 main 分支的 changelog，平台内统一锁定，不让各服务自行跟进。

1.2 opt-in 机制

约定规定：已经按 v1.36.0 或更早版本输出属性的埋点库，默认不得切换到新版；需要新版时由使用者显式 opt-in：

这个开关还影响其它行为：Python 的 opentelemetry-util-genai 只有在该模式下才启用新的内容捕获模式（见第 5 节）。不设置它，同一个埋点库会继续输出 gen_ai.system 这类旧属性，这是「升级了依赖但看板没变化」的最常见原因。

1.3 属性迁移对照（按版本）

版本 旧 新 影响面
v1.28.0 gen_ai.usage.prompt_tokens / gen_ai.usage.completion_tokens gen_ai.usage.input_tokens / gen_ai.usage.output_tokens 早期成本看板、告警规则
v1.28.0 gen_ai.prompt / gen_ai.completion 属性 逐条消息的 log-based events（gen_ai.system.message、gen_ai.user.message、gen_ai.assistant.message、gen_ai.tool.message、gen_ai.choice） 内容捕获管道
v1.37.0 上一行的逐条消息事件 gen_ai.system_instructions / gen_ai.input.messages / gen_ai.output.messages，可放在 Span 属性上，或放进 gen_ai.client.inference.operation.details 事件 内容捕获管道、Langfuse 的输入输出展示
v1.37.0 gen_ai.system gen_ai.provider.name 所有按厂商分组的查询与面板
v1.37.0 gen_ai.openai.* openai.*（如 openai.request.service_tier） 厂商特定属性
v1.38.0 — gen_ai.tool.definitions（推理与 invoke_agent Span）、gen_ai.tool.call.arguments / gen_ai.tool.call.result（execute_tool Span）、评测事件 gen_ai.evaluation.result 新增
v1.39.0 — MCP 约定（mcp.method.name 等） 新增
v1.40.0 — retrieval Span、gen_ai.agent.version、gen_ai.usage.cache_read.input_tokens / gen_ai.usage.cache_creation.input_tokens 新增
v1.41.0 单一 invoke_agent Span 拆为 client / internal 两种；新增 invoke_workflow、gen_ai.usage.reasoning.output_tokens、流式首块时延指标 Agent 建模
v1.42.0 主仓库 迁至 semantic-conventions-genai 查阅定义的位置

工程建议：平台统一 opt-in 最新版，并在 Collector 用 transform 处理器做「旧 → 新」的兜底改名（示例见 03 篇 OTTL 一节）。兜底只适用于同义改名（如 gen_ai.system → gen_ai.provider.name、prompt_tokens → input_tokens）；消息内容从逐条事件改为结构化属性属于数据形态变化，Collector 里重组成本高且易错，必须升级埋点库解决。

2. Span 建模：按 operation 划分

gen_ai.operation.name 是所有 GenAI Span 的判别器，v1.41 定义的取值和对应建模：

operation Span 名 SpanKind 典型场景
chat / generate_content / text_completion {operation} {request.model} CLIENT（进程内模型可为 INTERNAL） 一次 LLM 调用
embeddings embeddings {request.model} CLIENT 向量化
retrieval retrieval {data_source.id} CLIENT 向量库或检索服务查询
execute_tool execute_tool {tool.name} INTERNAL 函数调用、工具执行
create_agent create_agent {agent.name} CLIENT 在远程 Agent 服务上创建 Agent
invoke_agent invoke_agent {agent.name} CLIENT 或 INTERNAL 调用一个 Agent
invoke_workflow invoke_workflow {workflow.name} INTERNAL 多 Agent 编排工作流

2.1 推理 Span（Inference）

每次 LLM 调用生成一个 Span，如 chat deepseek-chat。核心属性：

属性 示例 说明
gen_ai.operation.name chat 操作类型判别器
gen_ai.provider.name deepseek / openai / anthropic Provider 判别器，决定伴随哪些厂商特定属性
gen_ai.request.model deepseek-chat 请求的模型
gen_ai.response.model deepseek-chat-20260601 实际响应的模型（灰度或路由后可能不同）
gen_ai.usage.input_tokens 1834 输入 Token，包含缓存命中部分
gen_ai.usage.output_tokens 412 输出 Token
gen_ai.usage.cache_read.input_tokens 1200 命中 Provider 缓存的输入 Token（v1.40）
gen_ai.usage.reasoning.output_tokens 256 推理模型的思考 Token（v1.41）
gen_ai.response.finish_reasons ["stop"] / ["tool_calls"] 停止原因，排查截断与死循环的关键
gen_ai.request.stream true 是否流式（v1.41）
gen_ai.response.time_to_first_chunk 0.83 流式首块时延，单位秒（v1.41）
gen_ai.request.temperature 等 0.2 采样参数族 gen_ai.request.*
error.type 429 / TimeoutError 低基数错误标识

两个容易算错成本的细节：

  • 输入 Token 口径：约定要求 input_tokens 包含缓存读写部分。Anthropic 原生返回的 input_tokens 不含缓存，约定给出的换算是 input_tokens + cache_read_input_tokens + cache_creation_input_tokens。成本计算时应把 cache_read 部分按缓存价单独计费，而不是重复加总。
  • 请求模型与响应模型：成本按 gen_ai.response.model 计价更准确，按 gen_ai.request.model 分组看路由效果，两个维度不要混用。

2.2 Embedding 与检索 Span

  • Embedding：gen_ai.operation.name=embeddings，附 gen_ai.request.encoding_formats、gen_ai.embeddings.dimension.count（v1.38）。
  • 检索（v1.40）：gen_ai.operation.name=retrieval，gen_ai.data_source.id 标识数据源（Milvus collection、文档库等）。查询文本 gen_ai.retrieval.query.text 与召回文档 gen_ai.retrieval.documents 属于内容级数据，与消息内容一样默认不采集，开启时必须遵循官方 JSON schema。

检索 Span 的价值在于把「答错」拆成「没召回」和「召回了但模型没用上」两类问题：前者看召回文档与 query，后者看推理 Span 的输入内容。

2.3 工具执行 Span（execute_tool）

工具内部的真实动作（HTTP 调用、SQL、向量检索）应作为子 Span 由常规埋点产生，而不是塞进工具 Span 的属性里——这样服务拓扑图才能反映工具的真实依赖，工具慢在哪一跳也能直接看出来。

2.4 Agent 与工作流 Span

v1.41 把 invoke_agent 拆成两种，选哪种取决于 Agent 在哪里运行：

情况 选择 说明
调用远程托管的 Agent 服务 invoke_agent，SpanKind CLIENT 可带 server.address 等远端属性
进程内框架执行（LangGraph、Spring AI 等） invoke_agent，SpanKind INTERNAL 本平台的主要形态
一张图里编排多个 Agent（supervisor、handoff） 顶层 invoke_workflow，每个子 Agent 一个 invoke_agent gen_ai.workflow.name 标识工作流

常用属性：

属性 说明
gen_ai.agent.name / gen_ai.agent.id Agent 标识（如 vehicle-diag-agent）
gen_ai.agent.version Agent 版本（v1.40），用于对比 Prompt 或图结构改版前后的效果
gen_ai.agent.description 自由文本描述
gen_ai.conversation.id 会话标识，跨请求聚合多轮对话
gen_ai.tool.definitions 该 Agent 可用的工具定义（v1.38），体积大，按需开启

LangGraph 一次图执行的典型结构：invoke_agent 根 Span → 每个 node 一个子 Span → node 内的 LLM 与工具调用再下一层。这是多数生产 Agent 排障的主战场：只埋 LLM Span 会漏掉规划、节点间路由、子 Agent 交接这些真正的耗时点。

2.5 MCP Span（v1.39）

MCP 约定与 GenAI 约定同仓维护，客户端与服务端各自产生 Span：

  • Span 名为 {mcp.method.name} {target}，如 tools/call query_dtc_knowledge；没有低基数的 target 时只用方法名。
  • 关键属性：mcp.method.name（tools/call、tools/list、resources/read 等）、mcp.session.id、mcp.protocol.version、mcp.resource.uri；被调用的工具名复用 gen_ai.tool.name。
  • 指标：mcp.client.operation.duration、mcp.server.operation.duration、mcp.client.session.duration、mcp.server.session.duration。

当 Agent 通过 MCP 调工具时，链路上会同时出现 execute_tool（Agent 侧的语义）与 tools/call（协议侧的语义）两层 Span，两者是父子关系而不是重复埋点。

2.6 评测（Evaluation，v1.38）

评测结果用 gen_ai.evaluation.result 事件表达，属性包括 gen_ai.evaluation.name、gen_ai.evaluation.score.value、gen_ai.evaluation.score.label、gen_ai.evaluation.explanation，事件挂在被评测的那次操作上。实践中评测通常在 Langfuse 侧完成（见 08 篇），OTel 侧约定主要用于跨平台交换评测结果。

3. 标准指标（Metrics）

指标 类型 关键维度 用途
gen_ai.client.token.usage Histogram gen_ai.token.type（input/output）、gen_ai.request.model、gen_ai.provider.name Token 用量与成本归因
gen_ai.client.operation.duration Histogram 同上 + error.type LLM 调用时延分布与错误率
gen_ai.client.operation.time_to_first_chunk Histogram 同上 客户端视角的流式首块时延（v1.41）
gen_ai.client.operation.time_per_output_chunk Histogram 同上 流式输出节奏（v1.41）
gen_ai.server.time_to_first_token Histogram 模型服务端（vLLM 等）暴露 服务端视角的 TTFT
gen_ai.server.time_per_output_token Histogram 同上 解码速度

客户端与服务端两组时延指标要对照着看：客户端首块时延明显大于服务端 TTFT，时间就花在网关、网络或排队上，而不是模型本身。

指标维度只能用低基数属性。gen_ai.conversation.id、user.id 这类每个会话都不同的值放进指标维度，会让 Prometheus 的时间序列数失控。

4. 内容捕获（Prompt/Completion）与隐私

默认不捕获消息内容，只记录元数据（模型、Token、耗时）。按需开启：

内容捕获的三种落地形态：

形态 对应开关 适用场景 代价
Span 属性内联 SPAN_ONLY POC、低敏场景，Langfuse 直接展示输入输出 内容与链路同权限、同留存
独立事件（gen_ai.client.inference.operation.details） EVENT_ONLY 需要对内容单独设置留存期与访问控制 查看内容要跨信号关联
外部存储引用 埋点库的上传钩子（Python util-genai 提供） 大内容、强合规 需要额外的对象存储与权限体系

纵深防御三层（生产必做，详见 10 篇）：

  • SDK 层：非必要不开启内容捕获；
  • Collector 层：redaction 处理器做属性白名单与值屏蔽，transform 处理器用 OTTL 正则脱敏（手机号、VIN、身份证），配置见 03 篇；
  • 后端层：Tempo、Langfuse 访问控制，缩小泄露爆炸半径。

5. 私有属性命名规范

约定覆盖不到的业务字段（租户、业务通道、车辆标识等）需要自定义属性。本系列统一规则如下。

5.1 规则

  1. 自定义字段绝不放进 gen_ai.*，也不放进 mcp.*、openai.*、http.*、db.*、otel.* 等任何官方命名空间。原因有三：约定仍在 Development，今天没用到的名字明天可能被官方占用并赋予不同含义；Langfuse、Datadog 等后端按 gen_ai.* 解析数据，私有字段混进去会被错误解读；Collector 的脱敏和路由规则按命名空间编写，混用会让规则失效。
  2. 统一使用反向域名前缀 com.example.*（以你的组织域名替换 com.example）。不用看似简短的 app.*：语义约定里已经存在面向客户端应用的 app 命名空间（app.installation.id、app.crash.id、app.build_id、app.screen.*、app.widget.*、app.jank.*），官方命名指南明确建议私有属性使用反向域名前缀（官方示例为 com.acme.shopname），以免日后与官方新增字段冲突。前缀较长的代价，可以在 SDK 里用常量封装抵消。
  3. 先查官方，再造新名。已有标准属性的直接用：用户用 user.id，会话用 session.id 并与 gen_ai.conversation.id 对齐，环境用 deployment.environment.name，错误用 error.type。
  4. 格式：全小写，点号分隔命名空间，多词用下划线（com.example.vehicle.vin_hash），名字中不写单位。
  5. 指标命名：不加 _total 后缀（导出到 Prometheus 时会自动追加，自己加了会变成 _total_total）；单位写在 instrument 的 unit 字段，如 {iteration}、{CNY}。
  6. 按基数分级：低基数字段（枚举值、租户）可以同时进 Span 和指标维度；高基数字段（车辆标识、用户标识）只进 Span 和日志，禁止作为指标维度。
  7. 敏感值只放派生值：身份类字段只放哈希或假名化结果，名字以 _hash 结尾，方便 Collector 规则识别；明文禁止出现在任何属性中。

5.2 本平台的属性登记

以一个设备诊断 Agent 平台为例，Resource 与业务属性统一如下：

配套的私有指标：

指标 类型与单位 用途
com.example.diagnose.requests Counter，{request} 按分诊通道统计请求量
com.example.agent.loop.count Histogram，{iteration} 单次会话 Agent 循环次数，发现失控循环
com.example.token.cost Counter，{CNY} 按价目表折算的 Token 成本
com.example.tool.failures Counter，{failure} 工具失败次数，维度为 gen_ai.tool.name 与 error.type

建议在仓库中维护一份属性登记表（名称、类型、基数级别、是否敏感、负责人），代码评审时对照检查，新增属性先登记后使用。

6. 本章小结与自查清单

  • 全平台统一设置 OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental，并以 v1.41 定义为基线；
  • 看板与告警只引用新属性名，旧名由 Collector 兜底改名；
  • 推理、Embedding、检索、工具、Agent、工作流、MCP 各类 Span 都有归属，Agent 编排层不缺埋点；
  • Token 指标进入 Prometheus，成本可按模型 × 租户 × 路由归因，缓存 Token 单独计价；
  • 内容捕获默认关闭，开启场景有脱敏与访问控制方案；
  • 私有属性使用 app.* 前缀，二级名不与官方 app.* 属性冲突，不占用 gen_ai.* 命名空间。

2026-09 补记：新仓库 main 分支的 breaking 变更

截至 2026-09 末，semantic-conventions-genai 仍无 release，但 main 分支又合入了几项会影响看板的变更（均未发布，埋点库尚未跟进）：

  • 缓存写入 Token 改名（2026-08-20）：gen_ai.usage.cache_creation.input_tokens 改为 gen_ai.usage.cache_write.input_tokens，同时新增按模态区分的 gen_ai.usage.{text,image,audio}.* 属性。
  • Token 指标拆分（2026-09-22）：gen_ai.client.token.usage 直方图及其依赖的 gen_ai.token.type 被替换为按方向、按操作拆分的指标：计数器 gen_ai.client.inference.usage.input_tokens、gen_ai.client.inference.usage.output_tokens、gen_ai.client.inference.usage.cache_read.input_tokens、gen_ai.client.inference.usage.cache_write.input_tokens、gen_ai.client.inference.usage.reasoning.output_tokens，以及直方图 gen_ai.client.inference.operation.input_tokens / gen_ai.client.inference.operation.output_tokens，并用新属性 gen_ai.token.modality 区分模态。
  • finish_reason 收口（2026-09-01）：gen_ai.output.messages[].finish_reason 废弃，统一用 gen_ai.response.finish_reasons。
  • 内部 invoke_agent Span 去掉缓存 Token（2026-08-27）：跨多次推理汇总的缓存数字容易误读，改为从各推理 Span 自行汇总。

应对方式不变：在埋点库正式跟进之前不改线上属性；成本看板的查询提前准备新旧两套指标名，待平台统一升级埋点库时一并切换。
