OTLP 协议与 Collector 实战

OTLP gRPC 与 HTTP 怎么选，Collector 管道怎么设计，内存保护、持久化队列与重试怎么配，头部与尾部采样怎么取舍，OTTL 怎么脱敏，出了问题按什么顺序排查。

Flywhl 24 分钟 发布于 2026.07 #可观测性#OpenTelemetry#Collector

先读结论

  1. 只让 Collector 对外暴露 OTLP 端口：任何绕过 Collector 直连后端的链路，都会让脱敏和采样失效。
  2. memory_limiter 第一、batch 最后、派生指标在采样之前，这三条顺序决定了数据是否准确、是否会丢。
  3. sending_queue 挂 file_storage 后，后端故障与 Collector 重启都不丢队列数据；数据卷必须对 UID 10001 可写。
  4. Agent 会话长，尾部采样的 decision_wait 要覆盖单轮对话耗时，并用 decision_cache 兜住晚到的 Span。

OTLP 是统一的遥测协议，Collector 是统一的遥测枢纽。本篇聚焦工程实操：协议怎么选、管道怎么设计、可靠性怎么保证、采样怎么做、数据怎么脱敏、出问题怎么查。文中配置都以 04 篇 .env 锁定的 Collector 版本（otelcol-contrib）跑过 validate，脱敏与持久化队列的行为也做过实测，04 篇的部署直接复用这里的配置。

1. OTLP 协议：gRPC 还是 HTTP

1.1 速查

项 OTLP/gRPC OTLP/HTTP
默认端口 4317 4318
编码 Protobuf Protobuf（推荐）或 JSON
路径 gRPC 服务方法 /v1/traces、/v1/metrics、/v1/logs
连接模型 HTTP/2 长连接、多路复用 每批数据一个请求，HTTP/1.1 或 HTTP/2
部分成功 响应中带 partial_success 同左，JSON 请求成功时响应体为 {"partialSuccess":{}}

Traces、Metrics、Logs 三类信号的 OTLP 定义均已 Stable；Profiles 于 2026-03-26 进入公开 Alpha，本系列不使用。

1.2 取舍

两种传输承载的是同一套 Protobuf 数据模型，差别只在「路怎么走」：

场景 选择 原因
同一 Docker 网络或 K8s 集群内，SDK → Collector、Collector → Tempo gRPC 长连接省握手，二进制编码，吞吐最高
中间经过 Nginx、API 网关或企业代理 HTTP 七层代理普遍支持 HTTP/1.1，gRPC 需要 HTTP/2 端到端贯通
浏览器、Serverless、移动端 HTTP 浏览器无法直接发 gRPC；需要在 Collector 上配 CORS
发往 Langfuse HTTP Langfuse 的 OTLP 接收端只支持 HTTP（Protobuf 或 JSON）
多副本 Collector 前面有负载均衡 优先 HTTP，或 gRPC + 七层负载均衡 gRPC 长连接会「粘」在建连时的副本上，四层负载均衡下流量会严重倾斜

两点常被忽略的共性：

  • 压缩：两种传输都支持 gzip，SDK 侧用 OTEL_EXPORTER_OTLP_COMPRESSION=gzip 开启。Prompt 与回答内容进入 Span 后单个 Span 可达几十 KB，压缩收益明显。
  • 重试语义：OTLP 规定 HTTP 429、502、503、504 以及 gRPC 的 UNAVAILABLE 等状态可以重试；400 这类错误表示数据本身有问题，重试也没用，会被直接丢弃。Collector 的 memory_limiter 拒收时返回的是可重试错误，所以「过载拒收」不等于「丢数据」，前提是上游会重试。

1.3 SDK 侧标准环境变量

所有语言的 SDK 都认同一组环境变量，这是「零代码切换后端」的基础：

三个最常见的坑：

  1. 路径拼接规则不同：用 HTTP 时，通用变量 OTEL_EXPORTER_OTLP_ENDPOINT 是基础地址，SDK 会自动追加 /v1/traces；按信号的 OTEL_EXPORTER_OTLP_TRACES_ENDPOINT 则原样使用，必须写全路径。两者混用，要么 404，要么路径重复。
  2. 默认协议因语言而异：例如 Java Agent 2.x 默认 http/protobuf（4318），不显式设置时很容易把 HTTP 请求发到 4317。统一在部署模板里显式写 OTEL_EXPORTER_OTLP_PROTOCOL。
  3. 直连后端等于绕过治理：上面的 Langfuse 直连只适合本地调试。生产链路一律经 Collector，否则第 5 节的脱敏规则、第 4 节的采样策略都管不到这部分数据。

2. Collector 架构、部署模式与管道设计

2.1 组件与发行版

  • 发行版：otelcol（core，组件精简）与 otelcol-contrib（组件最全，含 tail_sampling、transform、redaction、file_storage 等，本系列默认）。生产环境可以用官方的 OpenTelemetry Collector Builder 裁剪出只含所需组件的自定义发行版，镜像更小、攻击面更少。
  • 版本节奏：Collector 仍是 v0.x，大约每两周一个版本，配置键会随版本调整。两个已经发生、且会直接导致「配置照抄却跑不通」的变化：v0.104 起 receiver 与 extension 的默认监听地址从 0.0.0.0 改为 localhost，容器内必须显式写 0.0.0.0；自身指标的暴露方式改为 service.telemetry.metrics.readers。版本号统一在 04 篇 .env 锁定，升级前先在本地用 validate 子命令校验配置。

2.2 部署模式

模式 形态 职责
Agent 每台主机或每个 Pod 一个（DaemonSet / Sidecar） 就近接收、补资源属性、快速转发
Gateway 集中式多副本 采样、脱敏、路由、对外认证、多后端分发
合一 单实例 POC 与本地环境（04 篇采用）

2.3 管道设计原则

  1. 内存保护放第一位。memory_limiter 必须是每条管道的第一个处理器：它拒收时数据还没被后续处理器复制和缓存，上游收到可重试错误后会退避重发。放在后面，数据已经占了内存，保护就失去意义。
  2. 先丢弃，再加工。确定无用的数据（健康检查 Span、调试日志）尽早用 filter 丢掉，别让它们消耗 transform 的正则开销和队列空间。
  3. 脱敏在分叉之前。所有后端共享的脱敏规则放在公共管道里，处理完再通过 connector 分叉到各后端。每个分支各自脱敏，迟早有一条分支漏配。
  4. 派生指标在采样之前。从 Trace 生成 RED 指标必须看到全量 Span，否则错误率、调用量都会失真（详见 4.6 节）。
  5. batch 放最后。攒批应发生在所有丢弃动作（过滤、采样）之后，这也是 batch 处理器文档的明确建议。
  6. 按后端隔离故障。每个 exporter 配独立的 sending_queue：某个后端宕机只会堆积它自己的队列，不拖慢其它后端。
  7. 单一入口。只有 Collector 对外暴露 OTLP 端口，Tempo 等后端的 OTLP 端口不映射到宿主机，从网络层面杜绝绕过脱敏的旁路。
  8. Collector 自己也要被观测。把 :8888 的自身指标抓进 Prometheus，对队列水位、发送失败、拒收三类指标设告警（见 7.2 节）。

3. 基准配置（逐段注释）

以下是本系列中心 Collector 的配置骨架（04 篇的 deploy/otel-collector/config.yaml）。Langfuse 分支在 08 篇追加，这里只包含 LGTM 三个后端：

要点：

  1. 处理器顺序：memory_limiter 第一、batch 最后，中间先清理敏感头、再做兼容映射、最后脱敏；
  2. Prometheus 3.x 与 Loki 3.x 都能原生接收 OTLP，不再需要 prometheusremotewrite、loki 这类专用 exporter（旧版本集群仍需要）；
  3. otlphttp 的 endpoint 是基础地址，exporter 会自动追加 /v1/metrics、/v1/logs，这一点与 SDK 的通用变量一致；
  4. 指标管道没有接内容脱敏：指标只应携带低基数维度，内容不该出现在这里，出现了就是埋点问题，要在源头修。

3.1 可靠性配置详解

memory_limiter：内存超过软限制（硬限制减去 spike）时拒收数据，超过硬限制时额外强制 GC；恢复到软限制以下后自动放行。容器环境用 limit_percentage，让容器的内存上限决定 Collector 的上限；同时设置环境变量 GOMEMLIMIT 为硬限制的约 80%，让 Go 运行时提前回收（04 篇 compose 中容器上限 1 GiB、GOMEMLIMIT=800MiB）。拒收是可重试错误，只有上游不重试时才会真正丢数据。

batch：send_batch_size 是触发发送的阈值，不限制批大小；send_batch_max_size 才是上限，用于把超大批次切开，避免单个请求超过后端的消息大小限制；timeout 决定低流量时的最大延迟。注意 batch 处理器把数据攒在内存里，进程崩溃时这部分数据会丢。需要把攒批也纳入持久化范围时，可以改用 exporter 自带的 sending_queue.batch 攒批并去掉 batch 处理器；本系列 POC 保留 batch 处理器，配置更直观。

sending_queue：每个 exporter 一个发送队列，默认在内存中、容量 1000 个批次、10 个消费者。队列满时新数据被立即拒绝（block_on_overflow: false），日志出现 Exporting failed. Rejecting data.，otelcol_exporter_enqueue_failed_spans 增长，错误沿管道回传给 receiver——实测 OTLP/HTTP 客户端收到 503，SDK 会按可重试错误退避重发，重发也失败才真正丢失。同一条管道挂多个 exporter 时，一个后端的队列满会让整批数据向客户端报错，客户端重发后其它后端可能收到重复数据，这是「按后端隔离」的另一个理由。配置 storage 指向 file_storage 扩展后改为磁盘队列，Collector 重启后从磁盘继续发送。本地实测：Tempo 不可达时队列中积压 1 个批次，重启 Collector 后 otelcol_exporter_queue_size 仍为 1，数据没有丢。

retry_on_failure：默认首次等待 5 秒、退避上限 30 秒、单批总重试时长 300 秒。max_elapsed_time 决定能扛住多长的后端故障：超时后这批数据被丢弃；设为 0 则永不放弃，但队列会被积压的旧数据占满，新数据反而进不来。本系列取 10 分钟，覆盖后端重启和短暂网络故障。

file_storage：目录必须存在且对 Collector 进程可写。官方镜像以 UID 10001 运行，而 Docker 新建的命名卷属主是 root，直接挂载会在启动时报 permission denied 并退出（实测复现）。04 篇用一个一次性的 busybox 容器先执行 chown，再启动 Collector。

各种故障下数据会不会丢：

场景 仅内存队列 磁盘队列（file_storage）
后端短暂不可用（短于 max_elapsed_time） 队列未满就不丢 不丢
后端长时间不可用 超时或队列满后丢弃 磁盘队列满或超时后丢弃
Collector 重启或崩溃 队列与 batch 中的数据全部丢失 队列数据保留；batch 处理器和尾部采样缓冲中的数据仍会丢
Collector 内存逼近上限 memory_limiter 拒收，上游重试 同左
应用进程退出 SDK 未刷出的数据丢失，需在退出钩子里调用 shutdown 或 force_flush 同左

4. 采样策略

4.1 头部采样（Head Sampling，SDK 侧）

parentbased_* 保证下游服务服从上游的决策（通过 traceparent 中的采样标志传递），同一条 Trace 不会被切成「有的服务采了、有的没采」。traceidratio 按 Trace ID 计算，同一个 ID 在任何节点上结论都一致。

优点是开销最小，未采样的 Span 连创建成本都很低；缺点是决策发生在请求开始时，不知道这条链路后面会不会出错、会不会变慢，错误链路按比例一起被丢掉。

4.2 尾部采样（Tail Sampling，Collector 侧，生产推荐）

先缓冲完整的 Trace，再按规则决策，实现「错误全留、慢请求全留、正常流量抽样」：

多条策略之间是「或」的关系：任一策略判定保留，整条 Trace 就保留；只有显式的 drop 类策略能一票否决。

4.3 头部还是尾部：决策表

条件 推荐 说明
POC、日调用量小 不采样（SDK 100%） 数据量可控，排障需要全量
流量大、只关心整体趋势 头部采样 成本最低，趋势指标另由 Metrics 负责
必须保住错误与慢请求 尾部采样 需要缓冲内存，并保证同一 Trace 到达同一实例
流量极大且要保住错误 两者结合 SDK 侧先按较高比例头部采样降量，Collector 再做尾部采样；错误链路的保留率受头部比例限制
网关自己发起 Trace 网关 100% 采样，Collector 统一裁决 避免网关与 SDK 各采各的（见 07 篇）

4.4 Agent 长会话的特殊问题

尾部采样假设「一条 Trace 在 decision_wait 内结束」，而 Agent 会话恰恰可能持续数分钟：

  • 决策过早：Trace 还没结束就做了决策，之后才出现的错误 Span 不会改变结论；若此前判定为丢弃，这个错误就丢了。
  • 晚到的 Span：决策后到达的 Span 由 decision_cache 按已有结论处理；缓存没配或被挤出时，它会被当成一条新 Trace 重新决策，Tempo 里就看到残缺的链路。
  • 内存压力：缓冲量约等于 num_traces × 每条 Trace 的 Span 数 × 单个 Span 大小。按每条 50 个 Span、每个约 1 KB 估算，5 万条就是约 2.5 GB；开启内容捕获后单个 Span 可能大一个数量级。

工程上的做法：一轮对话一条 Trace，会话级别用 gen_ai.conversation.id 聚合，而不是把整个会话塞进一条 Trace；decision_wait 取单轮耗时的 P99 再留余量；decision_cache 容量设为 num_traces 的数倍；内容捕获的数据量要计入 Collector 的内存预算。

4.5 多副本部署

尾部采样要求同一 Trace 的所有 Span 到达同一个 Collector 实例。多副本时需要两层：第一层用 loadbalancing exporter 按 Trace ID 分发，第二层做尾部采样。拓扑与扩缩容注意事项见 10 篇。

4.6 采样与派生指标的先后

从 Trace 派生的 RED 指标（调用量、错误率、时延）必须在采样之前计算。在采样之后计算，错误全留、正常流量只留 10%，算出来的错误率会被放大数倍。

这对 Tempo 的 metrics-generator 同样成立：它只能看到 Collector 采样后写入的 Trace。因此：

  • 不做尾部采样时（本系列 POC），用 Tempo metrics-generator 生成 RED 指标与服务拓扑，配置最简单；
  • 启用尾部采样后，改在 Collector 里用 spanmetrics connector 在采样前生成指标，并关闭 Tempo 的 span-metrics 处理器，避免两套数字互相矛盾（配置见第 6 节）。

5. OTTL 加工：脱敏与语义约定兜底

5.1 transform：正则脱敏

transform 处理器用 OTTL 语言做模式化改写。第 3 节配置里的 transform/pii 用 replace_all_patterns 扫描所有字符串属性值，而不是逐个列举属性名：GenAI 内容可能出现在 gen_ai.input.messages、gen_ai.output.messages、gen_ai.system_instructions、gen_ai.tool.call.arguments、gen_ai.retrieval.query.text 等多个属性里，逐个列举迟早漏掉新增的属性。

实测效果（输入是一个带内容捕获的推理 Span）：

编写规则时的几个要点：

  • 正则引擎是 RE2：不支持回溯引用和前后断言。\b 按 ASCII 单词边界判断，汉字与全角标点都算非单词字符，所以 \b1[3-9]\d{9}\b 在中文语境里能正确命中手机号，又不会误伤更长的数字串。
  • 双重转义：YAML 双引号字符串里的 \\d 才是正则里的 \d。另外 Collector 会把配置中的 ${...} 当作环境变量展开，替换串里需要字面量 $ 时要写成 $$。
  • 顺序有讲究：先替换 18 位身份证号，再替换 11 位手机号和 17 位 VIN，避免长串被短规则切碎后漏网。
  • 接受误伤：VIN 规则会把 17 位纯数字编号也替换掉。脱敏规则宁可多遮，不可少遮；确有需要保留的字段，用 where 条件或 redaction 的 ignored_keys 显式豁免。
  • 日志一并处理：内容以事件（EVENT_ONLY 模式）落到日志时，内容在 LogRecord 的属性里，所以 log_statements 也要覆盖。

5.2 redaction：白名单与值屏蔽

redaction 处理器适合强合规场景，采用「失败即关闭」的白名单模型：allow_all_keys: false 时只保留 allowed_keys 中列出的属性，其余全部删除；blocked_values 用正则屏蔽命中的值：

一个实测的反例：为了屏蔽鉴权令牌写了 blocked_key_patterns: [".*token.*"]，结果 gen_ai.usage.input_tokens 也命中，整数 100 被替换成字符串 ****，成本看板和 Token 告警全部失效。键模式要用锚定的精确写法（如 ^http\.request\.header\.authorization$），上线前按 5.3 节的方法验证。

另外，summary: debug 会在 Span 上写出被屏蔽的键名，这本身可能泄露信息，生产环境用 info 或 silent。

5.4 语义约定兜底映射

第 3 节的 transform/semconv-compat 只在新属性缺失、旧属性存在时补写新属性，不删除旧属性。这样多语言 SDK 版本不一致时，看板只需查询新属性名；等所有服务完成升级后，再把这段规则连同旧属性一起移除。实测 gen_ai.system="deepseek" 的 Span 和指标经过它之后都带上了 gen_ai.provider.name="deepseek"。只做同义改名，结构性变化（如消息内容格式）必须升级埋点库解决（见 02 篇）。

7.2 按链路逐段定位

数据从 SDK 到后端要经过四段，每一段都有对应的证据，按顺序排查，不要一上来就改配置：

段 看什么 判断
SDK 应用日志中的导出错误；临时加一个控制台 exporter 没有导出错误且控制台有数据，问题在下游
receiver otelcol_receiver_accepted_spans、otelcol_receiver_refused_spans、otelcol_receiver_failed_spans accepted 不增长说明数据没到 Collector；refused 增长说明被下游拒收（memory_limiter 或发送队列已满）
processor otelcol_processor_incoming_items 与 otelcol_processor_outgoing_items 之差 差值就是被过滤或采样掉的量，与预期比例对照
exporter otelcol_exporter_sent_spans、otelcol_exporter_send_failed_spans、otelcol_exporter_queue_size / otelcol_exporter_queue_capacity 发送失败或队列水位持续上升，问题在后端或网络

以上指标名以本系列锁定的版本为准，不同版本可能带 _total 后缀，写 PromQL 时可用 {__name__=~"otelcol_exporter_send_failed_spans.*"} 兼容。建议至少对三项设告警：队列水位超过容量的 70%、发送失败数持续增长、receiver 拒收数持续增长。

7.3 按症状速查

现象 高频原因 处置
SDK 报 connection refused 或 UNAVAILABLE 协议与端口错配（gRPC 发到 4318）；或 receiver 只监听了 localhost 核对 OTEL_EXPORTER_OTLP_PROTOCOL；容器内 endpoint 写 0.0.0.0:4317
OTLP/HTTP 返回 404 按信号的 endpoint 没写 /v1/traces，或通用 endpoint 多写了一遍路径 按 1.3 节的拼接规则修正
Collector 启动即退出，日志含 permission denied file_storage 目录对 UID 10001 不可写 用初始化容器 chown -R 10001:10001 数据卷（见 04 篇）
日志反复出现 Exporting failed. Will retry the request after interval.，队列水位上升 后端不可用或容器网络 DNS 解析失败 检查后端健康与服务名；超过 max_elapsed_time 后该批数据会被丢弃
SDK 收到 503，Collector 日志含 Exporting failed. Rejecting data.，otelcol_exporter_enqueue_failed_spans 增长 发送队列已满，新数据被拒绝 先恢复后端；再评估调大 queue_size 或启用磁盘队列
SDK 收到 503，receiver 拒收数增长，但 exporter 队列并未满 memory_limiter 拒收 查内存大户（尾部采样缓冲、超大 Span），再考虑扩容
Trace 缺一段 中间服务没有透传 traceparent；多副本尾部采样未按 Trace ID 分发；decision_wait 太短 检查网关与 HTTP 客户端埋点（06、07 篇）；按 4.4、4.5 节调整
指标在 Prometheus 查不到 没开 --web.enable-otlp-receiver；或名字被转换后没认出来 点号变下划线，秒单位追加 _seconds，Counter 追加 _total，{token} 这类注释单位被丢弃：gen_ai.client.token.usage 查 gen_ai_client_token_usage_bucket
Collector 内存持续上涨或被 OOM 杀掉 未配 memory_limiter；尾部采样缓冲过大；开启了内容捕获 补处理器、设置 GOMEMLIMIT、下调 num_traces，重新估算内存预算
Token 数变成 **** redaction 的键模式误伤 改为锚定的精确键名，按 5.3 节回归测试
脱敏后仍能在后端看到手机号 应用直连后端绕过了 Collector；或内容落在日志正文而规则只覆盖属性 关闭后端 OTLP 端口的宿主机映射；补 log_statements
Langfuse 收不到数据 用了 gRPC（它只支持 OTLP/HTTP）；鉴权头错误 走 otlphttp exporter，鉴权写法见 08 篇
Grafana 从 Trace 跳日志查不到 OTLP 日志的 trace_id 是 Loki 结构化元数据，不在日志正文中，行过滤 |= 匹配不到 数据源用 | trace_id="..." 的自定义查询（见 04 篇）
