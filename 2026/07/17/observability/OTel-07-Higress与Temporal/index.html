Higress 与 Temporal 链路观测

补齐两类链路断点：Higress AI 网关的 Token、首 Token 时延与 Trace 接入，Temporal 工作流跨 Workflow/Activity 的上下文传播…

Flywhl 11 分钟 发布于 2026.07 #可观测性#Higress#OpenTelemetry

先读结论

  1. ai-statistics 的首 Token 时延是累计值加计数，只能算平均值，要看 P95 得靠客户端直方图。
  2. Higress 的 tracing 服务名必须是 Higress 服务来源里的名字，本地 Docker 场景通常是 xxx.dns。
  3. Temporal Python 的 TracingInterceptor 只在 Client 上注册一次，Worker 会自动继承，重复注册会让每个 Workflow/Activity 出两层 Span。

本篇解决两类「链路断点」：① AI 流量网关（Higress）的 Token、首 Token 时延观测与 Trace 接入；② 异步工作流（Temporal）跨 Workflow/Activity 的上下文传播。两者是企业级 Agent 平台区别于玩具 Demo 的关键观测能力。版本基线：Higress v2.2.x，Temporal Server v1.31，Temporal Python SDK 1.30、Java SDK 1.37。

第一部分：Higress AI 网关观测

1.1 Higress 在观测体系中的定位

Higress（Envoy 内核）作为 AI 流量统一出口，与 SCG 分工：SCG 管业务微服务的南北向流量，Higress 管 LLM/MCP 流量（多模型路由、token 限流、语义缓存）。其观测价值在于模型无关的网关视角：无论后端是 DeepSeek、通义还是本地 Ollama，Token 与延迟都在同一个位置按同一口径度量，可以和应用侧埋点（文档 05）互相对账。

1.2 ai-statistics 插件：三信号各给什么

Higress 通过 ai-proxy + ai-statistics 插件组合（默认按 OpenAI 协议解析）提供：

  • Metric：输入/输出 Token、流式请求首 Token 时延、请求总耗时，可按路由、上游集群、模型、消费者维度聚合，以 Envoy 统计指标形式暴露；
  • Log：访问日志的 ai_log 字段附带 model、input_token、output_token、llm_first_token_duration、llm_service_duration；
  • Trace：Span 上附加 model、input_token、output_token 三个属性。

指标名与语义（以插件文档为准）：

指标 含义 类型
route_upstream_model_consumer_metric_input_token 输入 token 累计 计数
route_upstream_model_consumer_metric_output_token 输出 token 累计 计数
route_upstream_model_consumer_metric_llm_first_token_duration 流式请求首 Token 耗时累计（毫秒） 计数
route_upstream_model_consumer_metric_llm_stream_duration_count 流式请求数 计数

第二部分：Temporal 异步工作流观测

2.1 问题定义

诊断类业务的典型断点：HTTP 请求触发 Temporal Workflow 后立即返回，Workflow 在 Worker 进程中异步执行数分钟。默认情况下 Worker 里的一切与触发请求不在同一条 Trace。目标形态：

2.2 Python SDK：TracingInterceptor 只注册一次

Temporal Python SDK 的 temporalio.contrib.opentelemetry.TracingInterceptor 把 Trace 上下文写入 Temporal Header（键名 _tracer-data），随 Workflow 与 Activity 任务流转。关键规则来自 SDK 源码与官方说明：Worker 会把 Client 上所有实现了 worker.Interceptor 的拦截器自动排在自己的拦截器列表前面，所以拦截器只在 Client 上注册一次。

常见的错误写法是在 Client 与 Worker 上各注册一个 TracingInterceptor，这样 Worker 实际持有两个实例，每个 Workflow 和 Activity 都会产生两层同名 Span（RunActivity:run_agent 下面再套一个 RunActivity:run_agent），Activity 耗时统计也随之翻倍计数。正确写法：

Span 属性：StartWorkflow:* 等客户端 Span 带 temporalWorkflowID；Workflow 侧另带 temporalRunID；RunActivity:* 再加上 temporalActivityID。在 Tempo 中按工作流聚合：{ span.temporalWorkflowID = "diag-s-demo-001" }。

验证是否注册重复很简单：在 Tempo 里打开一条工作流 Trace，看 RunActivity:* 的直接子节点是不是另一个同名 RunActivity:*。

2.3 TracingInterceptor 与新的 OpenTelemetryPlugin

SDK 1.30 的 contrib 目录里同时有两套方案：

维度 TracingInterceptor（本文采用） OpenTelemetryPlugin（实验性）
API 稳定性 稳定 实验性，可能有破坏性变更
Workflow Span 时长 恒为 0（创建即结束） 真实时长
Span 可见时机 创建即上报，可观察进行中的工作流 工作流结束后才出现
Workflow 内自定义 Span 只能用 temporalio.contrib.opentelemetry.workflow.completed_span() 可直接用标准 OTel API
TracerProvider 复用文档 05 的 setup_telemetry() 需改用 SDK 提供的 create_tracer_provider()（重放安全）

长时间运行的诊断工作流更需要「进行中可见」，而且与文档 05 的引导模块兼容，所以这里选 TracingInterceptor。Workflow Span 时长为 0 不影响分析，耗时看 Activity Span 即可。

2.4 四个必须知道的工程约束

  1. Workflow 代码内不要用普通 Tracer 建 Span：Workflow 要求确定性、可重放，重放时普通 Span 会被重复创建。真实 I/O 与 LLM 调用一律放在 Activity 里，这与「LLM 不进入确定性关键路径」的架构原则一致；Workflow 内确需打点，用 completed_span()。
  2. 定时任务与 CLI 触发没有父 Span：TracingInterceptor 默认只在存在客户端 Span 时才创建 Workflow Span。由 Temporal Schedule 或命令行启动的工作流会完全没有 Workflow 侧 Span；需要时构造拦截器传 always_create_workflow_spans=True，代价是重放后可能出现孤儿 Span。
  3. 长工作流与尾采样：Workflow 可能存活数小时，远超尾采样的 decision_wait。接受「一个 Workflow = 多段 Trace」的模式：各段靠 temporalWorkflowID 串联，用上面的 TraceQL 聚合查看；尾采样策略里对带 temporalWorkflowID 的 Span 单独设置保留规则，避免同一工作流的片段被随机丢掉一部分。
  4. 重试的可视化：Activity 重试会产生多个 RunActivity Span，面板里按 status = error 定位首个失败点，而不是只看最终成功的那次。

依赖为 io.temporal:temporal-opentracing 与 io.opentelemetry:opentelemetry-opentracing-shim。另外，Java SDK 1.37.0（2026-07-13）新增了 temporal-opentelemetry 模块，提供挂在 WorkflowServiceStubsOptions 上的 OpenTelemetryPlugin，一次性装好指标桥接、上述 OpenTracing 拦截器与退出时的冲刷；用 setOpenTelemetry(...) 传入应用已有的 OTel 实例，就不会另建导出器。该模块刚发布，新项目可以评估，存量项目维持上面的显式写法即可。

2.6 Temporal 平台自身指标

SDK 指标由 Core 运行时产出。2.2 的写法经 OpenTelemetryConfig 把指标推给 Collector，与业务指标走同一条管道；durations_as_seconds=True 让时长类指标以秒为单位，与 OTel 约定一致。重点关注：

指标（SDK 侧） 说明
temporal_workflow_task_schedule_to_start_latency Workflow 任务从入队到被 Worker 取走的等待时间，持续升高说明 Worker 容量不足
temporal_activity_schedule_to_start_latency Activity 任务的同类指标，LLM 类 Activity 并发打满时首先恶化
temporal_request_failure 与 Temporal Server 的请求失败次数

如果团队已有 Prometheus 抓取体系，也可以换成 PrometheusConfig(bind_address="0.0.0.0:9464") 暴露拉取端点；此时默认时长单位是毫秒、名称不带单位后缀，写告警阈值时要按毫秒计算。

本章验收清单

  • Higress 出口 Span 与应用侧 LLM Span 同 trace_id，且带 gen_ai.usage.*（经 Collector 映射）；
  • Grafana 可见按模型、路由维度的 Token 吞吐与平均首 Token 时延，并与应用侧指标对账；
  • 触发 API 的 Trace 中能看到 StartWorkflow:*，Worker 的 RunWorkflow:* / RunActivity:* 正确挂树，且没有同名 Span 嵌套；
  • Activity 内 LLM 调用的 gen_ai.* Span 出现在工作流 Trace 下；
  • Temporal 调度等待时延指标已接入并配置告警阈值。
