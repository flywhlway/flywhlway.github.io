07 · Higress 与 Temporal 链路观测

本篇解决两类”链路断点”：① AI 流量入口（Higress AI 网关）的 Token/TTFT 观测与 Trace 接入；② 异步工作流（Temporal）跨 Workflow/Activity 的上下文传播。两者是企业级 Agent 平台区别于玩具 Demo 的关键观测能力。

第一部分：Higress AI 网关观测

1.1 Higress 在观测体系中的定位

Higress（Istio/Envoy 内核）作为 AI 流量统一入口，与 SCG 分工：SCG 管业务微服务南北向，Higress 管 LLM/MCP 流量（多模型路由、token 限流、语义缓存）。其观测价值在于模型无关的入口视角：无论后端是 DeepSeek、通义还是本地 Ollama，Token 与延迟在网关处统一度量。

1.2 ai-statistics 插件：开箱即用的三信号

Higress 通过 ai-proxy + ai-statistics 插件组合（默认 OpenAI 协议格式）提供：

  • Metric：输入/输出 Token、首 Token 响应时间（流式 TTFT）、请求总耗时——支持在 网关 / 路由 / 服务 / 模型 四个维度观测，直接暴露为 Prometheus 指标；
  • Log：访问日志附加 input_token、output_token、model、llm_service_duration、llm_first_token_duration 字段；
  • Trace：Token 等信息以 span attribute 写入链路。

2.3 三个必须知道的工程约束

  1. Workflow 代码内不要直接创建普通 Span：Workflow 必须确定性可重放（replay），SDK 在 Workflow 上下文里提供的是”重放安全”的追踪封装；真实 I/O 与 LLM 调用一律放 Activity——这与 示例业务平台「LLM 不入确定性关键路径」的架构原则天然一致；
  2. 长工作流与采样：Workflow 可能存活数小时，链路极长。尾采样 decision_wait 无法覆盖时，接受”一个 Workflow = 多段 Trace + 用 temporal.workflow.id 属性串联”的模式，在 Tempo 用属性查询聚合：{ span.temporalWorkflowID = "diag-xxx" }（属性名以 SDK 实际输出为准，可在 Span 详情确认）；
  3. 重试的可视化：Activity 重试会产生多个 RunActivity Span，务必在面板中按 status=ERROR 过滤首个失败点，而不是只看最终成功的那次。

2.4 Java SDK 提示

Java 侧使用 temporal-opentracing 模块 + OpenTracing→OTel shim（opentelemetry-opentracing-shim）注入 WorkflowClientOptions/WorkerFactoryOptions 拦截器，效果等价；细节以 Temporal Java SDK 当前文档为准（替换点(项目方)：按所用 SDK 版本核对 artifact 坐标）。
