Dify 1.12 私有化部署与排障实录

4C6G 家用服务器上以「内网穿透 → Nginx Proxy Manager → Dify 1.12.1」部署：必改 .env 项、pgvector 兼主库、插件进程代理注入…

Flywhl 19 分钟 更新于 2026.09 #Dify#Docker Compose#私有化部署

先读结论

  1. Cookie 的 secure 标志只看 CONSOLE_WEB_URL 与 CONSOLE_API_URL 是否以 https 开头；Dify 自带 nginx 会用自己看到的协议覆盖 X-Forwarded-Proto（这条链路里是 http），外层反代加这个头没有用。
  2. 1.x 的模型调用从 plugin_daemon 发出，代理必须注入 plugin_daemon；只在 .env 里写 HTTP_PROXY 不会进入任何容器。
  3. pgvector 兼主库时，DB_PASSWORD、PGVECTOR_PASSWORD、PGVECTOR_POSTGRES_PASSWORD 三者必须一致，而且 PGVECTOR_POSTGRES_PASSWORD 只在首次初始化数据目录时生效。
  4. 改 REDIS_PASSWORD 必须同步改 CELERY_BROKER_URL 里内嵌的密码，否则 worker 认证失败。

场景与约束

这份实录对应一台 4 核 6 GB 的家用服务器，部署 Dify 社区版 1.12.1（官方 docker/docker-compose.yaml）。环境有下面这些既定条件：

  • 宿主机的 80/443 已被 Nginx Proxy Manager（下文简称 NPM）占用，后面还要挂别的子域服务；
  • 服务器没有公网 IP，公网入口由内网穿透隧道提供，HTTPS 在隧道侧终止，隧道以 HTTP 转发给 NPM；
  • 以后多个子域要共享登录态；
  • 外部多模态模型需要回拉用户上传的文件；
  • 模型 API 必须经宿主机上的 HTTP 代理出网。

文中对外域名写作 dify.example.com，根域 example.com；宿主机局域网地址写作 <宿主机IP>，代理端口写作 <代理端口>。所有 *_ChangeMe_* 形式的值都是占位符，上线前必须替换。

部署里真正需要分清的是三条互不相干的流量，每条由不同的配置负责：

流量 路径 由谁决定 本文做法
入站 隧道 → NPM → Dify nginx → web/api *_URL 系列变量、NPM Proxy Host、EXPOSE_NGINX_PORT Dify nginx 映射到宿主机 18080，NPM 反代过去
模型调用出站 plugin_daemon 内的模型插件进程 → 模型 API plugin_daemon 容器的 HTTP_PROXY/HTTPS_PROXY/NO_PROXY 用 override 文件注入，插件子进程会继承
工作流出站 HTTP 请求节点、工具、代码沙箱 → 外网 SSRF_PROXY_*、SANDBOX_HTTP(S)_PROXY 指向 ssrf_proxy（squid） 保持默认；需要翻墙时给 squid 配上游

第二条是 1.x 与 0.x 最大的差别：模型供应商以插件形式运行在 plugin_daemon 里，控制台里的「凭据校验」和工作流里的 LLM 调用都从 plugin_daemon 发出。plugin_daemon 0.5.3 启动插件子进程时先继承自身环境，再追加它读到的 HTTP_PROXY、HTTPS_PROXY、NO_PROXY，所以代理只要打进 plugin_daemon 就能覆盖所有模型插件。

第三条要单独说：sandbox 只挂在 ssrf_proxy_network 上，这个网络在 compose 里声明为 internal: true，不能直接出网。把 SANDBOX_HTTP_PROXY 改成宿主机代理地址，sandbox 根本连不到；正确做法是保持它指向 ssrf_proxy，再让 squid 转发给上游代理（见后文可选配置）。

关键决策

决策点 选择 理由 代价
入口 NPM → <宿主机IP>:18080 只改 .env，不动官方 compose；NPM 以后给其他子域复用 多一跳宿主机端口，需防火墙不对外放行 18080
入口（备选） NPM 容器执行 docker network connect docker_default <NPM容器名>，转发到 nginx:80 不占宿主机端口 NPM 容器重建后要重新 connect；网络名随 compose 项目名变化
主库与向量库 同一个 pgvector 容器 4C6G 上少跑一个 PostgreSQL 与一个 Weaviate，备份只管一个数据目录 向量规模到百万级以上、检索并发很高时再迁 Qdrant/Milvus
插件库 保持默认 DB_PLUGIN_DATABASE=dify_plugin plugin_daemon 连库失败时会自己 CREATE DATABASE，无需手工建库，也不必与主库合并 无
代理注入 新增 docker-compose.override.yaml 官方 compose 头部声明为生成文件、不应手改；override 升级时不冲突 多维护一个文件
默认 profile COMPOSE_PROFILES=pgvector 官方默认值是 ${VECTOR_STORE},${DB_TYPE}，会连 db_postgres 一起拉起；api 对 db_postgres 的依赖标了 required: false，不启动它也不影响 api 创建 api 不等待 pgvector 健康，首次启动可能重启一两次

向量库只在两种情况下值得离开 pgvector：单库向量过百万且需要复杂过滤，或者要多副本高可用。Weaviate 与 Milvus（后者会拉起 etcd + minio + milvus 三个容器）在 6 GB 内存上都偏重，Chroma 更适合本地原型。

.env 改动清单（唯一一份）

从 docker/.env.example 复制出 .env，只改下面这些项，其余保持默认：

生成口令时，SECRET_KEY 用 openssl rand -base64 42，其余进连接串的口令用 openssl rand -hex 24：base64 输出里的 /、+、= 会破坏 redis:// 与数据库连接串的解析。

几个容易写错的点：

  • NEXT_PUBLIC_COOKIE_DOMAIN 在 .env.example 里的注释就是「跨子域时设为 1」，填成域名字符串是常见误写；
  • COOKIE_DOMAIN 留空且 URL 为 https 时，后端会给 Cookie 加 __Host- 前缀（__Host- Cookie 不能跨子域共享），在浏览器开发者工具里能直接看到；
  • 出网代理变量故意叫 EGRESS_*：Compose 做变量替换时 shell 环境变量优先于 .env，运维终端里若恰好有 HTTP_PROXY=http://127.0.0.1:...，会被悄悄注入容器；
  • RESPECT_XFORWARD_HEADERS_ENABLED 保持默认 false。它只是给 Flask 套上 ProxyFix，而 Dify 自带 nginx 的 proxy.conf.template 固定写了 X-Forwarded-Proto $scheme，在这条链路里传给 api 的永远是 http，打开它得不到 https。

出网代理：override 文件

在 docker-compose.yaml 同目录新建 docker-compose.override.yaml，Compose 会自动合并它：

宿主机侧还要满足两点：代理监听在 0.0.0.0（或 docker 网桥地址）而不是 127.0.0.1，并开启允许局域网连接；宿主机防火墙放行来自 docker 网段到 <代理端口> 的连接。容器里的 127.0.0.1 是容器自己，这一点是最常见的失败原因。

NO_PROXY 里必须有 api：plugin_daemon 通过 http://api:5001 回调 Dify，Go 的 HTTP 客户端遵循 NO_PROXY，漏写就会把内部回调送进代理。Postgres 与 Redis 走的是各自的 TCP 协议，不读这些变量，列上无害。网段写法（CIDR）并非所有 HTTP 客户端都支持，服务名逐个列出最稳。

可选：让 HTTP 请求节点与代码沙箱也走代理

1.12.1 的 squid 模板在 http_access deny all 之前留了 include /etc/squid/conf.d/*.conf，模板里也注释了 cache_peer 上游代理的写法。用挂载的方式追加一个配置文件，就不用改官方模板：

SSRF_PROXY_* 与 SANDBOX_HTTP(S)_PROXY 保持指向 http://ssrf_proxy:3128。直接把它们改成宿主机代理，等于绕过了 Dify 的 SSRF 防护，而且 sandbox 所在的内部网络也连不到宿主机。

每个叶子对应的定位命令与修复如下：

叶子 定位命令 根因 修复

A5 curl -sIk https://dify.example.com/ | grep -iE '^(http|server|location)' 流量没到 NPM，或隧道把 Host 改成了隧道自己的域名 在隧道侧开启保留 Host 头；实在不支持时临时把隧道域名也加进 NPM 的 Domain Names
A6 同上，分别测 http:// 与 https:// 只开了 https 隧道 隧道侧配置 http→https 跳转
B3 curl -sI http://127.0.0.1:18080/ Dify nginx 没起，或宿主机防火墙拦了 NPM 容器到 18080 docker compose ps nginx；放行 docker 网段到 18080
B5 docker compose logs --tail=120 api 常见是 password authentication failed，见 E2 按 E2 修复后 docker compose up -d
B6 docker compose logs --tail=80 nginx | grep upstream Dify nginx 在启动时解析 api 的地址；--force-recreate api 后 api 换了容器 IP，nginx 仍指向旧地址 docker compose restart nginx；以后重建 api 就顺手重启 nginx
C3 浏览器开发者工具看 Cookie 是否带 Secure、名字是否带 __Host- is_secure() 只看两个 CONSOLE URL 是否以 https 开头，http 访问时浏览器不保存 secure Cookie 局域网也用 https 域名访问；确需内网直连就另起一套 http 的 URL 配置，不要混用
C4 对比地址栏域名与 .env 里所有 *_URL 某个 URL 少了一个点、或子域不同，Cookie 域与请求域对不上 统一所有 URL，改完 docker compose up -d
D2 上文验收第 5 步 代理只写进 .env，没有进容器；或 NO_PROXY 漏了 api 补 override，docker compose up -d
E2 docker compose logs --tail=80 worker、docker compose logs --tail=80 api worker 报 Redis 认证失败：CELERY_BROKER_URL 仍是旧密码；api 报 Postgres 认证失败：pgvector 数据目录首次初始化时用的是旧口令，之后改 PGVECTOR_POSTGRES_PASSWORD 不再生效 同步连接串；或进容器改口令：docker compose exec pgvector psql -U postgres -c "ALTER USER postgres WITH PASSWORD 'Db_ChangeMe_hex32';"

插件处理文件失败（文档解析类插件报取文件超时）另查两项：FILES_URL 是否从公网可达，INTERNAL_FILES_URL 是否为 http://api:5001。官方注释写明 FILES_URL 是文件处理插件的必填项。

调参顺序：先改工作流结构（分页、分段、外置存储），实在不够再把对应变量调到「刚好够用」。把 MAX_VARIABLE_SIZE 调大十倍，代价是数据库里的运行记录、日志与 Redis 事件都跟着膨胀，4C6G 机器最先被拖垮的是 Postgres。

长文本外置：MinIO + 存储网关

变量体积上限（约 200 KB）与 HTTP 响应上限（1 MB）决定了：长报告、大批量结果不能在工作流变量里流转。做法是变量里只放引用与摘要，正文落对象存储。

MinIO 侧只做一次准备，给网关一个仅限单个 bucket 的账号：

对象存储的 AK/SK 不进工作流，只进一个很薄的存储网关（FastAPI + boto3 即可）。网关对 Dify 暴露三个接口，Dify 侧用 HTTP 请求节点调用，网关的访问令牌放在工作流的 secret 类型环境变量里：

接口 入参 出参 说明
POST /v1/blob/put-text key、text、content_type object_key、size 每段一个对象；S3 语义没有追加写
POST /v1/blob/compose prefix、part_count、dest_key object_key、url 网关内按序拼接后写回一个对象，返回预签名下载链接
GET /v1/blob/presign key、expires url 按需重新签发下载链接

长报告的编排顺序：分段生成 → 每段上传 → 循环结束后合并 → 输出链接与摘要。不要先生成整篇再上传，整篇文本在变量里就可能先撞上限。

  1. 循环节点：循环变量 part（number，初值 1）、done（boolean，初值 false）、summary（string，初值空），退出条件 done 为 true；
  2. 循环内 LLM 节点：以主题、段号与累积摘要为输入，要求只输出 JSON：chunk_markdown、chunk_summary、is_last，用 max_tokens 控制每段长度；
  3. HTTP 请求节点：调 put-text，key 用 reports/{{#sys.workflow_run_id#}}/part-{{段号}}.md；
  4. 变量赋值节点：summary 追加本段摘要，part 加 1；条件分支判断 is_last，为真时把 done 置 true；
  5. 循环外 HTTP 请求节点调 compose，结束节点输出摘要与下载链接。

批量处理同理：外层循环按游标分页，内层迭代处理一页，页大小 20–50，迭代并行度 3–5；每条结果在迭代内部直接写入网关，迭代的输出只返回一个短状态字符串，避免聚合出大数组。这些节点在 DSL 里的具体写法见《Dify DSL 工作流设计与校验》。

HTTP 请求节点的流量走 ssrf_proxy。网关若只在内网可达，最省事的是把网关容器加入 Dify 的默认网络，用服务名访问；调用失败时先看 docker compose logs ssrf_proxy 里是否有 TCP_DENIED。

Dify 前台联调：迁移成功、运行时连接池超时

给 Dify 配一个 C 端前台时（例如 DifyChat 这类「前端 + Node 平台层 + MySQL」的项目），遇到过一个很迷惑的故障：平台层容器启动时数据库迁移执行成功，随后初始化管理员时报：

active=0 idle=0 说明连接池一个连接都没建起来，不是池被占满。迁移能过，说明地址和口令大概率没错，差别在「谁去连」：迁移由 ORM 的迁移引擎执行，运行时走 Node 驱动的连接池，两者在认证插件协商、连接时机上都不同。当时的环境里平台层用宿主机 IP 连另一个 compose 里的 MySQL，多了一层 NAT 与防火墙，MySQL 刚启动时还在抖动期。

硬约束清单

  • 所有 *_URL 显式写 https 对外地址，与浏览器地址栏完全一致；TRIGGER_URL 与 ENDPOINT_URL_TEMPLATE 不能留 localhost
  • 跨子域登录：COOKIE_DOMAIN=根域，NEXT_PUBLIC_COOKIE_DOMAIN=1
  • 不依赖 X-Forwarded-Proto 判断 https；RESPECT_XFORWARD_HEADERS_ENABLED 在本链路保持 false
  • NPM 不勾 Force SSL；http→https 在隧道侧做
  • DB_PASSWORD = PGVECTOR_PASSWORD = PGVECTOR_POSTGRES_PASSWORD，且在首次 up 之前定好
  • REDIS_PASSWORD 与 CELERY_BROKER_URL 同步；SANDBOX_API_KEY 与 CODE_EXECUTION_API_KEY 相同
  • 进连接串的口令只用字母数字
  • 代理只通过 override 注入 plugin_daemon、api、worker、worker_beat，NO_PROXY 含 api
  • SSRF_PROXY_*、SANDBOX_HTTP(S)_PROXY 保持指向 ssrf_proxy
  • 改 .env 后用 docker compose up -d；重建 api 后重启 nginx
  • 宿主机防火墙不对外放行 18080、18443、5003
  • 长文本、大数组走外置存储，变量里只放引用与摘要

2026-09 补记：升级到 1.13–1.17.1 时部署侧的变化

本文正文以 1.12.1 为准。截至 2026-09 的最新版本是 1.17.1，升级时与本文配置相关的变化有：

  • .env 结构重排（1.15.0 起）：docker/.env.example 只保留启动必需的变量（1.17.1 约 300 行），可选与各供应商变量拆到 docker/envs/ 下的 *.env.example，复制去掉 .example 后缀即可启用，docker/.env 的值优先。本文的运行时限制类变量、pgvector 连接变量都不在新的主文件里。升级时不要用旧 .env 整体覆盖，按新结构逐项迁移本文的改动。
  • SECRET_KEY 可留空（1.17.1 已确认）：留空时自动生成并持久化到存储目录。
  • 新增服务：1.14 起支持多人协同编辑，1.17.1 中对应 api_websocket 服务，挂在 collaboration profile 下，默认 COMPOSE_PROFILES 追加了 collaboration，前端通过 NEXT_PUBLIC_SOCKET_URL（默认 ws://localhost）连接。经 NPM 反代时要打开 Websockets Support，并把该变量改为对外的 wss:// 地址。1.16 引入 Dify Agent（Beta），1.17.1 的 compose 里 agent_backend、local_sandbox、agent_ssrf_proxy 没有 profile 门控，默认随 up 启动，6 GB 内存的机器升级前要先评估余量。
  • 内网访问开关：1.17.1 新增 SSRF_PROXY_ALLOW_PRIVATE_IPS，填 CIDR 列表即可放行 HTTP 请求节点、工具、插件访问内网地址，存储网关在内网时不必再改 squid。
  • 1.17.1 的 nginx proxy.conf.template 仍把 X-Forwarded-Proto 写成 $scheme，本文关于 https 判定的结论不变。
