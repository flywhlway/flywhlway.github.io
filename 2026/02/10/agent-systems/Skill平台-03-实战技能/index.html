先读结论

  1. 分工写在 SKILL.md 第一段：脚本给证据，模型给结论；报告脚本反向校验结论引用的证据是否属于本簇。
  2. 每个脚本先定输出契约：stdout 只打摘要与路径，stderr 首行报数据质量，退出码 0/1/2 各有明确的下一步。
  3. 相邻技能互相让渡：升级期间的伴生码归 OTA 技能，升级结束后仍 testFailed 的码移交 DTC 技能；依赖只单向声明，防止成环。
  4. 脚本内嵌的码表、拓扑必须与 reference 做 CI 双源同步检查，未映射码只提示维护者回填，运行时不自改规则。

03 · 两个实战技能：OTA 日志诊断与 DTC 根因分析

企业级 Skill Registry 平台工程手册 · 第 03 篇：把 01 篇的三级披露与 02 篇的 description 四段结构落成两个可投产的技能，04–11 篇引用的技能范例均出自本篇。
前置阅读：01 篇 §3（Discovery / Activation / Execution）、02 篇 §3（四段结构）与 §6.3 第 15、16 例。
本篇回答：一个诊断类技能从目录树到脚本退出码应当是什么样；两个业务相邻的技能如何切边界、如何互相移交。

0. 设计总纲：脚本给证据，你给结论

两个技能共用一条分工，写在各自 SKILL.md 的第一段——模型对开头的遵循度最高：

工作 由谁做 理由
解析、计数、排序、码表查找、时间窗关联、聚类统计 脚本 确定性、可回归、结果体量可控
根因裁决、推翻脚本给出的候选、置信度、个体或批次的最终表述、下一步取证 模型 需要结合对话上下文与领域常识
码表、拓扑等领域真值的增补 维护者发版 运行时不得自改规则（07 篇 §8）

这条分界带来三个可验证的性质：模型从不逐行读原始日志，上下文里只有脚本产出的结构化证据；每条结论都能回溯到一个证据编号；数据质量（解析率、丢弃率）由脚本量化，而不是由模型”感觉”。

三个脚本管道共同遵守的契约（07 篇 §5.3 执行协议的技能侧实现）：

契约项 约定 模型据此做什么
stdout 只打一行摘要 + 产物路径；大结果写 /workspace/*.json 需要细节时用 view 读产物的局部
stderr 首行 数据质量行，如 parse_rate=0.957 total=23 ... 按 SKILL.md 阈值表决定继续、降级或停止
stderr 后续行 带固定前缀的可决策信息：UNPARSED / UNMAPPED / DROPPED / VERDICT_INVALID / UNKNOWN_PLATFORM 进入 SKILL.md「错误处理」对应条目
退出码 0 成功；1 业务失败（证据不足、格式不识别、裁决不合法）；2 用法错误 1 走 fallback，2 按 --help 改参数重试一次
写文件 临时文件 + os.replace 原子替换 重跑安全，中断不留半个 JSON
输出体量 列表字段截断：每车证据前 5 条、未解析行前 20 条、msg 截断 200 字符 上下文成本有上界
依赖 只用 Python 标准库，无网络 满足 offline-analysis 沙箱档（07 篇 §5.1）

两个技能的一览：

技能一 ota-log-diagnosis 技能二 dtc-root-cause
skill_ref vehicle.diag:ota-log-diagnosis@2.3.1 vehicle.diag:dtc-root-cause@1.5.2
输入 OTA 全链路日志（云端调度、车端 UA、ECU 刷写） 远程诊断导出（DTC + 状态字节 + 冻结帧）
脚本管道 parse_logs → classify_failure → generate_summary normalize_dtc → correlate_dtc
模型的核心裁决 失败在哪环 / 为什么 / 个体还是批次 首发码 / 伴生原因 / 根因类别 / 个体还是批次
移交出去 升级结束后仍 testFailed 的码 → B 升级或刷写场景 → A
运行位置 云侧，沙箱档 offline-analysis 同左

A. 技能一：ota-log-diagnosis

A.1 边界与阶段模型

本技能只做一件事：排查已经发生的升级失败。规划升级（分批、灰度）归 ota-campaign-planning，车机应用崩溃归 ivi-crash-analysis，与升级无关的故障码归 dtc-root-cause。

排查的骨架是九阶段模型，日志中每一行都落在某个阶段上；furthest_stage（到达的最远阶段）与 failure_stage（首个错误所在阶段）的组合，就是”失败在哪环”的机器化表达：

序 阶段 主要日志源 典型失败
1 DISPATCH CLOUD 圈车范围外、证书失效
2 RECEIVE UA 车辆离线、任务回执丢失
3 PRECHECK UA 电量低、非 P 挡
4 DOWNLOAD UA 下载源 5xx、链路超时、分区空间不足
5 VERIFY UA 哈希不符、签名失败、差分基线不符
6 CONFIRM UA 用户拒绝或预约过期
7 INSTALL UA / ECU UDS 否定响应、刷写超时
8 ACTIVATE UA / ECU 新分区启动失败、回滚
9 REPORT UA / CLOUD 结果回执丢失

A.3 SKILL.md 全文

逐节对照 02 篇与 08 篇的要求：

  • description 与 02 篇 §3 模板逐字一致：①能力陈述 → ②触发场景（OTA 失败、卡滞、刷写中断、差分包校验失败、回滚、文件名关键词）→ ③泛化子句（”车辆升级出问题了”且无日志）→ ④负面边界（两个相邻技能各自点名）。
  • 第一段是分工声明与数据纪律；第二段是断点续做条件，放在开头是因为它决定从哪一步开始。
  • 第 1 步把”数据质量如何影响结论”写成数值阈值表，模型执行”低于 0.60 时”远比”解析质量差时”稳定。
  • 第 3 步是路由表：每行一个触发情况对一份资料的一个位置，不出现”详见 references/“。
  • 第 4 步把”给出专业结论”拆成三个必须回答的问题，并规定结论的数据格式——下一步的脚本要校验它。
  • 错误处理覆盖三个脚本的全部非零退出；边界写明默认归属、移交信号、移交话术。

A.4 parse_logs.py：流式解析与解析率报告

输入契约：文件或目录（递归 *.log / *.txt / *.gz），任意编码错误以替换字符计数而不中断。输出契约：

四个设计点：

  1. 内存 O(VIN 数)：逐行读取，每台车只保留状态（最远阶段、首个错误、最多 5 条证据、按码去重的 DTC）。100 万行日志与 1 万行日志的内存差别只在车辆数。
  2. 解析率先于一切：stderr 首行永远是 parse_rate=... malformed=... encoding_replaced=...，这是 SKILL.md 第 1 步阈值表的输入。低于 0.60 时 exit 1 并附最多 3 条未识别的错误行，让模型能向用户说清”是什么格式没认出来”。
  3. 字段白名单 + 截断：只保留 16 个已知键，msg 截断 200 字符。未知键不进产物，既控制上下文体量，也把原始日志中的任意文本挡在模型视野之外。
  4. input_digest 在读取时顺带计算：单遍完成，供断点续做判断”产物是否对应本次输入”。

A.5 classify_failure.py：码表归类与批次聚类

几个取舍：

  • 类别由首个 ERROR 决定，不是最后一个。刷写失败后的回滚、回执等后续错误是结果而非原因。
  • 没有错误码时区分两种情况：无终态事件记 STALLED（日志中断或真实卡滞，需要补日志），有失败终态却无错误码记 NO_ERROR_EVIDENCE（日志级别配置过高，错误行被过滤）。两者的下一步取证完全不同，因此不合并。
  • 批次信号的小样本保护：样本不足 10 台时占比无意义（3 台车里 1 台失败就是 33%），此时只看簇大小是否 ≥ 3。
  • 伴生码与遗留码的切分：升级终态之前出现的码进 dtcs_during_upgrade，由本技能解释；终态之后仍 testFailed（状态字节 bit0）的码进 post_upgrade_dtcs，成为移交 B 的机器信号。
  • 未映射码只报告，不定义：stderr 的 UNMAPPED 行明确要求模型提示维护者回填，规则的增补走发版（07 篇 §8）。

A.6 generate_summary.py：证据与裁决的合流校验

模型在第 4 步写 verdict.json，本脚本负责两件事：把证据与裁决合成报告；在合成前校验裁决是否守规矩。

校验项与它们守护的 SKILL.md 规则：

校验 守护的规则 失败时 stderr
每个簇都有裁决 第 4 步”对每个 cluster 回答” C2: 缺少裁决
evidence_id 属于本簇车辆 “至少引用一个本簇的 evidence_id” C1: 证据 ['E3'] 不属于本簇车辆
解析率 < 0.90 时不得 high 第 1 步阈值表 解析率 0.82 < 0.90, confidence 最高 medium
未映射码簇只能 low 错误处理第 3 条 未映射码簇 confidence 只能为 low
batch 结论须有批次信号 第 4 步第 3 问 batch_signal=false, 批次结论须先补充同因子车辆证据

这是”脚本给证据，你给结论”的闭环：结论由模型写，但结论与证据的引用关系由脚本核验。模型编造证据编号、把单车问题夸大成批次、在解析质量差时给出高置信度，这三类最常见的输出缺陷在交付前被拦截，而不是等用户发现。

B. 技能二：dtc-root-cause

B.1 边界与方法

输入是远程诊断平台的故障码导出：每行一个码，带 ECU、状态字节、首次出现时间与冻结帧。多码同现是常态——一次供电跌落可以让半车 ECU 报通信丢失。技能的方法论三条：

  1. 先定首发，再解释伴生。按首次出现时间排序，在时间窗内链式聚成 episode，最早的码是首发候选。
  2. 用拓扑解释伴生关系。失联码（U0100 与 ECM、U0140 与 BCM、U0146 与网关、U0155 与仪表，SAE J2012 标准码）指向的节点、所在总线、网关上下游，决定一个伴生码”为什么会出现”。
  3. 冻结帧做定位证据。电压低于 9V 指向供电，诊断会话为 0x02（编程会话）指向刷写过程，车速非零说明发生在行驶中。

一个关键的反直觉点：根因节点可能根本没有自己的码。网关失效时，所有节点都报”与网关失联”，网关自身不上报——脚本用 common_lost_target（≥2 个失联码指向同一节点）把这个信号显式化。

B.2 目录结构

B 没有报告脚本，这是刻意的：结论是一张每车一行的表，模型直接写的成本低于再维护一个脚本；A 需要报告脚本，是因为逐车明细可达数百行，且裁决需要机器校验。脚本化的判据是”确定性 + 体量”，不是”每个技能都要三段管道”。

B.3 SKILL.md 全文

description 与 02 篇 §6.3 第 16 例逐字一致。第④段把交叉场景写死：OTA 升级失败即使伴随 DTC 也归 A——这是两技能最常见的双触发点，边界必须在 L1 层就可判定，不能等激活后再判断。

B.4 normalize_dtc.py

输出契约（每个事件）：

  • 列名别名表是这个脚本唯一需要随接入方增长的部分；新导出来源只加别名，不改逻辑。缺必需列时 exit 1 并打印实际列名，模型可以直接把列名展示给用户确认。
  • 码格式校验：[PBCU][0-3][0-9A-F]{3}，可带 -XX 失效类型字节（FTB）。形如 P05G2 的录入错误被计入 DROPPED bad_code，不进入关联。
  • 状态字节解码成 ISO 14229-1 的 8 个标志位名称，模型不需要记忆 bit 位。

B.5 correlate_dtc.py

relation 的判定顺序即优先级：供电关系 → 失联指向首发节点 → 失联指向共同目标 → 同总线 → 网关下游 → 无关。unrelated 不是错误，而是交给模型的信号——这个码很可能是同一时间窗里的另一个独立故障。

B.7 manifest.json 与依赖方向

与 A 的 manifest 对比，差别在依赖：A 声明 requires B，B 不声明 requires A。两技能互相让渡，但依赖图必须是有向无环图（04 篇 §5.2 环检测）；若双向声明，注册 lint 直接阻断。B → A 的移交靠同族订阅保证 A 可见；租户只订阅了 B 时，SKILL.md 边界节的第三条给出了 A 不可用时的降级话术。

B.9 失败模式与降级

移交的三个要素在两份 SKILL.md 中都写全：识别信号（机器字段优先，对话线索其次）、移交对象（技能名）、话术（让用户感知到的是连续服务而不是拒绝）。只写”不处理 X”而不写移交话术，模型在边界处只能生硬拒绝。
