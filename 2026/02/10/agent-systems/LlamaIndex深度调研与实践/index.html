LlamaIndex 2026：从 RAG 框架到文档 Agent 平台

梳理 LlamaIndex 从 RAG 框架到 Workflows 与文档 Agent 平台的演变…

Flywhl 21 分钟 更新于 2026.09 #Agent#RAG#LlamaIndex

先读结论

  1. LlamaIndex 现在是三层：开源 RAG 框架（core 0.14.x）、独立的 Workflows 运行时、LlamaCloud 托管的文档解析与抽取服务。
  2. 检索质量与文档处理选 LlamaIndex，复杂有状态编排选 LangGraph；两者可以通过把检索器包装成工具来组合。
  3. 生产中必须同时锁定 llama-index-core、llama-index-workflows 和各集成包版本，元包 llama-index 不会替你锁住 core。
  4. 增量摄取依赖稳定的 doc_id；默认 doc_id 每次随机，重复运行会把所有文档重新切分和向量化。

定位演变：从“连接私有数据”到“文档 Agent”

LlamaIndex 最早的标签是“把私有数据接到大模型上的数据框架”，核心能力是读取、切分、索引、检索。三年下来，它的重心移动了两次：先是从“查询引擎”走向事件驱动的 Workflows，再是公司层面把投入集中到文档解析与抽取这类“文档 Agent”能力上。

时间 事件 对使用者的影响
2023-02 PyPI 上的 llama-index 包首发（项目由 GPT Index 更名） 名字与 import 路径定型
2024-02 0.10 拆出 llama-index-core，各模型、向量库集成成为独立包 from llama_index.core import ... 与按需安装集成包成为标准写法
2024-08 core 0.10.59 首次加入事件驱动的 Workflows 可以表达循环、分支、并行的检索与 Agent 流程
2025-06 Workflows 独立为 llama-index-workflows，1.0 于 2025-06-25 发布 编排运行时可脱离 RAG 部分单独使用
2025-08-29 Workflows 2.0 当前 Agent 实现（FunctionAgent 等）都跑在它上面
2025-09-08 llama-index 0.14.0 本文写作时仍在 0.14.x（2026-02-10 发布 0.14.14）
2025-11-18 LlamaAgents 开放预览，命令行工具 llamactl 以模板方式创建并部署文档 Agent 到 LlamaCloud
2026-01-21/22 新 SDK llama-cloud 1.0 与 LlamaParse API v2 替代原来的 llama-cloud-services 客户端

需要区分的一点：2024 年那个把 Agent 部署成微服务的 llama-agents 项目已经停止更新，和 2025 年底的 LlamaAgents 不是同一个产品。

所以今天谈 LlamaIndex，实际上是三件事：

  • 开源框架：llama-index-core + 数百个集成包，负责 RAG 的全链路。
  • Workflows：事件驱动的异步编排运行时，Agent、多 Agent 和 LlamaAgents 模板都构建在它之上。
  • LlamaCloud：托管的 LlamaParse（解析）、LlamaExtract（结构化抽取），以及 SDK 里以 beta 形式出现的 split、sheets 等能力。

抽象 作用 常用类 容易踩的坑
Document 一份源文件及其元数据 Document、SimpleDirectoryReader 默认 doc_id 随机，增量更新失效
Node 切分后的片段，带前后关系与元数据 TextNode、SentenceSplitter 元数据会参与 embedding 与提示，过长会挤占 chunk
Index 组织 Node 的数据结构 VectorStoreIndex、SummaryIndex 本地 JSON 持久化会整体加载进内存
Retriever 按查询取回 Node index.as_retriever(similarity_top_k=...) top_k 过大时噪声直接进入生成
Postprocessor 过滤、重排、时间衰减 SimilarityPostprocessor、各类 reranker 相似度阈值随 embedding 模型变化，不能照抄
ResponseSynthesizer 把 Node 组织成提示并生成回答 get_response_synthesizer(response_mode=...) refine 模式调用次数等于片段数
QueryEngine / ChatEngine 检索 + 后处理 + 合成的固定流水线 index.as_query_engine() 表达不了“检索不够就改写重试”这类回环
Workflow 事件驱动的步骤编排 Workflow、@step、Event、Context 默认超时 45 秒
Agent 基于 Workflow 的工具调用循环 FunctionAgent、ReActAgent、AgentWorkflow FunctionAgent 要求模型支持 function calling

ResponseSynthesizer 的三种常用模式：compact（默认，尽量把片段塞进一次调用，放不下再 refine）、refine（逐片段迭代改写答案，准确但慢）、tree_summarize（分组总结再汇总，适合“概括全部资料”类问题）。

几个值得注意的行为：

  • persist 会在目录下写出 docstore.json、index_store.json、default__vector_store.json、graph_store.json、image__vector_store.json 五个文件，加载时全部读入内存。几千个片段以内没问题，更大规模应换外部向量库。
  • 持久化的只有向量，不记录生成向量用的模型。换了 Settings.embed_model 再加载旧索引，不会报错，只会检索得一塌糊涂。建议把模型名写进目录名或单独的元数据文件，加载时比对。
  • response.source_nodes 是做引用和排查的第一手材料，上线时应该连同分数一起记录。

QueryEngine 是一条固定流水线。一旦需要“检索结果不合格就改写查询重试，最多两次，还不行就拒答”这样的逻辑，就该用 Workflow。下面是借鉴 Corrective RAG 思路的简化实现：

  • 步骤之间靠事件类型连接。retrieve 的返回注解是 AnswerEvent | RetrieveEvent，返回后者就形成回环。run() 开始时会校验事件图：某个事件有步骤产出却没有步骤消费，会直接抛 WorkflowValidationError，而不是运行到一半静默卡住（构造实例时不会报）。
  • timeout 默认 45 秒。调用 LlamaParse 或长链 Agent 的 Workflow 很容易超时，要显式设置，或设为 None 并在外层控制。
  • workflow.run() 必须在事件循环内调用。asyncio.run(workflow.run(...)) 会抛 RuntimeError: no running event loop，要像上面一样包一层 async def。
  • ctx.write_event_to_stream 发出的自定义事件，是给前端推进度、做审计日志的标准出口。
  • llama_index.core.workflow 只是对独立包 workflows 的重新导出，两者的 Workflow 是同一个类；新代码也可以直接 from workflows import Workflow, step, Context。

Agent：FunctionAgent 与多 Agent 交接

单 Agent

用一个按调用次数返回预设工具调用的 Mock 模型验证了事件流，输出为 [tool] firmware_diff({'base': '2.3.1', 'target': '2.4.0'}) -> 可差分升级 和 [tool] ops_docs({'input': '差分失败先查什么'}) -> …。由此可以确认两个细节：普通函数的 docstring 就是工具描述；QueryEngineTool 的参数名是 input。

边界条件：

  • 把不支持 function calling 的模型（包括 MockLLM）交给 FunctionAgent，构造时不报错，运行时才抛 ValueError: LLM must be a FunctionCallingLLM。这类模型改用 ReActAgent。
  • 多轮记忆在 Context 里。不显式传入时，默认是 ChatMemoryBuffer，上限取模型上下文窗口的 75%；对 gpt-4.1-mini 这类百万 token 窗口的模型，等于不设上限，每轮成本会随对话线性增长。应显式传入 agent.run(q, ctx=ctx, memory=Memory.from_defaults(session_id=..., token_limit=8000))（from llama_index.core.memory import Memory）。
  • 服务端要跨请求保存会话时，用 ctx.to_dict(serializer=JsonSerializer()) 序列化存库，下次用 Context.from_dict(agent, data, serializer=JsonSerializer()) 恢复，实测恢复后历史消息完整、可以继续对话。

多 Agent 交接

AgentWorkflow 用“交接”（handoff）组织多个 Agent：每个 Agent 声明可以把对话交给谁，由当前 Agent 的模型决定何时交接。

交接完全由模型决定，是一种“软路由”。如果分派规则是确定的（例如按设备类型、按租户），用普通 Workflow 的分支步骤实现更可控、更便宜。

与 LangChain / LangGraph 的分工

需求 优先选择 理由
复杂 PDF、表格、扫描件的解析与切分 LlamaIndex + LlamaParse 解析、切分、元数据、节点关系是它的主场
检索质量调优（切分、混合检索、重排、评估） LlamaIndex 抽象粒度细，内置检索评估
长时运行、需要人工审批中断与恢复的 Agent LangGraph checkpoint、中断恢复、时间旅行是一等能力
多轮对话的上下文注入与记忆分层 LangChain 1.x create_agent + middleware 每次模型调用前后都有钩子
简单的工具调用 Agent 两者皆可 FunctionAgent 与 create_agent 能力相当，按团队熟悉度选
从文档中抽取固定结构的数据 LlamaExtract 或自建抽取 Workflow 托管服务省去 schema 迭代以外的工程量

常见的组合方式是“LlamaIndex 负责找得准，LangGraph 负责编排”：把 LlamaIndex 的检索器包装成 LangChain 工具。

这里只包装检索器、不包装 QueryEngine，是为了避免两层 LLM 调用：外层 Agent 已经会根据片段生成回答，再让 QueryEngine 先合成一遍，只会增加延迟、成本和二次改写带来的失真。

文档 Agent 与 LlamaAgents

生产注意事项

版本与依赖

  • 元包不锁 core。llama-index==0.14.14 声明的依赖是 llama-index-core>=0.14.14,<0.15.0，并附带 OpenAI 模型与 embedding、文件读取器、LlamaParse 读取器、CLI 等一篮子集成。只写 pip install llama-index==0.14.14 的项目，日后重新安装时会拿到届时最新的 0.14.x core，而不是 0.14.14。生产环境应直接依赖 llama-index-core 并逐个声明所需集成，用锁文件固定全部版本。
  • Workflows 版本单独锁。llama-index-workflows 发布频率远高于 core（写作时已到 2.14），Agent 的行为变化往往来自它。
  • 0.x 的次版本号就是大版本。例如 0.11 起调用 ServiceContext 直接抛 ValueError（改用 Settings），0.13 删除了 AgentRunner 系列旧 Agent 实现。升级按“读 changelog → 跑评估集 → 再上线”执行。

持久化与增量摄取

文档会持续新增和修改，每次全量重建索引既慢又贵。IngestionPipeline 配合 docstore 可以只处理变化的文档：

用两份 Markdown 文件实测：首次写入 2 个节点，重复运行 0 个；修改其中一份后再运行，只处理 1 个节点，向量库总数仍是 2（旧向量被替换）。反例是去掉 filename_as_id=True：默认 doc_id 每次随机生成，重复运行时两份文档都被当作新文档重新切分和向量化。

还有三个边界：

  • filename_as_id 使用的是文件的绝对路径，部署目录一变，所有文档都会被当作新文档。跨环境迁移时应自己构造稳定 ID（如相对路径或业务主键）。
  • SimpleVectorStore 不存原文，不能用 VectorStoreIndex.from_vector_store 从它恢复索引（会报 Cannot initialize from a vector store that does not store text）；外部向量库一般存原文，才能这样用。
  • docstore 和 vector_store 需要一起持久化，只保存其中一个会导致下次运行时判断失误。

评估

上面的 evaluate 用 generate_question_context_pairs 让模型为每个片段出题，再测检索的命中率（hit_rate）和倒数排名均值（MRR）。这是成本最低的起点，但合成问题往往直接复用片段里的措辞，分数偏乐观；应该尽快补上真实用户问题。生成质量用 FaithfulnessEvaluator（回答是否有资料支撑）和 RelevancyEvaluator（回答是否切题）补充。评估集要和代码一起进版本库，任何切分参数、embedding 模型、解析档位的变化都先跑评估。

全局 Settings 与并发

Settings.llm 与 Settings.embed_model 是进程级全局变量。多租户服务里按请求修改它们会互相覆盖。应在构建组件时显式传入：VectorStoreIndex(..., embed_model=...)、index.as_query_engine(llm=...)、FunctionAgent(llm=...)，只把 Settings 当作开发期默认值。

适用与不适用

适合：

  • 文档是主要知识来源，且格式复杂（PDF 表格、多栏排版、扫描件）。
  • 团队需要系统地调检索质量：切分策略、混合检索、重排、评估闭环。
  • 需要“检索 → 判断 → 重试 → 生成”这类带分支和回环的流程，但不需要长时间挂起等待人工。
  • 需要把文档抽取做成服务，且可以接受托管（LlamaCloud）。

不适合或需要搭配：

  • 核心难点是长时运行、人工审批、可回放的状态机：编排交给 LangGraph，LlamaIndex 只做检索层。
  • 数据主要是结构化数据库：Text-to-SQL 或直接的业务 API 往往比 RAG 更准。
  • 文档不能出内网却想用 LlamaParse：只能换开源解析方案。
  • 只有十几份短文档：全文放进长上下文模型，可能比建索引更简单、更准确。

2026-09 补记：到 2026-09 的变化

以下信息按 2026-09-28 的 PyPI 发布记录与包内容核对。

  • 版本线：llama-index 与 llama-index-core 到 2026-09-21 发布 0.14.25，仍在 0.14.x；llama-index-workflows 在 2026-09-25 发布 2.25.0，半年多里从 2.14 走到 2.25，锁版本的建议依然成立。
  • 旧 SDK 的维护期限：llama-cloud-services 从 2026-02-11 的 0.6.93 起在说明中加入弃用公告，写明维护到 2026-05-01，要求迁移到 llama-cloud>=1.0；同一仓库的 llama-parse 包同样如此，两者最后一个版本都是 2026-02-13 的 0.6.94。还在用 from llama_cloud_services import LlamaParse 的代码应尽快迁移。
  • llama-cloud 进入 2.x：2.0.0 于 2026-03-31 发布，2026-09-08 已到 2.16.0。对照 2.16.0 的包内容，本文的 client.parsing.parse(tier=..., version=..., upload_file=..., expand=["markdown"]) 签名与返回结构仍然兼容；抽取入口由 client.extraction 改为 client.extract，split 从 beta 移到顶层，另有 classify 等资源。version 可选的日期版本已更新到 2026 年年中，锁定日期版本的做法不变。
  • LlamaAgents：2026 年 2 月推出 LlamaAgents Builder；llamactl 到 2026-09-16 已发布 0.10.4，本文列出的 0.4.5 命令结构是否有调整，升级前以 llamactl --help 为准。
