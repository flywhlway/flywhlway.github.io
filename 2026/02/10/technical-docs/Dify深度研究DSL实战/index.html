Dify 深度研究工作流实战：DSL 全解与编排/执行分层

一份可导入 Dify 1.12.1 的两轮检索深度研究工作流（规划→并行检索→反思补搜→带引用成文），逐节点解读与排障…

Flywhl 29 分钟 更新于 2026.09 #LangGraph#Dify#DSL

先读结论

  1. 在 Dify 内做深度研究，用固定轮数的迭代比开放式循环更可控：步数、时长、变量体积都能事先算清。
  2. 检索结果先在代码节点里压成带 URL 的短摘要再交给 LLM，是控制变量体积与引用质量的关键一步。
  3. 任务超过 20 分钟、需要浏览器渲染或中途失败要续跑时，Dify 只留入口与交付，研究循环交给 LangGraph 一类的 Runtime，用 Webhook 触发器回调收结果。

这篇解决什么

「深度研究」指的是：把一个开放问题拆成若干检索式，并行搜集证据，发现缺口后补搜，最后写成每个结论都能追溯到来源的报告。本文回答两个问题：

  1. 在 Dify 1.12.1 里，用原生节点能把这件事做到什么程度——给出一份完整、可导入的 DSL，并逐节点说明为什么这样写；
  2. 什么时候该停止往 Dify 里堆节点，改为「Dify 编排、外部 Runtime 执行」，两者之间用什么契约衔接。

DSL 的 Schema 规则与校验脚本在《Dify DSL 工作流设计与校验》，部署与运行时限制调参在《Dify 1.12 私有化部署与排障实录》，这里不重复。

流程与设计取舍

flowchart LR
  S["开始：研究问题"] --> P["LLM：规划 3~5 个检索式"]
  P --> PP["代码：解析 JSON（失败退回原问题）"]
  PP --> I1["迭代：第一轮检索（并行 3）<br/>每条：SearXNG JSON → 去重截断成摘要"]
  I1 --> R["LLM：反思，给出发现、缺口、补搜式"]
  R --> RP["代码：解析补搜式（去重，最多 3 个）"]
  RP --> I2["迭代：补充检索（可能为空）"]
  I2 --> W["LLM：只用材料成文，[n] 标注来源"]
  W --> E["结束：报告 + 补搜式"]

几处关键取舍：

取舍 选择 理由
轮数 固定两轮（首轮 + 一次补搜），不用循环节点 研究质量的大头来自「第一次反思后的补搜」，第三轮以后边际收益很低；固定轮数让步数、时长、Token 可预估，排障时每轮的输入输出都能在运行记录里直接看到
检索通道 HTTP 请求节点直连自建 SearXNG 不依赖任何搜索插件的版本与哈希，DSL 可以 dependencies: [] 导入；SearXNG 聚合多个引擎、无需 API Key
结构化输出 LLM 输出 JSON 文本，由代码节点解析 不要求模型支持结构化输出；解析失败有兜底，不会让整条链断掉
摘要位置 检索结果在迭代内部先压成摘要 原始 JSON 动辄上百 KB，直接进 LLM 既费 Token 又可能撞变量体积上限；摘要里保留 URL，成文时才能引用
迭代容错 remove-abnormal-output 单个检索式失败时丢弃该条结果，而不是整轮终止或往数组里塞 null
并行度 3 自建 SearXNG 背后仍是公共搜索引擎，并发过高容易被上游限流

按 1.12.1 的默认限制核算一次运行的预算（限制项的完整说明见部署篇）：

预算项 本流程的量级 默认上限
节点执行步数 首轮 5 条 × 3 步 + 补搜 3 条 × 3 步 + 主链约 9 步，约 35 步 WORKFLOW_MAX_EXECUTION_STEPS=500
运行时长 检索每条 2–5 秒，3 次 LLM 调用，通常 1–3 分钟 WORKFLOW_MAX_EXECUTION_TIME=1200 秒
最大变量 首轮输出 ≤ 5 × 4000 字符 MAX_VARIABLE_SIZE=204800 字节
代码节点数组 检索式 ≤ 5，补搜式 ≤ 3 CODE_MAX_STRING_ARRAY_LENGTH=30
单次 HTTP 响应 SearXNG JSON 通常在几十 KB HTTP_REQUEST_NODE_MAX_TEXT_SIZE=1 MB

DSL 全文（Dify 1.12.1 / DSL 0.5.0）

保存为 deep_research.yml，在控制台「导入 DSL 文件」即可。这份 DSL 已用校验篇的 dsl_lint.py 检查通过，三个代码节点的函数也在本地用构造数据跑过（正常 JSON、重复 URL、非 JSON 响应、规划失败四种输入）。

逐节点说明

开始节点只收一个 paragraph 类型的 question。研究范围、时间窗口等约束直接写在问题里，比加一堆表单字段更灵活。

规划（plan）要求模型只输出 {"queries": [...]}，并点名要覆盖「定义、现状数据、主要分歧、最新进展」四类检索式。点名维度是为了避免模型给出五个同义改写。温度 0.2，规划阶段要的是稳定而不是多样。

解析检索式（parse_plan）用正则取出第一个 {...} 再 json.loads，因为不少模型会把 JSON 包在 Markdown 代码围栏里。解析失败或结果为空时退回用原问题检索，所以运行记录里第一轮只有一条迭代，就说明规划失败了。

第一轮检索（s1）是并行迭代：iterator_selector 指向检索式数组，output_selector 指向迭代内摘要节点的 digest，迭代输出因此是一个字符串数组。迭代内用 {{#s1.item#}} 取当前检索式。

SearXNG 检索（s1_search）的 params 是多行字符串 q:… 与 format:json。这里有一个隐蔽的坑：HTTP 请求节点在没配置错误策略或重试时，收到 403 之类的非 2xx 响应不会失败，而是把状态码和 HTML 错误页作为正常输出往下传。SearXNG 没开 JSON 格式时就是这种情况，下游摘要节点会把它识别为「不是 JSON」。

结果摘要（s1_digest）按 URL 去重，每个检索式最多取 6 条，每条摘要截断到 300 字符，整段截断到 4000 字符，输出形如 - [标题](URL)：摘要 的 Markdown 列表。这个格式同时服务两件事：反思节点能判断证据是否充分，成文节点能直接生成编号引用。

反思（reflect）要求模型输出已确认的发现（附 URL）、缺口和最多 3 个补搜式；证据已足够时给空数组。这是整条链路里对质量影响最大的节点：没有它，研究就退化成「搜一次就写」。

解析补搜式（parse_reflect）会去掉首轮已经搜过的检索式，并同时把 findings 截断后交给成文节点。

补充检索（s2）与首轮结构相同。补搜式为空数组时，迭代直接以空数组成功结束（1.12.1 的迭代节点对空输入有专门处理），不需要额外的条件分支。

撰写报告（writer）的系统提示强调「只使用给定材料」「材料不足写证据不足」「正文 [n] 对应参考来源编号」，输入是审稿结论加两轮摘要。结束节点输出报告正文与补搜式，后者便于事后判断反思是否在起作用。

导入与跑通步骤

  1. 准备 SearXNG：在 settings.yml 的 search.formats 中加入 json（默认只有 html，未开启时 JSON 请求返回 403）；若启用了 server.limiter，放行 Dify 的出口地址。让 SearXNG 容器加入 Dify 的默认网络，服务名为 searxng。

  2. 按 HTTP 请求节点的真实路径测试：HTTP 请求节点经 ssrf_proxy 发出，所以要从代理这条路径验证，而不是在宿主机上 curl：

    能打印出 JSON 开头即通。报 403 且响应来自 squid，说明代理拒绝了到内网地址的请求，按部署篇调整 ssrf_proxy。

  3. 安装模型插件：DSL 里写的是 langgenius/openai/openai 的 gpt-4o-mini，没装 OpenAI 插件时三个 LLM 节点会提示模型不可用，逐个换成你已有的模型即可。

  4. 导入并设置环境变量：导入后在「环境变量」里确认 SEARXNG_BASE。

  5. 试跑：用一个有明确时间范围的问题试跑，在运行记录里依次检查：第一轮迭代的条数是否等于检索式数量、每条摘要是否含 URL、反思输出的 followups 是否合理。

  6. 发布与调用：发布后可在网页端使用，也可以用应用 API Key 调 POST /v1/workflows/run，研究类任务建议 response_mode 用 streaming，避免阻塞模式下客户端先超时。

排障：从现象到根因

现象 根因 处理
所有摘要都是「检索返回的不是 JSON」 SearXNG 未开启 JSON 格式（403），或被 limiter 拦截（429） 修改 search.formats / limiter 配置，按第 2 步复测
第一轮迭代输出为空数组 每条检索都失败，remove-abnormal-output 把它们全部丢弃 在运行记录里展开单条迭代看 HTTP 节点报错，多为 ssrf_proxy 到 SearXNG 不通或连接超时
第一轮只有一条迭代，检索式就是原问题 规划节点没按 JSON 输出，走了兜底 换指令遵循更好的模型，或在提示词末尾给一个完整示例
报告里出现材料中没有的数字或来源 模型越过材料补充事实 降低成文温度；在系统提示中要求每个数字后必须带 [n]；增加每条检索的结果数，减少「无米之炊」
followups 总是空的 反思节点过早判断「证据足够」 在反思提示里要求至少指出一个缺口，除非每个子问题都有两个以上独立来源
运行在网页端中途断开、后台其实跑完了 前端等待超时早于工作流完成 用流式调用；网页端等待时长由 TEXT_GENERATION_TIMEOUT_MS 控制
节点报 Output digest is missing. 改代码时某个分支提前 return，漏掉了 digest 让每个返回分支都带上全部声明的键

边界：什么时候不该再往 Dify 里塞

常见的说法是「Dify 工作流是 DAG，做不了循环，所以做不了深度研究」。这个判断不准确：1.12.1 有循环节点和迭代节点，上面的流程也完全在 Dify 内运行。真正的边界在下面这几条硬指标上：

需求 Dify 1.12.1 内的上限或现状 超出后的表现
研究轮数 循环节点最多 LOOP_NODE_MAX_COUNT=100 轮，整次运行 500 步 开放式「搜到够为止」难以保证在上限内收敛
单次运行时长 WORKFLOW_MAX_EXECUTION_TIME=1200 秒 小时级研究无法在一次运行里完成
状态与续跑 状态只活在单次运行里，没有跨运行的任务树与检查点 第 40 分钟失败只能从头再跑
网页获取 HTTP 请求节点只拿原始响应，1 MB 上限，不执行 JavaScript，不保持登录态 动态渲染页、需要登录的站点拿不到正文
代码执行 沙箱单次执行默认 15 秒，网络经 ssrf_proxy 不适合跑浏览器或长时间抓取
中间结果体积 单个变量约 200 KB 大量原文与证据无法在变量里流转

只要命中其中任意一条，就该换成分层结构：Dify 只做编排与交付，研究循环交给外部 Runtime。

分层架构：Dify 编排，Runtime 执行

各层的职责边界：

  • Dify 负责产品面：统一入口、模型与凭据、提示词版本、运行日志，以及把最终报告写入知识库或推送出去。它不持有研究过程中的任何状态。
  • Runtime 持有研究状态：用状态图表达「规划 → 执行 → 反思 → 判断是否继续」，每个节点执行后写检查点，失败从最近检查点恢复。LangGraph 的 Postgres 检查点（langgraph-checkpoint-postgres）可以直接承担这件事。
  • 浏览器服务独立部署：Chromium 内存占用高、崩溃概率不低，放进 Dify 沙箱既跑不动也拖垮宿主；用异步 Playwright 并按域名限制并发。
  • 证据以「URL + 内容哈希 + 抽取段落」入库，原始网页进对象存储，报告里的每个引用都指向证据 ID，而不是只存一段 LLM 生成的摘要。

衔接契约：按任务时长选模式

Dify 没有「等待 N 秒」的节点，轮询只能靠服务端阻塞，所以衔接方式由任务时长决定：

任务时长 模式 Dify 侧做法
10 分钟以内 同步长请求 一个 HTTP 请求节点调 Runtime 的同步接口，读超时不超过 HTTP_REQUEST_MAX_READ_TIMEOUT（600 秒）
10–20 分钟 提交 + 长轮询 HTTP 节点提交任务拿到 task_id；循环节点里放一个 HTTP 节点调「阻塞等待」接口（服务端最多挂起 300 秒），完成即退出循环。总时长受 1200 秒上限约束
20 分钟以上 异步回调 工作流 A 提交任务，把工作流 B 的 Webhook 触发器地址作为回调；Runtime 完成后 POST 结果，工作流 B 负责入库或推送。用户侧进度直接读 Runtime 的状态接口

Runtime 对外只需要四个接口：

接口 请求 响应
POST /research/tasks question、max_rounds、callback_url（可选） task_id
GET /research/tasks/{task_id} — status（queued / running / succeeded / failed）、progress、report_url
GET /research/tasks/{task_id}/wait?timeout=300 — 完成立即返回，否则到时返回当前状态
回调 POST {callback_url} task_id、status、report_url、sources 2xx

回调与轮询的响应里只放报告的对象存储链接和来源清单，不放报告全文：Dify 单个变量约 200 KB，Webhook 请求体默认上限 10 MB（WEBHOOK_REQUEST_BODY_MAX_SIZE），长报告放进变量迟早撞墙。

Runtime 里必须做对的四件事

  1. 任务树而不是任务列表：子问题之间有依赖（先确定口径，才能比较数据），用树或 DAG 记录父子关系与状态，反思节点可以针对某个子树补搜，而不是整体重来。
  2. 显式的停止条件：最大轮数、Token 预算、「连续一轮没有新来源」三者任一满足即停止。只靠模型自己判断「够了」，要么一轮就停，要么停不下来。
  3. 反思独立成节点：反思的输入是「问题 + 当前证据」，输出是缺口与下一步检索式，与执行节点分开，才能单独评估和替换提示词。
  4. 浏览器按需启用：先走检索 API 与静态抓取，只有正文为空或明显是动态渲染的页面才交给浏览器服务，否则成本和耗时都会失控。

可以直接参考的开源实现：langchain-ai/open_deep_research（基于 LangGraph 的深度研究参考实现）、langchain-ai/langgraph（状态图与检查点）、browser-use/browser-use（让 LLM 驱动浏览器）、unclecode/crawl4ai（面向 LLM 的网页抓取与正文抽取）、searxng/searxng（自建元搜索）。在 4C6G 的机器上，浏览器服务建议放到另一台机器，或把并发限制在 1–2。

硬约束清单

  • 研究轮数固定且可预估；步数、时长、最大变量先按预算表核算再上线
  • 检索结果在迭代内压成带 URL 的摘要，原始响应不进 LLM、不进下游变量
  • SearXNG 开启 JSON 格式，并从 ssrf_proxy 路径验证可达
  • 迭代用 remove-abnormal-output，代码节点对非 JSON 输入有兜底
  • 成文提示要求只用给定材料、每个数字带引用、证据不足直说
  • 任务超过 20 分钟、需要浏览器渲染或需要续跑时，改为外部 Runtime + Webhook 回调
  • 回调与轮询只传报告链接与来源清单，不传全文

2026-09 补记：1.13 之后对这套方案的影响

  • 人工审核节点（1.13）：Human Input 节点可以让工作流暂停等待人工输入。放在「规划」之后，由人确认或修改检索式再继续，是对本文流程最直接的增强；1.12 上要做到这一点只能借助外部系统。
  • Dify Agent 与沙箱（1.16 Beta、1.17）：1.16 引入带 Linux 沙箱与 Skills 的 Dify Agent，1.17 增加 E2B 沙箱、工作区级 Skill 管理与统一 Tracing。执行层的一部分能力开始进入 Dify 内部，但本文「边界」一节的判断依据（时长、状态持久化、续跑）需要在新版本上逐项复核，本文未在 1.17 上复测。
  • DSL 版本：1.17.1 对应 DSL 0.7.0，跨版本导入的判定规则见校验篇补记。把本文的 0.5.0 DSL 迁到新版本时，导入后在画布里保存一次再导出，以导出稿作为新版本的正式稿。
