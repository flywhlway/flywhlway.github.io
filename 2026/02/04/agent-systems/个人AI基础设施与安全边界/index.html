OpenClaw（原 Clawdbot）爆红之后：个人 AI 基础设施的安全边界

从 OpenClaw 的信任模型和 CVE-2026-25253 攻击链出发，梳理本地执行型个人 Agent 的五类风险，给出附理由与验证方法的个人加固清单…

Flywhl 12 分钟 更新于 2026.09 #供应链安全#Agent#OpenClaw

先读结论

  1. 只绑定 localhost 挡不住浏览器这座桥：CVE-2026-25253 通过受害者浏览器外泄网关令牌，再反向连回本机网关，1 次点击即可远程执行代码。
  2. 网关令牌等于操作员权限，审批开关和沙箱配置都能被它改掉；令牌一旦可能泄露，必须轮换，不能只升级版本。
  3. 技能和插件是代码加指令，要按不受信任的第三方代码审查；市场里已出现成批投递窃密木马的恶意技能。
  4. 旧包名 clawdbot 在 npm 上停在 2026.1.24-3，只升级旧包拿不到修复，要切换到 openclaw 包并升级到 2026.1.29 及以上。
  5. 企业不能只靠封禁影子 AI，需要同时具备终端发现能力、授权治理和一个可审计的替代方案。

从「会聊天」到「能动手」：本地执行型个人 Agent

OpenClaw 这类个人 Agent 和网页版聊天助手的区别，不在模型更聪明，而在它拿到了三样东西：长期运行的进程、真实的系统权限、来自外部的输入通道。

按官方文档的描述，它的核心是一个运行在用户机器上的 Gateway 进程，在单一端口（默认 18789）上同时提供 WebSocket 和 HTTP 服务。围绕这个进程有几类能力：

  • 消息通道：WhatsApp、Telegram、Slack、Discord、iMessage 等。别人发来的消息可以直接触发 Agent。
  • 工具：执行 Shell 命令（exec）、读写文件、驱动浏览器、定时任务。配对的 macOS 节点还可以远程执行 system.run。
  • 技能与插件：技能以 SKILL.md 加脚本的形式存在；插件在 Gateway 进程内运行，与 Gateway 拥有相同权限。
  • 本地状态：配置、渠道凭证、模型 API Key 和 OAuth 令牌、会话记录，全部保存在 ~/.openclaw/ 目录下。

信任模型：三类主体，三种权限

官方安全文档把问题归结为三件事：谁能跟 Agent 说话，Agent 能在哪里动手，Agent 能碰到什么。拆开来看，系统里有三类主体，应当给它们不同的权限：

主体 实际能做什么 应有的信任级别
操作员（持有网关令牌的人或程序） 修改配置、调整审批与沙箱、调用任意工具 最高，等同于本机管理员
消息发送者（已配对或在白名单中的联系人） 触发 Agent 执行任务 按人授予，默认只能触发只读或受限工具
内容（网页、邮件、文档、工具输出） 不应有任何权限，但会进入模型上下文 零信任，只能作为数据

多数事故都出在这三层混在了一起：内容里的指令被当成主人的指令，发送者拿到了操作员才该有的工具，或者操作员令牌被一个网页拿走。官方文档写得很直白：提示注入没有被解决，系统提示词只是软约束，真正起强制作用的是工具策略、执行审批、沙箱和渠道白名单。

名称演变与 CVE-2026-25253

两个月里改了四次名字

时间 名称 说明
2025-11-24 warelay GitHub 仓库创建时的名字
2025-12 Clawdis 第一次更名
2026-01 Clawdbot 以这个名字爆红，npm 包名为 clawdbot
2026-01-27 Moltbot 因收到商标方面的请求而更名
2026-01-29/30 OpenClaw 定名，npm 包改为 openclaw

频繁更名直接带来一个运维问题。截至写作时，旧包 clawdbot 在 npm 上的最新版本停在 2026.1.24-3（2026-01-25 发布），而下面这个漏洞在 2026.1.29 才修复。如果用 npm update -g clawdbot 升级，永远拿不到修复。正确做法是安装 openclaw 包（官方文档说明新包保留了 clawdbot 命令作为兼容入口）。搜索引擎里旧名字对应的教程和仓库，也要格外留意来源。

攻击链

以下内容依据 GitHub 安全公告 GHSA-g8p2-7wf7-98mq（对应 CVE-2026-25253，CVSS 3.1 评分 8.8，向量 AV:N/AC:L/PR:N/UI:R），以及报告方 depthfirst 公开的技术分析。受影响版本为 2026.1.28 及以下，修复版本为 2026.1.29。

sequenceDiagram
  participant V as 受害者浏览器
  participant A as 攻击者服务器
  participant G as 本机 Gateway（仅监听 loopback）
  V->>V: 点击构造链接，Control UI 读取 ?gatewayUrl=攻击者地址
  V->>A: 页面加载即自动连接，握手中携带已保存的网关令牌
  A-->>V: 令牌到手；恶意页面脚本在受害者浏览器中运行
  V->>G: 从浏览器发起到 ws://localhost:18789 的连接（未校验 Origin）
  G-->>V: 以操作员身份认证通过
  V->>G: 关闭执行审批，把 exec 执行位置改到宿主机
  V->>G: 调用 system.run 执行任意命令
  1. 令牌外泄：Control UI 直接信任查询串中的 gatewayUrl，不做校验，页面加载时自动连接，并在 WebSocket 连接载荷中带上已保存的网关令牌。受害者只要点开一个构造好的链接，令牌就会发到攻击者的服务器。
  2. 绕过仅本机监听：公告明确指出，即使 Gateway 只监听 loopback，这个漏洞依然可以利用，因为出站连接是由受害者的浏览器发起的。depthfirst 的分析补充说，当时 Gateway 的 WebSocket 服务端不校验 Origin 头，攻击者页面的脚本可以在受害者浏览器里直接连 ws://localhost:18789，这是一种跨站 WebSocket 劫持。
  3. 关掉防护：拿到操作员权限后，按 depthfirst 的描述，攻击者先通过 exec.approvals.set 把审批设为 ask: "off"，再用 config.patch 把 tools.exec.host 设为 gateway，让命令离开沙箱、在宿主机上执行。
  4. 执行代码：最后通过 node.invoke 调用 system.run，在宿主机上执行任意命令。

修复方式是去掉「加载即自动连接」的行为：切换到新的网关地址时，必须由用户在界面上确认。

这条攻击链说明了三件事：

  • 「只监听 127.0.0.1」保护的是网络层，保护不了浏览器这一层。 本机浏览器能访问 localhost，浏览器里跑着任意网站的脚本，所以本机服务必须校验 Origin 并强制认证。
  • 审批和沙箱只要能被同一个令牌改掉，就不算安全边界。 令牌泄露之后，这些配置在攻击者手里只是一次 API 调用。
  • 升级不等于恢复。 如果在未修复版本上点过来路不明的链接，除了升级，还要轮换网关令牌，并检查配置是否被改过。

2026-01-31 同一批公开的还有两个命令注入漏洞，也在 2026.1.29 修复：CVE-2026-24763（Docker 执行路径中通过 PATH 环境变量注入，8.8 分）和 CVE-2026-25157（sshNodeCommand 中通过项目根路径注入，7.7 分）。

风险分类

类别 典型路径 已公开的依据 首要缓解
本地 RCE 本机浏览器或进程作为跳板，改配置后执行命令 CVE-2026-25253、CVE-2026-24763、CVE-2026-25157 及时升级；令牌轮换；专用低权限账户
网关对外暴露 监听局域网地址或做端口转发；反向代理把外部请求变成 127.0.0.1 后被当作本地连接自动信任 据媒体报道，2026-01 下旬有研究者用 Shodan 检索控制面板指纹，发现数百个暴露实例，其中部分无需认证；官方文档已加入 gateway.trustedProxies 的配置说明 只监听 loopback；远程访问走 Tailscale Serve；代理配置 trustedProxies 并覆盖 X-Forwarded-For
技能与插件供应链 技能说明里要求先执行一条「前置依赖安装」命令；插件在进程内运行；npm 安装时会执行生命周期脚本 据 The Hacker News 报道，安全厂商 Koi Security 于 2026-02-01 发布审计结果：ClawHub 上的 2857 个技能中有 341 个是恶意技能，其中 335 个属于同一投毒活动，主要投递 macOS 窃密木马 Atomic Stealer，并使用 clawhub1、clawhubb 这类仿冒名称 不安装未审计的技能；插件使用 plugins.allow 白名单；固定版本
凭证与会话令牌 openclaw.json 中的网关令牌、auth-profiles.json 中的模型 API Key 和 OAuth 令牌、渠道凭证、会话记录，都以文件形式存放在家目录 官方文档列出了这份凭证存放位置清单；技能的 env / apiKey 配置会注入宿主进程，而不是沙箱 目录权限 700、文件 600；全盘加密；使用有额度上限的专用 API Key
提示注入导致越权 邮件、网页、文档里夹带指令，Agent 用自己的工具权限去执行 官方文档承认提示注入没有被解决；早期测试中 Agent 曾把 find ~ 的完整输出发到群聊 读取不可信内容的 Agent 只给只读工具；高危工具需审批；启用沙箱

其中最容易被低估的是最后一类。攻击者不需要能给 Agent 发消息，只要 Agent 会去读一封邮件或一个网页就够了。官方给出的一种缓解方式值得采纳：先用一个无工具或只读的「阅读 Agent」对不可信内容做摘要，再把摘要交给有工具权限的主 Agent。

个人加固清单

先给一份基线配置（json5，放在 ~/.openclaw/openclaw.json），下面的表格逐条说明理由和验证方法：

措施 理由 验证方法
切换到 openclaw 包并升级到 2026.1.29 及以上（写作时最新为 2026.2.2 系列） 旧包 clawdbot 停在 2026.1.24-3，仍受 CVE-2026-25253 影响 npm ls -g --depth=0 应只看到 openclaw，没有独立的 clawdbot 包；在已升级版本上打开带 gatewayUrl 参数的控制台链接，界面应弹出确认
升级后轮换网关令牌 在旧版本上点过的链接可能已经泄露令牌，升级并不会让旧令牌失效 生成新令牌并重启后，用旧令牌连接应被拒绝
只监听 loopback，远程访问走 Tailscale Serve 局域网监听或端口转发会让攻击面扩大到整个网络；Serve 可以让 Gateway 保持只监听本机 macOS 执行 lsof -nP -iTCP:18789 -sTCP:LISTEN，Linux 执行 ss -ltnp | grep 18789，只应出现 127.0.0.1；从另一台设备执行 nc -vz <本机IP> 18789 应失败
使用反向代理时配置 gateway.trustedProxies，并让代理覆盖而不是追加 X-Forwarded-For 否则经代理进来的请求来源都是 127.0.0.1，会被当成本地连接 从外网访问应被要求认证；检查代理配置中请求头是否为覆盖写入
私聊用 pairing 或 allowlist，群聊要求 @ 才响应 陌生人能触发 Agent 是最常见的事故起点 openclaw pairing list <channel> 核对已批准的发送者；让陌生账号发消息，应只收到配对码
沙箱 mode: "all"，工作区只读；读取不可信内容的 Agent 禁用 exec、browser 沙箱默认可选且关闭，关闭时 exec 直接在宿主机执行；沙箱容器默认没有网络 openclaw security audit 不应再提示工具影响范围过大；在会话中让 Agent 执行 whoami 和 hostname，结果应来自容器
用专用的非管理员系统账户运行 Gateway，辅助功能、屏幕录制、完全磁盘访问等权限按需授予 即使 RCE 成功，攻击者也拿不到你日常账户下的 SSH 密钥、浏览器 Cookie 和文档 用 ps 查看网关进程的属主；在该账户下尝试读取主账户家目录，应被拒绝
~/.openclaw 目录权限 700，配置文件 600，开启全盘加密 令牌、API Key、会话记录全是明文文件，是窃密木马的首要目标 openclaw security audit --fix 会收紧权限；用 stat 复核
不安装未审计的技能；不执行技能说明里要求的下载或粘贴命令；插件用 plugins.allow 白名单并固定版本 技能市场已出现成批投毒；插件在进程内运行，npm 安装时会执行生命周期脚本 安装前阅读 SKILL.md 和随附脚本，检查是否有外部下载、base64 解码、curl | sh 这类片段；避免不看差异就执行 clawhub update --all
浏览器控制使用专用配置文件，不用日常浏览器 日常配置文件里有已登录的会话，Agent 能访问的范围就是你能访问的范围 在 Agent 的浏览器里打开常用站点，应处于未登录状态
模型 API Key 单独申请，并设置消费上限 凭证被窃后，损失有上限，也便于单独吊销 在模型服务商控制台确认该 Key 独立存在且设置了额度
定期执行 openclaw security audit --deep，并订阅仓库的安全公告 项目处于 1.0 之前，迭代快，安全公告密集 审计报告无高危项；GitHub 仓库 Watch 设置中勾选 Security alerts

如果怀疑已经被入侵，按官方文档的顺序处理：先停止 Gateway 并把监听改回 loopback；再轮换网关令牌、远程客户端凭证、渠道令牌和模型 API Key；然后检查 ~/.openclaw/agents/<agentId>/sessions/*.jsonl 中有没有异常的工具调用，检查 extensions/ 下有没有不认识的插件，再核对 gateway.bind、gateway.auth、tools.elevated 最近是否被改动过。

企业视角：影子 AI 与终端管控

对企业来说，OpenClaw 的问题首先是看不见。员工在办公电脑上装了它，把公司的 Slack、邮箱、日历接进去，调用的是个人账户的模型服务。这就同时造成了几个问题：

  • 数据外流：公司消息和文档进入个人模型账户的上下文，没有经过数据防泄漏审查。
  • 凭证落在终端：公司系统的 OAuth 令牌以明文形式存放在员工家目录，窃密木马会优先收集这些文件。
  • 内网横向移动：如果 Gateway 监听了局域网地址，或者开启了完整模式的 mDNS 广播，同网段的主机都能发现并尝试连接它。

发现手段

发现之后的处置，取决于企业有没有替代方案：

策略 适用情况 必须同时做的事
禁止 研发终端接触生产凭证、合规要求严格 提供审计完备的内部 Agent 平台，否则员工会转到个人设备上用，并把公司数据带过去
受控允许 小规模试点 规定使用专用终端或虚拟机；只允许接入非敏感的渠道；技能从内部镜像的白名单中安装；模型走公司的网关
集中提供 需求普遍 把「个人助理」能力做到企业平台里：按用户身份授权，有副作用的工具需要审批，操作留存审计记录，工具执行放在隔离沙箱中

另外有两项治理动作，和终端管控同样重要：一是定期审查 Slack、Google Workspace、Microsoft 365 里第三方应用的 OAuth 授权，吊销来路不明的授权；二是在 EDR 中把 ~/.openclaw/ 下的凭证文件纳入敏感文件访问监控。

2026-09 补记：技能市场投毒、治理变化与后续漏洞

  • 技能市场投毒持续发酵：2026-02 起，多家安全厂商陆续发布分析，确认 ClawHub 上有数百个恶意技能以「安装前置依赖」为名投递窃密木马。据后续报道，随着市场规模扩大到一万余个技能，被识别出的恶意技能增加到八百余个。OpenClaw 于 2026-02-07 在官方博客宣布与 VirusTotal 合作：技能发布时即扫描，判定为恶意的直接阻止下载，可疑的加警告标签，所有在架技能每天重新扫描。官方博客同时承认，用自然语言写成的恶意指令和精心构造的提示注入不会触发病毒特征，扫描无法覆盖。所以上文「不装未审计技能」这一条依然有效，市场侧的扫描只是其中一层防线。
  • 项目治理变化：据 TechCrunch 等媒体 2026-02-15 报道，作者 Peter Steinberger 加入 OpenAI，项目转交 OpenClaw Foundation，继续以开源方式运作。
  • 后续 CVE：写作当天（2026-02-04）公开的 CVE-2026-25593，是 Gateway WebSocket 的 config.apply 接口存在本地未授权 RCE：本机任意进程可以写入不安全的 cliPath，从而注入命令。该漏洞 CVSS 8.4，已在 2026.1.20 修复，按上文升级到 2026.1.29 及以上的用户不受影响。2026-02-14 至 02-15 又集中公开了数十条安全公告，其中包括插件安装路径穿越、节点调用审批绕过导致 RCE、借助命令替换或 Windows cmd.exe 解析绕过 exec 白名单等 critical 和 high 级别问题。这说明审批和白名单在实现层面被多次绕过，不能作为唯一的安全边界，沙箱、独立账户和网络隔离才是兜底。
  • 现状：截至 2026-09，GitHub 仓库约 39 万 star，公开的安全公告累计约 720 条（其中 critical 14 条、high 249 条），2 月和 3 月最为集中，各有两百余条。最新版本为 v2026.9.6（2026-09-23）。公告数量这么多，对个人用户意味着「及时升级」本身就需要一个固定流程，比如每周检查一次更新并执行 openclaw security audit，不能等出事再补。
