Dify DSL 工作流设计与校验：Schema 硬约束与导入预检

对照 Dify 1.12.1 源码整理 DSL 0.5.0 的 Schema 硬约束：导入各阶段各校验什么、节点与容器的字段规则、导出时被改写的内容…

Flywhl 24 分钟 更新于 2026.09 #工作流#Dify#DSL

先读结论

  1. 导入只校验顶层结构、变量定义和节点类型名；节点字段写错要到画布渲染、发布或运行时才暴露，所以导入成功不等于可用。
  2. if-else 只写 cases；数值比较运算符是 ≠ ≥ ≤ 这类 Unicode 符号；LLM 节点必须带 context；环境变量条目用 name 而不是 variable。
  3. 1.12 的控制台接口用 Cookie 鉴权，所有需要登录的请求都要带与 csrf_token Cookie 一致的 X-CSRF-Token 头，登录密码要 Base64。
  4. 最终入库的 DSL 应是「导入 → 画布保存 → 再导出」得到的那一份，而不是生成器的原始输出。

导入成功，为什么还会打不开

用 LLM 或脚本生成 Dify DSL，最常见的挫败是：导入提示成功，一点开应用就白屏，或者能打开但运行第一步就报字段错误。原因是 Dify 的校验分散在五个阶段，导入只覆盖了最前面的一小段。以下对照 1.12.1 的 api/services/app_dsl_service.py 与 workflow_service.py 整理：

阶段 校验内容 典型报错或现象
导入 YAML 必须是映射；version 必须是字符串；缺 kind 自动补 app；必须有 app 段；workflow / advanced-chat 必须有 workflow 字典；环境变量与会话变量逐条构造；dependencies 逐条解析 Missing app data in YAML content、missing name、Invalid version type
草稿同步（导入时同步执行） 每个节点的 data.type 必须是合法枚举值；开始节点与触发器节点不能共存；features 结构校验 'xxx' is not a valid NodeType、Start node and trigger nodes cannot coexist in the same workflow
画布渲染 前端按自己的数据结构读取节点，容器、条件分支、句柄对不上就崩 白屏、client-side exception
发布 模型是否存在、凭据是否可用、图结构 Model xxx not found for provider xxx
运行 每个节点的 data 用对应的 Pydantic 模型校验 缺字段、类型不符、输出校验失败

换句话说，节点内部字段写错，导入阶段几乎不会报。生成 DSL 的正确目标不是「能导入」，而是「导入后画布能打开、发布能通过、单步能跑」。

导入接口的返回状态与 HTTP 码：

status HTTP 含义 处理
completed 200 版本一致，已写入 进入画布核对
completed-with-warnings 200 DSL 次版本号低于实例 已写入，重点检查老版本字段
pending 202 DSL 版本高于实例，或主版本号低于实例 10 分钟内调用 confirm 才会写入
failed 400 结构错误 按 error 修正

版本号与跨版本导入

DSL 版本号与 Dify 版本的对应关系（到本文写作时的 1.12）：

Dify 版本 DSL version
1.0–1.2 0.1.5
1.3 0.2.0
1.4–1.6 0.3.0
1.7 0.3.1
1.8–1.9 0.4.0
1.10–1.12 0.5.0

兼容判定只比较版本号：高于实例一律 pending；主版本号低于实例也是 pending；次版本号低于实例是 completed-with-warnings；其余 completed。另有一条特殊逻辑：版本不高于 0.1.5 且没写 dependencies 时，导入会按节点里引用的模型供应商和工具自动推断「最新版」插件依赖。社区里大量模板停留在 0.1.x，导入 1.12 时会得到警告和一串待安装插件，这是预期行为。

生成器应当把 version 固定写成目标实例的版本（1.12 为 "0.5.0"），不要为了「新」写更高的版本号。

顶层骨架

Schema 硬约束

顶层与变量

  • version 必须是字符串。YAML 里 0.5.0 本身是字符串，0.5 却是浮点数，稳妥做法是始终加引号。
  • 带 app_id 的覆盖导入只允许 workflow 与 advanced-chat 应用。
  • 环境变量与会话变量每条必须有 name、value_type、value，value 不能是 null。用 variable: 代替 name: 会直接导入失败（missing name）。建议同时写 id（UUID）与 description，与导出格式保持一致。
  • 环境变量界面上可选的类型是 string、number、secret。secret 在导出时（不勾选包含密钥）值会被清空，导入后要重新填写。
  • dependencies 的条目格式为 type: marketplace + value.marketplace_plugin_unique_identifier: 组织/插件:版本@哈希。哈希对不上会被标为缺失依赖；手写 DSL 时宁可留空，在插件页手动安装。

节点与边

  • 节点外层：id（字符串，纯数字 ID 要加引号）、type、position、data。普通节点外层 type 一律是 custom，真正的节点类型写在 data.type；迭代与循环的起始节点外层分别是 custom-iteration-start、custom-loop-start；画布注释是 custom-note。
  • data.title 必填，所有节点的数据模型都以它为必需字段。
  • 边：source、target 必须指向存在的节点；targetHandle 为 target；sourceHandle 普通节点为 source，条件分支节点为对应的 case_id，ELSE 分支固定为 false，问题分类器为分类 id，开启失败分支的节点另有 fail-branch。
  • 不在容器里的节点不需要 isInIteration: false 之类的字段，官方导出的外部节点也没有。容器内的节点才有硬性要求，见下面的片段。

data.type 界面名称 备注

常用节点的字段约束

节点 必备字段 易错点
llm model.provider、model.name、model.mode、prompt_template、context 1.x 的 provider 形如 langgenius/openai/openai，写 openai 会找不到模型；context 没有默认值，不用也要写 {enabled: false}；结构化输出用 structured_output_enabled: true + structured_output.schema，前提是所选模型支持
if-else cases[].case_id、logical_operator、conditions[] 顶层 conditions 是已弃用字段，只写 cases；每个条件含 id、varType、variable_selector、comparison_operator、value
条件运算符 — 合法值：contains、not contains、start with、end with、is、is not、empty、not empty、in、not in、all of、=、≠、>、<、≥、≤、null、not null、exists、not exists。写 !=、>=、starts with 都不合法
code code_language、code、variables、outputs 语言只有 python3、javascript；输出类型只有 string / number / object / boolean 及对应的 array[...]；声明的每个输出键都必须出现在返回值里，否则报 Output xxx is missing.；数组元素类型必须一致
tool provider_id、provider_name、provider_type、tool_name、tool_label、tool_configurations、tool_parameters 插件工具的 provider 形如 langgenius/tavily/tavily，provider_type: builtin；tool_parameters 每项是 {type, value}，mixed 对应含引用的字符串，variable 对应选择器列表，constant 对应常量；当前导出带 tool_node_version: '2'
http-request method、url、authorization、headers、params headers 与 params 是 键:值 按行分隔的字符串；鉴权写 {type: api-key, config: {type: bearer, api_key: ...}}；body 的 data 是 [{type: text, value: ...}] 列表；1 MB 的上限作用在响应体
assigner version: '2'、items[] 每项含 variable_selector、operation（如 over-write、append、+=）、input_type（variable / constant）、value
end outputs[] 每项 variable、value_selector、value_type

变量引用

  • 文本里（提示词、URL、模板以外的字符串）用 {{#节点ID.变量#}}，系统变量 {{#sys.query#}}、{{#sys.workflow_run_id#}}，环境变量 {{#env.NAME#}}，会话变量 {{#conversation.name#}}。
  • 选择器字段（*_selector）用列表：["节点ID", "变量"]、["env", "NAME"]、["sys", "files"]。
  • 模板转换节点的 template 是 Jinja2，里面引用的是本节点 variables 里声明的名字，不是 {{#...#}}。
  • 引用的节点 ID 必须真实存在。改节点 ID 时，文本引用与选择器要一起改，这是手工编辑 DSL 最容易漏的地方。

生成方法：让实例自己提供上下文

让 LLM 凭记忆写 DSL，字段与插件标识必然漂移。更可靠的做法是把实例里的真实信息喂给它：

  1. 母版：从自己的实例导出一两个结构相近、能正常运行的应用，作为 few-shot 母版。它们带着与实例完全一致的字段形态与插件标识。
  2. 可用能力清单：用控制台接口拉取已安装插件与可用模型，只允许生成器使用清单里的 provider、tool_name。
  3. 约束清单：把上一节的硬约束原样放进提示词。
  4. 目标版本：明确写 version: "0.5.0"。

用到的控制台接口（前缀 /console/api）：

用途 方法与路径
登录 POST /login，JSON email、password（Base64）、remember_me
应用列表 GET /apps?page=1&limit=100（limit 上限 100）
导出 DSL GET /apps/{app_id}/export?include_secret=false，返回 {"data": "<yaml>"}
导入 POST /apps/imports，mode 为 yaml-content 或 yaml-url，可带 app_id 覆盖
确认导入 POST /apps/imports/{import_id}/confirm
依赖检查 GET /apps/imports/{app_id}/check-dependencies，返回 leaked_dependencies
已装插件 GET /workspaces/current/plugin/list
可用模型 GET /workspaces/current/models/model-types/llm

1.12 的控制台鉴权有两个脚本必须处理的细节：登录成功后令牌只放在 Cookie 里（响应体只有 {"result": "success"}），不再返回 access_token；此后每一个需要登录的请求（包括 GET 导出）都要带 X-CSRF-Token 头，值等于 csrf_token Cookie。实例配置为 https 且没设 COOKIE_DOMAIN 时，Cookie 名会带 __Host- 前缀。

导入预检与回导出

预检不要每次新建应用：先在控制台建一个与 DSL 同模式的空应用当「预检 App」，脚本每次带 app_id 覆盖它的草稿。脚本依次做登录、导入（pending 时默认停下，由人确认版本差异）、依赖检查、导出、规范化差异对比：

差异里常见的几类，含义各不相同：

  • dependencies 被补全：说明实例按节点反推出了插件依赖，把导出稿里的标识回灌到生成器的能力清单；
  • 知识检索节点的 dataset_ids 变成一串 Base64：导出加密，正常；
  • 触发器节点的调度配置、Webhook 地址、订阅 ID 被改写或清空：导出策略，见下一节；
  • 其余字段的增删：生成器的模板与实例不一致，按导出稿修正模板。

画布一步不能省

脚本只能覆盖导入与草稿同步两个阶段。画布渲染的校验在浏览器里，接口替代不了：打开预检 App，确认没有白屏、检查清单（Checklist）没有报错，随手拖动一个节点触发一次草稿保存，再跑一次 dsl_roundtrip.py（或直接在控制台导出）。入库的是这份经过画布保存后的导出稿，生成器的原始输出只算草稿。

导出与迁移时被改写的内容

内容 导出时的行为 迁移时怎么办
secret 类型环境变量 不勾选包含密钥时值被清空 导入后重填；DSL 里永远不放真实密钥
工具与 Agent 节点的 credential_id 不勾选包含密钥时删除 导入后在节点里重选凭据
知识检索的 dataset_ids 默认按工作空间 AES 加密 跨工作空间导入时解密失败的 ID 会被静默丢弃；源实例设 DSL_EXPORT_ENCRYPT_DATASET_ID=false 导出明文 UUID，目标实例里仍需存在同 ID 的知识库，否则重选
trigger-schedule 写入默认调度配置（每天 12:00 AM、UTC） 导入后重新设置调度并发布
trigger-webhook 清空 webhook_url 与 webhook_debug_url 发布后使用新生成的地址
trigger-plugin 清空 subscription_id 重新订阅

yaml-url 方式导入另有三点：github.com/.../blob/... 形式的链接会被自动改写为 raw.githubusercontent.com；抓取经 ssrf_proxy 发出，连接与读取超时都是 10 秒，网络受限的私有化实例常在这里失败；内容超过 10 MB 直接拒绝。

定时执行：Schedule Trigger 与外部调度

一个流传很广的说法是「开源版不能定时触发工作流，只能外部 cron 调 API」，这对 1.12 已经不成立：1.10 起 workflow 模式内置 Schedule、Webhook 与插件事件三类触发器。用定时触发器要注意：

  • 触发器只能用于 workflow 模式，且与开始节点互斥，一个工作流里二者只能选其一（草稿同步时就会校验）；
  • 调度配置支持可视化（hourly / daily / weekly / monthly）与 cron 两种模式，时区单独设置，默认 UTC；
  • 只有发布后才生效；自托管实例依赖 worker_beat 上的轮询任务，对应 ENABLE_WORKFLOW_SCHEDULE_POLLER_TASK，默认开启；
  • 从 DSL 导入后调度会被重置，见上表。

仍需要外部调度的场景只剩两类：advanced-chat 应用（没有触发器），以及调度逻辑依赖外部系统状态。这时用 Service API，以应用的 API Key 调用：

生成前对照的硬约束清单

  • version: "0.5.0"（带引号，不高于实例版本），kind: app，app.mode 与目标一致
  • 环境变量、会话变量每条都有 name、value_type、非空 value；DSL 中不含任何真实密钥
  • 所有节点 ID 是唯一的字符串，外层 type 与 data.type 分层正确，data.title 齐全
  • data.type 取自 1.12.1 枚举；variable-assigner 与 assigner 没有混用
  • 开始节点与触发器节点不同时出现；触发器只出现在 workflow 模式
  • 容器：start_node_id 指向 *-start 子节点，容器内节点都有 parentId、isIn*、*_id
  • 条件分支只用 cases，运算符在合法列表内，边的 sourceHandle 对应 case_id 或 false
  • LLM 节点带 context，provider 为三段式标识
  • Code 节点声明的输出与返回值一一对应，数组长度不超过实例限制（默认 30）
  • 所有 {{#节点ID.变量#}} 与选择器都指向存在的节点
  • 通过 dsl_lint.py → 导入预检 → 画布保存 → 再导出，入库的是导出稿

2026-09 补记：1.13 之后的 DSL 变化

  • 版本号：1.13–1.15 为 0.6.0，1.16–1.17 为 0.7.0。1.17.1 的兼容判定逻辑与本文一致，所以 0.5.0 的 DSL 导入 1.17.1 会得到 completed-with-warnings；反过来把 0.6.0 / 0.7.0 的 DSL 导入 1.12 会进入 pending，强行确认后，新版本才有的节点无法运行。
  • 新节点：Human Input（人工输入）节点作为正式功能随 1.13 发布，data.type 为 human-input。1.12.1 源码里已有这个类型的早期实现，但它不属于 1.12 的正式功能，所以本文的 lint 白名单没有收录；面向 1.13 以上生成 DSL 时要加进去。1.16 的 Dify Agent（Beta）带来 DSL 0.7.0。
  • 接口：1.17.1 的控制台登录仍要求 Base64 密码，导入、确认、依赖检查三个接口路径不变，dsl_roundtrip.py 的调用方式不受影响。1.15 起官方另提供了 difyctl 命令行工具，本文没有评估它对 DSL 导入导出的支持。
