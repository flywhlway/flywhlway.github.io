0. TL;DR — 一页结论

如果你只想看结论：

  • 最终推荐：以 GSD（Redux 社区分叉）为「跨工具规格主干」，在 Claude Code 内叠加 Superpowers 作为「执行质量层」的融合方案。
  • 核心理由：你的环境有两个硬约束——① 需要 Claude Code 与 Cursor 协同 ；② 项目是中大型。在这两个约束下，只有 GSD 能让两个工具共享同一套落盘的规格 / 计划 / 状态（.planning/），因为 GSD 原生支持 Cursor 运行时，而 Superpowers 本质是 Claude Code 插件、无法驱动 Cursor。
  • 安装级别：GSD 工具本体用户级（global）安装（跨工具、跨项目复用）+ 项目状态 .planning/ 始终随仓库提交（项目级、可版本化）；Superpowers 作为 Claude Code 官方市场插件天然是用户级。
  • ⚠️ 必读风险：原始 GSD 仓库（gsd-build/get-shit-done）已停更，原作者于 2026-05 失联、其关联的 $GSD Solana 代币被公开指为 rug-pull。务必使用社区延续分叉 open-gsd/get-shit-done-redux（npm: @opengsd/get-shit-done-redux），并把它当作一次供应链审查来对待（详见 §8）。

如果你追求极简、单工具：只在 Claude Code 里用 Superpowers。
如果你追求单一工具栈贯穿两个 IDE：只用 GSD。
如果你追求最高工程严谨度 + 双工具协同（推荐）：GSD 主干 + Claude Code 内 Superpowers 质量层。

1. 背景与需求理解

在给出方案前，先把你的实际场景拆清楚，因为选型结论高度依赖这几个约束：

约束维度 你的情况 对选型的影响
工具栈 Claude Code + Cursor，两个基础订阅，协同开发 决定性约束：是否支持多运行时
项目规模 个人中大型软件工程项目 偏向需要持久化状态、阶段化、抗上下文腐烂的方案
使用者 个人开发者 / 单人小队 两个工具的设计初衷都对口（solo / small team）
诉求 最高效合理、可复用、文档化沉淀 偏向标准化工作流 + 落盘可复用资产

关键判断：中大型项目最致命的问题是 context rot（上下文腐烂）——随着对话堆积，模型逐渐丢失早期决策、自我重复、偏离原始意图。Spec-driven development（规格驱动开发，SDD）正是为此而生：把「设计决策」写成磁盘上的文件（spec → plan → code），并在每一对环节之间插入人工评审关口。GSD 和 Superpowers 都是这条路线上的工具，只是切入的「层」不同。

2. 什么是 Spec Coding / 规格驱动开发

两个工具共享同一套底层方法论，理解它能让后续对比更清晰。SDD 的核心是三份按顺序产生的文档 + 三道评审关口：

  1. Spec（规格）：用自然语言写清「这次改动要做什么、不做什么」——支持的格式、交付方式、半成品时的行为、明确排除项。评审关口 1：在它变成计划前评审，拦截范围蔓延和「错误根因」式的方案。
  2. Plan（计划）：把规格拆成带编号的原子任务，每个任务点名文件、改动、顺序、测试。评审关口 2：在它变成代码前评审，拦截半成品实现和与代码库不一致的模式。
  3. Code（代码）：按计划一次一个任务地写出来。评审关口 3：合并前评审，拦截「读起来没问题、一遇到失败测试就崩」的计划。

它和 Claude Code 内置的 Plan Mode（连按两次 Shift+Tab）的本质区别：Plan Mode 把计划留在内存里、单轮对话内完成、无落盘、无跨阶段评审；SDD 把 spec 和 plan 作为磁盘文件持久化，每一阶段过人工评审，产物跨会话存活。这正是中大型项目能否跑得动的分水岭。

经验法则：当一次改动触及约 4 个以上文件，或「它到底该怎么表现」本身就是难点时，就该上 SDD。

3. 两大工具概览

3.1 GSD（Get Shit Done）

  • 定位：轻量但强大的「元提示（meta-prompting）+ 上下文工程 + 规格驱动开发」系统。

  • 维护现状（重要）：原作者 TÂCHES（Lex Christopherson / 网名 glittercowboy）。原仓库 gsd-build/get-shit-done 曾积累约 63.8k stars，但已停止作为活跃开发地。2026-05 起活跃开发迁移至社区治理的 open-gsd/get-shit-done-redux（详见 §8 风险）。npm 包：@opengsd/get-shit-done-redux。

  • 工作流（六命令主循环：discuss → plan → execute → verify → ship）：

    阶段 命令（连字符形式，Claude Code / Cursor 通用） 作用
    初始化 /gsd-map-codebase、/gsd-new-project 索引代码库、深度上下文采集、构建 .planning/ 结构与路线图
    讨论 /gsd-discuss-phase N 暴露「灰色地带」决策并锁定，写入 CONTEXT.md（澄清怎么实现，不扩范围）
    UI 契约 /gsd-ui-phase N 前端阶段先锁定设计契约（间距、字体、配色、文案、注册表安全）
    计划 /gsd-plan-phase N 研究 + 生成 PLAN.md + 自检
    执行 /gsd-execute-phase N 波次（wave）并行执行，原子 git 提交，每个 plan 跑在全新上下文窗口
    验证 /gsd-verify-work N 目标回溯式（goal-backward）验证 + 人工 UAT
    交付 /gsd-ship N 从已验证的工作创建 PR，收尾并准备下一里程碑

  • 内部架构：70+ 斜杠命令、30+ 专用 agent（planner / executor / verifier / code-reviewer / security-auditor 等）、90+ 内部工作流编排、持久化记忆、11 个运行时守护钩子（含 prompt 注入检测 gsd-prompt-guard.js、上下文用量监控、提交质量门）。

  • 抗上下文腐烂机制：独立 plan 在同一 wave 内并行、依赖 plan 排到后续 wave；每个 plan 跑在自己的全新 200k 上下文窗口里，零累积腐烂。

  • 里程碑 / 工作流（workstream）：/gsd-workstreams 支持对一个里程碑的不同区域并行推进——对中大型项目分模块作战很关键。

  • 多运行时支持（决定性优势）：开箱支持 Claude Code、Cursor、OpenCode、Gemini CLI、Kilo、Codex、Copilot、Windsurf、Antigravity、Augment、Trae、Qwen、CodeBuddy、Cline 等。通过 npx 安装，交互式多选运行时 + 选择 global / local 范围。

  • 配置哲学：「缺省即启用（absent = enabled）」——所有工作流特性默认开，你显式关掉不要的（如 /gsd-settings 里关 UI gate）。

3.2 Superpowers

  • 定位：一套「能真正落地的」agentic 技能（skills）框架 + 软件开发方法论。

  • 维护现状：作者 Jesse Vincent（GitHub: obra），MIT 许可，GitHub 约 194k stars（体量极大、社区活跃、治理稳定）。

  • 安装与激活：通过 Anthropic 官方插件市场一键安装：/plugin install superpowers@claude-plugins-official。一个 SessionStart 钩子会自动加载 using-superpowers 技能，开机即生效，无需逐项目配置。

  • 核心技能（自动触发，无需手动调度）：

    技能 作用
    brainstorming 苏格拉底式对话打磨设计，产出 spec 文档
    writing-plans 把已批准的 spec 转成带编号的任务清单
    subagent-driven-development 一次一个任务执行计划，测试先行（red-green-refactor），每个任务后跑一个 code-review 子代理
    requesting-code-review 合并前对完整 diff 跑独立的 code-review 子代理（冷读代码，不带父上下文的框架偏见）

  • 斜杠命令：/superpowers:brainstorm、/superpowers:write-plan、/superpowers:execute-plan。

  • 工程纪律强制：强制「红-绿-重构」TDD（测试必须先失败再实现）、四阶段调试方法论（先查根因再动手）、设计前先做苏格拉底式头脑风暴。

  • 自治执行：说「go」后启动子代理驱动的开发流程，逐任务推进、自检、评审、继续——常能连续自治工作约数小时不偏离计划。

  • 多运行时：以 Claude Code 为native；Codex 支持为实验性。不原生支持 Cursor。

  • 适用边界：最适合单仓库 solo 工作、整个代码库能装进一个 Claude Code 会话的场景；面对超大 / 多仓库时相对吃力。

一句话总结对比：GSD 是「项目级的流程操作系统」，Superpowers 是「Claude Code 里的工程师良心」。两者不在同一层，因此既可单选，也能融合。

5. 针对「Claude Code + Cursor 双订阅」环境的适配分析

这是你场景里最关键的一节。

5.1 决定性事实：只有 GSD 能贯穿两个工具

  • 你希望 Claude Code 与 Cursor 协同。协同的前提是两个工具看到同一份事实来源——即落在仓库里的 spec / plan / 状态。
  • GSD 原生支持 Cursor 运行时，命令在两个工具里都是连字符形式（/gsd-new-project、/gsd-plan-phase 1…），且 .planning/ 落盘在仓库内。于是：在 Claude Code 里 /gsd-plan-phase 产出的计划，Cursor 打开同一仓库能直接读、直接执行，反之亦然。这就是真正的「协同」。
  • Superpowers 是 Claude Code 插件，依赖其 skills / 插件市场 / SessionStart 钩子机制，在 Cursor 里不可用。它能让 Claude Code 这一侧的工程质量飞跃，但无法把这套纪律带到 Cursor。

5.2 两个工具的天然分工

结合各自特性，最顺手的协同分工是：

  • Cursor：擅长 IDE 内的高频迭代、就地补全、可视化探索、快速读改。→ 适合「读共享计划状态 + 快速探索 / 局部修改」。
  • Claude Code：擅长长程自治、多 agent、终端化重活。→ 适合「按阶段严格执行 + 验证 + 交付」，并在此叠加 Superpowers 的 TDD / code review 纪律。

两个基础订阅各自的额度（Claude Code 与 Cursor 的用量限制各自独立）也因此被合理分流：探索 / 轻量改在 Cursor 消耗，重活 / 自治执行在 Claude Code 消耗，避免单边触顶。

6. 三种方案对比

方案 A：单选 Superpowers（Claude Code only）

  • 优点：安装最简单（一条命令）、自动触发几乎零心智负担、TDD / 调试 / code review 纪律业界最强、社区与治理最稳。
  • 缺点：完全放弃 Cursor 侧的协同——Cursor 退化为普通编辑器，无法共享这套工作流；面对中大型多模块项目时，单会话假设会吃紧。
  • 适合：你愿意把主战场收敛到 Claude Code、Cursor 仅作轻量编辑器。

方案 B：单选 GSD（双工具）

  • 优点：Claude Code 与 Cursor 真正协同、状态落盘可版本化、里程碑 / workstream / 波次并行天然适配中大型项目、单一工具栈贯穿两个 IDE、心智模型统一。
  • 缺点：命令多、学习曲线较陡；TDD / code review 的「强制力」不如 Superpowers 那样深植于每个任务；需要承担 redux 分叉的供应链 / 治理风险。
  • 适合：你重视双工具协同与项目可扩展性，愿意投入学习成本，并能做好依赖审查。

方案 C：融合 —— GSD 主干 + Claude Code 内 Superpowers 质量层（推荐）

  • 思路：让两者在不同的层各司其职，而不是让它们抢同一个「头脑风暴→计划→执行」循环的方向盘。
    • GSD = 跨工具的规格 / 计划 / 状态主干：.planning/ 作为唯一事实来源，Claude Code 与 Cursor 共享。负责 macro 生命周期（discuss → plan → execute → verify → ship）、里程碑、波次并行。
    • Superpowers = Claude Code 内的执行质量层：在执行密集型阶段，借助其 TDD（红-绿-重构）、四阶段调试、冷读 code review 子代理，把单个任务的实现质量拉满。
  • 优点：兼得「双工具协同 + 中大型可扩展（GSD）」与「最强工程纪律（Superpowers）」。
  • 代价 / 注意：两者都会注入工作流指令，若同时全自动驱动会「抢方向盘」。融合的纪律是——任一阶段只让一个工具当 driver：GSD 负责阶段编排与状态，Superpowers 的技能在 Claude Code 执行阶段被「点名」使用（TDD / debug / review），而不是让它的 SessionStart 自动接管整个循环。属于进阶玩法，需要你清楚边界。
  • 适合：你（中大型项目 + 双订阅协同 + 追求最高效合理）。

7. 安装级别：用户级 vs 项目级

这是常被忽略却很关键的决策。要区分「工具本体」和「项目状态」两件事：

对象 推荐级别 理由
GSD 工具本体（命令 / agent / 技能） 用户级（global） 你要在 Claude Code 和 Cursor 两个运行时、且未来多个项目里复用；global 一次装好，避免每个项目 / 每个工具重复安装
GSD 项目状态 .planning/ 项目级，且随仓库 git 提交 它是规格 / 计划 / 决策的事实来源，必须可版本化、可回溯、可被两个工具共享；无论工具本体装哪，.planning/ 永远在项目内
GSD 项目配置 .planning/config.json 项目级，提交 每个项目的工作流开关 / 模型档位应随项目走
Superpowers 用户级（天然如此） 它是 Claude Code 官方市场插件，安装即对所有项目可用，无项目级概念

反模式提醒：不要把 GSD 工具本体只装在单个项目（local）却又指望在 Cursor 和其他项目里用——会反复缺命令。也不要把 .planning/ 放进 .gitignore——那等于丢掉了协同与可追溯的全部价值。

8. ⚠️ 必读：GSD 的治理 / 供应链风险

这是本次选型中最需要你知情决策的一点，务必读完再动手：

  • 原始仓库 gsd-build/get-shit-done（历史上约 63.8k stars）的 README 已自我声明「项目已迁移」，不再是活跃开发地。
  • 据多方公开转述：2026-05 前后，原维护者 TÂCHES（Lex Christopherson）变得不可联系、删除了社交账号；与该生态公开关联的 $GSD Solana 代币被指为 rug-pull（卷款跑路）。
  • 社区随后发布延续公告，将活跃开发迁移至 open-gsd/get-shit-done-redux（open-gsd 治理）。声明称迁移时代码与跑路前的 tree 逐位一致（bit-perfect），仅 URL 与 npm 包名变更；原作者与旧血统不再是该项目的一部分。
  • Claude Code 插件包装方 jnuyens/gsd-plugin 自 v2.43.6 起将上游指针切到 redux。

对你的行动指引：

  1. 只用社区延续分叉：open-gsd/get-shit-done-redux / npm @opengsd/get-shit-done-redux。移除任何旧的 get-shit-done-cc、@gsd-build/* 全局包。
  2. 把它当一次供应链审查：安装前过一遍仓库的近期提交与 release notes；中大型项目里，工具能跑 shell、读写代码库，信任边界要谨慎。
  3. 锁定版本：在项目里固定 GSD 版本（而非永远跟随 latest），升级前看 CHANGELOG。
  4. 善用其内建防护：GSD 自带防误提交密钥的机制，建议同时用 deny 规则禁止 agent 读取敏感文件（.env、密钥等）作为纵深防御。
  5. 风险偏好分流：若你对此类事件高度敏感，且 Cursor 协同非硬需求，可改走「方案 A：只用 Superpowers」（治理更稳）。这是完全合理的选择。

Superpowers 侧目前无同类治理事件，单一活跃维护者 + 官方市场分发，信任面更干净。

9. 最终推荐方案

GSD（Redux）为跨工具主干，Claude Code 内叠加 Superpowers 为质量层。

整体形态：

  • GSD：用户级安装到 Claude Code + Cursor 两个运行时；.planning/ 状态随项目仓库提交，成为两个工具的唯一事实来源。
  • Superpowers：用户级安装到 Claude Code，在执行密集阶段提供 TDD / 调试 / code review 纪律。
  • 分工：
    • 规划与状态（discuss / plan / verify / ship 的编排）→ GSD，两个工具皆可读写。
    • 快速探索、就地小改、读取共享计划 → Cursor + GSD。
    • 严格分阶段执行、长程自治、高质量实现 → Claude Code + GSD（执行阶段点用 Superpowers 的 TDD / review 技能）。

为什么是它而非单选：

  • 你的两个硬约束（双工具协同 + 中大型）排除了「只用 Superpowers」作为完整方案——它无法触达 Cursor、单会话假设对中大型吃紧。
  • 「只用 GSD」可行且简洁，但会浪费掉 Claude Code 这侧本可获得的、业界最强的 TDD / code review 纪律。
  • 融合用极小的额外管理成本（守住「一阶段一个 driver」的边界），换来两边的长板叠加。

何时降级为单选（务实退路）：

  • 想要最低复杂度、且能接受放弃 Cursor 协同 → 方案 A（仅 Superpowers）。
  • 对 GSD 治理风险高度敏感、又必须双工具 → 评估是否暂时接受「Cursor 仅作编辑器 + Claude Code 用 Superpowers」，等 redux 分叉信任度进一步建立后再引入 GSD。

11. 落地最佳实践

  • 范围纪律：/gsd-discuss-phase 只澄清「怎么实现」，绝不在讨论里扩功能；要加功能就开新阶段 / 里程碑。这是抑制 AI 范围蔓延的第一道闸。
  • 善用 4 文件法则：触及约 4 个以上文件、或「该怎么表现」本身是难点时，才值得走完整 SDD；更小的改动直接做，避免流程开销淹没收益。
  • 一阶段一 driver：融合方案的铁律。GSD 管编排与状态，Superpowers 在执行层管实现质量，互不抢方向盘。
  • 中大型分模块：用 /gsd-workstreams 把里程碑按区域（如 backend-api / web / infra）拆成并行工作流，对应你项目的分层架构。
  • 每阶段后清场：阶段间用 /clear + /gsd-progress --next，最大化「每 plan 全新上下文」的抗腐烂收益。
  • 冷读评审：合并前固定跑一次独立 code-review 子代理（Superpowers requesting-code-review 或 GSD gsd-code-reviewer），让评审者不带实现者的框架偏见。
  • 把决策沉淀进仓库：.planning/CONTEXT.md、PLAN.md、路线图全部提交——这与你长期偏好的「结构化、可复用文档」高度契合，未来回看 / 交接 / 复盘都受益。
  • 断点恢复：长程执行被打断时，借 GSD 的 /compact 续跑能力（插件包装支持自动恢复）继续，而非重开。

12. 风险与注意事项小结

风险 说明 缓解
GSD 供应链 / 治理 原作者失联 + 代币 rug-pull，现为社区分叉 只用 @opengsd/*、移除旧包、锁版本、读提交记录、deny 敏感文件
两工具抢方向盘 GSD 与 Superpowers 同时全自动会冲突 一阶段一 driver；执行层才点用 Superpowers 技能
学习曲线 GSD 命令 / 概念多 先跑通一个最小阶段闭环，再逐步用 workstream / 高级命令
订阅额度 双订阅各自有用量上限 探索在 Cursor、重活在 Claude Code，分流消耗
过度流程化 小改动套全流程反而变慢 4 文件法则，小事直接做
Cursor 侧能力差异 Superpowers 不覆盖 Cursor 接受 Cursor 主要承接「读共享计划 + 快速实现」，纪律由 Claude Code 侧把关
