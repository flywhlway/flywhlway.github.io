Claude Code 多智能体编排：从子代理到 Agent Teams

按 Claude Code 2.1.5x 的真实能力梳理多智能体编排：子代理字段与隔离语义、Agent Teams 研究预览、worktree 并行…

Flywhl 20 分钟 更新于 2026.09 #AI工具#开发效率#Claude Code

先读结论

  1. 多智能体首先是上下文管理手段：把高噪声的搜索、测试输出关进子代理，主会话只收结论。
  2. 子代理是向调用者汇报的工人；Agent Teams 的队友是能互发消息、共享任务列表的完整会话，token 用量随人数近似线性增长。
  3. 并行写代码的前提是文件边界清楚：用 isolation: worktree 或 --worktree 隔离工作区，用文件归属避免互相覆盖。
  4. 每种编排模式都要连同失败模式一起设计：委派消息写足上下文、规定汇报格式、用 hook 把「完成」绑定到可验证的检查。
  5. 顺序依赖强、改动小、需要频繁来回的任务，单会话更快也更便宜。

多智能体解决什么，又带来什么

Claude Code 的单个会话本身就是完整的 agent 循环：读文件、跑命令、改代码、再验证。多智能体并不会让模型更聪明，它解决的是单会话的三个结构性瓶颈：

  • 上下文污染：一次全仓搜索、一轮完整测试、一段日志排查，输出动辄几万 token。它们留在主会话里，会挤占后续推理空间，还会在自动压缩时把早期的关键约束一起压掉。子代理在独立上下文里消化这些噪声，只把结论交回。
  • 串行等待：「鉴权模块怎么管 session」「迁移脚本怎么跑」「前端怎么拿 token」三个互不依赖的问题，单会话只能一个接一个查。
  • 角色混杂：同一个会话既写代码又评审自己的代码，天然带着实现者的预设。一个只读、只看 diff、提示词不同的评审者，才算得上第二视角。

代价同样是结构性的，而且经常被低估：

代价 具体表现 缓解手段
token 成本 每个子代理从零开始读文件、建立上下文；Agent Teams 的每个队友都是完整的 Claude Code 实例，用量随人数近似线性增长 搜索类代理用小模型；控制并发数；任务结束及时关闭队友
协调开销 子代理看不到主对话历史，只能拿到主会话写的委派消息；消息写得薄，它就重复探索甚至误解目标 委派时写明路径、约束、验收标准和汇报格式
结果合并 摘要有损；并行改动撞上同一个文件；两份调查结论互相矛盾时需要裁决 按文件划分归属；用 worktree 隔离；要求结构化汇报
启动延迟 子代理需要时间收集上下文，小任务委派出去反而更慢 一句话能说清的改动不委派

选形态之前，先对照场景：

场景 推荐形态 理由
小改动、单文件修复 单会话 委派开销大于收益
大范围只读搜索、跑测试只看失败项 子代理 输出噪声大，只需要结论
三个以上互不依赖的调查 并行子代理 结果汇总即可，不需要互相讨论
调查者需要互相质疑、交叉验证 Agent Teams 队友之间能直接发消息
前端、后端、测试各自独立的新功能 Agent Teams 或多个 worktree 会话 各自持有文件，长时间并行
两种实现方案都想试 两个 --worktree 会话 完全隔离，最后比较 diff

子代理：定义、调用与隔离语义

定义文件与作用域

子代理是一个带 YAML frontmatter 的 Markdown 文件：frontmatter 是配置，正文是它的系统提示词。1.0.60（2025-07-24）起可以用 /agents 交互式创建，也可以直接写文件。存放位置决定作用域，同名时高优先级覆盖低优先级：

位置 作用域 说明
--agents 命令行 JSON 当前会话 2.0.0 引入，适合脚本里临时注入
.claude/agents/ 当前项目 提交进仓库，团队共享
~/.claude/agents/ 本机所有项目 个人通用角色
插件的 agents/ 目录 启用该插件的地方 优先级最低

tools 与 disallowedTools 的取舍：白名单适合角色边界清楚的代理，比如「只能读」；黑名单适合「除了写文件什么都能做」，好处是 MCP 工具会自动继承，不用逐个列出。

内置子代理

  • general-purpose：全部工具，承担需要既探索又修改的多步任务。

前台与后台：前台子代理会阻塞主会话，权限确认直接弹给你；后台子代理与你并行工作。运行中按 Ctrl+B 可以把当前任务转到后台（2.1.0 起 bash 命令和代理统一用这个快捷键），background: true 则让代理始终后台运行。后台运行时你不在旁边盯着，最好事先在 permissions.allow 里放行它确实需要的命令，否则它会卡在权限上或者直接被拒。

2.0.28 起 Claude 可以恢复之前的子代理继续工作，恢复后保留该子代理完整的历史。「继续刚才那个评审，这次看授权逻辑」比重新委派一个新评审便宜得多，因为不用重读同一批文件。

隔离语义：子代理能看到什么

项目 子代理是否可见 实践含义
主对话历史 否，只收到主会话写的委派消息 委派消息必须自带背景和验收标准
主会话已读过的文件 否 子代理会重读，这部分 token 是重复支出
Claude Code 默认系统提示词 否，只有定义文件正文加上工作目录等基本环境信息 正文要写清工作方法和输出格式
项目 CLAUDE.md 是 项目级规则不必在正文重复
工具 由 tools 与 disallowedTools 决定 只读角色要从工具层面去掉写能力
权限 继承主会话的权限设置，可用 permissionMode 调整 后台运行前先放行所需命令
再派生子代理 否，子代理不能嵌套 多层拆分只能由主会话完成
回到主会话的内容 只有最终那条消息 在正文里规定汇报格式和长度

最后一行决定了子代理能省多少上下文：一个子代理读了 40 个文件、跑了 10 次测试，主会话只多出它最后那段汇报。汇报格式如果不加约束，这个收益会被一份几千字的「详细报告」抵消掉。

Agent Teams：研究预览

Agent Teams 在 2026-02-05 随 Opus 4.6 一起发布（2.1.32），是研究预览，默认关闭，需要在 settings.json 或 shell 环境里开启：

组成与协作方式

组件 角色
负责人（team lead） 你正在对话的主会话，负责建团队、拆任务、分派和汇总
队友（teammates） 独立的 Claude Code 实例，各自拥有上下文窗口
共享任务列表（task list） 任务分待处理、进行中、已完成三态，可设依赖；队友既可被指派，也可自己认领
邮箱（mailbox） 代理之间的消息通道，消息自动投递，不需要轮询 
flowchart LR
    U[你] --> L[负责人会话]
    U -. 直接对话 .-> T1
    L -->|创建任务| TL[(共享任务列表)]
    TL -->|认领| T1[队友 A]
    TL -->|认领| T2[队友 B]
    TL -->|认领| T3[队友 C]
    T1 <-->|消息| T2
    T2 <-->|消息| T3
    T1 -->|完成通知| L
    T3 -->|完成通知| L

它和子代理的根本区别在通信拓扑。子代理只向调用者汇报，彼此之间不说话；队友之间可以直接发消息，你也可以绕过负责人单独给某个队友下指令。队友启动时会加载 CLAUDE.md、MCP 服务器和 Skills 等项目上下文，但不继承负责人的对话历史，负责人创建它时写的那段提示就是它全部的任务背景。

团队状态存在本地：团队配置在 ~/.claude/teams/{team-name}/config.json，任务列表在 ~/.claude/tasks/{team-name}/。

几个操作要点：

  • 显示模式：in-process 模式下所有队友都在当前终端里，按 Shift+Down 轮换选中队友（2.1.47 起只用这一个键并循环切换），选中后直接输入就是给它发消息。分屏模式给每个队友一个独立 pane，需要 tmux 或 iTerm2，可在 settings 里用 teammateMode（"in-process"、"tmux"、"auto"）选择。
  • 先计划后动手：对高风险改动，可以要求队友先在只读的计划模式下出方案，交负责人审批后再实施。
  • 复用子代理定义：「用 security-reviewer 这个 agent 类型创建一名队友」，角色定义一次，子代理和队友两用。
  • 质量门禁：2.1.33 新增两个 hook 事件。TeammateIdle 在队友即将空闲时触发，以退出码 2 结束可以把反馈发回去让它继续干；TaskCompleted 在任务被标记完成时触发，退出码 2 会阻止完成并反馈原因。
  • 催它别抢活：负责人有时不等队友就自己动手实现。看到这种情况，直接告诉它「等队友完成各自任务再继续」。

研究预览的已知限制

以下是 2 月下旬版本的限制，决定了它目前适合什么、不适合什么：

  • /resume 和 /rewind 不会恢复 in-process 队友。恢复会话后负责人可能给已经不存在的队友发消息，需要让它重新创建。
  • 任务状态可能滞后：队友忘记把任务标成完成，依赖它的任务就一直卡着，需要人工核实后更新状态。
  • 关闭慢：队友要先做完手头的请求或工具调用才退出。
  • 一个会话只有一个团队；队友不能再组建自己的团队；负责人身份不能转让。
  • 队友启动时统一继承负责人的权限模式，不能在创建时逐个设置。
  • 分屏模式不支持 VS Code 集成终端、Windows Terminal 和 Ghostty。

适用边界

适合 Agent Teams 的任务有一个共同点：参与者需要交换中间结论，而不只是交付最终结果。典型场景是研究与评审（多个视角并行，互相质疑）、竞争假设式调试（每人验证一个假设，证据不足的一方被其他人反驳），以及跨层但文件边界清楚的新功能。

不适合的情况：步骤之间顺序依赖强、多人需要改同一个文件、只需要结果不需要讨论。最后一种用并行子代理就够了，便宜得多。

并行开发与 git worktree

子代理和队友默认共享同一个工作目录。并行读没有问题，并行写就会互相覆盖文件，测试结果也会互相干扰。隔离有三条路：

  1. 手动多会话：claude --worktree feature-auth（2.1.49，简写 -w）会在 .claude/worktrees/feature-auth/ 下创建工作树和名为 worktree-feature-auth 的分支，并在其中启动会话；另开一个终端换个名字，就是第二个隔离会话。记得把 .claude/worktrees/ 加进 .gitignore。
  2. 子代理声明式隔离：在定义文件里写 isolation: worktree，子代理在临时 worktree 中工作，没有产生改动时自动清理。
  3. 原生 git：git worktree add ../app-feature-a -b feature-a，进入目录后启动 claude。不依赖任何新版本特性，所有版本都能用。

worktree 解决的只是文件层面的冲突，下面这些摩擦仍然存在：

  • 新 worktree 是干净检出：没有 node_modules，也没有被 gitignore 掉的 .env，每个 worktree 都要重新安装依赖、准备本地配置。
  • 端口、数据库、缓存目录是共享的：两个会话同时起开发服务器会抢端口，同时跑集成测试会互相污染测试库。给每个 worktree 约定端口偏移和独立的测试库名。
  • 合并仍然靠人：worktree 把冲突推迟到合并时，并没有消除冲突。拆任务时按模块划清文件归属，比事后解决冲突省力。
  • 非 git 版本控制：2.1.50 新增的 WorktreeCreate 与 WorktreeRemove hook 可以替换默认的 git 逻辑，接入其他版本控制系统。

Agent Teams 的队友目前共享负责人的工作目录，所以在团队场景里，文件归属必须在拆任务时就写进每个队友的提示里。

什么时候不要用多智能体

  • 改一个函数签名并更新 5 处调用：主会话搜一次就能改完，拆给子代理反而要把上下文讲两遍。
  • 强顺序依赖的链条：改 schema、生成迁移、改 ORM 模型、改接口，每一步都依赖上一步的产物，并行只会带来等待和返工。
  • 需要频繁来回的工作：前端样式迭代要你看效果、提意见、再改，子代理的隔离反而切断了反馈回路。
  • 多人同改一个热点文件：路由表、依赖注入容器、全局配置，并行修改造成的覆盖和冲突，比省下的时间多。
  • 瓶颈在人的评审：你一天只能认真审两个 PR，开五个并行工作者只会堆出一摞待审 diff。
  • 陌生代码库上直接并行实现：先用一个探索子代理摸清结构，再决定要不要拆、怎么拆。

成本与可观测

成本控制

  • 模型分层：纯搜索、列清单交给 haiku，需要推理的评审用 sonnet 或 opus；Agent Teams 可以在组队提示里直接要求队友使用 Sonnet。
  • 收紧汇报：子代理的最终消息全部进入主会话上下文。并行 5 个、每个汇报 2000 字，主会话就多了 1 万字，汇报长度是最容易控制的成本项。
  • 及时收尾：团队任务结束后让负责人逐个关闭队友（如「让 researcher 队友关闭」），不要让空闲的实例挂着。
  • 看数据而不是凭感觉：2.1.30 起 Task 工具的结果会附带 token 数、工具调用次数和耗时，最贵的子代理一眼可见；2.1.0 起后台代理的 token 也计入 spinner 显示的计数。会话层面用 /cost（API 计费用户的本会话花费）、/usage（订阅计划额度）、/context（上下文占用构成）和 /stats（历史统计）。

可观测

子代理的生命周期可以用 hook 记到本地文件里，事后按代理类型统计次数和耗时。SubagentStart 的输入包含 agent_id 与 agent_type，SubagentStop 的输入包含 agent_id 与 agent_transcript_path：

子代理的转录与主会话分开存放，主会话压缩不会影响它。排查「子代理为什么得出这个结论」时，顺着 agent_transcript_path 看它自己的完整推理，而不是只看主会话里那段摘要。团队层面需要看板时，用 CLAUDE_CODE_ENABLE_TELEMETRY=1 配合 OpenTelemetry 导出器，把用量汇总到已有的监控系统。

2026-09 补记：半年后的变化

  • Agent view：2.1.139（2026-05-11）以研究预览形式加入，claude agents 在一个屏幕里列出所有后台会话，按运行中、等待你输入、已完成分组，也可以直接派发新会话。正文里「多开几个 worktree 会话」的手工编排，现在可以在这里统一派发和查看。
  • Dynamic workflows：2.1.154（2026-05-28）引入，Claude 为任务编写一段 JavaScript 编排脚本，由后台运行时调度数十到上百个子代理，用 /workflows 查看。2.1.160（06-01）起触发关键词从 workflow 改为 ultracode，用自己的话提出要求仍然可以启动。它适合比本文模式一、二规模更大、需要能重复运行的编排。
  • 子代理可以嵌套了：2.1.172（06-10）起子代理默认可以再派生子代理。当前文档的默认上限是三层，可用 CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH 调整，设为 1 即关闭嵌套。正文「子代理不能嵌套」只适用于 2 月的版本。
  • Explore 不再固定用 Haiku：2.1.198（07-01）起 Explore 继承主会话模型，在 Claude API 上最高用到 Opus。想保留低成本探索，可以在项目或用户级定义一个同名的 Explore 子代理并写上 model: haiku，它会覆盖内置版本。
  • 权限继承：2.1.212（07-16）起 Task 工具的 mode 参数被废弃并忽略，子代理默认继承父会话的权限模式。需要不同的模式，就写进定义文件的 permissionMode；按当前文档，bypassPermissions 只有在主会话本身处于该模式时才对子代理生效。
  • Todo 与任务工具：2.1.233（08-14）起，TodoWrite 以及 TaskCreate、TaskGet、TaskUpdate、TaskList 在新一代模型上默认不再提供，设置 CLAUDE_CODE_ENABLE_TODO_TOOLS=1 可以恢复；2.1.268（09-10）进一步收窄为只在 Opus 4.0–4.7、Sonnet 4.0–4.6 等旧系列上默认提供。对 Agent Teams 的直接影响是：没有这组工具的代理用不了共享任务列表，只能靠消息协调。依赖任务列表管理依赖关系的团队流程，要么开启该变量，要么把任务顺序写进负责人的提示里。
