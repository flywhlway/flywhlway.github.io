第七篇 Robot Data Engine

模型（第五篇）与硬件（第六篇）就位后，决定胜负的是燃料供给系统。本篇用你最熟的武器——Kafka、Flink、ClickHouse、Iceberg、MinIO、Milvus——建机器人数据飞轮：从端侧触发回传，到湖仓组织、筛选挖掘、数据集构建、Replay 与 Evaluation，最终给出「从回传到新模型上线」的转速优化清单。这是全书里你存量优势最大的一篇：组件全是原班人马，新的只是数据形态与飞轮语义。

7.0 本篇导读

7.0.1 机器人数据与产业物联网数据的三大差异

维度 产业物联网数据 机器人数据 工程含义
形态 信号为主（结构化时序） 多模态时序：视频×N 路 + 关节序列 + 事件，强对齐 湖仓要能管「大对象+时序+对齐关系」
用途重心 运营分析、诊断 直接变成训练数据（模仿学习吃演示） 数据质量门禁 = 模型质量门禁
价值密度 较均匀 极不均匀：失败/干预片段是金矿 筛选挖掘是核心能力而非附属

一句话：产业物联网数据引擎是「分析引擎」，机器人数据引擎是「训练燃料工厂」——同一套组件，装配目标不同。

7.1 数据分层模型：先把「数据」拆开

7.1.1 五层数据模型

层 内容 载体 保留策略
L1 遥测流 5Hz 聚合状态、端侧指标 Kafka → ClickHouse 明细 7 天/聚合 90 天/小时级长存（4.8.1）
L2 事件流 任务回执、告警、干预、E-Stop、QoS 事件 Kafka → CH + PG 长存（低量高价值）
L3 片段数据 触发式 bag 片段（多模态原始） MinIO 按价值分级：训练候选长存，其余 30~90 天
L4 数据集 质检后的训练视图（LeRobotDataset） MinIO + Iceberg 元数据 版本化永久（可复现训练）
L5 衍生资产 特征/嵌入/评测集/统计报表 Milvus / Iceberg / CH 随版本管理

分层的意义：每层有独立的写入方、消费方、成本模型与治理规则——「数据平台失控」的病根几乎都是层间混用（拿 L1 当训练数据、把 L3 当日志存）。

7.1.2 一条数据的旅程（把五层串起来）

机器人抓取失败 → 端侧触发（L2 事件：grasp_failed）→ snapshot 保存前后 20 秒 bag（L3 片段）→ 边缘裁剪脱敏后回传 MinIO → 索引服务提取元数据与嵌入（7.4）→ 筛选漏斗判定「训练候选」（7.5）→ 人工补采正确演示 → ETL 进入数据集 v2026.07（L4）→ 训练出 vla-2.4 → 评测通过 → 模型 OTA。每一步都在你已有的组件上，只是编排目标是「喂模型」。

7.1.3 与产业物联网平台的映射

机器人数据层 产业物联网 备注
L1 遥测 信号时序 原样
L2 事件 告警/工单/DTC 事件 原样
L3 bag 片段 影子模式回传片段/CAN 黑匣子 体积大 2~3 个数量级
L4 数据集 智驾训练集 治理同构
L5 衍生 特征库/指标集市 原样

7.1.4 企业实践建议

数据平台立项的第一份文档就是这张五层表 + 各层的「写入方/消费方/成本/保留」四栏——它同时是架构图、预算表与治理规范。先立法后建仓，避免「先堆数据后治理」的返工（你在产业物联网数据平台上验证过的顺序）。

7.1.5 面试可能问什么

  1. 机器人数据平台怎么分层？（要点：五层模型 + 每层四栏 + 混层是失控病根）
  2. 机器人数据与产业物联网数据的差异？（要点：多模态对齐、直接变训练燃料、价值密度极不均）

7.1.6 最佳实践

  • 每层设「准入 Schema + 写入方白名单」，跨层流动只能经 ETL 作业——数据也要走「任务语义」。
  • L3→L4 的转化率（片段变成训练数据的比例）作为数据运营指标——它度量筛选与补采的健康度。

7.1.7 常见误区

  • ❌ 全量 bag 当日志长存——L3 必须按价值分级，否则存储账单三个月教做人。
  • ❌ 训练直接读 L3 原始片段——绕过 L4 版本化数据集，训练不可复现，事故不可归因。

7.1.8 Obsidian 永久笔记

  • 五层数据模型：遥测/事件/片段/数据集/衍生，每层四栏治理。
  • 数据引擎是训练燃料工厂：同一套组件，装配目标是喂模型。
  • L3 到 L4 转化率：筛选与补采健康度的运营指标。

7.2 回传链路：从机器人到湖

7.2.1 全链路架构

flowchart LR
  subgraph Robot["机器人"]
    TRG["触发引擎：错误码/干预/低置信度/新场景/随机抽样"]
    SNAP["snapshot 环形缓冲（2.21.4）"]
    CLIP["裁剪+脱敏+压缩（话题白名单）"]
  end
  subgraph Site["站点边缘"]
    EBUF["边缘缓冲与限速队列"]
  end
  subgraph Cloud["云端"]
    UPS["上传服务（分片/续传/校验，网关通道）"]
    MIO2["MinIO L3 片段区"]
    IDX["索引服务（7.4）"]
    KEV["Kafka L2 事件（元数据先行）"]
  end
  TRG --> SNAP --> CLIP --> EBUF --> UPS --> MIO2 --> IDX
  TRG -->|"事件立即上报"| KEV
  KEV -.元数据先到，片段后到.- IDX

关键设计：元数据先行——触发瞬间事件即经 MQTT/Kafka 上云（KB 级），bag 片段（GB 级）走网关文件通道慢慢传；索引服务先用事件建「占位索引」，片段到达后补全。好处：云端第一时间知道「发生了什么」，不必等数据到齐——这就是你们「告警先行、日志后到」的翻版。

7.2.2 触发策略五件套（录什么由平台定义，2.21.6 的落地）

触发器 目的 配额建议
错误码/异常 事故证据 不限额（高优）
人工干预 长尾金矿（5.4.4） 不限额
模型低置信度/动作分歧 OOD 挖掘（5.6.1） 每机每日上限
新场景指纹（场景嵌入距离大） 覆盖度扩张 每站每日上限
随机抽样 无偏基线（防「只见异常」的分布扭曲） 小比例常开

触发策略是配置制品（走配置 OTA），由数据团队按训练需求季度调整——「采什么」从此是数据战略的执行器而非工程师手感。

7.2.3 带宽账（说服所有人的一页）

假设：单片段 = 前后 20 秒 × 3 路 720p H.265 ≈ 100300MB；每机每日触发 10 片段 ≈ 13GB/机/日；万台 = 1030TB/日原始候选。结论三条：必须边缘筛选（站点边缘先做去重与粗筛，只上传候选的 2050%）；必须压缩与降采样（原始未压图像流想都别想）；夜间错峰上传（站点带宽日历，4.9 预热的反向应用）。这笔账是数据平台预算与触发配额谈判的基础。

7.2.4 可靠性：断点续传与对账

分片上传 + 每片校验 + 断点续传（对象存储 multipart 原语）；端侧与边缘各有持久化队列（断电不丢）；日终对账作业：事件流里的触发记录 vs 实际到湖片段，差集自动重传或标记丢失——4.9.4 对账四步在数据面的具体化。丢失率进数据运营指标。

7.2.5 与产业物联网平台的映射

回传链路 产业物联网 备注
元数据先行 告警先行日志后到 同款
触发五件套 影子模式触发策略 加了分歧与场景指纹
夜间错峰 车辆停车回传 站点版
日终对账 数据完整性对账 原样

7.2.6 企业实践建议

把「触发配额 + 带宽日历 + 保留策略」合并为一份**《数据采集策略》季度文档**，由数据、平台、算法三方会签——采集是三方共同的预算行为，单方调触发器是数据平台失控的起点。

7.2.7 面试可能问什么

  1. 设计机器人的数据回传链路。（要点：触发五件套、元数据先行、边缘筛选、对账）
  2. 万台机器人的带宽账怎么算？（要点：单片段体积 × 触发频次 × 规模，三条结论）

7.2.8 最佳实践

  • 片段命名与分区：site/robot_id/date/trigger_type/task_id——检索效率与成本分摊在命名时决定（2.21.8 升级版）。
  • 脱敏在边缘完成（人脸/工牌模糊化），带出站点的数据默认已合规——合规左移。

7.2.9 常见误区

  • ❌ 触发器由端侧工程师随手改——采集即预算，必须配置化+会签。
  • ❌ 只采异常不采随机基线——训练分布被「异常放大镜」扭曲，模型学出偏见。

7.2.10 Obsidian 永久笔记

  • 元数据先行：事件秒到、片段慢传、占位索引补全。
  • 触发五件套：异常/干预/分歧/新场景/随机基线。
  • 带宽账三结论：边缘筛选、压缩降采、夜间错峰。

7.3 湖仓组织：四件套各就各位

7.3.1 分工总表

组件 角色 存什么
MinIO/S3 对象底座 bag 片段、视频、数据集物理文件、模型制品（与 4.3.3 共库分桶）
Iceberg（Delta 同理） 表格式层 片段元数据表、帧级索引表、数据集清单表、血缘表——ACID + 时间旅行 + Schema 演进
ClickHouse 分析服务层 L1 遥测、L2 事件的交互式查询与大盘（4.8）
Milvus 语义层 场景/片段嵌入向量，支撑「以景搜景」（7.4.3）

心法一句：对象层管字节、表层管事实、服务层管查询、语义层管相似——你的湖仓方法论原文，机器人只是多了「对象层特别肥」这一个特征。

7.3.2 Iceberg 上的核心表设计（示意）

要点：数据集 = 清单 + 变换配置，而非拷贝——同一批 clip 可组装出多个数据集版本，存储零复制、血缘天然清晰；Iceberg 的时间旅行让「用三个月前的数据集状态复现训练」成为一条 SQL。

7.3.3 时序对齐：机器人湖仓的特色难题

多模态训练要求帧级对齐（图像帧 ↔ 关节状态 ↔ 动作标签）。方案：ETL 阶段从 bag 解出帧级索引表（clip_id, stream, frame_ts, offset），对齐规则用「最近邻 + 最大偏差阈值」（2.19.3 时间旅行的离线版）；超阈帧标记为 misaligned 并计入质检。对齐质量是数据集卡片的必填指标——训练侧最难排查的「玄学不收敛」常源于此。

7.3.4 与产业物联网平台的映射

湖仓 产业物联网 备注
四件套分工 你的湖仓栈 原文
清单式数据集 特征表引用式组装 零复制思想同款
帧级对齐表 多传感器对齐 智驾数据同款难题
时间旅行复现 数据版本回溯 Iceberg 核心价值

7.3.5 企业实践建议

分桶策略上把「模型制品桶」「L3 片段桶」「L4 数据集桶」物理分开并配不同生命周期与副本策略——三类对象的访问模式与合规要求完全不同，混桶是成本与合规的双输。

7.3.6 面试可能问什么

  1. 机器人湖仓怎么组织？（要点：四件套分工心法 + 清单式数据集 + 帧级对齐表）
  2. 为什么数据集不做物理拷贝？（要点：清单+变换配置、零复制、血缘与时间旅行）

7.3.7 最佳实践

  • 一切表带 model_ver / robot_id / site_id 三键——与 4.8.2 日志三键呼应，跨域联查免 JOIN 灾难。
  • 对齐阈值与质检规则版本化——数据处理逻辑也是「制品」。

7.3.8 常见误区

  • ❌ 用文件目录约定代替表格式层——没有 ACID 与演进能力的「湖」三个月变沼泽。
  • ❌ 帧对齐放到训练脚本里现做——每个训练任务各对齐一遍，慢且不一致。

7.3.9 Obsidian 永久笔记

  • 湖仓四件套心法：对象管字节、表管事实、服务管查询、语义管相似。
  • 数据集是清单不是拷贝：clip 引用 + 变换配置 + 时间旅行复现。
  • 帧级对齐表：TF 时间旅行的离线版，对齐质量进数据集卡片。

7.4 索引与检索：让 bag 变成可搜索资产

7.4.1 三级索引

元数据索引（Iceberg clip_meta：谁/何时/何机/何触发/多大）；事件索引（片段内的结构化事件时间线：错误码、任务阶段、干预点——支持「跳到干预前 5 秒」）；语义索引（Milvus：片段/关键帧嵌入，支持以景搜景与文本搜景）。三级对应三类问句：「找哪台机哪天的」「找发生了什么的」「找长得像这样的」。

7.4.2 索引流水线

flowchart LR
  ARR["片段到湖（7.2）"] --> META["解析 bag → clip_meta 入表"]
  META --> EVT["事件抽取 → 事件时间线表"]
  EVT --> KEYF["关键帧抽取（触发点/阶段切换/等间隔）"]
  KEYF --> EMB["视觉编码器出嵌入 → Milvus"]
  EMB --> CAP["可选：VLM 生成片段描述 → 文本可搜"]
  CAP --> RDY["状态置 indexed，进筛选漏斗（7.5）"]

VLM 自动描述（「机械臂在货架第三层抓取蓝色料盒时打滑」）是检索体验的质变点——它把「以文搜景」变成现实，成本按关键帧计，值得花。

7.4.3 以景搜景：数据挖掘的放大器

场景：模型在「反光地面」上频繁失败 → 取一个失败片段的嵌入 → Milvus 近邻检索出全机队历史上的同类场景 → 一次性打包成「反光地面」专项数据集与评测集。一个 corner case 变成一个 case 家族——这是智驾数据挖掘的当家能力，你把它带进机器人域即可。

7.4.4 与产业物联网平台的映射

索引检索 产业物联网/智驾 备注
三级索引 日志索引+事件索引+场景库 语义层是增量
以景搜景 corner case 挖掘 当家能力平移
VLM 描述 数据自动标注 新工具，老思路

7.4.5 企业实践建议

给数据团队做一个「数据检索台」（三级索引统一查询界面 + 片段预览播放器）——它是数据平台的「门面产品」，直接决定算法团队对平台的口碑；预览播放器读 MCAP（Foxglove 内嵌或自研），不必等下载。

7.4.6 面试可能问什么

  1. 如何让 PB 级 bag 可被检索？（要点：三级索引三类问句 + 索引流水线 + VLM 描述）
  2. 以景搜景的价值？（要点：case 变 case 家族，专项数据集与评测集一键成型）

7.4.7 最佳实践

  • 嵌入模型版本化并支持重建索引——换编码器 = 换语义空间，必须可重放。
  • 检索结果一键成集（勾选 → 生成 dataset_manifest 草案）——检索到数据集的路径越短，飞轮越快。

7.4.8 常见误区

  • ❌ 只建元数据索引——「找长得像的」这类最有价值的问句无解。
  • ❌ 全帧入向量库——按关键帧抽样，成本与召回的平衡点在触发点附近。

7.4.9 Obsidian 永久笔记

  • 三级索引三类问句：元数据/事件/语义 ↔ 找哪台的/找发生了什么/找长得像的。
  • 以景搜景：一个 corner case 变一个 case 家族。
  • 检索一键成集：从检索到 dataset_manifest 的最短路径。

7.5 筛选与挖掘：从片段到训练候选

7.5.1 四级漏斗

flowchart LR
  F1["① 机械质检（自动）：完整性/对齐/频率/时长"] --> F2["② 内容粗筛（自动）：去重/静止剔除/遮挡检测"]
  F2 --> F3["③ 价值判定（半自动）：触发类型加权 + 场景稀缺度 + 模型分歧度"]
  F3 --> F4["④ 人工终审（抽样）：标注成功失败/干预点/补采需求"]
  F4 --> OUT["训练候选池（curated）"]
  F1 -.约30%淘汰.-> X1[废弃]
  F2 -.去重合并.-> X2[归档]

漏斗的经济学：①②全自动且便宜，把人工（④，最贵）只花在③筛出的高价值样本上。转化率与各级淘汰原因分布是数据运营周报的固定栏目——淘汰原因的分布变化往往先于故障暴露端侧问题（例如「对齐超阈」突增 = 某批设备时钟漂了）。

7.5.2 挖掘五策略（主动找数据，而非等触发）

失败家族扩展（7.4.3 以景搜景）；分歧挖掘（影子并跑的动作分歧 Top 片段，5.6/4.3.6 的副产品）；覆盖度缺口分析（场景嵌入聚类，找「训练集里没有、现场里常见」的簇）；难例回流（评测集里模型持续失败的场景，反向到湖里找同类）；新品/新场景冷启动（新 SKU 上线前定向采集任务——用 4.7 的 Fleet 任务面下发「采集任务」）。五策略共同点：都以检索与嵌入为地基——7.4 建得好，挖掘就是查询。

7.5.3 质量门禁：数据的准入测试

进入 L4 前的硬门禁清单：帧对齐率 ≥ 阈值、动作范围合法（无超限位样本）、时间戳单调、标注完备（成功/失败/干预点）、脱敏完成、许可与来源可追溯。门禁结果写入 quality_flags（7.3.2）。把数据当代码对待：有 lint、有测试、有 review、有版本——这句话值得贴在数据团队墙上。

7.5.4 与产业物联网平台的映射

筛选挖掘 智驾数据 备注
四级漏斗 数据清洗+价值分级 人工只花在刀刃
难例回流 corner case 闭环 同款
覆盖度缺口 场景库缺口分析 嵌入聚类实现
数据当代码 数据质量工程 你的主张，这里更刚需

7.5.5 企业实践建议

给④人工终审建「标注工作台」时优先做快捷键与预跳转（自动跳到干预点前 5 秒）——标注效率的瓶颈从来不是工具功能多少，而是每条片段的处理秒数；把「单片段终审耗时」做成指标并持续压缩。

7.5.6 面试可能问什么

  1. 数据筛选怎么设计？（要点：四级漏斗 + 经济学 + 淘汰原因分布的告警价值）
  2. 除了被动触发还怎么找数据？（要点：挖掘五策略，共同地基是检索与嵌入）

7.5.7 最佳实践

  • 每个门禁规则可解释、可复核、版本化——被拒数据要能回答「为什么」，否则算法团队不信任漏斗。
  • 淘汰不等于删除：机械质检废弃项短存 7 天供抽查，防止门禁 bug 静默吞金矿。

7.5.8 常见误区

  • ❌ 人工审全量——成本爆炸且质量反降（疲劳标注）；人工只审③的产出。
  • ❌ 门禁只看单条不看分布——分布漂移（某站点样本占比失衡）是更隐蔽的毒药。

7.5.9 Obsidian 永久笔记

  • 四级漏斗：机械质检→内容粗筛→价值判定→人工终审，人工只花在刀刃。
  • 挖掘五策略：失败家族/分歧/覆盖缺口/难例回流/冷启动定向采集。
  • 数据当代码：lint、测试、review、版本，一个不能少。

7.6 数据集与血缘：可复现的燃料

7.6.1 数据集构建流水线

dataset_manifest 草案（检索一键成集/漏斗产出）→ 变换配置（对齐/裁剪/重采样/归一化统计量计算）→ ETL 作业（Flink/Spark 批）→ LeRobotDataset 物理化（5.4.3 训练视图）→ 数据集卡片生成 → 注册进血缘。两个工程要点：归一化统计量在这里诞生（然后随模型制品四件套走，6.2.6——闭环了）；数据集不可变：发现问题发新版本，绝不原地改（与制品不可变同一纪律，4.3.3）。

7.6.2 血缘五节点

flowchart LR
  C["clip（L3 片段）"] --> D["dataset vX（L4 清单）"]
  D --> T["training run（超参+代码版本+算力记录）"]
  T --> M["model vY（注册表 4.10.3）"]
  M --> P["deployment（哪些机型/站点/灰度环，4.3）"]
  P -.线上失败片段.-> C

血缘打通后，两类高价值问题变成一次查询：正向追溯「这个数据集训出的模型都部署在哪」（数据合规召回的技术前提——某片段被要求删除时，能定位受影响的模型与部署）；反向归因「线上这次失败，训练集里有没有同类场景」（有=模型问题，没有=数据缺口，责任与行动立判）。

7.6.3 Feature Store 的机器人对应物

机器人域没有经典的「在线特征服务」刚需（VLA 端到端吃原始观测），但 Feature Store 的两个思想完全成立：「统计量商店」——各数据集/机型/场景的归一化统计量、动作分布、场景分布集中管理版本化（防 5.3.2 的统计量漂移事故）；「嵌入商店」——Milvus 里的场景嵌入即「离线特征」，供挖掘与评测复用。名字不重要，**「加工产物集中版本化」**的纪律才是 Feature Store 的本体。

7.6.4 与产业物联网平台的映射

数据集血缘 你的经验 备注
血缘五节点 数据→模型→部署血缘 加了反向归因回路
数据集不可变 制品不可变 同一纪律
统计量商店 Feature Store 元数据 思想平移
合规召回 数据删除权落实 血缘是技术前提

7.6.5 企业实践建议

血缘别单独立项建「血缘系统」——把五节点的关联键（clip_id/dataset_id/run_id/model_ver/deploy_id）作为各系统的必填外键，血缘查询用 Iceberg 联表实现。轻实现重纪律，三个月可用；反之「血缘平台」项目常常一年不落地。

7.6.6 面试可能问什么

  1. 训练如何做到可复现？（要点：不可变数据集 + 清单式 + 时间旅行 + 血缘五节点）
  2. 数据合规删除怎么落实？（要点：正向追溯定位受影响模型与部署，重训或豁免流程）

7.6.7 最佳实践

  • 数据集卡片自动生成并强制字段（来源分布/对齐率/许可/统计量指纹）——5.4.9 的升级版，无卡不训练。
  • training run 记录环境指纹（镜像、代码 commit、超参、随机种子）——复现的最后一公里。

7.6.8 常见误区

  • ❌ 「先训起来，血缘以后补」——事后补血缘的成本是事前的十倍且永远补不全。
  • ❌ 统计量散落在训练脚本里——集中进统计量商店，随制品四件套分发。

7.6.9 Obsidian 永久笔记

  • 血缘五节点：clip→dataset→run→model→deployment，外键即血缘。
  • 数据集不可变：发现问题发新版，绝不原地改。
  • 统计量商店：Feature Store 思想在机器人域的本体。

7.7 Replay 与 Evaluation：飞轮的质检环

7.7.1 三种 Replay

类型 做法 解决什么
数据回放 bag –clock 时间线重演（2.21.3） 事故复现、人工分析、演示
算法回放（开环） 新模型消费历史观测，只比输出不执行 便宜的大规模回归：新旧模型在同一历史上的动作分歧分布
闭环重放（仿真） 场景重建进仿真器，模型闭环跑（第八篇） 开环回放答不了的「后续会怎样」

开环回放的局限必须讲透：模型输出不同 → 后续状态本应不同 → 但历史观测不会变——分歧只能提示风险，不能判定优劣。所以三种 Replay 是递进关系而非替代关系，闭环问题最终交给仿真与真机。

7.7.2 评测分层与评测集治理

评测体系 = 第五篇三级评测（离线→仿真→影子真机）的数据侧实现。评测集治理四条：评测集与训练集物理隔离（清单级互斥校验，防泄漏——数据版的「测试不碰生产」）；评测集分族（按任务族/场景族/难度分层出分，总分掩盖问题）；难例持续入集（7.5.2 难例回流的归宿）；评测集也版本化（模型对比必须锁同版评测集，否则数字不可比——5.2.9 的教训制度化）。

7.7.3 评测流水线（自动化到「一键出报告」）

模型候选 → 开环回放（全量历史分歧报告）→ 仿真基准（第八篇场景包，分族出分）→ 报告聚合（与上一版对比、与门禁对比）→ 结论：进影子 / 打回。整条流水线是 CI 化的：模型提交即触发，报告机器可读（6.7.8 的原则）——评测从「算法团队自证」变成「平台流水线裁决」，这是平台中立性的体现。

7.7.4 与产业物联网平台的映射

Replay/评测 智驾 备注
三种 Replay 日志回放/开环回灌/闭环仿真 完全同构
评测集隔离与分族 智驾评测集治理 同款纪律
CI 化评测 回归流水线 平台裁决

7.7.5 企业实践建议

先建开环回放，再建仿真闭环：开环回放只需要湖仓与推理服务（都已有），两周可上线并立即产生价值（每个新模型的全量历史分歧报告）——用最便宜的 Replay 先把「模型对比有据可依」立起来，仿真闭环（第八篇）随后补位。

7.7.6 面试可能问什么

  1. 三种 Replay 的区别与递进关系？（要点：数据/开环/闭环；开环分歧只提示不判定）
  2. 评测集怎么治理？（要点：隔离/分族/难例入集/版本化四条）

7.7.7 最佳实践

  • 分歧报告按场景族聚类展示——「哪类场景分歧大」比「平均分歧多少」有用十倍。
  • 每次影子/灰度破线事件自动生成「评测集候选」——线上事故是评测集的最好来源。

7.7.8 常见误区

  • ❌ 拿开环分歧小当「新模型更好」的证据——它只说明「行为像旧模型」，可能恰恰是没进步。
  • ❌ 评测集常年不更新——模型在陈旧考卷上刷高分，线上照样翻车。

7.7.9 Obsidian 永久笔记

  • 三种 Replay 递进：数据回放/开环回放/闭环仿真，分歧只提示不判定。
  • 评测集四条治理：隔离、分族、难例入集、版本化。
  • 先开环后闭环：两周上线开环回放，先让对比有据可依。

7.8 机器人数据飞轮：全图与转速

7.8.1 数据飞轮完整图（全书承诺的交付物）

flowchart TB
  A["① 机队部署：模型 vX 运行（第四、六篇）"] --> B["② 触发采集：五件套触发 + 定向采集任务（7.2）"]
  B --> C["③ 回传入湖：元数据先行 + 片段慢传 + 对账（7.2）"]
  C --> D["④ 索引：元数据/事件/语义三级（7.4）"]
  D --> E["⑤ 筛选挖掘:四级漏斗 + 五策略（7.5）"]
  E --> F["⑥ 补采标注：遥操作补齐正确演示（5.4.2）"]
  F --> G["⑦ 数据集：清单式版本化 + 卡片 + 血缘（7.6）"]
  G --> H["⑧ 训练：预训练+微调（云 GPU）"]
  H --> I["⑨ 评测：开环回放→仿真→影子（7.7 / 第八篇）"]
  I --> J["⑩ 模型 OTA：灰度环+门禁+自动回滚（4.3）"]
  J --> A
  I -.打回.-> E
  J -.破线回滚+现场包.-> B

十环节对照 5.8.1 的九环节 Pipeline：Pipeline 是「一个模型的旅程」，飞轮是「无数次旅程的循环」——本图多出的 ②③④⑤⑥ 正是数据引擎的主场，也是本篇存在的意义。

7.8.2 转速度量：一个指标统领全篇

飞轮转速 = 从「线上触发产生」到「针对性新模型全量上线」的天数（5.8.7 的第一性指标在此定义）。拆解为环节耗时：回传延迟（②③）+ 索引筛选（④⑤）+ 补采标注（⑥）+ 数据集构建（⑦）+ 训练（⑧）+ 评测（⑨）+ 灰度（⑩）。每环节设 SLO 并周报——瓶颈几乎永远在 ⑥补采标注 与 ⑨评测排队，而不是训练算力（管理层直觉常常相反，用数据纠正它）。

7.8.3 转速优化清单（按 ROI 排序）

  1. 检索一键成集（7.4.7）：从「发现问题」到「数据集草案」压到分钟级。
  2. 开环回放前置（7.7.5）：评测排队最便宜的解药。
  3. 标注工作台的秒级优化（7.5.5）：单片段终审耗时减半 = ⑥环节产能翻倍。
  4. 定向采集任务化（7.5.2）：冷启动与缺口补齐不再等自然触发。
  5. 评测/灰度并行化：影子评测与下一环灰度流水线化（4.3.6 的环与烘烤重叠推进）。
  6. 血缘外键化（7.6.5）：归因从「开会两小时」变「查询两秒」。

7.8.4 与产业物联网平台的映射

飞轮十环节 ≈ 智驾数据闭环全流程；转速指标 ≈ 「corner case 到 OTA 的周期」。你在数据平台的全部运营方法论——SLO 化、瓶颈分析、周报驱动——原样适用。1.6.2 的判断在此闭环：算法收敛后，转速就是公司的核心竞争力，而转速是纯粹的平台工程。

7.8.5 企业实践建议

把 7.8.1 全图贴在数据/平台/算法三个团队的共享看板顶端，每个环节标注当前 SLO 与实际值——飞轮图不是汇报插图，是三团队的共同作战地图；每季度用它做一次瓶颈复盘并重排 7.8.3 的投资顺序。

7.8.6 面试可能问什么

  1. 画出机器人数据飞轮并指出瓶颈。（要点：十环节 + 转速定义 + 瓶颈在补采标注与评测排队）
  2. 如何把转速从月级压到周级？（要点：优化清单前三项 + 环节 SLO 化）

7.8.7 最佳实践

  • 转速指标分任务族统计——「抓取类 12 天、导航类 30 天」比一个总数可执行得多。
  • 每次转速改善写成案例归档——平台团队的价值叙事由这些案例构成。

7.8.8 常见误区

  • ❌ 给训练堆 GPU 来「加速飞轮」——瓶颈不在 ⑧，钱花错了地方。
  • ❌ 飞轮各环节分属不同团队却无共同指标——转速必须是跨团队的北极星。

7.8.9 Obsidian 永久笔记

  • 数据飞轮十环节：Pipeline 是一次旅程，飞轮是循环。
  • 转速定义：从线上触发到针对性新模型全量上线的天数。
  • 瓶颈在补采与评测：不在训练算力——用数据纠正直觉。

7.9 本篇总结

7.9.1 十条核心结论

  1. 机器人数据引擎是「训练燃料工厂」：组件原班人马，装配目标换成喂模型。
  2. 五层数据模型（遥测/事件/片段/数据集/衍生），每层四栏治理，混层是失控病根。
  3. 回传三纪律：元数据先行、边缘筛选、夜间错峰；触发五件套配置化并三方会签。
  4. 湖仓四件套心法：对象管字节、表管事实、服务管查询、语义管相似。
  5. 数据集是清单不是拷贝：零复制、时间旅行、血缘天然清晰。
  6. 三级索引答三类问句；以景搜景把一个 corner case 变成一个 case 家族。
  7. 四级漏斗把人工花在刀刃上；数据当代码：lint、测试、review、版本。
  8. 血缘五节点靠外键不靠平台；数据集与评测集都不可变、都版本化。
  9. 三种 Replay 递进：开环分歧只提示不判定，闭环问题交给仿真与真机。
  10. 飞轮转速是第一性指标，瓶颈在补采标注与评测排队——不在训练算力。
