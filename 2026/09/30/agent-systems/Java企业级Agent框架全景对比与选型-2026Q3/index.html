0. 执行摘要（TL;DR）

0.1 七条核心判断

  1. 行业阶段变化：2026 年 Java Agent 框架已从“LLM 调用封装期”进入“Agent Harness（运行时工程）期”。竞争焦点从“能不能调模型、能不能调工具”转向“能不能无状态水平扩展、会话可恢复、工具执行可隔离可审批、上下文可压缩、协议可互通”。
  2. 四大主力已明显分化，不再是同质竞争：
    • Spring AI = Spring 官方的“AI 标准基座层”（模型/工具/MCP/RAG/可观测抽象），2.0 GA 于 2026-06-12 发布，基线 Spring Boot 4；官方高层 Agent 抽象尚未就位——官方计划 2026 年 11 月以实验项目形式发布 Spring AI Agents，2027 年中并入 3.0。
    • Spring AI Alibaba = “Graph 工作流 + 阿里云/Nacos 生态集成层”，最新正式版 1.1.2.2（2026-03-10，基于 Spring AI 1.1.2 / Boot 3.5），2.0 线仅有 M1.1 预览；官方已明确“Workflow 型选 SAA、Agentic 型选 AgentScope”，并规划底层全面接入 AgentScope，处于内核转型期。
    • AgentScope Java = “Agent 原生的生产级 Harness 运行时”，2.0 GA 于 2026-07-10 发布，具备无状态 Agent、28 类事件流、三态权限 + HITL、五阶段中间件、Workspace/沙箱、分布式后端、A2A/MCP/AG-UI、四层 Skill 体系，是当前 Java 生态中运行时能力最完整的框架；代价是 API 变动激进、RAG 与长期记忆在 v2 中重写。
    • LangChain4j = “框架无关、集成面最广的通用库”，社区规模最大（约 13.1k Star），月度发布并维护多条补丁分支；1.20 引入实验性非阻塞 AI Service 与可选 Jackson 3；agentic 模块功能丰富但版本号仍为 beta。
  3. 基线迁移是前置条件：Spring Boot 3.5 / Spring Framework 6.2 开源支持已于 2026-06-30 结束。所有 Spring 系选型在 2026 下半年都绕不开 Boot 4 + Jackson 3 + JSpecify 迁移，这直接影响 SAA 稳定线（仍绑定 Boot 3.5）的可用性评估。
  4. 协议已成为解耦的真正抓手：MCP（工具）、A2A（Agent 间）、AG-UI（前端事件）、OpenTelemetry（观测）四类协议在主流框架中已基本普及，平台设计应以协议为契约、框架为可替换实现。
  5. 没有“一个框架打天下”的最优解：业务嵌入视角 Spring AI / LangChain4j 得分最高，平台运行时视角 AgentScope Java 得分最高（见第 6 章双权重评分）。
  6. SAA 并未“停更”，但节奏明显放缓：main 分支持续有提交，但半年无正式版、2.0 预览仍基于 Spring AI 2.0.0-M1（上游已发布 2.0.1 GA 与 2.1.0-M1），新平台不宜把它作为唯一长期内核。
  7. Kotlin/多端方向出现新变量：Koog 1.0（承诺稳定模块一年内无破坏性变更）与 ADK for Kotlin 1.0（Android 端侧推理扩展）为车机/边缘侧 Agent 提供了 JVM 选项，值得纳入观察。

0.2 一句话推荐

以“协议契约 + 双引擎”构建企业 Agent 平台：
Spring AI 2.x 作为全公司 Java AI 应用的默认基座（模型接入、工具、MCP、RAG、可观测）；
AgentScope Java 2.x 作为平台托管的自主型、长任务 Agent 运行时（会话、沙箱、权限、分布式恢复）；
确定性流程编排按项目基线选择 SAA Graph（存量 Boot 3 项目，锁版本）或 LangGraph4j / 持久化工作流引擎（新建 Boot 4 项目）；
LangChain4j 作为 Quarkus / 非 Spring 团队的指定框架与集成补充；
全部通过 MCP / A2A / AG-UI / OTel 解耦，并在模型侧以统一 AI 网关收敛凭证与路由，保证任一框架可在 12 个月内被替换。

2.2 五个关键技术趋势

  1. 工具调用循环“外置化、可组合化”
    早期框架把工具调用循环写死在各模型实现内部，无法插入审批、重试、审计、工具检索等横切逻辑。2026 年主流框架都把循环提升为一等公民：Spring AI 2.0 把工具循环放进 Advisor 链（ToolCallingAdvisor），AgentScope 2.0 用 onReasoning / onActing / onModelCall 五阶段中间件包裹 ReAct 循环，SAA 用 Hook + Interceptor，LangChain4j 用 Guardrail + AgentListener。

  2. 协议标准化

    • MCP：Spring AI 2.0 随 MCP Java SDK 2.0 支持 2025-11-25 规范，Streamable HTTP 取代 SSE 成为默认；LangChain4j 1.19 已实现 2026-07-28 规范的 MCP Client，Spring AI 也在推进该规范。
    • A2A：A2A Java SDK 已越过 1.0 进入 1.2.0.Final，SAA、AgentScope、LangChain4j 均提供 A2A 集成，Nacos 承担 Agent 注册发现。
    • AG-UI：AgentScope Java 已对齐 AG-UI 事件规范，面向前端渲染 Agent 过程。

  3. Agent Skills 成为新的能力封装单元
    按“描述常驻、正文按需加载”的渐进式披露理念组织能力。SAA 1.1.2.0 在 ReactAgent 中集成 Skills；AgentScope 2.0 提供 Classpath / 文件系统 / Nacos / Marketplace 四层来源并支持“提议→筛选→晋升”的自进化闭环；Spring AI 社区项目 spring-ai-agent-utils 提供符合 AgentSkills 规范的实现。

  4. 上下文工程工程化
    从“简单滑动窗口”演进为：结构化压缩（保留目标/状态/发现/下一步）、超大工具结果落盘只留占位符、工具检索（数百工具按需暴露）、推理内容保真回放（Spring AI 2.1 的 ReasoningPart + 不透明签名载荷）。

  5. 平台基线整体换代
    Spring Boot 4 / Spring Framework 7 / Jackson 3 / JSpecify 空安全成为 Spring 系新基线；LangChain4j 提供 Jackson 3 可选；非阻塞化方面，AgentScope 与 SAA 原生基于 Reactor，LangChain4j 1.20 刚引入实验性非阻塞 AI Service，Spring AI 则同时支持阻塞（适配虚拟线程）与 Reactor 流式。

2.0 的三项关键设计升级：

  1. 统一工具调用（Unified Tool Calling）：1.x 时代每个 ChatModel 内部各自实现工具循环，外部无法拦截；2.0 由 ChatClient 自动注册 ToolCallingAdvisor 统一实现“调用→执行→回填”全回合，Advisor 链支持循环重入，同一机制驱动工具循环、结构化输出重试循环与评估循环。需要逐轮控制时可关闭自动循环、手工驱动。
  2. 面向数百工具的渐进披露：ToolSearchToolCallingAdvisor 对全部工具建立会话级索引，由模型按需检索相关工具，而非每次请求携带全部工具定义——官方配套文章称该架构可显著降低 Token 消耗（社区周报引用为最高约 64%，属厂商口径）。
  3. 结构化输出自纠：即便开启原生结构化输出，模型仍可能返回不合规 JSON，StructuredOutputValidationAdvisor 在校验失败时自动纠正重试。

2.0 的“做减法”：核心只保留 OpenAI（统一为官方 SDK 实现，可接入 OpenAI 兼容协议的模型）、Anthropic（官方 SDK，可接入 Anthropic 兼容协议的模型如 MiniMax）、Amazon Bedrock、Google GenAI、Mistral、DeepSeek、Ollama；OCI 生成式 AI 与 Azure Cosmos DB 改由 Oracle、Microsoft 厂商自行维护。对国内用户的含义：通义千问、GLM、Kimi 等不在核心内，需通过 OpenAI/Anthropic 兼容端点或 SAA Extensions 中的 DashScope 实现接入；DeepSeek 保留原生模块。

MCP 一体化：

  • @McpTool / @McpResource / @McpPrompt 注解并入核心，一个方法注解即可把 Spring Bean 暴露为 MCP 能力；统一的 McpSyncRequestContext / McpAsyncRequestContext 提供日志、进度、采样、征询（elicitation）入口。
  • WebMVC/WebFlux 传输实现从 MCP SDK 迁回 Spring AI，发布节奏与框架一致；Streamable HTTP 为默认，其无状态变体以牺牲双向通信换取远程部署的水平扩展；STDIO 保留用于本地进程集成。
  • 企业特性：Micrometer Span、OTel 兼容指标；OAuth 2.0 与 API Key 安全由社区项目 mcp-security 提供（9 月 0.1.14 增加 Origin 校验等加固）。

2.1.0-M1 的方向信号：

  • MessagePart：AssistantMessage / UserMessage / ToolResponseMessage 内容改为有序的 TextPart / ReasoningPart / ToolCallPart / ToolResultPart / MediaPart / UnknownPart 列表，推理签名等不透明载荷可原样回放——这是为“推理模型 + 工具循环”的长链路 Agent 打地基。
  • OpenAI Responses API：新增无状态的 OpenAiResponsesChatModel，通过 spring.ai.openai.chat.api=responses 一键切换；官方说明在较新的 OpenAI 旗舰模型上，推理强度与工具调用组合需走 Responses 端点。
  • 当前限制：仅 Responses 模型原生产出 MessagePart；除内存实现外，ChatMemory 仓库暂不持久化 MessagePart（计划在 2.1.0-RC1 解决）。

核心设计要点：

  1. 双层 Agent：ReActAgent 是无状态推理内核，所有单次调用的可变状态通过 Reactor Context 传播，一个实例可并发服务多个 (userId, sessionId)；HarnessAgent 通过中间件与工具包通道叠加 Workspace、记忆、沙箱、子 Agent、Skill、Plan Mode，不改动推理循环本身。
  2. 统一消息与事件流：ContentBlock 消息模型（Text/Data/ToolUse/ToolResult/Hint 等）+ 28 类类型化事件，前端可实时跟随文本增量、工具调用、用户确认等生命周期事件，Agent 执行因此可观测、可交互、可中断。
  3. 权限与 HITL 一等公民：PermissionEngine 基于静态规则、工具类型与入参内容分析给出三态决策，敏感操作自动进入审批；审批恢复时发出可与请求关联的确认结果事件；子 Agent 继承父级拒绝规则与 Plan Mode。
  4. 上下文工程：结构化压缩（保留任务目标、当前状态、关键发现、下一步）；超大工具结果自动卸载到磁盘、上下文只保留占位符；文件工具强制“先读后改”。
  5. Workspace 抽象：把“Agent 做什么”与“在哪里执行”解耦，本地、Docker、Kubernetes、E2B 沙箱统一接口，内置预热池（亦服务于并行 RL Rollout 场景）。
  6. 企业级分布式：一行配置 DistributedBackend（Redis/OSS/MySQL/PostgreSQL/COS）；状态按 (userId, sessionId) 自动分区；跨副本会话恢复、沙箱状态快照、子 Agent 跨副本路由。
  7. 协议互通：内置 A2A、MCP，适配 AG-UI；A2A 可配合 Nacos Agent Registry 自动注册发现。

3.3.4 1.x → 2.0 的破坏性变更（迁移必读）

  • Pipeline / SequentialPipeline / FanoutPipeline / MsgHub 被移除，改用中间件 + 子 Agent + 事件流表达多智能体协作。
  • Memory 体系与 Session 旧接口被 AgentState + AgentStateStore 取代；hook 包整体迁移到 Middleware（旧 Hook 暂经桥接兼容）。
  • RAG（Knowledge / RAGMode）与长期记忆模块在 v2 中被标记废弃并按新架构重写，官方建议新代码不要依赖。
  • 旧的 coding/file 工具因缺少工作区与权限隔离被废弃，改用 Harness 等价工具。
  • 模型提供商从 core 拆出为独立 agentscope-extensions-model-*，需显式引入依赖。

4.4 共存与冲突分析

  1. Spring AI 2.0 GA × SAA 2.0-M1.1：SAA 预览基于 Spring AI 2.0.0-M1，而 M1 → GA 期间 Options 改为不可变 Builder、Provider 模块重组、MCP 包路径迁移，二者 API 不兼容，同一应用内无法共存。
  2. Jackson 2 × Jackson 3：两者包名不同（com.fasterxml.jackson 与 tools.jackson）可在类路径共存，但会带来双份序列化配置、双份模块注册与体积膨胀；Boot 4 应用中引入 LangChain4j 时建议启用 langchain4j-jackson3 收敛。
  3. Reactor × 虚拟线程：AgentScope 与 SAA Graph 为 Reactor 原生；Spring AI 与 LangChain4j 以阻塞 API 为主（可配合虚拟线程）。在同一进程混用时需警惕在 NIO 线程上 block()（AgentScope 2.0 GA 专门修复过此类问题）以及 Reactor Context 与 OTel Context 的传播断链。
  4. 双模型层重复：Spring AI 与 AgentScope 各有模型抽象，同一平台内并用时，建议以统一 AI 网关（OpenAI 兼容协议）收敛凭证、路由、限流与审计，两套框架只配置网关地址，避免密钥与路由规则双维护。
  5. MCP SDK 版本收敛：Spring AI 2.0 绑定 MCP Java SDK 2.0；同进程引入其他依赖 MCP SDK 的框架时需做依赖收敛检查（mvn dependency:tree + Enforcer 规则）。
  6. 推荐部署形态：不同框架以独立微服务部署，通过 MCP（工具）/ A2A（Agent）/ HTTP+SSE/AG-UI（前端）互通，而非在一个 JVM 内混装多个 Agent 框架。

8.1 设计原则

  1. 协议即契约：工具统一走 MCP，Agent 间统一走 A2A，前端统一走 AG-UI/SSE，观测统一走 OTel GenAI 语义约定——框架只是实现，12 个月内可替换。
  2. 模型收口到 AI 网关：所有框架只认一个 OpenAI 兼容端点，凭证、路由、限流、配额、内容安全、审计在网关层统一完成，消除多框架的“双模型层”问题。
  3. 状态外置、实例无状态：会话、Checkpoint、记忆、沙箱快照全部外置（Redis/PostgreSQL/对象存储），Agent 实例可随时扩缩与滚动发布。
  4. 工具默认拒绝：高风险工具（写操作、下发指令、资金/车控）默认“需确认”或“拒绝”，审批事件可追溯。
  5. 两类负载分开部署：AI 增强型业务服务（嵌入现有微服务，低延迟）与 Agent 原生长任务服务（独立运行时集群，可沙箱、可长时运行）分属不同资源池。
  6. 配置中心化：Prompt、Skill、模型参数、MCP/A2A 注册信息进入配置/注册中心，支持灰度与回滚。
  7. 评估闭环：离线评测集 + 线上采样 + LLM-as-Judge，版本发布前必须过评估门禁。

9.4 常见反模式

  • 把 Agent 框架当成平台：框架只解决“单个 Agent 怎么写”，注册、网关、评估、审计、配额仍需平台建设。
  • 同一 JVM 混装多个 Agent 框架：带来 Jackson/MCP SDK/Reactor 冲突与双模型层，应服务化隔离。
  • 为了多智能体而多智能体：能用单 Agent + 工具检索 + Skills 解决的，不要拆成多 Agent；多 Agent 显著增加 Token 与调试成本。
  • 自主 Agent 直连高风险写操作：必须经过权限引擎/HITL 与审计。
  • 追新预览版上生产：SAA 2.0-M1.1、Spring AI 2.1-M1、LangChain4j agentic beta 均应限定在评估环境。

11. 最终推荐与实施路线

11.1 推荐结论

(1) 基座标准：Spring AI 2.x（强制）

  • 所有新建与升级到 Boot 4 的 Java 服务，AI 能力一律基于 Spring AI 2.x 的 ChatClient / Advisor / VectorStore / MCP。
  • 企业领域能力统一以 Spring AI MCP Server 暴露，形成“工具资产层”。
  • 理由：官方背书、与 Boot 4 同步演进、MCP 官方实现方、可观测一流；且官方 Agent 能力将在 2026-11（实验）→ 2027 年中（3.0）逐步补齐，基座投资不会浪费。

(2) Agent 运行时：AgentScope Java 2.x（平台级，受控引入）

  • 用于平台托管的自主型、长任务、需沙箱与多租户的 Agent；以独立运行时集群部署，经 MCP 调用工具资产层、经 A2A 与其他 Agent 互通。
  • 引入条件：锁定 2.0.x 补丁线；建立升级回归评估集；知识检索通过 MCP 调用独立检索服务（规避 v2 RAG 重写期）；团队完成 Reactor 与事件流培训。

(3) 确定性编排：按基线二选一

  • 存量 Boot 3 项目：SAA 1.1.2.2 Graph（锁版本，并规划随 SAA 2.0 GA 升级）。
  • 新建 Boot 4 项目：LangGraph4j 1.8 + Spring AI 2.x；SAA 2.0 GA 后重新评估切换。
  • 天级/周级、跨系统强一致流程：交给持久化工作流引擎，Agent 作为其中的活动节点。

(4) LangChain4j：指定场景的标准

  • Quarkus / Jakarta EE / Micronaut 团队的指定框架；需要特殊模型或向量库集成时作为补充；agentic 模块在 GA 前仅用于非核心链路。

(5) SAA 的正确用法

  • 用其 Graph、Nacos 集成（A2A 注册、动态配置、Prompt 管理）、DashScope 适配与 Studio/Admin；把它视作 Spring 生态与 AgentScope 之间的集成与编排层，而非唯一长期内核。

如果只能选一个：

  • 以业务服务 AI 化为主的企业 → Spring AI 2.x；
  • 以建设企业级 Agent 平台为主的企业 → AgentScope Java 2.x（同时以 Spring AI 构建工具资产层）。
