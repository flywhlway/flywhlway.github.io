以 mem0ai 2.2.1 源码为准，讲清 v3 记忆算法的单次抽取、只增不改与三路检索融合…

Flywhl 26 分钟 发布于 2026.09 #LangGraph#Agent#上下文工程

先读结论

  1. Mem0 是夹在 Agent 框架与向量库之间的长期记忆中间件，管的是关于人、Agent、会话且随时间增长的事实，与检索静态文档的 RAG 互补。
  2. v3 算法单次 LLM 调用只做 ADD 抽取，新旧事实并存并通过 linked_memory_ids 关联，业务侧不能再依赖 UPDATE/DELETE 事件。
  3. 检索分是语义、BM25、实体三路的动态融合分，threshold 只过滤语义分，阈值必须按查询类型重新标定。
  4. 默认配置下中文语料的三路检索有两路基本失效，需要替换分词与实体抽取函数，并在每次升级 mem0 前回归测试。

本文以 mem0ai 2.2.1 源码为准重写。基于 mem0 1.x / 2.0 早期心智模型的常见写法（图记忆、UPDATE/DELETE 事件、deepseek-chat 等）已失效，详见第 0.2 节勘误表。

1. Mem0 是什么：v3 记忆算法的最小心智模型

1.1 一句话

Mem0 是 Agent 的长期记忆中间件：把对话里值得复用的事实抽成“记忆原子”存起来，下次按相关度召回。它不是 Agent 框架，也不是向量库；它夹在两者中间，负责“记什么”和“怎么找回来”。

它与 RAG 的区别在于：RAG 检索的是静态知识文档；Mem0 管的是关于某个人 / 某个 Agent / 某次会话、随时间增长的事实。实际系统通常两者都要。

1.2 写入：单次调用、只增不改

flowchart LR
    A[新消息 messages] --> B[按 user/agent/run 取最近 10 条相关旧记忆<br/>+ 会话最近 10 条消息缓冲]
    B --> C[一次 LLM 调用<br/>ADDITIVE_EXTRACTION_PROMPT]
    C --> D["JSON: {memory:[{id,text,attributed_to,linked_memory_ids}]}"]
    D --> E[批量向量化]
    E --> F[MD5 哈希去重]
    F --> G[批量写入向量库]
    G --> H[SQLite 历史表记 ADD]
    G --> I["实体抽取 → {collection}_entities 集合"]

要点：

  1. 一次 LLM 调用：旧算法要两次（抽事实 + 决定增删改），新算法只做抽取，时延大约减半。
  2. 只增不改：车主先说“常去张江门店”，后来说“改去江宁门店”，两条都会保留；新记忆通过 linked_memory_ids 指向旧记忆，检索时由相关度与时间信号决定谁排在前面。
  3. 服务方的话也是事实：抽取结果带 attributed_to: user | assistant。“客服承诺 3 天内回电”这类 assistant 侧事实会和用户陈述一样入库，这正是售后、客服场景最有价值的记忆。
  4. 去重靠哈希：只有完全相同的文本会被去重，同义不同字的不会。因此“至少一次”投递的队列重试是安全的。

1.3 检索：三路信号融合

源码层面有三个值得记住的细节：

  • threshold 过滤的是语义分，而且在融合之前生效：语义分低于阈值的候选，关键词再准也不会出现在结果里。
  • 分母是动态的：同一条记忆，本次查询有关键词命中与没有命中时，得分可能相差一倍。所以不要把 0.x 分数当绝对值用，要按查询类型标定。
  • explain=True 会在每条结果上附带 score_details，包含 semantic_score、bm25_score、entity_boost、max_possible_score 等字段。调参和排障全靠它，配套工程的界面直接把它画成三色条。

1.4 三类实体 ID 与作用域

参数 语义 典型用法
user_id 人 车主、客户、员工
agent_id 哪个 Agent 的记忆 同一用户在“售后助手”和“销售助手”下各记各的
run_id 一次会话 / 任务 短期、会话级记忆

写入时至少要提供其中一个；检索时在 filters 里按需组合。metadata 中若出现 user_id / agent_id / run_id / actor_id 会被剥离（2.0.16 起），防止借 metadata 越权写到别人的作用域里。

4. API 完整参考（Memory / AsyncMemory，2.2.1）

4.1 签名速查

方法 签名要点 说明
add add(messages, *, user_id=None, agent_id=None, run_id=None, metadata=None, expiration_date=None, infer=True, memory_type=None, prompt=None) messages 只能是 str / dict / list[dict]，否则 Mem0ValidationError(VALIDATION_003)
search search(query, *, top_k=20, filters=None, threshold=0.1, rerank=False, explain=False, show_expired=False) filters 必须含至少一个实体 ID；threshold 须在 [0,1]
get_all get_all(*, filters=None, top_k=20, show_expired=False) 无 offset / 游标分页（见第 8.6 节）
get get(memory_id)
update update(memory_id, text=None, metadata=None, expiration_date=<不变>) 写一条 UPDATE 历史，重算向量、BM25 文本与实体链接；data= 已废弃
delete delete(memory_id) 同步清理实体链接
delete_all delete_all(user_id=None, agent_id=None, run_id=None) 实体 ID 走顶层参数；按 1000 条分批删除
history history(memory_id) 该条记忆的 ADD / UPDATE / DELETE 轨迹
reset reset() 清空向量集合、实体集合与历史库，慎用
close close() 释放连接池；支持 with / async with

非对称规则：add() 与 delete_all() 的实体 ID 放在顶层参数；search() 与 get_all() 的实体 ID 放进 filters。项目里建议封装一层 service，只暴露一种写法（配套工程 memory/service.py）。

AsyncMemory 的方法签名与 Memory 完全一致，都是 async；from_config() 是普通的类方法，不需要 await；close() 是同步方法。

4.2 filters 表达式

支持的算子：eq ne gt gte lt lte in nin contains icontains，通配 "*"，以及逻辑 $or、$not。pgvector 从 2.0.3 起支持全部算子；in / nin 的值必须是 list（2.0.18 起会做校验），各向量库支持程度不一，换库时要回归测试。

4.3 infer=False：原文入库

不经过 LLM，逐条消息原样入库（仍会向量化、写历史）。适用场景：CRM / DMS 工单结论、维修记录这类已经结构化、不应被改写的事实，同时也省掉抽取成本。

4.4 expiration_date：临时事实

传 ISO 时间戳（2026-10-03T00:00:00Z）会直接报 expiration_date must be a valid date in YYYY-MM-DD format，这一点实测踩过。

4.5 rerank 与 Reranker

默认关闭。召回量大（top_k≥20）且对前 3 条排序准确度敏感时才值得开启，它会额外增加一次模型调用的时延。

4.6 历史数据迁移与时间

开源版 add(timestamp=...) 会抛出 ValueError（Platform 专属）。实测 2.2.1 在 metadata 中携带 created_at 时，写入阶段会保留该值，可用于历史回填：

这是未文档化的行为，仅建议在一次性迁移脚本里使用，升级后要回归验证。

4.7 异常体系

mem0.exceptions 中的 Mem0ValidationError、LLMError、EmbeddingError、VectorStoreError、DatabaseError 都带 error_code 与修复建议。两个在 2.x 中变化的行为：

  • LLM 失败不再静默：2.0.11 起抽取失败直接抛 LLMError，以前返回 []，现在队列可以据此重试。
  • 写入全部失败会抛错：2.2.1 起向量库拒绝全部记录时抛 VectorStoreError，以前会把没写成功的记录也报告成 ADD。

6. 中文场景专题：让三路检索真正生效

6.1 问题：默认配置下中文只剩语义一路

6.3 顺带修正：pgvector 的 BM25 量纲不匹配（与语言无关）

mem0 用 sigmoid(steepness × (raw − midpoint)) 归一化 BM25，其中 midpoint = 5 ~ 12 是按真正的 BM25 原始分（0–20+）标定的。但 pgvector 的 keyword_search 返回的是 ts_rank_cd，实测单词命中恒为 0.1，归一化后只有约 0.03。结果是：

  • 关键词信号形同虚设；
  • 只要有任何关键词命中，分母 max_possible 就从 1.0 变成 2.0，所有结果的综合分被整体减半。

8. 工程化架构：热路径 / 写路径分离

8.1 为什么不能在请求里同步 add()

  • 时延：每次 add() 要做一次 LLM 抽取（1–3 秒），这部分时间对当前这一轮的回答没有任何贡献。
  • 可靠性：LLM 超时或限流时，要么整轮失败，要么吞掉异常导致记忆静默丢失。
  • 隔离：高峰期抽取会和面向用户的答复争抢模型配额。
  • 可运维：同步调用无法重试、无法观察积压、无法削峰。

8.3 关键设计决策

决策 做法 原因
图内只读、图外写 LangGraph 只有 recall、respond 两个节点；落库消息、提交任务放在 API 层 节点可重试且无副作用；检查点只承载会话状态
先落表再入队 extraction_jobs 记录载荷与状态，再 enqueue_job(_job_id=job.id) 可观测、可重放；_job_id 保证幂等
至少一次投递 ARQ max_tries=4，失败时抛 Retry(defer=2**n) 指数退避 mem0 按 MD5 去重，重复执行安全
队列故障降级 入队异常只把任务标记为失败，不影响答复 “记不住”可以接受，“答不了”不行
答复与连接解耦 一轮对话在后台 asyncio.Task 中执行，SSE 只消费事件队列 浏览器中途断开也能完成落库与记忆写入（实测修复过这个问题）
流式实现 节点内 get_stream_writer() 发自定义事件，API 用 stream_mode="custom" 转成 SSE 事件 recall / token / done / error 召回结果可以先于答复展示给坐席
双库 copilot：业务表 + LangGraph 检查点；copilot_memory：mem0 向量 + 实体 读写模式与备份策略不同
SQLite 历史库 api 与 worker 挂载同一个卷 多副本时需要改为单写者，或把 update/delete 也路由到 Worker

thread_id 直接使用会话 ID，进程重启后可以续聊。连接池参数中的 autocommit 和 prepare_threshold=0 是 checkpointer 的硬性要求。

9. 配套工程：mem0-service-copilot（车主服务记忆中台）

9.1 场景

新能源汽车售后服务中心。坐席接到车主诉求（热线、App、企业微信、门店）后录入工作台，系统依次完成：

  1. 按车主 ID 召回长期记忆（联系偏好、常去门店、既往故障、此前的服务承诺），并展示三路打分；
  2. 流式生成建议答复；
  3. 对话结束后，Worker 异步抽取新事实，写回记忆库；
  4. 主管在记忆库中修订或删除错误记忆，操作全部留痕；CRM 工单结论以 infer=False 原文导入。

9.2 一键启动

默认使用离线演示引擎（MEMORY_ENGINE=demo），不需要任何模型或密钥：

  • 向量：字符 n-gram 加 jieba 词的特征哈希；
  • 抽取：一套遵循 mem0 抽取 prompt 输入输出契约的规则引擎。

除这两个外部依赖被替换外，写入、去重、实体链接、BM25、混合打分、历史审计全部走 mem0 原生代码，所以界面上看到的打分明细是真实的 mem0 行为。演示引擎也用于 CI。

切换到生产引擎：在 .env 中设置 MEMORY_ENGINE=live，填写 DEEPSEEK_API_KEY，本机执行 ollama pull bge-m3，然后 docker compose down -v && docker compose up -d --build。两种引擎的向量空间不同，切换时必须清空记忆集合。

9.5 验证步骤（建议逐条走一遍）

  1. 在工作台为“陈思远”新建会话，录入“左前轮胎压又报警了，想这周六去张江服务中心检查”。右侧召回列表中，“张江服务中心”相关记忆排在前面（琥珀色实体加权段）。
  2. 答复完成约 1 秒后，“记忆写入”显示“成功 · 新增 N 条”。到记忆库中能看到新条目，来源会话可以点回。
  3. 在记忆库修订一条记忆并设置过期日。详情中出现“人工修订”历史，系统页审计新增一条记录。
  4. 执行 docker compose stop worker 后继续对话：答复不受影响，任务停在“排队中”。执行 docker compose start worker 后积压任务被消费，写入补齐。
  5. make test：单元测试 9 项（中文补丁回归、BM25 校准、离线引擎契约）；make test-int：一轮 SSE 对话 → Worker 写入 → 语义检索命中。

10. 生产最佳实践清单

记忆质量

  • custom_instructions 写明“记什么、不记什么”，并把服务承诺列为一等事实。
  • 结构化来源（CRM、DMS）用 infer=False 导入，避免被 LLM 改写。
  • 临时事实（出差、临时联系方式）一律带 expiration_date。
  • 入库前做 PII 过滤（手机号、证件号、银行卡）：LLM 抽取不保证遵守指令，要在 Worker 中做正则兜底。

检索

  • 所有召回都开 explain=True 并记录日志，阈值基于日志标定，不要凭感觉设。
  • 中文必须处理 BM25 与实体两路（第 6 章）；pgvector 务必做 BM25 量纲校准。
  • top_k 按提示词预算设置（5–8）；只有排序敏感时才开 rerank。

架构

  • add() 放到异步队列；任务先落表、幂等入队、指数退避、失败可重放。
  • 图（Agent）内只读，副作用放在图外；答复流程与客户端连接解耦。
  • 后台列表走只读 SQL；所有写操作走 mem0 API 并记审计。
  • 换嵌入模型就换集合名；demo 与 live 引擎不要共用集合。

安全与运维

  • API Key 由网关注入，浏览器不持有；前置 SSO 写入 X-Operator。
  • MEM0_TELEMETRY=false（关闭 PostHog 上报与提示信息）。
  • 备份两个库和 mem0 历史卷；Worker 心跳超过 60 秒告警；队列积压告警。
  • 升级 mem0 时先阅读 changelog，再跑中文补丁回归测试。

11. 排错速查

症状 原因 处理
ValueError: Top-level entity parameters ... not supported in search() 旧写法 search(user_id=...) 改为 filters={"user_id": ...}
ValueError 提示 timestamp 仅 Platform 可用 开源版调用了 add(timestamp=...) 或 search(reference_date=...) 移除；迁移场景见第 4.6 节
expiration_date must be a valid date in YYYY-MM-DD format 传了 ISO 时间戳 改传 YYYY-MM-DD
中文检索 bm25_score 恒为 0、entity_boost 恒为 0 spaCy 英文模型不处理中文 第 6.2 节补丁
有关键词命中后，所有分数整体变低 pgvector 的 ts_rank_cd 量纲与 sigmoid 参数不匹配，分母被抬到 2.0 第 6.3 节校准
Qdrant 下没有 BM25 信号 未安装 fastembed pip install fastembed
DeepSeek 返回模型不存在或行为异常 仍在使用已退役的 deepseek-chat deepseek-v4-flash / deepseek-v4-pro
本地模型抽取结果为空 思考模型输出 <think> 前缀，JSON 解析失败 关闭思考或换非思考模型
LLMError: LLM extraction failed 2.0.11 起抽取失败会直接抛出 队列重试；检查超时与限流
插入时维度报错 嵌入维度与 embedding_model_dims 不一致 对齐维度，换集合名
召回返回 0 条 语义分全部低于 threshold（默认 0.1） 看 explain；降低阈值或检查嵌入模型
浏览器断开后答复丢失 生成逻辑绑定在 SSE 生成器上 用后台 task + 事件队列（第 8.3 节）
多副本部署后历史记录错乱或出现 locked 错误 SQLite 历史库并发写 共享卷单写者，或把 update/delete 路由到 Worker
