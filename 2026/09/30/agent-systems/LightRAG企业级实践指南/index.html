先读结论

  1. Graph RAG 在企业里的失败多源于语料没按图谱友好方式准备、RAG 被当黑盒接入业务、POC 脚本承载不了可靠性与审批，而不是检索不准。

  4. 诊断结论进入远程处置前，由 Temporal 工作流承载 Signal 审批、进度查询与超时升级。

前言：这份指南解决什么问题

Graph RAG 在企业里最常见的失败模式并不是“检索不准”，而是三件更隐蔽的事：语料没有按图谱友好的方式准备，导致实体碎片化；RAG 被当成问答黑盒直接接进业务，结论无法溯源、幻觉无法拦截；POC 阶段的同步脚本无法承载真实业务所需的可靠性与人工审批。

本指南以“车辆远程智能诊断”这个多跳推理需求极强的场景为主线，按 原理 → 部署 → 知识工程 → Agent 集成 → 评测 → 生产化 的顺序，把 LightRAG 从单机试用推进到可以向业务方演示、可以按清单推向生产的状态。全文重实操、轻理论，每一章都对应工程中的具体文件。

第 1 章　LightRAG 原理速通

1.1 定位：为什么诊断场景需要 Graph RAG

传统向量 RAG 把文档切成片段、按语义相似度召回。它擅长回答“U0146 是什么意思”这类单点问题，但回答不了“BootLoader 为 BL-2.0.8 的车升级 CGW-3.3.0 失败并报 U0146，根因是什么、有没有通告”。这个问题的答案分散在三篇文档里：DTC 手册说明 U0146 可由 CGW 回滚引起，OTA 手册的兼容矩阵说明 BL-2.0.x 刷 CGW-3.3.0 必然校验失败，TSB 通告给出该批次车辆的两段式升级方案。三段文字彼此的向量相似度并不高，纯向量检索很难同时召回。

LightRAG 在索引阶段用 LLM 把文本抽取为“实体 + 关系”写入知识图谱，查询时同时走图谱（沿关系边多跳扩展）和向量（语义召回原文），再把两路结果合并为上下文。U0146、CGW、BL-2.0.8、CGW-3.3.0、TSB-2026-013 在图谱里通过关系边相连，多跳检索就能把整条因果链一起取回。与微软 GraphRAG 相比，LightRAG 不依赖离线社区聚类，支持增量插入与按文档删除后自动重建受影响子图，工程上更适合知识持续更新的企业场景。

1.2 索引管线

几个直接影响效果与成本的事实：

  • 抽取成本集中在 LLM：每个 Chunk 至少一次抽取调用，外加实体合并时的摘要调用。开启 ENABLE_LLM_CACHE 后，重复灌注同一内容几乎零成本。
  • 实体名就是图谱主键：“CGW”“中央网关”“Gateway”若混用，会被抽成三个节点，多跳链路就此断开。这是企业图谱质量差的首要原因，第 4 章专门处理。
  • 文档状态可追踪：PENDING → PARSING → (ANALYZING) → PROCESSING → PROCESSED / FAILED，失败文档可通过 /documents/reprocess_failed 重试。

1.3 六种查询模式

模式 检索路径 适用问题 诊断场景用法
naive 仅向量召回 Chunk 单点事实 对照组，量化图谱增益
local 低层关键词 → 实体 → 邻接关系 某个实体的定义与属性 查询故障码含义、部件职责
global 高层关键词 → 关系 → 相关实体 跨文档的规律、主题总结 某类故障的通用排查思路
hybrid local + global 需要兼顾细节与主题 较少单独使用
mix 图谱（local+global）+ 向量 Chunk 因果链、多跳推理 根因分析、TSB 匹配（默认）
bypass 不检索，直接调用 LLM 闲聊或调试 不用于诊断

调参经验：top_k 控制图谱侧实体/关系条数，chunk_top_k 控制向量侧 Chunk 条数，max_total_tokens 是上下文总预算。开启 Reranker 后可以适当调大召回、依靠重排提纯；未开启时宁少勿多，避免噪声稀释关键证据。

1.4 存储选型矩阵（1.5.7）

存储类型 开发测试 生产推荐 PostgreSQL 一体化
KV（原文、LLM 缓存、Chunk） JsonKVStorage RedisKVStorage / MongoKVStorage PGKVStorage
向量（实体/关系/Chunk） NanoVectorDBStorage MilvusVectorDBStorage / QdrantVectorDBStorage PGVectorStorage（HNSW）
图谱 NetworkXStorage Neo4JStorage / MemgraphStorage PGTableGraphStorage（1.5.6 新增，无需 AGE）
文档状态 JsonDocStatusStorage PGDocStatusStorage / MongoDocStatusStorage PGDocStatusStorage

PGTableGraphStorage 是 1.5.6 起的重要变化：图谱直接建在 PostgreSQL 普通表上，不再依赖 Apache AGE 扩展，官方 pgvector/pgvector 镜像或 RDS、PolarDB 这类托管 PostgreSQL 即可承载全部四类存储。官方说明它将取代基于 AGE 的 PGGraphStorage 成为 PostgreSQL 上的首选图存储，并提供了从 AGE 迁移到表存储的离线工具。

选型建议：团队已有 PostgreSQL 运维能力、数据量在百万实体以内、希望最少组件时选一体化；需要复杂图分析（Cypher、GDS 算法）或向量规模很大时选专用存储。本工程两种都提供，一个参数切换。

1.5 Workspace 多租户

WORKSPACE 在同一套存储上按命名空间隔离数据（只允许字母、数字和下划线）。典型用法是按业务域划分知识库：vehicle_diag（诊断）、rd_kb（研发）、after_sales（售后）。一个 LightRAG Server 实例对应一个 workspace；多知识库可以部署多个实例共享底层存储，由网关按路径路由（配合 LIGHTRAG_API_PREFIX）。

1.6 1.5.x 系列值得关注的新能力

  • /query/data：只检索不生成，返回结构化的实体、关系、Chunk 与引用列表，是把 LightRAG 当作 Agent 检索内核的标准接口（第 5 章核心）。
  • 领域实体类型画像：ENTITY_TYPE_PROMPT_FILE 以 YAML 注入实体类型定义与抽取示例（第 4 章）。
  • 多策略切分：固定 token（F）、递归字符（R，默认含中文句读）、段落语义（P）、语义向量（V），以及 Word 文档智能标题识别（1.5.5）。
  • 角色化 LLM：EXTRACT / KEYWORD / QUERY / VLM 四个角色可分别指定模型、并发与超时。
  • 生产加固：请求体上限、登录防爆破、写入准入控制（积压超限返回 429）、可关闭 API 文档页。
  • 双入口 WebUI（1.5.7）：/webui 管理端与 /workspace 终端用户问答端，支持品牌定制与全局 USER_PROMPT_PREFIX。
  • 知识治理 API：实体/关系的创建、编辑、删除与合并，按文档删除后自动重建受影响子图。

3.2 工程的分层 Compose 设计

make up PROFILE=full|lite 等价于 docker compose -f docker-compose.yml -f docker-compose.<profile>.yml up -d。之所以用叠加文件而不是 Compose profiles：LightRAG 需要按档位同时切换环境变量和依赖关系，而 profiles 只能控制服务启停，叠加文件则能确定性地合并 env_file 与 depends_on。两个档位都已用 Docker Compose v5 执行 config -q 校验通过。

几个关键设计：

  • 镜像固定版本：ghcr.io/hkuds/lightrag:v1.5.7，官方发布流水线以 git tag 作为镜像 tag，并对官方镜像做了 Cosign 签名，可用 cosign verify 校验供应链。
  • 敏感信息单点注入：deploy/lightrag/lightrag.env 不含任何密钥，可入库；DeepSeek Key、LightRAG API Key、WebUI 账号、JWT Secret 均由 Compose 从根 .env 注入。整个工程只有根 .env 一个文件需要填写。
  • PostgreSQL 选 pg17：LightRAG 要求 PG14+，而 pg18 官方镜像的数据目录挂载路径发生了变化，沿用旧写法会导致数据写到匿名卷里。
  • Milvus 固定 v2.6.11：Milvus 3.0 已 GA，但 LightRAG 官方 setup 模板仍锁定 2.6.11，本工程与官方验证版本保持一致，升级前需自行回归。
  • Redis 必须 noeviction + AOF：LightRAG 把原文、Chunk 与 LLM 缓存放在 KV，一旦被淘汰就是静默的数据丢失。
  • 健康检查驱动启动顺序：LightRAG 等待全部存储 healthy 才启动，业务服务等待 LightRAG 与 Temporal healthy。

第 4 章　领域知识工程：Graph RAG 成败的一半

同样的 LightRAG、同样的模型，知识工程做得好与不好，多跳召回率可以相差一倍以上。这一章的每一条都对应工程里的具体文件。

4.1 语料准备三原则

原则一：实体名规范化先于入库。 在 data/knowledge/06-terminology.md 中维护“规范名称 ↔ 别名”对照表，入库前把别名统一替换为规范名。版本号书写也要统一：CGW 固件写作 CGW-3.3.0，BootLoader 写作 BL-2.1.5，通告写作 TSB-2026-013。对照表本身也入库，让图谱获得“别名 → 规范名”的关系，用户提问时即使用别名也能命中。

原则二：因果关系写成显式陈述句。 LLM 抽取关系依赖文本中的明确表述。“BL-2.0.x 刷写 CGW-3.3.0 必然触发校验失败并回滚”能被抽成一条带因果语义的关系边；“见兼容矩阵”则什么也抽不出来。工程中 OTA 手册的“重要结论”段、DTC 手册的“处理建议”段都是按这个原则写的。表格适合承载对照信息，但关键结论应在表格后用一句话复述。

原则三：为鉴别诊断准备反例。 只有正例的知识库会让模型“见到 U0146 就套 TSB-2026-013”。07-field-cases.md 专门收录反例工单：U0146 由诊断 CAN 线束磨损引起（无 OTA 记录、BootLoader 已满足兼容矩阵），以及 OTA 因低压电量不足失败（失败阶段是写入而非校验）。反例里明确写出“何时不适用该通告”，这是让 Agent 学会鉴别诊断的关键语料。

4.2 领域实体类型画像（ENTITY_TYPE_PROMPT_FILE）

LightRAG 默认的实体类型是通用的（人物、组织、地点、事件等），对车辆诊断文本会产生大量 Other。1.5.x 允许用 YAML 注入领域画像，文件放在 PROMPT_DIR/entity_type/ 下（官方镜像中 PROMPT_DIR=/app/data/prompts），通过 ENTITY_TYPE_PROMPT_FILE=vehicle_diag.yml 引用。

编写要点（均来自对 1.5.7 源码的核验）：

  • 当前抽取模式所需的示例段必须存在且非空，否则启动时报错。工程里两段都保留，便于切换抽取模式。
  • 文本模式示例中的 {tuple_delimiter}、{completion_delimiter} 占位符会被格式化替换；JSON 模式示例不做格式化，里面的花括号可以直接写，不需要转义。
  • 示例要用真实领域数据而不是占位符，一两个高质量示例胜过十条规则。示例中刻意演示了“版本不兼容”这类诊断领域特有的关系表述。
  • 修改画像后只对新抽取的内容生效。已入库的文档需要删除重灌，或清空后整体重建。

4.3 切分策略选择

策略 原理 适用
fixed_token（F） 按 token 数硬切 结构松散的日志、纯文本
recursive_character（R） 按分隔符层级递归切分，默认含中文句读 中文手册、通告（本工程默认）
paragraph_semantic（P） 段落感知 + 语义合并 章节结构清晰的长文档
semantic_vector（V） 相邻句向量距离断点 主题跳跃频繁的材料

工程使用 recursive_character，chunk_token_size=800、chunk_overlap_token_size=80。诊断手册按“一个故障码/一条通告一个小节”组织，800 token 基本能让一个小节完整落在一个 Chunk 内，避免“故障描述”和“处理建议”被切到两个 Chunk。Word 文档可以利用 1.5.5 起的标题识别能力走段落语义策略。

4.4 幂等灌注（scripts/ingest_knowledge.py）

脚本只依赖 Python 标准库，宿主机无需安装任何包。核心逻辑：

  1. 以文件名作为 file_source 提交，同名文档已存在时服务端返回 409，脚本视为“已入库”并跳过，因此可以放心重复执行，也可以放进 CI；
  2. 遇到写入准入限流（429）自动退避重试；
  3. 按 track_id 轮询 /documents/track_status/{id}，直到全部 processed 或 failed，期间打印 pipeline_status 的最新进度；
  4. 最后输出 /documents/status_counts 统计，存在失败文档时以非零码退出。

内容更新的标准流程是“删除旧文档 → 提交新版本”：kb_admin.py list 找到文档 ID，kb_admin.py delete <id> 删除（LightRAG 会自动重建受该文档影响的实体与关系），再执行 make ingest。

4.6 知识生命周期：通告替代、失效与版本化

诊断知识不是一次性资产。TSB 会被新版通告替代，兼容矩阵会随新固件扩展，旧结论如果仍留在图谱里，Agent 就可能引用一份已经作废的处置方案。生产环境需要把知识生命周期管理当作一等公民：

  • 文档即版本单元：file_source 带上版本号或发布日期（如 TSB-2026-013_v2.md），发布新版时先删除旧版文档（LightRAG 会重建受影响的实体与关系），再灌注新版，避免新旧结论并存于同一个实体描述中。
  • 在正文中显式写出替代关系：新版通告首段写明“本通告替代 TSB-2026-013 第 1 版”，图谱会抽取出“替代”关系；分析 Prompt 可以追加一条规则：存在替代关系时只采信最新版本。
  • 失效通告不要只打标记：LightRAG 检索不会理解“已作废”标签的业务含义，作废文档应直接删除；如需留档，放在独立的归档 workspace 中。
  • 与发布系统联动：TSB 发布系统在通告“发布 / 修订 / 作废”时触发灌注流水线，执行“删除旧版 → 灌注新版 → 运行检索评测”，评测不通过则告警并回滚到上一版文档集。
  • 定期全量重建：增量删除与合并长期运行后，实体描述会因多次摘要合并产生语义漂移，建议每季度在预发环境全量重建一次并与线上评测结果对比。

5.3 证据模型：从“参考文档”到“证据编号”

多数 RAG 系统的可解释性停留在“列出参考文档”，业务方无法判断哪一句结论来自哪一段知识。本工程把 /query/data 返回的每一个实体、关系、Chunk 统一为 Evidence，放入 EvidenceStore 并分配稳定编号：

几个细节：

  • 关系优先：渲染给分析模型时按“关系 > 实体 > 原文”的优先级在字符预算内装填。关系边承载因果语义，是多跳推理的骨架；原文 Chunk 最长，放在最后。
  • 跨轮次去重且编号稳定：LangGraph 状态中的 evidence 字段挂载自定义 reducer merge_evidence，第二轮补采的证据只追加新编号，已有编号不变，分析模型在第二轮仍能引用第一轮的证据。
  • 来源反查：LightRAG 返回的实体可能只带 reference_id 不带 file_path，统一在转换时反查 references 列表补齐。

5.4 LangGraph 引擎：显式状态机与证据补采

flowchart LR
  A[recall_memory<br/>记忆召回+规则预分诊] --> B[plan_queries<br/>LLM 检索规划]
  B --> C[retrieve<br/>并行 /query/data]

  D --> E[verify<br/>引用落地校验]

各节点职责（services/diag-agent/app/agent/graph.py）：

节点 类型 职责 失败策略
recall_memory IO 按 VIN 召回历史诊断记忆；执行规则预分诊（DTC 所属系统、OTA 回滚、低压 SOC、多网络故障码、无 OTA 记录等标记） 记忆异常降级为空
plan_queries LLM 生成 2～4 条检索意图，每条指定 local / global / mix 模式 输出不合法时回落到确定性规则计划
retrieve IO asyncio.gather 并行调用 /query/data，结果并入证据仓库 单条失败记录错误，不影响其余
analyze LLM 基于编号证据输出结构化报告（JSON Mode + Pydantic 校验 + 一次自修复） 返回置信度为 0 的降级报告
verify 确定性 引用落地校验；决定是否补采 —
save_memory IO 把本次结论写回 mem0 异常降级

规则预分诊是一个容易被忽视的设计：DTC 所属系统、OTA 是否回滚、低压 SOC 是否低于 30%、是否有多个 U 类码同时出现，这些判断零成本、确定、可单测。它既作为结构化线索喂给规划与分析模型，也是 LLM 规划失败时兜底计划的依据。

证据补采回路：当分析模型声明 need_more_evidence，或落地率低于阈值，且检索轮次未达 MAX_EVIDENCE_ROUNDS（默认 2）时，verify 用报告中的 followup_queries（或无证据支撑的结论）生成补充检索，已执行过的检索语句自动去重，然后回到 retrieve。

结构化输出的工程化（agent/llm.py）：DeepSeek 支持 response_format={"type": "json_object"}。调用时绑定 JSON Mode，拿到文本后剥离可能的代码围栏、截取首尾花括号，用 Pydantic 校验；校验失败时把错误信息作为下一轮用户消息让模型自修复一次。这种方式不依赖特定供应商的工具调用实现，换模型时最稳。

5.5 引用落地校验（grounding）：三道确定性闸门

agent/grounding.py 中的 verify() 不调用任何模型，逐条检查分析报告：

  1. 伪造引用剔除：推理链每一步引用的编号必须存在于证据仓库，不存在的编号被剔除并记入 invalid_ids；一个有效编号都没有的结论记为“无证据支撑”。落地率 = 有证据支撑的步骤数 / 总步骤数。
  2. TSB 核验：报告声称命中的 TSB 编号必须出现在某条证据的标题或正文中，否则置空并记录调整原因。这一条专门拦截“模型凭印象编造一个通告编号”的高危幻觉。
  3. 一致性修正：落地率低于 MIN_GROUNDED_RATIO（默认 0.6）时置信度封顶 0.5；顶层“远程可执行”与逐条动作不一致时以逐条动作为准。

校验结果随报告一起返回，前端可以直接展示“每条结论 → 证据编号 → 源文档”的引用链：

这套机制的价值在于把“是否可信”的判断从模型转移到代码：模型负责推理，代码负责核对它有没有编造依据。离线测试 test_grounding.py 覆盖了伪造编号、伪造 TSB、远程标记不一致三类情况。

5.7 mem0 车辆长期记忆

memory/vehicle_memory.py 以 VIN 作为 user_id，沉淀“这台车”的历史诊断结论。full 档位写入 Milvus（与 LightRAG 共用实例、独立 collection），lite 档位写入 diagdb 的 pgvector。关键设计：

  • 惰性初始化 + 线程化：AsyncMemory.from_config 会同步建立连接与集合，放入 asyncio.to_thread 避免阻塞事件循环；
  • 全面降级：初始化、检索、写入任何一步异常都降级为空记忆，外围能力永不阻塞诊断主链路；
  • 记忆只作线索不作证据：Prompt 明确要求历史记忆不得作为证据引用，校验阶段也只认 EV-xx 编号。这避免了“上次诊断错了、这次继续错”的错误自我强化。

mem0 2.2 的检索接口为 search(query, filters={"user_id": vin}, top_k=5)，返回 {"results": [...]}。

要点：

  • 确定性约束：Workflow 中不做任何 IO，HTTP、数据库、远程下发全部放在 Activity；Activity 模块通过 imports_passed_through 导入。离线测试 test_workflow.py 用与 Worker 启动时相同的沙箱运行器校验工作流定义。

第 7 章　评测与调优

没有评测的 RAG 调参等于盲调。工程提供两层评测，都可以放进 CI 做回归。

7.1 检索层评测（make eval）

data/eval/golden_cases.jsonl 定义了 6 个黄金问题，每个问题标注期望关键词与期望来源文档。scripts/eval_retrieval.py 对五种模式逐一调用 /query/data（只检索不生成，速度快、成本低），计算：

  • keyword_recall：检索上下文中命中期望关键词的比例，衡量证据覆盖；
  • source_recall：期望来源文档出现在引用列表中的比例，衡量跨文档多跳能力；
  • latency：检索耗时。

判读方法：mix 的来源召回应明显高于 naive，这是图谱多跳的直接体现；若 local 的关键词召回偏低，通常是实体名不规范导致低层关键词匹配不到实体；若 global 偏低，通常是关系描述过于简略。每条用例还会打印缺失的关键词，直接指向需要补充或改写的语料。明细写入 eval_report.json，便于版本间对比。

7.2 端到端评测（make eval-e2e）

data/eval/e2e_cases.jsonl 覆盖三个工况，逐项判定：TSB 是否命中（或正确地不命中）、根因是否包含期望关键词、远程可执行判定是否正确、证据落地率是否 ≥ 0.8。工况三（线束故障、不应命中 TSB）是最有价值的负例，它检验的是 Agent 会不会过度套用通告。

7.3 引入 RAGAS 与 Langfuse 数据集（可选）

需要更细的生成质量指标时，可以用 RAGAS 计算 faithfulness（回答是否忠于上下文）与 context precision / recall。更贴近业务的做法是依托 Langfuse：工程师对诊断结果打分后，把低分 trace 加入 Langfuse Dataset，每次调参或升级模型后在数据集上重跑并对比分数，形成持续评测。

7.4 调参优先级

按投入产出比从高到低：

  1. 语料与实体规范化（第 4 章）：投入最小、收益最大，任何调参都无法弥补实体碎片化；
  2. 领域实体类型画像：直接决定图谱中有效节点与边的比例；
  3. Reranker：接入 bge-reranker-v2-m3 后可把 chunk_top_k 调大到 20～30，由重排保证精度；
  4. 切分参数：让“一个故障码 / 一条通告”尽量落在一个 Chunk 内；
  5. 查询参数：top_k、max_total_tokens、KG_CHUNK_PICK_METHOD；
  6. 模型分层：抽取用 deepseek-flash，分析节点（LLM_MODEL_ANALYST）对疑难工况可切到 deepseek-v4-pro。

8.1 性能与成本

环节 主要开销 优化手段
灌注 每个 Chunk 一次抽取 + 合并摘要 抽取角色用便宜模型；开启抽取缓存；MAX_PARALLEL_INSERT 与 MAX_ASYNC_LLM 匹配供应商限流
检索 关键词提取 1 次 LLM + 向量与图谱查询 关键词角色用低延迟模型；Neo4j/Milvus 索引与内存规划
诊断 规划 1 次 + 分析 1 次（+ 可选补采） 规划节点可换更小模型；证据字符预算 EVIDENCE_BUDGET_CHARS 控制输入 token

诊断链路的典型耗时构成是“两次 LLM 调用 + 2～4 次并行检索”。对时延敏感的场景可以把高频故障码组合的检索结果做短期缓存（知识库更新时失效），也可以为 TOP 故障组合预先生成诊断模板。

8.2 安全加固清单

  • LightRAG：ENABLE_API_DOCS=false、WHITELIST_PATHS=/health、强随机 TOKEN_SECRET、WebUI 账号密码使用 bcrypt 哈希（{bcrypt} 前缀）、设置请求体上限与写入准入；
  • 网络：LightRAG、Neo4j、Milvus、Redis、PostgreSQL 均不对公网暴露，只允许 diag-agent 所在网段访问；登录限流放在网关层；
  • 密钥：API Key、数据库口令放入 Vault 或 K8s Secret，不进镜像、不进仓库；
  • 数据：诊断报告与车辆记忆涉及 VIN，按个人信息保护要求做脱敏（日志与 trace 中可对 VIN 做掩码）与留存期限管理；
  • 供应链：用 cosign verify 校验官方镜像签名，镜像固定 tag 并同步到企业私有仓库；
  • 远程下发：dispatch_remote_actions 对接真实 OTA 平台时必须使用幂等键、回执校验与二次鉴权，审批人信息全程留痕。

8.4 备份与恢复

  • 知识库：原始文档（Git 或对象存储）是唯一真源，图谱和向量都可以从原始文档重建。常规备份覆盖 PostgreSQL（pg_dump）、Neo4j（neo4j-admin database dump）、Milvus（milvus-backup）和 Redis AOF。
  • 重建演练：定期在预发环境执行“清库 → 全量灌注 → 评测”，同时校验备份可用性和灌注流水线的健康度。
  • 业务数据：diagdb 的诊断报告表按常规业务库备份；Temporal 历史按 namespace 保留期（本工程 72 小时）配置归档。

8.5 可观测体系

三层可观测互补：Langfuse 看 LLM 调用链路、token 成本与质量评分；Temporal UI 看业务流程执行与审批；LightRAG 的 /health 与 /documents/pipeline_status 看知识内核状态。生产中再把 diag-agent 的请求指标（QPS、P95、错误率）和 LightRAG 的健康状态接入 Prometheus / Grafana，关键告警包括：落地率持续偏低、TSB 被置空的比例上升、灌注失败文档数、审批超时升级数。

8.7 多车型、多知识库扩展

当平台从单一车型扩展到多品牌、多车型时，有两种组织方式：

方式 做法 适用
单库 + 适用范围实体 所有车型共用一个 workspace，文档中显式写出 VehicleScope（车型、VIN 段、生产批次），分析 Prompt 强制核对适用范围 车型平台化程度高、知识大量复用
多库 + 路由 按平台或品牌拆分 workspace（每个对应一个 LightRAG 实例，共享底层存储），diag-agent 根据 VIN 前缀路由到对应知识库，通用知识库并行检索后合并证据 车型差异大、数据权限需隔离

本工程的 VehicleScope 实体类型与 TSB 适用条件核对规则，正是为单库模式预留的。采用多库模式时，LightRAGClient 可以扩展为按 workspace 持有多个客户端实例，EvidenceStore 的去重键加上 workspace 前缀即可直接复用，校验逻辑不需要修改。

第 9 章　FAQ 与踩坑记录

Q1：v1 工程启动后所有 LLM 调用报模型不存在？
deepseek-chat 与 deepseek-reasoner 已于 2026-07-24 下线，过渡期的 deepseek-v4-flash 也已于 2026-09-10 下线。当前可用的是 deepseek-flash（V4.1 Flash）与 deepseek-v4-pro，在根 .env 修改 LLM_MODEL 即可。建议在配置中心维护模型名，而不是硬编码在代码里。

Q2：重复执行灌注脚本报 409？
这是 1.5.7 的预期行为：同名 file_source 的文档已存在。工程脚本会自动跳过。需要更新内容时，先按文档 ID 删除旧版本再提交。

Q3：调用 GET /documents 返回 404 / 405？
1.5.7 已移除该接口，改用 POST /documents/paginated。同时注意 DELETE /documents（不带路径）是清空当前 workspace 的全部文档，按 ID 删除要用 DELETE /documents/delete_document。

Q4：Temporal 用 auto-setup 镜像启动报弃用警告，或新版本找不到该镜像？
官方已弃用 auto-setup，改为 temporalio/server + temporalio/admin-tools 初始化任务的模式，见 3.3 节。server 与 admin-tools 必须使用相同版本号。

Q5：Milvus 要不要直接上 3.0？
可以评估，但 LightRAG 官方 setup 模板当前锁定 2.6.11，客户端依赖 pymilvus 的版本范围也需要一并核对。生产升级前请在预发环境完成灌注与检索回归。

Q6：换成 pg18 后数据“消失”了？
pg18 官方镜像调整了数据目录结构，挂载点需要改为 /var/lib/postgresql。本工程统一使用 pg17 以避免这个问题；升级到 pg18 时请按官方说明调整卷挂载并做数据迁移。

Q7：可以中途更换 Embedding 模型吗？
不可以。维度写入向量表结构后不可变更，即使维度相同，不同模型的向量空间也不兼容。更换模型必须清空并全量重建，这也是“原始文档是唯一真源”的原因。

Q8：容器内访问宿主机 Ollama 失败？
Linux 上需要 extra_hosts: host.docker.internal:host-gateway（工程已配置），并确保 Ollama 监听 0.0.0.0（设置 OLLAMA_HOST=0.0.0.0 后重启）。macOS 与 Windows 的 Docker Desktop 原生支持该主机名。

Q9：实体抽取结果里大量 Other 类型？
检查 ENTITY_TYPE_PROMPT_FILE 是否生效：文件是否位于 PROMPT_DIR/entity_type/ 下，当前抽取模式所需的示例段是否存在。修改画像后需要重灌才对已有文档生效。

Q10：诊断报告的 matched_tsb 被置空了？
这是引用落地校验的第二道闸门在起作用：模型给出的 TSB 编号没有出现在任何检索证据中。先用 /api/v1/knowledge/search 检查该通告能否被检索到，再检查通告文档是否已入库、编号书写是否规范。

Q11：登录防爆破在多 worker 部署下不准？
计数器存在进程内存中，多个 worker 各自计数，有效阈值会被放大。严格的限流应放在 API 网关或 WAF 层。

Q12：未部署 Reranker 时每次查询都有告警？
QueryParam.enable_rerank 的默认值取自 RERANK_BY_DEFAULT，未设置时为 true。未部署 Reranker 时可以在 LightRAG 配置中设置 RERANK_BY_DEFAULT=False，或在请求中显式传入 "enable_rerank": false。

Q13：mem0 初始化失败会影响诊断吗？
不会。记忆模块在任何异常下都降级为空记忆，/ready 接口会显示 memory: failed。常见原因是 Milvus 尚未就绪或 Ollama 不可达。

Q14：Langfuse 看不到 trace？
确认三点：Langfuse 已启动且可以用 admin@vd.local 登录；diag-agent 的 /ready 显示 tracing: true（密钥已配置）；容器内 LANGFUSE_BASE_URL 指向 http://host.docker.internal:3000。trace 为批量异步上报，通常有数秒延迟。

附录 D　v1 → v2 迁移步骤

  1. 备份并停止 v1：make down。v1 的 Embedding 仍为 bge-m3（1024 维），向量数据理论上可复用，但 v2 引入了领域实体类型画像与新的切分策略，建议全量重建以获得完整收益。
  2. 更新配置：以 v2 的 .env.example 为模板重建根 .env，重点修改 LLM_MODEL=deepseek-flash；新增 STACK_PROFILE、DIAG_ENGINE、MAX_EVIDENCE_ROUNDS、APPROVAL_TIMEOUT_MINUTES。
  3. 替换部署文件：使用 v2 的 docker-compose*.yml 与 deploy/ 目录。Temporal 从 auto-setup 切换到新模式后使用新的数据库初始化流程，旧的 Temporal 数据库可以直接丢弃（POC 无需保留历史工作流）。
  4. 调整调用方：把 GET /documents 改为 POST /documents/paginated；把 DELETE /documents 的按 ID 删除用法改为 DELETE /documents/delete_document；Agent 取证从 /query + only_need_context 改为 /query/data。
  5. 重建知识库：make clean && make up && make ingest，然后执行 make eval 与 make eval-e2e，与 v1 结果对比。
  6. 接入新能力：按需启用 Langfuse（make langfuse-up）、DeepAgents 引擎（DIAG_ENGINE=deepagents）、lite 档位（make up PROFILE=lite）。

本指南与配套工程随上游版本持续演进。升级任一组件前，请先在预发环境运行 make test、make eval 与 make eval-e2e 完成回归。
