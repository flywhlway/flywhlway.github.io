2026 年 9 月 Agent OS 主流技术框架与路线调研报告

截至 2026 年 9 月底，梳理自称 Agent OS 的五条技术路线，对比运行时、沙箱、协议、记忆、治理五组件的主流做法与产品现状…

Flywhl 24 分钟 发布于 2026.09 #MCP#行业洞察#Agent

先读结论

  1. Agent OS 截至 2026-09 仍是五条路线的命名权之争，不是边界统一的产品类别；各路线共享运行时、沙箱、协议、记忆、治理五组件。
  2. 真正收敛的是协议层：MCP 成为工具层事实标准，A2A v1.0 成为 Agent 间协作标准；microVM 隔离与 OpenTelemetry GenAI 语义约定是趋同的基础设施实践。
  3. OpenAI Agent Builder 关停、AutoGen 并入 Agent Framework、Google 产品线合并，押注单一平台的风险在上升，选型应优先看协议开放性与可迁移性。
  4. 安全与授权是最大的未解风险：MCPTox 平均攻击成功率 36.5%，Agent 能力的增长快于其安全与授权模型的成熟度。

摘要

截至 2026 年 9 月，“Agent OS” 仍不是一个业界公认的、有统一边界的操作系统级产品类别，而是五条路线争夺同一命名权的战场：①模型厂商的 agent runtime/harness；②云厂商的托管 agent 基础设施；③开源框架的“OS 化”演进；④以 MCP 为中心的协议中间层；⑤为 agent 设计的 OS 内核 / 终端派。真实收敛发生在协议层与基础设施层：MCP（2026-07-28 规范，已捐 Linux Foundation 旗下 AAIF）与 A2A（v1.0.0，2026-03-12）成为事实标准，执行沙箱以 microVM 为“最小可接受隔离级别”，可观测性以 OpenTelemetry GenAI 语义约定为默认底座。

本轮调研中，时间点最晚的证据为 2026-09-29（AWS 中国区 Bedrock AgentCore 可用性新闻、SOSP 2026 AgenticOS workshop），报告内容的时间基准为 2026 年 9 月底。

三条最值得记住的判断（详见分节）：

  1. 选型已从“框架之争”变为三层分工：托管运行时（治理/身份/规模化）+ 代码优先框架（控制力）+ 安全沙箱（执行隔离）；从架构要素看则是五组件——运行时 + 沙箱 + 协议 + 记忆 + 治理。两种表述是同一事物的“按交付层看”与“按组件看”两个视角。
  2. 最大结构性事件是统一收编 + 关停低代码画布：OpenAI Agent Builder 官方宣布 2026-11-30 关停，AutoGen 并入 Microsoft Agent Framework，Google 把 Agent Builder/Agent Engine/ADK 统一为 Gemini Enterprise Agent Platform。
  3. 安全是当前主要矛盾：MCPTox 实测平均攻击成功率 36.5%、对 o1-mini 最高 72.8%（AAAI-26），且能力更强的模型反而更易被攻破；OpenClaw/ClawHub 技能生态爆发供应链攻击 ClawHavoc。

报告未覆盖的范围（已知局限）：浏览器/Computer-Use 运行时、企业 RPA 的 agent 化、中国厂商中的百度/智谱/Kimi/MiniMax、日韩欧厂商、EU AI Act 等监管一手材料、以及任何跨方案的成本与延迟基准——这些均为本轮调研的缺口，已在正文相应位置标注“需验证”。

证据说明：本报告区分官方一手材料、基金会/厂商自宣口径与第三方评测/媒体转述三类来源。凡未能交叉确证的数字，均在文中明确标注“未能确证”。

一、五条技术路线：谁在自称 Agent OS

需要先说明方法论限制：检索中没有任何单一权威来源系统性地把“Agent OS”归纳为几条路线；下述划分是基于多来源交叉归纳的结果，属本报告的分析框架，而非某来源原文。该划分并非互斥——它混用了“供应方类型 / 部署形态 / 抽象层”三种切分维度，因此路线之间必然重叠（例如 AWS AgentCore 同时属于路线 2 与路线 4 的落地载体）。更准确的理解方式是两个正交轴：横轴 = 抽象层（协议 → 框架 → 运行时 → 内核/OS），纵轴 = 交付形态（自托管开源 → 托管云服务）。下述五条路线只是该平面上被厂商重点营销的五个点位。

操作性定义（本报告采用）：所谓 Agent OS，指把 AI agent 的运行要素——agent loop 调度、上下文/记忆、工具接口、执行沙箱、身份与权限、可观测性——收敛为一套可复用、可替换、有明确接口边界的基础层的技术方案。这一定义不要求它真的是操作系统内核。

路线 1：模型厂商的 agent runtime / harness（“托管 agent loop”）

  • 代表：Anthropic Claude Managed Agents（2026-04-08 public beta）+ Claude Agent SDK；OpenAI Agents SDK + Responses API（Agent Builder 已宣布 2026-11-30 下线）；Google ADK 2.0 + Managed Agents（Google I/O ‘26）。
  • 官方口径：Anthropic 工程博客提出“拆解 brain 与 hands”，把 session / harness / sandbox 虚拟化为可独立替换的接口，使 container 变为 “cattle”（可弃置）。
  • 来源：Anthropic 官方 https://www.anthropic.com/engineering/managed-agents ；第三方 https://www.vibecodingacademy.ai/blog/claude-managed-agents-guide ；https://virtualizationreview.com/articles/2026/05/19/google-io-26-fills-out-enterprise-agent-stack-with-managed-agents-adk-2,-d-,0.aspx

路线 2：云厂商托管 agent 基础设施

  • 代表：AWS Bedrock AgentCore（Runtime/Gateway/Identity/Memory，2025-10 GA，2026-09-29 中国区可用）；Google Gemini Enterprise Agent Platform（Cloud Next ‘26 由 Vertex AI Agent Builder 改名）；腾讯云 Cube 沙箱（2026-04 开源）。
  • 官方口径：“不用自己拼 runtime、工具层、memory、identity”。
  • 来源：https://aws.amazon.com/bedrock/agentcore ；https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform ；中国区 https://www.prnasia.com/story/549909-1.shtml ；Cube https://www.infoq.cn/article/40UQ0beY3L25lo1rWVzb

路线 3：开源框架“OS 化”演进

  • 代表：OpenClaw（第三方称 2026-03 前后 star 超越 React，但具体 star 数未能确证，媒体报道数值从 248k 到 355k 互相矛盾）；学术侧 AIOS（AGI Research，把 LLM Agent OS 内核拆为 scheduler / context / memory / tool / access manager）。
  • 来源：AIOS 官方 https://github.com/agiresearch/AIOS ；论文 https://arxiv.org/html/2403.16971v5 ；OpenClaw 媒体口径 https://www.ayautomate.com/blog/openclaw-open-source-ai-agent

路线 4：以 MCP/工具协议为中心的中间层

  • 代表：MCP、A2A/ACP/UCP；治理层 MCP Gateway（Gravitee、Snowflake、Stacklok 等）。
  • 口径：“AI 的 USB-C”；第三方称 MCP 月 SDK 下载 9700 万、5800+ server（第三方博客口径，2026 年中），但官方口径为 >10,000 个活跃公共 server、约 97M/月 SDK 下载（Py+TS，2026-02/03）——两者为不同时点、不同统计口径，均未能由独立权威源交叉确证。Datadog 称 MCP 工具调用自 2025Q4 增长 22 倍（未找到原始报告，需验证）。
  • 来源：协议地图 https://www.digitalapplied.com/blog/ai-agent-protocol-ecosystem-map-2026-mcp-a2a-acp-ucp ；Snowflake https://www.snowflake.com/en/blog/engineering/enterprise-mcp-gateway-ai-agent-governance

路线 5：为 agent 设计的 OS 内核 / 虚拟机派

  • 代表：学术 AgenticOS @ SOSP 2026（第 2 届 “OS Design for AI Agents” workshop，2026-09-29 布拉格，含 HARNESS workshop）；终端侧 HarmonyOS 7 / 荣耀 Agentic OS（2026-06-24 MWC 上海）、阶跃星辰原生 Agent OS、openEuler 超节点 OS；企业侧阿里 ANOLISA（2026-03，仅中文媒体转述，无官方一手材料确证）。
  • 官方/媒体口径：“从应用的容器变成智能体的舞台”“60 年来最大一次 OS 范式重构”。
  • 来源：https://os-for-agent.github.io ；https://sigops.org/s/conferences/sosp/2026/workshops.html ；荣耀 https://www.honor.com/cn/news/honor-agentic-os

小结：路线 1、2 是“托管”思路（把运行时变成云服务），路线 3、5 是“内核化”思路（把框架/设备抽象成 OS），路线 4 是“协议化”思路（用标准而非 OS 来解耦）。三者在 2026 年的实际形态高度重叠——大多数所谓 Agent OS，本质是“运行时 + 沙箱 + 协议 + 记忆 + 治理”的组合。

本报告识别到的可能遗漏方向（本轮未充分取证，标记为待补）：

  • 浏览器 / Computer-Use 运行时：以浏览器为 agent 执行环境的一派（含 GUI 自动化），在架构上介于路线 2 与路线 5 之间，本轮仅间接接触到，需验证其在 2026-09 的代表方案。
  • 企业 RPA 厂商的 agent 化：传统 RPA 平台向 agent 演进，可能与 Agent OS 直接竞争企业流程市场，本轮未覆盖。
  • 中国厂商覆盖不全：仅覆盖腾讯、阿里、字节、华为/荣耀、阶跃星辰；百度、智谱、Kimi、MiniMax 等本轮未检索。
  • 非英语世界空白：日、韩、欧厂商方案本轮未覆盖。

二、关键架构组件的当前主流做法

2.1 上下文与记忆：从“塞 prompt”到文件系统式与 OS 式分层

  • 文件系统式记忆成为主流：Anthropic memory tool + context editing（官方工程博客）。
  • 压缩/修剪/分层为普遍工程实践：Manus 公开其上下文工程经验。
  • OS 式分层记忆：Letta 的 core memory ≈ RAM / archival memory ≈ 磁盘。
  • 框架竞争格局：Mem0 / Zep(Graphiti) / Letta / Cognee。
  • 来源：https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents ；https://manus.im/zh-tw/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus ；https://agentmarketcap.ai/blog/2026/04/11/agent-memory-architecture-production-2026

2.2 执行沙箱：microVM 是生产级下限（业界倾向，非成文规范）

  • 多个第三方评测与厂商工程文章倾向：Firecracker microVM 是生产级最小可接受隔离级别，配合 gVisor、容器与快照恢复（E2B 冷启动约 150ms）。
  • 须注意：本判断来自厂商博客与第三方评测的趋同看法，而非任何标准组织的规范；容器派（含 K8s 生态）与 WASM/WASI 派仍在大量使用，4.4 节列出的 WASM Component、Sysbox 即为并存的替代方案。
  • 代表产品：E2B、Modal、Daytona、Cloudflare、Blaxel（多按 CPU/内存计价）；K8s 生态亦有 agent-sandbox/CRD 类方案（需验证其在 2026-09 的成熟度）。
  • 注意：该类对比多来自厂商博客与第三方评测，非权威规范，需谨慎引用。
  • 来源：https://www.digitalapplied.com/blog/ai-agent-sandboxing-isolation-patterns-2026 ；https://northflank.com/blog/how-to-sandbox-ai-agents ；https://blog.logrocket.com/comparing-ai-agent-sandbox-platforms-e2b-modal-daytona-and-more

2.3 工具调用与权限治理：MCP + Gateway + Identity + 风险分级审批

  • 组合形式：MCP 作为工具接口 → MCP Gateway 作治理层 → Identity/OAuth 作凭证层（AWS AgentCore Identity；PwC agent OS 用 MCP 做策略对齐访问）。
  • 风险分级审批进入产品：Claude Code 的 YOLO classifier 分三档（放行 / 软拒 / 硬拒）。
  • 来源：https://www.pwc.com/us/en/services/ai/agent-os.html ；https://m.36kr.com/p/3749464991187458

2.4 多 agent 编排：Lead agent + 并行 sub-agent + 上下文隔离

  • 一个被广泛推荐（但无行业统计支撑）的模式是 orchestrator / sub-agent 两层结构，sub-agent 运行在独立子进程与独立文件系统中以隔离上下文（Anthropic research system 与 Claude Agent SDK subagents）。
  • ⚠️ 本报告未能找到独立量化数据证明“orchestrator/sub-agent 已是工业主流”，只能说它被主要厂商作为推荐架构反复宣传。
  • 来源：https://tech-insider.org/au/how-to-use-claude-agent-sdk-2026 ；https://arxiv.org/html/2604.14228v1

2.5 可观测性：OpenTelemetry GenAI 语义约定成为默认底座

  • LangChain、MLflow、Arize Phoenix、LangWatch 均已 OTel-native。
  • 来源：OpenTelemetry 官方 https://opentelemetry.io/blog/2025/ai-agent-observability ；https://www.langchain.com/resources/agent-observability

2.6 记忆与沙箱的补充说明

  • 2.1 节的“文件系统式记忆成为主流”同样属于从厂商实践反推的倾向判断，而非行业统计；单一来源（Anthropic 工程博客）不足以支撑“主流”一词，此处按“主要厂商已采纳的做法”理解。
  • 2.3 节的风险分级审批（Claude Code YOLO classifier）为单一产品特性，不代表行业已普遍实现。

3.3 开源/独立框架

  • LangGraph：有状态图 + checkpoint，最成熟的生产级编排；开源 + LangGraph Platform 托管（约 $35/月或按节点计量）。
  • CrewAI：角色化协作，上手最快，但 MCP 原生支持滞后。
  • AutoGen：已并入 Microsoft Agent Framework，转维护模式。
  • Claude Agent SDK / OpenAI Agents SDK / Mastra / Strands：原生支持 MCP。
  • 协议侧：MCP 是事实标准；A2A 一年内超 150 组织，深度嵌入 Google/Microsoft/AWS（数字为基金会自宣口径）。
  • 来源：https://www.truefoundry.com/blog/langgraph-pricing ；https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year

3.4 选型分界线（三条）

  1. 云绑定深度 vs 数据主权：已在单一云深度集成、看重身份/治理/规模化 → 该云托管运行时（AgentCore / Foundry Agent Service / Gemini Enterprise Agent Platform）；跨云、要数据主权或成本可控 → 开源自托管（LangGraph / AgentScope / Dify CE / Coze Studio）。
  2. 交付速度 vs 控制力 vs 关停风险：弱代码团队要可视化快交付 → Coze / Dify / Copilot Studio / 百炼，但须接受锁厂与平台关停风险（OpenAI Agent Builder 2026-11-30 关停即为反例）；要精细控制循环/状态/拓扑 → 代码优先框架（显式图选 LangGraph，角色协作选 CrewAI，Claude/MCP 生态选 Claude Agent SDK，微软栈选 Agent Framework，Google 栈选 ADK）。
  3. 编排与安全执行解耦：把沙箱运行时（E2B / Modal / Daytona / Cube Sandbox / OpenSandbox）作为独立一层，不要与编排框架耦合。

⚠️ 本节多数对比来源为厂商博客或第三方评测，“成熟度/短板”判断带有主观色彩；GA 时点与区域限制建议以各厂官方文档为准。

三点五、实践维度：成本、延迟、锁定与合规

上文偏重架构，但选型的实际成败常取决于四个被营销材料系统性忽略的维度。

成本

  • 本报告只检索到两处可引用的价格锚点：LangGraph Platform 约 $35/月或按节点计量（第三方博客口径）；沙箱产品（E2B/Modal/Daytona）多按 CPU·内存·时长计价。
  • 托管运行时的成本模型（按 token、按 vCPU·s、按 agent 会话）与自托管的 TCO（GPU、运维、沙箱基础设施）缺乏公开可比数据，本报告未能确证任何跨方案成本对比。这是本轮调研最大的数据缺口，建议在具体 POC 中自建测算。

延迟

  • 仅一处可用锚点：E2B 沙箱冷启动约 150ms（第三方口径）。
  • Agent 端到端延迟主要由模型推理而非运行时基础设施决定；沙箱冷启动与快照恢复在交互式场景中是关键变量，但未找到跨厂商延迟基准。

供应商锁定与迁移风险

  • 2026 年最具说服力的证据不是论证而是事实：OpenAI Agent Builder 与 Evals 官方宣布 2026-11-30 关停；AutoGen 并入 Agent Framework 转维护模式；Google 三条产品线合并更名。低代码平台与已被整合的框架存在实质关停/迁移成本。
  • 相对而言，协议层（MCP/A2A）与沙箱层（兼容 E2B 接口者有 Cube Sandbox 等）的可迁移性更高；把编排逻辑写在开放协议上的自托管框架，迁移成本最低。
  • ⚠️ 各方案的具体迁移工作量无公开量化数据，未能确证。

合规与监管

  • ⚠️ 本报告在本轮检索中未能获得关于 EU AI Act 对 agent 系统具体适用条款的一手材料，“高风险系统”义务是否覆盖 agent 运行时/沙箱，需另行验证。
  • 可确证的相邻动向：NIST 在沙箱隔离边界的讨论中被第三方文章引用（未能定位 NIST 原始文件，需验证）；FIDO Alliance 已于 2026-04-28 成立 Agentic Authentication TWG，属身份合规方向的实际动作。
  • 结论：把合规当作选型硬约束的条件尚不成熟，因标准本身仍在制定中；但身份/授权类标准（FIDO、IETF 草案）值得提前跟踪。

四、标准化协议与生态：MCP 与 A2A 的收敛与残留分裂

4.1 MCP：事实上的工具层标准，已中立化治理

  • 版本（可确证）：最新规范为 2026-07-28，是自 2024-11 发布以来最大一次修订（RC 自 2026-05-21）。核心变化：无状态协议核心（可在普通 HTTP 基础设施上水平扩展）、多轮往返请求 MRTR、OAuth 2.1 授权加固、可缓存列表结果；四大 Tier-1 SDK（TS/Python/Go/C#）同日发布。Cloudflare 的工程博客也从边缘基础设施视角确认了“无状态化 + 可水平扩展”是本版规范的核心取向（https://blog.cloudflare.com/mcp-v2）。
  • 治理（可确证）：Anthropic 于 2025-12-09 将 MCP 捐给 Linux Foundation 下的 Agentic AI Foundation（AAIF），MCP 为创始项目（另有 Block 的 goose、OpenAI 的 AGENTS.md）。
  • 扩展（可确证）：MCP Apps（2026-01-26，首个官方扩展，允许 server 返回 iframe 沙箱内的交互 UI）由 MCP 与 OpenAI 联合开发。
  • 采纳：官方口径 >10,000 个活跃公共 server、约 97M/月 SDK 下载（Py+TS，2026-02/03）；OpenAI 于 DevDay 2025-10 采纳；覆盖 ChatGPT、Gemini、Microsoft Copilot/VS Code、GitHub、Cursor、Vercel 等。
  • 来源：https://blog.modelcontextprotocol.io/posts/2026-07-28 ；https://blog.cloudflare.com/mcp-v2 ；https://www.anthropic.com/news/donating-the-model-context-protocol-and-establishing-of-the-agentic-ai-foundation ；https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation ；https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps

4.2 MCP 安全：当前生态的主要矛盾（可确证）

  • MCPTox（AAAI-26）：在 45 个真实 server、20 个模型上测得平均攻击成功率 36.5%，对 o1-mini 最高 72.8%，且能力更强的模型反而更易被攻击。
  • OWASP 已发布 MCP Top 10（含 MCP03:2025 Tool Poisoning）。
  • CSA 记录 Cursor 的 CurXecute（CVE-2025-54135，CVSS 8.6）。
  • 来源：https://arxiv.org/html/2508.14925v1 ；https://ojs.aaai.org/index.php/AAAI/article/view/40895 ；https://owasp.org/www-project-mcp-top-10/2025/MCP03-2025%E2%80%93Tool-Poisoning ；https://labs.cloudsecurityalliance.org/research/csa-research-note-mcp-tool-poisoning-auto-execution-20260701

4.3 A2A：Google 提出、已捐基金会、有生产落地但“非普遍必需”

  • 治理（可确证）：由 Google 提出，2025-06 捐给 Linux Foundation（A2A Project）。
  • 成熟度（可确证版本）：v1.0.0 于 2026-03-12，v1.0.1 于 2026-05-28。一周年（2026-04-09）宣布 >150 组织支持、Google/Microsoft/AWS 深度集成、已有生产用例（属基金会自宣口径）。
  • 分工（业界共识，非规范强制）：MCP = agent ↔ 工具/资源；A2A = agent ↔ agent、跨代码库协作。注意批评声：不少 2025 demo 并不需要 A2A，其必要性被指抽象。
  • 竞争协议被“收编”而非并存：IBM 的 ACP 于 2025-08 与 Google 的 A2A 合并入 Linux Foundation（LF AI & Data）；ANP、AG-UI 属互补层。
  • 来源：https://developers.googleblog.com/en/google-cloud-donates-a2a-to-linux-foundation ；https://www.linuxfoundation.org/press/linux-foundation-launches-the-agent2agent-protocol-project-to-enable-secure-intelligent-communication-between-ai-agents ；https://www.ibm.com/think/topics/agent-communication-protocol

4.4 身份、支付与互操作标准

  • 支付/身份（可确证）：Google 的 AP2（2025-09，typed mandates，三角色）已于 2026 捐给 FIDO Alliance；Mastercard 联合的 Verifiable Intent（AP2 兼容）同捐 FIDO；FIDO Alliance 于 2026-04-28 成立 Agentic Authentication TWG。另有 Shopify + Google 的 UCP（2026 初），与 AP2 分工（UCP 管“订什么/向谁订”，AP2 管“谁授权 + 审计”）。
  • IETF（工作稿级，尚未成 RFC）：draft-klrc-aiagent-auth-00（2026-03，AWS/Zscaler/Ping 等作者，主张 agent 即 workload、用 WIMSE/SPIFFE ID + 短期凭证）；以及 OAuth on-behalf-of、AAuth、draft-ietf-oauth-spiffe-client-auth 等。
  • W3C（社区组级）：AI Agent Protocol CG、AI Agent Memory Interoperability CG（1.0 charter 2026-06-19 通过）、WebAgents CG 互操作报告；2026-09-08/09 与 GS1 合办 “E-Commerce for Humans and AI Agents” 研讨会。正式规范为预期 2026–2027，非既成事实。
  • 沙箱/代码执行：以 microVM / WASM Component(WASI) / Sysbox 为主，无跨厂商统一规范（此项“未能确证”存在标准）。
  • 来源：https://blog.google/products-and-platforms/platforms/google-pay/agent-payments-protocol-fido-alliance ；https://fidoalliance.org/fido-alliance-to-develop-standards-for-trusted-ai-agent-interactions ；https://shopify.engineering/UCP ；https://www.ietf.org/archive/id/draft-klrc-aiagent-auth-00.html ；https://www.w3.org/groups/cg/agentprotocol ；https://www.w3.org/community/ai-agent-memory-interop

4.5 现实安全事件：技能/工具供应链攻击（可确证）

  • ClawHavoc（2026 初）：OpenClaw / ClawHub 技能生态供应链攻击，称 1,100+ 恶意技能；Bitdefender 称早期约 17% 技能含恶意载荷（第三方口径，原始报告未定位，需验证）；Snyk “ToxicSkills” 扫描 3,984 个技能，13.4% 恶意、36% 含提示注入。
  • 来源：https://unit42.paloaltonetworks.com/openclaw-ai-supply-chain-risk ；https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub ；https://www.ibm.com/think/x-force/what-openclaw-reveals-about-agentic-ai-security-risks

五、未收敛的争议点

  1. “Agent OS 是否真需求、该如何定义”：批评方指它是“means everything and nothing”的 buzzword，各厂商都自称 Agent OS；辩护方（Data Science Dojo）认为它是真实架构模式而非具体产品。⚠️ 需注意：本报告所引“辩护方”来源本身带有推广性质，批评方亦未被指名到具体权威机构，此争议的权威取证仍需补充。
    来源：https://datasciencedojo.com/blog/agentic-os-architecture ；https://www.requesty.ai/blog/the-rise-of-the-agent-operating-system
  2. “上下文工程 vs RAG”：2026 主流收敛为互补而非对立——context engineering 是更上层的策展学科，RAG 是其内部检索组件；但“long context 是否让 RAG 过时”的争论持续（position bias、成本、更新频率）。
    来源：https://atlan.com/know/context-engineering-vs-rag ；https://www.elastic.co/search-labs/blog/rag-vs-long-context-model-llm
  3. 沙箱隔离粒度：容器（轻，但共享内核；有第三方文章引 NIST 指其边界不清，未定位 NIST 原始文件）vs microVM（强隔离，但有启动/存储开销）。microVM 建设成本高是被反复提及的痛点。
    来源：https://www.infoq.cn/article/40UQ0beY3L25lo1rWVzb ；https://manveerc.substack.com/p/ai-agent-sandboxing-guide
  4. 评估标准缺失 + “agent washing”：多个第三方来源称“怎么评估 agent 好不好，行业还没有标准”；有二次转述称 Gartner 2026 将 agentic AI 置于 hype peak，“agent washing” 真实存在（Gartner 原始报告未定位，需验证）。
    来源：https://pixelmoksha.com/blog/the-rise-of-agentic-ai-why-2026-is-being-called-the-agent-era ；https://www.kore.ai/blog/ai-agents-in-2026-from-hype-to-enterprise-reality
  5. 身份与授权的收敛点不明：AP2 与 UCP（Google 系）、FIDO 的 Verifiable Intent、IETF 的 OAuth/SPIFFE 草案并存，谁最终胜出尚不明朗。

七、核心结论

  1. “Agent OS” 截至 2026-09 仍是命名权之争，而非成熟产品类别。五条路线（模型厂商 runtime、云托管基础设施、开源框架 OS 化、协议中间层、OS 内核/终端派）共享同一套组件：运行时 + 沙箱 + 协议 + 记忆 + 治理。
  2. 真正收敛的是协议层：MCP（2026-07-28 规范，AAIF/Linux Foundation 治理）成为工具层事实标准，A2A v1.0.0 成为 agent 间协作标准，ACP 被合并收编。需注意两点限定：其一，“事实标准”指的是生态采纳广度，而非规范强制力；其二，厂商私有的工具接口仍在头部产品内部存在（如 Claude Agent SDK 强绑定 Claude 生态），只是对外的新增工具集成已普遍以 MCP 为入口。
  3. 工程共识集中在基础设施层（但多为趋同实践，非成文规范）：microVM 作为生产级隔离下限、文件系统式/分层记忆、orchestrator + sub-agent 上下文隔离、OpenTelemetry GenAI 语义约定作可观测性底座。这些是主要厂商的趋同做法，没有标准组织背书。
  4. 最大变化是格局收编：OpenAI 砍掉低代码画布（Agent Builder 2026-11-30 关停）、AutoGen 并入 Agent Framework、Google 三产品线合并——“选择平台”的长期风险显著上升，选型应优先考虑协议开放性与可迁移性。
  5. 最大未被解决的风险是安全与治理：MCPTox 平均 36.5% 攻击成功率（对 o1-mini 最高 72.8%）、ClawHavoc 事件、OWASP MCP Top 10、FIDO/IETF 身份标准尚未定型——2026 年的 Agent OS 能力增长快于其安全与授权模型成熟度。
  6. 建议的落地姿态：编排层用代码优先框架（保留可迁移性）+ 沙箱独立解耦（不绑编排）+ 协议层锁定 MCP/A2A + 记忆与可观测性按开放标准实现；避免把核心资产押在会被关停的厂商低代码平台上。
  7. 成本与合规是本报告的空白：所有公开材料都缺跨方案成本/延迟基准，且 EU AI Act 对 agent 的适用条款本轮未取得一手材料。任何基于本报告的预算与合规决策都必须用自有 POC 与法律意见补足。
