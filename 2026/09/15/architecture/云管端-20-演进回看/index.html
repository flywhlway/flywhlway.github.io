站在 2026 年回看云管端 AI Agent 平台：哪些判断成立，哪些需要修订

用 2025 年下半年到 2026 年 9 月的公开事实…

Flywhl 15 分钟 发布于 2026.09 #云管端#架构设计

先读结论

  1. 治理优先、上下文优先、MCP 加 A2A 双协议这些主干判断成立；变化集中在实现方式和风险边界。
  2. Skill 自研格式、前缀缓存零成本两条被推翻：前者让位于 Agent Skills 开放标准，后者遇到显式断点缓存与写入溢价。
  3. 注册中心与 AI 网关从自研转为采用开源；安全边界从运行时注入扩展到技能市场与网关依赖的供应链。
  4. 需要重开 ADR-03、ADR-04、ADR-10、ADR-11，另新增 Skill 标准、长程运行时、供应链准入三条 ADR。

回看的口径

这个系列的 00–18 篇写于 2025 年 8 月到 12 月，19 篇在 2026 年 1 月收束，知识面停在 2025 年年中，前提是 MCP 与 A2A 双协议。本篇写于 2026-09-15，只做一件事：拿这一年里可以查证的公开事件，逐条检验当时的判断，并给出具体的架构改动。

每条判断的结论分三种：

  • 成立：方向与事实一致，架构不用改。
  • 修订：方向对，但实现方式、边界或风险性质变了，要改模块或 ADR。
  • 推翻：判断本身被事实否定，要撤回。

凡是我根据事实推出来的判断，正文都写成建议，不写成事实。端侧 SLM 与落点决策这一年没有出现足以改变判断的公开事件，本篇不单列。

八个修订点

1. 协议层：MCP 按规范版本管理，去掉会话与 Sampling 假设

发生了什么：MCP 进入 AAIF 之后，治理中立了，但版本没有变慢。2026-07-28 版去掉会话机制，Roots、Sampling、Logging 被废弃，这是一次破坏性演进。Spring AI 2.0 已经把 Streamable HTTP 设为默认传输。

对原判断的影响：ADR-03 当时担心”规范波动”，这个担心仍然成立，只是性质变了：不再担心押错厂商，而是要持续跟进一个会删功能的中立标准。

架构改动：

  • 注册中心给每个 MCP Server 记录适配的规范版本与传输方式；网关按版本做兼容与告警，旧版本接入列出迁移期限。
  • 网关与 Agent 运行时不再依赖 MCP 会话做粘性路由或保存状态，状态放回运行时自己的检查点。
  • 依赖 Sampling 的 Server（让客户端代为调用模型）需要改造。改造后 Server 若自己调模型，必须经 LLM 网关，否则会在 MCP Server 里长出新的旁路调用，违反”先收口”原则。
  • 依赖 Logging 的 Server，日志改走 OTel 埋点。

重开：ADR-03，补充”规范版本跟进策略”与”废弃特性迁移清单”。

2. 能力单元与注册中心：Skill 采用开放标准，注册中心只自研治理层

发生了什么：Agent Skills 在两个月内从发布走到开放标准，主流编码工具陆续支持；Nacos 3.1 与 3.2 把 MCP、A2A、Skill、Prompt 的注册都做成了现成能力；官方 MCP Registry 也已上线预览。

对原判断的影响：04 篇把 Skill 定义为”意图级的中间粒度”，这一点成立；但我当时建议”自研 Skill Registry，参考 MCP 的 tool 描述规范扩展格式”，这一条被推翻。自研格式意味着平台上的技能无法被主流 Agent 直接复用，外部技能也进不来。

架构改动：

  • Skill 的存储格式改用 Agent Skills 标准，平台特有的信息作为扩展元数据挂在标准之外：至少 10 条正例与 5 条反例、权限声明、owner 与复核周期、SLA。
  • 注册中心的存储与发现采用开源实现（Nacos 3.2 一类），自研部分收缩为治理层：准入审核、正反例校验、冲突检测、弃用流程、调用前的强制校验。
  • Prompt Registry 承接提示词的版本与灰度，19 篇”配置化换取秒级回滚”不必再自建一套配置通道。
  • 19 篇阶段三的”端云 Agent 同构（一份 manifest 双编译）”改为以标准技能包为单位分发，端侧只下发经过分档裁剪的技能子集。

重开：新增 ADR-13”能力单元采用 Agent Skills 开放标准，平台元数据以扩展字段承载”；03 篇注册中心模块改为”开源注册中心加自研治理层”。

3. 网关：唯一出口不变，能力取自开源

发生了什么：一年前自研 AI 网关插件是合理选择，因为开源方案还不完整。现在 Gateway API Inference Extension、Envoy AI Gateway（含 MCPRoute）、Higress（托管 MCP Server）都已发布正式版本或进入 CNCF，Istio 1.31 还能把 agentgateway 作为 waypoint 挂进服务网格。

对原判断的影响：ADR-04”模型访问统一走 LLM 网关”与 ADR-01”管道层是唯一跨域通道”都成立；”规模化后自研网关插件”这一条需要修订。

架构改动：

  • LLM 网关的 Token 限流、多模型路由、Fallback 与 MCP 路由改用开源网关的现成能力；自建推理的负载路由用 Inference Extension。自研只保留 model_intent 映射、成本归因与语义缓存策略。
  • 云内东西向流量（Agent 之间、Agent 到 MCP Server）交给网格 waypoint 做鉴权、限流与遥测；Agent 网关收缩为端云南北向入口和 A2A 桥接。端云之间仍然只走管道层，ADR-01 不变。
  • 存量业务 API 优先在网关侧托管为 MCP Server，替代自研适配层；但工具描述要重写成面向模型的版本，并按 04 篇的要求重新评测，不能把接口文档原样暴露。

重开：ADR-04（自研范围收缩）、ADR-11（存量接入优先走网关托管）。

4. 运行时：交互式与长程任务拆成两类运行时

发生了什么：Agent Teams 与 Dynamic workflows 让一个任务编排数十到上百个 Agent 成为可用形态；deepagents 0.7、deepseek-harness（插件化 Agent Harness）说明 Agent Harness 已经成为独立的选型对象；LangGraph 1.2 提供节点级 timeout。

对原判断的影响：07 篇默认 Agent 任务是秒到分钟级，这对车内交互仍然成立；但云端的知识运营、诊断分析、评测集生成、代码类任务，已经适合交给长程多 Agent。”外层 Workflow 加内层 Agent”和”禁止自由讨论、只用层级委派”两条仍然成立，需要修订的是”阶段一不做多 Agent”的范围与预算模型。

架构改动：

维度 交互式运行时 长程运行时
典型任务 车内问答、车控、导航 知识补全、故障归因分析、评测集生成
时延约束 首字预算 1225 ms（01 篇） 分钟到小时，无首字约束
多 Agent 形态 最多一层委派 层级委派，可并行数十个子 Agent
预算 单任务三重预算 预算树：总预算按子任务逐级分配，子任务超支上报而非自行扩额
状态 会话内存加 Checkpointer 持久化检查点，可中断、可恢复、可人工审批
副作用 只在 Workflow 节点内，二次确认 默认只读；写操作集中到收尾阶段，人工批准后执行
  • 两类运行时分资源池部署，长程任务不得挤占交互链路的模型配额。
  • 选型时评估 Harness 而不只是编排框架：看它是否支持预算树、检查点、子 Agent 的上下文隔离，以及能否把 Trace 写到 OTel。

重开：新增 ADR-14”长程 Agent 运行时独立部署，采用预算树与持久化检查点”；07 篇运行时章节按两类重写。

5. 记忆：写路径只追加，图记忆降为实体链接

发生了什么：mem0 v2.0 把抽取改为单次、只做新增（ADD-only），检索改为语义、BM25、实体三路混合，并用实体链接取代了原来的 Graph Memory。

对原判断的影响：08 篇的”事件溯源加物化视图”与这个方向一致，成立。我把这一变化理解为：在写入时判断”更新还是删除”成本高且容易出错，业界正在把冲突合并挪到读时或后台处理。需要修订的是两处：图记忆不再作为独立存储形态；记忆召回也应采用混合检索。

架构改动：

  • 记忆写路径改为只追加事件；冲突合并、失效判断放在物化视图的后台任务里做，在线读路径只读物化结果。这与”回溯干预”天然兼容：撤销一条记忆等于追加一条失效事件。
  • 召回从纯向量改为语义加关键词加实体的混合检索，实体表同时服务于 19 篇”摘要不保护实体”的反模式修复。
  • 图记忆从候选中移除，用实体链接（记忆条目到实体 ID 的关联）满足家庭成员、设备归属这类关系查询。
  • 若验证期采用了 mem0 v1.x，升级到 v2.0 是一次数据模型迁移，要按 04 篇”记忆模型退出成本为高”的预案执行：来源字段留在自有存储，框架只作抽取与召回实现。

重开：ADR-05 小修（写路径只追加、图记忆降级），不改三层划分。

6. 可观测：映射层保留，后端按可替换处理

发生了什么：OTel 本身在 2026-05 从 CNCF 毕业，但 GenAI 语义约定一年里从 v1.37 走到 v1.41，还迁了仓库，至今仍是 Development 状态。与此同时，Langfuse 被 ClickHouse 收购。

对原判断的影响：05 篇”对齐 OTel GenAI，但保留一层内部字段映射”被证明是对的：上游字段不承诺稳定，内部看板和训练样本不能直接绑定上游字段名。另一处要修订的是观测平台的退出成本：平台所有权变更之后，数据是否能完整导出、是否能换后端，要在选型时就验证。

架构改动：

  • 埋点 SDK 基于 OTel SDK 实现，映射层记录”内部字段、上游字段、语义约定版本”三元组，升级语义约定时只改映射。
  • 所有 GenAI 数据先进 OTel Collector，再分发到观测平台与数据湖；观测平台只当查询与分析前端，换平台不丢历史。
  • 埋点 Schema 新增三个字段：reasoning_effort、推理 Token 数、缓存写入 Token 数。没有这三个字段，修订点 8 的成本变化无法归因。字段口径仍以 05 篇为准。

重开：ADR-10 修订为”埋点 SDK 基于 OTel 实现，内部 Schema 经版本化映射对齐上游”。

7. 安全：准入范围扩到供应链

发生了什么：ClawHub 事件说明技能市场本身会被投毒；LiteLLM 事件更直接，它正是 04 篇列入候选、系列推荐起步期使用的那类模型网关，攻击落在平台最核心的唯一出口上。欧盟 CRA 的报告义务从 2026-09-11 起适用。

对原判断的影响：12 篇”间接注入是首要风险、三方 MCP 统一准入”仍然成立，但防线只设在运行时：内容进入上下文之后怎么隔离。现在同样危险的是另一条路径：恶意代码随技能包或依赖升级进入平台。

架构改动：

对象 准入要求
三方 Skill 包 来源白名单；内容与脚本审查；锁定版本与哈希；脚本类技能一律在沙箱执行
三方 MCP Server 沿用 12 篇的安全清单，另加版本与哈希锁定、升级重新审核
平台自身依赖（网关、SDK、Agent 框架） 私有镜像加哈希锁定；禁止生产环境直接从公共源安装或自动升级；关键组件维护 SBOM
模型与端侧包 沿用端侧下发的验签与原子切换
  • 安全应急流程增加”供应链事件”类型：发现受影响版本后，按 SBOM 定位受影响的服务与车端版本，一次性吊销相关凭据。LiteLLM 这类组件就处在网关里，接触的正是模型凭据。
  • 面向欧盟市场的产品，要提前具备漏洞与安全事件的上报流程；是否适用 CRA 需要逐个产品判定，但流程不能等判定完才开始建。

重开：新增 ADR-15”供应链准入覆盖技能包、MCP Server 与平台自身依赖”；12 篇的准入章节扩写。

8. 模型与成本：路由加上 effort，前缀缓存按成本模型管理

发生了什么：推理模型与可调 effort 成为主流模型的标配；OpenAI 自 GPT-5.6 起采用显式断点缓存，写入按 1.25 倍计价，缓存存活 30 分钟。

对原判断的影响：

  • “按难度分级用模”成立，但分级的手段多了一维：同一个模型用不同 effort，成本和时延差异显著，路由只选模型已经不够。
  • 01 篇首字预算里”模型首 token 320 ms”的前提，是模型不先长时间思考。交互链路如果用高 effort，这一项会直接击穿预算。
  • 19 篇把”Prompt 稳定内容前置”列为投入产出比最高、几乎零成本的一项。稳定内容前置本身仍然要做，但”零成本”不再成立：断点要显式管理，写入有 25% 溢价。粗略算，TTL 内被复用一次通常就能回本（取决于读取折扣）；打了断点却从不复用的前缀，就是纯损失。

架构改动：

  • model_intent 映射到”模型加 effort 档位”二元组，由网关配置决定；交互式意图默认最低档，高档只开放给长程运行时和异步任务。
  • 01 篇首字预算表注明 effort 前提，并按档位给出模型首 token 的分档预算；高档位请求不进入交互链路。
  • Prompt Builder 增加断点管理：只在系统指令、工具描述这类 30 分钟内会被多次复用的段后面打断点；以网关计量的缓存写入与读取 Token 为依据，按周复核断点收益。
  • 10 篇的缓存层次保持”前缀缓存、计量、语义缓存”的顺序，但前缀缓存从”零成本”改为”有成本模型的优化项”。

重开：ADR-04 补充”路由单元为模型加 effort”与”缓存断点由平台统一管理”。

如果今天从零开始

一年前需要自研的东西，今天大半可以直接采用。路线仍是收口、闭环、自演进三段，但每段的自研量明显下降，省下的人力应该投到治理层和闭环上。

仍然自研的只有五块：记忆中心、落点决策、边缘 Agent 框架控制面、RAG 门户与评测，这四块与 19 篇相同；新增的一块是注册中心之上的治理层。

今天起不再做的事：

  • 不自研 Skill 格式、MCP 网关与 Token 限流插件。
  • 不依赖 MCP 会话、Sampling、Logging 这些已废弃或已移除的机制。
  • 不把前缀缓存当作免费优化，断点的写入与复用都要进计量。
  • 不在生产环境直接从公共源安装技能包或升级平台依赖。
  • 不在交互链路上开高 effort。

结语

回看下来，写这个系列时押注的是”治理与上下文比模型更重要”，这一年的变化没有动摇这一点，反而把它推得更远：模型能力和 effort 档位越丰富，路由、计量、准入这些治理动作就越重要。真正需要改的，是我低估了开源基础设施追上来的速度，也把安全边界划得太靠近运行时。下一次回看，重点检验两件事：注册中心之上的治理层是否撑得住标准技能包的规模，长程运行时的预算树能否把成本控制住。
