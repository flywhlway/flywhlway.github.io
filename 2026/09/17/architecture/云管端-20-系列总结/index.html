1. 这张架构图的架构评价

1.1 整体判断

原图是一张成熟度较高的企业级 AI 平台架构。判断依据不在于它画了多少组件，而在于它把重心放在了正确的地方：

观察 判断

模型被抽象在网关之后 ✅ 模型可替换，不锁定供应商
「管」独立成泳道，含三个网关 ✅ 把网关当一等公民，而非反向代理

知识含”门户 + 评测” ✅ 认识到 RAG 是工程问题

边缘 Agent 框架画在云端层 ✅ 控制面云端、执行面端侧

2. 十条核心结论

结论 1 · 这是治理架构，不是模型架构

原图圈注的 6 处——注册中心、埋点 SDK、语义缓存与 Token 治理、记忆可视化与回溯、RAG 门户与评测、Agent 网关——没有一处是关于模型本身的。这是成熟企业 AI 平台的正确形态：模型是可替换的后端资源，平台的价值在治理、上下文、闭环。

结论 2 · 最大的效果杠杆在上下文供给，不在模型选择

记忆中心 + 知识中心 + 能力中心三者决定约 80% 的效果差异。模型换代带来的增益，通常远小于把检索、记忆、工具裁剪做扎实带来的增益。这解释了为什么”反复换模型而效果不涨”是最常见的失败模式。

结论 3 · 端侧不是降级方案，而是更优路径

端侧闭环延迟约 390 ms，云端约 1225 ms（见 06 文档）。对端侧可覆盖的意图，走端侧同时更快、更省、更私密、离线可用——收益是四重的。因此落点决策应倾向端侧，而非把端侧当兜底。

结论 4 · 可观测必须先于优化

缺 route_reason、decision_reason、empty_recall、memory_hits 这四个字段，对应的四类问题（模型选择、端云落点、知识缺口、记忆影响面）就永久无法归因。这些字段成本极低（几十字节），但事后无法补齐。

结论 5 · 安全组件不可降级，性能组件可以

缓存、知识、记忆、能力中心故障时可熔断降级；围栏与认证故障时必须拒绝服务。这条区分必须写入运维手册，否则会出现”为了可用性把围栏关掉”的重大事故。

结论 6 · AI 平台的大部分变更不是代码变更

提示词、检索参数、知识内容、Skill 描述、模型权重——这些都不是代码，但都能全量影响用户。若只对代码做门禁，就会出现”改代码要评审，改一句提示词却能直接全量上线”的失衡。非代码变更必须同样纳入门禁与灰度。

结论 7 · 配置化是为了秒级回滚

把提示词、参数、模型权重、知识版本全部配置化，其唯一目的是让效果故障的恢复时间从小时级降到秒级。这是 AI 平台最重要的运维能力，因为效果类故障远多于崩溃类故障。

结论 8 · 间接提示注入是首要安全风险

架构接入了第三方 MCP 生态，意味着外部内容会进入上下文。防御的关键是架构隔离而非检测：工具结果与系统指令物理分区、工具最小权限、危险操作强制二次确认、出网白名单。单靠检测模型永远存在绕过。

结论 9 · 最容易被低估的是记忆污染与端云一致性

这两项在 Demo 阶段完全不可见，会在上量后集中爆发（表现为”记错了”和”回答自相矛盾”）。而它们都无法事后补救：记忆污染需要 source_trace_id 才能回溯，端云一致需要单写者原则才能保证。两者必须在阶段一确定。

结论 10 · 闭环是唯一的护城河

埋点 → 评测 → 知识补全 / 训练的飞轮一旦建成，平台效果会持续拉开与”直接调 API”的差距。而在闭环的价值排序中，知识补全 > 检索与提示词调优 > 评测集建设 > 微调 > RLHF——多数团队的投入顺序恰好相反。

5. 架构评审清单

用途：技术评审会现场逐条核对。任一”否”都应记录为风险项并给出关闭计划。

5.1 收口与治理

  • 全部模型调用是否只经 LLM 网关？（代码扫描证明无散落凭据）
  • 端侧是否只经三网关访问云端？无直连内部服务？
  • 未注册的 Agent / Skill / MCP 是否会被网关与能力中心双重拒绝？
  • Skill 注册是否强制 ≥10 正例 + ≥5 反例？
  • 每个能力是否有 owner 与复核周期？是否有 Sunset 机制？
  • 存量适配层是否设定了退役日期？

5.2 可观测

  • trace_id 是否端侧生成并贯穿到训练数据？
  • llm.call 六必填属性是否齐全？
  • decision_reason / route_reason / empty_recall / memory_hits（含 ID）是否齐全？
  • 骨架 Trace 是否 100% 采集（未因成本降采样）？
  • 错误与负反馈是否 100% 保存上下文快照？
  • 是否建立了质量层与业务层指标（而非只有服务指标）？
  • 是否有降级率、单会话成本异常、质量劣化三类告警？
  • 每类观测数据是否有对应的改进闭环？

5.3 安全

  • 出站围栏是否 100% 覆盖且 fail-closed？（演练验证过拒绝服务行为）
  • 入站内容安全是否在授权与转发之前？
  • 工具结果是否与系统指令物理分区并标记为不可信？
  • 是否有出网白名单？
  • 身份是否仅从传输层凭据派生（无自报）？
  • A2A 是否传递权限交集而非原始身份？
  • 不可撤销与车控类操作是否强制多因子确认？
  • 端侧策略不可达时是否 fail-closed（收紧而非放开）？
  • 是否有红队用例集并纳入 CI？
  • 合规删除是否级联到向量索引/缓存/记忆并有验证流程？

5.4 效果与成本

  • 检索是否为混合检索（向量 + 关键词）？
  • 元数据过滤是否在检索之前？
  • 是否有 Rerank（Top-50 → 5）？
  • 是否有查询改写？
  • 是否强制引用、无据则拒答？
  • 上下文是否有硬 Token 预算与固定裁剪优先级？
  • Prompt 是否稳定内容前置（启用前缀缓存）？
  • 语义缓存键是否包含知识版本与车型等全部维度？
  • 时效性意图是否强制 bypass 缓存？
  • 是否按任务分级用模（意图分类不用大模型）？
  • cost_tag 是否强制必填？
  • 是否有单会话成本熔断？

5.5 记忆与知识

  • 记忆是否带 confidence / valid_until / source_trace_id？
  • 记忆抽取是否保守（只抽明确表达，不做推断）？
  • 是否有记忆可视化与回溯干预（含影响分析视图）？
  • 干预是否秒级生效于在线读路径？
  • 记忆是否按命名空间隔离（含隐私区不出端）？
  • 端云是否遵守单写者原则？
  • 是否有三套评测集且盲测集由独立角色维护？
  • 是否有空召回 → 知识缺口工单的闭环？

5.6 可靠性与运维

  • 降级矩阵是否明确区分”可降级”与”不可降级”组件？
  • 配置类变更是否可秒级回滚？
  • 长连接是否实现三段式优雅下线？
  • 围栏是否与网关同 PriorityClass 与 PDB 联动？
  • 训练与推理是否物理隔离 GPU 节点池？
  • 是否有预留缓冲副本与定时预扩容？
  • 端侧下发是否满足六铁律（原子/验签/保留旧版/自检/灰度暂停/避开行驶）？
  • 数据湖格式是否支持行级删除？
  • 故障演练清单是否按月/季执行（含”围栏不可用”）？

7. 最后一句

这套文档的价值不在于它描述了一个架构，而在于它把架构图里那些”画在那里但没说为什么”的判断显式化了：为什么网关要分四个、为什么围栏在网关之后、为什么边缘框架画在云端、为什么记忆需要回溯干预、为什么 RAG 需要门户与评测。
