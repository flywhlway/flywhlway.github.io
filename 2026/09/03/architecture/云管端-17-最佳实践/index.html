1. 落地的第一性原则

从这张架构图与全套分析中，可以提炼出五条对落地成败影响最大的原则：

# 原则 一句话解释 违反的典型代价
1 先收口，再优化 所有 AI 流量必须先经过统一网关与注册中心，才有资格谈成本、质量、安全 旁路调用一旦形成，事后收口需推动数十个团队改造，通常失败
2 上下文质量 > 模型选择 记忆 + 知识 + 能力三者决定 80% 效果差异 反复换模型而效果不涨，浪费半年
3 可观测先于优化 没有 route_reason / decision_reason / empty_recall，任何优化都是盲调 优化靠猜，改动无法证明有效
4 配置化换取秒级回滚 提示词、参数、模型权重、知识版本全部配置化 效果故障恢复时间从秒级变成小时级
5 安全不可降级，性能可以 围栏与认证故障时拒绝服务；缓存知识记忆可熔断 为了可用性关掉围栏，引发合规事故

2.2 自研 vs 采购的判断标准

flowchart TB
    Q["某能力是否自研?"] --> Q1{"是否是差异化竞争力?"}
    Q1 -->|"是"| SELF["自研<br/>如：记忆回溯干预、落点决策、端侧框架"]
    Q1 -->|"否"| Q2{"开源方案是否满足 80% 需求?"}
    Q2 -->|"是"| OSS["用开源 + 定制插件<br/>如：网关、向量库、推理引擎"]
    Q2 -->|"否"| Q3{"商用方案成本是否可接受?"}
    Q3 -->|"是"| BUY["采购<br/>如：ASR/TTS、内容安全"]
    Q3 -->|"否"| SELF2["自研（但要评估长期维护成本）"]

本架构中明确建议自研的四项（因为它们是差异化能力且开源方案不满足）：

能力 为什么必须自研
记忆中心（含可视化与回溯干预） 事件溯源 + 命名空间隔离 + 端云同步是强定制需求（见 08 文档 8.1）
落点决策（端/云） 完全是本架构特有逻辑，无现成方案
边缘 Agent 框架（控制面） 端侧能力编译与分档下发是业务特化
RAG 门户与评测 与业务知识运营流程深度绑定

3. 分阶段落地路径

3.1 阶段一：收口（0–6 月）

目标：让所有 AI 流量可见、可管、可停。

工作项 交付物 验收标准
四网关职责分离 语音/Agent/双向认证/LLM 网关 无旁路调用；代码库中无散落模型凭据
AI 注册中心上线 MCP/Agent/Skill 注册 + 审核流 未注册能力调用 = 0
埋点 SDK 内置 运行时默认埋点 Trace 覆盖率 100%；route_reason/decision_reason/empty_recall 齐全
出站围栏上线 Guardrail 服务（fail-closed） 100% 覆盖出站；演练验证拒绝服务行为
身份从凭据派生 mTLS + OIDC 集成 无自报身份
配置化改造 提示词/参数/模型权重/知识版本 配置类变更秒级回滚
三重预算 Agent 预算强制执行 无失控 Agent；成本熔断生效
RAG 底座 结构化+父子分块、混合检索、Rerank、元数据过滤 召回率与准确率达可用基线
三套评测集 公开/回归/盲测集分离 变更有门禁
记忆基础 + 事件日志 三层记忆 + source_trace_id 可溯源（为阶段二回溯干预铺路）
单写者原则确定 端云冲突策略表 无端云记忆矛盾
训练推理 GPU 隔离 独立节点池 无 OOM 事故

阶段一不做的事：不做 GraphRAG、不做微调、不做多 Agent 自由协作、不追求语义缓存高命中率。这些都是阶段二三的事，提前做会因为缺少评测与观测而无法验证有效性。

3.2 阶段二：闭环（6–12 月）

目标：让质量与成本可度量、可优化。

工作项 预期收益
语义缓存上线（含维度键与失效联动） 成本 -25~35%；命中场景延迟 -700 ms
Prompt 稳定内容前置（启用前缀缓存） 首字延迟下降；自建推理算力节省
分级用模落地 成本 -40%（SLM 承载 ≥40% 请求）
上下文三路并行 + 预算硬约束 首字延迟 -210 ms
记忆可视化 + 回溯干预 记忆污染可秒级止损
RAG 门户上线 知识接入不再依赖研发排期
知识缺口工单闭环 知识覆盖率持续上升
隐式反馈指标（重问率/打断率） 暴露此前未知的失败模式
回归门禁接入 CI（阻断式） 劣化变更无法上线
端侧 SLM + 端侧知识包 端侧分流；离线可用；延迟 390 ms
A2A 权限交集模型 消除越权通道
红队用例集 + 误拦截率 SLO 安全可度量
影子环境 + 模型灰度 模型上线零风险
定时预扩容 + 缓冲副本 高峰不可用消除
合规删除级联与验证 合规可证明

3.3 阶段三：自演进（12–24 月）

目标：让平台自己变好。

工作项 预期收益
可观测八条闭环全部自动化（见 13 文档 11） 改进从人工驱动转数据驱动
落点决策学习化（用 decision_reason 历史训练） 端侧分流比例提升，成本与延迟双降
端侧蒸馏 pipeline（按算力分档） 端侧能力持续提升
SFT/DPO 月度节奏 风格与偏好对齐
失败案例池 + 根因自动派单 组织协作闭环
对确认需要多跳的子域引入 LightRAG 复杂问题可答
端云 Agent 同构（一份 manifest 双编译） 开发效率与一致性
成本自动优化（按实时质量成本动态调权） 持续降本
多区域就近接入与故障切换 区域级 RTO ≤30 min
混沌工程常态化 灾备方案真实有效

4. 反模式清单（Anti-Patterns）

4.1 架构反模式

反模式 为什么错 正确做法
把四个网关合并成一个 流量特征与故障域完全不同，任意合并都导致故障传播 按流量特征分离（见 11 文档 1.1）
业务直连模型 API 缓存、限流、围栏、计量全部失效 唯一出口 + 凭据托管
Planner 里写业务逻辑 退化为巨石服务，业务迭代阻塞平台 Planner 代码库中不得出现业务名词
User Agents 直连云端 端侧治理旁路 System Agent 强制代理
每个 Agent 自建记忆 用户体验割裂，隐私边界失控 记忆中心统一供给 + 命名空间隔离
工具结果拼进 system prompt 提示注入直通车 独立消息段 + 隔离标记
A2A 身份透传 权限提升攻击 权限交集 + 每跳鉴权
端云都能写同一条记忆 必然不一致，无法事后修复 单写者原则
围栏做成进程内库调用 升级节奏耦合，网关频繁重启 Sidecar 或独立服务
训练与推理共享 GPU 池 训练抢占显存导致推理 OOM 物理隔离节点池

4.2 工程反模式

反模式 为什么错 正确做法
只按 QPS 限流 100k token 与 100 token 请求 QPS 相同但消耗差 1000 倍 Token/s + 并发双维度
意图分类用大模型 延迟 +500 ms、成本 ×30 小模型或判别式分类器
无评测集就调参数 无法判断改动是否有效 先建三套集再调
Trace 从网关才生成 端侧闭环（可能 30%+ 流量）完全不可见 trace_id 端侧生成
降低骨架 Trace 采样率省成本 所有指标失真 骨架 100%，只采样快照
上下文塞满长窗口 成本延迟双升，效果反降（中间信息丢失） 硬预算 + 压缩 + 相关性过滤
一次给模型 200 个工具 选错工具概率远高于给 8 个 渐进式披露 + 数量上限
摘要压缩不保护实体 车型、日期、金额被压掉 结构化实体表不参与摘要
提示词不版本化 效果波动无法归因 等同代码管理 + 埋点记录版本
遇到任何效果问题就微调 浪费数月且效果不涨 强制根因分类（见 14 文档 2.3）
纯向量检索 型号/编号/错误码系统性失败 混合检索
检索后才过滤车型 Top-K 可能全被过滤，召回为空 过滤前置
知识更新不失效缓存 返回过期答案 知识版本进缓存键
Agent 无终止条件 无限循环烧算力烧钱 三重预算强制
埋点校验失败静默丢弃 某组件指标为零而无人察觉 死信队列 + 告警

4.3 治理反模式

反模式 为什么错 正确做法
注册中心是”文档站” 允许未注册即调用，注册立刻失去意义 网关与能力中心两处强制校验
Skill 描述含糊 路由必然出错（Planner 靠描述选能力） 强制 ≥10 正例 + ≥5 反例
没有弃用流程 一年后积累几十个无人维护的 Agent 注册时必填 owner + 复核周期 + 无流量自动进弃用
适配层永久存在 存量技术债变成新技术债 设 Sunset 日期
门禁是提示式而非阻断式 项目压力下必然被跳过 阻断式 + 绕过需高层审批与记录
提示词/知识变更不走门禁 一句话改动全量影响用户 非代码变更同样纳入门禁
评测集不分离 指标涨体验不涨（过拟合） 三集分离 + 盲测集独立维护
失败案例无 owner 大家都看到但没人负责 失败案例池 + 根因派单
为可用性关掉围栏 合规事故 写入运维手册：安全不可降级；配置变更需审批
灾备方案从未演练 真实故障时方案失效 月度/季度演练清单

5. 优先级排序（ROI 视角）

5.1 效果提升优先级

排名 措施 预期效果提升 实现成本 见效周期
1 知识补全（基于空召回工单） 直接消除某类失败 极低 周
2 查询改写 召回率 +15~30% 低 天
3 混合检索 + 元数据过滤前置 消除型号类失败与答错车型 低 天
4 Rerank（Top-50→5） 准确率 +10~20% 低 天
5 结构化切分 + 父子分块 片段完整性显著提升 中 周
6 强制引用 + 拒答策略 幻觉大幅下降 低 天
7 Skill 描述优化（正反例） 工具选择准确率提升 低 天
8 上下文预算与压缩 消除”检索越多越差” 中 周
9 记忆置信度阈值与时效衰减 消除错误记忆干扰 中 周
10 SFT / DPO 风格与偏好对齐 高 月

5.2 成本下降优先级

排名 措施 预期降本 实现成本
1 分级用模（SLM 承载简单任务） -40% 中
2 语义缓存（命中率 30%） -30% 中
3 Prompt 稳定内容前置（前缀缓存） -10~20% 极低
4 上下文压缩与预算 -20% 中
5 端侧分流 端侧部分零边际成本 高
6 工具结果裁剪 -5~10% 低
7 成本熔断（消除失控 Agent） 消除异常尖峰 低

第 3 项”Prompt 顺序调整”是全表中投入产出比最高的一项——只需调整拼接顺序，零新增组件，即可获得两位数的成本与延迟收益。

5.3 延迟下降优先级

排名 措施 收益 成本
1 语义缓存命中 -700 ms 中
2 上下文三路并行 -210 ms 低
3 意图分类端侧化 -120 ms + 一次往返 中
4 端侧闭环（可覆盖意图） 1225 ms → 390 ms 高
5 前缀缓存 首字下降 极低
6 Rerank 轻量化 -30~70 ms 低

7. 常见落地误区与纠偏

误区 表现 纠偏
“先做效果，治理后补” 半年后发现二十个团队各自直连模型 治理与效果同步做；阶段一必须完成收口
“用最强模型就有最好效果” 成本高企但用户仍不满意 效果瓶颈在上下文质量，不在模型
“上了 RAG 就没有幻觉” 检索到了但答案仍编造 强制引用 + 忠实度评测 + 拒答策略
“评测太慢，先上线看反馈” 劣化变更影响全量用户 阻断式门禁；评测自动化
“端侧只是降级方案” 端侧投入不足，能力停滞 端侧 390 ms vs 云端 1225 ms，是更优路径而非兜底
“多 Agent 越多越智能” 成本不可控、结果不可复现 生产用层级委派；禁用自由讨论
“记忆越多越个性化” 错误记忆持续污染，用户投诉 宁少勿错；置信度阈值保守
“可观测等稳定了再做” 优化全靠猜，无法证明有效 可观测必须先于优化
“微调能解决一切” 数月投入效果不涨 根因分类表：只有两类问题适合微调
“GraphRAG 更先进” 成本 ×10 效果不涨 先把混合检索+Rerank+改写做扎实
