踩坑提醒：disabled 是行级字段，配置无法禁用一行——必须用 patch 的 disabled: true。这也是为什么 DSH_TELEMETRY_DISABLED 的实现方式是”启动器把该行 patch 成 disabled”，而不是往 config 里塞一个开关。

B2.4 验证方式

dump 输出会标明每行由哪个文件提供、哪些 overlay 修改过它，!!js 保持未求值，找不到目标的 patch 报到 stderr。这是验证你的 bundle 是否正确落层的唯一可靠方式。

B3 · LLM 网关适配器：协议义务的逐条落地

第 2 篇 5.6 列出的六条义务中，义务 5（遵守 options.signal，传递给 fetch 或 SDK）不在下文单列，其余五条逐条展开。

B3.1 义务 1：usage 在 finish 之前，finish 之后什么都不发

为什么必须缓冲？ 很多网关把 usage 放在 finish_reason 之后的最后一帧。直接透传会违反顺序契约。缓冲到流结束再统一 flush 是官方推荐的稳健做法。

B3.2 义务 3：块 index 按首次出现的流顺序分配

同一逻辑块的每次 delta 复用首次分配的 index。这是回放保真度的前提。

B3.5 义务 6：不支持的字段显式报错

静默丢弃是最坏的做法——模型以为 stop 生效了，实际没有，行为差异会以极难定位的方式出现在下游。

B3.6 密钥处理

绝不读自定义密钥文件。 生产环境进一步应改为通过 ctx.credentials 按请求解析，这样轮换后的凭据在紧接着的下一次请求就生效。

B4 · 双层权限门禁：waterfall + 单调 guard

B4.1 为什么要两层

层 特性 用途
tools/pre-execute waterfall 可重排、可被后续层影响、支持 ask 策略：随部署、租户、审批状态变化的规则
ctx.tools.guard() 单调、后续监听器无法撤销 不变量：无论什么审批都不允许的硬约束

B4.2 第 1 层：策略

fail-closed 姿态：

策略服务不可用时默认拒绝。这与 dsh 自身 ctx.approval “无应答方时以 unavailable 关闭失败”的姿态一致。

B4.3 第 2 层：不变量

extractVin 递归遍历任意深度的参数结构（带循环引用保护），因为工具参数形状各异——bash 命令里可能内嵌 VIN，OTA 工具里 VIN 在数组里。

注意：exec.arguments 是已冻结的无损 JSON 快照，可以安全外发给策略服务，不必担心被下游修改。

B5 · 双通道审计

B5.1 通道 A：tools/result —— 权威结果

tools/result 观察的是不可变、JSON 无损的权威结果——已经过规范化、finalizeContent 之后的最终形态。这是审计应该记录的东西，而不是 tools/post-execute 里可能还会被改的中间态。

B5.2 通道 B：session/event —— 合规归档

这里必须用 session/event + event.type —— turn/*、tool/* 不是 Cordis 事件，直接 ctx.on('turn/end', ...) 永远不会触发。这是第 3 篇 12.9 表格里的坑 #2。

审计选取的事件集合覆盖了完整的问责链：谁在什么时候提了什么要求、模型做了什么决定、调用了哪些工具、审批结果如何、权限与沙箱模式是什么、上下文被压缩过几次。

B5.3 审计不得影响主流程

监听器抛错在 Cordis 中会被容纳（不会饿死其他监听器），但主动 catch 是更清晰的意图表达。

B6 · 业务工具：只读并行 vs 写操作串行

B6.1 只读工具（vehicle_query）

isConcurrencySafe 只有 true 才算选择加入——省略、抛异常、非 true 返回值、无效 defineTool 参数，全部视为独占。这个默认值很安全。

选择加入的执行不得修改父级持有的状态；共享状态必须容忍并发分发，记录器竞态只在可交换或 fail-closed 时允许。

B6.2 写操作工具（ota_batch_dispatch）

部署配置强制优先于模型参数 —— dryRunOnly 为真时，无论模型传什么 dry_run 都是 dry-run。这是”部署策略不建在工具里，但安全兜底必须建在工具里“的平衡点。

B6.3 领域失败 vs 基础设施失败

这是官方约定：”成功的领域结果即使表示不理想的状态，也应写入规范值；其 Native 渲染器可以解释该状态，例如进程以非零状态退出。”

对模型的意义：isError 意味着”重试或换方法”，规范值里的 accepted: false 意味着”这就是答案，去分析 rejectedVins“。

B6.5 异步通知（不唤醒）

inject() 不是唤醒——空闲 agent 保持空闲，内容留在 inbox 直到另一条消息将其唤醒。必须 try/catch 防已 dispose 的 agent。

B6.6 UI 卡片的纯函数约束

只依赖 args——不查数据库拿车型名、不读时钟标时间戳、不访问会话状态。因为这个函数在会话日志回放时也会被调用，任何外部依赖都会让历史卡片渲染出错或崩溃。

需要结果期事实的卡片走 output.presentationMeta → 持久化到 tool/result.meta → presentResult 读回。

B7.5 生产化前必做的五件事

  1. 改写协议转换 —— llm-gateway.ts 的 toWire / toChunk / parseSse 是 OpenAI 兼容方言的骨架，按你的网关实际协议重写
  2. 定义策略服务契约 —— permission-gate.ts 的 { verdict: 'allow'|'deny'|'ask' } 是示意，按你的授权体系（RBAC / ABAC / 工单系统）定义
  3. 加严审计脱敏 —— SECRET_KEYS 正则按你的字段命名扩充；考虑对 VIN 做哈希而非明文归档
  4. 验证沙箱强制完整性 —— 确认 SandboxEnforcement !== 'partial'；老内核 Landlock ABI 或 Windows ACL 场景需在容器层补一道
  5. 建立版本兼容矩阵 —— dsh 处于 developer preview，把 corp-dsh-bundle@x.y 与 dsh@a.b 的兼容关系写进 CI，每次 dsh 升级跑一遍 13 项验证清单

结语：一套真实的企业二开长什么样

corp-dsh-bundle/ 865 行给出了答案——不是 hello world，而是包含内网模型网关、双层权限、双通道审计、只读/写操作两类工具、随包 SOP 的完整形态，且每一处都对应前几篇里的某条约定。

照着这套骨架改，你会发现 dsh 二开的真正难点不在 API，而在理解每条约定背后的理由：为什么 finish 之后不能再发东西、为什么展示函数必须纯、为什么后台任务不能用 exec.signal、为什么 patch 不做深度合并。这些理由在本系列各篇里都标注了出处。

本篇基于 deepseek-ai/deepseek-harness@47f9438（v0.1.0-rc.5）。脚手架代码可直接构建，但协议转换、策略契约、脱敏规则三处标注了”按你的实际情况重写”——请勿原样上生产。
