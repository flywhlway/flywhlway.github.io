第 0 章 总论：为什么“协议为契约、框架为可替换实现”

0.1 论断的工程含义

2023–2024 年的 Agent 系统，“解耦”停留在代码层面：抽象一个 Tool 接口、抽象一个 Agent 基类、抽象一个 Callback。这种解耦的边界止于同一个框架、同一个进程、同一种语言。一旦更换框架（LangGraph → Google ADK）、跨进程/跨团队（Java 的诊断 Agent 调用 Python 的日志分析 Agent）、跨前端栈（React → 小程序），抽象层就全部失效，只能重写适配层。

2025–2026 年发生的根本变化，是四类跨框架、跨语言、跨进程的线级（wire-level）协议在主流框架中普及：

协议 解决的耦合面 一句话定义 契约形态
MCP Agent ↔ 工具/数据/提示 LLM 应用连接外部能力的标准接口 JSON-RPC 2.0 + JSON Schema（tools/resources/prompts）
A2A Agent ↔ Agent 异构 Agent 之间发现、委派任务、交换产物 Agent Card + Task 状态机 + JSON-RPC/gRPC/REST 三绑定
AG-UI Agent ↔ 用户界面 一次请求进、一条有序类型化事件流出 31 种事件的 JSON Schema + SSE/Protobuf 传输
OpenTelemetry Agent ↔ 观测体系 追踪/指标/日志三信号 + GenAI 语义约定 OTLP + W3C Trace Context + gen_ai.* 属性

四者的共同特征：都以“可序列化的线级消息 + 明确的状态机/事件序列”作为规范主体，而不是以某个 SDK 的类层次为主体。这意味着契约可以独立于任何实现被测试（契约测试）、被代理（Gateway）、被记录回放（审计）、被版本化（迁移）。

0.2 平台设计的推论

把“协议为契约、框架为可替换实现”落到平台设计，可以推导出五条硬性原则：

  1. 平台只依赖协议，不依赖框架 API。平台的注册中心、网关、审计、计费、灰度、回放等横切能力，只消费/生产协议消息（Agent Card、A2A Task、AG-UI 事件、OTLP 数据），绝不 import 任何 Agent 框架。
  2. 框架是“协议适配器 + 业务逻辑”的组合。LangGraph、CrewAI、ADK、Spring AI、Semantic Kernel、Pydantic AI 等在平台视角下是等价的：它们都必须“吐出 AG-UI 事件、暴露 A2A 端点、以 MCP Client 调用工具、以 OTel 上报遥测”。
  3. 协议边界即信任边界。鉴权、限流、脱敏、内容安全统一在协议网关执行，而不是散落在各框架中间件里。
  4. 协议版本是平台的一等公民。MCP 按日期修订、A2A 按 SemVer、AG-UI 0.x → 1.0、OTel 语义约定按 schema_url 演进，平台必须显式管理协议版本兼容矩阵。
  5. 跨协议的关联键要在设计期统一。traceparent 在四类协议中都有承载位置（MCP _meta、A2A metadata、AG-UI metadata/forwardedProps、OTLP 原生），必须在平台入口生成、贯穿到底。

第 1 章 MCP（Model Context Protocol）—— 工具/数据面协议（简要）

MCP 已被广泛介绍，本章仅做系统性梳理，重点放在 2026-07-28 修订版的关键变化与企业落地要点，为后续章节的跨协议协同做铺垫。

1.1 角色与原语

三角色：

  • Host：用户直接交互的 AI 应用（IDE、聊天应用、Agent 运行时）。
  • Client：Host 内部的连接器，Host 为每个 Server 创建一个 Client。
  • Server：暴露能力的程序（包装数据库、文件系统、SaaS、内部 HTTP API）。

三原语（服务端提供）：

原语 控制方 典型用途 关键方法
Tools 模型（model-controlled） 可执行动作：查询、写入、调用 API tools/list、tools/call
Resources 应用（application-controlled） 只读上下文：文件、记录、日志片段 resources/list、resources/read、resources/templates/list
Prompts 用户（user-controlled） 可复用的提示模板/工作流 prompts/list、prompts/get

传输：stdio（本地子进程）与 Streamable HTTP（远程，单一 POST 端点，响应可为 JSON 或 SSE 流）。旧的 HTTP+SSE 传输自 2025-03-26 弃用，2026-07-28 正式进入 Deprecated 生命周期。

1.2 2026-07-28 修订版：走向无状态

这是 MCP 自发布以来最大的修订，对平台设计影响极大：

变化 旧行为（2025-11-25 及以前） 新行为（2026-07-28） 平台影响

1.5 企业落地要点（工具面）

  1. MCP 网关是必需品。统一 OAuth 2.1（资源指示器 RFC 8707、iss 校验 RFC 9207、Client ID Metadata Documents）、工具白名单、参数级脱敏（VIN、手机号）、结果大小限制、审计留痕。2026-07-28 的无状态化使网关可以做纯请求级路由，不再需要会话亲和。
  2. 工具描述即提示词工程。tools/list 结果直接进入模型上下文；要求 Server 返回确定性排序并合理设置 ttlMs，可显著提升 prompt cache 命中率与成本。
  3. structuredContent + outputSchema 是跨协议数据契约的起点。A2A 的 DataPart、AG-UI 的 TOOL_CALL_RESULT、OTel 的 gen_ai.tool.call.result 都应从同一份 JSON Schema 派生。
  4. 长任务用官方 tasks 扩展，与 A2A Task 生命周期对齐（第 2 章），避免各框架各造一套异步语义。
  5. 日志不再走 MCP Logging，全部改为 OTel（第 4 章），这也是官方给出的迁移方向。
  6. _meta.traceparent 必须透传。这是 2026-07-28 明确的约定，网关与 SDK 中间件都应默认注入/透传。

第 2 章 A2A（Agent2Agent Protocol）—— Agent 间协作协议（详细）

2.1 背景与定位

  • 发布：Google 于 2025-04-09 发布，2025-06 捐赠给 Linux Foundation，2025-07-31 发布 v0.3（gRPC 绑定、Agent Card 签名、/.well-known/agent-card.json），2026-03 发布 v1.0 RC，2026-08-27 宣布并入 Agentic AI Foundation（与 MCP 同一治理伞下）。
  • 支持方：Google、Microsoft、Salesforce、ServiceNow、SAP、AWS 等 150+ 组织；官方 SDK 覆盖 Python、Go、Java、JS、.NET、Rust；配套 A2A Inspector 与协议 TCK（一致性测试套件）。
  • 定位：解决“由不同团队、不同框架、不同语言、部署在不同网络的 Agent 之间”的发现、委派、协作问题。它把远端 Agent 当作不透明的对等体（opaque peer）：调用方不需要知道对方的内部状态、工具、记忆或模型，只需要 Agent Card 与 Task 状态机。
  • 与 MCP 的关系（v1.0 规范明确）：MCP 负责 Agent ↔ 工具/资源，A2A 负责 Agent ↔ Agent；互补而非竞争，一个 Agent 常同时是 MCP Client 与 A2A Server。

设计哲学对比：MCP 把远端当“函数”（同步、结构化输入输出、无长期状态）；A2A 把远端当“同事”（异步、多轮、有任务生命周期、可中途要求补充信息、可产出多份产物）。这也是为什么长任务、人机协同、跨组织协作应优先走 A2A 而不是把另一个 Agent 包装成 MCP Tool。

2.2 规范的三层结构

A2A v1.0 规范（§1.3）明确分为三层，正是“协议为契约、框架为实现”的教科书式实践：

层 内容 规范来源
L1 规范数据模型（Canonical Data Model） AgentCard、Task、Message、Part、Artifact、事件等，以 a2a.proto 为唯一权威定义 Protocol Buffers 3
L2 抽象操作（Operations） SendMessage、SendStreamingMessage、GetTask、ListTasks、CancelTask、SubscribeToTask、GetExtendedAgentCard、四个 PushNotificationConfig 操作 语义与状态转换规则
L3 协议绑定（Bindings） JSON-RPC 2.0、gRPC、HTTP+JSON（REST）三种，规范保证三者语义等价 传输细节、错误映射、流关闭机制

v1.0 把 a2a.proto 从“gRPC 实现文件”提升为规范的唯一真理来源，JSON 形态遵循 ProtoJSON（这也解释了枚举改为 SCREAMING_SNAKE_CASE、字段用 camelCase）。

v1.0 关键变化（相对 0.3）：

  • url / preferredTransport / additionalInterfaces 合并为 supportedInterfaces[]，每个接口独立声明 protocolBinding、protocolVersion、可选 tenant——一个 Agent 可同时服务多个协议版本，客户端按自身支持的版本选择接口，实现平滑迁移。
  • protocolVersion 从 Card 顶层移到每个接口。
  • supportsAuthenticatedExtendedCard 移到 capabilities.extendedAgentCard，通过 GetExtendedAgentCard 获取带鉴权后才可见的完整 Card。
  • 签名：signatures[] 使用 JWS（RFC 7515）对 JCS 规范化（RFC 8785）后的 Card（排除 signatures 字段）签名，公钥通过 jku 或平台信任库获取。企业注册中心应拒绝未签名或签名不匹配的 Card。
  • OAuth 流程现代化：移除 Implicit 与 Password 流，新增 Device Code（RFC 8628），Authorization Code 流增加 pkceRequired。

  • taskId：继续同一任务（回答 INPUT_REQUIRED 的问题）时，在后续 SendMessage 的 message.taskId 携带。终态任务不可再续，需开新任务。
  • contextId：逻辑会话标识，可跨多个 Task 共享，服务端据此关联上下文（类似 AG-UI 的 threadId）。

2.3.3 Message 与 Part（v1.0 统一 Part）

v1.0 的 Part 统一（迁移影响最大的破坏性变更）：

  • 移除 TextPart / FilePart / DataPart 与 kind 判别字段，改为单一 Part，以成员存在性判别：text / data / url / raw 四选一。
  • mimeType → mediaType，且对所有 Part 可用；filename 对所有 Part 可用。
  • 客户端判别逻辑从 if part.kind == "text" 改为 if "text" in part。

2.7 企业落地：注册中心、安全、多租户、可靠性

2.7.1 Agent 注册中心（A2A Registry）

平台需要一个只依赖 Agent Card 的注册中心：

  • 注册：Agent 启动时上报 Card（或注册中心定时抓取 well-known URI）；校验 JWS 签名，签名密钥由平台 PKI 签发。
  • 索引：按 skills[].tags、inputModes/outputModes、capabilities、supportedInterfaces[].protocolVersion 建索引，供编排 Agent 做“能力路由”。
  • 健康：定时调用 GetTask 一个不存在的 ID，期望 -32001，作为轻量探活（比调用业务技能更安全）。
  • 版本：同一 Agent 多版本并存时，以 supportedInterfaces 区分；注册中心提供“最高兼容版本”选择 API。

2.7.2 安全

  • 传输：TLS 1.3；内网 Agent 间推荐 mTLS（v1.0 mutualTls 安全方案）。
  • 认证：Card 中 securitySchemes 声明；平台统一 OAuth 2.0 Client Credentials（服务间）或 Authorization Code + PKCE（用户代理）；Device Code 用于 CLI/车机等受限输入设备。
  • 授权：GetTask/ListTasks 必须只返回调用者可见的任务；建议 TaskStore 以 (tenant, principal, taskId) 为键。
  • Push Notification 安全：Webhook URL 白名单、PushNotificationConfig.authentication 使用平台签发的短期 token，接收端校验 taskId 归属。
  • 扩展：required: true 的扩展未被客户端支持时拒绝（-32007），避免语义降级。

2.7.3 多租户（v1.0 原生）

  • 请求级 tenant 字段 + AgentInterface.tenant 默认值，使单一端点服务多个品牌/事业部。
  • TaskStore、PushNotificationConfigStore、审计日志全部以 tenant 分区。
  • OTel 资源属性 tenant.id 与 A2A tenant 对齐（第 4 章）。

2.7.4 可靠性与持久化

  • TaskStore 持久化：PostgreSQL（任务表 + 事件表，事件表按 taskId, seq 排序），或 Redis Streams。SubscribeToTask 从事件表回放，实现断线重连不丢事件。
  • 幂等：以 messageId 做幂等键，重复 SendMessage 返回同一 Task。
  • 超时与取消：为每个 Task 设置 SLA，超时触发 CancelTask 并记录 CANCELED 原因到 metadata。
  • 背压：流式产物分块大小（建议 ≤ 32 KB/事件）；大文件走 url Part 而非 raw。
  • 审计：网关记录每个 Task 的状态转换、Artifact 摘要（哈希 + 大小，不存正文）、调用方主体。

2.8 迁移：0.3 → 1.0 三阶段（官方建议 + 平台实践）

  1. 兼容层：客户端同时解析 kind 判别与成员判别；解析两种 Card 结构；根据 protocolVersion 选择适配器。
  2. 双栈：服务端在 supportedInterfaces 同时暴露 0.3 与 1.0 接口；输出统一为 1.0 格式；处理 A2A-Version 头；游标分页与页码分页并存。
  3. 仅 1.0：移除旧解析、旧接口、页码分页。

平台侧检查清单：Part 解析（关键）→ 流事件判别（高）→ Card 结构（高）→ 枚举大写（高）→ 错误体 google.rpc.Status（高）→ 游标分页（中）→ Card 签名校验（中）→ 扩展 required 校验（中）→ mTLS（低）。

第 3 章 AG-UI（Agent-User Interaction Protocol）—— 前端事件协议（详细）

3.1 背景与定位

  • 发布：CopilotKit 于 2025-05-12 发布，与 LangGraph、CrewAI 合作设计；2026 年发布 1.0 规范——这是 AG-UI 第一次拥有“行为规范”（0.x 只定义了事件形状，行为散落在 TypeScript 客户端实现中）。
  • SDK：官方 TypeScript（@ag-ui/core、@ag-ui/client、@ag-ui/encoder）、Python（ag-ui-protocol）、.NET 三个一等 SDK；模型从同一份 JSON Schema 生成。
  • 集成：LangGraph、CrewAI、Mastra、Pydantic AI、Google ADK、Agno、LlamaIndex、AG2、Microsoft Agent Framework、AWS Strands、Claude Agent SDK 等均有一等或伙伴集成；前端以 CopilotKit React 组件为参考实现，但任何能消费 SSE 的前端都可以对接。
  • 定位：解决“Agent 运行时 ↔ 用户界面”的实时交互契约——流式文本、工具调用、推理过程、共享状态、进度、人机协同、子 Agent 可视化。它有意不规定 Agent 内部结构与 UI 渲染方式。

一句话模型：一次请求进（RunAgentInput），一条有序的类型化事件流出。

3.2 角色与核心抽象

  • Producer（生产者）：发出事件流的一方——Agent、代理、桥接器、测试替身。
  • Consumer（消费者）：读取事件流的一方——客户端 SDK、UI、录制器、另一个代理。
  • 同时扮演两者的参与者（如网关）分别受两套规则约束。

四个标识符（均为不透明字符串，消费者不得解析其结构）：

标识符 含义 生命周期
threadId 一个会话/对话 由应用生成，跨 run 稳定
runId 一次运行 同一 thread 内不可复用
messageId 一条消息 跨 run 边界，thread 内唯一
toolCallId 一次工具调用，把结果与中断关联回调用 单次调用
subagentRunId（1.0） 一次子 Agent 调用（非子 Agent 定义） 单次调用

3.3 Run Input：唯一的“进”方向消息

字段语义：

  • messages：完整对话历史（AG-UI 是客户端持有历史的协议；服务端无状态即可）。消息角色：system / developer / user / assistant / tool / activity（1.0）。
  • tools：前端工具——由前端定义、由前端执行的工具（弹窗、跳转、表单、写本地状态）。Agent 通过 TOOL_CALL_* 请求执行，前端执行后把 tool 角色消息放进下一次 run 的 messages。1.0 起 tools、context 可省略（缺省等价于空）。
  • context：前端提供的上下文片段（页面状态、选中项）。
  • state：共享状态的当前快照，Agent 与前端双向同步。
  • forwardedProps：透传给 Agent 的任意属性，是承载 traceparent、租户、鉴权上下文的推荐位置。
  • metadata（1.0）：开放通道，按 key 合并。

3.4 事件模型：31 种事件、8 大事件族

3.4.1 事件信封

  • type：必填判别字段，31 个值之一。
  • timestamp：可选、仅供参考——消费者不得用它排序，到达顺序即协议顺序。
  • rawEvent：可选，提供商原生事件原样携带，不得据此推导协议行为。
  • metadata：可选开放通道。
  • subagentRunId：可归属于子 Agent 的事件可携带；RUN_STARTED/FINISHED/ERROR、MESSAGES_SNAPSHOT 是 run 级事件，不带归属。
  • “缺省即缺省”：可选字段没有值必须省略，不得发 null（开放对象内部的 null 是数据，必须保留）。

3.4.2 八大事件族总览

3.4.3 逐族详解

（1）运行与步骤

  • 每个 run 必须以 RUN_STARTED 开始，以 RUN_FINISHED 或 RUN_ERROR 结束，且恰好一次。
  • 1.0：RUN_FINISHED.outcome 报告 run 如何结束——success 或 interrupt（携带 interrupts[]，人机协同的核心，见 3.5.4）。
  • 1.0：RUN_FINISHED / RUN_ERROR 可携带 token 用量（统一口径：输入/输出为总数，缓存与推理 token 为其子集，缓存读写分开报；子 Agent 用量计入 run）。这与 OTel gen_ai.usage.* 应保持一致（第 4 章）。

（2）文本消息（流式模式）

  • 流式模式规则：START 开、若干 CONTENT 累积、END 关；delta 非空；同一 messageId 内不可交错其他消息的 CONTENT（可交错工具调用等其他族）。
  • TEXT_MESSAGE_CHUNK：便捷形式——消费者据 messageId 自动补齐 START/END，适合“一次性”或懒实现的生产者。

（3）工具调用（流式模式）

  • TOOL_CALL_ARGS.delta 拼接后必须是合法 JSON；前端可边流边做“部分 JSON 解析”渲染参数预览。
  • 对前端工具：Agent 只发 START/ARGS/END，随后结束 run（outcome: interrupt 或直接 finish）；前端执行后把 tool 消息塞进下一次 run 输入。对后端工具：Agent 自己执行并追加 TOOL_CALL_RESULT，前端只做展示。
  • 安全：工具参数是模型输出，是不可信输入；应用必须校验后再执行，且不得把流式内容当可执行标记渲染。

（4）推理（1.0 新增，替代 0.x THINKING_*）

REASONING_ENCRYPTED_VALUE 用于提供商的加密推理工件：消费者原样保存并在后续 run 回传，不读取。旧的 THINKING_* 在兼容边界被翻译为推理族，而不是丢弃。

（5）状态（快照–增量模式）

  • STATE_DELTA 使用 JSON Patch（RFC 6902）；消费者对当前状态依序应用。规则：增量只能应用于已知快照；丢失事件后必须等下一次快照重建。
  • MESSAGES_SNAPSHOT 用于服务端权威地重写对话（如摘要压缩后）。
  • 状态是双向的：前端修改 state 后随下一次 run 输入回传。生成式 UI 的“状态驱动渲染”即基于此。

（6）活动（1.0 新增）

活动是“内容为对象的消息”，用于结构化进度（扫描进度、检索命中计数、子任务列表），UI 按 activityType 选择渲染器。相较 STATE_*，活动是消息级、UI 消费，不进入应用状态存储。

（7）子 Agent（1.0 新增）

子 Agent 族让前端能把多 Agent 编排可视化（折叠面板、并行进度）。这正是 A2A 远端 Agent 在 AG-UI 中的映射位置（第 5 章）。

（8）透传

RAW 承载未翻译的提供商事件；CUSTOM 承载应用自定义事件（前端 opt-in 处理）。平台建议：内部约定 CUSTOM.name 使用反向域名前缀，避免多团队冲突。

3.4.4 事件模式（Patterns）——行为规范的核心

模式 规则要点
生命周期 开始/结束成对；结束恰好一次；错误后不再有事件
流式 START → CONTENT* → END；CHUNK 可由消费者自动补齐；同一 id 的流不可被同类流交错
快照–增量 快照建立基线；增量按序应用；增量必须有基线，否则丢弃并警告
中断–恢复 RUN_FINISHED.outcome.type = "interrupt" 携带中断；应用在下一次 run 输入中提供恢复信息（通常是 tool 消息或 forwardedProps.resume）

3.4.5 处理模型：未知 vs 畸形

1.0 把 0.x 的隐含行为写成了规范：

  • 中间件先于强制校验：所有翻译/中间件先运行，再做 schema 强制。
  • 未知的存活，畸形的致命：未识别的事件、字段、联合成员在翻译阶段保留，强制阶段丢弃未知事件、剥离未知成员并警告；已知字段取值畸形则整个流失败。
  • 结论：生产者可以安全地前向添加事件/字段（老消费者会忽略），但不能改变已知字段的形状。这是 AG-UI 的兼容性契约。

3.4.7 版本与兼容

  • 1.0 与 0.x：退役形状（如 THINKING_*）在兼容边界翻译，不丢弃。
  • 同一 metadata 的合并语义规范化：按 key、后写覆盖、不递归；ag-ui key 保留。

3.6 企业落地要点

3.6.1 AG-UI 网关（平台能力）

  • 鉴权与租户：前端 → 网关走用户态 OAuth/OIDC；网关解析用户与租户，写入 forwardedProps（不信任前端自报的租户）。
  • 路由：按 Agent 名路由到不同 Producer（不同框架/语言/团队），实现“一个前端、N 个 Agent 后端”。
  • 事件审计与回放：网关把每个 run 的事件流按 (threadId, runId, seq) 落盘（对象存储 + 索引）。回放即“重新发这条流”，用于问题复现、合规审计、评测集构建。
  • 安全过滤：对 TEXT_MESSAGE_CONTENT 做内容安全/脱敏；对 TOOL_CALL_ARGS 拼接后做 schema 校验；RAW 默认剥离（消费者需 opt-in）。
  • 限额：单事件大小（建议 ≤ 64 KB）、单 run 事件数、并发 run 数（按用户/租户）。
  • 协议版本：网关做 0.x ↔ 1.0 翻译（如 THINKING_* → REASONING_*），前端只认 1.0。

3.6.2 前端架构建议

  • 状态分层：STATE_* 进应用状态仓（Redux/Zustand/Pinia），ACTIVITY_* 与文本进 UI 消息列表，CUSTOM 进事件总线。
  • 中断 UI 统一组件：所有 outcome.interrupt 与前端工具调用走同一个“待办面板”，避免各页面各造确认框。
  • 子 Agent 可视化：按 subagentRunId 分组渲染折叠面板；SUBAGENT_STARTED.name 直接取自 A2A Agent Card 的 name。
  • 断线重连：SSE 断开后以同一 threadId 新建 run，携带最新 state 与 messages；服务端若支持“续跑”，通过 forwardedProps.resumeRunId 约定（属应用层契约）。

3.6.3 一致性测试

对任何 Producer 运行以下断言（可用 @ag-ui/client 的解析器或自写 SSE 读取器）：

  1. 首事件 RUN_STARTED，末事件 RUN_FINISHED/RUN_ERROR，且各恰好一次。
  2. 每个 TEXT_MESSAGE_START 有对应 END；CONTENT.delta 非空；同 id 不被同类交错。
  3. TOOL_CALL_ARGS 拼接后 JSON.parse 成功。
  4. STATE_DELTA 前必有 STATE_SNAPSHOT；补丁可应用。
  5. 无 null 顶层可选字段。
  6. 未知事件类型（构造一个 X_FUTURE_EVENT）被客户端丢弃并警告，而不是崩溃。

第 4 章 OpenTelemetry —— Agent 可观测协议（详细）

4.1 为什么 Agent 平台必须以 OTel 为观测契约

Agent 系统的可观测性有三个不同于传统微服务的难点：

  1. 调用链跨框架、跨语言、跨协议：一次用户请求可能经过 AG-UI 网关（TS）→ 编排 Agent（Python/LangGraph）→ A2A 专家 Agent（Java/Spring AI）→ MCP Server（Go）→ 多次 LLM 调用。任何单框架的“回调式追踪”都无法覆盖全链路。
  2. 成本与质量是一等指标：token 用量、模型型号、工具失败率、人机等待时长，与延迟、错误率同等重要。
  3. 内容是敏感数据：prompt/completion 里可能有 VIN、手机号、内部文档，必须在采集侧可控制、可脱敏。

OpenTelemetry（CNCF）提供了：统一 API/SDK（多语言）+ OTLP 线级协议 + W3C 上下文传播 + Collector 流水线 + 语义约定（Semantic Conventions）。2026 年的市场信号进一步印证了“以标准而非厂商为锚”的必要性：LLM 观测厂商快速整合（如 Langfuse 被 ClickHouse 收购、Galileo 被 Cisco 收购意向），而 Langfuse、Arize Phoenix、LangSmith、Datadog、Dynatrace、Grafana 等都已原生接收 OTLP + gen_ai.*。对平台而言，只要按 OTel GenAI 约定打点，后端随时可换。

platform_sdk.* 是平台提供的协议 SDK 薄封装（不含业务）：mcp_call 负责 MCP 网关寻址、_meta.traceparent 注入、结果 schema 校验；find_agent 负责注册中心查询与 Card 签名校验；emit 负责把节点内的自定义事件汇入当前 run 的 AG-UI 流（LangGraph 适配器暴露的事件通道）。替换框架时只需重写节点，platform_sdk 不变。

5.5 部署骨架（docker-compose）

验证路径：

  1. curl http://localhost:9100/.well-known/agent-card.json → 专家 Card；注册中心 GET /agents?skill=ota-failure-rca 返回同一 Card 且 signatureVerified: true。
  2. 前端发起一次诊断，浏览器 Network 面板看到完整 AG-UI 事件流（含 SUBAGENT_*）。
  3. Grafana → Tempo 用 agui.run.id 搜索，看到跨 5 个服务的 span 树：invoke_agent ota-diag-orchestrator → execute_tool query_ota_failure_logs → [MCP] tools/call → invoke_agent OTA 日志分析专家 → [A2A server] invoke_agent → chat deepseek-v4 …

第 6 章 平台设计：协议契约治理、框架替换、兼容矩阵与迁移路线

6.1 平台分层与“协议执行点”

平台只拥有 L4 与 L2 的契约，不拥有 L3 的代码。业务团队可用任何框架实现 L3，只要通过 L4 的契约测试。

6.2 契约治理制度

  1. 契约仓库（contracts repo）：集中存放 A2A Agent Card 模板、AG-UI 自定义事件命名规范、MCP 工具 inputSchema/outputSchema、OTel 属性字典（平台扩展属性）、Collector 配置。任何变更走 PR + 契约测试。
  2. 版本矩阵（每季度更新）：
协议 平台当前基线 允许的旧版本 计划淘汰

  2. 变更分级：新增可选字段/事件 = 兼容；改已知字段形状/语义 = 破坏性，需双栈过渡期。
  3. 契约所有权：每个 Agent Card、每个 MCP 工具 schema 有明确 owner 与 SLA。

6.5 迁移路线（从“框架耦合”到“协议契约”）

阶段 0（1–2 周）评估：盘点现有 Agent，标注其工具调用方式、Agent 间调用方式、前端对接方式、观测方式；识别“私有协议”。

阶段 1（1 个月）观测先行：全量接入 OTel（最低成本、最高收益），统一 gen_ai.* 与平台属性；上线 Collector 与看板。没有观测就无法安全替换框架。

阶段 2（1–2 个月）工具面标准化：把私有工具调用改为 MCP（2026-07-28），上线 MCP 网关；日志从 MCP Logging 改为 OTel。

阶段 3（2 个月）Agent 间标准化：为每个可复用 Agent 发布签名 Agent Card，上线注册中心；把“把 Agent 包成工具”的调用改为 A2A；建立契约测试。

阶段 4（1–2 个月）前端标准化：上线 AG-UI 网关；自研前端改为消费 AG-UI 1.0；把各框架的私有流式格式通过适配器统一。

阶段 5（持续）框架治理：允许业务团队自选框架；平台以契约测试 + 网关准入把关；每季度更新版本矩阵。

6.6 反模式清单

  1. 平台代码 import Agent 框架——平台被绑死，框架升级即平台升级。
  2. 在框架中间件里做鉴权/脱敏——每换一个框架重做一遍，且无法审计。
  3. 自造“内部 A2A”/“内部事件流”——2025 年前情有可原，2026 年后是纯负债。
  4. 用 MCP 模拟 A2A（长任务、多轮塞进 tool 调用）——超时、无进度、不可取消。
  5. 前端直接解析框架私有 SSE 格式——前后端强耦合。
  6. 观测只接一家 SaaS——无 OTel 层，供应商整合时被动迁移。
  7. 契约无 owner、无测试、无版本矩阵——协议演进（如 A2A 1.0 大改）时全线故障。
