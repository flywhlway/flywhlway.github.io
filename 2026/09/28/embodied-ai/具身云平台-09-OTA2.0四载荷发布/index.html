第 9 章 OTA 2.0：固件、模型、配置、技能四载荷发布

OTA 是车联网架构师迁移价值最高、也最容易“照搬出事故”的平面。

Flywhl 11 分钟 发布于 2026.09 #机器人云平台#OTA#灰度发布

先读结论

  1. 四类载荷：固件、模型、配置、技能（含地图），切换与回滚方式各不相同。
  2. 能跑但干活变差：模型 OTA 的本质风险。
  3. 不可变签名制品：对规范化清单签名，清单含摘要、兼容、契约、安全版本。
  4. 双槽热切换：备槽预加载、间隙原子切换、观察期后释放。
  5. 安全版本号：确认后才提升最低安全版本。

本章定位：OTA 是车联网架构师迁移价值最高、也最容易“照搬出事故”的平面。本章把 XOTA 的方法论扩展为 OTA 2.0：四类载荷、不可变签名制品、多维兼容矩阵、分发网络、端侧双槽与防回滚、以作业质量为门禁的灰度与自动回滚。
对应代码：p02-ota-rollout（制品签名、兼容检查、端侧 Agent、灰度引擎、200 台机队仿真）｜建议学时：6 小时

9.1 四类载荷

9.1.1 差异一览

载荷 内容 体积 频率 切换方式 回滚方式 门禁核心
固件 主控系统、驱动、MCU 固件 百 MB–GB 月/季 A/B 分区 + 重启 分区回切 启动成功、自检
模型 VLA、感知、VLM 权重或引擎 GB 级 周/双周 双槽热切换（不停机） 槽位回切（秒级） 作业质量
配置 参数、阈值、Prompt、功耗档位 KB 天 参数热更新 旧版本重下发 收敛 + 行为指标
技能 行为树、任务脚本、算法插件、地图 MB 周 插件/资源重载 旧版本重下发 任务成功率

9.1.2 模型载荷为什么最特殊

固件出问题通常是“起不来”或“崩溃”——显性、可快速检测。模型出问题往往是“能跑但干活变差”：成功率从 94% 掉到 88%，人工介入率悄悄上升，某类物体抓取变慢。崩溃率、CPU、内存全都正常。如果门禁只看稳定性指标，坏模型会一路灰度到全量。这是 OTA 2.0 与 XOTA 最本质的区别。

9.2 制品：不可变、可验证、可追溯

9.2.1 制品清单

所有载荷统一为不可变制品：同一个 artifact_id 永远指向同一份字节，改动一个比特也必须发新版本。p02 使用的清单格式：

三个关键字段：compat（兼容矩阵，第 6 章引擎矩阵的落地）、contract（模型三契约，第 13 章）、security_version（防回滚，9.4.3）。

9.2.2 签名：对清单签名，清单里有摘要

签名对象是规范化后的清单（字段排序、无多余空白），清单内含制品摘要。端侧验证顺序：用内置公钥验签名 → 下载后算摘要与清单比对 → 检查兼容矩阵 → 检查安全版本。

签名密钥按用途分离：固件、模型、配置各用一把，模型密钥泄露不影响固件信任链（第 16 章）。

9.2.3 兼容矩阵是多维的

维度 来源 不匹配的后果
机型 / 硬件版本 Device Profile 驱动或动作空间不符
GPU 架构 主控模块 引擎无法加载
JetPack / TensorRT 版本 固件基线 引擎无法加载或行为不一致
精度 制品构建参数 内存预算失真
模型契约（观测/动作/频率） 模型卡 vs Profile 能加载但动作错乱——最危险

兼容检查必须在云端排批时和端侧安装前各做一次：云端防止无效分发，端侧兜底防止元数据出错。

9.3 分发网络

9.3.1 四级瀑布

flowchart LR
  REG["制品库<br/>MinIO/S3"] --> CDN["CDN / 区域节点"]
  CDN --> SITE["站点缓存<br/>（发布前预热）"]
  SITE --> R1["机器人 A"]
  SITE --> R2["机器人 B"]
  R1 -. "站内 P2P（可选）" .-> R2

9.3.2 算一笔账

一个 8GB 模型发往 200 个站点、每站 50 台：直连中心云需要约 80TB 公网流量；站点缓存后公网流量约 1.6TB（每站一份），降低约两个数量级。代价是缓存容量与预热编排。预热两段式：发布批次确定后先把制品推到目标站点缓存（可以在夜间），批次开始时机器人从站内拉取。

9.3.3 下载纪律

分片下载、断点续传、逐片校验；限速（第 6 章的“平台是后勤”）；只在窗口条件满足时下载（充电中、空闲）；下载完成后全量摘要校验再进入安装阶段。

9.4 端侧 OTA Agent

9.4.1 状态机

stateDiagram-v2
  [*] --> 空闲
  空闲 --> 等待窗口: 收到升级任务
  等待窗口 --> 下载中: 充电中 且 无任务 且 电量达标
  下载中 --> 校验中: 下载完成
  校验中 --> 失败: 签名/摘要/兼容/安全版本 不通过
  校验中 --> 预加载: 通过（写入备槽）
  预加载 --> 自检: 加载备槽模型
  自检 --> 失败: 固定样例推理异常
  自检 --> 观察期: 原子切换到新槽
  观察期 --> 已确认: 观察期指标正常
  观察期 --> 已回滚: 指标破线 → 切回旧槽
  失败 --> 空闲
  已确认 --> 空闲: 释放旧槽
  已回滚 --> 空闲

9.4.2 双槽热切换

模型不停机切换的核心：新模型写入并预加载到备槽，用固定样例做推理自检，然后在两个动作分块的间隙原子切换指针。观察期内旧槽保留，任何破线都能秒级切回；观察期结束后才释放旧槽内存（第 6 章的“备槽内存”就花在这里）。

9.4.3 防回滚：安全版本号

攻击者可能把设备降级到存在已知漏洞的旧版本。每个制品带 security_version，端侧在安全存储中维护“已确认的最低安全版本”：安装的制品安全版本低于该值一律拒绝。注意区分“业务回滚”与“安全回滚”：观察期内切回旧槽是正常业务回滚（旧槽的安全版本仍然有效）；只有新版本确认后才提升最低安全版本。

9.4.4 窗口条件与“平台是后勤”

窗口条件由设备状态决定：充电中、无在途任务、电量高于阈值、非作业时段（站点日历）。窗口不满足时 Agent 等待而不是强行执行——这与车辆“熄火、驻车、电量充足才升级”的逻辑完全一致，只是条件换成了机器人语义。

9.5 模型 OTA：从影子评测到灰度环

9.5.1 全链路

flowchart LR
  A["模型工厂产出<br/>（离线评测通过）"] --> B["仿真评测门禁"]
  B --> C["影子评测<br/>新模型只算不控"]
  C --> D["环 0：内部机器人"]
  D --> E["环 1：单站点 1%"]
  E --> F["环 2：多站点 10%"]
  F --> G["环 3：50%"]
  G --> H["环 4：全量"]
  C -. "分歧样本回传" .-> DATA["数据引擎"]
  E & F & G -. "门禁破线" .-> RB["自动回滚 + 冻结"]

9.5.2 影子评测：零风险的第一道真机门

新模型部署到备槽，与在线模型同时推理但只有在线模型控制。比较两者在同一观测上的动作分歧：分歧分布是否异常、分歧集中在哪些场景。分歧样本自动回传进入数据引擎（第 12 章）——影子评测同时是一次高价值的数据采集。这正是车联网智驾“影子模式”的原样迁移。

9.6 灰度引擎：以作业质量为门禁

9.6.1 批次的四个维度

维度 做法 目的
站点 先单站点、再多站点 控制爆炸半径、便于现场响应
机型 / 兼容组 按引擎矩阵分组 避免一个组的问题污染判断
健康分 先升健康分高的 排除设备本身问题的干扰
时段 避开高峰班次 出问题时有人手处理

9.6.2 门禁指标

指标 规则示例 性质
任务成功率 较基线下降超过 2 个百分点 → 破线 作业质量
人工介入率 较基线上升超过 30% → 破线 作业质量（最灵敏）
急停次数 任何非人为急停增加 → 一票否决 安全
推理 P99 越过时延不等式 → 破线 端侧健康
安装失败率 超过 1% → 暂停排查 分发健康

基线必须是同批次、同时段的未升级对照组，而不是历史平均——站点当天的物料、光照、班次都会影响成功率。

9.6.3 烘烤期与自动回滚三动作

每个环在进入下一环之前有烘烤期（例如累计 N 个任务或 T 小时），样本量不足时不做判断。门禁破线时执行三个动作：回滚（已升级设备切回旧槽）、冻结（该制品禁止继续分发）、取证（打包破线时段的遥测、事件、分歧样本给算法团队）。回滚要常态化演练，不演练的回滚路径在需要时一定会出问题。

z_score 是两比例 z 检验。“超阈值”与“显著”缺一不可：小环样本少，3 个百分点的波动完全可能是噪声；只看阈值的门禁会频繁误回滚，团队很快就会习惯性地“手动放行”，门禁从此形同虚设。

9.7 编排：Temporal 工作流

9.7.1 为什么用工作流引擎

一次模型发布持续数天、跨数千台设备、中间有等待窗口、人工审批、自动回滚——典型的长事务。Temporal 的持久化执行让每一步可重试、可恢复、可审计，与你在 XOTA 中用它编排升级任务是同一用法。

9.8 技能与地图的发布

9.8.1 技能

技能（行为树、任务脚本、算法插件）介于配置与代码之间：体积小、迭代快、影响行为。纳入同一套制品纪律：签名、兼容（依赖的 ROS 接口版本与 Device Profile 能力）、灰度、以任务成功率为门禁。

9.8.2 地图

地图是站点级制品：同一站点的所有机器人共用。发布流程：新地图先在一台机器人上验证定位质量 → 站内分批切换 → 旧地图保留用于回滚。地图与模型不要在同一窗口同时变更，否则门禁破线时无法归因。

9.9 与 XOTA 的逐项对照

9.9.1 对照表

XOTA OTA 2.0 变化
固件 A/B 分区 固件 A/B + 模型双槽 新增不停机切换
差分包 固件差分 + 模型全量分片 模型通常不做差分
车型 × 域控 × 版本 机型 × GPU 架构 × JetPack × 精度 × 契约 维度更多
升级窗口（熄火、驻车） 充电、空闲、电量、站点日历 语义替换
分批灰度 环 + 四维批次 新增健康分、站点维度
崩溃率门禁 作业质量门禁 + 对照组 本质变化
影子模式（智驾） 影子评测（模型） 原样迁移

9.10 案例推演：“能跑但干活变差”

9.10.1 现象

一个新版抓取模型通过了离线评测与仿真评测，在环 1（单站点 1%）运行两天，安装成功率 100%、无崩溃、推理 P99 正常。第三天运营反馈：这个站点的“抓取重试次数”明显增加。

9.10.2 分析

门禁里只有成功率（重试后最终仍然成功，所以成功率几乎没变），没有介入率与单任务耗时。进一步看分歧样本：新模型在反光包装物体上的抓取位姿偏差明显——训练数据里这类物体很少，离线评测集也没有覆盖。

9.10.3 平台动作

  1. 门禁新增“单任务耗时”和“重试次数”两个作业质量指标；
  2. 影子评测阶段的分歧样本按物体类别聚类，作为评测集的补充来源；
  3. 把“反光包装”加入数据引擎的定向采集任务（第 12 章），形成“线上问题 → 定向数据 → 新模型”的闭环；
  4. 复盘结论写进门禁配置的 ADR：门禁指标集合本身也是需要版本化和评审的制品。

⚠️ 一线踩坑

  • 只看稳定性指标：坏模型一路灰度到全量。对策：介入率、耗时、重试次数进入门禁，急停一票否决。
  • 拿历史均值做基线：站点当天换了物料批次，误判为模型退化。对策：同批次同时段对照组。
  • 门禁没有统计显著性：本书编写 p02 时的真实教训——初版门禁只比较阈值，好模型在只有 3 台设备的内部环被噪声误回滚。加入两比例 z 检验后，在 30 个随机种子下好模型 0 次误回滚、坏模型 30 次全部被拦截（第 18 章）。对策：门禁 = 阈值 + 显著性 + 最小样本量。
  • 观察期结束前释放旧槽：需要回滚时只能重新下载，回滚从秒级变成小时级。对策：确认后才释放。
  • 地图与模型同窗口变更：出问题无法归因。对策：同一站点同一窗口只变一类载荷。

🛠️ 动手练习

  1. 阅读 p02 的清单格式，为一个“感知模型 + 配置”组合发布设计两份制品清单，并说明它们的兼容矩阵差异。
  2. 运行 python -m otaflow.demo --scenario bad（第 18 章），观察门禁在哪一环、因为哪个指标破线。
  3. 为你熟悉的场景设计一套门禁指标，包括指标、阈值、样本量要求、对照组定义。

🎯 面试与评审要点

  1. 模型 OTA 和固件 OTA 的最大差异？（能跑但变差 → 作业质量门禁；双槽热切换；引擎矩阵）
  2. GB 级模型发万台怎么做？（四级瀑布 + 预热 + 分片续传校验，两个数量级的流量账）
  3. 如何防止设备被降级到有漏洞的旧版本？（安全版本号，区分业务回滚与安全回滚）
  4. 灰度门禁为什么要对照组？（消除站点与时段因素）

📝 本章卡片

  • 四类载荷：固件、模型、配置、技能（含地图），切换与回滚方式各不相同。
