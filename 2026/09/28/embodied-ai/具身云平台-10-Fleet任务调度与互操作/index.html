第 10 章 Fleet 任务、调度与互操作

层与层之间只传“目标与结果”，不传“过程与指令”：L2 不关心机器人用哪条路径，L3 不关心 VLA 输出了哪些动作块。

Flywhl 10 分钟 发布于 2026.09 #机器人云平台#Fleet调度#VDA 5050

先读结论

  1. 四层任务模型：订单、机队任务、机器人任务、技能动作——层间只传目标与结果。
  2. 任务租约：进度续租、到期回收、迟到忽略、ID 幂等。
  3. 分配五要素：能力、状态、电量、位置、健康分。
  4. 锁必须有 TTL：共享资源的持有者心跳与本地降级。
  5. 避碰不上云：运动级协同一律本地。

本章定位：任务面决定机器人能不能“持续干活”。本章给出四层任务模型、任务租约、调度评分、充电与共享资源、多机协同分界，以及两个平台架构师必须了解的互操作标准——VDA 5050（基于 MQTT + JSON，车联网架构师最容易上手）与 Open-RMF。
对应代码：p01（任务状态机与租约回收）、p04（Agent 生成任务）｜建议学时：5 小时

10.1.2 层间契约

层与层之间只传“目标与结果”，不传“过程与指令”：L2 不关心机器人用哪条路径，L3 不关心 VLA 输出了哪些动作块。云平台的边界在 L3——这是第 3 章“云只下目标”和第 7 章“控制下行皆任务”在任务面的落地。

10.2 任务状态机与租约

10.2.1 状态机

stateDiagram-v2

  SENT --> ACCEPTED: 端侧准入通过
  SENT --> REJECTED: 忙/电量/类型/模式

  SENT --> RECLAIMED: 租约到期
  ACCEPTED --> RECLAIMED: 租约到期
  RUNNING --> RECLAIMED: 租约到期

10.2.2 租约：为什么任务必须有“保质期”

机器人会断网、会假死、会被人推走。如果任务没有租约，这些情况下任务会永远停在“执行中”，调度系统以为机器人在忙，业务订单无限期等待。租约的规则：派单时设定租约，端侧每次进度事件续租，租约到期未续则回收改派。

这套机制对你并不陌生：它就是 Kafka 消费组的会话超时与再均衡，只是“分区”换成了“任务”，“消费者”换成了“机器人”。

10.2.3 三个细节

  1. 长阶段也要续租：单个阶段可能超过租约时长（如长距离移动），端侧要有周期性进度心跳——p01 的测试 test_long_stage_keeps_lease_alive 专门验证这一点；
  2. 回收后的迟到成功：机器人恢复后上报“成功”，云端已回收改派——必须忽略迟到事件，并在业务层面处理“可能重复执行”；
  3. 幂等：任务 ID 是幂等键，端侧维护近期已执行任务 ID 表，重复下发不重复执行。

10.3 调度：派给谁

10.3.1 分配五要素

要素 数据来源 作用
能力 Device Profile 的 skills 硬过滤：不会做的不派
状态 在线判定（第 8 章） 硬过滤：只派 ONLINE
电量 遥测 硬约束：够完成任务并返回充电位

健康分 / 负载 孪生档案 评分：健康高、空闲优先

10.3.2 评分函数示例

10.3.3 调度演进三段

最近可用（先跑起来）→ 加权评分（本节）→ 批量优化（把一批任务与一批机器人一起求解，考虑路径冲突与节拍）。多数场景第二段就够用；第三段要等任务密度高、路径冲突成为主要瓶颈时再做。

10.4 充电调度

10.4.1 充电是一类任务

充电不是机器人的私事，而是需要平台排程的任务：充电桩有限、充电期间不可派单、多台同时低电量会造成“抢桩”。策略：阈值触发 + 错峰排程 + 机会充电（空闲时就近补电），充电任务与普通任务同样走状态机与租约。p01 的 charge 任务类型的最低电量门槛是 0——任何电量都允许去充电。

10.5 地图：站点的共享制品

10.5.1 地图的两层

几何层（占用栅格或点云地图，定位用）与语义层（工位点、货架、禁行区、限速区、电梯与闸机位置）。平台管理的重点是语义层：它变化更频繁（今天临时堆了料），并且直接影响调度与安全。

10.5.2 发布纪律

地图变更走第 9 章的制品纪律：版本化、签名、先单台验证定位质量、再站内分批切换、保留旧版本可回滚。禁行区的变更属于安全相关配置，需要审批。

10.6 共享资源：电梯、闸机、窄通道

10.6.1 资源锁

跨楼层搬运需要乘电梯，窄通道一次只能过一台，闸机需要开门。平台为这些共享资源提供带 TTL 的锁：机器人申请、获得后使用、使用完释放；TTL 到期自动释放，防止机器人故障后资源被永久占用。

10.6.3 两条纪律

  1. 锁必须有 TTL 与持有者心跳，否则一台机器人卡在电梯里，整层楼的机器人都会排队；
  2. 断云时有本地降级策略：机器人不应在没有锁的情况下进入共享资源，而是在安全等待区停下。

10.7 多机协同的分界

10.7.1 任务级归云，运动级归本地

协同类型 例子 归属 理由
任务分配 谁去搬哪一箱 云（Fleet） 需要全局视野，秒级即可
资源互斥 电梯、窄通道 云（锁）+ 本地降级 需要全局仲裁
路径协调 交通管制、让行 边缘或云（秒级） 需要多机视野
避碰 两台机器人迎面相遇 本地 毫秒级，不能依赖网络
协作搬运 两台共同抬一件物品 本地（机间直连） 高频同步

避碰上云是评审否决项：网络一抖，碰撞就发生了。

10.8 VDA 5050：用 MQTT 调度移动机器人

10.8.1 它是什么

VDA 5050 是德国汽车工业协会与机械设备制造业联合会共同发布的AGV/AMR 与主控系统通信标准，目标是让一个主控系统可以调度多家厂商的移动机器人。它的底层就是 MQTT + JSON——对车联网架构师来说，这是最友好的机器人标准。

10.8.2 主题结构

主题格式为 接口名/主版本/厂商/序列号/主题，例如 uagv/v2/AcmeRobotics/SN0001/order。核心主题：

主题 方向 内容 车联网类比
order 主控→机器人 由节点与边组成的路径订单 远程任务
instantActions 主控→机器人 立即动作（暂停、取消、充电） 实时远控指令
state 机器人→主控 位置、订单进度、动作状态、电量、错误 车辆状态上报
visualization 机器人→主控 高频位置（可视化用） 高频轨迹
connection 机器人→主控 在线/离线（配合遗嘱） 在线状态 + LWT
factsheet 机器人→主控 能力描述 车型信号矩阵 / Device Profile

10.8.3 订单的“已发布区 + 预览区”

released: true 的部分（base）机器人可以执行；released: false 的部分（horizon）只是预告，主控在交通条件允许时通过 orderUpdateId 递增的更新订单逐段“放行”。这是一种非常优雅的交通管制机制：主控掌握放行节奏，机器人掌握运动细节——正好符合 10.7 的分界原则。（示例为结构示意，字段以标准文本为准。）

10.8.4 与 ECL v1 的关系

本书的 ECL v1 面向“通用机器人任务”，VDA 5050 面向“移动机器人路径订单”。实际平台中常见的做法是：对移动底盘类机器人（AGV/AMR）直接支持 VDA 5050，对复合机器人与人形机器人使用自有任务协议，并在 Fleet 层做统一抽象。协议适配器是平台接入面的标准组件。

10.9 Open-RMF：多机队互操作

10.9.1 解决什么问题

当一个园区里同时运行多家厂商的机器人（清洁、配送、安防），各自的调度系统互不相识，会在走廊、电梯、门禁处互相堵死。Open-RMF（Robotics Middleware Framework，ROS 生态）提供：机队适配器（接入各厂商调度系统）、交通时间表（跨机队的路径冲突协调）、门与电梯适配器、任务分派。

10.9.2 平台视角的定位

Open-RMF 适合“多厂商共存的园区/楼宇”；单一厂商、单一机队的平台通常自建 Fleet 层即可，但资源锁、交通协调的设计可以借鉴它的抽象。评估时关注：与你的云平台如何分层（RMF 多部署在站点边缘）、与自有任务协议的映射、与楼宇系统（电梯、门禁）的对接成本。

10.10 与业务系统集成

10.10.1 集成层职责

  1. 订单转换：MES/WMS 的业务订单 → L2 机队任务（拆分、批次、优先级）；
  2. 状态回写：任务完成、失败、异常 → 回写业务系统，带业务单号；
  3. 异常升级：无法自动完成的任务（多次失败、需要人工）→ 生成工单进入人工处理队列。

集成层用 Temporal 工作流实现最自然：一个业务订单就是一个工作流，子任务是子工作流或活动，失败重试与人工介入节点都是工作流的一部分。

10.11 任务面的指标

10.11.1 三个核心指标

指标 定义 意义
无人工闭单率 无任何人工介入即完成的任务占比 任务面的第一 KPI：直接决定运营成本
派单成功率 派出后被接受并开始执行的比例 反映在线判定与准入是否准确
订单准时率 业务订单在承诺时间内完成的比例 业务方最关心的结果

“无人工闭单率”同时是数据飞轮的晴雨表：每一次人工介入都是一条高价值训练样本（第 12 章）。

10.12 案例推演：电梯锁死，半个楼层机器人排队

10.12.1 现象

下午两点起，6 楼有十几台机器人在电梯厅排队，订单准时率骤降。

10.12.2 根因

一台机器人在电梯内因定位丢失而停止，未释放电梯锁；锁的实现没有 TTL，只在机器人主动释放时才解除。电梯被永久占用，后续所有跨楼层任务都在等待。

10.12.3 平台动作

  1. 锁加 TTL 与持有者心跳，心跳停止即释放并告警；
  2. 电梯内停止的机器人触发“远程接管”工单（第 11 章），由远程人员把它引导出电梯；
  3. 调度器对排队超过阈值的任务自动改派或调整订单优先级；
  4. 把“电梯内定位丢失”加入故障图谱与数据回传触发条件——它是一个高价值的长尾场景。

⚠️ 一线踩坑

  • 任务没有租约：机器人断网后任务永远“执行中”。对策：租约 + 续租 + 回收，长阶段周期心跳。
  • 锁没有 TTL：一台故障机器人锁死电梯。对策：TTL + 持有者心跳 + 本地降级。
  • 避碰依赖云端：网络抖动时发生碰撞。对策：运动级协同一律本地。
  • 只统计成功率：人工介入后完成的任务也算成功，掩盖了真实运营成本。对策：无人工闭单率作为第一 KPI。

🛠️ 动手练习

  1. 在 p01 中实现一个最简调度器：给定任务类型与目标点，按 10.3.2 的评分函数从在线机器人中选择一台并派单，补测试。
  2. 为 p01 增加“资源锁”接口（申请、续期、释放、TTL 回收），并写出电梯场景的测试。
  3. 把 10.8.3 的 VDA 5050 订单映射成 ECL v1 的任务序列，写出映射规则与信息损失。
