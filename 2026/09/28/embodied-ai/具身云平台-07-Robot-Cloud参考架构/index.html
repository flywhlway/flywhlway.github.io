7.1 先写量级，再画框图

7.1.1 设计基线

架构图之前先写数字。本书的设计基线对标 2026 年头部玩家的中期规模：

维度 假设 推导
机器人数 1 万台 与 2026H1 全行业出货同量级的单一平台
站点数 200 个 工厂、仓库、门店、园区
遥测 每台 1–5Hz × 约 1KB 稳态约 10–50MB/s，按机器人 ID 分区即可
事件 每台每小时数十条 小量高价值，长期保存
数据回传 每台每天 1–3GB 触发片段 全机队每天 10–30TB 候选，必须边缘筛选
模型分发 每次 4–16GB × 引擎矩阵 × 1 万台 必须有站点缓存，否则单次发布数百 TB 公网流量
任务 每台每天数十至数百个 峰值随班次集中

7.1.2 三个数字改变架构

  1. 遥测量不是问题：车联网百万车级的遥测管道已经远超这个量级；
  2. 回传量是问题：比车联网大两到三个数量级，决定了数据面必须“端侧裁剪 + 边缘筛选 + 夜间错峰”；
  3. 模型分发量是问题：GB 级制品 × 万台，决定了分发网络必须是一等公民，而不是 OTA 的附属功能。

7.3 三句读图纪律

7.3.1 纪律一：南向只有两个门

MQTT 走高频小报文（遥测、事件、任务、影子），网关走会话与文件（诊断会话、日志拉取、数据片段上传、制品下载）。两类流量的 SLA、扩缩容特性、限流策略完全不同，混在一起必然互相拖累。出现“第三个南向入口”的方案，评审时要求给出充分理由。

7.3.2 纪律二：制品永不走 MQTT

GB 级的模型、固件、地图走分发网络（CDN + 站点缓存 + 站内分发），MQTT 只传“去哪里下载、校验和是多少”这样的指针。

7.3.3 纪律三：控制类下行一律是任务

OTA、调度指令、诊断动作、Agent 的决策——所有会改变机器人行为的下行，最终都收敛为带 ID、带租约、带审计的任务。没有任何旁路可以直接“遥控关节”。这一条是第 3 章“云只下目标”的架构化表达，也是第 15 章 Agent 安全的根基。

7.4.2 增量只有四块

逐项看完会发现，真正没有车联网对应物的只有四块：模型 OTA 子系统（双槽热切换、影子评测、引擎矩阵）、边缘推理（站点推理池与端侧运行时管理）、仿真接入（仿真评测与合成数据）、机器人语义的数据引擎（多模态片段、质量漏斗、训练数据集）。这张表就是你的转型叙事，也是立项时估算工作量的依据。

7.5.2 站点边缘的三项职责与三项“不做”

做：制品与数据缓存、秒级推理池、断云自治（本地任务队列、本地告警、凭据宽限）。不做：训练、全局调度、长期明细存储。边缘是“缓存与执行的延伸”，不是小号云——把能力堆上边缘会让 200 个站点的运维半径爆炸。边缘集群用 GitOps 拉模式管理：每个站点拉取自己的期望状态并上报实际状态，这与设备影子是同一哲学，只是对象从机器人换成了集群。

7.6.2 隔离纪律

遥测流不承载任务语义，任务流不搬运字节，学习流不进实时链路。三条流的 SLA、存储、失败处理方式都不同：遥测丢几条可以接受，任务一条都不能丢，学习流延迟一天也没关系。把它们混在同一条管道里，是平台后期最难拆的技术债之一。

7.7.2 ADR 制度

选型矩阵的每一行都对应一份架构决策记录：动机、备选、权衡、影响面、回退方案。改选型必须写 ADR——参考架构的一半价值在选型本身，另一半在“改选型有据可查”。

7.8 多租户与私有化交付

7.8.1 机器人平台的特殊交付形态

车联网平台通常是车企自营；机器人平台则常常要交付给客户：工厂、物流、零售客户出于数据主权与网络隔离要求，普遍要求数据不出厂、平台本地化部署。于是出现三种形态：

形态 说明 平台要求
公有云 SaaS 厂商统一运营 严格多租户隔离、按租户计量
混合云 控制面在厂商云，数据面与边缘在客户侧 控制与数据分离、断云自治
全私有化 整个平台部署在客户机房 平台可离线安装、可升级、可远程运维

7.8.2 设计原则

控制面与数据面分离：客户侧保留原始数据与边缘；厂商云只拿到脱敏的聚合指标、授权回传的训练片段与模型制品通道。租户是一等维度：从主题树、存储分区、密钥、配额到审计，全部带租户 ID。私有化可升级：平台自身也需要 OTA——用 GitOps 管理客户侧部署的版本与配置。

7.9 与工业系统集成

7.9.1 北向集成对象

机器人在工厂里不是孤立的：订单来自 MES/WMS，物料来自 ERP，协同对象是 AGV、输送线、电梯与门禁。平台需要一个集成层：把业务系统的订单转换成 Fleet 任务，把任务结果回写业务系统。

7.9.2 行业标准

标准 定位 平台意义
VDA 5050 AGV/AMR 与主控系统通信标准，基于 MQTT + JSON 车联网架构师最容易上手的机器人标准，第 10 章详述
Open-RMF 多厂商、多机队互操作框架（ROS 生态） 电梯、门禁、跨机队调度
OPC UA 工业设备信息模型 与产线设备对接

7.10 演进路线

7.10.1 四阶段

阶段 周期 交付 验收
P0 骨架 1–2 月 接入 + 身份 + 遥测 + 在线判定 + 最小 OTA “看得见、升得了”
P1 闭环 2–3 月 模型 OTA（双槽 + 灰度 + 回滚）+ 触发回传 + 开环回放 一次安全的模型灰度
P2 飞轮 3–6 月 数据引擎、三级评测、Fleet 任务面、诊断工作流 飞轮转速可度量
P3 规模 持续 多站点边缘、私有化交付、安全全量、Agent 平台 千台到万台

每个阶段独立可验收、独立产生价值——不做“两年后见”的大平台豪赌。

7.11 案例推演：一家车企工厂从 20 台到 2000 台

7.11.1 20 台（试点）

痛点：升级靠工程师上门，故障靠远程桌面，数据靠拷硬盘。平台动作：接入现有车联网平台的账号与接入层，上线 P0 骨架（本书 p01 的形态）。

7.11.2 200 台（多车间常态部署）

新痛点：模型每两周迭代一次，每次全量升级都有停线风险；不同车间机型与软件版本分化。平台动作：P1 模型 OTA（按车间与机型分批、以介入率为门禁、自动回滚），建立引擎矩阵与兼容矩阵；上线站点缓存。

7.11.3 2000 台（多基地、多客户）

新痛点：模型改进变慢（“不知道哪里还不行”），跨基地调度与资源冲突，部分基地要求数据不出厂。平台动作：P2 数据引擎与评测门禁把飞轮转起来；任务面接入 MES 与电梯门禁；私有化与混合云交付形态；安全面全量上线。

每一步都是车联网平台在“十万辆 → 百万辆”阶段经历过的事情，只是换了对象。

⚠️ 一线踩坑

  • 先画框图后算账：上线后才发现回传量把专线打满。对策：架构评审第一页必须是量级表。
  • 把边缘做成小云：在站点部署训练与全量存储，200 个站点运维失控。对策：边缘三做三不做写进架构原则。
  • 忽视私有化：SaaS 架构拿到工厂客户那里无法离线部署。对策：从 P0 就做控制面与数据面分离、租户一等维度。
  • 旁路下行：为了演示方便加了“直接下发速度指令”的调试接口，后来被当成功能使用。对策：纪律三作为评审否决项。

🛠️ 动手练习

  1. 以你熟悉的一个工厂为对象，重算 7.1.1 的量级表（机器人数、站点、回传量、模型分发量）。
  2. 用 7.4.1 的映射表，为你所在团队写出“直接可复用”的模块清单与“需要改造”的模块清单，各估一个人月数。
  3. 对照本书六个工程，在 7.2.1 的全景图上标出每个工程覆盖的平面，找出本书没有覆盖、你所在场景又必须有的能力。

🎯 面试与评审要点

  1. 画出你的机器人云平台架构，并给出量级假设。（八平面 + 三个改变架构的数字 + 三句纪律）
