第 20 章 实战四：具身 Agent 调度大脑——让一句话安全地变成一个任务

p04 把第 15 章的具身 Agent 平台做成可运行工程，并进程内驱动 p01 的仿真机队：Agent 下发的任务会被仿真机器人真实执行、续租、完成。

Flywhl 7 分钟 发布于 2026.09 #Agent#安全#实战项目

先读结论

  1. 接缝才是风险：Agent 与平台之间的状态、错误处理、过滤条件。
  2. 先结构后状态再风险：安全笼的检查顺序。
  3. 规划器可替换：换模型不动安全逻辑。

本章定位：p04 把第 15 章的具身 Agent 平台做成可运行工程，并进程内驱动 p01 的仿真机队：Agent 下发的任务会被仿真机器人真实执行、续租、完成。本章沿 11 幕剧本逐一对照安全笼的七道检查，并复盘构建中发现的三个真实缺陷。
代码位置：code/p04-embodied-agent（依赖 code/p01-robofleet-core）｜对应理论：第 10、15、16 章｜建议学时：6 小时

20.2.2 与 p01 的集成方式

P01FleetClient 直接包装 p01 的 FleetService：读取孪生（robot_view）、查询任务表（list_tasks）、创建任务（create_task）。换成 HttpFleetClient 即可对接独立部署的 p01 服务，Agent 代码不变。Agent 的 trace_id 作为 agent_trace_id 写入任务参数——从一句自然语言到机器人的一个动作阶段，沿同一个 ID 可追溯。

20.4 构建复盘：三个真实缺陷

20.4.1 缺陷与修复

# 现象 根因 修复
1 第 3 幕 Agent 崩溃，异常为 p01 的 TaskRejected: robot busy 自动选车用遥测里的 task_id 判断忙闲；amr-001 刚接单，遥测尚未刷新，被当作空闲选中 Fleet 客户端新增 is_busy()，查询权威任务表
2 同上，平台拒绝直接抛出到 Agent 外层 只考虑了安全笼拒绝，没考虑平台准入这第二道闸 捕获平台拒绝，返回 platform_rejected 并写审计
3 测试中自动选中了“维护中”的机器人 选车只看在线状态，没看生命周期 增加 lifecycle == active 过滤

此外，情景记忆最初写入时用了固定键、读取时按用户查询，导致“继续巡检”找不到上下文——修正为按用户记录。

还有第四个缺陷，单进程剧本永远发现不了：全家桶多进程联调（第 22 章）时，仿真机队的 ID 是 cap-001，而规则规划器的正则写死了 amr-、ros- 等前缀，所有指令都返回“无法规划”。修复是把 ID 匹配泛化，并补回归测试 test_planner_accepts_any_registered_id_format。教训：设备 ID 的命名空间属于设备注册表，不属于任何下游组件；也再次说明联调必须用与生产相同的形态跑一遍。

20.4.2 这三个缺陷说明了什么

它们都不是“AI 问题”，而是分布式系统问题：状态滞后、两个系统之间的错误处理、过滤条件遗漏。具身 Agent 平台的大部分工程风险，恰恰在 Agent 与平台的接缝上——这也是车联网平台架构师最有优势的地方。

20.5 代码导读

20.5.1 安全笼的顺序为什么是这样

顺序原则：先结构、后状态、再风险。结构性检查（工具是否存在、参数是否合法）不依赖任何外部状态，最快也最可靠；状态检查（在线、电量）依赖孪生；风险与污染决定是否需要人。速率限制放在状态检查之后，避免被拒绝的请求消耗配额。

20.5.2 规划器的可替换性

这就是“规划器只提议”的工程含义：换模型不需要重新评审安全逻辑，只需要重新评估规划质量。

20.6 实验

20.6.1 六个实验

  1. 接入一个 OpenAI 兼容大模型（DeepSeek 等），用 20 条指令对比规则规划器与大模型规划器的规划准确率，并统计安全笼拦截数；
  2. 构造 10 条变体注入文本（中英混写、同义改写、拆字），测试 injection.screen 的召回率，思考为什么不能只依赖它；
  3. 为“跨楼层”搬运增加风险规则：命中站点记忆“电梯高峰”时段则需要人审；
  4. 实现多步任务：一次指令生成三步计划，按顺序下发，任一步失败则停止并审计；
  5. 用 HttpFleetClient 对接以服务形态运行的 p01（第 17 章的多进程方式）；
  6. 把技能目录导出为 MCP 工具定义，让一个外部 Agent 以只读方式查询机队状态。

20.7.1 对照表
