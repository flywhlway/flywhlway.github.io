第 8 章 设备接入、身份与数字孪生

平台代码面向 Profile 编程，而不是面向某个机型：OTA 的兼容检查读 compute，Agent 的技能目录读 skills（第 15 章）…

Flywhl 11 分钟 发布于 2026.09 #MQTT#设备接入#数字孪生

先读结论

  1. Device Profile 编程：平台面向能力描述而不是面向机型。
  2. 信任锚在产线：没有产线证书永远进不了平台。
  3. 只碰自己的子树：主题 ACL 模板化。
  4. 三信号在线判定：连接 + 遥测新鲜度 + 机内活性。
  5. 影子三要义：单向写、delta 幂等、收敛超时告警。

本章定位：设备面与接入面是平台的地基。本章给出机器人身份体系、注册激活、接入层 ACL、ECL v1 端云协议规范、三信号在线判定、影子与数字孪生、生命周期与配置基线——每一项都附 p01 中的实现位置。
对应代码：p01-robofleet-core（service.py、protocol.py、sim_robot.py）｜建议学时：5 小时

8.1 设备模型

8.1.1 四个标识

概念 定义 车联网对应
Robot ID 平台唯一逻辑身份：证书 CN、主题树根、数据分区键、日志字段 VIN
SN / 部件序列号 本体序列号 + 关键部件（关节模组、主控、电池、相机）序列号 车辆 SN、零部件追溯
机型 / 硬件版本 决定兼容矩阵的型号标识 车型、配置字
Device Profile 该机型的能力描述：话题、任务、传感器、资源规格 车型信号矩阵

8.1.2 Device Profile 示例

平台代码面向 Profile 编程，而不是面向某个机型：OTA 的兼容检查读 compute，Agent 的技能目录读 skills（第 15 章），调度的约束读 max_speed_mps 与 safety。新机型接入时只需新增一份 Profile。

8.2 身份体系

8.2.1 两级 CA 与产线出生证书

信任结构：离线根 CA → 按产品线的中间 CA → 设备证书（CN = Robot ID）。设备证书在产线安全工位签发，私钥生成并保存在安全芯片或 TPM 中、永不导出（第 16 章）。没有产线证书的设备永远进不了平台——信任锚定在制造环节，与 TBox 产线灌装证书完全同构。

8.2.2 一根多用途

同一个 PKI 为不同用途签发证书：设备证书（连接云端 MQTT）、节点证书（机内 DDS 安全，第 16 章）、边缘服务证书（站点集群）。证书周期分层：根 CA 长期离线；中间 CA 可按产品线吊销止损；设备证书一年级自动轮换；接入令牌小时级。

8.2.3 教学实现与生产实现

p01 为了能在一台笔记本上跑通，用“注册时生成一次性密钥、平台只存哈希、激活时比对”的方式模拟身份：

生产实现把“共享密钥”换成“产线证书 + mTLS 握手 + 证书链校验 + 吊销检查”，其余流程不变。

8.3 注册与激活

8.3.1 首次开机时序

---
sequenceDiagram
  participant R as 机器人<br/>(云桥/OTA Agent)
  participant G as 接入网关<br/>(mTLS)
  participant I as 身份服务
  participant D as 设备服务<br/>(注册/生命周期)
  participant S as 影子服务

  R->>G: TLS 握手（产线设备证书）

  D-->>R: 激活成功 + 接入凭据 + 主题前缀
  R->>G: 建立 MQTT 长连接（设置遗嘱）
  R->>S: 首次全量 reported

8.3.2 两个硬门禁

  1. 激活即绑定配置基线：激活时必须落到唯一的“机型基线 + 站点覆盖”，杜绝没有配置归属的“裸设备”；
  2. 防克隆：激活请求携带部件序列号指纹，与主数据核对；同一 Robot ID 在两个地点同时激活要告警。

8.4 接入层

8.4.1 主题 ACL：每台机器人只能碰自己的子树

以 EMQX 为例，ACL 的思路是“用户名 = Robot ID，只允许读写 ecl/v1/${username}/#”：

上行只能发上行主题、下行只能订下行主题、只能碰自己的子树——一台机器人被攻破，也无法冒充其他机器人或偷听别人的任务。p01 在应用层再做一次校验：未激活设备的上行消息全部丢弃并计数（rejected_uplink_msgs，作为安全审计指标）。

8.4.2 会话与连接治理

问题 做法
弱网断续 持久会话 + QoS 1 + 端侧分级离线缓存（第 5 章）
重连风暴 端侧指数退避 + 随机抖动；服务端连接速率限制
ClientID 冲突 ClientID = Robot ID；重复连接踢旧并告警（可能是克隆）
大文件 永不走 MQTT，走网关文件通道

8.5 ECL v1 端云协议规范

8.5.1 主题树

主题 方向 QoS 保留 说明
ecl/v1/{rid}/telemetry ↑ 0/1 否 聚合状态，1–5Hz
ecl/v1/{rid}/event ↑ 1 否 故障、安全、业务事件
ecl/v1/{rid}/status ↑ 1 是 上线/下线；遗嘱消息发这里
ecl/v1/{rid}/shadow/reported ↑ 1 否 实际状态 + 机内活性
ecl/v1/{rid}/shadow/delta ↓ 1 否 期望与实际的差集
ecl/v1/{rid}/task/cmd ↓ 1 否 任务下发（带租约与 trace_id）
ecl/v1/{rid}/task/event ↑ 1 否 任务状态事件（兼作续租）

8.5.2 载荷示例

8.5.3 协议演进规则

  1. 只增不改：新增字段向后兼容，接收方忽略未知字段；
  2. 破坏性变更升版本：ecl/v2/... 与 v1 并行一段时间；
  3. 契约测试守门：p06 的契约测试逐项比对端云常量（任务类型、阶段、可写字段、主题格式），协议漂移在 CI 就被拦下。

8.6 三信号在线判定

8.6.1 为什么一个信号不够

信号 能发现 发现不了
MQTT 连接 + 遗嘱 断电、断网、进程崩溃 进程活着但业务线程卡死
遥测新鲜度 业务停止上报 上报正常但机内关键节点已死
机内活性（DDS Liveliness 汇总） 关键节点失活 —

8.6.2 判定规则

新鲜度用云端接收时刻判断，不信任设备时钟（设备时钟可能漂移）。第 5 章的漫游案例还要求加“短暂离线宽限”，避免 Wi-Fi 切换引起状态抖动。

8.6.3 状态的业务含义

状态 调度 告警 OTA
ONLINE 可派单 — 可纳入批次
DEGRADED 不派新单 站点值班 暂停
ZOMBIE 不派单，回收在途任务 站点值班（高优） 暂停
OFFLINE 不派单 超过阈值才告警 排除

8.7 影子：期望态驱动

8.7.1 三条要义

  1. 单向写权限：平台只写 desired，设备只写 reported，两边不会“打架”；
  2. delta 驱动：只下发差集；设备重连后再下发一次差集即可自动补齐，天然幂等；
  3. 收敛超时告警：desired 与 reported 长时间不一致，说明端侧拒绝或失败——这是配置漂移的实时探测器。

8.7.2 实现要点

端侧只接受白名单字段（report_hz、speed_limit、model_ver、mode），并在参数校验回调里做范围检查（第 4 章）。p01 的测试覆盖了“白名单拦截未知键 → 影子保持未收敛”的路径。

8.7.3 端到端链路

sequenceDiagram
  participant Ops as 运营/上层服务
  participant Sh as 影子服务
  participant Br as 云桥（端侧）
  participant Node as 目标节点参数
  Ops->>Sh: PATCH desired {report_hz: 2}
  Sh->>Br: shadow/delta {ver:5, delta:{report_hz:2}}
  Br->>Node: set_parameters（校验回调）
  Node-->>Br: successful
  Br->>Sh: shadow/reported {report_hz: 2}
  Sh-->>Ops: converged = true

8.8 数字孪生三层

8.8.1 影子、档案、仿真孪生

层 内容 价值
L1 影子 desired / reported / delta 运行态真相源
L2 全息档案 影子 + Profile + 部件与标定 + 软件版本 + 历史遥测与事件 + 健康分 运维、诊断、灰度与调度的数据服务
L3 仿真孪生 结构（URDF）与站点场景进入仿真器 推演、预演、培训（第 14 章）

建设顺序严格 L1 → L2 → L3，绝大多数运营价值在前两层。

8.8.2 孪生的 API 比 UI 重要

孪生不是大屏，而是其他平面的数据服务：OTA 读它筛选合格设备，灰度引擎读健康分排批次，调度读电量与位置分配任务，诊断读它作为会话首屏。唯一写入路径（影子服务），多路只读投影——防止各团队旁路直写设备状态。

8.8.3 健康分

健康分把多维指标压缩成一个可排序的数：关节温度与跟随误差、电池健康、近 7 天故障次数、人工介入率、标定新鲜度。它的用途是排序而不是诊断：OTA 先升健康分高的设备，调度优先派给健康分高的设备。健康分模型本身要版本化，能对同一段历史数据重算，保证批次决策可审计。

8.9 生命周期

8.9.1 状态机与平台动作

stateDiagram-v2
  [*] --> 已生产: 产线签发证书
  已生产 --> 已注册: 录入主数据
  已注册 --> 在营: 首次激活 + 绑定基线
  在营 --> 维护中: 故障/保养/召回
  维护中 --> 在营: 修复验证通过
  在营 --> 退役: 到期/报废
  退役 --> [*]: 吊销证书 + 数据归档

每个迁移都挂平台动作：进入“维护中”自动暂停该机的 OTA 批次与派单（p01 中 set_lifecycle 后派单会被拒绝）；进入“退役”触发证书吊销、影子冻结、数据归档。状态机就是运营流程的代码化。

8.10 配置基线

8.10.1 三层配置

机型基线（随机型发布）→ 站点覆盖（只写差异）→ 单机例外（审批制，数量要监控）。配置下发走影子期望态或配置 OTA；端侧落点是 ROS 2 参数（第 4 章）。单机例外越多，机队越难运维——把“单机例外数量”做成治理指标。

8.11 案例推演：假死机器人被派了活

8.11.1 现象

调度系统把一个紧急搬运任务派给了一台“在线”的机器人，十分钟后任务仍无进展，产线等料停线。

8.11.2 根因

该机器人的任务执行节点因单线程执行器里的同步等待而死锁（第 4 章），云桥进程仍然活着、MQTT 连接正常——只看连接的在线判定认为它“在线”。遥测也在上报，因为遥测由另一个节点负责；但机内活性（执行器节点的 Liveliness）早已丢失。

8.11.3 平台动作

  1. 在线判定升级为三信号，执行器节点纳入活性汇总，机器人被判为 DEGRADED，不再派单；
  2. 任务租约（第 10 章）保证即使判定漏网，任务也会在租约到期后被回收改派；
  3. 端侧修复死锁，并把“回调中禁止同步等待”写入代码规范与静态检查。

三道防线（判定、租约、端侧纪律）任何一道单独都不够。

车联网 机器人 迁移方式

⚠️ 一线踩坑

  • Robot ID 与证书脱钩：用自增 ID 当业务主键，证书 CN 另一套编号，审计时无法关联。对策：Robot ID 一处签发、处处引用。
  • ACL 放行通配：为了省事允许设备订阅 ecl/v1/+/task/cmd，一台被攻破即可偷听全机队任务。对策：模板化 ACL，只允许自己的子树。
  • 影子无白名单：云端误下发一个未知字段，端侧照单全收。对策：端云双侧白名单 + 参数校验回调。
  • 只看连接判在线：假死设备被派活（8.11）。对策：三信号 + 租约。

🛠️ 动手练习

  1. 运行 python -m robofleet.demo，对照输出解释第④幕“ZOMBIE + 任务回收”是哪两段代码共同作用的结果。
  2. 在 p01 的在线判定里实现“短暂离线宽限”：OFFLINE 在 5 秒内恢复不产生离线事件，并补一个测试。
  3. 为你的目标机型写一份 Device Profile，并说明 OTA、调度、Agent 分别会读取哪些字段。

🎯 面试与评审要点

  1. 设计万台机器人的身份体系。（两级 CA、产线锚定、CN=Robot ID、轮换吊销、一根多用途）
  2. 在线状态为什么不能只看 MQTT 连接？（假死；三信号；云端接收时刻判新鲜度）
  3. 影子的三条要义是什么？（单向写、delta 幂等、收敛超时告警）
  4. 协议如何演进而不破坏存量设备？（只增不改、升版本并行、契约测试）
