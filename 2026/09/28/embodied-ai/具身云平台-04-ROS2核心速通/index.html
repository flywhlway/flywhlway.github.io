4.1 ROS 2 是什么，不是什么

4.1.1 一句话定义

ROS 2（Robot Operating System 2）不是操作系统，而是运行在 Linux 之上的一套机器人软件框架：它定义了“节点如何通信”（话题、服务、动作、参数），提供构建、启动、录制、调试工具，并有一个庞大的开源软件包生态（导航 Nav2、机械臂规划 MoveIt、ros2_control 等）。

4.1.2 分层结构

flowchart TB
  APP["你的节点（Python / C++）"] --> CL["客户端库 rclpy / rclcpp"]
  CL --> RCL["rcl：通用 C 层（名字解析、参数、生命周期）"]
  RCL --> RMW["rmw：中间件抽象接口"]
  RMW --> DDS["Fast DDS / Cyclone DDS"]
  RMW --> ZEN["Zenoh（rmw_zenoh）"]

rmw 抽象层是理解 ROS 2 的钥匙：上层代码不关心底层用哪种传输，切换只需要改一个环境变量 RMW_IMPLEMENTATION。这和你在 Spring Cloud 里“面向接口编程、实现可替换”的思路完全一致。

4.1.3 2026 年版本怎么选

发行版 发布 支持到 一级平台 建议
Jazzy Jalisco 2024-05 2029-05（LTS） Ubuntu 24.04 量产端侧首选：与 JetPack 7.x（Ubuntu 24.04）对齐
Kilted Kaiju 2025-05 2026-11（非 LTS） Ubuntu 24.04 不建议新项目采用，已临近停止支持
Lyrical Luth 2026-05 2031-05（LTS） Ubuntu 26.04 新平台、x86 工作站、云端仿真；Ubuntu 24.04 上仅三级支持

决策规则：端侧跟着主控的操作系统走，云端和仿真可以先行一步。Thor 机队在 JetPack 升级到 Ubuntu 26.04 之前，用 Jazzy 最稳妥；仿真集群和开发工作站可以提前试用 Lyrical，为两年后的迁移积累经验。这和车联网“车端跟域控 SDK 走、云端可以先上新版本”是同一种判断。

4.2.2 五种原语的选型

原语 语义 典型用途 车联网对应
话题 Topic 发布-订阅，流式 传感器数据、状态 MQTT 主题
服务 Service 请求-响应，同步短操作 查询、切换模式 同步 RPC
动作 Action 长任务：目标、进度、结果、可取消 导航、抓取、巡检 远程任务 / OTA 任务
参数 Parameter 节点的可变配置 频率、阈值、开关 配置中心客户端
生命周期 Lifecycle 节点状态机 受管启动、就绪判定 服务 readiness

选型两问：数据是持续流吗？→ 话题。操作会超过约一秒、需要进度或取消吗？→ 动作；否则服务。

4.4 DDS 与发现：为什么机器人内部不用 MQTT

4.4.1 去中心化发现

DDS 没有 broker。节点启动时通过组播向同一网段“自报家门”（参与者发现），再交换各自的发布/订阅端点（端点发现），双方类型与 QoS 匹配后直接点对点通信。没有中心，就没有单点故障——这正是机内实时通信需要的特性。

4.4.2 五个理由

理由 解释
无 broker 单点 机内任何一个进程崩溃都不影响其他节点通信
低时延 点对点直连，同机可走共享内存，微秒级
强类型 消息结构在编译期确定，类型不匹配直接不连
细粒度 QoS 每个话题独立配置可靠性、持久性、时效
生态标准 ROS 2 全生态默认，驱动、算法包即插即用

所以正确的架构是 “机内 DDS，端云 MQTT”：云桥节点就是机器人的 TBox，把机内关心的话题聚合、降采样后翻译成 MQTT 上云（第 5 章实现、p06 工程落地）。

4.4.3 Domain ID 与隔离

同一网段的 DDS 节点通过 ROS_DOMAIN_ID（0–101 常用）隔离。两台机器人如果用同一个 Domain ID 又在同一个 Wi-Fi 下，会互相“看到”对方的话题——这是新手最常见的现场事故之一。规则：每台机器人一个 Domain ID，或者更好地，机内通信限定在本机（ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST）。

4.4.4 Zenoh：2026 年的新选项

rmw_zenoh 自 Kilted 起成为一级支持的中间件：它用路由器（zenohd）替代组播发现，天然适合跨网段、弱网与容器环境。平台视角的取舍：DDS 的零配置在单机内最好用；跨机、跨网段、需要穿越 NAT 时，Zenoh 更省心。一些团队已经开始用 Zenoh 直接做“机器人到边缘”的通信，但本书仍建议端云之间用 MQTT，原因是云端生态（EMQX、规则引擎、鉴权、计费）成熟得多。

4.5 QoS：只需掌握五个策略

4.5.1 五个关键策略

策略 选项 含义 车联网类比
Reliability RELIABLE / BEST_EFFORT 是否重传保证送达 MQTT QoS 1 / QoS 0
Durability VOLATILE / TRANSIENT_LOCAL 晚加入的订阅者能否拿到历史 保留消息 retained
History + Depth KEEP_LAST(N) / KEEP_ALL 缓存多少条 客户端队列
Deadline 时长 超过该周期没收到新数据就触发事件 心跳超时告警
Liveliness 自动 / 手动 + 租约 发布者是否还活着 遗嘱消息

4.5.2 兼容规则：订阅要求不能高于发布承诺

QoS 不匹配时 DDS 不报错、不连接，订阅者静默收不到数据——这是 ROS 2 头号排障问题。规则一句话：订阅方要求的不能高于发布方承诺的。发布方 BEST_EFFORT、订阅方 RELIABLE → 不连；发布方 VOLATILE、订阅方 TRANSIENT_LOCAL → 不连。反过来则可以。

4.5.3 四类通道配方

通道 Reliability Durability Depth 附加
高频传感器（图像、点云） BEST_EFFORT VOLATILE 1–5 同机走共享内存
控制指令 RELIABLE VOLATILE 1 Deadline + Liveliness 监控
状态与遥测 RELIABLE VOLATILE 10 云桥订阅后降采样
静态信息（标定、地图元数据） RELIABLE TRANSIENT_LOCAL 1 晚启动节点也能拿到

平台纪律：把这四类配方做成团队的“QoS 白名单”，代码评审只允许用白名单里的配置。这和你在车联网制定“MQTT 主题与 QoS 规范”是同一件事。

4.6 服务：同步短操作

4.6.1 最小服务

调用：ros2 service call /set_manual_mode std_srvs/srv/SetBool "{data: true}"。

4.6.2 一秒线原则

服务的回调会阻塞调用方。超过约一秒的操作（移动、抓取、下载）一律用动作。常见错误是用服务实现“去 A 点”——调用方卡住、无法取消、无法看到进度。

4.7 动作：它就是你熟悉的远程任务

4.7.1 三通道语义

动作由三部分组成：目标（请求执行，可被接受或拒绝）、反馈（执行中的进度流）、结果（最终成功或失败），外加随时可发的取消请求。

4.7.2 与车联网远程任务逐项对照

动作 车联网远程任务 / OTA 任务
send_goal 下发任务
goal_callback 接受/拒绝 任务准入校验（条件不满足即拒绝）
goal_id 任务 ID（幂等键）
feedback 进度回执（下载 30% → 校验 → 安装）
result 最终回执
cancel 撤销任务
状态机 ACCEPTED→EXECUTING→SUCCEEDED/ABORTED/CANCELED 任务状态机

你在 XOTA 里手工实现的那套任务协议，ROS 2 已经做成了标准原语。

4.9 生命周期节点：给节点加上就绪语义

4.9.1 四个主状态

stateDiagram-v2
  [*] --> Unconfigured
  Unconfigured --> Inactive: configure（加载配置、分配资源）
  Inactive --> Active: activate（开始发布与处理）
  Active --> Inactive: deactivate（暂停，不释放资源）
  Inactive --> Unconfigured: cleanup（释放资源）
  Unconfigured --> Finalized: shutdown
  Inactive --> Finalized: shutdown
  Active --> Finalized: shutdown

4.9.2 为什么平台关心它

受管节点在 Active 之前不对外发布数据，这给了机器人一个明确的“就绪”定义——正如 K8s 的 readiness 探针。平台可以：启动时按依赖顺序激活节点；OTA 切换模型时先让推理节点 deactivate、换模型、再 activate；在“维护模式”下统一让业务节点 deactivate。被云端编排的节点，都应当实现生命周期。

4.10 执行器与回调：最常见的死锁

4.10.1 执行器是事件循环

rclpy.spin(node) 启动一个执行器，它在一个（或多个）线程里轮询所有定时器、订阅、服务回调。单线程执行器里，任何一个回调阻塞，整个节点都停——订阅积压、定时器不走、服务不响应。

4.10.2 经典死锁与三种解法

在单线程执行器的回调里同步调用另一个服务并等待结果，会永远等下去：结果要由同一个执行器处理，而执行器正卡在等待里。

解法 做法 适用
异步调用 future = client.call_async(req)，用回调处理结果 首选
多线程执行器 + 回调组 MultiThreadedExecutor + ReentrantCallbackGroup 确需并发时
拆节点 把阻塞工作挪到独立节点或线程，结果经话题回传 重计算、IO

这条经验与你在 Netty 事件循环里“绝不在 EventLoop 线程做阻塞 IO”完全相同。

⚠️ 一线踩坑

  • QoS 静默不连：相机驱动发布 BEST_EFFORT，自研节点订阅默认 RELIABLE，现象是“话题存在但收不到”。对策：QoS 白名单 + CI 中检查端点兼容性。
  • Domain ID 串台：两台同型机器人在同一 Wi-Fi 下互相收到对方的速度指令。对策：机内通信限定本机，或按设备分配 Domain ID，并写入出厂配置。
  • 服务当动作用：用服务实现“移动到工位”，调用方卡住且无法取消。对策：一秒线原则写进代码规范。
  • 回调里同步等待：单线程执行器死锁，节点“看起来活着但什么都不干”——正是第 8 章“假死”的端侧根源之一。
