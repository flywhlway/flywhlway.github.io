第 6 章 端侧 AI：Jetson Thor 时代的推理部署与资源纪律

VLA 与感知模型最终跑在机器人的主控上。

Flywhl 12 分钟 发布于 2026.09 #端侧AI#Jetson#推理部署

先读结论

  1. 端侧优化确定性：看 P99、抖动、功耗、温度，不看 QPS。
  2. 统一内存一口锅：预算按总量算，备槽单列。
  3. 引擎矩阵：GPU 架构 × TensorRT 版本 × 精度。
  4. 模型制品五件套：权重/引擎、预处理契约、归一化统计量、模型卡、签名。
  5. 时延不等式：推理 P99 + 抖动 < chunk 时长。

本章定位：VLA 与感知模型最终跑在机器人的主控上。本章讲清平台架构师必须掌握的端侧约束——算力分档、统一内存、推理引擎的“不可移植”、量化、实时隔离、热稳态——以及它们如何反过来决定云端 OTA 与模型工厂的设计。
对应代码：p02（模型制品与双槽切换）、p01（端侧指标上云）｜建议学时：5 小时

6.1 认知反转：云端优化吞吐，端侧优化确定性

6.1.1 你的 AI Infra 经验哪些成立

云端经验 端侧是否成立 差异
量化降本 ✅ 更刚需 目标从“省钱”变成“装得下、跑得稳”
连续批处理 ❌ 基本失效 端侧只有一个消费者，batch≈1
KV Cache 复用 ⚠️ 部分成立 同一任务内指令前缀可跨帧复用
推理服务化 ⚠️ 变形 端侧是进程内调用，不是 HTTP 服务
显存规划 ⚠️ 重学 统一内存：CPU 与 GPU 共用一块内存
性能指标 ❌ 反转 看 P99 时延、抖动、功耗、温度，不看 QPS

一句话：端侧宁可留余量，也不要一次抖动。云端一次慢请求只是体验问题，机器人一次动作断流就是可见的卡顿，严重时是安全问题。

6.2 Thor 家族与选型

6.2.1 2026 年的主控分档

模块 FP4 算力（稀疏） 内存 功耗 适用
AGX Thor / T5000 2070 TFLOPS 128GB 40–130W 人形、多相机、大 VLA + 大 VLM 同机
T4000 1200 TFLOPS 64GB 约 70W 级 功耗与散热受限的人形/复合机器人
T3000 / T2000 更低 更小 更低 2027Q1 供货，面向大众化机型
AGX Orin（存量） 上一代 32/64GB 15–60W 在役机队主力，长期并存

6.2.2 选型四看

  1. 内存容量：模型 + 双槽切换 + 感知 + 系统 + 缓冲，最先见底的永远是内存；
  2. 内存带宽：大模型推理往往受带宽而非算力限制（Thor 约 273GB/s 量级）；
  3. 功耗与散热：直接决定续航与是否会热降频；
  4. 软件栈：JetPack 版本、TensorRT 版本、是否支持目标精度（FP4/FP8）。

6.2.3 峰值不是承诺

厂商标称的 TFLOPS 是稀疏、最低精度、理想利用率下的峰值。真实模型的有效算力常常只有标称的一小部分，还要扣除数据搬运、预处理、热降频。唯一可信的数字来自你自己的机型、自己的模型、热稳态下的实测——和你在云上“只信自己压测”的纪律一样。

6.3 统一内存：最先见底的资源

6.3.1 一口锅的含义

Jetson 的 CPU 与 GPU 共享同一块物理内存。好处是省去主机与显存之间的拷贝；坏处是模型权重、图像缓冲、ROS 节点、日志缓存、操作系统全在一口锅里抢。一旦内存耗尽，Linux 的 OOM Killer 不知道“控制进程比日志进程重要”。

6.3.2 内存预算表（T5000 128GB 示例）

项 预算 说明
操作系统 + JetPack 4GB
ROS 2 栈与业务节点 3GB 含云桥、录制器
感知模型（检测/分割/深度） 6GB INT8/FP8
VLA 主槽 16GB 如 3B 级 VLA（GR00T N1.7 官方建议推理≥16GB 显存）
VLA 备槽（热切换期间） 16GB 新旧模型同时驻留，双槽切换的隐性成本
慢脑小模型（可选，本地 VLM/LLM 兜底） 20GB 断网时的本地规划
图像/点云/录制环形缓冲 8GB
余量（防 OOM） ≥12GB 约 10%
合计 ≤128GB

“备槽”那一行是端侧选型最容易漏掉的：第 9 章的模型热切换要求新旧两份权重短暂同时驻留。T4000（64GB）上同样的配置就需要取舍——去掉本地慢脑或缩小 VLA。

6.4 推理运行时

6.4.1 2026 年的端侧运行时

运行时 定位 平台关注点
TensorRT NVIDIA 官方推理引擎，端侧首选 引擎按机型构建，见 6.5
TensorRT-LLM / TensorRT Edge-LLM 面向 Transformer/大模型；Edge-LLM 随 JetPack 7.1 提供 VLA 骨干、端侧 VLM
ONNX Runtime 跨平台，带 TensorRT 执行提供者 原型与跨硬件
原生 PyTorch 研发调试 不建议直接上生产（时延与内存不可控）
llama.cpp 类 小模型、CPU 兜底 语音、日志摘要等弹性负载

6.4.2 进程内调用，而不是服务

云端习惯把模型包装成 HTTP 服务。端侧应当是进程内库调用：少一次序列化、少一跳网络、少一个故障点。只有在同一台机器上多个节点共享一个模型时，才考虑本地服务化，并且要评估它对时延抖动的影响。

6.5 部署链与“引擎不可移植”

6.5.1 从训练产物到端侧引擎

flowchart LR
  PT["PyTorch 权重<br/>（模型工厂产出）"] --> ONNX["导出 ONNX<br/>固定输入契约"]
  ONNX --> BUILD["TensorRT 构建<br/>精度·校准·算子融合·内核调优"]
  BUILD --> ENG["引擎文件<br/>绑定 GPU 架构 × TRT 版本 × 精度"]
  ENG --> SIGN["签名 + 模型卡<br/>进入制品库"]
  SIGN --> OTA["OTA 分发到匹配机型"]

6.5.2 为什么引擎不能跨机型复制

TensorRT 在构建时会针对具体 GPU 架构与软件版本选择最优内核，产物因此绑定“GPU 架构 × TensorRT 版本 × 精度”。Orin 上构建的引擎拿到 Thor 上通常无法加载，同型号跨 JetPack 大版本也不保证兼容。这一条直接决定了云端设计：

策略 做法 优点 代价
A 端侧构建 分发 ONNX，机器人首次加载时本地构建 一份制品通吃 构建耗时长、占资源、结果有差异
B 按目标预构建 CI 为每个（机型 × JetPack × 精度）构建引擎矩阵 秒级加载、行为确定 制品矩阵膨胀，需要版本治理
C 混合 主力机型预构建，长尾机型端侧构建兜底 平衡 两条路径都要维护

推荐 B 为主、A 兜底。于是模型制品的兼容矩阵多了两维：GPU 架构与 JetPack 版本。这与你熟悉的“多车型 × 多域控 × 多固件版本”矩阵是同一种治理问题，第 9 章的 OTA 与 p02 工程都按此设计。

6.5.3 模型制品“五件套”

  1. 权重或引擎文件；2. 预处理契约（分辨率、归一化、通道顺序）；3. 动作归一化统计量（均值/方差，决定反归一化是否正确）；4. 模型卡（观测/动作/频率契约、训练数据版本、评测结果、许可）；5. 签名与校验和。五件套缺一不入制品库——这条规则能挡住大部分“换了模型机器人乱动”的事故。

6.6 量化：端侧的默认项

6.6.1 实用顺序

FP16 跑通基线 → FP8/INT8 达标就停 → 内存或时延仍不够再上 4 比特（Thor 的 Blackwell GPU 支持 FP4）→ 精度掉得太多才考虑量化感知训练。

6.6.2 动作模型的特殊性

分类模型有 softmax 的容错缓冲，而动作是连续量：量化误差会直接变成关节角误差。三条建议：骨干激进量化、动作头保守（保持 FP16）；量化后除了看成功率，还要看动作平滑度（加加速度统计）；用影子模式并跑“高精度版 vs 量化版”，以动作分歧分布作为门禁——这是最灵敏的退化检测器。

6.6.3 校准集是制品

INT8/FP8 校准需要代表性样本。校准集必须来自目标场景，必须版本化并进入数据血缘（第 12 章），场景变化（新站点、新光照）后要重新校准。

6.7 双频架构：让慢推理驱动快执行

6.7.1 动作分块

VLA 一次推理输出未来 H 步动作（一个 chunk），执行器以高频逐步执行，下一次推理在 chunk 耗尽前完成。于是 5–10Hz 的推理可以驱动 50Hz 以上的执行。这与智驾“规划输出一段轨迹、控制器高频跟踪”完全同构。

sequenceDiagram
  participant V as VLA 推理（约 5Hz）
  participant B as 动作缓冲
  participant X as 执行器（50Hz）
  V->>B: chunk N（10 步，覆盖 200ms）
  loop 每 20ms
    X->>B: 取下一步动作
  end
  Note over V: 在 chunk N 耗尽前启动推理 N+1
  V->>B: chunk N+1（P99 必须明显小于 200ms）
  Note over B: 缓冲水位是核心健康指标，见底即“卡一下”

6.7.2 时延不等式

推理时延 P99 + 抖动裕度 < chunk 执行时长。例如 chunk=10 步、执行 50Hz，chunk 时长 200ms，推理 P99 必须明显小于 200ms。不等式一旦被打破，动作缓冲见底，机器人就会“卡一下”。所以：

  • 端侧要把 chunk 缓冲水位作为核心健康指标上报；
  • 模型准入要用热稳态下的 P99 而不是冷机均值；
  • 任何可能拉高时延的变更（换模型、换精度、换 JetPack）都要重新验证这个不等式。

6.8 资源隔离：推理是客人，控制是主人

6.8.1 隔离四板斧

手段 做法 作用
CPU 核隔离 控制进程独占核（isolcpus / cgroup cpuset） 消除调度争抢
实时优先级 控制线程 SCHED_FIFO + mlockall 不被抢占、不被换页
cgroup 限额 推理、录制、OTA 进程限 CPU 份额与内存上限 防单进程吃垮系统
IO 限速 录制与下载限带宽、低 IO 优先级 防 IO 尖峰传导到控制

6.8.2 开机自检

隔离配置会漂移（有人手动改过、镜像更新丢了参数）。在机器人启动的就绪阶段做自检：核隔离参数、关键进程优先级、oom_score_adj、cgroup 限额是否生效——任一不符就不进入可作业状态，并上报事件。生命周期节点（第 4 章）的 configure 阶段正是放这个检查的地方。

6.9 热与功耗

6.9.1 热稳态压测

实验室十分钟压测一切正常，现场连续作业两小时后 GPU 降频，推理 P99 越过时延不等式——这是端侧最常见也最隐蔽的问题。规则：所有端侧性能基线都在两小时热浸泡后测量，机型规格书记录热稳态数据，而不是峰值数据。

6.9.2 功耗档位是架构决策

nvpmodel 切换功耗模式，jetson_clocks 锁定频率。锁频消除调频引起的抖动，代价是功耗与发热恒高。功耗档位属于机型基线配置（走配置 OTA），换档等于换了一台机器，所有时延基线都要重测。

6.9.3 六个必须上云的端侧指标

GPU 利用率、GPU 温度、降频比例、内存水位、功耗档位、推理时延 P99。采集方式是在端侧写一个指标节点解析 tegrastats 输出，并入遥测：

p01 的遥测载荷已经预留了 gpu_temp 字段，扩展其余指标只需要在端侧聚合节点里加字段、在云端时序表里加列。

6.10 端侧模型运行时的六件事

6.10.1 清单

  1. 槽位管理：A/B 双槽、原子切换、版本上报；
  2. 契约校验：加载时校验观测话题、图像尺寸、关节顺序、归一化统计量与本机 Device Profile 是否匹配，不匹配拒载；
  3. 观测同步缓冲：多路传感器按时间戳对齐，超阈丢帧并计数；
  4. chunk 缓冲与水位：水位见底前触发推理，水位作为健康指标；
  5. 失效降级：推理超时或异常时立即降级（停住、收臂、交还传统控制栈）；
  6. 指标上报：时延 P50/P99、水位、置信度分布、与影子模型的分歧计数。

这份清单就是你给算法团队的“模型上机验收标准”，也是 p02 端侧 Agent 模拟的内容。

6.10.2 云端大脑与端侧小脑的协同

慢脑（任务理解、长程规划）可以调用云端具身推理模型——2026 年已有 Gemini Robotics ER 2 这类通过公开 API 提供的能力；中脑（VLA）在端侧运行。协同时的两条纪律：云端只返回“目标与子任务”，不返回动作；断网时端侧必须有本地兜底（本地小模型或预定义任务脚本），否则网络抖动就会让机器人停工。第 15 章的 Agent 平台会把这两条写进架构。

6.11 案例推演：新模型上线一小时后动作开始卡顿

6.11.1 现象

某站点灰度第一环上线新版 VLA，前一个小时指标正常，之后人工介入率上升，现场反馈“机器人动作一顿一顿的”。

6.11.2 分析

假设 证据 结论
新模型推理更慢 冷机压测 P99 180ms，chunk 时长 200ms，余量很小 余量不足是前提
热降频 上线约 50 分钟后降频比例从 0 升到 30%，P99 升到 240ms 直接原因
内存压力 切换后备槽未及时释放，内存水位 92% 加剧抖动

6.11.3 平台动作

短期：自动回滚到旧模型（门禁指标“介入率”破线触发，见第 9 章）。中期：模型准入改为热稳态 P99；OTA Agent 在观察期结束后强制释放备槽。长期：机型规格书记录“热稳态下可承载的模型规模上限”，模型工厂在选择规模时以它为约束——用硬件规格反向约束模型选型，比事后优化便宜得多。

⚠️ 一线踩坑

  • 漏算备槽内存：热切换时 OOM，被杀的恰好是录制进程，事故现场数据全无。对策：预算表单列备槽，OOM 分数保护关键进程。
  • 在开发机上构建引擎直接下发：换机型即加载失败。对策：CI 按（机型 × JetPack × 精度）构建矩阵，文件名与模型卡记录三元组，加载时校验。
  • 冷机压测定标准：现场热稳态后时延越线。对策：一切基线在两小时热浸泡后测量。
  • 动作头一起量化：机器人轻微抖动、减速器磨损加快。对策：混合精度，动作头保守，门禁加动作平滑度。

  2. 为 6.5.2 的策略 B 设计引擎矩阵的命名规范与模型卡字段，并对照 p02 的制品清单（第 18 章）检查是否兼容。
  3. 为 p01 的遥测载荷设计“六个端侧指标”的字段与上报频率，说明哪几个需要趋势告警而不是阈值告警。

🎯 面试与评审要点

  1. 端侧推理与云端推理的最大差异？（确定性 vs 吞吐、batch=1、统一内存、热稳态）
  2. 为什么 TensorRT 引擎不能跨机型分发？OTA 怎么设计？（内核调优绑定架构与版本 → 引擎矩阵）
  3. 模型热切换对硬件有什么隐性要求？（双槽同时驻留的内存）
  4. 如何判断一个 VLA 能不能在某机型上用？（热稳态 P99 + 抖动 < chunk 时长）

📝 本章卡片

  • 端侧优化确定性：看 P99、抖动、功耗、温度，不看 QPS。
  • 统一内存一口锅：预算按总量算，备槽单列。
  • 引擎矩阵：GPU 架构 × TensorRT 版本 × 精度。
  • 模型制品五件套：权重/引擎、预处理契约、归一化统计量、模型卡、签名。
  • 时延不等式：推理 P99 + 抖动 < chunk 时长。
  • 推理是客人控制是主人：隔离四板斧 + 开机自检。
  • 热稳态基线：两小时浸泡后的数字才算数。
