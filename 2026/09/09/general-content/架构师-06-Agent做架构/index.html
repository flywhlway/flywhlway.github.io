当 Agent 也能做架构

「AI 时代架构师」系列收官篇：拆开 Agent 参与架构工作的五条工作流——ADR 起草、评审清单核对、依赖与调用链逆向、容量估算、变更影响分析…

Flywhl 16 分钟 发布于 2026.09 #架构思维#方法论#AI Agent

先读结论

  1. Agent 能做的是架构工作，不是架构：收集、比对、起草、计算可以交出去，签名那一格留给人。
  2. 每条工作流先设计判卷标准：能用规则判的写成检查器，数字由脚本算，事实带来源与日期。
  3. 按可验证性从高到低接入：先依赖逆向与容量估算，再评审核对与影响分析，最后 ADR 起草。
  4. Agent 的产出只能进入 proposed 状态，状态转移与风险豁免由人执行并署名。

架构师的终局：当 Agent 也能做架构

《复杂性的驯兽师》系列 · 第六篇（收官）

前五篇讲的是怎么驯服 AI 系统的复杂性。收官篇把镜头转过来，对准架构工作本身：当 Agent 开始起草 ADR、核对评审清单、逆向依赖、估算容量、分析变更影响，哪些活可以交出去、怎么交、交出去之后人还剩什么。

引子：一个让我脊背发凉，又如释重负的夜晚

不久前的一个深夜，我做了一个”元”一点的实验：让一个足够强的模型，为一个我熟悉的系统设计架构方案。我给了它需求、约束和非功能性指标。

它给出的方案条理清晰、术语准确、分层合理，还主动提到了缓存策略和降级考虑——如果这是一份新人的作业，我会打高分。那一刻，”AI 会取代架构师吗”这个被问烂的问题，第一次以切身的方式砸了过来。

但当我拿这份方案和真实场景较真时，如释重负的感觉又回来了。我问它：哪一个决策的前提最可能在半年后失效？它答不上来——它没有在真实的时间里，见过一个前提怎样从成立走向崩塌。我又问：如果预算只有一半，你砍哪一块、向谁解释？它给出的是平均主义的缩减，而不是带着立场和代价的取舍。我再问：上线三个月后出了一次没人预料到的事故，你怎么复盘、怎么承担？这个问题它根本无从回答。

那个夜晚我想清楚了一件事：AI 拿走的是”生成一个方案”，而架构师的价值从来不在生成方案，而在为方案负责。 但这句话如果停在这里，只是一句安慰。更有用的问题是：在”生成”和”负责”之间，还有大量具体的架构工作——查资料、翻代码、比对清单、算容量、排查影响——它们既不是纯生成，也不是纯判断。这一篇把这些工作一条条拆开：交给 Agent 时给它什么输入、要它什么输出、人在哪一步把关、它最可能怎么失败。最后再回到那四样生成不出来的东西。

一、先校准问题：Agent 做的是”架构工作”，不是”架构”

过去一年，Agent 参与工程工作的方式发生了质变。2026 年 2 月，Claude Code 以研究预览形式推出 Agent Teams：一个主导会话拆分任务，多个队友会话各自持有独立上下文并行推进、彼此交流发现。5 月底推出的 dynamic workflows 更进一步：由模型现场写出编排脚本，在一次会话里调度数十到上百个并行子 Agent，结果先经检查再汇总。据 Anthropic 官方博客介绍，Bun 借助它把运行时从 Zig 移植到 Rust，约 75 万行 Rust 代码，11 天完成，既有测试套件通过率 99.8%。与此同时，承载仓库约定的 AGENTS.md 和连接工具的 MCP 在 2025 年 12 月一起捐入 Linux 基金会旗下的 AAIF，Agent 读取项目规范、接入内部系统的方式正在标准化。

这个案例里最值得架构师注意的数字不是 75 万行，而是 99.8%。那套既有测试套件是整个工程的判卷标准——Agent 能把活干到什么程度，取决于你能给它什么样的判卷标准。代码移植有现成的测试可跑，架构工作却大多没有：一份 ADR 写得好不好、一次评审漏没漏项、一个容量估算靠不靠谱，都没有现成的断言。所以让 Agent 参与架构工作，第一件事不是挑工具，而是为每一类工作构造判卷标准——这是篇三的证据工程在架构师自己身上的应用。

在此基础上区分两个词：架构工作是产出物——资料、草稿、图、表、清单、计算；架构是决策——在这些产出物之上选择、取舍、署名、为后果负责。Agent 能承担的前者越来越多，后者的边界不随模型能力移动。下面五条工作流共用同一个骨架：

flowchart LR
    IN["输入<br/>可引用的事实源"] --> AG["Agent 产出<br/>草稿 + 证据定位"]
    AG --> DC{"确定性校验<br/>格式 · 来源 · 计算"}
    DC -->|不通过| AG
    DC -->|通过| HR["人审点<br/>只审判断"]
    HR -->|退回| AG
    HR -->|署名| REC["入库<br/>ADR 库 · 评审记录"]

骨架里有两条纪律。其一，能用确定性手段校验的，既不留给人，也不留给模型：字段是否完整、来源链接是否可达、数字是否由脚本算出，都要在人审之前自动拦下。其二，人审只审判断：如果审阅者的时间花在纠正格式和查证事实上，这条工作流就设计失败了。

二、五条工作流：输入、输出、人审点、失败模式

2.1 ADR 起草

要素 内容
输入 一段由人写的问题陈述与约束；仓库里的历史 ADR；候选方案的一手资料（官方文档、定价页、许可证、基准数据）；带”失效条件”字段的 ADR 模板
输出 ADR 草稿：背景、至少两个真实备选、逐项代价核算、推荐意见、失效条件候选、与既有 ADR 的冲突清单；每条事实附来源与抓取日期
人审点 备选是否完整（包括”什么都不做”）；各项代价的权重；失效条件的阈值；署名
失败模式 稻草人备选；事实过期或编造；结论先行；失效条件写成空话

四种失败模式各有一个确定性的对策。稻草人备选：两个明显不行的选项衬托一个推荐——要求每个被否决的选项写出”在什么条件下它会胜出”，写不出来的不算备选。事实过期或编造：价格、版本号、许可证条款最容易出错——每条事实必须带来源链接与抓取日期，由 CI 校验链接可达。结论先行：提问方式暗示了答案，Agent 顺着写——要求先写”反方最强论证”，再写推荐。失效条件空话化：”当业务发生重大变化时”不是失效条件——模板强制写成”信号 + 阈值 + 观测来源”。

CI 里三条规则就够用：status 为 accepted 时 decision_owner 不得为空；invalidation 的每一项必须同时有 threshold 与 source；evidence 的每一项必须有 url 与 retrieved。

2.2 架构评审清单自动核对

要素 内容
输入 版本化的评审清单（由篇二至篇五的速查表改写为可判定条目）；设计文档；代码仓库与 IaC；一个时间窗口内的追踪样本
输出 逐条核对表：符合、不符合或无法判断，每条附证据位置（文件与行号、配置路径或 trace ID）
人审点 全部”不符合”与”无法判断”；按比例抽检”符合”；是否接受风险、给出豁免
失败模式 讨好式的”全部符合”；只看文档不看实现；清单本身腐化

清单条目分两类，处理方式完全不同。可确定性判定的——依赖方向是否违规、业务代码是否直接引用厂商 SDK、模型调用是否全部经过网关、第三方 Action 是否按提交 SHA 引用、Agent 循环是否配置了轮次上限——不该每次都让 Agent 读一遍去”判断”，而应让 Agent 把它们写成检查器：架构适应度函数、静态分析规则、CI 断言。写一次，之后每次提交都零成本、零随机性地执行。篇三”能用规则判的绝不用模型判”在这里的推论是：让 Agent 写检查器，而不是当检查器。

需要理解才能判定的——LLM 输出是否可能绕过确定性层直达副作用、降级剧本是否覆盖”模型全部不可用”、工具返回是否被当作可信输入——才交给 Agent 逐条核对，并加三条约束：每条”符合”必须附证据位置，没有证据的自动降为”无法判断”，以此压住讨好倾向；至少一条证据来自代码或运行时，不能只引用设计文档，因为文档写着”走网关”和代码真的走网关是两回事；”无法判断”是合法且受欢迎的输出。

这条工作流本身也要按篇三的方法评估：把过去一年评审中人工发现的问题整理成回放集，用当时版本的设计与代码让 Agent 重新核对，看它能找回几条；它判为”符合”的条目，用篇三校准裁判的方法计算与人工结论的 κ。清单每次在事故复盘后更新，版本号写进核对报告。

2.3 依赖与调用链逆向

要素 内容
输入 多个代码仓库；构建清单与 lockfile；SBOM；部署清单与 IaC；网关路由与服务发现配置；追踪数据中的服务拓扑
输出 依赖图与调用图（结构化数据加可视化），每条边标注来源：静态（代码引用）、配置（路由与发现）、运行时（追踪中观测到）；三方差异清单
人审点 差异清单的解释；模块与领域的归属划分
失败模式 幻觉边；仓库超出上下文；漏掉动态调用

逆向是最适合并行 Agent 的架构工作：每个服务分给一个子 Agent，彼此独立，最后合并。关键在于合并与校验不交给模型——每条边必须有可复查的出处（文件与行号、配置项或 trace ID），没有出处的边不进图；合并、去重、差异计算由确定性脚本完成。这样即使某个子 Agent 依据命名”推断”出一条不存在的调用，它也会因为没有出处被挡在图外。

三方差异清单是这条工作流真正的价值。”代码里有、运行时从未出现”的边，要么是死代码，要么是低频路径（月结、灾备切换），前者可以清理，后者必须标注；”运行时有、代码里找不到”的边，通常来自反射、消息队列、配置驱动或外部系统回调，恰恰是变更时最容易被遗忘的依赖。运行时视角有一个前提：追踪的时间窗口要覆盖低频业务周期，只采一周数据会系统性地漏掉月度任务。

2.4 容量估算

要素 内容
输入 业务预测（峰值、增长率，由人给出）；线上指标（到达率、时长分布、gen_ai.usage.* 记录的 token 用量）；压测结果；价格表
输出 可执行的计算脚本与结果表：公式、参数、每个参数的来源标注（实测、合同或假设）、敏感性分析
人审点 业务预测与增长假设；安全余量取多少；超出预算时砍什么
失败模式 心算出错；单位混乱；把平均当峰值；参数无来源

这条工作流的铁律只有一条：数字由脚本算，不由模型算。 Agent 负责写脚本、找数据、标注来源，所有数字都来自运行结果：

算出的并发要对照供应商的速率限额与自建集群的实测吞吐；token 吞吐再接上篇四的成本公式与平衡点算例，就是一份完整的容量与成本方案。单位混乱是这类估算最常见的错误——每秒与每分钟、token 与字符、卡时与节点时——所以脚本里每个变量的注释都写明单位。平均与峰值的混淆由模板强制避免：峰值到达率与平均时长必须分别给出来源。

2.5 变更影响分析

要素 内容
输入 变更内容：代码差异，以及提示词、模型版本、检索索引与配置的变化；2.3 产出的依赖与调用图；服务目录与代码负责人；评估用例与能力的覆盖映射；SLO
输出 影响清单（模块、下游服务、对外接口、数据契约、评估子集、租户），每项附影响路径与等级；验证计划（跑哪些评估子集、灰度比例、回滚点）；需要通知的负责人
人审点 发布策略；可接受的风险；跨团队沟通
失败模式 只看代码差异；影响面过度放大；依赖图过期

只看代码差异是最危险的失败：篇三列出的三类静默回退——模型、提示词、知识库变更——都不体现在代码差异里。影响分析的输入必须包含这三类版本号的变化，否则 Agent 会对最危险的那类变更报告”无代码改动，无影响”。影响面过度放大是另一个极端：为了不漏，把所有沾边的模块都列为”可能受影响”，审阅者很快会对报告视而不见。约束方式是每项影响必须给出从变更点到受影响点的具体路径，并按”直接调用、数据契约、间接依赖”分级。依赖图过期则要求 2.3 的逆向定期重建，影响报告注明所用依赖图的生成时间。

2.6 五条工作流对照

工作流 判卷标准从哪里来 确定性校验拦什么 人签什么 并行化收益
ADR 起草 结局已知的历史决策回放 字段完整、来源可达 取舍与署名 低

三、给做架构工作的 Agent 划边界

前五篇为 AI 系统立下的规矩，对”做架构工作的 Agent”同样适用，一条都不能少：

  • 结构化：Agent 的产出只能进入 proposed 状态；从 proposed 到 accepted 的状态转移、风险豁免的批准，只能由人执行。这是篇二”LLM 可以建议，但不能直接执行副作用”在架构治理上的版本。
  • 证据：每条工作流有自己的评估集，用历史 ADR、历史评审发现、历史发布事故做回放；换模型、改提示词之前先回归。
  • 成本：动辄调度数十个子 Agent 的工作流，一次运行的 token 消耗远超日常对话。给每条工作流设预算，只对并行化收益高的工作（依赖逆向）放开并发。
  • 安全：做逆向和评审的 Agent 要读代码、配置和追踪数据，这些地方常常散落着密钥与个人数据。只发只读凭据、限制网络出口、追踪数据先脱敏——篇五的身份治理原则在这里一条不减。
  • 上下文：把架构约定（分层规则、禁止的依赖、必须经过的网关、ADR 模板）写进仓库的 AGENTS.md，让每一个进入仓库的 Agent 都先读到它。约定写在文件里而不是某个人的脑子里，才能被 Agent 和新人以同样的方式遵守——这是篇一”抽象同时服务人与模型”的直接应用。

接入顺序同样有讲究：按可验证性从高到低接入。依赖逆向和容量估算有运行时数据和脚本可以对账，最先接；评审核对和影响分析有历史回放可以评估，其次；ADR 起草的质量要等决策在时间里被验证，放在最后，而且接入之后也只负责起草。

四、护城河：签名那一格

回到引子里那三个追问。把五条工作流的人审点逐一归类，会发现它们恰好落在四个地方——也就是篇一结尾说的，那些无法被生成的东西。

4.1 责任：谁在 decision_owner 那一栏签字

五条工作流里，Agent 可以填写几乎所有字段，唯独 ADR 的署名人、评审的风险豁免、发布的放行不能由它来填。这不是权限配置上的保守，而是责任的本质：事故发生在凌晨三点，需要有人被叫醒、做决定、向用户交代，并在复盘会上为当初的取舍辩护。一个无法承担后果的主体，就不能被授予制造后果的权力。Agent 让起草变得廉价，也让”谁签的字”成为一份架构文档里最贵的那一行。

4.2 判断：权重、假设与可接受的风险

Agent 能把选项列全、把代价算清、把影响路径找齐，但有三件事给不了：各项代价的权重（哪种代价组织承受不起）、增长与峰均比的假设（明年业务会不会翻倍）、可接受风险的边界（这条”不符合”能不能豁免上线）。三者的共同点是，答案不在数据里，而在对组织意图的理解和愿意为之下注的立场里。引子里那个面对”预算砍半”给出平均主义缩减的方案，缺的正是这种立场。

4.3 时间：失效条件需要有人记得”为什么”

结构化的失效条件可以交给监控去盯，Agent 甚至可以在信号触线时自动起草一份”是否需要重新评估”的提案。但”前提已变、该改了”这个决定，需要知道这个决策当年为什么这样做、放弃了什么、那些放弃的理由今天是否还成立。一次 Agent 会话没有跨越三年的连续记忆；ADR 能记下文字，却记不下会议室里那些没写进文档的顾虑。架构师是系统在时间里的守护者，这种连续在场无法被一次生成替代。

4.4 信任：组织把权力授予有履历的人

组织愿意把技术方向托付给一个人，依据的是他可查证的判断履历：签过的 ADR、失效条件预判准了几次、评审里豁免的风险后来有没有出事。Agent 的产出本身不积累这种信任，它经由签字的人才获得效力。反过来，Agent 的普及让这份履历更容易被检验——当每份决策都有结构化的字段、来源和结局，”谁的判断经得起时间”就成了一个可以查询的问题。Agent 越能干，架构师的可信度越要靠记录说话，而不是靠头衔。

这四样——责任、判断、时间、信任——在五条工作流里有一个共同的位置：人审点。Agent 拿走的是收集、比对、起草、计算，留给人的是签名那一格。篇一提出的三个复利杠杆（决策、质量、知识的资产化）在 AI 时代更值钱，也正因为它们沉淀的正是这一格里的东西。

五、收官行动路线：一年接入五条工作流

最后，把全系列的方法和五条工作流合成一份年度路线。每个季度补齐系列里的一块方法，同时接入一条或两条 Agent 工作流，接入顺序按可验证性从高到低：

季度 补齐的方法 接入的 Agent 工作流 验收标志
第一季 篇一自评，篇二边界图与红线清单 依赖与调用链逆向 三方差异清单逐条有解释；边界图基于逆向结果而不是记忆
第二季 篇三评估集与语义层可观测 评审清单核对，先把可判定条目写成检查器 历史评审回放集上的召回率有数；检查器进入 CI
第三季 篇四成本看板，篇五威胁建模与身份治理 容量估算、变更影响分析 容量方案全部由脚本产出；影响报告的输入包含提示词、模型与索引版本
第四季 用”第三次重复”判据评估哪些能力值得平台化，对外写作 ADR 起草，结构化模板加 CI 校验 新 ADR 字段完整、来源可达、由人署名；一篇公开发布的年度实践总结

这份路线不必严格按季度执行，但顺序有它的道理：先让 Agent 做有客观答案的活，积累出对它的校准数据，再逐步交出更依赖判断的活。这和组织信任一个新同事的过程一模一样。

结语：技术会过时，而驯兽师不会

篇一的开头写下过一个判断：技术会过时，框架会更替，模型会迭代，但驾驭复杂性的思维方式不会贬值。六篇走下来，边界、契约、证据、账本、防线都会随技术演进而变化，甚至”Agent 能做哪些架构工作”这张清单，一年后也会变长。但清单再长，签名那一格不会被填上。

AI 时代最大的误解，是以为 Agent 会让架构师贬值。恰恰相反：当起草、比对、计算都变得廉价，”为什么这样做、放弃了什么、出了问题谁负责”的价值才空前凸显。Agent 把架构师从资料和表格里解放出来，逼着我们把时间花在只有人能做的事上——判断、负责、守护、赢得信任。

回到最开始的问题：当 AI 开始写代码，甚至开始做架构工作，架构师还剩下什么？剩下的，是那个站在所有工具、所有模型、所有生成之上，做出判断、承担后果、守护决策、赢得信任的人。

技术的浪潮一波接一波，冲走的是工具，留下的是人。愿你我，都是那个从容的驯兽师。
