导读：先给结论

读完本文，你应该能回答以下五个问题。先把答案放在最前面：

  1. 缓存的到底是什么？ 不是”答案”，而是模型对输入前缀完成计算后留下的中间状态——每一层注意力的 Key/Value 张量（KV Cache）。命中缓存，等于跳过这段前缀的 Prefill 计算，直接加载现成的 KV。
  2. “输出缓存”存在吗？ 计费意义上，主流平台只对”输入前缀”提供缓存折扣，输出 token 永远按输出价计费。但本轮输出会原样进入下一轮的输入历史，从下一轮起作为前缀被反复命中——这正是多轮 Agent 命中率高的原因之一。
  3. 为什么命中价只有未命中价的 1/10，甚至 1/120？ 物理层面，Prefill 是算力密集的大矩阵运算，命中只需”搬运”已存好的 KV，两者 GPU 成本相差一到两个数量级；商业层面，平台用巨大价差”雇佣”开发者把前缀做稳定，从而提升全局命中率与集群吞吐。
  4. 为什么 Coding Agent 命中率常在 90% 以上？ 长静态前缀、只追加的消息循环、秒级高频调用、100:1 以上的输入输出比，四个结构特征叠加，使单轮命中率在数学上趋近 1 − Δ/L，轻松超过 90%。
  5. 对 Agent 架构有什么启示？ 把”前缀稳定性”提升为一等架构约束，即 Cache-First Context Engineering（缓存优先的上下文工程）：上下文是只追加日志、越稳定越靠前、字节级确定性。第六章给出分层模型、12 条实践、可运行代码与监控体系。

一、先算一笔账：缓存是 Agent 成本的第一杠杆

设想一个典型的 Coding / 故障诊断类 Agent 会话：

  • 静态前缀（系统提示词 + 工具定义 + 项目规范）约 20k tokens；
  • 共执行 50 轮工具调用，每轮新增约 2k tokens（模型发出的工具调用 + 工具返回的文件内容、日志片段）；
  • 每轮模型输出约 300 tokens。

第 k 轮输入长度为 20k + (k−1) × 2k。50 轮累计输入约 345 万 tokens，累计输出只有 1.5 万 tokens，输入输出比约 230 : 1。这说明：Agent 的成本几乎全部由输入决定，而输入的成本几乎全部由缓存命中率决定。

用两类有代表性的价格做量级估算：

计费情形 Claude Sonnet 级（每百万 tokens：输入 $3、输出 $15、命中 $0.30、写入 $3.75） DeepSeek V4-Flash（每百万 tokens：未命中 1 元、命中 0.02 元、输出 2 元）
完全不命中 约 $10.58 约 3.48 元
命中率约 96.6% 约 $1.67 约 0.21 元
降本倍数 约 6.3 倍 约 16 倍

同一个 Agent、同样的任务、同样的效果，账单相差 6～16 倍。影响的不只是钱：命中的前缀无需重新 Prefill，首 token 延迟（TTFT）同样大幅缩短。Anthropic 在 2024 年发布 Prompt Caching 时给出的数据是：长提示场景成本最多降低 90%、延迟最多降低 85%。Manus 团队在其上下文工程经验总结中更是直言，KV Cache 命中率是生产级 Agent 最重要的单一指标。

二、技术原理：从 KV Cache 到跨请求前缀缓存

2.1 大模型推理的两个阶段

Transformer 自回归推理由两个性质截然不同的阶段组成：

阶段 做什么 计算特征 瓶颈 用户感知
Prefill（预填充） 一次性并行处理全部输入 token，计算每层的 K/V，并产出第一个 token 矩阵 × 矩阵，计算强度高 算力（FLOPs） 首 token 延迟 TTFT
Decode（解码） 每步生成 1 个 token 并追加到序列末尾，循环至结束 矩阵 × 向量，每步都要读全部权重和全部 KV 显存带宽 每 token 延迟 TPOT

打个比方：Prefill 是”读完整本卷宗”，Decode 是”逐字写判决书”。读卷宗可以多人并行、一目十行；写判决书只能一个字一个字地写，而且每写一个字都要回头翻一遍整本卷宗。

2.2 KV Cache：请求内的”草稿纸”

注意力计算中，第 i 个 token 需要与之前所有 token 的 Key、Value 做运算。如果每生成一个新 token 都把前面所有 token 的 K/V 重算一遍，计算量会随长度平方增长。KV Cache 的做法很朴素：把已算好的 K/V 留在显存里，Decode 时只为新 token 计算一次 K/V 并追加。

这是请求内缓存，所有推理引擎默认具备，不体现在账单上。本文讨论的”缓存命中”，是把这张草稿纸跨请求保留下来，让下一个请求直接接着用。

2.3 为什么能跨请求复用：因果注意力决定”前缀决定论”

Decoder-only 模型使用因果掩码（causal mask），第 i 个位置只能看到位置 1～i 的 token。逐层归纳可以得到一个关键性质：

第 l 层第 i 个位置的 K/V，只取决于模型权重和 token x₁…xᵢ，与位置 i 之后的任何内容都无关。

由此得到三条推论，它们是后文所有工程实践的理论根基：

  1. 前缀相同，则前缀部分的 KV 完全相同。 两个请求只要前 n 个 token 逐一相同（位置也相同），前 n 个位置的 KV 就可以直接复用。
  2. 中间改一个字，后面全部作废。 若第 j 个 token 发生变化，位置 j 及其之后所有位置的 KV 都会改变。因此缓存只认”前缀”、不认”子串”：同一段文字出现在两个请求里，只要它前面的内容不同，它的 KV 就不同。
  3. 缓存与模型强绑定。 换模型（乃至换量化版本、换 LoRA 适配器）就换了权重，KV 不可复用。

学术界也在探索打破”只认前缀”的限制，例如 CacheBlend 通过选择性重算少量 token，复用 RAG 场景中非前缀文档块的 KV。但截至目前，商业 API 的计费体系仍完全建立在”最长公共前缀”之上。

2.4 前缀匹配的数据结构：块哈希链与基数树

跨请求复用的核心问题是：新请求到来时，如何快速找到它与已缓存内容的最长公共前缀？ 开源推理引擎给出了两种经典实现。

（1）vLLM 自动前缀缓存（APC）：块哈希链

vLLM 借助 PagedAttention 把 KV 切成固定大小的块（默认 16 个 token 一块），像操作系统管理内存页一样管理 KV。每个”满块”计算一个哈希：

extra_keys 包括 LoRA 标识、多模态输入的内容哈希、租户隔离用的 salt 等。由于每个块的哈希都包含父块哈希，块哈希天然编码了”从开头到当前块的完整前缀”。新请求到达时，引擎从第一块开始逐块计算哈希并查表，直到第一个查不到的块为止，之前命中的块直接复用。未填满的尾块不参与缓存，这正是各平台命中数按一定粒度对齐的根源。淘汰策略是对引用计数归零的块执行 LRU。

（2）SGLang RadixAttention：基数树

SGLang 把所有缓存序列组织成一棵基数树（Radix Tree），边上存 token 序列，节点指向对应的 KV 页。查找最长前缀就是一次自根向下的匹配，天然适合”很多请求共享同一系统提示词、再各自分叉”的树状结构。配合”最长前缀优先”调度策略，调度器会优先执行能命中更多缓存的请求，进一步提升全局命中率。

两种实现的思想一致：以前缀为单位寻址，以块/页为单位存储，以引用计数加 LRU 管理生命周期。

2.5 KV 到底有多大：一笔显存账

缓存首先是一笔存储成本。单个 token 的 KV 体积为：

模型（架构） 计算 每 token KV 10 万 token 上下文
Llama-3-70B（GQA：80 层、8 个 KV 头、头维 128、BF16） 2×80×8×128×2 B 约 320 KB 约 32.8 GB
DeepSeek-V3（MLA：61 层、每层压缩潜向量 512+64 维、BF16） 61×576×2 B 约 69 KB 约 7 GB

两个结论：第一，长上下文的 KV 体量惊人，10 万 token 就可能吃掉一张 80GB 显卡的相当部分，而 HBM 是整个系统里最贵、最稀缺的存储，不可能长期为大量会话保留；第二，MLA 这类 KV 压缩架构把体积降低了数倍，让”把 KV 落盘长期保存”在经济上变得可行。DeepSeek 在 2024 年 8 月率先推出”硬盘缓存”并把命中价格压到极低，与其模型架构和自研存储体系密不可分。

2.6 多级缓存层次：从显存到分布式存储

工业级平台普遍采用多级 KV 缓存，思路与 CPU 的多级缓存如出一辙：

层级 介质 容量 加载速度 典型保留时长 对应的产品形态
L1 GPU HBM 数十 GB/卡 极快 秒～分钟 短 TTL 内存缓存（如 5 分钟）
L2 主机 DRAM 数百 GB～TB/节点 快（PCIe 等） 分钟～小时 扩展保留
L3 本地 NVMe SSD 数 TB～数十 TB/节点 中（GB/s 级） 小时～天 硬盘缓存、24 小时保留
L4 分布式内存池/存储 PB 级 取决于 RDMA 网络 天级 跨节点共享 KV 池

代表性工程包括：月之暗面 Kimi 的 Mooncake（以 KVCache 为中心的分离式推理架构，把集群的 DRAM/SSD 组织成分布式 KV 池）、开源的 LMCache（为 vLLM 等引擎提供 CPU、磁盘、远端多级 KV 卸载与跨实例共享）、DeepSeek 的 3FS 文件系统。OpenAI 的扩展缓存保留，同样是在显存不足时把 KV 张量卸载到 GPU 本地存储，从而把保留时长从分钟级延长到最长 24 小时。

你在 API 文档上看到的各种 TTL（5 分钟、30 分钟、1 小时、24 小时、”数小时到数天”），本质上是平台把 KV 放在哪一级存储、愿意为你保留多久的工程选择。

2.7 两个常见误解

误解一：”输出也能命中缓存”。 计费层面，输出 token 永远按输出单价收费，因为它是逐个新生成的，无从复用。但在多轮对话中，第 k 轮的输出会原样进入第 k+1 轮的输入历史；在第 k+1 轮被写入缓存后，它就作为前缀被后续轮次反复命中。自建引擎（如 vLLM）甚至会把解码阶段生成的满块直接纳入前缀缓存。所以更准确的说法是：输出以”未来输入前缀”的身份被缓存。

误解二：”缓存命中 = 结果被复用”。 前缀缓存只复用计算中间态，模型依然基于完整上下文重新采样生成，输出不因缓存而改变，也不保证两次相同。真正复用”答案”的是应用层的语义缓存：按向量相似度匹配历史问题并直接返回历史答案。它能省掉 100% 的调用，但存在答非所问、数据过时等正确性风险，适合 FAQ 类场景，不适合工具调用密集、状态持续变化的 Agent 循环。两者可以叠加，但不能混为一谈。

三、模型供应商平台如何实现缓存命中与计费统计

先看一眼演进脉络：2024 年 8 月，DeepSeek 上线硬盘缓存，Anthropic 推出 Prompt Caching；同年 10 月，OpenAI 上线自动缓存；2025 年 5 月，Gemini 上线隐式缓存。到 2026 年，”命中约 1 折、显式写入约 1.25 倍”已成为海外头部厂商的事实标准，OpenAI 也在 GPT-5.6 上引入了写入计费与显式断点；国内厂商则普遍采用”隐式为主、显式可选、命中价格极低”的策略。

3.1 端到端链路

把一个 API 请求从进入到计费的全过程展开，与缓存相关的环节如下：

flowchart LR
    A[客户端请求] --> B[API 网关<br/>鉴权 / 组织 / 区域]
    B --> C[模板渲染与分词<br/>工具 schema + 系统提示 + 消息 → token 序列]
    C --> D[前缀指纹计算<br/>断点识别 + 块哈希]
    D --> E{缓存感知路由<br/>前缀亲和 × 负载}
    E --> F[推理节点<br/>在 HBM / DRAM / SSD 中查找最长命中前缀]
    F --> G[加载命中部分的 KV]
    F --> H[对未命中部分执行 Prefill]
    G --> I[Decode 生成输出]
    H --> I
    I --> J[按断点/块写回缓存<br/>刷新 TTL]
    I --> K[计量：未命中 / 写入 / 命中 / 输出 四个桶]
    K --> L[计费与账单]

其中四个环节决定了命中率的上限。

（1）模板渲染：缓存看的是”最终 token 序列”。 平台缓存的不是你提交的 JSON，而是模板渲染后的完整 token 序列，包括平台注入的隐藏系统内容、工具定义、历史消息、图片等。OpenAI 文档明确列出：模型、工具定义（名称、描述、schema、顺序）、结构化输出格式、推理强度、上下文压缩等设置都会影响前缀。任何导致渲染结果变化的参数，都会在变化点”切断”前缀。

（2）缓存感知路由：负载均衡与缓存亲和的天然矛盾。 KV 存放在具体机器上，请求只有落到持有该前缀的机器才能命中。负载均衡希望请求均匀打散，缓存却希望同前缀请求”粘”在同一台机器上。平台路由器通常综合打分：前缀匹配越长越优先，负载越高越扣分。OpenAI 文档披露，其路由依据包括机器负载、请求开头若干 token 的哈希，以及可选的 prompt_cache_key；同一前缀与同一 key 的请求若超过每分钟约 15 次，就可能被溢出路由到其他机器而导致未命中。开源侧的 SGLang Router、vLLM Production Stack、NVIDIA Dynamo 的 KV 感知路由、llm-d 的前缀感知调度，解决的都是同一个问题。

（3）断点与粒度：命中不是逐 token 计算的。 平台只在特定”断点”位置写入与查找缓存。Anthropic 由开发者用 cache_control 显式标注断点（每个请求最多 4 个），并会从断点向前回溯约 20 个内容块寻找已有缓存；OpenAI 早期模型按固定间隔自动放置隐式断点，命中数向下取整到 128 的倍数，GPT-5.6 起支持显式断点并按精确边界计量；vLLM 等引擎以块为粒度。此外，各平台都有最小可缓存长度：常见为 1024 token，部分模型要求 2048 或 4096，百炼隐式缓存低至 256。

（4）隔离边界：缓存不跨组织、不跨区域。 主流平台都在组织（或工作区、订阅）级别隔离缓存，也不跨数据驻留区域复用。这既是安全要求，也意味着：公司内所有应用、所有用户只要共享同一个系统提示词，就可以互相”蹭”缓存。

最后必须牢记：除显式缓存的部分场景外，前缀缓存是尽力而为（best-effort）的。平台不承诺命中，只承诺命中部分按折扣计费。

3.2 两种产品形态：隐式缓存与显式缓存

四、为什么命中与未命中的价格相差几十倍

4.1 先把”几十倍”拆开看

“几十倍”实际上有三种口径：

口径 Anthropic / OpenAI / Gemini DeepSeek V4-Flash DeepSeek V4-Pro
未命中输入 ÷ 命中输入 10 倍 50 倍（1 元 vs 0.02 元） 120 倍（3 元 vs 0.025 元）
输出 ÷ 命中输入 Claude 约 50 倍（输出为输入的 5 倍） 100 倍 240 倍
写入 ÷ 命中输入 12.5～20 倍 无写入溢价 无写入溢价

也就是说，”命中与未命中相差几十倍”在 DeepSeek 等国内平台上是字面事实，在海外头部平台上是 10 倍；而”命中输入与输出”之间则普遍相差 50 倍以上。下面从物理成本、集群收益、剩余成本与定价策略四个层面解释。

4.2 成本根源一：Prefill 是算力活，命中是搬运活

以 Llama-3-70B 处理 10 万 token 的输入做量级估算：

  • 线性层计算：约 2 × 参数量 × token 数 = 2 × 70B × 10⁵ ≈ 1.4×10¹⁶ FLOPs；
  • 注意力计算（因果掩码下约 2 × 层数 × T² × 隐藏维度）：2 × 80 × 10¹⁰ × 8192 ≈ 1.3×10¹⁶ FLOPs，且随长度平方增长；
  • 合计约 2.7×10¹⁶ FLOPs。按 H100 的 BF16 稠密算力约 989 TFLOPS、实际利用率 40%～50% 估算，约需 55～70 GPU·秒。

命中缓存时，这些计算几乎全部省掉，代价变为：

  • KV 仍在 HBM 中：几乎零计算，只是占着显存；
  • KV 在主机内存中：32.8 GB 的 KV 在 8 卡张量并行下每卡约 4 GB，经 PCIe 5.0（单卡约 50 GB/s 量级）加载不到 0.1 秒；
  • KV 在 SSD 或远端存储中：秒级 IO，但可以逐层流水线加载、与计算重叠，而且不占用 GPU 的矩阵计算单元。

算力成本与搬运成本之间相差一到两个数量级，这就是 10 倍到上百倍价差的物理基础。上下文越长，注意力的平方项占比越大，命中节省得越多——这也是长上下文 Agent 对缓存格外敏感的原因。

4.3 成本根源二：命中释放的是整个集群的吞吐

缓存命中的收益并不只属于当前请求：

  • Prefill 不再阻塞 Decode。 长 Prefill 会占满 GPU，拖慢同批次其他请求的解码。命中后 Prefill 变短，更容易与 Decode 混合调度（如分块预填充），集群整体吞吐上升。
  • 首 token 延迟大幅下降。 省下的正是 TTFT 中的大头，用户体验与 Agent 单步执行速度同步提升。
  • 同样的硬件服务更多请求。 对平台而言，全局命中率从 50% 提升到 90%，意味着 Prefill 算力需求降到原来的五分之一，这部分节省足以支撑大幅让利。

4.4 为什么不是免费：命中之后仍然存在的成本

  1. 存储与机会成本：缓存占用的 HBM/DRAM/SSD 本可服务其他请求，HBM 尤其昂贵。
  2. Decode 仍需读取全量 KV：生成每个输出 token 时，注意力都要扫描全部上下文的 KV，无论这些 KV 是否来自缓存，这部分成本主要体现在输出价格里。
  3. 路由约束：为命中而牺牲的负载均衡自由度，会带来一定的排队与资源碎片。
  4. 限流不打折：以 OpenAI 为例，命中的 token 依然计入每分钟 token 限额（TPM）。

4.5 定价策略：写入溢价与命中折扣的”激励设计”

从商业角度看，缓存定价是一套精心设计的激励机制。

写入溢价是一份”保险费”。 Anthropic 与 OpenAI GPT-5.6 对写入收取 1.25 倍，本质是向开发者收取存储与淘汰风险的费用：你声明这段内容值得缓存，平台就要为它占用资源；如果你之后不再复用，资源就白白浪费了。好在盈亏平衡点非常低：

命中折扣是在”雇佣”开发者做前缀工程。 平台无法替你决定提示词结构，只能用价格信号引导：前缀越稳定，你越省钱，平台的全局命中率越高、单位算力产出越大。价差之大，使得”把时间戳挪到末尾”这类改动的投资回报率高到无法忽视。

架构优势决定定价底线。 DeepSeek 能把命中价压到未命中价的 1/50～1/120 且不收写入费，依托的是 MLA 带来的小体积 KV、硬盘级缓存与自研存储体系：它的缓存边际成本本就极低，于是可以把缓存当作竞争武器。

所以 90% 以上不是运气，而是”长前缀 + 小增量”结构的数学必然。反过来也说明：一次前缀断裂的代价，等于把整段上下文按全价重付一次，上下文越长，断裂越痛。

5.3 五个结构性原因

  1. 巨大且稳定的静态前缀。 编码 Agent 的系统提示词、几十个工具的 JSON Schema、项目规范文件（如 CLAUDE.md、AGENTS.md）加起来常达一两万 token，并在整个会话、甚至跨会话跨用户保持不变。
  2. 只追加的消息循环。 每一步只在尾部追加工具调用与工具结果，从不改写历史，前缀天然单调延伸。
  3. 高频、短间隔。 一个任务往往包含数十到上百次模型调用，间隔以秒计，远小于 5 分钟乃至 30 分钟的 TTL；而每次命中又会刷新 TTL，缓存几乎不会冷却。
  4. 输入输出比极度倾斜。 读文件、搜代码、跑测试会把大段文本灌入上下文，模型每步却只输出简短的工具调用或补丁，输入输出比通常在 100:1 以上（Manus 公开的平均值约为 100:1），成本几乎全部落在可缓存的输入侧。
  5. 单会话粘性天然友好。 同一会话、同一模型、同一组织的请求，路由亲和容易实现；成熟的 Agent 框架还会专门围绕缓存设计：自动后移断点、控制压缩时机、让子 Agent 共享同一套工具与系统前缀。

OpenAI 官方文档中的多轮 Agent 示例同样报告了超过 90% 的 token 命中率，与上述推导一致。

六、对 Agent 架构工程实践的借鉴：最佳实践指南

6.1 核心理念：Cache-First Context Engineering

传统提示工程关心”写什么”，缓存优先的上下文工程还要关心”按什么顺序、以什么字节形式写”。归纳为三条公理：

  • 公理一：上下文是只追加日志（Append-only Log）。 像事件溯源一样对待 Agent 上下文：历史事件不可变，只能追加新事件；需要”修改”时，追加一条更正事件。
  • 公理二：越稳定越靠前（Stability Ordering）。 按变化频率从低到高排列：全局不变 → 租户/领域级 → 会话级 → 本轮级。
  • 公理三：字节级确定性（Byte-level Determinism）。 语义相同不够，必须逐字节相同。任何非确定性来源（时间、随机数、哈希表遍历顺序、浮点格式）都是缓存的敌人。

6.2 四层上下文布局模型

层级 内容 变化频率 共享范围 缓存策略
L0 全局静态层 工具定义、角色与行为规范、输出格式约束、少样本示例 随版本发布 全组织所有会话 长 TTL 断点，版本化管理
L1 领域半静态层 租户/项目/业务领域知识（代码规范、车型知识等） 天～周 同租户或同领域会话 长 TTL 断点

需要特别说明的是：L3 的内容一旦发送，就成为下一轮 L2 的历史，必须原样保留。”放在最后”的动态信息在下一轮会变成稳定历史——这完全正确，缓存只要求”已经发送的内容不再改变”。

6.3 十二条最佳实践

A. 前缀构造

实践 1：静态前置，动态后置。 系统提示词只放真正不变的内容。当前时间、用户名、会话 ID、实时状态统统移出系统提示词，作为尾部消息注入；如确需提供日期，只精确到日，并放在本轮用户消息中。

实践 2：确定性序列化。 所有进入上下文的结构化数据（工具 schema、工具结果、配置）都经过同一个规范化函数：key 排序、固定分隔符、固定浮点精度、统一换行符。禁止直接序列化无序的哈希表或集合，工具 schema 在不同厂商格式之间的转换函数也必须是确定性的。

实践 3：工具集”掩码而非删除”。 工具定义位于前缀最前端，增删或重排一个工具就会让其后全部缓存失效。正确做法是：固定注册工具全集并排序；用 tool_choice、allowed_tools 或解码层的 logits 掩码控制本轮可用工具（Manus 的做法）；确需动态加载工具时，采用延迟加载并把新工具追加到上下文尾部，OpenAI 的工具搜索正是如此设计。

B. 历史管理

实践 4：历史只追加，更正也用追加。 不回写历史消息，不事后修剪旧工具结果。发现之前的结论有误时，追加一条”更正：……”消息，而不是修改原消息。

实践 5：用阈值触发的一次性压缩替代滑动窗口。 滑动窗口每轮删掉最旧的消息，等于每轮都在修改前缀开头，消息层缓存永远不会命中。正确做法是：上下文达到阈值（如窗口的 70%～80%）时，一次性把 L2 历史压缩为摘要，此后在新前缀上继续只追加。压缩那一轮付一次全价写入，换来之后几十轮的高命中。压缩时保持 L0/L1 不动、只替换 L2，静态层缓存依旧有效。

实践 6：大体量工具结果在写入时裁剪，而非事后裁剪。 读取大文件、拉取长日志时，先在工具侧截断或摘要，把全文存入文件系统或对象存储并返回引用路径，再写入上下文。一旦写入，就不再回头修改。

C. 断点与生命周期

实践 7：设计断点布局。 以 Anthropic 的 4 个断点为例，推荐分配为：L0 末尾（1 小时 TTL）、L1 末尾（1 小时 TTL）、最新一条消息末尾（5 分钟，每轮后移），第 4 个留给”单轮追加大量内容块”时的中间位置。注意 Anthropic 要求混用 TTL 时，长 TTL 的断点必须位于短 TTL 断点之前。OpenAI GPT-5.6 起可使用显式断点加”仅显式”模式，避免把本轮易变内容写进缓存、白付写入费。

实践 8：算清 TTL 与保温的经济账。 对 5 分钟 TTL，若预计用户会在较长时间后回来，可定时发送最小请求”保温”。每次保温成本约为 0.1 倍前缀价格（外加极少量输出），而过期重建需要 1.25 倍。因此保温次数少于约 12 次（约 1 小时）时划算；更长的空闲，直接选择 1 小时 TTL 或接受重建。不要对所有会话无差别保温，只对高价值、长前缀、高回访概率的会话保温。

实践 9：并发扇出前先预热。 同时启动 N 个共享前缀的子 Agent 时，它们会并发地各写一份缓存。应先串行发送一次请求完成写入（OpenAI GPT-5.6 为此提供了 prewarm 选项），再并发发送其余请求。

D. 多 Agent、路由与安全

实践 10：子 Agent 共享”家族前缀”。 同一系统内的主 Agent 与各类子 Agent 使用完全相同的 L0（同一套工具定义与基础规范），角色差异放在 L0 之后。这样任何子 Agent 的首轮请求都能命中 L0；子 Agent 的独立上下文又能防止主会话被大量中间结果污染，二者兼得。

实践 11：会话亲和路由与模型固定。 使用 OpenAI GPT-5.6 之前的模型时，为共享前缀的请求设置稳定的 prompt_cache_key，高流量时按确定性映射拆分为多个 key；自建推理集群时，在网关层按会话 ID 做一致性哈希或 KV 感知路由。一个会话内固定使用同一个模型与推理参数；”大小模型路由”应按会话或子任务粒度切换，而不是在同一上下文中来回切换。

实践 12：多租户隔离与缓存安全。 共享前缀缓存存在计时侧信道风险：攻击者可通过响应时间或命中计数，推测某段内容是否被他人发送过，学术研究曾在部分 API 中检测到跨用户共享缓存的现象。自建平台务必按租户隔离缓存（如 vLLM 的 cache_salt），SaaS 场景可用 prompt_cache_key 做分租户缓存核算；敏感数据不要放入跨租户共享的前缀。此外，扩展保留会把 KV 张量持久化到存储上，对数据驻留与留存有严格要求的业务需要评估合规影响（例如 OpenAI 对开启零数据留存的组织默认只使用内存缓存）。

隐式模式会在最新一条合格消息末尾自动放置断点，再加上稳定前缀后的显式断点，即可同时覆盖”跨会话共享的静态层”和”会话内滚动增长的历史层”。

6.5 可观测性与 FinOps 指标体系

没有度量就没有优化。建议在模型网关层统一埋点，核心指标如下：

指标 定义 目标与告警建议
token 命中率 R / (U + W + R) 编码/诊断类 Agent ≥ 85%；单轮问答类 ≥ 50%
写读比 W / R 持续高于 0.2，说明频繁重建，排查前缀漂移或 TTL 过短
有效输入单价 输入总费用 / 总输入 token 应稳定在命中单价的数倍以内

分桶 TTFT 按命中率分桶统计首 token 延迟 高命中桶应显著更低
前缀分叉次数 first_divergence 非空次数，按段打标签 L0/L1 分叉应接近 0

6.6 自建推理平台的缓存工程

私有化部署、数据不出域的场景下，缓存能力需要自己建设。推荐的组合如下：

  • 引擎层：vLLM（V1 引擎默认开启自动前缀缓存）或 SGLang（RadixAttention 默认开启，可选最长前缀优先调度）。
  • 多级缓存层：LMCache 将 KV 卸载到 CPU 内存与磁盘，并支持跨实例共享；规模更大时可参考 Mooncake 的分布式 KV 池与 PD 分离架构。
  • 路由层：最简方案是网关按会话 ID 一致性哈希；更优方案是 KV 感知路由，按”前缀匹配长度 × 实例负载”打分，同时照顾会话内复用与跨会话共享 L0/L1。
  • 隔离层：按租户注入 cache_salt，杜绝跨租户缓存复用与侧信道。

纯会话哈希只解决了会话内复用，无法让不同会话共享 L0/L1。对 Java/Spring Cloud 技术栈，可以在 Spring Cloud Gateway 或 Higress 中实现自定义负载均衡插件：以”会话 ID + L0/L1 前缀指纹”为输入，结合各实例上报的缓存命中与负载指标做加权选择，把同一领域的会话优先调度到已缓存该领域前缀的实例上。自建平台同样要打通 6.5 节的指标：vLLM、SGLang 都暴露了前缀缓存查询与命中类指标，可直接接入 Prometheus。

6.7 上线前检查清单

  • 系统提示词与工具定义中不含时间、ID、随机数等动态内容
  • 所有结构化内容经统一的规范化序列化函数输出
  • 工具全集固定且有序，动态可用性通过 allowed_tools 或掩码实现
  • 历史消息只追加；压缩为阈值触发的一次性操作，且不触碰 L0/L1
  • 断点布局已按四层模型设计，长 TTL 断点位于短 TTL 断点之前
  • 同一会话固定模型与推理参数；子任务使用独立会话
  • 并发扇出前有预热步骤
  • 网关层完成四桶归一化计量，命中率、写读比、前缀分叉已接入监控告警
  • 前缀稳定性单元测试已纳入 CI，提示词版本已打入指标标签
  • 多租户缓存隔离与数据留存合规评估已完成

6.8 落地示例：车联网故障诊断 Agent 的缓存化改造

以一个车联网远程诊断 Agent 为例，按四层模型重构上下文：

层级 内容 规模 共享范围
L0 诊断 Agent 角色规范、证据链输出格式、工具定义（查询故障码、拉取日志、查询 OTA 版本、检索知识库） 约 12k 全部工单
L1 车型级知识：ECU 拓扑、故障码字典摘要、诊断手册要点 约 20k 同车型工单
L2 工单会话：故障描述、日志证据、工具调用与结果 每轮 +3k 单工单
L3 当轮问题、当前时间 很小 不共享

假设每个工单平均 15 轮，按改造前后估算：第 k 轮输入为 32k + (k−1)×3k，单工单累计输入约 79.5 万 tokens。改造前，系统提示词里嵌入了当前时间和工单号，几乎每轮都不命中；改造后，L0/L1 被同车型工单共享、L2 只追加，累计命中率约 94%。以 DeepSeek V4-Flash 价格估算，单工单输入成本从约 0.80 元降至约 0.06 元；按每天 2 万个工单计，日输入成本从约 1.59 万元降到约 1200 元，降幅超过 90%，同时首 token 延迟显著缩短，诊断交互更流畅。

还有两条行业特有的注意事项：第一，VIN、车主信息等个人数据必须脱敏，且只能出现在 L2/L3，严禁进入跨工单共享的 L0/L1；第二，若使用公有云模型的扩展缓存保留，需结合汽车数据安全与个人信息保护的合规要求，评估 KV 张量落盘的影响，必要时选择内存级缓存或私有化部署。

七、总结

  1. 原理：前缀缓存复用的是 Prefill 阶段计算出的 KV 张量。因果注意力保证”前缀相同则 KV 相同”，因此缓存只认最长公共前缀，任何一个 token 的变化都会让其后的缓存全部失效。
  2. 实现：平台通过模板渲染、前缀哈希、缓存感知路由、多级 KV 存储与四桶计量实现缓存计费；隐式缓存胜在零改造，显式缓存胜在可控，二者正在融合。
  3. 价差：命中是”搬运”，未命中是”计算”，二者成本相差一到两个数量级；再叠加写入溢价与命中折扣的激励设计，形成了 10 倍到上百倍的价差。
  4. Coding Agent：长静态前缀、只追加循环、高频调用与极端输入输出比，使命中率在数学上必然趋近 90%+，一次前缀断裂则意味着全价重付整段上下文。
  5. 工程实践：以 Cache-First Context Engineering 为指导，用四层布局组织上下文，用规范化序列化保证字节确定性，用阈值压缩替代滑动窗口，用指纹测试与命中率监控守住回归，用路由与隔离兼顾性能与安全。

对 Agent 架构师而言，缓存不是一个锦上添花的优化开关，而是与数据模型、接口契约同等重要的架构约束。在 Agent 规模化落地的阶段，谁能把前缀稳定性工程化，谁就能以数分之一的成本和更低的延迟交付同样的智能。
