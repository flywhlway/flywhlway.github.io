高并发缓存选型：Redis 集群、KeyDB 与 Dragonfly 的取舍

从线程模型、兼容性、压测口径与迁移回滚四个角度，论证车联网缓存层在 Redis 7.0 集群、KeyDB 6.3 与 Dragonfly 1.x 之间的取舍…

先读结论

  1. Redis 6 起已有 I/O 多线程，KeyDB 的数据集仍由全局锁串行化，两者解决的是同一类 I/O 瓶颈，收益必须在同核数条件下实测。
  2. KeyDB 6.3 的功能基线停在 Redis 6.2，读不了 Redis 7.0 的 RDB，谈不上无缝迁移；Dragonfly 在 2023 年中只对齐到约 Redis 5.0 API。
  3. 2023 年的结论是主力保持 Redis 7.0 集群，按数据性质拆集群并先做近端缓存；KeyDB 不作主力，Dragonfly 只做限定场景试点。
  4. 2026 年回看：KeyDB 已停止维护，Redis 许可证两度调整，自建场景的默认选择转向 Valkey。

背景：缓存层在车联网平台里承担什么

车辆接入规模上来以后，缓存层不再只是「数据库前面挡一层」，而是承载了几类性质完全不同的数据。选型之前先把它们分开，因为它们对一致性、持久化和淘汰策略的要求互相冲突：

负载 访问特征 键设计 丢失的后果
车辆在线会话与连接路由 上下线时写，下行指令时读；每车一条 sess:{VIN} 下行指令找不到车辆所在接入节点，必须持久化且不可淘汰
车辆最新状态快照 实时计算作业（本系列 04 篇）按车覆盖写，App 与运营后台读 state:{VIN}（Hash） 可从时序库重建，允许短暂缺失
远控与升级任务的短期状态 指令幂等键、任务进度计数，TTL 从分钟到天 cmd:{VIN}:{reqId} 幂等失效可能导致指令重复执行
配置与字典 读多写少，少数键极热 cfg:{model}:{ver} 可回源，但热点键会打满单分片

2023 年上半年的现象是：高峰时段少数分片 CPU 打满、p99 延迟明显抬升。团队内出现了一个提议：换成多线程的 KeyDB，「QPS 翻倍、延迟降六成、完全兼容、无缝迁移」。本文的任务是把这个提议拆开验证——哪些成立，哪些没有依据，以及真正该怎么做。

先说结论性的判断方法：缓存选型比较的对象，永远是「同等 CPU 核数与内存下的完整部署」，而不是「一个 Redis 进程对一个多线程进程」。

先把「单线程」说清楚：三种线程模型

「Redis 是单线程」这句话从 Redis 6.0（2020 年）起就只说对了一半。三种实现的真实差异如下：

Redis：I/O 可并行，命令执行串行

Redis 6.0 引入 io-threads：主线程把就绪连接分发给 I/O 线程做 socket 读写，开启 io-threads-do-reads 后协议解析也交给 I/O 线程；命令本身仍由主线程串行执行。因此：

  • 瓶颈在网络系统调用（连接数多、value 大、无 pipeline）时，I/O 线程有效；
  • 瓶颈在命令执行（长 Lua 脚本、大集合的 O(N) 命令、大 key 删除）时，I/O 线程无效；
  • 官方 redis.conf 的建议是 4 核机器用 2～3 个 I/O 线程、8 核用 6 个，超过 8 个收益有限。

Redis 利用多核的正路是 Redis Cluster：16384 个哈希槽分布到多个分片，一台机器上可以跑多个分片进程。代价是客户端必须支持集群协议，跨槽的多键命令要靠 hash tag（{VIN}）把同一辆车的键放进同一个槽。

KeyDB：并行的是 I/O，不是数据集访问

KeyDB 从 Redis 分叉，每个工作线程（server-threads）运行一个完整的事件循环，独立处理自己那部分连接的收包、解析和回写；对数据集的访问依赖一把全局自旋锁。6.3.0 的发布说明写得很直白：这一版是「逐步摆脱全局锁」的阶段性成果，新增的 async commands 只覆盖 GET 和 MGET，默认关闭，开启后还要接受跨客户端写入可见性的放宽；另一项改进是利用自旋等待的 CPU 时间做 rehash。

这意味着原稿画的「多线程 + 数据锁并行执行 DB 操作」并不准确：写路径仍是串行化的，KeyDB 的收益主要来自把 I/O 与解析并行化——和 Redis 6 的 I/O 线程解决的是同一类瓶颈，只是实现方式不同（KeyDB 由线程独立处理连接全流程，省掉了主线程分发与等待）。推论有两条：

  1. 对比「未开 I/O 线程的单个 Redis」，KeyDB 的提升会很显著，但这个对照组本身不公平；
  2. 对比「开了 I/O 线程的 Redis」或「同核数的 Redis Cluster」，差距多大没有先验答案，线程数越多，锁竞争越可能吃掉收益。

「QPS 是 Redis 的两倍、延迟降低 60%」这类数字，脱离了对照组配置、数据形态和延迟分位就没有意义，不能作为决策依据。

Dragonfly：真正并行执行命令，但功能面尚窄

Dragonfly 采用无共享（shared-nothing）架构：键空间按线程切分，每个线程独占一个分片，单键命令投递给所属线程执行；多键原子操作基于 VLL 论文实现的事务框架协调，不依赖互斥锁。三者之中，只有它真正做到了命令执行的多核并行。

截至 2023 年 6 月（v1.3.0，5 月 18 日发布）它的边界同样清楚：

  • v1.0.0 在 2023 年 3 月 20 日发布，主从复制是这个版本才加入的；
  • 项目 README 自述实现了约 185 个 Redis 命令，大致对齐 Redis 5.0 API；
  • cluster_mode 只支持 emulated，即对客户端伪装成只有一个分片的集群，本身不能横向分片；
  • 许可证为 BSL 1.1，附加使用授权禁止以它对外提供内存数据存储服务，企业内部自用不受影响，但要过法务。

性能方面，厂商 README 给出在单台 c6gn.16xlarge 上相对 Redis 25 倍吞吐的结果，对照组是单个 Redis 进程；Redis 官方在 2022 年用同一机型上的多分片 Redis 集群做了反驳测试。双方的分歧恰好说明了本文的比较原则：对照组必须是同核数的 Redis 集群。

RDB 这一行决定了迁移路径：现网是 Redis 7.0，KeyDB 6.3 不能直接挂成它的从库完成全量同步，只能用基于命令重放的同步工具（如 RedisShake）或业务双写。「无缝迁移」在这里不成立。

应用侧还要用静态扫描加流量采样确认实际使用的命令集合：Redis 的 INFO commandstats 可以列出现网每个命令的调用次数，拿它和目标实现的命令支持表逐条比对，比阅读兼容性声明可靠得多。

容量口径与压测方法

容量假设

项目 取值 说明
车辆保有 200 万 三年规划口径
峰值同时在线 80 万 早晚通勤时段
状态快照写入周期 10 秒 原始信号走消息链路（本系列 06 篇）与时序链路（本系列 07 篇），缓存只存最新快照
状态快照大小 约 1.5 KB，Hash 约 60 个字段 保持在 listpack 编码阈值内
会话记录 约 200 B 持久化、不可淘汰

由此推出：

  • 状态写入常态 80 万 ÷ 10 秒 = 8 万次/秒，按集中补传与批量远控取 3 倍峰值系数，约 24 万次/秒；
  • 读取（App、运营后台、规则引擎）常态约 3 万次/秒，峰值按 10 万次/秒规划；
  • 内存：200 万 × 1.5 KB ≈ 3 GB 原始数据，计入编码与分配器开销按 2 倍估算约 6 GB，加上会话、任务状态与配置约 8 GB；一主一从、内存水位不超过 50%，物理内存至少 32 GB。

单分片能力不做假设，而是压测求出「在 p99 ≤ 2 ms 约束下单分片可持续承受的吞吐」，记为 S。分片数 = 峰值吞吐 ÷（S × 0.6），0.6 为故障转移与扩容窗口留出的余量。这组数字的意义不在绝对值，而在于把「需要多少 QPS」换算成「需要多少核、多少分片」，让三种方案在同一口径下比较。

压测怎么做才可比

  1. 同核数对照：8 vCPU 机器上，Redis 侧部署 4～6 个集群分片（或单分片开 I/O 线程两组都测），KeyDB 设 server-threads 为 4～6，Dragonfly 设 proactor_threads 为 8；压测机与被测机分开，网络带宽不成为瓶颈。
  2. 真实数据形态：value 大小按线上分布取区间，键空间取 200 万，访问分布用高斯而非均匀，以模拟热点车辆与热点配置。
  3. 真实连接数：线上是数百个服务实例、每实例数十个连接，压测的连接总数要对齐。连接数对 I/O 线程和 KeyDB 的收益影响很大，少量连接加深 pipeline 的测法会严重高估。
  4. 持久化与副本打开：AOF 每秒刷盘、带一个从节点，与生产一致；关掉持久化测出的数字不能用于容量规划。
  5. 梯度加压看分位：逐级提高请求速率，记录每一级的 p50、p99、p99.9，找出 p99 越过 2 ms 的拐点；只报最大吞吐没有意义。
  6. 故障注入：压测中执行 BGSAVE、主从切换、删除一个 100 MB 的大 key，观察尾延迟与恢复时间。

许可证 BSD-3-Clause（核心） BSD-3-Clause BSL 1.1

2023 年 6 月的决策：

  • 主力保持 Redis 7.0 Cluster，按数据性质拆成两个集群：会话与任务状态集群（noeviction、AOF 开启），状态快照与配置缓存集群（allkeys-lru、只开 RDB）。拆分后淘汰策略与持久化策略不再互相妥协。
  • 先治热点，再谈换引擎：热点配置改为进程内近端缓存（Caffeine 一类）配合 CLIENT TRACKING 失效通知，这一步通常能削掉读流量中最尖的那部分，效果远大于更换服务端。
  • I/O 瓶颈的分片开启 I/O 线程，以压测拐点决定线程数。
  • KeyDB 不作为主力：它能解决的问题 Redis I/O 线程加分片也能解决，却要付出功能回退到 6.2、迁移不可直连、维护节奏放缓三项代价。
  • Dragonfly 列入观察：仅在「单机大内存、读多写少、不依赖集群协议」的缓存上试点，前提是命令清单比对全部通过。

迁移与回滚步骤

即使是 Redis 同版本之间的拆集群、扩分片，也按同一套步骤执行：

  1. 命令清单比对：导出 INFO commandstats，与目标端支持列表逐条核对，不支持的命令先在应用侧改掉。
  2. 影子流量：用同步工具把现网数据持续同步到目标集群，读流量按 1% 旁路到目标端做结果比对，不返回给调用方。
  3. 可重建数据先切：状态快照与配置缓存可从时序库和配置中心回源，先切这一类；按服务逐个切换连接配置，每步观察 24 小时。
  4. 不可重建数据后切：会话与幂等键采用双写，新集群为主、旧集群为辅，读取以新集群为准；双写窗口覆盖最长 TTL。
  5. 回滚：连接配置保留旧集群地址，一个开关切回；回滚期间不需要反向同步可重建数据，会话数据依赖双写窗口内旧集群仍是完整的。
  6. 下线旧集群：双写窗口结束且连续一周无回滚后，停止双写并下线。

反例与风险

  • 只换引擎不治热点：热点键在任何实现上都会落在同一个线程或分片上，Dragonfly 也不例外。
  • 缓存当主存：会话数据若只在缓存里，需要明确 AOF 策略、副本数和故障切换时的丢失窗口；appendfsync everysec 意味着最多丢一秒写入。
  • KeyDB 多主复制：active-replica 与 multi-master 的冲突解决依赖时间戳，网络分区时存在写覆盖风险，不适合幂等键这类数据。
  • 大 key：一个 Hash 存全车队状态会让单次 HGETALL 阻塞主线程，也让集群无法均衡；键必须以车为粒度。
  • 压测对照组不公平：拿单个未调优 Redis 进程做对照得出的倍数，只能证明对照组没用满机器。

2026 回看：KeyDB 停更、许可证变局与今天的选择

经受住时间的判断

没有把 KeyDB 作为主力是对的。 KeyDB 最后一个版本是 2023 年 10 月 30 日的 v6.3.4，代码提交停在 2024 年 3 月下旬，此后事实上停止维护，功能基线永远停在 Redis 6.2。当年若全面迁移，今天就要再迁一次。好在迁出方向是「新版本读旧格式」，从 KeyDB 迁往 Valkey 或新版 Redis 比当年迁入容易。

「按数据性质拆集群、先治热点」这条与引擎无关，至今适用。

需要修正的地方

许可证不再是「默认安全」的一项。 2023 年表格里把 Redis 核心许可证写成 BSD-3-Clause 并视为无风险，这个前提在一年后被打破：2024 年 3 月 20 日起，Redis 7.4 及后续版本改为 RSALv2 与 SSPLv1 双许可；2025 年 5 月 1 日发布的 Redis 8 又增加了 AGPLv3 选项，并把 JSON、Time Series、查询引擎并入核心、新增 Vector Sets，截至 2026 年 9 月最新为 8.10。选型表今天必须把许可证作为一等维度，而且要评估「许可证在未来被改变」的可能。

「多线程」不再是分叉项目的专利。 Redis 被分叉后诞生的 Valkey（2024 年 3 月由 Linux 基金会托管，BSD-3-Clause）在 8.0（2024-09-15）重写了 I/O 多线程，8.1（2025-03-31）换用新的哈希表降低每键内存开销，9.0（2025-10-21）带来原子槽迁移、Hash 字段级过期与集群模式下的多数据库，9.1 于 2026-05-19 发布。当年 KeyDB 试图用分叉解决的问题，主线实现已经吸收。

Dragonfly 的功能面补齐了。 它持续高频发布，2026 年 9 月 16 日发布 v2.0.0，已能加载 Valkey 9 的 RDB，集群迁移与分层存储也在持续完善；许可证仍是 BSL 1.1。2023 年「约 Redis 5.0 API、不能横向分片」的判断只适用于当时。

今天会怎么做

  • 自建默认 Valkey 9.x 集群：许可证稳定、与 Redis 7.2 及之前的协议和数据格式兼容、多线程 I/O 已在主线；托管场景优先选云厂商的 Valkey 兼容服务。
  • 需要 Redis 8 新能力（向量检索、内置 JSON/时序）时再评估 Redis 8，并由法务确认 AGPLv3 或 RSALv2 的适用边界。
  • Dragonfly 用于单机纵向扩展有明确收益的场景，前提仍是命令清单比对与 BSL 条款审查。
  • 压测方法与迁移步骤不变：同核数对照、真实连接数、梯度加压看分位、双写覆盖最长 TTL。这部分是 2023 年这篇里最耐用的内容。
