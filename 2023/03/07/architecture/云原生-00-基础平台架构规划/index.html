车联网云原生基础平台规划：分层、边界与演进路线

面向车端中央计算与 SOA 化架构，拆解车联网云原生基础平台的六层分层、四条关键边界、选型决策与三阶段演进路线，文末以 2026 年视角复盘哪些判断经受住了时间。

先读结论

  1. 车联接入（有状态长连接、设备证书）与业务接入（无状态 HTTP、用户令牌）必须分开建设，统一网关只收敛南北向 HTTP 流量。
  2. 接入层只终结协议、不理解信号；信号解析、规则判断下沉到解析服务与实时计算，车型增加时接入层零改动。
  3. 车辆指令是带超时与幂等键的异步状态机，不是同步 RPC。
  4. 演进按阶段设退出条件（量化指标），新组件先在非核心链路双写试点，保留回切路径。

规划背景：车端变了，云端必须跟着变

2023 年前后，量产车的电子电气架构正在从「分布式 ECU + 若干域控制器」走向「中央计算 + 区域控制」。车端软件按 SOA 拆成服务，通过 SOME/IP、DDS 在车内通信，可以 OTA 的范围从少数几个控制器扩大到整车。这对云端提出了三类新要求：

  1. 车云接口从固定报文变成服务与信号模型。 车端暴露的是带版本的服务接口和信号目录，云端需要一份与车端对齐、能随车型和软件版本演进的信号字典，而不是为每种报文写一套解析代码。
  2. 数据从周期全量上报变成按策略动态采集。 采什么信号、多高频率、什么条件触发，都由云端下发的采集策略决定。云端要具备策略管理、灰度下发和效果回收能力（第 02 篇展开）。
  3. 规模与实时性同时上台阶。 在网车辆向百万级增长，远程控制、故障预警等场景要求秒级响应，原先以批处理为主、告警延迟以分钟甚至小时计的数据链路撑不住。

与之对照，原有平台的问题并不在某个组件，而在结构：服务按项目各自建设，App 网关、开放 API、账号网关各有一套路由与鉴权；限流、熔断、灰度只在少数服务里零散实现；中间件长期单一选型，面对热点车辆、大 key、突发重连时缺少手段。这次规划的目标，是在车端架构切换的窗口期把基础平台的分层和边界一次定清楚，而不是继续在旧结构上堆组件。

各层职责与「不做什么」同样重要：

  • 接入层：车联接入负责 TLS 终结、设备认证、按 VIN 限流、协议转换；业务接入负责用户鉴权、路由、灰度、WAF。两者都不包含业务判断。
  • 平台能力层：沉淀所有业务共用、与车强相关的能力。车辆主数据维护 VIN、车型、配置字、ECU 软硬件版本；信号模型维护信号字典与服务目录，按车型和软件版本管理；指令中心负责车辆指令的全生命周期；采集策略负责动态采集配置的编排与下发。
  • 基础服务层：与车型无关的通用能力，实时计算、规则引擎、调度、工作流、文件代理、位置服务。业务通过 API 或事件订阅使用，不直接依赖其存储。
  • 中间件层与底座：由平台统一运维，业务按规格申请，不自建。有状态中间件在本阶段仍部署在专用节点池或云托管服务上，不进入通用容器池。

OTA、远程诊断、售后、开放平台等上层业务不属于基础平台，它们是平台的第一批用户。

四条关键边界

分层图人人会画，真正决定平台能否长期演进的是边界。下面四条是规划中争论最多、也最需要写死的。

边界一：车联接入与业务接入分开建设

把所有流量收进一个「统一入口」看似整洁，但两类流量的物理特性完全不同：

维度 车联接入 业务接入
连接模型 长连接、有状态，单车常驻 短连接或 HTTP/2 复用，无状态
身份 设备证书 mTLS，一车一证 用户 OAuth2 / JWT，会话级
扩缩容 缩容即断连，需计划迁移 秒级弹性，随 QPS 自动扩缩
典型故障 重连风暴、心跳超时误判离线 流量突刺、慢调用拖垮线程池
流量形态 上行为主，小包高频 请求-响应，大小不一

因此统一网关（第 03 篇）只收敛南北向 HTTP 流量；MQTT 长连接由专用 Broker 集群承接，两者共享的只有证书体系和限流规则的管理面。

边界二：接入层只终结协议，不理解信号

接入层把车端上行统一封装为内部信封，写入消息队列后即完成使命。信号解析、单位换算、数据质量校验放在解析服务与实时计算里。这样新增车型、信号表变更都不需要发布接入层，而接入层恰恰是最不应该频繁发布的组件。

边界三：平台提供能力，业务不碰平台存储

业务使用平台只有两条路：调用平台 API，或订阅平台发布的事件主题。主题命名统一为 <层>.<领域>.<事件>.<版本>，例如 platform.vehicle.status-changed.v1，读写权限按主题前缀授予。跨边界直连数据库一律禁止，否则平台的每一次表结构调整都会变成跨团队协调。

边界四：车辆指令是异步状态机，不是同步 RPC

车辆可能休眠、可能在地库没有信号，指令从下发到执行完成可能几秒，也可能几分钟。用同步 HTTP 挂起等待结果，会在高峰期耗尽网关与业务线程。指令中心按状态机建模，业务通过回调或事件拿结果：

stateDiagram-v2
  [*] --> Created
  Created --> Waking: 车辆离线
  Created --> Sent: 车辆在线
  Waking --> Sent: 唤醒后上线
  Waking --> Expired: 唤醒超时
  Sent --> Acked: 车端确认收到
  Sent --> Expired: ACK 超时
  Acked --> Succeeded: 执行成功
  Acked --> Failed: 执行失败或前置条件不满足
  Expired --> [*]
  Succeeded --> [*]
  Failed --> [*]

三条硬约束：每条指令携带幂等键，车端按幂等键去重；每条指令携带过期时间，车端拒绝执行过期指令（避免解锁指令在数分钟后才被执行）；状态迁移全部落库并发出事件，任何超时都有明确终态。

演进路线

阶段 时间 范围 退出条件
一：底座与治理 2023 上半年 无状态服务全部容器化；统一镜像基线与 Helm Chart；Sentinel 覆盖对外入口与核心链路；网关级灰度；trace 贯通 核心链路限流熔断规则覆盖率 100%；发布失败回滚 ≤ 5 分钟；无状态服务扩容一倍 ≤ 3 分钟
二：接入与数据 2023 下半年 统一网关替换多套网关，旧网关保留为回切；实时计算接管信号解析与告警规则；新消息、缓存组件在非核心链路双写试点 信号到告警端到端 P95 < 5 s；旧网关流量 < 5%；试点组件连续 30 天无一级故障方可扩大范围
三：车云协同与网格 2024 中央计算车型量产后，采集策略与车端规则下发；服务网格在新业务域落地；多集群与跨可用区容灾 策略发布到 90% 在线车辆生效 < 30 分钟；跨可用区切换 RTO < 15 分钟

阶段之间不是串行等待，而是以退出条件作为「扩大范围」的闸门：例如统一网关可以在阶段一就开始小流量验证，但只有满足阶段二的退出条件才允许下线旧网关。

容量与性能要点

重连风暴是接入层的头号容量问题。 一次 Broker 滚动升级或负载均衡故障，可能让 50 万车辆在一分钟内集中重连，约 8,300 次/秒 TLS 全握手。RSA-2048 私钥签名的单核吞吐通常在每秒一两千次量级，仅握手就要占掉数个到十余个 CPU 核，还没算认证查库。应对手段要组合使用：车端重连采用指数退避加随机抖动；服务端开启 TLS 会话恢复，并对新建连接速率设上限；设备证书优先使用 ECDSA P-256，签名成本比 RSA-2048 低一个数量级；认证结果在 Broker 本地缓存，避免重连潮直接压到数据库。

消息分区按消费能力而不是写入能力规划。 以 VIN 作为分区键保证单车有序。峰值 10 万条/秒，若解析服务单分区稳定处理 3,000 条/秒，至少需要 34 个分区，考虑三年增长与再均衡余量取 96 个。分区数一旦确定就很难收缩，宁可一次给足。

热点车辆要在入口处理。 测试车、网约车等高频上报车辆会造成单分区倾斜。接入层按 VIN 做令牌桶限流，超出部分降采样而不是丢弃连接；测试车队走独立主题，不与量产车混跑。

车辆实时状态的瓶颈在写而不在存。 50 万在线车辆、每车约 1 KB 状态，总量不过 500 MB，但每 5 秒全量刷新一次就是 10 万次/秒写入。解析服务按 VIN 合并窗口内的多次更新，再批量写缓存，写入次数可以降一个数量级。

反例与风险

  • 把 MQTT Broker 放进按 CPU 自动扩缩的 Deployment。 缩容就是断开一批车辆，下一轮扩容又触发重连，形成自激振荡。Broker 应固定副本数，扩缩容走计划变更，并配合 PodDisruptionBudget 控制同时中断的节点数。
  • 在接入层写业务判断。 例如在网关里直接判断电池温度告警，前三个车型还能维护，第十个车型时没人敢改。
  • 新组件替换不设回切。 缓存、消息组件的替换必须经过双写、比对、灰度切读、保留回切四步，任何一步没有数据支撑都不进入下一步。
  • 一次性全量网格化。 按 Istio 当前版本官方性能文档，每 1,000 RPS 经过 Sidecar 约消耗 0.35 vCPU 与 40 MB 内存，P90 延迟增加约 2.65 ms；上千个 Pod 的规模下，资源成本与排障复杂度都需要先在小范围实测（第 01 篇展开）。
  • 把 Serverless 当成通用计算池。 冷启动与长连接、强状态场景天然冲突，本阶段只用于低频事件处理，例如报表生成、证书到期通知。

2026 回看：分层站住了，底座的边界往上移了

三年后回看这份规划，结构性的判断大多成立，技术选型则有几处需要改写。

经受住时间的判断

  • 车联接入与业务接入分离、接入层不理解信号、指令按异步状态机建模，这三条边界是整份规划中最稳定的部分。车型与车端软件版本数量持续增长，而这些边界让增长主要落在信号模型和解析服务上，接入层与指令中心的结构不必推倒重来。
  • 实时计算作为基础服务的定位没有问题。Flink 在 2025 年 3 月发布 2.0，此后 2.1 引入 Model DDL 与实时 AI 函数，到 2026 年 6 月已是 2.3，流处理平台反而承担了更多职责。
  • 按阶段设退出条件、新组件双写试点的方法论，比任何具体组件都更长寿。

需要修正的判断

  • 服务网格路线。 当年对 Sidecar 成本的担忧是对的，但答案不再是「小范围 Sidecar」。Istio Ambient 模式在 1.24（2024 年 11 月）GA，四层由节点级 ztunnel 承担，七层按需部署 waypoint，今天新建集群会直接走 Ambient。
  • 入口层的配置契约。 Gateway API 在 2023 年 10 月发布 v1.0，到 2026 年 6 月已迭代到 v1.6；Ingress NGINX 已于 2026 年 3 月退役。今天做统一网关，会把 Gateway API 作为配置契约，网关产品可替换，而不是绑定某个产品的私有 CRD 或 Ingress 注解。
  • MQTT Broker 的许可风险。 EMQX 自 5.9（2025 年 5 月）起把社区版与企业版合并为 BSL 1.1 许可，免费生产使用限于单节点。当年「开源版集群」的前提已不存在，今天的选型需要把商业授权成本或其他宽松许可的 Broker 纳入比较。选型表里应当增加一列「许可与治理风险」。

今天会怎么做

  • 在底座层增加模型与推理资源池：Kubernetes 1.34 中 DRA 核心能力 GA（2025 年 8 月），GPU 等加速卡可以按设备属性申请；推理流量用 Gateway API Inference Extension（v1.0，2025 年 9 月）按模型与负载路由；面向大模型调用的出口放在 AI 网关上，Envoy AI Gateway 在 2026 年 6 月发布 v1.0，Higress 自 2024 年起转向 AI 网关并于 2026 年 3 月进入 CNCF Sandbox。
  • 资源池声明式化：数据库、对象存储、消息实例等用 Crossplane（v2.0 于 2025 年 8 月发布，同年 10 月 CNCF 毕业）以 API 方式供给，替代工单式申请；多集群与跨地域调度交给 Karmada（2026 年 9 月 CNCF 毕业）。
  • 注册中心兼作智能体目录：Nacos 3.x（2025 年 4 月 GA）已能注册 MCP Server 与 A2A 智能体，平台能力层的「服务目录」自然延伸为「工具与智能体目录」，车辆能力可以被 Agent 以受控方式调用。

分层图本身几乎不用改，变化集中在两端：底座多了一层面向模型的算力与流量管理，平台能力层的消费者从「业务服务」扩展到「业务服务与智能体」。
