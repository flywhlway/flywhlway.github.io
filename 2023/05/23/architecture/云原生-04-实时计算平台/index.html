车辆信号实时计算平台：Flink 与动态规则引擎

基于 Flink 1.17 构建车辆信号实时计算平台：纠正「状态存在 Kafka」的误解，拆分解析与规则作业，用广播状态实现规则分钟级生效，按表达式、模板、决策三层组织规则…

Flywhl 12 分钟 更新于 2026.09 #架构设计#云原生#车联网

先读结论

  1. Flink 状态在状态后端（堆内存或本地 RocksDB），靠检查点持久化到对象存储；Kafka 只保存输入数据，偏移量随检查点一起保存。
  2. 规则分三层：单帧表达式用 Aviator，持续、窗口、计次等有状态逻辑由平台模板算子实现，跨事件的业务决策才用 Drools。
  3. 动态规则走 Kafka 压缩主题 + 广播状态；编译后的表达式不入状态，恢复时按规则定义重建。
  4. 告警链路用至少一次 + 确定性事件 ID 去重，不用精确一次事务写出，否则告警延迟被检查点间隔拉长。

平台要解决的问题

在建设实时计算平台之前，车辆告警与统计主要靠两种方式：一是每 5 分钟对分析库跑一轮 SQL 批量判断，二是在各业务服务里为不同车型手写判断代码。前者延迟以分钟计，后者每改一个阈值都要发版，而且同一条「电池过温」规则在三个服务里有三种写法。

新平台的目标是四个可验证的数字：

目标 指标
时效 信号进入平台到产生告警，P95 < 5 s（不含车端攒批时间）
规则迭代 规则变更从发布到全量生效 < 2 分钟，无需发布作业
容量 保有 150 万辆、峰值 10 万帧/秒，单帧约 200 个信号
可验证 任何规则上线前都能用历史数据回放，预估触发率

先纠正一个常见误解：Flink 的状态不在 Kafka 里

规划早期的设计稿里，把 Flink 的算子状态和键控状态画成「存放在 Kafka」。这是把 Flink 与 Kafka Streams 混为一谈了，后者确实用 Kafka 的 changelog 主题备份状态。Flink 的状态模型是：

  • 运行时状态在状态后端里。 HashMapStateBackend 把状态作为对象放在 TaskManager 的 JVM 堆上；EmbeddedRocksDBStateBackend 把状态序列化后存在 TaskManager 本地磁盘的 RocksDB 中。
  • 持久化靠检查点。 检查点把状态快照写到分布式存储（HDFS、S3 兼容的对象存储）。RocksDB 支持增量检查点；Flink 1.16 起生产可用的 changelog 状态后端，可以让检查点耗时更短、更可预期。
  • Kafka 只提供可重放的输入。 Kafka Source 的分区偏移量作为状态的一部分写进检查点。故障恢复时，状态从检查点恢复，Kafka 从检查点记录的偏移量重新消费，两者对齐，才得到精确一次的状态语义。
flowchart LR
  K["Kafka 分区<br/>输入数据"] -->|消费| TM["TaskManager<br/>状态后端：堆 / 本地 RocksDB"]
  TM -->|检查点：状态快照 + 消费偏移量| OS["对象存储<br/>检查点目录"]
  OS -.->|故障恢复：加载快照| TM
  TM -.->|按快照中的偏移量回退重读| K

这个纠正直接改变了三项设计：检查点存储要单独规划容量与生命周期；Kafka 的保留时长必须覆盖「最老可用检查点或保存点」到当前的时间差，否则恢复时数据已被删除；状态规模要按 TaskManager 的内存与本地盘来规划，而不是按 Kafka 集群。

作业按变更节奏拆分：解析作业随车型与信号模型变化，按月发布；规则作业的逻辑几乎不变，变的是广播进来的规则；诊断决策作业随业务策略调整。拆开后，改一个解析器不会重启告警链路，反过来也一样。代价是多一次 Kafka 往返，在延迟预算里约几十毫秒，可以接受。

早期设计稿中与 Flink 并列的 Spark 与自研流式 SQL 层，这次不再进入实时链路：流处理统一在 Flink 上，简单的聚合与 ETL 用 Flink SQL 表达，Spark 留给离线数仓（第 07 篇）。

选型

领域 候选 决策 理由
流计算引擎 Flink 1.17 / Spark Structured Streaming / Kafka Streams Flink 按键定时器、广播状态、事件时间与检查点机制成熟；微批模型的延迟与按键定时语义不如 Flink；Kafka Streams 是库而非平台，多作业统一运维弱
表达式引擎 Aviator 5.3 / MVEL / QLExpress / Groovy Aviator 编译为 JVM 字节码，求值在微秒级；可通过语法特性集合、类白名单与循环次数上限裁剪能力，适合执行外部输入的表达式
决策规则 Drools 8 / 自研决策表 Drools，限定在事件层使用 规则网络适合多条件组合与业务人员维护的决策表；编译与内存开销大，不能放在原始帧上
部署 Flink on YARN / Flink on Kubernetes Kubernetes + Flink Kubernetes Operator（1.4 以上），Application 模式 与平台底座统一；每个作业独立集群，故障与资源隔离；YARN 上的存量作业逐步迁移

Groovy 被排除的原因值得单独说：它是完整的编程语言，外部输入的脚本可以做任何事；动态编译还会不断生成新类，长期运行容易耗尽 Metaspace。

规则的三层模型

把所有规则都塞进一个引擎，是规则平台失控的常见原因。按表达能力与成本分为三层：

层 表达方式 例子 状态 单次成本
L1 表达式 Aviator 表达式，作用于单帧 BatTempMax > 55 && ChargeState == 1 无 微秒级
L2 模板规则 平台内置模板 + 参数 + L1 条件 充电时电池温度持续 30 秒超过 55℃ 每车每规则一份 一次状态读写
L3 决策规则 Drools 规则或决策表，作用于 L1/L2 产出的事件 同一车 10 分钟内先后出现绝缘告警与冷却液温度异常，且属于某批次电池包，升级为高优先级工单 Drools 工作内存 毫秒级，但只处理事件流

L2 的模板是有限集合，由平台开发并充分测试：持续（条件连续成立 N 秒）、窗口聚合（N 秒内均值、最大值）、变化率（单位时间变化量）、计次（M 分钟内出现 K 次）、超时（N 秒无数据）。规则作者只填参数，不写状态逻辑，这是让非开发人员也能安全编写规则的关键。

mode 为 SHADOW 时，事件写入影子主题，不进入告警服务，用于上线前观察真实触发率。

动态规则：广播状态

规则中心把每次发布写入一个压缩策略（cleanup.policy=compact）的 Kafka 主题，键为规则 ID，删除规则写入墓碑消息。规则作业把它作为广播流接入，与按 VIN 分区的信号帧流连接：

几个容易踩的点：

  • 广播状态在每个并行实例上各存一份，规则总量要控制在千条级；规则编译也会在每个实例上各做一次。
  • 规则到千条级后要建索引。 示例中每帧遍历全部规则只适合少量规则，实际按车型与信号模型版本预先分组，每帧只遍历适用的几十条。
  • 新规则没有历史状态。 一条「持续 30 秒」的新规则，最早在生效 30 秒后才可能触发；需要历史数据的规则，在回放环境里补算，而不是在线回填。
  • 全新启动的作业从压缩主题最早位置读取，得到全部现存规则；从检查点恢复的作业，广播状态随检查点恢复，再从记录的偏移量继续读取增量。

事件时间：全局水位线对百万车辆不成立

一个 Kafka 分区里混着上万辆车的数据。车辆驶出地库或隧道后，会一次性补传之前缓存的几分钟到几小时数据。如果规则作业依赖全局水位线，只有两种结果：要么这些补传数据全部被判定为迟到而丢弃，要么水位线为了等它们而停滞，拖慢所有其他车辆的告警。

因此规则作业不使用全局水位线，而是按车处理时间顺序：

  • 车辆状态中记录该车最近一帧的车端时间。新帧时间早于它超过阈值（例如 60 秒），判定为补传数据，转入侧输出，由补算链路处理，只记录、不实时通知。
  • 「超时无数据」一类判断使用处理时间定时器，按车注册，不依赖水位线。
  • 全局水位线只用于车队级统计作业，配置允许迟到时间，迟到数据通过侧输出写入修正表，由分析库合并。

一致性语义与告警延迟

Kafka Sink 的精确一次依赖事务：数据在检查点完成时才提交，下游以 read_committed 读取，就要等到检查点完成才能看到数据。检查点间隔 60 秒，告警就可能被延迟 60 秒，直接违反 5 秒的目标。

所以告警链路选择至少一次加幂等：事件 ID 由「规则 ID + 规则版本 + VIN + 触发时的车端时间」确定性生成，作业重放产生的重复事件 ID 完全相同，告警服务按 ID 去重即可。统计链路写 ClickHouse，使用可按主键去重合并的表引擎，重复写入同样无害。

容量规划

不要把帧拆成信号。 早期设计稿的数据流在入口处用 flatMap 把每帧拆成逐个信号的记录，10 万帧/秒 × 200 个信号就是 2,000 万条/秒，序列化与网络开销会压垮集群。规则作业以整帧为单位计算，帧内按名称取信号值。

状态后端按访问模式选。 估算规则作业的状态：150 万辆车，平均每车 10 条有状态规则、每条约 100 字节，原始数据约 1.5 GB，考虑 Java 对象开销按 3 倍计约 5 GB。48 个并行实例平均每个约 100 MB，完全放得进堆。而状态访问频率是每秒 10 万次读写，放在 RocksDB 里每次都要序列化与本地查找，放在堆上只是对象引用。因此规则作业用堆状态后端，配合 changelog 缩短检查点；窗口大、状态以 GB 计的统计作业用 RocksDB 加增量检查点。

计算量估算。 按车型索引后每帧适用约 30 条规则，每秒 300 万次表达式求值，按每次微秒级估算约需数个 CPU 核；加上反序列化与状态读写，规则作业以 48 并行度、每个 TaskManager 4 个槽位起步，压测后再调整。Kafka 信号帧主题的分区数取并行度的整数倍，避免个别实例分到更多分区而成为热点。

延迟预算。

环节 预算
接入层写入 Kafka ≤ 100 ms
解析作业 ≤ 300 ms
信号帧主题中转 ≤ 100 ms
规则作业（含缓冲刷写） ≤ 500 ms
告警服务去重与推送 ≤ 1 s
合计与余量 约 2 s，余量用于反压与故障切换

Flink 网络缓冲的超时时间（execution.buffer-timeout）默认 100 ms，吞吐与延迟都能接受，不需要调到 0。

规则发布流程

  1. 静态校验：语法检查；引用的信号必须存在于信号字典，类型匹配；选择器中的车型与信号模型版本合法。
  2. 回放评估：取最近 24 小时约 1% 车辆的信号帧回放，统计触发率。触发率超过每千车每小时 5 次，需要人工确认，这一步专门拦截单位写错（例如把℃当成 K）导致的告警风暴。
  3. 影子运行：以 SHADOW 模式发布，观察至少一个完整的使用周期（例如一个早晚高峰）。
  4. 正式生效：切换为 ACTIVE，版本号递增。
  5. 回滚：重新发布上一版本定义，1 分钟内生效。

反例与风险

  • 帧拆信号再计算。 数据量放大两个数量级，还丢失了同一帧内信号的同时性。
  • Drools 直接作用于原始帧。 为每辆车维护工作内存，内存随车辆数线性增长；规则库编译在秒级，放在热路径上就是告警延迟。
  • 告警链路用精确一次事务写出。 看似更严谨，实际上把告警延迟绑到了检查点间隔上。
  • 一个巨型作业包办一切。 解析、规则、统计放在一个作业里，任何变更都要全量重启。反过来每条规则一个作业，资源碎片化，同样不可取。
  • Kafka 保留时长短于恢复窗口。 从三天前的保存点恢复时，数据早已过期删除。
  • 状态不设 TTL。 报废车辆、已删除规则的状态永远不会被清理，状态规模只增不减。
  • 表达式引擎不做沙箱。 放开反射与类加载，规则编辑权限就等于生产环境的代码执行权限。

2026 回看：三层规则站住了，第三层正在被模型改写

经受住时间的判断

  • 状态与 Kafka 的职责划分、按变更节奏拆作业、告警走至少一次加幂等，这些是流计算的基本功，三年里没有变化。
  • 三层规则模型依然成立。L1 与 L2 覆盖了绝大多数告警规则，平台模板让规则作者无需理解 Flink 状态。
  • 按车处理事件时间的做法，在补传数据比例随车队规模增长的情况下，价值越来越明显。

需要修正的判断

  • 引擎版本与接口。 Flink 2.0 在 2025 年 3 月发布，移除了 DataSet API、SourceFunction、SinkFunction 等旧接口，最低 Java 版本提升到 11。2023 年新写的自定义连接器，应当一开始就基于新的 Source 与 Sink V2 接口，否则升级时要重写。
  • 大状态作业的部署方式。 Flink 2.0 引入存算分离的状态管理与 ForSt 状态后端，以分布式文件系统作为状态的主存储，大状态作业在 Kubernetes 上扩缩容快得多。当年统计作业「本地 RocksDB + 增量检查点」的设计，今天会改为 ForSt；规则作业状态小、访问密集，堆状态的选择仍然合理。
  • L3 的实现方式。 当年把跨事件的诊断决策交给 Drools。今天这一层的相当一部分工作，适合交给模型：Flink 2.1 引入 Model DDL 与实时 AI 函数，可以在 SQL 里直接调用模型对事件打分或生成解释；Flink Agents 子项目（0.1.0 于 2025 年 10 月发布）让事件驱动的智能体直接运行在流上。

今天会怎么做

  • 以 Flink 2.x 为基线（2026 年 6 月已发布 2.3），规则作业保持堆状态，统计与车队级作业使用存算分离状态。
  • 确定性规则负责触发，模型负责解释与分诊。 告警是否触发仍由 L1、L2 规则决定，保证可解释、可回放、可审计；模型与智能体只处理规则产出的事件，给出可能原因、关联历史案例与处置建议，输出进入工单而不是直接通知车主。
  • 电池、电机等部件的异常检测模型通过 Model DDL 接入统计作业，模型输出作为一个新的「信号」回到 L1 与 L2，与传统阈值规则组合使用，而不是另起一套告警体系。
