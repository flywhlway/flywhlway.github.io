统一网关：WAF、流量网关与微服务网关三合一

把 WAF、流量网关、多套 Spring Cloud Gateway 收敛为一层基于 Envoy 的统一网关：候选方案对比、Higress 选型条件、Nacos 对接与插件配置、分…

Flywhl 12 分钟 更新于 2026.09 #架构设计#云原生#车联网

先读结论

  1. 先二合一、再三合一：流量网关与微服务网关先合并，WAF 内置以引擎成熟度和压测结果为前提。
  2. 选 Higress 的前提是 1.0 GA、配置尽量落在 Ingress 与兼容注解上，并为 Gateway API 迁移留路。
  3. 网关只做通用的横切能力；聚合、编排等业务逻辑迁往 BFF 服务，MQTT 长连接与大文件上传不经过统一网关。
  4. 按域名组拆分多个数据面实例、共用控制面，控制单点故障的影响范围。

现状：一次请求穿过三层网关

车联网平台的南北向 HTTP 流量来自三类调用方：手机 App、第三方开放 API、内部运营系统。历史上每接入一类就建一套网关，形成了三层串联的结构：

flowchart LR
  C["客户端"] --> W["WAF<br/>独立集群"]
  W --> N["流量网关<br/>Nginx：TLS、域名路由"]
  N --> G1["微服务网关 A<br/>App 接入"]
  N --> G2["微服务网关 B<br/>开放 API"]
  N --> G3["微服务网关 C<br/>统一账号"]
  G1 --> S["Kubernetes 服务"]
  G2 --> S
  G3 --> S

这套结构的问题可以逐条量化：

  • 跳数与资源。 一次请求至少经过三个代理进程，每跳都有一次连接复用、头部解析与日志写入。三层网关各自按峰值预留容量，整体资源利用率低。
  • 配置分散。 一个新接口上线，要在 WAF 放行规则、Nginx 配置、Spring Cloud Gateway 路由三处分别变更，任何一处遗漏都会表现为难以定位的 403 或 404。
  • Nginx reload 伤害长连接。 配置变更触发 reload 后，旧 worker 要等存量连接关闭才退出；App 的长轮询与 WebSocket 连接会让多代 worker 并存，内存成倍上涨，频繁变更时尤为明显。
  • 鉴权重复实现。 三套微服务网关各有一份 Token 校验逻辑，版本不一，安全修复要改三遍。
  • 可观测断链。 WAF、Nginx、Java 网关的日志格式与追踪上下文各不相同，一次超时要在三处日志里人工对齐时间戳。

目标：两步走的三合一

目标架构是一层基于 Envoy 的统一网关，同时承担 WAF、流量网关与微服务网关的职责。但 WAF 内置并不是一个可以一步到位的决定，因此分两步：

阶段 形态 前提条件
二合一 WAF 保持独立；流量网关与三套微服务网关合并为统一网关 统一网关 GA 版本，完成压测与迁移演练
三合一 WAF 以插件形式内置到统一网关，独立 WAF 下线 WAF 引擎达到生产可用，开启规则集后的性能损耗可接受，误报率经过回放验证 
flowchart LR
  subgraph GW["统一网关数据面（Envoy）"]
    P1["WAF 插件<br/>三合一阶段启用"] --> P2["认证插件"] --> P3["限流"] --> P4["路由与灰度"]
  end
  C["客户端"] --> LB["云负载均衡<br/>四层"] --> P1
  CP["网关控制面<br/>监听 Ingress / 插件 / 服务来源"] -. xDS .-> P1
  P4 --> K["Kubernetes Service"]
  P4 --> NA["Nacos 注册的服务"]

有两类流量明确不进入统一网关：车辆的 MQTT 长连接由专用 Broker 集群承接（原因见第 00 篇）；车辆日志、录制片段等大文件上传，由业务接口签发对象存储的预签名地址，车端直传对象存储，避免大请求体占用网关缓冲与带宽。

选型

候选方案

2023 年 5 月可选的方案如下：

方案 数据面 配置生效方式 对接 Nacos 扩展方式 WAF 主要顾虑
Spring Cloud Gateway 3.1 / 4.0 JVM + Netty 配置中心动态刷新 原生 Java Filter 无 GC 带来的尾延迟；4.0 要求 Spring Boot 3 与 Java 17；不适合承担 TLS 与域名管理
Ingress NGINX / OpenResty Nginx 配置变更需 reload 无 Lua ModSecurity 模块（商业支持将于 2024 年 7 月终止） reload 影响长连接
Apache APISIX 3.x Nginx + Lua etcd 动态下发，无需 reload 支持 Lua、外部插件、Wasm 无内置 引入 etcd 运维与 Lua 技能栈
Istio Ingress Gateway 1.17 Envoy xDS 动态下发 需 ServiceEntry 转换 EnvoyFilter、Wasm 无内置 以 VirtualService 建模入口，对入口场景偏重
Envoy Gateway 0.4 Envoy Gateway API 无 功能面仍在快速迭代 无 仍处 0.x 早期
Higress 1.0.0-rc Envoy + Istio 控制面 xDS 动态下发 McpBridge 对接 Nacos、ZooKeeper Wasm 插件（C++、Go），可按全局、域名、路由生效 开源版暂无内置 2022 年 11 月才开源，GA 版尚未发布

为什么是 Higress，以及附带的条件

决定采用 Higress，理由集中在三点：

  1. 与服务网格路线同一数据面。 服务治理的远期方向是 Istio（第 01 篇），网关选 Envoy 系意味着 xDS、Envoy 指标与排障技能只需建设一套。
  2. 迁移成本最低。 它兼容大部分 Nginx Ingress 注解，包括完整的灰度注解；通过 McpBridge 直接发现 Nacos 中注册的服务，存量 Spring Cloud 服务无需改造就能挂到新网关后面。
  3. 变更不 reload。 路由、证书、插件配置都经 xDS 下发，长连接不受影响。

Envoy 为 C++ 实现、没有 GC 停顿，同等资源下吞吐与尾延迟通常优于 JVM 网关，但差距高度依赖插件链的长度，选型结论以自有流量模型的压测为准，不引用任何未经复现的倍数。

同时写明四个约束条件，任何一条不满足就回退到 APISIX 方案：

  • 以 1.0 GA 为生产上线前提。 当前是 2023 年 4 月发布的 1.0.0-rc，rc 只进入测试环境。
  • 配置尽量落在标准资源上。 路由使用 Kubernetes Ingress 与兼容注解，私有 CRD 只用于服务来源与插件。Gateway API 目前是 v0.6（Beta），Higress 尚未支持，但它是未来的标准，配置规范要按「能平移到 HTTPRoute」来设计。
  • 自研插件用 Go 编写并设性能预算。 每个插件在压测中单独度量 P99 增量，超过 1 ms 需要评审。
  • WAF 暂不内置。 开源版尚无 WAF 插件。可行路线是 Coraza：OWASP 旗下的 Go 实现，兼容 ModSecurity 规则语言与 OWASP CRS，并有面向 Envoy 的 Wasm 版本，v3 目前处于 RC 阶段。等它 GA，并在自有流量上完成误报与性能评估，再启动三合一。

关键配置

对接 Nacos 服务来源

路由到 Nacos 服务并按请求头灰度

网关层只做两种灰度：按请求头（内部测试人员、测试车辆的客户端配置携带灰度标记）与按权重。按 VIN 名单、车型、车端软件版本的大规模灰度，由服务层按标签路由完成（第 01 篇），网关只负责把标签透传下去。

插件按路由生效

这个插件适合开放 API 按调用方限流：调用方数量有限，可以逐个列出。它的计数在每个网关实例本地进行，集群总阈值要按实例数折算。按 VIN 这类百万级键的逐键限流不适合放在这里，仍由服务侧的热点参数限流承担。

认证与可观测：收敛之后才有的统一

三套网关合一，最大的收益不在省了几台机器，而在认证与可观测终于只有一份实现。

认证分两类调用方处理。 App 用户令牌采用 JWT，网关用缓存的公钥集本地验签，不逐请求调用认证服务；令牌有效期控制在 15 分钟，配合刷新令牌，主动吊销通过一份很小的吊销名单推送到插件。开放 API 采用 AppKey 加 HMAC 签名，签名覆盖方法、路径、时间戳与请求体摘要，时间戳偏差超过 5 分钟即拒绝，随机数在短期缓存中去重以防重放。

身份以内部请求头向下游传递。 验证通过后，网关写入 x-auth-user-id、x-auth-app-id 等内部头，下游服务只信任这些头。前提是网关在入口处先删除客户端自带的同名头，否则任何人都能伪造身份，这是收敛过程中最容易遗漏的一步。

访问日志统一字段。 所有域名使用同一份访问日志格式：追踪 ID、路由名、上游服务、上游耗时、总耗时、响应码，以及 Envoy 的响应标志（如上游连接失败、无健康上游、无匹配路由）。响应标志能直接区分「网关没找到路由」与「上游挂了」，是排查 5xx 最快的线索。网关作为链路起点生成 W3C Trace Context，并对接现有的 SkyWalking，使一次请求从入口到服务再到消息队列可以在一条链路里查到。

迁移路径

flowchart TB
  A["1. 并行部署统一网关<br/>导入现有 Ingress 资源"] --> B["2. 流量回放与对比<br/>状态码、响应头、延迟分布"]
  B --> C["3. 按域名切流<br/>1% → 10% → 50% → 100%"]
  C --> D["4. 迁移 Java 网关路由<br/>过滤器逐类改写"]
  D --> E["5. 旧网关保留 30 天<br/>作为回切目标后下线"]

Spring Cloud Gateway 上的自定义 Java Filter 是迁移中最费力的部分，按性质分三类处理：

过滤器类型 典型例子 去向
请求改写 路径重写、增删请求头、跨域 改为注解配置，零代码
认证鉴权 Token 校验、签名校验、调用方白名单 收敛为认证插件；需要查库的复杂鉴权收敛到独立认证服务，插件调用并缓存结果
业务逻辑 多接口聚合、按用户裁剪字段、协议转换 迁出网关，放到面向 App 的 BFF 服务

第三类是判断网关边界的试金石。网关一旦开始写业务聚合，就会变成所有团队都要改、谁也不敢改的单点。

容量与可用性

  • 容量规划方法。 以完整插件链压测单实例，得到稳定吞吐。例如 4 vCPU 实例在完整插件链下稳定承载 8,000 QPS（示例值，以实测为准），平台南北向峰值 3 万 QPS，按两倍冗余需要 8 个实例，再按可用区均衡部署，任一可用区故障时剩余容量仍能承接峰值。
  • 按域名组拆分数据面。 App、开放 API、内部运营三组域名各自一套网关数据面实例，共享同一控制面与插件仓库。Higress 1.0 支持只监听部分命名空间下的 Ingress，可以在同一集群内部署多套实例。开放 API 被刷时，不会拖垮 App 入口。
  • 控制面故障不影响数据面。 控制面不可用时，Envoy 按最后一次收到的配置继续转发，只是新变更无法生效。控制面按两副本部署，并对配置推送耗时设告警。
  • TLS 与证书。 TLS 在网关终结，证书由 cert-manager 统一签发与轮换；到上游服务的连接开启 keepalive，避免每请求建连。
  • 大规模路由的推送耗时。 路由达到数千条后，一次变更推送到所有实例的耗时需要纳入压测场景，而不只是测转发性能。

反例与风险

  • 在网关插件里写业务。 聚合、编排、字段裁剪写进网关，迁移与升级都会被业务逻辑绑架。
  • WAF 规则对车端请求一刀切。 车端的请求体多为 Protobuf 二进制，按通用规则检查会产生大量误报。三合一阶段要为车端路由单独配置规则集，或只检查请求头与 URL。
  • 所有域名共用一个数据面。 任何一个插件的缺陷或一次错误配置，都会让全部入口同时故障。
  • 插件失败策略未定义。 认证插件异常时是放行还是拒绝，要逐个插件明确：认证类失败即拒绝，观测类失败即放行。
  • 过度依赖私有扩展。 私有注解与 CRD 用得越多，日后迁移到标准 API 或其他实现的成本越高。
  • 早期项目的社区风险。 开源仅半年，版本迭代快、文档变动频繁。锁定版本、跟踪社区问题列表，并保持 APISIX 方案的可行性评估不过期。

2026 回看：三合一方向正确，配置契约应当更早押注 Gateway API

经受住时间的判断

  • Envoy 系统一网关与服务网格共用数据面，这一判断在之后几年被整个行业的走向印证。
  • 兼容 Nginx Ingress 注解的迁移策略，在 Ingress NGINX 于 2026 年 3 月退役时显出价值：入口早已迁离 Nginx，退役对平台没有影响。
  • 两步走的 WAF 策略。 事后看，Higress 在 2023 年 6 月加入了基于 Coraza 的 WAF 插件，Coraza v3 在 2023 年 5 月底 GA；ModSecurity 的商业支持在 2024 年 7 月终止，并于 2024 年 1 月起移交 OWASP 维护；OWASP CRS 4.0 在 2024 年 2 月发布。当年没有把三合一押在 ModSecurity 上，是对的。
  • BFF 逻辑迁出网关、大文件不经网关、按域名组拆分数据面，这些边界没有过时。

需要修正的判断

  • 配置契约。 Gateway API 在 2023 年 10 月发布 v1.0，Higress 在 2023 年 9 月的 1.2 版本支持 Gateway API，到 2026 年 6 月 Gateway API 已迭代到 v1.6。当年「用 Ingress 加注解、日后平移」的过渡期拖得越长，平移成本越高。今天会直接以 HTTPRoute 为路由契约，网关实现按一致性测试结果选择，私有扩展只放在插件里。
  • 网关承载的流量类型。 规划时只考虑业务 API。今天大模型调用已经成为南北向与出口流量的重要组成部分，它按 token 计费、响应以流式返回、单次耗时以秒计，限流、配额与路由逻辑都和普通 API 不同。

今天会怎么做

  • 业务 API 网关与 AI 网关分实例部署。 两者可以是同一产品，但数据面分开，避免模型调用的长耗时请求挤占业务入口的连接与内存。Higress 自 2024 年起转向 AI 网关方向，2.2.x 版本支持托管 MCP Server，并于 2026 年 3 月进入 CNCF Sandbox；Envoy AI Gateway 在 2026 年 6 月发布 v1.0；自建推理服务的入口可以采用 Gateway API Inference Extension（v1.0，2025 年 9 月），按模型与推理负载路由。
  • Java 网关只留在 BFF 场景。 Spring Cloud Gateway 5.0 于 2025 年 11 月随 Spring Boot 4 发布，对以 Java 为主、需要编写复杂聚合逻辑的 BFF 仍是合适的工具，但不再承担入口职责。
  • WAF 规则集按 CRS 4 管理，车端路由与 App 路由使用不同的规则集与误报白名单，规则变更走与代码相同的评审与回放流程。
