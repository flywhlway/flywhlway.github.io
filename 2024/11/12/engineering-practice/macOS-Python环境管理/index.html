macOS Python 环境管理：pyenv 与 uv 的分工与迁移

为什么不拿系统或 Homebrew 的 Python 开发；pyenv + venv、pyenv + uv、纯 uv 怎么选…

Flywhl 11 分钟 更新于 2026.09 #工程效率#Python#uv

先读结论

  1. 系统 Python 留给系统，Homebrew Python 留给 Homebrew 的其他软件，开发用自己能控制版本的解释器。
  2. 新机器、新项目直接用纯 uv；需要全局 python 命令或自定义编译时才保留 pyenv，且只让它管解释器。
  3. pyenv 与 uv 同时装了同一个版本时，uv 默认优先用自己下载的；想统一用 pyenv 编译的，设 python-preference = "only-system"。
  4. CI 用 uv sync --locked，锁文件过期会直接报错，而不是悄悄重新解析。

为什么不直接用系统 Python 或 Homebrew Python

macOS 上开箱就有两个 Python，都不适合拿来做开发。

来源 路径 问题
系统（Xcode Command Line Tools） /usr/bin/python3 版本由 Apple 决定，长期停在 3.9.6；它服务于系统和 Xcode 工具，往里装包会影响这些工具
Homebrew /opt/homebrew/bin/python3 它首先是其他 formula 的依赖，brew upgrade 可能把 python3 换到新的次版本，旧版本被清理后基于它建的虚拟环境就失效了；并且带 PEP 668 标记，直接 pip install 会被拒绝

后一条实测如下：

这个报错是有意为之：它在提醒你别往包管理器的 Python 里装东西。正确做法不是加 --break-system-packages，而是换一个自己能控制版本的解释器，再给每个项目建独立的虚拟环境。

所以要解决的问题有两层：解释器从哪来、怎么切换；项目依赖怎么隔离、怎么锁定。pyenv 只管第一层，uv 两层都能管。

三种方案怎么选

本文写作时点的版本：pyenv 2.4.17，uv 0.5.1（2024-11-08 发布），Python 3.13 已于 10 月 7 日发布。文中 uv 命令均用 0.5.1 实测，依赖解析加了 --exclude-newer 2024-11-12 以还原当时的结果。

维度 pyenv + venv/pip pyenv + uv 纯 uv
解释器来源 本机源码编译，需要编译依赖，每个版本几分钟 同左，或由 uv 下载 uv 下载预编译包（python-build-standalone），解压即用
终端里的 python pyenv shims 按目录切换 同左 无全局 python；项目内用 uv run python
虚拟环境 手动 python -m venv，或 pyenv-virtualenv uv 自动在项目下建 .venv 同左
依赖锁定 需另装 pip-tools 等 uv.lock，跨平台 同左
全局命令行工具 pipx uv tool uv tool
适合 暂不引入新工具的老项目 已习惯 pyenv、需要全局 python、需要自定义编译参数 新机器、新项目、CI

决策顺序：

  1. 新机器或新项目，没有历史包袱：纯 uv。
  2. 需要在任意目录敲 python 就得到指定版本（比如很多脚本写死了 #!/usr/bin/env python），或需要带特殊编译参数的解释器：pyenv + uv，pyenv 只管解释器，项目全部交给 uv。
  3. 团队 CI、文档都还围着 pip 和 requirements.txt 转，暂时动不了：pyenv + venv/pip，并按后文的迁移步骤逐个项目切换。

不再推荐 pyenv-virtualenv：它的 virtualenv-init 会在每次出现提示符时执行一次钩子，命名环境和项目目录的对应关系也只存在于本机；uv 在项目内建 .venv，环境和代码天然绑定。

总结

两层问题分开处理。解释器层：纯 uv 最省事，需要全局 python 命令或自定义编译时保留 pyenv，并用 python-preference 明确解释器来源，别让两边各装一份还互相覆盖。项目层：统一交给 uv，pyproject.toml 加 uv.lock 入库，本地 uv run，CI uv sync --locked。系统 Python 和 Homebrew Python 都不碰。

2026-09 补记：uv 的后续变化与 pyenv 是否还需要

本文写于 uv 0.5.1 时期。此后与本文相关的变化（据 uv 官方变更日志）：

版本与日期 变化 对本文的影响
0.6.0（2025-02-14） uv init 生成的示例文件由 hello.py 改为 main.py 迁移步骤里要删的文件名随之变化
0.8.0（2025-07-17） uv python install 默认把带版本号的可执行文件（如 python3.13）装进 ~/.local/bin；不带版本号的 python、python3 仍需实验性的 --default 选项 纯 uv 方案在终端里也能直接敲 python3.13 了；若 ~/.local/bin 排在 pyenv shims 前面，会遮蔽 pyenv 的同名命令，本文的 PATH 顺序正好避免了这一点
0.9.0（2025-10-07） 默认 Python 版本由 3.13 改为 3.14；同日 Python 3.14 正式发布 未固定版本、机器上又没有任何解释器时，会装 3.14。项目里有 .python-version 的不受影响
0.10.0（2026-02-05） uv python upgrade、uv python install --upgrade 转为稳定；安装新补丁版本后，虚拟环境会透明升级到该补丁版本（不跨次版本）；uv venv 覆盖已有环境需要显式加 --clear 常见问题表里”重建环境”的命令要加 --clear
0.12.0（2026-07-28） uv init 默认生成带构建系统的打包布局（代码在 src/<项目名>，带 [project.scripts] 入口）；要旧的非打包布局用 uv init --no-package 新建项目的文件清单与本文不同；应用型项目想保持扁平结构时加 --no-package

关于”还需不需要 pyenv”：到 2026 年 9 月，解释器的安装、按次版本放进 PATH、补丁版本升级，uv 都已经是稳定功能。pyenv 剩下的理由只有三个：需要不带版本号的全局 python 命令且不想用实验性的 --default；需要自定义编译参数的解释器；有依赖 pyenv shims 的现存脚本或工具。都不涉及的话，新机器可以只装 uv。
