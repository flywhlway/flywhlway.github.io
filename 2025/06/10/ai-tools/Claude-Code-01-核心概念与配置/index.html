Claude Code 核心概念与基础配置

基于 Claude Code 1.0.18 梳理其 agent 循环、安装认证、CLAUDE.md 记忆、settings 层级、权限规则与模式、自定义命令、非交互模式与成本控制…

Flywhl 21 分钟 更新于 2026.09 #AI工具#开发效率#Claude Code

先读结论

  1. Claude Code 是「模型决定调用什么工具、本地客户端负责执行与把关」的循环，配置工作本质上是在管上下文、权限、扩展三个面。
  2. CLAUDE.md 写可执行的命令、约束和坑，按项目 / 用户 / 导入分层；个人内容用 @~/ 导入，不进仓库。
  3. 权限规则 deny 优先于 allow，Bash 前缀规则按字符串前缀匹配；deny 清单是护栏不是沙箱。
  4. 团队共享的规则进 .claude/settings.json，模型选择和个人放行放 settings.local.json 或用户级配置。
  5. 用 -p 写脚本时解析 JSON 输出的 subtype，达到 --max-turns 上限时进程退出码仍是 0。

Claude Code 于 2025 年 2 月 24 日以研究预览形式发布，5 月 22 日随 Claude Opus 4 / Sonnet 4 正式 GA（1.0.0）。本文以 6 月 9 日发布的 1.0.18 为准，命令、配置键和行为都对照了当时的官方文档与安装包实际代码；个别文档与代码不一致的地方会单独指出。

它是什么：跑在终端里的工具调用循环

Claude Code 不是补全插件，而是一个 agentic coding 工具：你在终端里用自然语言描述任务，模型决定要读哪些文件、改哪几行、跑什么命令，由本地的 Claude Code 进程实际执行，再把结果交回模型，直到模型认为任务完成。

flowchart LR
    U["用户输入或 -p 提示"] --> C["组装上下文<br/>系统提示 + CLAUDE.md + 对话历史"]
    C --> M["模型推理"]
    M -->|"请求调用工具"| P{"权限检查<br/>deny 规则 → allow 规则 / 当前模式 → 询问用户"}
    P -->|"放行"| T["本地执行工具<br/>Read / Edit / Bash / MCP"]
    P -->|"拒绝"| M
    T -->|"结果回填"| M
    M -->|"不再调用工具"| R["输出最终回答"]

这张图决定了后面所有配置的意义：

  • 上下文面：模型每一轮能看到什么。CLAUDE.md、对话历史、它读过的文件都在这里，窗口满了要压缩。
  • 权限面：模型想做的事，哪些直接放行、哪些要问人、哪些一律拒绝。由 settings.json 的规则和当前权限模式决定。
  • 扩展面：模型能调用哪些工具。内置工具之外，还有自定义斜杠命令（复用提示词）和 MCP 服务器（接入外部系统，见本系列第 2 篇）。

1.0.18 的内置工具按是否需要授权分两类，这也是权限规则的作用对象：

类别 工具 默认是否询问
只读 Read、LS、Glob、Grep、NotebookRead、TodoRead / TodoWrite、Task（子任务，文档表格中列为 Agent） 不询问
执行命令 Bash 询问；选「不再询问」后对该项目目录与该命令永久生效
修改文件 Edit、MultiEdit、Write、NotebookEdit 询问；选「不再询问」后仅本次会话有效
网络 WebFetch、WebSearch 询问

两个推论：一是只读工具默认不拦，模型读到的任何文件内容都会作为上下文发往模型 API，敏感文件要靠 deny 规则挡；二是修改类授权只在会话内有效，而 Bash 授权会写进项目配置长期生效，点「不再询问」前要想清楚这条命令的前缀会覆盖哪些变体。

安装与认证

安装

1.0.18 的安装方式只有一种：npm 全局包。

几个容易踩的点：

  • 不要用 sudo npm install -g。Claude Code 会自动更新，全局目录需要当前用户可写。遇到权限错误，官方推荐的做法是把 npm 前缀改到用户目录（npm config set prefix ~/.npm-global 并把 ~/.npm-global/bin 加入 PATH）后重装；也可以运行 claude migrate-installer，把全局安装迁移为 ~/.claude/local 下的本地安装，从此不再依赖全局 npm 目录的写权限。
  • WSL 里用错了 Windows 版 Node：which node 指向 /mnt/c/... 时会报 exec: node: not found 或平台检测错误，应在 Linux 发行版内用包管理器或 nvm 装 Node。
  • 自动更新异常：claude doctor 检查自动更新器状态，claude update 手动升级；实在不想自动更新可设 DISABLE_AUTOUPDATER=1。

认证方式怎么选

首次运行 claude 会引导登录，之后可以用 /login 切换账号、/status 查看当前账号与系统状态。

方式 计费 适合 注意
Anthropic Console（OAuth） 按 token 计费，需在 Console 开通付费 需要精确核算、设置工作区消费上限的团队 管理员可在 Console 批量邀请成员，「Claude Code」角色只能创建 Claude Code 用的 API Key
Claude Max 订阅 包月，含 Claude Code 用量 个人重度使用 默认模型策略是先用 Opus 4、达到一定用量比例后切 Sonnet 4
Claude Pro 订阅 包月 个人轻度使用 自 1.0.11（6 月 4 日）起可用，/model 里只有 Sonnet 4
Amazon Bedrock / Google Vertex AI 走云厂商账单 已有云上合规与采购流程的企业 通过 CLAUDE_CODE_USE_BEDROCK=1 或 CLAUDE_CODE_USE_VERTEX=1 及对应云凭据启用

脚本或 SDK 场景常用环境变量 ANTHROPIC_API_KEY；需要短期凭据时用 settings 里的 apiKeyHelper 指向一个输出 Key 的脚本，默认每 5 分钟或遇到 HTTP 401 时重新调用，可用 CLAUDE_CODE_API_KEY_HELPER_TTL_MS 调整间隔。macOS 上 Claude Code 把凭据存在系统钥匙串里。

记忆体系：CLAUDE.md

CLAUDE.md 是启动时自动载入上下文的 Markdown 文件，用来告诉模型「这个项目怎么干活」。它每次会话都占用上下文，写什么、放哪一层都值得推敲。

三个位置与查找规则

类型 位置 用途
项目记忆 ./CLAUDE.md 团队共享：架构、命令、规范，提交进仓库
用户记忆 ~/.claude/CLAUDE.md 个人跨项目偏好
项目本地记忆 ./CLAUDE.local.md 个人的项目内偏好；当前文档已标为弃用，建议改用导入

查找规则有两条：

  1. 向上递归：从当前工作目录开始，一路向上读取每一级的 CLAUDE.md 和 CLAUDE.local.md。在 monorepo 的 packages/api/ 下启动，根目录和 packages/api/ 的 CLAUDE.md 都会被加载。
  2. 子目录按需：工作目录之下子目录里的 CLAUDE.md 不会在启动时加载，而是在模型读取该子目录的文件时才纳入。

因此 monorepo 的合理布局是：根目录放全局约定和通用命令，各子包放自己的构建与测试说明，从哪一层启动就自然得到对应的组合。

@ 导入

CLAUDE.md 可以用 @路径 导入其他文件，相对路径和绝对路径都可以：

规则与边界：

  • 导入可递归，最多 5 层；/memory 可以查看当前实际加载了哪些记忆文件。
  • 行内代码和代码块里的 @ 不会被当作导入，所以写 @anthropic-ai/claude-code 这类包名要放进反引号。
  • 官方弃用 CLAUDE.local.md 的理由是它在多个 git worktree 之间不共享；把个人内容放在家目录，再从项目 CLAUDE.md 里导入，每个 worktree 都能用到。代价是项目 CLAUDE.md 里会出现一行指向个人文件的导入，团队需要约定统一的文件名。
  • 导入的内容和 CLAUDE.md 本体一样全量进入上下文。把一份 3000 行的设计文档挂在导入里，等于每次会话都为它付费；长文档更适合写一句「设计细节见 docs/design.md」，让模型需要时自己读。

写入方式

  • /init：让 Claude 分析仓库并生成一份 CLAUDE.md 初稿。它能提取出构建命令和目录结构，但写不出团队踩过的坑，生成后要人工删改再提交。
  • # 快捷写入：输入以 # 开头，例如 # 测试统一用 vitest，不要引入 jest，Claude Code 会询问写进哪个记忆文件。适合在纠正模型时顺手沉淀。
  • /memory：用系统编辑器打开记忆文件，适合整理结构。

该写什么、不该写什么

适合写进 CLAUDE.md 不适合
精确的命令：怎么跑单个测试、怎么做类型检查 「保持代码整洁」这类没有判断标准的口号
仓库特有的约束：哪些目录不能改、迁移文件怎么建 lint / formatter 已能自动保证的格式细节
已知的坑：某个测试依赖本地服务、某个脚本很慢 整本架构文档（改成按需阅读的指引）
压缩时要保留什么（见下文 Summary instructions） 密钥、内网地址、个人账号

官方给的写法建议很实用：具体（「用 2 空格缩进」胜过「格式要规范」），每条一个列表项，按主题用标题分组，并随项目演进定期修订。

settings.json：层级与优先级

文件位置

层级 路径 是否入库 典型内容
用户 ~/.claude/settings.json 否 个人通用的权限放行、环境变量
项目共享 .claude/settings.json 是 团队统一的权限规则
项目本地 .claude/settings.local.json 否（创建时 Claude Code 自动配置 git 忽略） 个人在该项目的放行、模型选择
企业托管 macOS：/Library/Application Support/ClaudeCode/managed-settings.json；Linux / WSL：/etc/claude-code/managed-settings.json 由管理员下发 不可被覆盖的安全策略

企业托管文件名需要特别注意：当前官方文档写的是 policies.json，而 1.0.18 代码实际读取的是 managed-settings.json。部署后用 /permissions 查看规则列表，该界面会标注每条规则来自哪个文件，据此确认策略已生效。

优先级

从高到低：企业托管策略 > 命令行参数 > 项目本地 > 项目共享 > 用户。企业策略用于兜底，任何层级都不能放宽它；命令行参数（如 --allowedTools）适合一次性覆盖；项目本地高于项目共享，个人可以在自己机器上补充团队配置。

1.0.18 支持的配置键

键 作用 建议放在
permissions allow / deny 两个规则数组 共享规则放项目层，个人放行放本地层
env 每次会话注入的环境变量 与项目强相关的放项目层
model 默认模型（别名如 sonnet、opus，或完整模型名） 本地或用户层；订阅类型决定可用模型，不宜统一
includeCoAuthoredBy 提交与 PR 是否附带 Claude 署名，默认 true 项目层，统一团队提交规范
apiKeyHelper 动态生成凭据的脚本 用户层或企业层
cleanupPeriodDays 本地对话记录保留天数，默认 30 用户层或企业层
enableAllProjectMcpServers、enabledMcpjsonServers、disabledMcpjsonServers 项目 .mcp.json 中 MCP 服务器的审批结果 本地层（第 2 篇展开）

主题、通知方式、详细输出等界面偏好还在旧的全局配置里，通过 claude config set -g <key> <value> 修改（如 theme、preferredNotifChannel、verbose）。官方已声明 claude config 会逐步让位于 settings.json，新配置优先写进 settings 文件。

权限：规则语法与模式

规则语法

规则格式为 Tool(可选说明符)，只写工具名表示匹配该工具的全部调用。deny 优先于 allow，同一操作同时命中两边时按拒绝处理。

Bash

  • Bash(npm run build)：精确匹配这条命令。
  • Bash(npm run test:*)：匹配以 npm run test 开头的命令。
  • 规则能识别 && 等 shell 操作符，Bash(safe-cmd:*) 不会顺带放行 safe-cmd && other-cmd。

1.0.18 的前缀匹配实现就是字符串 startsWith：Bash(npm run test:*) 同样会放行 npm run test-reset-db。要么让危险脚本的名字与放行前缀区分开，要么对这类脚本改用精确规则。

Read 与 Edit

  • 遵循 gitignore 语法，相对路径以 .claude/settings.json 所在的项目目录为基准；// 开头表示绝对路径，~/ 开头表示家目录。
  • Edit(docs/**)：允许或禁止修改 docs 目录；Read(~/.zshrc)：匹配读取家目录下的 .zshrc；Edit(//tmp/scratch.txt)：匹配绝对路径。
  • Edit 规则作用于所有内置改文件工具（Edit、MultiEdit、Write 等）；Read 规则会尽力套用到 Grep、Glob、LS 这类读取工具，但官方措辞是 best-effort。

其他

  • WebFetch(domain:example.com)：按域名匹配抓取请求。
  • mcp__github：匹配 github 这个 MCP 服务器的全部工具；mcp__github__create_issue：只匹配单个工具。服务器名是你在 Claude Code 里配置时起的名字。

deny 清单不是沙箱

Read(.env) 能拦住 Read 工具，却拦不住模型发起 cat .env 或 python -c "print(open('.env').read())"；Bash(curl:*) 放在 deny 里，wget 和各种脚本语言照样能发请求。deny 规则的价值在于挡住「顺手」的误操作，真正的防线是：未放行的 Bash 命令默认要人确认。所以团队配置的思路是「allow 尽量窄、deny 挡明显的坑、其余交给人审」，而不是试图用 deny 穷举危险命令。

权限模式

交互会话里按 Shift+Tab 在三种模式间循环，状态栏会显示当前模式：

模式 行为 适用场景
默认 按规则放行，其余逐次询问 日常开发、陌生仓库
auto-accept edits 文件修改自动接受，Bash 仍按规则询问 已经对齐方案、改动集中在代码文件时
plan mode 只分析与规划，不改文件、不执行命令 动手前先让模型出方案，评审后再切回执行

第四种是 bypassPermissions，通过 claude --dangerously-skip-permissions 启用，跳过全部权限检查。官方只建议在隔离环境中使用，并提供了一套 devcontainer 参考实现：容器内用防火墙把出站流量限制在 npm registry、GitHub、Anthropic API 等白名单域名，其余一律拒绝。在自己的开发机上直接开 bypass，等于把 Bash 的最终决定权交给模型。

1.0.18 的 settings 里还没有「默认启动模式」这个配置项，每次会话从默认模式开始。非交互场景的权限用 --allowedTools / --disallowedTools 控制，见后文。

/permissions 可以随时查看和增删规则，以及每条规则来自哪个文件。

自定义斜杠命令

把常用提示词存成 Markdown 文件，就能像内置命令一样调用。

类型 位置 调用方式（1.0.18）
项目命令 .claude/commands/*.md /project:文件名
个人命令 ~/.claude/commands/*.md /user:文件名
子目录命名空间 .claude/commands/frontend/component.md /project:frontend:component

一个修复 issue 的项目命令：

调用：/project:fix-issue 123。

这一版命令文件的实现细节决定了几条写法约束：

  • 没有 frontmatter。文件内容原样作为用户消息发出，菜单里显示的描述取自第一个非空行（去掉开头的 #），超过 100 字符截断。所以第一行应当写成一句能说明用途的标题。
  • $ARGUMENTS 只替换第一处。实现用的是字符串 replace，同一个文件里写两次 $ARGUMENTS，第二处会原样保留。需要多次引用参数时，在第一处引出后用「上述 issue」之类的指代。
  • 没写 $ARGUMENTS 时，参数会以 ARGUMENTS: <参数> 的形式追加在提示词末尾。
  • 命令不自带权限。命令里要求执行的 Bash 仍然走当前会话的权限规则，命令文件本身不能预先放行工具。

命令和 CLAUDE.md 的分工可以按触发频率来判断：每次会话都该遵守的约束放 CLAUDE.md；只在特定任务时才需要的流程（修 issue、写迁移、做发布检查）做成命令，避免常驻上下文。

非交互模式与会话管理

-p 与输出格式

常用参数：

参数 作用
--output-format text / json / stream-json 输出格式，脚本里用 json
--max-turns N 限制 agent 轮数，防止跑飞
--allowedTools / --disallowedTools 本次运行额外放行或禁止的工具规则，如 "Bash(git diff:*)"
--model 指定模型别名或全名
--add-dir 追加可访问的工作目录（1.0.18 新增）
--verbose 输出完整的逐轮过程，排查问题用
--permission-prompt-tool 指定一个 MCP 工具在非交互模式下裁决权限请求

-p 模式下没有人可以点确认，未被规则放行、又需要授权的操作会被拒绝，除非用 --permission-prompt-tool 交给 MCP 工具裁决。脚本要能跑通，就必须把所需工具显式列进 --allowedTools 或项目 settings。

JSON 结果与退出码

1.0.18 的 json 输出是一个 type: "result" 对象，关键字段有 subtype、result、session_id、is_error、num_turns、duration_ms，以及费用字段。subtype 有三个取值：success、error_max_turns、error_during_execution。

继续与恢复会话

  • claude -c（--continue）：继续当前目录最近一次对话；claude -c -p "再检查一遍类型错误" 可以在非交互模式下接着跑。
  • claude -r <session-id> "问题"（--resume）：按 ID 恢复指定会话；不带 ID 时进入交互式选择。上面脚本保存的 session_id 就可以用来追问：claude -r "$(cat .claude-review-session)" -p "针对第 2 条给出修复补丁"。

上下文与成本管理

上下文

  • 默认开启自动压缩，上下文用到约 95% 时触发，输入框下方会显示「Context left until auto-compact」的剩余比例；可在 /config 里关闭。
  • /compact [指令] 手动压缩，可附带保留重点，如 /compact 保留测试失败输出和已修改的文件列表。也可以在 CLAUDE.md 里写一段 # Summary instructions，让每次压缩都遵循同样的取舍。
  • /clear 清空对话历史。换任务时优先 /clear，而不是在一段长对话里连续切换主题：旧任务的文件内容和中间结论会持续占位，还可能误导新任务。

模型选择

/model 交互切换，--model 按次指定，settings 的 model 或环境变量 ANTHROPIC_MODEL 设置默认值。1.0.18 的选项随账号类型不同：

账号 可选 说明
Console（API） 默认（Sonnet 4）、Opus 4 界面标注的价格：Sonnet 4 每百万 token 输入 / 输出 $3 / $15，Opus 4 为 $15 / $75
Max 订阅 默认、Opus、Sonnet 默认策略为 Opus 4 用到一定用量比例后切换 Sonnet 4；固定选 Opus 会约 5 倍速度消耗用量额度
Pro 订阅 Sonnet 只有 Sonnet 4

提示词里的思考关键词会触发扩展思考，1.0.18 的代码里分三档预算：think 为 4000 token，think hard、think deeply 等为 10000 token，think harder、ultrathink 等为 31999 token。思考 token 按输出计费，适合用在方案设计和疑难排查上，不必挂在每条指令里。

成本

  • /cost 显示本次会话的 token 用量与费用；订阅用户执行时只会提示用量已包含在订阅内。
  • 官方给出的参考数据：开发者平均每人每天约 $6，90% 的用户日均低于 $12。
  • 即使空闲，也有少量后台调用（输入时的趣味提示语生成、为 --resume 生成的历史会话摘要等），官方估计通常每个会话低于 $0.04；DISABLE_NON_ESSENTIAL_MODEL_CALLS=1 可关闭非关键路径的模型调用。
现象 优先动作
回答开始遗忘早先约定 /compact 并在指令里点名要保留的约定，或把约定写进 CLAUDE.md
同一会话已换过多个任务 /clear 后重新描述当前任务
模型反复全仓搜索 在提示词里给出入口文件或目录，减少探索性读取
API 账单超预期 先看 /cost 与 Console 用量，再检查 CLAUDE.md 与导入的体积、是否滥用 Opus 与 ultrathink

CLAUDE.md 片段

.claude/settings.json

逐项说明：

  • allow 只放验证类命令。测试、类型检查、lint、只读 git 命令是模型最频繁、风险最低的操作，放行后能省掉大半确认；npm install、git commit 这类改变状态的命令仍然逐次确认。npm run test:* 用前缀规则，是为了覆盖 npm run test -- 某个文件；相应地，package.json 里不要出现以 test 开头的破坏性脚本。
  • deny 挡三类坑。.env 系列防止密钥被读进上下文（gitignore 语法下不带 / 的模式在任意层级都生效）；migrations/** 把 CLAUDE.md 里「已合并迁移不可改」的约束变成硬规则，新增迁移仍通过 npm run db:new 走 Bash 确认；git push、npm publish 这类对外产生影响的操作一律由人执行。
  • 禁止改权限文件本身。否则在 auto-accept edits 模式下，模型对 settings 文件的修改无需确认，相当于可以给自己扩权。
  • BASH_DEFAULT_TIMEOUT_MS。Bash 工具默认超时 2 分钟，全量测试会被中途杀掉，模型可能误判为测试失败；调到 5 分钟（不超过默认 10 分钟的上限 BASH_MAX_TIMEOUT_MS）。
  • 显式写出 includeCoAuthoredBy。默认值就是 true，写出来是为了让团队对提交署名有明确约定，想关掉时只改这一处。
  • 没有写 model。成员的订阅类型不同，Pro 用户根本选不了 Opus，模型放在各自的 .claude/settings.local.json 或用户级配置里。

2026-09 补记：一年后哪些建议需要调整

本文写于 1.0.18，一年多来 Claude Code 迭代到 2.1.x，下表只列与本文内容直接相关的变化。

另外几处细节也有变化：

  • 权限模式：除 auto 外，当前还有 dontAsk 模式，凡是需要询问的操作一律拒绝，只执行预先放行的工具，适合无人值守脚本；permissions.disableAutoMode 可以在托管策略里禁用 auto 模式。
  • Bash 规则写法：当前文档把 Bash(npm run test *) 这种空格加 * 的写法作为主写法，确认对话框「不再询问」时写入的也是这种形式；:* 后缀仍然等价可用。
  • CLAUDE.local.md：当前文档已不再标注弃用，它与 CLAUDE.md 一样逐级加载，适合放不入库的个人项目偏好；跨 worktree 共享仍然推荐从家目录导入。
  • 企业托管：managed-settings.json 之外，还可以通过 MDM 或 claude.ai 控制台下发的服务端托管设置分发策略。

回头看，本文最需要修正的是三处：安装方式改为原生安装；团队配置里的署名项改用 attribution，并按需加上 defaultMode；超过百行的 CLAUDE.md 拆到 .claude/rules/。上下文、权限、扩展三个面的划分，以及「allow 窄、deny 挡坑、其余人审」的权限思路，到现在仍然适用。
