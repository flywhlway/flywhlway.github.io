04 · engineering:* 模式：命名空间、插件与千级技能的组织结构

企业级 Skill Registry 平台工程手册 · 第 04 篇
前置阅读：01 篇 §8（两级路由）、02 篇 §5.6（priority 仲裁）
本篇回答：engineering:architecture 这类带前缀的技能名背后是什么组织模式，为什么它是千级技能治理的正确原语，以及依赖/继承/组合在技能体系里的正确实现方式。

1. 概述：从技能到技能族

单个技能解决”一件事怎么做”；平台真正要管理的是技能族（skill family）——一组同属一个能力域、共享 owner、共享发布节奏、共享参考资料的技能。观察 engineering:architecture、engineering:code-review、engineering:debug……这组技能，能提炼出四个结构事实：

  1. 名字携带两段语义：<namespace>:<skill>，冒号左边是族，右边是族内成员；
  2. 它们作为一个插件（plugin）整体安装/卸载——分发单元是族不是个体；
  3. 族内成员的 description 呈现互斥切分：debug 管”报错栈/行为异常”，incident-response 管”生产事故流程”，边界清晰无重叠——这是同一 owner 统一设计的痕迹；
  4. 族的粒度对齐一个工作流域（工程师日常），不对齐技术栈。

这四条就是企业平台该抄的作业。本篇把它展开成完整的组织模型。

2.1 命名文法

2.2 namespace 承载的四重绑定

namespace 不只是名字前缀，它是四个平台机制的共同锚点：

这个”一锚四绑”是本篇最重要的设计：它让组织结构（Conway）、分发结构、路由结构、权限结构四者天然对齐，避免四套各自为政的分组体系互相打架——那是千级技能平台的头号内耗来源。

代价也要说清：四绑意味着 namespace 的拆分/合并是平台级重量操作（等于同时做组织变更+发布迁移+路由重划+权限迁移）。所以 namespace 的初始划分要按”两年内稳定的能力域”设计，宁粗勿细——族内技能多可以再拆，族本身频繁重组是灾难。

3. Plugin：分发与治理单元

3.1 plugin manifest

一个 plugin 是 namespace 在某一时刻的内容快照 + 元数据信封：

关键字段说明：

  • skills[].version 独立于 plugin.version：技能各自 SemVer 演进，plugin 版本表达”经过集成验证的组合”。这解决单体版本的最大痛点——族内一个技能打补丁不应逼迫全族升大版本；但用户安装的永远是 plugin 版本，保证族内组合是被测试过的（技能间边界互斥性是组合级属性，单测不出来）。
  • shared_resources：族内多技能共享的 reference 上提到 plugin 级，单份分发、单点更新。这是”技能间复用”的第一正解（§5 展开为什么不是继承）。
  • routing_card：plugin 自带 L0 域卡片的 description——两级路由的域描述由族 owner 维护，而不是平台侧手工汇总。域卡片同样进 02 篇的触发评测闭环。

订阅粒度 = plugin 是刻意的治理选择：允许租户按单技能挑选，会产生族内组合爆炸（code-review 装了而 debug 没装，二者 description 的互相让渡边界失效），组合级质量保证随之瓦解。租户级的细粒度需求用技能级禁用列表满足（减法），而不是技能级订阅（加法）——默认完整族，例外显式声明。

4. namespace 与两级路由的同构映射

01 篇方案 C 的 L0 域卡片从哪来？答案已经在 §3.1：plugin 的 routing_card 就是域卡片。同构映射带来三个免费收益：

  1. 路由表的维护责任自动归位：域描述写不好 → 该域全族触发率下降 → 指标打到族 owner 头上，无需平台仲裁”这段描述谁负责改”。
  2. 域内 L1 列表 = plugin 的 skills 列表，无需第二套目录。
  3. 域粒度天然合理：plugin 粒度按”工作流域”设计（§1 事实 4），恰好是路由域的正确粒度——反过来说，如果某个 plugin 的 routing_card 写不出一段内聚的域描述，那是 namespace 划分错误的最早期信号，比任何评审都灵敏。

例外处理：跨域技能（如 vehicle-data-compliance 既属产业物联网又属合规）不做多域挂载——多挂载 = 路由层的重叠病。归属主域（compliance），在相邻域的 routing_card 里加一句让渡（”涉及车辆数据合规时切到 compliance 域”），与 02 篇技能级负面边界的成对维护完全同构，只是上升了一层。

5. 依赖、继承与组合

5.1 为什么技能体系不该有继承

面向对象直觉会想要 vehicle-diag-base 基类技能 + 子技能 override。这在技能体系里是错的，原因在运行时模型：

  • 技能的”执行体”是模型的推理，不是类实例。所谓继承只能实现为”激活子技能时把父技能正文也注入”——即隐式双倍 L2 成本 + 两份指令的优先级歧义（子技能说 A 父技能说 B，模型听谁的没有语言级 override 语义）。
  • 继承层级使 01 篇状态机的观测失真：激活事件属于子还是父？触发率算谁的？
  • 版本演进灾难：父技能升版 = 所有子技能行为隐式变更，且组合从未被逐一测试。

5.2 三种正确的复用原语

原语 机制 适用 成本
共享 reference plugin 级 shared_resources，各技能 SKILL.md 各自引用 领域资料复用（码表、模板、SOP） 零上下文额外成本（按需 L3）
显式依赖声明 manifest requires.skills，Runtime 保证共同可见（同会话 L1 同时注入） 技能 A 的流程中某步”移交”给技能 B（03 篇 A↔B 互相让渡即最小案例） 依赖闭包进入订阅解析，需环检测
编排型 meta-skill 一个技能的正文就是”按序激活并串联多个原子技能”的工作流指令 固定多阶段流程（如”新服务上线” = system-design → threat-modeling → deploy-checklist） meta-skill 自身占一个 L1/L2；被编排技能保持原子性不受污染

依赖声明的解析语义要钉死：依赖保证的是可见性（L1 共同在场），不是激活（不预载对方 L2）。移交发生时由模型按对方 description 正常激活——依赖机制不绕过渐进式披露。

环检测规则：依赖图必须是 DAG；conflicts_with（02 篇）与 requires 互斥——又依赖又冲突是元数据自相矛盾，注册 lint 阻断。

5.3 组合的反模式：胶水技能

把”先跑 A 再跑 B”写成新技能但不加任何领域价值——这类胶水 meta-skill 会指数繁殖（N 个原子技能有 2^N 个组合）。准入判据：meta-skill 必须携带原子技能都不拥有的知识（阶段间的裁决逻辑、跨阶段的数据传递约定、整体的验收标准），纯顺序调用不准注册——那是一句话就能对模型说清的事，不需要技能。

6. Capability Metadata：能力声明与运行时准入

族级组织后，capability 声明的作用从”文档”升级为”准入判定输入”：

Runtime 在 Discovery 阶段的可见性过滤（01 篇 §3.1）据此增加第四重：租户 ∩ 角色 ∩ surface ∩ capability 可满足。一个 required_tools: ["bash"] 的技能在无沙箱的 surface 上直接不注入 L1——比”注入了但激活后发现工具缺失”提前两个阶段失败，且不浪费预算。data_access 声明则是 11 篇数据权限审计的静态输入：技能声明的访问面与其脚本实际行为的偏差检测（声明 read 却尝试写）是供应链防线之一。

7. 权限模型：namespace 级继承 + 技能级收紧

两条硬规则：

  1. 只收紧不放宽：技能级不允许出现”本技能对 namespace 未授权的租户额外开放”——那会使权限审计从”看族”退化为”逐技能遍历”，千级规模下不可审计。需要更宽授权的技能说明它放错了族。
  2. activation_approval 挂在 L2 读取点（01 篇附录 B 的 onSkillRead 二次鉴权）：高危技能”可发现、激活需批”——模型知道能力存在并能向用户解释审批流程，但正文在批准前不可读。这比”直接不可见”的用户体验好一个量级（用户至少知道该找谁）。

compliance:* 这类强制族走相反的特例通道：规则白名单强制注入（02 篇 §5.5 主拓扑的第一路），租户不可禁用——这是唯一允许”平台推翻租户减法”的族类型，且此类族的注册需要平台级（而非族 owner 级）审批。

8. 千级技能的组织结构

8.1 Taxonomy：两维设计

标签绝不参与路由——用标签做第二套分组去影响触发是最常见的架构污染（”给所有 beta 技能降 priority”之类）。生命周期只过滤可见集，进了可见集之后路由一律凭 description。

8.2 千级规模的度量画像

一个健康的 1,500 技能平台大致呈现：

指标 健康区间 恶化信号
namespace 数 40~80 >150：族粒度过细，四绑机制的管理开销超过收益
单族技能数 P90 ≤25 巨族出现 = 该域 owner 团队本身需要拆分（Conway 反向成立）
跨族 requires 边数 / 技能数 <0.3 依赖稠密化 = 域切分与真实工作流错位
L0 域卡片总 token <4k 超限说明族数失控，回到第一行
90 天零激活技能占比 <15% 僵尸技能堆积，触发 §8.3 退役流程

8.3 仓库形态对比

形态 优 劣 适用
Monorepo（全平台一仓） 跨族重构原子化；lint/评测基建单份 权限粒度粗；发版队列争用；与”族=团队”的自治矛盾 <200 技能的早期
Polyrepo（一族一仓） 与 ownership 完全对齐；发版独立 共享基建漂移（每仓一套 CI 各自腐化）；跨族改动难 族自治文化强的组织
Registry-native（推荐） 仓库形态不做平台约定：族自选 repo，Registry 只认签名的 plugin 产物；平台以强制流水线模板（复用 lint/评测/签名步骤）替代仓库统一 需要建设发布流水线产品化能力 千级规模的目标态

Registry-native 的本质：把一致性约束从”源码组织”移到”产物契约”——这与容器生态从”统一构建脚本”演进到”OCI 镜像标准”是同一条路径，06 篇的分发体系将直接建立在这个产物契约上。

8.4 退役流程

千级平台每年退役量约 10~20%。deprecated 不是删除：

description 层面的连带动作最容易漏：退役技能的负面边界让渡对象要反向更新——A 退役了，所有写着”不用于 X，用 A”的技能必须改指新归属，否则制造成群的两不管地带。Registry 用 conflicts_with/requires 反向索引自动生成这份改动清单。

值得单独指出：MCP server 的分组语义与 plugin 高度互补而非竞争——plugin 组织”知识与流程”，MCP server 组织”工具与凭证”。你的统一技能中心里二者的连接点就是 §6 的 required_tools：技能声明工具需求，解析到租户已装配的 MCP server，缺失即 Discovery 过滤。这条线在 07 篇 Runtime 中落地。

10. 反模式

  • AP-1 技术栈命名空间：python:、langgraph:——用户任务不按技术栈到达，路由域随之失效（01 篇建议 7 的族级重申）。
  • AP-2 组织架构镜像：dept-a.team-b.squad-c:* 三层命名——重组一次全平台改名。namespace 对齐能力域，能力域比组织架构稳定。
  • AP-3 单技能 plugin 泛滥：每个技能自成一族以图发版自由——四绑机制的固定开销 × N，且 L0 域卡片数失控。发版自由的正解是 §3.1 的技能级独立 SemVer。
  • AP-4 标签路由：用 maturity/channel/自定义标签影响触发（§8.1 已禁）。
  • AP-5 隐式跨族依赖：SKILL.md 正文写”参见 sre:k8s-troubleshooting”而 manifest 无 requires——01 篇 AP-5 的族级版本，订阅解析不知情，目标租户可能根本没订那个族。
  • AP-6 胶水 meta-skill（§5.3）。
  • AP-7 多域挂载（§4 例外处理已禁）。

11. 生产建议与检查清单

  1. namespace 文法、四绑机制、只收紧权限模型——三者进平台规范 v1，后改无穷贵。
  2. plugin 订阅粒度 + 技能级禁用减法；组合评测（族内边界互斥性测试）进发布流水线必选步。
  3. routing_card 与技能 description 同等对待：进触发评测闭环、有 owner、有 SLO。
  4. requires/conflicts_with 的 DAG 检查、互斥检查、退役反向索引三件套在 Registry 侧实现（05 篇 schema 承接）。
  5. Registry-native 产物契约优先于仓库形态统一；流水线模板产品化是配套投资。
  6. 度量画像（§8.2）做成平台健康看板，namespace 数与零激活占比设告警线。
  • 命名文法 lint（含层级 ≤2、族内唯一）
  • plugin manifest schema 校验 + 签名验证
  • 族内组合评测：任意两技能 trigger_examples 互不命中对方
  • 订阅解析含 requires 闭包 + 环检测
  • capability 四重可见性过滤上线
  • activation_approval 挂接 onSkillRead 鉴权点
  • 退役流程的负面边界反向更新自动清单
  • 健康画像看板（族数 / 单族 P90 / 依赖密度 / 零激活占比 / L0 预算）

三个语义钉子：① 版本冲突走 SemVer 交集调和，调和失败是订阅时错误而非会话时错误（租户管理员立即看到，而不是用户会话里炸）；② 禁用表在闭包解析之后应用，且被依赖技能不可禁——保证 requires 承诺的共同可见性；③ 输出是冻结集，直接对应 01 篇附录 B 的 DiscoverySnapshot.pins。

附录 C：namespace 初始划分工作法

四绑机制让初始划分变得昂贵而重要，给一个可操作的工作坊流程：

  1. 任务语料聚类（自下而上）：取 3~6 个月真实用户 query（02 篇附录 B.3 的管道产出），按任务意图聚类，得到候选域列表及其流量占比。
  2. 团队能力盘点（自上而下）：列出愿意承担 owner 职责（评审、oncall、SLO）的团队及其能力边界。
  3. 交叉裁决：候选域 × 团队做映射。三种病理立即处理——
    • 一个域对多个团队 → 域太粗，按语料子簇再切；
    • 一个团队对多个碎域 → 域太细，并族；
    • 有域无团队 → 该域技能延后建设（没有 owner 的族不准建，孤儿族是治理债的最大来源）。
  4. 稳定性压测：对每个拟定 namespace 问一个问题——“未来两年内哪些组织/业务变化会迫使它改名或拆分？”能说出具体场景的重新设计。
  5. 产出物：namespace 清单 + 每族 routing_card 初稿 + owner 登记，作为 Registry 初始化数据。
