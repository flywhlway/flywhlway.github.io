2. L1 · 交互接入层（Interaction Layer）

要素 内容
作用 把物理世界的模拟信号转换为平台可处理的数字信号，并完成第一道降噪与语义无关的前处理
职责 唤醒词检测、语音活动检测（VAD）、回声消除与降噪、音频编码、多模态输入采集、端点检测
输入 麦克风阵列音频、摄像头帧、屏幕交互事件、车辆状态信号
输出 编码后的音频流、本地初步 ASR 文本、模态元数据
依赖 车机音频硬件、DSP／NPU、本地 ASR 引擎
调用关系 上游=用户；下游=L2 端侧运行时（System Agent）与 L3 语音网关（双路）
数据流向 麦克风 → 音频服务 → ①System Agent（本地判定通路）②语音网关（云端 ASR 通路）
设计目的 让”是否上云”的决策发生在音频进入云端之前，从而同时满足隐私、时延与成本三项约束

2.1 为什么这样设计

图中音频服务同时指向 System Agent 和 语音网关，这是一个容易被忽略但极其关键的设计：它构成了双通路（Dual-Path）输入。

  • 若只走云端 ASR：隧道、地库、跨境场景直接不可用；且所有音频都上云，隐私合规压力大。
  • 若只走端侧 ASR：复杂长句、专有名词、方言识别率不足。
  • 双通路：端侧做唤醒＋短指令＋兜底，云端做复杂语义。二者由 System Agent 仲裁。

推断设计：建议采用「端侧流式 ASR 先出结果，云端 ASR 结果到达后按置信度覆盖」的乐观策略，可把感知时延降低 200–400 ms。

2.2 风险

风险 缓解
误唤醒率高导致体验下降与无效流量 二级唤醒确认 + 声纹校验 + 场景抑制（如导航播报中提高阈值）
音频上云触发数据合规问题 privacy_flags 声明 + 音频不落盘 + 仅上传特征而非原始波形（高敏场景）
双通路结果冲突造成”跳字/改口” 覆盖策略需带最小稳定窗口，避免 UI 抖动

3. L2 · 端侧运行时层（Edge Runtime Layer）

要素 内容
作用 端侧 Agent 的执行容器与本地总控，是离线可用性的唯一保障
职责 会话状态管理、落点决策（端/云/混合）、User Agents 生命周期、端侧记忆与知识读写、能力权限校验、端侧模型推理调度、断网续传
输入 L1 音频与文本、云端下发的能力清单与策略、车辆状态
输出 端侧执行结果、上云请求、待同步的记忆与埋点缓冲
依赖 边缘 AI 基础能力（记忆/知识/能力中心）、边缘安全系统、端侧小模型
调用关系 上游=L1；下游=L3（Agent 网关、双向认证网关）、端侧 SLM、User Agents
数据流向 System Agent 为中心的星型结构：向下调 SLM 与安全系统，向内读写边缘记忆/知识，向上经网关到云
设计目的 把”端”从瘦客户端升级为具备完整 Agent 能力的自治节点，云端不可达时降级而非失效

3.1 System Agent 与 User Agents 的分工（图示）

图中 System Agent 位于主干链路，User Agents 从 System Agent 分支而出——这是总控 + 应用的双层 Agent 结构：

flowchart LR
    SA["System Agent<br/>（唯一总控）"]
    UA1["User Agent A<br/>陪伴/娱乐类"]
    UA2["User Agent B<br/>学习/教育类"]
    UA3["User Agent N<br/>可扩展"]
    SLM["端侧小模型"]
    SEC["边缘安全系统"]
    EAI["边缘记忆 / 知识 / 能力"]

    SA -->|会话派发 · 上下文注入| UA1 & UA2 & UA3
    UA1 & UA2 & UA3 -->|能力申请| SA
    SA --> SEC --> SLM
    SA <--> EAI
维度 System Agent User Agents
数量 单例 多实例、可动态装载
职责 仲裁、路由、资源与权限、会话所有权 场景化对话与任务执行
生命周期 与车机同生命周期 按需创建/挂起/销毁
是否可直连云 可（经网关） 不可，必须经 System Agent
失败影响 全局 局部

为什么 User Agents 不能直连云：若允许直连，则端侧限流、权限、埋点、落点决策会出现旁路，与 P2（网关唯一入口）冲突。System Agent 在端侧扮演的正是”端内网关”角色。

3.2 风险

风险 缓解
端侧资源（内存/算力）被 Agent 抢占影响车机主功能 cgroup/资源配额 + 分级降载 + 主功能优先抢占
端侧记忆与云端记忆冲突 单写者原则 + 版本向量 + 冲突以云端为准（除隐私本地项）
端侧 Agent 版本碎片化 边缘 Agent 框架统一版本协商，能力清单带最小版本要求
待同步缓冲丢失 本地持久化队列 + 断点续传 + 上限淘汰策略

4. L3 · 管道网关层（Pipe & Gateway Layer）

原图把「管」独立为泳道，说明这一层在该架构中是一等公民，而非简单反向代理。三个网关职责严格分离：

网关 承载流量 核心能力 为什么独立
语音网关 音频流 长连接保持、流式转发、编解码、会话粘性 音频是高带宽长连接，与请求响应式 API 的资源模型完全不同，混部会互相拖垮
Agent 网关 Agent 请求与流式响应 SSE 流式、A2A 桥接、内容安全、限流、鉴权 AI 流量的形态（流式、长耗时、Token 计量）传统 API 网关不擅长
双向认证网关 端云状态同步 mTLS、设备身份、防重放、通道加密 同步通道是”数据面”，需与”控制面”隔离
要素 内容
作用 端云之间唯一的信任边界与协议转换层
职责 身份认证、授权、限流与配额、协议转换（长连接↔SSE↔内部 RPC）、入站内容安全、A2A 协议桥接、流量染色
输入 端侧请求、端侧音频、端侧同步数据
输出 归一化的内部请求、流式响应回传、同步确认
依赖 身份系统（OIDC/车辆证书）、内容安全服务、限流存储（Redis）
调用关系 上游=L2；下游=L4 NLU、L5 Planner、L6 基础能力层
数据流向 双向：请求下行到云，流式 token 上行回端；同步通道为双向增量
设计目的 把安全、限流、协议、可观测四件事从业务代码中彻底剥离

4.1 Agent 网关三大能力（图示圈注）

flowchart TB
    subgraph AGW["Agent 网关"]
        SSE["SSE 流式<br/>· 首包快返<br/>· 心跳保活<br/>· 断线续传 Last-Event-ID<br/>· 背压与分片"]
        A2A["A2A 桥接<br/>· Agent 间寻址<br/>· 会话与任务映射<br/>· 跨域 Agent 调用<br/>· 协议版本协商"]
        CS["内容安全<br/>· 入站敏感词/注入检测<br/>· PII 识别与脱敏<br/>· 违规请求阻断<br/>· 审计留痕"]
    end
    IN["端侧请求"] --> CS --> A2A --> SSE --> OUT["云端编排"]

顺序很重要：内容安全必须在最前（拒绝越早成本越低），A2A 寻址在中，SSE 在最后负责回传。若把内容安全放在 SSE 之后，等于已经消耗了模型资源才发现请求违规。

4.2 风险

风险 缓解
长连接数超出网关承载 连接数配额 + 空闲回收 + 水平扩容 + 就近接入 POP
入站内容安全成为延迟瓶颈 轻量规则前置 + 模型检测异步（对流式输出做分段复检）
SSE 在弱网下频繁断连 Last-Event-ID 续传 + 心跳 + 客户端指数退避
A2A 桥接被用作跨域越权通道 Agent 身份 + 调用白名单 + 每跳鉴权（不信任传递身份）

5. L4 · 云端接入层（Cloud Ingress Layer）

要素 内容
作用 把原始信号（音频）转换为编排层可消费的结构化语义
职责 云端 ASR、文本归一化（数字/单位/标点）、纠错、简单槽位预抽取、语言识别、说话人分离
输入 语音网关转发的音频流
输出 ASR 文本 + 置信度 + 时间戳 + 预抽取槽位
依赖 ASR 引擎、领域词表（热词）、纠错模型
调用关系 上游=L3 语音网关；下游=L5 Planner
数据流向 音频 → 流式 ASR → 归一化 → ASR 文本 → Planner
设计目的 让编排层只处理文本语义，不关心声学细节；同时通过热词与纠错显著提升领域识别率

5.1 为什么独立成层而不合并进 Planner

  1. 技术栈异构：ASR 是流式声学模型，Planner 是文本推理，扩缩容特征与 GPU 需求完全不同。
  2. 多入口复用：文本入口（键盘输入）不需要 ASR，直接进 Planner。
  3. 可替换性：ASR 供应商更换频繁，隔离后不影响编排层。

5.2 风险与缓解

风险 缓解
领域专有名词识别错误导致意图误判 热词表按场景动态下发 + 后处理纠错 + Planner 容错（模糊匹配）
流式 ASR 中间结果引起 Planner 反复触发 仅在端点检测确认后触发编排；中间结果仅用于 UI 回显
长音频导致 ASR 延迟累积 分段识别 + 增量送 Planner（长指令场景）

6. L5 · 编排层（Orchestration Layer）

这是整个架构的决策中枢，由 Planner + Cloud Agents 两部分组成。

要素 内容
作用 把用户意图映射为一组可执行的能力调用，并驱动执行到结果
职责 意图分类、落域路由、任务拆解、上下文装配、Agent 派发、工具选择、结果校验、记忆写回触发、埋点
输入 ASR 文本／文本请求、端侧上下文、能力清单、上下文包
输出 流式回答、工具调用指令、记忆更新事件、埋点事件
依赖 L6 基础能力层（记忆/知识/能力）、L7 模型服务层、L8 注册中心
调用关系 上游=L3/L4；下游=L6、L7、存量业务平台、第三方 MCP
数据流向 文本进 → 上下文聚合 → 模型推理 → 工具执行 → 结果出 → 记忆与埋点回写
设计目的 让”意图口径”在全平台统一，避免每个业务各自定义意图体系导致体验割裂

6.1 Planner 与 Cloud Agents 的边界（关键设计）

sequenceDiagram
    participant P as Planner（决策）
    participant R as 注册中心/能力中心
    participant A as Cloud Agent（执行）
    P->>R: 按意图查询候选 Agent 与工具
    R-->>P: 候选清单 + 权限 + 版本
    P->>P: 选择 Agent + 裁剪工具集 + 设定预算
    P->>A: 派发任务（Task + Context Bundle + Budget）
    A->>A: 自主执行（可多轮 ReAct，可调工具）
    A-->>P: 流式结果 + 执行轨迹
    P->>P: 结果校验（格式/安全/一致性）
维度 Planner Cloud Agents
定位 决策者（做什么） 执行者（怎么做）
是否感知业务细节 否，只感知意图与能力元数据 是
是否可长时运行 否，追求低延迟 是，可多轮 ReAct
变更频率 低（平台级） 高（业务级）
扩容依据 QPS 各自业务量

反模式警告：Planner 一旦开始”顺手把业务逻辑写进去”（例如为某场景硬编码回答模板），就会退化为巨石服务，业务迭代必须改平台代码。判定标准：Planner 代码库中不应出现任何具体业务名词。

6.2 风险

风险 缓解
意图体系膨胀、类目重叠 意图注册制 + 定期归并 + 用真实 Trace 做混淆矩阵分析
意图分类误判导致落错域 置信度阈值 + 多意图并行探测 + 澄清追问 + 用户纠正回流训练
Planner 单点故障 多副本无状态 + 规则兜底路由 + 端侧降级
上下文装配过大导致效果下降与成本上升 上下文预算硬约束（见 01 文档 3.4）+ 压缩 + 相关性过滤

7. L6 · AI 基础能力层（AI Foundation Layer）

要素 内容
作用 为所有 Agent 统一供给”上下文”与”能力目录”，是平台差异化的核心资产层
职责 记忆的存取与演化、知识的入库检索评测、能力的聚合与路由适配、端侧 AI 能力的云端管控
输入 编排层查询、数据平台离线产出、端侧同步数据、知识源文档
输出 上下文包（记忆/知识/能力三段）、端侧能力与策略下发包
依赖 向量库、关系库、缓存、对象存储、Embedding/Reranker 模型
调用关系 上游=L5 编排层、L3 双向认证网关（端云同步）；下游=存储、L7（Embedding 调用）、L8 注册中心
数据流向 在线读多写少；离线由 L9 数据平台批量更新画像与知识
设计目的 把”上下文”从各 Agent 的私有实现提升为平台服务，实现跨 Agent 的记忆与知识共享

7.1 四大子域

子域 图中构成 一句话职责
记忆中心 短期记忆、长期记忆、用户画像、可视化、回溯干预 让平台”记得住”且”记错了能改”
知识中心 RAG 门户、RAG 评测、RAG 底座 让平台”查得准”且”质量可度量”
能力中心 路由适配、能力聚合、查询门户 让平台”知道自己有什么能力”
边缘 Agent 框架 端侧长短记忆、端侧 RAG、端侧能力中心、端侧模型路由 让端侧具备与云端同构的能力抽象

7.2 为什么把「边缘 Agent 框架」放在云端层

这是原图一个非常值得注意的设计：端侧的四项能力（长短记忆/RAG/能力中心/模型路由）被画在云端 AI 基础能力层内部。

解读（推断设计）：这里表达的不是”运行在云端”，而是端侧能力的控制面在云端——云端负责定义、编译、下发端侧能力配置，端侧只负责执行。

flowchart LR
    subgraph CTRL["控制面（云）"]
        DEF["能力定义与版本"]
        POL["落点与路由策略"]
        PKG["端侧知识包/模型包构建"]
    end
    subgraph DATA2["执行面（端）"]
        RUN["端侧记忆/RAG/能力/路由运行时"]
    end
    CTRL -->|经双向认证网关下发| DATA2
    DATA2 -->|运行指标与同步数据回传| CTRL

这种”控制面云端、执行面端侧”的划分，是车云协同架构的标准做法：避免端侧成为无法治理的黑盒。

7.3 风险

风险 缓解
基础能力层成为所有 Agent 的共享故障域 按子域独立部署与熔断，任一子域故障可单独降级
多 Agent 共享记忆导致隐私越界（A Agent 看到 B 的私密上下文） 记忆分区 + 命名空间 + 按 Agent 授权的记忆视图
知识与记忆的写入竞争 写入走事件队列串行化 + 幂等键
端侧包体膨胀 知识包按场景切分 + 增量下发 + LRU 淘汰

8. L7 · 模型服务层（Model Serving Layer）

要素 内容
作用 把异构模型资源抽象为统一、可治理、可替换的推理服务
职责 多模型路由与切换、语义缓存、Token 与流量治理、限流与配额、Fallback 与熔断、成本归因、出站安全围栏
输入 编排层推理请求（model_intent + messages + tools + policy）
输出 流式或整体推理结果、Token 与成本明细、缓存命中标记
依赖 自建推理集群、外部模型 API、缓存存储、Guardrail 服务
调用关系 上游=L5、L6（Embedding/Rerank）；下游=模型池、Guardrail、L9（计量回流）
数据流向 请求 → 缓存判定 → 模型选择 → 推理 → 围栏 → 回传；旁路输出 Token 明细到数据平台
设计目的 让模型成为”可插拔的后端资源”，把成本与稳定性风险收敛到一个可控组件内

8.1 为什么安全围栏在模型网关之后

图中安全围栏防护位于 LLM 网关右侧末端，即出站方向的最后一跳。

  • 放在网关之前（入站）：只能审查提问，无法审查模型生成内容，无法防止有害输出。
  • 放在网关之后（出站）：可审查最终内容，是合规的必要位置。
  • 正确做法是两侧都有：入站 Guard 在 Agent 网关（内容安全），出站 Guard 在模型网关之后（安全围栏）。原图恰好体现了这一对称设计。

8.2 风险

风险 缓解
网关成为全平台单点 多副本 + 多区域 + 客户端侧 SDK 内置备用直连策略（仅限降级态并强制审计）
缓存返回过期或错误答案 缓存键包含知识版本与用户维度；对时效性意图强制 bypass
流式场景下围栏难以整段判定 分段增量判定 + 高风险片段截断 + 尾部整体复检
Token 计量不准导致成本无法归因 以网关计量为唯一口径，禁止业务侧自报

9. L8 · 治理层（Governance Layer）

要素 内容
作用 定义”平台上存在哪些能力”，是整个架构的元数据权威源
职责 MCP Server 注册审核、Agent 注册与版本、Skill 注册与描述规范、权限与可见性、上下线与灰度、依赖与兼容性校验
输入 业务研发提交的注册申请、第三方 MCP 生态接入、存量业务平台适配声明
输出 能力清单（供能力中心与 Planner 消费）、权限策略、版本与灰度规则
依赖 关系库、审核流程、身份系统
调用关系 上游=研发/三方；下游=L6 能力中心 → L5 Planner
数据流向 写入低频、读取高频 → 强缓存 + 变更事件推送
设计目的 把能力从”代码里的函数”变成”平台上的资产”，实现可发现、可鉴权、可计量、可下线

9.1 三类注册对象的差异

维度 MCP（工具） Agent Skill（技能）
粒度 单个工具/工具集 具备自主决策的执行体 面向意图的能力封装
是否有 LLM 参与 通常无 有 可有可无
描述重点 入参/出参 Schema 职责边界、可用工具、上下文需求 触发条件、意图示例、期望效果
主要风险 越权、注入 失控循环、成本 意图冲突
审核重点 权限最小化、输出可信度 预算与终止条件 与既有 Skill 的冲突检测

Skill 描述质量决定路由质量：Planner 是靠描述文本做能力选择的，描述写得含糊，等于路由必然出错。建议强制 Skill 注册时提供 ≥10 条正例意图与 ≥5 条反例（”什么情况下不要用我”）。

9.2 风险

风险 缓解
注册中心不可用导致全站无法路由 各消费方本地快照 + 只读降级（禁止新上线）
三方 MCP 变更导致线上行为漂移 版本锁定 + 契约快照 + 变更需重新审核
存量业务平台适配层长期存在成为技术债 适配层设 Sunset 日期，能力逐步原生化
影子能力（未注册即上线） 网关侧强制校验能力 ID，未注册直接拒绝

10. L9 · 数据与训练层（Data & Training Layer）

要素 内容
作用 把线上运行产生的行为数据转化为平台改进能力，构成自演进闭环
职责 埋点接入与清洗、会话与轨迹重建、指标计算、金标集管理、自动评测、数据集构建、SFT/DPO/RLHF、模型注册与发布
输入 埋点 SDK 上报事件、网关 Token 明细、用户反馈、人工标注
输出 指标看板、评测报告、训练数据集、新模型版本、知识与画像更新
依赖 消息队列、数据湖/数仓、训练集群、模型注册中心
调用关系 上游=L5/L7 埋点；下游=L6（画像与知识更新）、L7（新模型上线）
数据流向 见下图
设计目的 把”效果好不好”从主观判断变为可度量指标，并让改进自动化 
flowchart LR
    T["埋点 SDK<br/>Planner + Agents + 网关"] --> MQ["消息队列"] --> ODS["原始层 ODS"]
    ODS --> DWD["明细层<br/>会话/轨迹/工具/Token"]
    DWD --> DWS["汇总层<br/>意图分布/成功率/成本"]
    DWS --> BI["指标看板"]
    DWD --> GOLD["金标集构建"]
    GOLD --> EVAL["自动评测与回归"]

    DS --> TRN["训练 SFT/DPO"]

    MREG --> DEPLOY["灰度发布"]

    DWD --> KUP["知识补全/纠错"] --> KN["知识中心"]

10.1 风险

风险 缓解
埋点口径不一致导致指标不可信 埋点 Schema 集中管理 + SDK 内置 + CI 校验
用户数据进入训练集引发合规问题 授权范围校验 + PII 脱敏 + 数据分级 + 可撤回机制
评测集过拟合，线上不涨 金标集分为公开集/回归集/盲测集三份，盲测集不参与调优
反馈稀疏（用户不点赞不点踩） 隐式反馈（重问率、打断率、任务完成率）作为主信号

11. 横切层：安全与可观测

横切层 在各层的落点
安全层 L2 边缘安全系统（本地权限与沙箱）→ L3 双向认证与入站内容安全 → L5 工具最小权限 → L7 出站安全围栏 → L8 注册审核 → L9 数据合规
可观测层 L2 端侧埋点缓冲 → L3 网关访问日志与流量染色 → L5 埋点 SDK（Trace 主干）→ L7 Token 与延迟明细 → L9 汇总与评测

为什么必须横切而非独立成层：安全与可观测若做成”某一层的能力”，必然出现覆盖盲区（例如只在网关做安全，则内部服务间调用无保护）。原图把安全元素分布在云、管、端三处，正是横切思想的体现。

12. 层间依赖约束（Layering Rules）

规则 说明 违反示例
R1 只能向下依赖 上层可调下层，下层不得反向调用上层 记忆中心直接回调 Planner ❌
R2 不得跨层穿透 相邻层之外不得直连 Cloud Agent 直连外部模型 API ❌
R3 横切层可被任意层调用 安全与可观测例外 ✅
R4 异步例外 下层可通过事件通知上层，但不得同步调用 数据平台发布”画像更新”事件 ✅
R5 端侧不得直连云内部服务 必须经 L3 端侧直连知识中心 ❌

13. 演进路线

阶段 分层演进动作
阶段一 明确 9 层边界并写入代码库结构；网关强制校验；建立层间 Schema 仓库
阶段二 L6 基础能力层子域独立部署与独立 SLO；L7 引入语义缓存与多模型 Fallback
阶段三 L2 端侧运行时与 L6 控制面完成同构抽象（同一份能力定义编译出端云两套运行时）；L9 闭环自动化
