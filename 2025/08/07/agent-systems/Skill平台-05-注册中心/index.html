05 · Skill Registry 架构：元数据、API、存储与发布治理

企业级 Skill Registry 平台工程手册 · 第 05 篇
前置阅读：04 篇（plugin 产物契约、订阅解析）、02 篇（校验 API 已给出发布流水线第一闸）
本篇回答：Registry 作为平台心脏的完整设计——存什么（Schema/DDL）、怎么进（发布审批流）、怎么出（发现与解析 API）、怎么找（三索引搜索）、怎么评（统计与评分）、怎么隔（租户模型）、怎么联（事件体系）。

1. 概述：Registry 的职责边界

先钉边界，再谈架构。Registry 是控制面，只做五件事：

  1. 真理源：技能/插件的元数据与产物指针的唯一权威记录；
  2. 准入闸：发布流水线的编排与裁决记录；
  3. 解析器：把租户订阅解析为冻结集（04 篇附录 B 的服务化）；
  4. 索引：面向人（Marketplace 搜索）与面向机器（embedding 补充召回）的双索引；
  5. 账本：激活/执行统计、评分、评测结果的聚合存储。

Registry 不做的事同样重要：不在会话关键路径上（Runtime 读本地缓存，06 篇）；不执行技能（07 篇 Runtime 的事）；不存产物本体（对象存储的事，Registry 只存内容哈希与指针）。违反第一条是最常见的架构事故——Registry 一抖动全平台会话初始化失败。

2. 总体架构

组件间一条铁律：写路径全部经发布服务的状态机，读路径全部可缓存。搜索/解析/统计三服务对 PG 只读；发布服务是唯一写入方——这使审计（11 篇）只需覆盖一个服务的写日志。

3. 元数据 Schema（权威版）

02/03/04 篇分散出现的字段在此合并为权威 Schema。顶层四实体：Skill（抽象身份）、SkillVersion（不可变快照）、Plugin、PluginVersion。

Schema 的三条设计纪律：

  1. quality 段只能由平台服务回写——发布方自填质量数据在 schema 层就不给字段权限（API 侧 400），杜绝”自报триgger 率”。
  2. file_tree 带角色标注：分发层（06 篇）据此实现”元数据全同步、reference 懒拉取”；审计层据此检查”声明为 script 的文件是否出现在非执行路径”。
  3. 一切版本化字段进 SkillVersion，Skill 只存身份与当前指针——历史版本永不可变，回滚与审计因此免费。

4. 数据库 Schema（PostgreSQL DDL 核心）

值得辩护的三个决定：

  • manifest 整体入 JSONB + 关键字段抽列：schema 演进快的领域（routing/capabilities 字段年年加），全列化会把每次演进变成 DDL 迁移；抽列的标准是”进 WHERE/JOIN 的才抽”。
  • 依赖关系展开成关系表而不留在 JSONB：反向查询（谁依赖我/谁与我冲突）是退役流程与影响面分析的高频路径，JSONB 反查在千级规模可用、万级依赖边时进入慢查询区。
  • 统计表按天预聚合：原始事件留在观测系统（07 篇），Registry 只收日聚合——控制面数据库不接原始遥测流量，这是 §1 边界的存储层执行。

5. 版本语义：什么算 breaking

技能不是 API，SemVer 需要重新定义兼容性维度。五维兼容性判定：

维度 MAJOR（破坏） MINOR（扩展） PATCH
description 触发域 收窄或转移触发域（原有场景不再触发） 扩展触发域 措辞微调且评测集回归全绿
输入契约 不再接受原格式 新增可选输入 —
输出契约 结构化输出字段删除/改名 新增字段 报告措辞
工具/权限需求 新增 required_tools 或权限升级 — —
依赖 新增 requires / 改 conflicts 放宽版本约束 —

其中最反直觉的是第一行：description 的语义变更可以是 breaking——某租户的用户已习惯某类说法能触发该技能，收窄触发域等于砍掉他们的既有能力。发布流水线用”新旧 description 在旧评测集上的触发率对比”自动判级：旧集回归跌幅 >10% 强制 MAJOR。工具/权限升级判 MAJOR 的原因在租户侧：订阅解析时权限不满足的新版本不能被自动升级选中。

7. Registry API（OpenAPI 3.1 核心路径）

as_of 时间点解析值得强调：事故复盘时”复现当时那个会话看到的技能集”是刚需，产物不可变 + 时间点解析让这件事是一次 API 调用而不是考古工程。

9. 统计与评分

评分的信号工程比公式重要。四类信号及其偏差：

信号 采集 偏差与修正
explicit_star 会话内主动评分 极化偏差（只有极端体验才评）→ 只作定性告警，不进质量分主项
implicit_correction 激活后 3 轮内用户显式纠正（02 篇附录 B 的护栏一） 最可靠的负信号，权重最高
implicit_redo 同任务换说法重来 与探索行为混淆 → 仅统计”重来且未再触发同技能”
implicit_adoption 技能产出物被下载/转发/进入后续工作流 最可靠的正信号；需 surface 埋点支持

rating_composite = w·(1-correction_rate) + w'·adoption_rate，星级只画在详情页。统计管道单向流：Runtime 遥测（07 篇）→ 流式聚合 → activation_stats_daily / ratings → quality 段回写 → 搜索排序与 SLO 看板。Registry 永不反向查询原始遥测。

10. 租户隔离与事件体系

隔离三层：

  1. 数据层：控制面表全部带 tenant_id + PG RLS（行级安全策略），平台运营角色走独立 BYPASS 审计通道；
  2. 内容层：私有技能（租户自研）与公共技能同库不同可见域——visibility: platform | tenant:<id> | namespace-private，搜索与解析在索引层过滤而非结果层过滤（防时序侧信道枚举他租户私有技能名）；
  3. 产物层：对象存储按租户前缀 + 内容寻址，公共产物单副本共享（内容哈希天然去重）。

事件主题与消费方：

事件是事实广播不是指令：消费方各自幂等处理，Registry 不追踪消费进度——控制面与周边系统的耦合度由此钉在最低档。

11. 设计选项对比：中心化 vs 联邦

单中心 Registry 联邦（各 BU 自建 + 汇聚层） 混合（中心 + 只读镜像）
真理源 唯一 多源，汇聚层做聚合视图 唯一，镜像只读
跨 BU 复用 天然 汇聚协议复杂，版本语义易漂移 天然
自治程度 靠 namespace 权限模型模拟 完全自治 同单中心
一致性故障面 单点（靠只读缓存兜底） 汇聚层成为新单点且更复杂 镜像滞后可控
适用 绝大多数企业 强合规隔离的集团多法人 多地域/边缘（06 篇）

结论直白：除非法人级合规强制隔离，不要联邦。联邦的全部成本花在”重新发明单中心已有的一致性”上。多地域诉求用混合模式的只读镜像解决，写路径永远单点。

12. 反模式

  • AP-1 Registry 上会话关键路径：Runtime 每次会话初始化直连 resolve。正解：本地缓存 + 事件驱动标脏（06 篇）。
  • AP-2 可变版本：允许覆盖已发布版本”修个小错”。产物不可变是回滚、审计、as_of 复现的共同地基，一破全破。
  • AP-3 质量字段自填：见 §3 纪律 1。
  • AP-4 全量人审：见 §6，必然橡皮图章化。
  • AP-5 统计直连：控制面 DB 接原始遥测流。见 §4 第三决定。
  • AP-6 结果层租户过滤：先查全量再滤结果，私有技能名通过计数/时延侧信道泄露。
  • AP-7 搜索单索引通吃：人机两类查询共用一套排序——机器召回被人气分污染，冷门但正确的技能永远进不了补充召回。

13. 生产建议与检查清单

  1. 边界五做五不做（§1）写进架构 ADR，作为后续一切需求评审的准绳。
  2. Schema 三纪律 + DDL 三决定按本文实现，manifest JSONB 化保住演进速度。
  3. 五维兼容性判定 + 旧评测集回归自动判级，SemVer 从约定变成机制。
  4. 分级审批 + owner 信誉分，人审火力集中 elevated。
  5. as_of 时间点解析从第一天实现——事后补需要给全部历史表加时态语义，成本十倍。
  6. 事件体系用”事实广播”语义，消费方幂等，不做消费追踪。
  • 发布服务为唯一写入方，写审计全覆盖
  • SkillVersion 不可变（对象存储 WORM 或等价策略）
  • quality 段 API 层写保护
  • 依赖展开表 + 反向索引 + 退役清单自动化
  • 分级审批规则可配置 + 信誉分账本
  • RLS + 索引层租户过滤 + 私有产物前缀隔离
  • 三索引分排序：tsvector / tag / 多向量各就其位
  • 日聚合统计表 + 单向统计管道
  • resolve 支持 as_of + 422 冲突前置到订阅时
  • 事件主题清单与消费方注册表
