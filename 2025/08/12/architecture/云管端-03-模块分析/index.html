M01 · 音频服务（Audio Service）

  • 定位：端侧音频前端，链路第一跳。
  • 功能：唤醒词检测、VAD、AEC/降噪/波束成形、增益控制、音频编码、端点检测、本地流式 ASR（可选）。
  • 输入：麦克风阵列 PCM、车辆状态（车速、车窗、媒体音量）。
  • 输出：编码音频流（Opus/AAC）、本地 ASR 文本与置信度、唤醒事件。
  • 上游：用户 / 麦克风硬件。下游：M02 System Agent、M07 语音网关（双通路）。
  • 数据流：PCM → 前处理 → ①本地 ASR → System Agent ②编码流 → 语音网关。
  • 内部能力：多麦克风融合、声源定位（分区唤醒）、车噪抑制模型、误唤醒抑制。
  • 实现建议：DSP/NPU 上跑前处理与唤醒；音频不落盘；用环形缓冲保留唤醒前 500 ms 以避免丢字。
  • 可替代方案：车机 SoC 原生音频框架 / 商用车载语音前端 SDK / 开源 WebRTC APM（AEC3、NS）。
  • 最佳实践：分区唤醒（主驾/副驾/后排独立会话）；播报中自动提高唤醒阈值；把误唤醒率与漏唤醒率作为一对独立 SLI 分别定 SLO，不合并成单一”准确率”。

M02 · System Agent（系统智能体）

  • 定位：端侧唯一总控，端内网关 + 落点决策者 + 会话所有者。
  • 功能：会话生命周期管理、落点决策（端/云/混合）、User Agents 装载与派发、能力权限申请、端侧上下文装配、断网缓冲与续传、结果仲裁（端云双结果择优）。
  • 输入：M01 音频/文本、M17 下发的能力清单与策略、车辆状态、云端流式结果。
  • 输出：端侧执行指令、上云请求、TTS 播报内容、端侧记忆写入、埋点缓冲。
  • 上游：M01。下游：M03、M04、M05、M06、M08、M09。
  • 数据流：星型中心。所有端侧交互必须经它，不允许旁路。
  • 内部能力：状态机（见 01 文档 4.3）、预算控制器（时延/算力）、优先级队列、幂等去重。
  • 实现建议：做成常驻轻量进程，自身不含大模型，落点决策用规则 + 小分类器；所有对外调用设硬超时；崩溃后 5 s 内自恢复且能重放未完成会话。
  • 可替代方案：车机既有语音总控服务扩展 / 基于状态机框架自研 / 轻量 Agent 运行时嵌入。
  • 最佳实践：把”落点决策”独立为可热更新的策略文件（规则 DSL），使不发版即可调整端云比例；对每次决策记录 decision_reason，否则线上问题无法归因。

M03 · User Agents（用户智能体集群）

  • 定位：面向具体场景的应用级 Agent，端侧可动态装载。
  • 功能：场景化多轮对话、场景任务执行、个性化人设、场景内工具调用。
  • 输入：System Agent 派发的任务与上下文、端侧记忆切片。
  • 输出：对话回复、执行动作请求（须经 System Agent 授权）、场景记忆写入。
  • 上游：M02。下游：经 M02 间接访问 M04/M06/M08。
  • 数据流：不直连云、不直连模型，全部经 System Agent 代理。
  • 内部能力：人设与语气模板、场景状态、话题延续、多轮澄清。
  • 实现建议：以声明式清单（manifest）定义 Agent：所需能力、所需记忆命名空间、最大轮次、预算上限；运行在受限沙箱内。
  • 可替代方案：轻量插件化框架 / 云端 Agent 的端侧镜像（同定义双运行时）。
  • 最佳实践：每个 User Agent 必须声明终止条件（最大轮次、最大工具调用数、最大耗时），否则会出现无限循环消耗算力；人设与业务逻辑分离，人设可热更新。

M04 · 边缘 AI 基础能力（Edge AI Foundation）

  • 定位：端侧的记忆 + 知识库 + 能力中心三件套，云端基础能力层的端侧对等实现。
  • 功能：端侧短期/长期记忆存取、端侧知识检索、端侧可用能力目录查询、与云端增量同步。
  • 输入：System Agent 读写、M24 端云同步下发包。
  • 输出：端侧上下文包、待同步变更集。
  • 上游：M02、M24。下游：本地存储（嵌入式 KV / SQLite / 嵌入式向量索引）。
  • 内部能力：本地向量检索（小规模、量化索引）、TTL 与容量淘汰、变更日志（用于同步）、隐私分区（不可上云项）。
  • 实现建议：向量维度降到 256–384 并量化（int8），索引规模控制在万级；知识包按场景切分按需下载；记忆写入走 WAL 保证掉电不丢。
  • 可替代方案：SQLite + FTS5（关键词）+ 简易向量表 / 嵌入式向量库（如 sqlite-vec、usearch、Faiss 移动版）/ 纯规则知识库（车辆手册场景足够）。
  • 最佳实践：端侧知识库优先解决高频且答案稳定的问题（车辆功能说明、常用设置），这类问题占比常达 30%+ 且完全不需要上云，是成本与体验双赢点。

M05 · 边缘安全系统（Edge Security System）

  • 定位：端侧安全策略执行点（PEP），位于 System Agent 与端侧模型/执行能力之间。
  • 功能：能力调用权限校验、沙箱隔离、本地内容策略、敏感操作二次确认、本地审计日志、模型输入输出本地过滤。
  • 输入：System Agent 的能力调用请求、云端下发的安全策略。
  • 输出：允许/拒绝/降级决策、审计记录。
  • 上游：M02。下游：M06 端侧小模型、端侧执行能力（车控等）。
  • 数据流：图中 System Agent → 安全系统 → 车端小模型，说明端侧模型调用是被强制经过安全系统的——这是防止端侧 Agent 直接驱动车辆能力的关键设计。
  • 内部能力：策略引擎（本地可离线执行）、能力白名单、速率限制、危险意图识别。
  • 实现建议：策略以声明式规则下发并本地缓存；离线时使用最后一次有效策略且默认收紧（fail-closed）；车控类能力必须双因子（语音 + 触屏确认）。
  • 可替代方案：本地策略引擎（OPA/Cedar 的轻量实现）/ 车机既有权限框架扩展。
  • 最佳实践：安全默认拒绝（deny by default）；对”不可撤销操作”（解锁、行驶相关）与”可撤销操作”（调空调、播音乐）分级，前者永不允许纯语音一次触发。

M06 · 端侧小模型（Edge SLM）

  • 定位：端侧推理算力载体，提供离线可用与低时延能力。
  • 功能：意图分类、槽位抽取、短文本生成、摘要压缩、闲聊兜底、Embedding 生成（端侧 RAG 用）、内容安全初筛。
  • 输入：经安全系统校验的 Prompt 与上下文。
  • 输出：分类结果 / 生成文本 / 向量。
  • 上游：M05。下游：结果回 M02。
  • 内部能力：量化推理（int4/int8）、NPU/GPU 加速、模型多任务复用（一个基座 + 多 LoRA）、按算力等级选档。
  • 实现建议：优先用”一个小基座 + 多任务 LoRA/适配器”而非多个独立模型，显著节省内存；把 Embedding 模型与生成模型分开（Embedding 更小更常驻）。
  • 可替代方案：开源小模型量化部署（Qwen/Llama/Phi/Gemma 系列小尺寸）+ 推理运行时（llama.cpp / MNN / NCNN / ONNX Runtime / TensorRT / 厂商 NPU SDK）。
  • 最佳实践：端侧模型不追求”全能”，只追求三件事做到极致：意图分类、槽位抽取、上下文压缩。这三件事恰好是延迟预算表中占比最高且最容易端侧化的环节（见 01 文档 6.1）。

M07 · 语音网关（Voice Gateway）

  • 定位：音频流专用接入网关。
  • 功能：长连接管理、音频流转发、编解码协商、会话粘性、带宽自适应、音频链路鉴权。
  • 输入：端侧编码音频流。输出：转发至 M10 NLU 的音频流；ASR 结果回传通道。
  • 上游：M01。下游：M10。
  • 内部能力：连接池、心跳保活、丢包处理、抖动缓冲。
  • 实现建议：与 Agent 网关物理隔离部署（资源模型不同）；采用 WebSocket 或专用流协议；就近接入 POP 降低 RTT。
  • 可替代方案：自研流媒体网关 / 商用 RTC 网关 / gRPC 双向流。
  • 最佳实践：把音频链路的 SLI 定为”首字识别延迟 + 断连率 + 丢包重传率”三项；不要与 API 网关共用限流配额池。

M08 · Agent 网关（Agent Gateway）

  • 定位：AI 流量的统一入口，原图圈注的重点建设项。
  • 功能：SSE 流式回传、A2A 协议桥接、入站内容安全、认证鉴权、限流配额、请求染色、审计。
  • 输入：端侧 Agent 请求（含身份、trace、上下文）。输出：内部编排请求；流式结果回端。
  • 上游：M02。下游：M11 Planner。
  • 内部能力：见 02 文档 4.1（内容安全 → A2A → SSE 三段顺序）。
  • 实现建议：无状态化，会话状态放 Redis；SSE 支持 Last-Event-ID 续传；限流按「设备 + 用户 + Agent + 意图」四维；入站安全用轻量规则前置、模型检测异步。
  • 可替代方案：云原生 API 网关 + AI 插件（Higress / Kong / APISIX / Envoy）；自研 Go/Rust 网关。
  • 最佳实践：AI 网关与传统 API 网关的关键差异是必须理解 Token 与流式语义——限流单位应是 Token/s 而非 QPS，超时应区分”首包超时”与”整体超时”。仅按 QPS 限流的网关在 AI 场景下几乎无效。

M09 · 双向认证网关（Mutual-Auth Gateway）

  • 定位：端云数据同步通道的安全边界。
  • 功能：mTLS 双向认证、设备/车辆身份校验、证书生命周期管理、防重放（nonce + 时间窗）、通道加密、同步流量限速。
  • 输入：端侧同步请求（记忆变更、埋点批量、能力版本协商）。输出：云端同步响应与下发包。
  • 上游：M04（经 M24）。下游：M14/M15/M16/M17。
  • 内部能力：证书吊销校验（CRL/OCSP）、身份到租户的映射、批量同步的幂等处理。
  • 实现建议：使用短周期证书 + 自动轮转；车辆身份由制造阶段注入的设备根证书派生，禁止业务层自报身份；同步接口全部幂等（幂等键 = 设备 ID + 变更序号）。
  • 可替代方案：SPIFFE/SPIRE 工作负载身份体系 / 自研 PKI + HSM / 车规 HSM 密钥存储。
  • 最佳实践：把”设备身份”与”用户身份”彻底分离（一车多用户、一人多车）；同步通道与请求通道分离，避免大批量同步挤占交互链路带宽。

M10 · 语义理解服务（NLU）

  • 定位：声学到文本语义的转换与归一化层。
  • 功能：云端流式 ASR、文本归一化、纠错、语言/方言识别、说话人分离、热词增强、槽位预抽取。
  • 输入：M07 转发音频流。输出：ASR 文本 + 置信度 + 时间戳 + 预抽取槽位 → M11。
  • 上游：M07。下游：M11。
  • 内部能力：领域热词动态加载、上下文偏置（结合当前场景提升识别率）、标点与数字规整。
  • 实现建议：流式输出中间结果供 UI 回显，仅在端点确认后触发编排；热词表按场景（导航中/听歌中/车控中）动态切换。
  • 可替代方案：商用 ASR 云服务 / 开源方案（Whisper 系列、FunASR、SenseVoice、Paraformer）自建。
  • 最佳实践：把 ASR 的领域适配当作持续工程而非一次性配置——用线上 Trace 中的”用户重问/纠正”样本，每周更新热词与纠错规则，这是识别率提升最快的路径。

M11 · Planner（规划器）

  • 定位：架构决策中枢，云端唯一的意图与路由权威。
  • 功能：意图分类、落域路由、任务拆解、上下文装配、Agent 与工具选择、预算设定、结果校验、记忆写回触发、全链路埋点。
  • 输入：M08 编排请求、M10 ASR 文本、M21/M22 可用能力、M16 能力清单。
  • 输出：任务派发（→M12）、推理请求（→M18）、记忆更新事件（→M14）、埋点（→M23）、注册查询（→M20）。
  • 上游：M08、M10、M21、M22。下游：M12、M14、M15、M16、M18、M23。
  • 数据流：图中 Planner 是唯一同时连接「输入源、Agent 集群、模型网关、基础能力层、注册中心、数据平台」的模块——扇出最高，因此也是最高风险单点。
  • 内部能力：意图分类器（小模型/分类模型）、落域规则引擎、上下文预算控制器、Prompt 组装器、结果校验器、埋点 SDK（M13）。
  • 实现建议：无状态化 + HPA；意图分类禁止使用大模型（延迟与成本双杀），用小模型或判别式分类器；上下文并行拉取（记忆/知识/能力三路并发）；提供规则兜底路由用于分类器故障。
  • 可替代方案：图编排框架（LangGraph / Temporal 工作流 / 自研 DAG 引擎）；纯规则路由 + 语义相似度检索路由。
  • 最佳实践：Planner 代码库中不得出现任何业务名词（判定标准见 02 文档 6.1）；意图分类与工具选择解耦为两个可独立评测的阶段，否则效果回归时无法定位是分类错还是选工具错。

M12 · Cloud Agents（云端智能体集群）

  • 定位：业务执行体，承载具体场景的多轮推理与工具编排。
  • 功能：ReAct 多轮推理、工具调用、结果组装、场景化人设、长任务执行、流式输出。
  • 输入：M11 派发的任务 + 上下文包 + 预算。输出：流式结果、执行轨迹、记忆写入、埋点。
  • 上游：M11。下游：M18 LLM 网关、M21 MCP 工具、M22 存量业务、M14 记忆、M23 埋点。
  • 内部能力：推理循环与终止条件、工具结果校验、失败重试与补偿、上下文裁剪、埋点 SDK。
  • 实现建议：每 Agent 独立部署、独立配额、独立 SLO，避免互相影响；预算（最大轮次/工具数/Token/耗时）由 Planner 下发并在 Agent 内强制执行；工具返回值视为不可信输入，必须二次校验与隔离。
  • 可替代方案：Agent 框架（LangGraph / LlamaIndex Workflows / AutoGen / CrewAI / Spring AI / 自研）。
  • 最佳实践：把 Agent 的”执行轨迹”作为一等产物上报（每步的思考、工具、参数、结果、耗时），这是 AI 系统唯一有效的调试手段；对话式 Agent 与任务式 Agent 分开设计，前者优化流畅度，后者优化成功率。

M13 · 埋点 SDK（Telemetry SDK）

  • 定位：横切可观测能力的强制接入点，原图在 Planner 与 Cloud Agents 内部各画一份并圈注。
  • 功能：Trace/Span 生成与透传、Token 计量、工具调用记录、上下文快照采样、用户反馈采集、异常上报、本地缓冲与重试。
  • 输入：运行时事件。输出：结构化事件 → M23 数据平台（埋点数据回流）。
  • 上游：M11、M12、M18。下游：M23。
  • 内部能力：采样策略（错误全采、正常按比例）、敏感字段脱敏、批量压缩上报、背压保护。
  • 实现建议：SDK 内置于运行时基础镜像，业务无需手工调用；Schema 集中管理并在 CI 校验；上下文快照按比例采样（全量存储成本不可接受）。
  • 可替代方案：OpenTelemetry SDK + GenAI 语义约定；LLM 可观测平台 SDK（Langfuse / Phoenix / OpenLLMetry）。
  • 最佳实践：Trace ID 必须从端侧生成并贯穿到训练数据。多数团队的 Trace 从云端网关才开始，导致”端侧决策为什么没上云”这类问题永远查不清。原图把埋点 SDK 画在模块内部而非旁挂，正是强调”默认埋点”（P7）。

M14 · 记忆中心（Memory Center）

  • 定位：跨 Agent 共享的用户上下文资产层。
  • 功能：短期记忆（会话内）、长期记忆（跨会话事实）、用户画像、记忆召回、记忆写入与演化、可视化、回溯干预（原图圈注）。
  • 输入：M11/M12 的读写请求、M24 端侧同步、M23 离线画像更新。
  • 输出：记忆切片（带置信度与来源）、画像切片。
  • 上游：M11、M12、M24、M23。下游：Redis / 关系库 / 向量库。
  • 内部能力：记忆抽取（从对话中提炼事实）、去重与冲突合并、置信度与时效衰减、命名空间隔离、审计与人工修正。
  • 实现建议：短期记忆放 Redis（TTL = 会话周期）；长期记忆走”事件溯源 + 物化视图”，保留原始来源以支持回溯；写入异步化避免拖慢主链路。
  • 可替代方案：Mem0 / Zep / LangGraph Checkpointer（PostgresSaver）/ 自研（PG + pgvector + 事件表）。
  • 最佳实践：记忆必须可解释与可撤销。原图专门圈注”可视化 + 回溯干预”，这是成熟度的标志：用户投诉”你为什么记错了”时，运营需要能看到这条记忆来自哪一轮对话并一键失效。详见 08 文档。

M15 · 知识中心 / RAG（Knowledge Center）

  • 定位：企业知识的统一供给与质量保障层，由「RAG 门户 + RAG 评测 + RAG 底座」三件套构成（前两项原图圈注）。
  • 功能：
    • RAG 底座：文档接入、解析、切分、Embedding、索引、混合检索、Rerank。
    • RAG 门户：知识源接入自助化、切分与检索参数配置、知识生效状态查看。
    • RAG 评测：金标问答集、召回率/命中率/答案正确性评测、回归对比。
  • 输入：知识源文档、M11/M12 检索请求、M23 知识补全。
  • 输出：检索片段 + 引用元数据 + 相关性分数。
  • 上游：M11、M12、知识运营。下游：向量库、全文索引、对象存储、M18（Embedding/Rerank 调用）。
  • 内部能力：多格式解析、语义/结构化切分、混合检索（向量 + 关键词 + 元数据过滤）、Rerank、引用溯源、知识时效标记。
  • 实现建议：切分保留结构（标题路径进入 chunk 元数据）；检索必须混合（纯向量在专有名词与型号查询上表现差）；强制引用（无引用不作答）。
  • 可替代方案：向量库（Milvus / Qdrant / Weaviate / pgvector / LanceDB）；RAG 框架（LlamaIndex / Haystack / RAGFlow / Dify）；图增强（GraphRAG / LightRAG）。
  • 最佳实践：先建评测集再调参数。绝大多数 RAG 项目失败于”凭感觉调切分大小”。原图把”RAG 评测”与”RAG 门户”并列圈注，说明该架构已认识到 RAG 是工程问题而非算法问题。详见 09 文档。

M16 · 能力中心（Capability Center）

  • 定位：能力的运行时聚合与路由适配层，注册中心的”消费面”。
  • 功能：路由适配（把注册元数据翻译为可执行调用）、能力聚合（跨来源统一视图）、查询门户（能力检索与描述查看）。
  • 输入：M20 注册中心的能力清单、M11 的能力查询。
  • 输出：裁剪后的工具清单（tool manifest，含权限与 Schema）。
  • 上游：M20、M11。下游：M21 MCP、M22 存量业务。
  • 内部能力：协议适配（MCP ↔ 内部 RPC ↔ REST）、能力版本协商、权限过滤、渐进式披露（按意图只暴露相关工具）、健康探测与自动摘除。
  • 实现建议：能力清单强缓存（秒级刷新）+ 变更事件推送；按意图裁剪工具集，单次不超过 10–15 个工具描述，否则模型选择准确率显著下降。
  • 可替代方案：MCP Gateway / 服务注册发现（Nacos / Consul）+ 自研适配层。
  • 最佳实践：工具集裁剪是效果杠杆而非性能优化。把 200 个工具全塞进 Prompt，模型选错工具的概率远高于只给 8 个相关工具。渐进式披露（先给类目，再按类目展开）是当前公认最佳做法。

M17 · 边缘 Agent 框架（Edge Agent Framework）

  • 定位：端侧 AI 能力的云端控制面（见 02 文档 7.2 的关键解读）。
  • 功能：端侧长短记忆定义与同步策略、端侧 RAG 知识包构建与下发、端侧能力中心清单编译、端侧模型路由策略下发。
  • 输入：云端能力/知识/记忆定义、端侧算力等级与版本上报。
  • 输出：端侧能力清单包、知识包、模型选择策略、同步策略。
  • 上游：M14/M15/M16、M20。下游：经 M09/M24 下发至 M04。
  • 内部能力：按算力等级分档编译、增量差分包、版本协商与回滚、灰度下发。
  • 实现建议：端云共用同一份能力定义源（Single Source of Truth），分别编译为云端运行时配置与端侧包；下发必须支持灰度与快速回滚。
  • 可替代方案：OTA 配置下发通道复用 / 远程配置平台（Feature Flag 平台）扩展。
  • 最佳实践：把”端侧能力”当作可发布的制品（有版本、有变更记录、可回滚），而非硬编码在车机固件里。这是端云协同架构与”车机内置助手”的本质区别。

M18 · LLM 网关（LLM Gateway）

  • 定位：模型资源的统一抽象与治理层，成本与稳定性的总闸门。
  • 功能：多模型切换、语义缓存、Token 流量治理（原图圈注三项）；另含限流配额、Fallback、熔断、重试、成本归因、Prompt 版本管理。
  • 输入：M11/M12/M15 的推理请求（model_intent 语义化声明）。
  • 输出：流式/整体结果、Token 与成本明细（→M23）。
  • 上游：M11、M12、M15。下游：模型池（自建 + 外部）、M19 Guardrail、M23。
  • 内部能力：模型能力矩阵与路由策略、语义缓存（向量近似匹配）、前缀/KV 缓存、Token 预算与配额、并发与队列、多厂商适配。
  • 实现建议：请求只声明意图不指定模型（P5）；缓存键必须包含知识版本与用户维度；对时效性意图强制 bypass 缓存；熔断按厂商与模型两级。
  • 可替代方案：LiteLLM / Portkey / OpenRouter / Higress AI 插件 / Envoy AI Gateway / 自研。
  • 最佳实践：把限流单位从 QPS 改为 Token/s + 并发数双维度；把成本标签（业务/Agent/场景/用户群）作为必填字段，否则成本治理无从下手。详见 11 文档。

M19 · 安全围栏防护（Safety Guardrail）

  • 定位：出站方向的最后一道内容管控（图中位于 LLM 网关右侧末端）。
  • 功能：有害内容检测、敏感话题拦截、PII 泄漏检测、越狱输出识别、事实一致性初筛、违规内容改写或阻断、审计留痕。
  • 输入：模型生成内容（流式分段或整体）。输出：通过 / 改写 / 拦截 + 审计记录。
  • 上游：M18。下游：回传链路、审计存储。
  • 内部能力：规则 + 分类模型双层、分档策略（不同业务不同严格度）、流式分段判定、高风险截断。
  • 实现建议：独立服务或 Sidecar，不做进程内库调用（升级节奏不同）；流式场景分段判定 + 尾部整体复检；本地短超时并 fail-closed（超时视为不通过）。
  • 可替代方案：商用内容安全服务 / 开源（Llama Guard、NeMo Guardrails、Guardrails AI）/ 自研规则 + 小模型。
  • 最佳实践：安全组件不可降级（见 01 文档 7）。同时必须建立”误拦截”反馈通道——过度拦截造成的体验损伤同样会导致产品失败。详见 12 文档。

M20 · AI 注册中心（AI Registry Center）

  • 定位：平台元数据权威源，原图最上方并被圈注，是”统一注册”的目标（图中两条”统一注册”箭头指向它）。
  • 功能：MCP 管理、Agent 管理、Skills 管理；含注册审核、版本管理、权限与可见性、灰度规则、依赖与兼容校验、上下线。
  • 输入：研发注册申请、M21 三方 MCP 声明、M22 存量业务能力声明、M11/M12 的自注册。
  • 输出：能力清单与元数据（→M16 → M11）、权限策略。
  • 上游：研发、M21、M22、M11、M12。下游：M16、M17。
  • 内部能力：Schema 校验、描述质量检查、冲突检测（意图重叠）、变更审批流、审计。
  • 实现建议：低 QPS 高可用；读走强缓存 + 变更事件；注册即校验（Schema、描述完整度、示例意图数量）；提供沙箱环境先验证再上线。
  • 可替代方案：服务注册中心（Nacos/Consul）+ 自研元数据层 / API 门户产品扩展 / MCP Registry 规范实现。
  • 最佳实践：注册中心的价值 = 强制性。若允许”未注册也能调用”，注册中心立刻退化为文档站。必须在网关与能力中心两处强制校验能力 ID。

M21 · 第三方 MCP 生态（Third-Party MCP Ecosystem）

  • 定位：外部能力的标准化接入面（图中位于左上，指向 Planner 并向注册中心统一注册）。
  • 功能：以 MCP 协议暴露的外部工具与数据源接入。
  • 输入：Planner/Agent 的工具调用。输出：工具执行结果。
  • 上游：M11、M12（经 M16 适配）。下游：外部服务。
  • 内部能力：协议适配、认证凭据托管、超时与重试、结果 Schema 校验。
  • 实现建议：三方 MCP 一律最小权限 + 独立凭据 + 出网白名单；结果进入上下文前必须隔离标记（视为不可信数据）；版本锁定，变更需重新审核。
  • 可替代方案：OpenAPI 工具封装 / 自研 Tool Adapter / 函数调用网关。
  • 最佳实践：工具返回值是提示注入的主要入口。必须做到：工具结果不与系统指令同区、结果内容经二次 Guard、禁止工具结果直接触发新的工具调用（需模型显式决策且计入预算）。

M22 · 存量业务平台适配（Legacy Business Platform Adapter）

  • 定位：上一代业务能力（Gen-N / Gen-N+1）的接入适配层。
  • 功能：把存量 REST/RPC 业务能力封装为平台可注册、可鉴权、可计量的能力。
  • 输入：Planner/Agent 调用。输出：业务执行结果。
  • 上游：M11。下游：存量业务服务。
  • 内部能力：协议转换、字段映射、错误码归一、超时与降级、能力描述生成。
  • 实现建议：适配层薄且无业务逻辑；为每个存量能力补齐”AI 可用的描述”（存量 API 文档通常不足以让模型正确调用）；设定 Sunset 日期。
  • 可替代方案：MCP Server 封装存量能力（推荐，统一为一种协议）/ BFF 层扩展。
  • 最佳实践：不要试图一次性重写存量系统。正确路径是：适配接入 → 观察真实调用分布 → 只把高频能力原生化 → 低频能力长期保留适配。原图保留存量平台入口，体现的正是这种务实迁移策略。

M23 · 数据平台（Data Platform）

  • 定位：闭环的数据底座（图中右上角，接收”埋点数据回流”）。
  • 功能：埋点接入、清洗、会话与轨迹重建、指标计算、金标集管理、评测、数据集构建、训练与模型注册。
  • 输入：M13 埋点事件、M18 Token 明细、用户反馈、人工标注。
  • 输出：指标看板、评测报告、训练集、新模型（→M18）、画像与知识更新（→M14/M15）。
  • 上游：M13、M18。下游：M14、M15、M18。
  • 内部能力：见 02 文档 10 的数据流图。
  • 实现建议：埋点走消息队列解耦；数据分层（ODS/DWD/DWS）；金标集三分（公开/回归/盲测）；训练数据必须校验授权范围。
  • 可替代方案：企业既有数仓/数据湖复用 + LLM 可观测平台（Langfuse/Phoenix）承接 Trace 层。
  • 最佳实践：隐式反馈优于显式反馈。重问率、打断率、任务完成率、追问轮次这些信号密度远高于点赞点踩，是评测与训练的主信号。详见 14/15 文档。

M24 · 端云状态同步服务（Edge–Cloud State Sync）

  • 定位：图中”车云信息同步”双向箭头所代表的同步能力（跨 L3/L6）。
  • 功能：记忆增量双向同步、能力清单与知识包下发、埋点批量上传、版本协商、冲突解决。
  • 输入：端侧变更集、云端下发包。输出：同步结果与确认。
  • 上游：M04、M17。下游：M09 双向认证网关 → M14/M15/M16。
  • 内部能力：增量差分、变更日志与序号、幂等、冲突合并策略、断点续传、带宽与时机控制（避免行驶中大流量）。
  • 实现建议：单写者原则——同一记忆域只允许一端为权威写方；采用版本向量检测冲突；同步时机避开交互高峰与弱网；大包走后台低优先级通道。
  • 可替代方案：CRDT（适合可自动合并的场景）/ 事件溯源 + 单向物化 / 复用 OTA 差分下发通道。
  • 最佳实践：端云一致性问题在 Demo 阶段完全不可见、上量后必然爆发（表现为”回答自相矛盾”）。必须在阶段一就确定单写者与冲突策略，事后补救成本极高。
