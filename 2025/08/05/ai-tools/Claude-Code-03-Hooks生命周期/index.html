Claude Code Hooks 生命周期：用确定性规则约束 Agent

基于 Claude Code 1.0.68 梳理 Hooks：八个生命周期事件、stdin 输入、退出码与 JSON 决策控制…

Flywhl 17 分钟 更新于 2026.09 #AI工具#开发效率#Claude Code

先读结论

  1. Hook 由 Claude Code 在固定时点执行，不依赖模型记性，适合“每次必须发生”或“绝不能发生”的规则。
  2. 只有退出码 2 会阻断并把 stderr 回灌给 Claude；1 等其它非零码只告警，脚本自身崩溃等于放行。
  3. PreToolUse 先于权限系统运行，返回 allow 会跳过权限确认，自动放行比拦截更需要谨慎。
  4. Stop hook 用 decision: block 把 Claude 拦回来继续干活，必须配合 stop_hook_active 或计数防止死循环。
  5. 约定写 CLAUDE.md，门禁用权限规则，需要看参数内容或必须执行的动作才上 Hook。

在 CLAUDE.md 里写“提交前跑测试”“不要碰 .env”，多数时候管用，但它终究是提示词的一部分：上下文一长、任务一急，模型就可能跳过。Hooks 换了一条路——把规则写成 shell 命令，由 Claude Code 在生命周期的固定时点执行，模型想不想得起来都不影响。

Hooks 在 1.0.38（2025-06-30）发布，本文以写作时的最新版本 1.0.68 为准。一个多月里事件从 4 个增加到 8 个，输入输出协议也补了几轮，下文逐项注明引入版本。

PostToolUse 工具执行成功之后 工具名 1.0.38

这些事件在一次会话中的位置如下，虚线表示与主循环并行的旁路事件：

flowchart TD
  S([启动 / 恢复 / clear]) -->|SessionStart| W[等待输入]

  M -->|生成工具调用| P{PreToolUse}
  P -->|放行| A[权限检查]
  P -->|"阻断：原因回灌"| M
  A -->|允许| T[执行工具]
  T -->|PostToolUse| M
  M -->|回复结束| E{Stop}
  E -->|"decision = block"| M
  E -->|放行| W
  M -.->|Task 子代理结束| SS[SubagentStop]

图里最容易被忽略的是 PreToolUse 与权限检查的先后：hook 先跑，它给出的决定可以直接替代权限系统的判断。这一点决定了后文“自动放行要谨慎”的结论。

配置结构：事件 → matcher → hooks

Hooks 写在 settings 文件的 hooks 字段里，四个层级都能配：

  • ~/.claude/settings.json：用户级，对所有项目生效；
  • .claude/settings.json：项目级，随仓库提交，团队共享；
  • .claude/settings.local.json：项目本地，不提交；
  • 企业托管策略文件：管理员统一下发。

结构是三层嵌套：事件名对应一个数组，数组每项是一组“matcher + 命令列表”。

几条规则：

  • matcher 区分大小写。 普通字符串精确匹配（Write 只匹配 Write 工具），也支持正则（Edit|MultiEdit|Write、Notebook.*）；*、空字符串或省略表示全部。MCP 工具名形如 mcp__<server>__<tool>，可写 mcp__github__.* 匹配整个服务器。UserPromptSubmit、Notification、Stop、SubagentStop 不用 matcher，直接省略。
  • type 目前只有 command。 timeout 以秒为单位，可按命令单独设置（1.0.41 起）。
  • /hooks 菜单可以交互式增删 hook，写入对应的 settings 文件。
  • 配置在启动时做快照。 会话进行中直接改 settings 文件不会立刻生效，Claude Code 会提示 hooks 被外部修改，需要在 /hooks 里复核后才应用。这是安全设计，后文还会提到。
  • 1.0.68 新增 "disableAllHooks": true，排查问题时可以一键停用全部 hook。

输入：一切数据走 stdin

Claude Code 以 JSON 形式把事件上下文写进 hook 进程的 stdin。所有事件都带 session_id、transcript_path（会话记录 JSONL 路径）、hook_event_name（1.0.41 起），1.0.54 起还带 cwd。各事件的专有字段：

事件 专有字段
PreToolUse tool_name、tool_input
PostToolUse tool_name、tool_input、tool_response
Notification message
UserPromptSubmit prompt
Stop / SubagentStop stop_hook_active：当前是否已经因为 Stop hook 而继续执行
PreCompact trigger（manual / auto）、custom_instructions（/compact 后跟的文字）
SessionStart source（startup / resume / clear）

tool_input 的结构随工具而定：Bash 是 command；Read、Edit、MultiEdit、Write 都有 file_path，Edit 另有 old_string / new_string，Write 另有 content。

工具参数不会被放进环境变量。文档为 hook 注入的环境变量只有 CLAUDE_PROJECT_DIR（1.0.58 起，项目根目录绝对路径），其余信息都要从 stdin 解析。拿不准某个工具的输入长什么样时，先挂一个“录音” hook，跑一轮再看文件：

输出：退出码与 JSON 两条通道

退出码

退出码 含义 输出去向
0 成功 stdout 只在 transcript 模式（Ctrl-R）可见；UserPromptSubmit 与 SessionStart 例外，stdout 会加入上下文
2 阻断型错误 stderr 自动交给 Claude 处理，具体效果见下表
其它（含 1） 非阻断错误 stderr 显示给用户，流程照常继续

退出码 2 在各事件上的效果：

事件 退出码 2 的效果
PreToolUse 阻止本次工具调用，stderr 给 Claude
PostToolUse 工具已执行，stderr 作为反馈给 Claude
UserPromptSubmit 拒绝处理并擦除这条提示，stderr 只给用户
Stop / SubagentStop 不允许结束，stderr 给 Claude（或子代理）
Notification、PreCompact、SessionStart 无阻断作用，stderr 只给用户

这里有个设计上的陷阱：脚本自己出错也是“其它非零”。jq 没装（127）、JSON 解析失败、set -e 提前退出，都会被当成非阻断错误，工具调用照常执行——安全类 hook 一崩溃就等于放行。所以拦截型脚本必须显式把自身异常转换成 exit 2（失败即拦截）；反过来，格式化、通知这类辅助 hook 不应轻易用 2，否则一个环境问题就会卡住 Claude 的正常工作。

JSON 输出

需要更细的控制时，在 stdout 输出 JSON 并以 0 退出。

适用事件 字段 效果
全部 continue: false + stopReason 让 Claude 停止后续处理；stopReason 只给用户看。优先级高于任何 decision: "block"
全部 suppressOutput: true 不在 transcript 模式显示 stdout
PreToolUse hookSpecificOutput.permissionDecision：allow / deny / ask，配 permissionDecisionReason allow 绕过权限系统直接执行，理由给用户；deny 拒绝本次调用，理由给 Claude；ask 弹出确认，理由给用户（1.0.59 起）
PostToolUse decision: "block" + reason 把 reason 作为反馈自动发给 Claude
UserPromptSubmit decision: "block" + reason；hookSpecificOutput.additionalContext 拒绝并擦除提示（reason 只给用户）；或在不拦截时追加上下文（1.0.59 起）
Stop / SubagentStop decision: "block" + reason 不许结束；reason 必填，Claude 靠它知道接下来做什么
SessionStart hookSpecificOutput.additionalContext 把字符串注入会话上下文

PreToolUse 旧写法 decision: "approve" | "block" 已标记弃用但仍兼容。注意 continue: false 与 permissionDecision: "deny" 的区别：前者让整个处理停下来，后者只否决这一次调用，Claude 会读到理由并换个做法。

执行模型

  • 并行执行。 同一事件匹配到的所有 hook 并行运行。两个 hook 不能依赖执行顺序，也不要同时写同一个文件；需要顺序就合并进一个脚本。
  • 超时。 默认 60 秒，timeout 可单独调；一个命令超时不影响其它命令。被取消的 hook 不会产生任何决定，拦截也就不存在了，所以跑测试这类慢任务必须把超时调到实际耗时之上。
  • 运行环境。 在当前目录执行，继承 Claude Code 的环境变量。Claude 的工作目录可能已经切换过，引用项目内脚本一律用 "$CLAUDE_PROJECT_DIR"/...。
  • 可见性与调试。 PreToolUse、PostToolUse、Stop 的执行进度显示在 transcript 模式；Notification 的输出只进 debug 日志。claude --debug 会打印匹配过程、实际执行的命令和退出码，是排查“hook 为什么没触发”的第一工具。

路径外层的转义引号是为了应对目录名含空格。脚本兼容 macOS 自带的 bash 3.2。

例 1：拦截危险 Bash 命令

为什么用 PreToolUse。 它是命令执行前唯一的拦截点。权限规则的 Bash 匹配是前缀式的，Bash(git push --force:*) 拦不住参数换了位置的 git push origin main --force；hook 能用正则看完整命令，还能把“为什么拦、该怎么做”写进 stderr，Claude 读到后通常会改用 --force-with-lease 或转而询问用户。--force-with-lease、rm -rf ./dist、git reset --soft 这类安全变体都不会被误拦。

失败时的行为。 jq 缺失或输入无法解析时按阻断处理，宁可误拦也不漏放。要清楚它的边界：正则黑名单挡得住手滑，挡不住刻意绕过（变量拼接、base64 -d | sh、python -c），它是护栏而不是沙箱，不可信的任务应放进容器或虚拟机里跑。

例 2：保护 .env 与密钥文件

为什么用 PreToolUse + JSON。 单纯禁止读 .env，权限规则 "deny": ["Read(.env)"] 就够了，而且更简单。这里用 hook 是因为多了三件权限规则做不到的事：.env.* 一律拒绝但放行 .env.example；同一路径读写区别对待；拒绝理由里给出替代路径，Claude 不会反复重试同一个被拒的操作。禁止 Claude 改写 .claude/settings.json 也有必要——否则它可能在“修复问题”时顺手删掉挡路的 hook，虽然启动快照机制保证本次会话不受影响，下次启动就生效了。

失败时的行为。 deny 只否决这一次调用，会话继续。它的盲区是 Bash：cat .env、grep -r API_KEY . 不经过这四个工具，需要在例 1 里补规则，或者干脆不在工作区放明文密钥。

例 3：编辑后自动格式化

为什么用 PostToolUse。 格式化需要文件已经落盘，而且它是纯确定性动作，交给模型做既浪费回合又不稳定。只处理 tool_input.file_path 指向的单个文件，不跑全仓格式化，避免改动与本次任务无关的文件、污染 diff。

失败时的行为。 这个脚本刻意区分两种失败：工具没装属于环境问题，静默 exit 0；格式化器报错通常意味着 Claude 刚写出了语法错误的代码，用 exit 2 把错误信息交给它——PostToolUse 阶段工具已经执行完，2 在这里不是阻断，而是即时反馈。如果团队不希望打断 Claude，改成 exit 1 只提示用户即可。

例 4：测试不绿不收工

为什么用 Stop。 模型说“已完成”是自我评估，Stop 是唯一能把它拦回来的时点。decision: "block" 的 reason 会成为 Claude 的下一步指令，所以要写清楚“修什么、不许做什么”；附上失败输出末尾 40 行，省掉它再跑一遍测试找原因。

失败时的行为。 三道保险：工作区无改动直接放行，纯问答不会被测试拖慢；stop_hook_active 加计数文件限制最多拦 3 次，超过后用 exit 1 放行并提示用户，避免陷入“修不好—被拦—再修”的死循环；timeout 设为 300 秒，高于测试实际耗时，否则 hook 被取消，拦截形同虚设。测试集很大时，把 npm test 换成只跑受影响用例的命令，如 jest --onlyChanged、pytest --lf。还要意识到 hook 只检查“测试是否通过”，挡不住模型为了过测试去改测试，reason 里的约束加上人工审 diff 才是完整闭环。子代理的收尾可以用同样的思路挂在 SubagentStop 上。

该用 Hook、CLAUDE.md 还是权限规则

需求 首选 为什么不是另外两个
命名风格、架构偏好、“优先用 X”这类需要判断的约定 CLAUDE.md 规则常有例外，需要模型结合语境取舍；写成 hook 会误伤
某类调用一律禁止或免确认，如 Read(.env)、Bash(curl:*)、Bash(npm run test:*) 权限规则 声明式、无脚本维护成本，deny 优先于 allow；hook 能做但更脆弱
要看参数内容才能判断，且要告诉 Claude 为什么、该怎么改 PreToolUse hook 权限规则只有前缀和路径匹配，给不出理由；CLAUDE.md 不保证执行
每次改完都必须发生的动作：格式化、代码生成、审计日志 PostToolUse hook “记得格式化”写进 CLAUDE.md 会被忘；权限规则管不到调用之后
完成标准：测试必须通过才算完 Stop hook 其余两者都无法否决模型的“我做完了”
每次会话都需要的动态信息：当前分支、最近提交、未关闭的 issue SessionStart hook CLAUDE.md 是静态文本，写进去就会过期
提示词里不能出现密钥 UserPromptSubmit hook 另外两者都在模型看到提示之后才起作用

一句话概括：CLAUDE.md 是建议，权限规则是门禁，Hook 是流水线。三者叠加使用，而不是互相替代。

安全注意事项

  • Hook 以当前用户的完整权限运行任意命令，没有沙箱。 能读写你账号能访问的一切文件，写错一个 rm 与恶意脚本的破坏力相同。
  • 项目级 hook 随仓库分发。 .claude/settings.json 里的 command 对每个拉取仓库的人都会执行。把 .claude/ 目录的变更当作 CI 配置变更来审查（例如纳入 CODEOWNERS），打开陌生仓库前先读一遍其中的 hooks。
  • 启动快照是一道防线，不是全部。 会话内对 settings 的修改需要在 /hooks 复核后才生效，挡住了“会话中途被改写”的路径；但下一次启动会读取新配置，所以例 2 里禁止 Claude 改写 settings 仍然必要。
  • allow 比 deny 危险。 PreToolUse 返回 allow 会绕过权限系统，自动放行的条件要写得尽量窄，最好只对只读工具使用。
  • 拦截型 hook 失败即拦截。 依赖缺失、解析失败都要转换成 exit 2，别让一次崩溃变成放行。
  • 输入不可信。 变量一律加引号（"$path" 而非 $path），检查路径中的 ..，脚本用绝对路径引用，避开 .env、.git/、密钥文件。

2026-09 补记：事件扩展到 30 多个，hook 不再只能跑 shell

本文写于 1.0.68 时期。一年后回看，核心协议——stdin JSON、退出码 2 阻断、decision / permissionDecision 字段——保持兼容，上面四个脚本无需修改即可运行；变化主要在三个方向。

事件扩展。 截至 2026 年 9 月官方文档列出 33 个事件。对工程最有用的几个：

事件 版本 用途
SessionEnd 1.0.85 会话结束时清理临时资源、归档日志
SubagentStart 2.0.43 向子代理注入额外上下文（不能阻止其启动）
PermissionRequest 2.0.45 权限弹窗出现时按自定义逻辑自动批准或拒绝
PostToolUseFailure — 工具执行失败后记录或给出修复提示
Setup 2.1.10 由 --init、--maintenance 等参数触发的仓库初始化与维护
ConfigChange 2.1.49 会话中配置文件变动时审计，可选择阻止
WorktreeCreate / WorktreeRemove 2.1.50 代理使用 worktree 隔离时自定义创建与清理
InstructionsLoaded 2.1.69 追踪 CLAUDE.md 与 .claude/rules/*.md 何时被加载
PostCompact 2.1.76 压缩完成后记录生成的摘要、同步外部状态
StopFailure 2.1.78 因限流、鉴权失败等 API 错误结束回合时告警
CwdChanged / FileChanged 2.1.83 类似 direnv 的环境随目录切换
TaskCreated / TaskCompleted / TeammateIdle 2.1.33 起 多代理协作中的任务与成员状态管控

原有事件也有增强：Stop 输入新增 last_assistant_message（2.1.47），不再需要解析 transcript 就能拿到最后一条回复；PreToolUse 可以返回 additionalContext（2.1.9）；PreCompact 从 2.1.105 起可以阻止压缩。

hook 类型从 1 种变成 5 种。 除 command 外，prompt 把 hook 输入交给模型做单轮判断，最早在 2.0.30 用于 Stop；agent 启动可调用 Read、Grep 等工具的验证子代理，仍标注为实验特性；http（2.1.63）把输入 POST 到指定 URL，由响应体返回同样格式的 JSON；mcp_tool（2.1.118）直接调用已配置 MCP 服务器上的工具。并非所有事件都支持全部类型，SessionStart 就只接受 command 和 mcp_tool。执行层面，工具类 hook 的默认超时从 60 秒改为 10 分钟（2.1.3）；新增 if 字段（2.1.85），用权限规则语法（如 Bash(git *)）预先过滤，减少无谓的进程启动；async: true 让 command hook 在后台运行、结果在下一轮交给 Claude。本文例 4 若改成异步就失去了拦截能力，异步只适合通知、日志这类不需要做决定的任务。

分发渠道。 插件可以在 hooks/hooks.json 中携带 hooks，脚本路径用 ${CLAUDE_PLUGIN_ROOT} 引用，2.1.0 起插件也能提供 prompt 与 agent 类型；同一版本起，skill 与子代理的 frontmatter 可以声明只在自身生命周期内生效的 hooks。企业侧可用 allowManagedHooksOnly 只允许托管配置中的 hooks 运行，排障时用 --safe-mode（2.1.169）一次性停用 CLAUDE.md、插件、skills、hooks 与 MCP。这也意味着，本文“审查项目级 hook”的要求需要扩展到所安装的每一个插件。
