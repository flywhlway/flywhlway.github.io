前言

这份指南要回答的问题很具体：当你的 API 从”一次性返回 JSON”变成”持续推送
事件流”之后，你手里的接口文档和调试工具还够用吗？

答案是：文档工具（Swagger UI / Knife4j）基本够用但体验落后；调试工具
（旧版 Postman、curl）在流式场景下要么看不到过程、要么要写额外脚本。
过去一年，一批新工具——Scalar、Yaak、Bruno——针对这个缺口做了专门优化。
本文把它们放进一个真实的 LangGraph Agent 项目里，逐一验证”到底好用在
哪、边界在哪”，而不是停留在功能列表对比。

约定：全文出现的命令、代码、运行结果，均在 langgraph-agent-api-poc/
工程中实测通过（Python 3.12 / FastAPI 0.141 / LangGraph 1.2 / LangChain
1.3 / Bruno CLI 4.0，2026-08）。如果你按本文操作却得到不同结果，大概率
是版本差异，请对照附录 D 的版本清单排查。

第一部分：背景——为什么 LLM / Agent API 需要新一代工具

1.1 从”一次性响应”到”事件流”：API 形态的根本变化

传统 REST API 的心智模型很简单：

Swagger UI 的 “Try it out” 就是照着这个模型设计的：发请求、转圈、拿到
一整个 Body、格式化展示。这套模型服务了 REST API 十几年，问题不出在
它本身，而出在 LLM / Agent API 完全不是这个形状：

画成时序图更直观——这也是本文配套 POC 工程里 /api/v1/chat/stream
端点的真实事件序列（第三部分会给出这条时序对应的完整 curl 实测输出）：

sequenceDiagram
    participant C as 调用方（Yaak / Bruno）
    participant A as Agent API（FastAPI + LangGraph）
    participant T as 工具（Tool）
    participant M as LLM

    C->>A: POST /api/v1/chat/stream
    A->>M: 发起推理
    Note over A,M: event: thinking
    M-->>A: 决定调用工具
    A->>T: 执行 get_weather(city)
    Note over A,T: event: tool_start
    T-->>A: 返回结果
    Note over A,T: event: tool_end
    A->>M: 携带工具结果继续推理
    Note over A,M: event: thinking
    M-->>A: 逐 token 流式输出
    loop 每个 token
        A-->>C: event: token
    end
    A-->>C: event: finish（完整答案 + 工具调用轨迹）

一次 Agent 调用可能跨越几秒到几十秒，中间夹杂着模型的中间推理、一次或
多次工具调用、以及最终答案的逐 token 输出。用户（或者调试这个 API 的你）
关心的不只是”最后拿到了什么”，还包括”过程中发生了什么、卡在哪一步、
哪次工具调用返回得不对”。这些信息只存在于事件流的中间状态里——
一次性等待到底的调试方式，天然丢失了这些信息。

1.2 传统工具的结构性局限

以 Swagger UI / Knife4j 为代表的传统组合，在处理这几类协议时体验分化
明显：

协议 LLM/Agent 场景常见度 Swagger UI Knife4j
普通 JSON 高 ✅ 完善 ✅ 完善
SSE（text/event-stream） ★★★★★ 主流 部分支持，展示差 基本继承 Swagger 能力，无改进
Chunked Transfer ★★★★★ 主流 不友好 不友好
JSON Lines（.jsonl） ★★★★ 常见 基本无展示能力 不支持
WebSocket Agent 场景大量使用 不支持 不支持
MCP Stream 新兴但增长快 不支持 不支持

Knife4j 值得单独说一句：它的技术栈是 Knife4j → SpringDoc → OpenAPI → SwaggerUI，本质是换了一层更好看的 UI，并没有在协议支持上做任何扩展——
所以它在 Spring AI / 任何 SSE Controller 上的表现，和原生 Swagger UI
没有本质区别，同样只能等一整个响应结束后一次性展示。

这不是这两个工具”没做好”，而是它们的设计假设（一次请求—一次响应）从根
上就和”一次请求—一串事件”的场景不匹配。

1.3 新一代工具全景图

围绕”文档”和”调试”两个职责，目前收敛出几个方向：

工具 定位 REST SSE WebSocket MCP 备注
Scalar API 参考文档 + 轻量调试 ✅ 已知局限（见 2.6） 部分 实验性 Agent 配置 OpenAPI 3.1/3.2 渲染质量目前业内领先

Hoppscotch Web API 客户端 ✅ ✅ ✅ – 适合免安装、临时调试

本文选择 Scalar / Yaak / Bruno 三者深入讲解，是因为它们分别代表三种
互补的定位（文档门户 / 桌面全能调试 / Git 原生团队协作），组合起来
基本覆盖企业场景的完整需求，这也是第五部分要讲的参考架构的由来。

第二部分：Scalar —— 从入门到企业级

2.1 Scalar 是什么

Scalar 是一套开源 API 平台，核心是”用一份 OpenAPI/Swagger 文档，渲染出
现代化的交互式参考文档”，同时自带一个可独立使用的 API 测试客户端
（@scalar/api-client）。它常被拿来直接替换 Swagger UI，原因很直接：
同样吃一份 openapi.json，渲染出来的文档在排版、代码生成、搜索、暗色
模式这些维度上普遍被认为优于原生 Swagger UI，而接入成本只有几行代码。

2.4 把 OpenAPI 版本讲清楚：3.1 现状与 3.2 的流式新特性

这里有个容易踩的认知误区，值得单独展开。

FastAPI 目前（fastapi==0.141.1 实测）默认且只会生成 OpenAPI
3.1.0。FastAPI(openapi_version=...) 这个参数确实存在，但它只是把
生成结果里 "openapi": "3.1.0" 这行字符串替换掉，不会让 Schema
结构真的符合你指定的目标版本——FastAPI 核心维护者在官方 GitHub
讨论里把这种做法直接称为”hack”，滥用它可能生成不合法的 OAS 文档。

同时，OpenAPI 3.2.0 已于 2025 年 9 月正式发布，和 LLM/Agent 场景
最相关的新特性是把流式响应变成了 OpenAPI 的一等公民：新增 itemSchema
关键字，可以在 content 对象里显式描述”这是一个流，每条消息长这样”，
而不再是只能笼统写一个 text/event-stream + 一坨 string schema。
Redocly 等文档工具已经跟进支持渲染 3.2；但截至本文写作时，FastAPI
的内置生成器还没有原生输出 3.2 语法的能力。

所以 POC 工程里对 SSE 端点的文档化，采用的是一个更稳妥的折中方案
（见 app/openapi_ext.py）：

  1. openapi_version 老老实实保持 FastAPI 真实生成的 3.1.0，不伪造版本号；
  2. 用标准的 responses + text/event-stream 内容类型，把这是一个流
    描述清楚；
  3. 额外挂一个 x-sse-events vendor extension（x- 前缀是 OpenAPI
    官方预留给扩展字段的约定，Scalar / Redocly 等工具都会原样保留展示），
    结构化列出这个流会推送哪几类事件：

打开 /scalar 页面对应端点，就能在文档里直接看到这份事件说明——
这比”祈祷调用方去读你写在 Wiki 里的另一份说明”可靠得多。如果你的
团队想要更严格的 3.2 itemSchema 语义（比如要生成强类型 SDK），
目前现实的做法是：用一个构建期脚本读出 FastAPI 生成的 openapi.json，
在其基础上补丁式地把 text/event-stream 部分改写成 3.2 语法后再发布，
而不是等 FastAPI 官方支持——这个脚本本身不复杂，但已经超出本文范围。

2.5 已知限制：Scalar 调试 FastAPI SSE 流的现状

这一点非常重要，直接关系到你该拿 Scalar 干什么、不该指望它干什么。

Scalar 内置的 API 测试客户端理论上支持流式响应，但截至本文写作时，
scalar/scalar 官方仓库有一个仍未关闭的 Issue（#7282，2025-11 提交），
描述的现象是：用 FastAPI 的 StreamingResponse 返回 text/event-stream
时，Scalar 的”Test Request”面板会卡住、看不到任何消息，而用浏览器原生
EventSource 连接同一个端点却完全正常。也就是说，问题出在 Scalar 客户端
对这类分块流的处理上，不是 FastAPI 或你的接口本身有问题。

实测复现：打开 POC 的 /scalar 页面，找到 POST /api/v1/chat/stream，
点击右侧”Test Request”发送——文档区域（Schema、示例、x-sse-events
说明）展示完全正常，但如果你期待像 Yaak / Bruno 那样看到事件逐条刷新，
目前大概率会失望。

结论：把 Scalar 定位成”文档门户 + 简单 REST 接口的轻量试调用”，
流式接口的交互式调试交给下一节的 Yaak 和 Bruno——这不是妥协，而是
三个工具本来就该分工不同（详见第五部分）。

2.6 企业级集成

多环境与鉴权：结合 2.3 的 servers + authentication 参数，可以
让同一份文档同时服务本地开发、预发、生产三套环境，团队成员切换下拉框
即可，不需要维护三份文档。

CI 自动发布文档：Scalar 只需要一份 openapi.json，所以典型的 CI
流程是——测试通过后，GET /openapi.json 落盘，作为构建产物发布到内部
文档站（可以是一个纯静态的单 HTML 文件，用前面提到的 CDN 方式加载
@scalar/api-reference），文档和代码天然同步，不存在”文档忘了更新”
的问题。

跨域与代理：如果你的文档站和 API 服务不同源，浏览器直接调用会遇到
CORS 限制。Scalar 提供了官方代理 scalar_proxy_url="https://proxy.scalar.com"
可以直接用；企业内网环境通常更倾向于自建反向代理或直接把 CORS 头配置
在网关层（本文第五部分会提到，这一层其实和你现有的 AI 网关配置是同一
件事，不需要为 Scalar 单独再搭一套）。

第三部分：Yaak —— 从入门到企业级

3.1 Yaak 是什么

Yaak 是一款桌面 API 客户端（基于 Tauri，体积和资源占用明显小于
Electron 系应用），定位是”Postman 的本地优先替代品”：核心卖点是
本地优先、不强制云同步、不需要账号——所有请求历史都存在你自己的
设备上，密钥用系统 Keychain 加密（ChaCha20-Poly1305）。它由做过
Insomnia 的开发者独立开发，目前是个人维护的开源项目。

对本文的场景来说，Yaak 最重要的能力是：REST / GraphQL / gRPC /
WebSocket / SSE 全部在同一个客户端里统一处理，不需要为不同协议切换
不同工具。

3.2 安装与快速上手

从 yaak.app 下载对应平台的安装包（macOS / Windows /
Linux 均支持），打开后创建一个 Workspace，即可开始添加请求。

3.3 两种方式导入本项目的 API

Yaak 官方支持导入 OpenAPI 3.0/3.1、Postman Collection v2/v2.1、
Insomnia v4+、Swagger 2.0、curl 命令（Settings → Import Data）。
对应 POC 工程 yaak/ 目录，提供两条路径：

方式一：直接导入 OpenAPI（零文件、最快）

Import → From URL → 粘贴 http://localhost:8000/openapi.json。
Yaak 会读取 FastAPI 生成的 OpenAPI 3.1 描述，为每个 operation 自动
生成请求。优点是零维护、永远和代码同步；缺点是请求体是按 JSON Schema
生成的占位符（比如 "message": "string"），需要你手动换成有意义的值。

方式二：导入预置的 Postman Collection（推荐用于本教程演示）

yaak/langgraph-agent-poc.postman_collection.json 是一份标准的
Postman Collection v2.1 文件——选择这个格式而不是 Yaak 私有的工作区
导出格式，是因为 v2.1 是 Yaak 官方明确支持导入、同时被 Bruno / Insomnia
等几乎所有主流客户端通用识别的”最小公分母”格式，可移植性最好。
Import → From File，选中该文件即可，导入后已经预置好天气 / 计算两条
工具调用路径的示例请求体，以及 baseUrl 环境变量。

3.4 SSE 流式调试实战

这是 Yaak 相对 Scalar 的核心差异点。打开导入后的”Chat SSE 流式调用”
请求并发送：Yaak 识别到响应头 Content-Type: text/event-stream 后，
会自动切换到流式响应视图——thinking / tool_start / tool_end /
token / finish 五类事件会像日志一样逐条追加显示，你可以清楚看到
“模型先调用了 get_weather，拿到结果后又开始逐 token 吐出最终答案”这个
完整过程，而不是等连接关闭后才看到一整块文本。

3.5 环境变量与请求链

Yaak 支持在多个 Workspace / Environment 之间切换 baseUrl 等变量
（{{baseUrl}} 模板语法），也支持”请求链”——把上一个请求的响应字段
引用到下一个请求里，适合”先登录拿 Token，再用 Token 调用业务接口”这类
场景。本 POC 没有鉴权环节，暂时用不上，但企业内部接入真实网关时通常会
用到。

3.6 企业级集成

CLI 与 MCP Server：Yaak 官方文档明确写着”Connect your own agents
via the CLI or MCP server”——也就是说，Yaak 本身可以作为一个工具被
其他 Agent（包括 Claude Code）调用，而不仅仅是人类打开 GUI 使用。
对于已经在搭建内部 Agent 工作流的团队，这意味着可以让编码 Agent 直接
读取、甚至回归校验 Yaak 里维护的请求集合，形成”Agent 调试 Agent API”
的闭环。

Secrets 与安全：请求中的密钥可以标记为 Secret，加密存储在操作系统
的 Keychain 里，不会明文写进导出文件——这一点在把 Collection 分享给
同事或提交进仓库时尤其重要。

Git 协作：”Mirror workspace data to a directory” 功能可以把工作区
数据镜像成一个纯文本目录，配合 Git 做版本控制和 Dropbox 之类的网盘同步，
不强制使用 Yaak 自己的云服务。

导出与迁移：需要说明一点——Yaak 目前没有原生的”一键导出为
Postman 格式”能力（它的原生导出是自己的工作区 JSON），社区维护了一个
yaak2postman CLI 工具补这个缺口。如果你的团队需要”Yaak 里调试、
再把 Collection 分发给还在用 Postman/Bruno 的同事”这种双向流转场景，
建议一开始就采用本文 3.3 节”方式二”的思路——用通用的 Postman v2.1
格式作为团队共享的”源文件”，各自导入自己习惯的客户端，而不是依赖某个
工具的私有格式作为唯一真源。

3.7 结合 POC 实操小结

  1. 导入 yaak/langgraph-agent-poc.postman_collection.json；
  2. 依次发送”健康检查” → “Chat 同步调用（天气）” → “Chat 同步调用（计算）”，
    确认返回结构符合预期；
  3. 发送”Chat SSE 流式调用”，观察响应面板的实时事件流；
  4. 尝试把请求体里的 message 换成别的问题（比如同时问天气又要求算术），
    观察 Agent 依次触发两次工具调用的完整事件序列。

第四部分：Bruno —— 从入门到企业级

4.1 Bruno 是什么

Bruno 是一款开源、Git-First 的 API 客户端，和 Yaak 最大的理念差异在于：
每个请求都是磁盘上的一个纯文本文件（.bru 格式，使用专门设计的
Bru DSL），Collection 就是一个普通文件夹，可以原样提交进你的 Git
仓库、走 PR review、和业务代码同一个生命周期管理。这也是它被称为
“Git-Friendly API Client”的原因——不是”支持导出到 Git”，而是它本身
就没有别的存储形式。

4.2 安装与创建第一个 Collection

打开 Bruno 桌面版，New Collection，选择一个本地目录——Bruno 会在这个
目录下生成一个 bruno.json 文件，这个文件的存在与否是 Bruno 判断
“这是不是一个合法 Collection”的依据。

4.3 Bru 语言语法精讲

Bru 是一种块状（block-based）DSL，每个 .bru 文件由若干个块组成，
块内是简单的 key-value 或者文本。以 POC 工程里实际使用、并且已经用
真实 Bruno CLI 跑通的请求文件为例（bruno/langgraph-agent-poc/02-chat-sync-weather.bru）：

几个关键 Block 的作用：

Block 作用
meta 请求名称、类型（http / graphql）、在文件夹内的排序（seq）
get / post / put / delete HTTP 方法块，内含 url、body 类型、auth 方式
headers 请求头，字典块；key 前加 ~ 可以临时禁用某一行而不删除它
body:json / body:text / … 请求体，按类型分块
vars 定义变量（也可以出现在环境文件里，见下）
script:pre-request / script:post-response 请求前后执行的 JS 脚本，常用来做 bru.setEnvVar() 之类的变量传递
tests 用 Chai 断言库风格写测试用例，bru run 会汇总执行结果
assert 更轻量的断言写法（res.status: eq 200），适合简单场景
docs 给这个请求写 Markdown 说明，桌面版里会在”Docs”标签页展示

4.6 测试与断言

POC 里给天气、计算两条同步调用路径都写了 tests 断言，覆盖三层验证：

  1. HTTP 状态码是否正确；
  2. 响应体结构是否符合预期（answer 字段存在）；
  3. 业务语义是否正确——不只是”接口没报错”，而是”Agent 确实调用了
    该调用的工具，工具返回的结果也确实正确”（比如断言
    tool_calls[0].output 里包含计算的正确结果 90）。

这一层业务语义断言，恰恰是 Agent API 测试里最容易被忽略、但又最重要
的部分——传统 REST 接口”状态码 200 + 字段存在”往往就够了，但 Agent
接口即便状态码和结构都对，也完全可能因为模型没有触发预期的工具调用而
在业务上是错的。

第五部分：三者协同的企业级参考架构

5.1 职责边界：文档、调试、可观测性不应该是同一个工具

前四部分刻意把 Scalar 和 Yaak/Bruno 分开讲，背后是一个明确的架构判断：
“给人看的文档”、”给人用的调试工具”、”给系统用的运行时观测”，是三件
不同的事，不应该指望用一个工具全包圆。

  • Scalar 回答”这个接口长什么样、该怎么调”——面向第一次接触这个 API
    的人，强调可读性；
  • Yaak / Bruno 回答”这次调用具体发生了什么、哪一步不对”——面向正在
    开发/联调的人，强调交互性和过程可见性；
  • OpenTelemetry / Langfuse 回答”生产环境里这类调用整体表现如何、
    P99 延迟多少、哪个环节最容易失败”——面向运维/SRE，强调聚合视角
    和长期趋势    。

把这三层职责混在一起，通常是”Swagger UI 里硬塞一个日志查看器”这种
四不像方案的根源。

5.3 落地到你现有技术栈的建议

如果你的 AI 网关已经是 Higress 或 Kong、可观测性已经走 OTel 统一埋点
再分发到 Tempo/Prometheus/Loki/Langfuse——那么引入 Scalar/Yaak/Bruno
不需要新增任何基础设施，只是在已有分层上补齐”文档”和”调试”这两块：

  • 网关层不用动：Scalar 读取的是服务自己暴露的 openapi.json，
    Yaak/Bruno 发出的请求本质上和任何其他客户端一样要经过网关鉴权/限流——
    三个新工具都是”网关的调用方”，不是要接入网关内部的新组件。
  • 可观测层不用动：Scalar/Yaak/Bruno 产生的是调试期的人工调用，
    Langfuse/OTel 观测的是运行时的真实流量，两者本来就是互补而非重叠
    的数据源——不需要、也不应该把调试工具的请求硬接进生产 Trace 链路。
  • 真正要做的两件事：
    1. 给 FastAPI / Spring Cloud 服务补上本文第二部分讲的 OpenAPI 元数据
      （Tags、Examples、x-sse-events 之类的扩展），让 Scalar 出来的
      文档质量对得起”企业级”三个字；
    2. 把 Bruno Collection（或 Yaak 的 Postman 导出）作为契约测试纳入
      CI，衔接到已有的 Deploy Checklist 流程里，作为”发布前最后一道
      接口层回归”。

这也符合”确定性系统 × 概率性 AI 融合”（deterministic × probabilistic
fusion）一贯的思路——LLM 的输出是概率性的，但围绕它的接口契约、事件
schema、CI 回归应该是确定性的、可重复验证的。Bruno 的 tests 断言
（4.6 节）本质上就是在给”Agent 是否触发了正确的工具调用”这件事，
建立一层确定性的护栏。

5.4 分阶段落地建议

不建议一次性把三个工具都铺开，比较务实的顺序：

  1. 第一阶段：先给最核心的 1-2 个 Agent 服务接入 Scalar，把文档
    这块的欠账还上——成本最低（几行代码），团队认知负担也最小；
  2. 第二阶段：选一个正在联调的新接口，用 Bruno 建 Collection、
    写 tests 断言，接入 CI 作为回归的一部分——这一步开始能看到
    “调试即测试”的复利；
  3. 第三阶段：把 Bruno Collection（或对应的 Postman 导出）分发给
    团队，个人偏好用 GUI 调试的同事可以选 Yaak 导入同一份文件——不需要
    强制统一工具，统一的是”契约”这份文件本身。

6.6 常见问题 FAQ

Q: stub 模式下换一个问题，Agent 没有调用任何工具就直接回答了？
A: 正常现象——app/stub_llm.py 的关键词匹配只覆盖”天气””计算”两类
场景，其他问题会走”不调用工具，直接返回一段说明性文字”的分支。想验证
更多工具调用场景，直接换成真实模型（6.3 节）。

Q: Scalar 的 Test Request 面板发 SSE 请求没反应？
A: 这是 2.5 节讲过的已知限制（scalar/scalar#7282），不是你的配置
问题。用 Yaak 或 Bruno 调试 SSE。

Q: Bruno CLI 提示脚本相关的沙箱/权限错误？
A: 检查 Bruno CLI 版本，v3.0.0 起默认 Safe Mode，需要外部 npm 包或
文件系统访问的脚本要显式加 --sandbox=developer（4.7 节）。

Q: 想要多轮对话记忆，session_id 好像不起作用？
A: 当前版本 session_id 只是透传字段（见 app/main.py 里的
configurable.thread_id），没有接入持久化的 LangGraph checkpointer。
生产环境可以接入 PostgresSaver / RedisSaver 等实现，这部分被
刻意排除在本 POC 范围之外，以保持”只讲文档/调试工具”这条主线的
聚焦。
