token 经济学：AI 原生架构的成本工程

《复杂性的驯兽师》系列 · 第四篇

上一篇建好了质量防线，末尾抛出一个更冷峻的问题：证明了系统”好”，还要证明它”值”。这一篇算这笔账。大模型让边际成本归零的时代终结，token、GPU、上下文成为新的稀缺资源，成本第一次重新成为一等架构约束。本文给出从单次调用到基础设施的完整成本工程体系——三本账、容量规划公式、FinOps 治理，让每一个 token 都可核算、可优化、可决策。

引子：一份让 CFO 皱眉的账单

先讲一个数字。某个多智能体能力上线首月，账单是团队预估的两倍多。排查过程在篇一里出现过——近七成 token 消耗在一个质量把关的评审 Agent 上，它陷入与生成 Agent 的反复自我修正，每轮携带全量历史。加一条”最大修正轮次”的确定性护栏后，成本直接降了六成。

这件事真正的教训不在于那条护栏，而在于一个更基础的失职：上线之前，没有人能说出这个系统单次会话大概花多少钱。 我们精心设计了它的边界、契约、降级、评估——唯独没有为它的成本建过任何模型。它像一辆没装油表的车，跑起来才发现油箱在漏。

这暴露了一个行业性的认知滞后。过去二十年，云计算把软件的边际成本摊薄到近乎归零，”成本核算”逐渐淡出架构师的日常词汇——加一次调用、多一个副本、跑一遍验证，几乎都是免费的。这种”成本无感”的思维惯性，撞上大模型时会付出真金白银的代价：LLM 的每一次调用都在燃烧成本，而且这成本随调用量线性、在多智能体系统里甚至指数放大。

架构师必须把成本重新请回决策桌的正中央。这一篇讲怎么算三本账——调用账、容量账、人力账，以及怎么用 FinOps 把它们管起来。

一、成本为什么回来了：三种新稀缺资源

要理解成本工程，先理解 AI 时代到底新增了哪些稀缺资源。传统架构里，CPU、内存、带宽、存储早已被云的弹性和规模效应驯服。大模型引入了三种定价逻辑完全不同的新资源：

token——按量计费的水表。 这是最直接的一种。输入 token 和输出 token 分别计费（通常输出更贵），价格随模型能力分档，越强的模型每 token 越贵。token 的关键特性是它不是一次性成本，而是流量成本——系统每服务一个请求就消耗一次，调用量涨十倍，这部分成本就涨十倍。传统软件优化关注的是”占用多少”（内存、磁盘），AI 成本优化关注的是”流过多少”（token 吞吐），这是思维方式的根本切换。

GPU——按卡时燃烧的火炉。 如果选择自建推理，成本载体从 token 变成 GPU 卡时。GPU 的特性是固定成本高、利用率决定单价——一张卡不管有没有请求都在折旧，所以自建的经济性完全取决于能不能把利用率压满。这引出了自建与调用 API 之间那个必须精确计算的盈亏平衡点（第三节展开）。

上下文窗口——寸土寸金的工作台。 这是最隐蔽的一种稀缺。上下文窗口看似很大，但它既是能力也是成本——塞进去的每一个 token 都要计费，且塞得越多不代表答得越好（篇三讲过噪音反而拉低质量）。上下文是一块需要精打细算的工作台，把无关信息堆上去，是同时在花钱和降质。

三种资源对应三本账，也对应三种优化重心：

资源 成本性质 优化重心 对应账本
token 流量成本，随调用量线性 每次调用花得值不值 调用账
GPU 固定成本，利用率定单价 自建还是调 API 容量账
上下文 隐性流量成本 塞进去的信息密度 调用账
维护/风险 隐性长期成本 自研还是采买 人力账

看清这张表，成本工程的任务就清晰了：把每一种稀缺资源的消耗变得可见、可算、可优化。下面逐本账展开。

二、调用账：让每一次 token 消耗都花得值

调用账是最日常、也最容易见效的一本。核心问题只有一个：这次调用，花得值不值？ 优化手段分两条主线——分级路由（不为简单任务付旗舰价）和上下文手术（不为无效信息付 token 费）。

2.1 分级路由：不是所有请求都配得上旗舰模型

一个最常见的浪费是”一刀切用最强模型”——因为省心。但系统里的任务复杂度是分布的：意图识别、格式转换、字段抽取这类简单任务，小模型完全胜任；只有复杂推理、多步分析才真正需要旗舰模型。为所有任务都付旗舰价，等于用头等舱运快递。

分级路由的做法，是在网关层根据任务类型把请求分派给不同档位的模型：

flowchart TD
    R[请求进入网关] --> C{任务复杂度判定}
    C -->|简单: 分类/抽取/格式化| S[小模型<br/>低价·低延迟]
    C -->|中等: 常规问答/摘要| M[中档模型]
    C -->|复杂: 多步推理/根因分析| L[旗舰模型]
    S --> Q{置信度达标?}
    Q -->|否| M
    Q -->|是| OUT[返回]
    M --> OUT
    L --> OUT

两个设计要点让它既省钱又不掉质量：其一，复杂度判定本身要廉价——用规则（基于任务类型、输入长度、是否命中特定意图）或一个极小的分类模型来判，判定成本必须远小于它节省的成本，否则得不偿失。其二，置信度兜底升级——小模型处理后若自评置信度不足，自动升级到更强模型重试，用”先便宜试一次、不行再加钱”的策略兜住质量下限。这条升级链和篇二的失败语义、篇三的评估阈值是同一套机制的复用。

实践效果：在我们的平台上，约八成流量被小模型消化，整体调用成本降到一刀切方案的约三分之一，而用户可感知的质量没有差异——因为那八成本就是简单任务，旗舰模型在上面是杀鸡用牛刀。这是成本工程里最典型的”免费的午餐”：省钱和体验不冲突，冲突的只是”省心”。

2.2 上下文手术：为信息密度付费，而非文本长度

第二条主线针对上下文这个隐性成本。很多系统的 token 账单虚高，不是因为调用次数多，而是因为每次调用都塞了太多无效上下文——把整份长文档、整段对话历史、整个知识库切片一股脑喂进去。这既贵又降质。

上下文手术就是把”塞进去”改造成”精准投喂”，几种主要术式：

检索定位替代全文投喂。 与其把整份长文档塞进上下文让模型自己找，不如先用检索定位到相关段落，只投喂这几段。单次调用的输入 token 可以下降一个数量级，而且因为噪音更少，回答质量反而更稳——这是篇三”知识建模优于全文切片”在成本维度的回响。

分段摘要替代长文本直读。 处理超长文档时，用”先分段摘要、再基于摘要推理”的两级流水线，替代把全文塞进单次调用。虽然多了摘要这一步调用，但避免了反复携带全文的巨额输入成本，总账更省。

历史压缩替代全量携带。 多轮对话中，不必每轮都携带全量历史。滚动摘要（把早期对话压缩成摘要，只保留近期原文）能把长会话的上下文成本从随轮次线性增长压成近似常数——引子里那个”每轮携带全量历史”的评审 Agent，病根正在这里。

缓存复用替代重复计算。 对于稳定不变的前缀（系统提示词、固定的领域知识、工具定义），利用提示词缓存机制避免每次重复计费。系统提示词往往很长且每次调用都一样，缓存它的收益立竿见影。

举一个把两条主线叠加的真实手术。某个知识密集型问答能力，最初的实现是”取回最相关的十几篇文档全文 + 拼接近十轮完整对话历史 + 每次带上很长的系统提示词，一股脑喂给旗舰模型”。这套实现质量尚可，但单次调用输入 token 巨大，且每次都在重复计费同样的系统提示词。三刀下去：第一刀分级路由，先用小模型判断问题类型，纯闲聊和简单查询根本不进旗舰模型；第二刀检索改造，从”全文投喂十几篇”改为”精准定位到段落级、只投喂相关片段”，输入 token 直接砍掉一个数量级；第三刀上下文治理，系统提示词走缓存不再重复计费，对话历史改滚动摘要不再全量携带。三刀叠加，单次调用成本降到原来的零头，而因为噪音大幅减少，回答的准确性和稳定性不降反升——评估集分数还涨了。这个案例是下面这句话最好的注脚。

一个贯穿始终的洞察，值得单独强调：省钱的方案往往同时是更好的架构。 检索定位比全文投喂更省 token，也让模型看到的信息更聚焦、答得更准；历史压缩省钱，也避免了长上下文里的信息淹没。成本优化和质量优化在这里高度同源——因为它们惩罚的是同一种东西：无效信息。当你为削减成本而精简上下文时，你顺手也提升了信噪比。这是成本工程最令人愉快的性质：它很少要求你在省钱和做好之间二选一。

三、容量账：自建推理还是调用 API，把信仰之争变成算术题

调用账优化的是”怎么用得省”，容量账回答一个更大的战略抉择：推理能力自建，还是调用 API？ 这个问题在很多团队里是一场信仰之争——有人觉得自建才可控、长期才划算，有人觉得 API 才省心、才不用养 GPU 运维团队。信仰之争没有答案，但它其实是一道可以精确计算的算术题。

3.1 盈亏平衡的推导逻辑

自建的经济性取决于一件事：你的调用量，能不能把 GPU 的固定成本摊薄到低于 API 的单价。 推导路径是从业务需求倒推所需资源，再对比两种方案的总成本：

第一步，从 SLA 倒推吞吐需求。 已知峰值 QPS、平均输入输出 token 数、延迟目标，推导出系统需要的推理吞吐（通常以每秒 token 数衡量）。延迟目标在这里是硬约束——它决定了单请求能容忍的排队和计算时间，进而决定了并发能力要求。

第二步，从吞吐推导卡数。 单卡的有效吞吐由几个因素共同决定：模型参数量与显存占用、量化方案（降低精度换取更高吞吐和更低显存）、批处理策略（把多个请求合批提升 GPU 利用率）、以及模型服务框架的调度效率。用所需总吞吐除以单卡有效吞吐，得到需要的卡数——这里必须留出余量应对峰值和故障。

第三步，两种方案的总成本对比。 自建总成本 = GPU 折旧 + 电力与机房 + 运维人力（这一项最容易被漏，见人力账）；API 总成本 = 月度调用量 × 单价。两条成本曲线的交点，就是盈亏平衡点。

3.2 决策不只看平衡点

平衡点是核心，但真实决策还要叠加几个因素，构成一张完整的决策表：

考量维度 倾向自建 倾向 API
调用量规模 大且稳定，远超平衡点 小或波动剧烈
调用量可预测性 可预测，便于规划容量 突发难测，需弹性
数据合规 数据不能出域，必须私有化 无强合规约束
模型定制需求 需要领域微调、深度定制 通用能力够用
团队能力 有 GPU 运维与推理优化能力 无相关团队，不想养
延迟与可用性掌控 需要端到端掌控 可接受供应商 SLA
现金流模式 能承担前期资本支出 倾向按量付费的运营支出

一个务实的组合策略是混合部署:基线的、稳定的、合规敏感的负载走自建，把 GPU 利用率压满以获得低边际成本；突发的、峰值的、探索性的负载溢出到 API，用它的弹性兜住波动。这等于用自建覆盖成本曲线的稳定段、用 API 覆盖波动段，取两者之长。这本身也是一次典型的架构权衡，该落进 ADR——背景是负载特征与合规要求，选项是纯自建/纯 API/混合，决策依据是算出来的平衡点加上上表的定性因素，而失效条件可以写成”当调用量稳定跌破平衡点、或合规要求解除时，重新评估自建部分的存续”。

核心态度是：先算再买。 把”要不要自建推理”从会议室里的口水仗，变成一张摆在桌上的成本推导表。算出来的平衡点也许会推翻某一方的直觉——这正是它的价值。

四、人力账：最容易被漏掉、也最贵的一本

前两本账都关于机器成本，第三本关于人——它最容易被完全忽略，却常常是压垮一个技术决策的最后一根稻草。

自研组件的隐性维护成本。 一个诱人的决策是”自己写一个，省掉许可费/订阅费”。但这笔账通常只算了眼前：省下的许可费，够不够付它未来三年的维护人力？一个自研组件需要人持续修 bug、跟进依赖升级、适配新需求、写文档、答疑——这些人力成本摊到三年，往往远超当初省下的那点许可费。软件的成本大头从来不是构建，而是维护；自研省的是构建成本，却把维护成本全额扛了下来。

采买/托管的隐性成本。 反过来，采买也不是没有隐性成本：供应商锁定的退出成本、API 变更被迫跟进的适配成本、以及万一供应商出问题(涨价、停服、安全事件)的风险成本。篇一那个自建 AI 网关的决策之所以成立，正是因为把”供应链风险的期望损失”也计入了总账——不是因为自建的构建成本低，而是因为算上风险后，自建的总成本更优。

这本账没有公式化的最优解，因为它高度依赖团队现状(有没有相关能力)、组织阶段(现金流状况)、风险偏好(能不能承受供应商风险)。但有一条通用纪律：任何”自研 vs 采买”的决策，强制在 ADR 里列出四项总账，谁也不许只算构建成本就下结论。

五、FinOps 治理：让成本从一次性核算变成持续能力

前面三本账是”怎么算”，这一节是”怎么持续管起来”。成本工程不是上线前算一次就完事，而是要像可用性、质量一样，变成一项被持续度量、持续优化、持续治理的运营能力——这就是 FinOps 在 AI 系统上的落地。它有三个支柱。

5.1 单位经济学：把成本拆到最小价值单元

总账单是个滞后的、粗粒度的数字，它涨了你都不知道涨在哪。FinOps 的第一件事，是把成本拆解到最小价值单元，建立”单位经济学”看板。诊断场景我们盯这几个单位成本：

每次会话成本——单个诊断会话平均消耗多少 token/多少钱。这是最基础的单位，它的异常波动是最早的预警信号。每个采纳结论成本——把成本和篇三的价值指标(采纳率)挂钩：一个被采纳的有效结论，到底花了多少钱？这个指标才真正回答”值不值”，因为它把分母从”所有调用”收窄到”产生价值的调用”。每租户/每场景成本——成本在不同租户、不同业务场景间如何分布，哪个租户是成本大户，哪类场景性价比最低。

单位经济学的威力在于它让成本可归因、可对比、可优化。当每会话成本突然上涨，你能立刻下钻是哪个环节、哪个租户、哪类请求导致的——这和篇三语义层可观测的归因思路完全一致，只是度量对象从质量换成了成本。事实上，成本 span 就挂在同一套追踪体系里(篇三那张记录清单表的最后一行正是”token 消耗与延迟分解”)，质量归因和成本归因共享同一套埋点。

5.2 预算护栏：把成本失控挡在发生之前

单位经济学是事后度量，预算护栏是事前防御——在成本失控真正发生之前用确定性机制挡住它。几道关键护栏：

Agent 循环上限。 这是多智能体系统最重要的一道护栏，也是引子里那个六成成本的直接解药。任何可能自我循环的 Agent(反思、修正、子任务分解)必须设置确定性的轮次上限、token 上限、时长上限——没有上限的循环等于没有熔断的调用，一个逻辑 bug 就能烧穿预算。这条护栏本质上是篇二”为每个 Agent 循环设置确定性上限”在成本维度的同一条命令。

租户配额。 多租户系统按租户设置 token 配额与限流，防止单个租户(或单个失控的集成)的异常调用拖垮整体成本，也让成本可以公平地分摊和计费。

成本异常告警。 把成本纳入监控告警体系，和延迟、错误率同等对待。设置基线，当每会话成本、每小时总消耗偏离基线到一定幅度时告警——让成本异常像故障一样被主动发现，而不是月底看账单才震惊。

护栏的设计哲学和篇二的韧性防线一脉相承：用确定性的硬约束，兜住概率性组件的不确定行为。 模型可能因为一个提示词的微妙变化陷入长循环，但轮次上限会在它烧穿预算前把它拦下。

5.3 成本进 ADR:让成本成为决策的显式变量

FinOps 的第三个支柱是把成本嵌进决策流程本身。具体做法很简单：任何 AI 相关的架构决策，ADR 里成本模型和性能指标同栏呈现。 选模型时，质量、延迟、成本三维一起看(篇一权衡思维的模型三角)；选架构时，把方案的成本影响写清楚；选自建还是采买时，列出第四节那张四项总账。

这样做的意义，是防止成本成为一个”事后才想起”的变量。太多系统是先按技术理想做完，上线后被账单吓到，再回头做成本优化——而很多成本问题是架构层面的，一旦定型就很难改(比如同步调用链导致无法批处理、上下文设计导致无法缓存)。成本必须在架构设计阶段就作为一等约束参与权衡，而不是运维阶段的补救。 一个好的实践指标是：让每个架构师都能脱口说出自己系统的月度 token 账单——就像他能脱口说出 QPS 和 P99 一样。当这个数字成为团队的共同常识，成本就真正进入了架构的肌肉记忆。

六、落地速查表：成本工程十八项

把成本工程压成一张可验收的清单：

调用账:□ 网关分级路由，简单任务走小模型，复杂度判定本身廉价 □ 小模型置信度不足自动升级兜底 □ 上下文手术四术式：检索定位/分段摘要/历史压缩/缓存复用 □ 牢记”省 token 往往同时提质量”，精简的是无效信息

容量账:□ 自建 vs API 先算盈亏平衡点再决策，不打信仰之争 □ 从 SLA 倒推吞吐、从吞吐推卡数，留峰值与故障余量 □ 决策叠加合规/定制/团队能力/现金流七维 □ 优先考虑混合部署：自建覆盖稳定段，API 覆盖波动段

人力账:□ 自研决策必算三年维护人力，不只比构建成本 □ TCO 四项齐全：构建+运行+维护+风险期望损失 □ “自研 vs 采买”强制在 ADR 列全四项账

FinOps:□ 建单位经济学看板：每会话/每采纳结论/每租户成本 □ 成本 span 复用质量追踪体系，归因同源 □ Agent 循环三上限(轮次/token/时长)必设 □ 租户配额与限流防单点拖垮 □ 成本异常纳入告警，像故障一样主动发现 □ ADR 中成本与性能同栏 □ 每个架构师能脱口说出系统月度 token 账单

十八项打勾，就是让 AI 系统的成本”可算、可优、可控、可决策”的完整路径。

结语：账算清了，但门锁好了吗

回到标题。”token 经济学”的核心，是把一个被云计算时代遗忘的能力重新捡起来——精确核算每一个技术决策的经济后果。大模型让成本重新成为一等约束，而三本账、容量公式、FinOps 治理，就是让成本从月底账单上的一次惊吓，变成设计阶段就握在手里的一个变量。省钱的方案往往同时是更好的架构，因为它们共同厌恶无效信息与失控循环——这是成本工程送给架构师的一份意外礼物。

但成本可控，不等于系统安全。恰恰相反，当你为了省钱引入分级路由、混合部署、缓存复用、多租户共享时，你也打开了一系列新的门：一个被注入的提示词能不能骗过廉价的小模型？一个恶意用户能不能通过共享缓存窥探别人的数据？一个被污染的检索文档能不能劫持你的 Agent 去调用它本不该碰的工具？账我们算清了，但每一处为效率打开的门，都可能是攻击者的入口。

更根本的是，AI 系统引入了一类传统安全清单上根本不存在的威胁——威胁主体第一次包括了”被注入后的模型本身”，一个流畅地执行着恶意指令的、叛变的自己人。
