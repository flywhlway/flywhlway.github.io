1. 数据流分类

本架构中存在六类性质完全不同的数据流。混淆它们是架构设计中最常见的错误——例如把同步流与主链路共用通道，会导致大批量同步挤占交互带宽。

flowchart LR
    F1["① 主链路流<br/>请求-响应<br/>同步 · 低延迟 · 高频"]
    F2["② 控制流<br/>能力/策略下发<br/>低频 · 强一致"]
    F3["③ 埋点流<br/>可观测数据上报<br/>异步 · 海量 · 可丢弃"]
    F4["④ 同步流<br/>端云状态增量<br/>异步 · 幂等 · 大批量"]
    F5["⑤ 离线闭环流<br/>数据→评测→训练<br/>批处理 · 天级"]
    F6["⑥ 异常与降级流<br/>熔断/回退/告警<br/>事件驱动"]
流类型 通道 延迟要求 可靠性要求 承载组件
① 主链路 Agent 网关 / 语音网关 P95 ≤ 1.2 s（首字） 最高 Planner、Agents、LLM 网关
② 控制流 双向认证网关 分钟级 强一致 + 可回滚 注册中心、边缘 Agent 框架
③ 埋点流 消息队列 秒~分钟级 至少一次，可采样 埋点 SDK、数据平台
④ 同步流 双向认证网关（独立通道） 分钟级 幂等 + 断点续传 端云同步服务
⑤ 离线闭环 数据管道 小时~天级 完整性优先 数据平台、训练平台
⑥ 异常降级 内部事件总线 秒级 至少一次 熔断器、告警

关键设计约束：④ 同步流与 ① 主链路必须物理隔离通道（不同端口/不同网关实例/不同带宽配额）。原图把「双向认证网关」与「Agent 网关」并列而非合并，正是这一约束的体现。

2.2 数据在各环节的形态变化

环节 数据形态 体积量级 关键变换
麦克风 PCM 16 kHz 16 bit 32 KB/s 模拟→数字
音频服务 Opus 编码流 3–6 KB/s 降噪 + 压缩（约 8:1）
NLU UTF-8 文本 + 元数据 100–500 B 声学→语义
Planner 入口 编排请求 JSON 1–4 KB 加入身份、上下文引用、预算
Context Bundle 结构化上下文 10–30 KB（≈7.4k token） 记忆+知识+能力聚合
Prompt 最终提示词 15–40 KB 模板注入 + 预算裁剪
模型响应 流式 token 200 B–4 KB 生成
围栏后 校验通过内容 同上 可能改写/截断
回传 SSE 事件流 分片 20–200 B/事件 分片流式
埋点 结构化事件 5–50 KB/请求（含采样快照） 观测数据化

注意体积拐点：Context Bundle 环节数据量放大约 10 倍，是全链路最大的成本与延迟放大点。这解释了为什么上下文预算管理（01 文档 3.4）与压缩（04 文档 B6）是核心优化项，而非可选项。

4.1 控制流的强一致要求

要求 实现方式
原子切换 端侧先下载校验完整包，再原子替换，避免半新半旧
可回滚 保留上一版本，回滚为本地切换（不依赖网络）
灰度 按设备集分批，每批观察窗口后再扩量
签名校验 下发包签名，端侧验签失败即拒绝并告警

5.1 埋点事件 Schema（推断设计）

字段 必填 说明
trace_id ✅ 端侧生成，全链路唯一
span_id / parent_span_id ✅ 层级关系
session_id ✅ 会话边界
event_type ✅ intent/retrieve/llm_call/tool_call/guard/memory_write/decision
component ✅ 产生事件的模块 ID（M01–M24）
ts_start / ts_end ✅ 纳秒精度时间戳
status ✅ ok/error/degraded/blocked
intent / intent_confidence 意图事件
route_reason 路由事件 为什么选了这个后端
model / prompt_version 模型事件
token_in / token_out / cost 模型事件
cache_hit / cache_similarity 模型事件
tool_name / tool_latency / tool_status 工具事件
guard_result / guard_rule 围栏事件
decision_reason 落点决策 端侧为什么没上云
context_snapshot_ref 采样 上下文快照引用（按比例采样）
feedback 可选 显式与隐式反馈

最容易被漏掉的两个字段是 route_reason 与 decision_reason。没有它们，”为什么这次回答质量差”永远只能靠猜。

5.2 采样策略

场景 采样率 原因
错误 / 降级 / 拦截 100% 问题排查刚需
用户负反馈（点踩/重问/打断） 100% 训练数据金矿
正常请求（骨架 Trace） 100% 指标计算需要全量
正常请求（上下文快照） 1–5% 存储成本约束
端侧决策事件 100% 体积小、价值高

6. 同步流（Edge–Cloud Sync）

stateDiagram-v2
    [*] --> 空闲
    空闲 --> 待同步: 本地变更累积 或 定时触发

6.1 冲突解决策略

数据类型 权威方 冲突策略
长期记忆（事实类） 云端 云端优先；本地变更作为候选事实重新走抽取流程
用户偏好（设置类） 最后写入方 时间戳 + 版本向量，晚者胜
隐私标记记忆 端侧 永不上云，仅本地存在
会话短期记忆 端侧 不同步（生命周期短）
能力清单 / 策略 云端 云端单向下发，端侧只读
埋点数据 端侧 单向上行，幂等去重（幂等键 = 设备 ID + 序号）

单写者原则：每一类数据只允许一端为权威写方。违反此原则的架构最终必然出现”记忆自相矛盾”，且无法通过增加逻辑修复——只能重新设计。

7.1 闭环节奏（推断设计）

闭环 频率 触发方式 产出
指标看板 实时/小时 流式计算 延迟、成功率、成本、缓存命中
知识缺口修复 日 自动挖掘 + 人工确认 知识补充与纠错
画像更新 日 批处理 画像特征表
评测回归 每次变更 CI 触发 通过/阻断
金标集扩充 周 负反馈样本挖掘 新增标注样本
SFT/DPO 训练 月 数据量阈值触发 新模型版本

闭环的价值不在训练，而在”知识缺口修复”。多数团队高估模型微调的收益、低估知识补全的收益。实际上”检索不到”造成的失败远多于”模型能力不足”。

8.1 降级事件必须可观测

要求 原因
每次降级产生埋点事件（含降级原因与层级） 否则线上质量下降无法归因
降级率纳入 SLO 看板 “可用但一直在降级”是隐性故障
降级持续超阈值触发告警 防止长期带病运行
用户可感知的降级需明确表达 假装正常会造成更大信任损失

9.1 关键实体设计说明

实体 设计要点
TURN 以 trace_id 为主键，是连接线上运行与离线训练的枢纽实体；route_reason 与 decision_reason 为可归因性核心字段
MEMORY_ITEM + MEMORY_EVENT 事件溯源模式：MEMORY_ITEM 是物化视图，MEMORY_EVENT 是不可变事件日志，二者共同支撑”回溯干预”
SKILL 显式记录正反例数量，作为注册质量门禁指标
CHUNK 必须带 embedding_version，否则更换 Embedding 模型时无法识别待重建索引的数据
DEVICE identity_ref 由证书派生而非业务自填，capability_version 支撑端云版本协商

10. 数据流风险与治理

风险 表现 治理措施
上下文膨胀 延迟与成本上升、效果反而下降 硬预算 + 相关性过滤 + 结构化压缩 + 上下文 Token 数纳入监控
同步流挤占主链路 交互延迟毛刺 通道隔离 + 带宽配额 + 行驶中抑制大包
埋点风暴 消息队列积压、成本失控 采样策略 + 本地聚合 + 背压保护
Trace 断裂 无法端到端归因 Trace ID 端侧生成并全链路强制透传；CI 校验
PII 随埋点入湖 合规风险 SDK 侧脱敏 + 清洗层二次校验 + 数据分级
缓存与知识版本不一致 返回过期答案 缓存键含知识版本；知识更新触发相关缓存失效
冲突解决策略缺失 端云记忆矛盾 单写者原则 + 版本向量 + 显式策略表（见 6.1）
Embedding 版本混用 检索精度悄然下降 embedding_version 强制字段 + 灰度重建 + 双索引并行验证

11. 演进路线

阶段 数据流演进动作
阶段一 六类流通道隔离；Trace 端到端贯通；埋点 Schema 集中管理；上下文 Token 数上看板
阶段二 上下文并行化与压缩；语义缓存接入并做失效联动；同步流幂等与断点续传完善
阶段三 离线闭环自动化（知识缺口自动挖掘→人工确认→自动入库）；落点决策从规则升级为学习型策略（用 decision_reason 历史数据训练）
