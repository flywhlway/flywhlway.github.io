Claude Code Skills 与插件：从技能编写到团队分发

基于 Claude Code 2.0.32 讲清 SKILL.md 格式、渐进式披露与触发机制，对比命令、Subagent、CLAUDE.md、MCP 的分工…

Flywhl 19 分钟 更新于 2026.09 #AI工具#开发效率#Claude Code

先读结论

  1. 常驻上下文的只有 name 和 description，description 写清“做什么 + 何时用”直接决定技能能否被选中。
  2. 正文与附带文件按需加载，脚本只有输出进入上下文；确定性步骤写成脚本，比写成文字说明更省也更稳。
  3. 项目约定写 CLAUDE.md，手动模板用斜杠命令，带脚本的多步流程用 Skill，隔离上下文用 Subagent，外部系统接 MCP。
  4. 插件把命令、子代理、技能、hooks、MCP 服务器打成一个包，经 marketplace.json 分发，团队用 extraKnownMarketplaces 与 enabledPlugins 预置。
  5. 安装技能和插件等同安装软件：脚本与 hooks 以你的权限运行，只装可信来源并逐个文件审查。

Claude Code 在 2.0.12（2025-10-09）推出插件系统与插件市场公测，一周后的 2.0.20（2025-10-16）加入 Agent Skills。前者解决“怎么把一套扩展分发给团队”，后者解决“怎么让 Claude 在需要时才加载某项专门能力”。本文以写作时的最新版本 2.0.32 为准，先讲技能的格式与加载机制，再用一个完整的提交信息技能演示写法，最后把它打包成插件、经市场分发给团队。

SKILL.md：一个目录，一个入口文件

技能就是一个包含 SKILL.md 的目录。SKILL.md 以 YAML frontmatter 开头，后接 Markdown 正文：

frontmatter 字段（依据 2025-10-16 发布的 Agent Skills 规范 1.0 与 Claude Code 文档）：

字段 必填 约束与用途
name 是 小写字母、数字、连字符，最长 64 字符；规范要求与所在目录同名；不能包含 XML 标签，也不能含保留词 anthropic、claude
description 是 非空，最长 1024 字符，不能含 XML 标签；写明“做什么”和“何时使用”
allowed-tools 否 技能激活时预先批准、无需逐次确认的工具，如 Read, Grep, Glob；目前只有 Claude Code 支持
license 否 许可证名称，或随技能附带的许可证文件名
metadata 否 字符串键值对，供客户端存放规范之外的属性

没有 triggers、keywords 之类的字段——触发完全依赖 description 的文字。

技能可以放在三个位置：

  • ~/.claude/skills/<技能名>/：个人技能，所有项目可用，适合个人习惯和实验中的技能；
  • .claude/skills/<技能名>/：项目技能，随仓库提交，团队成员拉取代码即可用；
  • 插件的 skills/ 目录：随插件安装自动可用。

修改技能后需要重启 Claude Code 才会重新加载。技能在 Claude Code、claude.ai 与 API 之间不同步，Claude Code 的技能完全基于本地文件系统，不需要上传。

渐进式披露：三层加载

技能能装进大量资料而不拖垮上下文，靠的是分层加载：

层级 何时加载 体量 内容
元数据 启动时，所有技能 每个技能约 100 token frontmatter 中的 name 与 description
指令 技能被判定相关时 建议少于 5k token SKILL.md 正文
资源 正文指引、任务需要时 实际不设上限 参考文档按需读取；脚本直接执行，只有输出进入上下文

由此可以推出几条写法原则（均来自官方最佳实践）：

  • 正文少于 500 行，把细节拆到独立文件，由 SKILL.md 像目录一样指过去；
  • 引用只下探一层：所有参考文件都从 SKILL.md 直接链接，避免 A 引用 B、B 再引用 C，Claude 可能只读到一部分；
  • 超过 100 行的参考文件在顶部放目录，只预览开头时也能看到全貌；
  • 确定性操作写成脚本：校验、格式转换这类步骤，脚本比让 Claude 临场生成代码更可靠，而且脚本源码不占上下文；脚本要自己处理错误，不要把异常原样抛给 Claude 收拾；
  • 路径一律用正斜杠，scripts/helper.py 而不是 scripts\helper.py；
  • 不写会过期的信息，如“2025 年 8 月前用旧接口”。

Claude 如何选择技能

做决定的那一刻，Claude 只看得到每个技能的 name 和 description，正文写得再好也帮不上忙。所以 description 必须同时回答两个问题：它做什么、什么情况下用它。

写法 问题
description: 帮助处理文档 太泛，和任何文档类请求都沾边，又和哪个都不精确匹配
description: 提交助手 只有名称没有触发条件，用户说“帮我 commit 一下”时无从关联
description: 按团队 Conventional Commits 规范为暂存区改动生成并校验提交信息。在用户要求提交代码、写 commit message 或执行 git commit 时使用。 能力、规范、触发场景齐全，中英文关键词都覆盖

几条经验：

  • 用第三人称。 description 会被注入系统提示，人称混乱会影响发现，写“为……生成”，不写“我来帮你”。
  • 写进用户真实会说的词。 文件扩展名（.xlsx）、工具名、中英文同义说法（“提交”与 commit）都是有效信号。
  • 相近技能要拉开触发词。 两个技能都写“用于数据分析”，Claude 会摇摆；一个限定“Excel 销售数据、CRM 导出”，另一个限定“日志与系统指标”，就不会混淆。
  • 一个技能只做一件事。 “文档处理”应拆成“PDF 表单填写”“Excel 数据分析”等独立技能。
  • 测试时换着说法提问。 检查该触发时是否触发、不该触发时是否安静；想确认加载了哪些技能，直接问 Claude “有哪些可用的 Skills”；技能没被加载时用 claude --debug 查看加载错误，常见原因是 YAML 缩进用了 Tab、缺少收尾的 ---、文件不在 <技能名>/SKILL.md 路径上。

该用 Skill、斜杠命令、Subagent、CLAUDE.md 还是 MCP

机制 由谁触发 进入上下文的方式 适合 不适合
CLAUDE.md 每次会话自动加载 启动即全文加载 项目通用约定、常用命令、架构概览 只在某类任务才需要的长流程，平时白占上下文
斜杠命令 用户输入 /名称；带 description 的自定义命令也可被 Claude 经 SlashCommand 工具调用（1.0.123 起） 调用时展开为提示词 单文件提示模板、带参数的固定操作，如 /review-pr 123 需要脚本和多份参考资料的流程
Skill Claude 依据 description 自主选择 元数据常驻，正文与资源按需 带脚本或参考资料的多步流程、需要团队统一的工作方式 必须每次确定执行的动作（用 Hook）；一两句话的偏好（写 CLAUDE.md）
Subagent Claude 委派，或用户点名 独立上下文窗口，只把结果交回主对话 大量搜索阅读、需要隔离上下文或限定工具权限的子任务 需要频繁与主对话共享中间状态的工作
MCP Claude 调用工具 工具定义随会话加载 接入外部系统：数据库、工单、浏览器、SaaS API 只有知识和流程、没有外部系统时，Skill 更轻

这几种机制经常组合：Skill 负责“怎么做”，其中调用 MCP 工具时写全限定名（如 mcp__github__create_issue）以免找不到工具；需要强制执行的环节交给 Hook；耗上下文的调研交给 Subagent。

完整示例：按团队规范生成提交信息

目标：用户说“提交一下”时，Claude 读取暂存区、按团队规范写提交信息、用脚本校验、用户确认后再提交。目录结构：

SKILL.md

scopes.md

scripts/staged_summary.sh

scripts/check_message.py

设计要点

  • 三层加载各得其所。 平时只有 description 常驻；用户说“提交一下”时才读正文；scopes.md 只在选 scope 时读取；两个脚本的源码从不进入上下文，Claude 只看到摘要与校验结果。
  • 摘要脚本控制体积。 大改动的 diff 可能有几千行，脚本只给文件清单、规模统计、最近提交风格与前 300 行 diff，需要细节时再按文件单独查看。管道里没有用 | head：在 pipefail 下 head 提前退出会让上游收到 SIGPIPE，把整个脚本判为失败。
  • 校验交给脚本而不是自觉。 “subject 不超过 50 字”写在正文里，模型未必每次数对；脚本给出确定结论，Claude 按报错修正即可。同一个脚本还能挂到 git 的 commit-msg 钩子上，人手写的提交和 Claude 写的提交走同一套标准。
  • allowed-tools 只预批只读步骤。 读取 diff、跑两个脚本免确认，真正写入历史的 git commit 故意不列入，让权限系统在最后一步再问一次。脚本用项目相对路径引用，是因为这是项目技能，路径固定、最不容易出错。

插件：把技能和配套能力打成一个包

项目技能靠 git 共享已经够用，但一套团队规范往往不止技能：还有斜杠命令、拦截危险命令的 hook、访问内部系统的 MCP 服务器。插件把这些组件打成一个可安装、可启停、可版本化的单元。官方文档也推荐通过插件分发技能。

目录与清单

组件 默认位置 说明
斜杠命令 commands/*.md 格式与 .claude/commands 相同；重名时用 /插件名:命令名 区分
子代理 agents/*.md 出现在 /agents 中，Claude 可按任务自动委派
技能 skills/<技能名>/SKILL.md 插件安装后自动可用
Hooks hooks/hooks.json 结构与 settings.json 中的 hooks 字段相同
MCP 服务器 .mcp.json 插件启用时自动启动，工具与普通 MCP 工具无异

除 .claude-plugin/plugin.json 外，所有组件目录都必须放在插件根目录，放进 .claude-plugin/ 里不会被识别。plugin.json 只有 name（kebab-case）必填：

可选的 commands、agents、hooks、mcpServers 字段用于指定额外路径，它们是对默认目录的补充而非替换，且必须是以 ./ 开头的相对路径。插件安装位置因人而异，hooks 与 MCP 配置里引用插件自带文件时一律用 ${CLAUDE_PLUGIN_ROOT}：

技能搬进插件后，SKILL.md 里按项目路径写的脚本命令要改成相对技能目录的写法（官方示例即 scripts/helper.py 这种形式），因为插件不再位于 .claude/skills/ 下。

市场：marketplace.json

市场是一个列出插件及其来源的 JSON 文件，放在仓库的 .claude-plugin/marketplace.json。团队通常建一个专门的仓库，把插件放在 plugins/ 下：

name、owner、plugins 必填；每个插件条目必填 name 与 source。source 可以是仓库内相对路径，也可以指向其它 GitHub 仓库（{"source": "github", "repo": "owner/repo"}）或任意 git 地址。条目的 strict 默认为 true，要求插件目录自带 plugin.json；设为 false 时条目本身即可充当完整清单。发布前用 claude plugin validate . 检查语法。

安装与管理

  • marketplace add 接受 GitHub 的 owner/repo、任意 git 地址、本地目录或 marketplace.json 的 URL；2.0.28 起可以用 owner/repo#v1.2.0 固定到分支或标签。
  • 安装后需要重启 Claude Code 才能使用新插件；直接输入 /plugin 进入交互界面，可浏览、安装并查看插件提供了哪些组件。
  • 删除一个市场会连带卸载从它安装的全部插件。
  • Anthropic 的官方技能仓库也是一个市场：/plugin marketplace add anthropics/skills 后，/plugin install document-skills@anthropic-agent-skills 安装 Excel、Word、PowerPoint、PDF 处理技能，example-skills 里的 skill-creator 可用来起草新技能。

本地开发插件时，把市场指向本地目录（/plugin marketplace add ./team-plugins），每次修改后卸载再重装即可验证。

团队预置

把市场和插件写进仓库的 .claude/settings.json，成员打开项目时就会收到安装提示：

成员信任该仓库目录后，Claude Code 会提示安装市场及 enabledPlugins 中的插件；安装需要成员明确同意，也可以跳过，跳过的选择记录在用户设置里。enabledPlugins 在用户级、项目级、本地设置中都能写，本地设置适合按机器临时关闭某个插件。市场来源类型有 github、git，以及仅供开发使用的 directory。

安全：装技能和插件就是装软件

技能的正文是写给 Claude 的指令，脚本和 hooks 以你的用户权限运行，而 Claude Code 中的技能拥有与本机其它程序相同的网络访问能力。恶意或被篡改的技能可以指挥 Claude 读取凭据、调用工具外传数据，做与声称用途不符的事。审查清单：

  • 只装可信来源。 自己写的、Anthropic 官方的、团队内部审查过的；陌生来源必须逐个文件审查，包括 SKILL.md、脚本、图片与参考资料。
  • 重点看这几类内容： 意料之外的网络请求、读取 ~/.ssh、.env、云厂商凭据等路径的操作、与技能描述不符的指令、从外部 URL 拉取内容的步骤——拉回来的内容可能携带恶意指令，今天可信的依赖明天也可能被篡改。
  • 插件里的 hooks 风险最高。 hook 不经过模型判断，事件一到就自动执行；.mcp.json 里的服务器会在插件启用时启动本地进程。审查插件先看 hooks/hooks.json 和 .mcp.json。
  • 检查 allowed-tools 预批了什么。 预批只读命令没有问题；出现不带限定的 Bash、Write，就是危险信号。它也不是沙箱，不要把它当作权限边界。
  • 固定版本，审查更新。 第三方市场用 #标签 固定版本；执行 /plugin marketplace update 之前先看上游 diff。
  • 团队走内部市场。 第三方插件先 fork 或镜像进内部仓库，审查后再上架；把市场仓库的变更纳入代码评审，与 CI 配置同等对待。

2026-09 补记：开放标准、命令并入 Skills 与供应链风险

本文写于 2.0.32 时期，之后技能体系变化很大，以下按主题补充。

开放标准与跨工具采用。 2025-12-18，Anthropic 把 Agent Skills 作为开放标准发布在 agentskills.io，同时推出组织级技能管理与技能目录（Skills Directory）。标准沿用 name（1–64 字符，小写字母、数字、连字符，不能以连字符开头或结尾）与 description（1–1024 字符）两个必填字段，新增可选的 compatibility（不超过 500 字符，说明运行环境要求）；allowed-tools 被标为实验性，采用空格分隔写法；推荐目录约定为 scripts/、references/、assets/，并提供 skills-ref validate 校验工具。随后 Codex（2025-12-19）、Gemini CLI（2026-01）、Cursor 2.4（2026-01-22）、VS Code 1.109（2026-02-04 正式版）先后支持 SKILL.md。需要跨工具复用的技能应只用标准字段：上传 claude.ai 或经 Skills API 分发时，出现规范之外的字段会直接报错，而不是忽略。

命令并入 Skills。 2.1.0（2026-01-07）起，技能默认出现在 / 菜单，可以像命令一样手动调用，user-invocable: false 可将其隐藏；2.1.3（2026-01-09）把斜杠命令与技能合并为同一机制，行为不变，.claude/commands/ 下的文件继续可用，统一视为技能。本文决策表中“斜杠命令”与“Skill”两行因此变成同一机制的两种触发方式：只允许手动触发的流程加 disable-model-invocation: true，只给 Claude 自动使用的加 user-invocable: false。在当前的 Claude Code 中，name 缺省取目录名，description 缺省取正文首个非空行，但为了跨工具复用和触发准确，两者仍应写全。

新的 frontmatter 能力。 2.0.43（2025-11-17）起子代理可以用 skills 字段预加载技能；2.1.0 起技能支持 context: fork，在分叉出的子代理上下文中运行（配合 agent 指定子代理类型），同版本还支持在技能 frontmatter 中声明 hooks，并实现了技能热加载，本文“修改后需重启”的说法已不再适用；2.1.80（2026-03-19）起支持 effort，调用技能时覆盖会话的推理强度。allowed-tools 的语义也更明确：授权只在调用技能的那一轮有效，用户发出下一条消息即失效，另有 disallowed-tools 用于在技能激活期间移除工具。2.0.74（2025-12-19）修复了“allowed-tools 未应用到技能所调用的工具”的问题，本文写作时的版本预批准不一定生效。

供应链风险。 技能从单个工具的扩展变成跨工具通用的格式，一个恶意技能能在多个代理里生效，攻击面随之放大。几个现实风险点：当前文档明确写道，项目技能的 allowed-tools 不受工作区信任约束，即使在从未信任过的目录里以 -p 运行也会生效，技能可以给自己申请很宽的工具权限；插件市场支持自动更新（2.0.70 起可按市场单独开关），一次上游更新就能替换已审查过的内容。对应的防线也已补齐：企业可以用托管设置 strictKnownMarketplaces 与 blockedMarketplaces 限定可用的市场（2.1.117 起在安装、更新和自动更新时都会校验），用 skillOverrides 对模型隐藏或关闭特定技能，用 Skill(名称) 权限规则禁止调用某个技能。实践上，第三方市场关闭自动更新并固定到标签，内部镜像审查后再上架，仓库里 .claude/skills/ 的变更与 CI 配置同等审查。
