5.1 什么是 VLA：从模块化到端到端

5.1.1 定义与三要素

VLA（Vision-Language-Action，视觉-语言-动作模型）：以视觉观测与语言指令为输入、直接输出机器人动作序列的策略模型。三要素：V（多视角图像/深度，有时含点云）、L（自然语言任务指令）、A（关节角/末端位姿/夹爪开合的连续序列）。一句话记忆（呼应 1.4.3）：VLA = 多模态大模型骨干 + 动作头——把输出 token 换成关节角。

5.1.2 与「LLM + 机械臂 SDK」的本质区别

关键区别不在「有没有大模型」，而在闭环层次：

维度 LLM + SDK（工具调用式） VLA（端到端策略）
LLM 输出 离散函数调用：pick(cup) 连续动作序列：Δ关节角×N 步
谁完成「怎么抓」 预写好的技能实现（视觉伺服/规划） 模型自己学出来
泛化边界 技能库的边界 数据分布的边界
频率 按需（秒级） 固定节拍（5~50Hz）
失败模式 调错技能 动作抖动/偏移/僵死
平台含义 技能=可测试的软件制品 策略=需评测的模型制品

第四篇的 Agent 三铁律正是建立在前者之上；VLA 是把「怎么做」这一层也交给模型——因此它必须进模型 OTA 与影子评测体系，而不是走代码发布流程。

5.1.3 模块化 vs 端到端：工程取舍表

维度 模块化（感知→规划→控制） 端到端 VLA
可解释 每级有中间量，可断点定位 黑盒，只能看输入输出
可测试 分级单测 + 集成 只能整体评测（任务成功率）
泛化 弱：新物体/新场景要改代码 强：靠数据覆盖
长尾 靠规则堆，越堆越脆 靠数据补
数据需求 低 极高（本篇 5.4）
安全论证 相对容易（可形式化约束） 困难，必须外挂安全层

【映射 🚗→🤖】这张表你在智驾看过一模一样的版本：规则规控 vs 端到端。产业结论也同构——分层混合是现阶段工程现实：VLA 负责「短时程操作技能」（抓取、插拔、开门），传统栈负责导航、避障与安全兜底；云端 Agent 负责长时程规划（第四篇 L2/L3）。

5.1.6 企业实践建议

在技术路线讨论中扮演「架构守门人」而非「路线站队者」：不论算法团队选模块化还是端到端，平台侧的要求恒定——必须能被评测、能被灰度、能被回滚、能被安全层兜底。把这四个「能」写进模型准入规范，路线之争就与平台稳定性解耦了。

5.1.7 面试可能问什么

  1. VLA 与 LLM Agent 调用机械臂 SDK 的区别？（要点：闭环层次、谁负责「怎么做」、泛化边界、失败模式）
  2. 端到端与模块化怎么选？（要点：取舍表 + 分层混合是现阶段现实 + 智驾同构）
  3. VLA 在系统里的位置？（要点：三层大脑，上有任务笼下有安全网）

5.1.8 最佳实践

  • 用「三层大脑图」作为与算法团队的第一张对齐图——它同时定义了接口与责任边界。
  • 策略与技能分开管：技能走 CI/CD，策略走模型 OTA + 影子评测，两条流水线不混。

5.1.9 常见误区

  • ❌ 「上了 VLA 就不需要传统栈」——安全监控、定位导航、E-Stop 一样都不能少。
  • ❌ 把 VLA 当成「更聪明的 LLM」——它是有硬节拍的实时控制组件，延迟预算是一等公民。

5.1.10 Obsidian 永久笔记

  • VLA 等于骨干加动作头：输出 token 换成关节角。
  • 三层大脑：慢脑规划（云边秒级）/ 中脑 VLA（机上 5~50Hz）/ 快脑安全（机上 kHz）。
  • 平台四能：可评测、可灰度、可回滚、可兜底——路线中立的准入标准。

5.2.3 Open X-Embodiment：数据侧的「ImageNet 时刻」

由 Google DeepMind 牵头、数十家机构共建的跨本体机器人数据集合集（百万量级轨迹、数十种本体），并训练出 RT-X 系列证明跨本体共训能提升单本体表现。对平台的三点含义：其一，数据格式统一是前提（RLDS/TFDS 与 LeRobot 格式的互通是数据工程的日常）；其二，跨本体意味着你的数据引擎要把 embodiment 作为一等维度（第七篇）；其三，开源数据决定了「先用公开数据预训练、用自家数据微调」是绝大多数公司的现实路径——与你在 LLM 时代「基座外购、领域微调」的策略完全一致。

5.2.4 LeRobot：把 VLA 变成可工程化的东西

Hugging Face 的 LeRobot 提供**数据集格式（LeRobotDataset）+ 训练脚本 + 策略实现（ACT/Diffusion Policy/π0 等）+ 真机部署接口 + 低成本硬件方案（SO-ARM 系列）**的完整栈。平台视角：它是机器人界的「transformers + datasets」——你的第一个 VLA 实验、第一个数据集 Schema、第一条评测流水线都应该从它起步，第十一篇实战项目的模型侧接口以它为准。

5.2.5 与产业物联网平台的映射

VLA 生态 智驾/LLM 生态 备注

LeRobot transformers + datasets 事实工程载体

5.2.6 企业实践建议

模型选型别一步到位追 SOTA：先用 LeRobot + ACT 在低成本臂上跑通「数据→训练→部署→评测」全链路，再换 OpenVLA 验证平台的 GB 级 OTA 与显存假设，最后按业务需要引入 π0/GR00T 级方案。平台的价值在于让换模型变成一次配置变更——链路先于模型。

5.2.7 面试可能问什么

  1. 讲讲 VLA 的技术谱系。（要点：ACT/DP 视觉运动策略 → RT 系列大模型骨干 → OpenVLA 开源基线 → π0 高频连续；OXE/LeRobot 是地基）
  2. Open X-Embodiment 的工程意义？（要点：跨本体共训、格式统一、预训练+微调路径）
  3. 为什么从 LeRobot 开始？（要点：全栈闭环最短、格式与评测可直接进平台）

5.2.8 最佳实践

  • 建立《模型雷达》季度更新：每个候选记录规模/动作表示/频率/许可/硬件依赖五列——技术演进快，靠表格而非记忆。
  • 优先选择「有开源部署接口 + 明确许可」的模型，避免把不可商用的权重带进产品线（合规坑）。

5.2.9 常见误区

  • ❌ 只看论文任务成功率选型——不同论文的评测本体、任务与协议都不同，跨论文数字不可比。
  • ❌ 忽视许可证与数据来源合规——模型注册表里必须有许可字段（4.10.3）。

5.2.10 Obsidian 永久笔记

  • VLA 谱系三支：视觉运动策略（ACT/DP）、大模型骨干（RT/OpenVLA）、高频连续（π0/GR00T）。
  • OXE 是数据地基：跨本体共训 + 格式统一 + 预训练微调路径。
  • LeRobot 是工程载体：数据格式/训练/部署/评测一站起步。
  • 链路先于模型：平台的价值是让换模型变成配置变更。

5.3 输入输出契约：平台最该盯的一页

5.3.1 观测空间（Observation）

组成 典型形态 平台关注点
主视角图像 13 路 RGB，224²448²，通常 10~30Hz 带宽、同步、时间戳（Header！）
腕部相机 近距 RGB 精细操作的关键输入
本体状态 关节角/速度/夹爪/末端位姿 与图像的时间对齐是头号工程问题
语言指令 短句 来自第四篇 L3 任务载荷
历史 最近 N 帧观测 决定显存与延迟

时间对齐是平台侧必须立规矩的地方：图像与关节状态的时间戳偏差超过一个控制周期，模型就在「用过去的图配现在的关节」——这就是 2.19.3 TF 时间旅行的同一课题在模型输入侧的翻版。规矩：所有观测走 Header.stamp，端侧做同步缓冲（近似时间同步器），偏差超阈值即丢帧并计数上报。

5.3.2 动作空间（Action）

三种常见坐标：关节空间（Δ关节角，最直接）、任务空间（末端位姿增量 + 夹爪，跨本体迁移性好）、底盘速度（移动机器人）。三个平台必问：绝对还是增量（增量对标定误差更鲁棒，但会累积漂移）、归一化区间与统计量（模型输出通常在 [-1,1]，反归一化用的均值/方差属于模型制品的一部分——参数漂移是最隐蔽的事故源）、控制模式（位置/速度/力矩，决定下游控制器接法）。

5.3.3 四种动作头的工程差异

动作头 代表 优点 工程代价
离散 token RT-2, OpenVLA 复用 LLM 词表与训练栈 量化误差、逐 token 解码慢
回归（直接输出） ACT 最快最简单 多模态动作被「平均」成中庸解
扩散 Diffusion Policy, Octo 多模态分布建模好 多步去噪 → 延迟随步数线性涨
流匹配 π0 连续、少步、可高频 实现复杂度高

平台侧的一句话理解：动作头 = 延迟与质量的旋钮。扩散步数、token 数、chunk 长度都是可调参数，它们直接决定你的延迟预算能否达标——所以模型卡里必须写清楚这些参数（5.9 接口清单）。

5.3.4 动作分块（Action Chunking）：延迟解药与安全隐患

机制：模型一次推理输出未来 H 步动作（chunk，典型 H=8~50），端侧以高频逐步执行，下次推理在 chunk 耗尽前完成——于是 5Hz 的推理可以驱动 50Hz 的执行。这是 VLA 能在算力受限的机上跑起来的关键工程技巧（ACT 提出、后续广泛采用），并顺带平滑了动作抖动。

代价必须讲清楚：chunk 执行期间模型是「盲」的——它在按 200ms 前的观测开环执行。因此有了工程三件套：chunk 长度是延迟与反应性的权衡旋钮；时序聚合/重叠执行（新旧 chunk 加权融合，减少切换突变）；快脑必须独立监控（5.1.4 的 C 层：碰撞/力矩/几何边界越界立即中断 chunk）。

  O["观测 t0（图像+状态+指令）"] --> M["VLA 推理 ~100~200ms"]
  M --> CK["动作 chunk：a(t0+1..t0+H)"]
  CK --> EX["执行器 50Hz 逐步执行"]
  EX --> W["chunk 剩余 30% 时触发下次推理（重叠）"]
  W --> O
  EX -.每步.-> SAFE["快脑安全监控：越界即中断"]

5.3.7 面试可能问什么

  1. 动作分块解决什么、代价是什么？（要点：低频推理驱动高频执行；chunk 内开环 → 需快脑监控与重叠执行）
  2. 关节空间还是任务空间输出？（要点：跨本体迁移 vs 直接性；增量 vs 绝对的漂移与鲁棒权衡）
  3. 归一化统计量放哪？（要点：属于模型制品；错配即事故，端侧契约校验）

5.3.8 最佳实践

  • 关节顺序、单位、坐标系约定写进模型卡并在 Runtime 断言——这三样是跨团队最常错位的隐性契约。
  • chunk 重叠执行 + 分歧监控（新 chunk 与旧 chunk 首步差异超阈值即告警），异常早发现。

5.3.9 常见误区

  • ❌ 认为「换个同类模型就能直接跑」——归一化统计量、关节顺序、图像预处理任一不同，行为即失控。
  • ❌ 用最新观测配旧动作 chunk 而不做时序聚合——切换突变引起可见抖动，长期损伤减速器。

5.3.10 Obsidian 永久笔记

  • VLA 三契约：观测/动作/频率，注册表必填 + Runtime 断言。
  • 动作分块即轨迹下发：低频推理驱动高频执行，chunk 内开环靠快脑兜底。
  • 归一化统计量属于制品：错配是最隐蔽的事故源。

5.4.2 真机遥操作采集：平台侧要建什么

采集链路：遥操作设备（主从臂/VR 手柄/手持夹爪装置）→ 记录器（同步录制图像+关节+指令，rosbag2/LeRobot writer）→ 质检（成功/失败标注、剪裁、异常剔除）→ 入湖（对象存储 + 元数据入库）。平台四件事：采集会话管理（谁、哪台机、什么任务、多少条）、数据质量门禁（时间戳连续性、频率稳定性、动作范围合法性——自动质检脚本挡掉 30% 的废数据）、成本看板（每条轨迹成本 = 人时 + 设备占用，让管理层看见数据的价格）、版本化数据集（可复现训练的前提，第七篇）。

【映射 🚗→🤖】这就是智驾数据采集车队的缩小版：采集员≈安全员，遥操作站≈采集车，质检与标注流程原样复用。你甚至可以把产业物联网的采集任务调度系统改名直接用（4.7 的 Fleet 任务面即可承接「采集任务」）。

5.4.3 数据格式：LeRobotDataset 的平台意义

LeRobotDataset 把「多路视频 + 时序状态/动作 + 任务描述 + 元信息」组织成标准结构（视频编码存储 + 表格化时序 + 数据集卡片），并原生对接训练与评测脚本。平台侧价值三条：统一 Schema（不同本体、不同采集端产出同构数据，是数据飞轮能转的前提）；视频编码存储（原始图像流转 H.264/265 后体积降一到两个数量级——直接决定你的存储账单）；与 OXE 互通（公开数据与自家数据可混训）。

决策建议：端侧录 rosbag2（MCAP，机内一切原始信号）→ 云端 ETL 转 LeRobotDataset（训练用视图）。Bag 是原始档案、Dataset 是训练视图——与你「原始日志入湖、加工出特征表」的分层完全一致。

5.4.4 数据配比与长尾

5.5 推理工程：延迟预算与部署

5.5.1 延迟预算分解（平台架构师的核心表）

以「50Hz 执行 + 5Hz 推理 + chunk=10」为例，一次推理的端到端预算（数量级示意，随硬件与模型剧烈变化）：

环节 典型耗时 优化手段
图像采集与传输 5~20ms 组合部署零拷贝（2.22）、降分辨率
预处理（缩放/归一化） 2~10ms GPU 预处理、避免 CPU 拷贝
视觉编码器 20~60ms TensorRT、FP8/INT8（第六篇）
语言/骨干前向 30~150ms KV Cache 复用（指令不变时）、量化
动作头解码 5~50ms 减少扩散步数/token 数
后处理与下发 1~5ms 反归一化 + 安全裁剪
合计 60300ms 必须 < chunk 时长（10/50Hz=200ms）

铁律：推理延迟 + 抖动裕度 < chunk 执行时长，否则动作断流（机器人「卡顿」）。这条不等式就是你与算法团队谈判的语言——它把「模型多大」翻译成了「能不能上线」。

5.5.2 双频架构：推理与控制解耦

工程要点：Chunk Buffer 是解耦点——推理慢一次不至于立刻断流（缓冲兜底），但连续慢就会耗尽（监控 buffer 水位并上报，这是端侧最重要的健康指标之一）。

5.5.3 显存、体积与你的 OTA

模型规模 FP16 显存 INT8/W4 量化后 Jetson 可行性（第六篇细化）
~100M（ACT/DP） 亚 GB — 轻松
~1B（Octo/RDT 级） ~2GB+ ~1GB 可行
~7B（OpenVLA 级） ~14GB+ 47GB Orin AGX 64GB 可行；Orin Nano 8GB 需强量化且延迟吃紧

三个平台推论：量化不是可选项而是默认项（第六篇）；模型体积直接换算成 OTA 分发账（4.3.4 的四级瀑布因它而存在：7B 量化后仍有数 GB × 万台）；显存决定能否双缓冲热切换（4.3.5！新旧模型同时驻留需要双份显存——这是端侧硬件选型时最容易被漏掉的一条约束，写进机型规格书）。

5.5.4 端侧 Runtime 设计要点

一个合格的 VLA Runtime（第六篇给部署细节、第十一篇给代码位置）必须有：模型槽位管理（A/B 双缓冲 + 原子切换 + 版本上报）、契约校验（5.3.6）、观测同步缓冲、chunk buffer 与水位监控、失效降级（推理超时/异常 → 立即降级到安全策略：停住/收臂/交还传统栈）、指标上报（延迟 P50/P99、buffer 水位、置信度分布、分歧计数 → 第四篇数据面）。这份清单就是你给算法团队的「模型上机验收标准」。

5.5.5 与产业物联网平台的映射

VLA 推理 你的 AI Infra 经验 备注

5.5.6 企业实践建议

把「延迟预算表」做成机型规格书的一节：给定机型（Orin Nano/NX/AGX）与控制频率，明确可承载的模型规模上限与量化要求——用硬件规格反向约束模型选型，比事后优化便宜十倍。这份表也是采购与算法团队争执时唯一的仲裁者。

5.5.7 面试可能问什么

  2. 7B 模型能上 Jetson 吗？（要点：量化后显存、双缓冲要双份、延迟与频率的匹配）
  3. 推理超时怎么办？（要点：chunk buffer 兜底 + 水位监控 + 超时降级到安全策略）

5.6 失效模式与安全带

5.6.1 六种典型失效

失效 现象 端侧检测 平台侧动作
分布外（OOD） 新物体/新布光下动作离谱 置信度/熵异常、动作幅度异常 触发回传 + 降级
动作抖动 高频振荡，减速器受损 动作二阶差分超阈 告警 + 限幅
僵死 停在原地反复微动 位移/进度停滞检测 超时中断任务
幻觉式操作 抓空气、对不存在的物体动作 力矩无接触反馈 中断 + 现场回传
语言误解 执行了别的任务 任务后校验（视觉核对） 判失败 + 人工复核
分块断流 卡顿、动作不连续 buffer 水位见底 降频/降级/告警

5.6.2 平台侧安全带四层

L1 契约层：Runtime 加载时校验观测/动作/频率契约（5.3.6）；L2 输出层：动作限幅（关节限位、速度/加速度上限、力矩上限）、几何围栏（工作空间/禁行区）——这一层必须独立于模型实现，是纯规则代码，可形式化审查；L3 监控层：快脑实时监控（碰撞、力矩突变、越界）→ 中断 chunk；L4 系统层：E-Stop（永不出本体，1.2.5）+ 人机共管区规则 + 任务级超时。

核心原则：安全不由模型负责。模型可以变、可以回滚、可以出错；安全层是恒定的、可审查的、独立演进的——这与你在智驾里「AEB 独立于端到端模型」的架构原则一字不差。

5.6.3 评测指标：模型好不好，用平台指标说话

指标 定义 用途
任务成功率 无干预完成 / 总尝试 主门禁（4.8.4）
人工干预率 干预次数 / 100 任务 主门禁
首次成功率 vs 重试成功率 分层看鲁棒性 定位「靠重试蒙对」
动作平滑度 加加速度（jerk）统计 机械寿命与体感
OOD 率 低置信度帧占比 数据补采信号
延迟 P99 / buffer 见底次数 见 5.5 上线门禁
安全事件数 限幅触发/中断/E-Stop 一票否决

三级评测：离线数据集（快、便宜、不可信）→ 仿真基准（中、可批量、有 gap，第八篇）→ 影子/小批真机（慢、贵、最可信，4.3.6）。三级门禁串联，逐级放行。

5.6.4 与产业物联网平台的映射

VLA 安全 智驾 备注
安全层独立于模型 AEB/安全监控独立于端到端 同一原则
三级评测 离线回放→仿真→影子/实车 完全同构
安全事件一票否决 智驾安全门禁 优先级最高
OOD 触发回传 corner case 挖掘 数据飞轮入口

5.7 Scaling 与云边分工

5.7.1 三条 Scaling 轴

模型规模：更大骨干带来更强语义泛化，但端侧显存与延迟是硬墙——所以行业出现「大骨干 + 轻动作专家」（π0 式）与「云端大脑 + 端侧小脑」两种解法。数据规模：跨本体共训（OXE）已被证明有效，数据仍是主瓶颈（5.4）。本体规模：一个策略服务多种本体，需要动作空间抽象与 embodiment 条件化——这是平台的活儿（Device Profile + 数据里的 embodiment 维度）。

5.7.2 云边分工矩阵（回答「VLA 能不能上云」）

部署形态 可行性 适用
全端侧 ✅ 主流 实时操作、断网可用（首选）
边缘池推理 ⚠️ 条件可行 有线内网 RTT<5ms 且抖动可控、固定工位（4.9.3 三问）
云端推理 ❌ 控制回路不可行 仅用于离线评测/影子并跑/大脑级规划
云端大脑 + 端侧小脑 ✅ 推荐 LLM 规划在云（秒级）+ VLA 执行在端（50Hz）——即三层大脑

结论一句话：VLA 是端侧组件，云是它的工厂与考场，不是它的运行时。这条结论把第四篇的架构与本篇缝死了。

5.7.3 与产业物联网平台的映射

Scaling 智驾 备注
大骨干+轻动作头 大模型蒸馏到车端 同一路线
跨本体共训 多车型共训 embodiment≈车型
云端大脑+端侧小脑 云端 Agent + 车端模型 结构同构
模型不上云做控制 智驾不依赖云闭环 铁律同源

5.7.4 企业实践建议

面对「能不能把 VLA 放云端省 GPU」的提问（一定会有人问），用 4.9.3 三问 + 5.7.2 矩阵回答，并把它写进架构原则文档——这类问题每季度都会重来一次，有文档就不必重新辩论。

5.7.5 面试可能问什么

  1. VLA 能不能云端推理？（要点：矩阵 + 三问 + 「云是工厂与考场不是运行时」）
  2. 一个策略服务多本体需要什么？（要点：动作空间抽象、embodiment 条件化、Profile 与数据维度）

5.7.6 最佳实践

  • 机型规格书与模型规模上限绑定演进：新一代硬件到位前，模型规模冻结——避免「模型跑在 PPT 上」。

5.7.7 常见误区

  • ❌ 拿云端 GPU 利用率的账去论证 VLA 上云——它是控制链路组件，账不能这么算。

5.7.8 Obsidian 永久笔记

  • VLA 是端侧组件：云是工厂与考场，不是运行时。
  • 三条 Scaling 轴：模型/数据/本体，本体那条是平台的活。

5.8.2 环节与平台平面对照表

环节 落在哪个平面 已有存量
1 需求与判据 任务面 + 评测规范 你的 Agent 评测方法论
2 采集 任务面（采集任务）+ 数据面 Fleet 调度可复用
3 处理 数据面（第七篇） Kafka/Flink/湖仓原班人马
4 训练 AI 面（训练平台） GPU 平台经验
5-6 评测 AI 面 + 仿真（第八篇） 评测门禁思想复用
7 打包 OTA 面（制品库+签名） 制品治理
8 分发 OTA 面（分发网络） 云管端升级 + 模型子系统
9 运行 边缘/端侧 + 数据面 可观测体系

九个环节没有一个是「纯算法」——七个落在你的存量能力上。这张表是本篇给你的最大信心：VLA 时代的机器人公司，缺的不是模型工程师，是能把这九环节连成飞轮的平台架构师。

5.8.3 平台架构师与算法团队的对话接口清单

向算法团队索要（写进模型卡，缺项即拒绝入库）：

  • 观测契约：话题清单、图像路数/分辨率/预处理、状态字段与关节顺序、历史帧数
  • 动作契约：空间（关节/任务）、绝对或增量、单位、归一化统计量文件、chunk 长度 H
  • 频率契约：推理频率、期望控制频率、可容忍的最大推理延迟
  • 资源契约：FP16/量化后显存、期望硬件、是否支持 TensorRT/ONNX 导出
  • 评测契约：训练数据集版本与卡片、离线指标、仿真基准分、已知失效场景
  • 合规契约：权重来源与许可、数据来源与许可

向算法团队承诺（平台的交付物）：数据集版本化与血缘、训练算力与调度、仿真基准环境、模型 OTA 与灰度回滚、影子评测与分歧回传、线上指标看板与失效现场包。这两份清单构成平台与算法的 SLA——把它贴在两个团队的协作文档首页。

5.8.4 与产业物联网平台的映射

九环节 ≈ 智驾模型的「采集→标注→训练→仿真→评测→OTA→影子」全流程；对话接口清单 ≈ 你与智驾算法团队的模型交付规范。名词一换，方法论零折损。

5.8.5 企业实践建议

用「九环节成熟度雷达」做季度评估（每环节 0~5 分），预算精确投向最短板——第一次评估通常会发现：训练算力不缺、模型不缺，缺的是 3（数据处理）与 9（影子评测）。这两处正是平台团队最该先动手的地方。

5.8.6 面试可能问什么

  1. 画出 VLA 的完整工程 Pipeline。（要点：九环节 + 闭环回流 + 每环节落点）
  2. 平台与算法团队如何协作？（要点：双向清单 = SLA；模型卡缺项拒绝入库）
  3. 你会先补哪个环节？（要点：数据处理与影子评测，给出成熟度雷达的判据）

5.8.7 最佳实践

  • 模型卡即准入契约：CI 里做 schema 校验，缺字段的模型连制品库都进不去（4.3.3 的准入门）。
  • 九环节每环设「单点耗时」度量，飞轮转速 = 从回传到新模型上线的天数——这是机器人公司的第一性指标（1.6.2）。

5.8.8 常见误区

  • ❌ 把 VLA 项目当「算法项目」立项——九环节里七个是平台工程，立项书必须体现。
  • ❌ 缺失环节 9（影子评测）就上灰度——没有影子的灰度是拿客户现场做实验。

5.8.9 Obsidian 永久笔记

  • VLA 九环节：需求/采集/处理/训练/离线评测/仿真评测/打包/分发/运行影子。
  • 七个环节是你的存量：VLA 时代缺的是连飞轮的平台架构师。
  • 双向清单即 SLA：模型卡六契约 ⇄ 平台六承诺。
  • 飞轮转速：从回传到新模型上线的天数。

5.9 本篇总结

5.9.1 十条核心结论

  1. VLA = 多模态骨干 + 动作头；它接管的是「怎么做」，因此是模型制品而非代码制品。
  2. 分层混合是现阶段现实：慢脑规划（云边）、中脑 VLA（机上）、快脑安全（机上）。
  3. 谱系三支：ACT/DP 视觉运动策略、RT/OpenVLA 大模型骨干、π0/GR00T 高频连续；OXE 与 LeRobot 是地基。
  4. 平台只盯三契约：观测、动作、频率——注册表必填、Runtime 断言。
  5. 动作分块 = 智驾的「轨迹下发 + 高频跟踪」，chunk 内开环必须靠快脑兜底。
  6. 延迟不等式：推理延迟 + 抖动裕度 < chunk 时长；P99 与抖动比均值重要。
  7. 双缓冲热切换要双份显存——端侧选型最易漏的一条约束。
  8. 数据是真正的战场：三源配方 + 质检门禁 + 触发回传补长尾；「一条演示的成本」要可视化。
  9. 安全不由模型负责：契约/限幅/监控/系统四层安全带独立演进，安全事件一票否决。
  10. VLA 九环节里七个落在你的存量平面上——飞轮转速是机器人公司的第一性指标。
