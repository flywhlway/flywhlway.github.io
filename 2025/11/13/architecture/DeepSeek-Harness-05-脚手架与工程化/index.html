A5 · Goal 领域：持久阶段与进程本地激活的正交分离

A5.1 两个正交状态

状态 性质 回答的问题
GoalPhase 持久（goal/change 事件） 目标发生了什么？active / paused / blocked / complete
GoalActivation 进程本地，永不持久化 续跑消费方能否开始另一个 Round？armed / disarmed

为什么分开？ 官方理由：

“激活态有意不参与持久回放，因此在恢复或 fork 后，只有随后通过 /goal 或模型工具执行一次经人类授权的恢复变更，自动工作才能开始。”

这是一条安全设计：进程重启不会让自动 Round 悄悄恢复运行。恢复一个持久目标 ≠ 恢复自动执行权限。

A5.2 数据模型

blocked 是唯一表示”因问题而停止”的持久状态——不用异常、不用 null、不用魔法字符串。

A5.3 回放的严格性

“续跑消费方会为每个获准的用户消息轮次标注正数且连续的 Round 编号和当前修订号；只有这些获准的 user/message 事件会推进 roundsStarted。

回放会拒绝：非正数 Round、编号缺口、陈旧修订号、已停止阶段、超出上限。”

这五条拒绝规则意味着：任何被篡改或损坏的目标日志都会在回放时大声失败，而不是折叠出一个看似合理的错误状态。

A5.4 Goal Round 与 Turn 的关系

  • Goal Round 是一个由目标触发的轮次，其中可包含零个或多个步骤
  • 同一会话中无关的人类轮次不消耗 Goal Round 上限

这个区分很实用：用户中途插一句”等等，先看看日志”不会浪费目标预算。

A6 · Hooks 协议桥接：复用现有 Claude Code / Codex 钩子

如果团队已有 Claude Code hooks 资产，这是零改写迁移的路径。

A6.1 三层结构

Codex 刻意重实现了 Claude Code 钩子协议的一个子集——相同的 hooks.json matcher-group 形状、相同的退出码/stdout 输出契约、相同的命令钩子执行模型。dsh 把真正共享的部分抽到一个库里，两个桥接各自只写差异。

A6.2 Matcher 语义差异

模式 行为
claude 纯 [A-Za-z0-9_|]+ 模式视为字面量（| = 精确匹配的或），其他视为正则
codex 始终是无锚定正则

两者都对 缺省 / '' / '*' 做 match-all。

防御设计：桥接解析器先丢弃无 matcher 主体的事件的 matcher 字段，再用 matcherDiagnostic 在注册任何钩子之前用稳定诊断拒绝无效正则。而运行时谓词仍然把无效模式包容为不匹配——因此直接调用库的调用方不会把异常抛进 agent loop。

这是一个双保险：配置期大声失败 + 运行期静默降级。

A6.3 凭据处理

runHook 会”在执行器的凭据擦洗之后合并 options.env“——用的是 dsh-shell 的受信任插件 API。这意味着钩子拿到的是干净环境 + 桥接显式提供的变量，而不是宿主的全部环境。

A6.4 接入方式

映射到的扩展点：agent/session-start、agent/pre-step、agent/request、tools/pre-execute、tools/post-execute、agent/turn-stopping。

注意：钩子命令是沙箱之外的受信任可执行代码，与 MCP server 命令同级。企业环境需要走白名单审批。

B2 · 组合层设计：cordis.patch.yml 逐行解读

B2.1 结构

一个 patch 文件是一个 patch 条目的 YAML 数组。insert 加新行，patch 按 id 定位既有行。

B2.2 !!js 表达式的三种典型用法

B2.3 覆盖 base 行的三个真实场景

踩坑提醒：disabled 是行级字段，配置无法禁用一行——必须用 patch 的 disabled: true。这也是为什么 DSH_TELEMETRY_DISABLED 的实现方式是”启动器把该行 patch 成 disabled”，而不是往 config 里塞一个开关。

B2.4 验证方式

dump 输出会标明每行由哪个文件提供、哪些 overlay 修改过它，!!js 保持未求值，找不到目标的 patch 报到 stderr。这是验证你的 bundle 是否正确落层的唯一可靠方式。

B3 · LLM 网关适配器：六条协议义务的逐条落地

B3.1 义务 1：usage 在 finish 之前，finish 之后什么都不发

为什么必须缓冲？ 很多网关把 usage 放在 finish_reason 之后的最后一帧。直接透传会违反顺序契约。缓冲到流结束再统一 flush 是官方推荐的稳健做法。

B3.2 义务 3：块 index 按首次出现的流顺序分配

同一逻辑块的每次 delta 复用首次分配的 index。这是回放保真度的前提。

静默丢弃是最坏的做法——模型以为 stop 生效了，实际没有，行为差异会以极难定位的方式出现在下游。

B3.6 密钥处理

绝不读自定义密钥文件。 生产环境进一步应改为通过 ctx.credentials 按请求解析，这样轮换后的凭据在紧接着的下一次请求就生效。
