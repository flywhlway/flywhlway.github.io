01 · 渐进式披露：Discovery / Activation / Execution 三段式运行时

企业级 Skill Registry 平台工程手册 · 第 01 篇
读者：AI 平台工程师 / Agent Runtime 架构师
本篇回答一个问题：为什么 Skill 系统能在挂载数千个技能的同时，保持基线上下文开销 O(N·ε) 而非 O(N·全量)，并且这个机制在你的平台上应该怎么实现。

1. 概述

渐进式披露（Progressive Disclosure）是 Agent Skills 体系的核心运行时契约。它规定：技能内容按”需要知道”的粒度分三级进入模型上下文：

级别 内容 进入上下文的时机 典型体量
L1 元数据 name + description 会话启动时，全量注入 60~150 token / skill
L2 主体 SKILL.md 正文 任务与 description 匹配时 1k~5k token
L3 资源 references / scripts / assets 执行中按需 无上限（scripts 可执行而不加载）

这不是 prompt 组织技巧，而是一个运行时协议：它定义了 Agent Runtime、文件系统（或 Registry）、模型三方之间的加载状态机。企业平台照搬”把所有技能文档塞进系统提示”的做法，在 50 个技能规模上就会崩溃；理解三段式协议后，同一套机制可以支撑数千技能。

2.2 注意力稀释：比 token 上限更早到来的失效

即使窗口装得下，长上下文中指令遵循质量随无关内容占比上升而下降（lost-in-the-middle 效应、指令间相互干扰）。一个未被任务需要的 4k token 技能文档不是”无害的冗余”，而是：

  • 稀释了真正相关指令的注意力权重；
  • 引入了跨技能指令冲突的可能（两个技能对同一格式给出不同规定）;
  • 增加了模型”错误地遵循了不该激活的技能”的概率——这在生产上表现为幽灵触发（ghost activation），比漏触发更难排查。

因此 L1 元数据的设计目标不是”压缩摘要”，而是路由表条目：给模型刚好够做出”要不要打开”决策的信息，一个字不多。（description 的设计科学见第 02 篇。）

2.3 与传统插件架构的本质区别

维度 传统插件（函数调用式） Skill 三段式
能力形态 结构化 API（schema 固定） 程序性知识（自然语言 + 脚本）
路由方 调用方显式指定 / function-calling 强制选择 模型基于 description 自主判断
加载成本 schema 全量常驻 元数据常驻，正文懒加载
组合方式 编排引擎硬编码 模型在上下文内自由组合多个已激活技能
失败模式 调用错函数 漏触发 / 误触发 / 幽灵触发

Skill 不是”更松散的 function”，而是把流程知识（怎么做、按什么顺序、注意什么坑）变成可分发的一等公民。你的平台如果只做了”markdown 文件的 CRUD”，等于只实现了 L2 的存储，三段式协议的价值一分没拿到。

3. 三阶段详解

3.1 Discovery（发现）

发生时机：会话/任务初始化。
动作：Runtime 将所有可见技能的 L1 元数据渲染进系统提示（或等价的常驻上下文区）。
产物：模型获得一张”能力路由表”。

生产实现要点：

  1. 可见性过滤先于渲染。多租户平台上，Discovery 阶段注入的列表 = 全量技能 ∩ 租户授权 ∩ 用户角色授权 ∩ 当前 surface 支持。权限判定放在这里而不是激活时，能同时省 token 和堵住”模型知道了不该知道的技能存在”这个信息泄露面。
  2. 渲染格式稳定。模型对路由表的解析质量依赖格式一致性。建议固定为：
  1. location 必须是可寻址的。Discovery 只给指针不给内容——这个指针（文件路径 / registry URI）是 Activation 阶段的入口。指针失效 = 技能事实上不存在。

3.2 Activation（激活）

发生时机：模型判断当前任务与某个 description 匹配。
动作：模型通过文件读取工具（view / cat）加载 SKILL.md 全文进上下文。
产物：该技能的完整流程知识对本轮及后续推理可见。

三个必须理解的运行时事实：

  1. 激活是模型的自主工具调用，不是框架注入。Runtime 不做”检测到关键词→注入正文”的旁路逻辑（那是 Cursor Rules 的 glob 模式，见 §7）。激活决策发生在模型的推理内部，依据只有 description。这意味着：激活质量 = description 质量，没有第二个杠杆。
  2. 激活有”复杂度门槛”。可观测的行为规律：模型只在”靠自身能力不能轻松完成”的任务上查阅技能。单步简单请求（”读一下这个 PDF”）即使 description 完全匹配也常常不触发——模型直接用基础工具做了。这不是 bug：技能是为”多步、专业、有坑”的流程准备的。设计评测集时必须用有实质复杂度的 query（详见第 10 篇）。
  3. 激活是幂等的、可叠加的。一次任务可以激活多个技能（如 docx + brand-guidelines），先后加载的正文在上下文里共存。平台侧要保证多技能间指令不冲突——这是 08 篇”规范”和 05 篇”评审流程”要管的事。

3.3 Execution（执行）

发生时机：技能正文已加载，模型按其指令行动。
动作：按需读取 references/，通过沙箱执行 scripts/，使用 assets/ 产出交付物。
产物：任务结果 + 遥测数据。

L3 的两条黄金路径：

  • references/ 走”读取”路径：内容进入上下文，供模型推理使用。所以 reference 文件要为”被模型读”优化：带目录、按域拆分（aws.md/gcp.md/azure.md 各自独立，只读命中的那个）、超过 300 行加 TOC。
  • scripts/ 走”执行”路径：代码不进入上下文，只有 stdout/stderr 进。一个 2,000 行的日志解析脚本，上下文成本 ≈ 一次 bash 调用 + 几百 token 输出。凡是确定性、重复性的操作，一律下沉为脚本——这是 token 成本优化中杠杆最大的一条。

4. 运行时状态机

单个技能在一次会话中的生命周期：

stateDiagram-v2
    [*] --> REGISTERED: 平台侧发布
    REGISTERED --> DISCOVERABLE: 会话初始化<br/>权限过滤通过, L1 注入
    DISCOVERABLE --> CANDIDATE: 模型推理中<br/>判定 description 匹配
    CANDIDATE --> ACTIVATED: 读取 SKILL.md 成功<br/>(L2 进入上下文)
    CANDIDATE --> DISCOVERABLE: 匹配置信不足, 放弃
    ACTIVATED --> EXECUTING: 开始按指令行动
    EXECUTING --> RESOURCE_LOADING: 按需读 references (L3)
    RESOURCE_LOADING --> EXECUTING
    EXECUTING --> SCRIPT_RUNNING: 沙箱执行 scripts
    SCRIPT_RUNNING --> EXECUTING: stdout 回流
    SCRIPT_RUNNING --> FAILED: 超时 / 非零退出且不可恢复
    EXECUTING --> COMPLETED: 任务达成
    EXECUTING --> FAILED: 指令不可执行 / 前置条件缺失
    FAILED --> EXECUTING: fallback 路径 / 重试
    COMPLETED --> [*]: 会话内保持已加载<br/>(上下文不回收)
    FAILED --> [*]

转移条件表（平台可观测/可干预点标注）：

转移 触发条件 平台可观测? 平台可干预?
REGISTERED→DISCOVERABLE 会话初始化 + ACL 通过 ✅ 注入日志 ✅ 权限/灰度开关
DISCOVERABLE→CANDIDATE 模型内部判定 ❌（黑盒） ⚠️ 仅通过 description 间接影响
CANDIDATE→ACTIVATED 文件读取工具调用 ✅ 工具调用日志 ✅ 读取时二次鉴权/审计
EXECUTING→SCRIPT_RUNNING bash/沙箱调用 ✅ ✅ 沙箱策略、超时、资源限额
→COMPLETED / FAILED 任务级判定 ⚠️ 需显式埋点 —

关键结论：DISCOVERABLE→CANDIDATE 这一跳是全链路唯一的黑盒，也是唯一无法用工程手段兜底的环节。所以企业平台的可靠性投资顺序应该是：description 评测闭环（10 篇）> 激活审计（07 篇）> 其它一切。

4.1 上下文驻留策略

注意状态机里 COMPLETED 后上下文不回收：已加载的 SKILL.md 在本会话剩余轮次持续可见。这带来两个工程含义：

  1. 同会话第二次使用零成本——这是好事；
  2. 长会话中已激活技能的指令持续生效，可能干扰后续无关任务——这是”技能串味”问题。缓解手段：SKILL.md 正文中的指令一律写成任务条件式（”当处理 X 时…”），而非无条件命令式（”总是…”）；平台评审时把无条件命令式指令列为阻断项（见 08 篇反模式 AP-7）。

注意第 3~4 步与第 5 步之间没有任何框架介入——激活完全由模型驱动。Runtime 的职责边界：注入路由表、提供存储寻址、提供沙箱、收遥测，仅此四件。把路由逻辑做进 Runtime（比如关键词匹配自动注入正文）是最常见的架构错误，见 §8 方案对比。

6. Token 与延迟的最小化机制

6.1 Token 侧：分层预算

给平台定一个可执行的预算规范：

层 预算上限 超限处理
L1 单技能 150 token（约 500 汉字 description 上限） 注册时 lint 阻断
L1 总量 上下文窗口的 3%~5% 超过则启用两级路由（§8 方案 C）
L2 单技能 500 行 / ~5k token 强制拆 references + 层级导航
L3 单 reference 无硬限，>300 行必须带 TOC 评审提示

500 行规则的原理：SKILL.md 是”指令”，reference 是”资料”。指令必须整体进入注意力焦点，资料只需片段命中。混在一起会让指令被资料稀释。判据：模型每次激活都需要的内容留在 SKILL.md，只有特定分支才需要的内容下沉 references。

6.2 延迟侧：存储拓扑

激活延迟 = 路由表寻址 + SKILL.md 读取。三种拓扑：

生产建议：拓扑 C + 会话级版本快照。会话中途技能内容变更是灾难性的（模型前后看到两个版本的指令），所以缓存失效粒度必须是”会话”而不是”TTL”。

6.3 避免不必要加载的四道闸

  1. Description 即闸门（第一道，最重要）：负面边界写进 description——“Do NOT use for X” 直接降低误激活。
  2. 复杂度门槛（模型内生）：简单任务不查技能，天然省了大部分无效激活。
  3. 域内变体拆分：cloud-deploy 主 SKILL.md 只含选型逻辑，references/aws.md 等按命中加载——避免”激活一个技能 = 加载它支持的所有变体”。
  4. 脚本化下沉：任何模型不需要”理解其实现”的逻辑都进 scripts/，执行而非阅读。

8. 企业平台的 Discovery 层设计选型

当技能数超过 L1 预算（经验值：300~800 个，取决于 description 平均长度），单级全量注入失效。三个演进方案：

方案 A：单级全量注入（基线）

  • 优点：零路由基础设施、模型看到全貌、组合能力最强。
  • 缺点：规模上限硬；跨域技能混杂加剧幽灵触发。
  • 适用：≤300 技能，或单域平台。

方案 B：Embedding 检索式注入

  • 优点：规模无上限。
  • 缺点：路由决策从模型内挪到了检索器——检索器不懂任务规划，只懂语义相似。多步任务中第 3 步才需要的技能，第 1 步的 query 根本检索不到。召回失败 = 技能对本次会话彻底不存在，且无法被模型的推理弥补。
  • 适用：单轮问答式产品。多步 Agent 平台慎用作唯一机制。

方案 C：两级路由（类目摘要 + 域内全量）——推荐

  • 本质：把渐进式披露向上再递归一层，路由决策仍留在模型内，只是路由表本身也懒加载了。
  • 成本：多一跳工具调用（+一轮延迟）；域划分质量成为新的失败面。
  • 配套：域卡片 description 的写法 = 该域所有技能触发场景的并集摘要，同样需要进 10 篇的评测闭环。
  • 可与方案 B 混合：embedding 检索作为域卡片的补充召回而非替代（belt-and-suspenders）。

决策矩阵：

技能规模 任务形态 推荐
<300 任意 A
300~3000 多步 Agent C
300~3000 单轮问答 B 或 C
>3000 多步 Agent C + B 混合

9. 反模式

  • AP-1 巨型 SKILL.md：把 references 内容内联进正文。症状：激活一次吃掉 20k token，且指令遵循质量下降。治理：500 行 lint + 评审阻断。
  • AP-2 框架旁路路由：Runtime 用关键词/正则检测用户输入自动注入技能正文。症状：glob 命中≠语义相关，误注入率高且模型无法”决定不用”。三段式协议的路由权必须留在模型。
  • AP-3 预载 references：激活时连带把所有 reference 读入”以防要用”。直接违背 L3 按需契约。
  • AP-4 Description 里写实现：把”怎么做”塞进 description 试图省一次激活。结果：L1 预算爆炸 + 模型跳过正文按残缺指令行动。
  • AP-5 技能间隐式依赖：SKILL.md 里写”参见 xxx 技能的做法”。激活不传递，另一个技能可能根本不在可见集。依赖必须显式声明进元数据（05 篇），由 Runtime 保证共同可见或内联必要内容。
  • AP-6 用技能承载易变数据：把每周更新的价目表/接口地址写进 reference。技能是流程知识，易变数据走工具实时获取。判据：变更频率高于技能发版频率的内容不属于技能。
  • AP-7 无条件命令式指令：正文写”所有输出必须为 JSON”。长会话中该技能完成后指令仍驻留，污染后续任务。一律改条件式。

10. 生产建议清单

  1. Discovery 注入格式全平台统一，进 CI 校验（schema + token 预算 lint）。
  2. 激活链路埋点三件套：skill_injected（L1）、skill_activated（L2 读取）、resource_loaded（L3），全部带 skill_id + version + session_id。没有这三个事件，10 篇的评测体系无从谈起。
  3. 版本一致性以会话为快照边界；会话中途禁止技能热替换（热更新语义见 06 篇：只影响新会话）。
  4. scripts/ 全部经沙箱执行，默认无网络、只读挂载技能目录、可写仅工作区（07 篇展开）。
  5. 平台早期就实施 500 行 / 150 token 两条预算红线——存量技能越多，事后治理越贵。
  6. 两级路由（方案 C）的域划分对齐组织的能力域而非技术栈：vehicle-diagnosis 是好的域，python-skills 不是。
  7. 把本篇状态机直接映射为 Registry 侧技能实例的观测模型：每个会话每个技能一条状态轨迹，是排查”为什么没触发”的唯一事实来源。

附录 B：Runtime 侧参考接口

状态机在 Runtime 中的最小接口（语言无关伪码，Java/Spring 控制面可直译为领域服务）：

设计要点：

  1. discover() 返回的 pins 是会话一致性的实现载体——后续所有 onSkillRead 按 pin 解析路径，Registry 侧发新版不影响进行中会话。
  2. onSkillRead 是二次鉴权点：L1 可见 ≠ L2 可读（某些敏感技能可以”可发现但激活需审批”，用于高危操作类技能的人审闸门）。
  3. 接口刻意没有 activate() 方法——再强调一次，激活不是 Runtime 的动作，Runtime 只有观测回调。

附录 C：遥测事件 Schema

三件套事件的最小字段（07 篇展开完整 tracing 体系）：

l1_position 单独说明：技能在路由表中的渲染位置。收集它是为了离线分析位置效应——列表首尾的技能是否有系统性触发率优势。若有（长列表下常见），两级路由的域内排序就应该按”专职优先 + 轮换”策略消偏，而不是固定字母序。

附录 D：本篇检查清单（平台落地自查）

  • L1 渲染格式有 schema，进 CI
  • 单技能 150 token / 总量 5% 双预算 lint
  • SKILL.md 500 行红线 + references TOC 检查
  • 存储拓扑为本地缓存 + 懒回源，会话级版本快照
  • 激活权 100% 在模型，Runtime 无任何正文旁路注入逻辑
  • 三件套遥测事件上线，含 l1_position
  • 技能可见性 = 租户 ∩ 角色 ∩ surface 三重过滤
  • 状态机各转移的观测点与干预点已映射到具体组件
  • 两级路由的域划分方案已评审（按能力域，非技术栈）
  • 无条件命令式指令列入评审阻断项
