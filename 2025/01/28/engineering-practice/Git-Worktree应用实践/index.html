Git Worktree 应用实践指南

让同一个 Git Repository 同时拥有多个独立的工作目录，每个目录可以处于不同 branch / commit，从而实现真正的并行开发。

Flywhl 12 分钟 发布于 2025.01 #工程实践#DevOps

概述

git worktree 是 Git 中一个非常值得掌握、但实际开发中经常被低估的能力。它解决的核心问题不是“多分几个 branch”，而是：

让同一个 Git Repository 同时拥有多个独立的工作目录，每个目录可以处于不同 branch / commit，从而实现真正的并行开发。

Git 官方定义就是“Manage multiple working trees”。一个 repository 可以拥有一个 main worktree，以及多个 linked worktree；这些 worktree 共享 Git object database，但各自拥有独立的 HEAD、index 和工作目录。

对于你这种 Cursor / ClaudeCode / Codex + Python/FastAPI + Agent 微服务 的开发模式，我尤其推荐把 Worktree 纳入日常工作流，因为它非常适合 多 Agent 并行开发。

1. 先理解：Worktree 到底解决什么问题

传统 Git 开发：

一个 Repository

  │

  └── 一个工作目录

          │

          ├── main

          ├── feature/a

          ├── feature/b

          └── hotfix

你只能：

git switch feature/a

然后：

git switch feature/b

如果当前有未提交修改，就需要：

git stash

git switch feature/b

…

git stash pop

这就是典型的上下文切换成本。

Worktree 则变成：

~/workspace/

│

├── flywhl-cloud/ # main

│

├── flywhl-cloud-agent/ # feature/agent

│

├── flywhl-cloud-security/ # feature/security

│

├── flywhl-cloud-evaluation/ # feature/evaluation

│

└── flywhl-cloud-hotfix/ # hotfix/xxx

实际上：

             ┌── main worktree

             │

Git Repository ──┼── feature/agent

             │

             ├── feature/security

             │

             ├── feature/evaluation

             │

             └── hotfix

它们共享 Git 对象存储，但每个 worktree 都有自己的：

  • 工作目录
  • HEAD
  • staging area / index
  • branch checkout 状态

所以你可以：

Cursor Window 1 → feature/agent

Cursor Window 2 → feature/security

Claude Code → feature/evaluation

Codex → hotfix

同时工作。

Git 官方文档明确说明，linked worktree 的管理信息位于 $GIT_DIR/worktrees，而 branch refs 等核心 Git 对象则共享。

2. Worktree vs Branch vs Clone

这是最重要的概念区别。
能力 Branch Worktree Clone
创建分支 ✅ 通常配合 branch ✅
同时打开多个分支 ❌ ✅ ✅
独立工作目录 ❌ ✅ ✅
Git object 是否共享 N/A ✅ ❌
磁盘占用 最低 较低 高
适合并行开发 一般 非常适合 可以
适合 PR Review 一般 非常适合 可以
适合 Hotfix 一般 非常适合 可以
适合多个 AI Agent 不方便 非常适合 可以
Repository 历史重复 不存在 不重复 重复

所以可以简单记：

Branch

= Git 逻辑上的开发分支

Worktree

= Branch + 独立物理工作目录

Clone

= 完整独立 Repository

Worktree 相比 clone 最大优势就是共享 Git object database，因此大型 repository 尤其有价值。

当前 HEAD

│

└── 创建 feature/auth

       └── ../project-auth

cd ../project-auth

git branch –show-current

得到：

feature/auth

5. 从已有 Branch 创建 Worktree

假设已经存在：

feature/payment

执行：

git worktree add ../project-payment feature/payment

现在：

project/

project-payment/

两个目录分别 checkout：

project → main

project-payment → feature/payment

6. 创建 Hotfix Worktree

这是 Worktree 最经典的应用场景。

假设你正在：

feature/agent

开发，而且当前有大量未提交代码：

feature/agent

├── 修改 20 个文件

├── Debug session

├── 本地测试

└── 未提交代码

突然线上需要：

hotfix/login-timeout

传统方案：

git stash

git switch main

git switch -c hotfix/login-timeout

…

git switch feature/agent

git stash pop

Worktree：

git worktree add -b hotfix/login-timeout ../project-hotfix main

然后：

cd ../project-hotfix

修复：

git add .

git commit -m “fix: login timeout”

git push origin hotfix/login-timeout

完成：

cd ../project

git worktree remove ../project-hotfix

你的原来的：

feature/agent

完全没有被打断。

这正是 Git 官方文档给出的典型 emergency fix 场景。

7. PR Review 是另一个非常好的场景

假设你当前：

feature/a

正在开发。

GitHub 上来了：

PR #128

feature/security → main

不要：

git stash

git switch feature/security

而是：

然后：

cd ../project-pr-128

直接：

甚至：

单独打开这个 PR。

Review 完：

你的原开发环境完全保持原样。

Worktree 非常适合这种“Review while coding”场景。

13. Worktree 与

stash

的关系

不是说 Worktree 完全取代 stash。

两者解决的问题不同。

stash

解决：

“我现在这几个修改暂时不想提交。”

例如：

git stash push -m “WIP parser”

worktree

解决：

“我需要同时维护多个开发上下文。”

例如：

Agent feature

Security feature

Hotfix

PR Review

Benchmark

因此：

临时保存修改 → stash

并行维护多个工作上下文 → worktree

这是一个非常重要的判断标准。

14. Worktree 的状态查看

执行：

git worktree list

例如：

/Users/me/workspace/project

abc1234 [main]

/Users/me/workspace/project-agent

def5678 [feature/agent]

/Users/me/workspace/project-security

789abcd [feature/security]

更详细：

git worktree list -v

脚本处理则推荐：

git worktree list –porcelain

15. 删除 Worktree

正常情况下：

git worktree remove ../project-security

注意：

remove Worktree

≠

delete Branch

例如：

git worktree remove ../project-security

只是删除：

../project-security

branch：

feature/security

仍然存在。

如果 branch 已经 merge：

git branch -d feature/security

所以完整清理：

git worktree remove ../project-security

git branch -d feature/security

16. 手动删除目录后怎么办？

不要直接：

rm -rf ../project-security

虽然文件目录没了，但是 Git 可能仍然认为 worktree 存在。

此时：

git worktree prune

推荐先：

git worktree prune -n

查看将要清理什么。

然后：

git worktree prune

官方文档也明确说明，如果 linked worktree 没通过 git worktree remove 删除，其管理元数据可以通过 prune 清理。

17. Move Worktree

如果：

../project-agent

想移动：

../worktrees/project-agent

不要直接 mv。

使用：

git worktree move ../project-agent ../worktrees/project-agent

然后：

git worktree list

确认。

18. Worktree Lock

如果 worktree 在：

外置磁盘

网络文件系统

不稳定挂载路径

可以：

git worktree lock ../project-agent –reason “external SSD”

解除：

git worktree unlock ../project-agent

对于普通 MacBook 本地开发一般不需要。

27. 一个非常实用的脚本

你可以在 Mac 上做一个简单的 helper。

#!/usr/bin/env bash

基于 origin/main

28. 推荐再增加一个清理脚本

例如：

#!/usr/bin/env bash

set -euo pipefail

git worktree list

echo

read -r -p “Remove worktree path: “ PATH_TO_REMOVE

git worktree remove “$PATH_TO_REMOVE”

echo

echo

git worktree list

可以避免误删。

29. 常见坑

坑 1：一个 Branch 不能同时 checkout 到两个 Worktree

例如：

git worktree add ../a feature/test

git worktree add ../b feature/test

通常 Git 会拒绝。

因为：

feature/test

 ↓

已经被 worktree A 使用

这是 Worktree 保持 branch 状态一致性的核心机制。

如果确实需要特殊操作，可以考虑：

git worktree add -f …

但不建议日常使用。

坑 2：Worktree 不是 Clone

不要误以为：

Worktree A

Worktree B

拥有两个完全独立的 Git Repository。

实际上它们共享 repository 的 Git object storage。

因此：

git gc

git repack

git fetch

等 Repository 级操作，需要理解它们的共享关系。

30. 坑 3：不要直接删除

.git/worktrees

不要：

rm -rf .git/worktrees

Git 官方内部管理结构不要手动修改。

优先：

git worktree remove

如果目录已经被手工删除：

git worktree prune

31. 坑 4：Submodule

如果项目大量使用：

Git Submodule

Worktree 要更加谨慎。

Git 官方目前仍明确提示：multiple checkout 对 submodules 的支持并不完整，因此不推荐在复杂 superproject/submodule 场景中盲目使用。

如果你的项目：

Spring Cloud

大量 Git Submodule

建议先做 POC。

32. Worktree Config

这是比较高级但非常有用的能力。

Git 默认很多 configuration 是共享的，但可以开启：

让某些 configuration 变成：

Worktree A → 独立配置

Worktree B → 独立配置

Git 官方文档对此有专门说明。

这对于：

不同 Worktree

不同 sparse checkout

不同 core 配置

不同开发环境

比较有价值。
