01 · 可观测性与 OpenTelemetry 体系总览（2026）

本篇回答三个问题：可观测体系由什么组成？OpenTelemetry 在其中扮演什么角色？2026 年的技术选型格局是什么？
阅读时间约 20 分钟，为后续实操篇建立统一心智模型。

1. 可观测性的四个信号

传统三大信号 + 2026 年正在孵化的第四信号：

信号 回答的问题 典型后端 数据特征
Metrics 系统趋势如何？（QPS/延迟/Token 消耗） Prometheus / Mimir 低基数、聚合、时序
Logs 具体发生了什么？ Loki / Elasticsearch 高吞吐、文本/结构化
Traces 请求经过了哪些服务、慢在哪？ Tempo / Jaeger 树状 Span、高价值低留存
Profiles CPU/内存花在哪些函数上？ Pyroscope 采样火焰图（OTLP Profiles 仍在演进）

AI Agent 系统在此之上叠加了 AI 信号维度——它们不是新信号类型，而是以属性（Attributes）、事件（Events）、指标（Metrics）的形式附着在三大信号上：

关键认知：AI 可观测 = 传统链路观测 + GenAI 语义约定（gen_ai.*）+ AI 业务层平台（Langfuse 等）。三者是叠加关系，不是替代关系。

2. OpenTelemetry 是什么、不是什么

OpenTelemetry（OTel）不是监控平台，而是一套「遥测数据的采集标准 + 实现」：

2026 年的关键节点：

  • 2026-05，OTel 从 CNCF 正式毕业，成为继 Kubernetes、Prometheus 之后的默认可观测标准；行业调研显示约半数组织已在生产使用。
  • 语义约定发布至 v1.41+；GenAI 语义约定迁移至独立仓库 open-telemetry/semantic-conventions-genai，覆盖 LLM 调用、Agent、MCP、工具调用、内容捕获、评测六个层面（状态仍为 Development，详见文档 02）。
  • Prometheus 3.x 原生支持 OTLP ingest 与 OTel 命名约定，Metrics 链路上 OTel 与 Prometheus 生态已完成合流。
  • 主流 AI 框架（LangChain/LangGraph、OpenAI Agents SDK、Spring AI、LlamaIndex、vLLM 等）与主流后端（Datadog、Grafana、Honeycomb、Langfuse）均已围绕 gen_ai.* 对齐。

结论（本文档集采用）：自托管 LGTM 栈（Loki + Grafana + Tempo + Mimir/Prometheus）+ OTel Collector 作为系统层；Langfuse 作为 AI 业务层。理由：

  1. 全开源、可控、无数据出境问题，满足车企/国企合规要求；
  2. Tempo 基于对象存储、无索引成本，TraceQL 可直接按 gen_ai.* 属性检索；
  3. Tempo metrics-generator 可从 Trace 自动生成 RED 指标与服务拓扑图，写入 Prometheus；
  4. Langfuse 原生作为 OTLP 后端接收 gen_ai.* Trace，与 LGTM「一次埋点、双端消费」。

3.3 Grafana Alloy 与 OTel Collector 的关系

Grafana Alloy 是 Grafana 发行的 OTel Collector 增强发行版：100% 兼容 OTLP，额外内置 Prometheus 抓取、loki.source.docker（直接采集容器 stdout 日志）等组件，并取代了已停止演进的 Grafana Agent/Promtail。

选型建议：

  • 纯 OTLP 汇聚 + 路由 → 官方 otelcol-contrib（组件最全，本文档集默认）；
  • 需要顺带抓取 Prometheus exporter、采集 Docker/K8s 容器日志 → Alloy；
  • 两者可共存：Alloy 做边缘采集（Agent 模式），otelcol-contrib 做中心网关（Gateway 模式）。

5. 本章小结

  • OTel 是标准与总线，LGTM 是系统层后端，Langfuse 是 AI 业务层后端；
  • 2026 年选型的最大变化：GenAI 语义约定成为事实标准（尽管仍在 Development），”AI 观测”不再需要私有 schema；
  • 下一篇（02）深入 gen_ai.* 语义约定——它是整套 AI 可观测体系的数据契约。
