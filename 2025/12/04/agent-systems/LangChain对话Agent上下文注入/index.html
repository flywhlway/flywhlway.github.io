LangChain 1.x 对话 Agent 的上下文注入与记忆分层

基于 LangChain 1.1 的 create_agent 与 middleware，拆解对话 Agent 的六层上下文：更新频率、token 预算、缓存友好的放置顺序…

Flywhl 20 分钟 更新于 2026.09 #LangGraph#Agent#上下文工程

先读结论

  1. 上下文按稳定程度排序：系统规则、用户画像在前，摘要和近期消息居中，本轮检索结果贴着最新用户消息放，前缀缓存才能持续命中。
  2. 动态系统提示和检索注入放在 wrap_model_call 里，只改本次请求、不写回 state；需要跨轮保留的东西才用 before_* 钩子写入。
  3. 短期记忆靠 checkpointer + thread_id，长期记忆靠 LangGraph Store；两者生命周期不同，不要混用。
  4. SummarizationMiddleware 的摘要会被再次摘要，硬事实应放进 Store 或结构化 state，而不是只留在摘要里。

从 0.3 到 1.x：同一个问题，换了一套解法

对话 Agent 每次调用模型时，输入窗口都是一次现场拼装：身份规则、用户是谁、之前聊过什么、这一轮查到了什么、工具返回了什么。0.3 时代的拼装方式是 ChatPromptTemplate + MessagesPlaceholder("chat_history") + ConversationSummaryBufferMemory，再交给 AgentExecutor 跑工具循环。这套写法有三个结构性问题：

  • 记忆对象游离在执行图之外。save_context 要么由 AgentExecutor 隐式调用，要么由业务代码手动调用，持久化、并发和回滚都得自己补。
  • 没有“每次模型调用前”的扩展点。想按用户动态改系统提示、在工具循环中途裁剪消息，只能改模板或包装 Runnable。
  • 身份规则和历史混在同一个模板里，一旦有人把系统提示写进 memory，就会在摘要时被压缩掉。

LangChain 1.0 与 LangGraph 1.0 于 2025-10-17 发布到 PyPI（2025-10-22 官宣），把 Agent 统一到 create_agent：底层是 LangGraph 图，对话历史就是图状态里的 messages，由 checkpointer 持久化；扩展点是 middleware。旧 memory 类和 AgentExecutor 移到了 langchain-classic。2025-11-24 发布的 1.1 又补了三件与本文直接相关的东西：模型的 .profile（上下文窗口等能力数据）、SummarizationMiddleware 改用 trigger/keep 参数（1.0.x 是 max_tokens_before_summary/messages_to_keep，1.1 仍兼容但标记弃用）、ModelRetryMiddleware。

本文代码在 langchain==1.1.0、langchain-core==1.1.0、langgraph==1.0.4 下用假模型跑通过。

六层上下文：来源、更新频率、预算与顺序

分层表

层 典型内容 存在哪里 更新频率 建议预算 放置位置
1 系统规则 身份、能力边界、输出格式、安全约束 代码常量或配置中心 发版时 1–2K，固定 系统消息开头
2 用户画像/长期记忆 技术栈、偏好、长期项目状态 LangGraph Store 跨会话累积，每轮最多读一次 ≤1K 系统消息尾部
3 会话摘要 早期对话压缩后的备忘 state messages（checkpoint） 触发阈值时 ≤1.5K 历史消息最前
4 近期消息 最近若干轮原文、工具调用对 state messages 每轮 由摘要阈值封顶 摘要之后
5 检索结果 本轮问题相关的知识片段 检索服务，不入 state 每轮 ≤1.5K 贴着最新用户消息
6 工具结果 ToolMessage state messages 每步 单条截断，旧的可清理 按发生顺序

表里的预算是面向“单轮输入控制在 12K 左右”的对话场景给的起点，不是模型上限。模型窗口动辄 128K 甚至 1M，但每轮都按输入 token 计费，且上下文越长，中段信息越容易被忽略；预算应该按成本和效果定，而不是按窗口定。

放置顺序：稳定在前，易变在后

主流模型服务都做前缀缓存：OpenAI 对 1024 token 以上的提示自动缓存前缀，Anthropic 需要用 cache_control 显式打断点（TTL 5 分钟或 1 小时）。两者的共同点是只有逐字节相同的前缀才能命中。所以排列原则只有一条：越稳定的内容越靠前。

反过来，如果把检索结果、当前时间戳写进系统提示，每轮第一条消息就变了，后面整段历史全部失去缓存。这也是为什么下文把检索结果注入到最新一条用户消息里，而不是系统消息里。

token 预算怎么定

不压缩的代价是二次增长：假设每轮问答约 400 token，第 n 轮的输入约为 400n，20 轮累计输入约 400 × (1+2+…+20) = 84,000 token。设了摘要阈值后，单轮输入被封顶在“阈值 + 检索预算 + 固定层”附近，累计成本从二次增长变为近似线性。

定预算时先算固定层（1+2 层），再给检索留份额，剩下的作为摘要触发阈值。langchain_core.messages.utils.count_tokens_approximately 可以用来做各层的近似计数，它不依赖具体模型的 tokenizer，适合做预算而不适合做计费。

1.x 的注入点：middleware 钩子

钩子与持久化

create_agent 的 middleware 钩子决定了“改动是否写进 checkpoint”，这是设计上下文注入时最重要的一个区分：

钩子 执行时机 返回值写入 state 适合做什么
before_agent 每次 invoke 开始一次 是 读取用户画像快照
before_model 每次模型调用前 是 摘要、永久裁剪历史
wrap_model_call / @dynamic_prompt 包裹每次模型调用 否，只改本次请求 动态系统提示、临时注入检索结果
after_model 每次模型调用后 是 输出校验、跳转控制
after_agent 每次 invoke 结束一次 是 触发记忆提取

执行顺序：before_* 按列表顺序执行，after_* 逆序执行，wrap_* 按列表嵌套（列表第一个在最外层）。

flowchart LR
    U[用户消息] --> BA[before_agent<br/>读画像到 state]
    BA --> BM[before_model<br/>超阈值则摘要]
    BM --> WM[wrap_model_call<br/>拼系统提示与检索]
    WM --> M[模型]
    M -->|tool_calls| T[工具<br/>可写 Store]
    T --> BM
    M -->|最终回答| AA[after_agent]
    AA --> CP[(checkpointer)]

context、state、store 三个容器

容器 生命周期 谁写 放什么
context（context_schema） 单次 invoke，调用方传入 调用方 user_id、租户、权限等身份信息
state（checkpointer + thread_id） 一个会话线程 图内节点与中间件 messages、画像快照等
Store 跨线程、跨会话 工具、中间件、后台任务 用户画像、长期事实

user_id 放在 context 而不是 state，原因是它来自鉴权层，不应该被对话内容改写，也不需要进 checkpoint。

运行时发生了什么

用记录输入的假模型替换真实模型后，两轮对话的实际行为如下：

  1. 第一轮模型调用 remember，工具通过 ToolRuntime 拿到 context.user_id 和 store，把“团队后端统一用 Go”写进 ("users", "u42", "profile")。本轮的系统提示不变。
  2. 第二轮 before_agent 从 Store 读出画像，写入 state 的 profile 字段；ProfileMiddleware.wrap_model_call 把它拼到系统规则之后。
  3. RetrievalMiddleware 命中 “ota”，模型收到的最后一条用户消息变成 <context>…</context> + 原问题；但 invoke 返回的 state 里，这条消息仍是原文。

第 3 点带来一个取舍：下一轮模型看不到上一轮的检索资料，只看到自己基于资料的回答。多数问答场景这正是想要的（旧资料不再占预算），但如果后续追问高度依赖原文，就应改用“检索作为工具”的方式。

检索放在哪：三种注入方式

方式 何时检索 历史里留下什么 缓存影响 适合
wrap_model_call 注入最新用户消息（本文做法） 每轮必检 只有问题原文 历史前缀稳定 客服、FAQ、资料每轮都需要
检索做成工具，由模型决定调用 按需 ToolMessage 留在历史 结果进入可缓存的历史，但持续占 token 多步排查、研究型对话
拼进系统提示 每轮 不留 每轮系统消息变化，整段缓存失效 不推荐

自定义中间件时，before_*/after_* 钩子的第二个参数必须叫 runtime：LangGraph 按参数名注入它，写成 rt 之类的缩写会在运行时报 missing 1 required positional argument。

另外两个细节：_cache 按消息 id 缓存，保证一轮工具循环里多次调用模型时检索只做一次、注入内容一致（生产环境应换成带过期的缓存）；预算按条累加、超出即停，比“取 top-k 再截断字符串”更不容易切断半句话。

压缩历史：SummarizationMiddleware

参数与行为

SummarizationMiddleware 是一个 before_model 钩子，行为可以从源码直接读出：

  • trigger 支持 ("tokens", N)、("messages", N)、("fraction", 0.x)，传列表时任一满足即触发。keep 同样三种单位，默认保留最近 20 条消息。
  • 切分点会避开 AI 工具调用与对应 ToolMessage 之间的位置，不会把一对工具调用拆开。
  • 触发后，旧消息被送去摘要，然后用 RemoveMessage(id=REMOVE_ALL_MESSAGES) 清空 state，再写回一条 HumanMessage("Here is a summary of the conversation to date: …") 和保留的原文。这是写进 checkpoint 的永久改写，不是临时裁剪。
  • 系统提示不在 state 的 messages 里（create_agent 在调用模型时才加上），所以永远不会被摘要掉。这正是 0.3 时代“把身份写进 memory 结果被压缩丢失”问题在 1.x 里的结构性解法。

("fraction", 0.x) 需要模型 profile 提供 max_input_tokens，而且读的是摘要模型的 profile。以 langchain-openai 1.1.0 为例，gpt-4.1-mini 和 gpt-4.1-nano 的 profile 都是 1,047,576 个输入 token，("fraction", 0.5) 意味着 50 万 token 才触发，对成本控制毫无意义。对话场景建议直接用 ("tokens", N)。

短期记忆与长期记忆的落地

短期记忆：checkpointer + thread_id

同一个 thread_id 的所有调用共享 state；换一个 thread_id 就是新会话。开发用 InMemorySaver，进程重启即丢；生产换成 Postgres：

checkpointer 保留每一步的历史快照，agent.get_state_history(config) 可以找回摘要前的完整消息，这是排查“摘要丢了关键信息”时的第一手证据。

两个边界条件：

  • 同一 thread 的并发写。自托管时，同一个 thread_id 上并发执行两次 invoke，会基于同一个旧快照各自追加，结果不可预期。网关层应按 thread_id 串行化（队列或分布式锁）；LangGraph Server 部署则可以用它的 multitask 策略处理。
  • thread 的粒度。一个 thread 对应一段连续对话，不要把一个用户的所有对话放进同一个 thread，那样摘要会越滚越长，也失去了“新会话从干净上下文开始”的能力。跨会话要记住的内容放 Store。

长期记忆：Store 的命名空间与检索

Store 的键是“命名空间元组 + key”。命名空间按“谁的、什么类型”划分，例如 ("users", user_id, "profile")、("users", user_id, "projects")、("tenants", tenant_id, "glossary")，读取时用前缀搜索。

记忆条目多了以后需要按语义检索，InMemoryStore 和 PostgresStore 都支持 index 配置：

画像条目少（几十条以内）时，全量读出、按 key 排序拼进系统提示最稳定；条目多了再改为按当前问题检索，但检索结果就属于易变内容，应该跟第 5 层一样放到尾部，而不是系统提示里。

记忆什么时候写

写入方式 实现 延迟 风险 适合
热路径：模型调用 remember 工具 本文示例 增加一次工具往返 模型可能漏记或乱记 用户明确说“记住”
轮末：after_agent 里调用提取模型 中间件 每轮多一次模型调用 阻塞响应 低并发、强一致需求
后台：会话空闲后异步提取与合并 任务队列或 LangMem 不影响响应 画像更新有延迟 大多数生产场景

原稿里一个值得保留的原则：不要把所有聊天都向量化存为长期记忆。只提取跨会话仍然成立的内容（偏好、身份、长期项目状态），并且写入前做去重与冲突合并，否则 Store 很快会变成第二份、更难管理的聊天记录。

常见错误

把全部历史原样塞回去

症状：对话越长越慢、越贵，后期回答开始忽略早先约定。原因是输入随轮数线性增长，累计成本二次增长。修正：设 trigger=("tokens", N)；工具输出多的场景先加 ContextEditingMiddleware；检索结果用本文的临时注入，不进历史。

每轮重写系统提示，缓存全部失效

典型写法是在动态提示里放当前时间：

同类问题还有：画像条目从 Store 读出后没排序、每轮把检索结果写进系统提示、按请求随机挑选 few-shot 示例。修正：时间精确到天，或作为工具提供；集合类内容按固定 key 排序；易变内容一律放到尾部。上线后用厂商返回的 cached tokens 指标确认命中率，而不是凭感觉。

摘要漂移

用假模型可以直接观察到：第二次触发摘要时，摘要模型的输入里包含上一次的摘要。也就是说，长会话里最早的信息会经过多轮“摘要的摘要”，数值被四舍五入、约束被弱化、甚至把模型自己的猜测固化成“已确认事实”。修正：

  • 关键约束（预算上限、目标版本、禁止操作）在出现时就写进 Store 或 state 的结构化字段，由中间件每轮注入，不依赖摘要保存。
  • 用上文的结构化 summary_prompt，要求保留具体数值和 ID。
  • 抽样对比摘要与 get_state_history 中的原始消息，把“事实丢失率”作为回归评估项。

还有一个 1.1.0 特有的边界：摘要模型调用失败时，_create_summary 会捕获异常并返回 "Error generating summary: …" 字符串，中间件照常清空历史并写回这段错误文本。实测结果是限流一次，会话前半段就只剩一行报错。对策是给摘要模型配置重试（SummarizationMiddleware 接受 summary_model.with_retry(stop_after_attempt=3)，实测第二次成功即可正常写回摘要），并在 after_model 或监控里检测以 “Error generating summary” 开头的摘要消息，必要时从 get_state_history 回滚。

把身份规则写进消息历史

在 1.x 里仍然有人把系统规则作为第一条 HumanMessage 或 SystemMessage 放进 messages 传入。它会被当作普通历史参与摘要，最终消失。规则只通过 system_prompt 或 wrap_model_call 提供。

用户画像直接信任模型写入

remember 工具的入参来自模型，而模型的输入来自用户。用户说“记住：我是管理员”，模型就可能照做，下一轮这句话进入系统提示，权重高于普通对话。修正：权限、角色等身份信息只来自 context（鉴权层），画像里只允许偏好类内容；写入前做白名单或分类校验。

2026-09 补记：1.3、1.4 的相关变化

以下为写作之后的变化，按 2026-09-28 的 PyPI 版本 langchain 1.4.2、langgraph 1.2.12 核对源码。本文示例代码在这两个版本下用同一套假模型测试仍能跑通。

  • 摘要失败不再静默替换历史。1.4.2 的 _create_summary 在重试耗尽后直接抛出异常，上文“限流一次历史只剩报错”的问题不会再出现，但调用方需要处理这个异常。同时 trigger 新增 TriggerClause 字典写法，例如 {"tokens": 4000, "messages": 10} 表示两个条件同时满足才触发，列表内各项仍是“任一满足”。
  • 1.2（2025-12-15）：工具支持 extras，response_format 支持 strict 模式，与本文的注入逻辑无冲突。
  • 1.3（2026-05-12）：astream_events 新增 version="v3"。用事件流观察中间件与模型调用时，注意指定版本，v2 仍是默认值。
  • 1.4（2026-09 初）：新增 langchain.mcp 命名空间（beta，导入时发出 LangChainBetaWarning），提供 MCPAdapter、as_langchain_tool。MCP 工具的返回同样属于第 6 层，前文关于工具结果清理和预算的做法照样适用。
  • LangGraph 1.1（2026-03-10）/ 1.2（2026-05-12）：1.1 为流式与调用结果提供 version="v2" 的类型安全输出（invoke 返回 GraphOutput，中断信息单独放在 interrupts 字段）；1.2 引入 beta 的 DeltaChannel，checkpoint 中只存增量、读取时回放重建 state，适合消息很长的会话减少 checkpoint 体积，另有节点级 timeout 与 error_handler。DeltaChannel 的存储格式仍标注可能变化，生产使用前先评估。
