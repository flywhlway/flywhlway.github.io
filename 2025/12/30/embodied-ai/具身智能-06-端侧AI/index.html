6.1 Jetson 家族与硬件选型

6.1.1 家族速查（截至本手册撰写时）

型号 内存 标称算力 功耗档 DLA 典型定位
Orin Nano 4/8GB 4/8GB LPDDR5 2040 TOPS（Super 版本更高） 7~15W(+) ❌ 轻量感知、AMR、教学
Orin NX 8/16GB 8/16GB 70100 TOPS 10~25W ✅ ×2 主力机型：感知+轻 VLA
AGX Orin 32/64GB 32/64GB 200275 TOPS 15~60W ✅ ×2 人形/多路感知+大 VLA
Thor 级新平台 更大 数量级提升（FP4） 更高 — 面向人形的新一代（选型前务必查最新规格）

选型不看 TOPS，看四件事：内存容量（第五篇：模型 + 双缓冲 + 感知 + 系统，8GB 极易见底）、内存带宽（大模型推理常是带宽瓶颈而非算力瓶颈）、功耗预算（决定电池续航与散热设计）、DLA 有无（能否把感知卸载出 GPU，给 VLA 让路）。

6.1.2 TOPS 的真相：为什么它不能算延迟

标称 TOPS 是峰值（通常按 INT8 稠密算力、MAXN 档、理想利用率），而真实延迟受制于：算子是否被引擎充分融合、内存带宽是否打满、数据搬运与预处理开销、功耗档位与温度降频、以及与其他进程的资源争抢。经验倍率：实际可用算力常在标称的 20%~50%——所以 6.5 节的结论是「唯一可信的数字来自你自己的机型压测」。这与你在云上「不信任厂商 benchmark、只信自己的压测」是同一条纪律。

6.1.3 统一内存（Unified Memory）：福利与陷阱

Jetson 的 CPU 与 GPU 共享同一块物理 DRAM，没有独立显存。福利：Host↔Device 拷贝可省（零拷贝路径），预处理链路更短。陷阱三条：「显存」与系统内存互相挤占——模型加载、图像缓冲、ROS 节点、日志缓存全在一口锅里抢饭，OOM 时被杀的可能是控制进程（灾难）；内存带宽是全系统共享的——感知拷图能把 VLA 的带宽吃掉；容量规划必须按总量算：系统+ROS 栈 + 感知模型 + VLA×2(双缓冲) + 图像/点云缓冲 + 余量 ≥ 总内存。

这就是 5.5.3「双缓冲要双份显存」的物理根源。写进机型规格书的内存预算表长这样：

项 Orin NX 16GB 示例预算
系统 + JetPack ~2GB
ROS2 栈与业务节点 ~1.5GB
感知模型（INT8） ~1.5GB
VLA 主槽（W4/INT8 量化后） ~4GB
VLA 备槽（热切换期间） ~4GB
图像/点云缓冲 + bag 缓冲 ~1.5GB
余量（防 OOM） ≥1.5GB

6.1.4 DLA：把感知卸载出 GPU

DLA（Deep Learning Accelerator）是 Orin NX/AGX 上的专用推理硬核（Nano 无）：能效高，但只支持 INT8/FP16 的有限算子集，不支持的层会回退（fallback）到 GPU——回退过多反而更慢。工程用法：把稳定的 CNN 类感知模型（检测/分割）放 DLA，把 Transformer 类 VLA 留 GPU，两者并行互不抢算力。这是端侧最实用的一次「算力扩容」，且不花钱。

6.1.5 与产业物联网平台的映射

端侧 AI 车端 备注
Jetson 智驾域控（Orin 本就同源） 心智直接迁移
统一内存预算 域控内存/算力预算表 机型规格书同款
DLA 卸载 域控里的专用加速核 同一手法
TOPS 不可信 域控算力标称与实测差 老朋友了

6.1.6 企业实践建议

把**《机型算力规格书》**作为平台团队的交付物：每个机型一页，写清内存预算表、功耗档、可承载模型规模上限、DLA 分工、实测延迟基线。它是采购、算法、结构三方的仲裁文件——没有它，模型选型永远靠嗓门大。

6.1.7 面试可能问什么

  1. Jetson 选型怎么做？（要点：内存/带宽/功耗/DLA 四件事，不看 TOPS）
  2. 统一内存的影响？（要点：共享一口锅、OOM 可能杀控制进程、带宽全局共享、预算按总量算）
  3. DLA 怎么用？（要点：CNN 上 DLA、Transformer 留 GPU、注意回退）

6.1.8 最佳实践

  • 内存预算表留 ≥10% 余量并配 OOM 守护（关键进程 oom_score_adj 保护），控制进程永不被杀。
  • 选型阶段就用目标模型跑一次真机压测，别信任何 PPT 上的 TOPS。

6.1.9 常见误区

  • ❌ 用 TOPS 比值估算延迟（「NX 是 Nano 的 2.5 倍，所以快 2.5 倍」）——带宽、回退与降频会把结论撕碎。
  • ❌ 忘记双缓冲与感知模型也吃内存——上线即 OOM 的头号原因。

6.1.10 Obsidian 永久笔记

  • 端侧优化确定性：云优化吞吐，端优化 P99+功耗+温度。
  • TOPS 是峰值不是承诺：实际常在 20%~50%，只信自己的压测。
  • 统一内存一口锅：模型/缓冲/ROS/系统互抢，预算按总量算并留余量。
  • DLA 卸载感知：CNN 上 DLA，Transformer 留 GPU。

6.2 部署链：PyTorch → ONNX → TensorRT

6.2.1 全链路

flowchart LR
  PT["PyTorch 权重（算法团队产出）"] --> EXP["导出：torch.onnx.export / dynamo"]
  EXP --> ONX["ONNX 图（含算子集 opset）"]
  ONX --> SIM["图简化/算子替换（onnx-simplifier）"]
  SIM --> BLD["TensorRT builder：精度/校准/层融合/kernel 自动调优"]
  BLD --> ENG["engine 文件（.plan）"]
  ENG --> RT["端侧 Runtime 加载执行"]
  PT -.替代路线.-> TRTX["Torch-TensorRT / TensorRT-LLM（大模型）"]
  TRTX --> ENG

三条路线的取舍：ONNX→TRT 通用性最好（跨框架、可离线构建），是感知模型主路线；Torch-TensorRT 省去导出摩擦，适合迭代期；TensorRT-LLM 面向 Transformer/LLM 类（含 VLA 骨干），有专门的注意力与 KV Cache 优化。

6.2.2 导出期的五个经典坑

其一，动态形状：不声明 dynamic_axes 就锁死 batch/分辨率，换输入即报错；其二，不支持的算子：自定义算子需写插件或改网络（这一步常把交付卡住一周）；其三，opset 版本：与 TensorRT 版本的兼容矩阵要对齐（写进模型卡）；其四，前后处理漏在框架里：Python 里的 resize/normalize 没进图，端侧行为不一致——必须把预处理契约与模型一起交付（呼应 5.3.6）；其五，训练态算子（dropout/BN 未 fold）——导出前 model.eval() 是常识但年年有人栽。

6.2.3 引擎构建：为什么 engine 不可移植（平台最关键的一条）

TensorRT builder 会针对具体 GPU 架构 + TensorRT/CUDA 版本 + 精度模式做 kernel 自动调优（tactic 选择），产物 .plan 因此绑定硬件与软件栈版本——AGX 上构建的 engine 拿到 Orin NX 上通常直接加载失败，甚至同型号跨 JetPack 版本也不保证兼容。

这一条把 6.2 与第四篇缝死了：你的模型 OTA 不能只分发一个 .plan。三种策略：

策略 做法 优点 代价
A. 端侧构建 分发 ONNX，机器人首次加载时本地 build 一份制品通吃 构建耗时（分钟~十几分钟）、占内存、结果不确定
B. 按目标预构建 CI 为每个 (机型 × JetPack 版本 × 精度) 构建 engine 矩阵 端侧秒级加载、行为确定 制品矩阵膨胀，需版本治理
C. 混合 主力机型预构建 + 长尾机型端侧构建兜底 平衡 两套路径都要维护

推荐 B（生产）+ A（兜底）：把「构建」放进 CI 制品流水线，engine 作为制品库的一等公民，兼容矩阵（4.3.3）新增两维——GPU 架构与 JetPack 版本。这是很多团队上线后才痛苦发现的架构级约束，你提前知道了。

6.2.4 端侧构建的工程细节（策略 A 兜底时）

必须做三件事：timing cache 复用（同机型缓存 tactic 选择结果，二次构建大幅加速）、构建期资源隔离（构建吃满 CPU/内存，必须在「非作业窗口 + 限核」下进行，否则拖垮控制回路）、构建失败降级（回落到上一版 engine 或 FP16 保守配置，并上报事件）。构建过程本身就是一次「任务」——用第三篇的 RobotTask 承接它，进度与结果自然进平台。

6.2.5 与产业物联网平台的映射

端侧部署链 车端 备注
ONNX→TRT engine 域控模型编译产物 同款绑定问题
engine 不可移植 编译产物绑定芯片/SDK 版本 兼容矩阵扩两维

6.2.6 企业实践建议

在制品库里把「模型制品」定义为四件套：权重/engine + 预处理契约 + 归一化统计量 + 模型卡（含 opset/TRT/JetPack/GPU 架构版本）。四件套缺一不入库——这条规则能消灭端侧「行为莫名不一致」的绝大多数事故。

6.2.7 面试可能问什么

  1. TensorRT engine 为什么不能跨设备分发？如何设计 OTA？（要点：tactic 绑定硬件+版本；三策略与推荐 B+A）
  2. ONNX 导出的常见坑？（要点：动态形状/自定义算子/opset/前后处理/eval 五条）
  3. 端侧构建的风险？（要点：耗时、抢资源、结果不确定；用任务承接 + 非作业窗口 + timing cache）

6.2.8 最佳实践

  • engine 文件名嵌 模型版本_机型_GPU架构_TRT版本_精度，加载时校验——命名即契约。
  • CI 每次构建都归档 build log 与层级 profile，性能回归时可对比 tactic 变化。

6.2.9 常见误区

  • ❌ 把开发机上构建的 engine 直接打进 OTA 包——机型/版本一变即挂。
  • ❌ 端侧构建放在作业时段——控制回路被构建进程挤兑，抖动与卡顿随之而来。

6.2.10 Obsidian 永久笔记

  • engine 绑定硬件与版本：模型 OTA 必须按 (机型 × JetPack × 精度) 建矩阵。
  • 模型制品四件套：权重/engine + 预处理契约 + 归一化统计量 + 模型卡。
  • 端侧构建是一次任务：非作业窗口 + 限核 + timing cache + 失败降级。

6.3 量化：端侧的默认项

6.3.1 全谱速查

方案 位宽 适用 端侧位置
FP16 16 通用基线 保守选择，延迟/内存翻倍
INT8（PTQ+校准） 8 CNN 感知 DLA 必需，感知主力
FP8 8 Transformer（Ada/Hopper/Blackwell 级支持） 新平台上的 VLA 优选
INT4 / W4A16（AWQ/GPTQ） 权重 4 LLM/VLA 骨干 显存瓶颈时的救命稻草
GGUF（llama.cpp 生态） 混合 CPU/小 GPU 上的 LLM 边缘小模型、快速验证
QAT（量化感知训练） 8/4 精度掉太多时 算法团队的活，成本高

选择顺序（工程实用主义）：FP16 跑通 → INT8/FP8 达标就停 → 显存不够再上 W4 → 精度崩了才谈 QAT。

6.3.2 校准数据集：最容易被忽略的制品

INT8 PTQ 需要校准集（几百张代表性样本）来统计激活分布。三条纪律：校准集必须来自目标场景（用 ImageNet 校准仓库机器人的检测模型 = 自找精度悬崖）；校准集要版本化并入制品血缘（4.10.3）——它决定了量化结果，属于可复现性的一部分；校准集要随场景演进更新（新站点/新光照 → 重新校准）。你在 LLM 量化里对校准集的直觉，这里同样成立且更敏感。

6.3.3 精度回归门禁

量化后必须过三关：逐层数值对比（余弦相似度/最大误差，定位是哪层崩了）→ 任务指标对比（检测 mAP / VLA 离线动作误差，跌幅超阈即拒绝）→ 端到端评测（第五篇三级评测串联）。把这三关做进 CI，量化就从「玄学调参」变成「可回归的流水线」——这正是平台团队该给算法团队的礼物。

6.3.4 量化对 VLA 的特殊性

第五篇提过动作是连续量：量化误差会直接变成动作误差（不像分类任务有 softmax 的容错缓冲）。工程建议三条：动作头（最后几层）保守精度（FP16 甚至 FP32），骨干激进量化——混合精度是标准做法；量化后必须看动作平滑度指标（jerk，5.6.3）而不只看成功率；影子模式并跑「FP16 版 vs 量化版」，用动作分歧分布做门禁——这是最灵敏的检测器。

6.3.5 与产业物联网平台的映射

量化 你的 LLM 经验 差异
PTQ/校准集 同款 端侧对校准集分布更敏感
AWQ/GPTQ/W4 同款 目标从省成本变成「能否装下」
混合精度 同款 动作头必须保守
量化门禁 评测流水线 加动作平滑度与分歧分布

6.3.6 企业实践建议

把「量化 + 精度回归」做成平台提供的自助流水线：算法团队提交权重与校准集，流水线自动产出多精度 engine 矩阵 + 精度报告 + 延迟报告。这一条服务能把模型上机周期从周级压到天级——是平台团队最容易被感知到的价值。

6.3.7 面试可能问什么

  1. 端侧量化怎么选？（要点：FP16→INT8/FP8→W4→QAT 的实用顺序 + DLA 只吃 INT8）
  2. 量化 VLA 与量化 CNN 的差异？（要点：动作是连续量、误差直传；动作头保守、看 jerk 与分歧分布）
  3. 校准集要注意什么？（要点：目标场景、版本化入血缘、随场景更新）

6.3.8 最佳实践

  • 每个量化制品附「精度-延迟-内存」三元报告，选型即读表，不再靠感觉。
  • 影子并跑高精度基线做分歧监控——量化退化在真机上最先表现为动作分歧上升。

6.3.9 常见误区

  • ❌ 用通用公开数据当校准集——分布不匹配，实测精度崩塌且难归因。
  • ❌ 全网络一刀切量化——动作头/输出层崩了，机器人抖给你看。

6.3.10 Obsidian 永久笔记

  • 量化是端侧默认项：FP16→INT8/FP8→W4→QAT 的实用顺序。
  • 校准集是制品：目标场景 + 版本化 + 入血缘。
  • 动作头保守量化：连续动作无容错缓冲，看 jerk 与分歧分布。

6.4 边缘 LLM：vLLM / SGLang / TensorRT-LLM / llama.cpp / MLX 的位置

6.4.1 先破一个幻觉：端侧 batch=1

vLLM/SGLang 的核心武器是连续批处理 + PagedAttention——它们优化的是「多请求并发下的吞吐」。而机器人端侧只有一个消费者、一个请求、固定节拍：batch≈1，连续批处理无用武之地。这是你的云端直觉在端侧最大的一次失效。端侧真正有用的是：算子融合、量化、KV Cache 复用（多轮同前缀）、显存分页（防碎片）、CUDA Graph（消除 kernel launch 抖动）。

6.4.2 引擎选型矩阵

引擎 端侧位置 说明
TensorRT / TensorRT-LLM ✅ 生产首选 NVIDIA 官方链路，Jetson 支持最好，延迟最优
llama.cpp / GGUF ✅ 快速验证 / CPU 兜底 部署极简，适合小模型与原型
vLLM / SGLang ⚠️ 站点边缘池可用 池化多机器人请求时才有价值（4.9.1 推理池）
MLX ❌ 端侧无关 Apple Silicon 专用——你的 Mac 开发机上跑实验有用
ONNX Runtime ⚠️ 备选 跨平台好，Jetson 上性能通常不敌 TRT

结论：机上 = TensorRT 系；站点池 = vLLM/SGLang；开发机 = MLX/llama.cpp。三个场所三种引擎，不要混用心智。

6.4.3 KV Cache 在机器人上的具体用法

VLA 的语言指令在一次任务内通常不变（「把杯子放到托盘上」重复 50 次推理）。因此指令前缀的 KV Cache 可跨帧复用，每次只增量计算视觉 token 与新观测——这是端侧最划算的一次优化（可省掉骨干前向的可观比例）。工程要点：任务切换时必须失效缓存（脏读会让机器人执行上一个任务的语义，属于 5.6.1 的「语言误解」类事故）；缓存占内存，计入 6.1.3 的预算表。

6.4.4 端侧 LLM 的真实负载：不是 VLA，是这三样

澄清一个常见混淆：VLA 走的是 TensorRT/TRT-LLM 的定制链路，不走「LLM 服务」那一套。端侧真正的 LLM 类负载是：语音交互（ASR + 小 LLM + TTS，秒级容忍）、本地兜底规划（断云时的简易任务分解，4.9.4 自治清单）、本地日志/故障摘要（诊断前置处理）。这三样的选型标准是「小、稳、能降级」——3B 以内、GGUF/TRT 量化、失败即回退规则或转云。

6.4.5 与产业物联网平台的映射

边缘 LLM 你的经验 差异
batch=1 现实 云端追吞吐 直觉反转
KV Cache 前缀复用 vLLM prefix caching 同思想，跨帧复用
站点池用 vLLM 你的推理服务栈 原样迁移
车机语音助手 座舱 ASR+LLM+TTS 完全同构

6.4.6 企业实践建议

在《机型算力规格书》里显式区分「实时推理预算」（VLA/感知，TRT 链路）与「弹性推理预算」（语音/摘要，可抢占可降级）——两类负载共享一块 DRAM，必须显式分池与限额，否则语音助手一句话就能顶掉 VLA 的显存（真实事故）。

6.4.7 面试可能问什么

  1. 机器人端侧该用 vLLM 吗？（要点：batch=1 → 连续批处理无收益；TRT 系首选；vLLM 归站点池）
  2. KV Cache 在 VLA 上怎么用？（要点：指令前缀跨帧复用；任务切换必须失效）
  3. 端侧 LLM 的真实负载？（要点：语音/兜底规划/日志摘要三类，小稳能降级）

6.4.8 最佳实践

  • CUDA Graph 用于固定 shape 的高频推理，消除 launch 抖动——P99 优化的性价比之王。
  • 弹性负载全部设内存上限与优先级，可被实时负载抢占。

6.4.9 常见误区

  • ❌ 把云端推理服务架构原样搬到机器人上（起 HTTP 服务、上批处理）——徒增延迟与故障面，端侧应是进程内库调用。
  • ❌ 忘记任务切换时失效 KV Cache——「按上一个任务的语义干活」的诡异事故。

6.4.10 Obsidian 永久笔记

  • 端侧 batch 等于 1：连续批处理失效，优化转向融合/量化/CUDA Graph。
  • 三场所三引擎：机上 TRT、站点池 vLLM、开发机 MLX/llama.cpp。
  • 指令前缀 KV 复用：任务内跨帧复用，切换即失效。

6.5 物理约束：功耗、散热、内存与存储

6.5.1 功耗档位：nvpmodel 与 jetson_clocks

Jetson 通过 nvpmodel 切换功耗模式（限定 CPU/GPU 核数与频率上限），jetson_clocks 锁定最高频（禁用动态调频）。这两个命令背后是架构决策而非调参：

档位 效果 适用
低功耗档（如 15W） 续航长、温度低、算力受限 电池敏感的 AMR
高性能档（MAXN） 算力全开、发热大 有线供电/散热充足的工位机器人
jetson_clocks 锁频 消除调频引起的延迟抖动 实时性敏感场景推荐（代价：功耗与发热恒高）

平台含义：功耗档位属于机型基线配置（走配置 OTA，2.13.4），且必须与延迟基线绑定测量——换档位等于换了一台机器，所有延迟数字全部作废需重测。

6.5.2 散热与降频：延迟 P99 的隐形杀手

热节流（thermal throttling）是端侧最阴险的问题：实验室 10 分钟压测一切正常，产线连续跑 2 小时后 GPU 降频 30%，VLA 推理超过 chunk 时长 → 5.5.1 的不等式破裂 → 机器人肉眼可见卡顿。三条纪律：压测必须做长时热浸泡（≥2 小时到热稳态，而非 10 分钟冲刺）；温度与频率必须进遥测上云（4.8.4 加两个指标：gpu_temp、gpu_freq_throttled_ratio）；机型规格书写明「热稳态下的延迟基线」而非峰值基线。

【映射 🚗→🤖】这就是车端域控的热管理与降频，你在智驾域控上遇到的同一课题——夏季车顶暴晒后算力衰减，结论也一样：按热稳态设计，不按峰值设计。

6.5.3 内存水位与 OOM 保护

统一内存（6.1.3）下 OOM 的后果可能是灾难性的——Linux OOM killer 不认识「控制进程比日志进程重要」。三层防线：预算表留 ≥10% 余量；关键进程设 oom_score_adj=-1000（永不被杀），日志/录制类设正值（优先牺牲）；内存水位进遥测 + 分级降级（水位高 → 停止 bag 录制 → 降图像分辨率 → 卸载备槽模型 → 最后才是拒绝新任务）。降级顺序必须预先定义并演练，这是机型规格书的一节。

6.5.4 存储：eMMC/NVMe 的寿命与带宽

三条易被忽略的坑：bag 录制写放大（连续高码率写入会显著缩短 eMMC 寿命——生产机型建议 NVMe，且触发式录制而非全量，2.21）；OTA 需要双份空间（新固件/模型下载 + 旧版本保留，A/B 与双缓冲都吃磁盘）；日志轮转必须设死上限（磁盘写满 = 机器人罢工，且往往在夜班无人时发生）。存储余量与寿命（写入量统计）同样应进遥测。

6.5.5 端侧监控：tegrastats / jtop 与指标上云

tegrastats（NVIDIA 原生）与 jtop（jetson-stats 社区工具）提供 CPU/GPU 利用率、频率、温度、功耗、内存水位。工程做法：写一个 jetson_metrics_node（ROS2 节点）周期解析并发布到遥测话题 → 云桥 → 第四篇数据面 → 大盘与告警。第三篇 telemetry_agg 里那行 gpu_load = 0.0 的 TODO，就在这里补上。

必上云的六个端侧指标：GPU 利用率、GPU 温度、降频比例、内存水位、功耗档位、推理延迟 P99。

6.6 资源隔离与实时性：推理不能抢控制

6.6.1 冲突的本质

一台机器人上同时跑着：1kHz 控制回路（硬实时）、50Hz 执行器指令、5Hz VLA 推理（吃满 GPU 与带宽）、感知（吃 DLA/GPU）、遥测/录制（吃 IO）、OTA Agent（偶发吃满 CPU/IO）。它们共享 CPU 核、一块 DRAM、一条内存带宽、一块磁盘。若不隔离，一次 bag 落盘或一次模型加载就能让控制回路抖动——机器人晃一下，可能就是一次安全事件。

6.6.2 隔离四板斧

手段 做法 作用
CPU 核绑定 控制进程独占核（isolcpus/taskset/cgroup cpuset），推理与业务用其余核 消除调度争抢
实时优先级 控制线程 SCHED_FIFO 高优先级 + mlockall 锁内存 不被换出、不被抢占
cgroup 限额 推理/录制/OTA 进程限 CPU 份额与内存上限 防单进程吃垮系统
IO 与带宽 录制/OTA 限速（ionice/cgroup blkio），大流量话题走共享内存 防 IO 抖动传导

这就是 2.6.6 的「控制节点隔离清单」的完整实现版——当时给的是评审要点，这里是施工手册。

6.6.3 推理侧的自律三条

其一，模型加载/构建只在非作业窗口（6.2.4）；其二，推理进程可被抢占且有超时——超时立即返回上一 chunk 或降级策略（5.5.4），绝不阻塞等待；其三，CUDA Graph + 固定 shape 消除 kernel launch 与内存分配抖动（6.4.8）。一句话：推理是「客人」，控制是「主人」——客人再重要也不能掀桌子。

把 16 步做成 Checklist 卡片贴进项目看板，每个模型上线拉一张——流程可视化是平台团队治理端侧混沌的第一步，也是新人最快理解「端侧为什么这么麻烦」的教具。

6.7.7 面试可能问什么

  1. 一个模型从训练完到上线，端侧要做哪些事？（要点：三阶段 16 步，重点讲 engine 矩阵、热稳态、影子）
  2. 端侧上线的门禁有哪些？（要点：契约校验、P99 不等式、隔离压测、分歧分布、灰度烘烤）

6.7.8 最佳实践

  • 每步都留「机器可读的产出物」（报告 JSON、engine 清单、压测曲线），归档进制品血缘——人类记忆不可审计。
  • 16 步中任一步失败都要能定位到唯一责任方（算法/平台/结构/采购），流程即责任划分。

6.7.9 常见误区

  • ❌ 跳过阶段一直接上模型——机型基线不稳，后面所有数字都是流沙。
  • ❌ 把 16 步当官僚流程——每一步都对应一类曾经的真实事故，删哪步就是复现哪个坑。

6.7.10 Obsidian 永久笔记

  • 三阶段 16 步：机型基线 → 制品化上机 → 影子灰度运营。
  • 每步都有机器可读产出：报告/清单/曲线入血缘，可审计可复现。

6.8 本篇总结

6.8.1 十条核心结论

  1. 云端优化吞吐，端侧优化确定性——P99、功耗、温度取代 QPS 成为一等指标。
  2. 选型看内存/带宽/功耗/DLA 四件事；TOPS 是峰值不是承诺，只信自己的压测。
  3. 统一内存是一口锅：模型、缓冲、ROS、系统互抢，预算按总量算并留余量。
  4. TensorRT engine 绑定硬件与版本——模型 OTA 必须建 (机型 × JetPack × 精度) 矩阵。
  5. 模型制品四件套：权重/engine + 预处理契约 + 归一化统计量 + 模型卡，缺一不入库。
  6. 量化是默认项：FP16→INT8/FP8→W4→QAT；校准集是制品；动作头保守量化。
  7. 端侧 batch=1，连续批处理失效：机上 TRT、站点池 vLLM、开发机 MLX/llama.cpp。
  8. 按热稳态设计而非峰值：2 小时浸泡后的 P99 才是能写进规格书的数字。
  9. 推理是客人、控制是主人：隔离四板斧 + 推理自律三条 + 开机自检防漂移。
  10. 三阶段 16 步 Deployment Guide：把端侧混沌变成可审计的流水线。
