家用服务器入口层：内网穿透 + Nginx Proxy Manager + 证书自动化

没有公网 IP 的家用服务器如何搭入口层：cpolar 隧道 + NPM 路由 + 通配证书签发与同步，附逐跳排障法、MinIO 反代要点与网络隔离。

Flywhl 18 分钟 更新于 2026.09 #Nginx Proxy Manager#MinIO#反向代理

先读结论

  1. 先想清楚 TLS 在哪一跳终止、证书归谁签发，再决定要不要同步证书。
  2. Let's Encrypt 的 live/ 目录全是相对软链，docker cp 默认只拷链接本身。
  3. 排障按 DNS → 隧道边缘 → 隧道客户端 → NPM → 上游逐跳打点，每一跳只回答通或不通。
  4. 上游容器一律不发布端口，只让 NPM 对外；管理端口只绑本机。

家里的服务器没有公网 IP，又想用自己的域名、HTTPS 访问 NAS、对象存储和几个自建应用，最常见的组合是：内网穿透负责把流量带进来，Nginx Proxy Manager（下文简称 NPM）负责按域名分发，证书自动签发、自动续期。

这套组合搭起来不难，难在出问题时分不清是哪一层坏了。本文按实际落地顺序整理：拓扑与 TLS 终止点、证书签发与同步（给出最终版脚本和 systemd timer）、一次真实踩到的 docker cp 软链陷阱、逐跳排障法、WebSocket / 大文件 / MinIO Console 的反代要点，最后是安全头与网络隔离。

写作时 NPM 的最新版本是 v2.13.0（2025-11-04 发布，此前 v2.12 系列之后停滞了较长时间）；隧道以 cpolar 为例，其它支持「自定义域名 + 自定义证书」的隧道服务思路相同。

几个关键决定：

决定 本文选择 原因
隧道协议 HTTP 隧道 + 自定义域名 + 自定义证书 浏览器访问标准 443 端口；TCP 隧道通常分配的是高位端口，不适合给人用的域名
外网 TLS 终止点 隧道边缘节点 边缘节点必须持有 *.example.com 的证书和私钥，这就是需要「证书同步」的原因
证书签发方 NPM（DNS-01 签通配证书） NPM 本来就要给内网 443 用同一张证书，只维护一份续期逻辑
隧道回源端口 NPM 的 80 边缘已解密，回源走 HTTP；回源到 443 会得到 400
是否加一层原生 Nginx 不加 每多一跳，排障就多一跳；只有需要 NPM 界面表达不了的复杂路由时才加

证书：签发、续期与同步

两种签发方式怎么选

场景 推荐 要点
入口是 NPM，需要通配证书 NPM 内置 Let’s Encrypt，选 DNS Challenge 通配证书只能用 DNS-01；在 NPM 里选 DNS 服务商并填 API 凭据，续期由 NPM 负责
入口是云主机上的原生 Nginx（没有 NPM） acme.sh 单域名可用 webroot（HTTP-01），通配证书用 DNS API
同一台机器已有 NPM 占用 80 端口 不要再跑 acme.sh standalone 端口冲突；要么交给 NPM，要么 acme.sh 走 DNS-01

两种工具不要在同一域名上混用：各自维护续期状态，谁最后写入证书文件谁生效，出问题时很难判断当前证书来自哪边。

还有一个背景变化：Let’s Encrypt 已于 2025 年 6 月停止发送证书到期提醒邮件。续期失败不会再有人通知你，下文的同步脚本顺带承担到期检查。

必须遵守的顺序与边界：

  • --issue 成功后才能 --install-cert。签发失败时执行安装，会得到 0 字节的证书文件，下一次 nginx -s reload 直接失败，已有站点跟着挂。
  • Nginx 只引用 --install-cert 复制出来的文件，不要直接引用 ~/.acme.sh/ 目录下的文件，那里的结构随版本可能变化。
  • 用 webroot（-w）时，-w 必须是该域名 80 端口 server 块实际提供 /.well-known/acme-challenge/ 的目录。多个站点 root 不同却共用一个 -w，是 webroot 失败的头号原因。更稳的做法是所有 80 端口 server 块统一加：
  • 签发报 404 时，先看报错里 CA 实际访问的 URL。一次真实案例：申请的是 oss.example.com，报错 URL 却是 https://example.com/.well-known/...。Let’s Encrypt 的 HTTP-01 会跟随重定向，说明该子域名的 80 端口被一条写死主域名的 return 301 带走了，落到主域名站点，那里没有 challenge 文件。修的是重定向规则，不是证书命令。
  • 手动验证 challenge 路径：echo ok > /var/www/acme/.well-known/acme-challenge/probe，再从外网 curl -i http://oss.example.com/.well-known/acme-challenge/probe，拿到 ok 再签。

为什么用 root 级 systemd，而不是用户级

最初的版本用 systemctl --user 管理隧道和同步任务，连续踩了三个坑：

  1. 退出 SSH 后用户级 systemd 被回收，timer 不再触发，需要 loginctl enable-linger <用户>；
  2. 用户级 unit 的环境与交互 shell 不同，docker 命令找不到或连不上 socket，日志只有一行 Start sync... 就中断（set -e 静默退出）；
  3. docker 组本身就等价于 root 权限，用普通用户跑并没有换来实质隔离。

所以最终把脚本和 timer 都放到系统级，以 root 运行，日志统一进 journal。若坚持用户级，至少要开启 linger，并在 unit 里显式写 Environment=PATH=...，且把脚本的 stderr 也导入日志，否则失败时什么都看不到。

docker cp 软链陷阱

这是同步脚本第一版的真实故障，单独拿出来，因为它的报错很容易误判成权限问题。

症状：同步脚本用 docker cp npm:/etc/letsencrypt/live/npm-1/fullchain.pem /tmp/x/ 导出证书，脚本在第一条 docker cp 处退出，报错类似：

根因：Let’s Encrypt（certbot）的目录结构里，live/<名称>/ 下的四个文件都是软链，指向 ../../archive/<名称>/ 下带序号的真实文件，每次续期序号加一、软链改指向。docker cp 从容器拷出时默认拷贝的是链接本身而不是目标，拷到宿主机的临时目录后，这条相对路径的软链指向一个不存在的位置，于是被判定为无效链接。

修复（三选一）：

方式 命令要点 适用
容器内解引用输出 docker exec npm cat .../fullchain.pem > 本地文件 本文脚本采用；与卷的挂载方式无关
让 docker cp 跟随链接 docker cp -L npm:.../fullchain.pem 本地目录/ -L（--follow-link）拷贝链接目标
宿主机直接读绑定挂载 cat /opt/edge/npm/letsencrypt/live/npm-1/fullchain.pem 仅当 /etc/letsencrypt 是绑定挂载时；相对软链在宿主机上同样能解析，但需要 root 才能读私钥

反例：直接从 archive/ 拷 fullchain1.pem。它今天能用，续期后变成 fullchain2.pem，脚本继续同步旧证书，而且因为「文件没变化」不会报任何错，直到证书过期。

验证：file /usr/local/etc/cpolar/certs/fullchain.pem 应显示 PEM 证书而不是 symbolic link；再用上一节的 openssl s_client 看边缘证书的到期时间。

逐跳排障法：DNS → 隧道 → NPM → 上游

外网打不开时，最浪费时间的做法是同时改好几处配置。正确做法是沿请求路径逐跳打点，每一跳只回答「通 / 不通」，第一个不通的地方就是要修的地方。

flowchart TD
    S[外网访问失败] --> Z{本机是否开了代理<br/>或 DNS 缓存旧记录}
    Z -->|是| Z1[关闭代理 / 刷新缓存后重试]
    Z -->|否| D{dig 结果是否<br/>CNAME 到隧道服务}
    D -->|否| D1[修 DNS 记录]
    D -->|是| E{openssl s_client<br/>拿到的是自己的证书吗}
    E -->|握手失败| E1[隧道离线 / 域名未绑定到隧道]
    E -->|证书不对或过期| E2[查 crt/key 路径与同步任务]
    E -->|是| C{NPM access 日志<br/>是否出现这次请求}
    C -->|没有| C1[查隧道客户端: 服务状态 / addr 是否指向 80]
    C -->|有| N{NPM 返回什么}
    N -->|默认欢迎页或 fallback 日志| N1[Proxy Host 域名不匹配]
    N -->|301 循环| N2[关闭该域名的 Force SSL]
    N -->|502 / 504| U[从 edge 网络内直连上游]
    U --> U1[上游未运行 / 不在同一网络 / 只监听 127.0.0.1 / 超时]

第 1 跳：DNS

应当 CNAME 到隧道服务在控制台里给出的目标。多个公共解析器结果不一致，说明改动还在传播，别急着改别处。

第 2 跳：隧道边缘

  • 握手失败或拿到隧道服务的默认证书：域名没有绑定到隧道，或隧道不在线；
  • 拿到的是自己的证书但已过期：同步任务没跑或 NPM 续期失败，查 journalctl -u npm-cert-sync.service；
  • 能拿到响应头：边缘到这里是通的，继续往里查。

第 3 跳：隧道客户端

常见错误是 addr 指向了 443：边缘已经解密，回源发的是明文 HTTP，NPM 会返回 400，内容是「The plain HTTP request was sent to HTTPS port」。

第 5 跳：上游容器

在 NPM 所在的网络里直接访问上游，排除 NPM 配置因素：

  • 解析不到容器名：上游没有加入 edge 网络；
  • Connection refused：上游只监听了容器内的 127.0.0.1，或端口写错；
  • 能通但经 NPM 仍 502：Proxy Host 里的 Forward Hostname / Port / Scheme 填错（上游是 HTTP 却选了 https 最常见）。

MinIO：API 与 Console 分两个域名

MinIO 有两个端口：9000 是 S3 API，9001 是 Web Console（需以 --console-address ":9001" 启动）。反代时给它们各一个子域名，不要共用，也不要把 Console 挂在路径下，路径方式需要额外配置且更易出错：

域名 上游 NPM 设置 Advanced 要点
s3.example.com minio:9000 不开 Websockets client_max_body_size 0; proxy_request_buffering off; proxy_buffering off; ignore_invalid_headers off; chunked_transfer_encoding off;
minio.example.com minio:9001 开 Websockets 同上，外加较长的 proxy_read_timeout

这组指令来自 MinIO 官方的 Nginx 反代示例（官方示例在 API 与 Console 两个 server 块中都放了上传大小与缓冲相关的四条），NPM 的 Advanced 配置正好落在 server 级。两个关键的反代语义：

  • S3 API 必须原样保留 Host。S3 V4 签名把 Host 头算进签名，反代改写了 Host（或端口），客户端会得到 SignatureDoesNotMatch（403）。NPM 默认传递 Host $host，一般无需改动；自写 Nginx 时按官方示例用 proxy_set_header Host $http_host;。
  • Console 需要 WebSocket。官方示例要求透传 Upgrade / Connection，没开 Websockets Support 时常见的表现是能登录、但页面数据加载失败或反复掉线。

MinIO 侧有两个与外部地址相关的变量，含义经常被混淆：

  • MINIO_BROWSER_REDIRECT_URL=https://minio.example.com：Console 的对外地址。只通过反代访问 Console 时必须设置。
  • MINIO_SERVER_URL：Console 回连 API 用的地址，登录请求就是发往这里。设置了它，就必须保证从 MinIO 容器内部能解析、能访问、证书匹配。在隧道拓扑里，公网域名从内网往往绕不回来，不需要时不要设置，Console 默认回连本机 API。

Console 登录 401：先判定是反代问题还是容器问题

POST /api/v1/login 返回 401 时，第一步不是改 Nginx，而是绕过反代直连一次：

  • 直连也是 401：与反代无关，按容器侧排查：凭据是否正确，MINIO_SERVER_URL 回连是否可达；
  • 直连 200、经域名 401 或登录后立刻被踢回：检查 Websockets Support 是否开启，是否在 Advanced 里改写了 Host 或 Origin；
  • 请求根本没到 MinIO（NPM 日志没有记录）：回到逐跳排障的前几跳。

反例：看到 401 就不断往 Nginx 里堆 X-Forwarded-*、Origin 头。多余的头不会修好凭据问题，改写 Origin 反而可能引入新的跨域校验失败。

安全头与网络隔离

安全响应头

在 Proxy Host 的 Advanced 中加一组通用头，HSTS 用 NPM 自带的开关，不要手写两份：

  • always 让 4xx/5xx 响应也带上这些头，错误页同样可能被嵌入或嗅探；
  • X-XSS-Protection 已被现代浏览器废弃，不必再加；CSP 与应用强相关，按应用单独配置，不要全站统一下发；
  • Nginx 的 add_header 继承规则是：某个 location 里只要出现任何 add_header，外层的 add_header 全部不再继承。NPM 在开启 HSTS 等选项时会在生成的 location 中写入 add_header，Advanced 里 server 级的头可能因此消失。以实测为准：

缺失时，把这组头交给上游应用输出，比与 NPM 生成的配置较劲更省事。

网络隔离

原则只有一条：只有 NPM 对外，其它容器一律不发布端口。

  • NPM 通过容器名访问上游（app:8080），上游不需要也不应该有 ports；
  • NPM 的 81 管理端口绑定 127.0.0.1，经 SSH 端口转发访问；
  • 发布端口会绕过 ufw：Docker 通过 iptables 直接转发已发布端口，ufw 的 INPUT 规则拦不住。确实要对内网开放某个端口时，绑定到内网网卡地址（如 10.0.0.10:5432:5432），或在 DOCKER-USER 链中加规则；
  • 敏感的数据库、缓存再单独放一个不接入 edge 的内部网络，只让需要它的应用同时加入两个网络。

总结

家用入口层的难点不在组件多，而在边界是否清楚：TLS 在隧道边缘终止，所以证书必须同步、NPM 不能再强制跳转；证书只由一个组件签发，同步脚本负责校验、原子替换和到期告警；排障沿请求路径逐跳打点；上游只在内部网络可见。把这几条定下来，新增一个服务只需要「加入 edge 网络 + 在 NPM 建一个 Host」。

2026-09 补记：NPM 版本与证书续期

  • NPM 在 2025-11 恢复发布后保持了稳定节奏：v2.14（2026-02-17）、v2.15（2026-05-31）、v2.16.0（2026-09-24）。
  • v2.16.0 新增界面内日志查看器，逐跳排障第 4 跳不必再进容器 tail 日志；新增按路径的访问控制，部分原本写在 Advanced 里的规则可以改回界面配置。
