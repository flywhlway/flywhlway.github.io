DeepSeek Harness 协议、工具与运行时

核心设计：Session 是一份由类型化 SessionEvent 组成的仅追加日志，是 agent 完整交互历史的唯一真源。

第 5 部分 · 核心机制原理深度解析

5.1 事件溯源会话日志（整个系统的地基）

核心设计：Session 是一份由类型化 SessionEvent 组成的仅追加日志，是 agent 完整交互历史的唯一真源。

运行时不变量：模型可见即已记录（Model-visible is logged）

“抵达模型请求的一切都必须能从日志重建，并由一项运行时不变量断言这一点。因此，新增一项模型可见输入就需要新增一个会话事件：扩展 SessionEventMap 并从日志渲染。”

这是一条被 ctx.invariants 服务在运行时强制的架构约束，不是文档建议。它的直接后果是：你不能”偷偷”往模型上下文里塞东西——任何注入都必须先落日志。

事件信封结构：

字段 含义
type 事件类型
seq 单调递增序号（连续无洞，包括原始 chunk）
time epoch 毫秒
data 载荷（Session.append 运行时用 isJsonValue 校验，非序列化载荷在源头被拒绝）
ignorable 未知类型跳过标记
surfaceOp surface 标记：存在则该事件生成一条 LLM 消息，并声明如何加入 surface 列表
sourceEventSeqs 溯源引用（如 assistant/message 精确列出对应的 assistant/chunk）

43 种持久事件类型（完整列表见附录 B），分为两类：

  • surface 事件（有 surfaceOp）：user/message、assistant/message、tool/result 等——参与派生历史
  • log-only 事件：compaction/*、todo/write、request/header、hook/*、sandbox/mode、plan/mode、approval/*、schedule/change 等——可持久化、可回放，但不进入派生历史

assistant/chunk 提供 token 级回放保真度：原始流式分片全部落盘，因此 UI 回放和实时流式看到的是同一份数据。

5.2 Turn / Step / Round 三级循环模型

层级 定义
Step（步骤） 一次模型请求，以及由模型响应引发的工具执行
Turn（轮次） 会话中一次对已接纳输入的排空过程；包含零个或多个步骤；在领取首条输入前打开，在不再欠下任何工作时关闭
Round 承载一个轮次的外层策略迭代（Goal Round、Ralph Round）；计数器归策略所有，不统计会话中每个轮次

完整轮次流程（官方伪码）：

waterfall 型扩展点（监听器必须调用 next()）：agent/pre-step、agent/request、llm/stream、tools/pre-execute、tools/execute、tools/post-execute
serial 型（无 next()）：agent/turn-stopping

agent/pre-step 决定模型看到什么——监听器可改写已领取的消息，也可直接拒绝。首次领取被拒绝或改写为空时，仍会关闭一个不含步骤的持久轮次，因此日志会记录这次尝试。这是审计友好的设计。

5.3 Agent 句柄与 Inbox

三种输入语义（决定你的扩展怎么把内容送进模型）：

方法 语义
followup() 排队一条消息并唤醒驱动器（用户提问、cron 触发的新任务）
steer() 中途引导——插入到当前工作流中
inject() 注入上下文，留在 inbox 中直到另一条消息将其唤醒（文件变更通知、子目录 AGENTS.md、skill 内容）——空闲的 agent 保持空闲

AgentHandle = { agent, dispose }。disposer 是一种能力（capability）：消费方中只有持有者能拆除这个 agent。dispose() 会停止循环、等待退出、注销 agent、从 store 移除会话，最后解绕其作用域世界。

setup window（创建时隙）：CreateAgentOptions.setup 在两个 id 都尚未发布时组装 agent 的作用域世界——凡经 agentCtx 注册的内容都先于 agent/created 与第一次提示词组装存在。setup 拒绝、commit 抛出或所有者 dispose 都会回滚整个事务，两个 id 均不发布。这是一个干净的事务边界设计。

5.4 系统提示词组装

order 约定：

order 内容
-100 harness 身份
0 部署 persona
100–199 工具指引
其他负数 在 persona 之前渲染

system-prompt/assemble 是一个 waterfall——“专家协作式的整体装配变换”。返回的装配结果具有权威性，因此监听器作者有责任保留活跃的 Code Mode 和结构化输出协议的贡献。

官方明确的最佳实践：对于需要在展示、查找和执行之间保持对齐的工具过滤，优先使用 ctx.tools.restrict() 而不是在 assemble 里裁剪 schema——注册表会保证三者对齐（提示词里没有的工具，执行时也拒绝，与”不存在的工具”无法区分）。

5.5 工具执行流水线（七个阶段）

五个扩展点如何选（这是二开最高频的决策）：

需求 用什么
可扩展的允许/拒绝/询问策略 tools/pre-execute（返回 PreToolDecision）
最终的单调拒绝，后续无法撤销 ctx.tools.guard()
截止时间 / 重试 / 指标（需包裹分发生命周期） tools/execute（只有它能替换 exec.signal）
替换展示内容或返回值 / 阻止结果 / 附加上下文 tools/post-execute
只观测不修改的审计与埋点 tools/result

执行身份保护机制：注册表在一次递归遍历中把 arguments 物化为分离的无损 JSON，在策略开始前冻结该值，并分配不透明的 exec.token。callId、name、arguments、agent、token、signal、可选的 parent token 在整个分发过程中保持不可变。只有 around-dispatch 包装器收到可变视图，且它可以替换并恢复 exec.signal，但不能移除它。

5.6 LLM Seam 与流式协议契约

添加一个模型提供方的最小形态：

六条硬性协议义务（两个官方实现共同验证）：

  1. usage 必须在 finish 之前发出；finish 之后不再发出任何内容。稳健做法是缓冲 finish/usage 直到提供方流结束标记再统一 flush
  2. 工具调用的 arguments 全程为原始 JSON 字符串；流式片段用 argumentsDelta。若提供方返回已解析对象，需在 block-end 时重新 stringify
  3. 按首次出现的流顺序分配块 index；同一块的每次 delta 复用该 index
  4. 错误只有两条合法路径：从 stream() 抛出（传输/协议故障，用带稳定 code 的 LlmError），或以 finish {kind: 'error' | 'aborted'} 结束流（提供方带内故障）
  5. 遵守 options.signal（传递给 fetch 或 SDK）
  6. 不支持的字段抛 LlmError(..., 'UNSUPPORTED')，而非静默丢弃

密钥管理约定（重要）：”密钥采用 Cordis 原生方式管理：schemastery Config 带环境变量回退，通过 cordis.yml 的 !!js process.env.MY_KEY 注入。切勿在代码中读取自行约定的密钥文件。“

replayState：如果提供方在后续调用中需要响应 ID、签名等原生元数据，将其最小无损 JSON 投影作为 finish.replayState 发出。只有当历史提供方路由和目标提供方路由当前由完全相同的适配器实例拥有时，LlmRuntime 才会传递该状态。

已交付的适配器：

包 说明
dsh-llm-deepseek DeepSeek chat-completions 直连 HTTP，SSE 由 eventsource-parser 分帧
dsh-llm-pi-ai pi-ai 多提供方孪生（休眠挂载，settings 里出现 llm-pi-ai: 段落才注册路由）
dsh-llm-retry 提供方路由级请求重试策略
dsh-llm-replay 测试用回放插件，短路 llm/stream

5.7 上下文管理三件套：Token Meter + Spill + Compaction

这是长任务能力的核心，三者分工明确：

ctx.tokenMeter —— 回放感知的 token 测量

拥有按会话隔离的回放折叠区；压力消费方共享不可变且带修订版本的测量结果。

ctx.spillStore + spill-policy —— 超大工具结果溢出

spill-policy 是 tools/post-execute 消费方，决定何时 spill；后端保存过大的工具文本，返回面向模型的定位信息和取回提示。这避免了单个工具结果撑爆上下文。

ctx.compaction —— 上下文压缩

两条触发路径：

触发点 场景
agent/pre-step（serial） 派生请求前的压力检查（主动预防）
agent/request-error（waterfall） 规范的上下文溢出恢复（被动补救）

任一触发后，先执行可选的工具结果剪枝（compaction-tool-result-pruner：可回放的、model-free 的 head/middle/tail 剪枝），再选择摘要压缩。

恢复时序非常讲究：发生在失败步骤结束之后、失败轮次结束之前；只有当剪枝或摘要生成推进了 surface replacement generation 时，系统才会开启一个全新的重试轮次，否则仍以原始请求错误为准（防止无效重试循环）。

三个 log-only 会话事件构成一把跨越整个操作的锁：

“最后释放锁”的设计意图：操作中途崩溃会表现为可检测的遗留锁（有 start 无匹配 end），而不是一个虚假声称压缩已完成的 end。这是一个教科书级的崩溃安全设计。

5.8 Scope 作用域机制

只有两层，扁平结构： 一项贡献（工具、提示词段、变量、限制、监听器）要么是全局的，要么归属于恰好一个 scope key。

关键约束：带作用域的注册不会向下继承给 subagent。 子树行为通过 lineage 数据（parentSession、持久 delegationDepth、运行时 subagentDepth）表达，从不通过 scope 结构。

概念 语义
scope key 不透明标识，按对象同一性比较。约定：一个活跃 agent 就是其自身 scope 的 key
shadowing 最具体者胜出：带作用域的工具/片段/变量仅在该 scope 内替换同名全局对应项
restriction tools.restrict() 为单个 scope 过滤全局工具集（多个 restriction 取交集）；被过滤掉的工具既不出现在提示词中，也拒绝执行
scope-local 注册 在过滤之后合并
scoped dispatch 关于某 agent 活动的事件以该 agent 的 carrier 分发；关于注册表本身的事件（”一个工具被添加了”）保持不过滤

5.9 Code Mode / PTC（Programmatic Tool Calling）

DSH_TOOLS_MODE 为进程选择 native / code / both。

机制： 在 code / both 模式下，工具注册表拥有一个保留的 run_code 传输工具。模型不再逐个发工具调用，而是写一段 TypeScript 程序：

关键设计点：

  • 每个可见的已注册工具都可通过 await tools.<name>(args) 调用，无需额外集成
  • 生成的 ToolArgsMap / ToolOutputMap 从同一组 schema 派生精确的参数类型与规范返回类型
  • 调用重新进入完整的、受守卫保护的工具流水线——子调用携带父级 token、记录 tool/code-dispatch、将拒绝呈现为具有约束力的驳回
  • 成功调用解析为策略处理后的最终规范 JSON 值，而不是渲染后的自然语言内容
  • 并发按原生约定调度：启动顺序遵循提交顺序，并发安全的函数体最多重叠执行 maxParallelSubCalls 个
  • 中间值只存在于执行期间，不持久化、不按提示词上限截断、不设字节上限；只有外层 run_code 日志/结果受配置输出上限和 spill 流水线约束

这对工具设计提出了新要求（官方明确指出）：

“请把 output.schema 设计为实用的程序化 API：直接返回句柄与字段；将面向人类的解释放入 output.render。Code Mode 绝不能通过解析自然语言文本取得 id。“

CodeRunFailure 的失败分类是正交独立报告的：exception / timeout / abort / worker-exit（基底 OOM）/ invalid-output / output-limit——“预算耗尽不是异常，中止不是超时，基底崩溃也不是二者中的任何一个”。

5.10 沙箱与权限体系

三种沙箱模式（SandboxMode 仅管控文件系统效果）

模式 语义
read-only 后端拒绝写入（POSIX runner 授予 /dev/null 接收器；Windows ACL runner 不授予任何显式可写根目录）
workspace-write 允许在 workspace 根目录及后端承诺的临时区域下写入（新会话默认）
danger-full-access 绕过隔离（此时消费方直接 spawn 原始 argv，不调用 ctx.sandbox）

网络与进程可见性不在此词汇范围内——这是一个重要的能力边界声明。

强制执行完整性是后端报告的事实

partial 表示活跃后端或较旧内核 ABI 仅管控子集。当前的部分强制执行情形：较旧的 Landlock ABI、Windows ACL runner 的 Everyone 与硬链接边界。要求绝对保证的消费方必须拒绝或向上暴露这一区别。

已交付的沙箱后端

平台 后端
Linux bwrap / Landlock（native/landlock-run）
macOS Seatbelt（sandbox-exec）
Windows ACL 受限令牌 spawn（dsh-sandbox-windows-acl）
远程 E2B（fs-e2b + subprocess-e2b，共享 ctx.e2b 生命周期）

架构澄清：容器、microVM 和远程执行是完整能力 seam 的同级实现，而非 ctx.sandbox 的提供方。ctx.sandbox 专门处理”与宿主共享文件系统和内核的子进程 argv 包装”。

逐调用策略解析

策略按每次能力调用解析并携带，不固定在提供方上——“两个消费方可能在同一瞬间在不同策略下受限（bash 在 read-only 下，而受限子 agent 需要其状态目录可写），且已批准的提权重试是一次带更宽策略的新调用”。

ctx.sandboxPolicy 统一保存部署默认模式和 workspace 根目录，bash 与 fs 从同一处读取，因此不会限制到不同的根目录。

审批与权限预设

  • ctx.approval seam：一次性权限决策通过 approval/request waterfall 分派；没有回答方时以 unavailable 关闭失败（fail-closed）
  • ctx.permissionPresets：面向用户的预设表（workspace-write / danger-full-access），一次切换写入 permission/preset 事件并贯通到两个选项事件
  • DSH_PERMISSION_MODE 更改进程后备值；General settings 中存储的权限影响后续 Web 会话，不改变已打开的会话

双层执行分类

ConfinedArgv 携带两种正交的 stderr 分类器：

  • denialSignatures：识别沙箱正常工作时受限命令被阻止
  • runnerFailureRules：识别沙箱 runner 在执行命令之前拒绝或失败

消费方应先检查后者，将其作为沙箱基础设施故障上报，而非普通任务失败。这个区分对生产环境排障非常有价值。

第 6 部分 · 能力 Seam 全景（56 个服务）

6.1 Seam 的三角色模式

定义（官方术语表原文精神）： 一个 seam 是一项可替换能力，包含三种角色：

角色 说明
Service Definition 声明接口的 Cordis Service——可以是 ShellExecutor 这样的抽象类，也可以是 WebRuntime 这样的具体注册表，绝不是 TypeScript interface
Service Provider 一个或多个实现
Consumer 一个或多个注入该服务的使用者（通常是面向模型的工具）

canonical 范例（packages/shell）：

三条铁律：

  1. Service Provider 与 Consumer 互不依赖
  2. 一个包可以承担多个角色（dsh-llm 同时是 Definition 和 Consumer），但单一角色本身不是 seam
  3. 不要预防性拆分——只有角色需要独立演进时才用不同包

Seam 带来的杠杆效应（架构文档的原话很精彩）：

“seam 正是替换一个提供方就能改变整个产品的原因。文件系统与进程提供方共享同一个执行世界，因此把它们指向远程沙箱，也就把 Bash、PTY 和 LSP 一并搬了过去，无需提供方专用 fork。”

6.3 Subagent Seam 深读（最复杂也最有价值的 seam）

六种提供方，同一接口：

提供方 传输
subagent-spawn-in-process 进程内全新子 agent
subagent-fork-in-process 进程内 fork（携带前缀种子）
subagent-dsh-sdk 进程外子 dsh 运行时（stdio JSON-RPC）
subagent-acp 进程外 ACP 子 agent
subagent-codex 官方 Codex app-server 协议（一次性）
subagent-claude-code 官方 Claude Code Agent SDK（一次性）

服务 API 的关键操作：

操作 语义
start(name, request) 一次性委派。拒绝 = 提供方已清理每个未发布的启动资源；发布后的故障通过 run 结算
startContinuable(spec) 建立可延续子 agent 并投递初始提示词。{ childId, messageId } 在子 inbox 接受提示词时 resolve，不等待轮次开始或消息落日志
followup(parent, childId, content) 从确切的活跃直接父级投递后续消息。常驻子 agent 的 inbox 直接接受；不在场的从持久 Session 冷恢复
interrupt(targetSessionId, authority) 在人类持久父地址或确切的活跃祖先 Agent 授权下中断。准入同步、效果异步；未认领的 inbox 工作、Activation、已发布后代全部保留
reportFrom(child, content) 从确切的活跃可延续子 agent 投递选定消息

权限模型非常严格：错误的父地址、过期、自我目标或非祖先调用方一律以 UNAUTHORIZED 拒绝。这是多 agent 系统里少见的严谨授权设计。

6.4 Skill Seam（渐进式披露）

分层机制：host + per-scope 分层（与工具注册表同构）——host 行和仓库插件落在全局层，agent preset 常驻组合挂载的插件落在该 preset 层；读取时合并全局层与查看作用域的链，最近层完全胜出重名，rank 只在单层内决定重复。

skill-filesystem 的发现根（按 rank 排序）：

Rank 来源 路径
100 project-dsh <projectRoot>/.dsh/skills
200 project-agents <projectRoot>/.agents/skills
300 custom Config.customSkillDirs
400 user-dsh <dshHome>/skills
500 user-agents <agentsHome>/skills（默认 ~/.agents）

支持 SKILL.md 与扁平 Markdown 两种格式，默认开启 chokidar watch（可切换轮询、配置稳定窗口、LRU 上限）。

模型评测基础设施 极简模式提供剥离 harness 辅助的基准环境；llm-replay 支持确定性回放
agent 平台产品（给别人用的 harness） bundle/profile 分发机制让你可以卖”能力包”
多模型/多厂商路由 ctx.llm seam + llm-pi-ai 已支持任意 OpenAI 兼容端点，配合 settings 热重载
需要 agent 自我扩展的研究场景 dsh-tool-cordis 让 agent 在运行时定义和挂载插件

10.2 需要谨慎评估的场景

场景 风险
需要立刻上生产的项目 官方全大写警告会有破坏性变更；SESSION_FORMAT_VERSION = 0 明确不承诺兼容
团队无 TypeScript / Node 深度经验 整个内核是 TS，Cordis 的服务/事件/effect 模型有明显学习曲线
只需要简单的”LLM + 几个函数” 用 OpenAI Function Calling 或轻量框架成本低得多，dsh 的组合体系是过度设计
强 Python 生态依赖的团队 Python SDK 只是 stdio JSON-RPC 客户端，插件必须用 TypeScript 写——扩展能力在 Python 侧不可用
需要图状态机式复杂编排 dsh 的编排原语是 subagent/workflow 脚本，不是 DAG；LangGraph 在这方面更直接

10.3 结合产业物联网 / IoT 平台的落地设想

以你的领域（产业物联网云平台、OTA、多 agent 架构）为例，dsh 的几个能力有直接映射：

dsh 能力 产业物联网场景映射
ctx.tools + seam 三角色 把 TSP 查询、设备诊断、OTA 任务下发封装为工具包；诊断能力的”本地 mock / 测试环境 / 生产环境”三种 provider 共用同一 Definition
事件溯源会话日志 诊断会话的完整证据链——每次模型请求、每次工具调用、每条注入上下文都可回放，满足”为什么 agent 判断这台车 ECU 异常”的追溯要求
ctx.sandbox + workspace-write agent 分析车端日志时限制在会话工作目录内，不触碰宿主
ctx.subagents 六种提供方 诊断主 agent 委派”日志解析子 agent”（进程内 fork，共享上下文）与”知识检索子 agent”（进程外 SDK，独立资源配额）
ctx.skills 分层发现 把各品牌/车型的诊断 SOP 写成 SKILL.md，放在项目 .dsh/skills；不同 preset 加载不同品牌的 skill 层
ctx.schedule 定时巡检任务（every_seconds），触发时 followup() 唤醒 agent
agent-presets “诊断模式”/“OTA 回归模式”/“只读排查模式”三个 preset，各自不同的工具集与权限
session-telemetry-otel 直接对接现有 OTel Collector，把 agent 轨迹纳入统一可观测性平面
ctx.compaction + spill 车端日志动辄几十 MB，spill-policy 自动溢出 + tool-result-pruner 剪枝是刚需

但要注意： 你现有的 Java/Spring Cloud 服务无法直接成为 dsh 插件。合理的边界是 dsh 作为 agent 运行时，通过 MCP 或自研工具包调用你的 Java 微服务（见 13.4）。

第 11 部分 · 实践应用指南

11.1 环境准备

源码模式注意：pnpm dsh 通过 node --import tsx/esm 启动 apps/cli/src/bin.ts，不会自动重新构建。缺 Typert Host 产物时启动会因模块解析错误失败；缺前端产物时会提示运行 pnpm run build。启动器不检查产物是否最新，陈旧 bundle 会继续运行旧版浏览器代码。

11.2 四种入口模式

命令 用途
dsh --profile <name> 启动 $DSH_HOME/profiles/<name>
dsh web --profile web 的硬编码别名
dsh --profile headless "任务描述" 一次性运行，打印最终答案并退出
dsh plugin --profile <name> <pnpm args> 在 profile 目录内转发给 pnpm 管理插件

参数边界规则（容易踩坑）：

启动器只解析自身 flag，第一个无法识别的 token 标志应用参数开始，其后全部交给 profile（通过 ctx.cmdlineArgs 不可变快照，多插件可各自解析）。

11.3 Web UI 上手流程

  1. 启动后打开 http://127.0.0.1:3080
  2. 设置 → 模型 → 输入 DeepSeek API 密钥并保存（无需重启，settings.yaml 热重载）
  3. 点击选择工作区，添加项目目录并选中（未选工作区前输入框不可用）
  4. 创建会话时选择 agent preset（标准 / PTC / 极简 / 创造）
  5. 发送任务

关键 UI 能力：

  • Trajectory 视图：按来源检查每条记录——系统提示词、推理、工具调用与结果、子 agent 调度、每次上下文注入
  • 权限审批：当前策略下需要审批的操作会弹出询问
  • 会话树：sidebar 多级树、搜索、分组、状态点
  • Deliverables：产出文件的轮次尾部与最终响应中的可点击文件引用

11.4 Headless 一次性运行

行为语义（生产集成必读）：

  • 通过核心注册表创建全新持久 Agent
  • 提交任务 → 等待完全停稳 → flush 会话
  • 从持久事件区间推导最后一个非空 assistant 文本与最终 turn/end 原因
  • stdout 打印文本；reason === 'completed' 时 exit 0，否则 exit 1
  • 成功运行不向 stderr 写任何内容，也不打开监听端口

11.5 Python SDK

生命周期语义（重要）：

  • 运行时延迟启动，在上下文管理器内持续复用
  • 复用同一 harness + session id 会保留该会话拥有的 Bash 进程（含 cwd、导出变量、shell 函数）
  • 独立任务应使用新的 session id；只有需要延续同一段持久对话时才复用

环境变量：

示例组合 minimal.cordis.yml 的构成（用于理解 SDK 默认能力边界）：

属性 值
面向模型的工具 仅 持久 bash + str_replace_editor
Bash 超时 300 秒
编辑器输出上限 16,000 字符
上下文压缩 关闭
文件系统 裸本地后端，可访问运行时进程可见的任何路径
权限 danger-full-access ⚠️
会话持久化 DSH_SESSION_ROOT 下未压缩 JSONL

⚠️ 安全提醒：该组合使用 danger-full-access，只能在可丢弃的 checkout 或容器内运行。持久 PTY 后端需要 POSIX 终端，因此不支持 Windows agent。

11.6 TypeScript SDK

与 Python SDK 的差异：TS SDK 的启动 spec 完全显式（command/args），因为它面向”知道自己在启动哪个运行时”的仓库邻近消费方（包括 dsh-subagent-dsh-sdk 后端）。打包运行时解析是 Python 发行版的职责。

协议方法（dsh-sdk-protocol）：

方向 方法 类型
client→server initialize InitializeParams → InitializeResult
client→server session/prompt → SessionPromptResult（持久入队回执）
client→server shutdown → {}
server→client session.event 运行时每个会话的事件，未过滤
server→client session.status 整体 running/idle 转换
server→client subagent.started / subagent.finished 子 agent 生命周期

关键语义：SessionPromptResult.messageId 标识入队的 UserMessage，不标识后续的 assistant 消息、轮次结束或提示词结果。客户端需要结合开放式 session.event 流与 session.status 自行界定”一次运行”。

stdout 即协议：部署绝不能组合 stdout logger；诊断信息必须走 stderr。

11.7 ACP（Agent Client Protocol）

方法 行为
initialize 协商版本，声明 baseline-only prompts（无 image/audio/embedded-context）
session/new 创建带绝对 cwd 的全新 agent；非空 additionalDirectories/mcpServers 会拒绝
session/prompt 拼接文本块，每会话仅允许一个在途请求，等待整体 idle。正常停稳 → end_turn；取消/处置/轮次被丢弃 → cancelled
session/cancel 只取消目标 agent；未知 id 是 no-op
session/update 每个已提交 assistant/message 的非空文本块发一个 agent_message_chunk（原始 delta 不发）
session/request_permission 一次性 allow/reject 选择

定位说明：ACP 包是传输适配器，不是 UI 集成或能力 seam。它不暴露编辑器导航、transcript 回放、命令、模式、配置选择器、推理、计划、标题或工具呈现——这些属于 Web host 与 client 模块。

11.8 MCP 接入

工具命名规则（设计得很严谨）：

  • 公共名 = mcp__<serverName>__<rawName>，与 Claude Code / Codex 同形
  • 归一化到 DeepSeek function-name 约定（64 字符，[A-Za-z0-9_-]）
  • 替换或截断改变名称时，追加 (serverName, rawName) 的 12 位十六进制确定性哈希，保证不同工具永不塌缩为同名
  • 名称是 (serverName, rawName) 的纯函数——连接顺序、重同步、其他服务器都不会重命名工具
  • HMR 热替换：编辑入口触发 disconnect + reconnect，无需重启进程

⚠️ 默认不启用 MCP：CLI 随附 dsh-mcp-client 作为 patch 层依赖，但默认不启用任何 MCP 服务器，因为每条服务器命令都是 agent 沙箱之外的受信任可执行代码。
