1. Langfuse 是什么（够用就好的理论）

一句话：Langfuse 是一个开源的「LLM 工程平台」（LLM Engineering Platform），专门解决「我的大模型应用在线上到底发生了什么、好不好、怎么变得更好」这三个问题。它对标的是 LangSmith、Braintrust，但完全开源、可自托管，并且原生构建在 OpenTelemetry 之上。

1.1 为什么传统 APM 救不了 LLM 应用

你已经有 Datadog / New Relic / SkyWalking 了，为什么还要 Langfuse？

传统 APM 擅长回答「这个 HTTP 接口 P99 延迟多少、错误率多少」。但 LLM 应用里真正要命的问题它答不了：

你想知道的问题 传统 APM Langfuse
这次回答为什么是这个内容？（完整 prompt + 上下文 + 模型输出） ❌ 看不到语义 ✅ 逐 token 级输入输出留痕
RAG 里检索这一步把整体回答质量拉低了多少？ ❌ ✅ 分步骤 span + 打分
改了一版 prompt 后，回答质量是涨了还是跌了？ ❌ ✅ 数据集实验对比
这条链路花了多少钱（token 成本）？ ❌ 只有耗时 ✅ 自动按模型计费聚合
多轮 Agent 的工具调用链是怎么展开的？ ⚠️ 只有调用栈 ✅ 树状嵌套 + 每步 I/O

核心差异：传统 APM 关注系统指标，Langfuse 关注语义 + 质量 + 成本。两者不是替代关系，而是互补——你完全可以让 Langfuse 通过 OpenTelemetry 和现有 APM 共存。

1.2 Langfuse 四大能力一图看懂

  • Tracing（追踪）：应用的「黑匣子」。每次请求生成一个 Trace，里面是一棵由 Observation 组成的树。
  • Prompt Management（提示词管理）：把 prompt 从代码里抽出来，在 UI 上版本化管理。改 prompt 不用改代码、不用重新发版。
  • Evaluation（评估）：质量怎么量化？通过 Score（评分）。来源有三种：人工标注、代码程序化打分、LLM 当裁判（LLM-as-a-Judge）。
  • Datasets（数据集）：把「输入 + 期望输出」沉淀成测试集，在上面反复跑「实验」，做回归与 A/B。

1.3 核心概念速查表（必背）

这几个名词贯穿全文，先建立直觉：

概念 是什么 类比
Trace 一次完整请求的顶层容器（如一次用户问答） 一次「分布式调用」的 traceId
Observation Trace 里的一个步骤，三种子类型 ↓ 一个 span
┗ Span 普通步骤（如「检索文档」「解析 JSON」） 函数调用 span
┗ Generation 一次 LLM 调用（带 model / 输入 / 输出 / token / 成本） 特殊的 span
┗ Event 瞬时打点（无持续时间） 日志点
Score 附加在 Trace/Observation/Session/Dataset Run 上的评分 质量指标
Session 把同一会话的多个 Trace 串起来（多轮对话） 会话 ID
Dataset 一组「输入 + 期望输出」测试用例 测试集
Dataset Run / Experiment 在数据集上跑一遍应用并记录结果 一次回归测试

关键心智模型：Trace（一次请求）→ 内含若干 Observation（步骤）→ 其中 LLM 调用是 Generation（自动带 token/成本）→ 用 Score 给它们打分 → 用 Dataset 批量、可重复地评估。

1.4 v2 → v3 架构演进：为什么要引入 ClickHouse / Redis / S3

如果你只是本地玩玩，可以跳过本节；但作为架构师，理解这次演进对你做容量规划很重要。

Langfuse v3（2024 年 12 月 6 日发布） 相比 v2 是一次「重型」架构升级。v2 时代只有「一个应用容器 + 一个 Postgres」，简单但扛不住量。Langfuse Cloud 与大规模自托管用户在百万级 trace 行时，Postgres 在写入和复杂聚合查询上都成了瓶颈。

v3 的关键改动（你部署时会直接遇到这些组件）：

  1. 追踪数据从 Postgres 迁到 ClickHouse：Trace / Observation / Score 这些海量、需要时序聚合的数据，搬到列式数据库 ClickHouse，查询和写入性能数量级提升。Postgres 仅保留用户、项目、配置等元数据。
  2. 引入事件驱动的异步摄取（Redis + S3/MinIO）：SDK 上报的数据，Web 容器先快速落到 S3（对象存储），只在 Redis 里留一个队列引用就立刻返回 200；随后 Worker 容器从 S3 取出、异步写入 ClickHouse。这样流量尖峰不会因为数据库慢而超时或丢数据。
  3. 拆成 Web + Worker 两个容器：Web 负责 UI 和 API，Worker 负责后台任务（异步摄取、发邮件、跑评估等）。

给自托管者的安心提示：所有新增组件（ClickHouse、Redis/Valkey、S3/MinIO）都是开源的，没有任何非 FOSS 依赖或商业许可要求，可以完全自托管。自托管跑的就是和 Langfuse Cloud 一模一样的代码库。

对你的实践含义：

  • 本地/小规模：用下一章的 Docker Compose 把六个组件一把拉起来即可。
  • 生产/高可用：官方建议上 Kubernetes（Helm Chart），Postgres / ClickHouse / Redis / S3 用云托管或独立集群，Docker Compose 不支持横向扩展。
  • Python SDK v3 要求自托管平台版本 ≥ 3.125.0（TS SDK v4 要求 ≥ 3.95.0），用最新镜像即可满足。

2. Docker Compose 自托管完整部署

本章给两条路：方式 A 用官方仓库两条命令快速验证；方式 B 用一份可控的 docker-compose.yml + .env，把每个密钥和参数都讲清楚，适合作为团队内网部署的起点。

2.1 架构与资源要求

v3 的 Docker Compose 会拉起 6 个容器：

容器 镜像 作用 对外端口
langfuse-web langfuse/langfuse:3 UI 控制台 + API（接收 SDK 上报） 3000（需暴露）
langfuse-worker langfuse/langfuse-worker:3 异步摄取、评估、邮件等后台任务 3030（仅本机）
postgres postgres:17 元数据：用户/项目/API Key/Prompt 5432（仅本机）
clickhouse clickhouse/clickhouse-server 追踪数据：Trace/Observation/Score 8123/9000（仅本机）
redis redis:7 队列 + API Key 缓存 6379（仅本机）
minio cgr.dev/chainguard/minio S3 兼容对象存储：原始事件 + 多模态 9090（API，需暴露多模态时）/9091（控制台，仅本机）

安全默认值：官方 compose 把除 langfuse-web(3000) 和 minio(9090) 外的所有服务都绑定在 127.0.0.1，只接受本机连接。生产部署时再用防火墙/安全组限制 3000 和 9090 的入站来源。

资源要求：

  • 本地试用：4 核 / 8–16 GiB 内存即可。
  • VM 部署：建议至少 4 核 / 16 GiB 内存 / 100 GiB 磁盘（如 AWS t3.xlarge）。可观测数据增长快，磁盘要给足。
  • 磁盘增长估算：ClickHouse 大约每百万条 trace 增长 1–2 GiB（取决于 prompt/输出长度）。

2.7 部署常见坑排查

现象 原因 解决
langfuse-web 启动即退出，报 encryption key 相关 ENCRYPTION_KEY 不是 64 位 hex 用 openssl rand -hex 32 重新生成
一直卡在 starting，worker 报连不上 CH/Redis 依赖容器未 healthy docker compose ps 看健康状态，logs 看具体服务

跑一段时间后写入变慢/报盘满 ClickHouse 随 trace 增长吃磁盘 扩容磁盘；规划数据保留策略；监控磁盘水位
想从外部机器上报却连不上 默认只暴露 3000/9090 配置防火墙/安全组放行 3000（和需要多模态时的 9090），其余保持内网
LANGFUSE_INIT_* 不生效 值加了双引号 / 数据库已非空 去掉引号；首次初始化才生效，已有数据请用 UI

通用排查三连：docker compose ps（健康状态）→ docker compose logs <service>（报错详情）→ curl .../api/public/ready（就绪探针）。

3.3 三种创建 Observation 的方式

v3 提供三种方式，可以自由嵌套、混用。OpenTelemetry 的上下文传播会自动处理父子关系。

方式一：@observe 装饰器（最省事，推荐做函数级追踪）

函数的入参/返回值会被自动记录为 observation 的 input/output；嵌套关系由 OTEL 上下文自动建立，无需手动传 parent。

方式二：start_as_current_observation 上下文管理器（要在一个函数内分多步时最清晰）

start_as_current_span / start_as_current_generation 是便捷方法；它们等价于通用形式 start_as_current_observation(as_type="span" | "generation", ...)。

方式三：手动 span（需要把对象传给下游、或跨服务时）

怎么选？ 函数边界清晰 → 装饰器；一个函数内分阶段 → 上下文管理器；要把句柄交给异步/下游 → 手动 span。三者可混用：装饰器里嵌上下文管理器、上下文里混手动 span 都没问题。

3.4 OpenAI / DeepSeek 集成：一行 import 自动追踪

最爽的来了：把 import openai 换成 from langfuse.openai import openai，所有 LLM 调用自动变成 Generation（自动记录 model、输入、输出、token、成本、耗时），并自动嵌套到当前 trace 下。

这次调用会在 Langfuse 里自动生成一个 Generation——你能看到完整 prompt、输出、token 用量和成本，一行业务代码都不用加。

为什么 DeepSeek 能用 OpenAI 集成？ 因为 DeepSeek 提供 OpenAI 兼容 API。同理通义千问（DashScope 兼容模式）、月之暗面、本地 vLLM/Ollama 的 OpenAI 兼容端点都能这样接。只要是 OpenAI 协议，langfuse.openai 都自动追踪。

3.5 给 Trace 打上 user / session / tags / metadata

线上排障最需要的就是「按用户筛」「按会话串起多轮」。在当前 trace 上设置即可：

  • user_id：在 UI 的 Users 视图按人聚合，看某用户的所有请求、成本、质量。
  • session_id：把多轮对话的多个 trace 归到一个 Session，完整回看一段对话。
  • tags / metadata：自定义维度，做筛选、分群、A/B 标记。

集成（OpenAI/LangChain）里怎么设置 trace 属性？ v3 的做法是：在被集成的库调用外面包一层 Langfuse span，在这层 span 上调 update_current_trace(...)。下一章 POC 会演示这种「外层 span 兜属性，内层集成自动追踪」的标准姿势。

4.9 LLM-as-a-Judge 自动评估

关键词命中只能查「形似」，查不了「语义对不对」。这时用 LLM 当裁判。两条路线：

路线 A：Langfuse 托管评估器（推荐，无代码、服务端运行）

在 UI 里配置，自动对新 trace 或数据集实验打分：

  1. Settings → LLM Connections：添加一个 LLM 连接（OpenAI / DeepSeek 等）。裁判模型必须支持结构化输出（structured output），这样 Langfuse 才能稳定解析评分结果。
  2. Evaluators → + Set up Evaluator：选内置模板（如 correctness / hallucination / helpfulness）或自定义评估 prompt。
  3. 变量映射：把评估模板里的变量（如 query / generation / ground_truth）映射到 trace 的对应字段（输入 / 输出 / 数据集期望答案）。
  4. 选择作用目标：对「新产生的 trace」实时评估，或对「某数据集实验/历史 trace」回填评估。
  5. 评估结果会自动写成 Score，进入 Metrics 仪表盘，和你的程序化分并列展示。

LLM-as-a-Judge 评估器是在 Langfuse 服务端运行的（由 Worker 异步执行，带限流与失败重试），不占用你的应用进程。这正是 v3 引入异步架构的原因之一。

5. 生产级最佳实践

POC 跑通只是起点。把 Langfuse 真正用进生产，下面这些经验能帮你少踩坑。

5.1 Trace 设计：粒度、命名与 Span vs Generation

粒度——既不要太粗，也不要太细：

  • ❌ 太粗：整条链路只有一个 span，出问题不知道是检索还是生成的锅。
  • ❌ 太细：把每个工具函数都埋点，trace 树几十层，噪声淹没信号、还涨成本。
  • ✅ 恰当：按语义阶段切分。一个 RAG 至少分「检索 / 生成」两步；一个 Agent 按「规划 / 工具调用 / 反思」分。让 trace 树读起来就是业务流程图。

命名——稳定、可聚合：

  • observation 名要稳定且去除可变参数。用 retrieve-docs，不要用 retrieve-docs-OTA升级失败（把变量塞进名字会让聚合统计碎掉）。可变信息放 metadata 或 input。
  • 团队约定统一命名前缀（如 rag.retrieve / rag.generate / agent.tool.<name>），便于在 UI 按前缀筛选。

Span 还是 Generation？

  • Generation 专指 LLM 调用——它额外承载 model、usage_details（token）、成本计算。凡是调模型的，一定用 generation（或用 langfuse.openai 自动生成）。
  • Span 用于其它一切：检索、解析、业务逻辑、工具调用。
  • Event 用于无持续时间的瞬时打点（如「触发了某规则」）。

尽早设置 trace 属性：在 trace 一开始就调 update_current_trace(user_id=..., session_id=...)，确保后续所有指标聚合准确。

5.2 成本与延迟控制

(1) 警惕 OTEL「基础设施噪声」：v3 SDK 是 OpenTelemetry 原生的，会自动捕获其它 OTEL 插桩库发出的 span（数据库、HTTP、框架等）。这是双刃剑——可能涌入大量与 LLM 无关的 span，既污染视图又增加成本。上线前先看 trace、按「instrumentation scope」过滤掉不需要的 span（官方有「filtering by instrumentation scope」指南）。

(2) 大输入/输出要节制：把超大文档全文塞进 input/output 会拖慢上报、撑大存储。对超大字段可截断或只记摘要/引用。

(3) 采样：超高 QPS 场景可对 trace 采样（按比例上报），在成本与可观测性之间权衡。核心链路全采、长尾按比例采是常见策略。

(4) flush 的纪律：

  • 短命进程（脚本/CLI/Serverless/批处理）：结束前必须 langfuse.flush()，否则缓冲区数据随进程退出丢失。
  • 长驻服务：正常运行靠后台异步上报，无需每次 flush；只在优雅退出钩子里 flush 一次（如上文 atexit.register(langfuse.flush)）。
  • SDK 设计上不会因为自身错误拖垮你的应用——上报失败会被捕获并记日志，不抛到业务侧。

5.3 数据安全：脱敏、加密与网络隔离

LLM trace 里常含敏感数据（用户输入、PII、内部知识）。自托管的最大价值就是数据不出域，但仍要做好：

  • 传输前脱敏（Data Masking）：Langfuse SDK 支持配置 mask 函数，在数据离开你的进程之前对敏感字段（手机号、身份证、密钥）做脱敏/打码。
  • 静态加密：ENCRYPTION_KEY 用于对敏感字段做静态加密存储；务必用 openssl rand -hex 32 生成的强密钥，并纳入密钥管理（不要硬编码进仓库）。
  • 网络隔离：生产部署只暴露 langfuse-web(3000)（和需要多模态时的 minio:9090），其余组件全部内网/绑定 127.0.0.1。前面加反向代理（Nginx/Traefik）做 TLS 终止。
  • 鉴权与 SSO：自托管支持配置 SSO、关闭开放注册、限制谁能创建组织。生产务必关闭默认开放注册。
  • 合规视角（你的领域尤其相关）：产业物联网数据涉及 WP.29/R155、数据出境合规等，自托管 + 脱敏 + 加密 + 审计是基础组合。

5.4 Prompt 工程闭环：版本、标签、A/B 与回滚

把 prompt 当代码一样管理：

  • 版本化：每次在 UI 改 prompt 都产生新 version；代码默认拉 production 标签那一版。
  • 标签灰度：用 label 控制发布。例如新版本先打 staging 标签，在测试环境 get_prompt(name, label="staging") 验证，达标后再把 production 标签切过去——切换瞬间生效、无需发版。
  • 生成与版本关联：调用时传 langfuse_prompt=prompt，UI 里就能看到「这条回答是哪个 prompt 版本产出的」，质量回归时能精确定位到版本。
  • A/B：不同标签指向不同版本，配合 Score 对比哪版回答质量更高。
  • 回滚：出了问题把 production 标签切回旧 version 即可，秒级回滚。
  • 缓存与降级：get_prompt 有客户端缓存（默认 TTL），即使 Langfuse 短暂不可用也能用缓存的 prompt，避免单点拖垮业务。

5.5 评估闭环：线上 + 离线 + CI 集成

成熟的 LLM 工程要「双轨评估」：

  • 线上（被动）：生产流量上挂 LLM-as-a-Judge 托管评估器 + 用户反馈分，持续监控真实质量，发现漂移。
  • 离线（主动）：每次改 prompt/换模型，先在 Dataset 上跑实验，和基线 run 对比，质量不退化才允许上线。
  • CI 集成：把离线实验脚本（如 evaluate.py）接进 CI——PR 触发时跑评测集，平均分低于阈值就卡住合并。这把「LLM 应用质量」变成像单元测试一样的硬门禁。
  • 代码评估器（Code Evaluators）：对确定性检查（JSON 可解析、schema 校验、关键词、工具调用是否正确）用代码评估器，比 LLM 裁判更可靠也更便宜；语义判断（有用性、语气、正确性）才上 LLM-as-a-Judge。

5.6 多环境与团队协作

  • environment 字段：SDK/上报支持设置 environment（dev/staging/prod）。用它隔离不同环境的数据，UI 里按环境筛选，避免开发流量污染生产指标。
  • 项目隔离：一个 Organization 下可建多个 Project，按产品线/团队隔离数据与 API Key。
  • Datasets 文件夹：数据集名用 / 可组织成文件夹（如 evaluation/ota-qa），便于团队按业务归类管理。
  • 权限：用组织/项目级成员与角色管理谁能看、谁能改 prompt、谁能配评估器。

5.7 为 Langfuse 本身做可观测与高可用

自托管意味着 Langfuse 也是你要运维的服务：

  • 健康探针：用 /api/public/health（存活）和 /api/public/ready（就绪）接 K8s liveness/readiness 或负载均衡健康检查。
  • 自身可观测：Langfuse 支持通过 OpenTelemetry 暴露自身指标，接你现有的监控告警。
  • 高可用：Docker Compose 不支持横向扩展（无内置负载均衡），只能纵向扩容（换更大机器）。需要 HA / 高吞吐时，按官方建议上 Kubernetes（Helm Chart），Web/Worker 多副本，Postgres/ClickHouse/Redis/S3 用云托管或独立集群，可做到多可用区（跨 Region 较难）。
  • 容量规划：重点盯 ClickHouse 磁盘（约每百万 trace 增长 1–2 GiB）和 Redis 内存（队列，noeviction 策略下满了会拒写）。提前设保留策略与扩容告警。
  • 备份演练：Postgres / ClickHouse / MinIO 三处都要备份，并定期演练恢复——备份没演练过等于没有。
