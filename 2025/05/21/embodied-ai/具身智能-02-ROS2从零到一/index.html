2.1 ROS 的历史：从实验室工具到机器人操作系统

2.1.1 定义：ROS 不是操作系统

ROS（Robot Operating System）名字里带 OS，但它不是内核，而是运行在 Linux 之上的通信中间件 + 构建工具链 + 算法包生态三合一。最贴切的类比：ROS 之于机器人 ≈「Spring Cloud + Maven + Maven Central」之于微服务——通信框架、构建体系、海量现成组件，三者合体成为事实标准。

2.1.2 ROS1 时代（2007–2020）：学术黄金期

2007 年斯坦福 Morgan Quigley 的 Switchyard 项目起源，Willow Garage 接手孵化，2010 年发布首个发行版。此后十年 ROS1 成为学术与原型开发的事实标准，沉淀了导航栈、SLAM、MoveIt 机械臂规划等庞大生态。ROS1 最后一个版本 Noetic 已于 2025 年 5 月 EOL——今天入行直接学 ROS2，无需回头补 ROS1。

2.1.3 ROS1 的四个致命缺陷

# 缺陷 表现 产业物联网类比
1 Master 单点 roscore 进程崩溃 → 全部节点失联 整车所有 ECU 依赖单个中心网关进程
2 无实时无 QoS 自研 TCPROS 协议，不可控延迟 用 HTTP 干 CAN 总线的活
3 无安全 同网段任何主机可发布任意话题 车内总线无认证对外敞开
4 单机假设 多机、弱网、跨平台支持极差 撑不起量产车队规模

2.1.4 ROS2 的设计目标：产品级机器人

2014 年官方宣布重写，2017 年 12 月发布首版（Ardent Apalone）。设计关键词：多机器人、实时、安全、跨平台、嵌入式、产品化。最核心的架构决策是：不再自研通信协议，把通信层整体外包给工业标准 DDS，ROS 自己专注于机器人领域抽象（消息类型、TF、工具链）。这与你经历过的「放弃私有协议、拥抱 MQTT/gRPC 标准」是同一种工程成熟。

2.1.7 与产业物联网平台的映射

ROS1 → ROS2 ≈ 产业物联网平台从「Demo 架构」到「量产架构」的重写：去 Master 单点 ≈ 去单体网关；引入 DDS-Security ≈ 全链路 PKI 改造；自研协议 → DDS 标准 ≈ 私有协议 → MQTT/gRPC 标准化；多机支持 ≈ 从单车调试到车队运营。

2.1.8 企业实践建议

在企业内制定《ROS2 版本生命周期规范》：新项目一律当前 LTS；每个 LTS EOL 前 12 个月启动迁移评估；OS/ROS/核心包三者版本捆绑管理成一张兼容矩阵表——照抄你们车端软件版本治理的模板即可。

2.2 DDS：机器人的通信基座

2.2.1 定义：以数据为中心的发布订阅标准

DDS（Data Distribution Service）是 OMG 组织制定的以数据为中心（Data-Centric）的发布/订阅中间件标准，出身于舰船作战系统、航空航天等硬实时分布式领域，由两份规范构成：DDS 规范（API 与 QoS 模型）+ DDSI-RTPS 规范（线上互操作协议）。「以数据为中心」的含义：网络中流通的不是无类型字节流，而是带类型定义、带 QoS 契约的结构化数据对象，中间件本身理解并管理这些数据的可靠性、历史与时效。

对照你熟悉的模型：MQTT 以「消息」为中心（Broker 只转发字节）、Kafka 以「日志」为中心，DDS 最贴切的类比是——一张分布式共享的、类型化的实时数据表 + 发布订阅通知。

2.2.2 DCPS 实体模型：六个核心对象

实体 职责 产业物联网类比
DomainParticipant 进程进入某 Domain 的成员身份，发现与资源的根 设备接入某租户的连接实例
Topic 类型化数据通道：名字 + IDL 数据类型 MQTT 主题 + Schema 强绑定
Publisher / DataWriter 发布侧容器 / 真正写数据的写者 发布客户端 / 具体发布会话
Subscriber / DataReader 订阅侧容器 / 真正收数据的读者 订阅客户端 / 具体订阅会话 
flowchart TB
  DP["DomainParticipant（每进程一个）"] --> PUB[Publisher]
  DP --> SUB[Subscriber]
  PUB --> DW1["DataWriter → Topic /odom"]
  PUB --> DW2["DataWriter → Topic /battery"]
  SUB --> DR1["DataReader ← Topic /cmd_vel"]
  DW1 -. "RTPS over UDP/共享内存" .-> RDR["远端 DataReader"]

重要资源事实：自 Foxy 起，ROS2 改为每个进程（Context）一个 DomainParticipant、节点共享——早期「每节点一个 Participant」曾导致发现流量爆炸。做容量规划时按进程数而非节点数估算发现开销。

2.2.3 RTPS 线协议：互操作与「可调可靠性」

RTPS（Real-Time Publish-Subscribe）定义报文（DATA / HEARTBEAT / ACKNACK / GAP）与可靠机制：可靠模式下 Writer 周期发 HEARTBEAT 宣告已发序列号，Reader 用 ACKNACK 上报缺口，Writer 补发——在 UDP 之上自建了一套强度可协商的可靠传输。相比 TCP：无队头阻塞、可按 Topic 独立配置可靠强度、天然支持组播。不同厂商 DDS 因 RTPS 而互通。类比：RTPS ≈ 消息队列世界的 AMQP 线协议，但把「可靠性强度」做成了每通道可配的旋钮。

2.2.4 自动发现：SPDP + SEDP 两阶段

阶段一 SPDP（参与者发现）：每个 Participant 周期性（Fast DDS 默认约 3 秒）向知名多播地址 239.255.0.1 + 按 Domain 计算的端口发送公告（含 GUID、单播地址表、协议版本）；收到者以单播回礼。阶段二 SEDP（端点发现）：互相认识的 Participant 通过内置可靠通道交换各自 DataWriter/DataReader 清单（Topic 名、类型、QoS），双方执行 QoS 兼容性匹配，匹配成功才建立用户数据通路。

端口公式（RTPS 标准）：PB=7400、DG=250、PG=2。Domain d：发现多播端口 = 7400+250d，用户多播 = 7401+250d，单播 = 7410+250d+2×participantId 起。Domain 0 即 7400/7401/7410/7411…——防火墙放行规则由此推导。

【映射 🚗→🤖】SPDP/SEDP ≈ 你的设备注册 + 服务发现合体，但完全去中心化：没有注册中心，靠多播自报家门。这既是它「上电即互联」的魔法来源，也是它出了本体、进了云网络就水土不服的根源（见 2.3.5）。

2.2.5 QoS 初见：六项策略与一条兼容规则

策略 取值 一句话 产业物联网类比
Reliability RELIABLE / BEST_EFFORT 丢包补发 or 尽力而为 MQTT QoS1 vs QoS0
Durability VOLATILE / TRANSIENT_LOCAL 新订阅者能否补收历史 Retained Message
History+Depth KEEP_LAST n / KEEP_ALL 缓存几条待发/待读 队列长度
Deadline 周期 数据必须按周期到达，违约触发回调 心跳超时告警
Liveliness 自动/手动 + 租约 写者生死监测 设备在线状态判定
Lifespan 时长 数据过期自动作废 消息 TTL

RxO 兼容规则（Requested vs Offered）：订阅端「要求」不得严于发布端「提供」，否则连接根本不建立、且默认静默无报错。头号新手坑：发布端 BEST_EFFORT + 订阅端 RELIABLE = 永远收不到一个字节。完整 22 项策略与调优放中卷 QoS 专章。

2.2.6 传输层：三档速度

同进程：intra-process 指针直传（µs 级）；同机跨进程：共享内存（Fast DDS 共享内存传输默认启用，几十 µs；零拷贝 data-sharing 需数据类型有界并显式配置；Cyclone 配 iceoryx 同理）；跨机：UDP 单播/组播（局域网亚毫秒）。这三档就是 100Hz~1kHz 控制与感知数据流的物理基础——MQTT 经 Broker 的两跳毫秒级往返在此结构性出局。

2.2.7 DDS 实现选型与 rmw 切换

实现 定位 备注
Fast DDS（eProsima） Jazzy 默认 功能全，共享内存默认开，Discovery Server 出自它
Cyclone DDS（Eclipse） 轻量稳健 曾为 Galactic 默认，Nav2 社区口碑好，零拷贝靠 iceoryx
Connext（RTI，商业） 车规/航天级 认证与工具链最强，按核收费
Zenoh（rmw_zenoh） 新一代 面向弱网/云边/跨广域，Jazzy 起提供官方二进制

切换只需：sudo apt install ros-jazzy-rmw-cyclonedds-cpp && export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp。全队必须统一实现：混用虽有 RTPS 互通，但 QoS 细节与共享内存行为差异是隐性深坑。

2.2.8 Domain ID：最简单的隔离手段

ROS_DOMAIN_ID（建议 0~101，默认 0）把同一物理网络切成互不发现的逻辑域——实验室十台机器人各占一个 Domain 即互不串台。【映射】≈ 你的多环境/多租户网络隔离（prod/staging VPC），只是实现在 UDP 端口层。经典事故：忘设 Domain，隔壁工位的 /cmd_vel 开动了你的底盘——Domain 规划表是机器人团队的第一份平台文档。

2.3 为什么不用 MQTT/HTTP：机器人为什么必须 DDS

2.3.1 平台架构师的第一直觉

你一定会想：MQTT 撑起了百万级产业物联网接入，HTTP 是万能胶，为什么机器人体内还要再学一套？答案分两半：机器人本体内部（机内总线场景），MQTT/HTTP 结构性不合格；而端到云链路上，MQTT/WebSocket 依然是主力。本节把两半都讲透，你会发现结论与整车「车内 CAN、上云 MQTT」惊人一致。

2.3.3 五个杀手级理由

  1. 无中心：Broker 崩溃 = 全机瘫痪；机器人摔倒的瞬间不能等 Broker 重启——控制链路上不允许存在任何中心组件，这与「刹车不过网关」同一伦理。
  2. 时延与拷贝：一帧图像要同时喂感知、录制、遥测三个消费者——DDS 组播/共享内存一次分发；MQTT 得先上 Broker 再各下发一份，带宽与延迟双输。
  3. QoS 粒度：同一台机器人上 /cmd_vel 要 RELIABLE + Deadline 10ms，/camera 要 BEST_EFFORT 丢帧无妨——MQTT 的 0/1/2 三档表达不了这种按通道定制的契约。
  4. 自动发现 + 强类型：新传感器上电即被全图发现且类型校验通过才互联，产线换件即插即用，无需改配置中心。
  5. 生死监测标准件：Liveliness/Deadline 让「节点假死」在中间件层被发现并回调告警——你在 MQTT 上手写过的应用层心跳方案，在 DDS 是开箱即用的标准能力。

2.3.4 但端到云依然是 MQTT/WebSocket 的天下：混合架构

DDS 依赖多播发现与稳定低延网络，一出本体（NAT、蜂窝网、公网）就水土不服；而云端接入面要的恰是你最熟的那套：海量长连接、鉴权计费、离线消息、水平扩展。工业标准答案：机内 DDS 域 + 云桥（Bridge）+ 云侧 MQTT/WebSocket/Kafka。

2.5 Node：机器人世界的微服务

2.5.1 定义与单一职责

Node 是 ROS Graph 中最小的执行与通信单元：一个有名字的对象，持有若干 Publisher / Subscription / Service / Action / Timer / Parameter。设计哲学与微服务一致——单一职责：camera 节点只出图、控制节点只算控制量、遥测节点只做聚合。与微服务的差别：多个 Node 可以住进同一进程（组件化组合，下卷 Composition 章），像「模块化单体」一样兑换进程内零拷贝性能。

2.5.2 解剖：Context 与接口容器

2.6 Executor 与 Callback：ROS2 的事件循环

2.6.1 定义：不 spin 不干活

Executor 是把「就绪工作项」（消息到达、定时器到期、服务请求）取出并调用对应 Callback 的调度器。Node 只是声明了回调，不交给 Executor spin 就永远不会执行——与「Netty 的 Handler 不挂到 EventLoop 上不会被触发」「Kafka consumer 不 poll 不消费」完全同构。

2.6.2 工作原理：WaitSet 模型

要点只有一句：回调执行期间调度器不回等待位——单线程 Executor 下，一个慢回调就能饿死整个节点的所有回调（定时器漂移、消息积压全由此起）。

2.6.3 Executor 家族与选型

Executor 语言 特点 适用
SingleThreaded rclpy/rclcpp 默认 串行、确定性最好 控制类、状态机类节点
MultiThreaded rclpy/rclcpp 线程池并发回调 IO 密集的聚合/桥接节点
StaticSingleThreaded rclcpp 启动时固化实体集，省每轮重建开销 实体固定的高频节点
EventsExecutor rclcpp（Jazzy 提供，experimental 命名空间） 事件驱动免轮询，低延迟低 CPU 资源敏感的端侧

rclpy.spin(node) 内部就是临时建一个 SingleThreadedExecutor——显式声明 Executor 是工程化节点的标志。

2.9 Topic 与消息体系：机器人的数据流

2.9.1 定义

Topic 是类型化的单向多对多数据流：任意多个 Publisher 向同名 Topic 写、任意多个 Subscription 读，双方只需约定「名字 + 消息类型 + 兼容 QoS」。它是机器人 90% 数据的载体：传感器流、状态流、控制量流、遥测流。与 MQTT 主题的三大差异再强调一次：强类型契约、无 Broker 直连、每通道独立 QoS。

2.9.2 消息 IDL：.msg 文件与代码生成

消息用 .msg 文件声明（字段类型 + 名称 + 可选默认值/常量），构建时由 rosidl 工具链生成 C++/Python 等语言代码与 DDS 类型支持。基础类型：bool byte int8~64 uint8~64 float32/64 string wstring，支持定长数组 float32[3]、变长数组 float32[]、有界数组 float32[<=10]、嵌套消息与常量。这就是机器人世界的 Protobuf/Avro——Schema 即接口，Schema 变更即接口变更，需要走兼容性评审。

2.9.5 通信流程与序列化

发布路径：用户对象 → rosidl 类型支持序列化为 CDR（RTPS 标准表示）→ rmw → DDS 按 QoS 投递 → 订阅端反序列化 → 回调。CDR 是紧凑二进制、跨语言跨厂商互通——抓包分析（Wireshark 有 RTPS 解析器）时看到的就是它。同进程 intra-process 通路则跳过序列化直传指针，这就是组合部署（2.5.8）省下的最大开销。

2.10 Service：同步请求响应

2.10.1 定义与 .srv 契约

Service 是一对一请求-响应原语，契约文件 .srv 用 --- 分隔请求与响应两段：

适用判据两条：耗时短（毫秒~一两秒）且幂等或可安全重试——查询状态、开关模式、触发一次性动作。等价物即 gRPC unary call / 你的同步 REST 接口。

2.10.2 底层机制：两条 DDS Topic + 序列关联

DDS 没有原生 RPC，ROS2 用「请求话题 rq/ + 响应话题 rr/ + 样本身份关联」拼出了 RPC 语义。理解这点的实用价值：服务不通时照样用 ros2 topic 思路排障（Domain/QoS/发现三查），因为它本来就是话题。

2.10.3 客户端范式：默认异步

复习 2.6.4 的铁律：回调里禁止同步等 Service 结果（spin_until_future_complete 只允许出现在脚本主流程里）。服务端侧同样两条纪律：回调必须快、必须幂等——客户端超时重试是常态，与你写 HTTP 接口的假设一致。

2.10.4 何时不用 Service（反模式清单）

长任务放 Service = 客户端盲等、无进度、不可取消、超时语义混乱——导航/校准/OTA 全部改用 Action（下一节）。持续数据查询放 Service 轮询 = 用 REST 轮询硬抗流式需求——改订阅 Topic。这两条反模式与「用同步 HTTP 做长作业/用轮询做推送」逐字对应，你的 API 设计直觉全部有效。

2.11.2 底层解剖：3 服务 + 2 话题

Action 不是新的传输机制，而是组合协议：send_goal 服务（提交并审核）、cancel_goal 服务（撤销）、get_result 服务（取结果）+ feedback 话题（进度流）+ status 话题（状态机广播），统一挂在 /<action>/_action/ 命名空间下。设计思想与你把「任务系统 = 创建接口 + 进度推送 + 结果查询 + 撤销接口」组合出来完全一致——只是 ROS2 把它标准化成了原语。

  • Feedback 频率控制在 1~10Hz 并做增量语义（进度百分比/阶段），别把 Feedback 当高频遥测用。
  • Result 必含机器可判读的结构化结果（success + 错误码 + 产物引用），供云端任务系统直接落库。

2.11.12 常见误区

  • ❌ 在 execute 回调里阻塞主 Executor（教学示例的 sleep 别照搬生产）——独立线程或 MultiThreaded + 回调组。
  • ❌ 忘记处理 is_cancel_requested——不响应取消的 Action 会把「可撤销」承诺变成谎言，云端任务将卡在 CANCELING。

  • Action 即 OTA 任务：审核/进度/状态/撤销/结果逐字段同构。
  • 抢占还是互斥：goal_callback 内自定义策略，导航抢占、OTA 互斥。

2.12 Lifecycle Node：受管生命周期状态机

2.12.1 定义与动机

Lifecycle Node（受管节点）给节点套上一个标准状态机：外部编排器可以显式驱动它「配置 → 激活 → 停用 → 清理」，而不是构造完就闷头跑。它解决的是普通节点的三大工程痛点：启动顺序不可控（相机没就绪，感知就开始订阅）、就绪时机不可知（进程活着 ≠ 服务可用）、故障后无法温和复位（只能杀进程重启）。你一眼就能认出这是什么：设备/服务的标准生命周期管理，与 OTA 升级状态机、K8s 的 readiness 语义同族。

2.12.2 四主状态与五迁移

stateDiagram-v2
    [*] --> Unconfigured
    Unconfigured --> Inactive: configure（加载参数/建接口/连硬件）
    Inactive --> Active: activate（开始发数据/干活）
    Active --> Inactive: deactivate（暂停但保留资源）
    Inactive --> Unconfigured: cleanup（释放资源回到出厂）
    Unconfigured --> Finalized: shutdown
    Inactive --> Finalized: shutdown
    Active --> Finalized: shutdown
    Finalized --> [*]

每次迁移经过对应回调（on_configure / on_activate / on_deactivate / on_cleanup / on_shutdown），返回 SUCCESS / FAILURE / ERROR 决定迁移成败；ERROR 进入错误处理路径。受管发布器（Lifecycle Publisher）只在 Active 态真正发数据——Inactive 时静默丢弃，天然实现「就绪前不出声」。

2.13 Parameter：节点的运行时配置面

2.13.1 定义与类型系统

Parameter 是节点的运行时键值配置，类型限于：bool、int64、double、string、byte[]、及各类型数组。三条硬规则：默认必须先声明后使用（未声明即取 → 抛异常）；每个节点自带参数服务（/node/get_parameters 等隐藏 Service），外部可读写；修改可被校验回调拦截。定位一句话：节点级配置中心客户端——声明即 Schema、回调即准入校验、YAML 即配置仓。

2.13.2 声明、校验与热更新

要点：校验回调只负责准入；通过后把新值应用到运行时（如重建定时器）要自己做——与配置中心「校验 + 生效钩子」两段式完全一致。

2.13.3 YAML 参数文件与注入链

注入优先级链（高→低）：ros2 param set 运行时修改 > 启动参数 -p > --params-file > 代码默认值——Spring 外部化配置优先级的机器人版。运维 CLI 四件套：ros2 param list / get / set / dump（dump 导出现场配置快照，排障利器）。

2.13.4 与云端配置 OTA 的打通（第四篇预埋）

配置 OTA 的端侧落点就是 Parameter：云端配置中心下发 → 云桥调用目标节点参数服务批量 set → validate 回调即端侧准入校验 → 成功/失败回执上云 → 失败自动回滚到上一版参数文件。灰度、版本化、回滚全在云端做，端侧只暴露这一个标准面——你们配置中心的推拉模型原样映射。

2.13.5 与产业物联网平台的映射

Parameter 产业物联网 备注
declare + 默认值 配置 Schema 注册 未声明即拒绝
validate 回调 配置准入校验 两段式生效

2.13.6 企业实践建议

2.14 QoS 完全深解

2.14.1 全景：DDS 22 项，ROS2 暴露关键 8 项

DDS 标准定义 22 项 QoS 策略；ROS2 在 API 层暴露工程最常用的 8 项（下表），其余（Partition、Ownership、LatencyBudget、TransportPriority、ResourceLimits、TimeBasedFilter 等）可经各 DDS 实现的 XML 配置文件下钻——平台架构师知道「还有一层旋钮在 XML 里」即可。

2.14.2 逐项语义速查

策略 取值 语义 默认
History KEEP_LAST / KEEP_ALL 缓存策略：留最近 N 条 or 全留 KEEP_LAST
Depth 整数 KEEP_LAST 的 N 10
Reliability RELIABLE / BEST_EFFORT 丢包补发 or 尽力而为 RELIABLE
Durability VOLATILE / TRANSIENT_LOCAL 迟到订阅者能否补收发布端缓存 VOLATILE
Deadline 周期 相邻样本最大间隔契约，违约触发事件 不设
Lifespan 时长 样本过期自动作废（防吃老数据） 不设
Liveliness AUTOMATIC / MANUAL_BY_TOPIC 写者活性判定方式 AUTOMATIC
Lease Duration 时长 活性租约，超时判死并触发事件 不设

2.14.3 RxO 兼容矩阵（背下这张表）

策略 发布端提供 订阅端要求 结果
Reliability BEST_EFFORT RELIABLE ❌ 不连接
Reliability RELIABLE BEST_EFFORT ✅（按 BEST_EFFORT 收）
Durability VOLATILE TRANSIENT_LOCAL ❌ 不连接
Durability TRANSIENT_LOCAL VOLATILE ✅（不补历史）
Deadline 100ms 50ms（更严） ❌
Deadline 50ms 100ms ✅
Liveliness AUTOMATIC MANUAL（更严） ❌

规律一句话：订阅端的要求不得严于发布端的承诺——与「消费者 SLA 不能高于生产者 SLA」同一常识，只是违约表现为静默不连接。

system_default 跟随 DDS 实现默认 特殊互操作

2.14.5 QoS 事件：把契约违约接进告警

三类事件可注册回调：Incompatible QoS（匹配失败——终于不静默了）、Deadline Missed（数据断流）、Liveliness Lost/Changed（写者判死）。工程接法：回调里打 OTel 指标 + 结构化日志 → 现有告警管道。这等于把「数据链路 SLA 违约」做成了中间件原生事件——你在 MQTT 上用心跳 + 看门狗手工实现的那套，这里是标准件，白捡。

Launch 是 ROS2 的声明式启动编排系统：一个 Python（或 XML/YAML）文件描述「启动哪些节点、注入什么参数、如何重映射、按什么条件与顺序」，ros2 launch pkg xxx.launch.py 一条命令拉起全部。定位一句话：机器人的 docker-compose——你看到 DeclareLaunchArgument 就想 environment，看到 IncludeLaunchDescription 就想 compose 的多文件合并，心智全通。

2.17.2 核心构件与完整示例

四大构件对照记忆：DeclareLaunchArgument/LaunchConfiguration（可传参变量）≈ compose 变量替换；IncludeLaunchDescription ≈ 多文件组合（子系统各自维护 launch，顶层拼装）；IfCondition/UnlessCondition ≈ profiles 条件启用；GroupAction + PushRosNamespace ≈ 给一组服务统一加前缀。

2.17.5 企业实践建议

launch 文件分三层治理：组件层（各子系统自带）→ 机型层（拼装组件 + 机型参数）→ 站点层（站点差异仅以参数文件覆盖）。机型层与站点层由平台团队评审持有——与你们「基础镜像/机型配置/站点配置」三层完全同构，也是第四篇配置 OTA 的分发单元。

2.17.6 面试可能问什么

  1. Launch 的核心构件与设计思想？（要点：声明式、substitution 延迟求值、事件编排；compose 类比）
  2. 如何保证节点按依赖顺序就绪？（要点：Lifecycle + 状态迁移事件，而非 sleep 碰运气）
  3. 多机型多站点的 launch 如何治理？（要点：组件/机型/站点三层 + 参数覆盖）

2.17.7 最佳实践

  • 一切启动皆入 launch，禁止手工 ros2 run 上生产——启动方式即部署契约，必须可版本化。
  • launch 里只放拓扑与参数，不写业务逻辑；复杂条件逻辑下沉到节点的 Lifecycle 回调。

2.17.8 常见误区

  • ❌ 用 TimerAction 延时来「等依赖就绪」——sleep 编排是启动竞态的遮羞布，用 Lifecycle 事件。
  • ❌ 参数散落在 launch 内联字典里——机型/站点差异全部走 YAML 文件，内联仅限固定值。

2.17.9 Obsidian 永久笔记

  • Launch 即 compose：声明式编排 + 变量替换 + 多文件组合。
  • 三层 launch 治理：组件层 / 机型层 / 站点层，平台持有后两层。
  • 用事件不用 sleep：Lifecycle 迁移事件驱动依赖启动。

2.18 Namespace：命名空间规划

2.18.1 作用域机制

三种名字解析：全局 /foo（绝对）、相对 foo（拼上节点所在命名空间）、私有 ~/foo（拼成 /ns/node_name/foo）。规范建议：代码里一律写相对名与私有名，绝对名只出现在 launch/remap 层——与「代码不写死环境地址、部署层注入」同一纪律。

2.18.2 多机器人隔离：Namespace 还是 Domain ID

判据 用 Namespace（同 Domain） 用 Domain ID
机器人间要协同/互相订阅 ✅ 必选 ❌ 互相不可见
完全独立、只求不串台 可以但发现开销共担 ✅ 更省更稳
单网段机器人数量 少量协同机群 数量多时按组分域

生产常态是混合：一个作业区一个 Domain，区内每台机器人一个 Namespace（/robot_007/...）——与「一个租户 VPC 内按设备前缀分主题」同构。

2.18.3 三级命名规范（本书统一约定）

/<robot_id>/<subsystem>/<resource>，例如 /robot_007/telemetry/battery、/robot_007/nav/cmd_vel。云桥上云时把这棵树直接映射为 MQTT 主题树/Kafka key——端云同一棵命名树，翻译层零心智负担。

2.18.4 与产业物联网平台的映射

Namespace 树 ≈ MQTT 主题规划树；PushRosNamespace ≈ 网关统一加设备前缀；私有名 ~ ≈ 实例内部主题约定。

2.18.5 企业实践建议

命名规范进《DDS 基线规范》附录并配 CI 检查（禁止裸全局名上生产）；robot_id 由设备管理系统统一签发，与证书 CN 一致——命名即身份的前奏（第九篇安全深化）。

2.18.6 面试可能问什么

  1. 三种名字解析规则？（要点：全局/相对/私有；代码写相对、部署层定绝对）
  2. 多机器人隔离方案选型？（要点：协同需求定 Namespace vs Domain，混合是常态）

2.18.7 最佳实践

  • 端云共用一棵命名树，云桥做纯前缀翻译。
  • robot_id 进 Namespace 而不是编码进话题名尾巴——树形结构才能整组授权与统计。

2.18.8 常见误区

  • ❌ 代码里写死 /robot_007/... 绝对名——换机即改码；交给 launch 注入。
  • ❌ 用 Namespace 当安全边界——它只是命名隔离，安全靠 DDS-Security/SROS2（第九篇）。

2.18.9 Obsidian 永久笔记

  • 三级命名树：/robot_id/subsystem/resource，端云同树。
  • 命名不是安全：Namespace 只做隔离与组织，鉴权另有体系。

2.19 TF：坐标变换树（运动学最小常识在此补齐）

2.19.1 为什么需要 TF

机器人是一台「行走的坐标系森林」：相机看到目标在相机系下是 (0.3, 0.1, 1.2)，机械臂要在基座系下规划，导航要在地图系下定位——任意两个坐标系间的换算需求无处不在，且机器人一动变换就变。TF（tf2 库）把全部坐标系组织成一棵随时间演化的树，任何节点广播自己负责的一段「父→子」变换，任何节点可查询「任意两帧在任意时刻」的复合变换——分布式维护、全局可查、带时间维度。

【映射 🚗→🤖】你其实见过退化版：车端「车体坐标 → 大地坐标」的换算与传感器安装标定。区别在于车只有一两级变换，机器人是一棵几十节点的树，于是需要一个中间件级方案。

2.19.2 核心概念与标准帧链（REP-105）

flowchart TD
  MAP["map（全局地图系：定位模块维护，允许跳变）"] --> ODOM["odom（里程计系：连续平滑，会漂移）"]
  ODOM --> BASE["base_link（机体系：机器人本体原点）"]
  BASE --> CAM[camera_link]
  BASE --> LIDAR[lidar_link]
  BASE --> ARMB[arm_base_link]
  ARMB --> L1[link_1]
  L1 --> L2[link_2]
  L2 --> EE["gripper（末端执行器）"]

背下这条链的分工：map→odom 由定位维护（修正漂移，允许小跳变）；odom→base_link 由里程计维护（高频连续，绝不跳变）；base_link 以下是结构安装关系（多为静态标定）。数据载体是 geometry_msgs/TransformStamped，经 /tf（动态）与 /tf_static（静态，TRANSIENT_LOCAL「粘滞」话题——2.14 配方的实战应用）广播。

2.19.3 广播与查询（含时间旅行）

时间旅行是 TF 的灵魂：图像是 80ms 前拍的，机器人已经动了——必须用图像时间戳时刻的变换来换算，否则目标位置系统性偏移。tf2 的 Buffer 缓存近期变换历史（默认 10 秒）供插值查询。这也解释了 2.9.10 的铁律：消息必须带 Header 时间戳。

2.19.4 URDF 与 robot_state_publisher

机器人结构用 URDF（XML）描述：link（刚体）+ joint（关节：类型/轴/限位）。标准套路：joint_state_publisher/驱动器发 /joint_states（各关节角）→ robot_state_publisher 读 URDF + 关节角 → 自动广播整棵 base_link 以下的 TF。你不需要会写 URDF，需要会读：看懂 link/joint 树 = 达成 L1 验收（1.8.4）。

2.19.5 运动学最小常识（平台架构师版，三句话）

其一，关节空间 vs 任务空间：前者是各关节角度向量，后者是末端在笛卡尔坐标的位姿——控制器在两者间换算。其二，正运动学 FK：给关节角算末端位姿（唯一解，TF 树本质上就在做这件事）。其三，逆运动学 IK：给末端目标位姿反解关节角（可能多解/无解，由规划库如 MoveIt 负责）。到此为止——更深属于控制岗，平台岗有这三句足以读懂一切接口文档。

2.19.6 与产业物联网平台的映射

TF 产业物联网 备注
TF 树 传感器安装标定 + 车体/大地换算（树形化） 分布式维护全局可查
/tf_static 标定参数下发（粘滞） TRANSIENT_LOCAL 实战
时间旅行查询 多传感器时间对齐 Header 时间戳是生命线
URDF 整车 DBC + 安装位说明书 结构即配置

2.19.7 企业实践建议

把「TF 树快照 + URDF 版本」纳入发版制品与数字孪生：云端渲染机器人姿态、诊断回放、仿真对齐全靠它们——TF/URDF 就是机器人的「结构数字资产」，平台团队要像管标定参数一样管理其版本与分发。

2.19.8 面试可能问什么

  1. map/odom/base_link 三帧的分工与维护者？（要点：定位修偏/里程计连续/结构安装三段论）
  2. 为什么查变换要传数据时间戳？（要点：时间旅行、运动补偿、Buffer 插值）
  3. robot_state_publisher 做什么？（要点：URDF + joint_states → 自动广播结构 TF）

2.19.9 最佳实践

  • 一帧只能有一个父亲（树不是图）：两个模块争发同一段变换是经典事故，用 tf2_tools view_frames 巡检。
  • 静态标定全部走 /tf_static + 标定文件版本化，禁止节点各自硬编码安装偏移。

2.19.10 常见误区

  • ❌ 用「最新变换」处理带时间戳的传感数据——高速运动下系统性偏移的头号来源。
  • ❌ 以为平台岗要推 IK 公式——会读 URDF、懂三句运动学、能查 TF 就达标。

2.19.11 Obsidian 永久笔记

  • REP105 帧链：map→odom→base_link，定位修偏/里程计连续/结构静态。
  • TF 时间旅行：按数据时间戳查变换，Buffer 缓存插值。
  • 运动学三句话：关节空间与任务空间、FK 唯一、IK 多解归规划库。

2.20 Clock：时间体系与仿真时间

2.20.1 三种时间源

时间 语义 用途
ROS Time 默认=系统时间；use_sim_time=true 时跟随 /clock 话题 一切业务时间戳
System Time 墙钟 日志对外对时
Steady Time 单调递增不可回拨 测耗时/超时

2.20.2 /clock 与 use_sim_time：让时间可控

仿真器或 Bag 回放以发布 /clock 的方式接管全系统时间；所有节点设参数 use_sim_time=true 即整齐切换。价值：回放可倍速/暂停/单步，仿真可比真实更快，而所有基于 ROS Time 的定时器、TF 查询、超时逻辑全部自洽。这是「时间也被依赖注入」——你写单测时 mock Clock 的思想，被做成了全系统开关。

2.20.3 与产业物联网平台的映射

use_sim_time ≈ 测试环境的可控时钟/回放对时；/clock ≈ 统一授时源；Steady vs System ≈ 你在 JVM 里 nanoTime 与 currentTimeMillis 的分工。跨机真实对时仍靠 NTP/PTP（chrony），机群数据对齐依赖它——与车队数据对齐同一课题。

2.20.4 企业实践建议

平台规范两条：业务代码一律 node.get_clock()（不许直接 time.time()，否则仿真/回放全失效）；机群统一 chrony 对时并把时钟偏移作为遥测指标上云告警。

2.20.5 面试可能问什么

  1. use_sim_time 的机制与价值？（要点：/clock 接管、回放倍速、全系统时间自洽）
  2. 测耗时用哪种时间？（要点：Steady，防回拨）

2.20.6 最佳实践

  • 定时器、超时、TF 全走 ROS Time；性能打点走 Steady——两条线永不混用。

2.20.7 常见误区

  • ❌ 节点里 time.time() 打业务时间戳——bag 回放与仿真下时间线立刻分裂。

2.20.8 Obsidian 永久笔记

  • 时间也被依赖注入：use_sim_time + /clock 让全系统时间可控。
  • 两条时间线：业务用 ROS Time，测耗时用 Steady。

2.21 Bag：机器人的黑匣子（≈ CAN 日志 + 影子回传）

2.21.1 定义与三大用途

rosbag2 按原始序列化格式（CDR）把任意话题流落盘，并可按原时序回放。三大用途：事故复现与调试（回放当时全部数据流）、数据闭环原料（训练数据的源头，第七篇主角）、回归测试（固定输入跑算法对比输出）。定位 = 你的 CAN 黑匣子日志 + 影子模式回传数据的合体，而且回放即重演——这是产业物联网日志做不到的杀手能力。

2.21.2 存储格式：MCAP（Jazzy 默认）

早期默认 sqlite3，自 Iron 起默认 MCAP：自描述（schema 内嵌）、追加友好、带索引、支持 zstd/lz4 压缩、工具生态开放（Foxglove 可直接可视化）。类比：从「私有日志格式」升级为「带 Schema 的开放容器格式」——好比你们把私有信号日志迁到 Parquet/Iceberg 的动机，机器人行业用 MCAP 提前收敛了。

2.21.3 CLI 实战

--clock 让回放进程发布 /clock，配合全体节点 use_sim_time=true（2.20），整个系统在「录制时刻的时间线」里重演——TF 时间旅行、超时逻辑全部自洽。回放老数据遇 QoS 不匹配用 --qos-profile-overrides-path 覆盖。

2.21.4 触发式录制与数据闭环（第七篇预埋）

全量 7×24 录制在带宽与存储上不可行（一台机器人的原始传感器流轻松日产 TB 级）。生产模式是触发式：

flowchart LR
  T[全话题流] --> RB["环形内存缓冲（rosbag2 snapshot 模式）"]
  RB --> TR["触发条件：错误码 / 人工干预 / 模型低置信度"]
  TR --> CL["边缘裁剪与脱敏（前后N秒、白名单话题）"]
  CL --> UP["回传对象存储 MinIO/S3"]
  UP --> IDX["云端数据引擎索引（第七篇）"]
  IDX --> RP["回放复现 / 训练 / 评测"]

rosbag2 内建 snapshot 模式（环形缓冲、服务触发落盘）就是这套玩法的端侧原语。【映射 🚗→🤖】这整条链 = 影子模式触发回传 + TBox 日志上传的机器人版；你在 AIDO 做过的「故障前后 N 秒 CAN 日志抓取」，把 CAN 换成 bag 即可整体平移。

2.21.5 与产业物联网平台的映射

Bag 产业物联网 备注
ros2 bag record CAN/信号日志落盘 多了完整重演能力
snapshot 触发录制 故障前后 N 秒抓取 AIDO 同款模式
MCAP Parquet 化的开放日志格式 Schema 内嵌
play –clock 台架回放对时 时间线整体重演

2.21.6 企业实践建议

制定《数据录制策略表》：按话题白名单 × 触发条件 × 保留时长 × 脱敏规则四维定义，由平台下发为配置（Parameter/配置 OTA），端侧只执行——把「录什么」从工程师手感升级为平台治理对象，这是数据飞轮质量的第一道闸门。

2.21.7 面试可能问什么

  1. rosbag2 的格式演进与 MCAP 优势？（要点：自描述/索引/压缩/生态；对齐开放数据格式趋势）
  2. 如何设计生产环境的录制策略？（要点：环形缓冲 + 触发式 + 裁剪脱敏 + 分片压缩回传）
  3. 回放为什么要 –clock + use_sim_time？（要点：时间线整体重演，TF 与超时自洽）

2.21.8 最佳实践

  • 录制永远包含 /tf /tf_static 与相关 Header 话题——没有变换与时间戳的传感数据是「死数据」。
  • Bag 文件名嵌 robot_id + 时间 + 触发原因，对象存储按此分区——检索效率在命名时就决定了。

2.21.9 常见误区

  • ❌ 全量长时录制当保险——存储带宽账算不过来，触发式才是生产形态。
  • ❌ 回放不接管时钟裸放——所有超时与 TF 查询在「现在」的时间线上错乱，复现失真。

2.21.10 Obsidian 永久笔记

  • Bag 即黑匣子且可重演：录制=CAN 日志，回放=时间线重演。
  • 触发式录制链：环形缓冲→触发→裁剪脱敏→回传→索引。
  • 录制策略是平台治理对象：白名单×触发×保留×脱敏四维配置化。

2.22 Component / Composition / Plugin：部署形态与扩展机制

2.22.1 Component：可动态装载的节点

Component 是编译成共享库的节点（rclcpp 类 + 注册宏 RCLCPP_COMPONENTS_REGISTER_NODE(ns::ClassName)），运行时装进通用容器进程 component_container。注意边界：组合是 rclcpp（C++）特性，rclpy 不支持——由此形成标准分工：性能敏感链路用 C++ 组件化，云桥/工具/编排类节点用 Python 独立进程，恰好贴合你的语言栈。

2.22.2 三种组合方式

① 手写 main 里塞多个节点（写死，少用）；② 运行时动态：ros2 run rclcpp_components component_container + ros2 component load /ComponentManager my_pkg ns::MyNode（调试利器，可 list/unload）；③ Launch 静态声明（生产标准）：ComposableNodeContainer + ComposableNode(extra_arguments=[{'use_intra_process_comms': True}])。容器有三款：单线程、多线程（_mt）、隔离执行器（_isolated），对应 2.6 的 Executor 选型。

高频大消息链路（相机→感知→跟踪） ✅ 零拷贝收益巨大 序列化税沉重
故障域需隔离（云桥/OTA agent/记录器） 一崩全崩 ❌ ✅
需独立重启/独立升级 ❌ ✅
资源受限端侧要省内存 ✅ 共享进程开销 每进程一份开销

这就是「微服务拆分 vs 合并」的老决策换了名词，评审话术都不用换：按链路流量与故障域切，不按组织架构切。

2.22.4 Plugin（pluginlib）：算法即插件

pluginlib 提供「基类接口 + 实现类共享库 + plugins.xml 声明 → 运行时按名装载」的插件机制（PLUGINLIB_EXPORT_CLASS(ns::Impl, ns::Base)）。Nav2 的规划器/控制器、RViz 的显示项全是 pluginlib 插件。≈ Java SPI/策略模式的动态装载版。平台视角的价值：算法成为可独立分发的制品——第四篇 OTA 体系里除固件、模型、配置之外的第四种载荷「算法插件包」由此而来。

2.25.2 第二篇十五条核心结论

  1. ROS2 = 「rclpy/rclcpp → rcl → rmw → DDS」五层；排障先定位层。
  2. DDS 以数据为中心：强类型 + QoS 契约 + 去中心发现，是 1kHz 世界的通信基座。
  3. 发现两阶段 SPDP/SEDP；RxO 违约静默不连——一切「收不到」先查 QoS。
  4. 机内 DDS、云上 MQTT，云桥即 TBox——双平面架构与整车同构。
  5. Graph 由发现涌现，无中心账本；契约快照进 CI。
  6. Node 即微服务：单一职责、外部化配置、优雅退出。
  7. Executor 即事件循环：慢回调饿死节点；回调内同步等待是头号死锁。
  8. Topic/Service/Action 选型两问：流式吗？超一秒且需进度/取消吗？
  9. 消息 Schema 即接口：标准库优先、接口仓集中、变更评审。
  10. Action 与 OTA 任务逐字段同构——你已经手工实现过它。
  11. Lifecycle 给节点 readiness 语义；被云端编排的节点必须实现。
  12. Parameter 是配置 OTA 的唯一端侧落点：声明即 Schema、校验即准入。
  13. QoS 治理三件套：白名单 Profile、契约快照、QoS 事件接告警。
  14. TF 三帧分工 + 时间旅行；Bag 触发式录制链是数据飞轮的端侧起点。
  15. Launch 三层治理 + Composition 决策表 + overlay 三层——部署形态皆是平台治理对象。
