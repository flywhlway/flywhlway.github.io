A 篇 · 深水区

A1 · Web/Host 全栈：Typert Remote RPC 与双半插件

第一卷把 packages/client（36 个包）、packages/host、packages/api、packages/typert 概括为”Web 表层”。实际上这里有一套独立于 agent 内核的、值得单独学习的全栈类型安全 RPC 架构。

A1.1 双半插件（dual-half plugin）模型

dsh 的 Web 插件不是”前端包 + 后端包”两个 npm 包，而是同一个包的两个面：

为什么这样设计？ 因为一个 UI 功能天然横跨两侧：ui-jobs 需要 Host 侧读 ctx.jobs 注册表 + 浏览器侧渲染任务列表。拆成两个包会让版本、依赖和生命周期永远对不齐。

A1.2 window.__DSH_BOOT__ —— 唯一的协议真源

关键设计点（都值得抄）：

  1. 图是 Node 半与浏览器半之间协议层的唯一真源——宿主组合出行，作为 <head> 中的第一个脚本注入，< 已转义，因此插件可控的字符串无法逃出 script 元素
  2. 没有有效 manifest 的页面无法启动——浏览器侧解析器在图缺失或畸形时大声抛错，而不是降级
  3. entries 顺序无语义——激活顺序完全由 fiber 的 inject 等待决定。这从根上消灭了”前端插件加载顺序”这类经典脆弱性
  4. 双层 rev：行的 rev 是该 bundle 的内容哈希（作为 URL 查询参数使缓存失效）；图的 rev 对全部行做哈希，因此任何一行变化都会改变它

A1.3 扫描的失败姿态是分裂的（这是最精妙的一处）

时机 畸形声明 / 缺失 bundle 的后果
激活趟（启动时） 聚合为一个大声的 AggregateError，列出每个损坏的包；fiber 进入 FAILED，由启动审计上报
稳态（运行中新增/变更） 只记录一条警告，且不得殃及其他包

为什么？ 启动时一个坏包意味着部署配置错了，必须立刻暴露；运行中一个坏包意味着某人正在开发调试，不该拖垮已经在跑的会话。同一条实现（脏集合 + 微任务 flush），两种失败姿态。

同时：包元数据按名缓存且永不过期——包括”非 client 包”这一否定结论。插件集合的变更在重启后生效。fiber 重启原样复用其行与 rev；bundle 内容变更只经 rebuilt() 到达图。

A1.4 Typert：跨 Host/Client 边界的类型安全调用

packages/typert 是一套编译器无关的 Remote 元数据体系。核心概念：

三条设计约束值得单独记住：

  1. InvocationDescriptor 是本地反射信息，不是 wire message。Host 与消费方各自构建彼此对应的 descriptor；请求只发送 endpoint 与具名 args。这意味着协议演进不需要同步部署两端的描述符——只需要保证 wire 字段兼容。

  2. 取消通过带外 carrier signal 表达：它在业务参数之后注入，绝不进入 args。这避免了”取消信号被序列化成业务参数”的经典污染。

  3. lookup resolver 卸载后，注册表仍保留其 wire 声明：

    “SRC 发现过程会继续把该参数归类为 lookup，并因不可用而失败，而不会把 wire 值当作普通业务对象接受。”

    这是一条安全性质的设计——服务下线不会让类型检查悄悄降级为”把裸字符串当对象用”。

两种 codec 模式：

模式 行为
strict 携带生成的 schema（typeSymbol + TypertSchema），完整校验
src-json 不恢复结构类型，只强制要求 JSON 安全值

Gateway 错误分类体系（TypertGatewayErrorCode）：ambiguous-endpoint / arguments-invalid / binding-invalid / context-failed / context-not-found / context-unavailable / definition-unavailable / input-invalid / invocation-unavailable / lookup-* 等。普通异常由 RPC 适配器归并为传输层 internal；lookup 策略通过 TypertLookupFailure 携带的既有 RPC error 原样返回——业务错误与基础设施错误严格分层。

A1.5 二开启示

如果你要给 dsh 加一个自己的 Web 功能面板：

必须注意： 包解析锚定在配置树的 ctx.baseUrl（cordis.yml 所在目录，该目录的包把每个被组合的插件声明为依赖）——这个锚点未设置时构造即抛错。所以自研 UI 插件必须作为 profile 的正式依赖安装，不能用 --patch 临时挂绝对路径。

A2 · 持久化深读：flush 检查点、崩溃恢复与冷读取阶梯

A2.1 flush 检查点：固定批处理窗口，不重置截止时间

“不重置截止时间”是关键——否则一个持续产事件的长轮次会让 flush 无限推迟。

失败处理姿态：

  • 后台写入被拒绝 → 保留对应事件并暂停自动重试
  • 新事件 → 开启新的固定窗口
  • 显式 session/flush → 立即重试
  • 失败通过 agent/error 和 logger 报告，绝不会把失败记录成已关闭轮次之后的会话事件

最后一条尤其重要：持久化失败不污染事件日志本身。日志的完整性优先于失败可见性。

配置的最大值只限制有意的批处理等待，不限制事件循环调度或后端完成持久化的延迟——这是一条诚实的 SLA 声明。

A2.2 崩溃恢复：不截断，用合成边界配平

后端重新加载一个在轮次中途崩溃的日志时，会发现一个已打开的 turn/start 却没有 turn/end。

它不会截断日志。 理由很实在：

“在长周期任务中，单个轮次可能非常庞大（许多步骤、大量工具输出），而这些事件在崩溃前已被持久追加。”

改为用一个合成的 turn/end { reason: { kind: 'interrupted' } } 关闭遗留轮次，在不改变其前后任何独立事件的情况下配平被中断的执行。

interrupted 是唯一一个不由循环发出的 TurnEndReason。

修复仅适用于冷会话：

情况 行为
冷会话 load(id) 提交合成修复
活跃 id load(id) 等待权威内存快照持久化，只在日志平衡时返回；活跃轮次未闭合则拒绝操作，而不是添加合成边界
HMR 接管活跃前缀，不关闭其中正在进行的轮次

A2.3 三个读取动词的分工

动词 行为
inspect(id) 构造不可变逻辑 Session 但不发布、不写入恢复内容。冷检查在内存中配平中断轮次，同时保持撕裂的物理尾部不变；检查已活跃的 Session 则借用其当前不可变快照（可能包含未闭合轮次）
prepare(id) 预留 Session、提交待处理修复、返回可 dispose 的发布句柄
load(id) 同样提交修复，但不发布 Session

使用协调器的实现会在有界 LRU 中保留这个精确的冷未发布 Session，因此重复历史读取与后续 prepare(id) 可复用同一次读取、解压、验证、冻结及 Session 构造。

A2.4 SessionHeader：与日志分开存储的元数据

为什么单独存？ 官方理由：格式版本、cwd、血统与 seed 边界是存储层关注点而非对话事件，因此不进入 SessionEventMap，也不会到达 deriveMessages()。

seedLength 这一条尤其值得学：持久化这个边界让 resume 和 replay 能区分父历史与子工作。

A2.5 SessionLocation：诚实的位置提示

JSONL 后端返回 transcript 绝对路径；SQLite 后端返回 undefined（各会话共享一个数据库）。

官方明确警告：返回的路径可能指向尚不存在的文件，或指向还不包含当前尚未 flush 轮次的文件。它是位置提示，不是授权或新鲜度保证。

这句话值得贴在任何”返回文件路径”的 API 上。

A3 · 会话投影：领域只写数学，框架负责驱动

ctx.sessionProjections 是一个被低估的机制——它解决的是”如何把日志派生状态高效推给 UI”这个通用问题。

A3.1 投影单元：三个纯同步函数

四条硬约束：

  1. 三个函数必须全部同步——异步单元会撕裂载体的一致性切面
  2. state 必须是纯 JSON——这是持久化缓存的前提
  3. 不感兴趣的事件必须返回同一个状态引用——Object.is 相等则产生零下游工作
  4. stateVersion 在序列化字段或折叠语义变化时递增——旧版本的持久 (sessionId, key, ver, seq, val) 行会被丢弃，而不是被向前应用成垃圾

A3.2 分工的精确边界

“框架负责驱动，领域负责计算：注册表只订阅一次 session/event，并把每个已提交事件折叠进每个单元；领域不持有任何订阅，客户端也从不折叠领域事件——它们收到的是成品值。”

这一句话把三方职责钉死了。对比常见做法（每个领域自己 subscribe、客户端自己 reduce），这个设计的收益是：

  • 只有一个订阅点 → 一致性切面天然对齐
  • 客户端不需要理解任何领域事件语义 → 协议面极小
  • 缓存可以在框架层统一实现 → 领域零成本获得持久化

A3.3 全量值规则

“携带状态的日志事件携带的是变更后的完整状态，绝不是裸增量——这让每次状态转移始终足够廉价，也让每个被供给的值自描述（对消费方即 last-wins）。”

这是 todo/write（整表快照）、goal/change（完整快照）等事件设计的统一理由。代价是事件体积，收益是回放逻辑近乎为零。

A3.4 冷读取阶梯（ctx.sessionProjectionCache）

结果：列表读取永远不需要加载完整日志。 检查点策略是”节流检查点 + 轮次/结束/分离时的必选检查点”。

对于会话数上千的部署，这是列表页能不能秒开的分水岭。

A4 · Workflow 引擎与 Ralph 循环

A4.1 Workflow seam 的定位

  • 不属于 agent loop 主干，是可选能力
  • 每个上下文只允许一个引擎——没有命名提供方注册表（第二个引擎通过插件配置替换第一个，而不与它同时运行）。这与 ctx.subagents 的多提供方形成对比
  • Service Definition：dsh-workflow；Provider：dsh-workflow-worker-thread；Consumer：dsh-tool-workflow、dsh-tool-ralph

A4.2 脚本 API（模型写的就是这个）

agent() 带 schema 时返回结构化值，否则返回最终文本；普通失败的子 agent 返回 null。

刻意不注入的东西：定时器、文件系统 API、Node 全局变量。

A4.3 隔离边界的诚实声明（这段值得完整引用）

“工作流脚本是模型编写的，与模型现有的 bash 访问权限有相同的信任前提。worker 内的 node:vm 是一种 API 塑形机制，不是安全边界：逃逸的脚本能以宿主进程的权限恢复 Node 能力。”

worker 提供的是这些收益：

收益 说明
CPU 隔离 脚本的同步自旋不占用宿主事件循环
真实终止 worker.terminate() 让 dispose 有一个真正的最终停止手段
环境清空 worker 以空环境启动（除未构建的 loader 管道），环境凭据不会通过 process.env 穿透
数据边界 Host/worker 消息用结构化克隆，脚本边界做纯 JSON 校验

“真正面向不可信脚本的沙箱需要在同一个 workflow seam 后面换一个不同的引擎。”

这是一个非常好的架构诚实性范例——明确区分”我提供了什么”和”我没提供什么”，而不是用”沙箱”这个词模糊过去。

A4.4 失败纪律：fatal 标志

理由：一个拼写错误的选项必须明确报错并终止脚本，绝不能消融为看似普通子 agent 失败的结果。

A4.5 run 序列（每次 agent() 调用）

竞态处理：provider 启动与已发布子 agent 分开跟踪。如果取消、worker 死亡或正常结算关闭了接纳窗口而某个 start 仍在途，共享信号会中止它；仍然兑现的 provider 由 Host dispose，永不告知 worker。

A4.6 Ralph 循环

Ralph 是”面向不可变目标的前台全新 agent 工作流“，作为普通插件建立在 ctx.workflowEngine + ctx.subagents 之上——没有往 agent-loop 里加任何 Ralph 模式。

核心约束：

  • 子 agent 不接收父会话或此前子会话的对话种子——工作区是长期记忆
  • provider 必须存在、支持结构化输出、且报告 inheritsParentContext: false
  • 配置的 provider 作为 WorkflowStartRequest.subagentProvider 携带，因此固定脚本无法检视或改变路由，普通 workflow 工具也不会因此获得 provider 选择器
  • 解析后的 Round 上限同时作为 maxTotalAgents 携带，与引擎的总子 agent 兜底协调
  • 无效、缺失或超大的报告会让 workflow 失败，而不是被截断或误认为上限耗尽
  • 普通子 agent 失败 → 报错并保留上一次成功交接；Ralph 不重试该轮

终端结果的措辞设计：complete/blocked 标签在 Native 渲染器中显式声明”这是某个 worker 报告的结果，不是独立认证”。这种措辞纪律在 agent 系统里非常必要——避免把子 agent 的自我报告当成客观事实。
