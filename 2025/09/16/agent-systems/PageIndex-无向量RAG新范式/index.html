PageIndex：无向量、推理驱动的长文档检索

从向量 RAG 在财报、法规等长文档上的失败模式出发，按 PageIndex 仓库源码拆解树索引生成与推理式树搜索…

Flywhl 16 分钟 更新于 2026.09 #MCP#Agent#RAG

先读结论

  1. PageIndex 用 LLM 为文档生成带页码的目录树，检索时让 LLM 读树选节点，再按页码取原文；不需要向量库，也不切块。
  2. 它把成本从查询端的向量计算挪到了 LLM：建树时整本文档至少过一遍模型，每次查询要把整棵树放进上下文。
  3. 适合结构清晰、单篇很长、问题需要跨章节推理的专业文档；不适合海量短文档、高并发低延迟和无文字层的扫描件。
  4. 2025-09 的开源仓库只负责建树，检索逻辑需要自己写或使用云端 API；MCP 服务以云端能力为基础。

向量 RAG 在长篇专业文档上的失败模式

向量 RAG 的默认流程是“固定长度切块 → 向量化 → 取 top-k 相似块”。在客服 FAQ、短文章上它足够好用，但放到几百页的年报、监管文件、技术手册上，会稳定地出现下面几类问题：

失败模式 典型表现 根因
相似不等于相关 问“研发投入同比变化”，召回的是风险因素里一段措辞相近的描述，而不是财务报表附注 向量只衡量语义距离，不理解“哪一节才是口径正确的出处”
切块割裂上下文 表头和数据行分在两个块；条款的例外情形在下一个块 块边界由长度决定，不由文档结构决定
文内引用断链 “详见附注 12”“参见 1.2 节”无法顺着找过去 引用语句与目标内容在语义上并不相似
结构性问题答不了 “第三章列了哪些风险”“这份文件分几部分” 答案在目录结构里，不在任何单个块里
同模板文档互相干扰 多个年度的年报格式一致，召回混入其他年份 向量几乎相同，只能靠元数据区分
检索过程不可解释 只能看到一串相似度分数 没有“为什么选这里”的推理记录

这些问题的共性是：专业文档的结构本身就是检索线索，而切块 + 向量把结构丢掉了。人类专家读年报的方式是先看目录、定位章节、读完再判断是否需要翻到附注，PageIndex 就是把这个过程交给 LLM。

PageIndex 是什么

PageIndex 由 Vectify AI 开源，GitHub 仓库 VectifyAI/PageIndex 创建于 2025-04-01，MIT 许可；PyPI 上的 pageindex 包更早（0.1.0 发布于 2025-03-12），它是云端 API 的 Python SDK，写作时最新为 0.1.8（2025-08-26）。README 把它概括为两步：

  1. 为文档生成一棵“目录式”的树状索引；
  2. 用 LLM 在树上做推理式搜索，找到相关节点。

仓库 README 引用了其金融文档问答系统 Mafin 2.5 在 FinanceBench 上 98.7% 准确率的结果。这是厂商基于自有系统公布的数字，系统还包含 PageIndex 之外的组件，应理解为方向性证据，而不是开源仓库可直接复现的指标。

以下原理部分依据仓库 2025-09-03 的代码（提交 42382bd）整理。

原理一：树索引怎么生成

生成流程

flowchart TD
    A[PDF 逐页抽取文本<br/>PyPDF2，按页计 token] --> B{前 20 页逐页判断<br/>是否为目录页}
    B -->|有目录且带页码| C1[解析目录<br/>计算印刷页码与物理页码偏移]
    B -->|有目录无页码| C2[按目录标题在正文中定位页码]
    B -->|无目录| C3[正文按 2 万 token 分组<br/>由 LLM 逐组生成目录]
    C1 --> V[校验：每个标题是否<br/>出现在声称的页上]
    C2 --> V
    C3 --> V
    V -->|准确率 100%| T[组装树]
    V -->|高于 60%| F[修正错误条目<br/>最多 3 轮] --> T
    V -->|不高于 60%| D[降级到下一种模式<br/>无目录模式也失败则报错]
    D --> C2
    D --> C3
    T --> L[页数超过 10 且 token 达到 2 万的节点<br/>递归细分为子节点]
    L --> S[写入 node_id、节点摘要<br/>可选文档描述]

几个关键点：

  • 三种模式逐级降级。优先利用文档自带的目录；目录不可靠时退化为“按标题找页”；再不行就让 LLM 通读全文自己编目录。每一级都要通过“标题是否真的出现在那一页”的校验，校验本身也是 LLM 调用。
  • 大节点递归细分。一个章节页数超过 max_page_num_each_node（默认 10）且 token 数达到 max_token_num_each_node（默认 20000）时，对这一段再跑一遍无目录模式，生成子节点。
  • 节点摘要用全文生成。开启摘要时，每个节点的完整正文都会送给 LLM 生成一段描述，所有节点并发执行。

树有多大

树需要整体放进 LLM 上下文，所以体积直接决定每次查询的成本。用 tiktoken（gpt-4o 对应的 o200k_base 编码）统计仓库 tests/results 里的四个示例：

示例文档 页数 节点数 最大深度 含摘要 树的 token 数
美联储 2023 年报 222 76 3 否 约 2.7K
PRML 教材 758 286 3 否 约 9.1K
某公司季度财报（q1-fy25-earnings） 22 41 3 是 约 9.9K
监管解释性文件（Regulation Best Interest） 28 9 2 是 约 2.2K

结论很直接：摘要是树体积的主要来源。一份 22 页、带摘要的财报，树的体积和 758 页、不带摘要的教材相当。摘要能显著提升 LLM 选节点的准确度，但要按文档规模权衡是否开启，或者只给上层节点加摘要。

原理二：推理式树搜索

开源仓库只负责建树，检索要自己实现。官方 tree-search 教程给出的基本做法是一次 LLM 调用：把问题和去掉正文的树交给模型，要求返回 JSON 格式的推理过程和节点 ID 列表，然后按 ID 取回节点正文，再生成答案。教程也说明，其云端检索 API 使用的是“LLM 树搜索 + 基于价值函数的蒙特卡洛树搜索（MCTS）”的组合，细节当时尚未公开。

这种方式带来两个向量检索没有的能力：

  • 检索过程可读。模型返回的 thinking 说明了为什么选这些节点，出错时能直接看出是理解错了问题还是目录本身有问题。
  • 专家知识直接写进提示词。教程的例子是“问题涉及 EBITDA 调整时，优先看 10-K 的 Item 7 与 Item 8 附注”。在向量 RAG 里做同样的事，往往要微调 embedding 模型或额外加重排规则。

多文档场景下，PageIndex 当时默认只在单文档内检索。官方 doc-search 教程给出三种先选文档、再做树搜索的策略：按元数据筛选、按语义检索文档、按文档描述让 LLM 选择（适合文档数量少的情况）。

优缺点与成本、延迟权衡

维度 PageIndex 的表现 说明
检索准确性 结构清晰的长文档上明显占优 取回的是完整章节，不存在切块割裂
可解释性 强 有推理文字和页码范围，便于审计
建索引成本 高 前 20 页逐页调用 LLM 判断是否为目录页；无目录模式下全文按 2 万 token 分组逐组送入 LLM；每个目录条目的页码校验各一次调用；摘要又把各节点全文送一遍。粗略看，整本文档至少要过 1～2 遍模型
查询延迟 秒级 每次查询至少一次读整棵树的 LLM 调用，再加答案生成；向量检索是毫秒级
查询成本 与树的大小成正比 上表中 2K～10K token 的树，每次查询都要付这部分输入
更新代价 以文档为单位重建 改了一页也要重新建树；对“一次写入、反复查询”的归档文档影响不大
扩展性 单文档内优秀，跨大量文档需要外层先选文档 不能像向量库一样直接在百万块上检索
基础设施 不需要向量库 树就是一个 JSON 文件，存对象存储或数据库即可

适合 PageIndex 的成本结构是：文档数量有限、单篇很长、查询频率不高但对准确性要求高。典型如投研、审计、合规审查、法律尽调，一次答错的代价远高于一次多花几秒和几分钱。

开源仓库：本地建树

run_pageindex.py 的参数及默认值（以代码中的 argparse 为准）：

参数 默认值 作用
--model gpt-4o-2024-11-20 建树与摘要使用的模型
--toc-check-pages 20 在前多少页里找目录
--max-pages-per-node 10 节点超过该页数（且 token 超限）时细分

--if-add-node-text no 在节点中保留正文

这一版本代码的边界条件，都能在源码中找到对应位置：

  • 只读文字层。PDF 文本由 PyPDF2 的 extract_text() 提取，扫描件没有文字层时，建出来的树没有意义。仓库 README 也说明它面向“简单 PDF”，复杂版面建议先用其云端 OCR 转成 Markdown。
  • 绑定 OpenAI 模型名。LLM 调用写死了 OpenAI 客户端（可通过 OPENAI_BASE_URL 指向兼容服务），但 token 计数用 tiktoken.encoding_for_model(model)。实测 qwen-plus、deepseek-chat 这类名称会抛 KeyError，文档没有目录、走到按页计数的分支时就会失败。
  • 失败不抛异常。LLM 调用重试 10 次仍失败时返回字符串 "Error"，节点摘要可能就是这五个字母；三种模式全部校验失败时才抛 Exception('Processing failed')。
  • 包名冲突。仓库里的 pageindex/ 目录与 PyPI 上的 SDK 同名。在仓库根目录运行 SDK 代码，from pageindex import PageIndexClient 导入的是本地目录（实测直接报缺少 tiktoken），两者要放在不同工程或虚拟环境里。

单次树搜索的主要失败方式是模型选了过大的父节点。上面用页数上限直接拒绝，更完整的做法是两段式：先只给模型看前两层，选中章节后再展开该章节的子树做第二次选择，树越大收益越明显。

与向量 RAG、GraphRAG 的对比

维度 向量 RAG GraphRAG（微软，2024） PageIndex
索引单元 固定长度的块 实体、关系、社区摘要 文档自身的章节树
建索引成本 低（只算 embedding） 很高（LLM 抽取实体关系并逐层生成社区摘要） 高（LLM 识别目录、校验、生成摘要）
查询延迟 毫秒级检索 + 一次生成 本地搜索较快，全局搜索需汇总大量社区摘要 秒级，至少两次 LLM 调用
检索依据 语义相似度 实体关联与社区归纳 LLM 对目录结构的推理
擅长的问题 事实型、措辞接近的问题 跨大量文档的全局性、主题性问题 单篇长文档内需要定位与跨章节推理的问题
规模 百万级块 语料级，但成本随语料线性上升 单文档内最佳，多文档要先选文档
可解释性 弱（分数） 中（可追溯实体与社区） 强（推理文字 + 页码）
对文档结构的依赖 无 低 高，没有清晰层级时优势消失
基础设施 向量库 图存储或 Parquet 文件 + 向量库 一个 JSON 文件

三者并不互斥。常见组合是：向量或元数据检索先从文档库里选出候选文档，PageIndex 在单篇文档内做精确定位；GraphRAG 用在“整个语料说了什么”这类全局问题上。

适用场景判断清单

优先考虑 PageIndex：

  • 单篇文档在几十页以上，并且有清晰的章节层级（年报、招股书、法规、标准、教材、设备手册）。
  • 问题需要“先找到哪一节，再读完整一节”，或者涉及附注、附录的交叉引用。
  • 答案需要附带页码出处，便于人工复核或审计。
  • 查询量不大（人工分析场景），可以接受秒级延迟和每次几千到一万 token 的额外输入。
  • 文档是“一次写入、反复查询”的归档材料，重建频率低。

不适合或需要搭配其他方案：

  • 海量短文档（工单、聊天记录、商品描述）：没有可利用的结构，向量或全文检索更合适。
  • 高并发在线问答，要求百毫秒级响应。
  • 扫描件且不能使用云端 OCR：先解决文字层，否则树建不起来。
  • 文档频繁局部修改，需要分钟级同步。
  • 问题是跨整个语料的归纳（“今年所有合同的共性风险”）：用 GraphRAG 或先做结构化抽取。

与 Agent 结合：MCP

2025-08-25 创建的 VectifyAI/pageindex-mcp 把云端能力封装成 MCP server，2025-09-15 发布的 1.3.0 加入了 OAuth 2.1 认证。两种接入方式：

实际使用时二选一。本地方式需要 Node.js 18 以上，首次运行会打开浏览器完成 OAuth 授权，支持上传本机 PDF；远程方式由 MCP 客户端处理 OAuth，只能通过 URL 提交 PDF。不支持 HTTP 传输的客户端可以用 mcp-remote 桥接。Claude Desktop 还可以直接安装它发布的 .dxt 扩展。

暴露给 Agent 的工具：

工具 作用 关键参数
process_document 上传本地 PDF 或提交 URL，执行 OCR 与建树 url（本地路径或 URL）
recent_documents 最近处理的文档及状态 limit
get_document 单个文档信息与状态 doc_id
get_document_structure 读取树结构，可控制深度 doc_id、max_depth（1–10）
get_page_content 读取指定页内容 doc_id、pages（如 "5"、"3-7"、"1,5,10"）
remove_document 永久删除文档及相关数据 doc_ids

这组工具的设计本身就体现了“推理式检索”：没有 search(query, top_k)，Agent 需要先用 get_document_structure 看目录，自己判断要读哪几页，再用 get_page_content 取原文，读完不够再回到目录。接入时有两点建议：

  • 先浅后深。max_depth 从 2 开始，定位到章节后再加深，避免一次把整棵树塞进上下文。
  • 收紧危险工具。remove_document 是不可恢复的删除，在 Agent 的工具白名单里默认去掉，或者要求人工确认。

不想把文档交给云端时，可以把上文的 tree_search 和 node_content 包装成自己 Agent 框架里的两个工具（读目录、按页取文），本地建树 + 本地检索，行为与 MCP 版本一致。

2026-09 补记：SDK 双模式与后续变化

以下按 2026-09-28 的 PyPI 与 GitHub 信息核对。

  • SDK 支持 local mode。pageindex 在 2026-08-13 的 0.2.10.dev1 首次加入本地模式，正式版 0.2.10 发布于 2026-08-19。PageIndexClient(api_key=...) 走云端；不传 api_key 时进入本地模式，用开源流水线和你自己的模型密钥建索引，数据默认存放在 ./.pageindex；也可以用 PageIndexCloudClient、PageIndexLocalClient 显式固定模式。本地模式的模型调用改为经由 LiteLLM 路由，token 计数也改用 litellm.token_counter，上文“本地代码绑定 OpenAI 模型名”的问题在 SDK 本地模式下不再存在；本地模式只支持 PDF，建索引是同步的。
  • 检索 API 标注弃用。0.2.10 中 submit_query、get_retrieval 注明为仅云端可用，且云端已将其标记为弃用，推荐改用 chat_completions。上文 0.1.8 的云端检索写法仍可作为理解接口的参考，新项目应按新接口实现。
  • Agent 集成内置化。0.2.10 提供 as_openai_tools、as_anthropic_tools、as_claude_mcp 等方法，以及 OpenAI Agents SDK、Anthropic SDK、Claude Agent SDK 的集成模块，不必再手写工具包装。
  • 规模与热度。README 新增了面向海量文档的 “PageIndex File System” 介绍和对话平台入口；仓库在 2026-09-28 约有 3.6 万 star，SDK 最新版本为同日发布的 0.2.20。
