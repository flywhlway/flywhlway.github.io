云管端 AI Agent 组件分析与选型决策

把八个组件族压缩为选型决策：每族先列必须回答的问题，再按适用条件、代价与退出成本比较候选。先锁定协议、Trace、记忆与 Embedding 等不可逆点，引擎与框架保持可替换。

Flywhl 14 分钟 发布于 2025.09 #云管端#架构设计

先读结论

  1. 选型看三列：适用条件、代价、退出成本；退出成本决定是现在必须选对，还是先用着再换。
  2. 难换的是协议与数据格式（MCP/A2A、Trace Schema、记忆模型、Embedding 版本），不是推理引擎与框架。
  3. 编排默认外层 Workflow 加内层 Agent；检索从混合检索加 Rerank 起步，图增强要由评测集证明。
  4. MCP 远程接入自 2025-03-26 版规范起走 Streamable HTTP，不要再按 HTTP+SSE 双端点实现。

本篇的定位

组件选型最常见的失误是按功能清单挑产品。本篇只做一件事：每个组件族选型前必须先回答哪些问题，候选方案在什么条件下成立、要付出什么代价、将来换掉它有多贵。组件原理放在各专章，具体开源项目的横向对比放在 18 篇。

每个决策表都用同样三列评估候选：

  • 适用条件：不满足就直接排除，不进入比较。
  • 代价：上线后持续付出的东西，包括延迟、运维、质量风险。
  • 退出成本：换掉它时要重做什么，例如数据迁移、索引重建、接口改写、重新评测。退出成本高的组件必须现在选对，或者用标准接口隔离；退出成本低的组件按当下最省的方案选。

先定不可逆点，再选可替换件

退出成本分布并不均匀。在这个平台上，真正难换的是协议与数据格式，而不是引擎与框架：

退出成本 对象 换掉时要重做什么 现在就要做的隔离
高 工具与 Agent 互通协议（MCP、A2A） 所有能力提供方重新适配 只选开放协议；注册中心记录每个接入对应的规范版本
高 Trace 与埋点 Schema 历史数据无法对比，看板、评测、训练样本全部返工 对齐 OTel GenAI 语义约定，同时保留一层内部字段映射
高 记忆数据模型 用户记忆迁移，来源追溯断裂 来源、置信度、有效期落在自有存储
高 Embedding 模型版本 全量重建索引并重跑评测 索引名带模型版本，支持双写切换
高 端侧模型格式与推理运行时 随 OTA 重新发版，重新适配 NPU 端侧推理封装为能力接口，业务不直接调运行时
中 向量库、观测平台、Agent 框架 迁移数据或改写编排代码 检索与编排经内部接口访问
低 云端推理引擎、模型供应商、Reranker 改网关配置并跑回归 业务只声明 model_intent 
flowchart LR
  P["协议与数据契约<br/>MCP / A2A / Trace / 记忆模型 / Embedding 版本"] --> S["有状态存储<br/>向量库 / 记忆库 / 特征表"]
  S --> R["运行时与框架<br/>编排引擎 / Agent 框架 / 网关"]
  R --> E["可替换引擎<br/>推理引擎 / 模型 / Reranker"]

越靠左越要早定、越难改；越靠右越应保持随时可换。下面各族的结论都服从这个顺序。

A 编排与能力接入

A1 执行形态：Workflow、Agent 还是组合

必须回答：

  1. 任务分支能否穷举？不能穷举的请求占多大比例？
  2. 是否产生副作用（车控、下单、写数据），失败后是否需要补偿？
  3. 单次任务是否会跨越分钟级，或经历进程重启？
  4. 业务能否接受成本与时延不可预测？
候选 适用条件 代价 退出成本
纯 Workflow（DAG 或状态机） 分支可穷举、SLA 严格、带副作用 长尾分支要人工补齐 低：节点输入输出契约固定
单 Agent 循环（ReAct 类） 多步、分支难穷举、工具只读或低风险 成本与时延不可预测，调试困难 中：换框架后提示词与工具描述需重评测
外层 Workflow + 内层 Agent 多数企业场景的默认形态 两套执行语义要在同一条 Trace 里对齐 中
持久化执行引擎托底（Temporal 类） 长任务、跨重启、需要补偿事务 独立集群，工作流代码须满足确定性约束 高：业务代码与引擎 API 绑定
多 Agent 协作 领域天然分工，且需要隔离上下文 协调开销、错误级联、归因困难 高：拓扑与消息约定难以平移

结论：默认由外层 Workflow 定骨架，Agent 只处理不可穷举的节点；带副作用的动作一律留在 Workflow 节点并要求二次确认；每个 Agent 都带轮次、工具调用次数、Token 与耗时三重预算。多 Agent 只在上下文隔离能换来可测的质量提升时引入。运行时设计见 07 篇。

A2 意图路由

必须回答：

  1. 入口背后有多少业务域、多少意图？意图集多久变一次？
  2. 路由能占用多少首字时延预算（预算分配见 01 篇）？
  3. 路由结果能否离线评测？
候选 适用条件 代价 退出成本
规则与关键词 意图少于 20 个且稳定 泛化差，规则互相冲突 低
判别式小模型分类 意图集稳定，有标注数据 标注与再训练 中：标注集可复用
语义相似度路由（意图向量检索） 意图多、变化快 近邻意图易混，依赖反例 低
大模型函数调用路由 长尾与组合意图 延迟与成本最高，结果波动 低
混合路由（向量召回 + 小模型判别 + 置信度阈值） 多业务域共享一个入口 两级组件运维 中

结论：多域入口选混合路由：高置信直接落域，中置信并行探测两个域，低置信反问用户；意图分类不用大模型；每次路由都记录 route_reason，否则线上无法解释为什么落到这个域。Planner 独立成服务的取舍见 00 篇 ADR-02 与 03 篇。

A3 能力接入：Tool、Skill 与 MCP

必须回答：

  1. 能力由谁提供：同团队、跨团队，还是第三方？
  2. 调用发生在本地（端侧、同进程）还是远程？
  3. 能力数量会不会超出模型能稳定选择的范围（经验值约 30 个）？
  4. 权限按用户、按 Agent，还是取二者交集？
候选 适用条件 代价 退出成本
进程内 Tool（框架原生函数调用） 能力少、同团队维护 与 Agent 框架绑定 中：换框架要重写注册代码
MCP Server，stdio 传输 端侧或本地单用户工具 进程生命周期管理，无多租户 低
MCP Server，Streamable HTTP 传输 跨团队、远程、多租户 需要网关统一鉴权与审计 低：开放协议
Skill 层（意图到能力组合的封装） 能力超过 30 个，选错工具成为主要失败原因 描述质量与冲突检测需要治理 中：自定义格式
存量 API 直接暴露为工具 迁移过渡期 描述写给人看，结果冗长 低

协议版本有三点要写进 ADR：

  • MCP 远程传输自 2025-03-26 版规范起为 Streamable HTTP，取代原先的 HTTP+SSE 双端点方式，新接入不要再按旧方式实现。
  • 2025-06-18 版规范把 MCP Server 定位为 OAuth 资源服务器，并加入结构化工具输出与 Elicitation（服务端向用户补问）。鉴权统一放在网关实现，不让每个 Server 各写一套。
  • 官方 MCP Registry 已于 2025-09-08 开放预览。内部注册中心的元数据字段宜向它看齐，避免日后维护两套描述。

结论：跨团队能力一律以 MCP Server 暴露，远程走 Streamable HTTP；能力超过 30 个就在注册中心引入 Skill 层，每个 Skill 注册时附不少于 10 条正例意图和 5 条反例；工具描述面向模型写，参数用枚举约束，结果裁剪后再回灌上下文。MCP 的安全基线见 12 篇。

A4 Agent 互通

必须回答：

  1. 端侧 Agent 是否要调用云端 Agent，跨域 Agent 是否要协作？
  2. 任务是同步问答还是长时异步？
  3. 身份与权限跨多跳时如何传递？
候选 适用条件 代价 退出成本
点对点 HTTP 调用 Agent 不超过 3 个，同团队维护 拓扑随数量平方增长 低
消息总线 + 自研寻址（NATS、Kafka 类） 内部同构 Agent，异步为主 私有协议，跨团队互通差 高：寻址与消息格式自定义
A2A 协议 + 中心桥接（Agent 网关） 端云与跨域协作、长任务、需要能力发现 多一跳延迟，每跳都要鉴权 低：开放协议，已于 2025-06 捐赠 Linux 基金会

结论：A2A 负责 Agent 之间的任务委托，MCP 负责 Agent 调用工具，两者不混用；桥接层对每一跳独立鉴权，按调用方与被调方权限的交集放行，不信任上游传来的身份。

B 记忆

必须回答：

  1. 用户能否要求”忘掉某件事”？记忆需要追溯到哪一轮对话吗？
  2. 记忆抽取在线同步做，还是会话结束后异步做？
  3. 事实型记忆与统计型画像是否分开存？
  4. 记忆召回最多占上下文预算的多少？
候选 适用条件 代价 退出成本
会话窗口 + 滚动摘要（Redis、框架 Checkpointer） 短期记忆，所有对话场景 摘要有损，最易丢实体与数字 低
开源或托管记忆框架（Mem0、Zep 类） 需要尽快上线长期记忆 冲突合并与审计能力参差，数据模型受框架约束 高：记忆模型与抽取逻辑绑定
自研事件溯源（PG + pgvector + 事件表 + 物化视图） 需要回溯干预、审计与合规删除 建设成本高 低：数据在自有模型里
特征表画像（Feast 类或自研） 稳定的统计倾向，如偏好类型、活跃时段 更新有延迟，冷启动无数据 中
图记忆 实体关系密集，如家庭成员与设备归属 抽取贵，更新难 高

上下文压缩的优先级：结构化压缩（转成字段或表格）优于选择式过滤，选择式过滤优于生成式摘要；压缩用小模型执行，压缩前后的内容都留存，便于效果归因。

结论：无论是否采用记忆框架，source_trace_id、confidence、valid_until 三个字段和原始来源都必须落在自有存储，框架只作为抽取与召回的实现。写入异步、幂等、可审计；涉及身份、健康、财务倾向的记忆走人工复核。详见 08 篇。

C 知识与检索

必须回答：

  1. 语料多大、多久更新一次、是否按车型或版本分区？
  2. 查询里型号、错误码、功能名这类专有词占多大比例？
  3. 有没有评测集证明多跳或全局性问题是主要失败类型？
  4. Embedding 换代时，全量重建能否在维护窗口内完成？

C1 向量存储

候选 适用条件 代价 退出成本
pgvector 百万级以下，已有 PG 运维能力 规模上去后性能与调优受限 低
嵌入式向量库（LanceDB 类） 端侧与轻量服务 生态相对年轻 低
独立向量库（Qdrant、Weaviate 类） 百万到千万级，需要混合检索与多租户 独立集群运维 中
分布式向量库（Milvus 类） 千万级以上 组件多，运维最重 中
云托管向量服务 没有运维团队，数据允许出域 厂商锁定 高

向量库的退出成本主要来自两处：索引重建，以及元数据过滤语法的改写。检索统一经内部接口访问，就能把后者压到最低。

C2 检索形态

候选 适用条件 代价 退出成本
纯向量检索 仅口语化语义问题 型号、错误码、功能名上系统性失败 低
混合检索 + Rerank（召回约 50 条，重排取约 5 条） 企业知识库的默认配置 Rerank 增加几十毫秒延迟 低
图与向量双索引（LightRAG 类） 需要关系推理且知识持续更新 建图成本 中
全量图谱（GraphRAG 类） 高价值、低更新频率、全局性问题 建图的大模型调用量极大，增量更新难 高

Embedding 与切分的决策点：中文语料选中文优化模型；维度不是越高越好，存储与检索成本会先于效果翻倍；索引名带模型版本；切分采用”按标题层级 + 父子分块”，标题路径写入 chunk 元数据，命中小块、返回父块。

结论：从混合检索 + Rerank + 评测集起步，元数据过滤前置（先按车型、版本过滤再检索）；只有评测集证明多跳问题是主要失败类型时，才对那个子域引入图增强。原理与评测见 09 篇。

D 模型服务

必须回答：

  1. 请求按难度分级后，分类、闲聊、复杂推理各占多少比例？
  2. 数据能否出域？流量是否稳定到值得自建推理？
  3. 哪些意图必须离线可用？这决定端侧 SLM 的职责。
  4. 失败时降到哪一级仍可接受？
候选 适用条件 代价 退出成本
商业模型 API（经网关访问） 起步期，流量波动大 单价高，数据出域，限流不由自己控制 低
自建推理引擎（vLLM、SGLang 类） 流量稳定、数据不出域、需要控制前缀缓存 GPU 成本与运维 中
端侧 SLM（llama.cpp、ONNX Runtime、厂商 NPU SDK） 离线可用、隐私敏感、高频轻任务 量化精度损失，模型随 OTA 更新 高：与硬件和 OTA 流程绑定
模型路由网关（LiteLLM 类，或 Envoy、Higress 插件） 多模型并存 策略复杂后必须靠可观测解释 低
Kubernetes 推理路由扩展（Gateway API Inference Extension，2025-09-09 发布 v1.0） 自建推理跑在 Kubernetes 上 需要推理服务暴露负载指标 低：遵循 Gateway API

结论：业务只声明 model_intent，模型选择、路由与 Fallback 都是网关配置（00 篇 ADR-04）；按难度分级用模，意图分类交给小模型；自建推理的负载均衡按未完成请求数或 Token 队列长度分配，不用轮询；Prompt 模板按代码管理，每次调用记录 prompt_version。降级矩阵见 01 篇，调用链上的逐步降级见 06 篇，模型平台与网关分别见 10、11 篇。

E 缓存与计量

必须回答：

  1. 用户问法收敛到什么程度？
  2. 答案对时效有多敏感，例如电量、天气、附近状态？
  3. 是否自建推理？这决定能否直接控制前缀缓存。
  4. Token 消耗以谁的计量为准？
候选 适用条件 代价 退出成本
Prompt 稳定内容前置 + 前缀缓存 所有场景 要固定 Prompt 各段顺序：系统指令、工具描述、知识、记忆、用户问题 低
网关 Token 计量与配额 所有场景，必选 全链路强制接入，限流按 Token/s 而非 QPS 中
精确匹配缓存 模板化请求 命中率低 低
语义缓存 问法高度收敛的 C 端场景 误命中直接答错，缓存键维度与失效策略复杂 中

结论：引入顺序是先调整 Prompt 结构让前缀缓存生效（几乎零成本），再建网关计量与配额，最后才上语义缓存。以网关计量为唯一口径，禁止业务自报。语义缓存的键维度、阈值与失效策略见 10 篇。

F 交互与流式

必须回答：

  1. 用户是否需要随时打断播报（barge-in）？
  2. 哪些语音意图必须在端侧识别？
  3. 客户端到云端的流是单向还是双向？
  4. 多模态输入在哪一层融合？
候选 适用条件 代价 退出成本
SSE 回答类单向流，需要穿透代理，需要断点续传 只能单向，长连接占用 低
WebSocket 语音全双工等双向实时交互 心跳与重连自己实现，部分代理兼容性差 中
gRPC 流 服务间内部调用 端侧与浏览器支持弱 中
端侧 ASR 车控指令、离线场景 词表有限 中：随 OTA 更新
云端流式 ASR 开放域问答 依赖网络 低

结论：回答流统一用 SSE（00 篇 ADR-09），首包尽快返回，心跳保活，客户端指数退避并按 Last-Event-ID 续传；语音全双工另走双向通道，打断能力要求播报与采集并行且回声消除有效。融合放在编排层之前，Planner 只处理统一的上下文包（契约见 01 篇）。

G 安全

必须回答：

  1. 注入防御主要靠检测，还是靠架构隔离？
  2. 哪些能力会执行模型生成的内容（代码、脚本、动态查询）？
  3. 流式输出如何分段检测？检测服务故障时放行还是拦截？
候选 适用条件 代价 退出成本
规则 + 分类模型检测（Llama Guard、NeMo Guardrails 类） 基线，所有入口 总能被绕过，有误拦截 低
架构隔离（指令与数据分区、工具最小权限、危险操作二次确认） 必选，主防线 约束工具与 Prompt 设计 —
容器 + seccomp 沙箱 可信度较高的内部脚本 隔离强度最弱 低
gVisor 类用户态内核 执行模型生成代码的通用场景 系统调用有性能损耗 中
Firecracker 类微虚拟机 多租户、不可信代码 启动与资源开销最大 中
WASM 运行时 端侧与轻量插件 语言与系统能力受限 中

结论：检测只是基线，隔离才是主防线；凡执行模型生成内容的能力都必须进沙箱，端侧同样如此；出站检测 fail-closed，并提供误拦截反馈通道。完整清单见 12 篇。

H 观测、评测与训练

必须回答：

  1. Trace 的数据格式用标准还是自定义？
  2. 是否需要 Prompt 版本管理、会话回放、评测联动？
  3. 评测集如何分层，哪一套作为发布门禁？
  4. 想靠训练解决的问题，是否已经确认 Prompt、RAG 与上下文质量解决不了？
候选 适用条件 代价 退出成本
OpenTelemetry + GenAI 语义约定（2025-08-25 发布的 v1.37，仍为 Development 状态） 必选的数据格式底座 字段仍在变化，需锁定版本 低
通用观测栈（Jaeger、Prometheus、Grafana、Loki 类） 延迟、成功率、资源等基础指标 不理解 LLM 语义 低
LLM 观测平台（Langfuse、Phoenix 类） 需要 Prompt 版本、会话回放、评测联动 多一套存储 中；以 OTel 为统一入口时为低
不训练：优化 Prompt、RAG 与上下文 默认 — 低
SFT 格式遵循、领域术语、回答风格 高质量问答对的构建 中
DPO 线上偏好信号充足（纠正、重问、点踩） 偏好对质量把控 中
RLHF + Reward Model 大规模精细对齐 数据、算力与团队投入都高 高

结论：数据格式押 OTel，平台可以换；Trace ID 从端侧生成，一直贯穿到训练样本；GenAI Span 至少带 model、prompt_version、Token 数、cache_hit、route_reason、guard 结果。评测分公开集、回归集、盲测集三套，回归集做发布门禁，LLM-as-Judge 先与人工标注校准。训练先 SFT 解决格式与术语，再 DPO 学偏好，大多数团队不需要 RLHF。埋点 Schema 见 05 篇，可观测见 13 篇，训练与数据平台见 14、15 篇。

上线前自查

  • 每个组件都填了退出成本，标为”高”的项都有对应的隔离手段。
  • 带副作用的动作都在 Workflow 节点里，且有二次确认与补偿。
  • 新增 MCP 接入按 Streamable HTTP 实现，注册中心记录了每个接入的规范版本。
  • 记忆的来源、置信度、有效期落在自有存储，支持单条失效与批量清空。
  • Embedding 索引名带模型版本，换代可以双写切换。
  • 网关是 Token 计量的唯一口径，每个 Agent 有日配额与异常熔断。
  • Trace 字段对齐 OTel GenAI 语义约定，并有一层内部字段映射。
