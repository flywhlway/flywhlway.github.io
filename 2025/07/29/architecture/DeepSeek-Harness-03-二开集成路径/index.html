12.3.2 execute() 的七条硬约定

# 约定 说明
1 参数已为你校验 defineTool 在 execute 前按 ParameterSchemaSpec 校验（类型、必填、字面量约束、oneOf 精确单分支、嵌套值）。但 schema DSL 无法表达的约束仍需手检（非空字符串、正数、跨字段规则）
2 注册借用你的只读定义 注册后不要修改 schema 或替换回调。热替换请 dispose 副作用再注册替代品
3 执行身份受保护 callId/name/arguments/agent/token/signal 全程不可变。把 args 视为只读
4 声明并返回规范 JSON 值 execute 只返回推导出的值。不要返回内容块，不要迫使调用方从自然语言里解析 id
5 抛异常或返回无效值 = isError 基础设施故障抛异常；成功的领域结果即使表示不理想状态也写入规范值（如”进程非零退出”）
6 遵守 exec.signal 信号触发时取消进行中的工作
7 用 exec.agent 发异步通知 agent.inject({ content, source: { kind: 'plugin', plugin: '<name>' } })——这不是唤醒，空闲 agent 保持空闲。需 try/catch 防 disposed agent

12.3.3 参数与输出 Schema DSL

统一词汇 ValueSchemaSpec 支持：string / number / integer / boolean / null / array / object / json（仅作者侧）/ oneOf（要求精确命中一个分支）。

关键规则：

  • 参数根是隐式开放对象，必填靠逐属性 required: true 标注
  • 显式对象节点必须声明 additionalProperties: true | false
  • { type: 'json' } 推导为 JsonValue，编译成仅含注解的原始 schema
  • InferValue<S> 在 16 层容器内保留字面量约束，之后回退 JsonValue（避免 TS 类型实例化栈耗尽）

12.3.4 长时间运行的工作（后台任务）

为什么不能用 exec.signal？ ctx.jobs.start() 发布 id 后，取消外层调用只应停止”等待本次调用”，不应终止已发布的工作——那个生命周期归 job_kill、owner dispose 和服务 teardown 所有。

producer 契约：同步 cancel、资源清理后 settle 且不 reject 的 done、可选的消费式 readOutput（负责有界输出格式化）。预先中止的调用属于失败（此时没有任务，其 id 无法满足成功输出 schema）。

12.3.5 UI 卡片（presentCall / presentResult）

卡片类型：

类型 用于 关键字段
generic 默认 title、kind（图标）、rawInput、content、locations（编辑器可跳转）
terminal 调用本身是 shell 命令 title=命令、description、cwd；结果侧带原始输出与退出元数据
diff 创建或修改文件 diffs: [{ path, oldText, newText }]（新文件 oldText: null）
search 仅结果侧 shape: 'matches'（grep，按文件分组）/ 'paths'（glob）+ truncated/total
web 仅结果侧 kind: 'search' | 'fetch'

三条硬性规则（违反会出问题）：

  1. 必须是纯函数——这些方法在实时流式和会话日志回放时都会运行，因此只能依赖 args（+ result），不做 I/O、不读会话状态、不用时钟/随机数
  2. UI 格式不进入模型结果——围栏 ```console 块、diff、相对化路径不应仅为服务 UI 而进入规范值或 Native 内容
  3. defineTool 对展示路径做软校验——格式错误或旧版日志的参数使包装器返回 undefined（通用回退）而非抛异常，展示绝不能导致回放崩溃

如果你发现自己想在 presentCall 内获取文件旧内容或工作目录——停下：那属于持久结果元数据或 UI 适配器，不属于展示器。

12.3.6 用 presentationMeta 承载可回放卡片数据

核心把它持久化在 tool/result 上并传给 presentResult，因此需要结果期事实的卡片（如 write/edit 的已应用 hunk）无需持久化规范值也能在回放中重现。嵌套 Code 分发没有卡片，因此跳过该投影器。

从 GitHub 安装的”构建脚本坑”

git 安装拉取的是源码不是构建产物，没有任何环节运行你的 build 脚本。两边各做一件事：

  • 作者提供自包含的 prepare 脚本（pnpm 在 git 安装后运行），不能假设 monorepo checkout 存在。官方给出的可用范例是 turtle-ui：prepare 运行专用 tsdown 配置直接转译 src/，不用项目引用也不做类型检查
  • 用户授权构建——pnpm ≥10 在显式允许前拒绝运行 git 依赖的 prepare：

⚠️ 请如实看待这项授权：它允许该包的代码在安装时于你的机器上执行，且不在 agent 运行的任何沙箱之内。只对源码可信的包授权，并锁定 commit（github:you/plugin#<sha>），让后续推送无法悄悄改变实际运行的内容。

企业环境建议：不要用 git 安装。发布到内部 npm registry（pnpm publish 时构建好 lib/），或交付 tarball（pnpm pack → dsh plugin add ./x-0.1.0.tgz）——两种形式都不需要任何构建权限。

12.9 二开常见坑与工程约束

# 坑 规避
1 waterfall 忘记调用 next() 静默短路整条流水线且不报错。只做观察的监听器必须委托
2 把持久会话事件当作 Cordis 事件监听 turn/*、tool/*、compaction/* 只能通过 session/event + event.type 观察
3 patch 只写改动的键 patch 替换整个 config，必须重述该行需要的每个键
4 在 patch 里用相对路径引用本地插件 必须绝对路径（patch 不改变 loader 的模块解析基准）
5 Windows 上同时挂 bash 和 pwsh 栈 两族注册同一个 bash 服务，会在加载时报错。切换配方必须完整
6 旁挂 dsh-fs-local 而没禁用 fs-sandbox 重复注册 ctx.fs，加载时失败
7 presentCall/presentResult 里做 I/O 或读时钟 回放时会出错。必须是 args（+result）的纯函数
8 后台任务用 exec.signal 取消外层调用会误杀已发布的任务。用任务自有信号
9 在 stdout 打日志（SDK/ACP 模式） stdout 即协议。诊断走 stderr
10 假设插件不会被卸载重载 服务消失 → 依赖插件自动 dispose；服务回来 → 自动重载。所有状态绑到 ctx.effect
11 Code Mode 下让模型解析自然语言取 id output.schema 必须是程序化 API
12 忽略 sandboxEnforcement === 'partial' 老 Landlock ABI / Windows ACL 只能部分强制。需要绝对边界时必须拒绝或向上暴露
13 源码模式忘记 pnpm run build 启动器不检查产物新鲜度，会静默跑旧代码
14 依赖 SESSION_FORMAT_VERSION 当前为 0，预发布格式，明确不承诺兼容性

⚠️ 关键合规警告（官方明示）：随附基础配置没有任何遥测脱敏规则。显式启用的导出可能包含消息文本、工具参数和结果，以及 workspace 路径。导出携带 harness home 的匿名用户 id（$DSH_HOME/.anonymous-user-id）作为 Resource 的 user.id。

14.2 值得学习的架构手法（即使不用 dsh）

这个仓库有若干设计值得直接搬到自己的系统里：

  1. “模型可见即已记录”作为运行时不变量 —— 把架构约束从文档提升为可执行断言（ctx.invariants）
  2. 能力 seam 的三角色分离 + 生成的能力图交叉校验 —— 让”接口/实现分离”从口号变成 CI 门禁
  3. 压缩锁”最后释放” —— 崩溃表现为可检测的遗留锁，而非虚假的完成标记
  4. 平台门控用取反表达式成对声明 —— 同一份配置文件，每个宿主恰好挂载一套
  5. patch 不做深度合并 —— 用”必须重述完整 config”换取”任何一行的来源永远可追溯到最多两层”
  6. 沙箱强制执行完整性作为后端报告的事实 —— full/partial 显式区分，而不是假装总是完整
  7. 文档由代码生成 + 双语配对门禁 —— 工具目录生成器真实启动每个插件读取运行时 schema
  8. 失败分类正交独立 —— “预算耗尽不是异常，中止不是超时，基底崩溃也不是二者中的任何一个”

建议在 P1 结束时做一次 go/no-go 评估——重点看三件事：破坏性变更的实际频率、你团队写 TS 插件的效率、以及模型在你们业务工具上的实际表现。

结语

DeepSeek Harness 最有价值的地方，不在于它开箱能做什么，而在于它用一套可验证的架构约束证明了”agent harness 可以完全由插件组合而成”——包括 agent loop 本身。

对于要自建 agent 平台的团队，即使最终不采用 dsh，它的三个设计也值得直接借鉴：

  1. 能力 seam 的三角色分离（Definition / Provider / Consumer，且 Provider 与 Consumer 互不依赖）
  2. 事件溯源日志 + “模型可见即已记录”运行时不变量（把可追溯性做成架构地基，而非事后补的埋点）
  3. 分层 patch 组合（用”不做深度合并”的简化，换取”任何一行的来源永远可追溯”）

同时必须清醒：这是一个 v0.1 developer preview，官方明确警告破坏性变更、会话格式版本号为 0、没有多租户、遥测无脱敏规则。适合现在投入研究与原型验证，不适合现在承载生产关键路径。

本文档基于 deepseek-ai/deepseek-harness@47f9438（v0.1.0-rc.5）源码与官方文档整理。所有 API 签名、配置字段与事件名称均来自实际源码，未做推测性补全。随上游快速迭代，部分细节可能变化——以仓库内 docs/ 生成目录为准。
