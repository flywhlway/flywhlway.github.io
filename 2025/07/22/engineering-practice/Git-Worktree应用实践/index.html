Git Worktree 实践：从 Hotfix 并行到「一个 Agent 一个工作树」

git worktree 让一个仓库同时检出多个分支：讲清共享对象库与独立 HEAD/索引的原理，实测全部子命令的行为与报错…

Flywhl 16 分钟 更新于 2026.09 #AI 编程#Git#Worktree

先读结论

  1. worktree 共享对象库和分支引用，只把 HEAD、索引和工作目录分开；比再 clone 一份省空间，比 stash 切换少打断。
  2. 同一分支同一时刻只能被一个 worktree 检出；remove 会拒绝有改动的目录，但会静默删掉被忽略的 .env 和本地数据。
  3. 多 Agent 并行的关键不在 Git，而在依赖、端口、数据库这些 Git 管不到的资源：给每个 worktree 分配独立端口和 Compose 项目名。
  4. 用 lock 标记正在工作的 worktree，用「已合入基线 + 无改动 + 未加锁」三个条件做批量回收。

问题：切分支的代价

一个仓库默认只有一个工作目录。手上的功能改了二十个文件、调试断点还开着，线上来了个紧急修复，常规做法是 git stash → 切到 main → 修 → 切回来 → git stash pop。这个过程有三处损耗：未提交的改动要搬家；IDE 和构建工具面对整棵树被替换，索引和增量缓存全部失效；stash 里的东西一多，很容易 pop 错。

另一种做法是再 clone 一份。隔离是彻底了，但历史要重新下载，两份仓库的分支和 fetch 状态也互不相通。

git worktree 介于两者之间：一个仓库、多个工作目录，每个目录检出不同的分支或提交，对象库和分支引用只有一份。

原理：一个对象库，多份 HEAD 与索引

flowchart LR

    O["objects/ 对象库"]
    R["refs/heads、refs/tags、refs/stash"]
    C["config、hooks/"]
    W["worktrees/app-hotfix/<br/>HEAD、index、logs"]

分工很清楚：

归属 内容 实际影响
每个 worktree 独有 HEAD、index（暂存区）、工作目录文件、refs/bisect 等少数私有引用 各自提交、各自暂存、各自 bisect，互不干扰
所有 worktree 共享 对象库、分支与标签、refs/stash、config、hooks/、远端跟踪分支 在任一目录 git fetch，其他目录立刻看到新提交；stash 列表也是同一份

最后一行容易被忽略：在 worktree A 里 git stash，主工作树 git stash list 能看到 stash@{0}: WIP on agent/t2: ...。并行开发时尽量不用 stash，改用临时提交。

三种隔离方式的取舍：

维度 同目录切分支 worktree 再 clone 一份
同时打开多个分支 否 是 是
历史与对象 一份 一份 两份，需重新下载
分支、fetch 状态 — 实时共享 各管各的，要来回 push/fetch
依赖目录（.venv、node_modules） 一份，切分支可能错配 每个目录一份 每个目录一份
适合 短暂切换、改动已提交 并行开发、Review、长任务、多 Agent 需要完全独立的配置或远端

子命令全集（实测）

以下输出在一个沙箱仓库中实测，设置了 LC_ALL=C 以得到英文提示（中文环境下提示会被翻译，含义相同），绝对路径缩写为 ~/code。仓库有 main 分支和一个 v1.0 标签。

add：创建

基于远端跟踪分支创建时要留意上游设置。git worktree add -b agent/x ../x origin/main 会输出 branch 'agent/x' set up to track 'origin/main'，新分支把 origin/main 当成了上游，之后在里面 git pull 拉的是 main、git push 的目标也不是你以为的分支。加 --no-track，首次推送时再用 git push -u origin agent/x 建立正确的上游。

list：查看

写脚本时用 --porcelain，每个 worktree 一段，段与段之间空一行，加锁和可清理状态也会单独成行：

git worktree list -v 会把锁的原因、可清理的原因展开显示，人工排查时比 porcelain 好读。另外 git branch 的输出里，被其他 worktree 检出的分支前面标 +，当前目录的分支标 *。

remove 与 prune：删除

实测三条行为，写清理脚本前必须知道：

  1. 已修改的跟踪文件和未跟踪文件都会阻止删除，需要 --force。
  2. 被 .gitignore 忽略的文件不会阻止删除，而且会被一并删掉。 在 worktree 里建了 .venv/ 和 node_modules/，remove 直接成功、目录消失。这意味着 .env、本地 SQLite、上传目录这类被忽略的数据，删的时候没有任何提示。
  3. 分支不会跟着删。remove 之后分支还在，要自己 git branch -d。反过来，分支正被某个 worktree 检出时删不掉：error: cannot delete branch 'feature/pay' used by worktree at '~/code/app-payment'。

如果目录是被 rm -rf 或 Finder 直接删掉的，Git 的登记信息还留在 .git/worktrees/ 里，list 会标记 prunable：

不清理的后果是那个分支一直被视为”已检出”，别处无法再检出它。

lock / unlock：防误删

锁的本意是保护放在移动硬盘、网络盘上的 worktree 不被 prune 清掉，但它同样适合标记”有人（或 Agent）正在里面工作”，后文的回收脚本就靠它跳过进行中的任务。

move 与 repair：搬家

如果已经用 mv 手动挪了目录，worktree 本身还能用（它的 .git 文件仍指向主仓库），但主仓库那一侧的登记指向旧路径，list 会显示 prunable，此时一 prune 就会丢掉登记。在主仓库里执行 repair 修复：

反过来，如果挪的是主仓库，就到每个链接工作树里执行一次 git worktree repair。

Git 2.48（2025 年 1 月）起可以用 git worktree add --relative-paths 或配置 worktree.useRelativePaths=true 让两端互存相对路径，整体搬动父目录后不必再 repair：

代价是仓库会开启 extensions.relativeWorktrees 扩展，更老版本的 Git 无法再操作这个仓库。IDE 自带的 Git、CI 镜像里的 Git 版本低于 2.48 时不要开。

四个典型场景

Hotfix 不打断当前工作

原来的工作目录一个文件都没动，IDE 索引和本地进程也没被打断。

PR Review 边写边看

Review 用的分支是临时拉下来的，看完用 -D 删掉即可。不要用 gh pr checkout：它会切换当前目录的分支，正好是要避免的事。

长任务与当前开发并行

跑完整测试、做数据迁移演练、打包镜像这类十几分钟的任务，最怕的是跑到一半你改了代码，结果不知道测的是哪个版本。先提交，再把这个提交检出到独立目录去跑：

AI 编程并行：一个 Agent 一个 worktree

Claude Code、Codex CLI、Cursor 这类工具的 Agent 都在某个目录里读写文件、跑命令。两个 Agent 共用一个目录，就会出现 A 改到一半、B 跑测试时读到半成品，或者两边同时改同一个文件。worktree 是这种并行的最小隔离单位：一个任务一个分支，一个分支一个 worktree，一个 worktree 一个 Agent。

目录与分支约定

两种放法：

布局 例子 优点 问题
仓库同级 ~/code/app/、~/code/app.worktrees/<任务>/ 不会被主仓库的 IDE、文件监听、rg、测试发现扫到 目录多一层，需要约定
仓库内部 ~/code/app/.worktrees/<任务>/ 集中，一眼能看到 必须加入 .gitignore；IDE 索引、pytest 收集、热重载监听都可能扫进去，要逐个排除

推荐同级布局。分支统一用 agent/<任务名>，任务名用短横线小写（agent/export-csv），这样 git branch --list 'agent/*' 就能列出所有 Agent 分支，回收时也不会误伤人手建的分支。

Git 管不到的资源

worktree 只隔离了 Git 跟踪的文件。下面这些要自己处理：

资源 默认情况 处理
依赖目录 每个 worktree 一份，新建时为空 进目录后 uv sync / pnpm install。两者都有全局缓存并用链接或写时复制装包，第二份通常只要几秒、额外空间很小
.env 等被忽略的配置 新 worktree 里没有 创建时从主工作树复制
端口 各 worktree 都读同一个默认端口，第二个服务起不来 每个 worktree 分配独立 APP_PORT
Docker Compose 默认项目名取目录名，容器和卷自动分开；但宿主机端口映射仍会冲突 显式设置 COMPOSE_PROJECT_NAME，端口走变量
数据库 都连 localhost:5432 的同一个库，A 的迁移会让 B 的测试失败 每个 worktree 用独立库名，或跟着 Compose 项目起独立实例

Compose 支持重复传 --env-file，后面的文件覆盖前面的，正好把”公共配置 + worktree 私有配置”叠起来。实测：

应用侧读配置时也叠加两份，例如 pydantic-settings 的 env_file=(".env", ".env.worktree")，后面的文件优先。

创建脚本：wt-new

放到 ~/bin/wt-new 并 chmod +x。在主工作树或任一 worktree 里执行都可以，目录总会落到 <仓库名>.worktrees/ 下。

.env.worktree 记得加进 .gitignore。端口按”已登记的端口集合”分配而不是按 worktree 个数递增，回收掉中间某个之后，空出的端口会被下一个任务复用，不会越涨越高。

派发、合并与回收

flowchart LR
  A["wt-new 任务名<br/>建分支、加锁、分端口"] --> B["在该目录启动 Agent<br/>只在这里读写"]
  B --> C{"结果可用？"}
  C -->|是| D["提交、推送、开 PR<br/>或本地 merge --ff-only"]
  C -->|否| E["git worktree remove --force<br/>git branch -D"]
  D --> F["worktree unlock"]
  F --> G["wt-gc --apply<br/>回收已合入的"]

几条纪律：

  • 任务要正交。 两个 Agent 同时改同一个模块，worktree 只是把冲突从”写文件时”推迟到”合并时”。拆任务时按目录或模块划界。
  • 并行数量看 Review 带宽，而不是机器性能。 同时开五个 Agent，最后卡在人读 diff 上。实践中三到四个比较能跟得上。
  • 合并前在 worktree 里跑完测试再 unlock。 unlock 是”这个任务我不再碰了”的信号。

脚本的边界：

  • Squash 合并识别不了。 分支被压成一个新提交合进 main 后，原分支不再是 main 的祖先。团队用 squash 时，改用”远端分支已被删除”作为合入信号：git fetch --prune 之后执行 git for-each-ref --format='%(refname:short) %(upstream:track)' refs/heads，上游显示 [gone] 的就是已合入的，删分支要用 -D。
  • 被忽略的文件不在 status --porcelain 里。 worktree 里如果有本地数据库文件、上传目录，脚本会连同目录一起删掉。重要数据放到 worktree 之外，或者对这种 worktree 一直加锁。

坑与边界

现象 原因 处理
fatal: 'feature/pay' is already used by worktree at ... 同一分支同一时刻只能被一个 worktree 检出；主工作树里 git switch 过去也会报同样的错 只读查看用 --detach；要改就从它拉新分支 -b
新 worktree 里子模块目录是空的，git submodule status 前面带 - 子模块不随 worktree 自动初始化 每个 worktree 里各执行一次 git submodule update --init
fatal: working trees containing submodules cannot be moved or removed 含子模块的 worktree 不能 move，remove 也要强制 确认子模块里没有未推送的改动后 remove --force
worktree 删了，.env 和本地数据也没了 被忽略的文件不阻止 remove，会被一起删掉 数据放 worktree 之外；进行中的加锁
分支残留越来越多 remove 不删分支 回收流程里配套 git branch -d
两个目录的 git stash list 一样 refs/stash 是共享引用 并行开发时用临时提交代替 stash
hook 在所有 worktree 生效 hooks/ 在共享目录里 需要差异化时用 extensions.worktreeConfig + config --worktree core.hooksPath
IDE 卡顿、全局搜索出现重复结果 worktree 放在仓库内部被索引 用同级布局；或在 IDE 里把该目录标记为排除
磁盘占用上涨 对象库共享，但工作树文件、依赖、构建产物每份都有 定期 du -sh ../app.worktrees/* 并回收；构建产物目录别留
开了 --relative-paths 后 IDE 报仓库格式不支持 extensions.relativeWorktrees 需要 Git 2.48+ 升级工具链里的 Git，或不用相对路径

总结

worktree 解决的是”同一个仓库同时处在几个状态”的问题，原理只有一句：对象和引用共享，HEAD、索引、文件分开。日常用到的就是 add、list、remove、prune 四个；lock 和 --porcelain 则是把它脚本化的关键。多 Agent 并行时，Git 这一层几乎不用操心，真正要设计的是依赖、端口、数据库的隔离，以及”谁在用、何时能删”的约定。

2026-09 补记：AI 编程工具开始原生管理 worktree

本文写于 2025 年 7 月，当时 worktree 要靠自己的脚本管理。到 2026 年，主流工具陆续把它做成了内置能力：

工具 内置能力
Claude Code claude --worktree <名称>（简写 -w）在 .claude/worktrees/<名称>/ 下创建 worktree，分支名为 worktree-<名称>；项目根的 .worktreeinclude（.gitignore 语法）指定要复制进去的被忽略文件，如 .env；子 Agent 可在 frontmatter 写 isolation: worktree；Agent 运行期间对其 worktree 持有 git worktree lock。2026-02-20 起提供 WorktreeCreate / WorktreeRemove hooks，可替换默认的 git 逻辑（例如改放到别的目录，或支持非 Git 版本库）
Codex app 2026-02-02 发布的桌面应用，多个线程并行，内置 worktree 支持
Cursor 3.0 2026-04-02 发布，Agents Window 可让多个 Agent 分别在本地、worktree、云端或 SSH 环境并行
Gemini CLI v0.36 起支持 Git worktree

对本文工作流的影响：

  • 创建环节可以交给工具。 wt-new 里的建分支、复制 .env、加锁，Claude Code 已经内置了同样的做法（.worktreeinclude 对应复制，运行期加锁对应 lock），说明这套约定方向是对的。
  • 端口和数据库隔离仍要自己做。 工具只负责文件隔离，.env.worktree 分端口、独立 Compose 项目名这一层没有被替代。
  • 布局不同要注意。 Claude Code 默认放在仓库内部的 .claude/worktrees/，官方文档建议把它加入 .gitignore；它和本文的同级布局可以共存，但同一个 worktree 只交给一方管理。Claude Code 的定期清理只处理它自己创建的 worktree，手工 git worktree add 的不会被它删掉，回收仍需要 wt-gc 这类脚本。
