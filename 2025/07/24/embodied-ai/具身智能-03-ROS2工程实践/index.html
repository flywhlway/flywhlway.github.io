3.1 开发环境：OrbStack + Docker Compose + ROS2 Jazzy

3.1.1 方案选择：为什么是容器

双系统/裸机 Ubuntu 对 Mac 用户不现实；传统虚拟机重且慢。OrbStack 在 Apple Silicon 上以近原生性能跑 Linux 容器，而 ros:jazzy 官方镜像原生提供 arm64——容器即工作站。额外红利：环境即代码（Dockerfile 进 git）、多容器天然模拟「机器人/云端」两侧、与你日常的容器工作流零摩擦。已知取舍：GUI 工具（rqt/RViz）在容器里麻烦，本篇以 CLI + Foxglove（读 MCAP）为主，不影响任何验收项。

3.1.6 AI 辅助工作流（VSCode / Cursor / Claude Code / Codex）

推荐分工：Claude Code 开在仓库根目录做跨文件工程活（生成节点骨架、写 launch、按 2.24 Runbook 排障、沿 rclpy→rcl→rmw 读源码链提问）；Cursor/VSCode 内联补全写具体函数；Codex 类工具跑批量重构。两条纪律：AI 生成的 QoS 与线程模型必须对照 2.14 配方表与 2.6 规范人工复核——这两处是 AI 最常犯错、也最难在测试里暴露的地方。

3.1.8 与产业物联网平台的映射

Compose 三容器 = 你台架联调环境的最小复刻：robot 容器 ≈ 台架上的域控，mqtt ≈ 接入 Broker，cloud ≈ TSP 最小桩；环境即代码 ≈ 你们的联调环境 IaC。

3.1.9 企业实践建议

把本节工程骨架直接升格为团队《机器人开发环境标准》：新人入职 30 分钟内 git clone && docker compose up 出全套环境——环境标准化是你在新团队交付的第一个平台化胜利，成本最低、感知最强。

3.1.10 面试可能问什么

  1. 如何为机器人团队设计开发环境？（要点：容器化、环境即代码、双平面拓扑、GUI 取舍）
  2. 容器里 DDS 发现的网络前提？（要点：同 L2 多播；跨宿主 Discovery Server）

3.1.11 最佳实践

  • 镜像里固定 RMW 实现与 Domain 默认值，杜绝「我机器上好的」类环境漂移。
  • ws/ 用 volume 挂载而非 COPY——代码在宿主机编辑、容器内构建，IDE 与构建互不打架。

3.1.12 常见误区

  • ❌ 上来就折腾 RViz GUI 转发——本篇一切验收 CLI 可完成，别在 X11 上烧掉第一周。
  • ❌ 云容器也装 ROS 图省事——破坏双平面架构，后续云桥的存在意义就被稀释了。

3.1.13 Obsidian 永久笔记

  • 容器即工作站：OrbStack + ros:jazzy arm64，环境即代码。
  • 三容器最小台架：robot/mqtt/cloud 复刻端-管-云。
  • AI 生成必复核两处：QoS 配方与线程模型。

3.3 实战项目：机器人遥测系统 v0.1

3.3.1 需求与验收标准

上行：机器人以可配置频率上报八类状态——位置、速度、姿态、关节、电池、CPU、GPU、错误码。下行：云端可下发五类任务——patrol（开始巡检）、stop、ota、reboot、calibrate，全程可见进度与结果、可取消。验收：curl 一次拿到最新状态；curl 发起 OTA 任务后能查询到 download→verify→install→restart 的阶段进度与最终结果。

3.3.2 接口契约（信号矩阵表 + 任务清单）

机内 Topic 类型 频率 QoS 上云
joint_states sensor_msgs/JointState 20Hz sensor_data 否（聚合后上）
odom nav_msgs/Odometry 20Hz sensor_data 否
battery sensor_msgs/BatteryState 1Hz default 否
telemetry/state robot_interfaces/RobotTelemetry 5Hz default ✅ MQTT robots/{id}/telemetry/state

消息（在 2.9.4 基础上补 velocity 字段成为终版）与任务契约：

设计决策（评审级理由）：平台类任务走一个通用 RobotTask（云端零改动接新任务类型，payload 弱类型换扩展性——与 云管端升级 通用任务模型同款取舍）；导航等高价值本体任务未来保留强类型专用 Action。MQTT 主题树与命名树同构（2.18.3）：上行 robots/{id}/telemetry/state，下行 robots/{id}/cmd/task，任务事件 robots/{id}/task/{task_id}/event。

3.3.12 企业实践建议

把 v0.1 当作团队的架构对齐样板间：新成员一天内跑通它，就同时理解了双平面架构、Action 任务模型、边缘降采样与契约治理四件事——比读十页架构文档快得多。样板间的每个「教学简化」（无鉴权、无离线缓存、SQLite）都在代码注释里标注对应的产品化篇章，形成天然的 backlog。

3.3.13 面试可能问什么

  1. 画出你的机器人端云链路并指出单点。（要点：3.0.2 图 + mqtt/bridge 单点与对策）
  2. 桥接节点如何处理两个事件循环？（要点：paho 线程只投队列，ROS 定时器消费——跨线程纪律）
  3. 云端下发任务如何做幂等与追踪？（要点：task_id 全链路贯穿、REPLACE/UPDATE 语义、互斥门）

3.3.14 最佳实践

  • task_id 由云端生成并贯穿 MQTT 主题、Action Goal、日志字段——分布式追踪的最小实现。
  • 遥测 JSON 字段名一次定版并文档化：它就是端云契约，改名等于破坏性变更。

3.3.15 常见误区

  • ❌ 在 paho 回调里直接 send_goal——跨线程踩 rclpy，偶发崩溃极难排查；队列缝合是铁律。
  • ❌ 拿 v0.1 直接上生产——它刻意省略了鉴权/离线缓存/持久化会话，产品化见第四、九篇。

3.3.16 Obsidian 永久笔记

  • 双事件循环队列缝合：外部 SDK 线程只投队列，ROS 定时器消费。
  • task_id 贯穿全链路：主题、Goal、日志同键，追踪即免费。
  • 样板间即架构文档：可运行的 v0.1 胜过十页 PPT，简化点即产品化 backlog。
