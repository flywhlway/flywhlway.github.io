第 0 部分 · 阅读指引与结论速览

0.1 一句话结论

DeepSeek Harness（CLI 名 dsh）不是”DeepSeek 版 Claude Code”，而是一个可以被组装成 Claude Code 的 agent harness 元框架。它把 agent 的每一项能力——模型适配器、工具注册表、会话日志、沙箱、存储、调度、UI，乃至 agent loop 本身——都实现为可替换的 Cordis 插件；产品形态由一份 YAML 配置树决定，而不是由代码里的 if/else 决定。

0.2 三个最值得关注的架构判断

# 判断 依据
1 没有特权内核 官方架构文档明确写道：”不存在需要打补丁的特权内核（no privileged kernel to patch）”。扩展方式是把插件挂到别的插件旁边，所有注册都是可撤销的副作用。连 ctx.agentLoop（agent 循环）都是一个可以整体替换的普通插件行
2 “模型可见即已记录”是一条运行时不变量 任何抵达模型请求的内容都必须能够从仅追加的 SessionEvent 日志重建，并由 ctx.invariants 在运行时断言。这使 fork / resume / replay / 遥测 / UI 渲染全部派生自同一条事件流
3 能力 seam 是一等公民的架构概念 一个 seam = Service Definition + Service Provider(s) + Consumer(s) 三种角色。这不是”接口 + 实现”的老调重弹，而是一条被文档、代码生成器和 CI 门禁共同强制的组织约束（56 个 ctx.* 服务键有生成的能力图交叉校验）

第 1 部分 · 项目定位、背景与工程指标

1.1 什么是 agent harness

在 LLM 应用工程里，”模型”和”agent”之间隔着一层往往被低估的基础设施。这一层负责：

  • 让模型理解环境：系统提示词组装、workspace 上下文、AGENTS.md 注入
  • 让模型使用工具：工具 schema 生成、调用分发、结果规范化、权限把关
  • 让模型持续工作：多轮循环、上下文压缩、子 agent 委派、后台任务、定时调度
  • 让运行可控可审计：会话日志、沙箱隔离、审批策略、遥测导出

这一层就是 harness（挽具/驾驭装置）。Claude Code、Codex CLI、Cursor Agent 本质上都是”模型 + 特定 harness”的组合产物。DeepSeek 官方对此的表述是：模型是 agent 的灵魂，harness 让 agent 理解环境、使用工具，并在真实场景中持续工作。

1.2 DeepSeek Harness 是什么 / 不是什么

它是：

  • 一个 MIT 协议的开源 agent harness 框架，CLI 名 dsh
  • 建立在 Cordis 元框架之上（设计见论文 A Programming Paradigm for Spatiotemporal Composability）
  • 一套开箱即用的产品组合：dsh web 直接启动一个完整 Web IDE 式编码 agent
  • 一套 SDK / 协议入口：Python SDK、TypeScript SDK、JSON-RPC stdio、ACP（Agent Client Protocol）

它不是：

  • 不是一个模型（模型走 ctx.llm seam，DeepSeek 官方适配器只是其中一个提供方）
  • 不是一个 CLI 工具的简单封装（dsh 只是启动器，产品形态在 profile 里）
  • 不是 LangChain/LangGraph 那样的”编排 DSL 库”——它管理的是进程内插件生命周期与能力装配，而不是有向图节点
  • 不是稳定生产平台——官方原文全大写警告：THERE WILL BE COMPATIBILITY-BREAKING CHANGES

1.4 工程规模指标（实测）

几个能说明工程成熟度的细节：

  1. 文档全部中英双语配对，且有 verify-translation-pairing 门禁校验配对新鲜度
  2. 四类目录文档由代码生成：config-catalog（12.9 万字符）、module-graph（12.5 万字符）、tool-catalog、persistence-catalog、capability-seams——生成器会真实启动每个工具插件读取 ctx.tools.schemas()，因为工具 schema 无法静态确定
  3. CI 门禁分层：ci-primary / ci-static / ci-coverage / ci-snapshot / ci-artifacts / ci-consumers / ci-windows-blocking / node-compat，甚至有 check:windows-wine（用 Wine 跑 Windows 门禁）
  4. .agents/ 目录：仓库自带 9 个供 AI agent 使用的 skill（文档翻译、prose 标准、pre-push 检查、agent note 归档等），以及大量 Agent Note 设计决策记录——这是一个”被 agent 开发、也为 agent 准备”的仓库

1.5 与主流方案的定位差异

维度 DeepSeek Harness Claude Code / Codex CLI LangGraph / AutoGen
抽象层次 harness 装配层 成品 agent 产品 编排 DSL 库
可替换粒度 每个能力（含 loop 本身） 有限（hooks / MCP / settings） 节点与边

关键差异点： Claude Code 的扩展点是”产品预留的孔”；DeepSeek Harness 的扩展点是”产品本身的装配缝”。前者你只能在设计者想到的地方插入；后者你可以替换任意一行——包括把 agent-loop 整个换掉。

第 2 部分 · 总体架构与分层模型

2.1 五层架构视图

层与层之间的关键约束：

  • L2 的 Consumer 绝不 import Provider，只 inject Service Definition
  • L3 的扩展插件依赖 dsh-agent（接口包），绝不依赖 dsh-agent-loop（具体实现），因此循环保持可替换
  • L4 的 patch 只能”按 id 定位行并替换其整个 config”或”插入新行”——没有深度合并（这是一个刻意的简化，见 4.2）
  • L5 的 UI 从 session/event 事件流渲染，通过 agent.followup() 驱动回去——UI 与内核之间只有事件与句柄两条通道

2.3 三个正交的事件域（选对事件域是大多数改动的第一个决定）

官方架构文档特别强调：”事件就是扩展点，而选对事件域是大多数改动的第一个决定。“

事件域 命名 性质 何时使用
会话事件 session/event 承载 turn/*、step/*、user/message、assistant/*、tool/* … 持久事实，追加到日志 事实必须在重新加载后仍存在时
Agent 事件 agent/*（inbox / status / pre-step / request / turn-stopping / created …） 实时控制，携带活跃 Agent 观察或拦截进行中的工作
能力事件 fs/*、tools/*、telemetry/*、skills/change、workflow/* … seam 附加点 附加策略与适配器，无需导入循环

关键澄清：turn/*、step/*、tool/call、tool/result、compaction/* 是持久化会话事件类型，不是同名的 Cordis 事件。要观察它们必须监听 session/event 并检查 event.type。这是新手最常踩的坑。

第 3 部分 · Cordis 内核机制原理

理解 dsh 的前提是理解 Cordis。以下是 harness 插件作者必须掌握的最小知识集。

3.1 五个核心概念

概念 说明
插件是实现 Service 的对象 可以是带 inject / apply(ctx) 的函数、对象，或 Service 子类
上下文是服务的容器 一个服务占据一个稳定的 ctx.<key>（ctx.tools、ctx.llm、ctx.sessions）；其他插件通过 key 查找服务，而非 import 具体实现
通过 inject 声明依赖 声明后等待服务就绪才启动；加载顺序由服务依赖表达，而非手动编排启动序列
类型化事件用于通信 通过 TS 声明合并注册事件名，再以 emit / waterfall / parallel / serial 分发
注册是可逆的副作用 提示词片段、工具 schema、适配器、监听器通过 ctx.effect() / ctx.on() 安装，reload 与 teardown 时按预期撤销

3.2 插件的三种形态

3.3 依赖的运行时语义（这一点非常关键）

服务消失时的行为链（这是 Cordis 最有价值的机制之一）：

  1. 依赖它的插件自动 dispose
  2. 服务重新出现时，插件自动重新加载

这从根本上防止了”插件持有已失效服务引用”的经典 bug。副作用是：你的插件必须假设自己随时可能被卸载重载，所有状态要么是无状态推导，要么绑定在 ctx.effect() 上。

3.4 四种事件分发模式

模式 是否 await 分发顺序 是否有返回值 典型用途
emit 否 按注册顺序观察 否 广播通知（session/event）
waterfall 否 按注册顺序观察 是 环绕中间件（tools/pre-execute）
parallel 是 并行 否 扇出通知
serial 是 按注册顺序 是 有序决策（agent/turn-stopping）
bail 否 按注册顺序，首个非空值胜出 是 短路检查

分发模式是事件公开约定的一部分——新的 harness 事件通过 @mode 标签记录模式，生成的目录会将声明与分发调用点做交叉校验。

3.5 Waterfall 语义（最容易写错的地方）

规则：

  • 调用 next() 执行下游监听器；返回值可被当前层包装后继续向外返回
  • 不调用 next() 直接返回 = 短路整条流水线（这是刻意设计，用于实现拦截/网关）
  • 协作式监听器修改共享的请求/决策对象后再委托
  • 仅当必须在普通注册之前运行时才用 prepend: true
  • 对单决策事件（如权限门禁），短路是设计意图；仅做标注/观察的监听器必须委托

实战警告：忘记调用 next() 是二开中最常见的静默故障——你的策略插件会让整个工具流水线失去后续所有策略层，而且不报错。

3.6 可逆副作用与 disposer

实践规则（官方措辞）：”每个注册都应有对应的 disposer：要么从 ctx.effect() 返回一个，要么使用 Cordis 提供的辅助方法自动处理。如果 teardown 顺序有要求，请将相关工作放在同一个 effect 中，以确保资源按预期顺序释放。”

3.7 服务隔离（isolate）——多实例的关键

cordis.yml 支持同一服务的多个实例，不同插件组看到不同实例：

plugin-a 与 plugin-b 各看到自己组内的 Bash 实例。这是 agent preset 实现”每个会话拥有不同能力集合”的底层机制——preset 中的服务行需要 isolate realm。

3.8 Loader 与 !!js 表达式

@deepseek-ai/cordis-plugin-include 将 !!js 解析为表达式节点：

求值时机很关键：Loader 在声明的注入激活后，基于该插件上下文（ctx.serviceName）插值条目的 config；disabled 字段则在每次挂载决策时基于 loader 上下文插值。这使得”命令行 flag 优先于配置行取值”能够成立，且在线编辑 cordis.patch.yml 时会根据仍在运行的服务重新计算表达式，不会重置当前正在使用的端口。

第 4 部分 · 组合体系：Profile / Bundle / Patch / Preset

这是 dsh 最有工程价值、也最容易被误解的部分。

4.1 三个核心概念

概念 载体 manifest 字段 回答的问题
Bundle（组合包） 一个 npm 包 dsh.bundle.patch “这个包贡献什么？”→ 一个 patch 文件
Profile $DSH_HOME/profiles/<name> 目录 dsh.profile.bundles “这套配置由哪些 bundle 按什么顺序组成？”
Agent Preset 含一份 agent.cordis.yml 的目录 preset.yml “单个会话的 agent 拥有哪些能力？”

两者从不重合：bundle 是你编写并分发的东西；profile 是用户用 dsh --profile <name> 启动的东西。

4.2 配置层叠顺序（严格按此顺序应用在空条目列表之上）

两条必须记住的规则：

  1. 后应用的层按行胜出
  2. patch 替换目标行的整个 config 值，不做深度合并

第 2 条是刻意的架构简化。它带来两个直接推论：

  • 你的 bundle patch 覆盖前面层的行时，必须重述该行需要的每一个键，而不能只写改动的那个
  • 用户可以在自己 profile 的 cordis.patch.yml 中覆盖你的行，无需改动你的包——所以优先给出用户大概率会保留的配置默认值，其余交给 schema 承担

同时这也解释了为什么”模式专属的值放在各模式 bundle 中，而不放在 base”：让任何一行最多只被”一个 bundle 层 + 用户层”触碰。

平台门控的精妙设计（值得学习）：

同一份 patch 文件，每个宿主恰好挂载一个 shell 栈。两个执行器家族注册同一个 bash 服务，因此如果用户想在 Windows 上恢复 bash，恢复配方必须完整（禁用 pwsh-sandbox/tool-pwsh + 重新启用 bash-sandbox/tool-bash），配方不完整会在加载时直接报错——这是”fail loud”哲学的体现。

  • 客户端侧（36 个 ui- 插件）*：ui-theme、locale、ui-layout、ui-sidebar、ui-settings*、ui-conversation、ui-tool、ui-cordis、ui-workflow-run、ui-deliverables、ui-workspace、ui-input-trigger、ui-commands、ui-skill、ui-subagent、ui-jobs、ui-goal、ui-message-feedback、ui-model-selection、ui-permission、ui-agent-preset、ui-plan、ui-user-questions、ui-trajectory

4.4 四种内置 Agent Preset（DeepSeek 官方称”四种运行模式”）

Preset 目录 中文名 order 能力构成
standard 标准模式 1 功能完整的编码 agent：文件编辑、Shell、文件与网页检索、Skills、计划、目标、子代理、工作流
code PTC 模式（Programmatic Tool Calling） 2 具备标准模式全部能力，但通过 Code Mode SDK 呈现工具，让模型用一个 TypeScript 程序组合多步操作
minimal 极简模式 3 仅持久 bash + str_replace_editor 双工具。系统提示词固定为 You are a helpful software engineer assistant.，无任何其他提示词段落或面向模型的插件
cordis 创造模式 4 标准模式 + 运行时检查、插件实验和 preset 创作指导（自带 cordis-plugin-development 与 editing-cordis-compositions 两个 skill）

极简模式的用途值得单独说明：它是模型基准评测环境——剥离所有 harness 辅助，用最小工具集测量模型本身的编码能力。这对做模型评估的团队非常有价值。

Preset 的运行时机制（很巧妙）：

“roster 把 preset 挂载 ONCE per process，每个命名它的会话通过把自己的 agent scope key 挂到该 mount 的 scope 下来加入。mount 的工具、提示词段落和投影单元只存在一次，覆盖所有加入的 agent——其插件按 Session/Agent 键化自己的状态，因此会话在同一个共享实例内保持隔离。”

作用域链是 agent → preset → global，最近者遮蔽最远者。这既避免了”每会话一份插件实例”的内存开销，又实现了会话级能力定制。
