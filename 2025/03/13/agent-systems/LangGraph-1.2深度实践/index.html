0. 版本基线与本地环境

0.1 为什么必须盯紧版本

LangGraph 在 2025‑10 发布 1.0，正式进入”2.0 之前不破坏向后兼容”的稳定承诺期。到 2026‑06，稳定线已到 1.2.4。1.x 相对 0.x 有几处会直接让旧代码报 Deprecation/ImportError 的变化，必须先记住：

主题 0.x 写法（已弃用） 1.x 正确写法
预制智能体 from langgraph.prebuilt import create_react_agent from langchain.agents import create_agent
自定义 State 允许 Pydantic / dataclass 只允许 TypedDict（继承 AgentState）
扩展点 散落的回调 / 自写节点 统一 Middleware 体系（before_model 等）
流式 v1/v2 事件 新增 v3 内容块流式（stream_events(version="v3")）
长线程开销 每步全量序列化 checkpoint 新增 DeltaChannel 仅存增量，长线程不再膨胀
持久执行 半成品 Durable Execution 成熟：节点级超时 / 错误恢复 / 优雅停机

记忆要点：1.x 把”快速搭智能体”的高阶能力下沉到了 LangChain（create_agent），把”底层图编排 / 持久化 / 多 actor”留在 LangGraph。两者共用同一个 LangGraph 运行时，可混用。

1. 核心抽象：State / Node / Edge / Command

LangGraph 只有几个核心概念，吃透它们，后面一切都是组合：

  • State（状态）：一个 TypedDict，是图里流动的”数据载体”。每个节点读它、返回”对它的更新”。
  • Reducer（归并器）：决定”节点返回的更新如何合并进 State”。默认是覆盖；add_messages 则是追加消息。
  • Node（节点）：一个函数 (state) -> dict（dict 是状态更新）。可以是纯 Python，也可以调 LLM、查库、发 MQTT。
  • Edge（边）：固定边 add_edge 或条件边 add_conditional_edges，决定下一步去哪。
  • Command：节点直接返回 Command(update=..., goto=...)，把”更新状态”和”路由”合二为一，是 1.x 推荐的高级写法。

3. 持久化与记忆：Checkpointer / Store / 断点续跑

这是 LangGraph 区别于”一次性 Chain”的核心价值，也是你做 OTA 这种长流程、可中断、可审计业务的根基。

  • Checkpointer：每执行一步就把 State 快照落盘。带来三件事——多轮记忆、崩溃后从断点恢复、时间旅行（回到任一历史步）。
  • thread_id：会话/任务的隔离键。同一个 thread_id 共享历史，不同 thread_id 互不干扰（天然适合”一车一线程”或”一次发布一线程”）。
  • Store：跨线程的长期记忆（KV + 向量检索），适合存”用户偏好””设备画像””历史故障知识”。

4. 人在回路（HITL）：interrupt 与审批闸门

OTA 里”灰度放量””全量推送””回滚”都是高危操作，必须有人工确认环节。LangGraph 用 interrupt() 把图”暂停”在某个节点，把控制权交还给外部（人/上游系统），人确认后再 Command(resume=...) 续跑。这一切建立在 Checkpointer 之上——暂停期间状态安全落盘，等几小时再恢复也没问题。

Demo 8：OTA 放量审批闸门（可暂停 / 可续跑）

工程要点：interrupt 的暂停是靠 checkpointer 持久化的，所以必须 compile 时传 checkpointer。上游（Spring/FastAPI）拿到 __interrupt__ 后写工单/推企业微信，人处理完再调你的”resume”接口。create_agent 也支持同样机制（在工具上加审批中间件），原理一致。

5. 中间件（Middleware）—— 1.x 的生产命门

Middleware 是 1.x 最重要的工程化能力：不改业务逻辑，在模型调用 / 工具调用的前后切入横切关注点。对应到你的场景：PII 脱敏、成本控制（动态选模型）、限流降级、审计日志、guardrail。

五个核心钩子：

钩子 时机 典型用途
@before_model 调模型前 裁剪历史、注入上下文、限流
@after_model 模型出结果后 内容审查、违规拦截
@wrap_model_call 包裹整个模型调用 动态选模型、重试、降级
@wrap_tool_call 包裹工具调用 错误兜底、权限校验、审计
@dynamic_prompt 生成系统提示 按角色/上下文动态 prompt

Demo 9：三合一中间件（脱敏 + 成本路由 + 审计）

中间件按列表顺序形成”洋葱模型”——请求由外向内进，响应由内向外出。LangChain 还内置了一批开箱即用的 middleware（如对话摘要 SummarizationMiddleware、PII、人审 HumanInTheLoopMiddleware、模型降级 fallback），生产优先复用内置，再写自定义。

6. 多智能体编排：Supervisor + 子图

单 Agent 工具一多就”注意力涣散”。生产做法是分而治之：一个 Supervisor（调度者）按任务把请求路由给若干”专家 Agent”，每个专家是独立子图、独立工具集、独立 prompt。LangGraph 里有两种主流形态：

  • Supervisor（中心调度）：一个上层图，节点是各专家；Supervisor 用 LLM 或规则决定下一个交给谁。适合诊断这种”先分诊、再会诊”的场景。
  • Swarm（去中心交接）：Agent 之间用 handoff 工具互相移交控制权。适合协作型任务。

下面用最透明的”手写 StateGraph + Command 路由”实现 Supervisor，便于你完全掌控（生产也可直接用 langgraph-supervisor 库）。

8.3 生产硬指标（别等出事才补）

  1. 持久化必上 Postgres：PostgresSaver/AsyncPostgresSaver + 连接池；InMemory 仅限本地。
  2. 节点级超时与错误恢复：1.x 支持给节点配超时、失败重试与优雅停机；外部工具（ClickHouse/MQTT/HTTP）一律设超时，并用 wrap_tool_call 兜底降级。
  3. Durability 模式：长流程用 durability="sync"（每步落盘，最安全）；高吞吐短任务可用 "async" 或 "exit" 换性能。
  4. 并发控制：fan‑out 的并行分支数、对下游 LLM/DB 的 QPS 要限流，避免把 ClickHouse/DeepSeek 打挂。
  5. 递归上限：config={"recursion_limit": 25} 防止 Agent 死循环烧 token。
  6. 密钥与配置：API Key 走环境变量/密钥管理，不进代码、不进 checkpoint。
  7. 可观测 + 评测：LangSmith 全链路追踪 + 对诊断结论建离线评测集，回归时跑分。
  8. 幂等：用稳定 thread_id（如 发布ID/VIN+日期）保证重试不重复执行副作用动作。

9. 【领域实战 A】产业物联网 OTA 智能灰度发布与回滚决策 Agent

9.1 业务问题

一次整车 OTA 发布的典型生命周期：选灰度车群 → 小比例放量 → 监控关键健康指标（升级成功率、回滚率、异常 DTC 增量、关键 KPI）→ 达标则逐级放量，劣化则自动建议回滚并触发人工审批。痛点在于：放量/回滚的判断规则多、数据源杂、且高危动作必须留审计与人审。

LangGraph 恰好提供：带状态的流程编排（逐级放量是天然的循环）+ 工具集成（接你的指标平台）+ HITL（回滚审批）+ checkpointer（全程审计、可中断恢复）。

  • 可恢复：配 PostgresSaver 后，进程重启或审批等待数小时都不丢状态。

11. 工程化落地清单、反模式与 0.x→1.x 迁移

11.1 生产上线 Checklist

  • 持久化用 PostgresSaver/AsyncPostgresSaver，连接池就绪，setup() 已执行
  • 每个外部工具（ClickHouse/MQTT/HTTP/LLM）都设了超时，并有 wrap_tool_call 降级兜底
  • 所有高危副作用动作（回滚/全量推送/远程指令）走 HITL interrupt 审批，且动作幂等
  • recursion_limit 设了上限；并行 fan‑out 分支数与下游 QPS 有限流
  • thread_id 用业务稳定键（工单号/发布ID/VIN），保证重试幂等、可审计
  • 长流程 durability="sync"；密钥走环境变量，绝不进 checkpoint
  • LangSmith 追踪开启；核心结论（诊断根因/放量决策）建了离线评测集
  • 结构化输出（Pydantic）作为对下游系统的契约，而非自然语言
  • 用 langgraph dev + Studio 做过可视化联调；用 langgraph build 出过镜像

11.2 高频反模式（踩过的坑）

  1. 忘记 reducer：messages 不加 add_messages → 多轮记忆丢失。需要累积的字段一律显式声明 reducer。
  2. 把大对象塞进 State：State 每步都会被 checkpoint 序列化。日志原文、二进制别进 State，存外部存储后在 State 里放引用（id/路径）。
  3. 工具无超时：一个卡死的 ClickHouse 查询能挂住整条链路。外部调用必设超时 + 兜底。
  4. HITL 不配 checkpointer：interrupt 依赖持久化，否则无法恢复。
  5. 单 Agent 塞几十个工具：注意力涣散、错调工具。超过 ~8 个工具就考虑拆多智能体或用中间件动态筛选工具。
  6. 在 0.x 思维里找 create_react_agent：1.x 用 langchain.agents.create_agent；自定义 State 必须是 TypedDict。
  7. 用自然语言做系统间契约：下游要解析就用结构化输出，别让 Spring 侧去正则抠模型的散文。

11.3 0.x → 1.x 迁移要点

项 迁移动作
from langgraph.prebuilt import create_react_agent 改为 from langchain.agents import create_agent（参数 prompt→system_prompt）
自定义 State 用了 Pydantic/dataclass 改写为 TypedDict（继承 AgentState 或 TypedDict）
自写的回调/钩子 迁移到 Middleware（before_model/after_model/wrap_*/dynamic_prompt）
结构化输出旧写法 用 response_format=ToolStrategy(Schema) 或直接传 schema 走 ProviderStrategy
老的 stream 事件 v1/v2 富前端可升级到 v3 内容块流式
长线程 checkpoint 偏大 升级到 1.x 自动受益于 DeltaChannel（仅存增量）

官方承诺 1.0→2.0 之间不破坏向后兼容，所以现在压到 1.2.x 是安全的长期投资；锁版本 langgraph==1.2.4 并在 CI 里跑评测回归即可。

C. 常见报错速查

报错 原因 / 解决
ImportError: cannot import name 'create_react_agent' 0.x 写法，改用 from langchain.agents import create_agent
interrupt 不暂停 / 无法 resume compile 时未传 checkpointer，或没用同一个 thread_id
多轮对话只剩最后一条消息 messages 字段缺 add_messages reducer
GraphRecursionError Agent 死循环，调高/排查 recursion_limit，检查工具是否始终不收敛
Postgres checkpointer 首次报表不存在 忘了执行 cp.setup()（幂等，首启调用一次）
结构化输出字段缺失/类型错 用 ToolStrategy(Schema) 提升兼容性；给 Field 写清 description
本地模型连不上 检查 LOCAL_BASE_URL（LM Studio :1234/v1，Ollama :11434/v1）与模型名

结语

这份指南的主线是：LangGraph = 带状态的图执行引擎，LLM 只是节点里的一种计算。把”状态/节点/边/Command”这套骨架吃透，再叠加 1.x 的四件生产武器——持久化（断点续跑/审计）、HITL（高危审批）、Middleware（横切治理）、多智能体（分诊会诊）——就足以支撑 OTA 放量决策、故障诊断专家系统这类真实业务。建议从领域 A、B 两个 POC 起步，把 mock 数据源逐个替换成你的 ClickHouse / 知识库 / 诊断网关，并接入现有 Gateway→WebFlux→FastAPI→LangGraph 链路，再用 LangSmith 建评测闭环持续打磨。
