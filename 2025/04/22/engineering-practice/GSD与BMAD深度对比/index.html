1. 背景：为什么需要 SDD 框架

1.1 Vibe Coding 的致命缺陷

2025 年初，Andrej Karpathy 提出了”Vibe Coding”的概念——开发者描述意图，AI 生成代码，无脑复制粘贴。这种模式在小型 Demo 和原型阶段效率惊人，但在真正的生产项目中，它会产生三类系统性缺陷：

上下文腐烂（Context Rot）：随着会话长度增加，AI 的输出质量呈非线性下降。Chroma 2025 年的研究对 18 个前沿模型进行测试，发现每一个模型都在上下文增长时出现性能退化。一个 200K Token 的上下文窗口可能在仅用到 50K Token 时就已经出现显著退化。实际观察表明，在 20-30 轮交互后就会出现可量化的腐烂，40 轮之后加速恶化。具体表现为：

  • 0–30% 上下文：峰值质量，输出全面、一致
  • 50%+：开始”简洁化”，切角、遗漏需求
  • 70%+：出现幻觉，遗忘早期规格说明

跨会话失忆：每次新会话 AI 都从零开始，前一个会话的架构决策、技术约定、踩过的坑统统消失。

规格漂移：没有明确的规格文件作为真理源，随着需求演进，代码逐渐与原始意图背离，产生无法追溯的技术债。

1.2 SDD 的解法

Spec-Driven Development 将结构化规格（Specification）而非即兴提示（Prompt）作为开发的源头，代码是规格的生成产物，而非随机意图的结果。截至 2026 年上半年，SDD 框架生态已形成 30+ 工具的竞争格局，其中 GSD 和 BMAD-METHOD 是关注度最高、社区最活跃的两个代表性框架，两者合计拥有超过 11 万 GitHub Star。

2.2 诞生脉络

GSD 于 2025 年 12 月由开发者 Lex Christopherson（化名 TÂCHES / glittercowboy）创建，最初定位是”给 Claude Code 的轻量工作流系统”。在不到 5 个月内积累了超过 6 万 GitHub Stars，2100+ 提交，138 名贡献者，57 个版本发布——这是开源历史上最快的增长曲线之一。

2026 年 4 月初，原作者 TÂCHES 突然从公众视野消失，其社交账号相继注销，一个与项目相关联的 $GSD 代币被公开指控为”拉地毯（rug-pull）”骗局。项目治理陷入危机。2026 年 5 月 22 日，社区贡献者 trek-e 发起分叉，以 MIT 许可证在 open-gsd/get-shit-done-redux 延续开发，代码经过独立安全审计，剔除了所有代币相关内容。

BMAD-METHOD 由 Brian Madison 创建，早于 GSD 出现，经历了从”提示工程工具”到”企业级敏捷 AI 框架”的完整演进，目前由其创立的 BMad Code LLC 进行商业化运营，采用 MIT 开源。v6 系列（2026 年 spring）引入了跨平台 Agent 团队、Skills 架构和 Web Bundles，标志着该框架的成熟期。

3. GSD 深度解析

3.1 核心设计哲学

GSD 的核心洞察只有一句话：

“复杂性在系统中，不在你的工作流里。”
— TÂCHES（GSD 原作者）

GSD 的设计哲学是将所有工程复杂性封装在框架内部，对用户暴露的只是几个简单命令。它明确将自己定位为反仪式（Anti-Ceremony）框架，直接点名 BMAD 的”迭代计划、故事点、干系人同步、回顾会”为不必要的企业剧场。

3.2 解决的核心问题：上下文腐烂

GSD 对上下文腐烂的解法是架构性的，而非提示性的：

  1. 主会话轻载：主会话始终保持在 30-40% 上下文占用，不在主会话中执行重度工作
  2. 子代理新鲜上下文：所有重度任务（研究、规划、执行、验证）由拥有全量 200K Token 干净上下文的独立子代理执行
  3. 文件系统状态机：通过 .planning/ 目录下的 STATE.md、CONTEXT.md 等结构化文件在会话间持久化状态，任何代理重置都不会丢失项目决策

3.5 Wave 并行执行机制

Wave 是 GSD 区别于串行 AI 工作流的关键特性：

  • 独立任务在 Wave 内并行执行
  • 有依赖关系的任务等待前序 Wave 完成后进入下一 Wave
  • 每个执行器均在全新的 200K Token 上下文中启动
  • 每个任务产生独立的原子提交，形成清晰的 Git 历史

3.6 质量门控体系

v1.34.0 引入四种规范化门控类型：

  • Pre-flight Gate：执行前的可行性验证
  • Revision Gate：执行中的修订触发
  • Escalation Gate：质量问题的上报机制
  • Abort Gate：不可恢复情况的中止

4. BMAD-METHOD 深度解析

4.1 核心设计哲学

BMAD 的核心主张是：

“通用 AI 产出通用结果。当你让 Claude 担任具有特定专长的高级架构师时，质量会发生质变。”

BMAD 不是上下文管理工具，而是开发过程的完整结构化——从构思、需求到架构、实现、测试、文档，每个阶段都有专属的 AI 专家人格（Persona）参与。

其设计信条是”AI 作为思维伙伴，而非思维替代”——Agent 不替你思考，而是通过结构化的敏捷流程激发你更好地思考。

4.2 规模自适应智能（Scale-Adaptive Intelligence）

BMAD 的核心差异化能力是根据项目复杂度自动调整规划深度和流程严肃性：

  • Bug 修复：轻量工作流，直接切入
  • 新功能：中等流程，PRD + 架构审查
  • 企业级平台：完整仪式，全 Agent 团队协作 + 冲刺规划 + 回顾

这使得团队无需在”流程过多”和”结构不足”之间二选一。

5.2 目标用户画像

GSD 的典型用户：

  • 独立开发者 / 小团队（1-5 人）
  • 追求快速交付，不愿承担仪式成本
  • 项目复杂度中等，但担心长时间会话的质量退化
  • 熟悉 Claude Code，希望在现有工具上叠加工作流

BMAD 的典型用户：

  • 中等规模团队（5-20 人）
  • 采用敏捷方法论，习惯角色分工
  • 项目架构错误代价高昂（监管领域、绿地平台）
  • 需要完整的 SDLC 产物链用于审计和传承

7.3 实测案例引用

来自独立的”三款规格驱动工具实测”（2026 年 4 月）：

BMAD Full 在迭代精化上得分 5/5。对抗性代码审查（/bmad-bmm-code-review）在传递前就能发现问题，测试中捕获了标准审查会遗漏的内容。Party Mode 在实现前让多个 Agent 人格过一遍设计。对于合适的项目，这种复杂性税是值得的。

GSD 在同一对比中被标注为”独立开发者的 Vibe Coding 工具”（相对 BMAD 的企业级定位），其 /gsd-quick 的低摩擦路径得到好评，但深度文档能力被认为不及 BMAD。

敏捷文化 轻敏捷或无流程 已有敏捷文化 正在建立敏捷

8.2 典型场景判断

明确选 GSD 的场景：

  • 你是独立开发者，在 Claude Code 上构建复杂 SaaS
  • 长会话后 AI 质量明显退化，这是你的首要痛点
  • 不需要 PRD 文档或架构文档，但需要 Git 历史可追溯
  • 希望在本地模型（Ollama、LM Studio）或计量 API 上使用
  • 项目规格明确，主要问题是执行一致性

明确选 BMAD 的场景：

  • 你有 5 人以上的开发团队，有角色分工
  • 构建核心业务系统，架构错误会造成数月的技术债
  • 监管合规场景，需要完整的决策追溯链（PRD → 架构 → Story → 代码）
  • 团队已经在使用敏捷，希望 AI 融入而非替换现有流程
  • 明确需要多视角（PM + 架构师 + QA）交叉验证

考虑轻量替代的场景：

  • 单个 Bug 修复或小型功能：直接 Claude Code + CLAUDE.md
  • 需要 CI/CD 深度集成的场景：考虑 OpenSpec 或 Kiro
  • 多 AI 工具混用（Copilot + Claude Code + Amazon Q）：考虑 SpecKit

13. 高级策略：混合使用

社区实践表明，GSD 和 BMAD 并非竞争关系，而是解决相邻问题的互补工具，可以叠加使用。

13.1 层次模型

社区共识：gstack 用于战略决策，GSD 用于上下文稳定性，Superpowers 用于执行纪律——三者作为互补层而非竞争关系。

13.2 BMAD + GSD 协作工作流

这个组合获得了 BMAD 的规格严谨性和 GSD 的执行效率，代价是学习两套工具的门槛。

14. 对 Synapse 项目的选型建议

基于你的 Synapse（helmsman 代号）Agent 平台项目的具体情况：

14.1 项目特征分析

  • 规模：Solo 开发，已有完整规格套件（PRD + 15 个 ADR + GSD 交付文档）
  • 复杂度：LangGraph 内存架构 + PostgreSQL 持久化 + 本地 Embedding + DeepSeek-V4
  • 首要风险：长 Claude Code 会话的上下文腐烂（多个相互关联的 Agent 层）
  • 文档就绪：PRD 和架构设计已完成，不需要 BMAD 的规划 Agent

14.2 推荐方案

主推：GSD Redux（open-gsd/get-shit-done-redux）

理由：

  1. 规格文件已就绪，Synapse 的文档体系完全可以作为 GSD 的规格输入，跳过 BMAD 规划阶段
  2. 独立开发的上下文腐烂风险是核心痛点，GSD 的新鲜子代理机制直接解决
  3. Wave 并行执行对 LangGraph 各组件（memory、persistence、embeddings、API layer）的并行实现有直接收益
  4. 支持 DeepSeek-V4 通过 OpenRouter 接入，与本地模型策略兼容

配合策略：

  • 使用 BMAD 的 Party Mode 思路进行关键架构决策的 Pre-mortem（邀请”架构师”和”安全审查者”角色质疑设计），但不走完整 BMAD 流程
  • 将现有 15 个 ADR 组织为 GSD 的 CONTEXT.md 和每阶段的 DISCUSS.md 输入
  • 使用 jnuyens/gsd-plugin（Claude Code 插件版）以获得更好的 Claude Code 原生集成

15. 总结

15.1 结论性判断

GSD 和 BMAD 不是同一问题的两种答案，而是两个不同问题的专属答案：

GSD BMAD
它解决的核心问题 AI 在复杂项目中的上下文退化 AI 在复杂项目中的流程无序
最佳比喻 专业的”工程项目经理”，确保每个工人都在峰值状态下工作 专业的”虚拟全栈团队”，每个角色都有其职责
一句话定位 让 Claude Code 从始至终保持高质量 让 AI 成为你完整敏捷团队的成员

对于绝大多数独立开发者和小团队：从 GSD 开始（使用 Redux 社区版），当你感到需要更多架构纪律和文档完整性时，引入 BMAD 的特定工作流（至少使用 Quick Flow）。

对于中等规模团队和企业项目：从 BMAD 开始建立规范，用 GSD 优化长周期实现阶段的上下文管理，用 Superpowers 强化执行纪律。

15.2 行业大趋势

无论选择哪个框架，它们都在指向同一个论断：当前的前沿编码模型已经足够强大，能够生产生产级代码——问题是它们被提示和驱动的方式使其无法始终如一地做到。每个框架以不同方式回答同一个问题：哪种干预最重要？ 上下文纪律（GSD）、角色分工（BMAD）、规则约束（Superpowers）。

未来的竞争焦点不再是哪个 LLM 写代码更好，而是哪个系统能最有效地协调 AI 代理的工作。SDD 框架生态代表了这个方向的最早期、最具活力的探索。
