Nacos 3.x：从服务注册到 MCP / A2A 注册中心

Nacos 3.x 相对 2.x 的变化与升级清单、Spring Cloud Alibaba 最小正确配置、注册失败决策树、MCP 与 A2A 注册中心的用法边界及生产部署建议。

Flywhl 16 分钟 更新于 2026.09 #MCP#Nacos#Spring Cloud Alibaba

先读结论

  1. 3.x 服务端要求 JDK 17，控制台独立到 8080，控制台与 Admin API 默认开启鉴权，密钥必须自己配置。
  2. Spring Boot 3 下用 spring.config.import 接入配置中心，bootstrap.yml 默认不再加载。
  3. 排查注册失败先找 register finished 日志，再按连不上、没触发、注册错位置、注册了但调不通四类分流。
  4. MCP / A2A Registry 解决的是目录、版本与元数据治理，不替代网关的鉴权与流量控制。

Nacos 3.0.0 于 2025-04-25 GA，3.1.0 于 2025 年 9 月下旬发布。这一代有两条主线：一条是把 2.x 积累的安全与运维问题做了一次「破坏性收口」（JDK 17、鉴权默认开启、API 重新分类、控制台独立部署）；另一条是把 Nacos 从微服务注册中心扩展成 AI 资源的注册中心（MCP Registry、A2A Registry）。

本文写于 3.1.0 发布后不久，面向两类读者：正在把 2.x 升级到 3.x 的团队，以及在 Spring Cloud Alibaba 里接 Nacos 却「服务注册不上」的开发者。内容依次是：3.x 的变化与升级清单、最小正确配置、注册失败决策树、MCP / A2A 注册中心的用法与边界、生产部署建议。

3.x 相对 2.x 改了什么

维度 2.x 3.x 升级影响
运行时 服务端 JDK 8+ 服务端 JDK 17、Spring Boot 3.4；Java 客户端仍支持 JDK 8 服务端镜像或主机要换 JDK，业务应用不必
端口 控制台与服务同在 8848（/nacos） 服务端 8848，控制台独立为 8080（nacos.console.port）；gRPC 9848 / 9849 不变 反代、防火墙、书签里的控制台地址要改

鉴权的三个开关与两组密钥

3.1 默认配置（conf/application.properties）中与鉴权相关的部分：

  • token.secret.key 是签发登录 token 的密钥，要求 Base64 编码、原始长度不少于 32 字节。用 openssl rand -base64 32 生成，集群内所有节点必须一致。不要使用文档注释里的示例值，也不要沿用网上教程里的固定串。
  • server.identity.key/value 用于节点间请求的身份识别，同样集群内一致、不可泄露。
  • 生产环境建议把客户端 API 鉴权也打开（nacos.core.auth.enabled=true），并为每个应用建独立账号、只授予所需命名空间的读写权限。打开之前先确认所有客户端都配置了用户名密码，否则会在同一时刻集体注册失败。

默认账号必须处理：新部署首次访问 http://<控制台>:8080/ 会要求为 nacos 用户设置密码；从 2.3 及更早版本升级上来的数据库，users 表里的 nacos 用户可能仍是早年公开的默认密码，升级后第一件事是改掉它。

2.x → 3.1 升级清单

  1. JDK：服务端节点换 JDK 17；自建镜像的基础镜像同步更换。
  2. 数据库：用新发行包的 conf/mysql-schema.sql 与现有库对比补齐缺失的表，再执行升级手册中的增量语句。从 2.1 及以后升级，至少要给 his_config_info 增加 publish_type、gray_name、ext_info 三列；从 2.0 升级还要给配置相关表增加 encrypted_data_key 列。先改库，再启动新版本。
  3. 配置键改名：server.port → nacos.server.main.port，server.servlet.contextPath → nacos.server.contextPath。直接拿 2.x 的 application.properties 覆盖会让这些设置静默失效。
  4. 鉴权密钥：按上一节填好 token 密钥与服务身份键值。
  5. 控制台入口：控制台改到 8080，更新反向代理与防火墙；如需隔离，可单独部署 console 形态。
  6. 运维脚本：调用 /nacos/v1/... 运维接口的脚本迁移到 v3 Admin API（或官方的 maintainer SDK）。3.1 的默认配置中，旧客户端 API 的兼容开关默认开启，旧 Admin / 控制台 API 的兼容开关默认关闭。
  7. 客户端：2.x 与 3.x 客户端都能连 3.x 服务端；1.x 客户端依赖已废弃的 v1 HTTP API，升级服务端之前先把业务侧客户端升到 2.x 以上。
  8. 命名空间：3.x 启动时会把空 ID 命名空间与 public 做兼容同步（nacos.config.namespace.compatible.mode，默认开启），首次启动可能较慢，看日志确认迁移完成后再放量。
  9. 集群：逐台滚动升级；如果在 3.0.0 上已经登记过 MCP 服务，升级到 3.0.1 及以上需要先用社区提供的迁移工具把旧 MCP 数据迁到 public 命名空间。

Spring Cloud Alibaba 最小正确配置

版本对应

2025.0.0.0（2025-10-17） 2025.0 3.5.x 3.0.3

两条线都能连接 3.x 服务端。Spring Boot 与 SCA 版本不匹配时，常见表现是启动期的类找不到或自动配置冲突，先对齐版本，再谈注册问题。

依赖

同时需要按 Spring Cloud 官方方式导入对应版本的 spring-cloud-dependencies BOM。

application.yml

几个要点：

  • Spring Cloud 2020.0 起（Spring Boot 3 对应的版本都在其后），bootstrap.yml 默认不再加载，写在里面的 Nacos 配置等于没写。统一放进 application.yml，配置中心用 spring.config.import 接入。没有写 spring.config.import 又引入了 config starter，启动会直接报缺少该属性的错误。
  • namespace 填的是命名空间 ID。控制台新建命名空间时可以自定义 ID，建议直接用 dev / test / prod 这类可读 ID，从根源上避免「填了名称」的问题。3.x 中默认命名空间的 ID 是 public。
  • 客户端除了 8848 还要能连 gRPC 端口，端口号 = 主端口 + 1000（默认 9848）。9849 与 7848 是集群节点之间用的，客户端不需要。
  • 自动注册发生在 Web 容器启动完成之后。不是 Web 应用（例如 spring.main.web-application-type=none 的批处理服务）不会自动注册。

分支说明与验证命令

1. 连不上（Client not connected、请求超时）

最隐蔽的是 Docker 端口映射：把服务端映射成 18848:8848 时，客户端会按 18848 + 1000 = 19848 去连 gRPC，所以必须同时映射 19848:9848。只映射 8848 的结果是 HTTP 探活正常、gRPC 连接失败。

2. 鉴权拒绝

服务端开启了客户端 API 鉴权，而应用没配置 username / password，或账号没有该命名空间的权限。用同一账号手动登录并查询验证：

3. 注册流程没有被触发

没有报错、也没有 register finished，通常是下面四种之一：没引 spring-cloud-starter-alibaba-nacos-discovery；配置写在未加载的 bootstrap.yml 里；显式关闭了 spring.cloud.nacos.discovery.register-enabled 或 enabled；应用不是 Web 应用。@EnableDiscoveryClient 在新版本中不是必需的，加不加都不是这类问题的原因。

4. 注册了但在别的位置

日志里有 register finished，控制台却看不到，先看控制台左上角当前选中的命名空间，以及日志中的分组。namespace 填成了显示名称时，实例可能被注册到一个控制台列表里不存在的命名空间 ID 下，于是「注册成功、控制台看不到」。

5. 能看到但调不通

应用跑在容器里时，默认注册的往往是容器网桥 IP，其他主机上的调用方访问不到；多网卡主机可能选中了错误的网卡。显式指定：

MCP Registry 与 A2A Registry

它解决什么问题

当团队里的 MCP Server 和 Agent 从几个变成几十个，会出现和微服务早期一样的问题：地址写死在各个客户端配置里、版本升级要逐个通知、工具描述改一个字就要重新发布、测试和生产混在一起。Nacos 3.x 把这些问题放回它擅长的模型里解决：命名空间隔离环境，版本管理支持灰度，元数据集中存放且可以动态修改。

MCP Registry

3.0 起，Nacos 可以登记 MCP Server 的元数据：名称、版本、协议类型（stdio、SSE、streamable HTTP）、访问端点，以及工具列表与描述。工具描述、启停状态可以在控制台动态修改，不必重新发布 MCP Server。3.0.1 起支持多命名空间与多版本管理（可将某个版本设为最新版，便于灰度）。

MCP Server 进入 Nacos 的几种方式：

方式 做法 适用
控制台手工登记 填写端点或 stdio 启动配置、工具定义 第三方或存量 MCP Server
Spring AI Alibaba 自动注册 引入 spring-ai-alibaba-starter-nacos-mcp-server，配置 spring.ai.alibaba.mcp.nacos.server-addr、namespace、username、password、registry.enabled=true Java 自研 MCP Server
Python 自动注册 nacos-mcp-wrapper-python，用 NacosMCP 代替原生 server，NacosSettings 中设置 SERVER_ADDR、NAMESPACE、USERNAME、PASSWORD Python 自研 MCP Server
导入（3.1） JSON 文件导入，或从官方 MCP Registry 一键导入 复用社区已有的 MCP Server

消费侧常用 nacos-mcp-router，它本身是一个 MCP Server，有两种模式：

  • router 模式（默认）：向大模型暴露 search_mcp_server、add_mcp_server、use_tool 三个工具，让 Agent 按任务在 Nacos 中检索并调用合适的 MCP Server，而不是把几十个 Server 的工具一次性塞进上下文；
  • proxy 模式（MODE=proxy）：把 stdio 或 SSE 协议的 MCP Server 转换成 streamable HTTP 对外提供。

此外，Nacos 可以按官方 MCP Registry 规范对外提供标准的注册表 API（如 /v0/servers，具体路径以所用版本文档为准），供兼容该协议的客户端直接查询。这部分需要额外端口与资源，默认关闭：

3.1 已跟进官方注册表协议 2025-09-16 版本。这个协议仍处于 v0 阶段、演进很快，对接它的客户端要固定版本并关注变更。

A2A Registry（3.1 新增）

A2A 协议中，每个 Agent 用 AgentCard 描述自己：名称、描述、版本、服务地址、协议版本、技能列表（skills）、提供方等。Nacos 3.1 把 AgentCard 作为一等资源管理，AgentCard 与 Agent 的服务端点分开登记，通过「名称 + 版本」关联，同一命名空间内 Agent 名称必须唯一。

登记与发现的方式：

  • 控制台：Agent 管理 → Agent 列表 → 创建 Agent，填写 AgentCard。
  • Admin API：
  • Java SDK：AiFactory.createAiService(properties) 得到 AiService，用 releaseAgentCard 发布、registerAgentEndpoint 登记端点、getAgentCard / subscribeAgentCard 发现与订阅（可用的最低客户端版本以官方文档为准）。
  • Spring AI Alibaba：spring-ai-alibaba-starter-a2a-server、spring-ai-alibaba-starter-a2a-registry、spring-ai-alibaba-starter-a2a-client，配置前缀 spring.ai.alibaba.a2a.nacos.*（server-addr、username、password、discovery.enabled）。

适用边界

适合 不适合或需要额外措施
MCP Server / Agent 数量多，需要统一目录、版本与环境隔离 只有两三个 MCP Server，静态配置更简单
已有 Nacos 集群和 Java / Spring 技术栈，希望复用运维体系 需要调用鉴权、限流、审计：Nacos 只管注册与元数据，调用链路要交给网关
需要不发版就调整工具描述、启停某个工具 把「谁能改工具描述」当成小事：描述会直接进入大模型上下文，能改描述就能影响 Agent 行为，控制台权限必须收紧
内网 Agent 之间相互发现 跨组织公开发布：AgentCard 中的 url 与技能描述需要单独做信息脱敏与访问控制

反例：把 MCP Registry 当成 MCP 网关，期望它帮你做认证与流量转发。它存的是「去哪里找、长什么样」，真正的调用仍是客户端直连 MCP Server，或经 nacos-mcp-router、网关代理。

生产部署建议

拓扑

  • 集群规模：3 个节点起步，奇数个。节点间 Raft（7848）与集群 gRPC（9849）只在节点之间开放。
  • 数据源：外置 MySQL，并由数据库侧负责高可用（主从切换、备份）；嵌入式 Derby 只用于单机试用。
  • 入口：客户端配置完整的节点列表，或经负载均衡访问。经负载均衡时，8848 与 9848 必须同时转发，且对外端口保持「主端口 + 1000」的关系。
  • 控制台：只对运维网段开放 8080，或用 console 形态单独部署在运维网络里。
  • 绝不暴露公网：Nacos 历史上出现过多次鉴权绕过类漏洞，注册中心与配置中心只应存在于内网。

上线前自检

  • token 密钥与服务身份键值已替换为随机值，且集群内一致；
  • nacos 管理员密码已初始化或修改，不存在历史默认密码；
  • 客户端 API 鉴权已开启，每个应用独立账号、最小权限；
  • 8848 / 9848 可从应用网段访问，7848 / 9849 仅节点间可达，8080 仅运维网段可达；
  • MySQL 有备份与恢复演练；
  • 用一个测试服务走通注册、发现、配置下发、配置变更推送全流程。

总结

升级到 Nacos 3.x 的主要成本在鉴权与 API 收口：密钥必须自己配置，控制台换了端口，旧运维接口要迁移。业务侧的注册问题大多与版本无关，先找 register finished，再按连不上、没触发、注册错位置、注册了调不通四类分流即可。MCP 与 A2A Registry 是 3.x 最大的增量，适合 Agent 数量多、需要统一治理的团队；它负责目录与元数据，调用安全仍要交给网关与权限体系。

2026-09 补记：3.2 的 AI Registry 三件套与 3.3 RC

  • 3.2.0（2026-03-27）：新增 Skill Registry 与 Prompt Registry，与 MCP Registry 合称 AI Registry 三件套，Agent 可用的技能与提示词也纳入版本化、可灰度的集中管理；新增 OIDC / OAuth2 鉴权插件，可对接企业统一身份。同一版本起，v1 / v2 旧 API 移出主发行包，需要时通过独立的 nacos-api-legacy-adapter 恢复，仍依赖旧 API 的 1.x 客户端要在这之前完成升级。3.2 的库表新增了 AI 相关表（如 ai_resource、ai_resource_version），升级前同样要先执行增量 SQL。
  • 3.2.4（2026-08-27）：当前推荐的生产稳定线。滚动升级到该版本前，需确认所有节点的 nacos.core.auth.server.identity.key/value 一致；此版本起已废弃的 v3 接口默认返回 410，可用兼容开关临时恢复。
  • 3.3.0-RC（2026-09-21）：提供协议中立的 Agent 注册，不再只围绕 A2A。按官方镜像说明，3.3 起客户端 API 鉴权默认开启（未设置 NACOS_AUTH_ENABLE 时即为开启），未配置账号的客户端会直接注册失败，这是升级 3.3 时注册失败决策树中「鉴权拒绝」分支最可能的来源。
  • 2.x：仍在维护（2.5.4），暂不需要 AI 能力、又受 JDK 版本约束的存量系统可以继续留在 2.5 线，但应开启鉴权并替换所有默认密钥。
