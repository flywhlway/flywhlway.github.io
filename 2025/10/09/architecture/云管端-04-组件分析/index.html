A · 编排与 Agent 组件族

A1 · Agent（智能体）

  • 介绍：具备目标、可感知上下文、能自主选择动作并观察结果的执行体。区别于”函数”的关键在于它自己决定下一步做什么。
  • 原理：以 LLM 为决策核心的循环：观察 → 思考 → 动作 → 观察（ReAct 范式）。每轮把历史轨迹回灌进上下文，直到满足终止条件。
  • 设计原因：把”多步不确定任务”从硬编码流程中解放出来。传统 Workflow 要求穷举分支，Agent 只需给定目标与工具。
  • 业内实现方式：ReAct（思考+行动交替）、Plan-and-Execute（先整体规划再执行）、Reflexion（失败后自我反思重试）、Multi-Agent 协作（分工+仲裁）。
  • 企业最佳实践：强制三重预算（最大轮次、最大工具调用、最大耗时/Token）；执行轨迹全量上报；对话式与任务式 Agent 分开设计与评测。
  • 推荐开源：LangGraph（状态图，可控性最好）、AutoGen（多 Agent 会话）、CrewAI（角色分工）、LlamaIndex Workflows、Spring AI / Spring AI Alibaba（Java 栈）。
  • 推荐商业：各云厂商 Agent 平台、企业 Agent 编排产品。
  • 优缺点：✅ 灵活、可处理长尾；❌ 不确定性高、成本不可预测、调试困难。
  • 适用场景：多步任务、需工具组合、需求分支多且难穷举。不适用：确定性强、SLA 严格、单步即可完成的场景（此时 Workflow 更优）。

A2 · Planner（规划器）

  • 介绍：把用户输入映射为「意图 + 落域 + 执行计划」的决策组件。本架构中它是独立服务（图示）。
  • 原理：两阶段——① 判别式意图分类（快、便宜、可评测）；② 生成式任务拆解（仅复杂意图触发）。
  • 设计原因：若让每个 Agent 自行判断”该不该我处理”，会出现重叠与遗漏；集中式 Planner 保证意图口径统一。
  • 业内实现方式：分类器路由（BERT 类模型/小模型）、语义相似度路由（意图向量库检索）、LLM 路由（函数调用选 Agent）、混合路由（先向量召回候选，再小模型判别）。
  • 企业最佳实践：混合路由 + 置信度阈值 + 澄清追问。高置信直接落域；中置信并行探测两个域；低置信反问用户。意图分类禁用大模型（延迟与成本双杀）。
  • 推荐开源：LangGraph 条件边、语义路由库（semantic-router）、自研分类器 + 向量召回。
  • 推荐商业：NLU 平台的意图识别模块。
  • 优缺点：✅ 口径统一、可评测、延迟低；❌ 中心化单点、意图体系需持续治理。
  • 适用场景：多业务域共享入口的平台型架构（本架构正是此类）。

A3 · Router（路由器）

  • 介绍：泛指按策略选择后端的组件，本架构中存在三处路由：意图→Agent（Planner）、请求→模型（LLM 网关）、任务→端/云（System Agent 落点决策）。
  • 原理：策略函数 f(请求特征, 后端状态, 约束) → 后端。约束包括时延预算、成本预算、隐私标记、能力可用性。
  • 设计原因：把”选择逻辑”从业务代码中抽出，使之可配置、可灰度、可 A/B。
  • 业内实现方式：静态规则表、加权随机、成本感知路由（便宜模型优先，失败升级）、质量感知路由（用小模型预测难度再选大小模型）、延迟感知路由。
  • 企业最佳实践：路由策略必须可热更新且带 A/B 能力。同时记录 route_reason，否则线上”为什么走了这个模型”无法解释。
  • 推荐开源：LiteLLM Router、RouteLLM（难度预测路由）、Envoy/Higress 路由插件。
  • 推荐商业：Portkey、云厂商 AI 网关。
  • 优缺点：✅ 成本与体验可调；❌ 策略复杂后难以推理，需强可观测支撑。
  • 适用场景：多模型/多后端/端云协同场景。

A4 · Workflow（工作流）

  • 介绍：确定性的多步执行编排，节点与边预先定义。
  • 原理：DAG 或状态机驱动，每节点输入输出契约固定，支持重试、补偿、持久化。
  • 设计原因：Agent 不确定性不适合强 SLA 场景。Workflow 与 Agent 应共存而非二选一。
  • 业内实现方式：DAG 引擎、状态机、持久化工作流（Durable Execution）。
  • 企业最佳实践：“外层 Workflow + 内层 Agent” 是最稳的组合：流程骨架确定（可靠），单个节点内允许 Agent 自主（灵活）。
  • 推荐开源：Temporal（持久化执行，最成熟）、LangGraph、Airflow（离线）、Dify/n8n（低代码）。
  • 推荐商业：企业流程编排平台。
  • 优缺点：✅ 可靠、可观测、可重放；❌ 分支需穷举、长尾场景成本高。
  • 适用场景：车控指令、订单类操作、需要事务与补偿的业务动作。

A5 · Skill（技能）

  • 介绍：面向意图的能力封装单元，是注册中心三类对象之一（图示 Skills 管理）。
  • 原理：Skill = 触发条件（意图示例）+ 执行体（Workflow/Agent/Tool）+ 输入输出契约 + 权限声明。
  • 设计原因：Tool 粒度太细（模型难以从上百个工具里选对），Agent 粒度太粗（无法复用）。Skill 是面向意图的中间粒度。
  • 业内实现方式：Skill 清单 + 描述向量化 + 按意图召回；渐进式披露（先给类目再展开）。
  • 企业最佳实践：注册时强制提供 ≥10 条正例意图 + ≥5 条反例（”什么时候不要用我”）。反例是提升路由准确率最有效且最被忽视的手段。
  • 推荐开源：自研 Skill Registry；参考 MCP 的 tool 描述规范扩展。
  • 优缺点：✅ 路由准确率高、可复用；❌ 需要治理（冲突检测、描述质量）。
  • 适用场景：能力数量超过 30 个的平台，必须引入 Skill 层。

A6 · MCP（Model Context Protocol）

  • 介绍：把工具、资源、提示词以标准协议暴露给模型运行时的开放协议。本架构中 MCP 管理位于注册中心（图示）。
  • 原理：Client-Server 模型。Server 声明 tools / resources / prompts；Client（Agent 运行时）发现并调用。传输层支持 stdio 与 HTTP/SSE。
  • 设计原因：解决 N×M 集成问题——N 个 Agent 对接 M 个工具，从 N×M 份适配代码降为 N+M。
  • 业内实现方式：官方 SDK（多语言）；企业内部把存量 API 封装为 MCP Server；MCP Gateway 做统一鉴权与审计。
  • 企业最佳实践：三条铁律——① 最小权限（每个 MCP Server 独立凭据与出网白名单）；② 版本锁定（三方 Server 变更需重新审核）；③ 输出隔离（工具结果视为不可信输入，不与系统指令同区）。
  • 推荐开源：MCP 官方 SDK、MCP Gateway 实现、社区 Server 生态。
  • 优缺点：✅ 生态快速增长、集成成本低；❌ 规范仍在演进、安全模型需自行加固。
  • 适用场景：需要接入大量外部能力的平台。风险提示：MCP 是当前提示注入的主要入口，详见 12 文档。

A7 · Tool（工具）

  • 介绍：模型可调用的确定性函数，含名称、描述、参数 Schema。
  • 原理：模型输出结构化调用意图（function call），运行时执行并把结果回灌上下文。
  • 设计原因：模型不擅长计算、查询实时数据、执行副作用操作；工具补齐这些能力。
  • 企业最佳实践：工具描述面向模型而非面向人写（说明何时用、何时不用、参数含义与取值范围）；参数 Schema 严格（枚举优于自由文本）；结果精简（不要把 5000 行 JSON 回灌上下文）。
  • 优缺点：✅ 确定、可测；❌ 描述质量直接决定调用正确率。
  • 适用场景：全场景基础设施。

A8 · A2A（Agent-to-Agent 通信）

  • 介绍：Agent 之间的寻址、任务传递与协作协议。本架构中 Agent 网关承担 A2A 桥接（图示圈注）。
  • 原理：Agent 具备可发现的身份与能力声明，通过标准消息格式传递任务与结果，支持异步与流式。
  • 设计原因：端侧 Agent 需调用云端 Agent；跨业务域 Agent 需协作。若各自点对点对接，拓扑不可维护。
  • 业内实现方式：中心化桥接（本架构选择）、消息总线、A2A 协议规范实现。
  • 企业最佳实践：每跳独立鉴权，不信任传递身份。A2A 极易成为越权通道：Agent A 有权限，Agent B 借 A 的身份调用高权限能力。必须在桥接层做调用白名单 + 权限交集计算。
  • 推荐开源：A2A 协议实现、消息总线（NATS/Kafka）+ 自研寻址层。
  • 优缺点：✅ 解耦、可扩展；❌ 增加一跳延迟、需强安全设计。
  • 适用场景：端云协同、多域 Agent 协作。

B · 记忆组件族

B1 · Short-Term Memory（短期记忆）

  • 介绍：会话内的上下文，含最近对话轮次与临时状态。
  • 原理：会话 KV 存储 + 滑动窗口 + 摘要压缩。窗口满时把最早轮次压缩为摘要。
  • 设计原因：模型上下文窗口有限且长上下文显著增加成本与延迟；同时”最近的”比”久远的”更重要。
  • 企业最佳实践：Redis 存储，TTL = 会话周期；滚动摘要（每 N 轮压缩一次，摘要与原文双存以支持回溯）；摘要必须保留实体与数字（这是压缩最容易丢失且最致命的信息）。
  • 推荐开源：Redis、LangGraph Checkpointer。
  • 优缺点：✅ 简单高效；❌ 压缩必然有损。
  • 适用场景：全部对话场景。

B2 · Long-Term Memory（长期记忆）

  • 介绍：跨会话持久化的用户事实与偏好。
  • 原理：从对话中抽取事实 → 去重与冲突合并 → 带置信度与时效存储 → 检索时按相关性召回。
  • 设计原因：让平台”记得住”，是个性化体验的基础。
  • 业内实现方式：向量记忆（语义召回）、图记忆（实体关系）、结构化记忆（字段化偏好）、混合记忆（推荐）。
  • 企业最佳实践：事件溯源 + 物化视图——保存原始来源（哪一轮对话说的），物化为当前有效记忆。这样才能支持原图圈注的”回溯干预”。记忆必须带 confidence、source_trace_id、valid_until。
  • 推荐开源：Mem0、Zep、自研（PG + pgvector + 事件表）。
  • 优缺点：✅ 长程个性化；❌ 记忆污染风险高、冲突处理复杂。
  • 适用场景：高频复用、强个性化产品。详见 08 文档。

B3 · User Profile（用户画像）

  • 介绍：结构化的用户特征集合（图示”用户画像”）。
  • 原理：在线行为埋点 → 离线聚合计算 → 特征存储 → 在线按需切片读取。
  • 设计原因：长期记忆是”事实条目”，画像是”统计特征”，两者互补。画像适合稳定倾向（偏好类型、活跃时段），记忆适合具体事实。
  • 企业最佳实践：按意图只取相关字段（画像可能有 200 个字段，一次注入 5 个）；画像更新走离线批处理，避免在线计算；敏感字段单独授权。
  • 推荐开源：特征平台（Feast）、自研 PG/HBase 特征表。
  • 优缺点：✅ 稳定、可解释；❌ 更新有延迟、冷启动无数据。
  • 适用场景：个性化推荐、语气与内容偏好适配。

B4 · Memory Recall（记忆召回）

  • 介绍：按当前查询选出相关记忆的过程（图示中记忆模块的核心动作）。
  • 原理：查询改写 → 向量检索 + 元数据过滤 → 时效与置信度加权 → Top-K 截断 → Token 预算裁剪。
  • 企业最佳实践：召回必须做时效衰减（半年前的偏好权重应低于上周）；召回结果附带来源以便回溯；召回数量硬上限（记忆过多会挤占知识空间并引入噪声）。
  • 优缺点：✅ 精准个性化；❌ 召回错误的记忆比没有记忆更糟。
  • 适用场景：全部有记忆的场景。

B5 · Memory Manager（记忆管理器）

  • 介绍：负责记忆抽取、写入、合并、失效、可视化与人工干预的管理组件（对应图示”可视化 + 回溯干预”）。
  • 原理：异步事件驱动。对话结束触发抽取任务 → 候选事实 → 与既有记忆比对（新增/更新/冲突）→ 写入并记录变更日志。
  • 设计原因：记忆写入若同步执行会拖慢主链路；且抽取需要模型调用，成本与延迟都不适合在线。
  • 企业最佳实践：记忆写入异步 + 幂等 + 可审计；提供运营界面查看某用户全部记忆、来源与生效状态，并支持单条失效与批量清空；对高风险记忆（涉及身份、健康、财务倾向）设置人工复核。
  • 优缺点：✅ 可解释可修复；❌ 建设成本高（这正是原图将其圈注为重点的原因）。
  • 适用场景：面向真实用户长期运营的产品，必备。

B6 · Context Compression（上下文压缩）

  • 介绍：在保持信息量的前提下减少 Token 的技术集合。
  • 原理：抽取式（保留关键句）、生成式（摘要重写）、选择式（相关性过滤丢弃无关片段）、结构化（转为表格/字段）。
  • 设计原因：上下文预算是硬约束（见 01 文档 3.4）。”检索越多效果越好”是错觉——无关内容会稀释注意力。
  • 企业最佳实践：结构化压缩优于生成式摘要（无幻觉风险、Token 效率更高）；压缩前后都记录，便于归因；用小模型做压缩（成本 1/20）。
  • 推荐开源：LLMLingua（提示压缩）、自研结构化模板。
  • 优缺点：✅ 直接降本降延迟；❌ 有损，需评测保障。
  • 适用场景：长会话、多轮工具调用、长文档问答。

C · 知识与检索组件族

C1 · Embedding（向量化）

  • 介绍：把文本映射为稠密向量以支持语义检索。
  • 原理：编码器模型输出定长向量，语义相近的文本在向量空间距离更近。
  • 企业最佳实践：中文场景务必选中文优化模型；向量维度与效果非线性（1024 维往往不比 768 维好多少，但存储与检索成本翻倍）；Embedding 模型一旦更换必须全量重建索引，因此选型要慎重且记录版本。
  • 推荐开源：BGE 系列、GTE、E5、Jina Embeddings、Qwen Embedding。
  • 推荐商业：各云厂商 Embedding API。
  • 优缺点：✅ 语义泛化；❌ 对专有名词、型号、编号敏感度差（必须配合关键词检索）。
  • 适用场景：语义相似检索。

C2 · Chunking（切分）

  • 介绍：把长文档切成可检索单元。
  • 原理：固定长度 / 递归分隔符 / 语义边界 / 结构化（按标题层级）/ 父子分块（小块检索，大块提供上下文）。
  • 企业最佳实践：结构化切分 + 父子分块是当前最优组合：按标题层级切分保证语义完整，标题路径写入 chunk 元数据（”车辆设置 > 空调 > 自动模式”），检索命中小块但返回父块。
  • 优缺点：切分策略对 RAG 效果的影响常大于换模型。
  • 适用场景：全部 RAG 场景。

C3 · Retriever（检索器）

  • 介绍：根据查询返回候选片段的组件。
  • 原理：向量近邻检索（ANN）、稀疏检索（BM25）、元数据过滤、多路召回后融合。
  • 企业最佳实践：查询改写是第一优先级优化项（口语化查询直接检索效果差；先用小模型改写为检索友好表述，召回率常提升 15–30%）；多路召回 + RRF 融合。
  • 推荐开源：向量库自带检索 + Elasticsearch/OpenSearch BM25。
  • 适用场景：全部 RAG 场景。

C4 · Hybrid Search（混合检索）

  • 介绍：向量 + 关键词 + 元数据过滤的组合检索。
  • 原理：并行执行多路检索，用 RRF（倒数排名融合）或加权分数合并。
  • 设计原因：纯向量检索在车辆型号、错误码、专有功能名上系统性失败；纯关键词在口语化提问上失败。二者互补。
  • 企业最佳实践：默认开启混合；权重按查询类型动态调整（含数字/编号则提高关键词权重）；元数据过滤前置（先按车型/版本过滤再检索，避免答错车型）。
  • 推荐开源：Milvus / Qdrant / Weaviate / LanceDB（均支持混合）、ES + 向量插件。
  • 优缺点：✅ 显著提升召回；❌ 需调权重、复杂度上升。
  • 适用场景：企业知识库必选。

C5 · Reranker（重排序）

  • 介绍：对候选片段做精细相关性打分并重排。
  • 原理：Cross-Encoder 同时编码「查询+片段」，精度远高于向量点积，但计算量大，故只对 Top-N（如 50）候选重排。
  • 企业最佳实践：召回 50 → 重排取 5 是性价比最高的配置；Rerank 是 RAG 中投入产出比最高的单点改进（常带来 10–20% 准确率提升）；延迟控制在 50 ms 内（小模型 + 批处理）。
  • 推荐开源：BGE-Reranker、Jina Reranker、Cohere Rerank（商业）。
  • 优缺点：✅ 精度提升明显；❌ 增加延迟与算力。
  • 适用场景：对准确性要求高的知识问答。

C6 · Vector Database（向量库）

  • 介绍：存储与检索高维向量的数据库。
  • 原理：ANN 索引（HNSW 图索引 / IVF 倒排 / PQ 量化），以精度换速度。
  • 企业最佳实践：先评估规模再选型——百万级以下 pgvector 或 LanceDB 足够且运维成本最低；千万级以上再考虑 Milvus；必须支持元数据过滤 + 混合检索 + 多租户隔离。
  • 推荐开源：Milvus（大规模）、Qdrant（易用+性能均衡）、Weaviate（模块化）、pgvector（复用 PG 生态）、LanceDB（嵌入式/列式，适合端侧与轻量场景）、Chroma（原型）。
  • 推荐商业：Pinecone、各云厂商向量服务。
  • 优缺点：✅ 语义检索基础设施；❌ 索引重建成本高、运维复杂度常被低估。
  • 适用场景：知识库、记忆、语义缓存三处均需。

C7 · RAG / GraphRAG / LightRAG

变体 原理 优势 代价 适用
朴素 RAG 切分→向量→检索→拼接→生成 简单、快、成熟 无法处理跨文档关系与多跳问题 单点事实查询（占比通常 70%+）
GraphRAG 抽取实体关系构图 → 社区摘要 → 图上检索 擅长多跳推理与全局性问题（”总结所有相关问题的共性”） 建图成本极高（大量 LLM 调用）、更新困难 高价值、低更新频率的知识域
LightRAG 图 + 向量双索引，增量更新友好 兼顾关系与成本，支持增量 仍比朴素 RAG 重 需关系推理且知识持续更新
HybridRAG 图检索 + 向量检索结果融合 覆盖面最广 复杂度最高 成熟阶段的优化选项
  • 企业最佳实践：不要一上来就上 GraphRAG。正确路径：朴素 RAG + 混合检索 + Rerank + 评测集 → 用评测集定位失败案例 → 只对”确实需要多跳”的子域引入图增强。多数团队在朴素 RAG 尚未调好时就转向 GraphRAG，结果成本上升而效果不涨。
  • 推荐开源：LlamaIndex、Haystack、RAGFlow、Dify、Microsoft GraphRAG、LightRAG。
  • 详见 09 文档。

D · 模型服务组件族

D1 · LLM / SLM / VLM

类型 定位 本架构中的位置 选型要点
LLM 云端主力推理 LLM 网关后的模型池 长上下文能力、函数调用稳定性、中文能力、流式质量
SLM 端侧与高频轻任务 端侧小模型（图示）+ 云端分类任务 量化后精度损失、内存占用、NPU 兼容性
VLM 多模态理解 模型池（推断设计） 图像分辨率支持、OCR 能力、延迟
  • 企业最佳实践：按任务分级用模——意图分类用 SLM，闲聊用中等模型，复杂推理用大模型。多数平台把 60%+ 请求错误地送给了最贵的模型。
  • 优缺点：LLM 强但贵慢；SLM 快省但能力有限；VLM 场景刚需但延迟高。

D2 · Model Router（模型路由）

  • 介绍：按 model_intent 与策略选择具体模型（图示”多模型切换”）。
  • 原理：能力矩阵（模型×能力×成本×延迟）+ 策略引擎 + 实时健康状态。
  • 企业最佳实践：业务只声明语义意图，不指定模型（P5）。这使换模型成为网关配置变更。同时记录 route_reason 与实际模型，便于成本与效果归因。
  • 推荐开源：LiteLLM、RouteLLM。
  • 适用场景：多模型环境必选。

D3 · Model Fallback（降级链）

  • 介绍：主模型失败时的备选链路。
  • 原理：熔断器 + 有序降级链：主模型 → 同能力备用 → 更小模型 → 语义缓存近似 → 端侧 SLM → 显式失败。
  • 企业最佳实践：降级链必须端到端演练（定期故障注入）；降级时向用户表达能力受限而非假装正常；降级事件必须告警且计入 SLO。
  • 优缺点：✅ 可用性显著提升；❌ 降级后质量下降需被感知与度量。

D4 · Load Balance（负载均衡）

  • 介绍：模型实例间的流量分配。
  • 原理：AI 场景不适用轮询——请求耗时差异巨大（长上下文 vs 短问答）。应使用**最少未完成请求数（least-outstanding-requests）**或按 Token 队列长度分配。
  • 企业最佳实践：以「预估输出 Token 数」加权；自建集群配合连续批处理（continuous batching）；预热连接避免冷启动。
  • 推荐开源：vLLM / SGLang（推理引擎自带调度）、Envoy 自定义 LB。

D5 · Prompt Builder（提示词构建）

  • 介绍：把系统指令、上下文包、工具描述、用户输入组装为最终 Prompt。
  • 原理：模板引擎 + 变量注入 + 预算裁剪 + 版本管理。
  • 企业最佳实践：Prompt 必须版本化并纳入发布流程（等同代码）；模板与内容分离；每次调用记录 prompt_version，否则效果波动无法归因；上下文按优先级裁剪（系统指令 > 用户当前问题 > 知识 > 记忆 > 画像）。
  • 推荐开源：Jinja2 模板 + 自研版本管理、Langfuse Prompt Management。
  • 优缺点：✅ 可控可回归；❌ 模板膨胀后维护成本高。

E · 缓存组件族

E1 · Semantic Cache（语义缓存）

  • 介绍：按语义相似度复用历史回答（图示圈注，本架构重点）。
  • 原理：查询向量化 → 向量库检索 → 相似度超阈值则返回缓存回答。
  • 设计原因：车载场景问法高度收敛（”怎么开空调””附近充电桩”），命中率可观。每提升 5 个百分点命中率约等于省 10% 推理算力（见 01 文档 6.2）。
  • 企业最佳实践：缓存键必须包含维度——知识版本、车型/配置、用户群、语言；时效性意图强制 bypass（天气、剩余电量、附近状态）；相似度阈值宁高勿低（0.92+），误命中造成的答错代价远高于省下的成本；缓存回答需二次通过围栏。
  • 推荐开源：GPTCache、自研（Redis + 向量库）。
  • 优缺点：✅ ROI 最高的降本手段；❌ 误命中风险、缓存失效策略复杂。
  • 适用场景：高频问法收敛的 C 端场景，本架构高度适用。

E2 · Prefix Cache / KV Cache

  • 介绍：推理引擎层面复用已计算的注意力键值。
  • 原理：相同前缀（系统指令 + 工具描述 + 知识片段）的 KV 可复用，仅计算新增部分。
  • 企业最佳实践：把稳定内容放前面、变化内容放后面（系统指令 → 工具描述 → 知识 → 记忆 → 用户问题）。这一条 Prompt 组织顺序的调整即可让前缀缓存命中率大幅提升，是零成本优化。自建推理时开启 Prefix Caching。
  • 推荐开源：vLLM（Automatic Prefix Caching）、SGLang（RadixAttention）。
  • 优缺点：✅ 显著降低首字延迟与成本；❌ 仅自建推理或支持该特性的厂商可用。

E3 · Token Cache / 计量

  • 介绍：Token 消耗的计量、配额与治理（图示”Token 流量治理”）。
  • 原理：网关侧统一计量 → 多维度归因（业务/Agent/场景/用户）→ 配额与限流 → 成本看板。
  • 企业最佳实践：以网关计量为唯一口径，禁止业务自报；限流单位用 Token/s 而非 QPS；对每个 Agent 设日配额与告警；异常消耗自动熔断（防止死循环 Agent 烧钱）。
  • 优缺点：✅ 成本可治理；❌ 需全链路强制接入。

F · 交互与流式组件族

F1 · ASR / TTS

  • ASR：见 03 文档 M10。要点：流式、热词、上下文偏置、端云双通路。
  • TTS：流式合成（首包 < 200 ms）、情感与语速可控、播报可打断（barge-in）。
  • 企业最佳实践：打断能力（barge-in）是车载体验的分水岭——用户能随时插话打断播报。这要求 TTS 播放与 ASR 采集并行且 AEC 有效。
  • 推荐开源：Whisper/FunASR/SenseVoice（ASR）、CosyVoice/Piper/edge-tts（TTS）。

F2 · Input Fusion（输入融合）

  • 介绍：多模态输入的统一处理（推断设计，图中以音频为主入口但架构预留）。
  • 原理：各模态独立编码 → 时间对齐 → 统一为 Context Bundle 的 modality 段。
  • 企业最佳实践：融合发生在编排层之前，让 Planner 只处理统一表示；车载场景重点融合”语音 + 屏幕焦点 + 车辆状态”（用户说”这个”时需知道屏幕上是什么）。
  • 适用场景：车载指代消解（”把这个加到收藏”）、图像问答。

F3 · Streaming / SSE

  • 介绍：流式响应传输（图示 Agent 网关”SSE 流式”）。
  • 原理：单向服务端推送，基于 HTTP，天然穿透代理与 CDN，支持 Last-Event-ID 断点续传。
  • 设计原因（ADR-09）：相比 WebSocket，SSE 实现简单、穿透性好、无需心跳协议自定义；代价是单向（但 AI 回答场景本就是单向流）。
  • 企业最佳实践：首包尽快返回（哪怕是”正在思考”占位）；心跳保活防中间设备断连；分段做安全检测；客户端指数退避重连 + 幂等续传。
  • 优缺点：✅ 简单可靠、感知延迟低；❌ 单向、连接数占用。

G · 安全组件族

G1 · Input Guard / Prompt Injection 防御

  • 原理：规则（关键词、模式）+ 分类模型 + 指令与数据分区 + 输出格式约束。
  • 企业最佳实践：最有效的防御是架构层面的隔离而非检测——工具结果与系统指令物理分区、工具最小权限、危险操作强制二次确认。单靠检测模型永远存在绕过。
  • 推荐开源：Llama Guard、Rebuff、NeMo Guardrails。

G2 · Output Guard / Content Filter

  • 见 03 文档 M19、12 文档。要点：出站必检、流式分段、fail-closed、误拦截反馈通道。

G3 · Sandbox（沙箱）

  • 原理：能力执行在受限环境（无网络/只读文件系统/资源上限/系统调用白名单）。
  • 企业最佳实践：任何执行模型生成内容的能力（代码执行、脚本、动态查询）必须沙箱化；端侧沙箱同样必要（图示边缘安全系统承担此职责）。
  • 推荐开源：gVisor、Firecracker、容器 + seccomp、WASM 运行时。

H · 观测与训练组件族

H1 · Tracing / Metrics / Logging

组件 作用 推荐方案
Tracing 单请求全链路归因（含 Agent 每步思考、工具、Token） OpenTelemetry + GenAI 语义约定；Langfuse / Phoenix / Jaeger
Metrics 聚合指标（延迟、成功率、Token、缓存命中、成本） Prometheus + Grafana
Logging 结构化日志与审计 Loki / ELK
  • 企业最佳实践：Trace ID 从端侧生成并贯穿到训练数据（见 03 文档 M13）；GenAI Span 必须包含 model、prompt_version、token 数、cache_hit、route_reason、guard_result 六个属性，缺任一项都会导致某类问题无法归因。详见 13 文档。

H2 · Evaluation（评测）

  • 原理：金标集 + 自动指标（召回率、正确率、格式合规率）+ LLM-as-Judge + 人工抽检。
  • 企业最佳实践：三套集分离——公开集（可调优）、回归集（发布门禁）、盲测集（不参与调优，用于真实评估）；LLM-as-Judge 需与人工标注做一致性校准；每次 Prompt/模型/检索参数变更强制跑回归。
  • 推荐开源：Ragas（RAG 评测）、DeepEval、Promptfoo、OpenAI Evals。

H3 · SFT / DPO / RLHF / Reward Model

方法 需要什么数据 成本 适用
SFT 高质量问答对 低 风格对齐、格式遵循、领域术语
DPO 偏好对（好答案/差答案） 中 从线上反馈直接学习偏好，当前性价比最高
RLHF 偏好数据 + Reward Model + RL 训练 高 大规模精细对齐，多数企业不需要
Reward Model 大量偏好标注 高 作为自动评测器亦有价值
  • 企业最佳实践：先 SFT 解决格式与术语，再 DPO 解决偏好；数据来源优先用线上真实 Trace（用户纠正、重问、点踩即为天然偏好信号）；绝大多数企业不需要 RLHF——投入产出比远低于把 RAG 与上下文质量做好。详见 14 文档。
